## Commentary

### Yesterday

**21 tasks closed.** Two of them change what you can see; the rest were the
safety net repairing itself, and that is worth reading in that order.

The one you would notice first: **moving a pane divider with the keyboard now
does the same thing as dragging it with the mouse.** It did not. Nudging a
divider in a nested layout jumped it the wrong way by about a finger's width,
and holding the key out and back left the boundary somewhere other than where it
started. Both defects had already been fixed for the mouse months ago — the
keyboard was a second implementation of the same gesture that nobody had put
through the same fixes. Now there is one.

The one you would not have noticed, and should: **a build living in this repo
could take over your `ghoztty://` links, and had.** Every time a script started
the staging release we build to package a delivery, Windows was told that
clicking a Ghoztty link should run a binary in a scratch folder that ordinary
development rebuilds and deletes. Your machine was left in that state. A build
that sits inside a source checkout now registers nothing at all.

Underneath those, yesterday was the **acceptance-suite debt** being worked off:
the full sweep run on 2026-08-21 turned about fifty silent reds into owned tasks,
and thirteen of them closed yesterday. The theme running through nearly all of
them is the same and it is a good one — *the check was wrong, not the code*. The
scrollback flush was firing all along; the chooser tests were pressing keys at a
list that had not appeared yet; four screenshot scripts were typing into a box
nobody was looking at; the reboot test killed the agent, left the shell running,
and then called the survivor a bug.

Two of those deserve their own line. **The 30-minute stability soak reached its
own verdict for the first time ever** — the suite runner had a single 10-minute
cap and had been killing it 20 minutes short on every sweep, then scoring it as a
hang. So the property the quality bar names by name, *reliable under hours-long
use*, had never actually been measured. It has now, and the first complete run
found something real about frame rate under load. And **acceptance scripts were
leaving live processes behind** — six of them, five while reporting ALL PASS.
That is the worst kind of defect a test suite can have: the leak is invisible
where it happens and the next script inherits the failure. One script was scored
red in the sweep purely because of its neighbour.

### Reflection

**The instrumentation is now big enough to be its own source of bugs.** Nineteen
of yesterday's twenty-one closures were harness repairs, and almost every one was
a measurement defect rather than a product defect. That is not a complaint — it
is the expected bill for having finally run the whole suite end to end — but it
changes what "green" is worth. A suite that can be wrong in fifty places is a
suite whose greens need the same scepticism as its reds.

Yesterday's reflection proposed that **every gate should be asked, at least once,
to prove it can fail**, and yesterday's work is the evidence for it: several of
the fixes explicitly deleted their own guard and watched the assertion go red
before trusting it, and those are the ones I would bet on today. The sharper
version, worth adopting as a rule: *an assertion nobody has ever seen fail is not
a measurement, it is a decoration.* The suite already has this habit under a
name (`-NegativeControl`); what it does not have is any way to tell which
individual assertions have ever demonstrated teeth. That is a report we could
build.

The second theme is newer and I think more important: **we have no inventory of
the things this project writes outside its own folder.** The URL-scheme fix was
one instance — a registry key the user's shell obeys, written by a dev build, and
every lane green through all of it, because no unit test can see the *decision*
to write. The same shape is already known to exist in at least one other place
(the autostart entry that survives a reboot, filed as T1146), and nobody has
enumerated the rest: file associations, PATH, Start menu, jump lists, the
per-user scheduled task. The build-mode isolation rule we rely on covers
*endpoints* — pipes and state directories — and says nothing about
*registrations*. I have filed **T1151** to enumerate every such write and put a
location gate on each, because finding these one incident at a time means the
user's machine is the detector.

On the **cutover to `main`**, the picture is unchanged and close: five of ten
criteria unmet, and only two of them are work. Both open P0s belong to the Mac
seat, and the Mac regression build (T87) is the real gate. The one item on this
seat is a single overdue harness (fork-identity, owned by T1134). The branch
fully contains main and 1467 commits are waiting to become the trunk. It stays
true that the bottleneck is a Mac-seat validation pass, not Windows work.

## Feature ideas

### User-facing

- **Copy a wrapped line and get one line** (High) — a long command or URL that
  wrapped across three rows should paste as one string, not three with hard
  newlines jammed in. This is the single most common way a copied line arrives
  broken, and it bites hardest on exactly the things you copy: URLs and commands.
- **The port a pane just opened becomes a link** (High) — when a program in a
  pane starts listening on a port, offer `http://localhost:<port>` as something
  you can click, in the pane and on its tab. Every dev server prints its URL in a
  slightly different shape and half of them are not clickable today.
- **Resizing the window rewraps what is already on screen** (High) — narrow a
  window and the text that is already there should reflow, not stay chopped at
  the old width with the tail lost. Every resize currently costs you the
  readability of everything above the prompt.
- **The wheel scrolls inside programs that do not handle it** (High) — `less`,
  `git log`, a TUI menu: turn the wheel and it should move, translated into the
  arrow keys those programs do understand. Right now the wheel does nothing in
  the exact places you most want to skim.
- **Snap Layouts from our own maximize button** (Medium) — hover the maximize
  button and get the Windows 11 layout flyout, the way every native window does.
  Custom title bars usually lose this, and it is how a lot of people arrange
  windows.
- **Paste from a history of what you copied here** (Medium) — a small picker of
  your recent copies from this terminal, so the command you yanked two minutes
  ago is not gone because you copied something else since.
- **Drag a selection out of the pane** (Medium) — grab selected output and drop
  it into a chat, an editor or a bug report, instead of copy, switch, paste.

### Feel and performance

- **Scrolling that feels like the rest of Windows** (Medium) — precision-touchpad
  momentum and pixel-smooth scrolling instead of jumping three lines at a time.
  It is a small thing you feel every single day, and it is one of the clearest
  tells between a native-feeling app and a ported one.
