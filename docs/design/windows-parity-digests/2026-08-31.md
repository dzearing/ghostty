## Commentary

### Yesterday

The install epic went from a plan to a thing a stranger can download. Windows now
offers **one** installer instead of two (T1175), that installer **ends with a
terminal on screen** instead of a silent finish (T1176), a Ghoztty that cannot
start **says so in a dialog** in a quarter of a second instead of vanishing
(T1177), and the app **updates itself** - click the notification, answer one
question, and the new build installs and reopens with your sessions intact
(T1178). Underneath that, the box got an inventory of every Ghoztty on it
(T1188), and the loop's supervisor stopped flashing a console window onto the
desktop mid-typing (T1192).

Then the whole thing was shipped and walked. **win-v1.35.0** was published
through CI and the website was retargeted at it, so the download page hands out
exactly one Windows MSI (T1186) - and the "Remote Agent" section came off the
site this morning, because one installer means one button.

**And then the user actually installed it on a cleaned machine**, which is the
gate the merge to `main` waits on ("I want to go to the website and be able to
install the prod version on a new machine and it should just work"). Most of it
passed: one installer offered, the install completed, `ghoztty` on PATH, `+list`
and `+sessions` working with the agent alive, the Start Menu shortcut pointing at
the right exe, About and `--version` agreeing on 1.35.0.

One check failed, and it is the one worth having. Installing **over a running
Ghoztty** said "configuring", disappeared with no message, and then demanded a
reboot it did not need. That is exactly the defect class T1177 just killed for
startup, wearing an installer's clothes.

### Today's focus

**T1204** - give installing-over-a-running-copy a graceful path. Restart Manager
is the mechanism Windows already has for this (it asks the running app to close
and brings it back), and a collided transaction needs to fail with something a
person can read instead of a dialog that closes itself. It is the head of the
queue on its own priority, and it is the only remaining hard FAIL from the
clean-machine walk.

Behind it, from that same walk: **T1205** ("I think I'm on the newest build but
I'm not sure" - every surface reports a different answer) and **T1203**
(SmartScreen greets a new user before Ghoztty ever runs, because the MSI is
unsigned).

### Reflection

The theme of this week is that **the last mile is a different discipline than the
feature work**. Everything that failed yesterday failed at a seam nobody owned:
the installer meeting a running process, the version meeting three different
surfaces, the download meeting SmartScreen. None of these are hard engineering;
all of them are what a new user hits in their first two minutes, and none of them
were findable from inside the loop. They were findable by one person spending ten
minutes installing the thing.

That suggests a process change worth making: **the clean-machine walk should be a
recurring ritual, not a one-off gate.** It produced three real tasks - two of
them P0 - in a single pass, at a rate no sweep or harness on this box has
matched. The cheap version is a checklist the user runs after each published
release; the better version scripts what can be scripted (install over a running
copy, read the version back from every surface) and leaves only the genuinely
human parts to a person.

The second recurring theme is **silence as the defect**. T1177 (startup), T1204
(install), the T1192 console flash, the go-loop guard sitting 26-red - all the
same shape: something that fails or acts without saying anything. The codebase
has gotten good at making failures loud in the *loop's* machinery; the install
path is where that habit had not reached yet.

Third, a quieter one: `-NoGuardDue` has now been used on three consecutive
packaging commits, because the MSI guard can only be cleared by Docker. That is
T1189, and it is the exact thing go.md warns about - a hatch used routinely stops
meaning anything. Letting CI's MSI build clear that stamp would end it.

### Decisions

No open decisions await the user. The directive steering today is the one from
the install handoff: the loop prepares and the human disposes. The machine
inventory was taken read-only, nothing was uninstalled on the loop's own
judgement, and that stays the default for anything touching the machine the user
is sitting in front of.

## Feature ideas

### User-facing

- **Tell me plainly which build I am running, everywhere** (High) - one version
  string, the same in About, `--version`, Apps & Features and the update
  notification, with "up to date" or "update available" beside it. Today the
  honest answer to "did the update work?" takes three checks and still leaves
  doubt.
- **A first-run welcome that proves the install worked** (High) - the terminal
  that opens after installing says hello, names its version, and offers two links
  (keybindings, docs). It turns "did it install?" into something you can see
  rather than infer.
- **Install without the scary warning** (High) - a signed installer, so the first
  thing a new user meets is Ghoztty and not a full-screen SmartScreen wall.
  Nothing else on this list matters if people bounce here.
- **Update quietly while I work, apply when I close** (Medium) - an option for
  the update to stage itself and take effect at the next launch, so the prompt
  never interrupts a long-running session.
- **Show me what changed in this version** (Medium) - the update notification and
  About both link to a short, human release note, so upgrading is a choice rather
  than a leap.

### Technical and stability

- **The installer asks the running Ghoztty to step aside** (High) - Restart
  Manager integration, so upgrading over a live terminal closes it politely and
  brings it back with its sessions attached, instead of colliding.
- **A scripted clean-machine rehearsal** (Medium) - a harness that installs,
  installs again over a running copy, reads the version back from every surface
  and reports a verdict, so the first-two-minutes experience is measured on every
  release instead of discovered by hand.
- **Let CI's MSI build clear the packaging guard** (Medium) - the packaging check
  can only be satisfied by a toolchain that is not on this box, so it is waived on
  every packaging commit. A waiver that is routine is not a check.
