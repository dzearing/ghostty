**The loop spent the day making its own tests tell the truth.** Seven of the
eleven tasks that closed were the same shape: a check that could not actually

The unfocused-split dim was being measured off an empty pixel, so the dim

reporting product failures when the real problem was that it could not reach the
app it was driving. None of that is visible in the terminal you use. All of it
decides whether the next real defect gets caught or waved through.

**Two new safety nets went in under the hood.** The `+list` command has two
separate encoders, one on Mac and one on Windows, that have to agree field for
field; until yesterday the only thing keeping them in step was a comment asking
people to be careful. Now the Windows build compares the real bytes it emits
against the Mac encoder's declared shape and goes red when they drift. Separately,
the counter that decides when a split pane's contents get freed was open-coded
twice and untestable; it is now a small piece of arithmetic with six tests, and
the case that used to turn "free it" into "leak everything under it" is an
outright assertion rather than a silent wrap.

**One thing you would actually notice.** A remote window that loses its
connection now re-dials instead of going permanently dead, and a machine that
restarts underneath a remote window now has to leave that window in a defined
state rather than wherever it happened to land.

**Nothing shipped — again — and for a new reason.** The last release is still
`win-v1.36.0` from 08-31. On 09-01 the publish fired and stopped because Docker
Desktop was not running. Yesterday it never fired at all: the publish is gated on
the first push at or after 17:00, the day's last push was 14:28, and the loop
does not guarantee an evening. So there are now two separate ways for a full day
of work to reach nobody, and you have been running the same build for three days
while nineteen tasks closed behind it.

### Reflection

**The instruments got better and the output got worse.** Yesterday was, by any
internal measure, a good day — eleven closures, three of them the kind of
foundational fix that pays out for months. By the only measure you can see, it
was a zero: the software on your machine is unchanged since Sunday. That gap is
worth naming rather than smoothing over, because the loop has no natural pressure
against it. Every gate in the turn asks whether the code is correct; none of them
ask whether it left the building.

**The pattern behind both publish failures is the same.** Each depends on
something the loop cannot control — a container the user must start, a clock the
loop must still be alive to reach — and each fails *quietly and correctly*, which
is the worst combination. The skip is logged, the watermark is preserved, the
turn carries on. Nothing is broken; nothing ships. The lesson generalizes: a step
whose failure mode is "nothing happens" needs a gate that measures elapsed
reality, not just a log line. Concretely, **days-since-last-publish belongs on
the health line beside `digest=missing`** — the same shape of check, for the same
reason, and it would have flagged this on 09-01 instead of waiting for you to.

**The 17:00 rule encodes an assumption the loop does not satisfy.** It was
designed as "the day's work is done", borrowed from the morning refresh it
replaced. But this loop has no workday: it turns whenever it turns, and yesterday
it simply stopped before evening. A signal keyed on a wall clock inside a process
with no schedule is a coin flip. Publishing on a *task-boundary count* or on
"first push after N hours since the last publish" would carry the same intent
without the assumption.

**Toward the cutover**, the picture is unchanged and it is still yours to move:
T1179's clean-machine install walk is the P0 gate, and it needs you to install
from the website over a running Ghoztty and say what happened. T1074 needs that
plus the Mac seat's regression build. Fixing the publish helps here directly —
T1179 cannot be re-run against work that never gets released.

## Feature ideas

### User-facing

- **Copy out of a remote or WSL pane and have it land in Windows** — *High.* You
  select output inside an SSH or WSL session today and the copy goes to that
  machine's clipboard, not yours; you end up re-selecting in a local pane or
  piping to a file. A clipboard bridge would make copy mean the same thing in
  every pane, local or not.
- **Blur the secrets before you share it** — *High.* Screenshots and feedback
  reports go out with whatever was on screen — tokens, connection strings, a
  password echoed by a script that should not have. Detect the obvious shapes and
  mask them in the captured image, with a one-click reveal if you meant to include
  them.
- **Turn what you just ran into a script** — *High.* Pick a run of commands out of
  the history, and get a saved `.ps1` or `.sh` with them in order and the working
  directory set. Every good workflow starts as five commands you typed once and
  will never remember; this is the moment they become reusable.
- **A scratch pad beside the shell** — *Medium.* A pane that is a notepad rather
  than a terminal, saved with the session and reopened with it. The place for the
  connection string, the half-written command, and the "remember to revert this"
  that currently live in a text editor on another monitor.

### Chrome and interaction

- **Choose where a link opens** — *Medium.* A link in output goes to the browser
  today, full stop. Let a markdown file, an image, a diff, or a docs URL open in a
  viewer pane instead, remembered per kind, so the thing you always want in a pane
  stops taking a round trip through Chrome.
- **Tidy a window full of tabs** — *Medium.* "Close others" and "close to the
  right" from the tab menu, with a preview naming what is about to go and which of
  those panes are busy. Reclaiming a window after an afternoon currently means
  closing tabs one at a time and hoping none of them was running something.
- **Respect Windows high contrast** — *Medium.* When the system is in a
  high-contrast theme our chrome and palette should follow it, not sit at our own
  colors. This is the difference between usable and unusable for people who need
  that mode, and it is a setting we can simply read.
