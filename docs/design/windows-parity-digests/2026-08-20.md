## Commentary

### Yesterday

**Two ways to crash the app by typing were found and fixed.** Typing a long
filter into the Activity Monitor killed the terminal outright (T989), and so did
typing one into the machine chooser (T990) — the same defect in two places, and
both were reachable by anyone who held a key down in a search box. Every text
field in the app was then swept for the same shape (T990's follow-up), so this
class is closed rather than patched twice. Nothing about it was subtle once
found, which is the uncomfortable part: it survived because nobody had ever
typed a long string into those boxes.

**Copy and paste stopped disappearing.** When another program touched the
clipboard at the wrong moment, a copy or paste would silently do nothing
(T947). Windows hands the clipboard to one process at a time and ours gave up
on the first refusal; it now waits its turn like every other app. The harness
written for it immediately found a second, narrower version of the same problem
— today's first task.

**A restart now finishes the job even when the timing is wrong.** If a window
launched before the session manager was ready, it used to leave you at a blank
terminal until the next launch; the restore now completes itself once the
manager answers (T976). Alongside it, a busy pane's scrollback is saved when
enough has printed rather than only every thirty seconds (T969), so a crash
takes less of your output with it.

**The test suite stopped being able to lie.** This was most of the day's work
and it is worth naming plainly, because none of it is a feature: a GUI test
could pass while measuring a blank photo of a window (T303); a run that skipped
an entire section still printed a pass (T962, T995); the floor run could be
killed by the process sample it takes of itself and still exit zero (T982); an
agent restart that started killing panes would have shipped green (T974); and
two harnesses had been standing red for weeks against UI that was renamed
months ago (T987, T988). Each of those is a way for a real regression to reach
you behind a green light, and each is now closed.

**And the window's colors have one explanation each.** A window is light or
dark for one reason now instead of three (T309), and the title/tab band stays
tinted to your terminal rather than to your wallpaper (T306) — a deliberate
call, filed as D81 in case you want the Windows Terminal look instead.

### Today's focus

**First, the clipboard bug the last one uncovered** (T992). Our copy claims no
owner window, which means the two steps of a copy — clear, then write — are not
atomic: another app can slip between them and your copy quietly ends up holding
its content, or nothing. It is a small, measured fix in the same file T947
touched.

**Then the upstream absorption starts** (T957, T956). You answered D80
yesterday — take upstream Ghostty's last three months in stages, starting now —
and the first stage deliberately merges no upstream code at all: a permanent
remote so the plan's commits stay resolvable, merge drivers for the files where
both sides only append, and a script that re-applies the Ghoztty identity over
an upstream tree. That last one turns 52 of the 131 risky files into a
mechanical step, in this merge and every future one.

### Reflection

**Yesterday was the day the safety net was inspected instead of trusted, and it
had holes in it.** Six separate ways for a test to pass without testing
anything were found and fixed in a single day. That is a good day's work and
also an indictment: the suite is the only thing standing between this branch
and a regression reaching you, and its own correctness had never been a subject
of study. The pattern across all six is identical — the *verdict* was computed
from something other than the *observation*: a photo that was blank, a section
that never ran, a process list that was empty, a row name that no longer
existed. The generalisable rule, and the one worth building into the harness
libraries rather than fixing case by case, is that **every assertion must fail
closed**: absence of evidence has to read as failure, never as a pass. Three of
the fixes already encode that; nothing obliges the next harness to.

**The queue crossed a line worth noticing: there are no unblocked P0s or P1s
left that this seat can act on.** Every remaining high-priority item is parked
on something outside the code — two are waiting on the elevated Turbo-Boost
commands, one on an armed watch with no new occurrence. Today's four P1s exist
because triage created them this morning out of your two answered decisions and
one measured bug. That is a healthy state, but it changes what the loop should
optimise for: with 291 P2s and no forced ordering among them, *what comes next*
is now almost entirely a triage judgement rather than a queue lookup. The
biggest risk in that regime is drift — closing whatever is cheap rather than
whatever moves the goal.

**Which is why the merge-back should now set the pace.** You answered D80 with
"start now, in stages", and the honest reading of that answer is that upstream
absorption is no longer one task among 291 — it is the thing the remaining
backlog should be sequenced around. The fork is ~764 commits behind and drifts
another ~250 a month, so every week the P2 pile is worked in preference to the
merge makes the merge harder. Concretely, from tomorrow the triage should ask
of each promotion "does this survive the merge, or will upstream rewrite the
file underneath it?" — the divergence inventory already answers that per file,
and it is sitting unused as a triage input.

**M1's membership needs to be frozen, and the date should be Saturday.**
Yesterday proposed it; nothing has changed except the numbers, which moved from
189/248 to 196/254 — seven closed, six added, still a target that admits
members as fast as it loses them. The proposal is now concrete: **at the end of
2026-08-22, M1 closes to new members and everything filed afterwards goes to
M2.** The rule against demoting tasks to move the number stays exactly as it
is; this is the other half of it. Unless you say otherwise before then, that is
what Saturday's triage will do.

## Feature ideas

### User-facing

- **Put my windows back on the right monitors** (High) — after a restart, a
  restored layout should return to the screens and positions it left, not pile
  onto the primary display. On a multi-monitor desk this is the difference
  between "my setup came back" and "I have to rebuild it".
- **Copy what that command printed, without selecting it** (High) — one key
  copies the entire output of the last command (or the one under the cursor),
  using the same command boundaries the prompt already marks. Selecting three
  screens of a stack trace with a mouse is the most common small misery in a
  terminal.
- **Tell me how long that took — and whether it is slower than usual** (Medium)
  — a finished command shows its duration next to its exit status, and flags it
  when it is well off its own historical time. "The build is slow today" stops
  being a feeling.
- **A link to a line of output that you can paste anywhere** (Medium) — deep
  links already jump to a window or pane; extend them to a position in the
  scrollback, so a bug report or a chat message can point at the exact line
  rather than a screenshot of it.
- **Follow the system's text size, not just its colors** (Medium) — Windows'
  accessibility text scaling should move the app's chrome the way it moves
  every other app. Today someone who scales text to 150% gets a terminal that
  ignores them.

### Stability and performance

- **A "why is this slow" readout you can actually send** (Medium) — one panel
  showing frame time, how far behind the pane's output is, and the round trip
  to the session manager, with a button that attaches it to a feedback report.
  Performance complaints are currently unanswerable without a build.
- **A first run that finds your shells for you** (Medium) — on first launch,
  detect PowerShell, cmd and each installed WSL distro, show them, and let the
  user pick a default. Today the shell flavors exist but nothing introduces
  them.
