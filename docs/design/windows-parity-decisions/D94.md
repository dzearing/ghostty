# D94 - Should a restored pane's own commands give up half the CPU to keep its output fast?

## Why this needs a call

A pane that keeps its session alive across restarts runs your shell inside a separate helper process, and Windows decides on its own to run helper processes on the slower half of the CPU. That is why printing a lot of text in such a pane has been taking about twice as long as in a plain one - the thing the user reported. Moving the terminal's own plumbing off the slow half recovered a good part of it with no cost to anything. Recovering the REST means moving your commands there too, and the fast half is only a third of the machine's total capacity - so the same build that takes four minutes in an ordinary pane would take noticeably longer in a restored one. That is a trade between how fast text appears and how fast your work finishes, and which one matters is not ours to assume.
