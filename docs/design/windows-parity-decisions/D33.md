# D33 - How should a Windows release be cut, given main has no Windows source at all?

## Why this needs a call

release-windows.yml was written to ride the same vX.Y.Z tag push as the macOS release, and that turns out to be impossible before merge-back: a workflow runs from the tree of the ref that triggered it, and origin/main carries no Windows frontend whatsoever. So the release either happens from the Windows branch or it does not happen. What is genuinely arguable is whether to publish a Windows build off a branch that has not merged back - the version number will match a macOS release whose core source is different.

## Resolution

Chosen: When we feel we are at a good enough state to merge to main, we will do a merge and then do the windows releases. Until then we should keep working on parity and reliability and readiness for merging. I think m1 goal should be something like full feature parity or at least exhaustive consideration for all features. when we're done with m1 we should hten move on to phasing the merge back to main and the release process. Eventually i would like to have a windows dev process where we work off the release version of ghoztty and use the debug version (in parallel) to build and test features. Then once we've released updates, we check for updates and install the newest release version and resume development on the release version. but on windows. this is currectly how i work with mac.
