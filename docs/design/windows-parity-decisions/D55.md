# D55 - Should the work queue sort by priority before its hand-curated order, so an unordered P1 stops sorting behind an ordered P2?

## Why this needs a call

The queue sorts by order first, then priority. Yesterday nine P0s with no order sat behind an ordered P2 band and five were hand-pulled to the front (D49). This morning all five are closed, and the same starvation reappeared one tier down: the win-seat head is an ordered run of P2 harness tasks at positions 312-319 while 107 open P1s carry no order at all. Two consecutive mornings where a human ordering pass was the only thing keeping the loop off the wrong work is a property of the sort, not of the tasks.

## Resolution

Chosen: User directive, 2026-08-12: 'fix the queuing and task recording to use priority for figuring out what to prioritize!! This is critical. And triage should have flexibility to reassess priorities which should affect what comes next.' Implemented: next/list sort priority -> order -> id, and set-priority journals the transition so a re-triage is a visible queue edit. Acceptance: sections K and K2 of test\win32\parity-tasks-seat.ps1, teeth-checked (8 assertions go red under the old sort).
