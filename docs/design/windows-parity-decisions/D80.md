# D80 - Should Ghoztty start absorbing upstream Ghostty's last three months of terminal improvements, and in stages?

## Why this needs a call

Ghoztty forked from Ghostty in May. Since then upstream shipped 764 commits of terminal-engine work - faster scrollback, rendering changes, reworked OSC and ssh handling - none of which this build has. Taking them is not free: upstream also moved to a new Zig compiler, and that one change touches more than half the files where both projects have edited the same code, so the app has to move with it. The user would notice either way - either the terminal gradually gains upstream's improvements with a disruptive stretch in the middle, or it keeps behaving exactly as it does today and quietly falls further behind.

## Resolution

Chosen: Take upstream's improvements in stages - with two constraints added on
2026-08-22 that the original wording did not carry.

**Direction is one-way.** Changes may flow *from* ghostty-org/ghostty *into*
this fork. Nothing ever flows the other way: Ghoztty does not open pull
requests against ghostty-org, does not push a branch there, and is not
upstreamed. The user's words:

> We will NEVER EVER EVER merge back to ghostty. I don't even want that to be a
> question.

> We ONLY push changes to my dzearing personal account ghoztty github repo!

The `upstream` remote is configured fetch-only to make that structural rather
than a matter of discipline - its push URL is set to a string that is not a
repository, so `git push upstream` fails before it can reach the network.
`origin` (github.com/dzearing/ghoztty) is the only place anything is pushed.

**The trigger is the user, not the loop.** "Starting now, in stages" described
a cadence the loop would drive on its own. It does not. A pull from upstream
happens when the user specifically calls for one, and the sequence is fixed:

1. Upstream lands in **our Ghoztty mac build** first, because Ghostty is a
   mac-centric project and its changes are written against that seat.
2. Only then does the result funnel into the **windows port**.

At step 1 the windows port is not a consideration - the only question is what
belongs in our mac build. Porting forward is step 2's problem.

Stage 0's plumbing (the fetch-only remote, the union merge drivers, the
fork-identity overlay and its verifier, the divergence inventory) stays: it is
what makes a user-called pull cheap when one comes.

**Terminology.** This repo's docs call this "merge-back", which reads as
merging *back into* upstream and is exactly the phrase that caused the
confusion. Going forward the operation is an **upstream pull** or **upstream
sync**; T1097 renames it in the live docs.
