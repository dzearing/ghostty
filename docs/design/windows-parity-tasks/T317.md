# T317 - The win32 test lane segfaults intermittently in terminal.PageList (page.verifyIntegrity -> hash_map.get)

## In plain terms

One of the automated test suites sometimes crashes for no visible reason, and
running it again makes the crash go away. That teaches everyone to shrug and
re-run — which is dangerous, because a suite that cries wolf can no longer
warn us about a real breakage. This task's crash turned out to be the same
memory-corruption ghost already being tracked in T443, which the user has
decided to stop chasing and instead watch with tripwires armed. What was left
to do here was one measurement nobody had made: re-run the exact dice-roll
(the "seed") from the original crash and confirm it does not bring the crash
back.

- [x] Re-run the exact failing seed (0xefa4b814) enough times to say whether it

- [x] Record that this crash and T443's are one defect, so nobody hunts it
      twice — see RESULT below; T443 cross-references this file
- [x] Leave the floor lanes green and the T443 armed watch as the standing

## Summary

`zig build test -Dapp-runtime=win32` — a standing floor lane — **segfaulted on
the first run of the T312 turn and passed on an immediate re-run of the same
tree, unchanged.** That is the same failure shape T258 filed for `test-agent`,
one lane over, and it has the same cost: it trains every turn to re-run a floor
lane until it goes green, which is exactly how a real regression gets waved
through as "the flake again".

Filed from T312 (2026-08-01), which hit it and had to establish by re-run that
its own change was not the cause. It is not: the change is confined to
`chooser_rows.zig` / `MachineChooser.zig`, and the crash is in the terminal
core.

## Details

Two threads worth pulling, in this order:

1. **Is it the seed?** The runner prints `--seed=0x...` and it differs per run.
   `growRows` → `grow` → `assertIntegrity` → `lookupHyperlink` reads the page's
   hyperlink map; a segfault *inside* the map's `get` on a page that was just
   grown points at a stale/uninitialized map pointer after a page realloc,
   not at a data race. Re-run the failing seed explicitly (`zig build test
   -Dapp-runtime=win32 --seed 0xefa4b814`) before anything else — a
   deterministic repro turns this from a flake into a bug.
2. **Is it Windows-only, or is it upstream?** `page.zig` / `PageList.zig` are
   shared core, not win32 code. Check whether the none-runtime lane can produce
   it too (it passed in the same turn) and whether upstream Ghostty has the
   same test. If it reproduces off-Windows this belongs upstream, and the
   deliverable here is the repro plus the report.

Do NOT "fix" this by retrying the lane or by marking the test flaky. The floor
lanes are the evidence the whole loop rests on; a lane that fails 1 run in N is
a lane whose green means nothing.

## RESULT (2026-08-06) — same defect as T443; the seed is proven not the trigger; folded into the armed watch

This crash is **the T443 corruption seen from the win32 lane**. The stack here
(`verifyIntegrity → lookupHyperlink → hash_map.get`) is the exact chain T443's
crash dumps decode — a page pointer arriving at the hyperlink hash map with its
high 32 bits replaced (T443 § START HERE). T443 has since consumed six
contexts, ruled out the source tree (a byte-identical crash-day binary soaked
clean), CPU contention (32-way, 0 crashes), and machine uptime, and the **user
resolved decisions D10 and D12 (2026-08-05): stop hunting, park it as an armed
watch** — `floor-lane.ps1` re-runs any crashed test binary under cdb and
captures an all-thread dump on the next natural occurrence.

What this task uniquely owned — its exact failing seed — is now measured:

- **Seed 0xefa4b814 does not reproduce the crash.** 10 runs of the win32 test
  binary at HEAD with `--seed=0xefa4b814` (5 concurrent, so the box was under
  load), **0 crashes** (`test-binary-soak.ps1`, label `t317-seed-0xefa4b814`,
  logs in `%TEMP%\ghoztty-soak`). This matches T443's same-seed experiment on
  the agent binary (same seed crashed at different tests or passed outright):
  the seed orders the tests deterministically but does not carry the trigger.
- One of the 10 runs went red on an unrelated failed TEST, not a crash:
  `remote.agent.atomic_write` "concurrent writers never error or tear (T183)"
  failed under the 5-way load. That is a real, separate finding — filed as
  **T508**.
- Full floor the same day: `floor-lane -Lane all` → none/win32/agent ALL PASS;
  P1–P3 ALL PASS.

Disposition: **skipped(duplicate → T443)**, not `done` — the validation item
"root cause named" is deliberately unmet, because the user's D12 call is that

catching an occurrence, not one spent re-deriving the wreckage. When the watch

file except to follow that pointer.
