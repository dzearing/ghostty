# T276 - T272's interactive-script sweep misses screen-DC probes: color-contrast.ps1 needs no foreground grab yet only works on the input desktop

## In plain terms

The acceptance tests used to interrupt whoever was at the keyboard, so they were
moved onto an invisible second desktop. A check was then added to make sure no
test quietly moves back - but it only looked for tests that STEAL THE KEYBOARD,
and that is not the only way a test can need the real screen. A test can also
take a picture of the screen, which only works on the desktop you are looking
at, while touching no keys at all. One test did exactly that for months and the
check could not see it.

After this, the check asks the question that matters - "can this test run while
you work?" - instead of one symptom of it. A test that needs your screen has to
say so in writing, and if it stops needing it, saying so becomes an error too,
so the list cannot fill up with names that no longer belong on it.

## Goals

- [x] The check counts a screen-capture read as needing the real desktop, not
      only a keyboard or focus grab
- [x] It does NOT flag the far more common innocent cases: a picture of one
      window, or a comment explaining that screen capture is dead here
- [x] The one test that legitimately needs it is declared, and the sweep is
      proven to go red on a real undeclared one
- [x] The harness's own written list stops claiming a test needs the real
      desktop after that test stopped needing it

## Summary

T272 swept `test/win32/` for scripts that still take the user's foreground and
produced a five-row table it presents as complete: two misses, three
interactive-by-design. **The sweep pattern cannot find every such script**, and
T214 found one it missed.

The pattern was `SendInput` / `SetForegroundWindow` + "does not dot-source
`lib\TestDesktop.ps1`". `color-contrast.ps1` (T150) calls NEITHER. It reads
pixels with `GetDC(NULL)` + `GetPixel` - the COMPOSITED SCREEN - which is dead
off the input desktop (DWM composes only the input desktop), and it needs its
window visible on that desktop for the reads to mean anything. So it is an
input-desktop script that grabs no input.

`split-dim.ps1`, already on T272's list as a miss, uses the same `GetDC(NULL)`
+ `GetPixel` mechanism - it was caught only because it ALSO grabs foreground.
That is luck, not coverage.

## Evidence (VERIFIED - call sites read, 2026-08-01)

- `color-contrast.ps1:60-90` declares `GetDC`/`ReleaseDC`/`GetPixel`, and
  `ScreenPixel(x, y)` reads `GetDC(IntPtr.Zero)`. No `SendInput`, no
  `SetForegroundWindow`, no `TestDesktop.ps1`.
- `split-dim.ps1:64,143` - same mechanism, plus the `GrabForeground` that put
  it on T272's list.
- `grep -l 'PrintWindow|CopyFromScreen|GetPixel'` over `test/win32/*.ps1`
  returns 22 files; the two above are the only ones still reading a SCREEN DC
  rather than a window capture.

## The fix

1. **Widen the check T272 item 3 is going to build.** It must fail on
   `GetDC(IntPtr.Zero)` / `GetDC(0)` / `CopyFromScreen` as well as on
   `SendInput` / `SetForegroundWindow` - anything that only works on the input
   desktop, not just anything that takes focus. Being un-runnable in the loop
   is the property that matters; stealing focus is one cause of it, not the
   definition of it.
2. **Declare `color-contrast.ps1`** in the `lib\TestDesktop.ps1` exception
   list. T214 already added it there with its reason (its whole oracle is
   colors the RENDERER chose - derived foreground, regenerated palette,
   draw-time contrast floor - none of which exist outside GL pixels); this
   task is what keeps the declaration honest by making the check enforce it.
3. ~~Decide whether `split-dim.ps1`'s migration (T272) can keep a screen-DC read
   at all, or whether it has to move to `Get-TestWindowPixels` on the
   `GhozttyDimOverlay` window. The dim overlay is layered GDI chrome, so the
   window capture should work - but it is a different measurement (per-window,
   pre-composite) and the difference has to be stated, not assumed away.~~
   **ANSWERED 2026-08-01 (T225): NO screen-DC read survives.** The prediction
   held on both counts. `Get-TestWindowPixels` on the `GhozttyDimOverlay` reads
   the real fill (`255,0,0` under `--unfocused-split-fill=#ff0000`, `16,16,20`
   under a defaulted fill on `--background=#101014`), and the difference is
   stated in the script header: the substitute asserts the two INPUTS to the
   composite (painted fill + layered alpha), not DWM's composite of them. So
   after T225, `color-contrast.ps1` is the ONLY remaining screen-DC reader in
   `test/win32/`, which is exactly the population items 1 and 2 have to cover.

## Classification rule the T225 answer adds (fold into the check's docs)

`split-dim`'s probe was carried as a terminal-content probe by THREE task files
(T214's table, T225's blocker table, item 3 above) for one reason: it sampled a
point that lay OVER the terminal. What it actually sampled was a layered window
in front of it. **Where a probe reads is not what it reads** - the question is
which window's painter owns those pixels, which is route 1 stated in the
contrapositive. Worth a line wherever the widened check explains itself, because
a screen-DC read is exactly the mechanism that makes the two indistinguishable
by inspection: a window capture names its target, a screen DC names a point.

## What changed against the plan

**Item 2 is obsolete, and the header that claimed otherwise was the real
defect.** This task was written on 2026-08-01 expecting to DECLARE
`color-contrast.ps1` as interactive-by-design. T275 (2026-08-11) landed route 0
first and migrated it onto `Get-TestPaneCapture`, so it reads no screen DC at
all any more and must NOT be declared - a declaration for a script that no
longer needs the input desktop is itself a finding (`stale-declaration`), which
is the rule working. What was left behind was prose: `lib\TestDesktop.ps1`'s
"TERMINAL-CONTENT PROBES THAT STAY ON THE INPUT DESKTOP" block still listed it
with its screen-DC reason. Fixed in place, with the note that its old shape is
*why* the audit's rule is phrased the way it is.

So the negative control the Validation section asked for ("remove
color-contrast from the list") does not exist to run. Its replacement is
stronger, not weaker: `-TeethCheck` plants a real undeclared screen-DC reader
in the swept directory (arm C1b), which is the same claim without depending on
one script's current shape.

**The detector needed a second pass, not a longer pattern.** A screen-DC call
site spans several PowerShell tokens - `[Drv]`, `::`, `GetDC`, `(`, `[IntPtr]`,
`::`, `Zero`, `)` - so the per-token regex the foreground family uses cannot
match one no matter how the pattern is written (measured: D1/D4/D5 failed
against exactly that). The foreground family is per-token *because* every
watched user32 name is a lone identifier. The screen-DC family therefore scans
the whole source with comment spans BLANKED length-preservingly
(`Hide-ForegroundAuditSpan`), so offsets still map to line numbers and a
`// GetDC(IntPtr.Zero) is dead here` note inside a here-string still costs
nothing.
