# T154 — ctrl+v does not paste screenshots into Claude Code panes

## Summary

**ctrl+v does not paste screenshots into Claude Code panes (alt+v does).** User-reported 2026-07-29. ROOT-CAUSED BY INSPECTION — a one-flag omission, and the machinery to fix it already exists and is already used by this binding's own neighbors. `Config.zig:6934-6938` binds Windows `ctrl+v` → `paste_from_clipboard` with a plain `put()` and **no `performable` flag**. `Surface.startClipboardRequest` documents the contract at `Surface.zig:6744-6746` — *"Returns true if the request was started, false if it was not (e.g., clipboard doesn't contain text for paste requests). This allows performable keybinds to pass through when the action cannot be performed"* — and the win32 side ALREADY honors it: `Surface.clipboardRequest:1214` returns false when `GetClipboardData(CF_UNICODETEXT)` is null, which is exactly the image-on-clipboard case. But the fall-through at `Surface.zig:3662` is gated on `leaf.flags.performable`, so without the flag ghoztty swallows ctrl+v unconditionally, pastes nothing (no text on the clipboard), and Claude Code never receives the keystroke it would have used to read the image from the clipboard itself. alt+v works precisely because it is unbound and reaches the TUI as `ESC v`. This is a Windows-only divergence: the shared block at `Config.zig:6553-6558` binds cmd+v (Mac) / ctrl+shift+v (elsewhere) **with** `performable = true`, and ctrl+c / ctrl+k in the very same Windows mirror block use `putFlags(..., .{ .performable = true })` — ctrl+v is the only one that forgot. Fix: switch it to `putFlags` with `performable = true`. **Testable prediction to confirm first:** on today's build `ctrl+shift+v` should ALREADY paste an image correctly into Claude Code while `ctrl+v` does not — verify that asymmetry before changing anything, because it proves the diagnosis end-to-end. Then audit the rest of the Windows ctrl-mirror block for other bindings that should be performable but are not. Validation: an on-box case that puts an image (no text) on the clipboard and asserts ctrl+v reaches the pane, plus a text-clipboard case asserting ctrl+v still pastes text and does NOT leak a stray `^V`

## Resolution (2026-07-29)

The filed diagnosis was correct in every particular, and the testable
prediction held. `src/config/Config.zig` win32 mirror block: ctrl+v switched
from `put()` to `putFlags(..., .{ .performable = true })`, matching ctrl+c and
ctrl+k beside it.

**New validation: `test/win32/clipboard-paste.ps1` (12 assertions).** The
oracle is a PowerShell probe running INSIDE the pane, blocked on
`[Console]::ReadKey($true)`, printing the raw character code it received —
which separates the three outcomes exactly, and makes a swallowed chord
visible as "the probe never printed":

| case | clipboard | chord | probe char |
|---|---|---|---|
| A | text `ZQTOKEN` | ctrl+v | 90 (`Z`) — pasted |
| B | image only | ctrl+v | 22 (`^V`) — fell through |
| C | image only | ctrl+shift+v | 22 — control, always was performable |
| D | text | ctrl+v | full token on the input line |

**Red/green on the same box, 20 minutes apart** (not a claim, a measurement):
pre-fix run = `1 FAILED / 11 passed`, the single failure being B with
`probe char=-1` (nothing arrived at all) while C passed with 22 — i.e. the
asymmetry the row predicted, proving the defect is the FLAG and not the
chord. Post-fix = `ALL PASS (12 assertions)` x3.

Floor: `zig build test -Dapp-runtime=none` + `-Dapp-runtime=win32` +
`zig build test-agent` all exit 0; P1/P2/P3 ALL PASS. New unit test in the
none lane (`default keybinds: windows ctrl clipboard mirrors are
performable`) pins the flag on both ctrl+v and ctrl+c so a future edit cannot
drop it silently.

**Audit of the rest of the block** (the row asked for it): ctrl+n/t/w/q/d/p,
ctrl+shift+b and ctrl+f4 all perform unconditionally, so `performable` would
be a no-op; `scroll_to_top`/`scroll_to_bottom` (ctrl+home/end) always return
true in `Surface.performBindingAction`, same conclusion; tab cycling and
`goto_tab` already carry the flag. **One real gap found, one block over:**
shift+insert -> `paste_from_selection` is bound non-performable in the shared
non-darwin block, and win32 `clipboardRequest` returns false for any
non-standard clipboard — so it can never perform AND is swallowed. Filed as
**T156**. Building the validation script also exposed **T157** (the standing
`keybinds-t01.ps1` fails its own positive control — its driver never focuses
the pane child, so its 14 reds are harness artifacts, not product defects).
