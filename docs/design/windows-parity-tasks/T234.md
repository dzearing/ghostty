# T234 - Reclaim vertical space: no tab strip at one tab, menu into the caption bar

## Summary

User directive, 2026-07-31, verbatim: *"don't we own the header? can't we put a
'...' button to the left of the minimize button, and use that space? Then we do
not need to use tabs by default, wasting precious vertical space. The mac client
does not use tabs by default."*

Correct on all three counts, and it is the largest single UX win available in
the Windows chrome:

- ~~**We do own the caption bar.** The window already runs a custom-drawn
  caption (T78 title font, T203 accent/theming, T205's in-titlebar tab work), so
  hosting a control there is a paint + hit-test change, not a new mechanism.~~
  **FALSE — corrected 2026-07-31, see `deps: [T254]`.** The caption is stock
  DWM: every window is plain `WS_OVERLAPPEDWINDOW` (`Window.zig:562`), there is
  no `WM_NCCALCSIZE` handling anywhere in `src/apprt/win32/`, and T78/T203 only
  *ask DWM to restyle its own caption* (`DWMWA_CAPTION_COLOR` /
  `DWMWA_TEXT_COLOR` / the T78 note that a standard frame always draws with the
  system caption font). T205 had recorded this correctly a day earlier. So the
  custom caption is a new mechanism, it is split out as **T254**, and this task
  resumes — as the button rect plus the visibility rule it claimed to be — once
  T254 lands.
- **The strip costs 32 DIP today** (40 after **T232**) of every window, always,
  even with one tab - to display a choice that does not exist. That is 2-3
  terminal rows given up permanently for nothing.
- **Mac does not show a tab bar at one tab**, so this is parity, not a
  divergence.

## The design

1. **The tab strip is not painted when `tab_count == 1`.** It appears when a
   second tab opens and disappears when the count returns to one. The terminal
   is sized from the space that remains, in one layout pass, so the transition
   does not double-resize the panes (a resize storm is visible and costs a
   reflow of every pane's scrollback).
2. **A "..." (overflow) button sits in the caption bar, immediately left of the
   system minimize button**, and is present at every tab count. It carries what
   the hamburger carries today: the window menu. With the strip hidden it is
   the ONLY route to those commands, so it can never be conditional.
3. The strip's own hamburger becomes redundant once the caption button exists.
   Decide explicitly in the task: either drop it (preferred - two entry points
   to one menu next to each other is what made the "+"/hamburger read as an
   undifferentiated cluster in the first place) or keep it and document why.

### Constraints that will bite

- **Caption hit testing.** The button lives in the non-client area, so its
  rect must be excluded from `HTCAPTION` in `WM_NCHITTEST` or the window drags
  when the user clicks it. It also must not overlap the system button group at
  any DPI, and the group's width changes with DPI and with maximize state.
- **Snap Layouts.** Windows shows the snap flyout on hover over the maximize
  button (`HTMAXBUTTON`); a custom button placed too close can steal that hover
  or break the flyout. Test it explicitly.
- **The button obeys the design system**: 28 DIP square, >= 32 DIP hit box,
  4 DIP clear of the minimize button, same hover/pressed/active treatment as
  every other icon button, visible keyboard focus.
- **T205 overlap.** T205 ("tabs belong INSIDE the titlebar") targets the same
  region. Sequence them deliberately - this task makes the strip conditional
  and adds a caption control; T205 moves the strip itself into the caption. If
  T234 lands first, T205's scope shrinks to "the 2+-tab case", which is
  probably the better order. Record the decision.

## Validation

- One tab: the strip is absent, and the terminal's row count increases by
  exactly the strip's height in rows versus today (measured, not assumed).
- Opening a 2nd tab shows the strip; closing back to 1 hides it. No pane
  content is lost or scrambled across either transition.
- The "..." button: correct at 100/125/150/200%, in both themes, maximized and
  restored; clicking it opens the window menu; dragging the caption beside it
  still moves the window; the Snap Layouts flyout still appears on maximize
  hover.
- A new acceptance script (or an extension of `menu-bar.ps1`) covering the
  hidden-strip case, ALL PASS x3 with a negative control.

## Outcome (2026-07-31)

Both halves shipped as one change, because they are one change: the strip could
not go away while it was the app's only menu host.

**The button.** A fourth slot in `caption_layout.zig` — `Button.overflow`,
leftmost, with `Command.menu` so "what does this button do" still has exactly
one answer in the pure module. It paints the same 28 DIP square as everything
else through the same `paintIconButton`, with a new `icon_button.Glyph.overflow`
(three square dots, built middle-out and mirrored, sharing the caption
cluster's `mark_caption` extent).

Three decisions inside it that were not obvious going in:

1. **It is separated from the system trio by `pad_md` (8), not `pad_sm` (4).**
   They are different GROUPS of controls — ours and the OS's — and four evenly
   spaced squares is exactly the undifferentiated cluster the "+"/"≡" pair was
   reported as. Asserted in `nothing touches`, and in `caption-bar.ps1` as a
   plain-chrome pixel in the middle of that wider gap.
2. **It answers `HTSYSMENU`**, Windows' own hit-test code for "the control that
   opens this window's menu" (normally the top-left app icon). Reusing it rather
   than inventing a private code is what makes the button take the same
   non-client mouse path as its neighbours and announce itself correctly. Its
   one piece of `DefWindowProc` baggage — a double-click on `HTSYSMENU` means
   `SC_CLOSE` — is swallowed at the `WM_NCLBUTTONDBLCLK` site.
3. **It opens on PRESS, not on release**, like every Windows menu bar and like
   the strip's own "≡". `TrackPopupMenuEx` blocks and the popup eats the
   release, so there is no press state to arm; `handleNcLButtonUp` returns
   early on `Command.menu` rather than `unreachable`.

`openMenuBar` grew an anchor (`openMenuBarAt(.caption|.strip|.auto)`): there are
two hosts for one menu now, and a popup that appeared a band away from the
control the user clicked would read as the click having missed.

**The visibility rule.** `window-show-tab-bar = auto` is now
`tab_count > 1 or !customCaption()`. The second clause is load-bearing, not
defensive: a `window-decoration = none` window has no caption to host the "…",
so its strip stays and keeps being the menu host. A control surface with
nothing to control may disappear; the only route to the app's commands may not.

**The strip's own "≡" was KEPT**, which is the second of the two answers this
task allowed, and the reasons are written up as **T260**: it is still the only
menu host on a caption-less window, so it has to become *conditional* rather
than be deleted — and conditional changes `runWidth`, the datum three
acceptance scripts key off (the T256/T259 failure mode). Recorded as a
deferral, not as "fine as is".

**T205 sequencing** (the task asked for an explicit decision): T234 landed
first, so T205's scope is now "the 2+-tab case" only, as predicted.

### Measured, on the box at 125%

| | pane top below client top |
|---|---|
| one tab, default config | **45 px** (= `caption_h`, no strip) |
| `--window-show-tab-bar=always` | 95 px |

**50 physical px of terminal returned to every window, permanently** — 40 DIP,
2-3 rows. Opening a 2nd tab takes the pane from 45 → 95; closing back to one
returns it to 45.
