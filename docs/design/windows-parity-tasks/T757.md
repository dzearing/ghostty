# T757 - Terminal output does not linkify Windows paths (D:\...\file.mp4) - the shared url regex is POSIX-only

## In plain terms

A build tool or an agent prints where it put a file — `D:\Users\David\output\
clip.mp4` — into a terminal pane. On a Mac that kind of line becomes
clickable; here it stays dead text, because the pattern Ghoztty uses to spot
paths in terminal output only knows POSIX spellings. Windows paths are
written with a drive letter and backslashes, so none of them are ever
recognized. This is the same complaint T539 fixed for pane BANNERS, on the
surface the user most likely meant.

## Summary

`src/config/url.zig` (shared core, used by both frontends to find links in
terminal content) has three branches: scheme URLs, rooted/dot-relative paths
(`/…`, `./…`, `../…`, `~/…`), and bare relative paths (`src/config/url.zig`).
Every path branch is built from `path_chars`, which is
`[\w\-.~:\/?#@!$&*+;=%]` — **no backslash** — and no branch matches a drive
letter. ✓ VERIFIED by reading the regex (2026-08-11): a `D:\…` or
`\\server\share\…` path in terminal output cannot match, so it is never
underlined and never clickable.

T539 landed the equivalent for pane banners
(`banner_markdown.autolink`), and its sigil set is the model for what to add
here: a drive path (`D:\`, `D:/`), a UNC share, and the backslash spelling of
the relative sigils.

## Details worth settling before building

- **This is shared core, so it must not regress POSIX.** The regex is
  asserted by `test "url regex"` in the same file, which runs on every
  platform. Add Windows cases; keep every existing case matching. A
  drive-letter branch that is live on macOS is probably fine (a `D:\…` string
  is not meaningful there) but is a decision to state either way.
- **What a click DOES with a Windows path.** The banner side reveals a file
  in Explorer rather than opening it (T165). The terminal's link click path
  has to make the same call — check `Surface`'s link-open handling on win32
  before assuming it does.
- **Spaces.** The POSIX branches allow spaces in some segments; Windows
  paths under `C:\Program Files\…` will want the same care, and the same
  ambiguity limits apply.

## What the click does, and why no change was needed there

The task asked whether a click should REVEAL the file in Explorer, as a
banner link does (T165/T539). ✓ VERIFIED it should not, and does not:
that rule belongs to banners, and the TERMINAL's link click opens with the
default application on macOS too (`Ghostty.App.swift`'s `openURL` →
`NSWorkspace.shared.open`). win32's `App.openUrl` → `ShellExecuteW("open")`
is already the same answer, and `resolvePathForOpening` treats `D:\…` and
`\\srv\share\…` as absolute via `std.fs.path.isAbsolute`. Making Windows
reveal instead would have been the divergence, not the parity.

## Found while building this

  finds the whole link on that path (verified with an instrumented build)
  and something replaces the selection immediately after. Not introduced
  here; it is why this task's acceptance script uses a ctrl+right-click.
- **T801** (P2) — `%USERPROFILE%\foo` still does not linkify: the POSIX
