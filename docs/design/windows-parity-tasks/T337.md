# T337 - Layout blobs are lineage-shaped: a Mac viewer cannot decode a win32 blob and vice versa

## In plain terms

Ghoztty can rebuild another machine's whole set of terminal windows — every
window, tab and split — on the machine you are sitting at, with each pane
re-attached to the program still running over there. That worked between two
Windows machines and did nothing at all between a Mac and a Windows one: the
button was there, you pressed it, and it told you there was nothing to restore
even when the other machine had six windows open. Nothing failed and nothing was
logged, so the feature simply looked absent.

After this, sitting at a Windows machine and pointing Restore All at a Mac
rebuilds that Mac's windows here, laid out the way they are over there. The
other direction — sitting at a Mac, restoring a Windows machine — is the Mac
seat's half and is filed as T622.

## Goals

- [x] A Windows viewer rebuilds a Mac machine's windows, tabs and splits
- [x] Mac's per-tab records come back as ONE window with its tabs, in order
- [x] A blob that still cannot be read is skipped, never fatal
- [x] Another viewer's stale screen can never be painted into a restored pane
- [x] The blob's real schema contract is written down where it is called opaque
- [x] The other direction is filed rather than left undocumented

## What was built

A **translating reader**, not an envelope. `decodeLayouts`
(`src/apprt/win32/layout_blobs.zig`) now parses each blob generically once,
identifies its lineage by SHAPE — a macOS entry has a `tree` and no `tabs` — and
hands the Mac ones to the new `src/apprt/win32/mac_layout_blob.zig`, which:

- flattens the nested `tree` (including Swift's `{"leaf":{"_0":…}}` enum
  payload wrapper) into win32's indexed `nodes` array, root first, every child
  index above its parent;
- maps the leaf fields (`sessionID`→`session_id`, `surfaceID`→`pane_id`,
  `viewerLocation`→`viewer_location`, …) and DROPS the WP-D3 snapshot pair;
- regroups Mac's per-TAB entries into one window per `tabGroupID` in `tabIndex`
  order, the same regrouping Mac's own `SessionLayoutRestore` does.

Nothing writes anything new: the wire protocol, the agent and win32's own blob
are untouched, so no skew is possible against a running agent. Rationale for
choosing this over the envelope is decision **D41**; the schema contract is now
stated in `layout_meta.zig`'s header (the file that calls the blob opaque) and
in `docs/design/session-persistence.md` §5.4.2.

Filed out of the **T321 split (2026-08-02)**. Not a blocker for T334/T335/T336
(each machine restores itself, and Windows-to-Windows works end to end), but it
is a real hole in the cross-machine story and it should be decided rather than
discovered.

## The gap

`GET_LAYOUTS` blobs are **opaque to the agent by design** (`layout_meta.zig:9`:
"the agent is DELIBERATELY topology-agnostic"), which means the SCHEMA is a
contract between two VIEWERS - and the two viewers do not share one:

- Mac pushes a `SessionLayoutManifest.Entry` JSON
  (`SessionBrowserProbe.swift:109-135`, camelCase, `sessionID`).
- win32 will push a `session_layout.Window` JSON (T334) - snake_case,
  `session_id`, a FLAT `nodes` array with `left`/`right` indices where Mac
  nests. `session_layout.zig:29-33` already states the assumption that made
  this fine: the file "is never decoded by the macOS app", so "there is no
  cross-lineage key-compatibility constraint".

That assumption holds for the LOCAL restore file it was written about. It does
NOT hold for a blob pushed to an agent that a viewer on the other lineage can
pull. Restore All on a Mac pointed at a Windows machine gets N blobs it cannot
parse; the failure mode is the good one (`compactMap { $0.entry }` drops them,
so it shows "nothing to restore" rather than crashing) but the feature is
silently absent.

## What to decide — RESOLVED (see "What was built" above, and D41)

**Answered: none of these three.** A fourth option won, and the reason the other
three lose is the same fact: the blobs already sitting in live agents carry no
tag and never can, because an agent outlives the app that wrote them by design.
An envelope (1) or a shared schema (2) would describe only FUTURE blobs while
every existing one stayed undecodable, so a reader that tolerates the other
lineage's shape is required either way — which makes translating on read the
whole fix rather than half of one. Option 3 was rejected on the standing bar:
a feature that looks present and is not is the divergence this project does not
ship. The header note this section asked for was written regardless.

The original framing, kept for the record:

Three options, in rough order of preference:

1. **A blob envelope**: `{"lineage":"win32"|"macos","version":1,"body":{...}}`,
   each side decoding its own and ignoring the other's - honest, additive, and
   it makes the gap visible in the data instead of in a bug report. Costs a
   read-side tolerance bump on both sides (an old peer sees an unknown shape,
   which is exactly today's behavior).
2. **One shared schema** both viewers write - the most correct, the most work,
   and it has to survive the app<->agent compatibility rules in CLAUDE.md (an
   old Mac viewer's blobs stay in a live agent across an upgrade).
3. **Document the limit** and stop: cross-machine Restore All works within a
   lineage only. Cheapest, but it leaves a feature that looks present and is
   not.

Whichever is chosen, `layout_meta.zig`'s header should say what the blob's
schema contract actually is, since it is the file that calls it opaque.

## Validation criteria

- [x] A real-shaped macOS blob (camelCase, nested `tree`, `_0` payloads)
      decodes into a `session_layout.Window` with the same topology, ratios,
      session ids and pane ids — `layout_blobs.zig` "T337: a macOS blob restores
      as a window instead of being dropped" + `mac_layout_blob.zig` "a nested Mac
      tree flattens…" / "a deeper tree keeps every child index above its parent"
- [x] Two Mac blobs sharing a `tabGroupID` become ONE window with two tabs in
      `tabIndex` order, even when the reply lists them out of order —
      `mac_layout_blob.zig` "tab siblings become one window in tabIndex order"
- [x] A blob of neither lineage, a malformed Mac tree, and outright garbage are
      each SKIPPED and counted, with the good blobs in the same reply surviving
      — `layout_blobs.zig` "one malformed blob is skipped…" and "a mixed store
      decodes both lineages…"
- [x] A macOS blob's `screenSnapshot`/`screenSnapshotOffset` never reach a
      restored leaf (the T413 rule, which Mac's writer does NOT enforce) —
      `layout_blobs.zig` "a Mac blob's screen snapshot never reaches a restored
      leaf"
- [x] Hostile input costs an error, not the stack or an integer overflow: depth
      and node ceilings, saturating f64→i32, ratio/direction fallbacks —
      `mac_layout_blob.zig` "a pathologically deep tree is refused…" / "bad
      scalars fall back…"
- [x] Detection never misfires on a win32 window, a scalar, an array, `{}`, or a
      non-object `tree` — `mac_layout_blob.zig` "recognized by shape and a win32
      one is not"
- [x] **On the box, through the real binary**: a hermetic instance whose agent
      holds two MAC-shaped blobs rebuilds ONE window with TWO tabs and THREE
      panes (the split in tab one), ATTACHing every session id the blobs named —
      new `test\win32\layout-blob-cross-lineage.ps1`, ALL PASS (13 assertions)
- [x] **Negative control run**: `looksLikeEntry` forced to `false` and rebuilt
      reproduces the pre-T337 symptom exactly — a blank 1-window/1-tab/1-pane
      relaunch with none of the three sessions attached (C1–C3 red, C4 green),
      then reverted and rebuilt. The script can fail, so its pass means something
- [x] No regression on win32-shaped blobs, which now decode via
      `parseFromValueLeaky` rather than straight from bytes —
      `test\win32\session-crash-recover.ps1` ALL PASS (17) and
      `test\win32\layout-blobs.ps1` ALL PASS
- [x] Standing floor green: `zig build test` (`none` + `win32` lanes) and
      `test-agent` via `scripts\floor-lane.ps1 -Lane all`; P1–P3 acceptance
      scripts ALL PASS
- [x] The schema contract is documented where the blob is called opaque
      (`layout_meta.zig` header) and in `session-persistence.md` §5.4.2
