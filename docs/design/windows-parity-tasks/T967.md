# T967 - scripts\guard-due.ps1 is the only acceptance-gate script with no guard row of its own

## In plain terms

There is a safety net on this box that watches for "somebody changed this code
but nobody re-ran the test that covers it", and it names about fifty pieces of
code. It does not name itself. So the one script whose failure would silently
switch off every other reminder is the one nothing reminds you about.

## Summary

`scripts\guard-due.ps1` has an acceptance script — `test\win32\guard-due.ps1`,
47 arms, hermetic, about 20 seconds — and no row in its own coverage table.
Nothing ties an edit of the gate to a run of its harness.

Noticed while fixing T898, which edited `guard-due.ps1` (a new row, a new
`RunArgs` field, three touched return shapes). The acceptance was run by hand
and was green, but that was discipline, not a gate: had it been skipped, a
broken `Get-GuardState` would report `GUARD CURRENT` for everything and every
other row in the table would go quietly unenforced. That is strictly worse
than any single harness going stale, because it is the failure that hides all
the others — the same argument the table's own comment makes about the
go-loop row ("the loop's supervisor is the one thing whose failure nothing
else can catch").

## Details

The row is one entry, in the shape the others already use:

```powershell
[pscustomobject]@{
    Name   = 'guard-due'
    Script = 'test\win32\guard-due.ps1'
    Stamp  = 'test\win32\guard-due.stamp.json'
    Covers = @('scripts\guard-due.ps1', 'test\win32\guard-due.ps1')
}
```

Two things to check rather than assume when adding it:

- **`test\win32\guard-due.ps1` must stamp itself on a green run** (it does not
  today — it is one of the few harnesses here that never calls `update`), and
  it must do so from a run with zero failures, matching the F1 policy it
  asserts about everybody else.
- **Its own fixture arms must not trip over the new row.** Sections A-F drive a
  fixture repo with no `scripts\guard-due.ps1` in it, so the new row reads N/A
  there — the C10/C11 arms exist for exactly this and should cover it, but the
  run is the proof.

Nothing else in the table is self-referential, so this is the first row that
covers the script computing the answer; worth a moment's thought about whether
a `guard-due.ps1` edit that breaks stamping can leave a stamp claiming it did
not.

## Validation criteria

- [ ] A `guard-due` row exists and `guard-due.ps1 check` reports it
- [ ] Editing `scripts\guard-due.ps1` makes it DUE; a green run of
      `test\win32\guard-due.ps1` clears it
- [ ] `test\win32\guard-due.ps1` still ALL PASS (its own fixture arms are not
      disturbed by the self-referential row)
