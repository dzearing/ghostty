# T429 - The restart notice never names what was running: the agent records no command label for a plain shell pane

## Summary

**Split out of T425 (2026-08-03), which carried two symptoms of the user's one
report:** *"I expected 'Previous prompt:' to be preserved and the last known CWD
to be restored in the shell."* T425 said to split the moment the two stopped
sharing a cause. They did — measured on box, they are different mechanisms:

- **cwd** WAS recorded and was merely never refreshed after spawn → **T425**
  (fixed there).
- **the command label** was never recorded at all, for any session, ever →
  this task.

So the "previous command:" line is absent from the restart notice not because
the notice is broken but because there is nothing to print.

## Evidence (2026-08-03, from the box, ✓ VERIFIED by reading both)

The live release agent's `%LOCALAPPDATA%\ghoztty\local-agent\sessions.json`, all
four persistent sessions — **not one carries an `argv` key**, while every one
carries a `cwd`:

```json
{"version":1,"sessions":[
 {"id":"da392fc6…","cwd":"D:\\git\\ghoztty\\","pinned":true,"created_ms":1785781070609},
 {"id":"78e2a8ff…","cwd":"C:\\Users\\David","pinned":true,"created_ms":1785773925039},
 {"id":"1c514abd…","cwd":"D:\\git\\ghoztty\\","pinned":true,"created_ms":1785773924937},
 {"id":"d30c78af…","cwd":"D:\\git\\ghoztty","pinned":true,"created_ms":1785673742135}]}
```

`ghoztty +sessions` agrees — every row ends at `cwd=`, with no command:

```
da392fc64a9dbdf431a96e1ce02ceee2  alive  attached  idle  pid=2704   pinned  cwd=D:\git\ghoztty\
78e2a8fff9588922734bf0341afc23bc  alive  attached  idle  pid=36468  pinned  cwd=C:\Users\David
```

## Root cause

`server.zig:750-754` records the label from the REQUEST, and only from two of
its fields:

```zig
if (open.command) |cmd| {
    s.setArgv(cmd);
} else if (open.shell) |sh| {
    s.setArgv(sh);
}
```

A plain local GUI pane on Windows sends **neither**. `Surface.zig:1078` passes
`.shell = rb.shell`, which is null when the user has not configured one, and
`.command = remote_command`, null for an interactive pane. The agent then
resolves the shell **itself** — `resolveShellPath` (`pty_child.zig:992`):
`OPEN.shell` → `%COMSPEC%` → `C:\Windows\System32\cmd.exe` — and that resolved
value is never handed back to the session record. `Spawner.Result`
(`server.zig:159`) reports `child`, `pid` and `tty`; it does not report what was
actually spawned.

`OPEN.argv` is not a way in either: it is POSIX-only by design
(`pty_child.zig:1026`, "a Windows agent never receives it"), and on this box it
was null anyway — the log line is `local shell integration injected shell=zsh`,
which is `Surface.zig:659`, the **env-only** branch, not the argv-rewrite branch
at `:686`.

## The design question this task must answer FIRST

Recording the resolved shell is the small fix, and it may be the wrong one.
It would make the notice read:

```
    previous command: C:\WINDOWS\system32\cmd.exe
```

That is *true* and close to useless — arguably worse than the current silence,
because it asserts a command was running when the pane was simply a shell. What
the user was actually looking at was `claude`, running INSIDE that shell.

So decide between:

1. **Record the resolved shell** (cheap: add a field to `Spawner.Result`, extend
   the `open.command → open.shell → resolved` chain in `handleOpen`; no wire
   change, agent-internal only). Honest, low value, possible noise.
2. **Record the live FOREGROUND command** — what the user means by "previous
   prompt". The agent already samples the foreground pid every second
   (`session.zig:1050 sampleForegroundPids`, `s.fg_pid`) and already walks the
   process table for `PROC_LIST` (`proc.zig`), so the command line is reachable.
   This is the version with real value and the version that costs more: it needs
   a **new session field** (do NOT overload `argv` — `handleRelaunch`
   `server.zig:1381` re-executes `argv`, so overwriting it with a sampled
   foreground command would make `session-relaunch = auto` run `claude` instead
   of the shell), a new optional field on the DEAD `ATTACHED` reply, and a
   `sessions.json` field.
3. **Both**: the foreground command when known, the resolved shell as the
   fallback, with the notice wording distinguishing them (settle the wording in
   **T424**, which is already rewording this surface — do not reword it twice).

Option 2/3 crosses the app↔agent wire, so it is governed by CLAUDE.md's
**agent contract** rule: evolve additively, gate on the negotiated HELLO
capability, and degrade to today's behavior (no line at all) against a peer that
does not advertise it — an old agent talking to a new app is the normal case
right after an upgrade, which is *exactly* when this notice fires.

## Not a bug in the notice module

`session_notice.format` (`src/termio/session_notice.zig:50`) already does the
right thing with what it is given, and its unit tests already cover both arms —
`test "format: no recorded command omits the command line entirely"` pins the
current, correct behavior for a null label. The gap is entirely upstream.

## Validation

- Agent unit tests (`zig build test-agent`): a session opened with no
  `command`/`shell` still ends up with a non-null label in `sessions.json`.
- `test\win32\session-relaunch-notify.ps1` extended: a pane put through an agent
  restart comes back with the notice **naming** something, asserted in both
  carriers (the in-stream text and the sticky banner — see T423/T422 for why
  there are two).
- If option 2/3 is chosen: a skew test proving an app that asks a label-less
  older agent still gets a clean notice with no command line, rather than an
  empty `previous command:` (`sanitizedCommand` already treats whitespace-only
  as absent — keep that property).
