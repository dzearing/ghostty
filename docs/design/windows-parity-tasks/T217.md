# T217 - Migrate the keyboard-only GUI scripts onto the test desktop

## Summary

T212 split, part 2 of 3: the bulk, and the safe half. These scripts drive with
`SendInput`/`keybd_event` and grab foreground, but never touch the mouse, so
the T211 harness already covers everything they need - no new mechanism
research, just the mechanical conversion described in T212.

Measured surface (2026-07-30, 65 scripts in `test/win32`): 23 are
keyboard-only GUI drivers.

  agent-upgrade, claude-integration, clipboard-paste, command-registry,
  config-errors, confirm-dialogs, font-inherit, ipc-child-exited,
  ipc-machine-chooser, ipc-version, kb-actions, keybinds-t01, new-window-cwd,
  overlay-zorder, pane-banner, profile-latency, relay-account, remote-inherit,
  reset-window-size, session-reattach, split-dim, window-size-memory,
  window-title

(`split-zoom-nav` and `test-desktop-harness` are already migrated;
`test-desktop-spike` is the T207 spike and stays as it is.)

This is still large; expect to take it in batches of 4-6 scripts per context
and mark progress in this file rather than trying to land all 23 in one turn.

## The mechanical change per script

1. `Start-Process` -> `Start-OnTestDesktop`.
2. Delete the private `GrabForeground` copy -> `Focus-TestWindow`.
3. `SendInput` -> `Send-TestKeys` / `Send-TestText` /
   `Send-TestControlText` / `Send-TestControlKey`.
4. Bracket with `Start-TestForegroundWatch` / `Stop-TestForegroundWatch` and
   assert the launched pid never took foreground; assert
   `Test-TestDesktopLeak` is false.

Watch for: scripts whose probes read the **terminal surface** pixels - those
cannot be migrated as pixel assertions (see the CAPTURE LIMIT header in
`lib/TestDesktop.ps1`); chrome probes are fine. And expect product no-ops
rather than harness faults on focus/activation (T215).

**`split-dim` is BLOCKED, not merely pending** - it probes the terminal
surface's own pixels (`GetPixel` over a GhozttyTerminal child, to compare a
focused pane against a dimmed one), which is exactly the CAPTURE LIMIT case:
PrintWindow returns a flat fill there, and an assertion "migrated" onto that
would pass against nothing. It needs **T214** first. Do not count it against
this task's remaining 13 without saying so.

Harness additions batch 1 needed (all in `lib/TestDesktop.ps1`):

- `Set-TestWindowSize` (SetWindowPos, `-Grow` for "stretch by delta") and
  `Test-TestWindowZoomed` (IsZoomed) - the size tests' oracle and their
  posted-key positive control.
- `Send-TestWindowClose` (posted WM_CLOSE) - a posted Enter/Escape never
  reaches a standard dialog, because the dialog manager only sees translated
  messages.
- `Get-TestWindowClass` - lets a script check that an hwnd it got from
  elsewhere (`+list --json`'s window `id`) really is a `GhozttyWindow`.
- The worker thread now asks for **per-monitor-v2** DPI awareness before
  falling back to `SetProcessDPIAware`, so another process's window rect is
  never virtualized. `reset-window-size` compares exact pixel sizes.

Things batch 1 learned, for the next batch:

- **Scripts that let `+new-window` auto-spawn the app must launch it
  themselves.** Auto-spawn puts the GUI on the *user's* desktop, which is the
  whole thing being fixed. Start it with `Start-OnTestDesktop` first (env like
  `XDG_CONFIG_HOME` / `GHOZTTY_PIPE_SUFFIX` is inherited through
  `CreateProcessW`), then drive it with the usual `+...` verbs.
- **Set `GHOZTTY_PIPE_SUFFIX` unconditionally** while migrating. Several of
  these scripts only isolated the endpoint when `-ExePath` was passed, so a
  default run queried whatever instance answered the shared pipe.
- **`@()` at the CALL site, not inside the helper.** PowerShell unrolls a
  function's array return, so a one-element result arrives as a scalar whose
  `.Count` is `$null` - which reads as "0 panes" and fails an assertion that
  should pass. Cost: one false FAIL on `new window has 1 pane`.
- **A migrated script asserts more than it used to, so stale expectations
  surface.** `ipc-version` looked for the About box as a `#32770` MessageBox;
  it has been a native `GhozttyConfirmDialog` since the T50 chrome pass. The
  old script never noticed because its foreground grab kept losing the race
  and the whole section took its `SKIP palette test` branch. Assume every
  section that could SKIP has un-run assertions in it.

Harness additions batch 2 needed (all in `lib/TestDesktop.ps1`):

- `Invoke-TestDragResize` (WM_ENTERSIZEMOVE -> SetWindowPos ->
  WM_EXITSIZEMOVE) and `Send-TestSysCommand` (WM_SYSCOMMAND maximize /
  restore / minimize / close). A placement test turns on the difference
  between a USER resize and a programmatic one, and `Set-TestWindowSize` is
  the programmatic one - it deliberately does not look like a drag.
- `Get-TestWindowNormalRect` (GetWindowPlacement `rcNormal`) - the restored
  size, readable while the window is maximized.
- `Get-TestWorkArea` - SPI_GETWORKAREA **on the worker thread**. The work area
  is per-desktop and a background desktop has no taskbar, so the interactive
  desktop's is the wrong rectangle to clamp-check the app against.
- `Get-TestControlText` (WM_GETTEXT) and `Set-TestControlText` (WM_SETTEXT) -
  reading a prefilled dialog EDIT, and committing an exact value into one.
- All of these go through a new `Send()` helper that uses
  **SendMessageTimeoutW**, never plain SendMessage: a synchronous cross-process
  send into a wedged app would block the ONE worker thread the whole harness
  marshals through, and every later call with it.

Things batch 2 learned, for the next batch:

- **Turn `--session-persistence=false` on in any multi-launch script.** With
  persistence on, each section's app re-attaches to the surviving agent and
  restores the LAYOUT MANIFEST, whose geometry then competes with whatever
  the test is actually asserting - and the manifest write races the
  force-kill between sections, so it is nondeterministic. `window-size-memory`
  failed 6 assertions on its first run and passed the next three before the
  flag went in. `Kill-RepoInstances` does not close this hole: it kills
  `ghoztty.exe`, not `ghoztty-agent.exe`.
- **Dialog EDITs need WM_SETTEXT, not typing.** These dialogs arrive
  PREFILLED, and clearing one by keyboard needs a select-all chord, which
  does not reach a standard control (see the note on `Send-TestControlKey`).
  Read them back with `Get-TestControlText`; `Get-TestWindowText` is
  GetWindowTextW, which is cross-process cached and reads stale.
- **Deleting a SKIP branch is most of the value.** `window-title`'s S3
  section could skip itself when the foreground grab lost its race; on the
  test desktop the chord always lands, and the section's 6 assertions now
  always run. The script went from 39 to 50 assertions with no new coverage
  written - it just stopped hiding.
- The build needs `ZIG_GLOBAL_CACHE_DIR=D:\zig-global-cache` in the session
  env. Without it the zig 0.15.2 build runner panics
  (`convertPathArg` assert) on the cross-drive C: default - an opaque
  `reached unreachable code`, not a compile error.

Harness additions batch 3 needed (in `lib/TestDesktop.ps1`):

- `Get-TestLaunchedPids` - and it exists because batch 2 shipped a **vacuous
  assertion**. `Remove-TestDesktop` empties `$script:GhozttyTestDesktopPids`
  as it kills them, and the foreground-leak assertion runs AFTER the `finally`
  that calls it, so `command-registry` and `window-title` were scoring "no
  test-desktop app ever became foreground" against an EMPTY pid list - it
  could not have failed. (Batch 1's scripts were fine: they accumulate a local
  `$launched` inside the try, before cleanup.) The harness now also keeps
  `$script:GhozttyTestDesktopAllPids`, which cleanup does not touch, and
  `Get-TestLaunchedPids` reads it. Both batch-2 scripts are fixed. **Every new
  migration must use `Get-TestLaunchedPids` for that assertion.**

Things batch 3 learned, for the next batch:

- **A script whose keys go to a WINDOW must find the active surface first.**
  `GhozttyWindow` hands WM_KEYDOWN to `DefWindowProc` and only forwards FOCUS
  to the active pane (Window.zig, WM_SETFOCUS). SendInput hid that by
  following focus on its own; a POSTED key does not, so posting to the window
  is silently dropped. `Focus-TestWindow` then `Get-TestFocusedWindow` gives
  the pane the app actually considers active - which for `remote-inherit` also
  had to be the RIGHT pane, since the assertion is about what the new tab
  inherits. Do not substitute `Get-TestChildWindow` (first child in enum
  order), which is a different pane.
- **`+list --json`'s window `id` IS the hwnd** (`IpcHandlers.zig` formats
  `@intFromPtr(hwnd)`), so a script can address one SPECIFIC named window
  instead of trusting z-order enumeration - pair it with `Get-TestWindowClass`
  to prove what you got. That is how `remote-inherit` stopped needing an IPC
  "raise this window" call it only made so that a z-order-first search would
  land on the right one.
- **Ghoztty's own dialogs take POSTED Enter/Escape/Tab; standard ones do
  not.** `ConfirmDialog` reads raw WM_KEYDOWN in its nested pump and
  `RenameDialog`/`BannerDialog`/`MachineChooser` are routed from the App.run
  intercept, so `Send-TestControlKey` drives all of them. `Send-TestWindowClose`
  is only needed for a real `#32770`.
- **Guard every brightness probe with `Get-TestDistinctColors`.** All six
  dark-render probes in this batch pass on a real capture (64 distinct colors,
  mean luminance 39-43), but a mid-paint capture is solid black and would have
  passed "< 90" while proving nothing (T216). The guard turns each probe into
  two assertions, which is why these scripts gained assertions without gaining
  coverage.
- **Check whether the script even exits nonzero.** `config-errors` printed its
  failure count and then exited 0, so a red run scored as green in any suite
  driver that reads exit codes. Fixed here; worth a glance in every remaining
  script.
