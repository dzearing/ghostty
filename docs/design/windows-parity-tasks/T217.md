# T217 - Migrate the keyboard-only GUI scripts onto the test desktop

## Summary

T212 split, part 2 of 3: the bulk, and the safe half. These scripts drive with
`SendInput`/`keybd_event` and grab foreground, but never touch the mouse, so
the T211 harness already covers everything they need - no new mechanism
research, just the mechanical conversion described in T212.

Measured surface (2026-07-30, 65 scripts in `test/win32`): 23 are
keyboard-only GUI drivers.

  agent-upgrade, claude-integration, clipboard-paste, command-registry,
  config-errors, confirm-dialogs, font-inherit, ipc-child-exited,
  ipc-machine-chooser, ipc-version, kb-actions, keybinds-t01, new-window-cwd,
  overlay-zorder, pane-banner, profile-latency, relay-account, remote-inherit,
  reset-window-size, session-reattach, split-dim, window-size-memory,
  window-title

(`split-zoom-nav` and `test-desktop-harness` are already migrated;
`test-desktop-spike` is the T207 spike and stays as it is.)

This is still large; expect to take it in batches of 4-6 scripts per context
and mark progress in this file rather than trying to land all 23 in one turn.

## The mechanical change per script

1. `Start-Process` -> `Start-OnTestDesktop`.
2. Delete the private `GrabForeground` copy -> `Focus-TestWindow`.
3. `SendInput` -> `Send-TestKeys` / `Send-TestText` /
   `Send-TestControlText` / `Send-TestControlKey`.
4. Bracket with `Start-TestForegroundWatch` / `Stop-TestForegroundWatch` and
   assert the launched pid never took foreground; assert
   `Test-TestDesktopLeak` is false.

Watch for: scripts whose probes read the **terminal surface** pixels - those
cannot be migrated as pixel assertions (see the CAPTURE LIMIT header in
`lib/TestDesktop.ps1`); chrome probes are fine. And expect product no-ops
rather than harness faults on focus/activation (T215).

Things batch 1 learned, for the next batch:

- **Scripts that let `+new-window` auto-spawn the app must launch it
  themselves.** Auto-spawn puts the GUI on the *user's* desktop, which is the
  whole thing being fixed. Start it with `Start-OnTestDesktop` first (env like
  `XDG_CONFIG_HOME` / `GHOZTTY_PIPE_SUFFIX` is inherited through
  `CreateProcessW`), then drive it with the usual `+...` verbs.
- **Set `GHOZTTY_PIPE_SUFFIX` unconditionally** while migrating. Several of
  these scripts only isolated the endpoint when `-ExePath` was passed, so a
  default run queried whatever instance answered the shared pipe.
- **`@()` at the CALL site, not inside the helper.** PowerShell unrolls a
  function's array return, so a one-element result arrives as a scalar whose
  `.Count` is `$null` - which reads as "0 panes" and fails an assertion that
  should pass. Cost: one false FAIL on `new window has 1 pane`.
- **A migrated script asserts more than it used to, so stale expectations
  surface.** `ipc-version` looked for the About box as a `#32770` MessageBox;
  it has been a native `GhozttyConfirmDialog` since the T50 chrome pass. The
  old script never noticed because its foreground grab kept losing the race
  and the whole section took its `SKIP palette test` branch. Assume every
  section that could SKIP has un-run assertions in it.

Harness additions batch 2 needed (all in `lib/TestDesktop.ps1`):

- `Invoke-TestDragResize` (WM_ENTERSIZEMOVE -> SetWindowPos ->
  WM_EXITSIZEMOVE) and `Send-TestSysCommand` (WM_SYSCOMMAND maximize /
  restore / minimize / close). A placement test turns on the difference
  between a USER resize and a programmatic one, and `Set-TestWindowSize` is
  the programmatic one - it deliberately does not look like a drag.
- `Get-TestWindowNormalRect` (GetWindowPlacement `rcNormal`) - the restored
  size, readable while the window is maximized.
- `Get-TestWorkArea` - SPI_GETWORKAREA **on the worker thread**. The work area
  is per-desktop and a background desktop has no taskbar, so the interactive
  desktop's is the wrong rectangle to clamp-check the app against.
- `Get-TestControlText` (WM_GETTEXT) and `Set-TestControlText` (WM_SETTEXT) -
  reading a prefilled dialog EDIT, and committing an exact value into one.
- All of these go through a new `Send()` helper that uses
  **SendMessageTimeoutW**, never plain SendMessage: a synchronous cross-process
  send into a wedged app would block the ONE worker thread the whole harness
  marshals through, and every later call with it.

Things batch 2 learned, for the next batch:

- **Turn `--session-persistence=false` on in any multi-launch script.** With
  persistence on, each section's app re-attaches to the surviving agent and
  restores the LAYOUT MANIFEST, whose geometry then competes with whatever
  the test is actually asserting - and the manifest write races the
  force-kill between sections, so it is nondeterministic. `window-size-memory`
  failed 6 assertions on its first run and passed the next three before the
  flag went in. `Kill-RepoInstances` does not close this hole: it kills
  `ghoztty.exe`, not `ghoztty-agent.exe`.
- **Dialog EDITs need WM_SETTEXT, not typing.** These dialogs arrive
  PREFILLED, and clearing one by keyboard needs a select-all chord, which
  does not reach a standard control (see the note on `Send-TestControlKey`).
  Read them back with `Get-TestControlText`; `Get-TestWindowText` is
  GetWindowTextW, which is cross-process cached and reads stale.
- **Deleting a SKIP branch is most of the value.** `window-title`'s S3
  section could skip itself when the foreground grab lost its race; on the
  test desktop the chord always lands, and the section's 6 assertions now
  always run. The script went from 39 to 50 assertions with no new coverage
  written - it just stopped hiding.
- The build needs `ZIG_GLOBAL_CACHE_DIR=D:\zig-global-cache` in the session
  env. Without it the zig 0.15.2 build runner panics
  (`convertPathArg` assert) on the cross-drive C: default - an opaque
  `reached unreachable code`, not a compile error.

Harness additions batch 3 needed (in `lib/TestDesktop.ps1`):

Things batch 3 learned, for the next batch:

- **A script whose keys go to a WINDOW must find the active surface first.**
  `GhozttyWindow` hands WM_KEYDOWN to `DefWindowProc` and only forwards FOCUS
  to the active pane (Window.zig, WM_SETFOCUS). SendInput hid that by
  following focus on its own; a POSTED key does not, so posting to the window
  is silently dropped. `Focus-TestWindow` then `Get-TestFocusedWindow` gives
  the pane the app actually considers active - which for `remote-inherit` also
  had to be the RIGHT pane, since the assertion is about what the new tab
  inherits. Do not substitute `Get-TestChildWindow` (first child in enum
  order), which is a different pane.
- **`+list --json`'s window `id` IS the hwnd** (`IpcHandlers.zig` formats
  `@intFromPtr(hwnd)`), so a script can address one SPECIFIC named window
  instead of trusting z-order enumeration - pair it with `Get-TestWindowClass`
  to prove what you got. That is how `remote-inherit` stopped needing an IPC
  "raise this window" call it only made so that a z-order-first search would
  land on the right one.
- **Ghoztty's own dialogs take POSTED Enter/Escape/Tab; standard ones do
  not.** `ConfirmDialog` reads raw WM_KEYDOWN in its nested pump and
  `RenameDialog`/`BannerDialog`/`MachineChooser` are routed from the App.run
  intercept, so `Send-TestControlKey` drives all of them. `Send-TestWindowClose`
  is only needed for a real `#32770`.
- **Guard every brightness probe with `Get-TestDistinctColors`.** All six
  dark-render probes in this batch pass on a real capture (64 distinct colors,
  mean luminance 39-43), but a mid-paint capture is solid black and would have
  passed "< 90" while proving nothing (T216). The guard turns each probe into
  two assertions, which is why these scripts gained assertions without gaining
  coverage.
- **Check whether the script even exits nonzero.** `config-errors` printed its
  failure count and then exited 0, so a red run scored as green in any suite
  driver that reads exit codes. Fixed here; worth a glance in every remaining
  script.

Harness additions batch 4 (all in `lib/TestDesktop.ps1`):

- `Test-TestWindowEnabled` (IsWindowEnabled) - modality's observable side. An
  owner window is disabled for exactly as long as its modal dialog is up, and
  it is the only cross-process-safe way to assert that.
- `Send-TestInjectedChar` - text that did NOT come from the surface's own
  WM_KEYDOWN (screen readers, on-screen keyboards, automation). Read its

Things batch 4 learned, for the next batch:

- **A posted `VK_PACKET` keydown is NEVER translated into a WM_CHAR, so
  `SendInput(KEYEVENTF_UNICODE)` has NO faithful replacement off the input
  desktop.** This is the second measured mechanism limit after the capture
  one, and it was worth measuring rather than reasoning about: posting
  `WM_KEYDOWN(VK_PACKET, char in the lParam HIWORD)` is the documented-looking
  trick and it silently does nothing (the real packet carries its 16-bit
  character out of band; a posted lParam has only an 8-bit scan-code field).
  A posted `WM_CHAR` to the same surface arrives fine. So `kb-actions`'s T64
  section covers the app's injected-WM_CHAR handling but NOT `App.run`'s
  TranslateMessage exemption for VK_PACKET - filed as **T222**, and the
  assertions were RENAMED to say what they prove. Relabelling them instead
  would have been the exact vacuous-assertion failure batch 3 warned about.
- **Migrate the assertion, not just the mechanism.** Three `kb-actions`
  sections were wrapped in `if ($before -match ...) { } else { SKIP }` guards
  whose SKIP branch was silent; turning each guard into its own assertion
  ("T47 fill landed in the pane", "T50 shell-set title reached the tab label")
  is what took the script from 24 to 42 assertions. Same pattern as batch 2's
  `window-title`: the coverage was already written, it was just hiding.
- **A `-NegativeControl` on a script with nested optional sections needs a
  reachability guard.** If the section carrying the inverted assertion is
  skipped, the control run passes and proves nothing. `kb-actions` asserts
  `$false` with "NEGATIVE CONTROL never reached its inverted assertion" in
  that case.
- **The clipboard is NOT desktop-scoped, so clipboard tests migrate
  unchanged.** It belongs to the WINDOW STATION, and `CreateDesktopW` makes
  the test desktop inside the caller's own WinSta0 - so fixtures set by the
  script are the ones the app on the test desktop reads. (`clipboard-paste`
  still needs an STA host, for `System.Windows.Forms.Clipboard`, not for the
  desktop.)

Things batch 5 learned, for the next batch:

- **A helper that Asserts cannot also RETURN.** `new-window-cwd`'s `Assert`
  emitted its PASS/FAIL line to the PIPELINE, and the migration put a

  and `$app.Pid` was `$null`. Fixed by making `Assert`/`AssertEq` use
  `Write-Host`. Worth checking before adding an assertion to any helper in
  the remaining scripts; several of them print via the pipeline.
- **`Focus-TestWindow` + `Get-TestFocusedWindow` also picks the right pane
  when there are several WINDOWS.** Batch 3 used it to pick the right pane
  inside one window; `new-window-cwd` needs the right *window* (ctrl+n
  inherits from the focused pane, and every pane in that test is `cmd.exe`),
  and the same pairing does it - no title hunting. The old script pinned
  `--title=PROJWIN` purely so a title search could find the window; the pin
  stays as documentation, but nothing depends on it now.
- **The palette query field is a standard EDIT, so it takes
  `Send-TestControlText` + `Send-TestControlKey -Key Enter`,** not
  `Send-TestText`. `claude-integration` typed C-L-A-U-D-E as raw VKs through

- **`Test-TestWindowEnabled` turns "a dialog appeared" into "a MODAL dialog

  `claude-integration`'s first-run prompt asserts the owner window is
  disabled while it is up and enabled again after, which no assertion in the
  old script covered.
- **A `Wait-Class` copy whose last argument was a RETRY COUNT becomes a
  TIMEOUT in the harness idiom.** Both migrated scripts carried their own
  `Wait-Class($tries)` (tries x 100ms); the config-errors shape takes
  milliseconds. Converting the call sites is mechanical (`80` -> `8000`) but
  silent if missed - an 80ms wait for a dialog would just flake.

Things batch 6 learned, for the next batch:

- **A script can be almost entirely IPC-driven and still need the migration.**
  `session-reattach` drives everything through `+list`/`+sessions`/`+read` and
  the on-disk manifest; only its three GUI LAUNCHES touched the desktop. That
  made it cheap to move - and it is exactly why it had never been questioned.
  Look for the `Start-Process` sites first; the rest may already be portable.
- **Check whether a section's oracle still discriminates on the test desktop
  BEFORE trusting a green.** The T105 sections were the reverse of the usual
  worry: the risk was a vacuous PASS (the guard bypassed off the input desktop
  would drop every assert), and what actually happened was a genuine RED. Both
  outcomes need the same question asked - "what does the product do
  differently off the input desktop, and does this assertion still bite?" -
  and `onInputDesktop()` in `App.zig` is the list of places to ask it.
- **`GetForegroundWindow` is null for EVERY window on a background desktop, so
  any assertion built on it scores zero and passes.** `session-reattach`'s old
  F11b ("foreground stays parked") was deleted rather than relabelled for that
  reason. Grep a candidate script for `GetForegroundWindow` before migrating:
  every use is either a focus grab (replace with `Focus-TestWindow`) or an
  oracle that has to go.
- **A private win32 driver class can often be deleted outright, not ported.**
  `T105Drv`'s 120 lines became four harness calls plus a 12-line
  `Measure-FocusFlips` built on `Get-TestFocusedWindow` +
  `Get-TestChildWindows`. Reach for a new harness primitive only for what has
  no equivalent (here, one raw `PostMessage`).

Things batch 7 learned, for the next batch:

- **A whole script can be gated on a SKIP, not just a section.**
  `ipc-machine-chooser` ended `if ($aborted) { "SKIPPED (foreground
  unavailable)"; exit 0 }` - a busy box scored a green run that had asserted

  need the foreground; they SKIP, never fail"), which quietly took its entire
  GUI half out of a run. Both are gone: on the test desktop a chooser that does
  not open is a SETUP FAIL. Grep a candidate for `exit 0` before migrating it.
- **The dialog pixel probes migrate as-is - it is the CAPTURE PATH that
  changes.** Every probe in `ipc-machine-chooser` (the accent pill and its
  gutter, the column wash, the hairline rule, the filter's cue banner, the
  wrapped status strip, the detail-pane region signature) reads the chooser's
  own GDI chrome, and all of them produce the same verdicts through
  `Get-TestWindowPixels` as they did through `CopyFromScreen` - 64 distinct
  colors, pill tint 47, gutter 0. Only `Get-WindowShot`/`Get-ShotPixel` had to
  be rewritten. The CAPTURE LIMIT is about the OpenGL terminal surface, not
  about native dialogs, and this batch is the measured demonstration.
- **`Get-TestWindowRect -Client` already returns SCREEN coordinates**, so a
  script that had its own `ClientToScreen`-based `ClientOrigin` helper (which
  is how every client-space layout number gets probed on a capture) just drops
  it: `.Left`/`.Top` are the origin and `.Width`/`.Height` are the client size.
- **Modality was assertable in both scripts and neither asserted it.**
  `Test-TestWindowEnabled` on the OWNER, before and after, turns "a chooser
  window existed" into "a modal chooser owned its window" for two lines - the
  same win batch 5 got on `claude-integration`. Ask it of every dialog script.
- **`EnumChildWindows` is recursive, so a "is this hwnd inside that dialog?"
  test is a membership check on `Get-TestChildWindows -Class '*'`** - no
  GetParent walk, and no second mechanism to keep honest. That is what
  `relay-account`'s "keyboard focus stays inside the chooser while busy"
  (paired with `Get-TestFocusedWindow`) is built on now.

Harness additions batch 8 (all in `lib/TestDesktop.ps1`):

- `Get-TestWindows` - all TOP-LEVEL windows of a pid matching a class, same
  object shape as `Get-TestChildWindows`. `Get-TestWindow` answers "the
  window"; a script asserting *"no overlay windows remain on the glass"* or
  locating the strip glued above pane #1 needs "how many, and where".
- `Set-TestWindowPos` - a MOVE (optionally with a resize). `Set-TestWindowSize`
  deliberately never moves, and the move is load-bearing here: it is what
  exercises `WM_MOVE -> updatePaneBanners`, i.e. the overlay re-gluing itself
  to a pane that went somewhere else.
- `Get-TestLayeredAttrs` (GetLayeredWindowAttributes) - see the opacity note
  below.
- **`Get-TestChildWindows` gained `Width`/`Height`**, which `Get-TestWindows`
  also carries, so the two shapes are interchangeable. It was missing, and the
  cost is in the next note.

Things batch 8 learned:

- **"Composited pixel == own-DC pixel" has no off-desktop equivalent, so assert
  the attribute that DECIDES the composite.** That pair was T131's proof the
  glass card is opaque, and a background desktop has no composite to compare
  against. Relabelling one capture as "composited == own" would have been
  vacuous; instead the claim is now `GetLayeredWindowAttributes` reporting
  alpha 255 with LWA_ALPHA and **no colour key**, paired with the unchanged
  band-corner probe (which is what a translucent strip actually failed). This
  is the general move when a migration loses a comparison: find the state that
  made the two sides equal, not a weaker version of one side.
- **A `$null` property is a silent FAIL, not an error.** `Get-TestChildWindows`
  had no `Width`, so `$pane.Width` was `$null`, and `$null -eq 1810` just
  scores a red line - two of them, reading `"the pane really shrank ( -> px)"`.
  PowerShell will not warn about a property that does not exist. Same family as
  the batch-1 `@()` trap and the batch-5 pipeline-return trap: the language
  turns a typo into a wrong answer rather than a stack trace. **The tell is an
  assertion message with an empty interpolation in it** - if a FAIL prints
  `( -> px)` where numbers belong, suspect the probe before the product.
- **`Send-TestControlText` into a prefilled EDIT tests more than typing.** The
  banner editor arrives with `EM_SETSEL(0,-1)`, so posting a single WM_CHAR
  replaces the whole selection - which makes "the prefill was selected" an
  assertion rather than an assumption. Pair it with `Get-TestControlText` first
  to prove what it was prefilled WITH.
- **Ctrl+Enter to a dialog needs `Send-TestKeys`, not `Send-TestControlKey`.**
  `BannerDialog.handleKey` reads `GetKeyState(VK_CONTROL)`, which is the app
  thread's QUEUE state; `Send-TestControlKey` sets keyboard state without
  attaching, so the modifier never reaches it, while `Send-TestKeys` shares the
  queue via `AttachThreadInput` first. The harness header already says
  modifiers do not reliably reach a standard control - the fix is to route the
  chord through the window path even when the target hwnd is a control.
- **Posted clicks make a click-driven section keyboard-only.** `pane-banner`'s
  collapse/expand test was already `PostMessage(WM_LBUTTONUP)` rather than
  SendInput, which is why this script belonged in T217 and not T218 - worth
  checking before assuming a script that clicks is mouse-driven.
