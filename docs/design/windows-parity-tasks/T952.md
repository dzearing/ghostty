# T952 - crash tooling identifies a lane by embedded test names; a build-time lane stamp would make it exact

## Summary

T855 made lane resolution real by reading the zig test names embedded in each candidate binary, which is measured and covered. It is still a SIGNATURE TABLE (scripts/lib/CrashCatch.ps1, LANE_MARKERS): renaming or deleting one of the named tests makes every candidate fail to verify, and the crash tooling then refuses to resolve any binary for that lane. crash-stacks.ps1 section 7 now FAILS rather than skips when that happens, so the drift is caught by a harness rather than in the field - but the exact fix is for the LANE ITSELF to say what it built: floor-lane (or build.zig) writing a small marker beside the binary, or into a manifest, naming lane + optimize mode + filter, with resolution preferring that and falling back to the markers.

## In plain terms

The crash-diagnosis tools work out which of two identically-named test programs
they are looking at by reading a list of test names out of the file. It works,
and a test guards it -- but the list is maintained by hand, so renaming one of
those tests would make the tools stop recognising anything. The build already
knows exactly what it produced; having it leave a note beside the program would
turn a good inference into a fact.

## Validation criteria

- [ ] The lane's own build leaves a marker naming lane + optimize mode + any
      test filter beside (or alongside) the binary it produced.
- [ ] Resolution prefers that marker and falls back to the embedded test names,
      so an older build in the cache still resolves.
- [ ] A marker that contradicts the binary is a loud failure, not a preference.
- [ ] Acceptance coverage in `test\win32\crash-stacks.ps1` alongside the T855
      sections.
