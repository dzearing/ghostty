# T448 - Desktop notification click never verified to focus the pane that raised it on Windows

## In plain terms

When something finishes in a background pane, Ghoztty pops a Windows
notification. Clicking that notification is supposed to bring you straight
back to the pane that raised it. The code to do that is written, but nobody
has ever checked that it works end to end on this box - so if it is broken,
the way we would find out is a user clicking a notification and landing
nowhere.

## Goals

- [ ] The click-to-focus path is exercised on the box, not just read
- [ ] The right pane is focused when several panes exist, not just the right
      window
- [ ] Any defect the check turns up is fixed or filed

## Summary

Split out of T28 (2026-08-04). Unlike its three siblings this is a
verification task, not a port: the implementation already exists and is
plausible on inspection. What it lacks is evidence.

## Details

**What exists.** `App.zig:5723-5743` handles `WM_APP_TRAY`; on
`NOTIF_DESKTOP_UID` + `NIN_BALLOONUSERCLICK` it looks up
`notif_desktop_surface_id` via `core_app.findSurfaceByID` and performs
`.present_terminal` against that surface. The id is stamped when the
notification is raised (`showDesktopNotification`, `App.zig:5104-5114`, and
the Claude-integration path at `App.zig:4304-4305`). The renderer-unhealthy
balloon deliberately clears it to 0 first (`App.zig:4078`), so that one is
expected NOT to focus anything.

**What to check, in order:**

1. A notification raised from a background pane, clicked, focuses that
   pane's window AND makes that pane the focused pane within it.
2. With two windows open and the notification raised from the non-foreground
   one, the correct window is presented.
3. A pane that has since been closed does not crash the app -
   `findSurfaceByID` returning null is handled, but confirm it on the box.
4. `notif_desktop_surface_id` is not left stale across notifications from
   different panes (it is a single app-wide slot; the second notification
   overwrites it, which is correct - assert the LAST raiser wins).

**Test-method trap, and the reason this task is not trivial.** T240's lesson
applies directly: *an acceptance script that synthesizes the trigger cannot
validate the trigger.* Posting `WM_APP_TRAY` by hand proves the handler
body, not that Shell_NotifyIcon actually delivers
`NIN_BALLOONUSERCLICK` for our balloon - and the delivery is exactly the
half most likely to be wrong (it depends on `NOTIFYICONDATA.uVersion` being
set via `NIM_SETVERSION`, which is easy to miss). So:

- **Check the registration first by reading the code**: no
  `NIM_SETVERSION` / `NOTIFYICON_VERSION_4` means the balloon click arrives
  as `WM_LBUTTONUP` on the icon, not `NIN_BALLOONUSERCLICK`, and the handler
  is dead code. That would be the defect.
- A synthesized-message script is still worth having for the routing half
  (which pane gets focused), but it must SAY in its header that it does not
  cover delivery - the way `activity-monitor-remote.ps1` does.
- Balloons render on the interactive desktop, so a real click cannot run
  under `test/win32/lib/TestDesktop.ps1`. If a real-click check is possible
  at all it is a documented manual step, not a lane.

*Validation:* an on-box acceptance script in `test/win32/` covering the
routing cases above with the delivery caveat stated in its header, plus a
read-verified answer on the `NIM_SETVERSION` question recorded here. Both
`zig build test` lanes, `zig build test-agent`, and P1-P3 stay green.
