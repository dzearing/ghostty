# T448 - Desktop notification click never verified to focus the pane that raised it on Windows

## In plain terms

When something finishes in a background pane, Ghoztty pops a Windows
notification. Clicking that notification is supposed to bring you straight
back to the pane that raised it. The code to do that is written, but nobody
has ever checked that it works end to end on this box - so if it is broken,
the way we would find out is a user clicking a notification and landing
nowhere.

## Goals

- [x] The click-to-focus path is exercised on the box, not just read
- [x] The right pane is focused when several panes exist, not just the right
      window
- [x] Any defect the check turns up is fixed or filed

## Summary

Split out of T28 (2026-08-04). Unlike its three siblings this is a
verification task, not a port: the implementation already exists and is
plausible on inspection. What it lacks is evidence.

**Outcome (2026-08-07): the verification found the defect it was written to
look for.** The task itself named the suspect — a missing `NIM_SETVERSION` —
and that is exactly what was wrong, so click-to-focus had never worked on
Windows despite reading correctly. Fixed, plus a routing acceptance script and
unit tests. See "The answer on NIM_SETVERSION" and "Evidence" below.

## Details

**What exists.** `App.zig:5723-5743` handles `WM_APP_TRAY`; on
`NOTIF_DESKTOP_UID` + `NIN_BALLOONUSERCLICK` it looks up
`notif_desktop_surface_id` via `core_app.findSurfaceByID` and performs
`.present_terminal` against that surface. The id is stamped when the
notification is raised (`showDesktopNotification`, `App.zig:5104-5114`, and
the Claude-integration path at `App.zig:4304-4305`). The renderer-unhealthy
balloon deliberately clears it to 0 first (`App.zig:4078`), so that one is
expected NOT to focus anything.

**What to check, in order:**

1. A notification raised from a background pane, clicked, focuses that
   pane's window AND makes that pane the focused pane within it.
2. With two windows open and the notification raised from the non-foreground
   one, the correct window is presented.
3. A pane that has since been closed does not crash the app -
   `findSurfaceByID` returning null is handled, but confirm it on the box.
4. `notif_desktop_surface_id` is not left stale across notifications from
   different panes (it is a single app-wide slot; the second notification
   overwrites it, which is correct - assert the LAST raiser wins).

**Test-method trap, and the reason this task is not trivial.** T240's lesson
applies directly: *an acceptance script that synthesizes the trigger cannot
validate the trigger.* Posting `WM_APP_TRAY` by hand proves the handler
body, not that Shell_NotifyIcon actually delivers
`NIN_BALLOONUSERCLICK` for our balloon - and the delivery is exactly the
half most likely to be wrong (it depends on `NOTIFYICONDATA.uVersion` being
set via `NIM_SETVERSION`, which is easy to miss). So:

- **Check the registration first by reading the code**: no
  `NIM_SETVERSION` / `NOTIFYICON_VERSION_4` means the balloon click arrives
  as `WM_LBUTTONUP` on the icon, not `NIN_BALLOONUSERCLICK`, and the handler
  is dead code. That would be the defect.
- A synthesized-message script is still worth having for the routing half
  (which pane gets focused), but it must SAY in its header that it does not
  cover delivery - the way `activity-monitor-remote.ps1` does.
- Balloons render on the interactive desktop, so a real click cannot run
  under `test/win32/lib/TestDesktop.ps1`. If a real-click check is possible
  at all it is a documented manual step, not a lane.

*Validation:* an on-box acceptance script in `test/win32/` covering the
routing cases above with the delivery caveat stated in its header, plus a
read-verified answer on the `NIM_SETVERSION` question recorded here. Both
`zig build test` lanes, `zig build test-agent`, and P1-P3 stay green.

## The answer on NIM_SETVERSION: it was missing, and that WAS the defect

`NIM_SETVERSION` was never called for either balloon, so both icons kept the
shell's default pre-5.0 ("Windows 95") behavior, under which none of the
`NIN_*` balloon notifications is sent at all. `NIN_BALLOONUSERCLICK` therefore
never arrived, and BOTH handlers behind it — click-to-focus and the update
balloon's open-the-release-page — had never once run. MSDN
([Shell_NotifyIcon](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw),
remarks): *"NIM_SETVERSION must be called every time a notification area icon
is added (NIM_ADD). It does not need to be called with NIM_MODIFY. The version
setting is not persisted once a user logs off."* and *"Regardless of the
operating system version, you can select which way the Shell should behave by
calling Shell_NotifyIcon with dwMessage set to NIM_SETVERSION."*

**Version 3, not 4.** `NOTIFYICON_VERSION_4` enables the same messages but
repacks the callback (`wparam` becomes the cursor anchor, `lparam` becomes
`(event, uID)`) and wants the Vista-sized `NOTIFYICONDATAW`; our binding
deliberately stops at the Windows 2000 layout (no `guidItem`, no
`hBalloonIcon`), and `cbSize` is that size. Version 3 turns the notifications
on while keeping the `wparam = uID` / `lparam = event` packing the handler
already decoded.

**Shape of the fix.** New `src/apprt/win32/tray_notify.zig` owns the uIDs and
the decode (`classify`, unit-tested, including that a timeout or a hover must
NOT act); `App.zig` gained `setNotifyIconVersion` and both balloon paths now
run `NIM_ADD` (without `NIF_INFO`) → `NIM_SETVERSION` → `NIM_MODIFY` (with
`NIF_INFO`). The order is load-bearing: the version has to be registered
before the balloon exists. As a side effect that also removes a latent double
balloon — the old code passed `NIF_INFO` to both `NIM_ADD` and `NIM_MODIFY`.

## Evidence

- **Routing, automated**: `test/win32/notification-click-focus.ps1` — ALL PASS
  (38 assertions) on 2026-08-07. Covers all four cases this task named, plus
  "only a click acts" with a control post, plus the version-registration log
  read-back. `-NegativeControl` fails as required (1 FAILURE / 34 passed), so
  the focus oracle is not vacuous.
- **Unit**: four `classify` tests in the win32 lane, proven live by a
  deliberate break (red on the exact test) before being restored.
- **Registration, on the real shell**: a debug build launched on the
  INTERACTIVE desktop under `GHOZTTY_PIPE_SUFFIX=-t448probe`, raising an
  OSC 777 notification from a pane, logged no `NIM_SETVERSION failed` warning
  at all — this box accepts `NOTIFYICON_VERSION` against the real
  notification area. (On the background test desktop there is no notification
  area, so `NIM_ADD` and `NIM_SETVERSION` both fail; the script asserts the
  failure has that shape rather than the "version refused while icon
  accepted" shape, which is the real-defect signature.)
- **Not covered**: a human (or real input) clicking an actual toast. Filed as
  **T572** with the recipe and the reason the first automation attempt stalled.
