# T1191 - A win32 module's unit tests can sit un-run forever because nothing checks the lane's hand-written import list

## In plain terms

Some of the tests in this project never run, and nothing says so. They compile,
they look like tests, they sit in the file next to the code they check - and
the test suite quietly skips them, so the code they cover is as untested as
code with no tests at all, while reading as covered.

## Summary

`src/apprt/win32.zig` has a hand-written `test { _ = @import("win32/X.zig"); }`
block, and reachability through THAT CHAIN of test-block imports - not the
ordinary import graph - is what pulls a win32 module's tests into the lane. A
module can be imported and used by `App.zig`, compiled by every lane, and still
have every one of its `test` blocks silently skipped.

The evidence, from T1177: `src/apprt/win32/startup_error.zig` was imported and
used by `App.zig` and carried five unit tests. A deliberately broken assertion
inside one of them was run through `zig build test -Dapp-runtime=win32` -
`-Dtest-filter` and the FULL lane both - and both went **green**. Adding one
line to the list in `win32.zig` made the identical tree go red, naming the
test. So the failure mode is not theoretical and it is not loud: the only
reason it was caught is that the test was deliberately broken first, which
nobody does routinely.

**Measure it correctly, or the number will be wrong.** A naive "has tests but
is not named in `win32.zig`'s list" grep reports ~130 files and is
MISLEADING: a listed module carries its own `test { _ = @import(...) }` block,
so plenty of unlisted files are reached transitively and do run - the same lane
run that went green on the broken assertion also reported a failure inside
`claude_plugin_migration.zig`, which is not on the list. The real question is
reachability through the test-block chain, and the sweep has to compute it.

Two things to build:

1. **A sweep that fails.** Compute the set of files reachable from the lane's
   test roots through `test { _ = @import(...) }` blocks, transitively;
   enumerate every `src/apprt/win32/*.zig` that contains a `test` block; and
   FAIL on the difference. It belongs in the `none` lane as a unit test if it
   can read the tree from there, otherwise as an acceptance script beside the
   other meta-audits (`asserted-nothing`, `body-complete`), with a negative
   control that scores red on a file removed from the chain.
2. **The backlog it finds.** The count is unknown until the sweep runs, and
   every file it names is a module whose tests have never executed. Each one
   gets its tests actually run, and anything they turn up gets filed.

Worth deciding while building it: whether the list stays hand-written with a
sweep behind it, or whether the block is generated. The list carries real
commentary today (several entries exist to force a caller-less module to
COMPILE, and say so), which a generated block would lose - so the sweep is the
recommended shape and the comments stay.

## Validation criteria

- [ ] A sweep enumerates every win32 module with tests and every module the
      lane actually reaches through test-block imports, and fails on the
      difference.
- [ ] Its negative control: removing one known-good entry from the list makes
      the sweep go red, naming that file.
- [ ] The current gap is reported as a NUMBER (how many win32 modules have
      tests that never run), recorded here.
- [ ] Every module the sweep names has its tests running and green, or a filed
      task for what they turned up.
