# T403 - No structural guard that every A-to-C reply frame type has a client dispatch arm (the T96 defect class)

## In plain terms

When the app asks a remote machine to do something and waits for the answer,
the answer only gets through if somebody remembered to write a line of code
for that particular kind of answer. Miss it and the reply arrives, is thrown
away, and the app sits there for ten seconds before telling you the thing
failed — over something that actually worked. That already happened once:
closing a remote session from the chooser's Kill button looked like a hang.
After this, the list of answers is written down in one place, the app reads
its wiring from that list, and asking for an answer that is not on the list
fails loudly the first time anyone tries it instead of quietly wasting a
timeout.

## Goals

- [x] Declare the reply set once, in `protocol.zig`, beside the opcodes
- [x] Make the declaration exhaustive, so a new opcode cannot be added without classifying it
- [x] Have the control reader dispatch FROM that set instead of a per-reply arm
- [x] Guard the other direction: an RPC whose reply is not declared fails loudly at the request end
- [x] `none`-lane coverage for both, with a demonstrated negative control

## Validation criteria

- [x] `none` lane green with the set declared and dispatched from — `zig build test -Dapp-runtime=none` exit 0, and again as part of the floor below
- [x] Negative control: demote a reply from the set and the lane goes red, naming the cause — moved `close_session_result` to the `false` half; the lane failed in `remote.connection.test.closeSession: the agent's CLOSE_SESSION_RESULT wakes the RPC (T96)` on `rpcCall`'s `assert(protocol.isRpcReply(want))` (exit code 3, `reached unreachable code`). Restored and re-run green.
- [x] Floor green: `scripts\floor-lane.ps1 -Lane all` — `lib#1=PASS none#1=PASS win32#1=PASS agent#1=PASS`, ALL LANES PASS
- [x] P1-P3 acceptance scripts ALL PASS — P1 25 assertions, P2 20, P3 16, each `ALL PASS`

## Summary

T96 was one missing `switch` arm. `Connection.handleControlInternal`
(`src/remote/connection.zig`) ends in `else => {}`, so a reply frame type with
no arm is **silently ignored** — the parked RPC never wakes, the caller burns
its whole timeout and then reports failure over an operation that in fact
succeeded. Ten reply types had arms; `close_session_result` did not, and nothing
anywhere said so.

The shape is the problem, not the instance:

- The `else => {}` is load-bearing and correct — pushes and future frame types
  must be ignorable — so it cannot simply be removed to get exhaustiveness.
- "Which frame types are RPC replies" is not declared anywhere. It lives in the
  comment column of `protocol.FrameType` (`// A→C  {…}  reply to X`) and in
  which `rpcCall` sites pass which `want`.
- So adding a new RPC means remembering, in a second file, to teach the reader
  about the reply — and forgetting is invisible until someone times a real
  round trip.

## Fix direction

Declare the reply set once, in `protocol.zig`, next to the frame types it
describes — e.g. `pub const rpc_reply_types = [_]FrameType{ .opened, .attached,
.cwd, .sessions, .relaunched, .set_layout_result, .layouts, .proc_snapshot,
.proc_kill_result, .proc_spawn_result, .close_session_result }` — then either:

- have `handleControlInternal` dispatch **from** that set (the arms that only
  call `deliverRpcReply` collapse into one), so a new reply type is wired the
  moment it is declared; or
- keep the arms and add a `none`-lane test that asserts every member of the set
  is delivered, driving each one through a mock agent and failing on the
  timeout — the exact oracle that caught T96.

Prefer the first: a test proves the arm exists today, but only the dispatch
source makes the next one impossible to forget.

## Validation

Delete any single arm (or add a new reply type without wiring it) and the lane
must go red — the T96 negative control, generalized. Today that edit is green
in every lane and only shows up as a 10-second stall on a real box.

## Outcome

Shipped as three pieces, in `src/remote/protocol.zig` and
`src/remote/connection.zig`:

1. **The declaration.** `protocol.isRpcReply(FrameType) bool` names the thirteen
   A-to-C frames a parked caller can be woken by, beside the opcodes it
   describes and beside `onDataLane`, which exists for the same reason. Its
   switch is **exhaustive** - no `else` - so a new opcode does not compile
   until somebody says which side of the line it is on.
2. **The dispatch.** `handleControlInternal` no longer carries one arm per
   reply. The arms that only called `deliverRpcReply` are gone and its `else`
   dispatches from the declaration, so classifying a new reply wires it in the
   same edit. The `else` stays load-bearing and correct: pushes and unknown
   opcodes are still ignorable there. `.sessions` keeps its own arm - one frame
   type carries both the LIST_SESSIONS reply and the roster push, told apart by
   channel.
3. **The guard that bites.** Dispatching from the declaration makes a test that
   compares the two tautological, which the first attempt at this was - the
   negative control proved it by passing. So the request end asserts instead:
   `rpcCall` now runs `assert(protocol.isRpcReply(want))`, and an RPC whose
   reply is not declared fails by name on its first call in any lane rather
   than stalling for a full timeout on a box.

Two `none`-lane tests carry it: one in `protocol.zig` pinning the membership
(the T739 test's shape), one in `connection.zig` walking every `FrameType`
through the control reader and asserting delivery matches the declaration -
which catches the one thing the dispatch source cannot, an arm like `.sessions`
that shadows the set and forgets to deliver.
