# T189 - Windows menu system: design + pure command registry and menu model

## Summary

First half of T143 (*"on the mac version, there is a way to access the menu
bar. On windows, there's none."*), split out because the whole task - host
design, a ~60-item tree, an HMENU host with dispatch, and an on-box script
that walks every item - does not fit one context.

This half decides the HOST and lands the pure model plus the refactor that
makes a second command surface safe to add: `commands.zig`, the ONE registry
the command palette and the menu both read. T190 builds the GUI host on top of
it.

## Design

### The host: a tab-strip button, not `SetMenu`

The tree is rendered as a nested `HMENU` opened from a `≡` button at the right
end of the tab strip (T190 builds it), NOT installed as a classic menu bar
with `SetMenu`. Three reasons, in order of weight:

1. **Dark mode.** The classic menu BAR is drawn by the system frame and
   ignores the uxtheme dark-mode ordinals - only popup menus honor them, which
   is the whole T79 mechanism. A `SetMenu` bar would be a light gray strip
   pinned above a dark terminal on every dark theme, which is exactly the
   "looks like bare controls" failure the standing quality bar names.
2. **Layout.** A `SetMenu` bar lives outside the client area, and every layout
   path in `Window.zig` is written against "client top == tab strip". Moving
   that origin touches split geometry, the T101 banner inset, and the hero
   carousel, for no user-visible gain.
3. **Convention.** Windows' own modern terminals put this menu behind a
   caption/tab-strip button - Windows Terminal's `⌄`, VS Code's and Edge's
   hamburger. A 1995 menu bar would look older than the app, not more native.

Mnemonics (`&`) and accelerator hints (`\t`) both work in a popup menu, so the
keyboard affordances of a real menu bar survive the move. T190 also gives the
button F10/Alt activation.

### The tree

`menu_bar.root` mirrors macOS `MainMenu.xib` (File / Edit / View / Window /
Help) item for item wherever the command exists on Windows. Named deviations,
each with its reason in the source:

- **Exit lives in File**, not an application menu - Windows has no application
  menu. Its label becomes "E&xit (keep sessions)" when session-persistence is
  on (T89e).
- **Settings / Reload Configuration sit at the foot of the root popup**, which
  is where Windows Terminal, VS Code and Edge put them. They are macOS
  application-menu items with nowhere else to go.
- **Set Pane Banner…** is a Windows row (T129): the Mac chord is cmd+r, the
  Windows chord had to differ, and naming it nowhere is what made a working
  feature read as broken.
- **Swap Split** is a Windows submenu beside Select Split - the swap commands
  are real here (T18/T61) and had only the palette.
- **Previous/Next/Last Tab** are Windows rows under Window; macOS gets tab
  cycling from the system's own Window menu.
- **"Zoom" is "Maximize"**, the Windows word for the same thing.

Mac rows that are deliberately absent because the command does not exist or
does nothing on Windows: Undo/Redo (`NSUndoManager`), Services / Hide Others /
Show All / Bring All to Front (AppKit), Secure Keyboard Entry, Make Ghoztty the
Default Terminal, Terminal Inspector (`inspector` is a no-op on win32 today),
**Paste Selection** (win32 `supportsClipboard` returns false for `.selection`,
so there is no selection clipboard to paste - see T156), and **Float on Top**
(no win32 handler at all - filed as **T191**).

### One command list, two surfaces

The palette owned a private `palette_entries` array inside `Surface.zig`. A
menu is a second surface over the same commands, and two hand-maintained lists
of the same thing drift - which already cost us T57, where fork actions had
keybinds but never reached the palette's parallel list, so hero mode was
undiscoverable while working perfectly.

So: `commands.zig` owns the list. Each entry has a stable `Id`, a palette
name, an action, and a `Kind` (`binding` / `remote` / `about` / `claude` /
`help`). Menu items carry a `commands.Id` and their own title - titles are
allowed to differ ("Toggle Read-Only" reads right in a searchable palette,
"Terminal Read-only" reads right as a checkable menu row), but the COMMAND
cannot.

Anti-drift is a test, not a habit: `everyCommandIsPlacedOrOmitted` fails the
build unless each registry command is either in the tree or in
`menu_bar.omitted` with a written reason. Adding a command now forces a
decision instead of silently landing in one surface only.

Dispatch is one function - `Surface.performCommand(id)` - so a command cannot
behave one way from a menu and another way from the palette.

## Outcome (2026-07-30) - DONE

What landed:

- **`src/apprt/win32/commands.zig`** (new, pure): the registry - 70 commands,
  in palette display order, with `Kind`, `get`/`index`, and tests that every
  `Id` appears exactly once, names are unique, only local kinds carry a
  placeholder action, and `quit` is the only `quit_keep`.
- **`src/apprt/win32/menu_bar.zig`** (new, pure): the tree, `State`,
  `flags()` (gray-not-hide for rows whose target may not exist; the read-only
  check), `title()` (the T89e Exit flip), and the `menuCommandId` mapping
  (`@intFromEnum + 1`, so `TPM_RETURNCMD`'s 0 stays "dismissed"). Tests cover
  coverage-or-omission, no command twice, root shape, per-level mnemonic
  uniqueness, id round-trip, and the state gates.
- **`Surface.zig`**: `palette_entries` IS `commands.registry` now; the
  local-kind special cases in `executePaletteSelection` collapsed into the new
  `performCommand`.
- **`App.openUrl`**: extracted from the `open_url` action so the Help command
  (which has no binding) opens the docs through the same `ShellExecuteW` path.

Because the palette renders the registry, commands that previously had a
keybind and no palette row appeared in the palette for free: Close All
Windows, Show/Hide All Terminals, Command Palette, Find Next/Previous, Hide
Find Bar, Jump to Selection, Move Divider (4), Check for Updates…, Ghoztty
Help.

**Validation.** Both test lanes + `zig build test-agent` + P1-P3 green. New
`test/win32/command-registry.ps1` **ALL PASS (19) x3**, asserting by OUTCOME
(a row that is absent cannot dispatch, so an outcome proves presence too):

- **A** a pre-existing palette command still dispatches after the refactor
  ("New Tab" -> 2 tabs in `+list --json`),
- **B** negative control: a filter matching nothing dispatches NOTHING (tab
  count unmoved), and - verified against `handlePaletteKey` rather than
  assumed - the palette stays OPEN so the user can fix the filter; Escape
  closes it,
- **C** a command that reached the palette only because of the shared registry
  dispatches ("Show/Hide All Terminals" -> the window is hidden, not
  destroyed).

**Negative control, run for real:** renaming that one registry row and
rebuilding made the script fail **exactly one assertion - C's dispatch - and
nothing else** (18 passed / 1 failed), then restoring it went back to 19/19.
So section C measures the registry, not the weather.

Two things the work turned up, both filed rather than fixed here: **T191**
(`toggle_window_float_on_top` has no win32 handler, so Mac's "Float on Top"
row cannot exist yet) and **T192** (`zig build` fails its install step with
`AccessDenied` on `ghoztty-agent.exe` while a repo-lineage agent is running -
a FALSE build failure in the dev loop, found when the negative-control build
reported exit 1 while still shipping a new `ghoztty.exe`).

Next: **T190** - the tab-strip button, the HMENU host with accelerator labels
from the live keybind set, F10/Alt activation, and `menu-bar.ps1`.
