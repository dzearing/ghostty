# T634 - Viewer feedback: the composer toolbar chrome (pill, buttons, open/close, geometry)

## In plain terms

Pressing the feedback button should slide open a small message box under the
viewer's navigation bar — a rounded input with a button to attach a screenshot
and a button to send. This task builds that box and everything about how it
appears, sizes itself and goes away. Typing into it and sending it are the
next two tasks; what lands here is the thing you can see and open and close.

## Goals

- [x] A pure geometry module (`viewer_feedback_layout.zig`) asserted at
      1.0/1.25/1.5/2.0: the pill, its two circular actions, the footer, and
      the band height the pane insets by.
- [x] An owner-painted composer window that opens and closes from the feedback
      button, with the nav bar pinned open while it is up.
- [x] The page inset tracks the composer's height BOTH ways — a deleted line
      gives the space back.
- [x] Escape closes and Ctrl+Enter sends, both pane-scoped: a focused terminal
      keeps its own meaning for the same two chords.
- [x] The composer's text and open flag live on the PANE, so contents survive
      closing and reopening the toolbar.

## Summary

Second of the T384 split. The composer's **chrome**: the toolbar strip below
the nav bar, the pill that grows with its content (one line up to ~6), the two
circular buttons inside the pill's trailing edge (`+` screenshot, `↑` send),
and the open/close lifecycle. No text model, no images, no report — those are
T635/T636/T637.

Mac sites: `ViewerFeedbackBar.swift` (the toolbar host and its layout) and the
chrome half of `ViewerFeedbackComposer.swift`; layout is pinned on Mac by
`ViewerFeedbackBarLayoutTests` / `ViewerFeedbackChromeLayoutTests`, and the
win32 equivalent is a pure geometry module with the same coverage.

## Details

Behavior to match:

- The feedback button **toggles** the composer. The nav bar **stays pinned
  open** while the composer is open — it cannot auto-hide out from under it.
- `Escape` closes the composer. `Ctrl+Enter` sends (the win32 spelling of
  Mac's `Cmd-Enter`); plain `Enter` inserts a newline. Register these with the
  pane-scoped accelerator table (`viewer_accel.zig`), under the same
  override-only-while-the-viewer-has-focus rule as Ctrl+R / Ctrl+D: a focused
  terminal keeps its own bindings.
- **Composer state lives on the pane, not on the toolbar** — Mac is explicit
  that contents survive toggling the toolbar closed and open again. On win32
  the natural mistake is to own the buffer in the child window and destroy it
  with the window; own it in `ViewerPane` and let the chrome render it.
- The pill **grows with its content** and stops at ~6 lines, after which it
  scrolls. The pane's WebView2 host and the terminal below reflow to the
  toolbar's height the way they already do for the nav bar.

Geometry belongs in a pure module (`viewer_feedback_layout.zig`, sibling of
`viewer_nav_layout.zig`) and is asserted at 1.0, 1.25, 1.5 and 2.0. The win32
design system applies in full: 4 DIP spacing scale, >= 4 DIP between painted
edges, one icon-button size with the standard rest/hover/pressed/disabled/
focused states, radius scale, 3:1 contrast for glyphs, filled-shape glyphs
(never `LineTo` strokes) for the `+` and `↑`.

Open question for the turn that takes this: whether the composer is its own
child HWND or is painted into the pane's existing chrome surface. Whichever it
is, the caret and IME must work (see T635's control decision) and the pill must
not steal focus from the page when it is merely open.

**Answered: its own child HWND**, a sibling of `ViewerNavBar` under the pane's
host window. The two reasons are the ones that decided the nav bar as well —
the composer overlaps nothing, so a sibling window needs no z-order
negotiation with the TOC card (its band simply starts where the composer's
ends, which is what Mac has to arrange by layer order), and a real window is
what makes the acceptance script able to read the composer's class,
visibility and rect on a desktop where nothing can be screenshotted. It is
created hidden in `ensureNav` rather than on first open for a concrete
reason: the composer is edited from its own WndProc, which has no allocator
to reach for.

`SW_SHOWNA`, not `SW_SHOW`, so merely opening it does not yank activation
from the page; focus is given deliberately, by the pane, on the click that
opened it, and handed back to the page on close.

**What this task does NOT decide is the text control** — D43 is still open, so
the editing surface here is deliberately the smallest honest thing (a plain
UTF-8 buffer, `WM_CHAR` append, backspace, newline). No caret navigation, no
selection, no IME. T635 replaces that path with whatever D43 answers, and the
geometry, the paint, the open/close lifecycle and the pane's reflow all
survive the swap because none of them touch it.

**Filed while here:** D45 (should the pill be a capsule, when the design
system says an input field is 4 DIP — resolved as a documented exception) and
T640 (the two circular actions need tooltips and keyboard reach).

## Validation criteria

- [x] Unit tests (none lane): composer layout at 1.0/1.25/1.5/2.0 — pill
      bounds, both circular buttons inside the trailing edge with >= 4 DIP
      clearances, height for 1..6+ lines, and the toolbar height the pane
      reflows to.
      *How: seven tests in `viewer_feedback_layout.zig`, all four scales —
      band/pill/button clearances, monotonic growth 1..6 and a hard stop past
      it, the collapsed capsule and its pinned radius, the no-footer band, a
      never-inverted narrow pane, and hit-box (not paint) hit testing. Green in
      `zig build test -Dapp-runtime=none`. The `send` glyph rides the existing
      whole-set symmetry/clearance sweeps in `icon_button.zig`, and
      `viewer_accel.composerChord` has its own test (plain Enter is a NEWLINE,
      never a send).*
- [x] On-box acceptance script: the feedback button opens and closes the
      composer; the nav bar stays visible while it is open; Escape closes it;
      the WebView2 content area shrinks and restores by the toolbar height.
      *How: `test/win32/viewer-feedback.ps1`, ALL PASS (37). The content
      assertion reads the `Chrome_WidgetWin_0` widget's own top edge — the
      thing `setBounds` actually moves — so it is the page's real inset, not a
      proxy: 454 → 594 on open, → 628 on a third line, → 605 on deleting one,
      → 499 (the nav bar's own bottom) on close.*
- [x] On-box acceptance: text typed into the composer is still there after
      closing and re-opening the toolbar (state lives on the pane).
      *How: same script. The reopened composer is still the height its text
      makes it (106 px, not the 95 px empty band), and a Ctrl+Enter after the
      round trip reports `len=7` — the exact byte count typed before the
      close.*
- [x] On-box acceptance: with a terminal pane focused, Ctrl+Enter and Escape
      do their normal terminal thing — the composer bindings are pane-scoped.
      *How: same script's section H — both chords delivered to a terminal
      surface, then asserted that neither the last send nor the composer's
      open/closed state moved.*
