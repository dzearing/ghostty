# T348 - release-windows.yml has never been executed by GitHub - verify at the first real release

## Summary

T38 landed the workflow that publishes the Windows MSI + portable ZIP on
every `vX.Y.Z` tag push. Everything it *runs* was validated on box (the
cross-build with the workflow's exact flags, in a debian container with the
CI zig; the packaging; the whole chain through the on-box script's dry run)
- but **GitHub has never executed the job itself**. Two reasons it could not
be:

- `workflow_dispatch` is only offered once the workflow file is on the
  **default branch**. T38 landed on `users/dzearing/windows-amd64`, so
  `gh workflow run release-windows.yml` answers "workflow does not exist"
  until the branch merges to `main`.
- The only other trigger is a real `vX.Y.Z` tag push, which would also fire
  `release.yml` and publish a real macOS release. Not something to do for a
  test.

So the untested surface is the conventional part of the job - checkout,
`mlugg/setup-zig@v2` resolving 0.15.2 from `build.zig.zon`,
`apt-get install -y msitools wixl`, `actions/upload-artifact`, and the
`gh release create win-v<version>` call - plus one thing worth watching:
a single container run of the same cross-build **terminated unexpectedly**
mid-link (no diagnostic, agent exe) while the box was simultaneously running
a native ReleaseFast build, and passed cleanly on a retry with nothing else
running. That reads like resource contention rather than a code defect, but
"compiler died with no message" on a 4-core runner is exactly the shape of a
CI flake, so it is on record here rather than nowhere.

## In plain terms

The machinery that turns a version tag into the Windows installer and ZIP on
the download page had never actually been run by GitHub - everything about it
had only been proved on this desk. Until a real run happened, nobody could say
whether a Windows release would appear at all when the next version shipped.
It has now run for real, twice successfully, and the files it published were
downloaded and read back here rather than taken on trust. What that read-back
found is a separate problem, filed on its own.

## Details

Do this the cheap way, in order:

1. **The moment the branch reaches `main`**, run the workflow without
   publishing anything:

   ```
   gh workflow run release-windows.yml -f version=1.28.0 -f publish=false
   gh run watch --repo dzearing/ghoztty
   ```

   `publish=false` skips `gh release create` entirely and leaves the MSI +
   ZIP as workflow artifacts. Download them and check the two names carry
   version + arch and that the ZIP has `Ghoztty/ghoztty.exe`,
   `Ghoztty/ghoztty-agent.exe` and `Ghoztty/share/terminfo/ghostty.terminfo`
   (`test\win32\release-artifacts.ps1` section B is the same set of checks
   against a locally built ZIP).
2. **At the next real release**, confirm the pair actually published:
   `gh release view win-v<version> --json assets` lists both, and
   `gh release view v<version>` lists the DMG at the same version.
3. If the job fails on apt package names, note that Debian's msitools source
   package produces `msitools` (msiinfo/msibuild) and `wixl` as SEPARATE
   binary packages; both are installed for that reason.

Whatever the first run turns up, fold the fix back into
`dist/windows-installer/build-release-artifacts.sh` rather than the YAML
where possible - the YAML is deliberately thin so that the on-box path and
CI stay the same code.

*Validation:* a `win-v<version>` release exists whose two assets match the
macOS release's version, produced by a GitHub run rather than by hand, and
`test\win32\release-artifacts.ps1` still ALL PASS.

## What the first real runs showed (2026-08-21)

The premise expired without anyone re-reading this file: the branch never had
to reach `main`, because the workflow's other trigger is a `win-v*` tag push,
and T577/T895 made those a routine part of shipping. `Release (Windows)`
(workflow id 329724228) has six runs on record:

- `win-v1.31.0`, 2026-08-08: four failures then a success. Every failure was
  the msitools build (its submodule, its tag history, a too-old meson), fixed
  inside that session; none was the conventional GitHub surface this task was
  written to doubt, and none was the compiler-death shape the summary flags.
- `win-v1.33.0`, run **32129308721**, 2026-08-18, **success in 19m47s** -
  T895's release. That is the run whose output the world downloads.

Read back from GitHub rather than inferred from the green tick:

- `win-v1.33.0` carries exactly two assets - `Ghoztty-1.33.0-x64.msi`
  (21,583,360 bytes) and `Ghoztty-portable-1.33.0-x64.zip` (20,849,765 bytes).
  Both names carry version and arch.
- The macOS `v1.33.0` release exists at the same version, so the pair is in
  step (which is `scripts\check-release-parity.ps1`'s standing assertion).
- The published ZIP was downloaded to this box: its SHA-256 matches the digest
  GitHub records for the asset (`9279bf35...f52ee`), it has 565 entries under a
  single `Ghoztty/` root, no `.pdb` and no `.bak*`, and it contains
  `Ghoztty/ghoztty.exe`, `Ghoztty/ghoztty-agent.exe` and
  `Ghoztty/share/terminfo/ghostty.terminfo` - the three files step 1 names.

**The gap the read-back found:** neither artifact carries `ghoztty.com`, the
console-subsystem twin T245 added *after* the packaging scripts were written.
Without it a bare `ghoztty` from PowerShell resolves to a GUI binary the shell
does not wait for, so every CLI verb is silent for anyone who installed from
the download page. Filed as **T1052** (P1) rather than fixed here: it needs
both packaging scripts, the MSI File-table version patch, harness checks, and
a Docker-gated MSI validation - a task, not a footnote. That is precisely the
"fold the fix back into the packaging scripts" outcome this task was watching
for.
