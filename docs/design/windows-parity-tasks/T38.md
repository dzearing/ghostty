# T38 — Windows build in the release process (Phase H)

## Summary

Windows build in the release process — fold `publish-windows-release.ps1` (gnu-target ReleaseFast, per T100) into the standard release flow so every release produces the Windows zip + MSI alongside the Mac artifacts; installer/zip filenames MUST carry version + arch (e.g. `Ghoztty-<version>-x64.msi` / `Ghoztty-portable-<version>-x64.zip` — match the existing win-vX.Y.Z release asset convention from T24); agent exe included (T89h)

## Details

User directive 2026-07-13: when we release, the Windows build ships too.
Extend the release flow (currently Mac-centric; see `dist/` and the T24
release-channel work) to build/stage/publish the Windows artifacts (MSI
once T23 lands, portable ZIP meanwhile) alongside the Mac release —
same version, same tag, one process.

*Validation:* a release run produces and publishes both platforms'
artifacts with matching versions.

## What landed (2026-08-02)

The gap was measurable before it was fixed: the macOS channel was at
**v1.28.0** and the Windows channel at **win-v1.4.1** — 24 releases in which
a Windows user saw nothing. The cause is structural, not neglect: the macOS
release is a **tag push** (`release.yml`, `on: push tags v*`, macos-15
runner) and the Windows release was a **hand-run script on this box**. A
process that requires a second machine and a human runs when someone
remembers.

So the Windows half is now a workflow on the SAME trigger:

- **`.github/workflows/release-windows.yml`** — `ubuntu-latest`,
  cross-compiles for `x86_64-windows-gnu`, builds MSI + portable ZIP with
  wixl, and publishes them to a `win-v<version>` release
  (`--latest=false`). Nothing here needs a Windows runner.
- **`dist/windows-installer/build-release-artifacts.sh`** — the one
  definition of *what a Windows release ships*. Both publishers call it, so
  CI and a hand publish cannot produce different sets. It builds with the
  release stamps (`-Dversion-string=<semver>+<hash>`,
  `-Dwindows-update-check=true`, `-Dagent-semver`, `-Dwindows-file-version`,
  and now `-Dstrip=false` so a shipped build's crash dumps are debuggable —
  the local delivery build has carried that since T48 and the published one
  did not), then verifies the exe **embeds** the release semver by scanning
  the binary, which works on a Linux runner where the exe cannot be run.
- **`dist/windows-installer/build-portable-zip.sh`** — new artifact. Same
  payload as the MSI (exe + agent + `share/`, T89h) under a single
  `Ghoztty/` root, plus a versioned READ-ME-FIRST. It validates its own
  output (required entries present, no entry outside `Ghoztty/`, no corrupt
  member) rather than trusting that the write succeeded.
- **`scripts/publish-windows-release.ps1`** — still the on-box path, now
  packaging through the shared script, uploading both artifacts, and
  defaulting `-Version` to the newest `vX.Y.Z` tag so "same version" is the
  default rather than a number a human types.
- **`.claude/commands/release.md`** — Steps 3/5/8 now cover both platforms.

### Three decisions worth keeping

**A separate workflow, not a job in `release.yml`.** The macOS job is a
signing/notarization pipeline; a Windows failure must not be able to
interrupt it, and the two publish to different releases. The cost is that
the trigger can drift, so `release-artifacts.ps1` A2 asserts the two tag
patterns are IDENTICAL — a stricter pattern here is how "every release ships
Windows" quietly becomes "most releases do".

**The `win-v` tag stays.** T38's Details said "same tag"; that is wrong now
and the reason is a contract with already-shipped binaries: installed
Windows builds find updates by scanning the releases list for the newest
`win-v` tag (`update_check.zig:16`). Publishing the Windows assets onto the
`vX.Y.Z` release instead would make every installed build blind to updates
forever. Same VERSION, own tag. A2/A5/A6 assert the tag the workflow
publishes is the prefix the app scans for.

**One definition of the FILEVERSION rule.** The `yy.m.d.NN` formula existed
twice (build-msi.sh, and a PowerShell restatement in the publish script) and
both copies were live. `build-msi.sh --print-file-version` is now the single
source and the publish script asks for it. This is the T257 lesson applied
before it could cost anything.

### Found on the way: the publish script could not run at all

`publish-windows-release.ps1` carried a UTF-8 em dash in a BOM-less file.
PS 5.1 reads a BOM-less .ps1 as ANSI, where the em dash's last byte (0x94)
is a cp1252 **smart quote** — which CLOSES the string. The script was a
parse error under `powershell -File` from the day it was written (win-v1.4.1
must have been published through pwsh 7 or a bash hop). A17/A16 are the
gate: ASCII-only, and it parses.

## Evidence (2026-08-02)

- `scripts\publish-windows-release.ps1 -DryRun -BuildNum 3` — **exit 0**,
  full path: `-Version` defaulted to 1.28.0 from the newest Mac tag,
  FILEVERSION `26.8.2.3` read from build-msi.sh, native ReleaseFast
  cross-build, `exe reports 1.28.0+0bfbe4262`, then in-container
  `==> exe embeds 1.28.0+0bfbe4262`, `Ghoztty-1.28.0-x64.msi` (19.6 MB) and
  `Ghoztty-portable-1.28.0-x64.zip` (18.9 MB) — **both names carry version +
  arch, both at the same version** — and it stopped at
  `DRY RUN: skipping gh release create win-v1.28.0`.
- `test\win32\release-artifacts.ps1` — **ALL PASS** (28 assertions:
  A trigger/tag/name/parse invariants, B live packaging under Docker,
  C the documented process). `-Full` adds the dry-run publish (D1-D6), off
  by default because it runs a multi-minute ReleaseFast build.
- **The CI job's own build path, proven on Linux**: a debian container
  (the msitools image + zig 0.15.2 for linux) ran the exact flag set the
  workflow passes and produced `ghoztty.exe` (30M) + `ghoztty-agent.exe`
  (3.2M) for `x86_64-windows-gnu`. This is the step that could not be
  assumed — everything else in the job is checkout/apt/upload.
- Floor: both `zig build test` lanes + `test-agent` + P1-P3.
