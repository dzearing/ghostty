# T659 - Verify the reconciled +send-keys submission semantics on macOS against a real Claude Code composer

## In plain terms

The code that decides how an agent's typed prompt gets submitted was just
reconciled between the two seats. It was proven correct on Windows; someone
with a Mac needs to confirm the same prompt still submits there, because the
file is shared and a regression would break automation on both.

## Summary

T604 reconciled `src/cli/send_keys.zig`: this branch's bracketed-paste run
framing, `--keys-file=` and motion-based `--when-idle` now sit under main's
submission semantics from `a7f7476e1` (trailing-newline peel, `--enter`,
unknown-flag hard error, `Split`-returning `resolveArgument`).

`src/cli/send_keys.zig` is SHARED CORE, so the merged file reaches macOS on
merge-back with no Mac-side change required. What is required is validation
the win seat cannot perform: the peel's whole point is how a real TUI reads
the bytes, and the Mac's oracle is a real Claude Code composer.

Two things this branch has that main does not, which the Mac gains on
merge-back and should be sanity-checked rather than assumed:

- **motion-based `--when-idle`** (T46) — marker OR tail-unchanged-across-~1s,
  vs main's marker-only. Strictly a superset, but it polls differently.
- **`--keys-file=`** (T210), including its deliberate exemption from the
  trailing-newline peel (decision D52).

## Validation criteria

- [ ] `+send-keys --target=t "prompt\n"` submits into a real Claude Code
      composer on macOS (the peel path).
- [ ] `--enter` and a separate `Enter` argument each submit once; using two
      submits twice (documented, not a bug).
- [ ] A multi-line paste keeps its interior newline and submits once.
- [ ] `--keys-file=p.txt` with a trailing newline in the file does NOT submit
      on its own; `--keys-file=p.txt Enter` does.
- [ ] An unknown `--flag` exits 1 with the submit-spellings message instead of
      being typed into the pane.
- [ ] `zig build test -Dapp-runtime=none` green on macOS.
