# T524 - The relaunch guard dies WITH the app (job-object kill), so upgrade confirm still never brings Ghoztty back

## In plain terms

Clicking the mandatory agent-upgrade confirmation still shuts Ghoztty down
without bringing it back (user report 2026-08-06, fourth occurrence of the
T229/T421 shape). T421's relaunch guard - the supervisor that is supposed to
restart the app - arms correctly and then dies in the same instant the app
does, before executing a single instruction. It has never once fired in
production.

## Evidence (2026-08-06, all VERIFIED on-box)

- `%LOCALAPPDATA%\ghoztty\ghoztty.log`: four `relaunch guard: ARMED` events
  (guard pids 20196, 29336, 29072, 25868). In every one, ARMED is the ONLY
  guard line - `watching app pid` (the guard's FIRST statement in `run()`)
  never appears. The guard process never reached `main`.
- Release logging is a per-call atomic append that works from any process:
  proved by running the installed release exe in guard mode by hand
  (`GHOZTTY_RELAUNCH_GUARD=<dummy-pid>|<marker>|notepad.exe`) - it logged
  `watching`, detected the dummy's death, logged `ENDED during the agent
  refresh`, relaunched notepad, deleted the marker. **The guard mechanism is
  100% functional in isolation on the exact production binary (4c7de3afe).**
- `agent-refresh.marker` was still present this morning, hours after the
  incident - the refresh never completed and no guard ever cleaned up.
- The only app boot after the user's confirm is pid 31200 at 08:09:29 - the
  user's manual Start-menu launch.
- **The app runs inside a Windows Job object** (IsProcessInJob = true for the
  manually-launched pid 31200). A pane-tree shell (descendant of the agent)
  reports its own job as `LimitFlags = 0x3C00`: KILL_ON_JOB_CLOSE +
  BREAKAWAY_OK + SILENT_BREAKAWAY_OK. Kill-on-close jobs are all over this
  environment (ConPTY/tool harness/launchers).

## Why the guard dies

A child process joins its parent's job by default. The guard is spawned ~4 log
lines (milliseconds) before the app dies; a job-object teardown
(KILL_ON_JOB_CLOSE when the last handle closes, or an explicit
TerminateJobObject / tree kill) kills every member simultaneously - including
a child still in DLL load. `DETACHED_PROCESS` does not escape a job. This is
the only Windows mechanism consistent with all four incidents: spawn
succeeded, zero guard output, marker left behind.

This also feeds **T426**: if the app and the (old) agent share a
kill-on-close job whose last handle lives in the agent process, then
`TerminateProcess(agent)` tears down the job and kills the app mid-call -
exactly the observed clean death between `terminating agent pid N` and the
never-logged `terminate returned`, with no WER record.

## Fix (implemented: three tiers, because breakaway alone is REFUSED here)

Measured while implementing (2026-08-06): `CREATE_BREAKAWAY_FROM_JOB` fails
with **ACCESS_DENIED in this box's pane-shell job chain** - an outer job
forbids breakaway even though the inner one advertises BREAKAWAY_OK, and
nested-job breakaway requires every job in the chain to permit it. A
breakaway-only fix would have logged a warning and changed nothing. So
`spawnEscapingJob` (`relaunch_guard.zig`) escalates:

1. `CREATE_BREAKAWAY_FROM_JOB` - the clean escape, no-op for jobless callers.
2. **Shell-parent hop**: `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` pointing at
   explorer (GetShellWindow -> OpenProcess(PROCESS_CREATE_PROCESS)). Job
   membership follows the ACTUAL parent used for inheritance, so the child
   lands in the shell's job context - no breakaway permission involved. The
   environment (which carries the guard spec) is passed EXPLICITLY, because a
   spoofed parent would otherwise donate the SHELL's environment.
3. Inside the job, loudly - degraded, never absent.

Both spawn sites use it: `armImpl` (app -> guard) and `relaunch` (guard ->
replacement app), so the replacement escapes a jailed guard's job too.

Still open for T426: the same treatment for the LocalAgent spawn (a daemon
meant to outlive the app must never sit in anyone's killable job), plus
logging job membership of app+agent at refresh time to confirm the
shared-job death mechanism.

## Validation

- `test\win32\relaunch-guard.ps1` arm F (new): the GUARD is jailed in a
  kill-on-close job, relaunches a dead app from inside it, and the
  replacement is asserted OUTSIDE the job (direct IsProcessInJob probe) and
  SURVIVES the job's teardown. Fails pre-fix (the replacement inherits the
  job and TerminateJobObject kills it).
- Suite hardened on the way past: it now counts only ITS OWN processes (bare
  exe or `--title=t421*/t524*`) - a parallel session's harness was driving
  the same zig-out exe mid-run and its `+verb` one-shots read as strays; and
  `Wait-NewApp` excludes the guard pid, which is the same bare exe and used
  to be returned as the "relaunched app" in the instant before it exited.
- Real-world: next upgrade confirm on this box brings the windows back with no
  manual launch; the log shows `watching` -> `ENDED` -> `relaunched` (via
  which tier).
