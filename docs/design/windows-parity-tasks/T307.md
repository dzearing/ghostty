# T307 - A panel open when the accent changes never repaints: only Window handles WM_DWMCOLORIZATIONCOLORCHANGED

## In plain terms

Windows lets you pick an accent color, and Ghoztty paints parts of its own
chrome in it. Change the accent while a Ghoztty panel or window is on screen
and most of it keeps showing the old color — the strip across the top updates,
but the thumbnail carousel's selection border, the highlighted row in a
document's contents card, and the text boxes inside the Activity Monitor and
the machine chooser all stay the previous accent until you close and reopen
them. After this, everything on screen changes color the moment you pick the
new accent.

## Goals

- [x] One shared reaction to a system color change, instead of a handler per
      window that each invalidates a different amount
- [x] The window's whole client area repaints, not just the chrome row the old
      code was clipped to
- [x] Child windows repaint too — they never receive the notification
      themselves, so their owner has to redraw them (correct by reading; not
      scoreable on this harness, see T585)
- [x] An unrelated settings broadcast does not cost a full window repaint
- [x] The acceptance script proves the LIVE update, with the panel left open
      across the notification

## Summary

T305 wired the accent-change notification into `Window.zig` only. Every OTHER
window that paints the accent — the Activity Monitor, the machine chooser, the
hero carousel's own HWND-hosted tiles — reads `system_colors.accentCached()` at
paint time but has nothing that invalidates IT, so a panel that is already open
when the user picks a new accent keeps painting the old one until something
else happens to repaint it.

Found by T305's own acceptance script, which had to CLOSE and REOPEN the panel
around the notification to see the new color. That close/reopen is the
workaround standing in for this task.

## What is true at HEAD (VERIFIED by reading, 2026-08-01)

- `system_colors.accentCached()` / `invalidate()` are process-global, so
  dropping the cache from any window is enough to fix the VALUE.
- `Window.wndProc` handles `WM_DWMCOLORIZATIONCOLORCHANGED` and calls
  `system_colors.invalidate()` + `Window.invalidateChrome()`.
- `ActivityMonitor.zig`, `MachineChooser.zig` and `HeroCarousel.zig` have no
  handler for it at all. DWM broadcasts the message to every top-level window,
  so the panels DO receive it — they just fall through to `DefWindowProc`.

## Fix

Each accent-painting top-level window handles `WM_DWMCOLORIZATIONCOLORCHANGED`
by invalidating itself. The cache drop should stay idempotent and stay in one
place (`system_colors.invalidate()`); what each window adds is its own
`InvalidateRect`, since only it knows which of its regions carry the accent.

Consider whether the message deserves a shared helper next to
`Window.invalidateChrome` rather than three near-identical handlers — the same
call the design system makes about layout constants.

## What was actually wrong at HEAD (VERIFIED by reading, 2026-08-07)

The Summary above was written on 2026-08-01 and its list is out of date: T308
(778c44505, this morning) gave `ActivityMonitor` and `MachineChooser` their own
`WM_SETTINGCHANGE` / `WM_DWMCOLORIZATIONCOLORCHANGED` arms, so both panels
already live-updated. What was left:

- `Window.invalidateChrome` clipped the invalid rect to `captionHeight() +
  tabBarHeight()`, so nothing the window paints BELOW the strip was invalidated
  at all.
- **Child HWNDs never receive the broadcast** - it reaches top-level windows
  only - so their owner is the only place their repaint can come from, and the
  owner was invalidating a rect that does not contain them. That covers the
  viewer's contents card (`ViewerTOCPanel`, whose active row is filled with the
  raw accent) and the panels' own EDIT/STATIC children, whose brushes come from
  a `WM_CTLCOLOR*` that is only sent when the child repaints.
- `HeroCarousel` is NOT a separate window - it paints into `Window`'s DC inside
  `paintWindow` - so it needed the wider rect, not a handler of its own.

## Fix as landed

One shared helper, per the "consider a shared helper" note above:

- `system_colors.repaintForColorChange(hwnd)` - drop the process-global accent
  cache, then `RedrawWindow(RDW_INVALIDATE | RDW_ERASE | RDW_ALLCHILDREN)`.
  `Window`, `ActivityMonitor` and `MachineChooser` all call it; the three
  near-identical `InvalidateRect` bodies are gone.
- `system_colors.isColorSettingChange(lparam)` - because the redraw is now
  whole-window, `WM_SETTINGCHANGE` is filtered to the `ImmersiveColorSet`
  broadcast. Without it every environment or policy change would repaint every
  pane, and Ghoztty itself sends one from `PathInstaller`. A null lparam counts
  as a color change: the parameter is optional, and one extra repaint beats
  chrome that stays stale.
- `w32.lstrcmpiW` added - the canonical reader for that lparam precisely
  because it guards the dereference with SEH, so a sender that passes a bad
  pointer costs a mismatch rather than an access violation.
- `Window.invalidateChrome` survives as the narrow path for a non-color
  `WM_SETTINGCHANGE`.

## Evidence, including what could NOT be measured

The two candidate oracles for the child half, both built and both measured to
be undiscriminating on the win32 harness. Written down because the cost of
re-deriving them is two builds and two eight-minute runs:

- **The hero carousel's accent-outlined selected tile.** Built as section E,
  passed - and then passed AGAIN with `Window`'s handler reverted to
  `invalidateChrome()`. `Window`'s hero thumbnail refresh timer repaints the
  band every 150ms unprompted, so it picks the new accent up from the cache
  drop alone. A surface that repaints on its own cannot score whether anything
  invalidated it. (It also is not a child.)
- **The viewer's contents card (`GhozttyViewerTOC`).** The right shape, and it
  appears and captures fine on the test desktop - but its accent fill is gated
  on `isEmphasized()`, i.e. `GetForegroundWindow`, and `lib/TestDesktop.ps1`'s
  own header records that a background desktop has no foreground window at all.
  Measured: `E1 the card's selected row is filled with #ff0000` FAILS on a
  correct build.

Section E was removed rather than left passing-both-ways; both findings are now
in `chrome-theme.ps1`'s header under "WHAT THIS SCRIPT CANNOT CLAIM", and the
gap is **T585**.

Also fixed in passing, because it blocked this task's own validation:
`chrome-theme.ps1` called `Test-ExeIsDebugBuild`, a function that exists nowhere
in the repo (introduced by T308), so the script died on its first line. Replaced
with the two `lib/BuildMode.ps1` helpers that already existed. The process gap
behind it - nothing catches an acceptance script that cannot start - is **T586**.
