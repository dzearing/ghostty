# T389 - Viewer file injection holds three copies of the file at once (bytes + JS literal + UTF-16)

## Summary

`ViewerPane.renderFileContent` reads the file, builds
`window.__viewer.setMarkdown("…")` around an escaped copy of it, and then
widens that whole string to UTF-16 for `ExecuteScript` — three live
allocations, all alive at once, before anything is freed. At T90e's 32 MB cap
the peak is roughly 32 + 32 + 64 = **~128 MB of transient allocation for one
pane**, and a document full of quotes or backslashes escapes larger still.

Nothing is wrong today (the cap makes it bounded and a real document is four
orders of magnitude smaller), which is exactly why this is a task and not a
bug: it is a shape that only hurts on the input nobody tries until they do,
and the fix is cheap while the code is fresh.

## In plain terms

Opening a very large document in a viewer pane briefly used about four times
the file's own size in memory, because the text was held three separate ways
at the same moment on its way to the page. Nobody has hit it — the viewer
already refuses anything over 32 MB — but a big log or a generated report is
exactly the kind of file that would find it. After this the pane holds the
file and the one buffer it hands to the page, and nothing else.

## Goals

- [x] The document is escaped once, straight into the buffer the web view is
      handed — no intermediate copy.
- [x] Both output paths share one escape table, so a rule fixed in one is
      fixed in both.
- [x] The file's own bytes are released before the injection call rather than
      after it.
- [x] The page renders exactly the same text it did before.

## Validation criteria

- [x] A pathological source (every byte a quote or a backslash) produces the
      correct literal — none lane, "setMarkdownCallUtf16 survives a source that
      is nothing but escapes"; the expectation is built one escape at a time so
      it is not the implementation restated.
- [x] The UTF-16 output is byte-for-byte the widening of the UTF-8 output, for
      escapes, multi-byte sequences and the U+2028/U+2029 lookahead — none
      lane, "appendJsStringUtf16 writes exactly what widening the UTF-8 literal
      would".
- [x] Allocation failure at any point leaks nothing — none lane,
      `checkAllAllocationFailures` over `setMarkdownCallUtf16`.
- [x] A real markdown file still renders in a real pane — the win32 lane's live
      host-floor test rendered it through the new path and the page posted both
      headings back (`file mode: headings=2`).
- [x] The floor lanes stay green — `floor-lane.ps1 -Lane all`: lib, none,
      win32, agent all PASS.
- [x] The file-mode acceptance script still passes — `viewer-panes.ps1` ALL
      PASS (195), plus the three guards the edit made due: `viewer-nav-pin.ps1`
      (24), `printclient-audit.ps1` (8), `test-reach-audit.ps1` (14).

## Details

Options, roughly in order of cost:

- **Lower the cap.** 32 MB was picked to be generous, not to be defended; a
  viewer that refuses a 4 MB document would be wrong, one that refuses a 40 MB
  one would not. Cheapest, and it narrows the window rather than closing it.
- **Escape straight into the UTF-16 buffer**, skipping the UTF-8 intermediate.
  `appendJsString` would become a writer over a `u16` sink; the pure module's
  tests move with it and stay pure.
- **Post the content instead of executing it.** `PostWebMessageAsJson` hands
  the page a string through the same bridge T375 built, and the page calls
  `setMarkdown` itself — no JS literal to build at all, so the escaping problem
  and one whole copy both disappear. This is the structurally right answer and
  the largest change, and it needs the Mac side to agree (the shared
  `viewer.js` would grow a message handler), so it is a design decision rather
  than a refactor.

*Validation:* a none-lane test that a pathological source (every byte a quote
or a backslash) still produces a correct literal, plus whatever peak-allocation
assertion the chosen option admits — `std.testing.checkAllAllocationFailures`
already exercises the failure paths.
