# T295 - T287a: Activity Monitor remote data plane - dial/reuse a connection so a remote panel shows real data

## Summary

First half of the split of **T287** (2026-08-01). This is the half that closes
the user-visible gap T177 left behind: the chooser's Activity button opens a
panel that says *"Couldn't connect"* on purpose, because `buildSnapshot`'s
first statement is `if (self.source == .remote) return
error.RemoteSourceNotConnected;`. This task replaces that branch with a real
connection.

Two of Mac's three entry styles
(`macos/Sources/Features/Remote/RemoteActivityMonitor.swift`), which differ in
who OWNS the connection:

- `presentDialing` - dials a FRESH connection off the GUI thread and owns it.
  This is what the chooser's Activity button calls
  (`MachineChooserView.swift:1488`).
- `presentReusing` - rides a remote window's existing connection and does NOT
  own it, so closing the panel must not tear that window's session down. This
  is the palette entry point's remote branch
  (`RemoteActivityMonitor.openFromPalette:132-141`); win32's
  `Surface.performCommand`'s `.activity` arm is `openLocal` unconditionally
  today.

`presentLocal` already landed in T285.

## What the wire already gives us (VERIFIED by reading)

- `Connection.requestProcSnapshot(sort, limit, timeout_ns)`
  (`src/remote/connection.zig:1525`) - a caller-owned deep copy, `ok=false`
  becomes `error.ProcUnavailable`.
- `Connection.killProc` (:1716) and `Connection.spawnProc` (:1752) - the remote
  twins of the `proc_control.zig` / `proc_spawn.zig` calls T286 wired locally.
- `Connection.subscribeMetrics(interval_ms, ctx, handler)` (:1122) /
  `unsubscribeMetrics` (:1148). **This is not optional.** The agent's
  `handleProcList` builds its host sample from a fresh `metrics.Sampler` with
  no prior tick, and says so at `server.zig:1607`: *"host.cpu_pct here may read
  0 ... the panel subscribes to the live metrics stream separately for an
  accurate host CPU%."* Without the subscription the remote CPU gauge would
  read a flat, confident zero - the same class of lie as sampling this machine
  under another machine's name.
- Dialing: `relay_dial.dial(alloc, base, device, token, .raw)`. The chooser's
  machines are relay devices (`relay_directory.Device`), so the panel needs the
  relay base (`relay_directory.resolveBase`) and a bearer token
  (`IpcHandlers.resolveToken`) the way `App.openRelayWindow` does.

## Shape

- The panel grows `remote: ?RemoteState{ conn, owned }` next to its samplers,
  and `open` gains the reuse variant (an existing `*Connection` the panel must
  not free).
- The dial runs OFF the GUI thread (it blocks through a handshake), exactly
  like Mac's `dialAndOpen`. A dial that lands after the panel closed, or after
  the source moved, must free what it dialed rather than adopt it.
- `close` order is fixed by ownership: unsubscribe metrics FIRST (guarantees no
  further callback), then join the sample worker, then free the connection iff
  owned.
- The metrics callback fires on the connection's control-reader thread, so it
  parks its reading under the existing `pending_mutex` discipline and posts to
  the GUI thread - it never touches view state directly.
- Kill / New Process branch on the source, so a remote panel's buttons act on
  the remote machine (Mac's `killSelected` / spawn take the same branch).

## Outcome (2026-08-01, DONE)

Both entry styles landed and the ownership rule is asserted end to end.

**Where the dial LANDS is the interesting decision.** The obvious shape — a
detached thread that posts its result to the panel's own HWND — leaks a live
connection every time the user closes the panel mid-dial, because
`DestroyWindow` DISCARDS a window's queued messages and the message is what
carries ownership of the dialed transport. So the result posts to the APP's
message-only window (`WM_APP_ACTIVITY_DIALED`), which outlives every panel, and
`(slot, serial)` says whether the panel that asked is still there. The serial is
not decoration: slots are reused the instant they free, so a slot-only check
would hand a NEW panel a connection to the OLD panel's machine and caption it
with the new one's name. `panelMatches` is pure and unit-tested on exactly that
case.

Second decision, same shape: **close order is ownership order.** Unsubscribe
metrics first (that return is the guarantee no further callback can fire into
`self`), then — for an OWNED connection only — `shutdown()` BEFORE joining the
sample worker, because `shutdown` runs `failPendingRpcs` and an unresponsive
agent would otherwise hold the GUI for the whole 5 s RPC timeout. A BORROWED
connection is never shut down or freed: it is a window's shell.

Host CPU% comes from the pushed `metrics` stream and not from the snapshot.
That is not a refinement — `agent/server.zig:1607` says `PROC_SNAPSHOT.host`
is a one-shot read with no baseline, so reading it as CPU% paints a confident
flat zero.

### The oracle problem this created, and its answer

A loopback agent enumerates the same box, so "the table populated" proves
nothing — a panel that silently sampled THIS process would look identical under
another machine's name, which is the very lie the predecessor refused to tell.
The distinguishing field is the snapshot's ROOT PID (`PROC_SNAPSHOT.agent_pid`
for remote, this process for local), so `rebuild`'s state line gained `root=`
and the script asserts it equals the agent pid the harness started:

```
state: source=127.0.0.1:47913 total=303 shown=3 root=40288    (agent pid 40288, app pid 35688)
```

`D` is the ownership assertion and the reason the script exists: after the
reused panel closes, the remote pane still round-trips through the agent.
