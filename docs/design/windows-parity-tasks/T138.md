# T138 — The upgrade script forks the loop: TWO Claude sessions end up running go.md at once

## Summary

**The upgrade script forks the loop: TWO Claude sessions end up running `go.md` at once.** User-hit 2026-07-28 ("there are 2 windows trying to run the session… both windows tried to build T131"). Proven on the box: `claude` pid 16076 started 08:01 and was STILL ALIVE after the 09:46 upgrade, alongside `claude` pid 644 started 09:46:40 by the script's relaunch. `upgrade-ghoztty-windows.ps1`'s header states the assumption — *"killing ghoztty.exe kills the session's shell and Claude with it"* — and that assumption died with T89: the agent owns the PTY, is deliberately never killed, and the relaunched app RE-ATTACHES the surviving pane. So the script now produces a second session on top of the one it never killed, both resuming the same transcript via `--continue "read go.md and go"`, both picking the same first task. (`+sessions` returned 0 in the log — the pre-kill probe is ALSO wrong, `$oldExe +sessions` was run at the moment the exe was being replaced; fixing the probe is part of this.) No repo damage this time: the duplicate never committed. Fix: before relaunching, look for a pane already running claude in `WorkingDirectory` (via `+list --json` + the pane's process tree) and re-use it instead of opening a new window; the relaunch is only correct when the kill actually orphaned the session. Validation: an on-box case that starts a persistent claude pane, runs the script, and asserts exactly ONE claude process in the repo afterwards

## Resolution (2026-07-29)

DONE. The resume is now a **decision** instead of a fixed action, made from one
fact the script can actually know: is the Claude that launched it still alive
afterwards?

- `scripts/loop-session.ps1` (new, dot-sourced): resolves the launching claude
  (explicit `-LoopClaudePid` -> `$env:CLAUDE_PID` -> ancestry walk - the tool
  shell's chain is `powershell -> claude.exe -> cmd.exe -> ghoztty-agent.exe`,
  and the detached script inherits `CLAUDE_PID`), stamps it with its process
  start time so a recycled pid cannot impersonate it, and decides
  `none | reuse | relaunch`.
- **reuse** (session survived): bring the app back with a plain
  `Start-Process` - NOT `+new-window`, which would open the very window we are
  avoiding - wait for restore to re-attach the pane, then `+send-keys
  --when-idle` the prompt into it and verify with `+read`. The prompt is
  derived from the trailing quoted text of `-ResumeCommand`, so the two paths
  cannot drift.
- **relaunch** (nothing survived): unchanged behavior, plus the fix below.
- The pane target for the reuse comes from `$env:GHOZTTY_PANE_ID`, inherited
  the same way. Pane trees were NOT usable for this: `+list --json` reports
  `pid: 0` and `working_directory: ""` for agent-backed panes (T98; the cwd
  half filed as **T166**), which is also why the row's original plan - "find
  the pane running claude via `+list --json` + the process tree" - was
  abandoned.

Two more defects fell out of building it, both fixed here:

1. **The `+sessions` probe never worked.** It read the output line-by-line
   expecting one object per line; the command prints a pretty-printed ARRAY, so
   every line failed to parse and the log said `pre-kill agent sessions: 0` on
   a box with four live sessions - meaning the T89h SESSIONS-SURVIVE assert had
   been silently SKIPPING since it was written. (Not the row's guess that the
   probe raced the exe swap; it runs before it.) Now parsed as a whole payload,
   tolerating array / single object / NDJSON / noise.
2. **The relaunch could silently do nothing.** `+new-window --target=main` is
   idempotent - an existing `main` is FOCUSED and the `--command` never runs -
   and session restore brings the registered IPC names back. Measured on the
   PRE-FIX script (2026-07-29 negative control below): it logged `UPGRADE OK
   (relaunched...)` while the resume command had not run at all. The relaunch
   now starts the app itself, then verifies a window actually appeared and
   retries under a unique target if not (`RELAUNCH-WINDOW OK` / `RELAUNCH
   FAIL`). Also: `RELAUNCH-CWD` could only ever log UNKNOWN on a persistence
   box (T166), so it now falls back to `+sessions --json` cwd for sessions
   created in the last two minutes.

### Validation

`test/win32/upgrade-no-fork.ps1` - **ALL PASS x3** (48 assertions):

- **A** (pure, also runnable with `-PureOnly`): the decision table, the prompt
  derivation, the pid-reuse guard, and the `+sessions` parser - including A8,
  the pre-fix oracle, which shows the old line-by-line reader finding 0
  sessions in the output the command actually prints.
- **B** reuse: sandbox install + staging + LOCALAPPDATA, an agent-backed pane,
  a live stand-in loop process. Asserts the fork does not happen (the resume
  command's marker file never appears), the pane is the SAME one re-attached,
  no extra window, the prompt is delivered into the surviving pane, and - the
  probe fix's own oracle - `pre-kill agent sessions: 2` + `SESSIONS-SURVIVE
  OK`.
- **C** relaunch: loop process dead, `main` cleared -> the old behavior is
  intact and the resume command runs.
- **D** relaunch onto a restored window -> it still resumes (`RELAUNCH-WINDOW
  OK`), the defect (2) case.

**Negative control**, pre-fix script straight out of `git show HEAD:`, same
scenario as B (2026-07-29 20:47): it relaunched on top of a live session and
logged `UPGRADE OK (relaunched...)` - while `SESSIONS-SURVIVE SKIP` and
`RELAUNCH-CWD UNKNOWN` show both diagnostics blind, and the resume command
never actually ran, because `+new-window --target=main` focused the restored
window. So the pre-fix script produced a fork in the field and a silent stall
in the sandbox, depending only on which side of the restore race the request
landed - the two failure modes B and D now pin down.
