# T904 - A session's ConPTY can live in a per-session holder process the agent talks to over a pipe

## Summary

Increment 1 of the T705 split. Design:
`docs/design/agent-nondestructive-handoff.md`. The `HPCON` cannot cross a
process boundary via documented APIs, so instead of carrying a session's PTY
across an agent restart, ownership inverts: a tiny **holder process**
(`ghoztty-agent.exe --pty-host`, one per session) creates the ConPTY, spawns
the shell, owns its own kill-on-close Job Object over the shell subtree, and
serves one owner at a time over an owner-only-DACL named pipe
(`…\pty-host-<session-id>`).

Protocol (version-tagged, additive-evolution rules as the app-agent contract):
`HELLO` (holder build stamp + protocol version), `DATA` both ways, `RESIZE`,
`SIGNAL`, `EXIT` (code), and **offset-acknowledged replay** — the holder keeps
a bounded replay buffer of un-acked output so a reconnecting owner gap-fills
instead of dropping bytes (same shape as the existing app-agent gap-fill).

This task is the holder itself plus the protocol, NOT the agent-side spawn
path (T905) or adoption (T906). Everything decision-shaped is pure and
unit-tested in the `test-agent` lane; the ConPTY plumbing gets an on-box smoke.

## In plain terms

Today the background process that keeps terminal sessions alive personally
holds every session's plumbing, so replacing it means losing every session.
This builds a small, separate caretaker for each session that holds that
plumbing instead. Nobody sees anything change yet — this is the caretaker
existing and passing its tests, before the main process starts using it.

## Goals

- [x] `--pty-host` mode: ConPTY + shell + own kill-on-close job, serving a
      per-session control pipe. (`src/remote/agent/pty_host.zig`, reusing the
      production `PtySpawner`/`PtyChild` spawn path and `PipeListener`.)
- [x] Control protocol with versioned HELLO, DATA/RESIZE/SIGNAL/EXIT, and
      offset-acked bounded replay. (`src/remote/agent/pty_host_proto.zig`;
      HELLO additionally carries the shell pid + retained window + exit state
      so a reconnect after exit still learns the code.)
- [x] Pure protocol/replay logic unit-tested in the `test-agent` lane
      (frame round-trips incl. truncation/trailing-bytes/oversize-len, accum
      reassembly byte-at-a-time, replay ring wrap/overflow/ack, replayStart,
      session-id charset).
- [x] On-box smoke: `--pty-host-smoke` spawns real holders and drives echo,
      resize (`mode con` reports the new width), disconnect/reconnect with
      contiguous-offset gap replay, exit-code delivery, and the job-object
      subtree kill. Wrapped by `test\win32\pty-host.ps1` (18 smoke checks +
      live pipe-DACL assertions), which stamps the new `pty-host` guard row.

## Validation criteria

- [x] `zig build test-agent` green with the new protocol/replay units —
      via `floor-lane.ps1 -Lane all` (this turn).
- [x] An acceptance/smoke script drives a holder end to end: output flows,
      RESIZE reaches the shell (`mode con` reflects it), owner disconnect +
      reconnect replays the gap, EXIT carries the shell's code —
      `test\win32\pty-host.ps1` section A, ALL PASS (15 assertions).
- [x] Killing the holder terminates the shell subtree (its job) — smoke
      scenario B; killing the owner does NOT touch the shell — smoke
      lifecycle step (owner vanishes uncleanly, shell pid stays alive).
- [x] Holder pipe is owner-only DACL (same mechanism as the agent pipe:
      `PipeListener.bind`'s ownerOnlyDescriptor) — asserted LIVE in section B
      via `NamedPipeClientStream.GetAccessControl`: every allow ACE names the
      current user.
