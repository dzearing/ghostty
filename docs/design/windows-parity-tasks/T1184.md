# T1184 - There is no way to search the text inside a Windows viewer pane

## In plain terms

A viewer pane can be showing a long README, a diff, or a web page, and there
is no way to find a word in it. Ctrl+F should open a small find bar, highlight
every match, say which one you are on ("3/17"), and let Enter and the arrows
step through them - the same in every kind of viewer pane.

## Summary

Main intake 2026-08-30 (range `772e4fc3a..origin/main`). Upstream commit
**3213f83a9** *"feat(viewer): browser-style Cmd-F find-in-page in every viewer
pane"* added `macos/Sources/Features/Viewer/ViewerFindBar.swift` (+177), the
shared `src/viewer/find.js`, and `ViewerView.swift` wiring, with
`ViewerDiffPaneTests.swift` additions as proof.

The behavior to carry across (Windows keybind is **Ctrl+F**, and Ctrl+G /
Ctrl+Shift+G or F3 / Shift+F3 for next/previous - pick the Windows-native
spelling and say which in this file):

- Works in **every** mode: markdown, code, local HTML, website, git diff.
- Typing highlights all matches (yellow, current one orange) with a live
  "3/17" count; Enter/Shift-Enter and the bar's chevrons step and wrap.
- Escape closes the bar and clears highlights but **keeps the query**, so the
  next-match chord resumes it and Ctrl+F returns with it selected.
- The search is ours in JavaScript (`src/viewer/find.js`, shared core) and
  paints with the CSS Custom Highlight API so it mutates no DOM - a find on a
  live dev server cannot corrupt its rendering, and the paint cannot
  re-trigger the mutation observer that keeps the count live. Confirm WebView2
  supports the Highlight API at our pinned runtime floor and record the answer
  here; if not, the Mac's pre-17.2 selection fallback is the shape to copy.

  **ANSWERED (2026-09-01): yes, and there is no floor to pin.** WebView2 here
  is the EVERGREEN runtime — `webview2_paths.zig` resolves whatever is
  installed and nothing in the tree names a minimum version — so the runtime is
  a current Chromium, and the CSS Custom Highlight API has shipped in Chromium
  since 105 (2022). Mac's pre-Safari-17.2 selection fallback is therefore dead
  code on Windows; it stays in the shared file because the file is shared, and
  `supportsHighlights` degrades on its own if a box ever does turn up without
  the API.
- It ships as a user script injected into every document (like selection.js /
  links.js), not from `viewer.js`, or it never reaches a website.
- Honest limits: unlaid-out text excluded, a page with a visible frame says
  so, past 5000 matches the count reads "12/5000+", and a diff pane names the
  file it is searching plus whether the 20 000-row cap is in force.
- Escape/Return precedence across the pane's text fields (address edit, diff
  filter, find) is a pure function on Mac so it is testable - keep that shape
  on the win32 side and cover it in the `none` lane.

## Goals

- [x] Ctrl+F opens a find card in every viewer mode.
- [x] A live "3/17" count, with stepping and wrapping from the keyboard and
      from the card's own chevrons.
- [x] Escape closes and clears the highlights but keeps the query.
- [x] Both Windows spellings of next/previous answer: Ctrl+G / Ctrl+Shift+G
      and F3 / Shift+F3.
- [x] The search itself stays ONE shared file for both platforms.

## Validation criteria

- [x] Ctrl+F opens a find bar in all five viewer modes. `viewer-find.ps1`
      sections A, I and J assert markdown, a rendered HTML page and a git diff
      directly. Code and website panes take the same two `--view` paths as
      those (one bundled template, one arbitrary document), and the card is
      injected per-DOCUMENT rather than per-mode, so there is no per-mode
      branch left that could diverge.
- [x] All matches highlight, the current one is distinct, and the counter is
      live as you type and as a live page mutates underneath an open search.
      The count is asserted in sections C/D/I. The PAINT is `find.js`'s CSS
      Custom Highlight API, inside a compositor surface PrintWindow does not
      reach off the input desktop — the script says so in its header rather
      than asserting a picture it cannot see.
- [x] Enter / Shift-Enter and the next/previous chords step and wrap; matches
      scroll into view without the bar covering the match it just found.
      Sections D (Enter, and the wrap), E (the card's chevron, backwards and
      wrapping) and F (F3 from inside the page). Mid-pane scrolling is
      `find.js`'s own `reveal`, shared with Mac.
- [x] Escape closes and clears highlights but keeps the query; reopening
      restores it selected. Section G, both halves.
- [x] Key precedence across address edit / diff filter / find is covered by a
      pure-function test in the `none` lane: `viewer_find.fieldKeyAction`, and
      the four tests around "Escape belongs to the field being edited before it
      belongs to find".
- [x] An on-box acceptance script in `test/win32/` covers open, count, step,
      wrap and close, with a `-NegativeControl` arm that scores red:
      `test/win32/viewer-find.ps1` — 30 passed, 0 failed; the negative control
      fails with exactly its two inverted count assertions.
- [x] Floor lanes green (`floor-lane.ps1 -Lane all`) plus P1-P3.
