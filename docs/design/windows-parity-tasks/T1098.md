# T1098 - A corrupt installed agent makes the upgrade pop a blocking Windows dialog instead of failing cleanly

## In plain terms

When Ghoztty updates itself it checks the background helper it just installed by
asking it for its version number. If that helper file is damaged - a half-copied
download, a delivery that was interrupted - Windows refuses to run it and throws
up a grey "Unsupported 16-Bit Application" box in the middle of the screen. The
update then just sits there until somebody clicks OK. Since the update normally
runs first thing in the morning without anyone watching, that box can be waiting
for the user when they sit down, on top of whatever they were doing.

It should notice the file is not a real program, say so in its log, and fail the
update on its own.

## Goals

- [x] the update reads the file's header instead of trying to run it, so a
      damaged program can never raise a dialog
- [x] a damaged program on disk fails the update outright, rather than being
      reported as "could not tell" and shipped past
- [x] the same for the terminal itself, not only the background helper
- [x] the test suite notices a dialog nobody asked for and fails the script that
      raised it, instead of scoring it a pass

## Summary

Seen live on 2026-08-22 by the user, while the T1094 suite sweep was running
`test\win32\upgrade-staleness.ps1`:

```
Unsupported 16-Bit Application

The program or feature "\??\C:\Users\David\AppData\Local\Temp\ghoztty-staleness-3596\agent\install\ghoztty-agent.exe"
cannot start or run due to incompatibity with 64-bit versions of Windows. ...
```

Two distinct defects, filed together because they share one root cause.

**1. The product defect (the one that matters).** T281 made the upgrade READ THE
INSTALLED AGENT BACK - `AGENT VERIFY` launches `<install>\ghoztty-agent.exe
--version` and compares its build stamp against the staged agent's. That launch
has no precondition: if the path holds something that is not a valid PE image,
`CreateProcess` fails with `ERROR_BAD_EXE_FORMAT` and the Windows shell answers
it with a **system-modal dialog**, not an error code. The verify never returns
until a human clicks OK.

The real-box shape is not hypothetical: `AGENT VERIFY` exists precisely because a
delivery can leave a wrong or damaged `ghoztty-agent.exe` on disk (2026-07-20 -
the `.bak` was the still-mapped image of the running agent and neither the rename
nor the copy ran). A truncated copy is the same class of accident, and the check
built to catch it is the thing that hangs. T525's morning refresh runs
**unattended, at 5am, in the user's own session**, so the dialog lands on their
desktop with nothing to dismiss it.

**2. The harness defect.** `upgrade-staleness.ps1` section E8 is the negative
control for exactly this scenario. It writes a plain-text sentinel to the install
path to stand in for a stale agent:

```powershell
Set-Content -LiteralPath $eInstalledAgent -Encoding ascii -Value $sentinel
```

then runs the upgrade over it. So the script provokes the dialog every time it
runs. It scored **`ALL PASS (123 assertions)`** on this sweep, which is the real
problem: the modal is invisible to the verdict, it escaped onto the interactive
desktop rather than the background test desktop, and it is only known about
because the user happened to be looking at the screen.

## Where

- `scripts/upgrade-ghoztty-windows.ps1` - the `AGENT VERIFY` read-back (T281).
  Same question applies to the app-side `POST-SWAP VERIFY`, which launches the
  installed `ghoztty.exe` with `+version` and can fail the same way.
- `test/win32/upgrade-staleness.ps1` - section E8/E9, the sentinel write above.
- `test/win32/lib/` - whatever the suite grows to notice a stray modal.

## The work

1. **Gate the launch on the file being a real executable.** Read the PE header
   before running it (`MZ` at 0, a plausible `e_lfanew` to a `PE\0\0`) and treat a
   non-PE as `AGENT VERIFY FAILED` with a distinct reason, without ever calling
   `CreateProcess`. That turns the hang into the failure the surrounding contract
   already knows how to report - `NOT PROPAGATED`, exit 1 - and it is strictly
   better evidence than a launch, since the file cannot even in principle be the
   staged agent if it is not a PE.
2. **Belt and braces on the launch itself**: set the error mode so a failed
   `CreateProcess` returns rather than prompting (`SEM_FAILCRITICALERRORS |
   SEM_NOOPENFILEERRORBOX`) for the verify children, and put a timeout on the
   read-back so no future variant of this can block forever.
3. **Apply the same two to the app-side `POST-SWAP VERIFY`.**
4. **Make the harness able to see it.** A stray modal on the interactive desktop
   during a suite run should be a failure, not a thing a human notices. Cheapest
   honest version: `upgrade-staleness.ps1` asserts, after E8, that no window
   titled `Unsupported 16-Bit Application` (or class `#32770` owned by the run's
   process tree) exists. Better version: the same sweep in
   `scripts/suite-run.ps1`'s between-script pass, so it covers every script, next
   to the leak sweep it already runs.
5. Make E9's sentinel a deliberate NON-PE and say so in the comment - once the
   fix lands, the sentinel is testing the new PE gate, and that is worth naming.

## Validation criteria

- [x] running the upgrade with a text file at `<install>\ghoztty-agent.exe` exits
      nonzero and logs `AGENT VERIFY FAILED` with a not-a-PE reason, with NO
      dialog raised (asserted, not eyeballed) — `upgrade-staleness.ps1` E10/E11
      (exit 1, `AGENT VERIFY FAILED`), E14b/E14c (the reason is read off the
      header, never a launch result), E23 (no dialog appeared)
- [x] the same for a text file at `<install>\ghoztty.exe` and `POST-SWAP VERIFY`
      — new arm E18–E22: a damaged staging payload shipped over the staleness
      gate with `-AllowStaleStaging` ends `POST-SWAP VERIFY FAILED … not a
      runnable program`, exit 1, `NOT PROPAGATED`, and the whole run finishes
      unattended
- [x] `test\win32\upgrade-staleness.ps1` is ALL PASS and now fails if a modal is
      raised during section E — ALL PASS (144 assertions, was 123). E23 is the
      new gate and E23p/E23q/E23r are its positive control: a real `#32770`
      raised from another process is found, dismissed, and gone
- [x] a full `scripts\suite-run.ps1` pass raises no `#32770` dialog on the
      interactive desktop, or fails naming the script that did — the sweep runs
      between scripts beside the leak sweep; `test\win32\suite-run.ps1`
      section M drives a fixture that leaves a dialog up behind its own
      `ALL PASS` and asserts the runner scores it `fail`, names it, counts it,
      goes red, and dismisses it (ALL PASS, 51 assertions)
- [x] the E8 negative control still proves the 2026-07-20 skipped-swap case —
      E8/E9 unchanged in shape and still green; the sentinel is now documented
      as deliberately non-PE, so it tests the stale-agent case and the damaged
      one at once
