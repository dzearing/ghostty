# T529 - Reopened-after-kill windows re-attach but are FROZEN

## User report (2026-08-06, ~09:20, verbatim)

"the windows seemed to repaint correctly but were non interactive, not
painting, but seemed to still be working, as if we could not reconnect the
live stream, so resume didn't work."

## Context (exact, from logs - the repro recipe)

1. 09:19:36 - the upgrade delivery (staging 1cda2827c) KILLED the 2 release
   ghoztty processes and, because of `-NoResume` (see T531), did NOT restart
   the app. The running agent (pid 35492, build 20260806-8db5dc509 - one
   delivery older than the new app) was untouched, holding the live sessions.
2. 09:19:53 - the user manually reopened Ghoztty (new exe 1cda2827c).
3. `ghoztty.log` lines ~199505-199521: the fresh app connected to agent
   35492, ATTACHed 2 sessions (offsets + snapshots applied, cwds applied),
   logged `session-restore: restored 1 window(s)`, `attached 2 pane(s); 0
   live agent session(s) unattached` - every signal reports success.
4. What the user SAW: windows painted with correct content but dead - no
   input echo, no output flowing, "could not reconnect the live stream".

So the attach path completed by its own accounting and the result was a
still image. The gap between "attached" and "alive" is the bug - the same
empty-vs-absent failure shape as T421's `reuse: pane re-attached`.

## Suspects (? INFERRED - none verified)

- **App/agent build skew**: new app (1cda2827c, carries T524) against the
  older running agent (8db5dc509). The contract says additive-only, but this
  exact pairing froze. Check what changed on the agent wire between those
  two builds and whether HELLO negotiation covered it. (The 1.14.0 re-attach
  corruption precedent makes skew the first suspect.)
- **Replay-then-subscribe race**: snapshot applied (hence correct repaint)
  but the live output subscription / input channel never wired, or wired to
  a retired connection object.
- **Focus/foreground live-lock** ([[restore-focus-pingpong]] memory): "non
  interactive" could be input never reaching the pane rather than a dead
  stream - but that memory's shape was 2-window flip-flop; here 1 window
  restored per launch.

## Validation criteria

- [ ] Repro: kill the release app processes (script-style, agent untouched),
      reopen the exe, and prove the restored panes are LIVE - keystroke echo
      observed via +send-keys/+read, not just "attached" log lines.
- [ ] The attach path gains an aliveness proof (echo or output heartbeat)
      and logs loudly when a pane attaches but never goes live.
- [ ] Acceptance arm covering kill -> manual reopen -> interactive pane
      (extend session-reattach.ps1 or session-persistence lane).
- [ ] If skew is the cause: HELLO-gate the offending behavior per the agent
      contract rules in CLAUDE.md.
