# T968 - +new-window --name=X is silently ignored, so a scripted pane target never exists

## Summary

A script that names a pane at creation gets exit 0 and no registration; the next +send-keys/+read --target fails with 'target not found' and nothing says why. Found while writing test\win32\holder-soak.ps1 (T909).

## In plain terms

When you open a new terminal window from a script you can ask for it to be
given a name, so later commands can talk to it. The name is thrown away without
a word, so the very next command answers "that doesn't exist" and the script
looks broken for no visible reason.

## Details

`docs/claude/cli.md` draws the distinction deliberately: `+new-window
--target=<name>` registers a WINDOW, `+split --name=<name>` registers a PANE.
But `name` is a field on the shared `VerbArgs` struct
(`src/apprt/ipc/args.zig`), so `+new-window --name=X` parses cleanly, exits 0
and registers nothing — the failure surfaces one command later at
`+send-keys --target=X` as `target 'X' not found`.

Either honour it (register the new window's pane under that name, which is what
the flag reads as) or refuse it as an unknown flag for this verb. Silence is the
one option that is wrong. Whichever way it goes, both platforms move together
and `docs/claude/cli.md` says which it is.

## Validation criteria

- [ ] `+new-window --name=X` either registers a pane targetable as `X`, or
      exits non-zero saying the flag is not accepted here.
- [ ] The chosen behavior is the same on macOS and Windows.
- [ ] `docs/claude/cli.md` documents it, and an acceptance arm covers it.
