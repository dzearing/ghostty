# T1195 - Show update download progress instead of a balloon that says 'Downloading the update...' once

## Summary

With `auto-update = check`, clicking the update notification starts a
download of tens of megabytes and the only feedback is one balloon saying
"Downloading the update...". On a slow link that is a long silence with no
way to tell progress from a stall, and the Mac shows a progress bar.

`update_install.fetch` already reads the body in chunks, so the progress is
there to report; what is missing is somewhere to put it.

## In plain terms

If the update has to download when you click, you get one "downloading"
message and then nothing until it either installs or fails. On a slow
connection you cannot tell whether it is working.

## Goals

- [x] The download reports itself while it runs, in something the user can watch
- [x] A stall is named as a stall instead of looking like a slow link
- [x] A failure is visible and says what happens to the build they have
- [x] The unprompted background pre-download stays silent

## Validation criteria

- [x] A download that takes more than a moment shows progress the user can watch -
  test\win32\update-progress.ps1 case 1: a 12 MB asset trickled 64 KB at a time
  from a loopback server, consented to through the real balloon -> confirm-dialog
  path. The `GhozttyUpdateProgress` window appears and the panel's own report
  advances 1.2 MB -> 9.2 MB across 5 lines, each carrying a percentage derived
  from a real `Content-Length`.
- [x] A stalled or failed download is distinguishable from a slow one - case 1
  asserts a slow-but-moving transfer is NEVER called stalled and that a
  completed-but-not-a-package download says "The download failed"; case 2 stops
  the server mid-body and asserts the panel says "Stalled ... no data for Ns".
  The rule itself (movement, not clock) is `update_progress.StallTracker`, unit
  tested in every lane including a 120 s transfer with 9 s between chunks.
- [x] The `auto-update = download` path (already fetched before the click) shows
  no extra chrome - case 3 watches the whole background pre-download and asserts
  no panel window ever exists and no progress line is ever logged, with a control
  assertion that the download did run.
