# T299 - ActivityMonitor.zig is a mega file (3k lines): split the painter and the source/connection plane out

## In plain terms

Nothing about the Activity Monitor changes for anyone using it — this is
housekeeping on the code behind it. One file had grown to nearly five thousand
lines and was doing nine jobs at once: drawing the window, talking to remote
machines, polling for processes, handling the mouse and keyboard, and killing
or starting processes. When everything lives in one place, the rules that keep
a remote connection from being closed twice (or not at all) are impossible to
find, and a small mistake in one of them shows up much later as a hang or a
dead session. Splitting the file so each job sits in its own file with its own
rules written next to it is what makes those mistakes catchable.

## Goals

- [x] The painter comes out into its own file
- [x] The source / connection plane — the part with the ownership rules — comes
      out into its own file, with those rules documented where they are enforced
- [x] Nothing behaves differently: same functions, same tests, same acceptance runs
- [x] No file left over ~1,200 lines of code

## Summary

`src/apprt/win32/ActivityMonitor.zig` is **~3,000 lines / 110 KB** after T296,
against a standing bar that says *"No mega files. Split modules as they grow"*
(CLAUDE.md, the user's 2026-07-12 quality bar). It grew by accretion across
T285 (the window), T286 (process control), T295 (remote sources) and T296 (the
carousel), and each of those increments was individually reasonable.

The pure arithmetic was split out at every step and is fine —
`activity_layout.zig`, `activity_rows.zig`, `activity_actions.zig`,
`activity_cards.zig`, `trend_gauge.zig`. What is left in the big file is three
separable win32 concerns wearing one hat.

## The seams (already visible as section banners in the file)

1. **The painter** — `paint`, `paintCarousel`/`paintCard`, `paintGauges`,
   `paintControlBar`, `paintTable`, `paintRow`, `paintEmptyState`,
   `paintBanner`, `paintScrollThumb`, plus the palette and the GDI helpers
   (`fill`, `drawText`, `roundRect`, `ellipse`). ~900 lines that take a `Layout`
   and an HDC and touch no lifetime.
2. **The source / connection plane** — `startDial`, `dialWorker`, `onDialed`,
   `adoptDial`, `beginMetrics`, `onMetrics`, `startMachineList`,
   `machineListWorker`, `onMachines`, `switchToCard`, `teardownSource`,
   `resetForNewSource`, plus `RemoteConn` / `DialResult` / `MachineListResult`.
   This is the part with the ownership rules, and the part where a mistake
   leaks a connection or frees a live window's shell.
3. **The window itself** — creation, the registry, the wndProc, input routing,
   the sampling worker.

## Why it matters here specifically

Group 2 is where every dangerous rule lives: unsubscribe before join, join
before free, a borrowed connection is never freed, bump the serial so a stale
dial frees itself, drop a sample by generation. Rules like that are auditable
when they sit in one small file with their own tests, and invisible when they
are spread through a 3,000-line one.

## Details

Prior art is the sibling split this file's own header cites —
`chooser_layout.zig` / `MachineChooser.zig` — and
`IpcServer` / `IpcHandlers` / `IpcRegistry`. The painter can take an explicit
context (fonts, scale, palette) rather than `*ActivityMonitor`, which also makes
parts of it testable.

## What landed

`ActivityMonitor.zig`: **4,927 → 1,343 lines**. It now owns the window and
nothing else — state, open/close, the registry, the wndProc.

| File | Lines | Owns |
|---|---|---|
| `ActivityMonitor.zig` | 1,343 | the window |
| `activity_paint.zig` | 829 | every pixel |
| `activity_machines.zig` | 643 | machine list + carousel (T296) |
| `activity_probe_conn.zig` | 636 | per-card probe connections (T298) |
| `activity_input.zig` | 614 | mouse + keyboard focus ring (T289) |
| `activity_dial.zig` | 465 | the connection plane — dial, borrow, teardown (T295) |
| `activity_sample.zig` | 362 | poll loop, gate, snapshot |
| `activity_procs.zig` | 243 | Kill / New Process (T286) |
| `activity_view.zig` | 231 | filter / selection / scroll, layout, chrome |

Both seams the task named are out, and the dangerous one — `activity_dial.zig`
— now carries its ownership rules as a documented list at the top of the file
that enforces them. The header commentary went with the code it describes, so
`## Remote sources (T295)` is read in the dial file and `## Per-card metrics
probes (T298)` in the probe file.

The mechanism worth reusing: each plane imports the panel back
(`const ActivityMonitor = @import("ActivityMonitor.zig")`) and takes
`self: *ActivityMonitor`; the panel re-exports each plane's functions as
`pub const f = plane_mod.f;`, which keeps `self.f(x)` method syntax working at
every existing call site. That is what made a 3,600-line move mechanical rather
than a rewrite, and it is why the before/after function-set comparison could be
exact. Follow-up **T1013** writes the method down and points it at the five
win32 files that are bigger than this one was.
