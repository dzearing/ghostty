# T303 - Get-TestWindowPixels returns a silent flat capture for WinUI/XAML windows (PrintWindow cannot see DirectComposition)

## Summary

`Get-TestWindowPixels` guards exactly one capture limit: it refuses the
`GhozttyTerminal` surface, because T214 established that `PrintWindow` returns
a flat fill there and any assertion on that capture would pass against nothing.

**The same limit applies to every WinUI/XAML window and nothing guards it.**
Found while measuring T302's Windows-side reference: `PrintWindow(hwnd, dc,
PW_RENDERFULLCONTENT)` against Task Manager's main window returned a **flat
black 1379x1134 bitmap** - 1 distinct color over a 7px sampling grid, an 8 KB
PNG - and reported **success**. A vertical-seam scan over it then found zero
seams, which reads as "this app has no master-detail seam" rather than "there
is no capture".

The cause is architectural and permanent, not a bug to work around: WinUI /
XAML apps (Settings, Task Manager, most of Win11's own shell) composite through
DirectComposition and never paint into the window DC, so there is nothing for
`PrintWindow` to copy. The Win32 apps that *do* capture are classic GDI dialogs.

This is the "green and empty" failure class T271 and T283 exist for, one level
down: not an assertion that claims nothing, but a *capture* that contains
nothing while looking like a successful measurement.

## Fix

- Detect it in `Get-TestWindowPixels`: after `CaptureWindow` succeeds, sample
  the bitmap for distinct colors (`Get-TestDistinctColors` already exists) and
  **throw** when a capture of a non-trivial window is effectively uniform,
  naming DirectComposition as the likely cause and pointing at the CAPTURE
  LIMIT header. A caller that genuinely wants a flat surface opts in the way
  `-AllowTerminalSurface` does.
- Extend the CAPTURE LIMIT header in `test/win32/lib/TestDesktop.ps1` from "the
  terminal surface" to the general rule: *PrintWindow sees GDI, not
  composition.*
- Record the corollary for anyone reaching for a native reference:
  **a Win11 app cannot be used as a pixel reference at all**, so a spec that
  needs Windows metrics measures them through
  `SystemParametersInfoForDpi` / `GetSystemMetrics` / `uxtheme` / DWM instead
  (what T302 did) and cites Fluent as documentation, never as a measurement.

## Validation

- A case in `test/win32/test-desktop-harness.ps1`: capture a window that is
  known to be uniform and assert the new guard throws; capture a real ghoztty
  chrome window and assert it does not.
- `-NegativeControl` inverts the guard and FAILS.

## Notes

Second, smaller finding from the same probe, worth not repeating: **Task
Manager launches elevated**, so a non-elevated session cannot close it again -
`Stop-Process`, `CloseMainWindow` and `taskkill` all return Access Denied. A
test fixture the harness cannot clean up should not be a fixture.
