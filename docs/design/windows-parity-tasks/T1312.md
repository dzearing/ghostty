# T1312 - Nothing has ever asked a second scanner whether the Windows release is clean

## In plain terms

When Windows Defender called Ghoztty a trojan on someone's machine, we had no
way to check whether anyone else agreed. Every piece of evidence we have comes
from Defender itself. Until a second opinion exists, "it is a false positive"
is a reasonable belief rather than something anybody checked.

## Summary

T1293's first instruction is "verify rather than assume": submit the published
binaries to VirusTotal and compare engines. A lone Defender machine-learning
hit with every other engine clean is what a false positive looks like; several
independent detections would mean the release is compromised and would have to
be pulled. Those two outcomes lead to opposite actions, so the check is not
optional - and it has never been made, for any Ghoztty release.

The turn that tried could not make it either. VirusTotal's API needs a free key
that this box does not hold, its web upload needs a browser session (the Chrome
extension was not connected), and no other on-box scanner exists. What this box
CAN do, and did, is scan the published artifacts explicitly with Defender's own
engine and record the engine and signature versions:

| Artifact | Verdict |
|---|---|
| `Ghoztty-1.36.2-x64.msi` | no threats |
| `Ghoztty-portable-1.36.2-x64.zip` | no threats |
| `ghoztty.exe` | no threats |
| `ghoztty.com` | no threats |
| `ghoztty-agent.exe` | no threats |

Engine 1.1.26080.3, signatures 1.459.28.0 (2026-09-02), cloud protection at
MAPS Advanced, real-time protection on, no exclusion covering the scan path.
That rules out a signature match; it does not rule anything in, because the
verdict the user hit is a per-machine cloud call.

## What to do

1. Put a VirusTotal API key where the release secrets live, so the check can be
   scripted rather than done by hand once.
2. Add `scripts/verify-release-clean.ps1`: given a release tag, download every
   asset, hash it, query VirusTotal by hash, and print the engine-by-engine
   result plus a verdict. Hash lookup first (no upload), so a published binary
   that has already been scanned costs one request.
3. Run it as part of the release readback the way `scripts/verify-release-assets.ps1`
   is, so the question is asked on every release instead of the one time
   somebody remembered.
4. Record the result for `win-v1.36.2` in T1293 - engine names and counts, not
   a summary.

## Validation criteria

- [ ] A VirusTotal query for the published `ghoztty.exe` and `ghoztty.com`
      hashes returns a result, and the per-engine detections are recorded in
      T1293 by name.
- [ ] The check is a script with a harness, not a one-off: a fabricated
      multi-engine response makes it exit non-zero, demonstrated.
- [ ] The release readback calls it, and a release whose assets no scanner has
      ever seen says so rather than passing silently.
