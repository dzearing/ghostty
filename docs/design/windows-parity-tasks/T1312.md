# T1312 - Nothing has ever asked a second scanner whether the Windows release is clean

## In plain terms

When Windows Defender called Ghoztty a trojan on someone's machine, we had no
way to check whether anyone else agreed. Every piece of evidence we have comes
from Defender itself. Until a second opinion exists, "it is a false positive"
is a reasonable belief rather than something anybody checked.

## Goals

- [x] A script that asks an engine other than Defender about a published
      release, by hash, and names what it hears back
- [x] A harness proving that script can say DETECTED and UNKNOWN, not only
      CLEAN
- [x] The question gets asked automatically on every release instead of once,
      when somebody remembers
- [ ] An actual answer for `win-v1.36.2`, recorded in T1293 by engine name -
      blocked on a VirusTotal API key

## Summary

T1293's first instruction is "verify rather than assume": submit the published
binaries to VirusTotal and compare engines. A lone Defender machine-learning
hit with every other engine clean is what a false positive looks like; several
independent detections would mean the release is compromised and would have to
be pulled. Those two outcomes lead to opposite actions, so the check is not
optional - and it has never been made, for any Ghoztty release.

The turn that tried could not make it either. VirusTotal's API needs a free key
that this box does not hold, its web upload needs a browser session (the Chrome
extension was not connected), and no other on-box scanner exists. What this box
CAN do, and did, is scan the published artifacts explicitly with Defender's own
engine and record the engine and signature versions:

| Artifact | Verdict |
|---|---|
| `Ghoztty-1.36.2-x64.msi` | no threats |
| `Ghoztty-portable-1.36.2-x64.zip` | no threats |
| `ghoztty.exe` | no threats |
| `ghoztty.com` | no threats |
| `ghoztty-agent.exe` | no threats |

Engine 1.1.26080.3, signatures 1.459.28.0 (2026-09-02), cloud protection at
MAPS Advanced, real-time protection on, no exclusion covering the scan path.
That rules out a signature match; it does not rule anything in, because the
verdict the user hit is a per-machine cloud call.

## What to do

1. Put a VirusTotal API key where the release secrets live, so the check can be
   scripted rather than done by hand once. **STILL OPEN** - see below.
2. ~~Add `scripts/verify-release-clean.ps1`~~ - done. Given a release tag it
   downloads every asset, expands the portable zip, hashes the executables,

   and prints the engine-by-engine result plus a verdict.
3. ~~Run it as part of the release readback~~ - done. `daily-publish.ps1` calls

4. Record the result for `win-v1.36.2` in T1293 - **still open**, because there
   is no result yet. The hashes are recorded there instead, so the lookup is a
   30-second job the moment a key exists.

## What is blocking the answer

The machinery is built and demonstrated; nobody has been asked. VirusTotal's
API needs a key, and a key needs a free account signup - a credential action
this loop does not perform. The browser route is also shut: the Chrome
extension is not connected to this session, so the web UI cannot be driven
either. There is no other scanner on this box; Defender is the only engine
installed, which is the whole problem T1293 has.

**To unblock, in one minute:** sign up at
<https://www.virustotal.com/gui/join-us>, copy the key from
<https://www.virustotal.com/gui/my-apikey>, and save it as

```
%LOCALAPPDATA%\ghoztty\secrets\virustotal.key
```

(or set `GHOZTTY_VT_API_KEY`). Then the answer is one command:

```
powershell -NoProfile -File scripts\verify-release-clean.ps1 -Tag win-v1.36.2
```

The free tier's 4 requests/minute and 500/day are far more than this needs -
six hashes per release.

## The verdicts, and why each one is an exit code

| Exit | Verdict | Means |
|---|---|---|
| 0 | `CLEAN` | every asset had a report, no engine flagged it |
| 2 | `UNKNOWN` | an asset no scanner has ever seen. Not clean - nobody looked |
| 3 | `DETECTED` | engines flagged it, and they are named |
| 4 | `NOASK` | no key or no network. The absence of an answer, not an answer |

`UNKNOWN` is a separate code on purpose: the silent-pass hole this task exists
to close is a check that treats "never scanned" as "fine".

## Validation criteria

- [ ] A VirusTotal query for the published `ghoztty.exe` and `ghoztty.com`
      hashes returns a result, and the per-engine detections are recorded in
      T1293 by name. **NOT MET** - no API key, and the browser route is shut.
      This is the one thing left, and it is the one thing this box cannot do.
- [x] The check is a script with a harness, not a one-off: a fabricated
      multi-engine response makes it exit non-zero, demonstrated. Section C of
      `test\win32\verify-release-clean.ps1` builds a three-engine malicious
      response and asserts exit 3 with all three engines named; C5 asserts the
      count, after a `return ,` was found collapsing them into one detection
      called `System.Object[]` while still exiting 3.
- [x] The release readback calls it, and a release whose assets no scanner has
      ever seen says so rather than passing silently. Section D asserts exit 2
      and the words "nobody has looked" for a never-scanned asset; section G2
      asserts `daily-publish.ps1` still calls the checker.
