# T1090 - close-confirm-idle.ps1 section C cannot find the remote shell any more: it walks the agent's descendants, and the pty holder escapes them

## In plain terms

One of the on-box test scripts had quietly stopped being able to test the
thing it is named after. It checks that a terminal connected to another
machine does not nag you to confirm when you close an idle pane — but to do
that it first has to find the shell that pane is running, and it was still
looking in the old place. Nothing a user can see is broken; the safety net
under it was.

## Goals

- [x] Section C of `close-confirm-idle.ps1` finds the remote session's shell again
- [x] The whole script is back to ALL PASS
- [x] The negative control still fails section C

## Summary

`test\win32\close-confirm-idle.ps1` section C (the CROSS-MACHINE pane, T356)
found the remote session's shell by walking the descendants of the listening
`ghoztty-agent`. Since T905/T909 that is the wrong tree: a session's ConPTY,
shell and kill-on-close job live in a per-session **holder** process
(`ghoztty-agent.exe --pty-host`) which is spawned through
`job_spawn.spawnEscapingJob` specifically so it ESCAPES the agent's job — and
on the shell-parent-hop escape tier it loses its parent link too, so the shell
is not under the agent at all.

The section therefore failed on `C/remote the agent spawned a shell for the
remote session`, reproducibly, over a session that had one and was working
fine. Everything after that assertion was skipped, so T356's actual subject —
that an idle cross-machine pane closes without confirming — had no coverage at
all.

## Details

The PRODUCT side is unaffected and was verified rather than assumed:
`src/remote/agent/descendants.zig` answers `META{has_descendants}` from a full
system parent-map snapshot rooted at the session's shell pid, so where the
holder sits in the tree is irrelevant to it. This was purely a stale harness
oracle.

Fix: a `Get-PtyHolderPids` helper enumerates every repo-built
`ghoztty-agent.exe` whose command line carries `--pty-host`, and section C
searches the agent AND those holders. Both roots, not just the holders,
because the in-process fallback (`GHOZTTY_AGENT_PTY_HOLDER=0`, or a holder that
would not start — `spawnFn` falls back rather than failing the OPEN) still
parents the shell to the agent. A holder reached through the agent is skipped
as a waypoint; the walk already enumerates its children.

Found while adding T357's forced-confirm sections to the same script.
