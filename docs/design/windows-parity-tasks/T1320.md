# T1320 - The stall catch reads the composer from a drawn fixture, never from a real Claude Code pane, so a chrome change could switch it off silently

## Summary

T1319's composer arm is what catches an unsubmitted continuation in tens of minutes instead of at the 180-minute backstop, and its only test renders the box this repo BELIEVES Claude Code draws (go-loop-guard.ps1 section BB, built from code points). go-loop-pane-probe.ps1's own history says the TUI's wording and layout have drifted twice already. A drift that moves the composer marker would disable the catch with every arm still green. Wanted: an arm that reads a REAL Claude Code pane - or a cheap standing check that the marker shape is still what the probe expects.

## In plain terms

When the loop stops with a command typed but never sent, the supervisor notices
because it reads what is sitting in the input box. It knows what an input box
looks like from a picture this repo drew of one. If the app that draws it
changes shape, the picture stops matching, the supervisor goes quiet again, and
every test still passes.

## Validation criteria

- [ ] The composer marker is checked against a REAL Claude Code pane, not only
      against a rendered fixture - either an arm that opens one, or a standing
      check that runs against the loop's own pane and reports rather than fails.
- [ ] The check distinguishes "the composer is empty" from "I no longer
      recognise the composer", because today both answer '' and only one of them
      is a defect.
- [ ] Whatever is added is demonstrated red against a chrome shape the probe
      does not recognise (T1133).
