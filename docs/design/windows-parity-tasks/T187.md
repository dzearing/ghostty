# T187 - upgrade script declares RESUME-REUSE FAIL while the app IS up - a false negative that stalls the loop

## Summary

**The loop stalled this morning and a human restarted it** — the failure class
T138/T139 exist to prevent. Found by T144's own delivery.

`%TEMP%\ghoztty-upgrade.log`, 2026-07-30:

```
09:06:00 reuse: no running instance; starting the freshly installed exe
09:07:00 RESUME-REUSE FAIL: the app did not come back up; the session is alive
         but headless. NOT relaunching (that would fork the loop) - the go-loop
         watchdog covers the stall.
```

The app **had** come back up: `ghoztty.exe` pid 35456, `StartTime 9:06:00 AM`,
still running and answering `+list` normally afterwards. So the script's
readiness probe (`Wait-Instance 60`, polling `+list --json`) was a **false
negative**, and because a false "app is dead" is treated as fatal-but-don't-fork,
the resume prompt was never typed and the loop sat dead until the user pinged.

### The mechanism (from the source; MEASURE before fixing)

`src/apprt/win32/App.zig` binds the IPC pipe early (`App.init`, ~line 378) but
`run()` calls **`restoreSessionLayout()` synchronously, before
`GetMessageW`** (~line 547). The pipe exists, so a client connects — but
nothing accepts or handles until the message loop starts. **Time-to-IPC-ready is
therefore time-to-restore-complete**, which grows with the number of panes and
includes dialing the agent, probing liveness, and ATTACHing every pane. On this
box, with 3 windows / 5 panes, it exceeded 60s.

That is bigger than the upgrade script: **any `ghoztty +…` issued while the app
is restoring gets nothing**, which is the same user-visible class T111b fought
("No running Ghoztty instance found." from a running app).

Confirm with a number before fixing: hermetic debug instance, build a manifest
of N panes, kill the app only (never the agent), relaunch, and poll `+list`
from the instant of launch — restore-start latency vs an empty-manifest cold
start. If they differ by the expected order, the mechanism is proven.

### MEASURED 2026-07-30 — both filed mechanisms are REFUTED

Time from `Start-Process` to the first successful `+list --json`, debug build,
hermetic state, app killed but agent left alive (the upgrade script's exact
move):

| scenario | panes | time to IPC ready |
|---|---:|---:|
| cold start, no manifest | 1 | **427 ms** |
| restore, healthy agent | 5 | **451 ms** |
| restore, agent SUSPENDED across the relaunch (`NtSuspendProcess`, 40 s) | 4 | **10 755 ms** |

So restore is *not* slow, and it is not unbounded even when the agent is
completely wedged — `restoreSessionLayout` gives up and the message loop starts
in ~11 s. "The app did not come back up" is essentially never true after ~11 s.
The pre-loop restore is a latency risk worth knowing about, but it cannot
produce a 60 s IPC blackout, so fix (1) below is NOT what this defect needs.

### What the numbers do indict: the probe, not the app

`Get-ListJson` runs `& $oldExe +list --json` **with no timeout**, and
`Wait-Instance` only checks its deadline *between* calls. One `+list` that
blocks — which is exactly what a client that connects to a bound-but-not-yet-
accepting pipe can do — consumes the entire 60 s window without the loop ever
iterating, and `Wait-Instance` then returns `''` as if the app were dead. The
verdict is also keyed solely on IPC, never on the far simpler fact that the
process the script itself just started is alive and healthy. And no failed poll
is logged, which is why this had to be re-diagnosed from scratch rather than
read off the log.

### Shape of the fix

Driven by the measurements above, this is a **script-side** fix:

1. **Bound every probe call** so the deadline is real. A `+list` that hangs must
   cost one poll interval, not the whole window.
2. **Key the verdict on the process too.** The script started the exe itself and
   holds its pid; "did not come back up" must mean *the process is gone*, not
   merely *IPC has not answered yet*. A live process with slow IPC gets more
   time (the measured worst case is ~11 s; the deadline should sit far above it).
3. **Log every failed poll** — exit code and first line of output — so a
   recurrence is read off the log instead of re-measured.

The pre-loop `restoreSessionLayout` latency is real but small and bounded; it is
filed separately rather than fixed here, since the numbers say it is not this
bug.

### What landed

- `scripts/loop-session.ps1` — new `Invoke-GhozttyListJson -Exe
  -WorkingDirectory -TimeoutSec`, one BOUNDED probe returning `@{Json; Why}`.
  It lives in the shared lib rather than inside the upgrade script precisely so
  it can be driven by a test with a stand-in executable.
- `scripts/upgrade-ghoztty-windows.ps1` — `Get-ListJson` delegates to it;
  `Wait-Instance` takes the started process, logs the first failure and then
  every ~15 s, bails immediately if that process EXITED, and the reuse deadline
  goes 60 s → 180 s (the measured worst case is ~11 s, and the cost of calling a
  live app dead is a stalled loop). The `RESUME-REUSE FAIL` line now says WHICH
  of "process exited" / "process alive but IPC unreachable" happened — the old
  one asserted the first while the truth was the second.

### Validation

`upgrade-no-fork.ps1` section A gains **A22–A30**, driving the probe with
stand-in executables: a `.cmd` that sleeps 30 s must return within its own 3 s
bound and say `hung` (pre-fix this blocked for the callee's duration — the whole
defect); a `.cmd` that exits 1 must surface `exit=1` *and* its first output line
so the log explains itself; a healthy payload passes; `exit 0` with junk is
still not ready. `-PureOnly` ALL PASS. Full suite (sections B–D drive the real
script end-to-end through reuse and relaunch) re-run to prove the refactor did
not disturb the decision paths.
