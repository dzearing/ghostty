# T1268 - The update-apply harness can rename the repo build's ghoztty.exe aside and never put it back

## Summary

Section 8 of `test\win32\update-apply.ps1` arms the applier with
`GHOZTTY_UPDATE_APPLY = "<dead pid>|<fake msi>|<repo exe>"`, so the applier's
INSTALLDIR is the REAL `zig-out\bin`. If `ghoztty.exe` is locked at that
moment — a straggler from an earlier acceptance script, say — the applier does
what it is designed to do and RENAMES it aside (`ghoztty.exe.old-<n>`) so
msiexec can write a fresh one. The package is the fake one, msiexec rejects it
with 1620, and nothing ever writes `ghoztty.exe` back. The relaunch then fails
with `FILE_NOT_FOUND`, section 9 dies with `CreateProcessW failed: 2`, and the
turn is left with no build output at all.

Observed on 2026-09-01 during T1243's guard sweep: the run left
`zig-out\bin\ghoztty.exe.old-1788324281` and no `ghoztty.exe`; renaming it back
by hand made the same script pass 42/42. So the failure is not the applier
misbehaving — it is the harness pointing a destructive operation at the one
binary the rest of the turn depends on.

## In plain terms

A test that exercises "install an update" is allowed to move the freshly built
Ghoztty out of the way and then leave it there, because the fake installer it
uses always fails. When that happens, everything afterwards looks broken for a
reason that has nothing to do with the code being tested.

## Goals

- [x] Section 8 stops using `zig-out\bin` as the applier's install directory
- [x] The harness leaves the repo build exactly as it found it, even on a red run
- [x] A locked exe at section 8 no longer decides whether the run is destructive

## Details

The fix is to give the applier a throwaway INSTALLDIR — a scratch directory
under `$work` holding a COPY of `ghoztty.exe` — the way `update-real-msi.ps1`
already uses a sandboxed product identity for exactly this reason. The
assertions in sections 8 and 9 (`relaunched … ghoztty.exe as pid`, "the
terminal is still where it was") all read the applier's own log and hold just
as well against a copy.

A belt-and-braces second half: a `finally` that restores any
`ghoztty.exe.old-*` left in `zig-out\bin`, so a future harness that reaches
the same state cannot strand the build either.

## Validation criteria

- [x] `test\win32\update-apply.ps1` passes with `zig-out\bin\ghoztty.exe` held open by another process for the whole run - ALL PASS (52 assertions); the exe was held by a FileShare.Read handle for all three runs
- [x] After that run, `zig-out\bin\ghoztty.exe` exists and no `ghoztty.exe.old-*` remains - and it is section 11 of the harness that says so, not a human remembering to look
- [x] Sections 8 and 9 still assert the relaunch and the refusal, against the copy - both green; section 9 runs the applier out of the sandbox install dir, so a regression in the refusal costs a copy
- [x] A deliberately failed run (negative control) also leaves the repo build intact - `-NegativeControl` plants the 2026-09-01 stray after the applier arms: 1 FAILED / 51 passed, exit 1, no stamp, build still in place
