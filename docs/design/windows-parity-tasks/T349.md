# T349 - the download page offers no Windows terminal build

## Summary

`https://dzearing.github.io/ghoztty/` (the `gh-pages` branch) has exactly
one product download: `releases/download/v1.28.0/Ghoztty-1.28.0-arm64.dmg`.
The word "Windows" appears nine times on the page and every one of them is
either prose about the CLI or the **Remote Agent** section - which offers
the agent MSI from the relay, a different product from the terminal. A
visitor on Windows can read a page that describes a Windows terminal and
leave with nothing to run.

That was defensible while the Windows build was published by hand and 24
releases behind (win-v1.4.1 against v1.28.0): a download button pointing at
a year-old build is worse than none. **T38 removed the excuse** - every
`vX.Y.Z` tag now publishes `Ghoztty-<version>-x64.msi` and
`Ghoztty-portable-<version>-x64.zip` to `win-v<version>` automatically, so
the page can link a build that is always current.

## Details

The site is a `gh-pages` worktree edited by hand at release time
(`.claude/commands/release.md` Step 7), so this is two pieces of work:

- **The page**: a Windows download alongside the macOS one - MSI as the
  primary action, portable ZIP as the secondary ("no installer"), pointing
  at `releases/download/win-v<version>/...`. Match the existing button
  treatment; do not invent a second visual language for it. Note the page
  already has a live-fetch pattern for the agent's version badge (it reads
  the relay's `version.json`), so the alternative to hardcoding is fetching
  the newest `win-v*` release from the GitHub API and filling both hrefs -
  which would make this the one download on the page that never goes stale.
  Prefer that if it stays simple.
- **Step 7 of the release command**, which today says to replace the old
  version everywhere and explicitly says NOT to touch the Remote Agent
  section. It needs to say what to do with the Windows terminal links -
  nothing, if they are fetched live; one more substitution, if they are not.

Worth deciding at the same time: whether the page should say the Windows
build is unsigned (SmartScreen will warn), the way the portable ZIP's
READ-ME-FIRST does. A download that trips a scary dialog with no warning
reads as broken.

*Validation:* the published page offers both Windows artifacts, both links
return HTTP 200 for the current release, and a release run leaves them
pointing at that release (not the previous one).

## In plain terms

Someone on Windows lands on the Ghoztty site and wants to try it. They need
a download button that gives them something that runs, and they need to know
in advance that Windows will pop a scary "Windows protected your PC" box the
first time they open it — because the natural response to that box is to
click Cancel and assume the download was broken.

## Goals

- [x] The page offers a Windows installer alongside the macOS one, with a
      portable-ZIP alternative for people who do not want an installer.
- [x] The links are kept current by the release itself, not by someone
      remembering to edit the page.
- [x] The page warns about the unsigned-build SmartScreen dialog and says
      which two things to click, before the user downloads rather than after.
- [x] The copy of the page kept in the repo matches the page that is
      actually deployed.

## What landed (2026-08-07)

Most of this task was already done when it was picked up, by **T39** — the
Windows download card, the portable-ZIP alternative, the minimum-OS note,
the release-time link rewrite (`dist/website/update-windows-links.py`, run
by `release-windows.yml` right after it publishes) and the acceptance script
`test/win32/website-windows-download.ps1`. T39 also settled the "fetch live
from the GitHub API vs rewrite at release time" fork this task's Details
left open, and settled it the other way, with a stronger reason than this
task assumed: `win-v` releases are published `--latest=false` on purpose, so
there is no stable "latest" URL to fetch, and a rewrite has no runtime
dependency on an unauthenticated 60-req/hr API and works with JS off. That
decision stands; nothing here relitigates it.

What was actually left:

- **The unsigned/SmartScreen caveat**, which this task raised and T39 did
  not do. One more `.download-note` line under the Windows note — same dim
  centered treatment, no new CSS — naming the dialog verbatim
  (`"Windows protected your PC"`) and the two clicks that get past it
  (**More info** → **Run anyway**). The portable ZIP's READ-ME-FIRST has
  said this since T38, but that file is only readable *after* the download;
  the page is where someone decides whether to download at all. Deployed as
  gh-pages `d7586718e`.
- **The in-repo mirror had drifted a third time** — `relay/deploy/ghpages/
  index.html` sat at macOS `v1.28.0` against `v1.31.0` live, so check F of
  the acceptance script was already failing before this task started. Synced,
  and Step 7 of `.claude/commands/release.md` now spells the mirror out as a
  whole-file `cp` after a `git pull --rebase` rather than a prose aside: the
  drift keeps happening because `release-windows.yml` pushes its own commit
  to gh-pages in the same release, so re-typing just the macOS edit by hand
  reproduces the drift by construction.
- **New assertions** A15/A15b/A15c/A15d and A16 in
  `test/win32/website-windows-download.ps1` — the caveat exists, names the
  dialog, says what to click, does not claim the build is signed, and reuses
  the existing `.download-note` class rather than inventing one.

**The finding this turned up is bigger than the task**: the release
automation has never once run. `release-windows.yml` exists only on this
parity branch, not on `origin/main`, and tags are cut from `main` — so the
newest Windows release is still the hand-published `win-v1.4.1` from
2026-07-19 while macOS is at `v1.31.0`. Every link on the page answers 200,
which is why it stayed invisible; they answer with a three-week-old build.
Filed as **T577** (P0, M1).
