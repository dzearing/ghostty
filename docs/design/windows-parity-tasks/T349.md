# T349 - the download page offers no Windows terminal build

## Summary

`https://dzearing.github.io/ghoztty/` (the `gh-pages` branch) has exactly
one product download: `releases/download/v1.28.0/Ghoztty-1.28.0-arm64.dmg`.
The word "Windows" appears nine times on the page and every one of them is
either prose about the CLI or the **Remote Agent** section - which offers
the agent MSI from the relay, a different product from the terminal. A
visitor on Windows can read a page that describes a Windows terminal and
leave with nothing to run.

That was defensible while the Windows build was published by hand and 24
releases behind (win-v1.4.1 against v1.28.0): a download button pointing at
a year-old build is worse than none. **T38 removed the excuse** - every
`vX.Y.Z` tag now publishes `Ghoztty-<version>-x64.msi` and
`Ghoztty-portable-<version>-x64.zip` to `win-v<version>` automatically, so
the page can link a build that is always current.

## Details

The site is a `gh-pages` worktree edited by hand at release time
(`.claude/commands/release.md` Step 7), so this is two pieces of work:

- **The page**: a Windows download alongside the macOS one - MSI as the
  primary action, portable ZIP as the secondary ("no installer"), pointing
  at `releases/download/win-v<version>/...`. Match the existing button
  treatment; do not invent a second visual language for it. Note the page
  already has a live-fetch pattern for the agent's version badge (it reads
  the relay's `version.json`), so the alternative to hardcoding is fetching
  the newest `win-v*` release from the GitHub API and filling both hrefs -
  which would make this the one download on the page that never goes stale.
  Prefer that if it stays simple.
- **Step 7 of the release command**, which today says to replace the old
  version everywhere and explicitly says NOT to touch the Remote Agent
  section. It needs to say what to do with the Windows terminal links -
  nothing, if they are fetched live; one more substitution, if they are not.

Worth deciding at the same time: whether the page should say the Windows
build is unsigned (SmartScreen will warn), the way the portable ZIP's
READ-ME-FIRST does. A download that trips a scary dialog with no warning
reads as broken.

*Validation:* the published page offers both Windows artifacts, both links
return HTTP 200 for the current release, and a release run leaves them
pointing at that release (not the previous one).
