# T174 - Per-host remote defaults store + Host Settings dialog on Windows (T140 split 3/3)

## Summary

Split out of T140. Mac keeps per-host defaults (default working directory +
default shell, keyed by relay device id or host:port) in UserDefaults, edits
them from the chooser's row menu ('Host Settings...'), and applies them to new
remote windows AND to new tabs/splits on a remote window. Windows had NO such
store - Window.zig:849 said so in a comment ('No per-host default shell store on
win32 (yet)'), so a remote tab/split always fell back to the machine default.

DONE 2026-07-30. Three new pieces plus three wiring sites:

- **`host_defaults.zig`** - the store. `Settings{working_directory, shell}`, a
  `Key` union (relay device id, else `host:port` - Mac's `settingsKey`, host NOT
  normalized so the two platforms key a machine identically), normalize/parse/
  stringify, and a `Resolved` fixed-size holder so a call site can carry one
  machine's defaults across a dial without an allocation or a live store. Pure
  except four IO functions; 20 unit tests.
- **`HostSettingsDialog.zig`** - the editor. `ConfirmDialog`'s synchronous
  nested-pump shape (owner disabled, renderer + IPC stay live) with Mac's
  two-row accessoryView: a right-aligned label column, a working-directory EDIT,
  and an EDITABLE combo box carrying Mac's exact 6 shell presets, plus
  Save/Cancel. Pure layout math with 8 tests.
- **`chooser_menu`'s gate flipped** - `HOST_SETTINGS_AVAILABLE = true`, and
  `MachineChooser.promptHostSettings` seeds the dialog from the store and writes
  it back. Keyed on the DEVICE ID, so renaming a machine cannot orphan its
  settings.

Where the defaults apply (Mac's rule, deliberately not "everywhere"):

- **A new remote window takes BOTH** cwd and shell - seeded in
  `App.openDialedWindow`, the ONE remote-open tail, so the chooser, the T68
  inheriting re-dial and `+new-remote-window` all get it from a single site
  (Mac needs two: AppDelegate 1562 + 1869). Explicit values always win.
- **A tab/split on a remote window takes the SHELL ONLY** -
  `Window.buildRemoteInherit`. Its cwd inherits from the parent pane, because a
  per-host default cwd must not yank a split away from where its parent is
  (Mac `BaseTerminalController.newSplit` / `TerminalController`).
- **The local session-persistence agent is excluded**: it is this machine, not
  a "host" with defaults.

Storage: `%LOCALAPPDATA%\ghoztty\host_defaults[-debug].json`, overridable in
full by `GHOSTTY_HOST_DEFAULTS` (the `GHOSTTY_ACCOUNT_STORE` pattern - how the
acceptance script points the app at a scratch file instead of the user's real
settings). A file under LOCALAPPDATA rather than the registry because that is
the win32 analog this codebase already uses for app-owned preferences
(`window_memory.zig`, `update_check.zig`, `account.dat`). Never purged on
sign-out - these are local preferences, not account resources.

## Details

Two things worth keeping:

**The store is never allowed to fail loudly.** A corrupt, truncated or
hand-edited file parses to an EMPTY store (Mac's `try? JSONDecoder` rule), blank
rows and duplicate keys are dropped on read, and clearing both fields REMOVES
the row rather than storing two empty strings - so the file cannot accumulate
blanks and one bad write cannot wedge remote windows. Over-long values are
refused rather than truncated: half a path silently used as a cwd is worse than
no default (the `ConfirmDialog.readEdit` rule).

**`RemoteInherit.shell` is heap-owned, not an inline buffer.** The struct is
returned BY VALUE, so a pointer into its own bytes would dangle the instant it
was copied out to the caller's `inherit` local. It is freed alongside `cwd` in
the same `deinit`.

Two win32 details the dialog needed:

- The drop-down owns Enter and Escape while it is OPEN. Without that guard,
  picking a preset with the keyboard would also save-and-close the dialog behind
  the list. `CB_GETDROPPEDSTATE` decides; the acceptance script asserts both
  keys individually.
- Keyboard focus inside an editable combo lands on its inner EDIT, not on the
  combo, so both `ownsHwnd` (which decides whether the nested pump routes a key)
  and the Tab cycle resolve that child back to the combo's stop via `GetParent`.

The harness trap that cost the time: **`+send-keys` translates escapes in its
text**, so an absolute Windows path is not safe to send verbatim - the script's
`...\t174-elsewhere` arrived as a literal TAB (`\t`), cmd tab-completed
something else, the `cd` silently did not happen, and the split-cwd assertion
read as a product bug. Backslashes are doubled now, and the script proves the
parent actually moved before asking where its split landed.

## Validation

- **New `test/win32/host-settings.ps1` ALL PASS (61) x3** (plus 3 further
  back-to-back runs green after one flaky menu-open was hardened with a retry).
  Section A drives the REAL GUI against a fake relay: the menu now leads with
  `Host Settings...`, the dialog's two fields + 6 presets + Save/Cancel, F4
  opens the drop-down, Escape and Enter close the LIST and not the dialog,
  picking the first preset yields `cmd.exe`, Cancel writes nothing, Save writes
  `{"key":"dev-e2e","working_directory":"C:\\t174-wd","shell":"wsl.exe"}`,
  reopening seeds both fields, clearing both removes the entry. Fields are read
  with `WM_GETTEXT`, never a cross-process `GetWindowTextW` (the T176 trap).
- Section B drives a REAL loopback `ghoztty-agent`: it first MEASURES the box's
  default shell from the pane banner, then asks the store for the other one, so
  the assertion proves the store changed the shell rather than matching whatever
  this box defaults to. A new remote window lands in the stored cwd with the
  stored shell; an explicit `--working-directory` beats the store; a split takes
  the stored shell but keeps the parent's LIVE cwd (a second cmd-shell window is
  used for that half, because PowerShell's `Set-Location` deliberately does not
  move the OS process cwd and the inheritance is a GET_CWD on the child).
- `chooser-menu.ps1` updated for the 3-item menu (shape + one extra DOWN per
  keyboard walk) - ALL PASS (33). `ipc-machine-chooser.ps1`, `relay-account.ps1`,
  `confirm-dialogs.ps1` re-run green.
- Both test lanes (`-Dapp-runtime=none`, `-Dapp-runtime=win32`) exit 0,
  `zig build test-agent` exits 0, P1-P3 ALL PASS.
