# T188 - win32 restoreSessionLayout runs before the message loop, so IPC is dead for the whole restore (measured 451ms healthy, 10.7s vs a wedged agent)

## Summary

Split out of **T187**, which measured it and then proved it was NOT that
defect's cause — so it is recorded here on its own merits rather than fixed
opportunistically.

`src/apprt/win32/App.zig` binds the IPC pipe early (`App.init`) but `run()`
calls **`restoreSessionLayout()` synchronously before `GetMessageW`**. The pipe
therefore exists — a client connects and waits — while nothing accepts or
handles until the message loop starts. Every `ghoztty +…` issued during that
window gets nothing, or blocks: the same user-visible class T111b fought ("No
running Ghoztty instance found." from a running app).

**Measured on the box (debug build, hermetic state, app killed and relaunched
with the agent left alive):**

| scenario | panes | time to first successful `+list --json` |
|---|---:|---:|
| cold start, no manifest | 1 | 427 ms |
| restore, healthy agent | 5 | 451 ms |
| restore, agent SUSPENDED across the relaunch (40 s) | 4 | 10 755 ms |

So the exposure is small in the normal case and **bounded** even against a
completely wedged agent (restore gives up and the loop starts). That is why
this is a robustness item, not an outage: nobody has reported it, and T187's
60 s blackout was something else.

Worth fixing anyway, because the bound is a timeout rather than a design: a
larger layout, a slower disk, or a future restore step that waits on something
new all extend a window in which the app is running and unreachable. The fix
is the T48 pattern — post the restore into the message loop and run it from
there, so IPC is serviced throughout — and the validation is the measurement
above, asserting time-to-first-`+list` stays flat as pane count grows and when
the agent is suspended (the harness for both is in T187's evidence).
