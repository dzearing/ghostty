# T188 - win32 restoreSessionLayout runs before the message loop, so IPC is dead for the whole restore (measured 451ms healthy, 10.7s vs a wedged agent)

## Summary

Split out of **T187**, which measured it and then proved it was NOT that
defect's cause — so it is recorded here on its own merits rather than fixed
opportunistically.

`src/apprt/win32/App.zig` binds the IPC pipe early (`App.init`) but `run()`
calls **`restoreSessionLayout()` synchronously before `GetMessageW`**. The pipe
therefore exists — a client connects and waits — while nothing accepts or
handles until the message loop starts. Every `ghoztty +…` issued during that
window gets nothing, or blocks: the same user-visible class T111b fought ("No
running Ghoztty instance found." from a running app).

**Measured on the box (debug build, hermetic state, app killed and relaunched
with the agent left alive):**

| scenario | panes | time to first successful `+list --json` |
|---|---:|---:|
| cold start, no manifest | 1 | 427 ms |
| restore, healthy agent | 5 | 451 ms |
| restore, agent SUSPENDED across the relaunch (40 s) | 4 | 10 755 ms |

So the exposure is small in the normal case and **bounded** even against a
completely wedged agent (restore gives up and the loop starts). That is why
this is a robustness item, not an outage: nobody has reported it, and T187's
60 s blackout was something else.

Worth fixing anyway, because the bound is a timeout rather than a design: a
larger layout, a slower disk, or a future restore step that waits on something
new all extend a window in which the app is running and unreachable. The fix
is the T48 pattern — post the restore into the message loop and run it from
there, so IPC is serviced throughout — and the validation is the measurement
above, asserting time-to-first-`+list` stays flat as pane count grows and when
the agent is suspended (the harness for both is in T187's evidence).

## In plain terms

When Ghoztty starts up and puts your old windows back, the app is alive but
deaf: any `ghoztty +…` command a script or an agent fires during those first
few hundred milliseconds just sits there waiting, and against a sick
background agent it can wait ten seconds. Nothing tells the caller the app is
merely busy, so tooling reports "no running Ghoztty" about an app that is
right there on screen. After this, commands are answered while the restore is
still going on, so the startup window stops being a blind spot.

## Goals

- [x] IPC requests are served *during* session restore, not only after it
- [x] The worst case (a wedged/suspended agent) no longer holds IPC hostage
      for the whole dial timeout
- [x] A restore that services IPC cannot spawn a second agent by re-entering
      the agent resolve
- [x] An on-box harness measures time-to-first-`+list` for cold start,
      multi-pane restore, and a suspended agent

## Progress log

- 2026-08-08 17:55: claimed; work starting.
- 2026-08-08 18:00: root cause confirmed by reading the code, and the task's own prescribed fix does NOT work: IpcServer listener threads accept the connection and PostMessage WM_APP_IPC to the message-only hwnd, then BLOCK on Pending.done. So a request is served only when the GUI thread pumps. Merely posting restoreSessionLayout into the message loop (the T48 pattern the task suggests) changes when restore starts, not whether the GUI thread pumps during it - the handler still blocks the loop for the whole restore. Fix instead: a GUI-thread IPC pump (PeekMessageW filtered to WM_APP_IPC, the same drain IpcServer.deinit already does) called at the blocking points - LocalAgent.findOrSpawn's spawn poll loop (where the 10.7s wedged-agent case lives) and between windows/probe steps in restoreSessionLayout - plus a LocalAgent re-entrancy guard so an IPC-created window served mid-dial cannot re-enter findOrSpawn and spawn a second agent.
