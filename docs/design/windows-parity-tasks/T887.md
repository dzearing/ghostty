# T887 - Sharing uplink e2e: a session opened over a fake relay control channel must land in the SAME sessions.json the local pipe serves

## In plain terms

The point of "share this machine" is that a terminal you open from your laptop
is the same terminal you find waiting when you sit down at the desktop — one
list of sessions, not two. Today that is true because of how the code is
wired, not because anything has ever watched it happen: the existing test only
proves the machine calls home to the relay. This adds the missing half — drive
a session in over a stand-in relay, then ask the machine locally what sessions
it has, and see the same one.

## Goals

- [x] a loopback stand-in for the AGENT side of the relay (control channel +
      per-session data channel) that a test can drive
- [x] a session opened purely over that relay shows up in the local
      `+sessions` listing, by id
- [x] the same session is in the on-disk `sessions.json` the local pipe serves
- [x] it survives the remote client detaching
- [x] a negative control: with sharing switched off, nothing new arrives

## Summary

T546 landed the sharing uplink — the local session agent raises the relay
control loop in-process, over the same `SessionStore` the local pipe serves —
and `test\win32\agent-sharing-uplink.ps1` proved the DIAL half of it: an
enabled `sharing.json` produces a real `GET /v1/agent/control` at a loopback
listener with the relay.env bearer token, a disabled one parks it. What no
test reached was the payload half: the loopback listener answered 404, so
nothing had ever come DOWN the control channel, and "one store serves both
transports" rested on reading `serveControl` → `RelayWorker` → `serveOne`
rather than on evidence.

This task closes that with an on-box e2e. New `test\win32\lib\FakeAgentRelay.ps1`
is the agent-side half of the relay (`FakeRelay.ps1` is the client-side half
and stays untouched): one job, two loopback listeners.

- The **relay origin** the agent dials: a real RFC 6455 upgrade on
  `/v1/agent/control`, and another on `/v1/agent/data?session=<id>`.
- An **entry port** standing in for "a client asked this machine for a
  terminal": a raw TCP connect there mints a rendezvous id, sends
  `{"type":"open","session":"<id>"}` down the live control WebSocket, waits
  for the agent's answering data dial, and then bridges the two as a byte
  pipe (unmasking the agent's client frames, sending unmasked server ones —
  the same rules `FakeRelay.ps1` documents).

`test\win32\agent-relay-session-e2e.ps1` then drives the real thing:
`remote-test-client.exe 127.0.0.1 <entry> --hold=N` OPENs a session over that
relay and prints the agent-minted session id, and the same run asks the LOCAL
pipe — through the real `ghoztty +sessions` CLI, resolved from a suffixed
lineage's `port.json` — what it has. The claim is proved when both name the
same id, and the id is in the `sessions.json` on disk.

## Validation criteria

- [x] `+sessions` over the local pipe reports an empty roster before the relay
      is driven (baseline; harness section 2)
- [x] the agent's control dial reaches the fake relay and is UPGRADED, not
      404'd (section 1: `CONTROL up`, with the relay.env bearer token)
- [x] a client arriving at the entry port produces `{"type":"open"}` on the
      control channel and an answering `GET /v1/agent/data?session=<id>` from
      the agent (section 3: `OPEN sent` / `DATA up`)
- [x] the session id printed by the remote client is listed by `ghoztty
      +sessions` over the LOCAL pipe while the client holds it (section 4 —
      THE CLAIM)
- [x] the same id appears in the on-disk `sessions.json` the local pipe's
      store persists to (section 4)
- [x] the session survives the remote client detaching (section 5)
- [x] negative control: with `sharing.json` disabled, a second entry
      connection produces no new data dial and no second session in the store
      (section 6)
- [x] guard-due row added so a later edit to the uplink/control/worker code
      marks this harness DUE (`guard-due.ps1 check` names it)
