# T257 - Chrome geometry datum is re-derived per acceptance script; hoist caption/strip/tab-run measurement into TestDesktop.ps1

## Summary

**T256 is the second time one chrome geometry change broke acceptance scripts
that each re-derived the same datum privately.** T254 moved the tab strip off
client `y = 0` and cost 7 failures in `tab-strip.ps1` and 19 in `menu-bar.ps1`;
T235 changed what sizes a tab and cost 4 more in `menu-bar.ps1` alone. In both
cases the app change was one number in one place.

After T256 the two scripts each carry their own copy of:

- the caption band's height (`2 * round(4 * scale) + round(28 * scale)`),
- the strip's height (`3 * round(4 * scale) + round(28 * scale)`),
- the strip's top as a window-relative y,
- the right-anchored button band (`padR` + the 28 DIP painted square),
- and — in different forms — a pixel scan that finds the tab run's right edge.

`tab-strip.ps1` finds it as the longest content-black run at `barH - 2`;
`menu-bar.ps1` scans leftward from the menu button for the first non-strip
pixel. Same measurement, two implementations, two chances to be wrong.

`pane-banner.ps1`, `context-menu.ps1` and the other capture-based scripts have
their own variants of the same y math and should be audited in the same pass.

## The fix

Hoist it into `test/win32/lib/TestDesktop.ps1` next to `Get-TestWindowDpi`:

- `Get-TestChromeMetrics -Window <hwnd>` → `{ Scale, CaptionH, BarH, StripTop,
  PadL, PadR, Gap, BtnPaint, MenuLeft }`, all derived from the window's own DPI
  by the same construction the layout modules use.
- `Get-TestTabRunRight -Window <hwnd> [-Shot <shot>]` → the last tab's painted
  right edge, measured once, the way `Strip-Geometry` does it now.

Then T205 — which moves the strip INTO the caption row and will invalidate
`StripTop` again — is one edit in the library plus whatever assertions genuinely
change, instead of a script-by-script hunt.

## Validation

- `tab-strip.ps1`, `menu-bar.ps1`, `caption-bar.ps1`, `pane-banner.ps1` and
  `context-menu.ps1` ALL PASS with their negative controls still failing, with
  no private copy of the datum left in any of them.
- P1-P3 ALL PASS.

## Outcome (2026-07-31)

Done, with **T259** in the same pass as that task asked. The hoist landed in a
new `test/win32/lib/ChromeGeometry.ps1`, dot-sourced from the end of
`TestDesktop.ps1` — a sibling rather than 200 more lines in a file already at
1910, and every script that loads TestDesktop gets it with no second load line.

Two API entry points, and the split between them is the point of the file:

- `Get-TestChromeMetrics -Window` — everything DERIVED, from the window's own
  DPI by the same construction the layout modules use: `Scale`, `PadSm`,
  `PadMd`, `Gap`, `BtnPaint`, `BtnPad`, `BtnW`, `CaptionH`, `BarH`, `PadL`,
  `PadR`, `TabGap`, `TabTopPad`, `MinTabW`, `CornerR`, `TextPad`, `StripeH`,
  `Hairline`, the client rect and its window-relative origin (`OffX`/`OffY`),
  `StripTop` / `StripTopClient`, `MenuLeft`, `MenuX`, `PlusLimit`, `RunW`,
  `TabCap`.
- `Get-TestTabExtents` / `Get-TestTabRunRight` — MEASURED off a capture,
  because a tab's width comes from text metrics and a script cannot re-derive
  it (T235/T256). `Get-TestTabExtents` generalized T256's single leftward scan
  into every chiclet's `{Left, Right, Center}`, which is what let T259 click
  tab N without modelling a width; `Get-TestTabRunRight` is now the last
  extent's right edge, so there is ONE scan implementation, not two.

Private copies removed from **four** scripts, not the two the task scoped:
`tab-strip.ps1`, `menu-bar.ps1` (its `Caption-Height` is a one-line wrapper and
`Strip-Geometry` shrank from ~55 lines to ~15), plus `tab-strip-autohide.ps1`
and `tab-color.ps1`, which the write-up had not counted. `caption-bar.ps1`'s
`Px()` went too — deliberately keeping its measured-vs-derived oracle, which is
now the one place the shared derivation is checked against real pixels.

**A latent bug fell out of the hoist.** The layout modules round with Zig's
`@round` (half away from zero); `[math]::Round()` in PowerShell is BANKER'S
rounding. `menu-bar.ps1` passed `MidpointRounding::AwayFromZero`;
`tab-strip.ps1`, `tab-color.ps1`, `tab-strip-autohide.ps1` and
`caption-bar.ps1` did not. They agree at 100/125/150/200% (nothing lands on
.5, which is why nobody noticed) and disagree at **112.5%**, where `4 * 1.125`
is 4 in PowerShell and 5 in the app. One rounding now, in
`Get-TestChromeDip`, matching the app.

Two assertions got STRONGER rather than just relocated, both where a loose
bound existed only because the exact number was not reachable without a fifth
private copy:

- `tab-strip-autohide.ps1`: "a plausible strip" was `barH` between 30 and 56
  DIP; it is `-eq $m.BarH` now, so a strip returning at the wrong height fails.
- `tab-color.ps1`: `barH` between 20 and 80 became `-eq $m.BarH` (see T259).
