# T466 - A dead-but-relaunchable session is listed in the chooser roster with no way to revive it

## In plain terms

The machine chooser lists sessions you can take over. It also lists sessions
whose process is already gone — kept because the command they were running
is worth reading — but selecting one does nothing: Resume only works on a
live session. So the list contains rows that look like offers and are not.
Either those rows should offer to start the recorded command again, or they
should not be in the list.

## Goals

- [ ] A dead-but-relaunchable row either (a) offers a Relaunch action that
      restarts its recorded command, or (b) is not listed as a resumable row
- [ ] Whichever way it goes, a row in the roster that cannot be acted on does
      not look like one that can
- [ ] `docs/design/windows-parity-tasks.md` and CLAUDE.md's "Browsing and
      resuming sessions from the chooser" section describe the behavior that
      actually ships

## Evidence

`src/apprt/win32/chooser_sessions.zig:53-65` — `isConnectable` keeps a
session when `alive or relaunchable`, and the comment is explicit that a
dead, non-relaunchable tombstone is "an unreconnectable dead end — filtered
out as a client-side backstop" to the agent's own reaper. That half is
already right, on both sides: the agent reaps dead+unbound tombstones
(`src/remote/agent/server.zig:470-493` and `:1104-1119`).

What is left is the relaunchable tombstone. `isResumable`
(`chooser_sessions.zig:321-328`) is deliberately NOT `isConnectable` — it
collapses to `alive` — and CLAUDE.md states the rule outright: *"Dead-but-
relaunchable rows are listed — their recorded command is worth seeing — but
cannot be resumed; reviving one is a RELAUNCH, a different verb."* The verb
exists in the agent protocol. Nothing in the chooser calls it.

## The judgement this needs

Listing a row for its information value is a real argument, and so is the
user's ask that started this ("don't show me a bunch of sessions that can't
be restored"). Offering Relaunch satisfies both and is more work; hiding the
rows satisfies the ask and loses the recorded command. File a decision
(`scripts\parity-decisions.ps1`) rather than picking silently — and mirror
whatever wins on the Mac seat, since the roster is the same dialog there.

## Validation

- `none`-lane unit tests over `isResumable`/`isConnectable` for the chosen
  behavior, including the tombstone case.
- `test/win32/` acceptance: produce a relaunchable tombstone (kill the agent
  with a live session, restart it), open the chooser, and assert the row
  behaves as decided.
