# T279 - Audit PowerShell call sites that put free text on a ghoztty CLI argv (rename --title, set-banner): PS 5.1 silently strips quotes

## In plain terms

When one of our scripts hands the terminal a piece of text — a window title, a
status banner, the command to run in a new window — PowerShell mangles it on
the way if the text contains a double quote or ends in a backslash. Characters
disappear, the rest gets chopped into pieces, and everything reports success.
The real cost so far: every time the loop restarted itself, the instruction it
was meant to resume with was destroyed en route, and nothing anywhere said so.
After this, text arrives exactly as it was written.

## Goals

- [x] Enumerate the PowerShell call sites that hand the ghoztty CLI text a
      program composed, and say which can carry a quote or a trailing backslash
- [x] Pick a transport and prove it byte-exact against the real product
- [x] Fix the call sites that carry generated text
- [x] Write the rule down where the next caller will read it (CLI doc comments
      + CLAUDE.md)
- [x] An acceptance script that measures it, with the naive transport alongside
      as a negative control

## Summary

T210 fixed ONE call site — the resume prompt into `+send-keys` — and gave the
CLI a file transport (`--keys-file`) to fix it with. The underlying hazard is
not specific to `+send-keys`: **PowerShell 5.1 does not escape an embedded `"`
when it builds a native command line**, so ANY free text a PowerShell script
hands to `ghoztty.exe` as an argument is at risk, silently.

Measured on the box 2026-08-01 (argv oracle, `python -c` printing `sys.argv`):

| payload | what the child received |
|---|---|
| `pct %LOCALAPPDATA% and plus + and dash -Flag` | intact |
| `single 'quotes' inside` | intact |
| `has a " quote in it` | child never ran |
| `a "quoted phrase" mid string` | child never ran |
| `trailing backslash dir\` | child never ran |

And through `ghoztty +send-keys`, `/reset-context settle the
"DWM/PrintWindow" question ...` arrived **2 characters short with both quotes
gone** — quietly, exit 0.

## Which call sites

The ones that carry text a human or another program wrote, not a fixed literal:

- `+rename --title=<text>` — `scripts/go-loop-exec.ps1` `Set-Mark` builds
  `"--title=$Marker $Label"`; `$Label` is a parameter.
- `+set-banner <text>` — the banner is markdown a caller composed, with `|`
  tables and `[text](url)` links; `~/.claude/scripts/ghoztty-banner.sh` is bash
  (different rules) but any PowerShell caller has this problem.
- `+new-window --title=` / `--command=` / `--working-directory=` with paths that
  can end in `\` (a trailing backslash is the second half of the trap: it makes
  the CRT read the closing quote as escaped).
- `+split --command=`, `+new-remote-window --command=`.
- The acceptance scripts under `test/win32/` that pass titles/commands through.

Grep start: `Select-String -Path scripts\*.ps1,test\win32\*.ps1 -Pattern
'\+(rename|set-banner|new-window|split|send-keys|new-remote-window)'`.

## Deliverables

1. Enumerate every PowerShell → ghoztty CLI call whose argument is not a fixed
   literal, and say for each whether the text can contain `"` or end in `\`.
2. Decide the transport per verb. Two options, and the answer is probably both:
   - a `--<field>-file=<path>` for the verbs that carry long free text
     (`--title-file`, `--banner-file`), mirroring `--keys-file`; or
   - one shared PowerShell escaper for the short ones (`$s -replace
     '(\\*)"','$1$1\"' -replace '(\\+)$','$1$1'`), hoisted next to
     `New-LoopPromptFile` in `scripts/loop-session.ps1` so there is exactly one
     copy. Four copies of a rounding rule is what T257 was about.
3. Whichever is chosen, the CLI's own doc comment and CLAUDE.md say which
   transport is correct for generated text.

## What was measured (2026-08-11)

A `GetCommandLineW` oracle (a child printing both its raw command line and its
`sys.argv`) settles PowerShell 5.1's real rule, which is narrower and worse than
"it strips quotes":

- an argument is wrapped in `"` **only when whitespace appears at a position
  preceded by an EVEN number of `"` characters**;
- an embedded `"` is copied through **unescaped**.

| payload | what the child received |
|---|---|
| `--title=a "quoted phrase" mid string` | `--title=a quoted`, `phrase`, `mid`, `string` |
| `--title="leading quoted phrase" then more` | `--title=leading quoted phrase`, `then`, `more` |
| `--title=trailing backslash D:\my dir\` | `--title=trailing backslash D:\my dir"` |
| `--title=plain safe text` | intact |

**No escaper closes this.** Escaping `"` as `\"` leaves the `"` character in
place, so it still counts toward PowerShell's parity while the CRT no longer
treats it as structural. For text whose first whitespace is preceded by an ODD
number of quotes, PowerShell declines to wrap and the CRT splits the argument at
the spaces; the structural open quote that would fix that adds a second `"` and
flips the parity back. That is a proof about the shape of the problem, not a
failed attempt — a candidate escaper was written and measured first, and it
passes 17 of 18 payloads with exactly that class failing.

## The live defect this found

`upgrade-ghoztty-windows.ps1:905`/`:917` and `watchdog-ghoztty-windows.ps1:120`
passed the loop's own resume command on argv. Measured:

```
sent  --command=claude --dangerously-skip-permissions --continue "read go.md and go"
got   --command=claude --dangerously-skip-permissions --continue read
      go.md
      and
      go
```

So every relaunch after an upgrade or a freeze came up with `--continue read`
and no loop prompt, at exit 0, with `relaunched with resume: <the correct
string>` in the log. `go-loop-watchdog.ps1` had already met this and worked
around it with a generated `.cmd` shim, and its comment names the same symptom
("its log shows `--continue read`, the prompt truncated at the first space") —
so the defect was known at one site and unfixed at the other two.

## Call sites, and what each carries

| site | argument | can it carry `"` or end in `\`? |
|---|---|---|
| `upgrade-ghoztty-windows.ps1:905,917` | `--command=$ResumeCommand` | **yes, always** — fixed |
| `watchdog-ghoztty-windows.ps1:120` | `--command=$ResumeCommand` | **yes, always** — fixed |
| `go-loop-exec.ps1` `Set-Mark` | `--title=$Marker $Label` | yes (`$Label` is a parameter) — fixed via `Ghoz` |
| `go-loop-exec.ps1` `Send-Note` | `+send-keys` prose | already safe (T210 `--keys-file`) |
| `go-loop-watchdog.ps1:523` | `--command=$shim` | yes (a `$env:TEMP` path can hold a space) — fixed via `Invoke-Ghoztty` |
| `go-loop-watchdog.ps1:479-508` | `+send-keys` | already safe (T210) |
| both scripts' `--working-directory=$Repo` | a path | yes if it ends in `\` **and** contains a space — fixed with the rest |
| `task-dashboard.ps1` `+split` | fixed literals + a pane id | no |
| `test\win32\*.ps1` `--title=`/`--command=` | fixed literals (`P1Title`, `t145-recovery`, …) | no — a literal is composed by the author, and the shell they can see |
| `~/.claude/scripts/ghoztty-banner.sh` | banner markdown | out of scope: bash quotes correctly |

The pattern worth keeping: everything with a variable in it was fixed by
converting the SCRIPT'S ONE HELPER (`Ghoz`, `Invoke-Ghoztty`), not the
individual calls, so a call added later to those scripts is safe by default.

## Transport chosen

Build the command line ourselves and hand it to `CreateProcess` via
`ProcessStartInfo.Arguments` — `scripts\lib\NativeArgv.ps1`
(`ConvertTo-NativeArgToken` / `ConvertTo-NativeCommandLine` /
`Invoke-NativeExact`), dot-sourced by `loop-session.ps1` so the loop, the lock,
the upgrade and the watchdog share one copy. Total, and it fixes every flag of
every verb at once.

**No `--title-file` / `--banner-file` was added.** The defect is in our
PowerShell call sites, not in the product; a CLI flag is a cross-platform
obligation under the T141 rule, bought to work around one shell, and it would
need one flag per field forever. `--keys-file` stays the transport for a PROMPT,
whose bytes must skip key notation as well as quoting and can exceed a command
line's 32767-character cap. Filed as **D70** so the call can be overturned.

Bonus: `Invoke-NativeExact` settles T663 for its callers — reaching
`CreateProcess` directly captures a GUI-subsystem `ghoztty.exe`'s stdout with no
`2>&1` merge, so a stderr line can no longer land inside a `+list --json` a
script parses.
