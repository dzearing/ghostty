# T300 - The carousel is unreachable by Tab: keyboard focus only lands on it via a click in the panel

## In plain terms

The Activity Monitor has a row of machine cards along the top for switching
which computer it is watching. You could click one, but you could not get to it
with the keyboard: pressing Tab walked past the search box and the buttons and
never stopped on the cards. Anyone who does not use a mouse — or who simply had
their hands on the keys — had to reach for the mouse once before the arrow keys
would do anything. When this lands, Tab stops on the card strip like it stops on
everything else, the arrow keys (and Home/End) slide the highlight along it, and
Enter switches to the highlighted machine.

## Goals

- [x] Tab reaches the card strip from a freshly opened panel, with no click
- [x] Left/Right/Home/End move the highlight; none of them connect to anything
- [x] Enter or Space on the highlighted card switches the panel to that machine
- [x] A focused button still gets its own Space — the strip does not steal it

## Summary

T296's carousel has a real focus ring and real keys — Left/Right move the ring,
Return/Space commit — but they are live **only while the panel window ITSELF
holds focus** (`ActivityMonitor.handleKey`: `GetFocus() == self.hwnd`). The
panel opens with focus in the filter EDIT, so a keyboard-only user has no way to
GET there: Tab walks the native children (filter -> Show all -> New Process ->
Kill) and the carousel is not one of them, because it is painted, not a child
window.

So the switcher is mouse-reachable and, after a click anywhere in the panel
body, keyboard-drivable — but not keyboard-reachable from a cold open.

## Why the gate exists (do not just delete it)

The gate is load-bearing, not an oversight. Space and Return belong to whichever
BUTTON has focus; a switcher that swallowed them globally would make Kill and
New Process unpressable from the keyboard. Any fix has to keep that true.

## What was actually left to do (2026-08-07)

T289 landed first, as the ordering note below asked, and it took most of this
with it: the `GetFocus() == self.hwnd` gate is gone, `Focusable` /
`nextVisibleFocus` / the `VK_TAB` arm of `handleKey` are the written tab walk
(the panel is not a dialog, so nothing was inherited), and `open` ends with
`moveFocus(.filter)`. Cold-open Tab reach therefore already worked when this
task was claimed. Three things were still missing, and are what this task
shipped:

1. **Home/End on the carousel**, which the fix shape names and `handleKey` did
   not have. They are expressed as a full-length step through
   `activity_cards.focusFor`, so `moveFocus`'s clamp stays the ONE place the
   range is enforced — an edge key and an arrow key that ran off the same end
   cannot disagree about where the end is.
2. **An oracle.** Nothing said which focus stop held the keyboard, and the two
   owner-drawn stops (`carousel`, `table`) are both `self.hwnd`, so `GetFocus`
   answers the same for either. "Tab reached the carousel" had no observable
   until a *second* keystroke landed — which is precisely the claim an
   acceptance script needs to make on its own. `noteFocus` now logs
   `focus <old> -> <new>`, from the Tab path and from both mouse paths.
3. **The proof**: section F of `test/win32/activity-monitor-remote.ps1`, which
   drives the panel from a cold open with no click anywhere inside it.

## The shape of the fix

Give the carousel a place in the panel's tab order — most likely a real focus
STOP rather than a real child window, since the cards are painted:

- Tab from the last control lands "on the carousel", which paints its ring in
  an unmistakable focused state (T289 is the visible-focus task for the rest of
  the panel and should settle the visual language first — hence the ordering
  note below).
- While that stop holds focus, Left/Right/Home/End move the ring and
  Return/Space commit.
- Shift+Tab leaves it again.

Consider `WS_TABSTOP` on a zero-size child, or handling `WM_GETDLGCODE` on the
panel; whichever is chosen, the panel is NOT a dialog (no `IsDialogMessage`), so
the tab walk is the app message loop's job and has to be written, not inherited.

Order this after **T289** (visible keyboard focus in the panel) so there is one
focus treatment, not two.
