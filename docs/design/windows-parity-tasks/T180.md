# T180 - The hovered-URL bubble skips the T142 z-order heal (there is no pane drag preview)

> Filed as "Transient popups (pane drag preview) skip the T142 z-order heal".
> The site named in the original title is `setMouseOverLink`, not a drag
> preview, and the popup is not transient — see **What it actually was**.

## Summary

T142 gave the long-lived layered popups a z-order heal on every reposition
(`win32.healOverlayZOrder`): the banner strip, the dim overlay, the themed
scrollbar and the resize overlay. Two SHORT-LIVED popups were deliberately left
out and should be checked rather than assumed harmless:

- `Surface.zig:1532` — the pane drag preview, repositioned with `SWP_NOZORDER`
  as the pointer moves.
- `QuickTerminal.zig` (114/128/181) — intentionally `HWND_TOPMOST`, which is the
  legitimate case T142's owner-relative check exists to protect. Confirm it is
  never *reseated* by the heal (the quick terminal window IS the owner, so it
  should already fall into the "topmost owner, leave alone" branch — verify, do
  not reason).

The drag preview is created per drag and destroyed at drop, so a stray bit or a
top-of-band placement lasts only as long as the drag — that is the reason it was
skipped, not evidence that it is correct. Worth 15 minutes: reposition it via the
same helper if it costs nothing, or write down why it must not be.

Validation: extend `test/win32/overlay-zorder.ps1` with a section that starts a
pane drag, topmosts the preview popup mid-drag, keeps dragging, and asserts the
bit is gone; plus a quick-terminal case asserting its own popups stay topmost.

## What it actually was

**There is no pane drag preview.** `Surface.zig:1532` at the filing commit
(`3e77fa7`; ~1912 today) is `setMouseOverLink` — the **hovered-URL bubble**, the
browser-style status popup that names the link under the pointer. Nothing in
`src/apprt/win32` creates a popup for a pane drag.

That reverses the "worth 15 minutes, probably harmless" premise the task was
filed on. The bubble's HWND is **not** short-lived: it is created lazily on the
first link hover and destroyed only in `Surface.deinit`, so only its
*visibility* is transient. A stray `WS_EX_TOPMOST` on it therefore lasts for the
life of the pane, not the life of a gesture — the same permanent defect T142 was
filed for. And it is shown with `SW_SHOWNOACTIVATE`, which lifts a popup to the
top of the non-topmost band: hover a link in a BACKGROUND Ghoztty window and its
bubble parks over whatever application is actually in front. That is failure
mode 2 from `overlay_zorder.zig`, verbatim.

The quick-terminal half needed no change and is confirmed rather than reasoned:
`healOverlayZOrder`'s only `SetWindowPos` target is the overlay, never the
owner, and `isStray` leaves a propagated bit alone — so the quick terminal is
neither reseated nor demoted. Section H measures both halves on the box.

## In plain terms

Hover a link in a Ghoztty window that is sitting *behind* another app, and the
little bubble showing the URL could end up floating on top of that other app —
and stay there, over everything, long after you moved the mouse away. Every
other floating decoration Ghoztty draws already fixes its own stacking; this one
was skipped because it was assumed to disappear on its own. It doesn't. Now it
fixes itself the same way, on every hover and whenever the window is activated.
