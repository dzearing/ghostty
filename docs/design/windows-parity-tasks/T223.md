# T223 - Deferred-focus guard is disabled off the input desktop, and the T105 focus storm reproduces there

## In plain terms

When two terminal windows come back at once after a restart, they can start
fighting over which one you are typing into — flipping back and forth dozens of
times a second, so the app is unusable until one of them is closed. That was
fixed a while ago for the normal case, but the fix quietly switched itself off
whenever Windows is showing a different desktop than yours: while the screen is
locked, while a "do you want to allow this app" prompt is up, or in a
disconnected Remote Desktop session. Come back to a machine in one of those
states and the fight is on again. After this change the protection is always on,
and windows still hand keyboard focus around normally in every one of those
states.

## Goals

- [x] The window fight cannot happen off the user's own desktop either
- [x] Keyboard focus still moves normally there (dialogs, splits, tabs)
- [x] The two automated checks that reproduce the fight go green and stay green

## Summary

`App.performDeferredFocus` gates a queued `WM_APP_SETFOCUS` on the T105 rule
"only forward focus the window ALREADY holds" - and `shouldPerformDeferredFocus`
turns that gate **off entirely** when the process is not on the input desktop:

```zig
fn shouldPerformDeferredFocus(on_input_desktop: bool, foreground: ?w32.HWND, root: w32.HWND) bool {
    if (!on_input_desktop) return true;   // <- unconditional
    return foreground == root;
}
```

That bypass is **T211's** fix (corrected 2026-08-04 — this file originally
credited T215, which is the follow-up *audit* task; `git log -S` puts the code in
`713815f63 T211: shared test-desktop harness for GUI acceptance scripts`) and its
stated reason is sound (a background desktop
has no foreground window, so the guard would drop *every* focus change and
keyboard focus could never move). But the T105 live-lock the guard exists to
prevent is **not** actually foreground-dependent, and it reproduces on the
unguarded path. Measured on box 2026-07-31, migrating `session-reattach.ps1`
onto the T211 test desktop:

```
(restore-time focusFlips=43)   FAIL F10
(post-seed  focusFlips=39)     FAIL F11
```

against a pre-T105 baseline of `fgFlips=38 / focusFlips=36` in 3s and a post-fix
`0 / 0`. So the two-window restore ping-pong is fully back off the input desktop.
Everything else in that script (A-E, F1-F9) is green, so this is not a harness
fault: the layout restores, re-attaches and replays correctly while the GUI
thread's focus churns between the two windows.

## Why it matters beyond the test harness

`onInputDesktop()` compares the GUI thread's desktop name against
`OpenInputDesktop()`. That comparison goes FALSE for an ordinary app window in
every state where the input desktop is not `Default`:

- the workstation is **locked** (input desktop becomes `Winlogon`),
- a **secure desktop** is up (UAC prompt, secure screensaver),
- an **RDP session is disconnected**.

So this is not a test-only path. The same class of mistake as T216, where
`Surface.getCursorPos` erroring on a failed `GetCursorPos` killed every click
and also affected locked / secure / disconnected sessions.

## Resolution (2026-08-04)

The first candidate below is what landed, and it is a four-line change in
`App.shouldPerformDeferredFocus`:

```zig
if (on_input_desktop) return foreground == root;
return if (active) |a| a == root else true;
```

where `active` is `w32.GetActiveWindow()`. The reasoning the fix rests on:

- The predicate the guard actually wants is "has activation moved since this
  assert was queued?" `SetFocus` **activates the target's top-level parent**
  when it is not already active (documented), and that steal is precisely what
  re-fires the loser's `WM_SETFOCUS` forwarding. So the ping-pong is driven by
  *queue* activation, which exists on every desktop — not by foreground, which
  does not. That is why T211's bypass reopened the whole live-lock.
- `GetForegroundWindow` is input-desktop-scoped and returns null for every
  window on a background desktop, so it carries no information there.
  `GetActiveWindow` is scoped to the calling thread's message queue, so it
  still names exactly one of our windows. `Surface.zig` already leans on that
  same property for focus-follows-mouse ("only move focus between panes of the
  ACTIVE window").
- The **input-desktop branch is untouched**. That is the interactive path the
  T105 fix shipped on and it is not what was broken; a null `active` off the
  input desktop forwards, so a query that tells us nothing cannot re-break
  T211's "focus can never move" failure.

Measured on box after the change (same script, same bounds):

```
(restore-time focusFlips=0)   PASS F10     was 43, FAIL
(post-seed  focusFlips=0)     PASS F11     was 39, FAIL
session-reattach.ps1 ........ ALL PASS (38 assertions)
```

stable across three consecutive runs of the script.

The change narrows what gets delivered off the input desktop, so T211's "focus
can still move" property was re-proved rather than assumed, on the seven
off-desktop scripts most dependent on it — all ALL PASS:

| script | assertions | why it discriminates |
|---|---:|---|
| `focus-defer.ps1` | 17 | the direct T48/T211 regression: posts real clicks, asserts focus follows |
| `chooser-menu.ps1` | 57 | machine chooser, a separate active top-level window |
| `kb-actions.ps1` | 42 | keyboard actions driven through real key input |
| `context-menu.ps1` | 42 | popup menus taking and returning activation |
| `confirm-dialogs.ps1` | 27 | real Tab/Enter/Escape through modal dialogs |
| `test-desktop-harness.ps1` | 23 | the harness's own floor |
| `focus-follows-mouse.ps1` | 14 | already guards on `GetActiveWindow`, so it pins the new proxy |

Floor: `floor-lane.ps1 -Lane all` ALL LANES PASS (none 292s, win32 313s, agent
314s); P1–P3 ALL PASS.

`session-reattach.ps1`'s header and its F10/F11 labels announced "RED on T223",
which would now read as "expected to fail". They are relabelled as the oracle
they became — the `-le 2` bound and its do-not-relax note are untouched.

The three `shouldPerformDeferredFocus` unit tests were rewritten as the task
predicted: the input-desktop test now also pins that `active` is *not*
consulted there, and "background desktop always forwards" became "background
desktop guards on the active window" plus a separate null-active case.

## Direction (not yet chosen - spike first)

The guard's real predicate is "is this assert stale, i.e. did activation move
since it was queued?", and `GetForegroundWindow` is only the input-desktop
*proxy* for that. Candidates:

- Compare against the desktop-scoped active window instead
  (`GetGUIThreadInfo(...).hwndActive`, or `GetActiveWindow` on our own thread),
  which is meaningful on a background desktop where `GetForegroundWindow` is
  null. Likely the smallest correct change.
- Or make the assert carry a generation/serial stamped when it is queued and
  drop it if the window's activation generation moved on.

Whichever lands must keep BOTH properties: focus still moves off the input
desktop (T215 - the whole GUI acceptance suite depends on it), and two
back-to-back restored windows do not ping-pong (T105).

## Validation

- `test\win32\session-reattach.ps1` F10 and F11 go green (they are RED today
  and are the discriminating oracle; do not relax their `-le 2` bound).
- `zig build test -Dapp-runtime=none` and `-Dapp-runtime=win32` stay green,
  including the two `shouldPerformDeferredFocus` unit tests - which will need
  updating, since the "background desktop always forwards" case is exactly the
  behavior being changed.
- Re-run `test\win32\test-desktop-harness.ps1` and one keyboard-driven migrated

  desktop after the change.
