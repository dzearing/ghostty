# T39 — Website installer link for Windows (Phase H)

## Summary

Website: Windows installer download link — add the Windows download to the site next to the Mac one, pointing at the latest win-vX.Y.Z GitHub release asset; SAME filename format as published (version/arch in the installer name) so the link/copy stays consistent across releases; include portable-zip alternative + minimum-OS note

## Details

User directive 2026-07-13: the website must offer the Windows installer
with the same filename conventions as the other platforms — arch and
version in the filename (e.g. `Ghoztty-<version>-windows-x86_64.msi` /
`...-portable-x86_64.zip`; match the exact existing pattern when
implementing). The site lives in the gh-pages branch (see the relay
"ghpages mirror" commits on main). Depends on T38 publishing versioned
artifacts to link to.

*Validation:* website shows a working Windows download whose filename
carries arch + version, alongside the existing platform links.

## What landed (2026-08-02)

A second `.download-card` in the SAME `.download-cards` row as the macOS
DMG — "Windows Installer / x64 · Per-user, no admin" — plus a second
`.download-note` line carrying the version, the minimum-OS note and the
portable-ZIP alternative. No new CSS: `.download-cards` was already a
wrapping flex row with a mobile stack rule, so the second card is the
design system working rather than being extended.

The decision that shaped the task is **who keeps the link current.**
T39's own summary says "pointing at the *latest* win-vX.Y.Z release", and
there is no static URL for that: win-v releases are published
`--latest=false` on purpose (T38 — installed builds scan for the newest
`win-v` tag, so making one "latest" would hijack the Mac Sparkle flow).
The two candidates were a client-side GitHub API lookup and a release-time
rewrite. The rewrite won: it has no runtime dependency on an
unauthenticated API (60 req/hr shared per NAT), it works with JS off, and
it puts the site on the same trigger as the artifacts — which is exactly
the fix T38 made one layer down. **A step that needs a human to remember
it is how the Windows channel fell 24 releases behind**, and hand-editing
the site would have re-created that gap one level up.

So `.github/workflows/release-windows.yml` gained a website step that runs
**after** the publish and only when `PUBLISH == 'true'` — the links can
never precede the assets they point at — calling
`dist/website/update-windows-links.py`.

Three things about that script are deliberate:

- **It matches by element `id`, never by version number.** A regex loose
  enough to find "the version" on that page also finds
  `Ghoztty-1.28.0-arm64.dmg` and would silently retarget the macOS
  download at a Windows tag. C5 asserts the Mac link is byte-identical
  after a rewrite.
- **A missing anchor is an error, not a no-op.** A rewrite that matches
  nothing and exits 0 is the "empty rather than absent" failure this repo
  has now paid for three times (T214's capture, T303's `PrintWindow`), and
  here it would mean a release that reports success over a site that never
  moved. C7 renames one id and asserts a non-zero exit.
- **It is idempotent** and the workflow diffs before committing, so a
  re-run is not a churn commit.

**Found on the way: the gh-pages branch now has two concurrent writers.**
`release.yml` pushes `appcast.xml` from the same tag push. A plain `git
push` from both loses a race roughly half the time — and the loser is a
release whose appcast entry or download link silently never landed. Both
workflows now rebase-and-retry (5 attempts, backing off), and D4/D5 assert
it on both sides.

`relay/deploy/ghpages/index.html` is the in-repo mirror of the live page.
It had drifted again (v1.12.0 against a live v1.28.0 — the same drift its
own sync commit `0b8f47356` complained about). It is now synced, and F1
fails the acceptance script whenever it drifts, so the next one is caught
by a test rather than by reading two files side by side.

Copy fixed alongside, because the page said things a Windows visitor could
read as false: the hero badge (`macOS` → `macOS & Windows`), Install
Step 1 (which told everyone to drag to Applications; the MSI adds a user
PATH entry and a Start Menu shortcut — `build-msi.sh:319,338` — so "sets
up the `ghoztty` CLI for you" is true on both), and the download
subheading.

`.claude/commands/release.md` Step 7 now says which parts of the page are
hand-edited (macOS) and which must NOT be (Windows, Remote Agent).

### The minimum-OS number

**Windows 10 1809+, 64-bit.** 1809 is the ConPTY floor the app actually
requires (`windows-parity-details.md:2736`, `T79.md:33`); `win32.zig:250`
notes an older 1607 floor for one API, so 1809 is the binding one.
