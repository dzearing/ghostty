# T541 - Mac: 'Viewer: Open URL in Pane' prompt should run the shared omnibox completion (win32 T396 diverged deliberately)

## In plain terms

Both platforms now have a palette entry that asks for a web address and opens
it in a side pane. On Windows, typing a bare word like "cnn" works — it is
completed to `https://cnn.com` exactly the way the pane's own address bar
would complete it. On the Mac, the same prompt only prepends `https://`, so
"cnn" becomes the unresolvable `https://cnn`. The Mac prompt should use the
same address-completion rules as everything else.

## Summary

T396 gave win32 the three viewer palette entries. Its "Viewer: Open URL in
Pane…" prompt commits through `viewer_nav.completeAddress` — the omnibox
rules ported case-for-case from Mac's own `completeAddress` (scheme-less →
`https://`, single dotless word → `.com`, localhost → plain `http`). Mac's
`ViewerCommands.openURLFromPalette` (ViewerCommands.swift:44-64) predates
that and still does only `if !text.contains("://") { text = "https://" +
text }`, even though Mac's address bar already has the full `completeAddress`.
The win32 behavior is the deliberate pick (consistent with the address bar on
both platforms); this task brings the Mac prompt up to it.

## Details

- Change `openURLFromPalette` to run the same `completeAddress` the Mac
  address bar uses instead of the inline `://` check.
- The prompt's empty-input guard and sheet flow stay as they are.

*Validation:* a Mac unit test (or the existing completeAddress tests plus a
prompt-level test) proving "cnn" typed into the prompt opens
`https://cnn.com` and "localhost:3000" opens `http://localhost:3000`.

## Validation criteria

- [ ] Mac's "Viewer: Open URL in Pane…" prompt completes a bare host the
      same way the address bar does (shared `completeAddress` path, not a
      private `://` check).
- [ ] macOS test suite green.
