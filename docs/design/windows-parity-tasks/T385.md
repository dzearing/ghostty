# T385 - The win32 viewer shim hard-codes one message-handler name, so a second Mac handler would silently no-op

## Summary

`viewer_bridge.shim_js` installs exactly one handler,
`window.webkit.messageHandlers.viewerTOC`, because that is the only name Mac
registers today (`ViewerView.tocMessageName`). If a future Mac commit adds a
second `userContentController.add(_, name:)`, the shared JS will look up
`window.webkit.messageHandlers.<newName>`, get `undefined`, and its `post()`
will return quietly — **no error, on either side.** The Windows viewer would
lose a feature and nothing would say so.

A unit test asserts the name agrees between the shim and `selection.js`
("the shim names the same handler the shared JS looks up"), which catches a
RENAME. It cannot catch an ADDITION, and an addition is the likelier drift.

## Details

Two candidate fixes, and the choice is the task:

1. **Forward any name.** Make `messageHandlers` a `Proxy` (or install a getter)
   that manufactures a `{postMessage}` for whatever name is asked for, and have
   it wrap the payload as `{handler: "<name>", body: <message>}` so native can
   route. Costs a wire-shape change: `viewer_bridge.parse` would read `body`,
   and the JSON would then NOT be the same shape Mac's `WKScriptMessage.body`
   carries — which is the property P1 leans on to keep the parser a straight
   port. Weigh that carefully.
2. **Keep one name, make the drift loud.** Scan the Mac sources for every
   `userContentController.add(` name at test time and fail if the set is not
   exactly `{viewerTOC}`. Cheap, no wire change, and it turns a silent Windows
   regression into a red test in the lane that owns the divergence.

(2) looks right: the risk is a Mac-side addition, and a test that watches for
one is a smaller and more honest instrument than a protocol change made for a
handler nobody has written yet.

*Validation:* whichever is chosen, a test that FAILS when a second handler name
is introduced — demonstrated by adding a fake second name locally, watching it
go red, and removing it.

## In plain terms

The viewer pane on Windows talks to the app through a single named channel that
the Mac app opened first. If the Mac app ever opens a second channel, whatever
uses it — a future viewer feature — would do nothing at all on Windows: no
error, no warning, the button just would not work, and nobody would find out
until a user reported it missing. This adds a test that notices the day that
second channel appears, so the gap is caught here instead of in the wild.
