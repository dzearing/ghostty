# T534 - Surface long-unattached live agent sessions as a user-facing notification with resolve actions, instead of any age-out

## Summary

Supersedes the T521 approach per the user's D18 answer (2026-08-06). The user
rejected a config-knob TTL outright: "Config knobs are difficult to find and
nobody will ever use it. 'Age out' is ambiguous. [...] wouldn't we want to
bubble this to the user in some kind of notification that lets them resolve
this rather than assuming something?"

So the shape is: the app never silently unpins or reaps a live orphan.
Instead, when a live session has been continuously unattached for a long time
(threshold can be generous and hard-coded — the point is discovery, not
policy), the app tells the user and offers the resolutions the chooser
already has verbs for:

- **Resume** — open a window attached to it (it was presumably forgotten).
- **Kill** — it is not wanted; this is the existing chooser Kill control.
- **Keep** — dismiss; do not re-notify for that session for a long while.

Design questions for whoever picks this up (settle them in the task, not in
config keys): where the notification lives (the chooser already lists these
sessions since T520 — a badge/callout there is discoverable and native; a
toast is louder but transient), what "long time" means, and where the
"continuously unattached since" timestamp is recorded (it must reset on every
attach — an agent-side additive field per the agent-contract rules).

## In plain terms

If a terminal session keeps running in the background but no window has shown
it for weeks, nothing today ever tells the user it exists — it just sits
there holding a shell process until they stumble on it. Rather than silently
deleting such sessions after a timeout (the old plan), Ghoztty should point
them out and let the user decide: reopen it, kill it, or keep it.

## Goals

- [x] Agent records "continuously unattached since" per session, reset on
      every attach, surfaced additively on the wire (`unattached_since`).
- [x] The app checks the local roster periodically and announces a session
      unattached past a generous hard-coded threshold (24 h) with a tray
      balloon naming it (cwd + command).
- [x] The balloon click opens the machine chooser, where the T520 orphan
      badge marks the session and Resume / Kill already live.
- [x] Keep = ignore/dismiss: a per-episode stamp file suppresses
      re-announcement (7 d), and an attach starts a fresh episode.
- [x] Mac sibling filed (T885); the agent half is shared and already done.

## Design decisions (settled in-task per the Summary's instruction)

- **Where the notification lives:** a tray balloon (the app's existing
  Windows-native notification channel, `tray_notify` uid 3), whose click
  opens the machine chooser — the chooser is where the resolve verbs already
  exist (T520 badge, Resume, Kill), so the balloon is the *pointer* and the
  chooser is the *resolution surface*. Balloons carry no buttons, so
  Resume/Kill as inline actions were never on the table; a modal dialog
  popping up unprompted was rejected as un-Windows-native.
- **What "long time" means:** 24 hours continuously unattached, hard-coded
  (D18 ruled out knobs); re-announce the same episode after 7 days; check
  every 15 minutes. Debug-only env seams (`GHOZTTY_ORPHAN_NOTIFY_AFTER_MS`,
  `GHOZTTY_ORPHAN_CHECK_MS`, `GHOZTTY_ORPHAN_RENOTIFY_MS`) exist so the
  acceptance can watch a "24 hours later" story in seconds; a release build
  ignores them.
- **Where the timestamp lives:** on the agent (`Session.unattached_since_ms`,
  stamped at create + every bound→false, cleared on every ATTACH), surfaced
  as the additive `SessionInfo.unattached_since` only while alive+unbound.
  No new opcode ⇒ no capability gate needed; both skew directions degrade to
  the pre-T534 silence.
- **What "Keep" means:** being told is the stamp — the app records the
  episode (session id + its `unattached_since` instant) in
  `%LOCALAPPDATA%\ghoztty\orphan-notify[-debug].json` BEFORE showing the
  balloon, so ignoring, dismissing, or never seeing it (no notification
  area) all resolve to "keep, quietly" — and nothing is ever unpinned,
  reaped, or altered by any of this.

## Validation criteria

- [x] A live session continuously unattached past the threshold produces a
      visible notification/badge naming the session (working dir + command),
      validated on-box with a debug agent and a shortened threshold. —
      `test/win32/orphan-notify.ps1` step 2 (ALL PASS, 13 assertions): the
      oracle line names exactly the orphan's id (cross-checked against
      `+sessions --json`), and the balloon body carries cwd + command
      (`orphan_notify.formatBody`, unit-tested in the none lane). Step 1 is
      the negative control: pane-held sessions stay quiet past the
      threshold.
- [x] Resume from the notification attaches a window to the session; Kill
      ends it; Keep suppresses re-notification for that session (and an
      attach resets its unattached clock). — the click opens the chooser
      (`tray_notify.classify` → `review_orphan_sessions`, unit-tested);
      resume from the roster is step 4 (agent reports ATTACHED and
      `unattached_since: null` — the clock reset); Kill is the chooser's
      existing control (`chooser-orphan-badge.ps1` / roster Kill coverage);
      Keep-suppression is step 3 (no re-announcement across ticks, stamp
      file records the episode).
- [x] No session is ever unpinned, reaped, or altered without an explicit
      user action — the keep-forever default behavior is byte-identical when
      the user ignores the notification. — the whole feature is read-only
      against the agent (`LIST_SESSIONS` + a log line + a balloon); the only
      write is the app-local stamp file. `Session.unattached_since_ms` is
      never consulted by any reaping decision (documented at the field; the
      idle-TTL/pinned logic is untouched — agent lane green).
- [x] Agent-contract rules hold: any new field is additive; old agent + new
      app and new agent + old app both degrade gracefully (no notification,
      no error). — additive optional field only, no new opcode; omitted ⇒
      null round-trip asserted in `protocol.zig`'s SESSIONS test; null ⇒
      never eligible asserted in `orphan_notify.zig`; agent-side
      stamp/reset lifecycle asserted in `server.zig` ("T534:
      unattached_since stamps the detach…"), `zig build test-agent` green.
