# T641 - Viewer feedback: quote insertion into the composer, and un-hide the page Quote button

## In plain terms

Select some text in a viewer pane on a Mac and a small Quote button appears;
pressing it drops that passage into the feedback box as a quoted block, so you
can say "this bit here is wrong" and type your comment underneath. On Windows
that Quote button is hidden on purpose, because there was nowhere to put the
text. T635 built the message box; this task builds the quoted block and turns
the Quote button back on.

## Goals

- [x] The page's **Quote** button is back on Windows — the toolbar ships the
      same two buttons Mac's does.
- [x] Pressing it opens the composer and drops the passage in as its own
      block, indented, washed, with an accent bar down the left.
- [x] The quote's referential context (heading, containing block, offsets) is
      recorded against it, ready for the report writer.
- [x] Deleting the block takes its metadata out of the report, with nothing
      having to notice the deletion.
- [x] Typing after a quote produces plain text, including after select-all +
      delete + type.

## Summary

The second half of T635, split off when T635 shipped the composer's real text
control (D43's RichEdit answer) — see T635's progress log for why. Everything
here is about the QUOTE, not the typing:

- `viewer_bridge.Quote` arriving from `selection.js` becomes its own indented
  block in the composer, with a tinted panel and an accent bar down the left.
- The block carries an id, and the report's `quotes` array is derived **from
  the composer's storage**, so deleting the block drops its metadata (the same
  derive-from-storage rule the image carousel uses).
- Typing never inherits quote styling: the win32 trap is a run attribute
  inherited at the caret (RichEdit carries character formatting forward from
  the character before the caret), so quote formatting is refused at the
  source. Test select-all + delete + type.
- Ends with **deleting `viewer_bridge.hide_quote_js`**
  (`viewer_bridge.zig`), which is documented there as this job. Its unit test
  asserts the flag is present; that assertion inverts here.

The message already arrives fully parsed (`viewer_bridge.Quote`, landed in
T375) with `headingId`/`headingText`, `blockSelector`/`blockText`,
`offsetInBlock`, `documentOffset`. Store all of it against the quote id — the
report writer (T637) needs it. `sourceLine` is deliberately NOT in the message
and is resolved natively at send time; that is T637's job.

## Details

**Where the quote lives.** T635's composer is a RichEdit control, so the
control is the storage. A quote is a run marked with a distinguishing
`CHARFORMAT2` (a tint plus `CFE_PROTECTED`, which is what makes the block
atomic to edit), and quote metadata lives in a side registry keyed by id.
Identity is recovered from storage at serialize time: walk the quote-formatted
runs in document order and match each to the first unconsumed registry entry
with identical text. A deleted block has no run, so its metadata never
serializes — which is the rule, expressed without needing a per-run user field
RichEdit does not have.

Keep the matching/serialization pure and in the none lane (a `Doc` built from
`(text, quote spans, registry)`); the win32 side only extracts the spans.

**AS BUILT: the spans are derived from the TEXT, not from the runs.** The rule
above is exactly the one that shipped — walk in document order, match each to
the first unconsumed registry entry with identical text — but the thing walked
is the composer's own text rather than its formatting runs. Extracting runs
from RichEdit means binary-searching `EM_GETCHARFORMAT`'s mask over the
document on every serialize, and none of it can be exercised without a window;
matching line-aligned occurrences of each registry entry's passage gives the
identical answer, is a dozen lines, and put the whole rule in the none lane
where the task asked for it. A quote is inserted as its own block, so
"complete run of lines" is what keeps a passage the user merely TYPED
mid-sentence from being mistaken for a quote of it. Formatting is then
*derived from the spans* rather than being the source of them
(`applyQuoteFormatting`), so what is painted and what is filed cannot drift.

Two consequences the run-based version would not have had, both recorded in
`viewer_feedback_doc.zig`'s header: `CFE_PROTECTED` is not used (the block is
editable), and EDITING a quote's characters drops its context — which is the
honest answer once the text is no longer the passage the heading and block
selector describe.

Filed as decision D46.

**The visual.** Mac draws the accent bar in `drawBackground(in:)` precisely
because a background-colour attribute paints tight line boxes with no bar and
no rounding. RichEdit has the same limitation: `CHARFORMAT2.crBackColor` is
tight line boxes. The two routes are (a) reserve a left gutter with `EM_SETRECT`
and paint the bar in the parent's gutter, aligned to the quote's lines via
`EM_POSFROMCHAR`, or (b) paint under a transparent RichEdit (the flicker trap
D43 names). Prefer (a).
