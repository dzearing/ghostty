# T157 - keybinds-t01.ps1 is structurally broken: no pane SetFocus, no session-persistence=false

## In plain terms

The automated test that checks Windows keyboard shortcuts — new tab, split,
close pane, copy, paste, the command palette — was reporting failures that had
nothing to do with the shortcuts themselves; it was pressing keys at a window
that could not hear them. Since then most of it was rebuilt for other reasons,
so what was left was one shortcut still being tested wrongly: Escape to dismiss
the command palette. Now the whole check passes reliably, which means a future
change that really does break a keyboard shortcut will be caught instead of
being lost in noise nobody trusted.

`test/win32/keybinds-t01.ps1` — the standing acceptance script for the whole
Windows ctrl-mirror keybind set — currently fails **14 of 21** assertions on
the box, INCLUDING ITS OWN POSITIVE CONTROL ("typed text visible in pane").
A script whose positive control fails is reporting nothing about the product;
every red in it today is a harness artifact, so the Windows keybind set has
had no working regression coverage for an unknown span of time. Found while
building T154's `clipboard-paste.ps1` — its first draft copied this script's
driver and failed the same way, which is what exposed the mechanism.

Two independent causes, both proven on-box:

1. **The injected keys never reach the shell because the pane child has no
   keyboard focus.** The terminal surface is a `GhozttyTerminal` CHILD of the
   `GhozttyWindow` top-level (`App.zig:94,97`). `Chord`/`TypePlain` call
   `GrabForeground` and then `AttachThreadInput` + `SendInput`, but pass
   `IntPtr.Zero` for focus, i.e. they rely on the window having already
   focused its surface. A window raised programmatically (never clicked) is
   foreground with `GetFocus()` still on the FRAME, and every key is
   swallowed silently. **A/B evidence, same box, minutes apart:** identical
   driver, `SendInput` reporting 14/14 events delivered and
   `GetForegroundWindow() == top` both times — without `SetFocus(paneChild)`
   the pane tail stayed at a bare prompt; with it, `clipctl` echoed. The fix
   is one `SetFocus(FirstPane(top))` after the AttachThreadInput, the way
   `clipboard-paste.ps1` now does it.
2. **Session restore hands it other runs' windows.** It launches with no
   `--session-persistence=false`, so `ctrl+n opens a second window` observed
   **7** windows. Same trap T131 hit with `pane-banner.ps1`'s `bw` window.

## Details

Fix both, then re-run x3. While in there, audit the other chord-driving
scripts for cause 1 — `kb-actions.ps1` and anything else calling a
`Chord`-shaped helper with a zero focus handle (grep for
`Chord(.*IntPtr.Zero`). Cause 2 is a one-flag change; grep the suite for
`Start-Process` launches missing `--session-persistence=false`.

Do NOT assume the product bindings are broken because this script is red:
T154 verified ctrl+v, ctrl+shift+v, and plain typing end-to-end against the
same build with a working driver.
