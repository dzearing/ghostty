# T762 - A non-persistent (exec) +split still inherits the app-focused pane's cwd, not its parent's

## Summary

The remaining leg of T515. That task fixed the branches of
`IpcHandlers.handleSplit` that build a `.remote` override (session persistence
on — the default — and cross-machine windows): they now resolve the split
PARENT's live cwd through `Window.inheritedCwd` rather than leaving the field
null and letting the core answer.

The plain-exec branch (`session-persistence = off`, so no agent connection on
the window) still passes `args.working_directory` straight through, so with no
explicit path the cwd comes from the core's app-GLOBAL inheritance —
`apprt/surface.zig` `newConfig` reads `app.focusedSurface`, and win32's T185
`livePwd` refinement reads the same focused surface. With another window in
front, `+split --pane=<pane>` opens in THAT window's directory; with nothing
focused, in the shell's home. Same defect as T515 and T538, different seam.

The fix has a different mechanism from T515's, which is why it was split out:
there is no agent to ask, so the parent's cwd comes from the pane's own shell —
`Surface.livePwd`, which the T185 path already calls (just on the wrong
surface). Resolve it from `at.surface()` when `--working-directory` is absent.

Worth doing at the same time: the same rule for keyboard splits (ctrl+shift+d
et al.) on a non-persistent window, which take the `buildRemoteInherit == null`
path and land on the identical core fallback. Check whether the parent there is
always the focused pane (it usually is) before widening.

## In plain terms

With session persistence turned off, splitting a pane can still open the new
pane in the wrong folder — the folder of whichever window you last clicked in.
Everyone running the default settings is already fixed; this is the same fix
for the people who turned persistence off.
