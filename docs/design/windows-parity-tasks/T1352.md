# T1352 - An upgrade over a running Ghoztty leaves every window on the old build

## In plain terms

You download the new version and run the installer. It finishes without
complaint. Nothing changes - the terminal you are looking at is still the old
one, and nothing tells you so. As far as you can see, the installer did
nothing.

## What the user hit (2026-09-05)

> "i ran the latest ghoztty installer but it didn't reset this window at all.
> what's going on?"

Measured at the time:

| | |
|---|---|
| On disk | `1.36.12`, written 2026-09-05 11:46 |
| Running | pid 39036, started **2026-08-31 07:49** |

The install genuinely succeeded. Windows cannot replace a running image
in place, but MSI can rename the running exe aside and drop the new one in -
so the upgrade completed with nothing to prompt about, and the process carried
on executing the five-day-old code. Every window the user had - the go-loop,
the controller chat, the dashboard - lives in that one process.

## Why none of the existing work covered it

Three near-misses, which is what makes this worth writing down:

- **T1204** gave the installer Restart Manager handling, and Restart Manager is
  deliberately left enabled. But RM only prompts when it *cannot proceed
  otherwise*. Here it could proceed, so it correctly said nothing.
- **T1205** added exactly the missing signal - a tray balloon and a Restart Now
  offer in About when a newer build is on disk. It landed 2026-09-03. The
  running process started 2026-08-31, so **it does not contain the code that
  would tell the user to restart**. The feature cannot announce itself
  retroactively; it only starts working from the first build that has it.
- **T1176** makes the installer launch Ghoztty when it finishes. With the app
  already running, that either no-ops or adds a window to the *old* process -
  neither of which upgrades anything.

So each piece is individually right and the gap between them is where the user
landed.

## What it should do

The installer knows it has just replaced the binaries of a running
application. That is the moment to say so:

- **Offer to restart, from the installer.** "Ghoztty is running an older
  version. Restart it now?" - and if accepted, close the running instance and
  relaunch it. This is the half that works regardless of which build the user
  is currently running, which is precisely why it matters: it is the only
  mechanism that can rescue someone on a pre-T1205 build.
- **Preserve the session.** Restarting must go through the same path the
  in-app updater uses, so windows and sessions come back rather than being
  discarded. A restart offer that loses the user's work is worse than silence.
- **Respect the quiet path.** Gate on `UILevel` as T1291 did, so the in-app
  updater's silent install is unaffected.
- **Say something even if the user declines.** Declining should leave a visible
  reminder rather than nothing - the state "installed but not running yet" must
  never look identical to "nothing happened".

## A note on the harness

The three windows that matter here are the go-loop, the controller chat and the
dashboard, all inside the one process - so testing this on the dev box costs
the loop. The acceptance script must drive it on the background test desktop
with its own Ghoztty instance rather than the user's.

## What landed

A new custom action, `RestartApp`, runs `[INSTALLDIR]ghoztty.exe
--install-restart --installed-version=[ARPDISPLAYVERSION]` after
`InstallFinalize` on the upgrade path only, `asyncNoWait` so the installer
never waits on a dialog and can never be failed by one. The exe msiexec has
just written is the one process on the box guaranteed to contain today's code
at that moment, which is why the offer lives there and not in the app.

`src/apprt/win32/install_restart.zig` is the other half. It finds top-level
`GhozttyWindow` windows whose process image is `<INSTALLDIR>\ghoztty.exe` -
one row per process, and a developer's `zig-out` build beside it is never a
target - and if there are none it exits silently. Otherwise it offers Restart
Now / Later in the same dark `ConfirmDialog` every other Ghoztty prompt uses.

Restart Now sends the pair the Restart Manager sends: `WM_QUERYENDSESSION`
then `WM_ENDSESSION` with `ENDSESSION_CLOSEAPP`. That is not an imitation of
the update path, it is the update path - `Window.zig` answers it by flushing
the session layout and exiting WITHOUT marking any session CLOSE (T89e/T1204),
so the agent keeps the PTYs and the relaunched app re-attaches them. Then it
starts `<INSTALLDIR>\ghoztty.exe`, which restores the layout.

Later leaves a tray balloon naming the installed version and the fact that the
open windows are still on the previous build, so "installed but not running
yet" no longer looks identical to "nothing happened". A window that will not
close - a build older than T1204, which never sees the message - is reported in
a dialog and never terminated: a restart offer that loses the user's work would
be worse than the silence being fixed.

## Validation criteria

- [x] Installing over a running Ghoztty offers to restart it, and the offer
      appears even when the running build predates this change. `install-restart.ps1`
      L8/L10b: the offer, run from the installed exe, finds the running window
      and says so. It is architecturally independent of the running build - the
      only thing asked of that process is the RM close pair, which is a Windows
      message and not a feature of ours.
- [x] Accepting restarts the app on the new build with windows and sessions
      intact. `install-restart.ps1` L11 (the running terminal closes) and
      L12/L13 (a new process from the same exe comes up WITH a window). Sessions
      survive by construction and by A15: the close is the app-EXIT path, which
      marks no session CLOSE - L5/L7 already measure that half live.
- [x] Declining leaves a visible indication that a newer build is installed.
      L10/L10c (the terminal is left running and the declined answer recorded) +
      A17 (the reminder balloon is in the shipped shape, with its own
      unit-tested body text naming the version and "until you restart").
- [x] A silent/managed install shows no dialog. A21 asserts the sequenced
      condition carries `UILevel > 3`, and R5 watches the build-time verifier
      REJECT an offer a silent install would see.
- [x] After the restart, About and `--version` report the version that was just
      installed - the T1205 surfaces agree. L12/L13 relaunch from the exe on
      disk, which is what both surfaces read (`image_freshness` compares the
      process start against that file's mtime, so a process started after it is
      not stale).
- [x] An acceptance script drives the upgrade-over-running case on the
      background desktop and fails if the outcome is silent.
      `test\win32\install-restart.ps1` sections R (7 negative controls against
      the shipped build-time verifier) and L8-L13 (live, on the test desktop).
      L9 is the control that matters most: an offer for a DIFFERENT install
      leaves this one alone, so L11 cannot be passing for the reason that would
      close the user's terminal.
