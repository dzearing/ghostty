# T1352 - shell-integration cannot be forced to the two Windows shells (no cmd or powershell value)

## In plain terms

`shell-integration` in the config file lets you name the shell to integrate —
`bash`, `zsh`, `fish` and so on — for when auto-detection guesses wrong. The
two shells a Windows user actually runs, PowerShell and cmd, are not on that
list, so on Windows the setting is effectively "detect or off". Nobody notices
until detection guesses wrong, and then there is no way to say what they meant.

## Summary

`config.ShellIntegration` (`src/config/Config.zig:9109`) is
`none | detect | bash | elvish | fish | nushell | zsh`. `Shell` in
`src/termio/shell_integration.zig` carries two more — `.powershell` (T27) and
`.cmd` (T512) — and `setup()`'s `force_shell` handles both, so the machinery is
already there; only the config enum and the two `force` switches that map it
(`src/termio/Exec.zig` and `src/Surface.zig`) are missing the arms.

Filed while landing T512, which added `.cmd`. Neither T27 nor T512 needed the
force path to work, which is exactly why the gap survived both.

Worth doing carefully rather than mechanically: the enum is shared with the Mac
seat and the value set is user-visible config, so the doc comment above the
field (which lists the allowable values) has to grow with it, and the Mac build
has to accept a `shell-integration = cmd` it will never act on rather than
refusing to parse the file.

## Validation criteria

- [ ] `shell-integration = powershell` and `shell-integration = cmd` parse and
      force the named integration on a pane whose shell would detect otherwise
- [ ] the config field's doc comment lists them among the allowable values
- [ ] a Mac-targeted config parse accepts both values without erroring
- [ ] unit tests in the `none` lane, plus an on-box check that a forced pane
      really gets the integration
