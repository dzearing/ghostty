# T947 - Terminal copy and paste give up if any other process holds the clipboard for a moment

## Summary

Found while fixing T850. `OpenClipboard` does not queue: it fails outright
while ANY other process on the desktop holds the clipboard, which something
routinely does for a few milliseconds after a copy (the copying app itself,
Explorer, a clipboard-history service, an RDP clipboard bridge). Two call
sites in the terminal surface still take a single attempt and give up:

- `src/apprt/win32/Surface.zig:1687` — the PASTE read. A refused open logs
  `OpenClipboard failed` and the paste does nothing.
- `src/apprt/win32/Surface.zig:1818` — the COPY write. Same shape: the
  selection is silently not copied.

Every other clipboard user in the codebase now goes through
`src/apprt/win32/clipboard_open.zig` (eight attempts, 15ms apart, ~120ms worst
case): `clipboard_image` (the feedback composer's image paste) and
ViewerPane's text helpers (the link menu's Copy, T826). These two are the
last single-attempt opens left.

## In plain terms

Every so often, pressing copy or paste in the terminal does nothing at all —
no error, no message, just nothing. It happens when some other program on the
machine is touching the clipboard at that exact instant, which is a matter of
milliseconds and pure luck. The rest of the app already waits a moment and
tries again; the terminal itself does not, so it is the one place where the
user's keystroke can vanish.

## Goals

- [x] `Surface.zig`'s paste read goes through `clipboard_open.open`
- [x] `Surface.zig`'s copy write goes through `clipboard_open.open`
- [x] No single-attempt `OpenClipboard` call remains in `src/`
- [x] A harness exists that can SEE the defect, rather than a fix taken on
      trust: `test\win32\clipboard-retry.ps1`

## Validation criteria

- [x] `w32.OpenClipboard` appears only inside `clipboard_open.zig`. Verified
      by grep AND mechanized as arm C of `test\win32\clipboard-retry.ps1`, so
      the next clipboard call site cannot quietly reintroduce the shape.
- [x] A negative control proves the retry engages. `test\win32\clipboard-retry.ps1`
      holds the clipboard from a second process and drives a REAL copy through
      the terminal (OSC 52, which ConPTY passes through to
      `Surface.setClipboard`) - no GUI, no selection. Arm B churns 45ms held /
      25ms free and requires all eight copies to land; arm A holds continuously,
      which is past the retry budget, and requires the copy to be LOST, so the
      oracle is proven able to see a failure at all.
- [x] The control was RUN against the defect, not just described: with the copy
      site reverted to a single attempt, arm B scored **2/8** and arm C named
      `Surface.zig:1825`. With the fix, **8/8** and arm C clean.
- [x] Both zig test lanes green (`floor-lane.ps1 -Lane all`); the win32
      acceptance floor P1-P3 unchanged.
