# T205 - Tabs live below a standard titlebar instead of inside it

## Summary

User follow-up 2026-07-30, sent WITH a screenshot of stock Windows Terminal as
the reference:

> "ok this is normal terminal and it looks more polished than what you've
> built ... the hamburger icon ... doesn't horizontally align under the X above
> it"

The alignment complaint is a symptom; this is the cause. Ghoztty on Windows
draws a **standard OS titlebar** (window title + minimize/maximize/close) and
then a **separate tab strip row beneath it**. Windows Terminal - and Edge,
Explorer, Files, VS Code - put the tabs **inside the titlebar**: one row
holding tabs, the "+", the menu affordance, and the caption buttons.

That is why nothing lines up. There are two rows of controls with two
different owners (DWM owns the caption buttons, we own the strip), so a strip
button can only ever *approximately* sit under a caption button, and the
approximation drifts with DPI, with the caption button width, and with
Windows' own titlebar metrics. It is not fixable by nudging x coordinates -
the fix is to stop having two rows.

Secondary cost: a full row of vertical space (32 DIP strip + ~32 DIP caption)
spent on chrome in a terminal, where vertical space is content.

## Current state (verified by reading)

- `Window.zig:764` - `tabBarHeight()` returns a flat `32.0 * scale`, a strip
  that begins below the client-area top, i.e. below the OS caption.
- No `WM_NCCALCSIZE` handling anywhere in `src/apprt/win32/` - the non-client
  area is entirely the system's, so the caption is stock.
- `DwmExtendFrameIntoClientArea` is DECLARED in `win32.zig:1250` but has no
  call site. The binding exists; the feature does not.
- `DWMWA_CAPTION_COLOR` IS used (`Window.zig:453`), i.e. today's approach is
  "tint the system caption to match", which is the workaround this task
  replaces.

## What the reference screenshot shows

One row, left to right: tab, tab, tab (selected one filled with rounded top
corners), "+", a **chevron-down** dropdown, then a long draggable gap, then
minimize / maximize / close. Each tab carries a **profile icon** left of its
label. Ghoztty has none of: the merged row, the tab icons, or the chevron
(T190 chose a hamburger; worth revisiting against the reference, but that is a
separate call - record it either way rather than changing it silently).

## Deliverables

1. Custom frame: handle `WM_NCCALCSIZE` to reclaim the caption area, keep the
   resize borders and the drop shadow (the standard approach is to keep a
   1px top border and extend the frame, NOT to strip the non-client area to
   zero - a naive `WM_NCCALCSIZE` returning 0 loses the shadow and the snap
   behaviors).
2. Draw the strip in the reclaimed row. Caption buttons: either host the
   system ones or draw them, but if drawn they MUST match Windows' current
   metrics and hover/pressed treatment, and close must light red on hover.
3. `WM_NCHITTEST` must return `HTCAPTION` for the empty strip area so the
   window still drags by it, `HTMINBUTTON`/`HTMAXBUTTON`/`HTCLOSE` for the
   caption buttons so **Snap Layouts** still work on hover-over-maximize
   (this is the detail custom frames most often lose, and it is a real
   Windows 11 feature regression if missed).
4. Maximized state must add the correct top padding, or the strip is clipped
   off the top of the screen when maximized - the classic custom-frame bug.
5. High-contrast mode and the "show accent color on title bars" personalization
   setting both need a decision; a custom frame opts out of the system's
   handling of both.
6. Evaluate tab profile icons (the reference has them) - likely its own task
   once the row exists; file rather than fold in.

## Risks

This is the highest-risk item in the T202-T205 band: a custom frame touches
dragging, snapping, maximize, multi-monitor DPI changes, and accessibility.
It is also the one that makes the chrome actually read as Windows 11 rather
than as a strip bolted under a system titlebar. Do it AFTER T202/T203/T204
have settled the strip's own painting, so a frame regression is not tangled
with a layout regression.

## What shipped (2026-07-31)

**One chrome row.** On a window that owns its caption (T254) and is showing a
strip, the tab run now lives IN the caption band: tabs, "+", a drag gap, then
the "…" and minimize/maximize/close, all on one row. At one tab there is no
strip (T234) and the band stays standalone with the window title in it, so the
two states are 36 DIP and 40 DIP of chrome rather than 36 and 76.

- **`caption_layout.Metrics.init(scale, mode)`** gained `Mode.{standalone,
  with_tabs}`. Merged, `caption_h` IS `tab_strip_layout.bar_h` and `btn_top` is
  `icon_button.targetBox(ib, tab_strip.buttonHit(0)).top` — the STRIP's own
  button baseline, asked for rather than restated. Centering the 28 DIP square
  in the 40 DIP band would have put it 2 px above the "+" and the tab close
  "×", which are on that frame since T204 — i.e. it would have reproduced the
  user's original complaint inside the fix.
- **`Layout.band_left` is the seam.** The strip paints and blits
  `[0, band_left)`, the caption `[band_left, client_w)`. Both fill the identical
  chrome background so the seam is invisible; what it buys is that the two
  BitBlts are disjoint, so a caption repaint (hovering close) cannot erase a
  tab and the paint ORDER stops mattering. `Window.stripClientWidth` hands the
  strip `band_left + strip_pad_r`, which is exactly the width at which a
  menu-less strip lands the "+"'s painted limit ON the seam — asserted, not
  assumed, in "band_left is the seam".
- **`ncHitTest` gained `client_right`.** In the merged band the strip's own
  controls must answer `HTCLIENT` or every tab would drag the window instead of
  selecting. It is a parameter, not a `Layout` field, because the "+" follows
  the last tab and a tab's width comes from text metrics this module never
  measures; `Window` passes the rect the strip PUBLISHED at its last paint —
  the same rect `handleTabBarClick` reads. Clamped to `band_left`, so a stale
  rect can never swallow the close button.
- **Nothing horizontal changed.** The merge is a VERTICAL change: the caption
  cluster's x arithmetic is identical in both modes, asserted by "standalone's
  horizontal arrangement is untouched". That is why deliverable 2's "match
  Windows' metrics" and deliverable 3's HTMINBUTTON/HTMAXBUTTON/HTCLOSE work
  was already done by T254 and needed no revisiting.
- **`Window.chromeHeight()`** replaces every `captionHeight() + tabBarHeight()`,
  because that sum stops being the answer the moment the two are one row.
  `handleResize` now invalidates the caption too — `updateTabBarVisibility`
  routes through it, and the BAND ITSELF changes size when the strip appears.

**Deliverable 6 (tab profile icons) was filed, not folded in** — the task said
to. It is not filed yet as its own row; the reference has them and we do not,
and that is a separate visual change from the row merge.

### T257 paid for itself, and then charged interest

The app-side change touched **two** files (`caption_layout.zig`,
`Window.zig`); the script side was **one argument** (`-StripVisible`) added to
`lib\ChromeGeometry.ps1` and its nine call sites, exactly as T257 predicted
when it wrote *"T205 moves this datum a THIRD time … when it does, this file is
the edit."*

The interest was two scripts that had never controlled their own window size
and had been silently inheriting `window_placement-debug` (T85) from whichever
GUI script ran last — so their conditions depended on RUN ORDER:

- `tab-strip.ps1` — 3 red assertions on a default 782 px client, where the
  merged run (557 px) no longer holds three 281 px preferred tabs. Every
  condition it sets up is a ratio OF THE RUN and it was not controlling the
  input the ratio is taken of.
- `menu-bar.ps1` — 2 red, both ink probes: mid-strip landed inside a tab's
  title and the "strip's right end" probe landed on the "+" pushed to its
  limit. Both now sized to 1400x800, and the blank-control probe moved to
  `Strip-Geometry`'s `DeadX`, which is blank BY CONSTRUCTION rather than by
  luck.

Filed as **T267**, because the placement file is cleared by nobody and the
sweep is wider than these two.

Two more script-side corrections T205 forced, both of which would have passed
while asserting nothing:

- `menu-bar.ps1`'s `StripRightX` aimed at `clientW - padR - btn/2`, which on a
  merged row is the caption's **close button**. The assertion "clicking there
  opens no menu and no tab" would still have passed — a posted CLIENT click
  cannot press a caption button, which takes `WM_NCLBUTTONDOWN` — so it would
  have been green and empty. Retargeted to the strip's own right end
  (`BandLeft`).
- Its `stripRightInk` "no menu glyph at the strip's right end" probe was
  aimed at the same place, where close DOES paint a glyph — that one would have
  gone red against a correct build.
