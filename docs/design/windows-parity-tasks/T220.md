# T220 - Session-layout geometry can override a NEWER window-placement memory

## Summary

Two independent stores decide how big a restored window is, and it is not
clear which one is supposed to win:

- `%LOCALAPPDATA%\ghoztty\window_placement[-debug]` - the T85 placement
  memory: last USER-chosen size + maximized flag, written on WM_EXITSIZEMOVE
  and on maximize/restore transitions.
- `%LOCALAPPDATA%\ghoztty\session-layout[-debug].json` - the session-
  persistence manifest, which also carries per-window geometry and is
  replayed on re-attach.

Found while migrating `window-size-memory` for T217 (2026-07-31). With
session persistence ON, a relaunch after the app was killed opened at
`800,600` even though the placement memory said `950 700 0` - and did so
intermittently: 6 assertions failed on one run and the same script passed the
next three unchanged. `--session-persistence=false` makes it deterministic,
which is what the migrated script now does, so **the acceptance script is not
blocked on this**; the product question is.

## Details

The reproduced sequence, all on a throwaway `LOCALAPPDATA`:

1. Launch, drag-resize 800x600 -> 950x700. Placement memory becomes
   `950 700 0`; the layout manifest is written at some point too.
2. Force-kill the app (`Stop-Process -Force`).
3. Relaunch. Expected 950x700 (the placement memory). Sometimes 800x600.

The suspicion is that the manifest write races the kill, so step 3 replays a
manifest snapshotted BEFORE the resize, and the replayed geometry beats the
placement memory that was already updated. A force-kill is the test's doing,
but a crash is the same shape, and a crash is exactly when a user is most
likely to notice their window forgot its size.

Note `Kill-RepoInstances`-style cleanup does not remove the variable: it kills
`ghoztty.exe`, not `ghoztty-agent.exe`, so the agent (and its sessions)
survive into the next launch.

## What to decide, then enforce

1. **Which store wins**, stated once in the code and in
   `docs/design/session-persistence.md`. The likely answer is that the
   placement memory is authoritative for window SIZE and the manifest is
   authoritative for LAYOUT (splits, ratios, pane contents) - they are
   answering different questions and should not both write geometry.
2. Whether the manifest should carry geometry at all, or read it back from
   the placement memory on restore.
3. Whether the manifest write needs to be ordered against the placement write
   so a crash cannot leave the pair inconsistent.

## Validation

- A unit test in the none lane over the precedence rule.
- An on-box script: resize, force-kill, relaunch WITH session persistence on,
  and assert the remembered size - the case `window-size-memory` currently
  has to disable. Run it x3; the bug is intermittent, so a single green run
  is not evidence.
- `window-size-memory.ps1` keeps its `--session-persistence=false` (it is
  testing the placement memory in isolation, which is still the right scope);
  the new coverage is additive.
