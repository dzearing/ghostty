# T1178 - In-app update on Windows like the Mac: download and apply a new build from inside Ghoztty, no upgrade scripts

## Summary

Windows today detects a newer win-v release (T24 update_check.zig + balloon) but cannot install it - upgrading means scripts\upgrade-ghoztty-windows.ps1 and hand steps. Mac Ghostty updates itself. Give Windows the same: notify, download the MSI, verify it, and apply it (msiexec per-user, in-place upgrade) with the app relaunching afterwards, driven from the app UI. Retire the upgrade scripts as a user-facing path once this lands.

## In plain terms

Right now, when a new Windows Ghoztty is published, the terminal tells you
about it and then leaves you to it: you go to a web page, download an
installer, close Ghoztty, and run it. The Mac version just updates itself.
After this, so does the Windows one - a notification you click, one question
("Ghoztty will close, install the update and reopen"), and it is done. The
shells you have open are kept.

## Goals

- [x] The app finds the release's installer, not just its version number
- [x] It downloads it in the background and checks that what arrived is really an installer
- [x] Clicking the notification asks once and then installs and reopens
- [x] Open terminal sessions survive the update
- [x] A failed update still leaves a working terminal
- [x] `auto-update` (off / check / download) means the same thing it does on the Mac
- [x] The upgrade scripts are no longer the user-facing path

## Validation criteria

- [x] The `.msi` asset of the offered release is found, and never another release's - `update_apply.zig` unit tests (a feed carrying two win-v releases and a Mac DMG; asset-before-tag ordering; a zip-only release), plus `update-apply.ps1` scenarios 1 and 3
- [x] A body that is not an MSI package is refused before msiexec sees it - `looksLikeMsi` unit tests (HTML page, rate-limit JSON, empty, signature-only, right-size-wrong-bytes) + `update-apply.ps1` scenario 2, which asserts nothing was left on disk
- [x] `auto-update = download` (and unset) pre-downloads; `check` does not; `off` does not even check - `policyFromName` unit tests + `update-apply.ps1` scenarios 1, 4, 5
- [x] A debug build stages only into its own lineage's directory - `stagingDir` unit test + `update-apply.ps1` scenario 1 asserts `updates-debug` was used and `updates` was not created
- [x] The applier waits for the app to exit, runs msiexec non-interactively with no reboot, and relaunches - `update-apply.ps1` scenario 8 drives the real applier end to end and matches the exact command line (`/qb-!`, `/norestart`, `/l*v`)
- [x] A failed install still relaunches the terminal - scenario 8 uses a package msiexec REJECTS and still asserts the relaunch; scenario 9 asserts the same for the refusal path
- [x] Leftovers from a previous update are swept at the next launch - `update-apply.ps1` scenario 6 (a `.old-<stamp>` file is removed, a similarly named file is not)
- [x] Floor lanes + the new acceptance script green on the box - lib/none/win32/agent all PASS; `update-apply.ps1` ALL PASS (36); `update-check.ps1` ALL PASS (12); ipc-p1/p2/p3 ALL PASS (25/20/16)
- [x] The new coverage can FAIL - a deliberately broken `update_install` test made the win32 lane go red naming that test (T1191's wiring lesson), then was restored
