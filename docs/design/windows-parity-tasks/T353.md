# T353 - Website Windows link step has never been run by GitHub (T39 residual)

## In plain terms

When a Windows release is published, the download buttons on the website are
supposed to move to it automatically. Nobody had ever watched that happen, and
one part of it — what the site does when the release's other half is writing to
the same page at the same moment — could only ever run during a real release,
which meant the first time it ran would be the release it broke. It has since
run twice for real (1.33.0 and 1.34.0, both correct), and the risky part is now
rehearsed on this box on every test run instead of waiting for a bad day.

## Goals

- [x] Confirm from evidence whether the website step has ever run for real
- [x] Make the rejected-push retry runnable outside a release
- [x] Exercise it with a real collision, and prove the other writer's work
      survives the retry
- [x] Tie an edit of either website script to a run of the harness that
      covers it

## Validation criteria

- [x] `test\win32\website-windows-download.ps1` section G runs
      `dist/website/publish-windows-links.sh` against bare repos on disk:
      ordinary push, republish no-op, forced collision, exhausted retries,

- [x] The collision arm proves the loop, not just its text: `push rejected

      on `origin/gh-pages` (b19a35608, e45887d17)

## Summary

T39 added a "Update website Windows download links" step to
`.github/workflows/release-windows.yml`. Like every other step in that
workflow, **GitHub has never executed it** — the workflow lives on
`users/dzearing/windows-amd64`, and `workflow_dispatch` only becomes
available once a workflow file is on the default branch. This is the same
residual T38 recorded for the publish half, extended to the website half.

## Details

What IS validated on box (`test/win32/website-windows-download.ps1`):

- `dist/website/update-windows-links.py` run for real, with the same
  interpreter CI uses — it moves all three Windows anchors, leaves the
  macOS download byte-identical, is idempotent, and errors rather than
  no-oping when an anchor is missing.
- The workflow *text*: it calls the script, it is gated on
  `PUBLISH == 'true'`, and it runs after the publish step.

What is NOT validated, and can only be validated by a real run:

1. `python3` resolves on `ubuntu-latest` (it does; assumed, not observed).
2. The `git clone --branch gh-pages` with `x-access-token:$GITHUB_TOKEN`
   has push rights from *this* workflow (release.yml's identical clone
   proves the token works; this workflow has `permissions: contents:
   write` but has never pushed).
3. The **rebase-retry loop** actually resolves the race with
   `release.yml`'s concurrent appcast push. That path only executes when
   two pushes collide, which is exactly the case nobody sees until it
   fails a release.

Item 3 is the interesting one: the retry is dead code on a normal run, so
the first time it matters is the first time it is needed.

## What actually happened (2026-08-21)

The premise above was already stale when this task was picked up. GitHub HAS
run the step: `origin/gh-pages` carries `Update website Windows download to
win-v1.33.0` (b19a35608, 2026-08-18) and `win-v1.34.0` (e45887d17,
2026-08-21), both authored by `github-actions[bot]`. That answers items 1 and
2 by observation — `python3` resolved on the runner and the
`x-access-token:$GITHUB_TOKEN` clone had push rights.

Item 3 did NOT get answered by those runs, and would not have been by the next
one either: for v1.34.0 the appcast push landed at 14:08 UTC and the website
push at 21:33 UTC, so there was no race and the retry never executed. Waiting
for a release that happens to collide is not a test plan.

So the retry was made runnable instead. The step body moved out of the YAML
into `dist/website/publish-windows-links.sh` (byte-for-byte the same
behavior, plus a loud failure when the rebase itself fails), and section G of
`test\win32\website-windows-download.ps1` runs it against bare repos on disk
with a rival push staged through a `GIT_TEMPLATE_DIR` `pre-push` hook — the
same shape as release.yml's concurrent appcast push. The collision arm asserts
the rejection is real, that the rebase-retry lands on the second attempt, and
that the rival's `appcast.xml` is still on the branch afterwards, which is what
separates a rebase from a force-push.

Also fixed in passing: section F was red. The in-repo mirror of the page was
three releases behind the deployed one (v1.31.0 vs v1.34.0), because those
releases updated gh-pages and nothing syncs back. The mirror was resynced from
`origin/gh-pages`.

*Original validation plan, kept for the record:* the next real release. Watch
both workflow runs; confirm
gh-pages gets both an appcast commit and a "Update website Windows
download to win-vX.Y.Z" commit, and that the live page's `win-msi-link`
points at the release just published. If the two pushes did collide, the
Windows job's log will show a "push rejected (attempt N)" line — capture
it, because that is the only evidence the retry works.
