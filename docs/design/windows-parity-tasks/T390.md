# T390 - +reload verb: reload a viewer pane in place (P8, split from T90f)

## Summary

Win32 server half of +reload: web mode re-fetches from ORIGIN via CallDevToolsProtocolMethod Page.reload ignoreCache (Reload() fallback), file mode re-renders preserving scroll, no completed load = full load, terminal target = exact Mac error string exit 1.

## Done 2026-08-02

`ghoztty +reload --target=<viewer>` works on Windows. A website viewer
re-fetches its page from the origin; a file viewer re-reads the file and
re-renders it.

**The branch is the verb, so the branch is the pure part.** Mac's
`reloadContent` is a three-way switch wrapped in two COM calls, and the switch
is the whole behavioral contract: `viewer_content.reloadPlan(mode,
page_loaded)` returns `full_load` / `refetch` / `rerender` and is tested in the
none lane, including the case that is easiest to get wrong -- a pane with NO
completed load reloads by loading from scratch, in every mode. That case is
exactly when a user reaches for `+reload`, because the pane they are staring at
is empty.

`ViewerPane.page_loaded` is the new state it reads (Mac's `pageLoaded`):
cleared by every `navigate`, set from `onNavigationCompleted` -- and set there
for WEB mode too, which meant moving the flag above the `isFile` early return.
Left stale it would let a reload arriving mid-navigation re-render the OLD
file into the NEW page.

**Two vtable slots that were inside opaque runs.** `Reload` (31) and
`CallDevToolsProtocolMethod` (36) both sat in `post_script`/`history`, so
naming them meant splitting those runs into four shorter ones whose LENGTHS
hold the numbers in place. Both offsets are asserted with `@offsetOf`.
`Page.reload` with `{"ignoreCache":true}` is the only way to say "bypass the
cache" through this API -- `Reload()` is an ordinary reload -- and it stays as
the fallback for a refused DevTools call, because a reload that does nothing is
worse than one that may hit cache.

**The live test proves the cache bypass rather than assuming it.** The win32
lane's host-floor test grew a second loopback server whose page reports WHICH
fetch it came from, served with `Cache-Control: max-age=600` so a
cache-allowed reload would legitimately be entitled to skip the network. After
`reloadContent()` the pane reports `req2`, the server counted exactly 2 page
requests, and the second request carried `no-cache` -- the same claim from the
request side (Chromium sends `no-cache` for a bypassing reload and `max-age=0`
for an ordinary one). File mode is proven by changing the file ON DISK under a
loaded pane and watching the headings follow it (3 -> Delta/Epsilon).

Two things the test taught, both about oracles rather than about reload:

- **Chromium asks every origin for a `/favicon.ico` it was never offered.** The
  first server counted every request and reported 4 fetches for 2 loads -- and
  worse, answered the favicon request with an HTML body carrying the next
  number, which put the page one ahead of the truth. The server now counts and
  serves only its own path.
- **One heading is not a table of contents.** `viewer.js:indexHeadings` reports
  nothing below two headings, so the first re-render oracle (`# Only`) read as
  zero headings and was indistinguishable from a render that failed. The
  reloaded file has two.

**The two terminal refusals are different strings on purpose** and both are
Mac's byte-for-byte: `target '<name>' is a terminal pane, nothing to reload`
for a named terminal, `focused pane of '<name>' is a terminal pane, nothing to
reload` for a window whose focused pane happens to be one. They are also not
the `is a viewer pane, not a terminal` string the terminal-only verbs use --
that one points the opposite way.

*Validation:* `zig build test` both lanes + `zig build test-agent` green;
`test\win32\viewer-panes.ps1` ALL PASS (92) x3; P1-P3 ALL PASS. The acceptance
script's GUI-side oracle is the missing-file viewer filing a SECOND `viewer
file error` line when reloaded -- proof the re-render ran inside the app, not
just that the verb returned success. Its own first draft aimed the
window-target rejection at `vp`, a window that had grown viewer splits, so the
focused pane was a viewer and the case passed for the wrong reason; it now
aims at a window with a single terminal in it.
