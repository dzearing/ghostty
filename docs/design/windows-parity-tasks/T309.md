# T309 - applyChromeTheme and DarkMode still re-derive the window-theme light/dark decision instead of chrome_theme

## In plain terms

A window is either a light window or a dark window, and the title bar, the
band under it, and the right-click menus all have to agree about which. Three
different pieces of code were working that out separately, each with its own
arithmetic. On every normal background they land on the same answer, so nobody
has seen this — but pick a background sitting right on the line between light
and dark and they can disagree, and you would get a dark title bar over a light
tab strip, or menus that open in the wrong palette. After this there is one
answer, and everything reads it.

## Goals

- [x] One function decides light vs dark for a window, and everything else
      consumes it
- [x] The title bar, the USER menus and the tab tooltip stop doing their own
      arithmetic
- [x] The weighting matches the Mac's, so a background gets the same title bar
      on both platforms
- [x] A test that would fail if the answers ever drift apart again

## Validation criteria

- [x] `isDark` and `chromeBase` agree for every theme across a swept
      background range — the assertion that could not exist with two functions
      (`chrome_theme.zig`, "the chrome's side never disagrees with the surface
      it paints"; runs in the `none` lane: 76 tests with `-Dtest-filter=isDark`
      vs 74 with a nonsense filter)
- [x] The surfaces the explicit themes sit on are asserted to be on their
      nominal sides, so the sweep cannot pass vacuously
      (`isDark: the decision table, and the surfaces are on their nominal sides`)
- [x] Only `window-theme = system` consults the OS answer
      (`DarkMode.zig`, "only `system` reads the OS side"; win32 lane, 78 vs 77)
- [x] `test\win32\chrome-theme.ps1` stays green
- [x] Floor: both test lanes, `test-agent`, the `lib` compile, P1-P3

## Summary

There are now TWO answers to "what side of light/dark is this window on, given
`window-theme` and the terminal background", and they are computed by different
code with different math.

That is the exact defect T203/T304 was filed against, one level up: not a
disagreeing COLOR this time, but a disagreeing DECISION that colors are picked
from. Four copies is how the tab-strip geometry ended up with a latent DPI bug
nobody could see on this box (T257); two is how it starts.

## The two derivations (VERIFIED by reading at HEAD, 2026-08-01)

1. `Window.applyChromeTheme` (`src/apprt/win32/Window.zig:445`) — its own
   inline Rec.709-ish `0.2126/0.7152/0.0722` luminance over the background,
   `< 0.5` is dark, then a `switch` on the theme. Drives the DWM immersive
   dark-mode attribute and the caption tint. `DarkMode.apply` takes the same
   two arguments and makes the same call again for the USER menu palette.
2. `chrome_theme.chromeBase` (T304) — a `switch` on the same theme returning
   the surface the chrome paints FROM, with the light/dark question answered by
   `systemUsesLightTheme()` for `system` and by the caller's background for
   `auto`. `color_math.isLight`, when it is reached, is Rec.601
   (`0.299/0.587/0.114`), a DIFFERENT weighting from (1).

They agree on this box and on any ordinary background. They are not guaranteed
to agree near the crossover, and nothing asserts that they do.

## Fix

One function owns the decision — most likely `chrome_theme`, since it is pure
and already unit-tested at every luminance — and `applyChromeTheme` /
`DarkMode.apply` consume it. Pick ONE luminance weighting and say in a comment
why (`color_math.isLight` is already the repo's answer everywhere else, and
`contrastForeground` documents why Rec.601's answer is not trusted alone).

## Validation

- A unit test in the none lane that sweeps background x theme and asserts the
  DWM-mode decision and `chromeBase`'s side never disagree — the assertion that
  cannot exist while there are two functions.
- `test/win32/chrome-theme.ps1` and `window-theme`'s existing coverage stay
  green; both test lanes, `test-agent`, P1-P3.
