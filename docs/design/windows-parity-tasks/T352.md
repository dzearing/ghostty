# T352 - Acceptance scripts reuse FIXED --target names across runs; make them run-unique

## Summary

Every acceptance script hardcodes its target names: `p1win`, `p3a`, `soak`,
`prof`, `ipcload`. T248 removed the mechanism that made a leftover pane come
back (`Reset-GhozttyTestState`), which is the important half - but the names
themselves are still shared state between runs, and between scripts.

Two failure modes survive:

- Two scripts running back to back against the same instance can collide on a
  name. `+new-window --target=` is idempotent, so the second one silently
  FOCUSES the first one's window rather than failing.
- A run that dies before its cleanup (a timeout, a Ctrl-C, a crashed probe)
  leaves the name registered. The next run's reset clears it now, but any
  script that skips the reset - or a future one that forgets it - is exposed
  again. A run-unique name cannot be inherited by anyone.

`test\win32\target-staleness.ps1` already does this: its target is
`"t248w$PID"`, and its handshake files carry `$PID` too (the third part of the
T248 fix). `color-contrast.ps1` does it for its handshake files.

## What to do

- Give each script a run-unique prefix derived from `$PID` and use it for
  every `--target`/`--name` it registers.
- Keep the assertions reading the variable, not the literal - several match on
  `'\[target: p1win\]'` in `+list` output today.
- Do the same for any fixture handshake file that is not already unique.

## In plain terms

The tests that prove Ghoztty works build little throwaway terminal windows and
give them names. Every test used the same names every time, so a window left
behind by a test run that crashed was still sitting there under the name the
next run wanted - and because asking for a window by a name that already
exists just brings that window to the front, the next run would quietly grade
the leftovers from the last one instead of anything it had built. Nobody would
see a failure; they would see a pass that meant nothing. After this, each run
works in a space of its own that no other run can reach into.

## Goals

- [x] Every acceptance script's IPC endpoint is unique to the run, not just to
      the script
- [x] The two scripts that repeated their endpoint as a literal somewhere else
      (a bash fixture, a second instance) splice the live value instead
- [x] A checked rule fails the tree if a fixed endpoint comes back, with a
      reviewable opt-out for a script that genuinely needs one
- [x] The floor stays green

## Why the fix is the endpoint and not the names

The names were the symptom. A `--target=` name is only reachable through an IPC
endpoint, and 131 of these scripts pinned that endpoint to a fixed string
(`$env:GHOZTTY_PIPE_SUFFIX = '-vptest'`). Making the endpoint run-unique closes
BOTH failure modes in the Summary at one site per script, for every name the
script registers now or later - where prefixing the names would have been ~500
edits that left the endpoint, the window ids, and the sessions still shared.
`Set-GhozttyTestIsolation` had always appended `$PID`; the hand-rolled half of
the suite never did.

Note on the original "run twice concurrently" criterion: that is not a check
this box can honour, and not because of naming. `Reset-GhozttyTestState` kills
every repo ghoztty by exe path, so two overlapping runs would take each other's
instance down whatever their endpoints were - which is why go.md requires the
lanes and the acceptance scripts to run sequentially. The run-unique endpoint
is what makes SEQUENTIAL runs independent, including after one dies without
cleaning up, and that is the property actually tested above.
