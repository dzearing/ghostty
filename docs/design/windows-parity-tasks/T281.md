# T281 - Post-swap verification stops at ghoztty.exe: the agent binary and the mirrored install locations are still trusted to a Copy-Item return

## In plain terms

When a new Ghoztty is delivered to this box, three programs are copied into
place, and until now the delivery only ever checked ONE of them afterwards. The
one it did not check includes the background service that keeps your terminal
sessions alive across restarts — and that copy has failed before, silently,
leaving a months-old copy on disk while the delivery announced success. After
this, the delivery asks each program which build it is and refuses to call
itself successful if the answer is the old one. You notice when something goes
wrong: instead of finding out days later that a fix never arrived, the delivery
says so at the time.

## Goals

- [x] The delivery can read the agent's own build stamp (`ghoztty-agent --version`)
- [x] The agent binary ON DISK is verified after the swap, and a swap that did
      not take can no longer end in `UPGRADE OK`
- [x] `-AppOnly` (the morning refresh, which deliberately ships no agent) is a
      stated SKIP rather than a daily failure
- [x] Every mirrored install location is read back and named — the exe by its
      commit, the agent by its stamp
- [x] A live negative control reproduces the 2026-07-20 skipped swap

## Summary

T208 gave the delivery a number both ends can compare and then checked exactly
ONE file with it: `ghoztty.exe` in the primary install dir. Two other binaries
ship in the same delivery and are still trusted to "Copy-Item did not throw" -
which is the precise standard T208 exists to reject.

## The two halves

1. **`ghoztty-agent.exe`.** The swap moves the running agent's image aside and
   copies the new one in (deliberately without killing it - the running agent
   keeps its PTYs and the new binary takes over at the next cold start). Nothing
   reads the result back. That rename-aside dance already has a known failure
   mode with a `WARNING:` branch (2026-07-20: `Remove-Item` failed silently,
   `Move-Item` hit "already exists", and the agent swap was SKIPPED) - so a
   delivery can leave a months-old agent on disk and say `UPGRADE OK`.

   It is checkable today: `ghoztty-agent.exe --version` prints
   `ghoztty-agent <yyyymmdd>-<commit>` (verified on the box 2026-08-01:
   `ghoztty-agent 20260731-467417e96`), so the same
   `scripts/delivery-version.ps1` comparison applies once the parser learns that
   second shape. Note what must NOT be asserted: the RUNNING agent is expected to
   be older (CLAUDE.md's lazy-upgrade contract). The claim is about the bytes on
   disk.

2. **The mirrored install locations.** T208 automated the Desktop portable and
   the `\\homeassistant\share` copy, which the log shows were previously done by
   hand. They are best-effort by design (a sleeping NAS must not fail a
   delivery), but "best-effort" currently means the log records which file names
   were attempted - not that any of them landed as the delivered commit. A
   `+version` read per location, logged per location, would make the standing
   "deliver to every install location" bar checkable instead of assumed.

## Deliverables

- Teach the version parser the agent's `--version` shape and verify the agent
  binary ON DISK after the swap, distinctly from the running agent.
- Read back one `+version` per mirrored location and log it; a location that
  copied but does not report the delivered commit is a WARNING with the
  location named, not silence.
- Keep both non-fatal for the MIRRORS (unreachable NAS) but treat the primary
  agent binary the same way the primary exe is treated.

## Validation

- Extend `test\win32\upgrade-staleness.ps1`: its sandbox already stages a real
  binary and asserts on the log, so the agent half needs a staged
  `bin\ghoztty-agent.exe` plus a case where the rename-aside fails.
- Negative control that matters: an agent swap that is SKIPPED (the .bak is
  undeletable and the move fails) must not be able to end in `UPGRADE OK`.
