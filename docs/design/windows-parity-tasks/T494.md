# T494 - A torn zig-cache entry (zero-filled options.zig, overflowed timestamps) fails a floor lane as if the code were red - floor-lane.ps1 should recognize cache corruption and self-heal

## In plain terms

The nightly test runner sometimes reports a failure that has nothing to do
with the code: a build-cache file on disk got half-written (a crash or power
blip), and the compiler chokes on the garbage. A person looking at the red
result reads it as a broken change. The runner should notice "this is a
mangled cache file, not a mangled program", clear just that file, and try
again by itself.

## Goals

- [x] floor-lane.ps1 recognizes the cache-corruption signature and retries
      once after clearing the torn entry
- [x] The self-heal is loud in the log (which entry, why) so it never hides a
      real failure
- [x] A second failure after the heal is reported as a genuine FAIL

## Summary

Observed 2026-08-05 during the T253 floor run:

- `LANE none FAIL in 15s` with
  `.zig-cache\c\047ecd4ac00fbb503a242306e56ffc54\options.zig:1:1: error:
  expected type expression, found 'invalid token'` — that file was 2036 bytes
  of ZEROS (verified by reading the bytes), i.e. a torn write from some earlier
  crash, not a source problem. Deleting the entry and re-running the lane made
  it PASS with zero code changes.
- The win32 and agent lanes both warned `Invalid timestamp in cache entry:
  999999999999999999999999999999999999999999999999 err=error.Overflow` — a
  second, non-fatal corruption signature in the same cache.

The failure signature is recognizable: `error: expected type expression, found
'invalid token'` (or similar parse errors) pointing INTO `.zig-cache\`, plus
the timestamp-overflow warning. floor-lane.ps1 already parses the log for
`error:` lines; it can spot a path under `.zig-cache\` in the error location,
delete that one entry directory, log the heal, and re-run the lane once.
Guard against loops: at most one heal per lane per invocation, and the healed
re-run's result is final.

## Validation

## How it works

- `scripts\lib\CacheHeal.ps1` (new): `Get-TornCacheEntry` parses a red lane's
  log for compile `error:` lines whose file location resolves INTO a zig cache
  (`.zig-cache\` component, or under the global cache dir), and only names an
  entry when the path is `<cache-root>\<single-letter-bucket>\<hex-hash>\…` —
  so a mis-parsed line can never aim the delete at source. The HASH directory
  is the deletion unit (removing just the file would leave the entry manifest
  claiming the entry is intact). `Get-CacheCorruptionWarning` surfaces the
  non-fatal `Invalid timestamp in cache entry … error.Overflow` lines as
  corroboration. `Invoke-CacheHeal` deletes the entries with loud `CACHE HEAL`
  lines naming the entry and the compiler line that blamed it, re-verifying
  the `\<bucket>\<hash>` tail shape before touching anything.
- `scripts\floor-lane.ps1`: dot-sources the lib; on a lane FAIL it checks the
  log, heals at most ONCE per lane per invocation, and re-runs that lane once;
  the re-run's verdict is final, so a genuine failure fails again and is
  reported as such.
- `scripts\guard-due.ps1`: new `cache-heal` row covering the lib + harness
  (floor-lane.ps1 itself deliberately uncovered, same rationale as the crash
  rows).
- Bug found during testing: `return , $out` on an empty array makes an @()
  call site count 1 (the inner empty array becomes the element) — a phantom
  detection. Plain `return $out` with @() at call sites is the correct pair.
