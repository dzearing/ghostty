# T434 - test-agent builds and runs the same ~600 agent tests TWICE, concurrently, in two binaries

## In plain terms

One of the four automated check suites runs every one of its checks twice, at
the same time, in two separate copies of itself. That roughly doubles how long
it takes, and — because the two copies race each other for the same ports,
pipes and temp files on the machine — it is the leading suspect for why that
suite occasionally freezes instead of finishing.

## Goals

- [ ] `zig build test-agent` runs each agent test once, not twice
- [ ] The lane's wall time drops accordingly
- [ ] The freeze recorded in T430 is either gone or shown to have a different
      cause

## Summary

`zig build test-agent` wires **two** test artifacts (`build.zig`, the
`agent_step` block):

- `ghoztty-agent-test`, rooted at `src/agent_main.zig` → `remote/agent/main.zig`
- `ghoztty-agent-core-test`, rooted at `src/agent_core_test.zig` →
  `remote/agent_test.zig`

`remote/agent_test.zig` aggregates server, session, grid_snapshot, session_meta,
ring_snapshot, metrics, keepalive, self_update, socket_stream, socket_rw and
pipe_stream. **`remote/agent/main.zig` imports every one of those** (verified:
`main.zig:117-132`), and a zig test binary includes the tests of every file in
its import graph. So both binaries contain the same test set, and
`test_agent_step` depends on both run artifacts — which the build runner
executes **concurrently**.

Two consequences:

1. **Roughly double the lane time**, for zero extra coverage.
2. **Two processes running the same real-pty / loopback-socket / named-pipe
   tests at the same instant.** T430 recorded exactly this pair frozen together
   with identical `UserModeTime` across two samples 45s apart, and noted
   concurrency as a suspected aggravator without identifying its source. This
   is the source.

## Where to look

`build.zig`, the `agent_step` block (~lines 98-166). The comment on
`agent_core_test` says its ~140 tests "ran in NO build step", which was true
when it was written of the *standalone* `zig test -Mroot=…` invocation — but the
exe test binary already covered them via the import graph.

Do not just delete one: check first whether either binary reaches a test the
other does not (the exe root pulls tray/enroll/single_instance; the core root
pulls `grid_snapshot`'s src/terminal path). The answer is probably "keep the exe
root, drop the aggregator", but it must be established rather than assumed —
count the tests each binary reports today and diff the names.

## The other half: `ghoztty-agent-test.exe` links the WebView2 viewer

Same root question — what is actually in the agent lane's binaries. Verified on
2026-08-03 by string-scanning the built exes:

| binary | `EBWebView` | `host floor` | `ViewerPane` |
|---|---|---|---|
| `ghoztty-agent-core-test.exe` | no | no | no |
| `ghoztty-agent-test.exe` | **yes** | **yes** | **yes** |

and confirmed live: that process spawned an `msedgewebview2.exe` whose
`--user-data-dir` carried its own pid. **The agent is a headless daemon; its
test binary should not be able to open a browser.** T430 asked this question of
the core binary and answered "no"; the exe-rooted binary is where it is true.

The import path is not obvious — `remote/agent/main.zig`'s `@import` lines reach
no `apprt` — so the first job is to find it (`zig build test-agent --verbose`,
or bisect by commenting imports). Whatever it is, the win32 viewer tests running
in the agent lane is why the agent lane inherited the WebView2 hangs T430 fixed,
and it roughly doubles what this lane compiles.

## Validation

- Test count before/after, per binary, so nothing silently stops running.
- `ghoztty-agent-test.exe` no longer contains `ViewerPane` / `EBWebView`.
- `powershell -NoProfile -File scripts\floor-lane.ps1 -Lane agent -Repeat 5`:
  5 x PASS, and note the wall time against today's.
