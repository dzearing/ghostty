# T613 - Closing a remote window while its Activity Monitor panel is open crashes the app

## In plain terms

Open a terminal window on another machine, open the Activity Monitor from its
command palette, then close that window. The whole app dies — every other
window and everything running in it goes with it, with no message. You do not
have to touch the Activity Monitor for this; simply having it open is enough.

## Goals

- [ ] Closing a remote window under an open Activity Monitor panel leaves the
      app running, with every other window intact.
- [ ] The panel survives it too, and reports the machine as unreachable rather
      than pretending to still be sampling it.
- [ ] A regression arm asserts survival (section G4 of
      `test/win32/activity-monitor-remote.ps1`).

## Summary

`ghoztty +close --target=<remote window>` (and the title-bar X) segfaults the
process when an Activity Monitor panel is open for that window's machine.

**This is NOT the borrowed-connection dangler T301 fixed**, and it is older than
T301: it reproduces with T301's `ActivityMonitor.releaseBorrowed` neutered to a
no-op, i.e. against T296-era behavior. T301 added the release because a panel
holding a freed connection is its own use-after-free; this crash is a second,
independent one on the same path.

## Evidence

Reproduced on this box, 2026-08-08, against `-Doptimize=Debug`:

- `test/win32/activity-monitor-remote.ps1` section G4 (added by T301) —
  `G4 the closing window told the panel to let go of its connection` PASSES,
  and then the app is gone.
- A standalone repro (loopback agent + remote window + palette-opened panel +
  `+close`) crashes with **no panel involved in the switch at all**, so the
  carousel is not implicated.
- **Control 1**: the same close with NO panel open does not crash.
- **Control 2**: the same close WITH a panel open and `releaseBorrowed`
  short-circuited to `return` still crashes — this is what dates it before
  T301.

The fault is a `Segmentation fault at address 0x…000` — page-aligned, i.e. a
touched page the debug allocator had already unmapped — landing inside the
address range of the **surface** allocation the log named moments earlier
(`surface deinit: start addr=…`). Instrumented ordering: the crash happens
**after** `Window.onDestroy` has run to completion (transports released, dialed
freed, machine freed, window struct destroyed), i.e. back inside
`DestroyWindow`, while Win32 is destroying the window's CHILD HWNDs.

That is the hazard `Surface.deinit` already names in a comment:

> Don't call DestroyWindow on the child HWND here. The OPENGL32.dll driver
> hooks into window destruction and segfaults after we've already cleaned up
> the WGL context.

...and the crash stack carries an `OPENGL32.dll` frame between the USER32
frames, under `Window.zig:6272 DestroyWindow` ← `IpcHandlers.handleClose`.

So the shape to investigate: with a panel open the process's allocation
pattern differs enough that the freed page is actually unmapped rather than
merely stale, turning a latent read-after-free during child-window destruction
into a hard fault. The panel is the trigger, not the owner — which is why the
fix almost certainly belongs in the surface/window teardown ordering, not in
`ActivityMonitor.zig`.

## Where

- `src/apprt/win32/Window.zig` — `close`, `onDestroy`, `windowWndProc`.
- `src/apprt/win32/Surface.zig` — `deinit` (the deliberate no-DestroyWindow
  comment, ~line 934).
- `test/win32/activity-monitor-remote.ps1` — section G4 carries the arm.

## Validation criteria

- [ ] A standalone repro (remote window + palette-opened panel + `+close`)
      leaves the app alive, run 3× for a crash that may be allocation-timing
      dependent.
- [ ] `test/win32/activity-monitor-remote.ps1` G4 asserts app survival and the
      panel still being open, and the script is ALL PASS.
- [ ] The same close with the panel open does not crash under the title-bar X
      either, not only under `+close`.
- [ ] Both `zig build test` lanes plus `zig build test-agent` green; P1-P3 ALL
      PASS.
