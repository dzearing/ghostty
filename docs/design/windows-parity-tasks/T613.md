# T613 - Closing a remote window while its Activity Monitor panel is open crashes the app

## In plain terms

Open the command palette in a window — or the find bar — and then close that
window. The whole app dies: every other window and everything running in every
one of them goes with it, with no message. It was found by opening the Activity
Monitor on a remote window, but the Activity Monitor is only how you got there:
what does the damage is having opened the palette at all, in any window, at any
point in that window's life.

## Goals

- [x] Closing a window that has opened the palette (or the search bar) leaves
      the app running, with every other window intact.
- [x] The title-bar X does it too, not only `+close`.
- [x] Closing a remote window under an open Activity Monitor panel leaves the
      app running, and the panel survives it, reporting the machine as
      unreachable rather than pretending to still be sampling it.
- [x] Regression arms assert survival: `test/win32/palette-close-crash.ps1`
      (new, agent-free) and section G4 of
      `test/win32/activity-monitor-remote.ps1`.

## Summary

`ghoztty +close --target=<remote window>` (and the title-bar X) segfaults the
process when an Activity Monitor panel is open for that window's machine.

**This is NOT the borrowed-connection dangler T301 fixed**, and it is older than
T301: it reproduces with T301's `ActivityMonitor.releaseBorrowed` neutered to a
no-op, i.e. against T296-era behavior. T301 added the release because a panel
holding a freed connection is its own use-after-free; this crash is a second,
independent one on the same path.

## Evidence

Reproduced on this box, 2026-08-08, against `-Doptimize=Debug`:

- `test/win32/activity-monitor-remote.ps1` section G4 (added by T301) —
  `G4 the closing window told the panel to let go of its connection` PASSES,
  and then the app is gone.
- A standalone repro (loopback agent + remote window + palette-opened panel +
  `+close`) crashes with **no panel involved in the switch at all**, so the
  carousel is not implicated.
- **Control 1**: the same close with NO panel open does not crash.
- **Control 2**: the same close WITH a panel open and `releaseBorrowed`
  short-circuited to `return` still crashes — this is what dates it before
  T301.

The fault is a `Segmentation fault at address 0x…000` — page-aligned, i.e. a
touched page the debug allocator had already unmapped — landing inside the
address range of the **surface** allocation the log named moments earlier
(`surface deinit: start addr=…`). Instrumented ordering: the crash happens
**after** `Window.onDestroy` has run to completion (transports released, dialed
freed, machine freed, window struct destroyed), i.e. back inside
`DestroyWindow`, while Win32 is destroying the window's CHILD HWNDs.

That is the hazard `Surface.deinit` already names in a comment:

> Don't call DestroyWindow on the child HWND here. The OPENGL32.dll driver
> hooks into window destruction and segfaults after we've already cleaned up
> the WGL context.

...and the crash stack carries an `OPENGL32.dll` frame between the USER32
frames, under `Window.zig:6272 DestroyWindow` ← `IpcHandlers.handleClose`.

So the shape to investigate: with a panel open the process's allocation
pattern differs enough that the freed page is actually unmapped rather than
merely stale, turning a latent read-after-free during child-window destruction
into a hard fault. The panel is the trigger, not the owner — which is why the
fix almost certainly belongs in the surface/window teardown ordering, not in
`ActivityMonitor.zig`.

## Root cause (measured, 2026-08-11)

The allocation-timing theory above was wrong, and the panel is not even the
trigger — the **command palette** is, which is merely how you reach the panel.
A first-chance stack under `cdb` named it outright:

```
ghoztty!surfaceWndProc+0xb7          <- reads a freed *Surface
USER32!UserCallWinProcCheckWow
USER32!CallWindowProcW
OPENGL32!wglWndProc                  <- OPENGL32 subclasses the GL window
USER32!DispatchClientMessage         <- WM_DESTROY (msg=2)
win32u!NtUserDestroyWindow
ghoztty!close  ->  ghoztty!handleClose
```

One window procedure serves **three** windows: the terminal child HWND, the
search-bar popup and the command-palette popup all store the same `*Surface` in
their `GWLP_USERDATA`. Its `WM_DESTROY` handler cleared `Surface.hwnd`
unconditionally — and `Surface.deinit` destroys the two popups a few lines
*before* it clears the terminal window's `GWLP_USERDATA`:

1. `DestroyWindow(palette_hwnd)` delivers `WM_DESTROY` synchronously,
2. the handler sets `surface.hwnd = null` — the wrong window's field,
3. so the trailing `if (self.hwnd) |hwnd|` in `deinit` did nothing: the
   terminal window kept a `*Surface` freed moments later, **and** its deferred
   reap (T681) was never posted either — the USER-object leak T681 fixed came
   back for any pane that had ever opened a popup.

`Window.close` then calls `DestroyWindow` on the parent, Win32 destroys the
child, OPENGL32's `wglWndProc` subclass forwards the `WM_DESTROY`, and the
procedure dereferences the freed pointer at `[surface+0x12298]` = `Surface.hwnd`
— a page the debug allocator had already unmapped.

This is why every control in the Evidence section reads the way it does: "no
panel open" never opened the palette, and neutering T301's `releaseBorrowed`
changed nothing because T301 was never involved. It is also broader than the
title says: a plain LOCAL window is enough, and the search bar (ctrl+shift+f)
does it too.

## Fix

- `src/apprt/win32/surface_window_role.zig` (new, pure): `roleOf` classifies a
  handle against the three windows a Surface owns, and `destroyClears` says
  which fields a `WM_DESTROY` for that role may reset. Asserted in the `none`
  lane; wired in `src/apprt.zig`.
- `App.surfaceWndProc` derives **both** its guard and its `WM_DESTROY` clears
  from that one role, so the two cannot disagree about which window this is. A
  popup's destroy now clears only its own handle fields.

## Where

- `src/apprt/win32/App.zig` — `surfaceWndProc` (the guard + `WM_DESTROY`).
- `src/apprt/win32/surface_window_role.zig` — the routing rule.
- `src/apprt/win32/Surface.zig` — `deinit` (the popup destroys at ~921/939 and
  the `GWLP_USERDATA` clear + reap at ~971 that they used to disarm).
- `test/win32/palette-close-crash.ps1` — the agent-free regression arms.
- `test/win32/activity-monitor-remote.ps1` — section G4 now asserts survival.

## Validation criteria

- [x] A standalone repro (remote window + palette-opened panel + `+close`)
      leaves the app alive, run 3× for a crash that may be allocation-timing
      dependent. — 3/3 survive; the same repro was 2/2 crashes before the fix.
- [x] `test/win32/activity-monitor-remote.ps1` G4 asserts app survival and the
      panel still being open, and the script is ALL PASS.
- [x] The same close with the panel open does not crash under the title-bar X
      either, not only under `+close`. — arm B of
      `test/win32/palette-close-crash.ps1` (real `WM_SYSCOMMAND` SC_CLOSE).
- [x] Both `zig build test` lanes plus `zig build test-agent` green; P1-P3 ALL
      PASS.
- [x] Teeth-check: with the unconditional `surface.hwnd = null` put back, arm A
      of `palette-close-crash.ps1` goes red and the app is gone.
