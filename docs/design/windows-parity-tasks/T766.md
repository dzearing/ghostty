# T766 - persistence-flag.ps1 is RED at HEAD

## In plain terms

One of the tests that polices our other tests is currently failing, and has
been for a while. Its job is to make sure every test that opens a Ghoztty
window says out loud whether it wants the previous run's windows restored —
because a test that doesn't say gets whatever the last test left behind, and
then fails for reasons that have nothing to do with what it is testing. Four
window launches stopped saying. Nothing is wrong with the product; the guard
rail is just broken, and a broken guard rail that everyone has learned to
ignore is worse than no guard rail.

## Goals

- [ ] the four undeclared launches state their persistence (flag, or a
      `# persistence: <reason>` marker if a flag genuinely does not fit)
- [ ] `persistence-flag.ps1` is back to `ALL PASS`
- [ ] the two scripts still pass on their own subjects afterwards

## Summary

Found while validating **T255** (running the standing harness audits over a

## Why it matters

T158 exists because persistence is ON by default, so a GUI launched without
`--session-persistence=false` restores whatever panes the last launch left,
and each section writes the manifest the next one restores. That poisoned a
clean box twice (T131, then T155, where two scripts failed
`default setup: 2 visible panes` against a build whose geometry was correct).
The rule is not "always pass the flag" — it is **state which you want** — and
this sweep is the only thing that enforces it. A sweep that is red every time
you run it teaches the next session to skip running it.

The `url-scheme.ps1` sites are the interesting ones: they launch with a
`ghoztty-debug://open/urlwin` activation as the ONLY argument, and an
activation is deliberately answered before the single-instance bind, so the
intent there may genuinely be "this launch opens no window of its own" — in
which case the honest fix is the `# persistence: <reason>` marker rather than
a flag. Read the site before adding a flag to it.
