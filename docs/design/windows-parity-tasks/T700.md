# T700 - Mac: a +send-keys text run to a pane WITHOUT bracketed paste should follow xterm's LF-to-CR paste rule, as clipboard pastes already do

## In plain terms

Sending several lines of text to a plain shell works on both platforms, but for
different reasons — on a Mac it works by accident of how Unix terminals read
input. Making the Mac say what it means costs nothing today and stops the two
platforms drifting apart the next time something changes underneath.

## Summary

Follow-up from T661, which is landed on the Windows side. Two facts sit oddly
together in the shared core today:

- `src/input/paste.zig` (`encode`) implements the terminal-wide paste rule for
  CLIPBOARD pastes: a program in bracketed-paste mode gets newlines verbatim, a
  program that never asked gets LF mapped to CR. That is xterm's behavior and
  the comment there says so.
- `Surface.writePtyBracketed` — the `+send-keys` text-run path — does NOT.
  Its unbracketed branch falls through to `writePtyRaw` with the bytes
  untouched, so a text run's LF stays LF.

On macOS that difference is invisible: a POSIX pty in canonical mode accepts LF
as a line terminator, so `+send-keys "echo A\necho B\n"` runs both commands
either way. On Windows it is not invisible at all — conhost's VT input
translation SWALLOWS a bare LF, and the same send reached `cmd.exe` as
`echo Aecho B` (measured on box, 2026-08-10). T661 therefore implemented the
paste rule win32-side, in `IpcHandlers.prepareSendKeysRun`, using a new
`Surface.pasteIsBracketed` accessor.

So the rule now lives in two places, and only one of them is core. Moving it
into `writePtyBracketed`'s unbracketed branch would make it ONE rule for both
platforms and let win32 delete its copy. It is filed as `seat: mac` because the
change is in shared core and its only observable effect is on macOS, where this
seat cannot validate it — the win32 half is already green either way.

Expected macOS impact: none in practice for a shell (ICRNL makes CR and LF
equivalent at the line discipline), and a byte change only for a raw-mode
program that has not enabled mode 2004 — which is precisely the case xterm's
rule is about. Worth confirming rather than assuming, which is the task.

## Validation criteria

- [ ] `Surface.writePtyBracketed`'s unbracketed branch maps LF (and CRLF) to CR,
      matching `input.paste.encode`, with the reasoning stated at the call site.
- [ ] A macOS `+send-keys "a\nb\n"` against a mode-2004 program still delivers a
      literal LF inside the frame (no regression to the T604 contract).
- [ ] A macOS `+send-keys "echo A\necho B\n"` against a shell still runs both
      commands.
- [ ] win32's `IpcHandlers.prepareSendKeysRun` drops its `.text`-run branch once
      core owns the rule, and `test/win32/send-keys-bracketed.ps1` rounds 11, 12
      and 15 stay ALL PASS on the same expectations.
