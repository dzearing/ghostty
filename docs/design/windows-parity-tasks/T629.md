# T629 - macOS startup may have the same IPC blackout during session restore that T188 fixed on Windows

## Summary

T188 measured, on Windows, that the app answers no `ghoztty +…` for the whole
session restore: an IPC request is served only when the GUI thread pumps, and
the restore was a straight-line GUI-thread call that pumped nothing. Measured
451 ms for a healthy 5-pane restore and 10 755 ms against a wedged agent, with
every caller in that window unable to tell a busy app from a missing one.

macOS runs the analogous restore at launch and serves IPC on the main queue, so
the same shape is plausible there — but it was never measured, and the Windows
seat cannot measure it. This is the parity half: measure it, and if the blackout
is real, apply the equivalent fix (the win32 one is a narrow pump of only the
IPC message class, `src/apprt/win32/gui_pump.zig`, called from the blocking
stretches of startup; on macOS the natural equivalent may instead be running the
agent dial off the main queue).

## In plain terms

On Windows, commands sent to Ghoztty while it was putting your windows back used
to just hang, which made tooling report the app as missing. That is fixed there.
Nobody has checked whether the Mac does the same thing.

## Validation criteria

- [ ] A measurement on macOS of time-to-first-`+list` across a cold start, a
      multi-pane restore, and a wedged agent — the three arms
      `test/win32/ipc-startup-latency.ps1` uses
- [ ] If a blackout is measured: it is gone, proven by the same two-number
      oracle (first answer vs first window) separating
- [ ] If no blackout is measured: the measurement is recorded and the task
      closed as `skipped(not a defect on this platform)`
