# T179 - Test probes must restore HWND_NOTOPMOST after sampling

## Summary

**A pixel probe that topmosts a live window and never puts it back is what
manufactured T142's phantom bug** — a day of "windows in the background have
banners that overlap windows in the foreground" traced to a T131 probe
(`raiseshot.ps1`, since gone) leaving `HWND_TOPMOST` on two overlays. The class
of trap still exists in the repo: `test/win32/pane-banner.ps1:393` does
`SetWindowPos($top, HWND_TOPMOST, 100, 100, …)` to park a window where the glass
samples are stable and never restores `HWND_NOTOPMOST`. Today that leak dies
with the process (the script `Stop-Process`es its own GUI), but an exception path
under `$ErrorActionPreference = 'Stop'` — or anyone reusing the idiom against an
instance the script did not launch — reproduces the original incident exactly.

Fix: every probe that raises a window for sampling restores the z-order in a
`finally`-shaped path, and the shared `Topmost(h, on)` helper (already present in
`pane-banner.ps1`) is the only way to do it, so the restore is impossible to
forget. Audit `test/win32/*.ps1` for raw `SetWindowPos(..., (IntPtr)(-1), ...)`
calls while you are there.

Validation: after a full `pane-banner.ps1` run, no ghoztty window carries
`WS_EX_TOPMOST` (a one-line assertion at the end of the script), and the same
holds when the run is aborted mid-way.

Cheap, and it protects the next investigation from chasing a harness artifact
as a product defect.
