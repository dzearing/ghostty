# T179 - Test probes must restore HWND_NOTOPMOST after sampling

## Summary

**A pixel probe that topmosts a live window and never puts it back is what
manufactured T142's phantom bug** — a day of "windows in the background have
banners that overlap windows in the foreground" traced to a T131 probe
(`raiseshot.ps1`, since gone) leaving `HWND_TOPMOST` on two overlays. The class
of trap still exists in the repo: `test/win32/pane-banner.ps1:393` does
`SetWindowPos($top, HWND_TOPMOST, 100, 100, …)` to park a window where the glass
samples are stable and never restores `HWND_NOTOPMOST`. Today that leak dies
with the process (the script `Stop-Process`es its own GUI), but an exception path
under `$ErrorActionPreference = 'Stop'` — or anyone reusing the idiom against an
instance the script did not launch — reproduces the original incident exactly.

Fix: every probe that raises a window for sampling restores the z-order in a
`finally`-shaped path, and the shared `Topmost(h, on)` helper (already present in
`pane-banner.ps1`) is the only way to do it, so the restore is impossible to
forget. Audit `test/win32/*.ps1` for raw `SetWindowPos(..., (IntPtr)(-1), ...)`
calls while you are there.

Validation: after a full `pane-banner.ps1` run, no ghoztty window carries
`WS_EX_TOPMOST` (a one-line assertion at the end of the script), and the same
holds when the run is aborted mid-way.

Cheap, and it protects the next investigation from chasing a harness artifact
as a product defect.

## In plain terms

Some of our automated tests have to shove a window in front of everything else
for a moment so they can look at it. One of them once forgot to put the window
back, and for a whole day it looked like the terminal itself had a bug — status
bars from windows in the background were floating over the window in front. The
bug was in the test, not the product, and nothing could tell the two apart.

After this, a test cannot leave a window stuck in front. The one helper that
lifts a window now writes down what it lifted, and three separate paths put it
back — including when the test crashes half way through and never gets to its
own cleanup. A test that would have left a window stuck now says so out loud
instead of leaving the next person a mystery.

## Goals

- [x] The only supported way to pin a window from a test records the pin
- [x] The normal teardown every GUI test already runs puts it back
- [x] A test that dies mid-run — no cleanup path reached — still puts it back
- [x] A run that leaked a pin reports it, instead of it being invisible
- [x] No test script can pin a window outside the recorded helper
- [x] Every one of those claims is shown to be able to fail

## Validation criteria

- [x] `test\win32\probe-topmost-restore.ps1` ALL PASS (22 assertions) — the
      ledger, the restore, the teardown path, the interpreter-exit path, and
      the static "no raw pin anywhere" scan.
- [x] The same script with `GHOZTTY_TEST_TOPMOST_BREAK=1` goes **7 red** across
      sections A, C and D. Every arm asserts an *absence*, which passes just as
      happily when nothing ran, so this is what proves they measure something.
- [x] The static scan has its own teeth arm: it catches a synthetic raw pin on
      the executable line and is not fooled by the same text in a doc-comment
      or a commented-out line.
- [x] `test\win32\overlay-zorder.ps1` (the repo's only injector) ALL PASS,
      25 assertions, including the new end-of-run `no probe left a window
      topmost` arm. Non-vacuous by construction: the product healed all four
      injections, so the restore found nothing — and that the restore DOES
      record a survivor is proven in `probe-topmost-restore.ps1` §C rather
      than in place here.
- [x] Floor: `scripts\floor-lane.ps1 -Lane all` and P1–P3.
- [x] Audit result: `pane-banner.ps1`'s raw `SetWindowPos(..., HWND_TOPMOST)`
      named in the Summary is already gone — that script was rewritten onto the
      TestDesktop harness. The scan in section E is what keeps it gone.
