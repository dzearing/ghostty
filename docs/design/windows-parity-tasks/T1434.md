# T1434 - A floor lane blocked on another build's cache lock sits for 86 minutes and the watchdog never speaks

## Summary

Measured 2026-09-07 during T1431. A 'zig build test -Dapp-runtime=win32' lane launched at 11:24:30 while an acceptance script (ipc-p1/p2/p3, which rebuild through BuildFresh) was running its own 'zig build' in another shell. The lane's zig.exe blocked immediately - 0.09s CPU total and a 0-byte lane log, both still true 86 minutes later - and floor-lane.ps1 printed nothing at all: no STALL (StallSeconds=420) and no TIMEOUT (TimeoutSeconds=1800), so the run had to be killed by hand. That is precisely the failure the wrapper exists to prevent ('a wedge cannot look like a slow run', T982/T933). Two questions to answer with evidence before fixing: whether the progress sampler counted the OTHER build's CPU as this lane's (the T933 shape, one tree over from the lane's own), and whether the 30-minute timeout is armed at all on the path that was taken. Worth a second, cheaper signal too: a lane whose log is still 0 bytes after a minute is not building, whatever the CPU says. Concurrency itself is expected to serialise on zig's cache manifest locks (documented in test-binary-soak.ps1) - the defect is the silence, not the wait.
