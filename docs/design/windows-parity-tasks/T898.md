# T898 - The release-artifacts guard cannot be re-stamped while Docker is down, so an edit to its watched files leaves the guard due indefinitely

## In plain terms

One of the pre-commit safety checks demands that a certain test suite has been
re-run whenever the release wiring changes. Part of that suite needs Docker,
and the standing rule on this box is that Docker is never started without the
user asking. So when Docker is off, the check can never be satisfied — every
commit has to use the documented override, and an override used routinely
stops meaning anything.

## Goals

- [x] An edit to a release WIRING file (a workflow, the shared artifact script,
      the msitools installer, the on-box publish script, the harness) can be
      cleared by a normal run of the harness, with Docker down
- [x] An edit to a PACKAGING payload script (build-msi.sh, build-portable-zip.sh)
      still cannot be cleared without a real Docker run
- [x] No row is left permanently unstamped by the split (which would just move
      the wedge)
- [x] Both behaviors pinned by an acceptance script

## Summary

`test\win32\release-artifacts.ps1` only stamps its guard on a run with zero
failures AND zero skips (release-artifacts.ps1:261), because a Docker-less run
never looked at the packaging sections it would be vouching for. That is the
right bar for the packaging sections — but the guard's watch list also covers
purely static files (e.g. `.github/workflows/fork-ci.yml`, whose 2026-08-16
edit made the guard due), which sections A/C/E verify with no Docker at all.
With Docker down (never started unasked, per standing rule), the guard stays
due forever and every `parity-tasks.ps1 validate` needs `-NoGuardDue`.

Seen 2026-08-16 during T596: the harness ran ALL PASS (2 skipped, both
Docker), covering everything the fork-ci.yml edit could have broken, and the
guard still reported due.

## Options for whoever takes this

1. **Split the guard in two**: a `release-artifacts-static` guard watching the
   workflow/script wiring files (stamped by a green run even with Docker
   skips, since sections A/C/E fully cover them) and a
   `release-artifacts-packaging` guard watching the Docker-dependent payload
   scripts (stamped only by a zero-skip run). An edit to fork-ci.yml then
   stops being hostage to Docker.
2. **Stamp with a skip manifest**: record WHICH sections were skipped in the
   stamp and let `guard-due` re-report due only for files whose covering
   sections were skipped.

Either way the zero-skip bar for the packaging sections must survive — a
Docker-less run vouching for the MSI/ZIP payload is the exact lie T783's
mechanism exists to prevent.

## What was done (option 1, the row split)

`scripts\guard-due.ps1` now carries two rows where it carried one:

| row | watches | stamped by |
|---|---|---|
| `release-artifacts` | release-windows.yml, fork-ci.yml, build-release-artifacts.sh, install-msitools.sh, publish-windows-release.ps1, the harness itself | any run with **zero failures** — sections A/C/E/F prove all of them and none touch Docker |
| `release-artifacts-packaging` | build-msi.sh, build-portable-zip.sh | only a run with **zero skips**, i.e. section B really executed them under msitools-local |

Two supporting changes made the split honest rather than cosmetic:

- **B1b moved out of the Docker branch** (now `A19`). It is a regex over
  `publish-windows-release.ps1`'s text asking whether the script still defers
  the FILEVERSION rule to `build-msi.sh`; sitting inside `if ($dockerUp)` it
  meant a Docker-less run quietly stopped covering a file the wiring row
  vouches for.
- **The packaging stamp was seeded, not invented.** Its two hashes were copied
  verbatim out of `release-artifacts.stamp.json`, where the 2026-08-16
  zero-skip run at `5f3f8f45b` recorded them; both files are byte-identical on
  disk today (verified: the new row read `GUARD CURRENT` before any new run).
  Without the seed the new row would have been `no-stamp` DUE forever, which
  is the same wedge one name to the left.
- `guard-due.ps1` grew a per-row `RunArgs`, so the packaging row's `run:` line
  names `-RequireDocker` — a Docker-less run of that command FAILS instead of
  reporting `ALL PASS (2 skipped)` and leaving the guard due.

## Validation criteria

- [x] With Docker down, a green run of release-artifacts.ps1 satisfies the
      guard for an edit to a file the static sections fully cover
      (e.g. fork-ci.yml) — **measured on the box**: with Docker down the
      harness printed `ALL PASS (2 skipped)` and `STAMPED release-artifacts
      (6 files)`, and `guard-due check` then read `GUARD CURRENT
      release-artifacts (6 files, stamped 2026-08-18)`, clearing the DUE that
      the 2026-08-16 workflow edits had left standing since.
- [x] With Docker down, an edit to a Docker-covered packaging file still
      leaves its guard due (negative control) — `test\win32\guard-due.ps1`
      arms G7/G8 (fixture repo, no Docker involved): editing `build-msi.sh`
      makes the packaging row DUE and leaves the wiring row CURRENT. The live
      run above confirms the other side: the packaging stamp was **not**
      updated (`packaging stamp NOT updated (2 section(s) skipped)`).
- [x] Acceptance extended to pin both behaviors — section **G** (11 arms) of
      `test\win32\guard-due.ps1`, which is where guard-due's own policy arms
      live (section F already pins the same "who may stamp" question for
      go-loop-guard). The criterion above named `go-loop-guard.ps1`; that
      script has no guard-due arms at all, only its own stamping call, so the
      arms went where their family is. G1-G3 assert the live table's split,
      G4-G9 the behaviour over a fixture, G10-G11 the two-tier stamping policy
      at source level (both negative-controlled against the old policy text).
