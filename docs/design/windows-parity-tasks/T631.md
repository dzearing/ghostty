# T631 - a zig -Dtest-filter run that matches NOTHING exits 0, so a filtered lane can prove nothing while looking green

## Summary

Measured while validating T188. `zig build test -Dapp-runtime=win32
-Dtest-filter=pump` exited 0 and printed nothing against a build whose
`gui_pump` test had a DELIBERATELY broken assertion; the same broken build run
through the unfiltered lane reported
`error: 'apprt.win32.gui_pump.test.pump runs the hook with its context on the
installing thread' failed`. So the filter matched nothing, and "matched nothing"
is indistinguishable from "matched and passed" — both are a silent exit 0.

That makes a filtered lane worthless as evidence, which is a real hazard here:
the standing house rule is that a new test must be PROVEN to run, and the cheap
way to prove it (break it, run the filter) reports green either way. The
expensive way — the full lane, ~6 minutes — is what T188 had to fall back on.

The fix is a build-side guard: when `-Dtest-filter` is given and the run
executed ZERO tests, fail loudly instead of exiting 0. `build.zig` already
threads `test_filters` into every test step, so the count is available where the
filters are.

## In plain terms

A shortcut for running one test instead of all of them reports success even when
it ran nothing at all, so it can be used to "prove" a test passes that was never
executed.

## Where it landed

- `build.zig` — one `Collector` per top-level test step; `attach` at the end of

- `test/win32/test-filter-guard.ps1` + a `test-filter` row in
  `scripts/guard-due.ps1`.
- `docs/claude/testing.md` — the rule, and why the test COUNT was never the
  signal.

## What the fix turned on

The obvious implementation — fail when the run executed zero tests — does not
work here and would have shipped a guard that never fires. An unnamed `test {}`
block is compiled into the binary whatever the filter says, and this repo is
built out of `test { _ = @import(…); }` aggregators, so
`-Dtest-filter=zzz_nonexistent` reports **83/83 tests passed**. The signal that
does work is the test METADATA the runner reports: the binary's test names,
checked against the filters the same way the compiler checked them (a filter is
a substring of the fully-qualified name). A cache hit reports no metadata, so
filtered runs have their caching taken off rather than letting "cannot tell"
read as "matched nothing".
