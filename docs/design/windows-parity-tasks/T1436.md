# T1436 - A half-extracted dependency in the global cache takes every build down and the auto-heal does not see it

## Summary

On 2026-09-07 every build and all four floor lanes went red at once with:

```
error: failed to check cache: 'D:\zig-global-cache\p\N-V-__8AAIC5lwAVPJJzxnCAahSvZTIlG-HhtOvnM1uh-66x\fonts\ttf\JetBrainsMono-Regular.ttf' file_hash FileNotFound
```

That package directory held only `AUTHORS.txt`, `OFL.txt` and four macOS
AppleDouble sidecars (`._fonts` among them). The `fonts/` tree the message names
was gone entirely, so what was torn was the EXTRACTION of a fetched dependency,
not anything the compiler produced. Moving the package directory aside and
rebuilding re-fetched it, and everything went green in one step.

Two things are wrong.

1. **The auto-heal exists for exactly this and could not see it.**
   `scripts\lib\CacheHeal.ps1` finds torn cache entries by matching log lines
   shaped `path:line:col: error:`. This failure carries no line and no column,
   so `Get-TornCacheEntry` resolved nothing, `floor-lane.ps1` printed four
   identical FAILs with no diagnosis, and the box was down until a human
   recognised an unfamiliar message. It should also recognise
   `failed to check cache: '<path>' file_hash <reason>` and heal the PACKAGE
   directory under `<global-cache>\p\` that the named path falls inside - a
   different unit from the `o\` entries it deletes today, so
   `Resolve-CacheEntryDir` needs to learn about it.

2. **A torn package is silent until something needs it.** `go-loop-exec claim`
   reported `build cache ok: 1025.8 GB free, 1474 entries` minutes before this,
   because that check counts entries and free space and never asks whether any
   of them are whole.

Found while validating T617 (2026-09-07) and healed by hand that turn, which is
why the loop kept going. The torn copy was moved to
`<global-cache>\p\N-V-__8AAIC5lwAVPJJzxnCAahSvZTIlG-HhtOvnM1uh-66x.torn-20260907`
rather than deleted, so the evidence is still on the box for whoever takes this.

## In plain terms

One of the downloaded dependencies on the build machine ended up half-unpacked,
and from then on nothing would build at all - four different test lanes just
said FAIL with the same unhelpful line. There is already a repair that is meant
to notice this kind of damage and clean it up automatically, but it only reads
one shape of error message and this was another, so it did nothing. Someone had
to read the message and know what it meant. Next time the machine should fix
itself.

## Goals

- [x] The repair recognises a torn downloaded package, not only a torn generated file
      -- a `failed to check cache: '<path>' <field> <reason>` line now heals the
      `p\<package-hash>` directory the path falls inside (rule `torn-package`).
- [x] A lane that goes red for this reason says so, and heals, without a human
      -- proven end to end by arm 22 of `test\win32\floor-lane-cache-heal.ps1`:
      red -> CACHE HEAL -> re-run -> PASS.
- [x] The claim's cache report can tell "big and healthy" from "big and torn"
      -- `build-cache.ps1 check|sweep`, which the claim runs, now prints
      `BUILD CACHE TORN: N fetched package(s) look half-extracted`.

## Validation criteria

- [x] A fixture package directory with a file removed is detected by
      `Get-TornCacheEntry` from a log holding the real
      `failed to check cache: '<path>' file_hash FileNotFound` line.
      Arm 16, for both package-name shapes (anonymous `N-V-...` and
      `libxev-0.0.0-...`); the fixture reproduces the surviving torn directory's
      contents exactly.
- [x] The entry it resolves is the PACKAGE directory under `p\`, not the file
      and not the whole cache, demonstrated against a fixture tree. Arm 16
      ("the entry is the package dir, not the file").
- [x] A negative control: the same log line naming a path OUTSIDE the cache
      heals nothing. Arm 17 (a repo source path and a Downloads path). Arm 18
      adds the second control that matters -- a directory under `p\` whose name
      is NOT a package hash is refused, including the `<hash>.torn-20260907`
      copy set aside on this box.
- [x] `floor-lane.ps1` heals and re-runs on this shape rather than reporting a
      bare FAIL, shown end to end. Arm 22 runs `floor-lane.ps1 -Command` against
      a real process that fails while the torn package exists and passes once it
      is gone, so `FLOOR SUMMARY: command=PASS` is the proof. This needed the
      heal policy lifted out of the lane loop into `Invoke-CacheHealPolicy`,
      which `-Command` mode now runs too.
- [x] Whatever answers the integrity question is reachable from
      `go-loop-exec.ps1 claim`, so a torn cache is reported before it is hit.
      `Get-TornPackage` is wired into `build-cache.ps1`, which the claim runs as
      `sweep`; arm 21 asserts the torn line over a fixture cache and its absence
      over a healthy one. Measured at 88ms over the live 1,513-entry cache.
