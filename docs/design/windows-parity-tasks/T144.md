# T144 — New windows (ctrl+n) open in C:\Windows\System32. User-reported 2026-07-29: *"it keeps…

## Summary

**New windows (ctrl+n) open in `C:\Windows\System32`.** User-reported 2026-07-29: *"it keeps defaulting to windows system32 folder (HORRIBLE!) this should never be the default path for opening cmd."* Two defects, one symptom. (a) THE BUG: `Config.finalize` already resolves the win32 default to `.home` (`probableCliEnvironment()` returns false on Windows, so wd = `.home` → `HOMEDRIVE`+`HOMEPATH`), and `apprt.surface.newConfig` only overrides it from the parent pane's OSC-7 pwd — so `C:\Windows\System32` cannot come from config resolution at all. PRIMARY HYPOTHESIS (verify on the box before fixing, do not assume): the agent-backed spawn path drops the resolved cwd and the ConPTY child inherits the AGENT's own cwd, which is `C:\Windows\System32` because the T89h HKCU `Run` autostart entry launches it detached from there — the exact mechanism `src/apprt/ipc/args.zig:144-171` (T132) and `src/remote/agent/server.zig:755-762` already call out for the auto-launch and RELAUNCH paths, never fixed for the ordinary OPEN. Confirm by comparing the pane's cwd with `session-persistence=on` vs `off` and by reading the running agent's own cwd. Secondary candidate: `Exec.zig:1105` silently drops a cwd that fails `access()`. (b) THE MISSING ESCAPE HATCH: the user has NO config file — `%LOCALAPPDATA%\ghostty\` contains only a zero-byte, mis-named `config.ghostty` (the loader reads `config`, no extension), so nothing they could have set would ever load. Fix (a), then make the default reachable: honor `working-directory = <path>` from `%LOCALAPPDATA%\ghostty\config` on every new window/tab/split, and find out what wrote `config.ghostty` (a file-association or first-run artifact writing the wrong name is its own bug — a user who "set" a config and saw no effect would have no way to tell). Validation: on-box, ctrl+n from a Start-menu-launched app lands in `%USERPROFILE%` with no config and in the configured path with one, with persistence both on and off

## Details

### What was measured (2026-07-30)

The primary hypothesis was **confirmed, by direct measurement rather than by
inspection**. There is no supported API for "another process's current
directory", so the agent's `RTL_USER_PROCESS_PARAMETERS.CurrentDirectory` was
read out of its PEB while the user's real build was running:

```
27568  %LOCALAPPDATA%\Programs\Ghoztty\ghoztty-agent.exe   cwd=C:\WINDOWS\system32\
35324  D:\git\ghoztty\zig-out\bin\ghoztty-agent.exe        cwd=D:\git\ghoztty\
```

That second line is why this was never caught on the box before: a
repo-launched debug agent inherits the repo directory, so every debug session
looked fine. Only the **installed** agent — started by the T89h HKCU `Run`
entry — sits in System32.

### The defect

`src/Surface.zig` refused to forward the surface's resolved
`working-directory` to *any* remote agent. That rule is correct and load-bearing
for a CROSS-MACHINE agent (a local path may not exist on the remote OS; an OPEN
carrying one makes the agent's spawn fail and never reply OPENED — the stall
wedge). It was wrong for the LOCAL session-persistence agent, which runs on this
same machine: the OPEN carried **no cwd at all**, so the agent spawned the child
wherever the agent itself was sitting.

The consequence is the invariant this task really closes: **the same app with
the same config opened in two different directories depending on
`session-persistence`**, a setting that has nothing to do with directories.
Persistence off → exec backend → chdir into the resolved working-directory.
Persistence on (the default) → System32.

Mac has forwarded it since the local agent landed
(`TerminalController.swift`: *"The agent runs on THIS machine, so a local
working directory is valid there"*). Windows never ported that line. The rule now
lives in shared core as `termio.Remote.openWorkingDirectory(explicit, local,
is_local_agent)` — explicit remote cwd wins, else the local resolved cwd for the
LOCAL agent only, else null — so both apprts read it from one place. Mac gains
the fallback for the case where its `SurfaceConfiguration.workingDirectory` was
nil (a fresh window with nothing to inherit), which previously also fell through
to the launchd agent's cwd.

### Two premises in the filed row were wrong

- **"the loader reads `config`, no extension"** — it does not. Since Ghostty
  1.3.0 the default is `config.ghostty` (`src/config/file_load.zig`), with
  plain `config` kept only as a legacy fallback. The user's file is at the
  RIGHT path. It was simply **empty**.
- **"find out what wrote `config.ghostty`"** — Ghoztty itself did, and
  truncated it. `writeConfigTemplate` printed the ~2 KiB template into a
  4096-byte buffered writer and **never flushed** before `file.close()`, so
  every user who had no config got a zero-byte one instead of the documented
  template. That is not cosmetic: an empty file still counted as "a config
  exists" (`loadOptionalFile` mapped `FileIsEmpty` to `.@"error"`, which
  suppressed the template), so it was never retried. The user had nowhere to
  discover `working-directory` in the first place — which is exactly why they
  had no escape hatch from (a).

Fixed both: the writer flushes, and an empty config file now reports a distinct
`.empty` action that does not count as `present()`, so a truncated config
self-heals into the template on the next launch. A file that fails to PARSE
still counts as present and is never clobbered.

### Changes

- `src/termio/Remote.zig` — new pure `openWorkingDirectory` + 4 unit tests.
- `src/Surface.zig` — the remote backend calls it instead of forwarding only
  `rb.working_directory`.
- `src/config/Config.zig` — `writeConfigTemplate` flushes; `OptionalFileAction`

- `test/win32/new-window-cwd.ps1` — new acceptance script.

### Validation

`test/win32/new-window-cwd.ps1` **ALL PASS (39) ×3**. Both test lanes,
`zig build test-agent`, and P1–P3 green.

Sections: **A** the agent's cwd IS the launcher's (PEB read, so nothing passes
vacuously) and the startup window is in HOME anyway; **B** persistence OFF lands
in the same place as ON; **C** a configured `working-directory` is honored on
both backends; **D** the real **ctrl+n**, injected as keystrokes, inherits the
focused pane's directory; **E** a zero-byte config self-heals into the template.

Section D presses the actual chord because **the CLI cannot reproduce this
bug**: `ghoztty +new-window` always inserts `--working-directory=<caller's cwd>`
when the flag is absent (`src/cli/new_window.zig:268`), by design — a
CLI-opened window belongs where you typed. An early draft of this script
asserted on `+new-window` and "failed" for that reason; the report is about the
keybind, so the keybind is what is driven.

**Negative control** (`T144_NEUTERED`, `openWorkingDirectory` forced back to
returning only the explicit cwd): 8 assertions fail and they are exactly the
user's report — every persistence-ON shell lands in `c:\windows\system32` while
persistence-OFF stays in HOME, and ctrl+n's new window reports no directory at
all. The config half has its own unit-level negative control: dropping the
`flush()` fails `T144 writeConfigTemplate actually writes the template` and
nothing else.

### Harness traps this run

- **PowerShell unrolls a one-element array on return**, and a lone
  `PSCustomObject` has no usable `.Count` in PS 5.1 — so `(Windows-Of
  $tree).Count -ge 1` was *always false* for a single-window app, silently
  failing three assertions while the assertions after them passed. Fixed with
  the `return ,@(...)` comma idiom. `auto-launch-cwd.ps1` never hit this only
  because it always waits for ≥2 windows.
- **`function Cli` shadows nothing but `cli` is an alias for `Clear-Item`** —
  a scratch probe named its helper `Cli` and every call became a
  `Clear-Item` error. Name harness helpers something PowerShell does not
  already alias.
