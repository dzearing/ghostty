# T1292 - The encoder drift detector only covers +list, and only names and order

## In plain terms

When the Mac and Windows builds answer the same question, they are supposed to
answer it identically. T370 made that automatic for one answer — the list of
open windows and panes — but only for *which fields are there and in what
order*. A field whose TYPE changed on one side (a number that became a string,
a list that became a single value) still slips through, and the other messages
the two builds exchange have no check at all. A script that works on the Mac
can still quietly get a different answer on Windows.

## Summary

T370 built a drift detector: `src/apprt/ipc/list.zig`'s test parses
`macos/Sources/Features/IPC/IPCMessage.swift` and compares the Mac encoder's
field names, order and null-behavior against the key order a real
`serializeResponse` call emits. It is deliberately scoped: the shape that had
actually drifted, checked the way the task's option (1) described.

Two gaps stay open by construction.

## Details

**1. Value shape is unchecked.** The detector compares key names, order and
whether a key survives a null value. It says nothing about the TYPE behind the
key: `pid` going from `Int` to `String` on one seat, `ratio` from `Double` to
`Int`, `tabs` from an array to a single object. All of those are silent today
and all of them break a client that reads both servers. The Swift declarations
carry the types (`let pid: Int`), so a name→type map is extractable from the
same source the detector already parses; the Zig side has the types at
comptime on `List.Terminal` et al. Whether that comparison is worth its
complexity is the open question — decide it, do not default to it.

**2. Only `+list` is covered.** `IPCMessage.swift` also carries
`ReadResultData` (`+read`), and the Mac and Windows builds exchange other
shapes that exist twice with nothing tying them together — `+sessions --json`
being the obvious next one. `ReadResultData` is a single field today, which is
exactly when a check is cheap to add and nobody bothers.

The helpers T370 left behind (`swiftBlock`, `swiftCodingKeys`,
`swiftEncodedKeys`, `expectMacShape` at the bottom of `src/apprt/ipc/list.zig`)
are payload-agnostic; extending to another message is mostly deciding where
they should live once a second caller exists.

## Validation criteria

- [ ] A decision recorded (task file + log) on whether value-type comparison is
      worth adding, with its reasoning — not a silent skip
- [ ] If yes: a type change on one seat only turns a lane red, demonstrated by
      making the change, running the lane, and reverting
- [ ] Every payload `IPCMessage.swift` encodes is covered by a shape check, or
      named here as deliberately uncovered with the reason
- [ ] Both `zig build test` lanes, `test-agent` and the `lib` build green
