# T1292 - The daily publish can never run

## In plain terms

The loop fixes things every day and commits them, but nothing reaches the
website. The step that is supposed to publish a build asks for Docker to be
running, and starting Docker is not something the loop is allowed to do - so
every day it writes "skipping" into a log nobody reads, and the user keeps
downloading a build from days ago.

## What happened

The user's RDP fix (T1251, T1252) landed on 2026-09-01. On 2026-09-03 the
newest published release was still **win-v1.36.0 from 2026-08-31**, so the
user was still installing the build with the blocking OpenGL defect - two days
after it was fixed.

`%TEMP%\ghoztty-daily-publish.log` shows why:

```
2026-09-01 23:20 SKIP: due ... but Docker Desktop is not running (wixl packages
                  the MSI inside the msitools image, and starting Docker is the
                  user's call). Nothing published.
2026-09-01 23:20 SKIP: due ... but gh is not authenticated. Nothing published.
2026-09-02 (all day) NOT DUE: before 17:00 local - the day's work is not done yet
```

Three compounding failures:

1. **Docker is a hard requirement it can never satisfy.** The local publish
   path builds the MSI with wixl inside the `msitools-local` Docker image.
   Docker Desktop is deliberately kept down on this box (its WSL2 backend once
   took 28 GB and buried the machine), and the script itself says starting it
   is the user's call. So the gate is permanent.
2. **The 17:00 gate plus a stall equals nothing.** On 2026-09-02 the log stops
   at 14:28 - the loop stalled before ever reaching 17:00, so the day produced
   no publish and no complaint.
3. **A skip is invisible.** Each failure wrote one line to a temp log. Nothing
   surfaced in the health line, the digest, or the dashboard, so "no release
   for three days" had to be noticed by the user.

## The fix is already proven in this repo

`release-windows.yml` builds the MSI on **ubuntu-latest**, installing msitools
0.106 from source (`dist/windows-installer/install-msitools.sh`). **No Docker,
no local wixl.** That is how win-v1.35.0 and win-v1.36.0 were published, and
how win-v1.36.1 was published by hand on 2026-09-03 - a tag push and CI does
the rest.

So the daily publish should push a `win-v<version>` tag and let CI build it,
rather than requiring a local packaging toolchain the box will never have.

## What to build

- **Publish by tag push, not by local MSI build.** Docker stops being a
  precondition for shipping; it stays only for the local packaging harness.
- **A due-but-skipped publish is loud.** Surface it the way `digest=` now
  surfaces a missed digest (T1223): a `publish=` field on the health line
  reading published / due / skipped-with-reason. The morning digest already
  claims to name what shipped - it must say "nothing, because X" just as
  clearly.
- **Reconsider the 17:00 gate.** Tie the publish to work having landed, not to
  a wall-clock hour that a stalled loop can miss entirely.
- **Verify the whole path once.** A publish that has never succeeded is a
  publish nobody has watched work.

## Goals

- [x] Publishing needs nothing this box is forbidden to start
- [x] A day that stalls before the evening still ships its work
- [x] "Nothing shipped" is visible on the health line, not just in a temp log
- [x] A tag CI never built is not reported as a successful publish
- [x] One real release, made by this path, observed end to end

## Validation criteria

- [x] The daily publish creates a release with Docker not running, on a box
      with no local wixl. Verified by `test\win32\daily-publish.ps1` sections
      C6/F0/H (a real run with the Docker probe failing reaches the publisher and
      stamps), and by the live publish below.
- [x] A due publish that cannot proceed reports its reason on the health line,
      not only in a temp log. `publish=` on `go-loop-health.ps1`; section Z of
      `test\win32\go-loop-guard.ps1` scores stale-3d / ok / failed / never, with
      the stale arm degrading the run.
- [x] A day whose loop stalled before the gate still publishes the work that
      landed, or says why it did not. The catch-up rule, sections A8-A12 of
      `test\win32\daily-publish.ps1`.
- [x] The digest names the release that shipped, and names the absence when
      nothing did. Today's digest names the three-day absence and both of its
      causes; `publish=` is what makes the next one checkable rather than
      remembered.
- [x] The end-to-end path is exercised once and observed: commit → publish →
      the website offers the new version.
