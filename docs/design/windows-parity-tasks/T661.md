# T661 - win32 normalizeConptyInput rewrites LF to CR inside TEXT runs, so main interior-newline-stays-literal guarantee does not hold here

## In plain terms

Pasting a multi-line block into a pane on Windows does not deliver the line
breaks the way it does on a Mac — each one arrives as the character Enter
sends instead of as a plain line break. Most editors cope, but a program that
tells the two apart sees something the Mac never sends it.

## Goals

- [x] A line break pasted into a TUI arrives as a line break, not as Enter
- [x] A multi-line send to a plain shell still runs each line, as it does on a Mac
- [x] A prompt file that ends in a newline no longer submits itself
- [x] An older `ghoztty` on the box keeps working exactly as it does today

## Summary

Found while validating T604, which is what made it matter: T604 ported main's
`a7f7476e1` and with it a documented guarantee — *"Interior newlines stay
literal inside the paste, so `"a\nb\n"` pastes two lines and then submits."*
On Windows the interior newline does NOT stay literal.

`IpcHandlers.handleSendKeys` runs `verb_args.normalizeConptyInput` over
**every run**, text runs included (`src/apprt/win32/IpcHandlers.zig:1271`, and
again on the flat path at :1283). That helper
(`src/apprt/ipc/args.zig:397`) maps LF and CRLF to CR, on the reasoning that
"Enter is CR on a ConPTY" — correct for a KEY run, and applied to text runs as
well.

Measured, not inferred (`test/win32/send-keys-bracketed.ps1` round 12):

```
send:  +send-keys --target=P "a\nb\n"
bytes: 1b5b3230307e 61 0d 62 1b5b3230317e 0d
                       ^^ interior newline arrived as CR, not 0a
```

The peel half is right — the trailing newline left the frame and became a
keypress. Only the interior byte is wrong.

Same cause, second symptom (round 11): `--keys-file=` is deliberately exempt
from the peel at the CLI layer (decision D52, pinned by a none-lane unit
test), but the server normalizes the file's trailing LF to CR anyway, so a
prompt file ending in a newline submits on Windows and does not on macOS.
This one is PRE-EXISTING — older than T604 — and the docs quietly claimed
otherwise until T604 corrected them.

The fix is a narrowing, not a removal: normalization is right for `.key` runs
and wrong for `.text` runs, and the segmented path already knows which is
which. The flat path (no `--segments=`) has no such information and is where
the judgement call lives — an older CLI's flat payload cannot be split, so
whatever it does today probably has to stay.

## What landed

Two things the plan above did not anticipate, both forced by evidence.

**A text run is not simply verbatim — it follows the paste convention.** The
first cut wrote every resolved run byte-for-byte, and a probe on the box
immediately caught the cost: `+send-keys "echo AAA\necho BBB\n"` reached a
`cmd.exe` pane as `echo AAAecho BBB`, because conhost's VT input translation
SWALLOWS a bare LF. macOS runs both commands there for free, since a POSIX pty
accepts LF as a line terminator — so strict verbatim was a *new* divergence
wearing parity's clothes. The rule that is actually right is core's own, in
`src/input/paste.zig`: xterm maps LF to CR for an UNBRACKETED paste and leaves
it alone for a bracketed one. `IpcHandlers.prepareSendKeysRun` now applies
exactly that, so a TUI composer gets the literal line break main promises and a
shell still runs each line.

**The flat path needed a generation signal, not a heuristic.** A lone
`--keys-file=` resolves to ONE segment and the CLI emits `--segments=` only
when there are two or more, so the reported symptom lands on the flat path —
where a resolved CLI's bytes and a pre-T604 CLI's are byte-identical. So the
CLI now marks every request `--keys-resolved=1` (`apprt/ipc/args.zig`), and an
unmarked request is normalized unconditionally exactly as before. Additive, so
the macOS server — which never normalized at all — ignores it forever, and an
older win32 server ignores it too. Fork and alternatives: **D56**.

`Surface.pasteIsBracketed` was extracted from `writePtyBracketed`'s own branch
so the handler can ask the same question the writer asks; it is a refactor with
no behavior change on either platform.

## Validation criteria

      `1b5b3230307e 61 0a 62 1b5b3230317e 0d` on the wire.

      corrected expectations and stay ALL PASS. — ALL PASS, now 16 rounds

      matching macOS and honoring D52 end to end. — round 11 measures
