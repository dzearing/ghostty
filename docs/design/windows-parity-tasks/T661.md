# T661 - win32 normalizeConptyInput rewrites LF to CR inside TEXT runs, so main interior-newline-stays-literal guarantee does not hold here

## In plain terms

Pasting a multi-line block into a pane on Windows does not deliver the line
breaks the way it does on a Mac — each one arrives as the character Enter
sends instead of as a plain line break. Most editors cope, but a program that
tells the two apart sees something the Mac never sends it.

## Summary

Found while validating T604, which is what made it matter: T604 ported main's
`a7f7476e1` and with it a documented guarantee — *"Interior newlines stay
literal inside the paste, so `"a\nb\n"` pastes two lines and then submits."*
On Windows the interior newline does NOT stay literal.

`IpcHandlers.handleSendKeys` runs `verb_args.normalizeConptyInput` over
**every run**, text runs included (`src/apprt/win32/IpcHandlers.zig:1271`, and
again on the flat path at :1283). That helper
(`src/apprt/ipc/args.zig:397`) maps LF and CRLF to CR, on the reasoning that
"Enter is CR on a ConPTY" — correct for a KEY run, and applied to text runs as
well.

Measured, not inferred (`test/win32/send-keys-bracketed.ps1` round 12):

```
send:  +send-keys --target=P "a\nb\n"
bytes: 1b5b3230307e 61 0d 62 1b5b3230317e 0d
                       ^^ interior newline arrived as CR, not 0a
```

The peel half is right — the trailing newline left the frame and became a
keypress. Only the interior byte is wrong.

Same cause, second symptom (round 11): `--keys-file=` is deliberately exempt
from the peel at the CLI layer (decision D52, pinned by a none-lane unit
test), but the server normalizes the file's trailing LF to CR anyway, so a
prompt file ending in a newline submits on Windows and does not on macOS.
This one is PRE-EXISTING — older than T604 — and the docs quietly claimed
otherwise until T604 corrected them.

The fix is a narrowing, not a removal: normalization is right for `.key` runs
and wrong for `.text` runs, and the segmented path already knows which is
which. The flat path (no `--segments=`) has no such information and is where
the judgement call lives — an older CLI's flat payload cannot be split, so
whatever it does today probably has to stay.

## Validation criteria

- [ ] A `.text` run's interior LF reaches the pane as LF; a `.key` run's LF
      still reaches it as CR.
- [ ] `test/win32/send-keys-bracketed.ps1` rounds 11 and 12 are updated to the
      corrected expectations and stay ALL PASS.
- [ ] `--keys-file=` with a trailing newline no longer submits on its own,
      matching macOS and honoring D52 end to end.
- [ ] The flat (no `--segments=`) path's behavior is decided explicitly and
      recorded, rather than changed by accident.
- [ ] `CLAUDE.md`'s `+send-keys` section drops the win32 caveat T604 added,
      once the caveat is no longer true.
