# T982 - A floor run can die on a process-tree sample that came back empty

## Summary

scripts\floor-lane.ps1's Get-ProcessTree returns a PowerShell ArrayList, which unrolls to $null when the sample finds no processes; the very next line binds it to Get-SelfSpawnedTestPids -Tree, whose parameter refuses null, and the whole -Lane all run aborts mid-lane with a ParameterBindingValidationException instead of running the remaining lanes. Seen once on 2026-08-19 at the start of the lib lane. Fix is one @() at the call site (or a null-tolerant parameter), plus the same audit on the other helpers that take a tree.

## In plain terms

Before every commit, a script runs the whole test suite and watches it, so a
build that quietly hangs gets named instead of sitting there. That watcher was
taking a photo of the running processes every few seconds — and on a busy
machine the photo sometimes came back empty. An empty photo crashed the watcher
itself: the test run stopped dead with no pass, no fail, and no summary, and the
half-finished build was left running in the background. Nobody was told; it just
looked like the tests had never been run. Now an empty photo means "nothing to
see", and if anything else ever goes wrong while watching, that run is reported
as a failure instead of vanishing.

## Goals

- [x] an empty process-tree sample no longer aborts the run
- [x] the same null audit on every helper that takes a tree or a leak set
- [x] a lane always ends with a verdict, even when the watchdog itself errors
- [x] the failed lane's process tree is reaped rather than orphaned
- [x] acceptance arms that fail if either regresses

## Validation criteria

- [x] The empty sample is reproduced and fixed: `Get-ProcessTree` driven with a
      snapshot that matches nothing, and with a null snapshot (the CIM-failure
      case), answers an empty tree and can be handed straight to
      `Get-SelfSpawnedTestPids` without a binding error. Verified by arm 15 of
      `test\win32\floor-lane-leak-sweep.ps1`, which lifts the shipped
      `Get-ProcessTree` out of `floor-lane.ps1` with the parser so it tests the
      real function. Pre-fix control: the same call raised
      `ParameterBindingValidationException: Cannot bind argument to parameter
      'Tree' because it is null`.
- [x] A null leak set counts zero rather than one phantom leak (`@($null)` is a
      one-element array in PS 5.1). Arm 15.
- [x] A lane whose watchdog errors still prints `WATCHDOG ERROR`, reports
      `LANE command FAIL`, reaches `FLOOR SUMMARY`, exits non-zero, and leaves
      no process from its tree running. Arm 16, via the
      `GHOZTTY_FLOOR_LANE_FAULT` injection hook.
- [x] The three real verdicts are unchanged by the new try/catch:
      `scripts\floor-lane.ps1 -SelfTest` answers PASS / FAIL / STALL — ALL PASS.
- [x] `test\win32\floor-lane-leak-sweep.ps1` — ALL PASS (48 assertions), and it
      re-stamped the `lane-leak-sweep` guard.
- [x] Standing floor green: `scripts\floor-lane.ps1 -Lane all` (lib, none,
      win32, agent) and the P1-P3 IPC acceptance scripts.
