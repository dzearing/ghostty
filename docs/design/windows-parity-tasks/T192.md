# T192 - zig build install fails AccessDenied on ghoztty-agent.exe while a repo agent is running

## In plain terms

Ghoztty keeps a small background program alive after you close the app, so your
terminal sessions survive. On Windows a program that is running cannot have its
own file replaced — so rebuilding Ghoztty while one of those background programs
was still up made the build stop with an error, even though most of the new
build had already been written out. Anyone reading that error reasonably
concluded their change had failed to build, when in fact it had. Now the build
quietly slides the old file out of the way, writes the new one, and tidies up
the leftover the next time it can.

## Goals

- [x] `zig build` succeeds while a repo-built background agent is running
- [x] the newly built agent really is the one left on disk afterwards
- [x] nothing is killed to achieve it (a concurrent test run keeps its agent)
- [x] the file moved out of the way is cleaned up on a later build
- [x] the original failure is reproducible on demand, so it cannot come back unnoticed

## Summary

`zig build` exits **1** with

```
error: unable to update file from '.zig-cache\o\<hash>\ghoztty-agent.exe'
       to 'D:\git\ghoztty\zig-out\bin\ghoztty-agent.exe': AccessDenied
```

whenever a repo-lineage `ghoztty-agent.exe` from an earlier test run is still
alive (it is - the agent outliving the app is the whole point of T89), because
Windows holds an executable's image file open for the life of the process.

Observed 2026-07-30 during T189's negative-control build. The trap is not the
failure, it is the SHAPE of the failure: **`ghoztty.exe` had already been
installed successfully**, so the build reported exit 1 while the binary under
test really had changed. A session that trusts the exit code concludes "my
change did not build" and re-runs against a binary that is in fact new - or,
worse, treats a real test result as a stale-binary artifact. That is the T49
lesson class (a stale binary lying to you) with the sign flipped.

Related but distinct: **T167** is the agent single-instance guard blocking
hermetic test SANDBOXES. This one is the plain dev loop - `zig build` on a box
where a previous run left an agent.

## Details

Repro: run any on-box script that opens a persistent session (e.g.
`session-open.ps1`), let it leave `zig-out\bin\ghoztty-agent.exe` running,
then `zig build -Doptimize=Debug`.

Candidate fixes, cheapest first:

1. A build step (or a documented `scripts\` helper the acceptance scripts
   already call) that stops repo-lineage agents - matching the
   `Kill-RepoInstances` the test scripts do for `ghoztty.exe`, which is why
   `ghoztty.exe` never hits this.
2. Install the agent under a temp name and `MoveFileEx` it into place, so a
   running image only delays the swap instead of failing the build. This is
   what `scripts/upgrade-ghoztty-windows.ps1` already does for a delivery, and
   it is the same problem.
3. At minimum, make the failure legible: the build should say WHICH artifact
   could not be installed and that the others succeeded. Today a reader has to
   grep the log to learn that `ghoztty.exe` was fine.

## Validation

Start a repo-lineage agent, run `zig build`, and assert it succeeds and that
`ghoztty-agent.exe` on disk is the new one (compare the file's build id /
`+version` output after restarting it). Negative control: the same run on the
pre-fix build must fail with the AccessDenied above.

## Resolution

Option 2, with option 3 folded in and option 1 explicitly rejected.

`src/build/install_unlock_main.zig` is a build-time host tool wired by
`src/build/InstallUnlock.zig` and inserted ahead of every Windows install step
(`ghoztty.exe`, `ghoztty.com`, `ghoztty-agent.exe`, `ghoztty-agent-ca.dll`). Per
(source, destination) pair it:

1. sweeps leftover `<name>.old-*` siblings (a still-held one survives to the
   next build; that is not an error);
2. returns immediately when the destination is absent, or when size+mtime
   already match the source — `std.fs.Dir.updateFile` skips the copy in that
   case, so a lock on an already-current file is in nobody's way and must not
   cost a rename every build;
3. returns immediately when the destination opens for writing;
4. otherwise moves it aside to `<name>.old-<n>`.

Three things worth keeping:

- **`MoveFileExW`, not `std.fs.Dir.rename`.** Zig's rename opens the source with
  `GENERIC_WRITE | DELETE`; a running image is shared `FILE_SHARE_READ |
  FILE_SHARE_DELETE`, so that call returns AccessDenied on exactly the file this
  tool exists for. Measured — the first implementation used `Dir.rename` and the
  build still failed, with the tool's own "could not be moved aside" warning
  above zig's error.
- **Rename, never kill.** A build that terminated repo-lineage processes would
  take a concurrently running acceptance suite's agent, and its live sessions,
  with it. That is why candidate 1 was not taken; filed as decision D63.
- **A still-running process keeps the `ExecutablePath` it was created with**
  (verified on the box), so the `ExecutablePath`-filtered kills every acceptance
  script uses still find a moved-aside agent. Asserted in arm 3.

Candidate 3 (legibility) is covered by the two warning lines: the tool names the
artifact when it moves one aside, and names it plus the reason when it cannot —
in which case the install step is still allowed to fail the build on its own.
Nothing in the tool ever fails a build.

`GHOZTTY_INSTALL_UNLOCK=0` turns the guard off, which is what makes the original
failure reproducible from this tree rather than only on a box that happens to be
in the wrong state.

## Validation criteria

- [x] a build with a repo-lineage agent running exits 0 — arm 3 of
      `test\win32\build-locked-artifact.ps1`
- [x] the installed agent is the NEW binary — same arm, by searching the
      installed bytes for the `-Dagent-version` stamp that build was given
- [x] the moved-aside file is the OLD binary, and there is exactly one — same arm
- [x] the running agent survives the move and still matches the repo-path kill
      filter — same arm
- [x] the leftover is swept once the holder exits — arm 4
- [x] nothing is moved aside when nothing is holding the file — arm 1 (control)
- [x] the pre-fix failure still reproduces with the guard off — arm 2 (teeth),
      asserting exit != 0 and `AccessDenied` naming `ghoztty-agent.exe`
- [x] standing floor green: `scripts\floor-lane.ps1 -Lane all`, plus P1-P3
