# T383 - Viewer panes have no title: +list prints an empty view: row and the tab reads Ghoztty

## Summary

T374 made viewer panes real, and they arrive with `title = null`. So
`+list` (human) prints `view:   <url>` with an empty title where the Mac prints
the document's, and the tab strip shows the default `Ghoztty` for a pane that
knows exactly what it is displaying.

## Details

`ViewerPane.title` is allocated and freed and never SET — nothing subscribes to
`DocumentTitleChanged`, and nothing falls back to the file basename or the host
for a pane that has no document title yet. `+list --json` reports
`"title": ""`, and `PaneView.title()` returns null so `updateWindowTitle` uses
the tab default.

Titles belong to **T90g** ("chrome & command integration: titles, hero
exclusion, accelerator forwarding, dim walk, split-from-viewer cwd, palette
entries"), so this is not new scope — it is filed so the gap is VISIBLE between
T374 and T90g rather than living only in a reader's head. Fold it into T90g when
that starts, or take it here if T90g slips.

What it needs: `add_DocumentTitleChanged` + `get_DocumentTitle` (slots 46 and 48
of `ICoreWebView2`, right after `add_NewWindowRequested` — the opaque block T374
declared shrinks by two), pushed through `setTitle` and then
`updateWindowTitle`. The pre-load fallback should be the Mac's: the file
basename in file mode, the host in web mode, so a pane is never nameless while
its page loads.

*Validation:* `viewer-panes.ps1` — a `+split --view=<url>` pane reports a
non-empty `title` in `+list --json`, the human `view:` row carries it, and the
tab caption is not the default; a pane still loading reports the fallback rather
than an empty string.

## Done 2026-08-02

Taken here rather than inside T90g: T90g is a six-leg umbrella (titles, hero
exclusion, accelerator forwarding, dim walk, split-from-viewer cwd, palette
entries) and two of its legs already had rows of their own — this one and T380's
dim walk. Titles landed here; T90g keeps the other four.

**The Mac contract, copied rather than invented** (`ViewerView.swift`):
`initialTitle` names a file by `lastPathComponent` and a website by `url.host`,
falling back to the location itself when there is no host; and the `\.title`
observer is guarded by `isWebURL`, so a **file's name is its basename and stays
that way**. That guard is not a detail — a file pane loads the BUNDLED TEMPLATE,
whose `<title>` names the renderer, so without it every markdown pane in the app
would be called the same thing.

**What landed:**

- `viewer_content.urlHost` + `viewer_content.initialTitle` — the pure half, unit
  tested (userinfo with an `@` in the password, an IPv6 literal whose inner
  colons are not a port, a port with no path after it, `about:blank`, a
  percent-encoded `file://` basename).
- `webview2_iface`: `add_DocumentTitleChanged` (46) and `get_DocumentTitle` (48)
  carved out of what was one 10-slot opaque `window` run, plus
  `IID_DocumentTitleChangedHandler`, transcribed from the SDK's own
  `ICoreWebView2Vtbl` (slot order re-derived and checked against the header, not
  from memory) and pinned by two new `@offsetOf` asserts.
- `ViewerPane`: the handler on `com.CallbackOwning` like every other event
  subscription, registered for EVERY pane — a file pane becomes a web pane the
  moment the address bar lands (T159) and a subscription added only for the
  starting mode would be dead by then. `navigate` names the pane from the
  location; `setTitle` early-returns on an unchanged value, because a page fires
  the event more than once per load and each notification repaints the strip.
- `Window.onTabTitleChanged` → **`onPaneTitleChanged(*PaneView, …)`**. The
  `*Surface` in that signature was the last place "pane" and "terminal" were the
  same word on this path — exactly what `PaneView` exists to separate.
- Two ordering fixes, which is where the first run actually failed: a viewer is
  named *before* the tree or the tab exists (`createViewerPane` navigates, then
  the caller wraps it in a `PaneView`), so its own `setTitle` has no leaf to
  notify. `insertPaneAsTab` and `insertPaneAsSplit` now `refreshTabTitle` after
  the pane is in place — a no-op for a terminal, which has no title yet.
- `ViewerPane`'s `WM_SETFOCUS` sets `tab_active_pane` and refreshes the tab
  title, mirroring the terminal WndProc. Without it, clicking from a terminal
  into a viewer left the tab named after the pane the user just left, AND
  `onPaneTitleChanged`'s active-pane guard then dropped every later
  `DocumentTitleChanged`. (`heroOnPaneFocused` / `updateDimOverlays` are
  deliberately not on this path: hero excludes viewers, and the viewer dim
  overlay is T380.)
