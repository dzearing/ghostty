# T221 - Acceptance scripts that report FAILURE(S) but exit 0 (chooser-menu, host-settings)

## In plain terms

Two of the automated checks that guard Windows Ghoztty could fail and still
report success to anything that asked them by machine. They printed the right
thing on screen — "1 FAILURE(S)" — but handed back the number that means "all
good", so a human reading the output saw the problem and a script scoring the
output did not. Nobody notices until the day the only reader is a script.

Both are fixed now (they were repaired in passing by other work before this
task came up), so what this delivers is the thing that keeps them fixed: a
check over all 161 test scripts that a run which announces failure really does
report failure — and, in the other direction, that a run which passes does not
accidentally announce failure on its way out.

## Goals

- [x] `chooser-menu.ps1` and `host-settings.ps1` measured on the box: exit 1
      on a forced failure, exit 0 on a clean run
- [x] An analyzer that decides the question structurally, not by grepping for
      `exit 1` near a verdict line
- [x] A sweep over every acceptance script, reported with its count, so the
      class is closed rather than the two instances
- [x] A teeth check that proves the sweep can go red

## Summary

`test/win32/chooser-menu.ps1` and `test/win32/host-settings.ps1` end like this:

```powershell
if ($script:fail -eq 0) {
    "ALL PASS ($($script:pass) assertions, $($script:skip) skipped)"
} else {
    "$($script:fail) FAILURE(S) ($($script:pass) passed, $($script:skip) skipped)"
}
```

There is no `exit 1` in either file - a RED run leaves `$LASTEXITCODE` at 0.
Anything that scores these by exit code (a suite driver, a `; if ($?)` chain,
CI later) reads a failing script as passing. Every other acceptance script in
the directory exits 1 on failure; these two are the exceptions, found while
migrating `config-errors.ps1`, which had the identical bug and was fixed in
T217 batch 3 (2026-07-31, `8b900433b`).

`ipc-fake-server.ps1` also has no `exit 1` and is FINE - it is a helper
process, not an acceptance script, and has no verdict to report. Do not
"fix" it.

## Details

The fix is one line per script, but do the two other things while there:

1. Add `exit 1` to the failure branch of both scripts.
2. **Check the reverse direction too** - a script that exits 1 on failure is
   only half of it. Confirm each one actually exits 0 on success (an
   `$ErrorActionPreference = 'Stop'` throw in cleanup, or a native command
   left in the pipeline, can leave a nonzero code on a green run and make a
   passing script look red). Run both ways and read `$LASTEXITCODE`.
3. Grep the whole directory once more afterwards for the general shape -
   scripts that compute a `$fail`/`$failures` count and never exit on it -
   rather than trusting the "no `exit 1` anywhere" search that found these
   two. A script can contain an `exit 1` in a SETUP-FAIL branch and still
   fall off the end after a real assertion failure, which this search would
   not have caught.

## Outcome

The two named instances were **already fixed** when this task was claimed —
`chooser-menu.ps1` gained `exit 0` / `exit 1` in T218 (`65ed2bfba`) and
`host-settings.ps1` in T219 (`5320141f1`), both in passing while those tasks
rewrote the same verdict lines for other reasons. Step 1 was therefore a no-op,
and the work went where the remaining value was: step 3, closing the class.

`test\win32\lib\VerdictExitAudit.ps1` decides the question from the **AST**
rather than the text, and that is not a preference. A line-oriented first draft
reported 128 of 160 scripts as suspects, because in most of this suite the exit
shares the verdict's line (`else { "$fail FAILURE(S)"; exit 1 }`) and a
text reader then has to guess what "near" means. Branch membership is a
structural question, so it asks the parser: find the last emitted `ALL PASS`,
find its enclosing `if`, and walk the failure path — the other branches, then
whatever follows the `if` — looking for an exit that is not the constant 0.

Four findings, and the second pair are shapes the original task did not name:

- `fallthrough` — the failure path never exits nonzero. The T221 defect.
- `exits-zero` — the failure path reaches `exit 0`. Worse, because it looks
  deliberate.
- `pass-falls-through` — the **other direction** (validation criterion 2,
  generalized): in the suite's early-return shape, dropping the pass branch's
  `exit 0` makes a GREEN run print `FAILURE(S)` and exit 1.
- `no-verdict` — no `ALL PASS` is ever emitted. Legitimate for a helper;
  `ipc-fake-server.ps1` carries the `# verdict-audit:` marker T221 asked for
  in so many words ("do not fix it").

What the analyzer deliberately does not claim: it cannot judge a **computed**
exit code (`exit ([int]($failures -gt 0))`), which two scripts legitimately
use. Section C of the acceptance script measures real exit codes on the wire
instead — both canonical shapes, both directions, plus the unfixed shape as a
negative control, so the run demonstrates that the thing being guarded against
is real rather than only that the guarded shapes pass.
