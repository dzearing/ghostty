# T1172 - The off switch left the go-loop's own guard 37-red and its gate registry undeclared

## In plain terms

The loop that does this work has a safety net — a set of checks that prove the
watchdog restarts it correctly when a session dies. Adding an off switch broke
those checks: thirty-seven of them now fail, and the check that keeps a list of
every message the loop can print does not know about the three new ones. Nothing
is watching the watchdog until this is put back.

## Summary

Found by T1142's turn on 2026-08-23, roughly an hour after `fe457ac52` ("The
go-loop has an off switch, and it stops at a turn boundary instead of mid-build")
landed from another window on the shared tree. Both guards over
`scripts\go-loop-exec.ps1` went DUE with that commit and neither was run in it.
Run now, at `b49c5f34d`:

```
test\win32\go-loop-guard.ps1     37 FAILURE(S)
test\win32\gate-negatives.ps1    1 FAILURE(S) (34 assertions passed)
    FAIL A2 every label the two gates emit is declared here -
            undeclared: RESUMED, STOP REQUESTED, STOPPED
```

**go-loop-guard**: every watchdog-simulation section is red — H (watchdog
decisions, H1–H10), J (resume nudge, J3–J5), L (duplicate resolution, L1–L12),
N (shim vs nudge, N2–N5), R (transcript pulse, R7/R8/R12), P (beacon, P3). The
lock sections (F, G) and W15 still pass, so this is the watchdog's decision path
rather than the lock: `claim` now reads a stop flag BEFORE the lock and the
watchdog checks the same flag ahead of its "tasks remain" trigger, and the
fixtures those sections build have not been taught about it.

**gate-negatives**: the three labels the off switch introduced —
`STOP REQUESTED` (from `stop`), `RESUMED` (from `resume`) and `STOPPED` (the
claim's new exit-4 refusal) — are not in the registry at
`test\win32\gate-negatives.ps1:118`. `STOPPED` is a **gate**, not a status: it
ends the turn and hands back the lock, so under T1133 it owes a demonstration
that it can fire, and there is none in `go-loop-guard.ps1` (no arm mentions the
stop flag at all). The other two are `status` lines and only need declaring.

This is the shape both rules exist for, arriving on the rule's own subject:
T783 wrote the guard-due machinery *because* the go-loop guard sat 26-red for a
day with nothing tying a `scripts\go-loop-*.ps1` edit to its harness, and T1133
wrote "a new gate ships with the demonstration that it can fail" three days ago.
The machinery worked — both guards reported DUE at the very next claim — and the
turn that changed the code did not run what it named.

## Notes

T1142's commit could not clear this and did not try: the failures are entirely
in another turn's change, and a 37-red harness is not a thing to repair as a
side effect of an unrelated task. That commit used `-NoGuardDue` naming this
task — which is precisely the misuse T1165 was filed about, since the hatch
means "this harness cannot run here" and what is true is "this harness is red
for a task already in the queue". Worth citing there as the second instance.
