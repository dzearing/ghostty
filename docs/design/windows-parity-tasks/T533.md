# T533 - Dragging a divider should only resize its two adjacent panes

## User report (2026-08-06, verbatim - right after confirming T495 fixed)

"resizing the 2nd sizer now works perfectly as expected and it does not
affect the 1st sizer. but resizing the 1st sizer moves the 2nd sizer. I
expect moving sizers compensates for the window sizes so that other panels
aren't affected - only the 2 panels being sized are."

## In plain terms

With three panes side by side, dragging the first divider used to drag the
second one along with it — the pane on the far right silently shrank even
though nobody touched its edge. Now a divider only trades space between the two
panes it actually sits between, and every other pane keeps exactly the width it
had. Anyone who arranges panes and then adjusts one boundary notices, because
their layout stops rearranging itself behind them.

## Goals

- [x] Dragging a divider leaves every other divider on its pixel
- [x] The panes not adjacent to the dragged divider keep their exact size
- [x] Deep column runs and grids (a perpendicular split in the way) behave the
      same at every level
- [x] A drag that goes out and comes back lands where it started — no drift
- [x] A squeeze that cannot be honored degrades gracefully instead of
      oscillating

## What happens and why

T495 fixed the drag MAPPING; this is drag SEMANTICS. In the 3-column tree
`split(r1) -> [p1, split(r2) -> [p2, p3]]`, dragging divider 1 changes r1 -
the boundary between p1 and the whole right SUBTREE. r2 stays fixed, so p2
and p3 shrink/grow proportionally and divider 2 visibly slides. The user's
(and most UIs') expectation: divider 1 exchanges space between p1 and p2
ONLY; p3 keeps its absolute width, so divider 2 stays pixel-fixed.

## Direction

At `startDividerDrag`, record the absolute pixel positions of the dragged
divider's neighboring dividers (or every affected descendant boundary). On
each `updateDividerDrag` tick, after computing the dragged node's new ratio,
COMPENSATE: recompute the immediate child subtree's ratio(s) so the other
boundaries resolve to their recorded absolute positions. For the 3-column
case that is one adjustment: `r2' = (old divider-2 x - new region start) /
new region width`, clamped. General case: only the first split on the
shrinking/growing side needs compensation per level - walk while a boundary
moved. Keep it in pure geometry (`split_geometry.zig`) with tests at
1.0/1.25/1.5/2.0 per the design-system rule, including the deep-nesting case
(4+ columns) and the clamp interaction (a compensated ratio hitting [0.1,
0.9] must degrade gracefully, not oscillate).

**Check the Mac first** (platform symmetry): if SplitView.swift already
compensates (AppKit NSSplitView semantics do), this is a parity fix; if not,
land both halves or file the Mac seat's task alongside.

## What was built

`src/apprt/win32/split_resize.zig` — a new pure module, sibling to
`split_geometry.zig`: that one says where the DRAGGED divider goes, this one
says what the rest of the tree does about it. `plan()` returns the dragged
node's ratio plus the compensating ratios that put every other same-axis
boundary back on its pre-drag pixel. Three things fell out of stating the rule
that way, and each is asserted:

- **It recurses**, so a four-column run behaves like the three-column case at
  every level.
- **A perpendicular split is walked THROUGH, not around** — a vertical divider
  is not a boundary on the horizontal axis, but both of its children live in
  the range that changed, so a grid does not shear when one column boundary
  moves.
- **Nothing that did not move is touched.** The walk prunes any subtree whose
  axis range is unchanged, which leaves the other side of the tree
  bit-identical and keeps a drag O(depth).

Two details that are the difference between working and nearly working:

- **Every tick re-solves from a PRE-DRAG snapshot**, never from the previous
  tick. Ratios are `f16` and `split_geometry.axis` truncates, so re-deriving
  "hold it where it is now" a few hundred times drifts; solving against the
  original absolute positions also makes a drag exactly reversible.
- **The held ratio aims at the CENTER of its target pixel.** Aiming at the edge
  lands a pixel low every time anything rounds down, which is a boundary that
  creeps left on every drag rather than one that holds.

A clamped compensation (drag far enough and there is no ratio that keeps the
next boundary where it was) gives way at the same `[MIN_RATIO, MAX_RATIO]` band
a dragged divider obeys, and the walk continues against the geometry that
ACTUALLY resulted — so nothing below it is pinned to a position nobody can
reach. `Window.zig` snapshots the tab's tree at `startDividerDrag` into a fixed
128-node buffer (no allocation on the message loop) and re-validates it each
tick; a tree that does not fit, a divider whose own region will not resolve, or
a tree rebuilt mid-drag all fall back to the pre-T533 single-node resize rather
than to a wrong one.

## Validation criteria

- [x] Unit: 3-column compensation - drag divider 1, divider 2's absolute
      position unchanged; deep nesting; clamp edge; vertical analog —
      `src/apprt/win32/split_resize.zig`, 13 tests, every geometric one swept
      at 1.0/1.25/1.5/2.0, green in `zig build test -Dapp-runtime=none`. Also
      covers the defect itself as a control (uncompensated slide > 200px), the
      perpendicular-split walk, the untouched-subtree prune, reversibility
      across 50 ticks, a truncated plan buffer and a cyclic node slice.
- [x] On-box: split-divider.ps1 T495 section extended - after dragging the
      FIRST divider, the SECOND divider's x is unchanged (pane-rect oracle) —
      `test\win32\split-divider.ps1` ALL PASS (62 assertions); the new arms
      read `1064 -> 1064` for a ±120px drag of the first divider, with a
      control arm proving the first divider really tracked. **Teeth-checked**:
      with `dragSnapshotMatches` forced to false and the app rebuilt, those
      arms go red (second divider slid 54px, far pane 147 -> 93).
- [x] Mac behavior checked; matched or the other half filed — `SplitView.swift`
      does NOT compensate (each nested split's `split` binding is relative to
      its own geometry, exactly like our untouched tree), so this is a
      deliberate divergence, not a parity port. Mac half filed as **T754**.
- [x] Standing floor: `scripts\floor-lane.ps1 -Lane all` → none/win32/agent all
      PASS; P1/P2/P3 acceptance ALL PASS.
