# T533 - Dragging a divider should only resize its two adjacent panes

## User report (2026-08-06, verbatim - right after confirming T495 fixed)

"resizing the 2nd sizer now works perfectly as expected and it does not
affect the 1st sizer. but resizing the 1st sizer moves the 2nd sizer. I
expect moving sizers compensates for the window sizes so that other panels
aren't affected - only the 2 panels being sized are."

## What happens and why

T495 fixed the drag MAPPING; this is drag SEMANTICS. In the 3-column tree
`split(r1) -> [p1, split(r2) -> [p2, p3]]`, dragging divider 1 changes r1 -
the boundary between p1 and the whole right SUBTREE. r2 stays fixed, so p2
and p3 shrink/grow proportionally and divider 2 visibly slides. The user's
(and most UIs') expectation: divider 1 exchanges space between p1 and p2
ONLY; p3 keeps its absolute width, so divider 2 stays pixel-fixed.

## Direction

At `startDividerDrag`, record the absolute pixel positions of the dragged
divider's neighboring dividers (or every affected descendant boundary). On
each `updateDividerDrag` tick, after computing the dragged node's new ratio,
COMPENSATE: recompute the immediate child subtree's ratio(s) so the other
boundaries resolve to their recorded absolute positions. For the 3-column
case that is one adjustment: `r2' = (old divider-2 x - new region start) /
new region width`, clamped. General case: only the first split on the
shrinking/growing side needs compensation per level - walk while a boundary
moved. Keep it in pure geometry (`split_geometry.zig`) with tests at
1.0/1.25/1.5/2.0 per the design-system rule, including the deep-nesting case
(4+ columns) and the clamp interaction (a compensated ratio hitting [0.1,
0.9] must degrade gracefully, not oscillate).

**Check the Mac first** (platform symmetry): if SplitView.swift already
compensates (AppKit NSSplitView semantics do), this is a parity fix; if not,
land both halves or file the Mac seat's task alongside.
