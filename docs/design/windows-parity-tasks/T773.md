# T773 - +version answers for two binaries and nothing tells the delivery gates apart (filed as: a freshly built binary bakes a stale commit stamp)

## In plain terms

Every Ghoztty build stamps itself with the version of the code it was built
from, and the delivery scripts use that stamp to prove they shipped what they
just built. This was filed because the stamp looked stuck at an older value —
which would have blocked the daily refresh that keeps the user's terminal up to
date.

It turned out the stamp was fine. Asking Ghoztty for its version prints two
answers in one page: the version of the copy you asked, and, below it, the
version of the copy that is currently **running** on the machine. Those are
normally different, and the second one is the one that says "commit" next to
it — so it is the one a reader's eye lands on. The label was right; the reading
was wrong.

Nothing about the product changes. What this task leaves behind is that the
mistake is now hard to repeat: the scripts that read that page say plainly which
of the two answers they want, and tests fail if anything ever blurs them.

## VERDICT (2026-08-12): the premise is wrong — the stamp was never stale

`+version` answers for **two binaries**, and the evidence below read the wrong
one. Under its own `Version` block the command prints a `Running Instance`
block describing whatever Ghoztty is **running**, fetched over IPC
(`src/cli/version.zig` `printRunningInstance`, added by T52) — and that block
owns the only line literally labelled `commit`. `commit : 2929e42c0` is the
installed release the 05:17 morning refresh had delivered and the user had been
sitting in all day. It is not the probed binary's stamp, which is on the
`- version:` line above it.

That is also why the Debug and the ReleaseFast build "agreed": both probes had
dialed the same running app. Measured live at HEAD `66ad87d45`, one document,
two different commits:

```
  - version: 1.4.0-users-dzearing-windows-amd64-+66ad87d45   <- this binary (== HEAD)
Running Instance
  - commit  : 445780e49                                      <- the app that is running
```

`Resolve-GhozttyExeCommit` reads `66ad87d45` and `Test-CommitsMatch` against
HEAD returns `True`, so the delivery gates were reading the right number the
whole time and `launch-upgrade.ps1` would not have refused.

The agent's `20260811-3bbf0eefb` was not stale either, for a second and
unrelated reason: `GhosttyAgent.versionString` stamps the last commit that
touched the **agent's own compiled sources**, deliberately not HEAD (see its
doc comment — a HEAD-derived stamp made every app release look like a "newer"
agent and prompted users to reset live sessions to adopt an identical binary).
The app and the agent disagreeing is the design working, not a symptom.

### What the turn changed instead

The defect this leaves is real but different: nothing could tell the two blocks
apart on a reader's behalf, and their separation rests on **one space**
(`version:` vs `version :`) that no test held.

- `scripts/delivery-version.ps1` documents the two-block trap as the third
  named trap in its header and on `Get-CommitFromVersionText` itself.
- Arms **A31–A35** of `test/win32/upgrade-staleness.ps1` hold the separation
  with a payload whose two blocks name **different** commits (this day's
  shape). Teeth-checked: relaxing the anchor to `version\s*:` turns A33 and A34
  red, and nothing else.
- Arms **B11–B13** make the freeze checkable rather than assumed: the exact
  `git log` line `GitVersion.detect` bakes must name HEAD, and the exe's baked
  commit must be a real commit object reachable from HEAD.
- `Invoke-GhozttyVersionText` now bounds the running-app query with
  `GHOZTTY_IPC_TIMEOUT_MS=2000`. Reading a **file's** identity had a hard
  dependency on an unrelated running app answering within the probe's 20s
  deadline, and T755's default is 30s — so a busy or wedged app could turn
  "read this binary's stamp" into "the delivery cannot verify itself".

`2929e42c0` was HEAD at 05:17 today, which is when the morning refresh last
delivered (`%TEMP%\ghoztty-upgrade.log`: `POST-SWAP VERIFY OK … reports
'2929e42c0'`). So the stamp is not frozen forever — it is frozen at some earlier
build's value.

**The bits are NOT stale, only the label**: the staging exe and the installed
release differ in both SHA-256 and length (32,276,480 vs 32,229,376 bytes), so
the 18:33 build really did compile the 40 commits of `src/` changes. Note also
that the app and the agent disagree with each other (`2929e42c0` vs
`3bbf0eefb`), which rules out "the tree is what is stale" and points at the
version derivation itself.

## Why it matters

Three separate gates read this number and all of them are now reading a value
that does not describe the binary they are checking:

- `scripts/launch-upgrade.ps1` compares the staged exe's `+version` commit
  against `git rev-parse --short HEAD` and exits 3 (**STALE STAGING**) on a
  mismatch — so the next `morning-refresh.ps1` (T525) delivers nothing, and the
  user keeps running an old app while the loop reports normal turns.
- `scripts/deliver-windows-build.ps1` (T198) proves "every delivered
  `ghoztty.exe`/`ghoztty.com` answers `+version` with the commit being shipped".
- go.md's standing rule — "a delivery is still not done until you have READ that
  commit back" — is only as good as the stamp.

The forced-through path (`-AllowStaleStaging`) is worse than the refusal: it
ships a binary whose self-reported provenance is wrong, which is the exact
condition all of the above exist to catch.

## Where to look

- `src/build/GitVersion.zig` `detect()` — runs `git … log --pretty=format:%h -n
  1` through `b.runAllowFail` at CONFIGURE time; the result becomes
  `Config.version.build` (`src/build/Config.zig:338`) and is printed by
  `src/cli/version.zig`.
- The agent has its own derivation (`src/build/GhosttyAgent.zig`, the
  `YYYYMMDD-<sha>` stamp, `-Dagent-version=` override) and is stale at a
  DIFFERENT sha, so whatever this is, it is not one shared cache entry.
- Hypotheses worth testing in order: (1) the build-options module is not part of
  the compile's cache key, so a rebuild reuses an older options artifact;
  (2) `b.runAllowFail`'s result is cached across builds by zig 0.15.2;
  (3) the git invocation in the build environment answers from a different
  HEAD than an interactive `git log` does (a `GIT_*` env var, a stale index).
  Print the string the build actually bakes (a `-Dverbose`-style log line or a
  temporary `std.debug.print` in `Config.init`) before theorising further.

## Validation criteria

- [x] With a commit landed after the previous build, a plain rebuild produces an
      exe whose `+version` commit equals `git rev-parse --short HEAD`. — VERIFIED
      live: HEAD moved `b15b31e55` → `66ad87d45` (13:12), a plain `zig build
      -Dapp-runtime=win32 -Doptimize=Debug` at 13:16 baked
      `- version: …+66ad87d45`. It already held before the rebuild, too: the
      13:04 build carried `b15b31e55`, which was HEAD at 13:04.
- [x] The same holds for `ghoztty-agent --version`'s `<date>-<sha>` stamp. —
      RESTATED, because the criterion as written is not the contract: the agent
      stamps its last **agent-source** commit by design, and the rebuild
      produced `20260812-9fa2c1493` for a HEAD of `66ad87d45` because
      `9fa2c1493` is the newest commit touching `src/remote`. `66ad87d45` is a
      tracker-only commit and must NOT move the stamp.
- [x] `launch-upgrade.ps1` (no `-AllowStaleStaging`) reaches the delivery on a
      clean tree at HEAD instead of exiting 3. — VERIFIED at the gate itself
      rather than by running a real delivery (which would restart the user's
      terminal mid-turn): `Resolve-GhozttyExeCommit` on the staged shape returns
      `66ad87d45`, `Get-RepoHeadCommit` returns `66ad87d45`,
      `Test-CommitsMatch` → `True`, which is exactly the expression
      `launch-upgrade.ps1:195` branches on. Sections C/D/E of
      `test/win32/upgrade-staleness.ps1` drive the launcher end-to-end against
      a sandbox and are ALL PASS.
- [x] A regression check exists that would catch the stamp freezing again. —
      B11–B13 (above). B11 asserts the exact `git log` line the build bakes
      names HEAD, which is the freeze itself; B12/B13 refuse a stamp that is
      not a real commit reachable from HEAD. The artifact-level form ("the exe
      on disk carries HEAD") is deliberately NOT asserted here and the script
      says why: an mtime cannot tell "built from an older tree" from "the tree
      moved under a good binary", and both seats push to this branch.
- [x] A regression check exists for what actually went wrong — the two-block
      misread. A31–A35, teeth-checked both directions.
