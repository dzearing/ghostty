# T161 - Viewer page zoom + pane-scoped chords (ctrl+r reload, ctrl+d/ctrl+l address bar)

## Summary

Filed 2026-07-29 by the T127 re-scope. Two Mac viewer capabilities with no
T90b-T90h row: browser-style page zoom (Cmd +/-/0 plus pinch) and PANE-SCOPED
chords -- Cmd+R and Cmd+D mean something different while a viewer holds
keyboard focus and their global meanings are untouched everywhere else. The
override STRUCTURE ports as-is; the chords do not, because the Windows defaults
differ. Mapping pinned in `docs/design/viewer-panes-windows.md` P6/P7.

## Details

Mac sites: `ViewerView.PaneChord` (`:2110`), `handle(_:)` (`:2139`),
`paneHoldsFocus`, `ZoomAction` (`:2190`), `zoomFactor`, `pushZoomToWebView`,
`handleZoom`, `isViewerContentFocused`, `allowsMagnification = true`,
`focusAddressBar`.

Windows mapping (while a VIEWER pane holds focus; terminal panes keep every
global meaning, which is the invariant to test):

| Chord | In a viewer | Globally (unchanged) |
|---|---|---|
| ctrl+r | reload the pane | belongs to the shell |
| ctrl+d | focus the address bar | split right |
| ctrl+l, alt+d | focus the address bar | clear-screen / n/a |
| ctrl+plus/minus/0 | page zoom | font size |

Rationale on the record: `ctrl+r` is free precisely because a viewer pane has
no shell, so the reason the banner editor had to take `ctrl+shift+b`
(`src/config/Config.zig:7012-7019`) does not apply, and every Windows browser
already means reload by it. `ctrl+d` mirrors Mac's Cmd+D relationship exactly
(globally split-right, `Config.zig:6992-6996`); `ctrl+l` / `alt+d` are added
as Windows-native aliases because `ctrl+d`-for-address-bar is Mac muscle
memory.

Scope:

- `put_ZoomFactor` on the controller for keyboard zoom; copy Mac's step and
  clamp values exactly so the two clients zoom identically. Pinch / ctrl+wheel
  is Chromium's own -- no code, but assert it does not ALSO change font size.
- `add_AcceleratorKeyPressed` (T90a section 11) checks the pane-scoped table
  first, then the app keybind table, then lets the page have the key. Handler
  stays non-blocking (the browser process waits synchronously on it).
- Focus rule: the chords are live only while keyboard focus is inside the
  viewer pane -- its page or its nav bar (Mac also counts its feedback
  composer, which Windows v1 does not have; see T164).

*Validation:* `viewer-panes.ps1` grown, with POSITIVE CONTROLS mandatory
(T157's lesson: a keybind script that cannot prove it delivered the chord
proves nothing). ctrl+r with a viewer focused reloads; with a terminal focused
it reaches the shell. ctrl+d with a viewer focused puts the caret in the
address field; with a terminal focused it splits right. ctrl+plus with a viewer
focused zooms the page and leaves the terminal font size alone, and vice versa.
Zoom clamp is unit-tested in both lanes.

## In plain terms

A Ghoztty window can hold "viewer" panes — a rendered markdown file, a web
page, the task dashboard — next to normal terminal panes. Today those panes
have no page zoom (small text stays small) and none of the browser reflexes:
Ctrl+R doesn't reload the page, and there is no key that jumps to the address
bar. After this lands, a focused viewer behaves like a browser tab — Ctrl+R
reloads, Ctrl+D / Ctrl+L / Alt+D put the caret in the address bar, and
Ctrl+Plus/Minus/0 zoom the page in and out — while terminal panes keep every
one of those keys' normal meanings (Ctrl+R still reaches your shell, Ctrl+D
still splits, Ctrl+Plus still changes the font size).

## Goals

- [x] Ctrl+Plus/Minus/0 zoom a focused viewer's page, with exactly the Mac
      client's step (×1.1) and clamp (50%–300%), and survive navigation.
- [x] Ctrl+R reloads a focused viewer in place (the interactive `+reload`).
- [x] Ctrl+D, Ctrl+L, and Alt+D focus and select the address bar.
- [x] The chords work from the address field too (it is part of the pane);
      zoom stays content-only, matching Mac.
- [x] Terminal panes keep every global meaning — the pane-scoped table is
      checked only while a viewer holds focus.

## Implementation notes (2026-08-07)

- Pure half: `viewer_accel.zig` gained `PaneChord`/`paneChord` (ctrl+r,
  ctrl+d/ctrl+l, alt+d — exact modifiers only, Win key always rejected) and
  `ZoomAction`/`zoomAction`/`steppedZoom` with Mac's constants verbatim
  (`min_zoom` 0.5, `max_zoom` 3.0, `zoom_step` 1.1). Shift participates only
  in typing "+" on the main row, the exact set Mac's
  `charactersIgnoringModifiers` accepts.
- `ViewerPane`: `zoom_factor` (in-session only, deliberately not persisted —
  Mac parity), `handleZoom`/`pushZoom` over the newly typed
  `get/put_ZoomFactor` controller slots, and `claimsChord` ordering the
  Invoke-time claim zoom → pane chord → app table (re-resolved identically
  when the posted `WM_APP_VIEWER_ACCEL` lands). A non-default factor
  re-pushes in `onNavigationCompleted`, Mac's `didFinish` re-apply.
- Nav-bar leg: `ViewerNavBar.handleEditChord` + main-loop routing
  (`WM_KEYDOWN`, and a `WM_SYSKEYDOWN` intercept for alt+d) make the chords
  live while the address EDIT holds focus. Zoom is deliberately NOT in that
  leg — Mac scopes it to focused content via `isViewerContentFocused`.
- Pinch / ctrl+wheel: Chromium's own, as the scope pinned. The "does not
  ALSO change font size" concern is structural on win32: those wheel
  messages go to Chromium's child HWNDs, which never reach the Surface
  ctrl+scroll font path, and an off-desktop acceptance script cannot
  synthesize a pinch — so no runtime assert was added.
- The acceptance oracles (worth reusing): a raw-TCP no-store page server
  whose GET count proves a reload, and a page that mirrors
  `window.devicePixelRatio` into `document.title`, which
  `DocumentTitleChanged` carries into the `+list --json` leaf title — the
  only zoom readout visible outside a WebView2.
