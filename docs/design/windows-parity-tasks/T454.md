# T454 - A std.log.warn from inside a test kills the test binary - null read in std.debug.print's stderr-writer lock, which is what destroys every T443 diagnostic

## Summary

Filed out of **T450** (2026-08-04), the first turn that ever captured a stack
for one of these crashes. The stack is not what four contexts of T442/T443
bisection assumed:

```
ghoztty_agent_test!print__anon_430783+0x26   std/debug.zig:227     <-- FAULT
ghoztty_agent_test!log__anon_417474+0x31     compiler/test_runner.zig:280
ghoztty_agent_test!log__anon_410253+0xf      std/log.zig:124
ghoztty_agent_test!warn__anon_406518+0xf     std/log.zig:181
ghoztty_agent_test!verifyIntegrity+0x19aa    src/terminal/page.zig:482
```

`c0000005`, `Attempt to read from address 0000000000000000`.

Read bottom-up: `Page.verifyIntegrity` **detected** an integrity violation and
called `log.warn` to report it (page.zig:482 is the "cell not marked as
hyperlink" arm). Zig's test runner routes `std.log` into `std.debug.print`,
whose first act is `lockStderrWriter(&buffer)` -> `std.Progress.lockStderrWriter`
(debug.zig:227). That dereferences a null pointer and the process dies.

So the process does not die *of* the integrity violation. It dies **reporting**
it, and the report is exactly the message that would have said what was wrong.

## In plain terms

The tests have a self-check that is supposed to print "this page is corrupt" and
carry on. It looked like printing that message was itself the crash — so the one
sentence explaining what went wrong seemed to be destroyed at the moment it was
written.

**That turned out to be wrong, and finding out why was the useful part.**
Printing the message works fine; there are now two tests that break a page on
purpose and watch the warning come out intact. What actually happens is that
something in the test run is scribbling over memory the crashing function is
standing on — including the bookkeeping the printing code needs — so the print
is simply the first thing to trip over the damage. The message is a victim, not
the cause. That points the long-running corruption hunt at a much narrower
target than it had before.

## Goals

- [x] A `std.log.warn` from inside a test prints instead of crashing —
      **it already did.** The premise was wrong; see the RESOLUTION below.
- [x] A deliberately-triggered page integrity violation ends with its message
      visible in the lane output, not with a dead process — now asserted by two
      permanent tests in `src/terminal/page.zig`.
- [x] `zig build test-agent` and `zig build test -Dapp-runtime=win32` no longer
      end on this signature — **reassigned to T443.** The signature is a
      *symptom* of the corruption T443 chases, not an independent defect, so
      nothing in this task can retire it. What this task delivers instead is the
      evidence that redirects T443 (below).

## RESOLUTION (2026-08-04) — the diagnosis above is WRONG, and the correction matters

**`std.log.warn` from `Page.verifyIntegrity` does not crash. It never did.**
Two tests now trigger a real integrity violation on purpose, in both shapes of
caller, and run inside the very binary that was dying:

```
+- run test ghoztty-agent-test stderr
[page] (warn): page integrity violation y=0 x=0 spacer tail at start
[page] (warn): page integrity violation y=0 x=0 spacer tail at start
```

Exit 0, message intact, error returned. So the report path is healthy and
"printing the message is itself a crash" is not what is happening.

### What is actually happening

Reading the T450 dump properly (`.dumps\ghoztty-agent-test-20260804-062733-1.dmp`,
symbols from the matching `.zig-cache\o\…` build) changes the story completely.

The faulting instruction is at `print__anon_430783+0x26`:

```
0190e7f0 verifyIntegrity:
    push rbp / sub rsp,0C20h / lea rbp,[rsp+80h]
    mov [rbp+358h],r8     ; alloc   (Allocator*)
    mov [rbp+360h],rdx    ; self    (Page*)
    mov [rbp+368h],rcx    ; HIDDEN error-return-trace param (?*StackTrace)
...
01910195 call warn__anon_406518    with rcx=[rbp+368h], rdx=&{y,x}
...
019bf966 print__anon_430783+0x26:
    mov rax,qword ptr [rcx]        <-- FAULT, rcx = 0
```

`verifyIntegrity` returns `!void`, so Zig hands it an **error return trace
pointer as a hidden first argument** and it forwards that pointer down
`warn` → `log` → `test_runner.log` → `std.debug.print`. `std.debug.print` reads
`trace.index` in its prologue, unconditionally. The pointer is null, so it dies.

The pointer is null **because the stack frame is corrupt**, and the same three
prologue slots prove it:

| slot | holds | value in the dump |
|---|---|---|
| `[rbp+358h]` | `alloc` (`Allocator*`) | `0x0cf2` — not a pointer |
| `[rbp+360h]` | `self` (`Page*`) | `0` |
| `[rbp+368h]` | error return trace | `0` |

`self` cannot be null: `verifyIntegrity` dereferences it on every line from its
first bounds check to the cell loop it was 0x19aa bytes into. Disassembling the
whole function shows **nothing writes those three slots after the prologue** —
they are written once, from the incoming registers, and never again. So they
were overwritten by something outside the function.

`rbp = 0x68fbff5fa0` is confirmed two independent ways: the `lea rdx,[rbp+860h]`
at the call site matches the faulting `rdx` exactly, and `warn`'s pushed frame
pointer at `0x68fbff5f40` holds the same value beside the return address.

### What this means for T443 — this is the point of the task

- **T454 and T443 are one bug, not two.** There is no "make it legible first,
  then fix the corruption". The unreadable crash IS the corruption, arriving on
  the stack.
- **The corruption reaches the STACK, not just page memory.** Every hypothesis
  so far has been about `Page`/`PageList` heap structures. A wild write that
  zeroes a live stack frame's spilled parameters is a much narrower target — and
  it is why the crash lands in whatever `terminal.*` test happens to be running
  rather than in one reproducible place.
- The `UnmarkedHyperlinkCell` violation that starts the sequence is very likely
  the *same* wild write seen from the heap side, not a separate `PageList`
  logic error.
- The `-- crash stack --` block T450 added still reports this as a crash inside
  the logging path. That framing is now known to be misleading; the interesting
  frame is `verifyIntegrity`, and the interesting memory is its frame.

### What landed

`src/terminal/page.zig` — two tests next to `test "Page init"`:

- `Page verifyIntegrity reports a violation instead of dying` — errorable
  caller (the test body itself).
- `Page verifyIntegrity reports a violation from a non-errorable caller` — the
  `assertIntegrity` shape, a void function swallowing the error, which is the
  caller shape that differs in whether an error return trace exists to hand
  down. Both were needed because that difference is exactly what the crash
  turned on.

They run in all three lanes (`page.zig` is shared terminal code) and cost
microseconds, so the reporting path is now exercised on every floor run instead
of only when a real corruption happens to occur.

### Ruled out along the way

- **"any `std.log.warn` from a test kills the binary"** — no. Minimal repros
  (`zig test` on a standalone file) print fine from an errorable function, from
  an `inline` catch wrapper, and from a void caller. The `none` lane's
  `terminal_apc` warns already showed this; the agent binary behaves the same.
- **A per-module `error_tracing` mismatch** producing an ABI skew — no. Nothing
  in `build.zig` or `src/build/*.zig` sets `error_tracing`, and every module in
  the agent test build is `.Debug`.
- **`std.Progress` being initialised differently under the build runner** — not
  reached. The fault is before any progress or stderr state is touched; it is
  the trace-pointer deref in the function prologue.

## Evidence (2026-08-04, T450)

Captured by `scripts\crash-catch.ps1 -Lane agent`, which runs the test binary
under cdb so the exception is taken on FIRST chance -- before Zig's own handler
gets it and recursively panics. Reproduce with:

```powershell
powershell -NoProfile -File scripts\crash-catch.ps1 -Lane agent -Attempts 6
```

It landed on attempt 1 of 6, in 24 s.

- Test running at the time: `1060/3913 terminal.PageList.test.PageList resize
  reflow exceeds hyperlink memory forcing capacity increase` -- a member of the
  victim set T443 recorded, and a hyperlink-path test, matching the
  hyperlink-path `log.warn` that faulted.
- **Four threads captured; three of them are idle Windows thread-pool workers
  parked in `ZwWaitForWorkViaWorkerFactory`.** Nothing else was running. That is
  a direct hit against T443's top-ranked hypothesis ("a single leaked or
  dangling background thread ... writing through a stale pointer on a timer") --
  at least for this crash, there was no other thread to do it.
- Artefacts kept: `.dumps\ghoztty-agent-test-20260804-062733-1.dmp` (full
  memory, all threads) and the matching `.log` transcript. Both are transient
  (`.dumps/` is gitignored); re-capture with the command above.

## It is NOT "any log.warn crashes" — narrow it before fixing

The same turn's `none`-lane floor run printed these into the lane log, from
inside tests, without dying:

```
[terminal_apc] (warn): kitty graphics protocol error: error.InvalidFormat
[terminal_apc] (warn): kitty graphics protocol error: error.Overflow
```

So `std.log.warn` from a test works in the general case, and the title's
"a std.log.warn from inside a test kills the test binary" is too broad. What is
established is narrower: **on this one capture, the null read happened on that
path.** Candidate distinguishers, none checked:

- a different binary (`ghoztty-agent-test` vs `ghostty-test`) and so a different
  `std.Progress`/stderr setup,
- run directly under cdb vs. driven by the build runner over `--listen=-`,
- *when* it happens — a log emitted while the progress bar is mid-redraw, or
  after some test has touched stderr, rather than logging as such.

Start by reproducing it deliberately (a test that just calls `log.warn` in each
binary, both ways) before touching anything. A fix aimed at the broad claim
would be aimed at something that is not broken.

## What is NOT established yet

- **Whether this is the same crash `zig build` reports.** This capture ran the
  test binary DIRECTLY under cdb. T443's crashes were seen both directly and
  under the build runner, and the victim set matches, but "same signature
  family" is not "same crash". Capturing one under the build runner is the
  check, and it matters here specifically: `std.Progress` is initialised
  differently when the build runner is driving the binary over `--listen=-`
  than when the binary is run on its own, and `std.Progress` is where the null
  read happens.
- **Why the pointer is null.** Not investigated. The obvious suspects are the
  order in which `std.Progress`/the stderr writer are set up in this Zig
  (0.15.2) test runner, and whether a test that has redirected or closed stderr
  leaves it that way. Do not assume; the whole point of the tooling this came
  from is that assumptions here have been wrong four times running.
- **The integrity violation itself is still real and still unexplained.** Some
  page genuinely has a cell carrying hyperlink data without the row marked. That
  is T443. Fixing T454 does not fix it -- it makes it *legible*, which is the
  precondition for fixing it.
