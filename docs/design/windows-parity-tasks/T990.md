# T990 - Typing a long filter into the machine chooser panics the app too

## In plain terms

The machine chooser has a filter box like the Activity Monitor's, and typing
enough into it kills the whole terminal the same way — sooner if you are typing
a language whose characters are not ASCII. T989 fixed one field; this fixes the
other one that is known to crash, and measures every remaining text field in the
app so nobody has to find the next one by losing their work.

## Summary

T989 fixed one filter box; the machine chooser's is the same
256-unit-into-256-byte read and crashes the same way, and half a dozen more
fixed-buffer readers have never been measured.

## Details

The fix already exists: `utf16_text.toUtf8Truncating`
(`src/apprt/win32/utf16_text.zig`, T989) converts into a fixed destination
without ever writing past it, truncating on a codepoint boundary. What is left
is finding every reader that still calls `std.unicode.utf16LeToUtf8` into a
fixed buffer and pointing it at the helper — the `catch` those call sites are
written with cannot see an undersized destination, so each one is a panic with
a threshold rather than the graceful truncation its comment claims.

**Confirmed crasher** (both halves read, T989 turn):

- `MachineChooser.filterText` (`MachineChooser.zig:3362`) reads a `[256]u16`
  wide buffer, and all three callers (`:1231`, `:2718`, `:3023`) hand it a
  `[256]u8`. 255 three-byte characters need 765. Its doc comment says
  "truncated to fit"; it is not.

**Unmeasured, same shape** — each needs its wide buffer compared against what
its callers actually pass, and converting them all is cheaper than deciding
which are safe:

- `ConfirmDialog.readEdit` (`:699`), `[512]u16` into the caller's `o.buf`
- `HostSettingsDialog.readText` (`:568`), `[MAX_VALUE_LEN+1]u16` into
  `wd_buf` / `shell_buf`
- `NewProcessDialog.readText` (`:516`), `[MAX_VALUE_LEN+1]u16` into the
  caller's `cmd_buf` / `cwd_buf` slices
- `ShareMachineRow.hostName` (`:224`), `[256]u16` into the caller's `out`
- `BannerDialog.zig:503`, `RenameDialog.zig:513` and `:547`, `App.zig:6118`,
  `Surface.zig:2247/2631/2774/3365/4080/4251/4270`, `ViewerPane.zig:5733`

`ViewerNavBar.addressText` (`:528`) is the shape done right — its caller at
`:546` sizes the destination `address_cap_utf16 * 3` — and `ViewerPane`'s popup
router (`:2102`) guards with an explicit `wide.len * 3 > buf.len` check. Neither
needs changing, but both are worth reading first: the point of this task is that
the sizing rule stops being something each call site has to remember.

## What landed

`utf16_text.zig` grew two more bounded conversions beside T989's
`toUtf8Truncating`: `toUtf8Counting`, which also reports how much of the source
it got through, and `toUtf8AllOrNothing`, which converts only if all of it fits
and returns 0 otherwise — the behavior half a dozen readers documented
themselves as having ("0 when it does not fit — a truncated path is worse than
none") years before anything made it true.

All 20 fixed-destination call sites in `src/apprt/win32/` now go through one of
the three, chosen by what the text IS: a filter, a search needle, a title or a
label truncates; a device name, host name, path, command or URI is
all-or-nothing. Beyond the chooser's own filter, the ones that were reachable
crashes rather than measured-and-fine were the command palette's filter (256
units into 512 bytes), the terminal search box (512 into 1024), "Copy title to
clipboard" (512 into 1024), and the IME commit path.

The IME path is the one that did not take either answer. `sendImeText` received
an unbounded wide slice and converted it into 256 bytes, so an 86-character CJK
commit — or a paste through the IME — panicked; but truncating there would drop
text the user actually typed. It now converts in chunks and continues from where
each conversion stopped, which is what `toUtf8Counting`'s `units` exists for: the
terminal sees the same bytes, just in more than one callback.

New harness `test\win32\machine-chooser.ps1` (19 assertions) drives the real
chooser: typed three-byte characters past the old threshold, 300-character
ASCII and CJK pastes, and the filter still narrowing afterwards. Its B arm
deliberately does NOT type ASCII — `GetWindowTextW` caps that field at 255
units, so 255 ASCII bytes can never overflow a 256-byte destination, and an arm
typing 'a' was measured GREEN against the unfixed build.

## Goals

- [x] Typing or pasting any amount of text into the machine chooser's filter
      leaves the app running
- [x] Every fixed-buffer UTF-16 → UTF-8 reader in `src/apprt/win32/` either
      calls `utf16_text.toUtf8Truncating` or has a measured destination and says
      so in a comment
- [x] The stale "truncated to fit" / "0 when it does not fit" comments on the
      converted readers say what the code now does
