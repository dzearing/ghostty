# T1276 - A relay window whose agent dies goes terminally disconnected in seconds instead of climbing the reconnect ladder

## Summary

Observed while validating T609, which is what made it visible at all. Kill the
agent under a live RELAY window and, about three seconds later,
`+list --json` reports:

```json
"connection": { "state": "disconnected", "self_healable": false }
```

`self_healable: false` is the TERMINAL verdict — the fast ladder is not running,
no background re-dial is armed, and nothing will bring the window back. The
expected reading three seconds after a drop is
`{"state":"reconnecting","attempt":1}`, and the expected resting state after the
ladder is spent is `disconnected` with `self_healable: true`.

Evidence: `test\win32\ipc-relay.ps1` section 6, which prints the connection
object it read. Its assertion deliberately accepts either `reconnecting` or
`disconnected` — it exists to prove the FIELD tracks the link — so this harness
is green today and will stay green when this task is fixed.

## In plain terms

If the machine at the other end of a Ghoztty window restarts, the window is
supposed to quietly re-dial and pick your session back up. For a window opened
through the relay — which is how you reach a machine that is not on your
network, so the common case — it does not: within a couple of seconds it gives
up for good, and nothing short of closing the window and opening a new one
brings it back. This is the feature T366 built, not working on the path most
users are on.

## Details

The suspected cause, to be confirmed before fixing:
`RemoteReconnect.dialOnce`'s `.relay` arm turns `error.WebSocketUnauthorized`
into `dial = .unauthorized`, which is terminal on purpose — "a rejected bearer
is not an unreachable machine: retrying cannot sign anyone in, so the ladder
must stop instead of spending five attempts on a 401." That reasoning is right
for a genuinely rejected bearer. The question is whether a relay answers a dial
for a device whose agent is GONE with the same 401/403 it uses for a bad token.
If it does, an offline machine is being read as a bad credential and the two
must be told apart — an unreachable device is exactly what the ladder exists
for.

Second thing to check while in there: whether the ladder runs at all on the
relay path, or whether it stops even earlier. Three seconds is fast even for a
first dial plus a 401.

Do not weaken the `unauthorized` rule to fix this. A real 401 must still stop
the ladder; what needs to change is the classification of "device offline".

Confirm from the app log during a section-6 run (`remote reconnect: relay dial
device=… failed err=…` names the error the dial actually got).

## Validation criteria

- [ ] The app log names the error a relay dial gets when the far agent is dead,
      and it is distinguished from a rejected bearer
- [ ] Three seconds after the agent is killed under a relay window,
      `+list --json` reports `{"state":"reconnecting","attempt":N}`
- [ ] After the fast ladder is spent it reports `disconnected` with
      `self_healable: true`, and the 45s background re-dial is armed
- [ ] Restarting the agent brings the window back (the T368 walk)
- [ ] A genuinely rejected bearer STILL goes terminal in one attempt — the
      existing rule is not weakened. Demonstrated, not assumed
- [ ] `test\win32\ipc-relay.ps1` ALL PASS, with section 6 tightened from
      "left connected" to the specific expected state
- [ ] Floor lanes green
