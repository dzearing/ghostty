# T1104 - Ctrl+T from a viewer pane no longer opens a tab

## In plain terms

Pressing Ctrl+T should open a new tab, whichever pane you are in - including a document or web viewer. It does. What did not work was the test that watches it: on a busy machine the test let go of the Ctrl key before the app had a chance to read it, so a run under load reported a broken shortcut that nobody could reproduce by hand. The keyboard test rig now holds a modifier down until the app has actually caught up, the way a finger does.

## Summary

`test\win32\viewer-panes.ps1` scored `1 FAILURE(S) (185 passed)` in the T1094 sweep:

```
FAIL  T394 ctrl+t from a viewer added a tab
```

One red out of 186 assertions, so the viewer surface at large is healthy - this is a narrow, specific regression in keyboard routing from a focused viewer pane. T394 is the task that put the behaviour in, so the shape to look for is a viewer pane swallowing the accelerator, or the tab action resolving a target window from a pane that is not a terminal.

Worth checking whether other window-level chords have the same hole from a viewer - the script only measures Ctrl+T, so a pass here would not prove Ctrl+W, Ctrl+Shift+T and friends work.

## What was actually wrong

A viewer chord has TWO readers, in this order: Chromium classifies the key as
an accelerator from the modifier state, and only then raises
`AcceleratorKeyPressed` onto our UI thread, where the binding is matched. Each
reads the modifier state as it gets to it, and the second blocks the first.

With real hardware input that is safe. Modifier state travels with the message
stream: retrieving the ctrl-down message sets it, and the ctrl-up that clears
it is still behind the letter in the queue - so even a slow reader sees the
state that was in force when the key went down.

The harness does not use real input. `SendChordCross` pokes the state in out of
band with `SetKeyboardState`, and cleared it 400ms after posting the keys -
measured on a clock rather than on the app. Past that point the chord resolves
as a bare `t`, matches no binding, and opens nothing, which is exactly what one
242-script sweep saw and no quiet re-run ever did. The same shape in
`SendChord` (an 80ms hold) took `T161 CONTROL: ctrl+d from a terminal split
right` down beside it during this investigation, on a box loaded by nothing
more than the run itself.

So the product is fine and was not changed. `SendChord` and `SendChordCross`
now hold the faked modifiers until the app has demonstrably drained
(`PumpedTwice`: two consecutive answered `WM_NULL` pings, capped at 5s), then
release. A busy app makes the helper wait instead of making the assertion lie.

An app-side fix was tried first and reverted: resolving the modifiers from the
accelerator event stream instead of `GetKeyState`. It does not help, because
under the same starvation Chromium never raises the event at all - it reads the
same state to decide whether the key is an accelerator, and had already lost
it. Reading the app log for the starved chord shows `vk=0x11` arriving and no
`vk=0x54` behind it, which is what ruled the app out.

## The neighbour audit

Every modified chord any script sends at a viewer pane goes through
`Send-TestViewerChord` -> `SendChordCross`, and every modified chord sent at a
terminal goes through `Send-TestKeys` -> `SendChord`. The exposure was never
per-chord, so neither is the fix. What was measured after it:

- `viewer-panes.ps1` - ctrl+shift+p, ctrl+t, ctrl+w, ctrl+r, ctrl+d, ctrl+l,
  alt+d and the zoom chords from a focused viewer: ALL PASS (195).
- `viewer-window-chords.ps1` - the window-scoped actions (`reset_window_size`,
  `toggle_tab_overview`, `toggle_maximize`, and the two negative controls):
  ALL PASS (23). Bare F-keys, so it never had the exposure.
- `hero-nav.ps1` - ctrl+alt+up/down and ctrl+shift+space at a viewer tile:
  ALL PASS (40).
- `chooser-open-chord.ps1` - ctrl+shift+n at a viewer: ALL PASS (10).

A `forwards()` action with no test at all is a different gap, and it already
has a compile-time guard (`Window.viewer_dispatch_tags`). Nothing here is
missing a chord - only a delivery mechanism that could drop one.
