# T313 - Migrate the other five dialogs to type_ramp: Banner, Confirm, NewProcess, Rename, ActivityMonitor still carry their own font_h

## Summary

T310 introduced `src/apprt/win32/type_ramp.zig` (caption 12 / body 14 /
subtitle 20 semibold, from `win32-machine-chooser.md` §3.2) and pointed the
**Ctrl+Shift+N surface** at it — `chooser_layout.zig` and
`HostSettingsDialog.zig`. It deliberately stopped there, because T310's scope
was the surface T227 owns.

Five dialogs still write the ramp out themselves, all at the retired body size:

| File | Line at T310 | Value |
|---|---|---|
| `activity_layout.zig` | 360-362 | `font_h = px(15)`, `title_font_h = px(20)`, `caption_font_h = px(12)` |
| `BannerDialog.zig` | 96 | `font_h = px(15)` |
| `ConfirmDialog.zig` | 175 | `font_h = px(15)` |
| `NewProcessDialog.zig` | 206 | `font_h = px(15)` |
| `RenameDialog.zig` | 122 | `font_h = px(15)` |

So the chooser now reads at 14 and every other dialog at 15, which is a
DIFFERENT inconsistency from the one T310 removed — one the user can see by
opening two dialogs. Note `activity_layout` already has the ramp's SHAPE
(three roles, and its caption/title already agree with the ramp); only its body
size differs, so it is the cheapest of the five and the best first move.

## Details

- Point all five at `type_ramp`. `activity_layout`'s `title_font_h` /
  `caption_font_h` should come from the ramp too even though the numbers
  already match — a number that happens to agree is not a shared source, and
  the next ramp change is what proves it.
- Watch the knock-on: several of these dialogs derive control and line-box
  heights from `font_h` (e.g. `HostSettingsDialog`'s `item_h = l.font_h +
  px(6, scale)`), so a 1 px font change moves a control height. Assert the new
  numbers rather than letting them drift.
- Consider whether the `+ px(6)` line-box paddings should become the `sm` (4)
  leading the chooser now uses, so line boxes are one rule as well.

## What landed

- `type_ramp` gained `leading_dip` (4) and `lineBox(font, scale)` — the one
  rule for "a box that holds ONE line of this role". `chooser_layout` and
  `chooser_rows` had that arithmetic written out five times; they call it now.
- All five dialogs read `type_ramp.body` for `font_h`, and `activity_layout`
  reads all three roles plus the title WEIGHT (a new `title_font_weight` on its
  Layout, so `ActivityMonitor` no longer hardcodes a 600 beside a ramp size).
  Faces come from `type_ramp.face` everywhere those dialogs create a font.
- Line boxes that were flat constants now come from the ramp:
  `BannerDialog`'s label/hint (16 -> 18 at 1.0, which was 15+1 and would have
  clipped as soon as either number moved), `RenameDialog`'s label,
  `NewProcessDialog`'s and `HostSettingsDialog`'s label column (18 either way
  at every asserted scale — same number, now for a reason), and the Activity
  Monitor's card rows.
- **A bug T310 left behind**: `HostSettingsDialog` was migrated at the LAYOUT
  end only — `layoutFor` reported the ramp's 14 while `CreateFontW` still asked
  for 15, so the dialog measured itself against a size no text on it was drawn
  in. Both ends read the ramp now. A half-migrated dialog is worse than an
  unmigrated one, because its numbers look right.

**`HostSettingsDialog`'s `item_h = l.font_h + px(6)` was left at 6 on purpose.**
It is the combo box's ITEM height — an interactive, hit-testable row, not a text
line box — and the design system sizes a control to what it must hold rather
than to the text inside it (§0's corollary: size the band, don't squeeze the
control). The `lineBox` rule is for reserved TEXT boxes; conflating the two
would have shrunk a click target to justify a shared constant.

## In plain terms

Ghoztty's Windows dialogs did not agree on how big their text is. The machine
chooser had already moved to the shared size, so opening it next to the rename
box, the banner editor, a confirmation, or the Activity Monitor showed two
different-sized fonts in the same app. Now every one of them reads at the same
size, and the boxes those lines sit in grow and shrink with the font instead of
being fixed numbers that happened to fit.
