# T274 - Win32 chrome foregrounds are hardcoded light, so a light background gives sub-1.5:1 titlebar and tab text

## Summary

The win32 chrome computes its BACKGROUND from the user's config and then paints
FOREGROUNDS on it that are frozen constants chosen for a dark bar. The band
moves with `background`; the text and glyphs do not move with it at all.

Background, derived (`src/apprt/win32/Window.zig`):

- caption band `cap_*` = `config.background` + 20 per channel, clamped (:3221)
- tab strip `bar_*` = the same derivation (:3480), so the two rows match

Foregrounds, hardcoded:

| site | color | line |
|---|---|---|
| caption title text | `RGB(230,230,230)` | 3246 |
| caption button glyphs (min/max/close, non-hover) | `RGB(230,230,230)` | 3299 |
| active tab label | `RGB(230,230,230)` | 3497 |
| inactive tab label | `RGB(150,150,150)` | 3498 |
| tab close glyph (normal) | `RGB(150,150,150)` | 3501 |

With `background = ffffff` the band clamps to 255,255,255 and every one of them
lands far under the mandatory floors in `docs/design/win32-design-system.md`
(4.5:1 text, 3:1 chrome glyphs and meaningful boundaries):

| foreground | on a 255,255,255 band | floor | verdict |
|---|---|---|---|
| 230,230,230 (title, active tab, button glyphs) | **1.25:1** | 4.5 | unreadable |
| 150,150,150 (inactive tab, close glyph) | **2.96:1** | 4.5 text / 3.0 glyph | fails both |

A light `background` is an ordinary configuration, not a corner case, so the
user-visible symptom is a titlebar whose title and window buttons are all but
invisible and a tab strip whose labels are barely there.

## Evidence (measured on box 2026-08-01, debug build, test desktop)

`test/win32/test-desktop-harness.ps1` with `--background=ffffff` reads the
caption band at **meanLum 243** through `Get-TestWindowPixels` - i.e. the band
really is at/near 255 and the only thing pulling the mean down is the near-white
text sitting on it. The dark half (`--background=000000`) reads 24. The band
tracks `background`; the foregrounds in the table above are the same pixels in
both runs.

The contrast figures are WCAG 2.x relative-luminance ratios on those exact
sRGB values, not estimates.

## Fix

One resolver, not five edits. Add a pure module (e.g.
`src/apprt/win32/chrome_colors.zig`) that takes the resolved band color and
returns the whole foreground set - title, active label, inactive label, button
glyph, close glyph, and the hover/pressed shades - each **derived** to clear
its floor against that band, in the direction the band demands. `paintCaption`
and the strip painter both consume it, so the two rows cannot drift apart
(the same reason T254 reused `bar_*`'s derivation for `cap_*`).

Do not hand-pick a second pair of constants for "light bars". A constant that
is right for white and wrong for `#f5f0e8` is the same defect one shade over.
The inactive/active distinction must survive the derivation - it is a state
difference, and the design system says state is never color alone, so check
that the de-emphasised label still clears 4.5:1 rather than being allowed to
fail as "secondary".

Two existing pieces are worth reading first rather than re-deriving:

- **T150** did exactly this job for the terminal palette (contrast-aware
  remapping when the background changes) and its follow-up **T247** names two
  real bugs in that color math - a Rec.601 side-choice that put `#777777` on
  white at 4.42:1, and a one-sided L* search that returned still-failing
  colors. Do not port those in.
- **`icon_button.fillDelta`** already owns the hover/pressed shade direction
  and its SIGN is asserted (T233); the glyph color has to agree with it.

## Relationship to T273

T273 asks whether `window-theme` should drive the band at all. The two are
independent defects but they compound: any resolution of T273 that can put a
light band on screen makes these foregrounds unreadable there too. Land this
one first, or land them together.

## Validation

- Unit tests in the `-Dapp-runtime=none` lane over the resolver: for a spread
  of band colors (000000, 202020, 282c34, f5f0e8, ffffff, plus a saturated
  one), every returned foreground clears its floor, and active/inactive stay
  distinguishable. Floors asserted by computing the ratio, not by eyeballing
  constants.
- On-box: `test/win32/color-contrast.ps1` (or a new assertion there) captures
  the caption band and the tab labels at `--background=ffffff` AND at
  `--background=000000` and checks the measured ratio both ways. The
  light-background half is the one that fails today, so it is the negative
  control - confirm it FAILS against the current binary before the fix.
- `caption-bar.ps1`, `tab-strip.ps1`, `tab-color.ps1`, `menu-bar.ps1` stay
  ALL PASS (they read chrome pixels that this changes).

## Done by T305 (2026-08-01)

This task asked for "one resolver, not five edits": a pure module taking the
resolved band color and returning every chrome foreground DERIVED to clear its
floor, consumed by both `paintCaption` and the strip painter so the two rows
cannot drift. That module is `src/apprt/win32/chrome_theme.zig` (T304, the
derivation) and both painters consume it through `Window.chromePalette()`
(T305, the wiring). Every literal in the table above is gone.

The named failure case is measured, not argued. `test/win32/chrome-theme.ps1`
runs the caption band at `--background=ffffff`:

| | before | after |
|---|---|---|
| band | `255,255,255` (the `+ 20` clamp) | `#EBEBEB` = `wash(bg, 0.08)` |
| title | `RGB(230,230,230)`, **1.25:1** | derived, **14.89:1** |

Also scored at `#f3f3f3` (band `#e0e0e0`, title 13.71:1) and `#1e1e1e` (band
`#303030`, title 10.97:1), each against the value the app's own rule derives
rather than a pasted constant. The inactive tab label moved
`RGB(150,150,150)` -> `#A2A2A2` on the default dark bar as a side effect: 150
measured 4.4:1 there, i.e. it was under the text floor on the DARK theme too.

See T305 for the full evidence. Remaining hardcoded-dark surfaces are the
dialog panels, which are **T308** — not this task, which is specifically the
caption band and the tab strip.
