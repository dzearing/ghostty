# T449 - The Zig compiler itself crashes with access violations on this box - the corruption T443 is hunting is not confined to the ghoztty test binaries

## Summary

Filed out of **T444** on 2026-08-04, which set out to explain why a failing test
lane sometimes reports nothing but `exited with error code 5`. The answer is
that `5` is `0xC0000005 STATUS_ACCESS_VIOLATION` truncated to a byte, and the
process that took the access violation is **`zig.exe` itself** — the compiler,
not a ghoztty binary.

That is a first-class datum for **T443**, which has spent two whole contexts
looking for a corrupter inside code the `win32` and `agent` lanes share and the
`none` lane does not. The compiler shares none of that code. Whatever is
scribbling on memory here is not choosing its victims by module.

## In plain terms

The tests have been crashing at random for days, and the *compiler* had started
crashing too — a separate program with nothing to do with our code — which
looked like the machine itself might be faulty. Somebody had to check that
before another day went into hunting a bug in our own source.

**Answer: the machine is fine.** It was put through four minutes of work where
every answer is checked against a second calculation of the same thing, and it
got all 1.44 TB of it right. The compiler does have a bug, but it hits about
once in several hundred builds, while our tests crash on every single run — so
it cannot be the same thing. Our crash is ours, and it now has an actual address
to look at rather than a shrug.

## Goals

- [x] Establish whether this is a machine fault (memory / CPU / thermal), a

- [x] If it is the machine, say so with a measurement, not a hunch — and record

## THE VERDICT (2026-08-04)

**Keep bisecting our code. It is not the machine, and it is not a security
product. The compiler has a separate, much rarer bug of its own.**

The premise this task was filed on — "the compiler crashes too, therefore
whatever is scribbling on memory is not choosing its victims by module" — does
not survive measurement. Three things settle it:

**1. The two failure rates are nowhere near each other.** The ghoztty test
binaries fail **on demand** — three back-to-back `zig build test-agent` runs
this turn crashed **3/3**, and the 21-day Application-Error tally is 73 faults
across the three test exes. `zig.exe` faulted **8 times in the same 21 days**,
across weeks of near-continuous building, i.e. a rate somewhere in the
fractions of a percent per invocation. (An exact per-invocation rate is not
recoverable — nothing counts compiler launches — which is why the argument
rests on "every run" versus "8 in three weeks" rather than on a ratio.) A
machine-level corrupter that hits our test binaries every single time would not
leave the compiler almost entirely alone. And the 2026-08-03/04 cluster of
compiler crashes is explained by *exposure*: that was the night someone ran the
build in a tight loop dozens of times, not a night the box changed.

**2. The faulting offsets repeat, across separate processes and separate runs.**
This is the datum that ends the argument. Debug builds under ASLR report
module-relative offsets, so a repeated offset is a repeated *instruction*:

| binary | offset | seen |
|---|---|---|
| `ghoztty-agent-core-test.exe` | `+0x11a830` | probe runs 1 and 2, 2026-08-04 |
| `ghoztty-agent-test.exe` | `+0x1cb84e` | **four times** — 03:51:21, 03:57:50, probe run 1, and the floor run at this turn's boundary (05:23:41) |

Random corruption from failing hardware sprays; it does not land on the same
instruction three times. Something in our code faults at a specific, findable
place. **T443's first move should be to resolve those two offsets to source
lines** — that is a concrete lead neither previous attempt had.

**3. The machine computes correctly.** `scripts/hw-integrity-stress.ps1` ran 28
threads for 4 minutes doing SHA-256 plus an independent integer checksum over
freshly-allocated buffers, re-deriving and re-verifying each one:

```
RESULT iterations=23054 verified=1440.9GB mismatches=0
```

1.44 TB of self-verifying computation, zero disagreements. That does not prove
the box is perfect, but a machine corrupting memory badly enough to crash a
compiler eight times a week does not pass it clean.

### What each hypothesis was tested with

| hypothesis | test | outcome |
|---|---|---|
| Memory / CPU returning wrong answers | `hw-integrity-stress.ps1`, 1.44 TB verified | **eliminated** — 0 mismatches |
| Memory running above JEDEC (XMP/EXPO) | `Win32_PhysicalMemory` | 4×16 GB DDR5 at 4200 MT/s configured = **not** overclocked. Note two *different* Corsair kits are mixed (`CMT32GX5M2X6000C36` + `CMT32GX5M2B6400C32`), which is not ideal, but they are running at a conservative common speed |
| Unpatched Raptor Lake Vmin instability | microcode revision | i9-13900K on microcode **0x12F** — current; the Intel mitigations are applied |
| No hardware errors logged | WHEA-Logger | **the original "zero WHEA events" claim was wrong.** 6369 corrected errors in 30 days — but all 6369 are *corrected PCIe* errors on one root port, none memory or processor. Split to **T452** |
| A security product injecting into processes | `AppInit_DLLs`, registered AV, WER module list | **eliminated** — `LoadAppInit_DLLs=0`, Defender only, no third-party AV. (Nahimic audio services are present and are known injectors, but they target graphics apps and nothing places them in `zig.exe`) |
| Commit exhaustion → failed `VirtualAlloc` → null deref | `commit-pressure-probe.ps1` | **eliminated as a cause** — peak 49.4 GB of a 67.7 GB limit (73%). The margin is thinner than it should be; split to **T453** |
| A toolchain bug | fault offsets in `zig.exe` | **supported** — two of the eight faults are 48 KB apart in the same binary. Split to **T451** |

### What it means for results filed since 2026-08-01

Nothing filed against the test binaries needs retracting: those crashes are
reproducible on demand and land on repeating instructions. The one class that
does need care is a lane that fails with `compile test … failure` and no test
name — that is a `zig.exe` crash and is **not** a result about our code (T451
covers teaching the lane to say so and retry).

### Loose end this turn did not close

`scripts/zig-crash-repro.ps1` was written to replay the lane's exact ~10 KB
`zig test` command standalone against a non-ghoztty control. Both arms are
still failing for harness reasons — the control needs its working directory set
to the zig lib dir (std tests `@embedFile` test data by relative path), and the
ghoztty arm reports `zig test expects a zig source file argument` despite
carrying `-Mroot=`. Left to **T451**; it is the right vehicle for the
"try a second zig binary" experiment and is not on T443's critical path.

## Evidence

Three `zig.exe` access violations in two days, at three different fault offsets,
from the Windows Application log (`Application Error`, id 1000):

```
08/04 03:39:24  zig.exe  0xc0000005  module=unknown   +0x8669f77d80   (WER bucket type BEX64)
08/04 02:43:54  zig.exe  0xc0000005  module=zig.exe   +0x0230f248
08/04 01:18:58  zig.exe  0xc0000005  module=zig.exe   +0x037ddea2
```

The 02:43:54 one is inside the floor run T443/T444 were filed from; the 03:39:24
one is run 1 of the T444 repro loop. The `module=unknown` case is a jump to an
address in no loaded module at all — a wild control transfer, not a bad index.

Alongside them, the ghoztty test binaries abort the same way (`0x80000003`
STATUS_BREAKPOINT, i.e. Zig's own segfault handler firing):
`ghostty-test.exe` at 08/04 01:35:50 and 02:42:46, `ghoztty-agent-test.exe` at
08/04 03:51:21.

**The reproduction rate has gone up sharply.** Six consecutive
`zig build test-agent` runs on an unmodified tree on 2026-08-04 failed **6/6**
(T443 recorded roughly 4-in-6 on 2026-08-03), and once the build is cached a
failure lands in **16-58 s**, not minutes. Whatever this is, it is now cheap to
reproduce — which is the one piece of good news, and it is what makes a
controlled experiment affordable.

Two things NOT yet established, and they are the work:

- ~~**No hardware error is logged.** Zero WHEA events in 14 days.~~
  **WRONG — corrected 2026-08-04 by the verdict above.** There are **6369**
  WHEA events in 30 days. They were missed because id 17 is logged at
  *Warning* level, so a query filtered to Error level reports a clean log. All
  6369 turn out to be *corrected PCIe* errors on a single root port (split to
  **T452**), none of them memory or processor — so the conclusion that memory
  was not cleared still stood, but it stood for the wrong reason, and "zero
  WHEA events" was simply false. Memory was subsequently cleared by
  measurement instead (`hw-integrity-stress.ps1`, 1.44 TB, 0 mismatches), and
  the DIMMs are running at 4200 MT/s with no XMP/EXPO overclock.
- **There were video-stack faults at 08/04 01:35:49-50** — WER `BlueScreen`
  records `119` (VIDEO_SCHEDULER_INTERNAL_ERROR) and `3b`/`c000001d`, plus a
  `LiveKernelEvent 141` (display TDR) — coincident with a `ghostty-test.exe`
  crash. The system did not actually reboot (`Kernel-Power 41` last fired
  07/28 and 07/29), so these were recovered driver faults. Whether they are a
  cause, a symptom, or a coincidence with the WebView2 tests is unknown.

## Suggested approach (DONE — kept as the record of what was planned)

Every item below was carried out except the reboot-requiring memory test, which
was replaced by a userspace equivalent that needed no reboot and no downtime
(`hw-integrity-stress.ps1`). See the verdict at the top for outcomes.

Cheapest decisive experiments first, since the repro is now ~30 s:

1. **Run the box's memory test** (`mdsched.exe`, or MemTest86 for a real pass)
   and check whether memory is running above JEDEC speed in firmware. A machine
   fault would invalidate a lot of recent "flaky" attribution at once.
2. **Check for injected DLLs** in a crashed process — a security product's hook
   in `zig.exe` would be visible in the WER report's loaded-module list under
   `%LOCALAPPDATA%\CrashDumps` / `ReportArchive`.
3. **Try a different zig binary** (a second 0.15.2 extracted elsewhere, or a
   neighbouring version). If a different compiler binary crashes identically,
   the toolchain is exonerated.
4. Only then go back to bisecting ghoztty source.

Note `cdb` is still **not** installed on this box (only `dbghelp.dll` and
friends under `Windows Kits\10\Debuggers\x64`, no `cdb.exe`), so there is still
no just-in-time debugger — but the Application log now gives the faulting
module and offset for free, and `scripts/lib/CrashDiag.ps1` (T444) surfaces it
automatically on every red lane.

## A repeated fault site (2026-08-04, added at the T444 boundary)

The floor run at that turn's boundary crashed both suspect lanes and, because
the crash diagnostics were by then wired in, recorded where:

```
03:57:38  ghostty-test.exe             0x80000003  ghostty-test.exe+0x00000000000cc49e
03:57:49  ghoztty-agent-core-test.exe  0x80000003  (offset recorded in the lane log)
03:57:50  ghoztty-agent-test.exe       0x80000003  ghoztty-agent-test.exe+0x00000000001cb84e
```

`ghoztty-agent-test.exe+0x1cb84e` is the **same offset** that binary aborted at
in a separate run six minutes earlier (03:51:21). A repeated fault site is not
what pure environmental randomness predicts, and it is the cheapest lead here:
that offset can be resolved to a source line from the binary's PDB without any
debugger, which is more than either previous attempt had.

Note these are `0x80000003` (Zig's segfault handler aborting *after* printing
its own message) rather than the raw `0xC0000005` the compiler dies with — the
test binaries are Debug builds and catch the fault; `zig.exe` is ReleaseFast and
does not.
