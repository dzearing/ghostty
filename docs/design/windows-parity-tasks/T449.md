# T449 - The Zig compiler itself crashes with access violations on this box - the corruption T443 is hunting is not confined to the ghoztty test binaries

## Summary

Filed out of **T444** on 2026-08-04, which set out to explain why a failing test
lane sometimes reports nothing but `exited with error code 5`. The answer is
that `5` is `0xC0000005 STATUS_ACCESS_VIOLATION` truncated to a byte, and the
process that took the access violation is **`zig.exe` itself** — the compiler,
not a ghoztty binary.

That is a first-class datum for **T443**, which has spent two whole contexts
looking for a corrupter inside code the `win32` and `agent` lanes share and the
`none` lane does not. The compiler shares none of that code. Whatever is
scribbling on memory here is not choosing its victims by module.

## In plain terms

The tests have been crashing at random for days. It turns out the *compiler*
crashes at random too — a completely separate program that has nothing to do
with our code. That points away from a bug we wrote and toward something wrong
with the machine or its toolchain, and it is worth settling before anyone spends
another day bisecting our own source.

## Goals

- [ ] Establish whether this is a machine fault (memory / CPU / thermal), a
      security product injecting into processes, or a real toolchain bug
- [ ] If it is the machine, say so with a measurement, not a hunch — and record
      what it means for every "flaky test" result filed since 2026-08-01
- [ ] Give T443 a verdict it can act on: keep bisecting our code, or stop

## Evidence

Three `zig.exe` access violations in two days, at three different fault offsets,
from the Windows Application log (`Application Error`, id 1000):

```
08/04 03:39:24  zig.exe  0xc0000005  module=unknown   +0x8669f77d80   (WER bucket type BEX64)
08/04 02:43:54  zig.exe  0xc0000005  module=zig.exe   +0x0230f248
08/04 01:18:58  zig.exe  0xc0000005  module=zig.exe   +0x037ddea2
```

The 02:43:54 one is inside the floor run T443/T444 were filed from; the 03:39:24
one is run 1 of the T444 repro loop. The `module=unknown` case is a jump to an
address in no loaded module at all — a wild control transfer, not a bad index.

Alongside them, the ghoztty test binaries abort the same way (`0x80000003`
STATUS_BREAKPOINT, i.e. Zig's own segfault handler firing):
`ghostty-test.exe` at 08/04 01:35:50 and 02:42:46, `ghoztty-agent-test.exe` at
08/04 03:51:21.

**The reproduction rate has gone up sharply.** Six consecutive
`zig build test-agent` runs on an unmodified tree on 2026-08-04 failed **6/6**
(T443 recorded roughly 4-in-6 on 2026-08-03), and once the build is cached a
failure lands in **16-58 s**, not minutes. Whatever this is, it is now cheap to
reproduce — which is the one piece of good news, and it is what makes a
controlled experiment affordable.

Two things NOT yet established, and they are the work:

- **No hardware error is logged.** Zero WHEA events in 14 days. That does not
  clear the memory — a marginal DIMM or an unstable memory overclock (XMP/EXPO)
  corrupts silently and is the textbook cause of "the compiler crashes in a
  different place every time". It only means the CPU's own error reporting has
  not fired.
- **There were video-stack faults at 08/04 01:35:49-50** — WER `BlueScreen`
  records `119` (VIDEO_SCHEDULER_INTERNAL_ERROR) and `3b`/`c000001d`, plus a
  `LiveKernelEvent 141` (display TDR) — coincident with a `ghostty-test.exe`
  crash. The system did not actually reboot (`Kernel-Power 41` last fired
  07/28 and 07/29), so these were recovered driver faults. Whether they are a
  cause, a symptom, or a coincidence with the WebView2 tests is unknown.

## Suggested approach

Cheapest decisive experiments first, since the repro is now ~30 s:

1. **Run the box's memory test** (`mdsched.exe`, or MemTest86 for a real pass)
   and check whether memory is running above JEDEC speed in firmware. A machine
   fault would invalidate a lot of recent "flaky" attribution at once.
2. **Check for injected DLLs** in a crashed process — a security product's hook
   in `zig.exe` would be visible in the WER report's loaded-module list under
   `%LOCALAPPDATA%\CrashDumps` / `ReportArchive`.
3. **Try a different zig binary** (a second 0.15.2 extracted elsewhere, or a
   neighbouring version). If a different compiler binary crashes identically,
   the toolchain is exonerated.
4. Only then go back to bisecting ghoztty source.

Note `cdb` is still **not** installed on this box (only `dbghelp.dll` and
friends under `Windows Kits\10\Debuggers\x64`, no `cdb.exe`), so there is still
no just-in-time debugger — but the Application log now gives the faulting
module and offset for free, and `scripts/lib/CrashDiag.ps1` (T444) surfaces it
automatically on every red lane.

## Validation

- A named cause, backed by a measurement — not "it stopped reproducing".
- T443 updated with the verdict either way.

## A repeated fault site (2026-08-04, added at the T444 boundary)

The floor run at that turn's boundary crashed both suspect lanes and, because
the crash diagnostics were by then wired in, recorded where:

```
03:57:38  ghostty-test.exe             0x80000003  ghostty-test.exe+0x00000000000cc49e
03:57:49  ghoztty-agent-core-test.exe  0x80000003  (offset recorded in the lane log)
03:57:50  ghoztty-agent-test.exe       0x80000003  ghoztty-agent-test.exe+0x00000000001cb84e
```

`ghoztty-agent-test.exe+0x1cb84e` is the **same offset** that binary aborted at
in a separate run six minutes earlier (03:51:21). A repeated fault site is not
what pure environmental randomness predicts, and it is the cheapest lead here:
that offset can be resolved to a source line from the binary's PDB without any
debugger, which is more than either previous attempt had.

Note these are `0x80000003` (Zig's segfault handler aborting *after* printing
its own message) rather than the raw `0xC0000005` the compiler dies with — the
test binaries are Debug builds and catch the fault; `zig.exe` is ReleaseFast and
does not.
