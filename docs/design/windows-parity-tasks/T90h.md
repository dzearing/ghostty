## Re-scoped 2026-07-29 (T127)

Unchanged, except that the manifest reserves FOUR additive per-leaf fields
instead of two (`docs/design/viewer-panes-windows.md` P12): `kind`,
`viewer_location`, `viewer_home_location`, `viewer_origin_directory`. The
current Mac viewer persists the HOME location (where the pane was OPENED,
distinct from where it has navigated to -- the home button's target) and the
ORIGIN directory (`viewerOriginDirectory`, the worktree-provenance fallback).
Absent `kind` still means terminal, so old manifests keep loading.

Explicitly NOT restored: TOC panel open/closed state (Mac parity -- restoring an
overlay would hide the content it covers). The TOC card WIDTH is a preference,
not layout, and lives outside the manifest (T160).

## Done 2026-08-02

All four P12 fields land, and the restore walk grew its viewer arms.

**Schema** (`session_layout.zig`). `Leaf` gains `viewer_home_location` and
`viewer_origin_directory` beside the two T90a already reserved, plus one reader
-- `Leaf.isViewer()` -- so "absent `kind` means terminal" is stated ONCE instead
of at every restore site. An unrecognized future `kind` reads as a terminal, not
as a viewer, which is the additive-evolution rule applied to the tag itself: the
opposite default would have a newer manifest's third leaf kind try to navigate a
null location.

**Why two of the four cannot be recomputed**, which is the whole argument for
persisting them: `viewer_home_location` diverges from `viewer_location` the
moment the pane navigates, and restore points the pane at the LOCATION -- so
without the recorded home, Home quietly starts meaning "wherever you last were".
`viewer_origin_directory` is the provenance fallback for a pane whose location
names no directory at all (a website, `about:blank`); there is nothing to derive
it from later. The shared CLI already seeds it: `+new-window` inserts the
caller's cwd unconditionally and `cli/split.zig:seedViewWorkingDirectory` does
it for `--view=` splits, so `--working-directory` arrives on the win32 IPC path
as the origin, not as a cwd for a shell that does not exist.

**The restore walk.** `restoreBuildSubtree`'s anchor is now a `*PaneView`, not a
`*Surface` -- the narrowing was the actual blocker, since a tab whose first pane
is a viewer failed the WHOLE window on a null. Three sites branch on kind: the
window root (`createWindow(.viewer_open)`), an extra tab (`addViewerTab`), and a
split whose new pane is a viewer (`newViewerSplitAt`). `Window.replaceTabRoot`
(was `replaceTabRootSurface`) takes a `RootSpec` union for the same reason, so
T145's in-place recovery rebuilds the kind it recorded instead of turning every
tab into a terminal.

**Never-all-dead**: a viewer leaf returns attachable unconditionally. It owns no
session, so nothing about it can be "gone from the roster" -- that is what lets
an all-viewer window come back at all, and what stops a mixed tree from being
dropped when every terminal in it died.

`ViewerPane.Open` is the one struct all three open paths take (location + the
two restore-only overrides), and `applyOpenMetadata` runs AFTER `navigate` on
purpose: navigation seeds home from the location, and the recorded home has to
land on top of that seed rather than under it. A viewer leaf's TITLE is
deliberately not captured -- a viewer derives its name from its location, so a
recorded one could only go stale.

*Validation:* new `test/win32/viewer-restore.ps1`, ALL PASS (38), hermetic and
on the background desktop. **Proven discovered by two mutations**, because one
could not cover it: reinstating the `*Surface` narrowing in `restoreTab` turned
D1/I1-I3 red (the mixed window restored 1 pane of 3), and disabling the window
root's viewer arm turned D2/E1/G1/G2 red (`terminal,terminal,viewer`, and the
viewer-only window came back as a terminal). The first mutation alone left
F1/G1/G2 green *by accident* -- `createWindow` had already built the viewer tab
before `restoreTab` failed, so a one-pane window looked complete -- which is
exactly why the second run exists. `-NegativeControl` inverts H1 and fails, so
the re-ATTACH control is real too.

Also green: `viewer-panes.ps1` ALL PASS (111) x3, P1-P3 ALL PASS, both test
lanes, `test-agent`. New units in the none/win32 lanes cover the schema
round-trip, the pre-viewer manifest, the unknown-kind degrade, and the
home-override ordering.
