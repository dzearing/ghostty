# T527 - GUI dies silently mid-acceptance-run (no panic, log ends after an IPC action) - seen twice on 2026-08-06

## In plain terms

During automated testing the terminal app occasionally just vanishes — no
crash message, no error in its log, the log simply stops. When that happens
mid-test, dozens of later checks fail for the wrong reason. If it can happen
during tests it can presumably happen to a real user, silently taking their
windows with it.

## Summary

Twice on 2026-08-06, during T388 validation runs on the background test
desktop, the Debug `zig-out\bin\ghoztty.exe` process died with no panic
output and no crash-looking tail in its stderr log:

1. A full `viewer-panes.ps1` run (the git-HEAD copy, run as
   `test\win32\vp-head-tmp.ps1`): 26 asserts failed because the app was gone
   from roughly section 6/7 onward ("+reload requires a running Ghoztty
   instance", "GUI process alive after all scenarios" FAIL). The stderr log's
   last line was `info(win32_ipc): IPC: received action 'read'` — mid-run,
   then nothing: no `panic`, no `error:`, no unreachable, just end of file.
2. A minimal repro script: `SETUP FAIL: GUI died` ~3s after launch; the
   stderr log again ended mid-normal-operation (renderer resize messages).

Both runs were on a build that carried a temporary extra `log.info` in
`performDeferredFocus`; ~8 other GUI launches the same day (same build and
the clean one) ran fine, including three full `viewer-panes.ps1` runs. So
this is a low-rate intermittent, not tied to one script.

## Details

- No Windows Error Reporting correlation was checked at the time — the next
  occurrence should be cross-checked against the Application Error event log
  (`scripts/lib/CrashDiag.ps1` knows how), and ideally caught under cdb
  (`scripts/lib/CrashCatch.ps1` has the recipe, though the current harness
  targets test binaries, not the GUI).
- A silent death with no panic smells like an access violation on a
  non-main thread whose Zig segfault handler died recursively (the T450
  story), or a hard `ExitProcess` from a dependency (WebView2?).
- First actionable step: make the next occurrence self-diagnosing — enable
  WER LocalDumps for ghoztty.exe (needs elevation) or teach the acceptance
  launch path (`test\win32\lib\TestDesktop.ps1` Start-OnTestDesktop) to
  optionally run the GUI under cdb behind an env var, so the NEXT silent
  death leaves a minidump instead of a mystery.

## Validation criteria

- [ ] A capture mechanism exists such that the next silent GUI death during
      an acceptance run leaves a dump or a stack (verified by intentionally
      crashing a test build through the same path)
- [ ] Either the root cause is found and fixed, or after 2 weeks of runs with
      capture armed and no recurrence, this is downgraded/closed with that
      evidence recorded
