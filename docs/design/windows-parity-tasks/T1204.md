# T1204 - Installing over a running Ghoztty has no graceful path

## In plain terms

You run the installer while Ghoztty is open. It says it is configuring
something, then the window disappears and nothing else happens. You are not
told what went wrong, whether it installed, or what to do next.

## Goals

- [x] An installer can close the running terminal and get it back up by itself.
- [x] A per-user install never demands a reboot, and cannot inherit the
      machine's unrelated pending-reboot state as its own.
- [x] Both halves are measured rather than asserted - the app half live, the
      package half read back out of the compiled MSI.
- [ ] Nothing on the install path fails silently (the remainder: T1206, T1207,
      T1208, T1209).

## What actually happened (2026-08-31)

Two separate defects, and the user's report is the sum of both.

**1. A collided transaction dies silently.** The event log and
`%TEMP%\MSIe9cb7.LOG` record:

```
Error 1500. Another installation is in progress. You must complete that
installation before continuing this one.
Product: Ghoztty -- Installation failed.
Installation success or error status: 1602.
```

`msiexec /i Ghoztty-1.35.0-x64.msi` (pid 23680) was started at 06:52:35 and was
STILL RUNNING at 07:05. A second launch at 06:52:40 collided with it, reported
1500, and vanished. The likely sequence is the SmartScreen wall (T1203): the
first double-click starts an msiexec that then sits at a dialog, the user
double-clicks again, and the second one dies. Whatever the trigger, the user
saw only the disappearance.

**2. There is no Restart Manager handling at all.** `build-msi.sh` contains no
`RestartManager`, no `FilesInUse` / `MsiRMFilesInUse` dialog, no
`CloseApplication`. So even with no collision, installing over a running
Ghoztty has no defined behaviour: the running `ghoztty.exe`, `ghoztty.com` and
`ghoztty-agent.exe` are locked, and Windows Installer is left to either
schedule a reboot-replace or fail. Nothing asks the user to close the app, and
nothing offers to restart it afterwards.

**3. It demanded a reboot it did not need.** The user was told to restart the
PC. Checked at the time: `PendingFileRenameOperations` contained **no**
Ghoztty entries, and the on-disk build was already `1.35.0+890207079` - the
file replacement had completed. The `RebootRequired` (Windows Update) and
`RebootPending` (Component Based Servicing) flags were both set from something
unrelated, and Windows Installer echoed them as its own requirement. Three
processes were still holding the install directory: the stale `ghoztty.exe`
from the previous day plus two `ghoztty-agent.exe`. Closing those is the real
remedy; a reboot was never one. A per-user terminal must never ask for a
reboot - and it must not inherit an unrelated pending-reboot flag and present
it as its own.

## What it should do (the user's own framing)

> "shouldn't it handle that gracefully? ... I expected it to say something
> like... restart ghoztty ui layer? possibly restart the agent if its
> incompatible but show that dialog like mac installs? not just die"

- Detect that Ghoztty is running and **say so**, with the standard Files In Use
  dialog naming Ghoztty - not a silent stall.
- Offer to **close and restart it automatically** (Restart Manager's whole
  purpose), so an upgrade over a running app is a normal, expected operation.
- Never require a reboot for a per-user install.
- If a transaction is already in progress, say **that**, in words, instead of
  disappearing.
- Pair with T1178: the in-app updater installs over a running app **by
  definition**, so this is that path's precondition, not an edge case.

## Validation criteria

- [x] The app is a Restart Manager participant: Windows reports it registered
      for restart, it agrees to an installer's close, and it EXITS for one -
      which is what turns a locked file into a normal upgrade. Verified live in
      `test\win32\install-restart.ps1` sections L (L1-L5) against the debug
      build, with L7 as the control that a cancelled session end and a logoff
      leave it running.
- [x] It is registered for an UPDATE restart specifically - Windows reports
      flags=11, i.e. no `RESTART_NO_PATCH`, which is the bit that would defeat
      the whole registration (L2/L3).
- [x] The package never asks for a reboot: `REBOOT=ReallySuppress`, read back
      out of the compiled MSI's Property table by `build-msi.sh` so a wixl that
      drops it fails the build. Section E feeds that verifier five broken
      tables and watches it reject each (E2-E5), with E1 as the control.
- [x] Disabling the Restart Manager is refused rather than merely avoided:
      `MSIRESTARTMANAGERCONTROL=Disable` and a non-zero `MSIDISABLERMRESTART`
      both fail the build (E4/E5).
- [x] An acceptance script in `test/win32/` drives the case and fails if the
      app does not exit: `install-restart.ps1`, ALL PASS (26 assertions), with
      L5 watched going RED against a build whose exit was removed.
- [ ] Files In Use / "we are closing your terminal" is SAID, not just done ->
      **T1208**.
- [ ] The agent and its PTY holders survive the upgrade -> **T1207**.
- [ ] A collided transaction produces a visible message -> **T1206**.
- [ ] The in-app update path (T1178) is proven over the same route -> **T1209**.
