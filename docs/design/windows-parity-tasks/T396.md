# T396 - Viewer panes: command palette entries - Open File in Pane, Open URL in Pane, Open Browser Pane

## Summary

Split out of T90g (2026-08-02). Mac's palette carries three viewer entries
(`TerminalCommandPalette.swift:195-219` → `ViewerCommands.swift`); win32's
`commands.zig` registry has none, so there is no interactive way to open a
viewer pane at all — only the CLI.

## Details

The three, verbatim from Mac:

- **"Viewer: Open File in Pane…"** — `NSOpenPanel` sheet → viewer split
  right. Win32: `IFileOpenDialog` (or `GetOpenFileNameW`), non-blocking
  enough that the IPC pump keeps running.
- **"Viewer: Open URL in Pane…"** — a one-field prompt; a bare host is
  completed to `https://`. Win32 already has a one-field dialog pattern
  (`RenameDialog.zig`).
- **"Viewer: Open Browser Pane"** — `--view=about:blank` (P11). Its "caret
  already in the address field" half needs T159's address bar and lands
  with it; the entry itself does not wait for that.

Registry mechanics: each needs a new `commands.Id`, a `Kind` (they are
apprt-local like `.remote`/`.activity` — there is no binding action), and a
decision in `menu_bar.omitted` or a real menu row, or the static
exhaustiveness test fails. Mac puts them in the palette only.

The split itself goes through `Window.newViewerSplitAt` (already exists,
T374). Mac seeds the blank pane's `originDirectory` from the pane it split
from (`ViewerCommands.swift:35-38`) — keep that pin for T164; the field
itself is P12/T90h.

*Validation:* `test/win32/viewer-panes.ps1` grown — the palette lists all
three entries; "Open Browser Pane" produces a `+list --json` leaf with
`"type": "viewer"` and an `about:blank` url. Pure half: the bare-host →
`https://` completion is unit-tested in the none lane.
