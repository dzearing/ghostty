# T437 - The agent lane is now fast and flaky: two timing-sensitive tests fail intermittently under load

## In plain terms

One of the four automated check suites now finishes in about two and a half
minutes instead of seven — but it fails at random roughly a third of the time,
and never on the same check twice. Nothing is actually broken; the checks are
racing a stopwatch and sometimes lose. Until that is fixed, a red result from
this suite means "run it again", which is nearly as useless as the freeze it
replaced.

## Goals

- [x] `-Repeat 10` on the agent lane is 10 x PASS (2026-08-05, isolated
      worktree at `892c3ab44`: `FLOOR SUMMARY: agent#1..#10 = PASS`, run 1
      331s cold build, runs 2-10 at 149-155s)
- [x] Each of the two known flakes waits on a condition, not on a spin count
      or a wall-clock guess (landed via T346 `099bd6b5c` + T258 `23d13c7f8`,
      2026-08-05 — see Resolution below)

## Summary

T430 removed a ~173s fully-blocked wait from the agent lane (a Chromium
preconnect the viewer test server was reading from). The lane went from **430s
to ~150s** — and started failing intermittently, on a *different* test each
time. Measured 2026-08-03, same source, six consecutive runs:

| run | result | failing test |
|-----|--------|--------------|
| 1 | FAIL | `remote.agent.server."child exit emits EXIT after final DATA; reattach -> dead+exit_code; CLOSE frees"` |
| 2 | FAIL | `remote.agent.keepalive."keepalive: live link keeps getting pinged and is never closed"` |
| 3 | PASS | |
| 4 | PASS | |
| 5 | PASS | |
| 6 | PASS | |

Neither test is near anything T430 changed. The likeliest mechanism is that the
lane is now **denser**: `test-agent` runs two test binaries concurrently
(T434 — and they contain the *same* tests), so removing three minutes of idle
wait means more real work overlapping, and timing-sensitive tests that used to
have the box to themselves no longer do.

## The two flakes

1. **server.zig CLOSE spin.** The test spins up to 10,000 times waiting for the
   session to leave the table, then asserts. Under load it can exhaust the spin
   budget. It also currently reports as a mutex deadlock rather than as itself —
   that half is **T436**.
2. **keepalive live-link ping.** `remote.agent.keepalive."keepalive: live link
   keeps getting pinged and is never closed"`. Not investigated.

## Where to look

Prefer waiting on a **condition with a deadline** over a spin count: a spin
budget is a wall-clock guess wearing a different hat, and it gets tighter every
time the box gets busier. When a wait does time out it should say what it was
waiting for and for how long.

Fixing T434 first may make this disappear on its own — half the concurrent load
is a duplicate test run.

## Validation

`powershell -NoProfile -File scripts\floor-lane.ps1 -Lane agent -Repeat 10`
-> 10 x PASS. A lane that only usually returns green is not green.

## Resolution (2026-08-05)

Both named flakes were root-caused and fixed by two sibling tasks that landed
the same day, each with its own commit:

- **T346 (`099bd6b5c`)** — the actual fix for both flake sites. All 11
  yield-spin waiters in `server.zig`'s tests (including the CLOSE spin in
  "child exit emits EXIT …") were replaced with `waitUntil(pred, args)` from
  the new `src/remote/agent/test_util.zig`: a 10s **wall-clock deadline** with
  a 1ms poll, not an iteration count — a loaded box cannot burn it. The
  keepalive live-link test's 25ms staleness window (which measured the test
  thread's own scheduling latency, not link health) went to 60s, and its fixed
  120ms sleep became `waitUntil(pings >= 3)`. That satisfies this task's
  "condition, not spin count or wall-clock guess" goal at both sites.
- **T258 (`23d13c7f8`)** — bounded the other face of the same root cause: a
  wait for bytes that never arrive now fails red after a 30s liveness deadline
  (`error.LoopbackReadTimeout` naming the waiting test) instead of wedging the
  lane.

What this task then contributed: the independent **10× repeat validation** of
the combined result (below), plus a re-survey of T436's lock-held-assert
sites — T346's rewrite incidentally converted 3 of its 11 sites to scoped
`defer` blocks; the remaining 8 are recorded in T436 with fresh line numbers.

The `waitUntil` deadline is a liveness bound, not a performance assertion: it
only fires when the awaited effect never happens, and the authoritative
assertion stays after the wait so a real failure reports as itself (the
report-as-deadlock half remains T436's).
