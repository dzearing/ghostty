# T311 - T227b: account row identity - avatar/monogram and Sign Out as a link (findings 5,6)

## Summary

Second of three splits of **T227**. `docs/design/win32-machine-chooser.md` §4
findings **5** and **6**, both on the chooser's account row
(`chooser_layout.zig:107-111`, `RelayAccountRow.zig`):

- **5 - no avatar and no monogram.** Windows draws a static text plus a
  150 DIP button. Mac (§2.4) draws the email and a link over a **34 px
  accent-gradient monogram circle**. The circle is the only identity cue on the
  surface and it is simply absent.
- **6 - "Sign Out" is a button where Mac has a link**, and the two captions
  ("Sign in with Google..." / "Sign Out") share one fixed 150 DIP slot, so the
  button is sized for the longer caption in both states - the same
  fixed-slot-vs-content defect T235 fixed on the tab strip.

Both are painting + layout on one row, which is why they are one task and not
part of T310's arithmetic pass.

## Details

- The monogram takes its fill from the resolved accent (`chrome_theme.accentOn`
  against the account row's surface) and its glyph from
  `color_math.contrastForeground` - never a hand-picked pair. The gradient is
  the Mac cue; on win32 a two-stop `GradientFill` or a flat accent are both
  acceptable, but state which and why in the task file.
- The account row's slot must size to its caption like the action row already
  does (`chooser_layout.actionRow` is the precedent: the caller measures, the
  module packs), so the Sign In and Sign Out states stop sharing one width.
- Consume T310's type ramp for the email (caption) and the link (body).

## Validation

- `chooser_layout` unit tests at 1.0/1.25/1.5/2.0: the monogram circle, the
  email/link stack and the right-aligned control all nest in the account band,
  and the slot width follows the measured caption.
- `test/win32/ipc-machine-chooser.ps1`: the monogram is present and its fill
  tracks a PINNED accent (T305's lesson - an oracle for a system-derived pixel
  must state its input and restore it in a `finally`).
- `-NegativeControl` fails a load-bearing pixel claim.
- Floor: both `zig build test` lanes, `test-agent`, P1-P3.

## What shipped (2026-08-01)

The account row is now a **composition**, not a slot. `chooser_layout` stopped
naming one status rect and one button rect - the pair that could only ever
describe the signed-OUT state - and gained `AccountBand` + `accountRow(l, state,
text)`, the same packer shape T177 gave the detail pane's action row.

- **`chooser_layout.zig`.** `Layout.account_status` / `account_btn` are gone,
  replaced by `Layout.account: AccountBand` (band, gap, `avatar_d`, the two line
  boxes, the stack gap, the 240 email cap) and `accountRow`, which returns
  `{text, avatar?, link?, button?}` per `AccountState`. Also `Layout.control_h`,
  so "the surface's one control height" is a field rather than a thing you read
  off `cancel`.
- **The band is sized to its tallest content, not to a control** (design system
  §2.3): `max(avatar_d, email_h + 2 + link_h, control_h)` = **36 DIP**, up from
  28. That is the whole reason the row could not hold Mac's two-line stack
  before. The dialog did NOT grow - it is Mac's fixed 840x540 - so the 8 DIP came
  out of the body, and the list sheds it in whole rows the way the wrapping
  status strip already did.
- **`avatar_d` is 32, not Mac's 34.** 34 is off the 4 DIP scale; 32 is
  `SM_CXICON`, which is the rule the detail pane's mark already follows - so the
  two identity marks on the surface are one size instead of two nearby ones.
- **The monogram fill is FLAT accent, not a gradient** (`chrome_theme.accentOn`
  against the dialog surface, letter in `color_math.contrastForeground`). Stated
  because the task asked for the decision: the letter's contrast floor is
  computed against ONE color, and a gradient makes that floor a function of
  position - legible at one end of the disc and not necessarily at the other -
  for a cue (this is an identity mark, not a button) the shape already carries.
- **The letter is `type_ramp.bodyStrong`, not a new size.** Mac's `size * 0.42`
  of a 34 circle is 14.3 - which IS the ramp's body. So the mark lands on Mac's
  number while the ramp stays 12/14/20 (T310's whole point).
- **"Sign Out" is a LINK, and it is a second control.** `BS_OWNERDRAW` so it
  keeps the tab stop, the focus and `BN_CLICKED` that a clickable STATIC would
  throw away, with only the paint ours: accent text, no border, no underline at
  rest; underlined on hover/press; the system focus rect when focused, so no
  state is signalled by color alone. Hover comes from `WM_SETCURSOR` (which the
  child forwards to the dialog) rather than a subclass - the message already
  names the window under the pointer, so enter and leave are one test, and the
  hand cursor is set where it is already known.
- **Two controls, one live.** The signed-out state keeps a REAL themed button -
  an owner-drawn one would have been the only hand-painted button on a surface
  of themed ones, which is the inconsistency the design system calls a defect.
  `accountControl()` is the single answer to "the thing the user can press", so
  the focus cycle, the Enter handler and the click routing cannot disagree; the
  Tab walk's existing skip-the-hidden loop needed no change.
- **Finding 6 measured**: at this box's 1.25 the sign-in button is **198 px**
  against the retired slot's 188, and the link is **70** - three numbers where
  there used to be one.

## Evidence (2026-08-01, on the box)

`test/win32/ipc-machine-chooser.ps1` **ALL PASS, 65 assertions** (was 50), with a
new third run that seeds a DPAPI account store so the signed-IN composition is
reachable at all - neither existing run could reach it (run 1 has a credential
via `GHOSTTY_RELAY_TOKEN` but no account, so both were signed out at the ACCOUNT
tier). New assertions:

```
PASS the account button is sized to its caption, not the retired 150 DIP slot (width=198, retired=188)
PASS the account row carries both controls (found 2)
PASS exactly one account control is visible at a time (visible: 1)
PASS signed in, the account control reads 'Sign Out'
PASS the link is sized to ITS caption, not to a slot shared with sign-in (link=70, button=198)
PASS the link is not padded like a button (width=70, button floor=120)
PASS the account row shows the signed-in email (got 'monogram@example.com')
PASS the email and the link share a right edge (email=1271, link=1271)
PASS the email sits ABOVE the link, as a stack
PASS the monogram disc is filled with the pinned accent (rgb 61,142,248, want 61,142,248)
PASS the monogram draws its letter (153 non-fill pixels inside the disc)
```

`-NegativeControl` fails **exactly 2** - the detail-pane signature and the
monogram fill, each reached and each inverted. The monogram probe is
discriminating by construction rather than by inversion: it asserts the disc is
the PINNED accent, so a flat-black mid-paint capture, an absent avatar (the
dialog surface) and a wrong fill all fail it.

`test/win32/relay-account.ps1` **ALL PASS** - the sign-in -> sign-out round trip
still works IN PLACE through the recomposed row (`button flipped to 'Sign Out'`,
`status shows the signed-in email`, `status back to 'Not signed in'`), including
the busy state's focus hand-off, which now has to cover a control being HIDDEN as
well as disabled.

Its lookup needed one fix that is really a general rule: `Get-ChooserControls`
now filters on `Visible`. It identified the account control as "the topmost
BUTTON", which was sound while the row had one - with two, the hidden one is
still the topmost, so the signed-in run would have read the SIGNED-OUT caption
and reported a working flip as broken. **A control that is hidden is not on the
row.**

## Still open

  the doc does not record either way.
