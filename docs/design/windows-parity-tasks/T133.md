# T133 — Make the /reset-context composer-wipe fix durable

## Summary

**Make the `/reset-context` composer-wipe fix durable** (same class as T130, different plugin — `dzearing-skills`, not `ghoztty`). 2026-07-28 the reset failed a second way: the helper typed `/clear` correctly (`rc=0` in `/tmp/reset-context-last.log`) but two stray characters were already in the composer, so the submit sent **`nn/clear` as an ordinary message** — no clear, context kept growing, loop stalled again. This is the loop's own continuation mechanism failing twice in one session (see T132 for the first), so it is worth hardening rather than retrying. Fixed in the ACTIVE cache (`~/.claude/plugins/cache/dzearing-claude-marketplace/dzearing-skills/0.10.2/skills/reset-context/scripts/reset-context.sh`): send `C-u --when-idle` to kill the input line before typing `/clear`. Like T130, a plugin update silently reverts it — mirror into the `dzearing-skills` source repo + bump. While there, consider having the helper VERIFY the clear landed (read the pane and check the banner/greeting) and log LOUDLY if not, the same lesson T132 applied to the upgrade script: a continuation that silently no-ops is what makes these cost hours

## Resolution (2026-07-30)

Mirrored, hardened, and pushed: **`dzearing/dzearing-claude-marketplace`
`2ef7766`, dzearing-skills 0.10.2 → 0.11.0.** The source repo turned out to be
on this box already (`D:\git\dzearing-claude-marketplace` — the marketplace is
registered as a *directory* source, so `/plugin update` reads from that clone).

**The drift was exactly one hunk, and it was the load-bearing one.** The cached
0.10.2 helper carried the `C-u` composer wipe; source did not — 11 lines, the
whole difference between a reset that works and the 2026-07-28 stall. Nothing
else in the plugin had drifted (`diff -rq` over `skills/`, `hooks/`,
`scripts/`: identical), so this was the single cache-only fix, now source of
truth. Applied with the Edit tool rather than a rewrite, because the file's
`sed 's/\\/\\\\/g'` is the thing SKILL.md warns must never be retyped.

**Verification added (the "while there" half), designed around one rule: never
trade loop liveness for cleanliness.**

- After the two submits, the helper reads the pane back. Still-visible
  `/clear` ⇒ the command was taken as ordinary text (or never accepted).
- After the continuation, it checks the first 24 characters of the sent text
  are on screen — a session that clears and then eats its prompt is the same
  stall with a tidier context (the T132 class).
- Either failure calls `fail_loud`: a `!!! RESET-CONTEXT FAILED` block plus the
  **pane tail as evidence** into `/tmp/reset-context-last.log`, AND a pane
  **banner** telling the user what broke and how to recover by hand. The banner
  is the right channel precisely because it needs nothing but `ghoztty` itself
  (T130's no-jq announce made the same call), and the next prompt in that pane
  overwrites it, so a false alarm self-clears.
- The continuation is sent **whether or not** the clear verified. An uncleared
  context merely gets big; a missing continuation stops the loop dead.

**Validation: new `test/win32/reset-context.ps1`, ALL PASS (24) ×3** (and ×3
more before a flake-hardening edit; see below). The oracle is a pane running a
readline-based **composer model** — `read -r -e` so `C-u` is really
unix-line-discard as it is in Claude Code, clearing screen *and* scrollback on
the EXACT line `/clear` and echoing anything else as `RC-TEXT[…]`. That is the
distinction the defect fell through, so the harness can tell "ran the command"
from "sent a message" the way the real composer does.

- **A** (fixed helper, `nn` pre-typed): the pane runs the bare `/clear`
  (`RC-CLEARED`), no `RC-TEXT[nn/clear]`, the log records both verifications,
  and **no banner is set** — the happy path stays quiet.
- **B** (negative control — the same run with the `C-u` line deleted by `sed`,
  nothing else changed): the pane receives **`RC-TEXT[nn/clear]`**, the filed
  symptom reproduced verbatim, `RC-CLEARED` never appears, the log carries the
  loud block with the tail, the banner reads `**/reset-context FAILED** …`, and
  the continuation is still delivered.
- **C** (a proxy that clears and then keeps wiping the screen): the clear
  verifies, the *continuation* check catches the loss and shouts.
- **D** (durability, the point of the task): the active cache carries both
  fixes, the source copy is **byte-identical** to it, and the source plugin
  version is ≥ 0.11.0.

**One flake, chased not excused.** One early run failed a single assertion that
I filtered out of the output and could not identify. The plausible cause was
already visible in the same session: `+read` can transiently answer *"failed to
read terminal content"* for a pane `+list` already reports, which yields an
empty tail that reads exactly like a product verdict. `Tail` now retries an
empty read, and six subsequent runs were clean — and the underlying CLI race is
filed as **T181** rather than left as a harness workaround.

No app source changed; both test lanes, `zig build test-agent`, and P1–P3 were
re-run green to confirm that. The end-of-turn `/reset-context` of this session
runs the new helper, so the live path is exercised immediately — its log should
show `verified: /clear landed` and `verified: continuation is on screen`.
