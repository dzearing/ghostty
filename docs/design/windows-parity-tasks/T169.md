# T169 - +version's Running Instance section is Windows-only (Mac IPC server has no version verb)

## Summary

Found by T141's CLI parity audit. `ghoztty +version` is one shared CLI action,
but on Windows it additionally queries the running app over IPC (T52's `version`
verb) and prints a **"Running Instance"** section — version, commit, mode, exe,
modified, pid. On macOS the same command cannot: `macos/Sources/Features/IPC/
IPCServer.swift` has **no `case "version"`** (verified by grep: zero
occurrences), so the query fails and the section is absent.

That is the same class of divergence T141 was filed for, one level down: not a
verb that exists on only one platform, but a verb whose *answer* only one
platform can give. The user's rule ("I don't want commands that only exist on
one platform") reads naturally onto behavior too — `+version` should mean the
same thing on both seats.

Mac-seat work. Two defensible resolutions, and the choice is the first thing to
settle:

1. **Port the verb** (preferred): add `case "version"` to the Mac IPCServer
   returning the same JSON shape the win32 handler does (`handleVersion` in
   `src/apprt/win32/IpcHandlers.zig`), so the Running Instance section appears
   on both. `+list --json`'s `data.build` carries the same payload on Windows
   and is already additive, so the shape is settled and Mac-compatible.
2. **Drop the section on Windows** — cheaper, but it removes a genuinely useful
   answer ("which build is this window running?") that the box has needed
   repeatedly during this port, so prefer 1.

*Validation:* on the Mac seat, `ghoztty +version` prints a Running Instance
section against a running app, and `+list --json` still carries `data.build`;
`ipc-version.ps1` stays ALL PASS on Windows (its assertions are the contract the
Mac side must match).
