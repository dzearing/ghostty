# T358 - PROC_SPAWN detached processes miss the T42 user-env overlay: a command typed in Activity Monitor resolves against the agent's lean PATH

## In plain terms

Typing a program name into the Activity Monitor's "New Process" box — `python`,
`node`, `gh` — could fail with nothing happening, even though the same command
works fine in a terminal. The launcher was looking for programs using a bare
minimal search path instead of the user's real one, and because the launched
process has no window of its own, the "not found" error had nowhere to appear.
Now it uses the same full environment a terminal session gets, so anything you
can run from a prompt launches from the dialog too.

## Goals

- [x] A detached spawn resolves commands against the user's registry PATH, not
      the agent's inherited snapshot.
- [x] The environment block passed to Windows is built once, in a pure,
      unit-tested helper (sorted names, `=` in values, double-NUL terminator).
- [x] The fix degrades safely: if the environment can't be built, the spawn
      still happens with the old inherited environment.
- [x] `GHOZTTY_USER_ENV=off` still disables the overlay (negative control).

## Validation criteria

- [x] Unit tests on the block builder pass in both zig lanes — sorted
      case-insensitive ordering, a value containing `=`, the empty map's double
      NUL. (Verified: `zig build test -Dapp-runtime=none` and `-Dapp-runtime=win32`,
      plus `test-agent`, via `floor-lane.ps1 -Lane all`.)
- [x] On-box: `test\win32\agent-user-env.ps1` sections 1b/2b — a PROC_SPAWN
      from a PATH-stripped agent dumps an environment containing a user-PATH
      marker entry, and the same spawn with `GHOZTTY_USER_ENV=off` does not.
      (Verified: ALL PASS, 2026-08-06.)
- [x] `test\win32\activity-monitor.ps1` still ALL PASS (it asserts the spawn
      diag note format this change extends).
- [x] P1–P3 remain ALL PASS.

## Summary

T42 gave every agent-spawned PTY session the interactive user's registry
environment (`os/user_env.zig`, applied in `pty_child.zig:spawnChild`). The
agent's OTHER spawn path did not get it: `PROC_SPAWN` (§9.3), which
`proc_spawn.zig` serves with a **direct `CreateProcessW`** and a null
`lpEnvironment`, so the detached child inherits the agent process's own
environment verbatim — the same lean/stale snapshot T42 exists to fix.

## Why it matters more here than for a shell

A PTY session at least lands the user at a shell prompt. `PROC_SPAWN` is the
Activity Monitor's **New Process** command: the user types a bare command name
and the agent resolves it against PATH. On an agent started by the HKCU `Run`
entry / a scheduled task / a self-update relaunch, `python`, `node`, `gh` and
`ghoztty` itself are simply not found — with no shell to show the error in.

## Evidence

- `src/remote/agent/proc_spawn.zig:136,151` — `CreateProcessW(..., null /* env */, ...)`
  on both the breakaway and the fallback attempt.
- `src/remote/agent/pty_child.zig` calls `internal_os.user_env.overlay` before
  spawning; `proc_spawn.zig` has no such call.
- POSIX arm builds `/bin/sh -lc <cmd>` (a LOGIN shell), so this is Windows-only,
  exactly like T42.

## The fix

`user_env.overlay` already produces the right `EnvMap`. What is missing is
turning one into the UTF-16, `=`-joined, double-NUL-terminated block
`CreateProcessW` wants, plus `CREATE_UNICODE_ENVIRONMENT` in `dwCreationFlags`.
Put the block builder in `os/user_env.zig` next to the overlay (pure, so it is
unit-testable in every lane: ordering, the empty map, a value with `=` in it,
the double NUL) and have `proc_spawn.zig` pass it.

Note `CreateProcessW` requires the block's variable names to be **sorted** when
`CREATE_UNICODE_ENVIRONMENT` is used (documented requirement); assert that in
the unit test rather than hoping the map iterates in a useful order.

## Validation

- Unit tests on the block builder (both lanes).
- On-box: `remote-test-client --pipe=<pipe> --spawn=<cmd>` against an agent
  started with a STRIPPED PATH (the `test/win32/agent-user-env.ps1` harness
  already sets that condition up) — spawning a command that only exists on the
  USER PATH must succeed, and must fail with `GHOZTTY_USER_ENV=off` as the
  negative control.
