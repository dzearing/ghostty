# T637 - Viewer feedback: image chips, clipboard paste and images in the report

## In plain terms

Feedback about something you can see is usually best made with a picture. On a
Mac you can paste a screenshot into the feedback box and it becomes a small
`[Image #1]` tag in your text, with the picture itself filed alongside your
words. This task brings that to Windows, including the rule that a picture's
number never changes once it has one, so "Image #2" always means the same
picture.

## Summary

Fifth of the T384 split: the image half of the composer. Pasting an image
inserts an `[Image #N]` chip; the report writer from T636 gains a populated
`images` array and real PNG files under `images/`.

**Split, 2026-08-09**: the original task also carried the thumbnail carousel
and the screenshot capture. Three features in one file is more than one context
can do well, so the carousel is **T646** and the capture is **T647** (which
takes decision D44's answer). What stays here is the load-bearing vertical
slice — paste a picture, it reaches the report — which is what the other two
build on: both consume the storage, the numbering and the chip machinery below.

Mac site: the image half of `ViewerFeedbackComposer.swift`; pinned by
`ViewerFeedbackPasteTests`.

## Details

- **Chip numbers are stable, not positional.** Deleting `[Image #2]` leaves the
  sequence 1, 3 in both the text and the carousel — never renumbered — so a
  number always points at the same image. Both surfaces derive from one
  storage, the same derive-from-storage rule the quotes use.
- The chip is one atomic unit for selection, copy and delete (one Backspace).
  How that is expressed depends on T635's control decision; inherit it.
- Clicking a chip scrolls to its thumbnail and vice versa — **T646**, with the
  carousel it needs.
- The screenshot primitive is a fork, filed as decision **D44** and split out
  as **T647**.
- Paste must accept an image from the clipboard. On Mac the trap was
  `readablePasteboardTypes` — without it Cmd-V was *disabled* for an image-only
  clipboard and the override never ran. The win32 analog is registering for and
  honoring `CF_DIB`/`CF_DIBV5`/`CF_BITMAP` (and PNG as a registered format,
  which is what browsers put on the clipboard) in whatever paste path the
  composer control uses; a control that only asks for `CF_UNICODETEXT` will
  silently do nothing, which is the same silent no-op in a different costume.
- Images are written into the report folder as PNG with their pixel dimensions
  and byte size recorded in `images`. They are staged inside the same
  `.staging/` folder T636 renames, so an image can never be missing from a
  report a watcher can see.

## Validation criteria

- [x] Unit tests (none lane): chip numbering is stable across deletions
      (1,2,3 minus #2 leaves 1,3); the report's `images` array derives from the
      composer text and drops a deleted chip's entry.
      *Verified: `viewer_feedback_images.zig` — "chip numbers are stable across
      deletions, never positional" and "live: unknown chips are plain text and a
      duplicate attaches once". 12/12 in the `none` lane.*
- [x] Unit tests (none lane): a chip is one atomic unit — the span finder
      answers with the whole `[Image #N]` from any caret position inside or
      adjacent to it.
      *Verified: "chipAt: a caret inside a chip finds the whole thing, outside
      finds none" walks every interior offset, and
      "chipEndingAt/chipStartingAt: Backspace and Delete swallow a chip whole"
      covers two adjacent chips — the case that would otherwise leave
      `[Image #2` behind.*
- [x] On-box acceptance: put a PNG on the clipboard, paste into the composer —
      a chip appears; send, and the report folder contains the image with
      matching dimensions and byte size.
      *Verified: `test\win32\viewer-feedback-images.ps1` **ALL PASS (39)** —
      section A pastes a registered `"PNG"` (3688 bytes in, 3688 taken), and
      section E reads `images/image-2.png` back off disk byte for byte against
      what was put on the clipboard, with `pixelWidth`/`pixelHeight` 20x12.*
- [x] On-box acceptance: a report containing two images renders both as
      `![Image #N](images/image-N.png)` in `body`, with both files present.
      *Verified: same script, section E. The second image came from a
      BITMAP-only clipboard (no `"PNG"` format at all), so the DIB
      normalisation and the hand-written PNG encoder are on that path — it
      landed as 24x16, the size it was put there at.*
- [x] On-box acceptance: deleting a chip drops its image from the sent report
      (both the `images` entry and the file).
      *Verified: same script, sections B and E — one Backspace removes the whole
      `[Image #1]`, the next paste is still #2, and the published folder has no
      `images/image-1.png` and no `Image #1` anywhere in `body`.*
