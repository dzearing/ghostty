# T637 - Viewer feedback: image chips, thumbnail carousel and screenshot capture

## In plain terms

Feedback about something you can see is usually best made with a picture. On a
Mac you can paste a screenshot into the feedback box — it becomes a small
`[Image #1]` tag in your text with a thumbnail underneath — or grab one with a
button. This task brings that to Windows, including the rule that a picture's
number never changes once it has one, so "Image #2" always means the same
picture.

## Summary

Fifth of the T384 split: the image half of the composer. Pasting an image
inserts an `[Image #N]` chip; a thumbnail carousel below the input mirrors the
chips and scroll-syncs with them both ways; the `+` button (and Ctrl+Shift+S
from the keyboard) captures a screenshot; the report writer from T636 gains a
populated `images` array and real files under `images/`.

Mac site: the image half of `ViewerFeedbackComposer.swift`, plus
`ViewerView.captureFeedbackScreenshot`; pinned by `ViewerFeedbackPasteTests`.

## Details

- **Chip numbers are stable, not positional.** Deleting `[Image #2]` leaves the
  sequence 1, 3 in both the text and the carousel — never renumbered — so a
  number always points at the same image. Both surfaces derive from one
  storage, the same derive-from-storage rule the quotes use.
- The chip is one atomic unit for selection, copy and delete (one Backspace).
  How that is expressed depends on T635's control decision; inherit it.
- **Clicking a chip scrolls to its thumbnail and vice versa.**
- **The screenshot primitive is a fork, filed as a decision on this task.**
  Mac uses `screencapture -i -o` — an interactive whole-screen region grab —
  and its comment is explicit that `-c` is forbidden because it would clobber
  the user's clipboard. The obvious Windows equivalents (`ms-screenclip:`,
  `SnippingTool /clip`) do exactly the forbidden thing. The candidates are a
  ghoztty-drawn region selector over a screen snapshot (matches Mac's behavior,
  touches no clipboard, but is real UI work) and
  `ICoreWebView2::CapturePreview` (captures THIS pane only — no region
  selection, but no clipboard risk and almost no code). Take the decision's
  answer.
- **Whatever is chosen, the user's clipboard must come back unchanged.** That
  is a validation criterion below, not a footnote.
- Paste must accept an image from the clipboard. On Mac the trap was
  `readablePasteboardTypes` — without it Cmd-V was *disabled* for an image-only
  clipboard and the override never ran. The win32 analog is registering for and
  honoring `CF_DIB`/`CF_DIBV5`/`CF_BITMAP` (and PNG as a registered format,
  which is what browsers put on the clipboard) in whatever paste path the
  composer control uses; a control that only asks for `CF_UNICODETEXT` will
  silently do nothing, which is the same silent no-op in a different costume.
- Images are written into the report folder as PNG with their pixel dimensions
  and byte size recorded in `images`. They are staged inside the same
  `.staging/` folder T636 renames, so an image can never be missing from a
  report a watcher can see.

## Validation criteria

- [ ] Unit tests (none lane): chip numbering is stable across deletions
      (1,2,3 minus #2 leaves 1,3 in text and carousel); the report's `images`
      array derives from storage and drops a deleted chip's entry.
- [ ] On-box acceptance: put a PNG on the clipboard, paste into the composer —
      a chip appears with a thumbnail; send, and the report folder contains the
      image with matching dimensions and byte size.
- [ ] On-box acceptance: capture a screenshot from the `+` button and from
      Ctrl+Shift+S; the clipboard's contents before and after are byte-identical
      (put a known string on it first and read it back).
- [ ] On-box acceptance: a report containing two images renders both as
      `![Image #N](images/image-N.png)` in `body`, with both files present.
