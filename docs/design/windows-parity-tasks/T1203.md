# T1203 - The Windows installer is unsigned, so a new user meets a SmartScreen wall before Ghoztty ever runs

## In plain terms

You download Ghoztty from the website, double-click it, and Windows throws up a
full-screen warning saying it stopped an unrecognized app and naming the
publisher as unknown. Nothing is wrong - the file is exactly what we built -
but the person installing has no way to know that, and most people stop there.

## Goals

- [x] Every release signs the payload and the MSI the moment a certificate is
      configured, with no code change on that day
- [x] A release with no certificate configured still builds, and says openly
      that it shipped unsigned
- [x] A certificate that is configured and does not work fails the release
      rather than quietly shipping unsigned bits
- [x] The website tells people what is actually on their screen, and calls the
      override an override
- [ ] The certificate itself - T1246, gated on decision D87

## Summary

Hit by the user during the T1179 clean-machine walk on 2026-08-31. Running
`Ghoztty-1.35.0-x64.msi` downloaded from the site raises:

> **Windows protected your PC**
> Microsoft Defender SmartScreen prevented an unrecognized app from starting.
> App: Ghoztty-1.35.0-x64.msi
> Publisher: **Unknown publisher**

macOS ships **signed and notarized**; Windows ships **unsigned**. That is the
platform asymmetry CLAUDE.md calls the defect rather than a platform
difference - and it lands on the exact sentence the install epic exists to
make true.

The fix is an Authenticode signing certificate applied to `ghoztty.exe`,
`ghoztty.com`, `ghoztty-agent.exe` and the MSI, wired into
`release-windows.yml` with the certificate held as a repo secret. Note the
difference between certificate types, because it decides whether the warning
actually goes away: an **OV** certificate removes "Unknown publisher" but
still accrues SmartScreen reputation slowly, so early downloads can keep
warning; an **EV** certificate carries reputation immediately. Signing is also
what makes the T1178 in-app update trustworthy - an unsigned MSI downloaded
and executed by the app is a worse story than an unsigned one the user
double-clicked themselves.

## Details

Two things to correct on the way past:

1. The site's own note says to choose **More info** and then **Run anyway**.
   The dialog the user actually saw offered **Run anyway** and **Don't run**
   directly, with no More info link. The note should match what is on screen.
2. Until a certificate exists, the note is a mitigation and should be
   described as one - it does not make the installer trusted, it tells people
   how to override Windows.

## Validation criteria

The task splits at the line this seat cannot cross: buying a certificate needs
payment and identity validation, so that half is T1246 and the decision D87
that precedes it. What is provable here is that the day the certificate lands
in the repo secrets, every release is signed with no further code change - and
that until then a release still builds and says openly that it did not sign.

- [x] The release payload - `ghoztty.exe`, `ghoztty.com`, `ghoztty-agent.exe` -
      is Authenticode-signed BEFORE the MSI and the portable ZIP are cut, so
      both packages carry signed bits rather than only the MSI wrapper.
      Verified: sections G3-G4 of `test\win32elease-artifacts.ps1`.
- [x] The MSI is signed on top of that, since it is the file SmartScreen
      judges. Verified: G5 of the same harness.
- [x] Signing lives in the SHARED build script, so CI and the on-box publish
      path cannot ship differently. Verified: G2.
- [x] The certificate and its password arrive as repo secrets, never on a
      command line and never echoed. Verified: G7-G10 (`-readpass`, no
      `-pass`, no `echo` of either name in the workflow or the script).
- [x] The signature is SHA-256 and timestamped, and is read back with
      `osslsigncode verify` before it replaces the original file. Verified:
      G11-G13.
- [x] With no certificate configured the build still succeeds, prints an
      UNSIGNED banner and leaves the file untouched; with one configured that
      does not work it FAILS rather than silently falling back to unsigned.
      Verified by RUNNING the script both ways: G14-G16.
- [x] The website's SmartScreen note matches the dialog that is actually on
      screen and reads as a mitigation rather than a blessing. Verified:
      A15c/A15c2/A15e of `test/win32/website-windows-download.ps1`, plus F1
      (the in-repo mirror matches the deployed gh-pages page) after the
      corrected note was published.
- [ ] Moved to T1246: a real certificate, a signed MSI reporting `Valid`, and a
      clean-machine install with no "unrecognized app" screen.
