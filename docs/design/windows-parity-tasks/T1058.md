# T1058 - Ship workflow: merge the working branch back to main, then per-feature worktrees and PRs

## Summary

User directive, 2026-08-21: "when we feel like we're in a stable state and
feature complete, we would get this all merged back into main and continue work
from there or build individual worktrees for new features and make prs."

Today the loop commits straight onto `users/dzearing/windows-amd64`, one long
branch, hundreds of commits deep. That is fine for a solo sprint and wrong for
anything after it: there is no review point, no way to ship one feature without
shipping every other in-flight change, and no boundary at which quality is
checked (T1060) or CI is consulted (T1059).

## In plain terms

Right now everything goes into one big pile on one branch. It works, but nothing
is ever "finished and shipped" - it is just further down the pile. The change is
to draw a line: get the pile onto main once, and after that let each new feature
grow in its own copy of the repo, come back as a proposal that can be looked at
on its own, and merge when it is actually good. That gives us a place to say no,
and a place to say done.

## What this task owns

- The **entry criteria**: what "stable and feature complete" means concretely
  here, so the decision to cut over is a check and not a mood. Candidate floor:
  all lanes green, P1-P3 green, no P0 open, the guard sweep current, the watchdog
  clean over a real session.
- The **cutover itself**: merging the working branch to `main`. Note the prior
  art - T87 (Mac seat: macOS regression build + merge to main) is still `todo`
  and is a real dependency, since the merge cannot be validated from the Windows
  seat alone. T516 and T879 (divergence inventory, merge-back plan) are done and
  should be read first.
- The **after**: per-feature worktrees, one branch per feature, PR per branch,
  `main` as the trunk that new work forks from. Written into go.md so the loop
  actually follows it, including how a turn picks up mid-PR work and how the
  worktree is created and cleaned up.
- The **handoff to the other two**: PR health lands in the digest (T1059), and
  nothing merges without an adversarial review (T1060).

## Goals

- [ ] Entry criteria for the cutover are written down and checkable, not
      subjective.
- [ ] The merge to main is planned against T87/T516/T879 rather than improvised,
      with the Mac seat's part named.
- [ ] go.md carries the post-cutover turn shape: fork from main, worktree,
      branch, PR, review, merge - and what a turn does when it inherits an open
      PR instead of a fresh task.
- [ ] Worktree creation and teardown is a scripted, repeatable step, not a
      remembered incantation.

## Validation criteria

- [ ] The entry-criteria check runs and reports on the box, naming what is not
      yet satisfied.
- [ ] go.md's turn protocol describes the PR workflow end to end, and a reader
      following only go.md can execute one full feature through it.
- [ ] One feature is taken through the new path end to end as the proof - a
      worktree, a branch, a PR, a review, a merge - before the old path is
      retired.
- [ ] T87's Mac-seat half is either done or explicitly sequenced with a date, so
      the cutover is not blocked on an unowned step.
