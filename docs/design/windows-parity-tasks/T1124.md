# T1124 - The ghoztty:// handler is registered pointing into the repo's build output

## In plain terms

Clicking a ghoztty:// link on this machine launches a copy of the app out of the source folder rather than the properly installed one. That means a link can start a half-built or deleted development build instead of the terminal the user actually installed.

## Summary

`test\win32\url-scheme.ps1` scored `1 FAILURE(S) (31 passed)` in the T1094 sweep:

```
FAIL  ...and in particular does not point into this repo
      (got '"D:\git\ghoztty\zig-out-release\bin\ghoztty.exe" "%1"')
```

The registered handler points at `zig-out-release` inside the working tree. 31 assertions pass, so the scheme itself works - it is registered at the wrong target.

Why this matters beyond the test: this is real, current machine state. A `ghoztty://` link clicked by the user right now launches a build out of a scratch directory that gets rebuilt, moved and deleted by ordinary development. It also violates the standing rule that dev work must not reach into the user's installed experience.

The question to answer is HOW it got registered that way, because whatever did it will do it again. A test that registers the handler must restore the previous value, and a dev build should never claim a machine-wide scheme in the first place.

## Where

- the URL-scheme registration (`HKCU\Software\Classes\ghoztty`)
- `test/win32/url-scheme.ps1`
- whatever registers the handler at build, install or test time

## Goals

- [x] Point the registration back at the installed release and confirm a link opens it.
- [x] Find what wrote the repo path - a test that did not restore, or a dev build that registers on launch.
- [x] Make a dev build unable to claim the machine-wide scheme, and make any test that touches the registration restore it on the way out.
- [x] Have the script assert the restoration too, so this cannot be left behind again.

## Validation criteria

- [x] the registered handler points at the installed release, verified in the registry - it reads
      `"C:\Users\David\AppData\Local\Programs\Ghoztty\ghoztty.exe" "%1"`, and that exe answers
      `+version` (1.4.0-users-dzearing-windows-amd64-+2511b0694), so the entry names a handler that
      really runs rather than a path that merely looks right
- [x] the cause of the repo-path registration is identified and prevented - a GUI launch of the
      staging RELEASE build at `zig-out-release\bin`, which passed the build-mode gate because it
      really is a release build; prevented by the source-checkout location gate in
      `src\apprt\win32\url_scheme.zig`
- [x] a run of `url-scheme.ps1` leaves the registration exactly as it found it - asserted by the run
      itself: the last check of arm F compares the release class against the snapshot taken before
      anything of ours launched
- [x] `test\win32\url-scheme.ps1` is ALL PASS - 39 checks (was 31), including arm F and its control
- [x] the gate is unit-tested in the win32 lane: build output under a `build.zig` ancestor is a
      checkout, an install directory is not, and a missing directory is neither an error nor a
      checkout
