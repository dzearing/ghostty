# T1213 - The launch-time self-heals gate on two different ideas of where the app is allowed to live

## Summary

There are three launch-time self-heals that write something outliving the
process, and after T1124/T1146 they answer "may this build write it?" with two
DIFFERENT predicates:

- `PathInstaller` (user PATH) and `AgentIntegration` (the Claude first-run
  offer) require the exe to sit in the canonical install dir
  (`%LOCALAPPDATA%\Programs\Ghoztty`) — so a portable unpack is refused.
- `url_scheme` (the `ghoztty://` handler) and `LocalAgent` (the agent autostart
  Run key) require only that the exe is NOT inside a source checkout
  (`source_checkout.inSourceCheckout`) — so a portable unpack is allowed.

Both are defensible on their own and both are as intended today, but nothing
states the rule, so the next self-heal picks one by whichever neighbour its
author happened to read. Write the rule down (which predicate, and why: is this
thing the *installed* Ghoztty's to own, or merely not-scratch?), point the four
call sites at it, and decide deliberately whether the portable build should keep
being a second-class citizen for PATH and the integration offer — the user does
run the Desktop portable copy.

## In plain terms

Ghoztty quietly fixes a few things about itself when it starts — putting itself
on your PATH, claiming `ghoztty://` links, asking Windows to start its session
keeper at sign-in. Each of those checks whether it is a "real" install first,
and right now two of them mean "installed in the usual place" while the other
two mean "at least not a scratch build". Nobody wrote down which is right, and
the difference is why the portable copy on the Desktop never offers to set up
the Claude integration.

## Goals

- [ ] One documented rule for which location predicate a launch-time self-heal
      uses, and why.
- [ ] The four call sites reference it rather than each other.
- [ ] A deliberate answer for the portable build's PATH and integration offer.
