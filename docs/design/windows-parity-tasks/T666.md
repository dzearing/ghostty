# T666 - The second re-attach replays only the last screen

## In plain terms

Quit or crash the app once and your terminal comes back with its history. Do it
a second time and the history is gone: the pane comes back holding only what
was on the screen at the moment it died. Nothing warns you, and the text is not
recoverable afterwards.

## Goals

- [x] A pane restored twice in a row still holds the history it had before the
      FIRST restore, not just its last screen.
- [x] The restored history is readable text, not shredded text — replaying it
      correctly is part of keeping it.
- [x] `session-persistence.ps1` back to ALL PASS, with the B*.7 arms green.
- [x] Whatever is found is written down as which side dropped the history.

## Summary

Found while sweeping the restore scripts for T652, and **it is not T652's
doing** — the baseline script from `HEAD` (materialized with `git show` and run
unmodified) fails the same way.

`test/win32/session-persistence.ps1` section B kills the app three times in a
row, planting a marker in pane `spB` before each kill, and after each relaunch
asserts that EVERY marker planted so far is still readable:

```
PASS  B1.7 replayed scrollback holds all 1 cycle marker(s)
FAIL  B2.7 replayed scrollback holds all 2 cycle marker(s)
FAIL  B3.7 replayed scrollback holds all 3 cycle marker(s)
```

The pane's whole content after the second restore is 144 bytes — the marker
just planted, its "not recognized as an internal or external command" reply,
and a prompt. Not the previous cycle's marker, not the earlier liveness probes,
not even cmd.exe's startup banner:

```
D:\git\ghoztty>SPMK44176C2
'SPMK44176C2' is not recognized as an internal or external command,
operable program or batch file.

D:\git\ghoztty>
```

So the FIRST re-attach replays the ring and the SECOND replays roughly one
screen. The shape points at the WP-D3 delta path: attach #2 has a nonzero
offset and a grid snapshot, and what comes back is the snapshot rather than
snapshot + everything the ring still holds behind it.

## Details

- The script header claims section B has been fully green since 2026-07-21, so
  this is a regression somewhere between then and 2026-08-09, not a bound that
  was never met.
- B.9/B.10 (the pane is LIVE) PASS in every cycle, so the pane is working — it
  has simply lost its history. That is the pairing worth keeping in mind: the
  T652 liveness arms and this content arm fail independently, which is exactly
  why both exist.
- Start at `attach:` in the app log (`offset=` / `snapshot=`) for the second
  attach of a session, and at the agent side that decides what to send after a
  snapshot. `test/win32/session-snapshot-reattach.ps1` is the narrower oracle
  for the same path and should be run alongside.

## What it turned out to be

Neither side dropped the history: both delivered it, and then a repaint painted
over it. The app paints its persisted WP-D3 screen onto the pane's VISIBLE rows
(a repaint has no line feeds, so nothing scrolls), and the agent's ATTACH reply
is followed immediately by a repaint of the session's CURRENT screen that homes
to row 1 — `agent/grid_snapshot.zig` opens with `ESC[H ESC[2J`, and with that
capability suppressed ConPTY's own post-attach paint (`ESC[?25l ESC[H` +
per-line `ESC[K`) does the same job. Read straight off the wire by
instrumenting `drainRing`:

```
T666CHUNK len=1088 data=<E>[H<E>[2J<E>[?1004h<E>[?9001h<R><N>C:\…>T666MK0Z…
```

Only rows that had already reached SCROLLBACK survived, which is why cycle 1
passed (its whole history still fitted in the viewport) and every later cycle
came back holding exactly one screen. Same invariant T106 named for the
full-ring path; the snapshot path never got it.
