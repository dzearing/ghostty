# T462 - Chooser session rows show no CPU because win32 never subscribes to the agent's session_cpu stream

## In plain terms

The machine chooser lists a machine's sessions but never says which of them
is actually doing anything. On the Mac the same list carries a live CPU
meter per session, so you can tell the build that is chewing a core from the
five shells sitting at a prompt. The agent already measures and pushes those
numbers — Windows just never asks for them. When this lands, each session row
carries the same live meter.

## Goals

- [ ] The win32 chooser subscribes to `SESSION_CPU_SUB` for the selected
      machine and unsubscribes when the selection moves or the chooser closes
- [ ] Each session row renders a CPU meter, laid out per
      `docs/design/win32-design-system.md` (spacing scale, contrast floors,
      asserted at 1.0 / 1.25 / 1.5 / 2.0)
- [ ] The subscription is gated on the negotiated HELLO capability, and an
      agent that does not advertise it degrades to no meter rather than a
      wedge or a wrong number
- [ ] The `cpu_units` capability is honored, not assumed

## Evidence

`session_cpu` appears in exactly four files —
`src/remote/protocol.zig`, `src/remote/agent/server.zig`,
`src/remote/connection.zig` and `src/apprt/embedded.zig` (the C API the
Swift app consumes). Nothing under `src/apprt/win32/` references it, so the
whole producer side is present and unused here. The win32 chooser's own CPU
vocabulary (`activity_rows.zig:193-217`, `formatCpu`/`normalizedCpu`/
`formatHostCpu`) already exists for the Activity Monitor and is the natural
formatting to reuse so the two surfaces agree.

## Two protocol details that are easy to get wrong

- **`cpu_units`** (`protocol.zig`, near `cpu_pct`): the chooser's session
  meter needs no separate gate, but the Activity Monitor's process table —
  whose `cpu_pct` predates it — does. Read the comment at the capability
  before deciding which of the two surfaces you are gating.
- **The interval is a hint.** `Server.throttledIntervalMs` clamps the
  client's `interval_ms` to a floor, stretches it under host load and caps
  it, and tells the client the real interval in every frame. The UI must
  read the interval it is given rather than assume the one it asked for —
  that is how a slow stream stays distinguishable from a dead one.

## Depends on

T461. Without a warm per-machine connection there is nowhere to hang a
subscription: the roster's remote path frees its dial at the end of every
fetch.

## Validation

- Unit tests in the `none` lane for the row layout + meter formatting at all
  four scale factors, and for the capability gate (absent capability ⇒ no
  meter, no subscribe).
- An acceptance script in `test/win32/` that opens the chooser against the
  local agent, waits for at least two pushed frames, and asserts a numeric
  meter on a busy session and a quiet one on an idle session.
