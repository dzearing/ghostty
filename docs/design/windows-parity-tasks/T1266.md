# T1266 - An acceptance script can quietly stop measuring anything once its pane stops re-rendering

## Summary

T1239 migrated `holder-volume.ps1` onto the background test desktop and it went
red - not because the build changed, but because the SIZE of the pane's output
did. On the user's desktop the app renders every frame, so a ConPTY answers a
scrolling flood by re-rendering it: 20 KB of payload arrived in the agent's ring
as ~348 KB, roughly 17x. Off the input desktop nothing re-renders and the same
flood arrives at about its own size (~27 KB). The script's premise - "more
output than the holder can hold" - was being met by the amplification, not by
the payload, and neither the script nor anything else said so.

That is a general hazard, not one script's bug. Any acceptance script whose
premise is a VOLUME of terminal output (an overrun, a ring wrap, a scrollback
eviction, a throughput floor) may have been passing on amplification it no
longer gets, and the failure mode is the dangerous one: the assertion still
runs, still passes, and measures a smaller thing than it says it does. The two
`holder-volume` arms are the proof it can happen in both directions - the
measured arm went red, and its negative control went red the other way (with
the trigger OFF the marker was no longer lost, because 20 KB never overran the
holder).

## In plain terms

Some of the tests that check what happens when a terminal prints a LOT were
quietly relying on the app being on screen: a visible window makes Windows send
far more data through the pipe than the program actually printed. Now that the
tests run out of sight, those floods are much smaller, and a test can keep
saying PASS while checking something much weaker than it claims.

## Goals

- [ ] every script whose premise is an output VOLUME is identified
- [ ] each one's premise is asserted from a measured number, not assumed
- [ ] the hazard is written down where the next migration will read it

## Details

Where to look: scripts that flood a pane and then assert something about a
buffer - `holder-volume.ps1` (done, T1239), `holder-soak.ps1`, `send-keys-soak.ps1`,
`soak.ps1`, and anything reading `.ring` files or scrollback limits. The tell is
a script that types N bytes and then asserts a property of a buffer larger than
N without asserting how much actually arrived.

The remedy pattern is already in `holder-volume.ps1`: measure what the ring
RECORDED and assert both edges of the window the test needs (B3 "the flood
pushed more through the pane than the holder retains", B3b "and it stayed inside
the ring"). A premise asserted from a measured number cannot silently stop
holding.

`lib\TestDesktop.ps1`'s header should carry the hazard beside the capture
limits it already documents: PrintWindow's flat fill is the visible half of
"a background desktop renders nothing", and the output-volume collapse is the
invisible half.

## Validation criteria

- [ ] the volume-premise scripts are enumerated, with the check each one relies on
- [ ] every one of them asserts its premise from a measured number (or is
      recorded as not needing to)
- [ ] `lib\TestDesktop.ps1` documents the output-volume collapse alongside the
      capture limit
- [ ] the affected scripts are green on the box after the change
