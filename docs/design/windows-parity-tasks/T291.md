# T291 - Activity Monitor: New Process flashes a console window on every spawn

## Summary

Found while validating **T286**. `proc_spawn.spawnWindows` launches every
command with `CREATE_NEW_CONSOLE` (`src/remote/agent/proc_spawn.zig:113`), so
starting *anything* from the Activity Monitor's New Process dialog puts a
**visible console window** on the user's desktop — including a pure GUI command
(`notepad`), where the console flashes up, sits there while `cmd.exe /C` runs,
and vanishes. Mac's equivalent (`open -a Safari` through `/bin/sh -lc`) shows
nothing at all.

The flag is not gratuitous: the comment above it records that
`DETACHED_PROCESS` + `\Device\Null` std handles made `cmd.exe` **exit
immediately**, which is a worse failure (the panel reported a pid for a process
that was already gone). So this is not "delete the flag" — it is "find the
variant that keeps console apps alive without showing a window".

## In plain terms

Starting a program from the Activity Monitor's "New Process" dialog made a
terminal window pop up on screen every time — even for programs that have no
terminal output at all. On a Mac nothing appears; on Windows a window flashed
up and hung around. After this fix, starting a process shows nothing: the
program still runs (you can see it in the table), but no stray window appears.

## Goals

- [x] Starting a process from the New Process dialog no longer shows any
      console or terminal window.
- [x] The started process still actually runs (the earlier "invisible" attempt
      killed console programs at startup — that must not come back).
- [x] The acceptance test proves both, and provably FAILS against the old
      behavior (verified by a negative-control run).

## Validation criteria

- [x] `test/win32/activity-monitor.ps1` ALL PASS (85 assertions), including
      three new section-H checks: no new console-class window on the test
      desktop, no new delegated-terminal host process (OpenConsole /
      WindowsTerminal), and the spawn's actual `dwCreationFlags` carry
      CREATE_NO_WINDOW and not CREATE_NEW_CONSOLE. Verified 2026-08-06.
- [x] Negative control: the same script against a build with the old

- [x] The existing "the spawned process is really running" assertion still

      dead child). Verified in the same run.
- [x] Floor: `floor-lane.ps1 -Lane all` → none/win32/agent all PASS; P1–P3
      ALL PASS. Verified 2026-08-06.

## Details

Candidates, cheapest first:

- `CREATE_NO_WINDOW` instead of `CREATE_NEW_CONSOLE`. It allocates a console
  for the child but never shows it, which is exactly the shape wanted: console
  apps keep a console (so they do not die on startup the way the
  `DETACHED_PROCESS` variant did) and nothing appears on screen. This is the
  most likely one-line fix.
- If a hidden console turns out to break something, `STARTF_USESHOWWINDOW` +
  `wShowWindow = SW_HIDE` on the `STARTUPINFOW` is the fallback.

Whichever lands, keep the diagnostic note `spawnDetached` already returns
(`exit=STILL_ACTIVE` vs `exit=EXITED`): it is what proved the previous variant
was killing its own children, and this change is in exactly that blast radius.

Note the *agent's* remote spawn path uses the same function, so a fix here fixes
both the local panel and a remote source (T287).
