# T185 - Windows +list/window-inherit report a pane's INITIAL cwd, not its live cwd (no OSC-7 from cmd.exe/powershell)

## Summary

Found while fixing **T144**. `Surface.pwd()` returns
`self.io.terminal.getPwd()` — the value set by an **OSC 7** report from the
shell, seeded once at bring-up from the pane's starting directory
(`termio/Remote.zig` `t.setPwd(cwd)`, and the exec equivalent). On macOS,
ghostty's shell integration makes zsh/bash emit OSC 7 on every `cd`, so the
value tracks the user. On Windows the default panes are `cmd.exe` /
`powershell.exe` with **no shell integration**, so the pane's reported pwd is
frozen at whatever it started in, forever.

Two user-visible consequences:

1. `ghoztty +list --json`'s `working_directory` is a *starting* directory, not
   a current one. Any agent or script that asks "where is this pane?" gets a
   stale answer the moment the user `cd`s.
2. `window-inherit-working-directory` / `tab-` / `split-` inherit that same
   stale value. T144 made a new window inherit the focused pane's directory
   instead of the agent's, which is the big win — but "the directory you were
   just in" still means "the directory that pane opened in". A user who
   `cd`s into a project and presses ctrl+n does not land in the project.

Note the machinery for the right answer already exists and is used elsewhere:
the agent's `GET_CWD` (`protocol.GetCwd` → `child.queryCwd`) reads the child's
real cwd on demand, and `Window.buildRemoteInherit` already calls
`queryCwdTimeout` for tabs/splits on a remote window. So the shapes to consider
are (a) route `pwd()` through a bounded `GET_CWD` for agent-backed local panes
(and something equivalent for exec panes — `NtQueryInformationProcess` on the
child, the same PEB read T144's harness uses), and/or (b) ship PowerShell/cmd
shell-integration that emits OSC 7, which is the Mac-parity answer and also
fixes the title.

Validation must be measured, not argued: open a pane, `cd` somewhere else, and
assert `+list --json` reports the NEW directory and that ctrl+n lands there.
`test/win32/new-window-cwd.ps1` is the natural home (its section D already
presses the real chord and reads a pane's actual shell cwd with `cd`).
