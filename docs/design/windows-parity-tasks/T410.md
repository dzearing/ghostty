# T410 - The release log file grows without limit - the one diagnostic surface a user can send back is a file that only ever gets bigger

## In plain terms

When something goes wrong in the Windows build, the log file Ghoztty leaves
behind is the only record of what happened — and nothing has ever kept it from
growing. It was 9.4 MB on this box with no cap, so it gets slower to search
every day, it is awkward to send to anybody, and the only way it ever shrank was
somebody deleting it by hand. From now on the file stops at a size, the previous
one is kept beside it, and everything older is dropped. Nobody notices this while
the terminal is working; it is what keeps "zip the log and send it" a reasonable
thing to ask.

## Goals

- [x] The shared log stops growing without limit: it is archived at a size cap
- [x] Exactly two generations are kept — the live file and one archive — so the
      pair is small enough to zip and old enough to hold an incident
- [x] Rotating never loses the line that triggered it, and never splits one
- [x] Two writers crossing the threshold together cannot destroy the archive
- [x] The bound is measured on the real binary, not asserted

## Summary

Found by T108 (2026-08-03), and filed as two halves.

**Half one is already done.** T270 (2026-08-21, `701252680`) added
`src/os/log_stamp.zig`: every line in
`%LOCALAPPDATA%\ghoztty\ghoztty.log` now opens with
`<iso-8601-utc-millis> <pid> ` inside the same single write as its message, so
the shared sink demultiplexes by process and orders in time. Re-verified against
`logFn` (`src/main_ghostty.zig`) at claim time; nothing is owed here.

**Half two is what this task now is: the file is unbounded.** It is written by
the GUI app, the agent and every one-shot `ghoztty +…` CLI invocation — several
a second on a box driving Ghoztty from scripts — with no rotation and no cap.
The release build has no console, so this file is the ONLY diagnostic surface a
user-reported failure leaves behind, and an unbounded one is a file nobody can
be asked to send and nothing can usefully search.

## Fix

`src/os/log_rotate.zig`, called from `logFn` right after the write:

- **`max_bytes` = 4 MiB, two generations.** At the cap the live file is archived
  over `ghoztty.log.1` and the next line recreates `ghoztty.log`, so at most
  ~8 MiB is ever on disk. The check is asked on the append handle the writer
  already holds (`FILE_READ_ATTRIBUTES` added to it), so the usual answer costs
  one size query and no open.
- **The rename goes through the HANDLE, not the path.** Every writer decides to
  rotate independently, so two can cross the threshold in the same millisecond.
  A path rename is a real hazard there — the first archives the log, a third
  writer creates a fresh tiny one, and the second moves THAT over the archive,
  dropping the history the mechanism exists to preserve. A handle names a file
  object, so both racers rename the same file and the second is a no-op.
- The line that triggers rotation is written first, so it lands in the
  generation it belongs to, and the atomic-append shape (one line, one write) is
  untouched.

## Validation

- [x] Unit (`none` lane, `src/os/log_rotate.zig`): the threshold is inclusive;
      an oversize log becomes the `.1` generation with its bytes intact; a log
      under the threshold is left alone; a second rotation REPLACES the archive
      and never creates a `.2`; a missing log is a no-op; and the rename
      succeeds while another writer holds the file open (the sharing this
      depends on). 6 tests, green.
- [x] On box (`test\win32\log-append.ps1`, sections R0–R9, release build):
      seeds the live log onto the threshold read out of `log_rotate.zig`, runs
      the real exe, and asserts the archive appears carrying the seeded bytes,
      the live file is recreated well under the cap, the post-rotation lines are
      still well-formed, a second rotation replaces the archive rather than
      piling up, no `.2` exists, and the total on disk stays inside two
      generations.
- [x] The four floor lanes (`scripts\floor-lane.ps1 -Lane all`) green.
