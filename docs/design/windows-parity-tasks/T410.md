# T410 - Release log lines carry no timestamp and no pid, in a file three different programs append to - no on-box incident can be reconstructed after the fact

## Summary

Found by T108 (2026-08-03). T108's whole job was to root-cause two anomalies
seen on the user's release install on 2026-07-20. Both are gone, so the verdict
stands — but **the reason they could not be root-caused is that the log cannot
answer "when"**, and that will be true of the next incident too.

`%LOCALAPPDATA%\ghoztty\ghoztty.log` is written by `logFn`
(`src/main_ghostty.zig:207-215`) as exactly:

```zig
const prefix = if (scope == .default) ": " else "(" ++ @tagName(scope) ++ "): ";
const msg = std.fmt.bufPrint(&msg_buf, level_txt ++ prefix ++ format ++ "\n", args)
```

so every line looks like `info(win32): session-restore: restored 2 window(s)`.
**No timestamp. No pid.** And the file's own doc comment two screens up says it
is a SHARED sink — *"the GUI app, the agent and every one-shot `ghoztty +…` CLI
invocation append to the same file concurrently, and on this box there are often
several a second"*. The `FILE_APPEND_DATA` work (T229) made those writers
interleave whole lines instead of clobbering each other, which was the right
fix; it left the lines themselves unattributable.

The consequence, concretely, this turn: the orphaned session was created
2026-08-02 05:29:02 (known only from `Win32_Process.CreationDate`, not from the
log), and there is **no way to find the corresponding region of a 9.4 MB log**,
nor to tell which of the three programs wrote any line in it. The log has five
`session-restore: restored N window(s)` lines and no way to date any of them.

## Why this is worth a task rather than a shrug

- It is the second time the log's shape has cost an investigation. T229's own
  primary evidence — *"the app logged nothing after the confirm"* — could not be
  trusted, which is what motivated the atomic-append fix.
- The release build has no console, so this file is the ONLY diagnostic surface
  a user-reported failure leaves behind.
- Both halves are cheap, and one of them is three fields in a `bufPrint`.

## Fix

1. **Prefix every line with a timestamp and the pid**, e.g.
   `2026-08-03T04:13:25.412Z 24484 info(win32): …`. UTC-with-offset or local is
   a judgment call — pick one and say why in the comment; the requirement is
   that it is sortable and unambiguous across a DST boundary. The pid is what
   separates the GUI app from the agent from a one-shot CLI, so it is not
   optional garnish.
2. **Bound the file.** It is 9.4 MB on this box with no rotation and no cap.
   Rotate at a size (keep one `.1` generation) — enough that a user can zip the
   pair, not so much that it grows forever.

Keep the single `bufPrint` + single `write` shape: the atomic-append guarantee
depends on one line being one write, so the prefix must be part of the SAME
formatted buffer, never a second `write` call.

## Validation

- Unit: a formatting test in the `none` lane over the line-builder — asserts the
  prefix shape and that a message that overflows `msg_buf` still emits one
  well-formed truncated line (never a half-line and never two writes).
- On box: run the release exe and a `ghoztty +list` concurrently in a loop, then
  assert every line in the log matches the prefix grammar and that **two
  distinct pids** appear — the interleaving is the point.
- Rotation: drive the file past the threshold and assert exactly two
  generations survive, with the live file the smaller one.
