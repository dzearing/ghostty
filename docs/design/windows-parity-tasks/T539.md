# T539 - Clicking an absolute Windows path link does not open Explorer to the file

## In plain terms

A tool that prints a file path into a pane's banner — the video it just
rendered, the log it just wrote — used to leave that path as dead text.
Clicking it did nothing, because only a path written in markdown link syntax
was ever clickable. Now a path that stands on its own is clickable too: click
it and File Explorer opens with the file selected, Ctrl+click shows it in a
side pane, and the right-click menu offers Copy Path. Bare web addresses
linkify the same way. Text that only looks path-ish (`docs\design\foo.md`,
`www.example.com`) is deliberately left alone, so ordinary prose never sprouts
links.

## Goals

- [x] Identify the surface and the dead end (banner markdown had no autolink
      pass at all; only `[label](target)` became a link)
- [x] Bare Windows paths in banner text become links — drive (`D:\`, `D:/`),
      UNC (`\\server\share\…`), rooted (`/…`), `~\…`, `.\…`/`..\…`
- [x] Bare `http(s)://` URLs autolink too (the other half Mac has and win32
      did not)
- [x] A clicked path reveals in Explorer rather than launching its app
- [x] Prose stays prose: no bare-domain matching, no sigil-less paths, no
      autolinking inside code spans or an explicit link's label

## User report (2026-08-06, verbatim)

"D:\Users\David\Projects\ComfyUI\output\video\MiniMax_H3_smoke_00001_.mp4
links like that don't seem to open explorer to the file."

## First questions for whoever picks this up

Establish WHERE the path was rendered as a link before touching anything -
the three link surfaces have different specs and different code:

1. **Terminal content** (most likely: a path printed into a pane by a build/
   agent tool). Which detector linkified it - OSC 8 from the emitting
   program, or Ghoztty's own regex? What does a click currently DO (nothing?
   tries a browser with a `d:` scheme?), and what does the Mac do with a
   POSIX absolute path clicked in a pane (parity anchor: CLAUDE.md's banner
   spec says a file path click REVEALS in the file manager, never opens the
   app).
2. **Pane banner** autolinking: the documented sigils are `/`, `~/`, `./`,
   `../` - a drive-letter `D:\...` path may not be recognized AT ALL on the
   platform where drive letters are the native spelling. If banners are the
   surface, the fix is extending the sigil set to `[A-Za-z]:\` (and UNC
   `\\server\share`) on win32.
3. **Viewer pages** (markdown links to local files).

## Expected behavior (from the report + existing spec)

A clicked absolute-path link opens Explorer with the file SELECTED
(`explorer.exe /select,<path>` - the reveal-in-Finder analog the banner spec
already promises), never launches the file's associated app on plain click.

## Validation criteria

- [x] The reporting surface identified and named here with the click's
      current dead-end explained — the **pane banner**. Its markdown parser
      had no autolink pass at all (only `[label](target)` produced a link),
      so a bare path was plain text with nothing to click. T165 had already
      built the click side, which is why the click "did nothing" rather than
      doing the wrong thing.
- [x] Clicking `D:\...\file.ext` on that surface opens Explorer with the
      file selected — verified through the right-click menu, whose first row
      is by contract the left-click default and reads **Reveal in File
      Explorer** for the autolinked path (section 6j of
      `test\win32\pane-banner.ps1`; the menu, rather than a live
      `explorer /select`, so the run never opens a window on the user's
      desktop). Ctrl+click in the same section opens a viewer pane whose
      `url` is the exact path, backslashes and all, which is what proves the
      whole path reached the target and not just the visible text.
- [x] UNC `\\server\share\file` decided: **same treatment** — it is
      `banner_link.kindOf`'s `.file` already, Explorer selects a UNC path
      like any other, and the parser matches `\\` + a name character.
      Asserted by the "forward-slash drive path and UNC share" unit test.
      The one Windows-specific care it needed: the autolink pass runs BEFORE
      the backslash-escape branch, or `\\server` is eaten as an escape.
- [x] Mac parity checked: Mac already autolinks `/`, `~/`, `./`, `../` and
      `http(s)://`, and its banner spec reveals a clicked file path in
      Finder, so no Mac-seat task is owed. This change ports that pass and
      adds only the spellings that are native here (drive letters, UNC,
      backslash separators). Shared rules kept identical: scheme-only URL
      matching, the word-boundary test, trailing-punctuation shedding with
      the balanced-bracket exception, no autolinking inside a code span or
      an explicit link's label, and "no cwd ⇒ a dot-relative path stays
      text".
- [x] Both zig lanes, `test-agent` and P1–P3 green
      (`scripts\floor-lane.ps1 -Lane all`: none/win32/agent all PASS;
      P1/P2/P3 ALL PASS), plus `test\win32\pane-banner.ps1` ALL PASS (110).
