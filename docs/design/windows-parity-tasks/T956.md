# T956 - Fork-identity overlay: a script that re-applies Ghoztty branding and the .win32 apprt arms over an upstream tree, plus a verifier

## Summary

T879's analysis found that 52 of the 131 merge-risk files carry a fork delta of 10 lines or fewer, and that delta is always one of three mechanical overlays: the branding rename (com.mitchellh.ghostty -> com.dzearing.ghoztty, Bundle.main.bundleIdentifier! -> Bundle.loggerSubsystem), the apprt enum arm (.none => void -> .none, .win32 => void and siblings), or a path/name string carrying the fork identity. A checked-in script that re-applies that overlay to a tree, plus a verifier that greps for any surviving upstream identity string, turns 52 of 131 merge resolutions into take-theirs-then-run-the-script - and makes the same 52 free in every future merge stage. This is Stage 0 of docs/design/windows-parity-merge-back-plan.md and lands no upstream code, so it is safe before D80 is answered.

## In plain terms

This fork renamed the product - the app identity, the window titles, the
command name in the shell helpers - and it added a Windows frontend the
original does not have. Every time we pull work down from the original
Ghostty project, those same small edits have to be made again in dozens of
files, by hand, which is slow and easy to get subtly wrong. This task writes
those edits down as a script that can re-apply them to any tree, and a
checker that says whether anything from the original identity is still
showing. Nobody using the terminal sees this directly; what they get is that
improvements from upstream can arrive without the fork's own name and Windows
support breaking on the way in.

## Validation criteria

- [x] `scripts\fork-identity.ps1 check` exits 0 on the working tree, and
      `apply` changes nothing there (the tree already carries the identity).
      **How verified:** `test\win32\fork-identity.ps1` sections A and B - B
      goes through the real write path on a copy of all 52 U-files and
      compares SHA-256 before and after, so an in-place rewrite could not
      report "no change" and pass.
- [x] The overlay reproduces the fork's own files from the fork point, and
      the number is measured rather than asserted.
      **How verified:** section C stages the 52 U-files at `063ac3ecc`, runs
      `apply`, and diffs against HEAD: **28 of 52 byte-identical**, 104 of the
      210 changed lines removed. The residual 24 are printed by name. C6 is
      the control - `check` on the same tree BEFORE the overlay exits 1.
- [x] Every rule fires on the upstream form (no rule has quietly stopped
      matching).
      **How verified:** section D, one fixture per rule, 9 rules asserted by
      name plus 16 assertions on the rewritten text; D20 re-runs `apply` and
      requires "no change" (idempotence).
- [x] The strings that must stay upstream survive.
      **How verified:** section E - `xterm-ghostty`, the `GHOSTTY_*` variable
      names, upstream's repository URL, `appendingPathComponent("ghostty")`,
      `customModule="Ghostty"`, a `.none` arm in a non-app-runtime switch, and
      an app-runtime switch that already has its own `.win32` arm - asserted
      byte-identical after `apply` and silent under `check`. A blanket
      `ghostty` -> `ghoztty` rename passes section D and fails this one.
- [x] The harness is wired into the staleness gate.
      **How verified:** `fork-identity` row added to `scripts\guard-due.ps1`;
      a green run stamps `test\win32\fork-identity.stamp.json`, and the
      `-NegativeControl` run (red by construction) left the stamp byte-identical.
- [x] The plan doc says what the overlay really does.
      **How verified:** Stage 0 item 2 of
      `docs/design/windows-parity-merge-back-plan.md` is marked done and
      carries the 28/52 measurement with the three residual classes named.
