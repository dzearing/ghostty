# T186 - Mac seat: verify T144's shared-core changes on macOS (local-agent cwd fallback + config template flush)

## Summary

**Mac seat.** T144 fixed two defects in code that is shared, not win32-only, so
the Mac build changes behavior and nobody has run it there.

1. **`termio.Remote.openWorkingDirectory` (`src/termio/Remote.zig`, called from
   `src/Surface.zig`).** The LOCAL session-persistence agent now receives the
   surface's resolved `working-directory` when no explicit remote cwd was
   supplied. `TerminalController.swift` already sets `remoteWorkingDirectory =
   workingDirectory` for the local agent, so the common Mac path is unchanged —
   but where that was **nil** (a fresh window with nothing to inherit) the OPEN
   used to carry no cwd and the session was spawned in the **launchd agent's**
   cwd. It now gets the resolved default (`$HOME`). Verify that a fresh
   `cmd+n` under `session-persistence = on` opens in the same directory it does
   with persistence off, and that a cross-machine remote window still forwards
   **nothing** (that rule is load-bearing: a local path on a different-OS agent
   is the OPEN-stall wedge).

2. **`writeConfigTemplate` never flushed** (`src/config/Config.zig`). The
   template is ~2 KiB and the writer's buffer is 4096, so on **every** platform
   a user with no config got a **zero-byte** `config.ghostty` instead of the
   documented template — and an empty file then counted as "a config exists",
   so it was never retried. Fixed, plus an `.empty` `OptionalFileAction` that
   makes a truncated config self-heal. On macOS the template goes to
   `~/Library/Application Support/com.dzearing.ghoztty/config.ghostty`; check a
   clean-profile launch actually writes it, and that a **non-empty** config is
   never clobbered. This is very likely an upstream Ghostty bug too — worth
   reporting/upstreaming rather than carrying.

Windows evidence, harness traps, and the negative controls are in
`docs/design/windows-parity-tasks/T144.md`.
