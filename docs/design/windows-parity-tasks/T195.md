# T195 - Settle-window policy has no on-box test: a link blip must not trigger an in-place rebuild

## In plain terms

Your terminal panes are kept alive by a background helper. If that helper
really dies, the app quietly rebuilds every pane so you can keep working. But
if the connection to it only hiccups for a moment, rebuilding would be the
worst possible reaction — it throws away and re-makes panes that were never
broken, and on the Mac an early version of this did exactly that and killed
people's sessions. The app already waits five seconds before deciding, and
that waiting rule is unit-tested, but nothing had ever checked it on a real
machine. This adds that check: freeze the helper long enough for the app to
notice, unfreeze it, and prove not a single pane moved — plus the mirror-image
check that a freeze held longer than five seconds does rebuild.

## Goals

- [x] Induce a real link blip on the box, with no new product test hook
- [x] Time the resume against the app's own observable state, not a fixed sleep
- [x] Prove nothing was rebuilt, by an outcome rather than a log line
- [x] Pair it with a negative control that differs only in duration
- [x] Keep the script stable across repeated runs

## Validation criteria

- [x] `test\win32\agent-recovery.ps1` section G: a blip resumed inside the
      settle window leaves the terminal surfaces, the child pids, the session
      count, the viewer pane and the topology untouched, and the pane still
      answers a typed marker. Verified: ALL PASS (57).
- [x] Section H: the identical blip held until the app logs that it is
      recovering DOES replace every terminal surface, and the pane comes back
      responsive. Verified in the same run.
- [x] The instrument has teeth: run with the suspend deliberately held past the
      window, G6/G7/G8/G9 all go red. Verified by hand against a copy of the
      script before H was made permanent.
- [x] Stable under repetition: 7 clean runs, and the one failure mode found
      (H6 sampling the async teardown mid-flight, 2 runs in 5) fixed with
      `Wait-SurfacesReplaced`, then 4/4 green.
- [x] Standing floor green: `scripts\floor-lane.ps1 -Lane all`, P1-P3.

## Summary

Filed by T145. The half of in-place agent-crash recovery that is proven on the
box is the DESTRUCTIVE half: kill the agent, assert the windows rebuild. The
half that keeps recovery from being destructive — the 5s settle window that
makes a transient link drop a no-op — is only covered by pure unit tests in
`src/apprt/win32/agent_recovery.zig`. Nothing on the box proves the app
actually survives a blip without replacing every surface in every local window.

That is exactly the failure Mac shipped and had to fix in `e65cfa4d5`: in-place
recovery ran on a transient link blip (the incident link healed in 27ms) and
then destroyed the sessions it had just re-attached. The policy is ported and
unit-tested; the WIRING of it — that a heal inside the window really does reach
`link_recovered` and really does leave the panes alone — is not measured.

## Details

The transport FSM (`src/remote/connection.zig` §5.1) enters `reconnecting`
after three missed heartbeats (`heartbeat_interval_ms` = 3s) and returns to
`connected` on the next authentic packet, so a blip is inducible without any
new test hooks: SUSPEND the run's `ghoztty-agent.exe` long enough for the app
to log `shared local-agent link went down ... watching`, then RESUME it well
inside the 5s settle window.

The oracle must be an OUTCOME, not the log line: record each pane's child pid
(`+sessions --json`) before the suspend and assert they are UNCHANGED
afterwards. A rebuild always produces new children (T145's `agent-recovery.ps1`
section C asserts exactly that), so "same pids" is positive proof that no
rebuild happened — and it is the same measurement in both directions, which is
what makes the pair credible.

Suspending a Windows process without a debugger: `NtSuspendProcess` /
`NtResumeProcess` via `Add-Type` (the box already does P/Invoke of this shape
in `test/win32/menu-bar.ps1`), or suspend every thread with
`SuspendThread`/`ResumeThread`.

**Care required:** the settle window is 5s and reaching `reconnecting` takes
~3 missed heartbeats, so the suspend must be timed against the app's observable
state rather than a fixed sleep, and the resume must land inside the window. A
test that races here would be worse than no test.

**Validation:** a new section in `test/win32/agent-recovery.ps1` (it already
has the launch/split/session helpers): suspend -> confirm the watch started ->
resume inside the window -> assert the shell pids are unchanged AND the panes
are still responsive, with a negative control that resumes AFTER the window and
therefore does see new pids.

**Correction, measured while building this (2026-08-10): the pid oracle above is
wrong for this stimulus.** Pids answer the KILL in section C — the children died
with the agent, so the respawned one relaunches them — but they cannot answer a
SUSPEND: a frozen agent never loses a child, so a rebuild after a blip
re-ATTACHes the very same sessions and the pids are identical either way. Held
past the window on purpose, the control ran a real rebuild and the pid
assertion still passed. The oracle is instead the set of **`GhozttyTerminal`
child windows**: recovery keeps the window HWND and replaces the surfaces inside
it (`rebuildTabLeavesInPlace` → `replaceTabLeaf`), so a fresh set is positive
proof a rebuild ran and an unchanged set positive proof none did — one
instrument that reads in both directions under one stimulus. Pids are still
asserted, now as the documented negative result (H7), so the fact cannot
silently stop being true.
