# T1409 - The chooser link-hover ink metric silently compares only the blue channel

## In plain terms

One of the automated checks that watches the machine-picker window measures
"how much is painted here" to tell a hovered control from a resting one. It is
only ever looking at how BLUE each pixel is - the red and green it thinks it is
comparing are thrown away before the comparison. It happens to still catch the
thing it was written for, so nothing is failing today; but a change that lights
a control in a warmer color would slip straight past it.

## Summary

`test/win32/chooser-link-hover.ps1`'s `Measure-Ink` packs each pixel as
`($c.R -shl 16) -bor ($c.G -shl 8) -bor $c.B`. `$c.R` is a **[byte]**, and
PowerShell keeps a byte left operand's TYPE through `-shl`, so both shifted
terms truncate back to a byte and evaluate to 0: every key collapses to its
blue channel alone. The modal "background" it derives is therefore `(0,0,B)`,
and since the per-pixel values it compares are the same collapsed keys, the
`$d -gt 24` test sums two guaranteed zeroes and the blue difference.

Proven, not inferred: T588's `chooser-kill-hover.ps1` was written with the same
expression and its reference color came back as `(0,0,61)` against a card whose
real fill is `(50,54,61)`, with 94% of the box scoring as "ink". The `[int]`
casts that fixed it are commented there.

The T315 metric still discriminates (rest 342 / hot 407 are real blue-channel
differences from the underline), so this is a harness accuracy defect rather
than a live false pass - but it measures a third of what its comment claims.

## Details

Fix: `([int]$c.R -shl 16) -bor ([int]$c.G -shl 8) -bor [int]$c.B`, the shape
`chooser-kill-hover.ps1` already carries. Re-run `chooser-link-hover.ps1` and
its `-NegativeControl` afterwards; the numbers will move (a full-channel
distance is larger than a blue-only one) and the assertions that compare
against the resting value should still hold exactly.

Worth a sweep of the other PowerShell probes for the same packing while there:
`grep -rn '\-shl 16' test\win32` finds them.

## Validation criteria

- [ ] `Measure-Ink` casts to `[int]` before shifting, and the reference color it
  derives for a known-flat patch matches that patch's actual RGB.
- [ ] `test\win32\chooser-link-hover.ps1` is ALL PASS on the current build with
  the corrected metric, and its `-NegativeControl` still FAILS.
- [ ] Every other `-shl 16` pixel packer under `test\win32` is either fixed the
  same way or shown to be operating on `[int]` already.
