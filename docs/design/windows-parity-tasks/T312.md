# T312 - T227c: the owner-drawn machine list has no focus indicator (finding 10)

## Summary

Third of three splits of **T227**. `docs/design/win32-machine-chooser.md` §4
finding **10**, and it is a design-system §2.2 violation, not a nicety:
**focus is always visible**.

The chooser's Tab order exists and is unit-tested (`nextFocus`,
`MachineChooser.zig:1745-1854`), but the machine list is owner-drawn and draws
only SELECTION. So:

- a row that has keyboard focus but is not selected is **invisible**, and
- a selected row looks identical whether the list has focus or not, so Tabbing
  onto the list gives no feedback at all.

§3.2 states the target: every stop in the Tab order draws a focus indicator,
and the list draws it on the focused ROW, distinct from selection - because a
row can be selected while the list does not have focus. This is the same
three-state rule (selected-and-key / selected-not-key / hover) the viewer's
table of contents already follows on the Mac side.

## Details

- `ODS_FOCUS` in `WM_DRAWITEM`'s `itemState` is the signal; the row painter has
  to consume it rather than keying only off `ODS_SELECTED`.
- The indicator is a shape, not a color swap (§2.2: state is never color alone)
  - a focus rim inside the selection pill's own inset, so a focused-and-selected
  row reads as one control and not as two nested rectangles.
- The selection fill must also weaken when the list is not the focused control,
  which is the "neutral unemphasized" half of the rule.
- Keep it in `chooser_rows.zig` so it is asserted in the none lane like every
  other row color.

## Validation

- `chooser_rows` unit tests: the three states are mutually distinguishable and
  each clears the 3:1 chrome floor against what it sits on, at 1.0/1.25/1.5/2.0.
- `test/win32/ipc-machine-chooser.ps1`: Tab onto the list and assert the focused
  row changes pixels; Tab away and assert it reverts. The harness posts input on
  the background desktop, so use the T233 lesson - the trigger and the color are
  separate oracles when a hover/focus cannot be held.
- `-NegativeControl` fails a load-bearing pixel claim.
- Floor: both `zig build test` lanes, `test-agent`, P1-P3.

## Outcome (DONE 2026-08-01)

Three states, resolved in one place: `chooser_rows.rowPaint(bg, accent, state)`
returns the pill's `fill`, its `border` and its `ring`, and `drawRow` paints
what it is handed. The painter now reads `ODS_FOCUS` alongside `ODS_SELECTED`,
which is the whole defect — it could not previously tell "the list is the
control you are driving" from "a row is selected".

Three decisions are worth keeping:

- **The rim REPLACES the pill's outline instead of nesting inside it.** Drawing
  both puts two concentric rounded rectangles a pixel apart, which is the "two
  nested rectangles" this task's own Details section rules out. A focused row
  has to read as one control.
- **`focus_path_inset`, not `focus_ring_inset`, is what the painter uses.** GDI
  centres a pen on its path, so passing §2.2's "inset 1 DIP" straight through
  would hang half the 2 DIP rim over the pill's own edge. The metric carries
  the half-width, and the unit test recovers the stated inset from it
  (`focus_path_inset - ring_w/2 == round(1 * scale)`) rather than restating the
  number.
- **The unfocused selection is neutral and the floors are separate.** The rim is
  floored 3:1 against the FILL it lands in (`chrome_theme.accentOn(fill,
  accent)`), not against the row background it never touches — the same
  relative-resolution argument `chrome_theme.Palette` makes.

**Its consequence for the acceptance script is the interesting part, and it is
the lesson.** The chooser opens with focus in the FILTER, so the existing
"selected row is accent-tinted" probe had been measuring the *unfocused* state
all along and only passed because there was one state. It fails against a
correct build now. A pixel probe of a state-dependent surface has to SAY which
state it is in; this one did not, and nothing marked it. Both halves are
asserted now, in the state each belongs to.
