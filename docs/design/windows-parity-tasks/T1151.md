# T1151 - A dev build can still write machine-wide registrations the user's shell obeys

## In plain terms

Building and testing Ghoztty in this repo can quietly change settings on the
whole computer - which program opens Ghoztty links, what starts when you sign
in, and possibly more. It has already happened once for real: for days, clicking
a Ghoztty link would have tried to run a half-built file in a scratch folder.
When this lands, nothing built inside the source folder can change those settings
at all, and there is a list of every such setting rather than a new surprise each
time one is found.

## Summary

T1124 fixed one instance and revealed the class. The app's build-mode isolation
rule (T350) covers **endpoints** - the IPC pipe, the agent pipe, the state
directory - so a debug build cannot drive the user's terminal. It says nothing
about **registrations**: writes to HKCU, the filesystem outside the checkout, or
anything else the shell reads on the user's behalf. Those are invisible to every
lane, because a unit test can see the key name and the command string but never
the decision to write them.

Two instances are known:

- **URL scheme** (T1124, fixed): the staging release under `zig-out-release\`
  rewrote `HKCU\Software\Classes\ghoztty\shell\open\command` to a scratch path.
  Fixed with a LOCATION gate - an exe with a `build.zig` in any ancestor
  directory registers nothing.
- **Agent autostart** (T1146, open): the HKCU `Run` entry has the same
  build-mode-only gate and a worse blast radius, since the entry survives a
  reboot.

What is unenumerated: file associations, PATH edits, Start menu / shortcut
writes, jump list entries, per-user scheduled tasks, and anything else written
under `%APPDATA%`/`%LOCALAPPDATA%` outside the build's own state directory.

The fix has two halves: an **inventory** of every out-of-checkout write the app
and its scripts perform, and the **same location gate** applied to each (the
`build.zig`-ancestor marker T1124 established, not a new mechanism per site), so
the rule is "a build that lives in a source checkout registers nothing" rather
than a list of exceptions.

## Goals

- [ ] Enumerate every write the app, the agent and the repo scripts make outside
      the checkout and outside the build-mode state directory.
- [ ] Each such site either carries the location gate or is documented as
      deliberately ungated with the reason.
- [ ] One acceptance harness asserts the whole set, so a new registration added
      later without a gate goes red.
- [ ] A row in the `guard-due` coverage table so the harness re-runs when any of
      those sites change.

## Validation criteria

- [ ] The inventory names every site, each with file:line and its gate status.
- [ ] A launch of the repo's release build writes none of the enumerated keys or
      paths, with a control launch (gate seam disabled) proving the assertion has
      teeth.
- [ ] The user's real registrations are byte-identical before and after the run.
- [ ] `guard-due` reports the new harness CURRENT after a clean run.
