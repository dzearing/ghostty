# T706 - Screenshot capture: the keyboard caret starts on the POINTER's monitor, not the one the user is reporting on

## In plain terms

Start a screenshot from the keyboard on a two-monitor desk and the crosshair
can appear on the other screen — wherever the mouse pointer happens to be
parked. Someone working from the keyboard never moves that pointer, so it says
nothing about where they are looking. The crosshair should start on the screen
holding the window they are writing the report about.

## Summary

Noticed while building T671. `RegionSelector.homeMonitor` derives the "home"
monitor from `GetCursorPos`, and both the hint card and (since T671) the
keyboard caret's starting point are placed on it. That is right for a mouse
capture — the pointer IS the user's attention — and wrong for a keyboard one.

## Details

- The composer's owner window is already passed to `begin` as `owner`. The
  monitor containing THAT window is the better answer whenever the gesture
  did not start with the pointer, and is never worse: the pane the report is
  about is on it by definition.
- Options worth weighing: always use the owner's monitor (simplest, and the
  hint card would then also follow the pane rather than the pointer), or keep
  the pointer's monitor for the card and use the owner's only for the caret.
- Nothing here changes the capture itself, which photographs the whole virtual
  screen either way.

## Validation criteria

- [ ] Unit test (none lane): the home-monitor choice is a pure function of the
      owner rect / pointer point and the monitor list.
- [ ] On-box acceptance: with the pointer parked on a monitor other than the
      one holding the viewer window, the announced caret position at
      `capture=begin` falls inside the viewer window's monitor.
