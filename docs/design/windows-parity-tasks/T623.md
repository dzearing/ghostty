# T623 - A Mac window restored on Windows lands vertically mirrored: the layout blob records no source-screen height, so the Cocoa y-flip cannot be undone

## In plain terms

When you rebuild a Mac's windows on a Windows machine, they come back the right
SIZE with the right panes in them, but upside-down on the screen: a window that
sat at the top of the Mac's display lands near the bottom here. Nothing is lost
and every window is still on screen and grabbable — it just isn't where it was.

## Goals

- [x] A restored cross-lineage window lands the same way up it was left
- [x] No window is moved that did not need moving

## Summary

Fallout from **T337**, recorded rather than papered over. macOS measures a
window's y UP from the bottom-left of the primary screen; Windows measures it
DOWN from the top-left. The layout blob records only the window's own rect, not
the height of the screen it was authored against, so the flip **cannot be undone
from the data we have** — `y_win = screen_h - y_mac - h` needs a `screen_h`
nobody wrote down.

`mac_layout_blob.frameFrom` therefore passes the origin through verbatim and
`restore_frame.reanchor` re-centers anything that lands on no monitor at all.
The alternative considered and rejected was centering EVERY translated window on
the primary monitor: that discards the position for all of them and stacks a
restored multi-window session on one spot, which is worse for exactly the case
Restore All exists to serve.

The fix is an additive field, not a heuristic: have each viewer record the
work-area height (and origin) of the screen its window was on alongside the
frame, so the reader can convert. Both lineages ignore unknown fields, so it
costs nothing on an older peer — an old blob simply has none, and keeps today's
pass-through behavior. Guessing with the LOCAL screen's height instead would be
inventing information and would be wrong on every mismatched pair of displays.

**What landed (2026-08-16)** deviates from the sketch above in one deliberate
way: the field is the SOURCE PRIMARY display's FULL height
(`primary_screen_height` / Mac `primaryScreenHeight`), not the window's own
screen's work-area. Both global coordinate spaces are anchored at the
primary's full frame, so `y' = primary_h - y - h` is exact for every monitor
of the source arrangement and is its own inverse — one field and one formula
serve both directions. A work-area flip would be off by the menubar/taskbar,
and the window's own screen's height is the wrong constant for windows on
secondary monitors. win32 writes the field beside every captured frame
(`App.zig primaryScreenHeight()`), `mac_layout_blob.frameFrom` flips when a
Mac blob carries it, and the full contract for the Mac seat's writer/reader is
documented in T622.

Depends on **T622** only in the sense that the same field is needed at both
ends; either seat can add its own writer independently.
