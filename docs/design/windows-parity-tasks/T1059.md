# T1059 - The digest names every open PR and its CI health, so a red or stalled PR is a morning read

## Summary

User directive, 2026-08-21: the digest should outline the PRs that need merging,
and posted PRs should be monitored so they are building correctly and passing
tests. The daily digest (go.md step 0.5,
`docs/design/windows-parity-digests/<date>.md`) is already the first thing a
turn reads, and it already renders in the dashboard - so PR state goes there
rather than into a new surface nobody opens.

## In plain terms

Once work ships as proposals rather than straight onto the branch, a proposal
can sit there for a week going red and nobody would know. The morning read
should just tell you: here is what is waiting to merge, here is what is broken,
here is what has gone quiet. No dashboard to remember to check.

## Goals

- [ ] A new digest section lists every open PR: title, branch, age, CI status,
      and whether it is waiting on review or waiting on merge.
- [ ] CI status is real - read from the checks on the PR (`gh` CLI), not
      inferred from "it was green when I pushed".
- [ ] A red PR and a stalled PR are visually distinct from a healthy one; the
      digest says which of them needs a turn spent on it.
- [ ] Absence is handled: no open PRs prints the empty state, and an unreachable
      GitHub prints "unknown", never a fabricated green.

## Validation criteria

- [ ] Run against the live repo with at least one open PR and the section
      renders correctly in both the markdown and the dashboard view.
- [ ] A PR with a failing check is shown as failing (demonstrated against a real
      or planted red check), and a network/auth failure prints unknown rather
      than passing.
- [ ] The digest generation stays inside its time budget with the extra calls,
      and does not block the turn when GitHub is slow.
- [ ] Follows the digest protocol already in force: written for today only,
      never backfilled.
