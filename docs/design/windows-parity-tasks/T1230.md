# T1230 - Nothing checks what else a test run can write into the user's persistent state

## In plain terms

Running the tests is supposed to leave this machine exactly as it found it. One
place where it did not - the list of programs Windows starts at sign-in - was
found by eye, eight days after it started happening. There are half a dozen
other places a test run could change something permanent about the machine, and
nobody has checked any of them.

## Summary

T1168 found the suite writing permanent HKCU Run entries and closed that one hole. The general question is unanswered: the Run key is not the only durable place a run can reach. Scheduled tasks, HKCU\Software\Ghoztty, the DPAPI credential store, the user PATH, the Start Menu and the session-layout manifests are all writable by an acceptance script, and the only one anything sweeps is the Run key. Wanted: an enumeration of the persistent surfaces a run can touch, a before/after snapshot arm that fails when a suite run changes any of them outside its sandbox, and a decision per surface on whether isolation or teardown is the right answer.
