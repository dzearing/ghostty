# T212 - Migrate the SendInput-driving GUI scripts onto the test desktop

## Summary

T207 deliverable 3. With the T211 harness in place, move the GUI acceptance
scripts off the interactive desktop so the loop stops stealing the user's
foreground. Measured surface in `test/win32/` (63 scripts): 35 call
`GrabForeground`/`SetForegroundWindow`, 36 drive with `SendInput`/
`keybd_event`.

## The mechanical change per script

1. Launch via `Start-OnTestDesktop` instead of `Start-Process`.
2. Delete the script's private `GrabForeground` copy (30 scripts carry one)
   and call `Focus-TestWindow`.
3. Replace `SendInput` key/mouse calls with `Send-TestKeys` / posted mouse
   messages. **`SendInput` cannot be kept**: the T207 spike measured it
   returning 0 events accepted with `GetLastError` = 5 (ACCESS_DENIED) on a
   background desktop. That is the hard constraint of the whole approach.

Mouse-driven scripts (right-click context menus, tab-strip clicks, divider
drags) are the risky subset: the spike only proved KEYBOARD posting. Posted
`WM_LBUTTONDOWN`/`WM_MOUSEMOVE` do not move the real cursor, and
`TrackPopupMenuEx` menus run a modal loop that reads mouse state. Prove one
mouse script (`dark-menus.ps1` is the smallest) before converting the rest;
if posted mouse input cannot open a `#32768` menu, those scripts route to the
T207 option-B/batch bucket and that must be SAID in the log, not left silent.

## What T211 already settled (do not re-derive)

- The harness is `test/win32/lib/TestDesktop.ps1`; dot-source it and read its
  header. `test/win32/split-zoom-nav.ps1` is the worked example (launch,
  isolation assertion, chords incl. ctrl+alt+arrow, focus polling, foreground
  watch, `-NegativeControl`), and `test/win32/test-desktop-harness.ps1` is the
  harness's own acceptance script.
- **Extended keys need a real lparam.** Posting lparam 0 (what the spike did)
  works for plain letters and silently misroutes arrows/Home/End - the
  harness builds scancode + extended-bit + repeat itself, and sends
  WM_SYSKEY* for alt-without-ctrl. Anything hand-rolling a post must too.
- **Dialogs take plain keys and text, not chords.** `Send-TestControlText`
  posts WM_CHAR (standard controls need it; nothing translates a posted
  message) and `Send-TestKeys` posts WM_KEYDOWN only (the terminal runs
  ToUnicode itself, so posting both doubles every character). A modifier
  chord does NOT reach a standard control: ctrl+a arrives as a literal 'a'.
- **Expect product no-ops, not harness faults.** A background desktop has no
  foreground window, so foreground-gated product code silently does nothing
  there. One such bug was found and fixed in T211
  (`App.performDeferredFocus`); the sweep for the rest is T215. When a
  migrated script fails on focus/activation, suspect this before weakening
  the assertion.

## Validation

- Each migrated script ALL PASS x3 on the test desktop.
- Each migrated script's negative control still FAILS - an isolated harness
  that quietly stopped driving the app would otherwise look like a clean pass.
- A whole-suite run while the user types in another window never takes
  foreground: assert it programmatically by polling `GetForegroundWindow` on
  the interactive desktop throughout and requiring that no harness-launched
  pid ever appears (the T207 spike already does this and can be lifted).
