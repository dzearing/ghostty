# T1296 - A cross-machine RESUME drops the window name

## In plain terms

You pick one of your sessions off the other machine and bring it up here, and
the window arrives with no name - just whatever the shell happens to call
itself. Do that three times and you have three windows you cannot tell apart,
even though you had named them all on the machine they came from.

## What the user reported (2026-09-03)

> "restoring the window on the other machine did not bring over the window
> name."

Reported immediately after confirming the two machines could see each other, so
the remote-machine path itself is working - this is the restore losing one
field.

## What it turned out to be (2026-09-03, measured)

The **Restore All** path was never the one at fault. Its capture, its blob and
its rebuild all carry the name end to end, and the cross-machine fixture now
proves it (`chooser-restore-all-remote.ps1`, assertions A2 and E2 - a window
renamed before the machine is taken away comes back on the other side still
wearing that name).

The loss is in **resuming ONE session** from the machine chooser - clicking a
row and pressing Return, which is the natural single-window gesture and the one
the report describes. That path built a window from the session id and nothing
else:

- `App.resumeRelaySession` / `App.resumeLocalSession` opened a window with no
  name at all, so the title fell through to whatever the shell said next. The
  negative control shows exactly what the user saw: `C:\WINDOWS\system32\cmd.exe`.
- Nothing was available to name it WITH. The window name lives only in the
  layout record, and a remote roster had no layout record - `LIST_SESSIONS` has a
  `title` field but no agent ever fills it in, and the chooser's other source is
  this box's own manifest, which says nothing about another machine.

macOS does not have this gap: `AppDelegate.resumeBrowsedSession` sets
`controller.titleOverride` from the resumed session on both arms.

## The fix

- The session roster pulls the machine's **layout blobs alongside its roster**
  for a remote target (`GET_LAYOUTS` on the same pooled connection) and decodes
  them into the same shape the local manifest parses to. One accessor answers
  "what was this session's window called" for both machines.
- `persistedWindowNameFor` returns the name **and whether the user chose it**:
  the window's `title_override` is a pin the user typed and goes back as a pin;
  a pane's last terminal-reported title goes in on the terminal-reported path,
  so the resumed shell's next title takes over normally. Collapsing the two
  would either freeze a shell title forever or let a shell overwrite a name the
  user chose.
- The same layout view now also gives a REMOTE row its label in the chooser
  list, which was previously blank for the same reason.
