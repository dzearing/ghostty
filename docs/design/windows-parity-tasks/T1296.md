# T1296 - A cross-machine restore drops the window name

## In plain terms

You restore your windows on the other machine and they come back, but they have
lost their names - so a set of windows you had carefully labelled arrives
anonymous and you have to work out which is which.

## What the user reported (2026-09-03)

> "restoring the window on the other machine did not bring over the window
> name."

Reported immediately after confirming the two machines could see each other, so
the remote-machine path itself is working - this is the restore losing one
field.

## What is already known

**The title is on the wire.** `src/remote/agent/layout_meta.zig` says outright
that the record carries "the window frame, the split tree with per-leaf session
ids, titles", and `session.zig` keeps a `title` field per session that the
agent tracks alongside dimensions and cwd. `main.zig` describes the session
roster as `id/argv/cwd/title/pinned`. So the name is stored and transmitted.

That makes this a **drop on the applying side**: whatever rebuilds the window on
the receiving machine is not applying the title it was given. Worth checking in
this order:

1. Does the restore payload arriving on the second machine actually contain the
   title, or is it lost when the layout is serialised for a *remote* peer
   rather than a local relaunch? (A local restore may be exercising a different
   path that happens to keep it.)
2. Is the title applied at window creation and then overwritten - by the
   shell's own title escape, or by a default derived from cwd - rather than
   never applied at all? A title that appears and is then replaced looks
   identical to one that never arrived.
3. Does a *user-set* name (`+new-window --target=`, or a rename) survive
   differently from a shell-derived title? Those are different fields
   conceptually and the user means the name they chose.

## Validation criteria

- [ ] A window with a user-set name, restored on a second machine, comes back
      carrying that name.
- [ ] A shell-derived title behaves the same as it does on a local restore -
      no better, no worse.
- [ ] The distinction between a user-set name and a shell-set title is explicit
      in the restore path, so one cannot silently overwrite the other.
- [ ] An acceptance script covers the cross-machine case, not only the local
      relaunch that already works.
