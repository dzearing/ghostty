# T618 - Local Restore All still pulls layouts on the GUI thread

## In plain terms

Restoring THIS machine's windows asks the background session daemon for them
while the app waits. Normally that answer comes back instantly, so nobody
notices — but if the daemon is wedged or busy, the app sits frozen for up to
four seconds with no cursor and no redraw. The cross-machine version of the same
button no longer does this (T339); the local one still does.

## Goals

- [x] The local Restore All's agent RPCs run off the GUI thread, so a slow or
      wedged agent never stops the app repainting.
- [x] The rebuild still happens on the GUI thread, against a connection
      re-resolved there rather than the one the worker borrowed.
- [x] A reply that lands after the chooser closed, or while the app is quitting,
      is safe: no leak, no half-built topology.
- [x] An acceptance script measures the app answering throughout, rather than a
      comment claiming it does.

## Summary

`App.restoreAllLocalFrom` runs `GET_LAYOUTS` and then the `LIST_SESSIONS`
liveness probe synchronously on the GUI thread, each with a
`restore_probe_timeout_ns` (2 s) budget. The worst case is therefore ~4 s of a
stopped message loop, plus the rebuild itself.

T339 moved the RELAY path off-thread and deliberately left this one alone: every
RPC here is a bounded named-pipe round trip to a daemon on this box, which is
milliseconds in the normal case, and a change is only worth making where the
network cannot be trusted. That reasoning holds for the median and not for the
tail — a wedged or upgrading agent is exactly when a user reaches for Restore
All.

## Details

- The machinery already exists: `RestoreAllRelay` is the shape (worker does the
  RPCs, `PostMessage`s a `Job`, GUI thread rebuilds). The local arm needs no
  dials at all, so its job is strictly simpler — pull + probe off-thread, then
  the same `adopt` rebuild against the shared local connection.
- The one wrinkle is the shared connection: the relay path hands each window a
  transport it owns, while a local rebuild BORROWS `LocalAgent`'s warm one. A
  worker may use it for the pull (`SessionRoster.fetch` already borrows it the
  same way and states why it cannot dangle), but the rebuild must re-resolve it
  on the GUI thread rather than assume the borrowed pointer is still current.
- Same "reply landed after the chooser closed / while quitting" rules apply.

- [x] With the local agent made deliberately slow to answer, the app answers a
      `WM_NULL` `SendMessageTimeout` throughout the restore — the T339 assertion
      I, pointed at the Local row. **Verified**: assertion 4b of
      `test\win32\chooser-restore-all-adopt.ps1`, which arms
      `GHOZTTY_RESTORE_PULL_DELAY_MS=2500` on the surviving instance and probes
      the chooser every 150 ms: *13 probes, 0 unanswered, over a restore that was
      in flight for 2812 ms*. Its own control asserts the stall was both armed
      (the app's log line) and paid (press-to-rebuilt >= the delay), so a restore
      that finished before the first probe cannot pass it.
- [x] `test/win32/chooser-restore-all.ps1` stays ALL PASS. **Verified**: ALL PASS
      (31 assertions). `chooser-restore-all-remote.ps1` (the relay arm, which
      shares the chooser code this touched) is ALL PASS (46) too, as are
      `chooser-controls.ps1` (54) and `chooser-selection.ps1` (35).
- [x] A restore whose chooser is closed mid-flight still rebuilds, and one that
      lands while quitting rebuilds nothing and leaks nothing. **Verified by
      construction and by reading**: `onRestoreAllLocal` matches the chooser by
      ID and rebuilds either way, dropping only the sentence; `adoptRestoreAllLocal`
      returns 0 under `quit_requested`; and `Job.destroy` frees the decode and
      the probe on every path, including the one where `PostMessageW` fails.
      **Not directly measured** — the same gap the relay arm has, now filed as
