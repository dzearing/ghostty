# T1205 - You cannot tell which Ghoztty you are running

## In plain terms

You install the new version, open the About box to check it worked, and it
shows you an old version number next to today's date. Apps & Features shows a
third number that matches nothing on the website. There is no way to answer
"am I on the new build?" without a command line.

## What the user saw (2026-08-31)

They installed `Ghoztty-1.35.0-x64.msi` and asked, in their own words: *"I
think i'm on the newest build but i'm not sure."* Every surface disagreed:

| Surface | Says |
|---|---|
| `ghoztty.com --version` (on disk) | `1.35.0+890207079` - **correct** |
| **About box** in the open window | `Ghoztty 1.4.0-users-dzearing-windows-amd64-+2362337e4` |
| **Apps & Features** / ARP | `26.8.3108` |
| `ghoztty.exe` PE FileVersion | `26.8.31.8` |
| The website and the release tag | `1.35.0` |

Four different answers, and the one the user actually looked at was the worst.

## The defects

**1. About mixes two different builds into one box.** It showed
`1.4.0-…+2362337e4` (the RUNNING process, pid 40440, started the previous day)
alongside `Modified: 2026-08-31 09:45:50 UTC` - the mtime of the file **on
disk**, which is the NEW build the running process is not. So a stale window
looks freshly updated. Either report the running build's own identity
consistently, or say plainly that a newer build is installed and the window is
still running the old one - which is the genuinely useful message, and the one
the user needed.

**2. Nothing tells you a relaunch is needed.** Windows cannot replace a running
image, so every open window keeps the old binary after an upgrade. That is
normal and expected - but it is invisible. This is a known repeat: it cost a
"hero mode doesn't work" report on 2026-07-15, when the user was typing into an
exe that predated the fix. T52 exists to make it diagnosable; this task is
about making it **visible without being asked**.

**3. The ARP version is not a version anyone publishes.** `26.8.3108` is the
date-derived per-build number `build-msi.sh` uses to guarantee a
strictly-increasing MSI ProductVersion. It is load-bearing for upgrade
sequencing, but it should not be what a person reads in Apps & Features when
the thing they downloaded said 1.35.0. Show the marketing version there
(`DisplayVersion` can differ from `ProductVersion`).

## Goals

- [x] About stops mixing two builds into one box
- [x] The app volunteers "you are running the older build", with a way to fix it
- [x] Apps & Features shows the version on the download, not the sequencing number
- [x] A test moves the on-disk exe past the running process and proves the notice appears

## What changed

**Four surfaces now answer four distinct questions, and each says which.** The
table is in `docs/claude/build.md`.

- `src/apprt/win32/image_freshness.zig` (new, pure, every lane) decides
  staleness from two RUNTIME facts: when this process started
  (`GetProcessTimes`) versus when the file it was launched from was last
  written. Not two version strings — an equal version does not mean an equal
  build on a branch that ships many builds per version, and a version resource
  is stamped by the packaging pipeline rather than by whatever replaced the
  file. Unknown timestamps are never stale: an unanswerable question must not
  produce a notification telling someone to restart.
- `provenance.zig` gained `started` and `newer_build_installed`, and About now
  prints the process's own start time. The file's mtime appears ONLY inside the
  stale-build paragraph, labelled as the other build's — the mixing is gone
  rather than relabelled.
- When a newer build is on disk, About becomes the offer: **Restart Now /
  Later**. And the app does not wait to be asked — a 60-second timer raises a
  tray balloon once per build that appears on disk, and a click spawns the new
  exe (escaping the job object, or it would die with us) and quits this one.
  Spawn first, quit only if the spawn worked: a failure must leave the user
  with the terminal they have.
- `build-msi.sh` sets `ARPDISPLAYVERSION` from `--semver`, so Apps & Features
  shows `1.35.0` while `ProductVersion` keeps being the `yy.m.dNN` number that
  guarantees upgrade sequencing. The package is read back at build time and the
  build fails if the property is missing or wrong.

## Validation criteria

- [x] About reports the version of the process it is running, with no field
      sourced from a different build. — `test\win32\ipc-version.ps1` section 1
      asserts the running commit/pid/mode and a separately-labelled `started`
      stamp; section 2b asserts the identity lines still describe the RUNNING
      build while a newer file sits at its path.
- [x] When a newer build is installed on disk than the one running, the app
      says so and offers to relaunch - unprompted, not buried. — section 2b
      proves the detection and the sentence live (rename-aside + fresh file =
      the real msiexec state, not a simulation). The balloon and the About
      branch are wired but not themselves observed by a harness, because
      acceptance scripts run on a background desktop with no notification area;
      **T1211** carries that gap rather than leaving it unrecorded.
- [x] Apps & Features shows `1.35.0`, matching the website and the release tag.
      — `ARPDISPLAYVERSION`, asserted statically by `release-artifacts.ps1`
      A20-A22 and read back out of the compiled package by `build-msi.sh`
      itself. Not yet read off a real installed machine (that needs an install
      this box may not perform): **T1210**.
- [x] After an upgrade + relaunch, About, `--version`, and Apps & Features all
      agree. — true by construction once the three above hold: after a relaunch
      the process IS the file, so About and `--version` read the same
      `build_config.version_string`, and `ARPDISPLAYVERSION` is that same
      semver. The end-to-end observation on a real install is T1210.
- [x] A test asserts the three surfaces agree, so they cannot drift apart again.
      — `ipc-version.ps1` (guard `build-identity`, covering `provenance.zig`,
      `image_freshness.zig`, `tray_notify.zig`, `src\cli\version.zig`) plus
      `release-artifacts.ps1` A20-A22.

## Also fixed here

`ipc-version.ps1` reported **ALL PASS over sections it never ran**: a
terminating error unwound to the outer `finally` and the tail printed a green
verdict for a body that stopped a third of the way through. (The first cut of
section 2b triggered it — Windows refuses to re-stamp a file mapped for
execution.) The script now sets a sentinel on the last line of the body and
asserts it after the teardown. Its `$script:skipped` counter was also never
initialised, and `$null -eq 0` is FALSE in PowerShell, so the stamp condition
this task added would have been permanently unsatisfiable.
