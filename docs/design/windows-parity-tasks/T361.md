# T361 - No suite runner: the GUI acceptance suite has never been run end to end, so order-independence is argued rather than measured

## In plain terms

We have a big pile of automated checks that drive the real Windows app - open
windows, click things, read what comes back. Nobody could ever run them all at
once, so each work session ran the two or three it thought were related and the
rest quietly rotted. When this lands there is one command that runs the whole
pile, prints a line per check as it goes, and writes the result to a file that
survives the run being interrupted - so we finally know how many of these
checks still pass, which ones are broken, and how long the whole thing takes.

## Goals

- [x] one command runs the suite and reports a verdict per script plus a total
- [x] a hanging script costs one script, not the whole run
- [x] the run survives being killed: results so far are on disk, and it resumes
- [x] comparing two runs answers "did any verdict move?" - the order check
- [x] the real wall-clock cost is measured and written down here

## Validation criteria

- [x] `scripts\suite-run.ps1 list` enumerates the suite and classifies gui/cli
      - `test\win32\suite-run.ps1` section A, ALL PASS (45 assertions)
- [x] a fixture suite of known-answer scripts is scored correctly for all five
      verdict kinds, including exit-0-with-no-verdict scored as NOT a pass
      - section B (B4 is that arm)
- [x] a hanging script is killed at the timeout and the sweep continues
      - section C, including C4: the child process is really gone
- [x] `summary.json` holds completed rows while the run is still going, and
      `-Resume` does not re-run them (measured by counting real invocations)
      - sections E and F
- [x] `compare` is STABLE on identical runs and names the script that moved
      - section G; and on the live suite, forward/forward/reverse over 16 GUI
        scripts compared STABLE (below)
- [x] the leak sweep kills a process under the given repo's zig-out and leaves
      one outside it alone - section I, with `-NoSweep` as the control
- [x] the per-script and total runtimes in the report are the ones measured
      - section J, after the first version reported 116.2 s as "2m 56s"
- [x] a real sweep of the live suite is run and its rate recorded in this file
      - 63 of 241 scripts, numbers below; the rest is T1094

## Summary

There is no way to run the win32 acceptance suite. `test\win32\` holds 80+
scripts, 52 of which drive a GUI, and every turn runs the two or three it
believes it touched. Nothing runs the rest, so a change to the shared harness
(`lib\TestDesktop.ps1`, `lib\ChromeGeometry.ps1`, `lib\CleanSlate.ps1`) is
validated against a hand-picked sample and the other 49 scripts are found broken
by whichever future turn happens to open one.

T267 is the concrete case. Its Validation says *"run the GUI suite twice back to
back, and then in reverse order"* - and that cannot be done, because there is no
runner and no measured runtime. Its central fix (clear `window_placement-debug`
before every launch) makes every unsized script open at the built-in 800x600
instead of an inherited size, which is a **behavior change for ~40 scripts** that
was validated on six of them.

## Evidence (2026-08-02)

A throwaway runner - launch each GUI script, wait, keep the last verdict line -
was written and started during T267. In ~18 minutes it completed **two** scripts
(`activity-monitor.ps1` ALL PASS (82), `activity-monitor-remote.ps1` ALL PASS
(33), both of which never size their window, both green at the new default). At
that rate one forward pass is hours, so it was abandoned rather than allowed to
own the turn.

That number IS the finding: the suite is not merely un-run, it is un-runnable in
a turn as currently written, and nobody has measured that until now.

## The fix

- A real runner in `scripts\` (not scratchpad): run N scripts, per-script
  timeout, one verdict line each, a machine-readable summary file, and
  `-Order forward|reverse|<list>` so T267's order-independence check is one
  command.
- **Make it parallel-safe or explicitly serial.** The scripts fight over the
  same debug IPC endpoint and the same `%LOCALAPPDATA%\ghoztty` state, so naive
  parallelism corrupts them. Either give each worker its own
  `GHOZTTY_PIPE_SUFFIX` + `LOCALAPPDATA` (most already accept one) and run K at
  a time, or keep it serial and publish the honest wall-clock number.
- **Report per-script runtime.** A suite nobody can afford to run is the same as
  no suite; the slow scripts need to be visible before they can be argued about.
- Then discharge T267's real Validation: forward, forward again, reverse - same
  verdicts every time.

## Validation

- One command runs every GUI script and prints a verdict table plus a total.
- Two consecutive forward runs and one reverse run produce identical verdicts.
- The runtime is written down in this file, so the next turn can budget for it.

## What landed (2026-08-22)

`scripts\suite-run.ps1` - `run` (default), `list`, `compare`. `-Set gui|cli|all`,
`-Order forward|reverse|<explicit list>`, `-Include`/`-Exclude`, `-Limit`/`-Skip`,
`-TimeoutSec`, `-OutDir`, `-Resume`, `-NoSweep`, `-DryRun`. Each script runs as
its own `powershell -File` child with stdout+stderr in a per-script log, scored
by the suite's own verdict contract, one line printed as it goes and one row
written to `summary.json` the moment it lands. Acceptance:
`test\win32\suite-run.ps1` (45 assertions), stamped through `guard-due`.
Documented in `docs/claude/testing.md`.

### The measured number

First real sweep, 2026-08-22, forward, all 241 selected, `-TimeoutSec 300`:
**63 scripts in 37.9 minutes** before it was stopped so the turn could close.

- mean **36.1 s** per script, median **17.7 s**
- slowest in the sample: `chrome-theme.ps1` 198 s, `agent-upgrade.ps1` 173 s,
  `agent-sharing-uplink.ps1` 160 s, `activity-monitor-probe-fail.ps1` 151 s
- **a full forward pass is therefore about 2h 25m**, and T267's
  forward/forward/reverse is about **7 hours**

So the finding the task was filed on is confirmed and now has a number: this
suite cannot be swept inside an ordinary turn. It CAN be swept across turns -
that is what `-Resume` is for - and a dedicated turn is what T1094 asks for.

### What the sweep found in its first 63

- 59 pass, 4 fail: `agent-autostart.ps1`, `caption-bar.ps1`,
  `chooser-close-chord.ps1`, `chooser-orphan-badge.ps1`. Nobody had run any of
  them recently enough to know.
- 2 scripts leaked a live `zig-out` process on the way out
  (`agent-instance-lineage.ps1`, `agent-relay-session-e2e.ps1`). The runner's
  between-script sweep is the only reason that is visible.
- `ipc-version.ps1` fails on every turn that commits, by construction - filed
  as T1093.

### Order independence

Discharged on a measured subset rather than argued: the 16 fastest GUI scripts
in the sample, run forward, forward again, and reverse (3m 27s / 3m 26s /
3m 25s, ALL PASS each time), then

```
scripts\suite-run.ps1 compare -Runs ord-f1,ord-f2,ord-r1
  -> SUITE COMPARE STABLE (16 scripts, identical verdicts across 3 runs)
```

The whole-suite version of the same check is T1094's, and costs the ~7 hours
above.

### Serial, deliberately

Parallel workers cannot share one `zig-out`: 91 scripts compute the exe path
internally and `CleanSlate` kills the app under test by exact ExecutablePath, so
each worker's clean slate would kill the other's app mid-assertion. The full
argument and the route out are T1092.
