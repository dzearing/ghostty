# T483 - reset-context acceptance: B7 intermittently fails - the continuation is not delivered to a pane whose /clear failed

## In plain terms

The test that guards the session-restart machinery fails about one run in three,
in a part of it that has nothing to do with what is being tested. A test that
cries wolf is the same problem as an alarm that cries wolf: after the second
false failure nobody reads the result, and the run stops protecting anything.
Either the test is wrong about what it should expect, or a keystroke really does
go missing sometimes — and which of those it is matters, because the second one
would mean the loop's own continuation can be dropped.

## Goals

- [ ] know which of the two it is, from the diagnostics the run now prints
- [ ] `test\win32\reset-context.ps1` passes repeatedly (>= 5 consecutive runs)

## Summary

`test\win32\reset-context.ps1` section B drives the pre-fix helper (composer
wipe deleted) against `proxy-normal`, reproducing the filed 2026-07-28 symptom:
`nn/clear` arrives as ordinary text, the clear fails, and the helper shouts.
B7 then asserts the part that must hold anyway — **the continuation is sent
regardless** (liveness beats cleanliness).

Observed 2026-08-05 while extending the script for T182: B7 failed on 1 of 3
otherwise-identical runs. In the failing run the helper's OWN read-back also
reported the continuation missing (the B pane's banner carried the
`never echoed the continuation and did not repaint for 10s` text rather than the
usual `'/clear' is still on screen` one), so the pane oracle and the helper
agreed: `RC-TEXT[continue-marker-B]` never appeared. Runs 2 and 4 passed with
the identical script and no code change between them. Sections A and C-F were
stable across all runs.

## What is known

- It is **not** the T182/T261 change: sections E/F (added in the same commit)
  passed every run, and B is untouched by it.
- The B pane is the only one where `+set-banner` fires **before** the
  continuation send — a banner insets the terminal and reflows it, which is a
  difference worth suspecting before anything else.
- The other candidate is the T428 framing edge: if the trailing CR is consumed
  as part of the bracketed paste, the text sits unsubmitted in the composer,
  which produces exactly this pair of symptoms.

## The fix

First reproduce with the evidence the script now prints. B7 dumps the helper's
`typed/send-keys/continuation` log lines and the pane tail at the moment of
failure (added with T182 — the shared `/tmp/reset-context-last.log` is
overwritten by sections C-F, so the evidence had to be captured in-place).
That tells the two hypotheses apart: text sitting in the composer means the
submit was swallowed; nothing on screen at all means the write never landed.

## Validation

- Five consecutive `test\win32\reset-context.ps1` runs, all `ALL PASS`.
- If the cause is a real dropped submit, it also gets a unit or acceptance
  test at the layer where it happens, not just a steadier B7.
