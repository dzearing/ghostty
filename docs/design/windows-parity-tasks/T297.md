# T297 - Activity Monitor: the DIALED (owned-connection) path has no success-case coverage

## Summary

Filed by **T295**. The Activity Monitor reaches a remote machine two ways, and
only one of them is proven to WORK on the box:

- **Reuse** (borrowed connection) — `test/win32/activity-monitor-remote.ps1`
  drives it against a loopback agent end to end, including the ownership rule
  (the window's session survives the panel closing).
- **Dial** (owned connection) — `test/win32/chooser-menu.ps1` proves only that
  the button *attempts* a dial and *fails honestly* against a fake directory
  relay that is not an agent endpoint. **Nothing exercises
  dial → sample → free.**

That is the gap, and it is on the riskier of the two paths, because the dial is
the one that OWNS what it opens: it is the only path where `close` frees a
transport, where `shutdown()`-before-join has to unblock a parked RPC, and where
a dial landing after its panel closed has to be torn down by
`ActivityMonitor.onDialed` instead of adopted. Every one of those is a leak or a
use-after-free when it is wrong, and all of them are currently argued from code
reading plus a unit test of `panelMatches`, not from a run.

## Why it was not done in T295

The dial is relay-only (a chooser machine is a relay device), so a success case
needs a fake relay that answers `GET /v1/client/devices` **and** upgrades
`/v1/client/connect?device=<id>` to a WebSocket bridged to a real
`ghoztty-agent`. `chooser-menu.ps1`'s fake relay does the first half only.

## Shape

Extend the fake relay in `chooser-menu.ps1` (or hoist it to
`test/win32/lib/`, which is where a second consumer says it belongs) into a
minimal rendezvous bridge: accept the WebSocket upgrade and pipe frames to a
loopback agent's TCP port. `src/remote/relay_dial.zig` already accepts an
`http://` base as plaintext `ws://` precisely for loopback test relays, so no
TLS is involved.

Then assert, in a new lane of `activity-monitor-remote.ps1`:

- the chooser's Activity button dials and the panel samples with
  `root=<agent pid>` (the T295 oracle);
- closing the panel FREES the connection — the agent sees the client go away
  (its own log), and the app leaks nothing;
- a panel closed WHILE the dial is in flight (point the device at a listener
  that accepts and stalls) neither crashes nor leaks: `onDialed` logs
  "dial landed after its panel closed" and tears the transport down.

## Validation

- Both `zig build test` lanes plus `zig build test-agent` green; P1-P3 ALL PASS.
- The new lane passes, and its own negative control (asserting the panel
  sampled LOCALLY) fails.
