# T297 - Activity Monitor: the DIALED (owned-connection) path has no success-case coverage

## In plain terms

Picking a machine in the machine list and hitting **Activity** opens a live
process monitor for that machine. Nothing on this box had ever checked that it
WORKS — only that it fails politely when the machine is unreachable. So the
part where the app opens a connection of its own, shows you the other
machine's processes, and hands that connection back when you close the window
was believed rather than known, and the ways it could go wrong are the
expensive ones: a window that stays connected after you close it, or an app
that falls over when a slow machine answers a moment too late.

## Goals

- [x] a fixture where the machine in the list is a REAL reachable machine, not
      a directory entry
- [x] pressing Activity dials, connects, and shows the OTHER machine's
      processes (proved by the snapshot's root pid, not by the table looking
      populated)
- [x] closing the panel gives the connection back, measured from outside the app
- [x] closing the panel while the machine is still answering neither crashes
      nor leaks
- [x] a negative control that fails, so the run cannot be green by accident

## Summary

Filed by **T295**. The Activity Monitor reaches a remote machine two ways, and
only one of them is proven to WORK on the box:

- **Reuse** (borrowed connection) — `test/win32/activity-monitor-remote.ps1`
  drives it against a loopback agent end to end, including the ownership rule
  (the window's session survives the panel closing).
- **Dial** (owned connection) — `test/win32/chooser-menu.ps1` proves only that
  the button *attempts* a dial and *fails honestly* against a fake directory
  relay that is not an agent endpoint. **Nothing exercises
  dial → sample → free.**

That is the gap, and it is on the riskier of the two paths, because the dial is
the one that OWNS what it opens: it is the only path where `close` frees a
transport, where `shutdown()`-before-join has to unblock a parked RPC, and where
a dial landing after its panel closed has to be torn down by
`ActivityMonitor.onDialed` instead of adopted. Every one of those is a leak or a
use-after-free when it is wrong, and all of them are currently argued from code
reading plus a unit test of `panelMatches`, not from a run.

## Why it was not done in T295

The dial is relay-only (a chooser machine is a relay device), so a success case
needs a fake relay that answers `GET /v1/client/devices` **and** upgrades
`/v1/client/connect?device=<id>` to a WebSocket bridged to a real
`ghoztty-agent`. `chooser-menu.ps1`'s fake relay does the first half only.

## Shape

Extend the fake relay in `chooser-menu.ps1` (or hoist it to
`test/win32/lib/`, which is where a second consumer says it belongs) into a
minimal rendezvous bridge: accept the WebSocket upgrade and pipe frames to a
loopback agent's TCP port. `src/remote/relay_dial.zig` already accepts an
`http://` base as plaintext `ws://` precisely for loopback test relays, so no
TLS is involved.

Then assert, in a new lane of `activity-monitor-remote.ps1`:

- the chooser's Activity button dials and the panel samples with
  `root=<agent pid>` (the T295 oracle);
- closing the panel FREES the connection — the agent sees the client go away
  (its own log), and the app leaks nothing;
- a panel closed WHILE the dial is in flight (point the device at a listener
  that accepts and stalls) neither crashes nor leaks: `onDialed` logs
  "dial landed after its panel closed" and tears the transport down.

## What landed

`test\win32\activity-monitor-dialed.ps1` — a harness of its own rather than a
lane of `activity-monitor-remote.ps1`, because the two need different fixtures
(that one opens a panel from a remote WINDOW's palette; this one needs a
chooser, a relay device and a signed-in account) and that script is already 785
lines across six lanes.

The fixture T297 said had to be built already existed: `lib\FakeRelay.ps1`
(T319) is exactly the client-side bridge described in **Shape**, and four
harnesses already dial through it. So the work was the lane, not the fixture.

Two departures from the plan above, both recorded in the script's header:

- **The agent's own log is not the free oracle.** The agent logs nothing per
  connection, so "the agent sees the client go away" is unobservable from here.
  What is observable from OUTSIDE the app is its ESTABLISHED socket count
  (`Get-NetTCPConnection`), which is the stronger claim anyway: a panel that
  only believes it let go still holds one.
- **A `BRIDGE down` in the relay log is asserted for the LATE dial only.** A
  freed `WsClient` sends a bare TCP FIN and no WS close frame (deliberate —
  `ws_client.closeImpl`, the T81 panic), and `FakeRelay`'s pump only reads a
  bridge when `NetworkStream.DataAvailable` is true, which is
  `Socket.Available != 0` and therefore false at a bare EOF. So it notices a
  bridge it had pushed bytes through and leaks an idle one, exactly as its own
  header says. Asserting otherwise would be asserting a property of the fake.
