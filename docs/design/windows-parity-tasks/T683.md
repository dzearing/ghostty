# T683 - Mac: does +rearrange leak the dropped pane's session there too?

## In plain terms

On Windows we just found that rearranging a window's panes from the command
line, in a way that drops a pane, left that pane's program running invisibly
forever. The same command exists on macOS; nobody has checked whether it has
the same problem. This is the check, and the fix if it does.

## Summary

T128 measured the win32 `+rearrange` handler: a layout that omits a pane
destroyed the pane but never set close intent, so its agent session DETACHed
and lingered alive, pinned and unreferenced, forever. The fix marks close
intent on exactly the omitted leaves, gated on
`agent_recovery.closesDepartingLeaf` → `sessionSpared` so a session the new
tree still references is never ended (main's `e65cfa4d5` invariant).

Mac's `+rearrange` swaps trees through the Swift controller. Since main's
`e65cfa4d5` HARDENED the "departed leaf ⇒ close" inference out of the Mac swap
path — correctly, for recovery-style swaps — the same asymmetry may now apply
there: the dropped pane departs and nothing ends its session. Unverified from
this seat.

Measure it the way T128 did: two agent-backed panes, `+sessions --json`,
`+rearrange` to a layout naming only one, `+sessions --json` again. If the
dropped pane's session is still alive, adopt T128's shape — mark exactly the
omitted leaves, never a leaf whose session id the new tree still references.

## Validation criteria

- [ ] Measured on macOS: `+sessions --json` before/after a `+rearrange` that
      drops an agent-backed pane, recorded in this file either way
- [ ] If it leaks: the dropped pane's session ends and every kept pane's
      survives (the `sessionSpared` invariant holds)
- [ ] A Mac-side test covering both directions (drop ends it, reshuffle
      does not), mirroring `test\win32\rearrange-session-drop.ps1`
