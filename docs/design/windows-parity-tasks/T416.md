# T416 - The test hang follows the WebView2 host-floor test, not the lane: win32 lane wedged twice today with one binary and -j1

## Summary

Found by T118 (2026-08-03). **`zig build test -Dapp-runtime=win32` hangs the
same way T409 describes for `test-agent`** — the test binary sits at frozen CPU
and never exits — and it did so with **one** test binary resident and the build
run **`-j1`**. That refutes T409's framing ("its two test binaries deadlock when
run *concurrently*") and re-points the investigation at what both lanes share.

## Evidence (this box, 2026-08-03)

Hung run, sampled twice 8 s apart:

| fact | value |
|---|---|
| test binary | `.zig-cache\o\ba86b471763da0f4ba450f17c7369848\ghostty-test.exe --listen=-` |
| parent | `build.exe … test -Dapp-runtime=win32` (so: the WIN32 lane, not `test-agent`) |
| CPU | 51.36 s → 51.36 s (frozen, not spinning) |
| started | 07:11:30, killed at 07:24 |
| children | **6 `msedgewebview2.exe`** against `…\ghoztty\EBWebView-debug`, all spawned 07:12:23 — i.e. 53 s into the run, then nothing |

The same lane hung earlier the same morning (06:26, killed at 06:40, also
`ghostty-test.exe`, also zero CPU), and **passed** in between (exit 0, ~15 min),
so it is intermittent rather than a wedge introduced by a change.

Then, in the same turn, `zig build test-agent -j1` hung too:
`ghoztty-agent-test.exe` frozen at **121.5 s CPU** across a 9-minute sample,
one binary resident, killed at ~07:44. **Three hangs in one turn, in both
lanes, with `-j1` in force for two of them.** T409's `-j1` line should be
demoted from "workaround" to "changes the timing, sometimes".

## The discriminator T409 asked for, run: it is NOT `--listen=-`

T409's cheap experiment was "run the binary directly, without `--listen=-`".
Done, same turn, on the very binary the build runner had wedged:

```
.\.zig-cache\o\ba86b471763da0f4ba450f17c7369848\ghostty-test.exe   (no --listen)
  -> frozen at 48.92 s CPU (sampled twice, 10 s apart), 6 fresh
     msedgewebview2.exe children, killed by a 900 s watchdog
  last stderr before the freeze:
     [viewer_pane] (warn): reload: file re-rendered to headings=2 first=Delta
     [viewer_pane] (warn): watch: in-place save -> headings=3 first=Zeta
     [viewer_pane] (warn): watch: atomic save -> headings=2 first=Iota
```

**So the build runner is not involved at all** — no pipe, no grandchild handle
inheritance, no second binary. T409's cause 2 is refuted and its cause 1 is the
survivor. The freeze lands in the `ViewerPane` group, immediately after the
watch/reload tests and where the host-floor test stands up a real WebView2.

For contrast, the same script ran the two agent binaries directly right
afterwards and BOTH passed clean: `ghoztty-agent-test` **3787 passed / 76
skipped / 0 failed**, `ghoztty-agent-core-test` **3715 / 68 / 0**. The lane
that hangs under the build runner passes without it; the binary that hangs,
hangs either way.

## What that narrows

T409's two candidate causes were (1) a shared fixed-name resource — with the
`EBWebView-debug` user-data-dir named as the loudest suspect — and (2) the
build runner's `--listen=-` plumbing stalling when a child spawns a grandchild
that inherits the pipe handles. This run keeps BOTH alive but kills the
"two binaries at once" premise: there was one binary, and `-j1` (T409's stated
workaround) does not prevent it.

What both lanes share is the **WebView2 host-floor test** — the win32 lane's
`apprt.win32.ViewerPane.test."host floor: a real controller on a real window,
on this box"` and the WebView2 that `ghoztty-agent-test` stands up. In both
hangs the msedgewebview2 tree is alive and the test process is blocked. The
grandchild-inherits-the-`--listen=-`-handles theory (cause 2) fits a
single-binary hang exactly, and the WebView2 host is precisely a spawner of
grandchildren.

Also worth checking: this box has **long-lived `msedgewebview2.exe` processes
from 2026-07-29** belonging to the user's installed release (its own
`EBWebView` dir, no `-debug`), so a contended *browser-wide* singleton is not
ruled out by the user-data-dirs being different.

## Fix

1. Discriminate: run the win32 test binary directly (no `--listen=-`) in a loop
   until it hangs or clearly does not — that is the cheapest test of cause 2,
   and it needs no change to ship.
2. If `--listen=-` is implicated, stop the WebView2 host from inheriting the
   build runner's handles (spawn it with explicit non-inherited handles), or
   run that one test in a child process of its own.
3. If it is the user-data-dir, give each test run a unique one
   (`EBWebView-test-<pid>`), the way `session-snapshot-reattach.ps1` already
   gives itself a per-run `LOCALAPPDATA`.

Whatever the cause, **a floor lane must not be able to hang silently**: add a
watchdog/timeout so the lane fails loudly instead of looking busy forever
(T409's "no output, no failure, just a turn that looks busy" is the real cost,
and it has now consumed time in three separate turns).

## Validation

- 10 consecutive `zig build test -Dapp-runtime=win32` runs with no hang, or a
  hang that now reports a timeout failure within a bounded time.
- Same for `zig build test-agent` (T409's original lane) — the fix should close
  both, and if it does not, that itself is evidence worth recording.
