# T495 - Dragging the SECOND divider in a 3-column layout jumps ~200px right and stops tracking the mouse

## In plain terms

With three side-by-side panes, dragging the divider between the first two
works, but grabbing the divider between the last two makes it leap about
200px to the right the moment the mouse moves, and from then on it sits well
away from the pointer instead of following it. Any window with three or more
columns (or rows - the same math handles vertical splits) shows it.

## Goals

- [x] Every divider tracks the pointer 1:1, at any nesting depth
- [x] A grabbed divider that hasn't moved yet stays exactly where it was
- [x] Regression coverage for nested-split drag math (the existing tests only
      exercise the root divider)

## Summary

Reported live by the user 2026-08-05: three panes at roughly 1/3 each; first
divider drags correctly; the second jumps ~200px right and is mispositioned
relative to the mouse for the whole drag.

**Root cause (read from the code, not yet fixed):** `updateDividerDrag`
(`src/apprt/win32/Window.zig:2709`) maps the mouse to a ratio with

```
total = drag_start_rect.right - drag_start_rect.left   // surfaceRect(): the WHOLE content area
new_ratio = (x - drag_start_rect.left) / total
```

`drag_start_rect` is `self.surfaceRect()` (`startDividerDrag`, line 2701) -
the full window content rect. That is only correct for the ROOT split, whose
region IS the whole surface. A nested split's ratio is relative to **its own
sub-rectangle**. For 3 equal columns the tree is `split(1/3) -> [pane1,
split(1/2) -> [pane2, pane3]]`; the second divider sits at x = 2/3·W, so the
first motion tick computes `new_ratio = 2/3 = 0.667` and applies it to the
nested split, moving that divider to `1/3·W + 0.667·(2/3·W) = 0.778·W` - a
rightward jump of `0.111·W`, which on a ~1800px-wide window is exactly the
~200px the user measured. The divider then keeps absorbing the full-width
ratio for every subsequent move, which is why it tracks offset from the
pointer rather than under it.

**Fix sketch:** at `startDividerDrag`, capture the dragged NODE's own layout
rect (the per-node rects `layoutSplits` already computes when it walks the
tree - the same walk `hitTestDivider` uses) instead of `surfaceRect()`, and
compute the ratio against that rect in `updateDividerDrag`. The clamp to
[0.1, 0.9] then also becomes correct per-node. Put the mapping in
`split_geometry.zig` as pure logic and assert it at 1.0/1.25/1.5/2.0 scaling
per the design-system rule, with a nested-split case that reproduces the 3110
column geometry above.

## Validation

- Unit (win32 lane): pure ratio-mapping tests in `split_geometry.zig` - root
  divider unchanged; nested divider grabbed at its resting x yields its
  CURRENT ratio (no jump); pointer at the nested region's midpoint yields
  0.5; vertical analog.
- On-box: `test\win32\split-divider.ps1` extended with a 3-column drag of the
  second divider, asserting the divider's post-drag x tracks the sent pointer
  positions.

## What shipped (2026-08-06)

Exactly the fix sketch: `Window.splitRegionRect` (a sibling of
`dividerBandRectNode` returning the target split's own REGION rect) feeds
`startDividerDrag`'s `drag_start_rect`, and the pointer->ratio mapping moved
to `split_geometry.dragRatio` (pure, clamped [0.1, 0.9] per-node). The
region depends only on ANCESTOR ratios, which cannot change during the
node's own drag, so capturing once at drag start stays correct for the whole
gesture.

## Evidence (2026-08-06)
