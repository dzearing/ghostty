# T439 - RESUME-REUSE typed its prompt into a pane that had just re-attached, so it never arrived intact and the loop was left dead after a verified-good delivery

## Summary

Delivering T428 (2026-08-03 20:51): the swap and all three install locations
verified OK, then RESUME-REUSE typed the prompt 11 seconds after restarting the
app and re-attaching the pane, the arrival gate never saw it intact, and the run
exited 1 without submitting. The delivery was fine; the loop was dead.

## In plain terms

The upgrade installed correctly everywhere and then failed to tell the session
to carry on, so the loop stopped and a human had to restart it. The upgrade
noticed and said so, which is right — but "noticed" here means the work simply
stops for up to three quarters of an hour until a watchdog wakes up.

## Goals

- [ ] A verified-good delivery always re-enters the loop, or fails loudly in
      the turn that launched it rather than 45 minutes later
- [ ] The resume waits for the pane's session to be ready to receive, instead
      of typing on a fixed schedule after a re-attach

## Details

From `%TEMP%\ghoztty-upgrade.log`:

```
20:51:27 POST-SWAP VERIFY OK: ...\Programs\Ghoztty\ghoztty.exe now reports 'fca4acdf0'
20:51:34 resume decision: reuse (loop claude pid=16800 alive=True pane=6C13A7F3-...)
20:51:34 reuse: no running instance; starting the freshly installed exe
20:51:35 reuse: pane 6C13A7F3-... re-attached
20:51:45 RESUME-REUSE FAIL: the prompt did not arrive intact in pane ... it is NOT being submitted
```

Ten seconds between "pane re-attached" and the gate giving up. The send used
`--when-idle --idle-timeout=60`, so the idle poll is not the gap — the pane had
just been re-attached to a session-persistence PTY and the pane's *scrollback*
was being replayed while `+read` was being asked what is on screen. The gate
compares against a rendered tail (`Test-LoopPromptArrived`), so a tail that is
still filling in with replayed history cannot match, and the loop paid for it.

Note what this is NOT: not T428 (the Enter was never sent — the gate refused
before it), and not T210 (the prompt went via `--keys-file`, so nothing mangled
it in argv). It is the third distinct way this one handoff has failed, which is
itself the argument for making it robust rather than adding a fourth guard.

Candidate fixes, in order of appeal:

1. **Wait for the pane to be ready, not for a fixed count of polls.** After a
   re-attach, poll until the tail STOPS changing (the same stability signal
   `--when-idle` already uses) before typing at all.
2. **Retry the whole type-and-verify cycle** instead of exiting 1 on the first
   miss. It exits before its own `Escape` cleanup has any chance to matter.
3. **Do not fail the run silently to the watchdog.** `LAUNCH OK` was already
   reported to the launching turn by then, so nobody was watching — the same
   "reports success over a thing that did not happen" shape T200/T208 exist for.

## Validation

- `test/win32/upgrade-*.ps1` must stay ALL PASS.
- A new case that re-attaches a pane and immediately drives the resume, and
  asserts the prompt both arrives and is submitted.
