# T439 - RESUME-REUSE typed its prompt into a pane that had just re-attached, so it never arrived intact and the loop was left dead after a verified-good delivery

## Summary

Delivering T428 (2026-08-03 20:51): the swap and all three install locations
verified OK, then RESUME-REUSE typed the prompt 11 seconds after restarting the
app and re-attaching the pane, the arrival gate never saw it intact, and the run
exited 1 without submitting. The delivery was fine; the loop was dead.

## In plain terms

The upgrade installed correctly everywhere and then failed to tell the session
to carry on, so the loop stopped and a human had to restart it. The upgrade
noticed and said so, which is right — but "noticed" here means the work simply
stops for up to three quarters of an hour until a watchdog wakes up.

## Goals

- [x] A verified-good delivery always re-enters the loop, or fails loudly in
      the turn that launched it rather than 45 minutes later
- [x] The resume waits for the pane's session to be ready to receive, instead
      of typing on a fixed schedule after a re-attach

## Details

From `%TEMP%\ghoztty-upgrade.log`:

```
20:51:27 POST-SWAP VERIFY OK: ...\Programs\Ghoztty\ghoztty.exe now reports 'fca4acdf0'
20:51:34 resume decision: reuse (loop claude pid=16800 alive=True pane=6C13A7F3-...)
20:51:34 reuse: no running instance; starting the freshly installed exe
20:51:35 reuse: pane 6C13A7F3-... re-attached
20:51:45 RESUME-REUSE FAIL: the prompt did not arrive intact in pane ... it is NOT being submitted
```

Ten seconds between "pane re-attached" and the gate giving up. The send used
`--when-idle --idle-timeout=60`, so the idle poll is not the gap — the pane had
just been re-attached to a session-persistence PTY and the pane's *scrollback*
was being replayed while `+read` was being asked what is on screen. The gate
compares against a rendered tail (`Test-LoopPromptArrived`), so a tail that is
still filling in with replayed history cannot match, and the loop paid for it.

Note what this is NOT: not T428 (the Enter was never sent — the gate refused
before it), and not T210 (the prompt went via `--keys-file`, so nothing mangled
it in argv). It is the third distinct way this one handoff has failed, which is
itself the argument for making it robust rather than adding a fourth guard.

Candidate fixes, in order of appeal:

1. **Wait for the pane to be ready, not for a fixed count of polls.** After a
   re-attach, poll until the tail STOPS changing (the same stability signal
   `--when-idle` already uses) before typing at all.
2. **Retry the whole type-and-verify cycle** instead of exiting 1 on the first
   miss. It exits before its own `Escape` cleanup has any chance to matter.
3. **Do not fail the run silently to the watchdog.** `LAUNCH OK` was already
   reported to the launching turn by then, so nobody was watching — the same
   "reports success over a thing that did not happen" shape T200/T208 exist for.

## What landed

**It failed three times that day, not once.** `%TEMP%\ghoztty-upgrade.log` has
the identical shape at 09:04, 10:44 and 20:51 - every reuse-path delivery on
2026-08-03. Each one logs `reuse: pane <id> re-attached` **0-1 seconds** after
`starting the freshly installed exe`, and `RESUME-REUSE FAIL` 13-16s later.
`Wait-Instance` logs "answered after N failed poll(s)" only when N > 0 and never
did, so the VERY FIRST `+list` probe answered - the pane was listed within a
second of the app being launched.

That is the bug in one line: **`+list` presence was the only readiness gate.**
A pane is listed the moment restore builds its surface, while the agent is still
replaying the session ring into it. `--when-idle` cannot cover the gap either -
`src/cli/send_keys.zig` `waitForIdle` returns as soon as two consecutive reads
match, and a pane whose content has not arrived yet reads as empty, unchanged,
and therefore perfectly idle. So the send fired into a pane mid-restore and the
arrival gate compared against a tail that was still filling in.

Three changes, candidate fixes 1-3 from above, in that order:

1. **`Wait-LoopPaneReady`** (`scripts/loop-session.ps1`) - ready means the tail
   is NON-EMPTY **and** unchanged across N consecutive reads. Non-empty is the
   half `--when-idle` lacks: an un-replayed pane is the most convincing "stable"
   state there is. The reuse path waits on it before typing. Not fatal if it
   never settles - a pane whose session is simply printing should still be
   typed into, and the arrival gate is the real evidence either way.
2. **`Send-LoopPromptVerified`** (same file) - retries the whole
   type-and-verify cycle instead of exiting 1 on the first miss, clearing the
   composer between attempts so attempt N+1 cannot append to attempt N's
   fragment, and clearing it again on the way out. The T210 gate itself is
   untouched: text that did not read back intact is still never submitted.
3. **The failure no longer waits for the watchdog to notice.** The watchdog's
   own gates are written for a session that stopped on its own, so after a
   failed resume it reads `healthy` - the lock was beaten minutes earlier by the
   turn that launched the upgrade - and the loop stays dead for up to
   `-StaleMinutes` (45). `-Force` (new, `go-loop-watchdog.ps1`) skips the
   held-state and rearm gates for the one caller that KNOWS the loop is broken
   while the lock looks fine, and the upgrade invokes it on the spot. Everything
   downstream still applies, including "the pane is producing output, do not
   nudge": -Force says the heartbeat is not evidence, not that nothing is.
   `-ResumePromptFile` carries the prompt so the handoff has no argv hop (T210).

   The handoff is **gated on the lock being held by THIS pane**. That is the
   state it exists for, and requiring it rules out the dangerous neighbour: with
   no lock and no pane a forced tick falls through to `+new-window
   --command="claude --continue"`, which is the T138 fork.

## Found along the way

`test/win32/upgrade-no-fork.ps1` typed its section B and E fixture prompts - and
E1's `powershell -NoProfile -File ...\swallow.ps1` line - into this loop's live
Claude pane, because it isolates by `$env:USERNAME` and the pane's baked
`$GHOZTTY_IPC_SOCKET` outranks that. Filed as **T441** with the measurement; the
suite is fixed here (it now sets `GHOZTTY_PIPE_SUFFIX` and asserts isolation
before it types anything) because it blocked this task's validation. 21 other
scripts have the same hole, including P1-P3 - that sweep is T441's.
