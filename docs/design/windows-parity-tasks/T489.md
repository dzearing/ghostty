# T489 - A mistyped ghoztty CLI flag is either silently ignored or fails with no message

## In plain terms

Mistype a flag on a `ghoztty +...` command and you get no help finding it.
Some commands quietly ignore the flag and do the wrong thing; others fail and
print absolutely nothing, so all you have is a non-zero exit code. Either way
the terminal never tells you which word it did not understand.

## Goals

- [x] an unrecognized flag names itself in an error message (verb + flag +
      nearest-spelling suggestion + `--help` pointer, exit nonzero)
- [x] no field-parsing CLI verb silently ignores a flag it does not
      understand — the forwarding verbs (`+close`, `+split`, ... whose argv
      goes to the deliberately-tolerant server) are split out to T852
- [x] a `none`-lane unit test pins the message, plus an acceptance case

## Summary

Found while validating **T137** (2026-08-04) on `zig-out\bin\ghoztty.exe`
(Debug, win32). Two different wrong answers to the same mistake, neither of
which tells the user anything:

```
> ghoztty +show-config --session-persistence=false
exit=1   stdout=[]   stderr=[]

> ghoztty +list --bogus-flag=1
exit=0   (prints the window tree, flag ignored entirely)

> ghoztty +version --bogus-flag=1
exit=0   (prints the version, flag ignored entirely)
```

`+show-config` has an `Options` struct with no `_diagnostics` field, so
`cli/args.zig` `parse` returns `Error.InvalidField` (`args.zig:113`) — the
action propagates the error and the process exits 1 having written nothing to
either stream. `+list`/`+version` land on the tolerant side of the same
`canTrackDiags(T)` branch and swallow the field instead.

Neither is defensible: a typo in `--json` costs a script its output format
with no signal, and a rejected flag with an empty stderr is indistinguishable
from a crash. Note this is measured **through `cmd.exe` redirection**, not
PowerShell — `$LASTEXITCODE` after a native command in a PS 5.1 pipeline is
not trustworthy here (a clean `+validate-config` reports 1 in PowerShell and 0
through cmd), which is the standing reason on-box oracles gate on OUTPUT.

## Fix

Decide one behavior for every action and apply it uniformly: an unknown flag
should print `unknown option "--bogus-flag"` (naming the verb, and ideally the
nearest valid flag) on stderr and exit non-zero. That likely means giving the
action `Options` structs a diagnostics list, or handling `Error.InvalidField`
where actions are dispatched so the message exists in one place rather than
per verb.

## Validation

- `none`-lane unit test over the shared arg parser for the message text.
- An acceptance case per shape: a rejected flag prints something, and no verb
  exits 0 with an unrecognized flag.
