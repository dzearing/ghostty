# T1112 - chooser-close-chord.ps1 loses its Ctrl+W only inside a full sweep - it is green run on its own

## In plain terms

A check that Ctrl+W closes things is failing - but it also fails its own sanity check, the one that presses Ctrl+W in an ordinary terminal pane where it definitely should work. That pattern usually means the simulated keypress is not reaching the app at all, so this check currently proves nothing either way.

## Summary

`test\win32\chooser-close-chord.ps1` scored `3 FAILURE(S) (11 passed)` in the T1094 sweep:

```
1. positive control: Ctrl+W with a terminal focused closes the pane
  PASS the window holds two panes to start (found 2)
  PASS a terminal pane is there to aim the chord at
  FAIL Ctrl+W closed one pane (2 -> 2)

2. Ctrl+W with the chooser focused dismisses the CHOOSER
  FAIL Ctrl+W dismissed the chooser

3. FAIL the owner window is enabled again once the chooser is gone
```

**The positive control failing is the whole story.** Section 1 exists precisely to prove the chord CAN be delivered on this box before section 2 tests where it goes. It failed, so sections 2 and 3 are measuring nothing.

Everything else in the script is healthy - the chooser opens, has its filter field, disables its owner window, and the app survives. Only the keystroke does not land. That matches the input half of [[T1100]] and should be attributed there first.

History worth knowing: synthetic input on this box has failed for environmental reasons before (a service holding an unbeatable foreground lock and swallowing SendInput). Check the foreground owner before concluding anything about the product.
