# T1407 - Every other live-update claim in test/win32 rests on the same camera-repaints-it blind spot the paint probe just closed for the accent

## In plain terms

Several tests claim the app updates something on screen the moment it changes -
a banner, the activity readout, a themed panel. They all check it by taking a
photograph, and taking the photograph is itself what makes the app draw. So
they would all keep passing if the app stopped updating anything on its own,
which is exactly what was proved for the accent. Nobody has checked which of
the other claims are hollow the same way.

## Summary

T585 measured it for the accent and T1405 closed it: photographing a window
makes it paint (`-Sync` is `WM_PRINTCLIENT`, the default is
`PrintWindow(PW_RENDERFULLCONTENT)`), so a capture cannot distinguish "the app
invalidated this window" from "the app drew a frame because we asked". Every
`test/win32/` assertion phrased as *live update*, *refreshes*, *updates without
a relaunch* is a candidate for the same hollowness.

The tool now exists: `src/apprt/win32/paint_probe.zig` counts `WM_PAINT` per
surface and prints it under `GHOZTTY_PAINT_PROBE`, and `chrome-theme.ps1`
section G is the worked example (including G1, which measures that the chosen
surface is QUIET - a surface with a refresh timer, like the hero carousel's
150ms one, defeats a paint counter exactly as it defeated a pixel oracle).

The work is a SURVEY first, not a rewrite: enumerate the live-update claims,
and for each one measure - do not reason - whether it survives the code that
does the updating being removed. Only the ones that survive need a probe
surface and a G-style section. A claim that already goes red is fine and gets
recorded as such.

## Where

- `test/win32/*.ps1` - the live-update claims; start from a grep for
  `live`, `without a relaunch`, `refresh`.
- `src/apprt/win32/paint_probe.zig` - add a `Surface` per window that needs
  one, and call it from that window's `WM_PAINT` arm only.
- `test/win32/chrome-theme.ps1` section G - the pattern to copy.

## Validation criteria

- [ ] A written enumeration of the live-update claims in `test/win32/`, each
      marked survives-deletion / goes-red, with the build that showed it.
- [ ] Every claim found hollow either gains a paint-probe assertion that was
      RUN red against the deletion, or is re-labelled to what it really
      measures (the B4 remedy).
- [ ] The harnesses touched are green afterwards, and their guard-due rows
      cover any probe surface they now depend on.
