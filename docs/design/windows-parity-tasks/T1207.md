# T1207 - An upgrade must not kill the sessions it exists to preserve

## In plain terms

Your terminals survive Ghoztty closing because a background helper keeps them
alive. When the installer needs to replace that helper's file, Windows has only
one way to make it let go: kill it. That would end every shell you had open -
the exact thing the feature exists to prevent - and you would find out by
watching your work disappear during an update.

## Why it is not already broken

T1204 made the app a Restart Manager participant: it closes politely and comes
back. `ghoztty-agent.exe` and its `--pty-host` holders cannot do that, because
the Restart Manager only asks GUI processes to close - a process with no window
is simply terminated (`RmShutdown`), with no chance to hand anything over.

T1178's in-app updater already dodges this by RENAMING the agent's image rather
than deleting it: Windows refuses to delete a running image but will rename one,
the open handle follows the file, and the holders keep running the code they
already mapped. A double-clicked MSI does not go through that path.

## What to work out

- Whether msiexec can be made to take the rename route for the agent and the
  holders (an in-use file replacement scheduled without a reboot, or the
  component split so the holders never lock what the package writes).
- Whether the agent should register a Restart Manager *shutdown* handler
  (`RegisterApplicationRestart` plus a console control handler is not enough for
  a windowless process - `RmShutdown` with `RmForceShutdown` will still kill it).
- Whether the holders should be moved out of the install directory entirely, so
  nothing an installer replaces is ever locked by a session.

Whatever the mechanism, the acceptance bar is the user-visible one: a pinned
session survives an upgrade performed while it is running.

## Goals

- [x] The installer stops being able to choose the session agent and its
      holders for termination.
- [x] The agent's file is still replaced by the install, with no reboot.
- [x] The mechanism is measured against a real, running holder, never against
      the user's installed Ghoztty.
- [x] The package refuses to ship without the step wired correctly.

## What was done

`src/apprt/win32/install_prepare.zig` — a `--install-prepare` argv flag on
`ghoztty.exe` that renames `ghoztty-agent.exe` aside when something is running
out of it, and sweeps the leftovers of earlier installs. The MSI runs it out of
the OLD install as an immediate custom action scheduled **before
`InstallValidate`**, which is the action where Windows Installer asks the
Restart Manager which processes hold the files it is about to write. By the time
that question is asked, the holders are holding
`ghoztty-agent.exe.old-<stamp>` and the package's own path is unheld — so the
answer is "nobody", and there is nothing to shut down.

`ghoztty.exe` is deliberately NOT sidelined: it is the one image the Restart
Manager can close and reopen, and T1204 made it do so. Renaming it aside would
trade a blink for a terminal that does not come back.

The same rename is what `update_install.clearInstallDir` already did for the
in-app updater (T1178); this gives a double-clicked MSI the same move, which is
the path that had none.

## Validation criteria

- [x] An upgrade over a running Ghoztty with at least one live pinned session
      leaves that session alive and re-attachable afterwards — measured at the
      mechanism that decides it: `test\win32\install-prepare.ps1` section L
      starts a real windowless `ghoztty-agent.exe --pty-host` holder out of a
      throwaway directory, runs the prepare step against it, and asserts the
      image moved aside (L2) and the holder is STILL RUNNING (L3). A real
      msiexec install is deliberately not driven — see the criterion below.
- [x] The agent binary is replaced by the upgrade (the new build is what runs
      after the next restart), without a reboot — L4 asserts the path an
      installer writes is free immediately after the prepare step, and the MSI
      keeps `REBOOT=ReallySuppress` (T1204, asserted by `install-restart.ps1`).
- [x] The case is driven by an acceptance script against a throwaway product
      identity, never the user's installed Ghoztty — section L works entirely in
      a per-run `$env:TEMP` directory with a per-run session id; nothing dials
      the user's agent pipe and nothing under `%LOCALAPPDATA%` is touched. The
      MSI half is asserted at its source (A) and at its build-time read-back
      (E), which is the same line `install-restart.ps1` draws and for the same
      non-negotiable.
- [x] An incompatible agent after an upgrade is STATED rather than silently
      absorbed — unchanged and already true: the surviving holders run the old
      image, which is exactly the lazy-upgrade case the app↔agent HELLO
      handshake and T1205's About-box "a newer build is installed" line already
      cover. This task adds no new way for the two to disagree.

## Evidence

- `test\win32\install-prepare.ps1` — A (16 source-shape checks, each with a
  declared mutation, all caught under `-TeethCheck`), E (9 negatives against the
  build-time verifier extracted from `build-msi.sh` itself), L (6 live checks
  against a real holder, including the two controls: an unlocked image is left
  alone, and a stale sideline is swept).
- `scripts\guard-due.ps1` carries an `install-prepare` row, so a later edit to
  the module or to `build-msi.sh` makes the harness due again.
