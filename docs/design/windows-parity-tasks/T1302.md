# T1302 - Nothing has yet watched the Repair / Cancel prompt come out of a real msiexec

## In plain terms

When you run the installer for a version you already have, Ghoztty now asks
whether to repair or cancel instead of quietly doing nothing. The dialog itself
is tested; the installer ASKING for it is not - the case exists in the new
installer walkthrough but skipped on its first runs, because the newest
published package was built before that fix.

## Why it skipped

`test\win32\install-walkthrough.ps1` section D drives a real `msiexec /i` at
`/qr` over an install of the same version, waits for the app's
`GhozttyConfirmDialog`, clicks a button and reads msiexec's exit code (1602 for
Cancel, 0 for Repair). It runs only when the package carries the
`MaintenancePrompt` custom action; `win-v1.36.2` (commit `a5c770836`) predates
T1291, so the harness names that and skips rather than asserting the behaviour
of a build that never had it.

The daily publish supplies a package carrying the fix within a day of it
landing, so this is a re-run, not a rewrite.

## What to do

- Once a `win-v*` release built from `65da707e5` or later exists, run:

  ```
  powershell -NoProfile -File test\win32\install-walkthrough.ps1
  ```

- Section D must run rather than skip, and D1-D6 must pass. If the prompt does
  not appear under a real msiexec - the UILevel gate, the sequence position, the
  exit code mapping - that is the defect this case exists to find; file it.
- With D running and F5 unblocked (T1301), the walk has no skips left and stamps
  its guard row, which is what turns `install-walkthrough` from a report into a
  measurement.

## Validation criteria

- [ ] `install-walkthrough.ps1` runs section D against a published package and
      D1-D6 pass (dialog appears, buttons say Repair / Cancel, Cancel = 1602 and
      leaves the install untouched, Repair = 0).
- [ ] The run names the package it used, so the evidence says WHICH build was
      clicked through.
