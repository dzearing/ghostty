# T653 - A session id can outlive its byte stream

## In plain terms

Every terminal session has a running tally of how much it has printed. When
the background service that owns your terminals restarts, it can bring a
session back under the same name — but the tally starts over at zero, and
anything that wrote the old number down is now pointing at a place that no
longer exists. T532 fixed the damage that caused (windows that came back as
dead pictures). This task is about the mismatch itself: either the tally
should carry across, or a session that starts a new tally should not be
allowed to keep the old name.

## Goals

- [x] Establish from the code what actually happens to the tally on an agent
      restart
- [x] Settle the question and record the reasoning where the next person will
      find it
- [x] Leave a test that fails if the rule quietly changes

## Why this is filed separately

T532 is the VIEWER's defence and it is the right one to have permanently: a
client must never trust a resume point it did not check against the peer
(`Connection.resumeOffset`). But it is a defence, and the situation it defends
against is one this system creates on purpose:

- The agent's outbound offset (`session.out_offset`, the value reported as
  `ATTACHED.snapshot_at_offset`) counts bytes for the life of one CHILD.
- A session id is persisted in `sessions.json` and is deliberately reused when
  the agent materializes a session from disk and RELAUNCHes it (CLAUDE.md,
  "Session Persistence" / the reboot floor).

So after an agent restart, id `X` refers to a stream that starts at 0 while
every manifest and every attached viewer still holds offsets from the previous
stream. Nothing in the protocol says which of those two is wrong.

## The question to settle

1. **Carry the tally.** Persist `out_offset` (and enough of the ring) so a
   relaunched session continues its byte numbering. Recorded offsets stay
   meaningful, and gap-fill still works across an agent restart. Cost: the
   number becomes durable state that has to be written correctly, and a ring
   whose contents did NOT survive still cannot serve a replay for offsets it
   no longer holds — so the numbering would be honest while the DATA is not,
   which may just move the lie.
2. **Retire the id.** A RELAUNCH that starts a fresh stream mints a fresh
   session id (with the old one recorded as its predecessor, so the viewer can
   still find it). Then a stale manifest gets a clean `not_found` instead of a
   silently-different stream, and the reboot-floor restore reports honestly.
   Cost: touches the reboot-floor path and every consumer that assumes ids are
   stable across a relaunch.
3. **Nothing — the clamp is the answer.** Defensible, but then it should be
   WRITTEN DOWN in `docs/design/session-persistence.md` as a property of the
   protocol ("a session id does not imply a continuous byte stream; a client
   must validate its resume point against `snapshot_at_offset`"), so the next
   person does not rediscover it the way T532 did.

Whichever wins, the shared `ring_snapshot.zig` / reboot-floor code is where to
look first: it already snapshots ring CONTENT to disk for reboot scrollback,
so whether it also restores the OFFSET is the concrete first question, and the
answer may be that option 1 is already half-built.

## Answer (2026-09-08) - option 3: the id is not a stream, and now it says so

Established by reading the code, not assumed. `SessionStore.preloadRingSnapshot`
(`src/remote/agent/session.zig:2153-2177`) is the whole answer: on an agent
restart it loads the session's on-disk ring snapshot, **re-bases the ring at
offset 0**, appends the restart divider, and sets `out_offset` to the ring tail.
So a relaunched session does NOT resume the old numbering - it starts a fresh
count over the few KB that survived, under the id `sessions.json` recorded. The
code comment states the reason for base 0: a freshly restored viewer applies
DATA from 0 with no resync watermark, so a non-zero base would manufacture a
phantom gap.

Nothing on disk carries the old tally either - `session_meta.Record` persists no
output offset (its `holder_offset` is a *holder* stream watermark, sent as an
explicit ATTACH ack, which is the same principle one layer down: continuity is
negotiated, never implied by an identifier).

**Option 1 (carry the tally) is rejected**: only a ring's worth of bytes
survives, so an honest NUMBER over dishonest DATA would trade a detectable
mismatch for an undetectable one - the session could serve no replay below its
own head.

**Option 2 (retire the id) is rejected**: it puts a breaking change through the
app-agent compatibility boundary and through every consumer that assumes stable
ids (manifests, layout blobs, the chooser roster, `+sessions`), to remove a
mismatch a two-line clamp already handles on the side that cares.

**Option 3 stands, and the missing half was the writing-down.** The property is
now normative in `docs/design/session-persistence.md` section 5.4.3, with what
it obliges each side to do (the agent reports `ATTACHED.snapshot_at_offset`; the
client clamps to it via `Connection.resumeOffset` and rebases
`termio.Remote.attach_offset`; a head of 0 never clamps).

No decision file was opened: per the 2026-08-14 directive the user adjudicates
EXPERIENCE, and all three options are indistinguishable from the app - the
observable behaviour (a restored pane that is live) is identical under each.
This is a mechanism call, recorded here and in the log.
