# T268 - Diagnose the T229 field failure from the step trail: what the app was doing when it stopped

## In plain terms

When Ghoztty offers to restart its background helper and you say yes, the whole
terminal disappears instead. It is not a crash and not a freeze — Windows kills
it deliberately, because the app had been quietly adopted into the very group of
processes that the helper owns, and killing the helper takes down everything in
that group. The app never gets to do the part it promised: putting your windows
back. A guard process now relaunches it a moment later, so what a user sees is
their terminal blinking out and coming back empty rather than rebuilt.

This task is the diagnosis, and it is now settled with a measurement rather than
a hypothesis. The repair is [T675](T675.md).

## Goals

- [x] Read the T229/T421/T426 step trail out of a real field recurrence
- [x] Name the exact step the app stopped in
- [x] Establish the mechanism by measurement, not inference
- [x] Say plainly which earlier hypotheses are ruled out
- [x] File the repair as its own task with that mechanism as its subject

## THE ANSWER (2026-08-11, VERIFIED on box)

**The step: it dies inside `terminateAgent`, at the `TerminateProcess` call —
after the T426 job-facts measurement, before `pid N terminate returned`.**

**The mechanism: the app is a MEMBER of the agent's kill-on-close job, and the
agent holds that job's only handle.** Killing the agent closes the handle, and
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` terminates every member of the job — the
app among them. That is why there is no exception, no WER record and no further
log line: nothing went wrong in the app at all. Windows ended it on purpose,
one instruction into a call it never returned from.

Evidence, all of it checkable:

1. **The trail stops at the same place, every time.**
   `%LOCALAPPDATA%\ghoztty\ghoztty.log` carries **8** `user confirmed
   destructive agent refresh` lines and **6** step trails (T229's
   instrumentation postdates the first confirms; one trail has no confirm above
   it, which is the no-live-sessions path that needs none). Not one of the six
   completes: `agent restart: pid N terminate returned, exit wait=…` has **0
   occurrences in 425 018 lines**, and so does `terminated local agent pid`.
   The most recent (log line 421595, running `20260806-8db5dc509` → bundled
   `20260809-c30941aa0`, 3 live sessions) reaches `agent restart: job facts
   before the kill` and stops.
2. **The app did not crash.** No `Application Error` / `Application Hang` / WER
   record for `ghoztty.exe` around that refresh — the same absence T229 found
   three times.
3. **The relaunch guard watched it happen.** `relaunch guard: app pid 43076
   ENDED during the agent refresh` (line 421613), then `relaunched … as pid
   50572` — and pid 50572 is the app running on this box right now. The failure
   is not historical; it is what the current process is standing on.
4. **The job facts, measured at the kill:** `self_in_job=yes
   self_job_flags=0x2000 kill_on_close agent_in_job=yes SHARED_JOB=no`.
5. **Whose job that is, measured live from inside a pane.** A read-only probe
   run from this session (a descendant of a pane shell) reports
   `in_job=True`, `LimitFlags = 0x2000` — byte-identical to what the dying app
   logged — and the job's member list is **8 processes: the agent's three
   `cmd.exe` pane shells (`ppid=24620`, which is `ghoztty-agent.exe`) plus their
   descendants**. That is the process-global job `src/remote/agent/pty_child.zig`
   creates with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (0x2000, and no breakaway
   bits) and whose handle, by that file's own design comment, the agent "holds
   for its entire life and NEVER closes".
6. **How the app gets in.** `scripts\upgrade-ghoztty-windows.ps1` relaunches the
   app with a plain `Start-Process` from a hidden PowerShell that is itself a
   descendant of a Claude pane shell. A child of a job member is auto-assigned
   to that job, and this job grants no `BREAKAWAY_OK`, so there is no escaping
   it — which is also why the relaunch guard logs `breakaway spawn refused
   err=.ACCESS_DENIED; trying the shell-parent hop` (line 421596) on the way in.

### The control, from the same probe

The job's member list is **exactly** those 8 processes — no `ghoztty.exe` in it.
The app running right now is pid 50572, the one the relaunch guard started with
`escape=breakaway`, and it is therefore OUTSIDE the job that killed its
predecessor — and `IsProcessInJob(50572, NULL)` answers **False**, so it is in no
job at all, not merely a different one. (The live agent, pid 24620, answers
False too: T426's `spawnEscapingJob` is doing its half.) Same box, same build,
same lineage: the app that died was in a job with these exact flags
(`self_in_job=yes self_job_flags=0x2000`, by its own log line), the app that
replaced it is in none, and the only difference between them is how they were
launched.

That is the positive control for the repair as well as the diagnosis: escaping
the job is not a theory about what would help, it is the state the surviving
process is already in. It also predicts that a destructive refresh attempted on
this box *now* would succeed — which is precisely why this failure has always
looked intermittent, and why "it worked when I tried it" was never evidence.

## What this rules out

- **The T229 teardown hang** (`Connection.shutdown` joining peer threads) is not
  the cause. Moving it off the GUI thread was correct on its own terms and did
  not change the outcome, because the app was never hung — the trail proves it
  ran past the retire step and into the kill.
- **T426's shared-job hypothesis** — "the app and the OLD agent share a job" —
  is **ruled out in the field by its own measurement**: `SHARED_JOB=no`,
  answered conclusively (the member list came back complete, not truncated).
  The measurement was right and the question was wrong. What kills us is not the
  agent's MEMBERSHIP in our job but its OWNERSHIP of our job's last handle, and
  a process is never a member of the job it merely owns a handle to. This is
  worth stating loudly: a `no` on the wrong question reads exactly like an
  exoneration.

  T426's own `SHARED_JOB=yes` is not a contradiction and was not wrong — it came
  from `agent-upgrade.ps1` arm H, where the harness jails the app in a
  kill-on-close job and the pre-fix agent was spawned into it. That is the
  reverse direction (app's job killing the agent), it was real, and T426
  removed it by spawning the agent through `spawnEscapingJob`. The field
  direction is the one still live: the AGENT's job killing the app.

## Consequences worth naming

- The destructive refresh never performs the work its own dialog promises. The
  trail stops before `in-place recovery: re-dialed` and
  `destructive agent refresh finished: K window(s) rebuilt`, so the rebuild code
  is not "failing" — it is unreachable from this path today.
- The job kill takes **every** member down: the app, and every pane shell of
  every session, and their descendants. On this box that includes the Claude
  session running the loop.
- It was unreproducible in T229's four shapes for a reason that is now obvious:
  every one of them launched the app from a test harness, i.e. **outside** the
  agent's job. The bug is not in what the app does, it is in how the app was
  launched. Any future repro must start the app from inside a live pane.

What T229 established (all VERIFIED on box):

  refresh`, three times out of three. The next statement that logs is

- **No `Application Error` / `Application Hang` / WER event exists for
  `ghoztty.exe` around any of the three confirms.** So it did not crash. It
  either exited cleanly (nothing on that path logs, so it is indistinguishable)
  or it HUNG.
- It could NOT be reproduced on box, across four shapes: one fresh window /
  one idle pane (the pre-existing arm D), RESTORED windows with 3 live sessions
  across 2 windows, the same with every pane STREAMING output, and the same
  again under a genuinely older agent binary. Every one of them rebuilt
  correctly and the app survived.

## The leading hypothesis, and why it is only a hypothesis (SUPERSEDED — see THE ANSWER above)

Between the confirm line and the missing one, the GUI thread runs
`LocalAgent.retire` → `Connection.shutdown`, which **JOINS** the connection's
writer, control-reader, data-reader and heartbeat threads. A peer thread that
does not exit does not slow the app down, it wedges it — with no log line and
no crash event, which is exactly the observed signature.

T229 moved that teardown off the GUI thread (safe precisely because a retired
connection is deliberately never freed). If the hypothesis is right the failure
is gone. If it is wrong, the failure recurs — and now says where.

## What to do when it recurs

The step trail T229 added is the diagnostic. In `%LOCALAPPDATA%\ghoztty\ghoztty.log`:

```
warning(win32): user confirmed destructive agent refresh (...)
info(win32_local_agent): agent restart: begin (reading agent info file)
info(win32_local_agent): agent restart: retiring the shared connection (agent pid N)
info(win32_local_agent): agent restart: terminating agent pid N
info(win32_local_agent): terminated local agent pid N ...
info(win32_local_agent): in-place recovery: re-dialed the local agent (pid M)
info(win32): in-place recovery: rebuilt K window(s) ...
warning(win32): destructive agent refresh finished: K window(s) rebuilt
```

**The LAST line present names the step it stopped in.** A trail that ends at
`retiring the shared connection` is a teardown hang (hypothesis confirmed, and
the async teardown did not cover it); one that ends at `terminating agent pid`
is `TerminateProcess`/the exit wait; one that ends at `re-dialed` is the
rebuild.

If it stops after `begin` with the app still on screen, take a dump —
`cdb -p <pid> -c "~*k;q"` with MS public symbols, the T48 recipe in
`docs/design/t48-deadlock-dump-analysis.md` — and read the GUI thread's stack.
That is the one artifact that ends the guessing, and releases already ship
`-Dstrip=false` so it will symbolize.
