# T268 - Diagnose the T229 field failure from the step trail: what the app was doing when it stopped

## Summary

**T229 shipped the instrumentation and the leading-hypothesis fix, but it never
reproduced the field failure.** That is stated plainly here rather than buried
in T229's write-up, because the honest status of the user's bug is "probably
fixed, not proven fixed", and the next occurrence is the evidence that settles
it.

What T229 established (all VERIFIED on box):

- The app stops logging immediately after `user confirmed destructive agent
  refresh`, three times out of three. The next statement that logs is
  `restartForUpgrade`'s `terminated local agent pid ...` — **0 occurrences in
  the entire 8.6 MB log**, on any path.
- **No `Application Error` / `Application Hang` / WER event exists for
  `ghoztty.exe` around any of the three confirms.** So it did not crash. It
  either exited cleanly (nothing on that path logs, so it is indistinguishable)
  or it HUNG.
- It could NOT be reproduced on box, across four shapes: one fresh window /
  one idle pane (the pre-existing arm D), RESTORED windows with 3 live sessions
  across 2 windows, the same with every pane STREAMING output, and the same
  again under a genuinely older agent binary. Every one of them rebuilt
  correctly and the app survived.

## The leading hypothesis, and why it is only a hypothesis

Between the confirm line and the missing one, the GUI thread runs
`LocalAgent.retire` → `Connection.shutdown`, which **JOINS** the connection's
writer, control-reader, data-reader and heartbeat threads. A peer thread that
does not exit does not slow the app down, it wedges it — with no log line and
no crash event, which is exactly the observed signature.

T229 moved that teardown off the GUI thread (safe precisely because a retired
connection is deliberately never freed). If the hypothesis is right the failure
is gone. If it is wrong, the failure recurs — and now says where.

## What to do when it recurs

The step trail T229 added is the diagnostic. In `%LOCALAPPDATA%\ghoztty\ghoztty.log`:

```
warning(win32): user confirmed destructive agent refresh (...)
info(win32_local_agent): agent restart: begin (reading agent info file)
info(win32_local_agent): agent restart: retiring the shared connection (agent pid N)
info(win32_local_agent): agent restart: terminating agent pid N
info(win32_local_agent): terminated local agent pid N ...
info(win32_local_agent): in-place recovery: re-dialed the local agent (pid M)
info(win32): in-place recovery: rebuilt K window(s) ...
warning(win32): destructive agent refresh finished: K window(s) rebuilt
```

**The LAST line present names the step it stopped in.** A trail that ends at
`retiring the shared connection` is a teardown hang (hypothesis confirmed, and
the async teardown did not cover it); one that ends at `terminating agent pid`
is `TerminateProcess`/the exit wait; one that ends at `re-dialed` is the
rebuild.

If it stops after `begin` with the app still on screen, take a dump —
`cdb -p <pid> -c "~*k;q"` with MS public symbols, the T48 recipe in
`docs/design/t48-deadlock-dump-analysis.md` — and read the GUI thread's stack.
That is the one artifact that ends the guessing, and releases already ship
`-Dstrip=false` so it will symbolize.

## Validation

- The trail appears in order across a real delivery that shows the dialog, and
  ends at `destructive agent refresh finished`.
- If a recurrence is captured: the step it died in is named in this file, and
  the fix is a new task with that step as its subject.
