# T387 - Mac viewer: a UTF-8 BOM renders as a stray glyph and there is no file-size cap (T90e parity)

## Summary

T90e's Windows file viewer does two things `ViewerView.renderFileContent`
(`macos/Sources/Features/Viewer/ViewerView.swift:1921`) does not, and the
divergence is the defect either way round — one of them has to move.

1. **It strips a leading UTF-8 BOM.** Windows editors write one routinely, and
   left in place it is not invisible to the renderer: it becomes a stray glyph
   ahead of the first heading, so a `# Title` opened on Windows renders as
   `<something># Title`. Mac's `String(data:encoding:.utf8)` keeps the BOM.
   Windows-authored files are opened on Macs.
2. **It caps the file at 32 MB** (`viewer_content.max_file_bytes`) and shows
   `File is too large to display` past it. Mac's `Data(contentsOf:)` is
   unbounded, so `--view` on a multi-gigabyte file is an unbounded allocation
   driven by whatever path the caller passed — and the viewer then escapes it
   into a JS literal and widens that, so the peak is several times the file.

Both were deliberate, documented deviations at T90e rather than silent ones.
The parity rule says a feature that exists on one platform and not the other is
an unfinished feature; this task closes it from the Mac side, which is the
seat that can validate it.

## Details

- BOM: strip `\u{FEFF}` from the front of the decoded string in
  `renderFileContent`, before the `.markdown`/`.code` switch. The page must not
  do it — the shared JS renders on both platforms and the byte never should
  have reached it.
- Cap: read with a bound and route the overflow to
  `window.__viewer.setError("File is too large to display", <path>)`, matching
  the Windows string exactly so the two clients say the same thing.

*Validation:* a unit test in the macOS test target for each — a BOM-prefixed
markdown source rendering without the glyph, and an over-cap file producing the
error card rather than an allocation. Windows already covers both in
`viewer_content.zig`'s none-lane tests.
