# T1212 - The MSI packaging harness has been due since build-msi.sh changed, and it cannot run without Docker

## In plain terms

The check that proves the Windows installer package is built correctly can only
run when Docker is running, and Docker is usually not. So every change to how
the package is built ships with that check unrun - and nobody notices, because
the loop's own gate has to be waved past to get anything else out the door.

## Summary

`scripts\guard-due.ps1` has reported

    GUARD DUE release-artifacts-packaging: test\win32elease-artifacts.ps1 has
    not been run since these changed: dist/windows-installer/build-msi.sh

since before T1207 was claimed on 2026-08-31, and T1207 changed
`build-msi.sh` again. The harness needs `-RequireDocker`, Docker Desktop was
down, and starting it is not something this loop does unasked (its WSL2 backend
has buried the box before). So the turn committed under `validate -NoGuardDue`
with the reason stated - which is the hatch working as designed, but a hatch
taken twice in a row is a gate nobody is holding.

The gap to close is that the ONE harness covering how the shipped MSI is
assembled is gated on a daemon that is usually off. Options worth weighing:

- Split the harness: the parts that need no Docker (the wxs shape, the
  build-time verifiers extracted from `build-msi.sh` and fed synthetic tables -
  the pattern `install-restart.ps1` section E and `install-prepare.ps1` section
  E already use) become their own always-runnable guard row, and only the parts
  that genuinely need msitools stay behind `-RequireDocker`.
- Or have the guard row itself declare a Docker dependency, so the report says
  "due, and cannot run here" rather than the same undifferentiated DUE that a
  harness somebody simply forgot produces.

## Validation criteria

- [ ] The no-Docker half of the packaging harness runs on this box and stamps a
      guard row of its own.
- [ ] A change to `build-msi.sh` makes that row due, and running the harness
      clears it, with no Docker involved.
- [ ] Whatever still needs Docker is reported as blocked-on-Docker rather than
      as an ordinary due harness.
