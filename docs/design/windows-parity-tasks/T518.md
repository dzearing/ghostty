# T518 - Should skipped(duplicate -> X) and skipped(obsolete -> X) deps resolve through their target the way splits now do?

## Summary

T382 made deps resolve through skipped(split) parents. A skipped(duplicate -> X) or skipped(obsolete -> X) parent still satisfies dependents even when X is open, though the work arguably lands via X. Decide whether redirect skips should resolve through their target too, or whether a duplicate/obsolete skip genuinely ends the dependency. Watch for false blocking: many such statuses name tasks only as prose references (e.g. 'skipped(obsolete -> T157 - its remainder is now T157s validation)').

## In plain terms

When a card on the board is closed as "this is the same thing as that other
card", the work did not get done - it just moved. Until now the board treated
that closure as if the work were finished, so anything waiting on it was
released and could be handed out while the card that actually owed the work was
still open. Now the wait follows the redirect: a task waiting on a duplicate
waits for whatever the duplicate points at, and the board says so out loud.

## Goals

- [x] `skipped(duplicate -> X)`, `skipped(obsolete -> X)` and
      `skipped(superseded by X)` resolve through X, the way splits resolve
      through their children
- [x] only the redirect TARGET blocks - ids named later in the status prose
      never do, so no false blocking is introduced
- [x] redirect chains and targetless skips both behave (through / satisfied)
- [x] `validate` names a paper-satisfied redirect as its own kind, not as a
      split

## Answer

**Yes - they resolve through their target.** A duplicate/obsolete/superseded
skip closes the CARD, not the work: the work moved to the task the skip names,
which is exactly the argument T382 made for splits. Releasing a dependent while
the task that owes the work is still open is the same misroute wearing a
different reason string.

The false-blocking risk the task named is real but is a parsing question, not a
policy one, and it is what makes this different from a split. A split names
every child, so `Get-SplitChildren` harvests every id token in the status. A
redirect names exactly ONE target and then talks: *"duplicate of T1189, which
already tracks the Docker-gated packaging guard; T1063 and T1187 are two more of
the same"*. Harvesting that the split way would block on two bystanders. So
`Get-RedirectTarget` takes the FIRST id only - which is the true target in all
74 redirect statuses in the tracker today, across every phrasing in use
(`duplicate of X`, `duplicate -> X`, `obsolete -> X`, `superseded by X`,
`duplicate: fixed by X`).

Scope of the behavior change on today's data: **none**. Two open tasks depend on
a redirect skip (T676 -> T122, T913 -> T912) and both targets are already
closed, so nothing that was being offered stops being offered. This is a
correctness fix for the next one, not a queue edit.
