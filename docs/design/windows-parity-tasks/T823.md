# T823 - A Windows pane comes back as a shell, not a re-run, after a reboot

## Summary

Port main's session-relaunch=restore|rerun|prompt policy (default restore) to the Windows client: a restored pane opens the recorded cwd in a plain login shell of the pane's flavor instead of re-executing its recorded --command. Upstream c76b5c89d.

## In plain terms

Rebooting already brings your panes back as ordinary shells sitting in the
folder they were in, under a notice naming the command that was lost — Windows
got that in T230 and the Mac got it separately. What it did NOT get is the same
NAME for the setting: the two seats invented different words for the same three
choices, so the line you put in your config to change this behavior works on one
machine and is rejected on the other. After this, `session-relaunch` is spelled
the same way everywhere. Anyone who keeps one config across both machines
notices; everyone else keeps the same behavior they have now.

## Goals

- [x] a `session-relaunch` setting with `restore` / `rerun` / `prompt`, defaulting to `restore`
- [x] `restore` asks for a login shell of the pane's Windows flavor (pwsh / cmd / wsl), not `<shell> -li`
- [x] the restored shell starts in the session's recorded working directory
- [x] `rerun` still re-executes the recorded command
- [x] the acceptance harness for the default policy is wired into `guard-due`, so a
      `termio/Remote.zig` edit that breaks the reboot floor is due for a re-run

## Details

Upstream `c76b5c89d` (main, 2026-08-12) made the policy client-side: the
agent's synthesized relaunch OPEN already drops the recorded command when the
viewer supplies `Relaunch.argv`, so `restore` is "ask for a login shell". The
Windows translation is the shell-flavor invocation this repo already uses
elsewhere (`pwsh -NoExit -Command`, `cmd /K`, `wsl --`) in place of the Mac
`<shell> -li`.

That commit also fixed the agent never writing `Session.cwd` (only
`materialize` set it, so it was permanently null and every reboot respawn
landed in whatever cwd the agent happened to have). The agent is one codebase
for both platforms, so the fix arrives with the merge — but a restored Windows
pane landing in the right directory is a validation check here, not an
assumption.
