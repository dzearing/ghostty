# T1393 - Terminal still blinks to background on whole-window resize (T1031 regression or a second cause)

## Summary

Dragging the **top-level window frame** to resize makes the terminal session
"blink as if it is being erased and redrawn" — the flat background shows for a
frame before the text comes back. Reported interactively 2026-09-06.

This is the exact symptom **T1031** was closed as fixing ("status: done",
2026-08-20). So this is either a regression of that fix, or a second cause on
the same path that T1031's oracle cannot see. Treat it as P0: it is a
user-visible regression of a shipped fix, and the pattern of a "done" task whose
symptom is back is worth more than the frame it costs.

### What T1031 already put in place — read this before touching anything

- `Surface.has_presented_frame` (`src/apprt/win32/Surface.zig` ~line 154): set
  by the renderer thread once real pixels exist in the window.
- The window class's `WM_ERASEBKGND` (`src/apprt/win32/App.zig` ~line 9153)
  no longer fills unconditionally. It asks
  `resize_paint.shouldFillBackground(.{ is_surface_window, has_presented_frame })`
  and fills only when the answer is yes — the surviving cases being a surface
  with no presented frame yet, and the search/palette popups, which share the
  class and have no renderer.
- `Surface.in_live_resize` (~line 145) plus `parent_window.in_live_layout` put
  the pane on a **synchronous present** path in `handleResize`
  (`Surface.zig` ~line 3258): reset `frame_event`, wake the renderer, wait for
  a frame at the new size so DWM cannot stretch stale content.
- There is a **debug-build oracle**: `log.debug("surface erase surface={} presented={} fill={}")`.
  A cross-process probe cannot ask this question (the `WM_ERASEBKGND` HDC does
  not survive a process boundary — a previous probe "passed against nothing"),
  so the app states its decision to stderr and the script reads it.
- Existing harness: `test\win32\resize-flicker.ps1` (with
  `resize-flicker.stamp.json`), plus `test\win32\banner-resize-repaint.ps1`.

### Investigation order

Do **not** start by changing code. Start by finding out which of the two
worlds this is:

1. **Run the existing oracle.** Build Debug, drag the window frame, and read the
   `surface erase ... fill=` lines. If any line says `fill=true` for a surface
   window, `shouldFillBackground` or `has_presented_frame` has regressed — find
   the change that did it (`git log -S has_presented_frame`, `-S shouldFillBackground`).
2. **Run `test\win32\resize-flicker.ps1`.** If it still passes while the user
   can see the blink, the test is asserting the wrong thing — that gap is itself
   a finding worth as much as the fix, and the test must be strengthened as part
   of this task.
3. **If `fill=false` throughout, it is a second cause.** Candidates, in order of
   suspicion:
   - `in_live_resize` / `in_live_layout` not actually set for this interaction,
     so the synchronous-present wait never runs and DWM shows stale/stretched
     content. Note the comment at `Surface.zig` ~line 390: the divider and
     banner interactions "are not modal size loops, so neither raises
     `WM_ENTERSIZEMOVE`" — verify the window-frame drag genuinely does set it
     on **every** pane, including panes in non-active tabs and newly split ones.
   - Snap / maximize / Aero-snap / a double-click on the title bar, which resize
     **without** a modal size loop and so may miss the flag entirely. Ask
     whether the user's repro is a drag, a snap, or a maximize — the fix differs.
   - The top-level window's own class background brush (`hbrBackground`) or the
     non-client/tab-strip area erasing across the pane rect.
   - A pane whose renderer has not presented since the last size change, so
     `has_presented_frame` is legitimately false and the fill is "correct" but
     still visible.

### Fix direction

Whatever the cause, the fix must come with a test that **fails before it**.
T1031 shipped with an oracle and the symptom came back anyway, which means the
current coverage does not pin the behavior the user actually experiences. Extend
`resize-flicker.ps1` to cover the specific interaction that reproduces here
(frame drag vs snap vs maximize — cover all three), and keep the decision logic
in `resize_paint` so it stays unit-testable in the `none` lane.

Read `docs/claude/win32-ui.md` and `docs/design/win32-design-system.md` before
touching chrome, and `docs/claude/testing.md` before writing the harness half.

## In plain terms

Make the window bigger or smaller and the terminal blinks: for a moment the
text vanishes and you see a flat panel of background colour, then it comes
back. It is worst on the gestures that resize a window all at once — clicking
maximise, double-clicking the title bar, or snapping the window to half the
screen — because on those the app never waited for the terminal to redraw at
its new size before letting the new size show. When this lands, resizing a
window looks like the text simply changing shape, with nothing blanking in
between.
