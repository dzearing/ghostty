# T1014 - git-commit-guard accepts a BOM'd message file, which permanently corrupts the commit subject

## In plain terms

The activity feed on the dashboard is built from commit messages. On
2026-08-20 one of them ended up with an invisible junk character at the front
of its title, and because the commit had already been pushed there is no way
to take it back. The tool that makes these commits could have caught it in a
single line, and did not.

## Summary

`scripts\git-commit-guard.ps1 commit -MessageFile <path>` passes the file
straight to `git commit -F`. On this box PowerShell 5.1's
`Out-File -Encoding utf8` and `Set-Content -Encoding utf8` both write a UTF-8
**BOM** (5.1 has no `utf8NoBOM`), and `git commit -F` does NOT strip it — so
`EF BB BF` lands at the start of the SUBJECT LINE.

That happened on 2026-08-20 closing T299: commit `8c007dd52` has the subject
`﻿close T299 (commit ef41366f7)`. It is permanent, because correcting a
pushed subject needs a force push and force-push is user-gated here.

Two things it costs, both specific to this repo:

- `scripts/task-dashboard.js` decides whether a commit is a bulk tracker edit
  with `subject.startsWith('chore(tracker)')` (see its comment on why the
  modified-date column depends on that). A BOM defeats the check even when the
  prefix IS present, so a correctly-named tracker commit would still be
  counted as work on every task file it touched.
- The subject renders with a stray glyph in the Activity feed forever.

## Details

The guard already reads the commit back and fails loudly when it contains a
path that was not asked for (T948). This is the same shape of check on the
same operation — assert the message, not just the pathspec — and it belongs
next to it:

- Refuse a `-MessageFile` whose first three bytes are `EF BB BF`, naming the
  file and the one-line fix, BEFORE anything is staged.
- Refuse a message whose first line is empty or begins with whitespace, for
  the same reason: an unusable subject is unfixable after a push.
- Worth considering as the safer default rather than only a refusal: strip a
  leading BOM into a temp copy and commit that, printing what it did. A
  refusal is the safer first cut — silently rewriting a message file is its
  own surprise.

Related trap, same root cause, already documented in
`docs/claude/testing.md`'s ASCII-only rule for PS scripts: PS 5.1 encoding
defaults are wrong for every repo text file, which is why repo edits go
through the Edit/Write tools.

## Validation criteria

- [ ] A `-MessageFile` starting with `EF BB BF` is REFUSED before staging,
      with the file named and the remedy in the message.
- [ ] A message file whose first line is blank is refused the same way.
- [ ] A normal BOM-less message file still commits exactly as it does today
      (negative control: the refusal is not firing on every commit).
- [ ] Section W of `test\win32\go-loop-guard.ps1` covers all three, including
      the negative control, and the section is teeth-checked by removing the
      new guard and watching the assertions go red.
