# T203 - Tab strip ignores the system accent color and breaks in light themes

## Summary

Second half of the user's 2026-07-30 "looks HORRIBLY amateur ... not native to
Windows" report (geometry is **T202**, glyphs are **T204**). The strip's colors
are invented arithmetic over the terminal background with one hardcoded blue,
which is a reliable tell that a control was not built for the platform: a
Windows 11 user has a personalized accent color and a light/dark preference,
and this strip honors neither.

## Root causes (verified by reading, line numbers at HEAD)

All in `drawTabBar`, `src/apprt/win32/Window.zig`:

1. **The accent is a hardcoded literal.** Line 2683:
   `const accent_color = w32.RGB(0x3D, 0x8E, 0xF8);` - a fixed blue, unrelated
   to the user's chosen accent color. Windows exposes the real one
   (`UISettings.GetColorValue(UIColorType::Accent)`, or
   `DwmGetColorizationColor` as an older fallback). Note the SAME literal is
   used for the chooser's selection pill (T172), so whatever accent source
   lands here should be shared, not duplicated - one resolution site.

2. **Every other color is `background +N`, which assumes a dark background.**
   Lines 2666-2691: bar is `bg + 20` per channel, hover is `bg + 35`, text is
   fixed `RGB(230,230,230)` / `RGB(150,150,150)`. On a light theme those
   additions clamp toward white, so the strip, its hover state and the active
   tab all converge on the same near-white and the light-gray text goes
   illegible. The channel-add also skews hue on any non-gray background. It is
   an approximation of "slightly lighter", not a color system.

3. **No system theme integration.** `DarkMode.zig` exists and the app already
   consumes dark-mode signals elsewhere, but the strip does not derive from
   the system's light/dark setting or repaint on `WM_SETTINGCHANGE`. There is
   also no Mica/backdrop treatment on the titlebar band, which is the single
   most recognizable Windows 11 window cue and is what makes Terminal's strip
   read as part of the window frame rather than as a painted rectangle.

## Deliverables

1. A small color module resolving, in one place: system accent (plus its
   light/dark variants), the strip/hover/active fills, and text colors -
   derived with proper luminance-aware blending rather than per-channel
   addition, so light themes work by construction. Follow `color_math.zig`,
   which already exists for this kind of thing.
2. Point the tab strip AND the chooser's selection pill at the resolved
   accent, retiring the `0x3D8EF8` literal from both.
3. Honor the system light/dark setting and repaint on `WM_SETTINGCHANGE` /
   accent-change notifications without a restart.
4. Evaluate Mica (`DWMWA_SYSTEMBACKDROP_TYPE`) for the titlebar/tab band.
   Explicitly a judgment call, not a mandate - it interacts with the terminal
   background and with T202's chiclet merging into the pane. Record the
   decision either way, the way T124 records Liquid Glass as deliberately not
   ported.

## Validation

- Extend `test/win32/tab-strip.ps1`: sample the active-tab indicator and
  assert it tracks the system accent after changing it (accent is settable
  from the registry under `HKCU\Software\Microsoft\Windows\CurrentVersion\
  Explorer\Accent` + a broadcast, or via UISettings) - a MEASURED before/after
  flip, so it cannot pass by matching whatever the box happens to be set to.
  This is the same rule T174's host-settings script had to adopt.
- A light-theme pass: assert strip, hover and active fills are mutually
  distinguishable and that text contrast clears 4.5:1 in BOTH themes. Contrast
  is computable from the captured pixels; do not eyeball it.
- Negative control mandatory.
- Restore the box's original accent and theme in the script's teardown - see
  T179, a probe that leaves system state behind manufactures phantom bugs.
- Both test lanes, P1-P3, and the T202 regression set.
