# T327 - Send-TestMouse documents client coordinates but converts from SCREEN ones

Found 2026-08-01 while writing T318's Kill-click assertion, which failed with a
green build and a working feature.

## In plain terms

Nothing here is visible in the terminal - this is about the automated tests
that click things. The helper that clicks measures from the corner of the
SCREEN, but the note next to it said it measures from the corner of the
window, so a test written from that note clicks in the wrong place. The click
still reports success, so the test fails and the feature looks broken when it
is not - which sends whoever reads the failure hunting through the app for a
bug that was never there. It has cost that once already.

## Goals

- [x] the click helper states its own units, on itself, where a caller reads
- [x] the neighbouring helper stops speaking for it - it has the opposite
      convention and now says so
- [x] the rectangle helper every click point is built from says which space it
      returns (that was the real source of the confusion, and it was written
      down only inside code no caller opens)
- [x] the contract is MEASURED by the harness's own acceptance, so it cannot
      quietly stop being true
- [x] every existing click in the suite audited against it

## The defect

`GhozttyTestDesktop.MouseEvent` (`test/win32/lib/TestDesktop.ps1:1175-1214`)
takes SCREEN coordinates: it `SetCursorPos(sx, sy)` and then
`ScreenToClient(dst, ref p)` to build the posted lparam. But the only place the
harness DOCUMENTS the units is `Send-TestClickStorm`'s comment block a few lines
below, which says *"-X/-Y are CLIENT coordinates"* - true of that helper's
defaults, and the first thing a caller of `Send-TestMouse` reads.

`Send-TestMouse` itself has no parameter docs at all, so the neighbouring
comment is the only signal, and it points the wrong way.

## What it cost

T318's acceptance clicked the roster's Kill button at client coordinates. They
were converted a second time, landing ~(client origin) up and left of the
target, so the click fell outside the roster: `the Kill button opens a
confirmation` FAILED against a build where the button worked. The failure was
indistinguishable from a broken hit test, which is the expensive part - it sends
you looking in the app.

## The fix

Document the units ON `Send-TestMouse` (and on `Send-TestRawMessage` if it has
the same ambiguity), and rewrite `Send-TestClickStorm`'s comment so it says
which units ITS defaults are in without implying anything about its neighbour.
Cheap, and the class of bug is "a helper whose contract is stated in another
helper's comment".

Consider also auditing existing callers: any script passing client coordinates
to `Send-TestMouse` is clicking somewhere other than where it says, and would
only notice if the wrong point happened to be inert.

## Validation criteria

- [x] `grep` every `Send-TestMouse` call site and confirm its coordinates are
      screen-space (or are converted at the call site, as
      `test/win32/chooser-sessions.ps1` now does explicitly).
      **147 call sites in 38 files, all screen-space** - each one traced to
      its derivation (a `Get-TestWindowRect` origin, a `To-Screen` call, a
      pixel probe's screen point, or a caller-supplied screen point one hop
      up). Several are named `$cx`/`$cy` and are screen anyway; the name is
      not the unit, which is now said in the docs.
- [x] The scripts that use it stay ALL PASS.
      `test\win32\test-desktop-harness.ps1` -> ALL PASS (32 assertions),
      including the five new coords assertions; it re-stamped the
      `test-desktop` guard row from this code.

## What landed

Docs, in `test/win32/lib/TestDesktop.ps1`:

- `Send-TestMouse` now states `-X/-Y ARE SCREEN COORDINATES` on itself, names
  the double-conversion as a SILENT miss (the post succeeds and returns
  `$true`), and points at `Get-TestWindowRect` for where a point comes from.
- `Send-TestClickStorm` scopes its units to ITSELF - "THIS FUNCTION's -X/-Y
  are CLIENT coordinates, and it is the exception" - and says outright that
  the two do not share a convention. That sentence was the whole defect.
- `Send-TestRawMessage`: `-WParam/-LParam` pass through verbatim; nothing
  packs a point or converts a space.
- `Get-TestWindowRect` got a doc block at all. **This was the real root**: it
  is where every click point in the suite comes from, `-Client` reads like
  "client coordinates" and is not, and the answer lived only in a C# comment
  on `ClientRect` that no caller ever opens - the same disease one level down.

And a measured contract, in `test/win32/test-desktop-harness.ps1` (new
`coords` section, listed in the header's mechanism table): the window is
parked off the screen origin, then both rect forms are asserted to be in the
same space, `-Client` asserted not 0,0-based, and a point built off the
client rect asserted to hit-test ON the window - with the negative control
that the same offsets read as client-relative hit-test HTNOWHERE. A
0,0-based client rect turns that section red.

## Follow-up

A static auditor that could catch a future wrong call site by itself was
considered and NOT built here - filed as **T1032**. The rule that would have
caught T318 (`-X`/`-Y` must show screen evidence in the expression, or in a
same-file assignment one hop up) is decidable, but the shape it must not
false-positive on is the local click wrapper (`Open-TabMenu $x $y`,
`Send-PaneRight`, `Click-Thumb`), where the units arrive as parameters and
resolving them needs a small call graph. That is a real piece of work, not a
rider on a doc fix.
