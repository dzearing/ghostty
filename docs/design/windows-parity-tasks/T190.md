# T190 - Windows menu system: tab-strip menu button, HMENU host, dispatch + on-box script

## Summary

Second half of T143. T189 decided the host and landed the pure model
(`commands.zig` + `menu_bar.zig`, both unit-tested in every lane) and the
single dispatch entry point `Surface.performCommand`. None of it was REACHABLE
- there was no button and no `HMENU`. This task makes the menu exist on
screen.

## Details

Build, in `Window.zig` (tab strip) and a host next to the context menu's
tracking code:

1. **The button.** A `=` (U+2261) button at the right end of the tab strip,
   beside the existing `+` new-tab button: reserve its width out of
   `available_w`, paint it with the same hover treatment, store its hit rect
   (mirror `new_tab_rect`), and route a click to the menu. It must survive the
   tab strip reflowing (many tabs, DPI change).
2. **The HMENU.** Walk `menu_bar.root`: `CreatePopupMenu` per submenu,
   `AppendMenuW(MF_POPUP, @intFromPtr(sub), title)` for a submenu row,
   `MF_STRING | MF_GRAYED? | MF_CHECKED?` from `menu_bar.flags(...)` for a
   leaf, `MF_SEPARATOR` for a separator; `TrackPopupMenuEx` with
   `TPM_RETURNCMD` at the button's bottom-left. Item ids come from
   `menu_bar.menuCommandId`, so the result maps straight back with
   `fromMenuCommandId`.
3. **Accelerator labels.** Every bound row is labeled `Title\tChord` from the
   LIVE keybind set, exactly like the context menu's `Surface.menuLabel`
   (T129) - factor that helper so both callers share it rather than growing a
   second formatter. A rebind must relabel the menu; an unbound command shows
   no hint.
4. **Dispatch.** `fromMenuCommandId` -> `Surface.performCommand`. No second
   dispatch path - that is the T189 contract.
5. **State.** Fill `menu_bar.State` at open time from the focused surface and
   its window: selection, readonly, search bar, tab count, pane count,
   `session-persistence`.
6. **Keyboard.** F10 and a lone Alt press open the menu at the button - the
   classic menu-bar activation Windows users still reach for. Mnemonics then
   work inside the popup for free.
7. **Dark mode.** Nothing new: the T79 uxtheme path already themes popup
   menus, which is one of the reasons the host is a popup (T189 design).

## Validation

New `test/win32/menu-bar.ps1`, on-box, three runs:

- the button exists in the tab strip and opening it produces a menu - read the
  LIVE popup with the `MN_GETHMENU` technique `context-menu.ps1` uses
  (cross-process `GetMenuItemInfoW` on the returned HMENU; never
  `GetWindowTextW`, which reads a cache the app never sees);
- **every leaf in the tree is present**, with the titles and tree shape the
  model says - walk submenus recursively, since a count-only assert would miss
  a whole missing submenu;
- **choosing a row performs its command**, one representative per submenu,
  asserted by outcome (File -> New Tab grows `+list --json`; Window -> Zoom
  Split hides panes; View -> Terminal Read-only comes back CHECKED);
- **state gating is live**: Copy grayed with no selection and enabled with
  one, split rows grayed in a single-pane window, Exit reading "(keep
  sessions)" only with session-persistence on;
- **a rebind relabels the row** (the T129 assertion, ported);
- a negative control that fails when the menu is stubbed, so the run proves it
  measures the menu.

The menu/palette coverage gate already exists from T189
(`everyCommandIsPlacedOrOmitted`); extend it only if the host introduces
host-only rows.

## Outcome (2026-07-30) - DONE

The menu exists, opens three ways, and dispatches through the one T189 entry
point. `test/win32/menu-bar.ps1` **ALL PASS (52) x3**.

### What landed

- **`Window.zig` - the button.** `menu_btn_rect` / `hover_menu_btn` /
  `menu_open` beside the `+`'s state; `menuButtonWidth(scale)` (the same 36pt
  square) comes out of `available_w`, so the strip reflows around it at any tab
  count and DPI; the glyph is painted with the `+`'s hover treatment and stays
  lit while its popup is up (the Windows menu-button idiom). Hit-test added to
  the click, hover and mouse-leave paths.
- **`Window.zig` - both strip buttons are now pinned to the right EDGE**, not
  drawn after the last tab. Tabs stop shrinking at `min_tab_w`, so past a
  point they overrun `available_w` and everything drawn after them lands
  off-screen. That was a pre-existing "+" bug and nobody had hit it; it would
  now take the app's entire menu with it. The band is repainted before the
  buttons so an overrunning tab cannot show through.
- **`Window.zig` - the host.** `openMenuBar` -> `menuBarState` (tab count, leaf
  count, selection/readonly/search from the focused surface,
  `session-persistence`) -> recursive `buildMenuNodes` -> `TrackPopupMenuEx`
  (`TPM_RETURNCMD`) at the button's bottom-left -> `fromMenuCommandId` ->
  `Surface.performCommand`. `DestroyMenu` on the root frees the submenus, so
  the recursion owns no cleanup.
- **`menu_label.zig` (new, pure).** `formatTrigger`/`keyName` MOVED out of
  `Surface.zig` (not copied) plus `withAccel`, with its own unit tests. The
  context menu and the menu bar now format a chord through the same code, which
  is the point of item 3. `menuItemLabel` refuses to label a non-`binding`
  command, so New Remote Window / About / Help / the plugin install never show
  the placeholder action's chord.
- **`Surface.zig` - keyboard.** `trackMenuActivation` on the key path;
  `WM_APP_OPEN_MENU` (WM_APP+10) POSTS the open, so the key finishes being
  delivered and the modal loop never runs nested inside a keyboard WndProc (the
  T48 re-entrancy class). `alt_menu_armed` is cleared by any other key, by
  autorepeat, and on both focus edges (alt+tab).

### The decision this task had to make: the strip was not always there

The T190 brief assumed the tab strip exists. It did not:
`window-show-tab-bar` defaults to `auto`, which meant "hidden until you open a
second tab" - so as first built, the menu button was invisible in exactly the
default single-tab window the user was complaining about. A menu you can only
reach after opening a second tab is the same "there's no way to get to the
menu" report, one step further in.

So on win32 `auto` now shows the strip from the first window. The reasoning is
in `updateTabBarVisibility`: on macOS `auto` can mean "tabs only", because the
app menu lives in the system menu bar that is always there; Windows has no such
bar, and since this task the strip IS the menu host. Windows Terminal, VS Code
and Edge all show their strip with a single tab, so this is also the native
shape. `never` remains the opt-out and still reaches the menu by F10, a lone
Alt, or the command palette.

### Two narrowings on the keyboard activation, both deliberate

- **Alt only counts when it is alone** - armed on a first press with no other
  modifier, disarmed by any other key, by autorepeat, and by focus loss. So
  alt+key escape sequences, alt-as-a-modifier and alt+tab are untouched, and
  the release is never consumed (a client reading key releases still sees it).
- **F10 yields to full-screen TUIs.** `htop`, `mc` and friends bind F10, and
  they all run on the ALTERNATE screen; a shell prompt does not. F10 opens the
  menu on the primary screen and is passed through untouched on the alternate
  one - a measurable discriminator instead of a guess about what the child
  wants.

### The crash this would have shipped

`Window.close()` calls `DestroyWindow` **synchronously**, `onDestroy` removes
the window from the app's list and `alloc.destroy(self)` frees it. So File ->
Close Window / Close All Windows / Exit free the very `Window` whose menu host
is on the stack. The first version cleared the button's lit state in a `defer`,
i.e. AFTER the dispatch: a textbook use-after-free, and the row that triggers
it is the one every Windows user reaches for. It now clears the state the
moment `TrackPopupMenuEx` returns and touches nothing after
`performCommand`.

It was found by review, not by a crash - so the script gained the assertion
that would have caught it: choose File -> Close Window, accept the "processes
are still running" confirmation, then assert the window is gone AND the app is
still healthy (`+list` answers). With the `defer` put back, that run leaves the
app wedged - `+list` fails with "Failed to read IPC response length" - so the
assertion measures the defect and not just the click.

### Three things the validation MEASURED instead of assuming

- **The alternate-screen read is on the key path, so it needs the T114
  priority lock.** Written first with the plain `renderer_state.mutex`, F10
  right after a zoom (or while a child was flooding output) produced no menu
  within 3s and then opened one several seconds later, out of band - the busy
  pane held the mutex. Now `lockPriority`/`unlockPriority`, exactly like
  `isWin32InputMode`, which is on the same path for the same reason.
- **A ^C-killed TUI does not necessarily leave the alternate screen.** The
  harness's first "we are back on the primary screen" oracle was "+read starts
  working again", and it was wrong twice over: `+read` failing means "nothing
  to read", not "alternate screen", and the killed child never emits `?1049l`.
  The F10 that then correctly passed through was scored a FAILURE for three
  runs. The child now switches back itself and prints a marker, and seeing the
  marker in the pane is positive proof. The product was right; the oracle was
  not.

Also caught while building the script, and worth carrying to the next menu
harness: `GetMenuState(MF_BYPOSITION)` returns a submenu's ITEM COUNT in the
high byte, so any submenu with 8-15 items sets 0x800 and reads as
MF_SEPARATOR. Check `GetSubMenu` FIRST. (`context-menu.ps1` has the same
latent bug; its menu has no submenus, so it never fires.)
