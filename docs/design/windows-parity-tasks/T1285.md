# T1285 - P3 fails 9 of 15 when it runs straight after P2 in one shell, and is ALL PASS on its own

## In plain terms

Three checks are run before every change ships. The third one fails badly when
it runs right after the second, and passes completely when run on its own -
which means the failure is about the order they were run in, not about anything
being broken. A check that cries wolf gets ignored, and then it stops protecting
anything.

## Goals

- [x] find what P1/P2 leave behind that P3 reads - **nothing does.** 18 runs in
      order (six p1;p2;p3 triples back to back) were ALL PASS with identical wall
      times, so the run ORDER is not the variable. What the red run actually was:
      the app under test stopped answering IPC part way through, and the floor
      had no way to say so.
- [x] the floor is green whether it runs alone or third - 18/18 in order, plus
      the three run singly after the fix
- [x] the fix is in the harness, not in a retry - the fixture's exit code is
      READ (it used to be `[void]`-ed), a machine-readable answer is parsed off
      stdout alone, and an unreachable app ends the run with ONE setup failure
      carrying the CLI's own words instead of sixteen wrong ones

## Summary

Observed 2026-09-02 while running the standing floor for T1100: 'ipc-p1; ipc-p2; ipc-p3' in one PowerShell session ended with 'P3 ACCEPTANCE: 9 FAILURE(S) (6 assertions passed)', and ipc-p3.ps1 re-run alone immediately afterwards was 'ALL PASS (16 assertions)'. P1-P3 are the floor CLAUDE.md names for every change, so a red that depends on being run after its neighbour is a floor that cries wolf - and the shape (green alone, red in sequence) is state one script leaves behind for the next, not a product defect. Find what leaks between them and either clear it or make P3 immune.

## What it turned out to be

The premise in the title is wrong, and proving that is half the answer. Six
`ipc-p1; ipc-p2; ipc-p3` triples run back to back - 18 runs - were ALL PASS, with wall
times steady to the second across all six (10s / 22s / 32-34s every time). Order
is not the variable.

The red is intermittent, and it was reproduced once: P2 scored `16 FAILURE(S)`
while the run either side of it was green. Its transcript says what happened, and
it is not a product defect:

- `ConvertFrom-Json : Invalid JSON primitive: Waiting.` - the CLI's own
  five-second `Waiting for Ghoztty to answer '+list'` notice (`src/os/
  ipc_timeout.zig`) arrived in the SAME stream as the JSON, because
  `Invoke-OnTestDesktop` handed the child one file for stdout and stderr. A slow
  answer was scored as a malformed one.
- Every verb after the fixture failed, and the fixture itself was never checked:
  `[void](Ghoz @('+new-window', '--target=p2ide'))` throws its exit code away,
  and `[void](Wait-ListMatch ...)` throws away the answer to "did it appear?".
  So a window that never came up produced sixteen lines blaming `+split`,
  `+send-keys` and `+rename`.

Two false leads, both measured and dropped: the agent's `sessions.json` is stale
cross-run state that `lib\CleanSlate.ps1` does NOT clear (unlike the session
manifest and the agent's `layouts.json`), but a seeded 24-session store and the
real 5-session store both left `+new-window` at 300-450ms and `+split` under
150ms and resurrected no holders - filed as its own task rather than claimed as
this cause. A freshly written pair of binaries (Defender-cold) was green too.
