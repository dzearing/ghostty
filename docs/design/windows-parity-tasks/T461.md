# T461 - The chooser re-dials a remote machine on every roster fetch instead of holding one warm connection per machine

## In plain terms

Open the machine chooser, click a machine that is not this one, and every
refresh of its session list opens a brand-new connection to that machine,
uses it once, and throws it away — for a relay machine that also means a
fresh sign-in round-trip each time. The list is slower than it needs to be,
killing a session there often fails outright, and there is nowhere to hang
anything that has to keep listening (like a live CPU number). When this
lands, selecting a machine dials it once and everything about that machine
rides the same connection.

## Goals

- [x] One connection per remote endpoint, shared by the roster fetch, Kill,
      and any future subscriber
- [x] The connection is refcounted: dialed on first use, freed on last
      release, and it can neither outlive the chooser nor be freed while a
      subscriber still holds it
- [x] Two chooser rows that name the same endpoint share one connection
- [x] T328's symptom (a Kill on a remote row loses its connection between the
      dial and the reply) is re-tested against the pooled connection

## Evidence

`src/apprt/win32/SessionRoster.zig:340-369` — the remote branch of the fetch
worker dials the relay inside the worker and frees it on the way out
(`defer if (relay) |*r| r.deinit();`). Only the LOCAL agent has a warm
connection (`req.warm`, owned by `LocalAgent`). The note at
`SessionRoster.zig:388-394` records the consequence: a Kill on a remote row
comes back `error.ConnectionClosed` for both `CLOSE_SESSION` and the refetch
behind it, and a retry-on-fresh-dial WEDGED the worker, so it was not
shipped. That is a per-fetch-dial problem, and the pool is the fix the Mac
seat reached for.

## The Mac counterpart

`macos/Sources/Features/Remote/MachineConnectionPool.swift` (new in
60ccd4f45, 534 lines) plus `MachineConnectionPoolTests.swift`. Read the
commit message: it names three lifetime hazards it handles rather than hopes
about, and all three exist here too —

1. A blocking `LIST_SESSIONS` runs off the GUI thread, where the last lease
   can drop mid-call; the borrow has to keep the connection object alive
   across the call and release it back on the owning thread.
2. Invalidation (link dead) is delivered **synchronously** — "stop using this
   handle now", with the free immediately after. Only the initial replay to a
   late lease is async.
3. Keying is by ENDPOINT (relay device id, or `host:port`), not by chooser
   row, so duplicate rows share a socket.

Translate the design, not the Swift: the win32 side already has the worker
thread and the `DialResult`-to-GUI hop that `SessionRoster.zig` uses, so the
pool belongs beside `MachineChooser.zig`/`SessionRoster.zig` as its own
module (no mega files).

## Where it landed

- `src/apprt/win32/machine_pool.zig` — NEW, pure: the endpoint key, the phase
  machine, the lease refcount, the re-dial cooldown and the generation check.
  Registered in `src/apprt.zig`'s `none` lane.
- `src/apprt/win32/MachineConnectionPool.zig` — NEW, the resources: the dial
  worker (`WM_APP+28`), the link/replay notification (`WM_APP+27`, integer
  payloads only so nothing is allocated on a reader thread), the atomically
  refcounted `Entry`, and the per-slot dial `Recipe` so a re-dial needs nothing
  from the caller.
- `App.machine_pool` owns it; `App.msgWndProc` dispatches both messages.
- `MachineChooser.syncPoolLease` holds ONE lease on the selected remote
  endpoint, moved rather than accumulated; `onPoolChange` is the state feed.
- `SessionRoster.fetch` borrows for a `.remote` target instead of dialing; the
  worker's `relay_dial` call and the whole `OwnedRemote` deep-copy are gone, and
  the `unauthorized` verdict moved to the pool (the roster still prints the same
  `fetch failed … state=…` sentence, which is what the acceptance suite reads).

Two lifetime bugs found on the way, both fixed here:

- `MachineChooser.close` — the REAL teardown path — never called
  `roster.deinit()`, so every chooser dismissal leaked the fetched
  `OwnedSessions` and the parsed layout manifest. Only `destroyState` (the early
  returns in `open`) did. Both now go through one `releaseOwned`.
- That divergence is also what made the first run of the new acceptance script
  crash the app: the pool lease held `self` as its callback context, `close`
  did not release it, and the SECOND chooser's dial notified the first
  chooser's ghost. Segfault at `0xffffffffffffffff`, which is exactly the
  "crashes far from the cause" this task's Mac counterpart warns about.
