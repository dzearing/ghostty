# T1031 - Pane/window resize and banner expand-collapse flicker: panes clear and repaint every frame instead of resizing smoothly

## Summary

Reported by the user, 2026-08-20: "when i resize a pane, the panes flicker
fairly badly... It should be butter smooth but it seems like we're clearing and
repainting on every frame." Three interactions are named and all three run the
same layout path: dragging a split divider, resizing the whole window, and
expanding/collapsing the sticky banner.

## In plain terms

Grabbing the line between two panes should feel like sliding a physical
divider - the text on both sides just moves. Right now the panes blink: for a
moment each side goes flat background, then the text snaps back. Every frame of
the drag does that, so a slow drag looks like it is strobing. Same when you drag
the window edge, and same when the banner above a pane opens or closes. Nothing
is broken - the end state is correct - but it reads as cheap, and it is the
interaction people touch most.

## Investigation starting points (all `? INFERRED` from reading, none confirmed on the box)

Not a diagnosis - a list of the suspects the fixing turn should measure before
changing anything.

1. **Per-leaf `MoveWindow(.., bRepaint = TRUE)`, one child at a time.**
   `Window.layoutNode` (`src/apprt/win32/Window.zig:2968`, and the hero path at
   `:2772`/`:2818`) walks the split tree and moves each pane HWND individually.
   There is no `BeginDeferWindowPos`/`DeferWindowPos` batch, so during a single
   layout pass sibling panes are transiently at mismatched geometry, and each
   move schedules its own erase+paint.
2. **`WM_ERASEBKGND` fills the whole client with the background brush every
   time** (`src/apprt/win32/App.zig:8078`), with the comment that "the OpenGL
   renderer will overwrite the entire client area on the next frame". The next
   frame is the problem: that is one displayed frame of flat background per
   erase, which is exactly the flicker being described.
3. **`WM_PAINT` is asynchronous w.r.t. the renderer**
   (`src/apprt/win32/App.zig:8098`): it `ValidateRect`s and wakes the renderer
   thread. During a live resize the GL frame lands some time after the erase, so
   the composited result is background-then-content rather than one atomic
   frame. `surface.in_live_resize` is already tracked at
   `WM_ENTERSIZEMOVE`/`WM_EXITSIZEMOVE` (`App.zig:7995`) but check what, if
   anything, currently changes because of it.
4. **Divider bands are painted unbuffered via `GetDC` right after the layout
   pass** (`Window.zig:2841`). Deliberate and documented (T252 audited it and it
   stays for the moved-band case), but it is a second, separately-timed paint on
   top of the children.
5. **Banner expand/collapse goes through the same path** - it changes
   `view.bannerLayoutInset` and relayouts, so if 1-3 are the cause it explains
   the banner case for free, and fixing them should fix all three.
6. **Check the Mac seat for parity.** If AppKit is smooth here, the target is
   defined by it; if it flickers too, this is a both-seats task and needs the
   Mac half filed or landed.

## Directions worth measuring

- Batch the layout pass: `BeginDeferWindowPos`/`DeferWindowPos`/`EndDeferWindowPos`
  over every leaf, or `MoveWindow(.., FALSE)` + one invalidate at the end, so all
  panes land in a single frame.
- Stop erasing what will be fully repainted: erase only genuinely-exposed
  regions during resize, or skip the fill entirely when a fresh GL frame is
  guaranteed within the same paint cycle.
- Present synchronously while `in_live_resize` is set - render and swap inside
  the size/paint handling rather than waking the renderer thread and returning.
- Consider holding the last good frame (blit/stretch) instead of clearing to
  background while the new grid size is being rasterized.
- Whatever lands, it must not regress T252's moved-band repaint or T155's
  tiling, and must not reintroduce stale pixels at the divider.
