# T428 - +send-keys text is not framed as a bracketed paste on win32, so a trailing Enter never submits (Mac fixed in 9bac0250f)

## Summary

The Mac fix for 'prompt injected but Enter not pressed' (9bac0250f, on origin/main) added a --segments= payload and Surface.writePtyBracketed. src/apprt/win32/ has zero segment/bracketed-paste handling on main OR on this branch, so /reset-context and every other 'send text then Enter' caller leaves the text sitting unsent in the composer.

## In plain terms

When something types a message into a terminal window for you and then presses
Enter, the Enter was being ignored: the message just sat there, half sent,
until a human leaned over and pressed Enter themselves. That is how the
automatic "start a fresh session and carry on" step stalled on 2026-08-03 —
everything reported success and nothing happened.

The cause is that a long message and the Enter after it arrived as one
undifferentiated lump of typing, and a program receiving a lump that ends in a
newline cannot tell "the user pressed Enter" from "the user pasted text that
happened to contain a line break". After this change the message is handed over
labelled as pasted text, and the Enter arrives separately as a real keypress —
so it submits, first time, every time.

## Goals

- [x] Bring the shared half of the Mac fix (`--segments=`, `writePtyBracketed`)
      onto this branch
- [x] Teach the Windows IPC server to read `--segments=` and frame text runs,
      leaving `--keys=`-only sends byte-for-byte unchanged
- [x] One shared definition of the wire format, so the CLI that writes it and
      the server that reads it cannot drift apart
- [x] Unit tests in the none lane; a byte-exact acceptance script on the box
      with a negative control
- [x] `/reset-context` submits its continuation on the first Enter

## Details

### The symptom

Reported live by the user 2026-08-03: `/reset-context` cleared the session and
the continuation prompt was *injected but never submitted* - it sat in the
composer with no Enter applied.

The evidence, so nobody re-derives it:

- `%TEMP%\reset-context-last.log` (11:17-11:18, 2026-08-03) records `typed
  continuation (706 chars) rc=0` then `submitted continuation rc=0`. So
  `reset-context.sh` did reach its `+send-keys ... Enter` call and that call
  returned success. The failure is NOT the helper skipping the submit, and NOT
  the T210 argv drop (which loses the argument before send-keys ever runs).
- **The user pressed Enter by hand to submit it** (confirmed 2026-08-03). That
  is what makes the case: an `Enter` that reported rc=0 did not submit, and a
  human keypress on the same composer did.
- Read the log's captured pane tail with that in mind. It shows an *empty*
  composer with a spinner and `ctx: 0k/1000k`, which looks like the T261
  false-FAIL shape - but here the composer is empty **because of the manual
  Enter**, not because the automated one worked. Do not file this as another
  T261 sighting.

So the byte-level failure is real and the delivered-vs-effective gap is the
thing to fix. Still reproduce it before changing code - send a
several-hundred-character text argument followed by `Enter` at a Claude Code
prompt and confirm it lands in the buffer unsent - because the fix has to be
validated against a live repro either way, and the length threshold matters
(short text usually submits fine, which is why this looks intermittent).

### Why (from the Mac commit)

`+send-keys --target=t "some message" Enter` flattens every positional into one
`--keys=` payload, so the pane receives a single burst of bytes ending in `\r`.
A TUI's paste detection reads that trailing `\r` as a newline **inside pasted
text** - correctly, since that is exactly what a real multi-line paste looks
like - and the message stays in the composer. The longer the text, the more
reliably the length heuristic fires, which is why a 706-char continuation trips
it and a short `"ls" Enter` usually does not.

The Mac fix (`9bac0250f`, merged as `4fce5f458`, 2026-07-30) makes the argument
boundary survive to the pty write:

- `src/cli/send_keys.zig` - adjacent same-kind arguments merge into runs, and a
  new `--segments=` payload carries the run boundaries. It is sent **alongside**
  the old flat `--keys=`, only when there is a boundary to preserve, so an older
  app degrades to previous behaviour.
- `src/Surface.zig` - `writePtyBracketed()` frames a text run in `ESC[200~` /
  `ESC[201~` as **one** pty write, but only when the program in the pane has
  enabled mode 2004, and never when the data already contains `ESC[201~`. Key
  runs are written bare, outside the frame - so the `\r` after the closing
  fencepost is unambiguously a keypress. That is a property of the bytes, not of
  their timing, so no sleep anywhere in the path can substitute for it.
- `include/ghostty.h`, `src/apprt/embedded.zig`,
  `macos/Sources/Features/IPC/IPCServer.swift`,
  `macos/Sources/Ghostty/Ghostty.Surface.swift` - the Mac IPC server splits
  `--segments=` and calls the framed vs. raw write per run.
- Tests: `macos/Tests/Ghostty/SendKeysSegmentTests.swift`.

### What Windows is missing

Two separate gaps, both real:

1. **This branch does not have the shared half at all.**
   `users/dzearing/windows-amd64` is 42 commits behind `origin/main`;
   `git merge-base --is-ancestor 9bac0250f HEAD` fails. `src/cli/send_keys.zig`
   here still builds only `--keys=` (see its "Build the IPC arguments" comment).
2. **The win32 apprt never got a half, on this branch or on main.**
   `git grep segments origin/main -- src/apprt/win32/` returns nothing, and
   there is no `200~` / `bracketed` anywhere under `src/apprt/win32/`.
   `handleSendKeys` in `src/apprt/win32/IpcHandlers.zig` reads only `--target=`
   and `--keys=`, runs the bytes through `verb_args.normalizeConptyInput`, and
   queues one write. So merging main is necessary but NOT sufficient - the
   Windows server would receive `--segments=` and ignore it.

This is the standing platform-symmetry rule: the Mac shipped the capability and
Windows did not, which makes the divergence the defect.

### Scope

1. Bring the shared `src/cli/send_keys.zig` / `src/Surface.zig` half onto this
   branch (a main merge, or a cherry-pick if the merge is too large to take
   here).
2. Teach `handleSendKeys` (`src/apprt/win32/IpcHandlers.zig`) to parse
   `--segments=`, walk the runs, and call the framed write for text runs and the
   raw write for key runs. Keep `--keys=`-only requests byte-for-byte unchanged
   so an older CLI still works (agent-contract style: readers tolerate absent
   fields).
3. Confirm the framing composes with `verb_args.normalizeConptyInput` - the
   fenceposts must not be rewritten by ConPTY input normalization, and the frame
   must reach the pty as one write.

### Validation

- Unit (win32 lane): segment parsing - boundary preserved, missing `--segments=`
  falls back to flat `--keys=`, a text run containing `ESC[201~` is sent
  unframed, mode-2004-off sends unframed.
- Acceptance (`test/win32/`): a new script that runs a mode-2004 TUI in a pane,
  sends `+send-keys --target=<p> "text" Enter`, and asserts the text was
  **submitted**, not left in the buffer. A negative control that sends without
  the fix (or against a `cat` pane) must show the unsubmitted case, or the test
  proves nothing.
- End to end: `/reset-context` with a multi-hundred-character continuation
  submits on the first Enter, with no retry loop in the helper.

### Notes

- Do NOT "fix" this in `reset-context.sh` by pressing Enter twice. The `/clear`
  path already has that retry and it is a workaround for a different failure;
  an extra Enter against a composer that DID submit sends an empty message. The
  defect is in the byte stream, and that is where it gets fixed.
- Related: T210 (the resume prompt died on the last argv hop - a different
  failure in the same path), T133 (the composer wipe), T182 / T261 (the
  reset-context oracle, which is about *detecting* a failed reset, not causing
  one).

## Resolution (2026-08-03)

### What landed

1. **`origin/main` merged** (44 commits, this branch was 493 ahead). Only two
   files conflicted: `CLAUDE.md` (the `+send-keys` doc block, where this branch
   had the newer `--when-idle` and `--keys-file=` text) and
   `src/cli/send_keys.zig`, where main's segment splitting and this branch's
   in-order `--keys-file=`/`--target=` resolution had to become one function.
   They did: `resolveArguments` now walks the argument list in order, pulls
   `--target=` out, and records a span per run — with a `--keys-file=` payload
   counted as a **text** run, which is what makes `--keys-file=p.txt Enter` the
   reliable "send this prompt, then submit it" shape.

2. **One shared definition of the wire format**, `src/apprt/ipc/segments.zig`
   (`prefix` / `Kind` / `Segment` / `encode` / `decode`). The CLI encodes with
   it and the win32 IPC server decodes with it, so the two halves cannot drift
   — the same rule CLAUDE.md already applies to the socket-path derivation.
   Main had the encoder inline in `src/cli/send_keys.zig`; that copy is gone.

3. **`handleSendKeys` (`src/apprt/win32/IpcHandlers.zig`) reads `--segments=`**
   and writes one run at a time: `writePtyBracketed` for text, `writePtyRaw`
   for keys, each still passed through `verb_args.normalizeConptyInput` first.
   Degradation is deliberate at both ends: no `--segments=` (an older CLI, or a
   send with nothing to disambiguate) takes the original flat path untouched,
   and a `--segments=` that fails to parse logs a warning and falls back to the
   flat `--keys=` payload rather than failing the request — the bytes are the
   same either way, only the framing is lost.

4. **`reset-context.sh` sends the continuation and its Enter in ONE call**
   (`--keys-file=<tmp> Enter`), in the marketplace repo and both live plugin
   cache versions. Two calls could never be framed as one paste no matter what
   the CLI did: the CLI only knows about a boundary it can see. This also
   retires the `sed 's/\\/\\\\/g'` backslash-doubling hack, since `--keys-file`
   bytes are verbatim. Not the forbidden "press Enter twice" workaround — the
   Enter count is unchanged; only the framing is.

### Evidence

- `test/win32/send-keys-bracketed.ps1` (new): **ALL PASS**. Byte-exact capture
  from **raw VT input** — the in-pane helper switches stdin to
  `ENABLE_VIRTUAL_TERMINAL_INPUT` with no line input and no echo, the console
  mode a real TUI uses, so a fencepost is visible at all (a screen read could
  never see one). Measured:
  - mode 2004 ON, `"hello world" Enter` →
    `1b5b3230307e` `hello world` `1b5b3230317e` `0d` — framed, CR **outside**
    the closing fencepost.
  - mode 2004 OFF, same send → `hello world` `0d`, no fencepost anywhere. This
    is the negative control AND the regression guard for every ordinary pane.
  - `--keys-file=p.txt Enter` (the `/reset-context` shape) → framed, identical
    to the first case.
  - a lone text argument → flat, unframed. `+send-keys "cmd\n"` must keep
    executing in a shell, so a single run with nothing to disambiguate is left
    exactly as it was.
  - text containing `ESC[201~` → sent unframed rather than as a malformed
    frame, CR still last.
- Unit: `src/apprt/ipc/segments.zig` (round-trip over control bytes and
  non-UTF-8, empty value, malformed rejection, uppercase hex) and
  `src/cli/send_keys.zig` (boundary preserved, runs merged, single-argument
  forms stay one segment, `--keys-file=` is a text run and keeps its position).
- ConPTY question from Scope §3 answered empirically: mode 2004 set by the
  pane's program **does** reach our terminal through ConPTY, and the fenceposts
  survive `normalizeConptyInput` (it only rewrites LF/CRLF) and arrive in one
  piece.
