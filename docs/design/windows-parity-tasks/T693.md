# T693 - win32 lane crashes intermittently: the inbound-DATA-routing test frees its channel while the connection reader thread is still pushing into it

## Summary

The remote.connection test 'inbound DATA routing: bytes land in the right channel; unknown is dropped' registers 'defer conn.destroy(alloc)' BEFORE 'defer ch.deinit(alloc)'. Defers run LIFO, so the channel's ring buffer is freed first, while the connection's data-reader thread is still alive and still holds the channel in its map. The reader then writes into freed memory.

## In plain terms

One of the automated tests occasionally takes the whole Windows test run down
with it. It is not a slow test or a timing fluke: the test throws away a buffer
while a background thread is still writing into it, and what happens next
depends on which thread wins the race. Most runs are fine; the ones that are
not look like a random crash in unrelated code, which is the worst kind of red
run to inherit. Fixing it makes the test lane trustworthy again.

## Goals

- [ ] The test tears down in an order that cannot race
- [ ] Decide whether `Connection.destroy` should also be defending itself
- [ ] The win32 lane runs clean repeatedly

## Details

Observed 2026-08-10 03:53 during T168's floor run
(`scripts\floor-lane.ps1 -Lane all`), win32 lane, log
`%TEMP%\floor-lane-win32-20260810-035013-093.log`. Two threads panicked:

```
thread 38788 panic: reached unreachable code
  src\remote\connection.zig:1503  assert(self.writer_thread == null)   in destroy
  src\remote\connection.zig:3713  defer conn.destroy(alloc)            in the test

thread 49456 panic: index out of bounds: index 12297829382473034411, len 12297829382473034410
  src\remote\inbound_ring.zig:138  @memcpy(self.buf[start..][0..first], bytes[0..first])   in push
  src\remote\inbound_ring.zig:276                                                          in push
  src\remote\connection.zig:3264   self.channels.pushTo(channel, to_push)
  src\remote\connection.zig:3298   self.routeInboundData(...)           in dataReaderLoop
```

`12297829382473034411` is `0xAAAA_AAAA_AAAA_AAAB` and the length is
`0xAAAA_AAAA_AAAA_AAAA` - Zig's **undefined-memory poison**. So this is a
use-after-free being read as a bounds check, not a bounds bug.

Cause, from `connection.zig:3699-3718`:

```zig
const conn = try Connection.create(...);
defer conn.destroy(alloc);        // registered FIRST  -> runs LAST
var ch = try ring.Channel.init(alloc, ch_id, .{ .capacity = 4096 });
defer ch.deinit(alloc);           // registered SECOND -> runs FIRST
try conn.registerChannel(&ch);
```

Defers are LIFO, so `ch.deinit` frees the ring while `conn` is still live and
its `dataReaderLoop` still holds `&ch` in `channels`. The other panic is the
same fact from the connection's side: `destroy` asserts its writer thread is
already stopped, and it was not. The race only loses when the reader happens to
be mid-`push` at teardown, which is why it is intermittent - the crash-catch
re-run of the same binary completed clean (exit 0) minutes later.

Note the test loops over `all_encodings`, so every iteration re-runs the race.

Work: tear down in the safe order - stop/destroy the connection (or unregister
the channel) before the channel's memory goes away. Then decide whether
`Connection.destroy` should stop its threads rather than assert that someone
else already did; an assert that fires only under a race is a crash in Debug
and silence in ReleaseFast, and this teardown ordering is easy for production
callers to get wrong the same way.

## Validation criteria
