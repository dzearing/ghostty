# T735 - Mac: report the tab strip's hit regions in +list --json (the T231 half)

## In plain terms

On Windows, anything that needs to know where a tab or the "+" button is can
now just ask Ghoztty and get the exact rectangle back. On the Mac it still has
to guess. Nothing a user sees changes either way — this is the difference
between a tool (or a test) that keeps working when the tab bar's design moves
and one that quietly starts clicking the wrong thing.

## Summary

T231 made the win32 server publish the tab strip's clickable regions in
`+list --json`, per window:

```json
"chrome": {
  "dpi": 120,
  "tab_strip": {
    "band":    {"left":5,"top":5,"right":1153,"bottom":50},
    "tabs":    [{"left":5,"top":5,"right":351,"bottom":50}, null],
    "new_tab": {"left":358,"top":5,"right":399,"bottom":50},
    "menu":    null
  }
}
```

Client coordinates, physical pixels, right/bottom exclusive. `null` means
there is nothing there to hit (a tab that did not fit, a menu button the window
does not paint, a strip that has not painted yet); `tab_strip: null` means the
window shows no strip, which is deliberately distinct from the whole `chrome`
key being absent — that is how a caller tells "this server cannot say" from
"this window has no strip", and it is what the Mac reports today.

The Mac's IPC server (`IPCMessage.swift`) does not encode it. Per the CLI
symmetry rule, a field one platform's `+list --json` reports and the other's
never will is the divergence this project does not ship.

## Why it is worth doing

The reason it exists on Windows applies verbatim here: a consumer that cannot
ask has to re-implement the layout, and a second implementation cannot be
type-checked against the first. The win32 harness kept one and it rotted twice
(a fixed pixel offset that landed inside the menu button at 125% DPI, then a
modelled tab width that stopped matching once tabs were sized to their titles),
each time producing a pile of failing assertions against a completely healthy
product.

## Sketch

Mac's tab strip is SwiftUI/AppKit rather than a `layout()` function returning
rects, so the work is finding the honest equivalent of "the rect the hit test
reads" — the tab views' frames converted into the window's content-view
coordinates — rather than porting `tab_strip_layout.zig`. Encode it in
`IPCMessage.swift` beside the existing per-window fields, matching the win32
key names and the null rules exactly (the shared Zig model is
`src/apprt/ipc/list.zig`, `List.Chrome` / `List.TabStrip` / `List.Rect`, whose
golden tests pin the wire shape).

Note the coordinate convention has to be stated and matched: win32 reports
client-space pixels with y growing DOWN. AppKit's default is y-up, so a naive
frame handoff would report a mirrored strip that looks entirely plausible.

## Validation criteria

- [ ] `ghoztty +list --json` on macOS reports `chrome.tab_strip` for a window
      with a strip, with the same key names and null rules as win32.
- [ ] The reported tab rect is where the tab actually is: clicking its center
      through the accessibility/synthetic-event path selects that tab.
- [ ] A window with no strip reports `tab_strip: null` rather than omitting
      `chrome`.
- [ ] Floor: the `none` lane (the shared `list.zig` golden tests) and the Mac
      build.
