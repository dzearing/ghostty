# T1142 - A pane's screen falls minutes behind its own output during a burst

## In plain terms

When a pane prints a lot at once — a build, a long log — the worry was that the
window would sit there showing nothing while the text piled up somewhere behind
it, which reads as a terminal that has hung. Measured on both kinds of pane and
on both builds: **the shipped terminal keeps up.** It tracks a 4.5 MB flood to
within a poll interval and finishes it in about the time the plain Windows
console takes. What is genuinely slow is the *developer* build we run every test
against — about 12 KB a second — which is why a burst looked frozen in the
harness that first noticed this. Nothing a user runs is affected; what came out
of it is a standing measurement, so the next time someone sees a pane look stuck
there is a number to check instead of a story to retell.

## Summary

Measured while fixing T1116 on a Debug build: a pane printing ~350 KB of ConPTY output had all of it recorded in the agent's ring within 0.9 s, while the app's own terminal state (what +read and the user see) still showed nothing past the first screens FIVE MINUTES later. Measure the app-side DATA ingest rate (Debug vs ReleaseFast, agent-backed vs plain local pane) and fix it if the release build shows the same shape - a pane that looks hung during a build is a headline UX defect.

## What was measured

Instrument: `type` of N numbered lines (`L000001`…) into a pane, `+read
--lines=4` polled for the highest line the app had reached, and a marker file
the child stamps the moment it has finished WRITING — so "the child is done" is
read off the child, not inferred from the screen that is under measurement.

| build | path | payload | child done | app caught up | app-side rate |
|---|---|---|---|---|---|
| Debug | agent-backed | 180 KB | 1.1 s | 12.2 s | ~15 KB/s |
| Debug | local (Exec) | 180 KB | 13.7 s | 14.7 s | ~12 KB/s |
| ReleaseFast | agent-backed | 180 KB | 2.3 s | 2.3 s | child-limited |
| ReleaseFast | agent-backed | 4.5 MB | 4.5 s | 4.5 s | ~1.0 MB/s |
| ReleaseFast | local (Exec) | 4.5 MB | 7.2 s | 7.2 s | ~1.0 MB/s |
| conhost (control) | — | 4.5 MB | 2.3 s | — | ~1.9 MB/s |

Three findings, in the order they settle the question:

1. **The release build does not have the defect.** At 4.5 MB — 25x the burst
   that made a Debug pane look hung — the app's terminal state reaches the last
   line in the same poll sample the child finishes in. There is no backlog to
   fall behind with, so there is nothing here to fix in what ships.
2. **The Debug gap is the parser, not the agent transport.** The LOCAL path —
   no inbound ring, no `feedSliced`, no `yieldToPriorityWaiters`, a 64 KiB
   `ReadFile` straight into `processOutput` — measures the same ~12 KB/s. A
   structural throttle in the agent path could not produce that; Debug codegen
   of the terminal parse path does.
3. **What differs between the paths is who absorbs the backlog.** A local pane's
   ConPTY back-pressures the child down to the app's parse rate (child and
   screen finish together, 17.26 s / 17.26 s in the harness run). An
   agent-backed pane's ring takes the whole burst and lets the child run on
   (2.64 s / 18.00 s). That is the ring working as designed — and it is the
   thing that made T1116's flood evict its own marker, so it is now a written
   harness rule rather than a fact each turn rediscovers.

Release throughput sits at ~55% of conhost's on the identical payload. That is
a real gap but a different one from this task's premise (the screen never falls
behind), so it is filed rather than folded in: **T1167**.
