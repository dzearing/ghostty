# T430 - Two standing-floor lanes (test-agent AND test -Dapp-runtime=win32) hang forever in a WebView2 test, with no output and no timeout

## In plain terms

Before any change here is called finished, it has to pass four sets of automated
checks. Two of those four now sometimes never finish — they sit there producing
nothing, forever, instead of either passing or failing. There is no error to
read, so from the outside a stuck run looks exactly like a slow one.

That makes the checks useless as a safety net: whoever is working either waits
indefinitely, or gives up and kills the run and then cannot tell whether the
thing they killed was actually broken. The cause is a test that opens a real
browser window — and does it against the browser profile the real app uses,
which it also should not be doing.

## Goals

- [x] Both check suites always finish, pass or fail, within a bounded time
- [x] A stuck test fails with a readable message instead of hanging
- [x] No test touches the real browser profile — each run gets its own
- [x] No leftover browser processes after a run ends

## Resolution (2026-08-03)

Three changes, and one correction to the evidence above.

### 1. The win32 lane's hang, root-caused: close-then-join on a blocking accept

`ViewerPane.zig`'s two loopback page servers (`TestPage`, for the T375 bridge;
`ReloadPage`, for T390) tore down like this:

```zig
fn stop(self: *TestPage) void {
    self.server.deinit();   // close the listening socket...
    self.thread.join();     // ...and hope that woke the accept
}
```

**On Windows it does not.** `closesocket` is documented not to signal a blocking
call pending on that socket in another thread, so the serving thread can sit in
`accept()` forever and `join()` never returns — a wait with **zero CPU and no
output**, which is exactly the shape measured here (`UserModeTime` identical
across two samples 45s apart) and exactly where the lane was measured to stall
(`ViewerPane.test."host floor: a real …"`, after 3799/3828 tests).

The fix is the idiom this repo already uses in three other places
(`keepalive.zig`, `link_control.zig`, `self_update.zig`): set a `stopping` flag,
**send the listener a real connection** to wake the accept deterministically,
join, and only then close. The two ViewerPane servers were the outliers.

### 2. Profile isolation: `webview2.TestProfile`

The live-runtime tests drove WebView2 against
`%LOCALAPPDATA%\ghoztty\EBWebView-debug` — the same profile a debug Ghoztty
uses. `TestProfile.begin()` now points `LOCALAPPDATA` itself at
`%TEMP%\ghoztty-wv2test-<pid>` for the duration, so `userDataFolderW`'s real
derivation lands on a private root. Overriding the *input* rather than the
folder path is deliberate: the private profile cannot drift away from the
derivation the app actually uses. Covered by a unit test that resolves
`userDataFolder` inside and outside the override.

### 3. The lanes get a watchdog that can tell slow from wedged

`scripts\floor-lane.ps1` runs any lane (`-Lane none|win32|agent|all`) and never
returns without an answer:

- **CPU, not just the clock.** A lane that is *computing* burns CPU; a lane that
  is *wedged* does not. Zero CPU delta across the whole process tree **and** no
  new log bytes for `-StallSeconds` is reported as `STALL`, which a plain
  wall-clock timeout cannot distinguish from a slow test.
- **Diagnostic first, kill second**: process tree with CPU times, every thread's
  `ThreadState`/`ThreadWaitReason` (no debugger required — none is installed on
  this box), any WebView2 hosts with their user-data-dirs, and the log tail.
- **It sets `ZIG_GLOBAL_CACHE_DIR`** on the repo's drive inside the launched
  command, and quotes it — the two decoys recorded below, both fixed at the
  source so nobody re-runs them.
- **It logs through cmd.exe redirection**, unbuffered, so a killed run still has
  its output.
- **It sweeps leaked `msedgewebview2.exe`** by matching `--webview-exe-name=`
  against the test binaries, which a zig-out/zig-cache path filter never sees.
- Exit codes: 0 pass, 1 fail, 2 wedged, 3 wall-clock cap. `-Repeat N` stops at
  the first non-PASS.
- `-SelfTest` proves the three verdicts on synthetic commands (`exit 0`,
  `exit 7`, and a `waitfor` that blocks on a signal that never arrives), so the
  detector is covered without waiting on a real 30-minute wedge.

### 4. The blocked wait itself: Chromium preconnects

The wake-the-accept fix is necessary and **was not sufficient**. Watching a live
run showed the serving thread blocked in `recv`, not in `accept`:

```
ghoztty-agent-test.exe pid 43692 -- CPU frozen at 109.19s across four samples
127.0.0.1:61432  LISTEN
127.0.0.1:61432 <- 127.0.0.1:49713  ESTABLISHED   <- a connection with no request on it
127.0.0.1:61432 <- 127.0.0.1:49714  CLOSE_WAIT    <- the shutdown poke, never accepted
127.0.0.1:49714 -> 127.0.0.1:61432  FIN_WAIT_2
```

**Chromium preconnects**: it opens sockets to an origin speculatively and may
send nothing on them. The serve loop sat in `socket_rw.readStream` on one of
those, so it was not in `accept()` and the shutdown poke queued behind it,
unaccepted. That run un-blocked and went green after **~173 seconds** — the
browser's own idle-socket timer — which is why this reads as an intermittent
hang: it resolves if the browser is healthy, and never if it is not.

Accepted connections now get `SO_RCVTIMEO` (2s), and a connection that asked for
nothing is closed rather than answered. Effect on the win32 lane: **398s → 282s**
for the same tests.

### Correction to the evidence: which binary hosts WebView2

The notes below infer from `--webview-exe-name=ghoztty-agent-core-test.exe` that
the agent lane hangs in a WebView2 test, and ask whether the agent module graph
wrongly pulls in viewer code. Half right, and the half matters:

- **`ghoztty-agent-core-test.exe` contains no WebView2 code at all.** Verified
  by string-scanning the built binary: `EBWebView`,
  `CreateWebViewEnvironmentWithOptionsInternal`, `host floor` and `ViewerPane`
  are all absent. `src/agent_core_test.zig` → `remote/agent_test.zig` reaches
  server, session, grid_snapshot, session_meta, ring_snapshot, metrics,
  keepalive, self_update and the three stream modules — no `apprt`. So that
  particular attribution was wrong.
- **`ghoztty-agent-test.exe` does.** Same scan: all four strings present, and
  the live run above caught it spawning a WebView2 host whose `--user-data-dir`
  carried its own pid (`ghoztty-wv2test-43692`). So the agent lane really does
  run the viewer tests — the question "why does `test-agent` link WebView2 at
  all?" is a real one, it was just asked of the wrong binary. The import path
  from `src/agent_main.zig` is not obvious from the `@import` lines in
  `remote/agent/main.zig` and is not chased here; filed as **T434**.

## Summary

`zig build test-agent` — one third of the standing regression floor — **hangs
with no timeout and no output**, indefinitely. Found while validating T425
(2026-08-03): the same unchanged source went **exit 0 twice, then TIMEOUT three
times**. There is no failure text because nothing fails; the process simply
never returns, so a turn that trusts the lane either waits forever or reads its
own kill as a test failure it did not cause.

Two separate problems, and the second is the more serious one:

1. **It hangs.** A test blocks forever with no bounded wait.
2. **A unit test starts a real browser against the USER's profile directory.**
   Not a temp dir — `%LOCALAPPDATA%\ghoztty\EBWebView-debug\EBWebView`, the same
   profile a debug Ghoztty uses. A test lane must not touch live user state.

## Where to look

- **Why does `test-agent` link WebView2 at all?** The step name promises the
  agent; the binary is named `ghoztty-agent-core-test`. If the "core" module
  transitively pulls in `src/apprt/win32/` viewer code, that dependency is
  itself the bug — the agent is a headless daemon and its lane should not be
  able to open a browser. Splitting the module is likely cheaper than making a
  WebView2 test robust.
- **The blocking call.** A WebView2 `CreateCoreWebView2Environment` /
  controller-ready callback needs a running message pump; a unit test that waits
  on a completion handler without pumping (or without a deadline) waits forever.
  Every such wait needs a bounded timeout that FAILS the test rather than
  hanging the lane.
- **Profile isolation.** Whatever remains must point `--user-data-dir` at a
  per-run temp directory (the acceptance scripts already model this with a
  per-run `LOCALAPPDATA`), so a test can never contend with — or corrupt — the
  user's own browser profile.
- **Leak sweep.** Killing the test binary leaves its `msedgewebview2.exe`
  children running; they are invisible to a sweep that filters on
  `zig-out`/`zig-cache` paths, since that exe lives under Program Files. Match on
  `--webview-exe-name=` instead.

## Validation

- `zig build test-agent` run 10 times consecutively: 10 x exit 0, each under a
  bounded wall time. A lane that only usually returns is not green.
- No `msedgewebview2.exe` remains after the lane exits.
- No test writes under `%LOCALAPPDATA%\ghoztty\` outside a per-run temp root.

## Impact on the floor

### A decoy that cost three runs — do not repeat it

After force-killing the hung processes, three consecutive re-runs died instantly
with

```
error: unable to read results of configure phase from '.zig-cache\tmp\<hash>': FileNotFound
```

different hash each time. That looks exactly like a cache poisoned by the kill,
and it is NOT: clearing `.zig-cache\tmp` (848 entries) changed nothing, because
the cause was a **missing `ZIG_GLOBAL_CACHE_DIR`**. The runs had been launched
with `Start-Process cmd.exe`, which does not inherit a `$env:` var set in an
earlier shell — so zig fell back to its default global cache on `C:` while the
repo is on `D:`, which is the cross-drive build-runner failure CLAUDE.md already
warns about. It surfaces as this FileNotFound rather than as anything mentioning
drives or the cache dir.

So: this error means "the global cache is on the wrong drive" far more often
than it means "the cache is corrupt". Set the var **inside** the launched
command whenever a build is started detached, and do not go deleting cache
directories on the strength of the message.

And **quote it**, or the next run fails differently for the same reason:

```
:: wrong - cmd folds the space before && into the value
set ZIG_GLOBAL_CACHE_DIR=D:\zig-global-cache && zig build …
::   -> error: lld-link: could not open 'D:\zig-global-cache \o\…\kernel32.lib'
:: right
set "ZIG_GLOBAL_CACHE_DIR=D:\zig-global-cache" && zig build …
```

Two different-looking failures, one cause, and neither message names the
environment variable.

### Why this matters more than an annoyance

The standing floor is "both lanes green + `test-agent` green + P1-P3". Two of
those four can now hang indefinitely with no failure text, which means a turn
either waits forever or reads its own kill as a test failure it did not cause.
A hang that cannot be told apart from slowness is worse than a red test.
Whatever else this task does, it should give these lanes a **timeout with a
diagnostic** — the run that produced the numbers above only yielded them
because the kill flushed a log that PowerShell had been buffering, and two
earlier attempts produced nothing at all because `Stop-Job` discarded the
buffer. Log through `cmd.exe` redirection (unbuffered) rather than PowerShell's
`*>` when the point is to watch a long build live.

## New evidence, 2026-08-03 (found while validating T424) — the hang is a SPIN, not a block

Both floor lanes hung again in one turn, on a change that touched only two
string literals (`src/termio/session_notice.zig`, `src/termio/Remote.zig`).
Nothing near WebView2, nothing near the agent. That is the fourth consecutive
`test-agent` non-answer.

**The new fact, and the one worth chasing: the hung processes are burning CPU.**
Two `Win32_Process` samples ~45s apart of the agent lane's own test binaries:

```
ProcessId Name                        UserModeTime KernelModeTime
    36768 ghoztty-agent-core-test.exe   1074687500       26562500
    46108 ghoztty-agent-test.exe         980625000       20312500      <- sample 1
    36768 ghoztty-agent-core-test.exe   1074687500       26562500
    46108 ghoztty-agent-test.exe         980625000       20312500      <- sample 2, IDENTICAL
```

`UserModeTime` did not advance by a single tick between samples — so after
~107s and ~98s of real work respectively, both binaries stopped dead. That is a
**blocked wait, not a livelock**: a spin would keep the counter climbing. So the
diagnostic to write is a stack dump of the blocked thread (cdb / `procdump -ma`
on the hung pid), not a sampling profiler.

It also gives the lanes a cheap, honest watchdog that does not need the hang
root-caused first: sample `UserModeTime` twice N seconds apart, and if a test
binary has been alive for > M seconds with **zero** CPU delta, dump its stacks
and kill it with a diagnostic. That distinguishes "slow test" from "wedged
test", which a plain wall-clock timeout cannot.

The win32 lane repeated its documented shape exactly — `ghostty-test.exe`
started 18:17:14, spawned six `msedgewebview2.exe` children at 18:18:05, and was
still there with no output at 18:25 — confirming the WebView2 `ViewerPane` host
test as the site.

Both lanes were covered in slices for T424 (`-Dtest-filter`), which passed:
win32 169/169, agent 627/629 + 2 skipped.
