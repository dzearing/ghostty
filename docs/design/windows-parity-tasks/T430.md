# T430 - Two standing-floor lanes (test-agent AND test -Dapp-runtime=win32) hang forever in a WebView2 test, with no output and no timeout

## In plain terms

Before any change here is called finished, it has to pass four sets of automated
checks. Two of those four now sometimes never finish — they sit there producing
nothing, forever, instead of either passing or failing. There is no error to
read, so from the outside a stuck run looks exactly like a slow one.

That makes the checks useless as a safety net: whoever is working either waits
indefinitely, or gives up and kills the run and then cannot tell whether the
thing they killed was actually broken. The cause is a test that opens a real
browser window — and does it against the browser profile the real app uses,
which it also should not be doing.

## Goals

- [ ] Both check suites always finish, pass or fail, within a bounded time
- [ ] A stuck test fails with a readable message instead of hanging
- [ ] No test touches the real browser profile — each run gets its own
- [ ] No leftover browser processes after a run ends

## Summary

`zig build test-agent` — one third of the standing regression floor — **hangs
with no timeout and no output**, indefinitely. Found while validating T425
(2026-08-03): the same unchanged source went **exit 0 twice, then TIMEOUT three
times**. There is no failure text because nothing fails; the process simply
never returns, so a turn that trusts the lane either waits forever or reads its
own kill as a test failure it did not cause.

Two separate problems, and the second is the more serious one:

1. **It hangs.** A test blocks forever with no bounded wait.
2. **A unit test starts a real browser against the USER's profile directory.**
   Not a temp dir — `%LOCALAPPDATA%\ghoztty\EBWebView-debug\EBWebView`, the same
   profile a debug Ghoztty uses. A test lane must not touch live user state.

## Evidence (2026-08-03, VERIFIED on box)

The hung `ghoztty-agent-core-test.exe` has a **WebView2 host as its child**:

```
ProcessId   : 44276
Name        : msedgewebview2.exe
CommandLine : "...\msedgewebview2.exe" --embedded-browser-webview=1
              --webview-exe-name=ghoztty-agent-core-test.exe
              --user-data-dir="C:\Users\David\AppData\Local\ghoztty\EBWebView-debug\EBWebView"
              ...
```

Five such processes were alive under one hung test binary. Run history on
identical source (T425's branch state):

| run | result | note |
|-----|--------|------|
| 1 | hung >27 min | both test binaries alive; killed by hand |
| 2 | hung >11 min | killed by hand |
| 3 | **exit 0** | ~10 min |
| 4 | **exit 0** | after the tick wiring |
| 5 | TIMEOUT 500s | webview children present |
| 6 | TIMEOUT 500s | after killing every leaked webview host first |
| 7 | TIMEOUT 500s | after a full sweep (test exes, webviews, zig, build) |

Killing the leaked hosts between runs did **not** restore it, so a stale
user-data-dir lock is at most part of it — run 6 started from a swept box and
still hung.

**The hang is NOT in the agent code.** Every module filter passes in seconds:

```
-Dtest-filter=session.test      -> exit 0     (incl. the new T425 tests)
-Dtest-filter=server.test       -> exit 0
-Dtest-filter=pty_child.test    -> exit 0
-Dtest-filter=keepalive.test    -> exit 0
-Dtest-filter=relay_creds.test  -> exit 0
-Dtest-filter=proc.test         -> exit 0
-Dtest-filter=metrics.test      -> exit 0
```

So the offender is in whatever else `ghoztty-agent-core-test` links — the
viewer/WebView2 side — and `-Dtest-filter` is the workaround that keeps the
agent modules verifiable while this is open.

## Where to look

- **Why does `test-agent` link WebView2 at all?** The step name promises the
  agent; the binary is named `ghoztty-agent-core-test`. If the "core" module
  transitively pulls in `src/apprt/win32/` viewer code, that dependency is
  itself the bug — the agent is a headless daemon and its lane should not be
  able to open a browser. Splitting the module is likely cheaper than making a
  WebView2 test robust.
- **The blocking call.** A WebView2 `CreateCoreWebView2Environment` /
  controller-ready callback needs a running message pump; a unit test that waits
  on a completion handler without pumping (or without a deadline) waits forever.
  Every such wait needs a bounded timeout that FAILS the test rather than
  hanging the lane.
- **Profile isolation.** Whatever remains must point `--user-data-dir` at a
  per-run temp directory (the acceptance scripts already model this with a
  per-run `LOCALAPPDATA`), so a test can never contend with — or corrupt — the
  user's own browser profile.
- **Leak sweep.** Killing the test binary leaves its `msedgewebview2.exe`
  children running; they are invisible to a sweep that filters on
  `zig-out`/`zig-cache` paths, since that exe lives under Program Files. Match on
  `--webview-exe-name=` instead.

## Validation

- `zig build test-agent` run 10 times consecutively: 10 x exit 0, each under a
  bounded wall time. A lane that only usually returns is not green.
- No `msedgewebview2.exe` remains after the lane exits.
- No test writes under `%LOCALAPPDATA%\ghoztty\` outside a per-run temp root.

## Impact on the floor

Until this is fixed, `test-agent` cannot be taken as a gate: a TIMEOUT proves
nothing about the code under test. State the module-filter results instead, as
T425's evidence does.

## New evidence, 2026-08-03 (found while validating T423)

**It is not confined to `test-agent`.** `zig build test -Dapp-runtime=win32`
hangs the same way: no output, no timeout, indefinite. Measured this time, so
the numbers are worth keeping:

- The lane reached **3799/3828 tests passed, 29 skipped** and then stalled in
  `apprt.win32.ViewerPane.test."host floor: a real …"` — a WebView2 host test,
  the same component `test-agent` hangs in.
- **31 minutes of wall clock for ~50s of CPU.** That ratio is the cheapest
  possible detector and is worth using at the two-minute mark rather than the
  thirty-minute mark: a lane that is *computing* burns CPU, a lane that is
  *hung* does not. Nothing else about the two cases looks different from
  outside.
- Run **in isolation the same test passes in 20 s** (`-Dtest-filter="host
  floor"`, 78/78). So it is the intermittency this task already describes, not
  a broken test.
- It hangs **single-instance too**, so concurrency is not the cause. It may
  still be an aggravator: the first sighting had TWO `ghostty-test` binaries
  live at once against the one `EBWebView-debug` profile, which is a plausible
  way to make an intermittent hang reliable and is worth trying deliberately as
  a repro.

### A decoy that cost three runs — do not repeat it

After force-killing the hung processes, three consecutive re-runs died instantly
with

```
error: unable to read results of configure phase from '.zig-cache\tmp\<hash>': FileNotFound
```

different hash each time. That looks exactly like a cache poisoned by the kill,
and it is NOT: clearing `.zig-cache\tmp` (848 entries) changed nothing, because
the cause was a **missing `ZIG_GLOBAL_CACHE_DIR`**. The runs had been launched
with `Start-Process cmd.exe`, which does not inherit a `$env:` var set in an
earlier shell — so zig fell back to its default global cache on `C:` while the
repo is on `D:`, which is the cross-drive build-runner failure CLAUDE.md already
warns about. It surfaces as this FileNotFound rather than as anything mentioning
drives or the cache dir.

So: this error means "the global cache is on the wrong drive" far more often
than it means "the cache is corrupt". Set the var **inside** the launched
command whenever a build is started detached, and do not go deleting cache
directories on the strength of the message.

And **quote it**, or the next run fails differently for the same reason:

```
:: wrong - cmd folds the space before && into the value
set ZIG_GLOBAL_CACHE_DIR=D:\zig-global-cache && zig build …
::   -> error: lld-link: could not open 'D:\zig-global-cache \o\…\kernel32.lib'
:: right
set "ZIG_GLOBAL_CACHE_DIR=D:\zig-global-cache" && zig build …
```

Two different-looking failures, one cause, and neither message names the
environment variable.

### Why this matters more than an annoyance

The standing floor is "both lanes green + `test-agent` green + P1-P3". Two of
those four can now hang indefinitely with no failure text, which means a turn
either waits forever or reads its own kill as a test failure it did not cause.
A hang that cannot be told apart from slowness is worse than a red test.
Whatever else this task does, it should give these lanes a **timeout with a
diagnostic** — the run that produced the numbers above only yielded them
because the kill flushed a log that PowerShell had been buffering, and two
earlier attempts produced nothing at all because `Stop-Job` discarded the
buffer. Log through `cmd.exe` redirection (unbuffered) rather than PowerShell's
`*>` when the point is to watch a long build live.
