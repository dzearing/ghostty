# T255 - Background test desktop: a long-lived window ignores WM_CLOSE and WM_SYSCOMMAND

## Summary

Found while validating **T254** (the custom caption bar). The caption buttons
post `WM_SYSCOMMAND` with `SC_MINIMIZE` / `SC_MAXIMIZE` / `SC_RESTORE` /
`SC_CLOSE`, and none of them had any effect in the acceptance script — but the
cause is NOT in T254's handler, and proving that is the whole point of this
task existing separately.

## Evidence (VERIFIED on the box, 2026-07-31)

Three measurements, in order, against `zig-out\bin\ghoztty.exe` on a
`test/win32/lib/TestDesktop.ps1` background desktop:

1. **Our handler runs and is correct.** A posted `WM_NCLBUTTONDOWN` with
   `wparam = HTMAXBUTTON` lights the button's pressed fill — the pixel under
   the maximize square reads `45,45,45` against the band's `20,20,20`, i.e.
   exactly `icon_button.fillDelta(.pressed)`. That paint cannot happen unless
   the message reached `handleNcLButtonDown` and matched a button rect.
2. **`WM_SYSCOMMAND` does nothing on that window, by ANY route.** Posted
   `SC_MAXIMIZE` → `IsZoomed` still false. `SendMessage`d `SC_MAXIMIZE` (the
   harness's own `Send-TestSysCommand`, whose comment calls it *"the real
   maximize/restore path"*) → still false. `SendMessage`d `SC_MINIMIZE`
   returned 0 and the window rect stayed at its normal position.
3. **Even a plain `WM_CLOSE` does nothing** — and `WM_CLOSE` has no
   relationship to T254 at all. That is what rules the caption bar out as the
   cause.

The confusing part, and the reason this needs its own investigation: a
**freshly launched** window on the same desktop, same build, DOES close on
`WM_CLOSE`. The window that ignores everything is the one that has been alive
for a few seconds and has had `Set-TestWindowSize` called on it. So it is
state- or age-dependent, not categorical.

## Hypotheses to test (none confirmed yet)

- The app is in a modal or blocking state by then (a `TrackPopupMenuEx`-style
  loop, an agent dial, a `Condition.wait`) and its queue is being serviced for
  paint/hit-test but not for the messages that need `DefWindowProc` to act.
  Note `WM_NCHITTEST` (SendMessage) and `WM_PAINT` both work throughout — so
  the wndproc IS running, which argues against a wedged pump.
- Something in the app re-asserts window state (the T48 / restore-focus
  ping-pong family: `App.zig`'s run loop touching foreground/show state).
- A desktop-scoped restriction on state-changing calls (`ShowWindow` from
  `DefWindowProc`) that does not apply to a window that has not yet been
  positioned.

## Why it matters beyond T254

`test/win32/caption-bar.ps1` currently SKIPS its whole window-state section
with a printed reason, guarded by a `WM_CLOSE` positive control (the
`window-size-memory.ps1` ABORT idiom). That is honest, but it means **the
caption buttons' actual minimize/maximize/close effects, and the maximized
`WM_NCCALCSIZE` frame inset, are not covered by any automated test.** The
maximized inset in particular is the classic custom-titlebar bug — get it
wrong and the entire button row sits above the monitor's top edge, invisible
and unreachable, while the window looks perfect.

Any future test that needs to drive a window's state on the background desktop
hits the same wall, so this is infrastructure, not a T254 footnote.

## Validation

- Root-cause it (which of the hypotheses, or another), with the measurement
  that proves it.
- Either fix it, or give `TestDesktop.ps1` a documented way to drive window
  state that works — and then un-SKIP `caption-bar.ps1`'s section 5 so the
  minimize / maximize+restore / close / press-then-slide-off-cancels
  assertions and the maximized caption-on-screen check all run.
- Negative control mandatory.
