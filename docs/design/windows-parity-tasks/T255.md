# T255 - Background test desktop: a long-lived window ignores WM_CLOSE and WM_SYSCOMMAND

## In plain terms

A test that opens a Ghoztty window sometimes found it would not respond to
"minimize", "maximize" or "close" — it just sat there. We assumed the special
invisible desktop our tests run on could not do those things, and switched off
a whole block of checks because of it, which left the titlebar buttons with no
automated coverage at all.

The desktop was never the problem. The window was showing a dialog — "Processes
are still running in this window. Close anyway?" — and while that dialog is up
Windows itself refuses to minimize, maximize or close the window behind it.
Nobody could see the dialog, because the whole point of that desktop is that it
is off screen, so it looked like a dead window instead of a waiting one. The
tests can now spot that dialog, say which one it is, and answer it — so the
switched-off checks are back on.

## Goals

- [x] root-cause it with a measurement, not a hypothesis
- [x] give the harness a supported way to see and clear what is blocking a window
- [x] un-SKIP `caption-bar.ps1`'s window-state section
- [x] a negative control that must fail

## Summary

Found while validating **T254** (the custom caption bar). The caption buttons
post `WM_SYSCOMMAND` with `SC_MINIMIZE` / `SC_MAXIMIZE` / `SC_RESTORE` /
`SC_CLOSE`, and none of them had any effect in the acceptance script — but the
cause is NOT in T254's handler, and proving that is the whole point of this
task existing separately.

## Evidence (VERIFIED on the box, 2026-07-31)

Three measurements, in order, against `zig-out\bin\ghoztty.exe` on a
`test/win32/lib/TestDesktop.ps1` background desktop:

1. **Our handler runs and is correct.** A posted `WM_NCLBUTTONDOWN` with
   `wparam = HTMAXBUTTON` lights the button's pressed fill — the pixel under
   the maximize square reads `45,45,45` against the band's `20,20,20`, i.e.
   exactly `icon_button.fillDelta(.pressed)`. That paint cannot happen unless
   the message reached `handleNcLButtonDown` and matched a button rect.
2. **`WM_SYSCOMMAND` does nothing on that window, by ANY route.** Posted
   `SC_MAXIMIZE` → `IsZoomed` still false. `SendMessage`d `SC_MAXIMIZE` (the
   harness's own `Send-TestSysCommand`, whose comment calls it *"the real
   maximize/restore path"*) → still false. `SendMessage`d `SC_MINIMIZE`
   returned 0 and the window rect stayed at its normal position.
3. **Even a plain `WM_CLOSE` does nothing** — and `WM_CLOSE` has no
   relationship to T254 at all. That is what rules the caption bar out as the
   cause.

The confusing part, and the reason this needs its own investigation: a
**freshly launched** window on the same desktop, same build, DOES close on
`WM_CLOSE`. The window that ignores everything is the one that has been alive
for a few seconds and has had `Set-TestWindowSize` called on it. So it is
state- or age-dependent, not categorical.

## ROOT CAUSE (measured on the box, 2026-08-11)

**None of the hypotheses below. The desktop is not involved at all: the window
was DISABLED by the app's own close-confirmation dialog.**

`Window.wndProc`'s `WM_CLOSE` calls `confirmCloseIfNeeded`, which for a pane
whose shell has a running child raises `ConfirmDialog.show` — and that calls
`EnableWindow(owner, FALSE)` for the length of its own modal message loop
(`ConfirmDialog.zig:474`, restored at `:495`). A **disabled** window is one
`DefWindowProc` discards every `WM_SYSCOMMAND` for, so `SC_MINIMIZE`,
`SC_MAXIMIZE`, `SC_RESTORE` and `SC_CLOSE` all become no-ops while it is up —
and a second `WM_CLOSE` only re-enters `confirmCloseIfNeeded` and raises
another dialog. The state is therefore **self-perpetuating**: whatever raised
the first dialog makes every probe after it read as dead.

That explains all three original measurements at once, including the confusing
one. `WM_NCHITTEST`, `WM_PAINT` and our own `handleNcLButtonDown` keep
answering throughout, because the UI thread is pumping perfectly well — the
window is **blocked, not wedged**, and those two look identical from outside.
It also explains the age dependence: a freshly launched pane has
`core_surface_ready == false`, so `confirmCloseIfNeeded` returns true and the
window closes silently; a few seconds later the pane is ready and anything
running under its shell arms the dialog. On the interactive desktop you would
simply have seen it.

Measured, three arms, one process each (`test/win32/window-modal-block.ps1`):

| | idle shell | busy shell (`ping -n 60`) |
|---|---|---|
| `WM_CLOSE` | window closes | window stays, `enabled=False` |
| owned top-level | — | `GhozttyConfirmDialog` |
| `SC_MINIMIZE` | n/a | no-op (`WS_MINIMIZE` unset) |
| `WM_NCHITTEST` | n/a | still answers (12) |

and the reversal, which is what makes it a cause rather than a correlation:
dismiss that dialog, change nothing else, and the **same** `SC_MINIMIZE`
iconifies the window.

## Fix

- `test/win32/lib/TestDesktop.ps1` gains **`Get-TestModalBlocker`** and
  **`Clear-TestModalBlocker`**. The blocker is identified by BEHAVIOUR, not by
  class: the window must be disabled (that is what "blocked" means), and the
  blocker is an owned, visible top-level that can take **activation**. That
  last bit is the discriminator — the scrollbar, banner, dim layer and
  key-state indicator are all visible owned popups of the same window, and all
  are `WS_EX_NOACTIVATE` precisely so they never steal focus, so a class
  allowlist would have needed maintaining and this does not.
  `Clear-TestModalBlocker` answers the dialog and returns its CLASS, so a
  script that had to clear one can say which — an unexpected confirmation is
  itself a finding.
- `test/win32/caption-bar.ps1` section 5 is **un-SKIPped**: the guard and its
  SKIP branch are gone, the section always runs, and a control close that does
  not close is now interrogated (blocker named, answered, reported as a
  FAILURE) instead of being blamed on the desktop. 24 assertions → 27.

## Hypotheses to test (settled by the measurement above)

The first one was half right and its own reasoning talked it out of the answer:
there IS a modal loop, but the queue is NOT being selectively serviced — it is
serviced completely, and `DefWindowProc` declines the sys commands because the
window is disabled. "The wndproc IS running, which argues against a wedged
pump" was the correct observation attached to the wrong conclusion; a pumping
wndproc is what a BLOCKED window looks like, not evidence against one. The
second and third are refuted outright.

- The app is in a modal or blocking state by then (a `TrackPopupMenuEx`-style
  loop, an agent dial, a `Condition.wait`) and its queue is being serviced for
  paint/hit-test but not for the messages that need `DefWindowProc` to act.
  Note `WM_NCHITTEST` (SendMessage) and `WM_PAINT` both work throughout — so
  the wndproc IS running, which argues against a wedged pump.
- Something in the app re-asserts window state (the T48 / restore-focus
  ping-pong family: `App.zig`'s run loop touching foreground/show state).
- A desktop-scoped restriction on state-changing calls (`ShowWindow` from
  `DefWindowProc`) that does not apply to a window that has not yet been
  positioned.

## Why it matters beyond T254

`test/win32/caption-bar.ps1` **used to** SKIP its whole window-state section
with a printed reason, guarded by a `WM_CLOSE` positive control (the
`window-size-memory.ps1` ABORT idiom). That was honest, but it meant **the
caption buttons' actual minimize/maximize/close effects, and the maximized
`WM_NCCALCSIZE` frame inset, were not covered by any automated test.** The
maximized inset in particular is the classic custom-titlebar bug — get it
wrong and the entire button row sits above the monitor's top edge, invisible
and unreachable, while the window looks perfect.

Any future test that needs to drive a window's state on the background desktop
hit the same wall, so this is infrastructure, not a T254 footnote.
