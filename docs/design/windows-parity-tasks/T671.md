# T671 - Screenshot capture has no keyboard-only path: a region can only be selected by dragging

## In plain terms

The new screenshot button opens a picker you can only use with a mouse: you
have to drag a rectangle. Someone who works from the keyboard can start the
capture (Ctrl+Shift+S) and then has no way to finish it except to press
Escape. This gives the picker a keyboard.

## Summary

Noticed while building T647. The selector reads its whole gesture out of mouse
messages; the only key it answers is Escape. A capture that can be STARTED
from the keyboard and not FINISHED from it is worse than one with no chord at
all, because the chord promises a keyboard path that is not there.

## Details

- Arrows move a caret point; Shift+arrows extend from the anchor; Enter
  captures; Escape still cancels. Ctrl+arrow as the coarse step (say 32 px vs
  1 px) so crossing a 4K monitor is not a marathon.
- Tab (or Space, if T670 lands first and takes Space) to cycle candidate
  windows is a much better keyboard answer than nudging a rectangle by hand —
  worth doing whichever of the two lands second, and worth noting in the other
  task.
- The current selection rect must be ANNOUNCED, not just drawn: the hint card
  is already there and can carry `x,y  WxH` live, which also helps mouse users
  hit an exact size.
- Everything stays in the existing paint path — this adds no new drawing, only
  new ways for `anchor`/`cursor` to change.

## Validation criteria

- [ ] Unit tests (none lane): the key-driven cursor motion is pure — step
      sizes, clamping to the desktop, and Shift-extend from the anchor.
- [ ] On-box acceptance: with the selector up and NO mouse messages at all,
      arrows + Shift+arrows + Enter produce a capture of a predicted size
      (posted `WM_KEYDOWN`s only, which is what the harness can do anyway).
- [ ] On-box acceptance: Escape still cancels from the keyboard-driven state.
- [ ] On-box acceptance: the hint card shows the live selection size.
