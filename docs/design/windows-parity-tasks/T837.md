# T837 - The agent lane can leave its test binaries running long after it reports PASS

## Summary

Measured 2026-08-14 while validating T834. floor-lane.ps1 -Lane all reported 'LANE agent PASS in 191s' and the lane's own log stopped writing at 14:15:20, but ghoztty-agent-test.exe (pid 4136) and ghoztty-agent-core-test.exe (pid 14704), both started 14:12:14 by that lane, were still present at 14:40 with their CPU time frozen at ~122s across several minutes of sampling - alive, wedged, and 25 minutes past the verdict. They were gone by 14:45. floor-lane already sweeps leaked webview hosts ('leaked webview hosts swept: 0') and does not look for leaked test binaries.

## In plain terms

The test suite says it finished and passed, but two of the programs it started
are still sitting there afterwards, stuck and doing nothing. They hold on to
machine resources for as long as they live, and the next test run has to share
the box with them — which is exactly the kind of interference that makes a test
suite look randomly flaky.

## Goals

- [x] Every floor lane ends with a `leaked test binaries: N` number, whether or
      not anything leaked, so a recurrence is measured instead of stumbled on
- [x] A leak names itself: which binary, which pid, how much CPU it burned, how
      long it outlived its lane
- [x] A leak is explained before it is cleaned up — a non-invasive `cdb` stack
      of every thread, captured while the process is still alive
- [x] A leak is then reaped, so the next lane does not share the box with it
- [x] An acceptance harness proves all of that against a process that
      deliberately outlives its lane

## Details

Not reproduced on demand yet — this is one observation, recorded with its
numbers so the next occurrence can be recognised rather than re-derived:

| fact | value |

| verdict | `LANE agent PASS in 191s` |
| lane log last write | 14:15:20 |
| `ghoztty-agent-test.exe` | pid 4136, started 14:12:14, alive at 14:40 |
| `ghoztty-agent-core-test.exe` | pid 14704, started 14:12:14, alive at 14:40 |
| CPU of both, sampled minutes apart at 14:40 | ~122s, essentially unchanged |
| gone by | 14:45 |

Two things to establish, in this order:

1. **Does it recur, and how often?** A sweep at the end of `floor-lane.ps1`
   that counts surviving `*-test.exe` processes started by the lane would
   answer that as a by-product of the floor everybody already runs — the
   webview-host sweep in the same script is the pattern to copy, and its
   `leaked webview hosts swept: N` line is the reporting shape.
2. **Are they wedged at exit, or still working?** Frozen CPU says wedged.
   `cdb -pv -p <pid> -c "~*k; q"` on the next occurrence names the wait, and
   that is what turns this from a cleanup into a fix.

Worth holding next to **T443**: that hunt has established the build runner as
a necessary condition for the corruption it chases, and a lane that can leave
wedged binaries behind is a fact about the same condition. It is not evidence
of the same bug and should not be written up as such without a stack.

### What shipped (2026-08-17)

`scripts\lib\LaneLeak.ps1`, wired into `floor-lane.ps1` at the end of every
lane run — before the webview sweep, because a leaked test binary OWNS the
WebView2 hosts that sweep looks for, and a host whose owner is already dead is
the case it (and its profile-directory cleanup) handles cleanly.

**How a leak is identified.** The lane's process tree is gone by the time we
look, so parentage is not available. A leak is a process that carries one of
the lane's test-binary names, was NOT running when the lane started, and was
created at or after the lane started. The pid snapshot is what keeps the sweep
away from a binary somebody else was already running — including a debugger
session left attached by hand — and the creation-time rule is belt and braces
on top of it. The one case this cannot separate is a SECOND floor run
overlapping this one, which go.md step 3 already forbids for unrelated reasons
(a concurrent lane starves test waits badly enough to wedge them).

Detection runs even under `-NoSweep`, because the COUNT is the point of this
task and the killing is only the cleanup; `-NoSweep` reports and leaves the
processes alone. `-NoCatch` (the existing "do not spend minutes under a
debugger" switch) skips the stack.

**First real floor run with the instrument** (2026-08-17, 15:07): lib PASS 52s,
none PASS 282s, win32 PASS 356s, agent PASS 357s, every line ending
`leaked test binaries: 0`, and the whole run took 17.5 minutes of wall clock
against 17.5 minutes of lanes. So the leak did not recur today — which is now a
MEASUREMENT rather than the absence of one, and that is the entire point of
this task. (T933 measured the same floor at 61 minutes of wall clock for 17.6
of lanes three days ago; the number to watch is that gap.)

Deliberately NOT done here: making the agent test binaries exit with their
lane, and stopping a leaked child's CPU from convincing the stall detector the
lane is still working. Both belong to **T933**, which measured the same leak
costing ~40 minutes of dead time on a floor run; this task gives that one its
instrument.

## Validation criteria

- [x] The floor reports leaked lane test binaries the way it reports leaked
      webview hosts, so recurrence is counted rather than noticed by accident
      — every `LANE …` line now carries `leaked test binaries: N` next to the
      webview count, and a leak also prints a `LANE LEAK:` line naming the
      binary, its pid, its CPU and how long it outlived the lane. Proven by
      `test\win32\floor-lane-leak-sweep.ps1` arms "the LANE line counts the
      leaked test binary" and "the lane names the leak it found" (end to end
      through `floor-lane.ps1 -Command`), and on the real floor run below.
- [x] A leaked process is either explained by a captured stack, or swept —
      both, in that order: `Get-LeakedProcessStack` attaches non-invasively
      (`cdb -pv -p <pid> -c "~*k; q"`), writes every thread's stack to
      `.dumps\lane-leak-<pid>-<stamp>.log`, and only then is the process
      killed. Proven with a REAL cdb attach in the harness arms "a stack is
      captured for the leaked process", "the stack names threads" and "the
      non-invasive attach left the process alive", then "the sweep reaps the
      leaked process".
- [x] `test\win32\floor-lane-leak-sweep.ps1` (named for its sibling
      `floor-lane-cache-heal.ps1`, not the `floor-lane.ps1` this file first
      guessed) covers the sweep with a fixture that deliberately outlives its
      lane: a private copy of `waitfor.exe` blocking on a signal that never
      arrives — blocked, burning no CPU, which is the shape of the wedged
      binaries above. 21 arms, ALL PASS. Registered in
      `scripts\guard-due.ps1` as `lane-leak-sweep`, so an edit to
      `scripts\lib\LaneLeak.ps1` makes the harness due again.
