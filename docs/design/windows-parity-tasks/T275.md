# T275 - Generalise Surface.heroSnap into a capturable terminal-content path so GL pixels are assertable off the input desktop

## Summary

T214 decided the four routes a terminal-content probe can take off the input
desktop, and deliberately did NOT build the fifth - an app-side GL readback.
This task is that fifth route, filed with the reason it was deferred and the
reason it is cheaper than it looks, so the decision stays reversible.

**The app already has half of it.** `Surface.heroSnap*` has the pane's own
renderer thread capture its GL content into a DIB, and the GUI thread blits
that DIB into the PARENT window's DC inside `BeginPaint` - which is exactly
the boundary crossing a capture needs. `PrintWindow` reads the hero carousel's
thumbnails today (101 distinct colors, measured on the test desktop in T218
batch 6). So the missing piece is not "can the renderer hand pixels to GDI",
which is answered; it is a way for a test to ask for that snapshot on demand
and read it back.

Do NOT invent a second capture path. Generalise this one.

## Why it was deferred (T214, 2026-08-01)

The measured population of blocked assertions turned out to be small, and
every one of them had a cheaper route:

| blocked probe | route taken |
| --- | --- |
| `hero-mode.ps1` x2 `Get-PaneColorCount` | dropped in place, reason in the header |
| `window-color.ps1` pane-centre tint | substituted - the banner band is another native painter of the same effective background |
| `profile-latency.ps1` scroll pixel hash | interactive by design (the script's whole method is SendInput timing) |
| `color-contrast.ps1` (whole script) | interactive by design - see T276 |

Building a product-visible IPC capture verb for four assertions was the wrong
trade at that size. What would flip it: a THIRD script needing terminal
content, or `color-contrast.ps1` (an accessibility oracle) staying un-run in
the loop long enough to rot. Both are plausible, which is why this is filed
rather than closed.

## What it has to do

1. A way to request a snapshot of a specific pane's rendered content and get
   the pixels back out of process. `+read` is the shape precedent (named pane
   in, content out); the transport for a bitmap is the open question - a PNG
   written to a caller-supplied path is likely simpler than framing bytes
   over the IPC socket, and is directly consumable by an acceptance script.
2. It must reuse the renderer-thread capture `heroSnap` already performs,
   not add a second GL readback path with its own lifetime rules.
3. It must work with the pane NOT visible and NOT focused - that is the whole
   point, and hero mode already proves the renderer keeps producing for a
   hidden pane.
4. Decide whether it ships as a user-facing verb or stays behind a debug-only
   gate, and say which in the task. A test-only mechanism that ships to users
   is a surface we have to keep; a debug-only one cannot be used by the
   installed release the user runs.

## Validation

- The three assertions T214 dropped come back, and their negative controls
  FAIL: `hero-mode`'s "hero pane renders content" must go red against a pane
  that renders nothing, not merely pass against one that does.
- `color-contrast.ps1` migrates to the test desktop and keeps its measured
  contrast ratios within tolerance of the interactive-desktop numbers it
  reports today - same oracle, different capture.
- `test-desktop-harness.ps1`'s capture-limit section is updated rather than
  deleted: the flat-fill limit on a DIRECT `GhozttyTerminal` PrintWindow is
  still true, and the guard in `Get-TestWindowPixels` still has to hold. This
  task adds a way around it; it does not make the trap go away.
