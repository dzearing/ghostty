# T275 - Generalise Surface.heroSnap into a capturable terminal-content path so GL pixels are assertable off the input desktop

## In plain terms

The automated tests run on an invisible second desktop so they never steal your
screen. The price was that they could no longer SEE what a terminal was
actually showing - the picture they could take of a terminal pane came back as
one flat color - so three checks about colors and rendering were switched off,
and the accessibility check had to be run by hand.

Now the app hands out its own picture: the terminal asks its renderer for the
pixels it just drew and writes them to a file. That works for a pane nobody can
see, so all four checks are back on, running automatically, and a check that
the wrong colors reached the screen fails instead of quietly passing.

## Goals

- [x] a way to ask a specific pane for its rendered pixels, from outside the app
- [x] reuse the renderer capture hero mode already performs, not a second one
- [x] works for a pane that is neither visible nor focused
- [x] decide and record: shipped verb, or debug-only seam
- [x] the three assertions T214 dropped come back, with teeth
- [x] `color-contrast.ps1` runs on the background desktop

## Summary

T214 decided the four routes a terminal-content probe can take off the input
desktop, and deliberately did NOT build the fifth - an app-side GL readback.
This task is that fifth route, filed with the reason it was deferred and the
reason it is cheaper than it looks, so the decision stays reversible.

**The app already has half of it.** `Surface.heroSnap*` has the pane's own
renderer thread capture its GL content into a DIB, and the GUI thread blits
that DIB into the PARENT window's DC inside `BeginPaint` - which is exactly
the boundary crossing a capture needs. `PrintWindow` reads the hero carousel's
thumbnails today (101 distinct colors, measured on the test desktop in T218
batch 6). So the missing piece is not "can the renderer hand pixels to GDI",
which is answered; it is a way for a test to ask for that snapshot on demand
and read it back.

Do NOT invent a second capture path. Generalise this one.

## Why it was deferred (T214, 2026-08-01)

The measured population of blocked assertions turned out to be small, and
every one of them had a cheaper route:

| blocked probe | route taken |
| --- | --- |
| `hero-mode.ps1` x2 `Get-PaneColorCount` | dropped in place, reason in the header |
| `window-color.ps1` pane-centre tint | substituted - the banner band is another native painter of the same effective background |
| `profile-latency.ps1` scroll pixel hash | interactive by design (the script's whole method is SendInput timing) |
| `color-contrast.ps1` (whole script) | interactive by design - see T276 |

Building a product-visible IPC capture verb for four assertions was the wrong
trade at that size. What would flip it: a THIRD script needing terminal
content, or `color-contrast.ps1` (an accessibility oracle) staying un-run in
the loop long enough to rot. Both are plausible, which is why this is filed
rather than closed.

## What it has to do

1. A way to request a snapshot of a specific pane's rendered content and get
   the pixels back out of process. `+read` is the shape precedent (named pane
   in, content out); the transport for a bitmap is the open question - a PNG
   written to a caller-supplied path is likely simpler than framing bytes
   over the IPC socket, and is directly consumable by an acceptance script.
2. It must reuse the renderer-thread capture `heroSnap` already performs,
   not add a second GL readback path with its own lifetime rules.
3. It must work with the pane NOT visible and NOT focused - that is the whole
   point, and hero mode already proves the renderer keeps producing for a
   hidden pane.
4. Decide whether it ships as a user-facing verb or stays behind a debug-only
   gate, and say which in the task. A test-only mechanism that ships to users
   is a surface we have to keep; a debug-only one cannot be used by the
   installed release the user runs.

## What was built

A **debug-only IPC action**, `capture-pane`, with **no CLI verb** - see D69 for
the call and its alternatives. `src/cli/ghostty.zig`'s `Action` enum is shared
by every apprt, so a verb there is a cross-platform CLI surface (the T141 rule),
and this has exactly one consumer: the win32 acceptance suite, which must run
against a Debug build anyway (T350). A ReleaseFast build answers `unknown
action: capture-pane`.

| piece | file |
| --- | --- |
| pure: request shape, capture size, bottom-up BGRA -> top-down RGB | `src/apprt/win32/pane_capture.zig` (none lane) |
| the handler: resolve, capture, encode, write | `src/apprt/win32/ipc_capture.zig` |
| the wait for the renderer's answer | `Surface.captureContent` |
| harness: framed request + PNG readers | `test/win32/lib/PaneCapture.ps1` |
| acceptance | `test/win32/pane-capture.ps1` |

It reuses hero mode's readback rather than adding one: `heroSnapRequest` ->
`OpenGL.captureThumb` reads the OFFSCREEN target, which is why a hidden pane
works and why there is still exactly one GL readback path in the app.

## Validation criteria

- [x] The three assertions T214 dropped come back, and their negative controls
      FAIL. `hero-mode.ps1` phase 1 now asserts "hero pane renders content"
      (131 distinct colors) AND "HIDDEN pane renders content" (127) - ALL PASS
      (70 assertions). `window-color.ps1` asserts the tint reached the GL clear
      color beside the banner band it was substituted with - ALL PASS (35).
      Teeth: `pane-capture.ps1 -NegativeControl` expects pane B's glass to
      carry pane A's tint - exactly what a flat fill or a wrong-pane read would
      give - and goes red (1 FAILURE(S), exit 1).
- [x] `color-contrast.ps1` migrates to the test desktop and keeps its ratios.
      ALL PASS (16 assertions) on the background desktop: 18.43:1 default
      foreground, 10.6:1 index 250 (stock 1.67:1), 3.03:1 truecolor, 4.69:1 on
      mid-grey with a BLACK foreground. Two of those are analytically exact -
      4.69:1 IS pure black on #777777, and 3.03 sits on the renderer's nominal
      3.0 floor - so the readback is not merely close, it is the same numbers.
      The `ContrastDrv` screen-DC P/Invoke block is gone with it.
- [x] `test-desktop-harness.ps1`'s capture-limit section is updated rather than
      deleted. The three flat-fill assertions stand unchanged, and a FOURTH
      reads the SAME pane at the SAME moment through route 0: 94 distinct
      colors vs 1 through PrintWindow. `Get-TestWindowPixels` still refuses a
      `GhozttyTerminal` capture; TestDesktop.ps1's header says so explicitly
      ("route 0 does not go through PrintWindow at all").
- [x] Floor: `floor-lane.ps1 -Lane all` = none PASS / win32 PASS / agent PASS;
      P1 (25) / P2 (20) / P3 (16) ALL PASS.
- [x] Harness sweeps still clean: harness-exitcode-audit, skip-visibility,
      verdict-exit-audit, asserted-nothing (28), foreground-audit (26).
