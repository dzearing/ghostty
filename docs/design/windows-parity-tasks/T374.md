# T374 - T90d3: web-mode --view end to end + verb rejections + viewer-panes.ps1

## Summary

Flip T90b's interim 'viewers are not yet supported on Windows' error: +new-window --view=<url> and +split --view=<url> construct a real viewer PaneView in the split tree (web mode only), +list reports type=viewer/url and the view: prefix, terminal-only verbs (+read/+send-keys/+set-state/+set-banner) reject with 'target <name> is a viewer pane, not a terminal' exit 1, +close stays silent, NewWindowRequested -> Handled=TRUE + default browser WITHOUT discarding the deferral (T163 needs it). Grows test/win32/viewer-panes.ps1 (launched with --session-persistence=false).

## Done 2026-08-02

Viewer panes are real on Windows. `ghoztty +new-window --view=https://…` opens a
window whose one pane is a web view; `ghoztty +split --view=about:blank
--name=doc` puts one beside a terminal, and it resizes, focuses, closes and
lists like any other leaf.

**Half the task was already standing.** Reading it against the code first — the
T321 discipline — found that `+list`'s viewer branch (`type`/`url`, the `view:`
row, auto-registration) and all four terminal-only rejections were landed by
T90b/T90c and only ever exercised against zero viewers. What was actually
missing was the two ends: something to CONSTRUCT a viewer leaf from IPC, and
`Navigate` to point it somewhere. So the work came out as tree plumbing plus two
vtable slots, not the surface rewrite the title suggests.

**The interim error moved down a level rather than being deleted.**
`--view=README.md` still fails, now with `file viewers are not yet supported on
Windows; --view needs an http(s) or about: URL`. WebView2 will happily navigate
to a `file://` URL — the live test proves it — and that is exactly why the error
has to stay: rendering a markdown document as raw text is the same
silently-wrong-pane defect T90b fixed, one level down. The classifier is
`args.viewMode`, pure and unit-tested, and it deliberately does NOT key on
`://`: `file:///c:/src/README.md` names a FILE. T90e deletes the error and the
`.file` arm becomes the renderer.

**Two vtable slots, and both proven against the live runtime.** `Navigate` is
slot 5 of `ICoreWebView2` and `add_NewWindowRequested` is slot 44 — transcribed
from the SDK's own `WebView2.h` (the `DECLSPEC_XFGVIRT` annotations, which state
per slot which interface contributed it), never from memory, and asserted by
`@offsetOf`. The 38 slots between them are one length-only opaque block, the
rule `ICoreWebView2_13` already set.

**The oracle for `Navigate` had to be replaced twice, and that is the lesson.**
The first version navigated to `about:blank` and asserted `get_Source` came back
`about:blank` — which is what a freshly created web view reports ANYWAY. It was
green before the call under test ever ran: a green and empty assertion of
exactly the kind T216 named. The second version used a `data:` URL and came back
empty, because Chromium blocks top-level navigation to one. What works is a real
local file written to a temp dir: it needs no network, it is definitely not the
default source, and the assertion is by SHAPE (`file:///…/t374.html`) rather
than string equality, because pinning the exact spelling would be asserting
Chromium's URL normalization rather than our navigation.

**An event handler outlives the pane that registered it**, and that is a
different ownership problem from T373's one-shot completed handlers. A completed
handler is invoked once and released; `NewWindowRequested` lives as long as the
runtime keeps it, which is not a moment our code can name. So its context is the
pane's refcounted `Pending` token (already nulled when the pane dies — a late
popup from a closing view must not open a browser tab), and the token reference
has to die WITH the handler object, not with the pane. `com.CallbackOwning` is
that hook: one branch, taken once, immediately before the object frees itself.
The testing allocator is the oracle — the live test would report a leak if the
runtime kept the object past `Close`, and it does not.

`Handled = TRUE` is set FIRST and unconditionally, before anything that can
fail: whatever else goes wrong, a popup must not open a chrome-less WebView2
window we neither own nor can close. The deferral is left UNTAKEN rather than
taken and dropped — taking one and dropping it wedges the requesting page
forever, and T163 is the task that will need it.

**Two shared tails came out of the tree plumbing**, `insertPaneAsTab` and
`insertPaneAsSplit`. Both are the fallible-work-first shape the file already
used: everything that can fail happens in the caller, so each constructor owns
its own cleanup and the tab/tree bookkeeping exists once. `addViewerTab` and
`newViewerSplitAt` return the `*PaneView`, not the `*ViewerPane` — the leaf is
what a caller registers, focuses and finds, and a viewer has no `pane_view`
back-pointer to get there from (a `Surface` does).

The host window is created `WS_VISIBLE`. `visible` starts true and `setVisible`
short-circuits a value it already holds, so a hidden host window would have
depended on a layout pass to appear — a second source of truth for one bit.
`Surface.init` shows its child window for the same reason.
