# T570 - The Activity Monitor acceptance suite has no spawn-a-victim fixture for the REMOTE panel's Kill button

## Summary

**Rescoped 2026-09-05, before any code was written.** As filed, this card asked
for a spawn-a-victim fixture in `test/win32/activity-monitor-remote.ps1` so the
remote panel's negative control could press Kill, and it said so itself: *"Only
becomes required work if D29 is answered with its second option."* D29 was
answered with its FIRST option on 2026-08-11 — keep the harmless button — so the
remote fixture is explicitly not wanted, and building it would put the
acceptance suite in the business of terminating processes on a machine it does
not own.

What survives is the con D29 recorded against that answer: **Kill's own key path
was unasserted anywhere.** `activity-monitor.ps1` section L5 proves Kill BECOMES
a Tab stop once a row is selected, and section I proves a kill works when the
button is CLICKED, but nothing in either script had ever pressed Kill from the
keyboard — so a keyboard-only user's entire route to the panel's one destructive
action was untested, on both panels. D29's mitigation pointed at section L,
which covers the Tab stop and not the activation.

The deliverable is therefore that same assertion made where it is safe by
construction rather than by care: **the LOCAL panel**, whose section M already
spawns `ping -n 600 127.0.0.1` throwaways through the panel's own New Process
dialog and isolates them with a needle that matches nothing else in the app's
process tree. New **section O** does the whole route with no mouse in it — Down
to select, Tab onto Kill, Space to confirm, Tab onto the affirmative, Enter to
kill — and picks up a claim that was, until now, only a comment in
`activity_procs.zig`: `default_cancel = true` is there so *"an accidental Enter
must never kill anything"*, and O3 is the arm that presses that Enter.

## In plain terms

You can drive the Activity Monitor entirely from the keyboard — but nobody had
ever checked that the Kill button actually works that way. The tests only ever
clicked it with the mouse. If a keystroke had stopped reaching Kill, or if the
confirmation box had started opening with "Kill" selected instead of "Cancel" —
so that tapping Enter out of habit killed a process — nothing would have caught
it. Now a test spawns a harmless throwaway process, kills it using only the
keyboard, and separately proves that a stray Enter on the confirmation kills
nothing at all.
