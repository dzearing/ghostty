# T282 - Test harness cannot hold a hover: the hovered frame is never painted on the background desktop

## Summary

Every hover FILL in the win32 chrome is currently unassertable in pixels, and
three tasks have now paid for it separately: T233 (split divider), T209 (the
tab close "x" and the banner chevron), and by extension anything else the
design system says must light on hover.

T233 diagnosed the first half: a posted `WM_MOUSEMOVE` cannot HOLD a hover,
because `TrackMouseEvent` watches the REAL cursor and there is none over the
window on a background desktop, so `WM_MOUSELEAVE` lands within a frame. T209
measured the sharper statement, and it is worse:

**The hovered frame is never PAINTED at all.** `WM_MOUSELEAVE` is a POSTED
message and `WM_PAINT` is the lowest-priority message in the queue, so the
leave is always drained before the paint that the move dirtied - and that
paint renders the un-hovered state. This is not a timing window that a faster
capture can win. Measured: 300 posted moves in bursts of 25, interleaved with
`PrintWindow` captures, never once caught a lit fill - not on the close "x",
not on the "+" that has lit a fill since long before T204, not on the chevron.

## Why it matters

Each affected script currently proves the TRIGGER from a debug-log oracle and
SKIPS the COLOR, or proves the color through a state that happens to survive a
leave (T233 used a DRAG; `caption-bar.ps1` uses `caption_pressed`, which
`handleNcMouseLeave` deliberately does not clear). Those are real evidence,
but they are per-site workarounds: a control with no drag and no press - which
is every plain hover - has no route at all, and "SKIP" accumulates.

## What to build

Give the harness a way to hold a hover for one capture. Options, roughly in
order of preference:

1. **A capture that runs INSIDE the paint.** If `Get-TestWindowPixels` could
   force a synchronous repaint that is ordered after the move and before the
   leave, the race disappears. `RedrawWindow(RDW_UPDATENOW)` is a SENT message
   and jumps the posted queue, which is the wrong side - so this needs the
   move to be sent too, and the ordering guarantee written down rather than
   hoped for.
2. **Suppress the leave for the duration of a probe.** A test-only path that
   ignores `WM_MOUSELEAVE` while a debug flag is set is honest if it is loud,
   but it is product code that exists for tests - weigh against option 1.
3. **Prove the fill through a HELD state on each control**, the way T233 and
   `caption-bar.ps1` already do, and accept that plain-hover controls need a
   press or a latch to be assertable. Cheapest, and the weakest.

Whatever lands, the deliverable is that `tab-strip.ps1`'s 4c and
`pane-banner.ps1`'s 6g stop skipping - both already carry the assertions and a
positive control, so they only need the frame.

## Validation

- `tab-strip.ps1` and `pane-banner.ps1` ALL PASS x3 with NO `SKIP T204 hover
  fill` / `SKIP T209 chevron fill` line in the output.
- `T204_NEUTERED = true` makes the close-"x" and chevron fill assertions fail
  while the "+"'s (which predates T204) still passes - that asymmetry is the
  whole claim, and it is what a skip currently hides.
- `split-divider.ps1` still ALL PASS; if option 1 or 2 lands, its own
  `SKIP T233 hover trigger` path should be revisited in the same turn.
