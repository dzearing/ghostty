# T282 - Test harness cannot hold a hover: the hovered frame is never painted on the background desktop

## In plain terms

Buttons in Ghoztty's window chrome light up when you point at them — the tab's
close "×", the "+" that opens a tab, the little chevron on a pane banner, the
divider between two panes. The automated tests could never take a picture of
that: they run on an invisible second desktop where there is no real mouse
pointer, so Windows cancelled the hover a fraction of a second before the
window repainted, and the picture always came back showing the button at rest.
Tests that wanted to check "does this light up?" gave up and printed SKIP.

Now the app takes the picture itself, all in one uninterrupted step, so the
hovered frame really gets painted. Nobody using Ghoztty sees anything new — what
changes is that a button that quietly stopped lighting up would now be caught
by a test instead of shipping.

## Goals

- [x] A hovered frame can be captured on the background test desktop at all
- [x] `tab-strip.ps1` asserts the close "×" and "+" hover fills instead of skipping
- [x] `pane-banner.ps1` asserts the chevron fill instead of skipping
- [x] `pane-banner.ps1` asserts the link underline going solid on hover (same limit)
- [x] `split-divider.ps1` asserts the hovered band's COLOR directly, not only under a drag
- [x] The `T204_NEUTERED` control produces the asymmetry it claims (+ lit, × dark)

## Summary

Every hover FILL in the win32 chrome is currently unassertable in pixels, and
three tasks have now paid for it separately: T233 (split divider), T209 (the
tab close "x" and the banner chevron), and by extension anything else the
design system says must light on hover.

T233 diagnosed the first half: a posted `WM_MOUSEMOVE` cannot HOLD a hover,
because `TrackMouseEvent` watches the REAL cursor and there is none over the
window on a background desktop, so `WM_MOUSELEAVE` lands within a frame. T209
measured the sharper statement, and it is worse:

**The hovered frame is never PAINTED at all.** `WM_MOUSELEAVE` is a POSTED
message and `WM_PAINT` is the lowest-priority message in the queue, so the
leave is always drained before the paint that the move dirtied - and that
paint renders the un-hovered state. This is not a timing window that a faster
capture can win. Measured: 300 posted moves in bursts of 25, interleaved with
`PrintWindow` captures, never once caught a lit fill - not on the close "x",
not on the "+" that has lit a fill since long before T204, not on the chevron.

## Why it matters

Each affected script currently proves the TRIGGER from a debug-log oracle and
SKIPS the COLOR, or proves the color through a state that happens to survive a
leave (T233 used a DRAG; `caption-bar.ps1` uses `caption_pressed`, which
`handleNcMouseLeave` deliberately does not clear). Those are real evidence,
but they are per-site workarounds: a control with no drag and no press - which
is every plain hover - has no route at all, and "SKIP" accumulates.

## What to build

Give the harness a way to hold a hover for one capture. Options, roughly in
order of preference:

1. **A capture that runs INSIDE the paint.** If `Get-TestWindowPixels` could
   force a synchronous repaint that is ordered after the move and before the
   leave, the race disappears. `RedrawWindow(RDW_UPDATENOW)` is a SENT message
   and jumps the posted queue, which is the wrong side - so this needs the
   move to be sent too, and the ordering guarantee written down rather than
   hoped for.
2. **Suppress the leave for the duration of a probe.** A test-only path that
   ignores `WM_MOUSELEAVE` while a debug flag is set is honest if it is loud,
   but it is product code that exists for tests - weigh against option 1.
3. **Prove the fill through a HELD state on each control**, the way T233 and
   `caption-bar.ps1` already do, and accept that plain-hover controls need a
   press or a latch to be assertable. Cheapest, and the weakest.

Whatever lands, the deliverable is that `tab-strip.ps1`'s 4c and
`pane-banner.ps1`'s 6g stop skipping - both already carry the assertions and a
positive control, so they only need the frame.

## What landed

Option 1, moved to the side of the wire that can actually guarantee the
ordering. `capture-hover` is a debug-only IPC action
(`src/apprt/win32/ipc_hover.zig`, pure half in `hover_capture.zig`) that does
the whole probe inside ONE handler on the GUI thread: `WM_NCHITTEST`, then the
move SENT (a sent message is a direct call to the window procedure when sender
and target share a thread), then `RedrawWindow(RDW_UPDATENOW)` which sends
`WM_PAINT` on the same stack, then `PrintWindow(PW_RENDERFULLCONTENT)`. The
message loop is never reached between the move and the capture, and a POSTED
message is only ever drained by the message loop — so the `WM_MOUSELEAVE` the
move arms cannot land in the middle. The guarantee is about who is on the
stack, not about speed, which is what the header of `hover_capture.zig` states.

Option 2 was rejected for its failure mode: a "suppress the leave" flag is
product code whose bad day is a hover stuck lit. Nothing here has to be
un-done — the leave arrives on the next pump exactly as before, which
`hover-capture.ps1` section 4 asserts.

Same gate as `capture-pane` (T275): Debug/ReleaseSafe only, IPC only, no
`ghoztty +capture-hover` CLI verb (the T141 rule). Harness side:
`test/win32/lib/HoverCapture.ps1`, dot-sourced from `TestDesktop.ps1` so every
GUI script has it, and documented as route H in that file's CAPTURE LIMIT
header.

`T204_NEUTERED` had to be fixed to keep its own promise (below), which is a
finding the skips were hiding: the switch was consumed as one global
`universalHover()`, so it took the fill off EVERY icon button including the
"+", and "+ lit, × dark" — the asymmetry the acceptance scripts describe as
their positive control — was unreachable. It is `icon_button.lightsFill(glyph)`
now, per-glyph.
