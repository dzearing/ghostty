# T251 - split-divider-color has no contrast floor - a low-contrast pick makes the divider and its hover invisible

## Summary

Raised by **T233**, which added the divider's hover shade and asserted the
design system's 3:1 chrome-contrast floor for it — but could only assert it
for the **fallback** gray (128,128,128), because that is the only divider
color the product controls.

`split-divider-color` is an unconstrained user color. Nothing checks it
against the pane background, so `split-divider-color = #0a0a0a` on a black
terminal is an invisible divider, and T233's hover shade (+25/channel in a
dark theme) moves it to #232323 — still invisible. The control disappears and
its feedback disappears with it, which is exactly the failure the 3:1 floor in
`docs/design/win32-design-system.md` §2.3 exists to prevent for "chrome glyphs
and meaningful boundaries" (WCAG 1.4.11). A divider is a meaningful boundary.

Note this is NOT hypothetical-only: the same class of hole was the substance
of **T150** (palette entries sitting at 1.67:1 after a background change) and
its follow-up **T247**, so the project has already decided that "the user
picked it" is not a reason to render something unreadable.

## Open questions to settle first

- **What does Mac do?** `split-divider-color` exists there too. If Mac honors
  the raw value, diverging needs the same deliberate treatment T233's 2 DIP
  got — recorded in the design system, not silently different. Cite the Mac
  source line (the T240 lesson).
- **Adjust, or warn?** `color_math.contrastAdjusted(base, bg)` already exists
  (ported for T150) and would nudge the divider to the floor at paint time,
  which is consistent with how `min_contrast` treats terminal text. The
  alternative is to leave the color alone and surface a config diagnostic.
  Adjusting silently changes a color the user typed; not adjusting leaves a
  control they cannot see. Lean toward adjusting at PAINT time (so the config
  round-trips unchanged) unless Mac says otherwise.
- The floor must hold for **both** states — a rest color that clears 3:1 whose
  HOVER shade does not is still a defect.

## Validation

- Unit tests in `split_geometry.zig` beside the existing
  "rest AND hover clear the 3:1 chrome floor" test, extended to sweep
  adversarial user colors (near-black on black, near-white on white,
  mid-grays) rather than only the fallback.
- `split-divider.ps1`: a run with a deliberately terrible
  `--split-divider-color` still shows a band distinguishable from both panes.
