# T251 - split-divider-color has no contrast floor - a low-contrast pick makes the divider and its hover invisible

## In plain terms

You can choose the color of the line that sits between two split panes. Nothing
stopped you choosing one that is almost exactly the color of the panes — and if
you did, the line vanished, and so did the highlight that tells you the pointer
is over it. The thing you grab to resize your panes was simply not there any
more. After this, a color you pick is used as-is whenever it is readable, and
quietly lifted just far enough to be visible when it is not.

## Goals

- [x] A divider is never painted below 3:1 against the pane background, whatever
      `split-divider-color` says
- [x] The hovered/dragged divider clears the same floor — a legible line whose
      highlight is invisible is the same bug one frame later
- [x] The hover still reads as a change: it never lands on the rest color
- [x] A color that is already readable is painted exactly as typed, and the
      config file is never rewritten
- [x] The divergence from Mac is recorded in the design system, not silent

## Summary

Raised by **T233**, which added the divider's hover shade and asserted the
design system's 3:1 chrome-contrast floor for it — but could only assert it
for the **fallback** gray (128,128,128), because that is the only divider
color the product controls.

`split-divider-color` is an unconstrained user color. Nothing checks it
against the pane background, so `split-divider-color = #0a0a0a` on a black
terminal is an invisible divider, and T233's hover shade (+25/channel in a
dark theme) moves it to #232323 — still invisible. The control disappears and
its feedback disappears with it, which is exactly the failure the 3:1 floor in
`docs/design/win32-design-system.md` §2.3 exists to prevent for "chrome glyphs
and meaningful boundaries" (WCAG 1.4.11). A divider is a meaningful boundary.

Note this is NOT hypothetical-only: the same class of hole was the substance
of **T150** (palette entries sitting at 1.67:1 after a background change) and
its follow-up **T247**, so the project has already decided that "the user
picked it" is not a reason to render something unreadable.

## Open questions to settle first

- **What does Mac do?** `split-divider-color` exists there too. If Mac honors
  the raw value, diverging needs the same deliberate treatment T233's 2 DIP
  got — recorded in the design system, not silently different. Cite the Mac
  source line (the T240 lesson).
- **Adjust, or warn?** `color_math.contrastAdjusted(base, bg)` already exists
  (ported for T150) and would nudge the divider to the floor at paint time,
  which is consistent with how `min_contrast` treats terminal text. The
  alternative is to leave the color alone and surface a config diagnostic.
  Adjusting silently changes a color the user typed; not adjusting leaves a
  control they cannot see. Lean toward adjusting at PAINT time (so the config
  round-trips unchanged) unless Mac says otherwise.
- The floor must hold for **both** states — a rest color that clears 3:1 whose
  HOVER shade does not is still a defect.

## Answers to the open questions

- **What does Mac do?** It honors the raw value and checks nothing:
  `macos/Sources/Ghostty/Ghostty.Config.swift:535` `splitDividerColor` returns
  `split-divider-color` verbatim when set (its DEFAULT, used only when unset, is
  `background.darken(by: 0.08/0.4)` — note win32's fallback is instead a fixed
  `#808080`, a separate pre-existing divergence not touched here). So this IS a
  divergence, and it is recorded in `docs/design/win32-design-system.md` §5
  alongside the 2 DIP band, per the T233/T240 precedent.
- **Adjust, or warn?** Adjust, at PAINT time — the config round-trips
  unchanged, the same shape `min-contrast` uses for terminal text. Filed as a
  decision so the user can overturn it.
- **Both states** hold the floor. Where a color leaves no room for both the
  floor and a full 25-step hover, the MAGNITUDE gives way, never the floor.

## Validation criteria

- [x] Unit tests in `split_geometry.zig` sweep adversarial user colors (7
      backgrounds x 8 divider colors: near-black on black, near-white on white,
      mid-grays, pure blue at 2.44:1 on black) and assert 3:1 in BOTH states
      plus a visible rest→hover change — `zig build test -Dapp-runtime=win32
      -Dtest-filter=divider`, 93/93 passed.
- [x] The T251 report itself is pinned with its numbers (`#0a0a0a` on black:
      1.10:1 at rest, 1.42:1 hovered, pre-fix) in
      `dividerPaint: THE T251 report`.
- [x] A color that already clears the floor is asserted painted verbatim, so
      the floor cannot creep into a restyle.
- [x] `test/win32/split-divider.ps1`: new T251 section launches with
      `--split-divider-color=0a0a0a` on a black terminal and scores the
      measured band pixel by WCAG contrast against the pane background — >= 3:1
      at rest and mid-drag, and not the raw `#0a0a0a`.
- [x] Standing floor: both zig lanes + test-agent (`floor-lane.ps1 -Lane all`),
      P1-P3 acceptance.
