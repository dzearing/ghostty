# T453 - One test lane peaks at 73% of the system commit limit; the page file is 4 GB on a 64 GB box

## Summary

Filed out of **T449** (2026-08-04) as an eliminated hypothesis that is still
worth acting on. T449 suspected commit exhaustion as the cause of the `zig.exe`
access violations — a failing `VirtualAlloc` in C++ code that does not check
every allocation dereferences null, and one of the observed faults was at
address `0x10`, the textbook `nullptr->field`. So it measured it:

```
commit limit 67.7 GB (63.7 GB RAM + a 4 GB page file)
zig build test-agent, 3 runs:  peak commit 49.4 GB (73%), 41.8 GB (62%), 41.8 GB (62%)
```

**It is not the cause** — there was 18 GB of headroom at the worst moment. But
the numbers underneath are uncomfortably tight for a machine with 64 GB of RAM:

- The page file is **4 GB**, Windows-managed. The commit limit is therefore
  essentially just RAM, with no meaningful reserve behind it.
- The *baseline* is high before a build starts: ~33.5 GB of process commit at
  idle, of which a single `msedge.exe` held 12.2 GB.
- One lane peaked at 49.4 GB. `floor-lane.ps1` runs the three lanes
  sequentially, so nothing today doubles that — but a second build, a second
  agent session, or Edge growing a few more GB would.

## In plain terms

Builds on this box get within about 18 GB of the point where Windows starts
refusing to hand out memory, and the safety reserve behind physical RAM is only
4 GB. Nothing is failing because of it today. It is the kind of margin that
turns into baffling, unreproducible build failures the first time something else
on the machine is hungry.

## Goals

- [ ] Raise the page file to something proportionate (a reserve measured in tens
      of GB, not 4) so commit pressure degrades into paging rather than into
      allocation failures
- [ ] `scripts/commit-pressure-probe.ps1` (added by T449) records peak commit for
      any command — use it to confirm the headroom after the change
- [ ] Decide whether the floor should refuse to start when free commit is below
      some threshold, rather than failing halfway through in a way that looks
      like a code defect

## Notes

Changing the page file is a **machine setting on the user's box**, not a repo
change, so it needs the user's say-so rather than a commit. The measurement and
the recommendation are the deliverable here; the click is theirs.

## Validation

- Peak-commit-versus-limit recorded for a full `floor-lane.ps1 -Lane all` run,
  before and after any change.
