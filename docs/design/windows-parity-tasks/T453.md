# T453 - One test lane peaks at 73% of the system commit limit; the page file is 4 GB on a 64 GB box

## Summary

Filed out of **T449** (2026-08-04) as an eliminated hypothesis that is still
worth acting on. T449 suspected commit exhaustion as the cause of the `zig.exe`
access violations — a failing `VirtualAlloc` in C++ code that does not check
every allocation dereferences null, and one of the observed faults was at
address `0x10`, the textbook `nullptr->field`. So it measured it:

```
commit limit 67.7 GB (63.7 GB RAM + a 4 GB page file)
zig build test-agent, 3 runs:  peak commit 49.4 GB (73%), 41.8 GB (62%), 41.8 GB (62%)
```

**It is not the cause** — there was 18 GB of headroom at the worst moment. But
the numbers underneath are uncomfortably tight for a machine with 64 GB of RAM:

- The page file is **4 GB**, Windows-managed. The commit limit is therefore
  essentially just RAM, with no meaningful reserve behind it.
- The *baseline* is high before a build starts: ~33.5 GB of process commit at
  idle, of which a single `msedge.exe` held 12.2 GB.
- One lane peaked at 49.4 GB. `floor-lane.ps1` runs the three lanes
  sequentially, so nothing today doubles that — but a second build, a second
  agent session, or Edge growing a few more GB would.

## In plain terms

Builds on this box get within about 18 GB of the point where Windows starts
refusing to hand out memory, and the safety reserve behind physical RAM is only
4 GB. Nothing is failing because of it today. It is the kind of margin that
turns into baffling, unreproducible build failures the first time something else
on the machine is hungry.

## Goals

- [x] Raise the page file to something proportionate (a reserve measured in tens
      of GB, not 4) so commit pressure degrades into paging rather than into
      allocation failures — **already true when this task came up**: re-measured
      2026-09-04, the page file is 76 GB on D: and the commit limit is 139.7 GB
      against 33.1 GB in use. No click was needed; Windows' auto-managed page
      file grew it in the 31 days since filing.
- [x] `scripts/commit-pressure-probe.ps1` (added by T449) records peak commit for
      any command — use it to confirm the headroom after the change
- [x] Decide whether the floor should refuse to start when free commit is below
      some threshold, rather than failing halfway through in a way that looks
      like a code defect — **yes, but mostly as a WARNING.** See Decision below.

## Notes

Changing the page file is a **machine setting on the user's box**, not a repo
change, so it needs the user's say-so rather than a commit. The measurement and
the recommendation are the deliverable here; the click is theirs.

### What the box actually looks like now (2026-09-04)

```
RAM              63.7 GB
page file        76 GB on D: (auto-managed; peak usage 386 MB)
commit limit    139.7 GB
committed        33.1 GB at idle (24%)
free commit     106.6 GB
```

So the condition this task was filed for is gone: the 4 GB page file is now
76 GB, the limit is more than double RAM, and the worst lane T449 measured
(49.4 GB peak) would sit at 35% of it. Nothing to ask the user for.

### Decision: the floor gets a commit preflight, and it mostly warns

The third goal is the part still worth building, because the failure it
prevents is the expensive one: when commit is exhausted `VirtualAlloc` returns
null, a compiler that does not check every allocation faults on it, and the
lane goes red in a way that reads as broken code. T449 chased exactly that
shape for a whole task. Same class as T1054's full disk and T243's cross-drive
cache — when the ENVIRONMENT is the fault, say so instead of relaying a
message about something else.

It is deliberately NOT symmetric with the disk gate. Free commit is a
whole-machine number that a browser can move by 12 GB between the check and
the first compile, so a hard refusal keyed on "tight" would wedge the loop for
a condition that had already passed by the time anyone read it. The refusal
floor is therefore set where a lane **cannot complete at all** (8 GB, half the
~16 GB a lane draws), and the band above it (24 GB) warns and launches anyway.
An unreadable counter is `unknown` and never refuses — a gate that cannot
measure must not pretend it did.

Where it lives: `scripts\lib\CommitHeadroom.ps1` (pure verdict + the two
machine readings), wired into `scripts\floor-lane.ps1` beside the disk
preflight, with `-MinCommitFreeGB` / `-WarnCommitFreeGB` and `0` to disable.
Acceptance: `test\win32\floor-lane-commit-headroom.ps1`, whose negative
control is an impossible commit floor — the T1133 demonstration that the gate
can say something other than "fine".

## Validation criteria

- [x] **Peak-commit-versus-limit recorded for a full `floor-lane.ps1 -Lane all`
      run.** Measured 2026-09-04 through `commit-pressure-probe.ps1`, 1024s,
      508 samples: **peak commit 44.8 GB against the 139.7 GB limit (32%),
      no crashes** - against T449's 49.4 GB / 67.7 GB (73%) a month ago. All
      four lanes PASS (lib, none, win32, agent).
- [x] **The preflight refuses when it should.** `test\win32\floor-lane-commit-headroom.ps1`
      ALL PASS (14 assertions), including the negative control: an impossible
      commit floor refuses before any lane launches, reports the number it
      refused on, and exits 1 as `preflight=FAIL` rather than as a red lane.
- [x] **The preflight does not refuse when it should not.** Same harness, arm 11:
      a default-floor `-Lane lib` run goes through untouched, and the full
      four-lane run above never printed a COMMIT line.
- [x] **An unreadable counter is not a refusal.** Harness arm 7: a missing
      reading is `unknown`, which never fails.
