# T751 - persistence-flag audit is red: 4 launch sites in test\win32 still do not declare their persistence

## In plain terms

One of our own self-checks — the one that makes sure a test never accidentally
restores yesterday's windows into today's run — has been failing. Four test
launches never say whether they want session restore on or off, so the check
reports a failure every time anyone runs it. A self-check that is always red is
a self-check nobody reads.

## Summary

Found in passing while validating T611 (2026-08-11), on files that turn have not
touched: `test\win32\persistence-flag.ps1` reports

```
FAIL  A1 no launch leaves persistence unstated (undeclared: 4 of 171)
      undeclared: agent-attach-refused.ps1:276  $app = Start-OnTestDesktop -Exe $Exe -Arguments @() -StdErr ...
      undeclared: url-scheme.ps1:359  $a1 = Start-OnTestDesktop -Exe $exe -Arguments @("$debugScheme`://open/urlwin")
      undeclared: url-scheme.ps1:368  (same)
      undeclared: url-scheme.ps1:381  (same)
```

so the suite's persistence sweep exits 1 on a healthy tree. Both sites look like
deliberate intent that was simply never written down: `agent-attach-refused.ps1`
line 276 carries a `# persistence: on (default)` comment two lines ABOVE the
launch (the marker rule wants it on the launch), and `url-scheme.ps1`'s three
activation launches are second instances that forward and exit, which is one of
the marker's named exemptions.

The fix is to STATE the intent at each of the four sites — a `# persistence:`
marker naming why, or the flag — never to widen what the sweep accepts.

## Validation criteria

- [ ] `powershell -NoProfile -File test\win32\persistence-flag.ps1` prints
      `ALL PASS` and exits 0.
- [ ] Each of the four sites carries a stated reason a reader can check, not a
      blanket marker.
- [ ] `agent-attach-refused.ps1` and `url-scheme.ps1` still pass themselves.
