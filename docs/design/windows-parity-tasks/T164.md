# T164 - DEFERRED from viewer v1: worktree feedback capture on Windows (design-first)

## Summary

Filed 2026-07-29 by the T127 re-scope as the band's one BIG explicit deferral,
recorded as a row so the cut stays visible. Mac's viewer panes can file a
feedback report (plus screenshots and quoted passages) into
`<worktree>/temp/feedback/new/` when their content is attributable to a git
worktree. That is ~85 KB of Swift across four files whose hard parts are
platform-specific rather than portable, so it needs its own DESIGN pass before
any code. Design context: `docs/design/viewer-panes-windows.md` P10, inventory
rows 18/20.

## Details

Mac sites: `ViewerFeedbackBar.swift` (18 KB), `ViewerFeedbackComposer.swift`
(32 KB), `ViewerFeedbackReport.swift` (21 KB), `ViewerWorktree.swift` (14 KB),
plus `ViewerView`'s `toggleFeedback`, `sendFeedback`, `readPageContext`,
`writeFeedback`, `captureFeedbackScreenshot`, `handleQuoteMessage`,
`refreshWorktree`, `feedbackStagingURL`. CLAUDE.md's "Worktree feedback
capture" section is the behavioral spec and does not need re-deriving.

Three open decisions -- this is why it is design-first, not a port:

1. **Provenance leg 2 has no Windows analog.** Mac resolves
   `http://localhost:PORT` -> listening pid -> that pid's cwd with `lsof`.
   Windows can get the pid (`GetExtendedTcpTable`), but another process's cwd
   is not readable without `NtQueryInformationProcess` + a PEB read, WMI
   heuristics, or asking the pane's own shell. Weigh those against narrowing
   Windows provenance to the file and origin-directory legs (strategy D legs 1
   and 3), which are both fully portable.
2. **The `[Image #N]` chip model is `NSTextAttachment`-shaped** -- one atomic
   `U+FFFC` character that selects, copies, and deletes as a unit, with STABLE
   (non-positional) numbering. A win32 `EDIT` cannot carry attachments;
   RichEdit or an owner-drawn composer is a real choice with real cost.
3. **Interactive screenshot.** Mac uses `screencapture -i -o` and its comment
   is explicit that `-c` is forbidden because it would clobber the user's
   clipboard. The obvious Windows equivalents (`ms-screenclip:`,
   `SnippingTool /clip`) do exactly that. `ICoreWebView2::CapturePreview`
   captures THIS pane with none of that and may be the better primitive for a
   viewer-scoped report.

Portable and cheap by comparison: the report format itself (`report.json`,
`temp/feedback/.staging/` -> single atomic rename into `new/`, folder-relative
image paths, the generous `source`/`worktree`/`quotes`/`images` context), the
`git rev-parse --show-toplevel` resolution with its 15s per-location cache, and
the quote metadata (`headingId`, `blockSelector`, `blockText`, `offsetInBlock`,
`documentOffset`, `sourceLine` resolved by searching the file).

Carries with it: the QUOTE half of the selection toolbar (T162 ships Copy only
and hides Quote precisely because without a composer it has nowhere to put
text), the feedback button in the nav bar (T159 leaves room for it), and the
`chromeAlwaysVisible` / composer-focus interactions.

*Validation:* when taken -- filing a report from a viewer pane in a worktree
produces one self-contained folder in `temp/feedback/new/` with `report.json`
and every referenced image present (assert atomicity: a watcher must never see
a partial folder), a quote carries its heading + block context, and no
clipboard content is destroyed by the screenshot path.
