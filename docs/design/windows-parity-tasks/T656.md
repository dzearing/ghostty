# T656 - A --shell=wsl.exe --command= pane never runs its command: the whole command arrives in the distro as one quoted word

## In plain terms

Every shell you can pick for `--command=` runs your command - except WSL. Ask
for one there and instead of the command's output you get
`command not found`, naming the whole command line as if it were a single
program. And unlike the other shells, the pane does not stay at a prompt
afterwards either.

## Goals

- [ ] `--shell=wsl.exe --command="echo hi"` prints `hi`
- [ ] That pane is left at a live shell prompt in the distro, like every other
      flavor
- [ ] `test/win32/ipc-command-keepalive.ps1` gains a WSL arm (it currently
      documents the gap instead of covering it)
- [ ] CLAUDE.md and `wrapShellCommandArgv`'s doc comment agree about what the
      wsl row does

## Details

### Measured 2026-08-09, on the T468 build (post-fix, isolated debug instance)

```
ghoztty +new-window --target=wz --shell=wsl.exe "--command=echo WSL-MARKER"
ghoztty +read --name=wz --lines=10
    /bin/bash: line 1: echo WSL-MARKER: command not found
```

Not caused by T468 and not fixed by it: T468's subject was that the per-flavor
table was never APPLIED on the agent-backed path. This is the wsl ROW of that
table being wrong, and it is wrong identically on both paths (plain ConPTY and
agent) because both spawn the same argv through the same Windows command-line
quoting.

### Why it happens

`wrapShellCommandArgv` (`src/apprt/ipc/args.zig`) builds `{wsl.exe, --, "<the
whole command string>"}`. Windows command-line construction quotes that third
element as one argument, so the distro's shell receives a single word and looks
for a program with that name - hence `command not found` naming the whole line.
Every other row works because its shell takes exactly one command STRING
(`cmd /K <str>`, `pwsh -NoExit -Command <str>`, `sh -lic <str>`); `wsl --` is
the odd one out - it takes an argv, not a string.

### Two questions to settle before fixing

1. **How to hand the command over.** Either split the command into argv
   elements locally (which means parsing a shell command line on the Windows
   side - the thing the `.direct` argv form exists to avoid), or route it
   through a shell inside the distro: `wsl.exe -- <shell> -lic "<cmd>"`. The
   second matches how every other posix row already works.
2. **Which shell inside the distro, and does it keep alive.** The docs
   disagree with the code today: CLAUDE.md says "the shell stays alive after
   the command in EVERY case" and lists `wsl -- <cmd>`, while the doc comment
   on `wrapShellCommandArgv` says wsl "exits with the command - no login shell
   there". One of them has to give. Keeping alive requires naming a shell
   (`bash`? `$SHELL`? the distro default?) to `exec` back into, which is the
   real design content of this task.

File a decision if the answer is not obvious from the shells actually
installed - this is exactly the "which of two designs" fork step 5b covers.
