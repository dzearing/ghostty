# T324 - +sessions human output cannot distinguish a relaunchable tombstone from a genuinely dead one

## In plain terms

After a reboot, some terminal sessions can be brought back to life and some
are gone for good — and the command that lists them printed the same word,
"dead", for both. Anyone checking what survived a reboot was told a
recoverable session was lost. Now recoverable ones say `dead(relaunchable)`,
so the list answers the question it exists to answer.

## Goals

- [x] `+sessions` human output shows a relaunchable tombstone differently
      from a genuinely dead session
- [x] The chosen rendering is documented in CLAUDE.md's `+sessions` section
- [x] A unit test locks the distinction in

## Validation criteria

- [x] Unit test: `printTable` renders `dead(relaunchable)` for a relaunchable
      tombstone, bare `dead` / `dead(<code>)` for genuinely dead rows
      (`src/cli/sessions.zig` — "printTable distinguishes a relaunchable
      tombstone…", ran in the none lane)
- [x] Test floor green: `floor-lane.ps1 -Lane all` → `none#1=PASS
      win32#1=PASS agent#1=PASS` (2026-08-07)
- [x] On the box: started the debug agent against its real
      `local-agent-debug\sessions.json` (5 disk-materialized tombstones);
      `ghoztty +sessions` printed `dead(relaunchable)` for every row, and
      `--json` still reports `alive:false, exit_code:null, relaunchable:true`
      (shape unchanged)
- [x] P1–P3 acceptance scripts ALL PASS (run sequentially after the lanes)

Found 2026-08-01 alongside T322, which added `relaunchable` to the `--json`
row. The human column was left alone deliberately (T322's scope was the wire
hole); this task decides the display.

## The gap (VERIFIED on the box)

`src/cli/sessions.zig:203-209` prints the liveness column as `alive`,
`dead(<code>)`, or bare `dead`. A relaunchable reboot-floor tombstone has
`alive == false` and `exit_code == null`, so it prints exactly `dead` - the
same string as a session that died without an exit code and cannot come back.

Live output from the repo agent after T322 landed:

```
d02e666dfc76df29d58a14894013aee7  dead  detached  idle  pid=0  pinned  cwd=C:\Users\David
```

whose JSON row is `"alive": false, "exit_code": null, "relaunchable": true` -
i.e. a session that CAN be resumed via RELAUNCH, presented as dead.

## Why it is worth fixing

`+sessions` is the one command that works with the app closed, so it is what a
human or an agent reads when deciding whether anything is recoverable after a
reboot. "dead" is a wrong answer to that question for these rows, and the flag
that gives the right one is now already in hand at the call site.

## Fix

In `printHuman`, render the liveness column for `!alive and relaunchable` as
something that reads as recoverable (e.g. `relaunchable`, or
`dead(relaunchable)` - pick one and write it into CLAUDE.md's `+sessions`
paragraph, which currently documents only `alive` / `dead(<code>)`).

Keep it additive in spirit: scripts should be reading `--json`, and the JSON
shape does not change.

## Validation

- Unit: a `printHuman` test asserting the column for a relaunchable tombstone
  differs from a plain dead one (the file has a `printJson` test since T322 to
  copy the shape from).
- On the box: `ghoztty +sessions` against the current agent, which has real
  relaunchable tombstones in it today.
