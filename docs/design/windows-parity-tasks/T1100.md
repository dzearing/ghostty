# T1100 - The background test desktop cannot capture pixels or deliver real input, so scripts that need them are red for the environment

## In plain terms

Automated UI checks now run on a hidden second desktop so they do not steal the mouse and keyboard while you work. That hidden desktop turns out not to support taking a picture of a window, and in at least one case not to accept synthetic keystrokes either. Several checks that look at colours or press keys therefore fail there no matter whether the app is correct, which makes them useless as a signal.

## Summary

The T1094 full sweep produced a cluster of reds that all sit on the same two capabilities rather than on any product behaviour.

**Pixel capture is dead.** `test-desktop-spike.ps1` is the spike written to measure exactly this, and it says so directly:

```
FAIL  PrintWindow(PW_RENDERFULLCONTENT) returns real content (meanLum=51, distinct=60)
```

`caption-bar.ps1` fails the same way from the other end:

```
Get-TestWindowPixels: the capture is UNIFORM - 3858x2118, one color over its
whole interior, still uniform after 11 attempt(s) across 2000ms.
```

and `split-dim.ps1` / `split-dim-viewer.ps1` fail with an EMPTY measured colour (`got ''`), which is the same absence one layer up.

**Real input may be dead too.** `context-menu-real-input.ps1` never got started:

```
SETUP FAIL (plain): could not take the foreground (a fullscreen app or an input lock owns it)
```

and `chooser-close-chord.ps1` fails its own POSITIVE CONTROL (`FAIL Ctrl+W closed one pane (2 -> 2)`), which is the shape of a chord that never arrived rather than a chord that was mishandled.

This is the decision this task exists to force: either the test desktop is made able to do these things, or the scripts that need them are marked as requiring the interactive desktop and the suite reports them as SKIP with a reason - never as a silent FAIL that reads like a product defect. What must not happen is leaving them red, because a permanently-red script teaches everyone to ignore the colour.

## The pixel answer, settled (T1115, 2026-09-02)

The spike now measures all three capture routes BY REGION and is ALL PASS
expressing the finding. The answer is a SPLIT, and the split is what this task
needs:

| route | chrome band | terminal surface |
|---|---|---|
| BitBlt off the desktop DC (== `CopyFromScreen`) | returns FALSE - nothing at all | - |
| `PrintWindow(PW_RENDERFULLCONTENT)` | mean 79, **103 distinct** | mean 41, **2 distinct** |
| `PrintWindow(flags=0)` | mean ~80, ~100 distinct | mean ~40, ~2 distinct |

The interactive-desktop control is what makes it conclusive. Same build, same
call (PrintWindow on the top-level window, the child's rect sampled out of that
bitmap), same sampler: over the **surface rect** it returns **102 distinct**
colors on the interactive desktop against **1-2** on the background one. So the
flat surface is DESKTOP-dependent rather than an unconditional property of
PrintWindow, and `PW_RENDERFULLCONTENT` is not the deciding factor either -
`flags=0` reads identically on both.

This does not overturn `lib\TestDesktop.ps1`, which is the source of truth and
already carried the operative conclusion (its CAPTURE LIMIT, 2026-07-30, and
T303's "PrintWindow sees GDI, not composition"). It measured PrintWindow on the
GhozttyTerminal **child** hwnd - a different call from the top-level capture
above - and both agree on what matters here: on a background desktop the
terminal surface cannot be asserted. What T1115 actually fixed is that the spike
had never been reconciled with that finding and spent a month asserting the
answer the library had already revised.

**What that means for the dependent scripts:**

- A probe asserting **terminal content** pixels (glyph colors, cursor,
  selection highlight - anything the renderer draws into the terminal surface)
  **cannot run on a background desktop**. There is no capture route; all three
  were measured. `split-dim.ps1` and `split-dim-viewer.ps1` are in this class -
  their empty measured color is this flat surface one layer up.
- A probe asserting **chrome** pixels (title bar, tab strip, banner, the
  window's own painted controls) **can** run there, via `PrintWindow` into a
  memory DC - it just cannot use `CopyFromScreen`. `caption-bar.ps1` is in this
  class, so its "capture is UNIFORM" is a fixable helper problem
  (`Get-TestWindowPixels` reaches for `CopyFromScreen`), not a dead end.

So the capability this task has to declare is not one flag but two:
`chrome-pixels` (available via PrintWindow) and `surface-pixels` (unavailable).
Note also that the earlier reading of this spike was not wrong about the box -
it was scoring whole-window brightness, an oracle that cannot tell "chrome over
a flat client area" from "the whole window", which is why it read green in July
and red later with no behavior change in between.
