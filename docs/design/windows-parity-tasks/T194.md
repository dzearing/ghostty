# T194 - Crash-orphaned windows are lost on Windows: launch restore never consults the agent's authoritative layouts

## In plain terms

If Ghoztty crashes on Windows, the programs you had running keep running — a
background service holds onto them — but the windows themselves can vanish for
good. Ghoztty only ever asked one file on disk which windows to bring back, and
that file can get wiped out by the very crash you are recovering from. When it
does, your terminals are still alive and there is nothing on screen pointing at
them.

After this, a relaunch also asks the background service what it is holding, and
brings back anything the file forgot — same windows, same splits, the same
running processes, not restarts. Anyone whose Ghoztty has ever died and come
back empty notices.

## Goals

- [x] Restore always asks the agent for its layouts, instead of bailing the
      moment the local file is missing or empty
- [x] The two lists are merged by a pure, unit-tested rule (local wins; windows
      only the agent knows about are added)
- [x] Recovered windows are written back into the local file, so the next
      launch needs no round trip
- [x] An on-box test proves it end to end: crash, delete the file, relaunch,
      and get every window back on its ORIGINAL shell processes
- [x] The floor stays green, including the two acceptance scripts whose
      expectations this behaviour change moves

## Summary

**Split out of T145 (2026-07-30)** — T145 carried TWO independent mechanisms and
one of them needs machinery win32 does not have at all. T145 keeps the in-place
agent-crash recovery (Mac `03f0f1f30` + `e65cfa4d5`); this row is the OTHER
Mac commit, `20e505aaf` — *"recover crash-orphaned windows from the agent's
authoritative layout"*.

The defect it fixes on the Mac exists on Windows too, verbatim:
`App.restoreSessionLayout` (`src/apprt/win32/App.zig:1063`) trusts the
app-local `session-layout.json` ALONE and bails on
`if (file.windows.len == 0) return false;` (:1075) — the exact shape of the
`guard !restorable.isEmpty else { return }` early-out `20e505aaf` deleted.
After an app CRASH that manifest can regress (a relaunch that rebuilt nothing
then overwrote it), while the ever-running agent still holds every layout blob.
The PTYs are alive in the agent and the windows are simply lost.

## Details

The Mac fix: `restoreSessionLayoutWindows()` always consults the agent, pulls
its `GET_LAYOUTS` roster, and reconciles it with the local entries via a pure
`reconcileLayoutEntries()` (union keyed by entry id; LOCAL wins on collision —
it can only be fresher after a crash; agent-only windows are ADDED). A new
`SessionLayoutManifest.adopt(_:)` inserts the agent-recovered entries into the
local manifest so the in-place sync tracks them and they persist for the next
launch.

**The Windows prerequisite the Mac already had.** `20e505aaf` works because the
Mac PUSHES each window's layout blob to the agent
(`LocalAgentManager.pushLayout` → `SET_LAYOUT`, with `deleteLayout` on a clean
window close). **win32 never calls `SET_LAYOUT` at all** — verified: the only
references to `setLayout` in the tree are the shared-core
`src/remote/connection.zig:1653` definition and its agent-side handler; no
win32 caller exists. So a straight port of the reconcile half would union
against an always-empty agent roster and change nothing. This row therefore has
two parts, in order:

1. **Push**: mirror each window's `session_layout.Window` blob to the local
   agent on every `syncSessionLayout` (`App.zig:873`), keyed the same way the
   manifest keys it (`win.id`), with a delete on a clean window close. Must be
   best-effort and non-spawning (Mac's `warmSharedOwner` gate) — a layout push
   may never block the GUI or resurrect a dead agent, and the `SET_LAYOUT` RPC
   blocks through its ack so it cannot run inline on the message loop.
2. **Reconcile**: delete the `file.windows.len == 0` early-out, always
   `GET_LAYOUTS` when a connection resolves, union by window id with local
   winning, and write the adopted entries back into the local manifest.

Keep the union itself PURE (a `session_layout.reconcile(local, agent)` next to
the schema, unit-testable in both lanes) — that is the part `20e505aaf` covered
with three unit tests.

**Validation:** the Mac E2E shape ports directly — kill the app (crash, not
quit), DELETE the local `session-layout.json`, leave the agent running, relaunch
and assert every window comes back with the SAME shell pids (a true re-attach,
not a relaunch), and that the local manifest is re-adopted 0 -> N. Plus the
pure reconcile unit tests (union, empty-local recovery, adopt) and no
regression in `session-persistence.py` / `session-reattach.ps1`.

## Evidence (done 2026-08-04)

**Part 1 (push) was already done** — T334 shipped `App.pushLayoutBlobs`
(`SET_LAYOUT` per window, non-spawning via `sharedConnectionIfWarm`,
non-blocking via `setLayoutNoWait`, convergent against `pushed_layouts`) and
T338 moved the key onto the window's stable uuid. So this row landed part 2
only, plus the adopt.

**What landed:**

- `session_layout.reconcile(alloc, local, agent) -> Reconciled{windows,
  adopted}` — pure, in the `none` lane, next to the schema as the row asked.
  Local entries first in file order, then agent-only ones; keyed by
  `windowKey = uuid orelse id`, the same derivation the push uses. Two rules:
  **local wins on key collision** (after a crash the local entry can only be
  fresher, and it still carries the WP-D3 snapshots a blob strips), and **an
  agent window whose session is already claimed is dropped** even under a new
  key — one leaf is enough, the same unit rule `windowIsOpenOn` applies, because
  the agent rebinds a session to the newest attach and two attaches over one PTY
  would blank the first window to make a copy of it.
- `App.restoreSessionLayout` no longer bails on an absent/empty manifest. It
  loads the manifest as ONE source (`loadLocalManifest`, null-tolerant), always
  pulls the other (`pullAgentLayouts` → `GET_LAYOUTS` → `layout_blobs.decodeLayouts`,
  degrading to manifest-only on any transport/decode failure), reconciles, and
  restores the union.
- **Adopt**: `markLayoutDirty()` when `adopted > 0`. win32 regenerates the
  manifest wholesale from the live windows, so arming the debounced sync IS
  Mac's `SessionLayoutManifest.adopt(_:)`; the message loop `run` is about to
  enter fires it.

**Tests:** 7 new unit tests in `session_layout.zig` (agent-only added;
empty-local recovers the whole set; local wins on collision; a pre-T338 entry
keys on its id and still collides; a claimed session drops the agent copy;
session-less windows do not fold together; both-empty is an empty answer, not an
error). New acceptance `test\win32\session-crash-recover.ps1` — ALL PASS (17
assertions): builds a 2-window/3-pane layout, crash-kills the app, DELETES the
manifest, relaunches, and proves both windows and all three panes come back on
their **ORIGINAL shell pids** with no fourth session, then that the manifest goes
from ABSENT back to two windows with all three session ids. `-NegativeControl`
inverts C1 and correctly FAILS on this build.

**Two existing scripts encoded the old behaviour and were updated, not
relaxed:**

- `layout-blobs.ps1` section F asserted the relaunch opened a blank window
  beside the dead run's record. It now recovers instead, so F asserts ONE record
  under the SAME uuid (T338's claim restated on the path that now depends on it)
  plus no extra session, and a window opened AFTER the recovery still takes a
  fresh key. ALL PASS.
- `chooser-restore-all.ps1` section 3 asserted "the relaunched app restored
  nothing on its own" and had the BUTTON do the rebuild. That was the defect
  stated as an expectation. Section 3 now asserts the automatic recovery (both
  windows, both topologies, all five sessions ATTACHED per the agent's own
  roster, no blank window) and section 4 keeps the double-attach guard. ALL PASS
  (30 assertions). Coverage that moved is filed as **T486**.
- `lib\CleanSlate.ps1` gained `Clear-DebugAgentLayouts`: with a second restore
  source live, dropping the manifest alone stopped being a clean slate, so a
  reset that kills the agent now drops its debug layout store too (never with
  `-AppOnly` — the agent owns that file while it runs).

**Floor:** `floor-lane.ps1 -Lane all` → none/win32/agent ALL LANES PASS. P1 P2 P3
ALL PASS. `session-reattach.ps1` ALL PASS (38), `session-relaunch-notify.ps1`
ALL PASS (76), `viewer-restore.ps1` ALL PASS (38).
