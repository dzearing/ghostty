# T819 - The command palette and search popups ride the terminal's window class, so a DPI change while one is open repaints only the exposed strip

## In plain terms

If you open the command palette (or the find bar) and then drag the window to a
monitor with a different scaling, the popup resizes to suit the new monitor but
only the newly uncovered sliver gets redrawn — the rest keeps the picture it had
at the old size. Nothing else on Windows has this problem after T467; these two
are the last pair, and only because they borrow the terminal's own window class.

## Details

Filed by T467's audit (see `docs/design/win32-design-system.md` §5c). Both popups
are created with `App.TERMINAL_CLASS_NAME` (`Surface.zig`
`createCommandPalette` / `createSearchBar`), which carries `CS_OWNDC` and
deliberately NOT `CS_HREDRAW | CS_VREDRAW`: the terminal surface is redrawn
whole by the OpenGL renderer every frame, and forcing a full-client invalidate
on it would add an erase+paint per drag frame for nothing.

So the popups cannot simply be given the style — they need a class of their own.
`positionCommandPalette` / `positionSearchBar` size them as `<constant> * scale`,
so the size only ever moves on a DPI change (the popups are repositioned on
every surface resize, but a pure move invalidates nothing and needs nothing).
That is why this is a P2 and not the same defect T467 fixed.

Two shapes to weigh: a dedicated popup class per surface-owned overlay (right,
and gives `paintPalette` somewhere to live that is not `surfaceWndProc`'s
`is_palette_popup` branch), or invalidating by hand in the two `position*`
functions when the scale changed (smaller, and the promise every future caller
has to remember).
