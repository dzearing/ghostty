# T479 - The watchdog decides whether any work remains by counting rows in the FROZEN tracker table

## In plain terms

The safety net that restarts the automated work loop after a crash decides
"is there any work left?" by reading an old status table that stopped being
updated weeks ago. The number it gets is wrong every day, and it only keeps
working by luck — if anyone cleaned up that old table, the safety net would
quietly conclude all work is finished and stop restarting the loop forever.
After this fix it counts the real, live task files instead, so the answer is
true by construction and cleaning up old docs can't turn the supervisor off.

## Goals

- [x] The watchdog counts open work from the live one-file-per-task directory, not the frozen table
- [x] Tasks belonging to the Mac seat don't count — they can never justify restarting this box's loop
- [x] A missing or empty task directory reads as "unknown" and never blocks re-entry
- [x] The acceptance fixtures fabricate task directories, not tracker tables

## Summary

go-loop-watchdog.ps1 Get-RemainingTasks greps docs/design/windows-parity-tasks.md for todo/in-progress/blocked rows, and a tick that finds zero returns 'none' - the supervisor concludes the loop is finished, not stuck, and stops re-entering. That table has been FROZEN since 2026-07-29 (tasks moved to one-file-per-task under windows-parity-tasks/). Measured 2026-08-04: the frozen table yields 63 rows while there are 232 genuinely open task files. The count is fiction today and harmless only by accident - it is non-zero. Anyone who tidies that historical table to zero silently switches the supervisor off forever, which is the exact class of failure T440 was filed for. Fix: count via scripts/parity-tasks.ps1 (or the task directory) instead of the frozen table.
