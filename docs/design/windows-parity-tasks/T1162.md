# T1162 - A persistent session whose shell has already exited is still listed as running, forever

## Summary

Proven on the box while doing T1158. Six detached pinned sessions in the installed agent had their cmd.exe children killed; sixty seconds later ghoztty +sessions still reported all six as live against the dead pids, and they are still listed now. The agent never observes the exit. Mechanism, read from the code: markExited is reached from exactly one place, SessionStore.onChildOutput (src/remote/agent/session.zig:1341-1342), whose own doc says it 'reap-checks the child' and that 'a zero-length call is a reap nudge (the pty reader sends one on EOF)'. So exit detection rides the child's OUTPUT path and needs a live reader. For these sessions the ghoztty-agent --pty-host HOLDER is long gone (confirmed: the installed agent has no --pty-host children at all), so there is no reader thread, no EOF, no nudge, and no path to markExited. Nothing polls. Consequences: the session stays live forever; eapIdle skips it at session.zig:1729 (if (s.pinned and s.alive) continue), which is correct for a LIVE pinned pane and wrong here; it is written to sessions.json and re-materialised on every agent restart; and the chooser offers it as resumable. This is the half of T1158 that makes a leak permanent - T1158 fixed the SOURCE (the soak no longer seeds the user's agent) but a session that dies while unbound is still unreapable. Note the distinction that matters: this is NOT 'age out pinned live sessions', which would break the persistence feature the user wants. It is 'notice the child is gone'. A session whose process has exited is not a persistence case at all.
