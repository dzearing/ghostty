# T1162 - A persistent session whose shell has already exited is still listed as running, forever

## Summary

Proven on the box while doing T1158. Six detached pinned sessions in the installed agent had their cmd.exe children killed; sixty seconds later ghoztty +sessions still reported all six as alive against the dead pids, and they are still listed now. The agent never observes the exit. Mechanism, read from the code: markExited is reached from exactly one place, SessionStore.onChildOutput (src/remote/agent/session.zig:1341-1342), whose own doc says it 'reap-checks the child' and that 'a zero-length call is a reap nudge (the pty reader sends one on EOF)'. So exit detection rides the child's OUTPUT path and needs a live reader. For these sessions the ghoztty-agent --pty-host HOLDER is long gone (confirmed: the installed agent has no --pty-host children at all), so there is no reader thread, no EOF, no nudge, and no path to markExited. Nothing polls. Consequences: the session stays alive forever; reapIdle skips it at session.zig:1729 (if (s.pinned and s.alive) continue), which is correct for a LIVE pinned pane and wrong here; it is written to sessions.json and re-materialised on every agent restart; and the chooser offers it as resumable. This is the half of T1158 that makes a leak permanent - T1158 fixed the SOURCE (the soak no longer seeds the user's agent) but a session that dies while unbound is still unreapable. Note the distinction that matters: this is NOT 'age out pinned live sessions', which would break the persistence feature the user wants. It is 'notice the child is gone'. A session whose process has exited is not a persistence case at all.

## In plain terms

Ghoztty can keep a terminal session alive in the background so you can come
back to it later. If the program running in one of those background sessions
quits while nothing is watching it, nobody notices: the session keeps showing
up in the session list and in the "resume a session" chooser as though it were
still running, and it comes back every time the app restarts. Picking it does
nothing useful, because there is no longer a program to return to. After this
change the background service checks, a few seconds after the fact, whether
each session's program is really still there — and quietly closes out the ones
that are gone, so the list only offers sessions you can actually resume.

## Goals

- [x] The agent notices, without any viewer attached, that a session's shell
      process has exited.
- [x] A session it tombstones then follows the ordinary cleanup rules, so it
      leaves `sessions.json`, the session list and the chooser.
- [x] A still-running session is never declared dead — not by one bad process
      snapshot, not by a snapshot that failed outright, and not for a session
      that was born after the snapshot was taken.
- [x] Live panes are unaffected: this is "notice the child is gone", never
      "age out pinned live sessions".

## Validation criteria

- [x] A pinned, unbound session whose pid is absent from the process table is
      marked exited, and then reaped by `reapIdle` — unit test
      `SessionStore.sweepVanishedIn: a pinned session whose shell is gone is
      tombstoned and then reaped (T1162)` in `src/remote/agent/session.zig`,
      green in `zig build test-agent`.
- [x] One missing snapshot is not enough (two consecutive strikes required),
      a strike resets when the pid reappears, and a session younger than the
      snapshot or carrying a synthetic pid is exempt — unit test
      `…strikes reset, young sessions and synthetic pids are exempt (T1162)`.
- [x] Against this box's REAL process table, a session whose pid is running is
      never tombstoned by repeated sweeps — unit test `…a REAL process table
      never tombstones a running pid (T1162)`.
- [x] The tests are not vacuous: with `vanish_strikes_needed` temporarily set
      to 3, `zig build test-agent` went red (1 failed) and green again on
      revert.
- [x] On the box, end to end: a detached, holder-served pane whose holder and
      shell are both removed stops being reported as running, and a session
      whose shell IS running survives every sweep and stays interactive -
      `test\win32\session-vanished.ps1`, ALL PASS (18 assertions).
- [x] What that script does NOT prove, measured rather than assumed: a control
      run with `GHOZTTY_AGENT_VANISH_SWEEP=0` also passed section D, because
      killing a holder tears the session down by the holder-loss path too. The
      script therefore claims an outcome, not a mechanism, and says so; the
      inverted assertion was removed rather than kept green. T1226 owns building
      a state only the sweep can rescue.
- [x] Standing floor green: `scripts\floor-lane.ps1 -Lane all` (lib, none,
      win32, agent), the P1-P3 acceptance scripts, and the two harnesses the
      edit made due (`holder-volume.ps1`, `agent-relay-session-e2e.ps1`).
