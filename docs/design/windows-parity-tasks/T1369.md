# T1369 - A publish that FAILS still consumes the day, so nothing retries and nothing ships

## In plain terms

Every evening Ghoztty publishes the day's work so your terminal can offer you
the update. Today it pushed the tag, the build of that tag failed, and no
release was ever created — and then every later run said "already published
today" and stopped. The day's fixes are on nobody's machine, and nothing will
try again until tomorrow.

## Summary

Observed on 2026-09-05, in T1367's turn. `scripts\daily-publish.ps1` printed
both halves in the same breath:

```
PUBLISH DID NOT LAND: win-v1.36.13 was pushed 1h ago and there is still no
  release. Check the Release (Windows) run for that tag.
NOT DUE: already published today (2026-09-05)
```

The reconciliation (T1292) does its job — it correctly moved the watermark to
`failed` — but the *due* calculation reads only the date, so a `failed`
outcome is indistinguishable from a `published` one for the purpose of trying
again. The result is the shape T1294 was filed about, one step worse: not a
release with commits stranded behind it, but no release at all and a
watermark saying the day is done.

The specific failure this time was T1364's wixl sequencing bug
(`REINSTALL is armed at 2/6604`), fixed on `ef67291ae` an hour after the tag
was pushed — so a retry would have shipped. That is the normal case: the tag
is cut from a commit, the branch moves on, and the fix for whatever broke the
build is usually already sitting on it.

## Goals

- [x] `daily-publish.ps1` treats a watermark whose outcome is `failed` as NOT
      published — the next task-boundary push publishes again, from the branch
      head as it now stands. `attempting` (a run that died between the stamp
      and the publish) counts the same way.
- [x] Bound it so a repeatedly-red branch cannot mint a tag per push: a retry
      requires the head to have MOVED since the failed tag, and a small cap per
      day (`-MaxAttemptsPerDay`, 3; the count lives in the watermark's new
      `attempts` field and restarts with the date)
- [x] `go-loop-health.ps1`'s `publish=` says `failed` loudly rather than `ok`
      when the day's only attempt did not land. It already did for `failed`
      and degraded the run; what it did NOT catch was an `attempting` stamp
      nobody finished, which read `ok` on the strength of its date. It now
      reads that as `failed` once the stamp is over two hours old, so a
      publish in flight still reads `ok` for the ten minutes it takes.
- [x] The failed tag itself is left alone rather than re-pointed — a tag that
      names a commit is not a lie, it is just a build nobody could make. The
      retry walks to the next patch instead (`Resolve-DailyPublishVersion`
      already refuses a version that has a tag).
