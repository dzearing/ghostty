# T301 - Switching to a machine a remote WINDOW is already connected to re-dials through the relay instead of borrowing

## In plain terms

The Activity Monitor can show any machine you have a window on. Open it from a
window connected to another machine, flip it to "Local" to look at your own box
— and the other machine simply vanished from the strip of cards, with no way
back short of closing the window and starting over. Even when a card could be
coaxed back, going there tried to open a brand-new connection to a machine you
were already talking to: with no signed-in account that just says "Couldn't
connect", one window away from a link that works fine.

After this, the machines your windows are connected to always have a card, and
returning to one reuses the connection that window already has. Nothing is
dialed, nothing needs an account, and the panel shows the machine again
straight away.

## Goals

- [x] A machine a live window is connected to keeps its card in the carousel
      even while the panel is showing something else.
- [x] Switching to such a machine borrows that window's connection instead of
      dialing a second one — including a direct-TCP machine, which has no relay
      device id to dial with.
- [x] A window closing under a borrowing panel hands the panel its notice
      instead of leaving it holding freed memory.
- [x] A regression arm in `test/win32/activity-monitor-remote.ps1`.

## Summary

`switchToCard` always dials a **fresh, owned** relay connection for a remote
target (`ActivityMonitor.zig`, T296). That is the correct default — a borrowed
connection belongs to a window whose lifetime the panel cannot see — but it
produces one visibly wrong outcome:

**Open the Activity Monitor from a remote window's palette (it borrows that
window's connection), switch to Local, then switch back to that same machine.**
The panel now re-dials through the relay, so:

- with no signed-in account it simply **fails** — "Couldn't connect" — while a
  perfectly good live connection to that machine sits one window away;
- with an account it opens a **second** connection to a machine we are already
  talking to.

The direct-TCP case (`+new-remote-window --host/--port`) is the sharper one: a
`127.0.0.1:PORT` source has no relay device id at all, so the re-dial cannot
even be attempted correctly.

## Evidence

Reproduced as part of T296's acceptance work on this box:
`test/win32/activity-monitor-remote.ps1` section E switches a borrowed-connection
panel to Local and asserts the remote window's session survives (it does — the
borrowed connection is dropped, never freed). Switching BACK is the case this
task covers and the script deliberately does not assert it, because the current
behavior is the defect.

## The shape of the fix

When the switch target names a machine some live **window** is already connected
to, borrow that window's connection (`openReusing`'s ownership: `dialed == null`,
never freed by the panel) instead of dialing. That needs:

- a lookup from a card's identity to a window's connection — and cards are keyed
  by relay device id while a direct-TCP window is keyed by `host:port`, so the
  identity question has to be answered first (it is the same question T146's
  cross-machine session browse has to answer);
- a rule for what happens when that window CLOSES while the panel is borrowing —
  today only `openReusing` can create that state, and it is bounded because the
  panel is opened from the window and typically closes with it.

Mac does not have this problem in the same form: its `switchTo` dials
`host`/`port` from a local `MachineRegistry`, so a re-dial always succeeds and
the cost is only a duplicate connection.

## What landed

Three parts, because the repro turned out to be blocked before it even reached
the re-dial:

1. **`activity_borrow.zig`** (new, pure, `none` lane) — the identity key a
   machine is known by (relay device id, else `host:port`, the same derivation
   `Surface.openActivityMonitor` uses) and the borrow decision: the first
   CONNECTED window on that machine, or null to dial. A window whose link is
   down is not borrowed — that would trade a dial that might work for a
   connection that certainly will not.
2. **The card had to exist first.** `rebuildCards` now adds a card per live
   window's machine (`refreshWindowMachines`, held by value in `win_machines`
   so a closing window cannot leave a card slicing into freed strings). Without
   this the trip to Local was ONE-WAY: nothing lists a `127.0.0.1:PORT` box,
   and with no account the relay directory is empty, so the machine's card
   disappeared the moment it stopped being the active source. The re-dial the
   task title names was not even reachable.
3. **`switchToCard` borrows** when `borrowFromWindow` finds one, and
   `RemoteReconnect.releaseTransports` calls the new
   `ActivityMonitor.releaseBorrowed` so a closing window's transport is dropped
   by any panel riding it — the live one and every retired one. Placed AFTER
   `clearStateHandler` and the teardown joins: `releaseBorrowed` shuts the
   connection down to cut a parked sample worker loose, and doing that with the
   state handler still installed hands a dying transition to a window that is
   already mid-destroy.

Deliberately NOT extended to the chooser's Activity button: dialing your own
connection is what that entry means on both platforms, and it is the only entry
that can reach a machine no window is on.

      rather than truncation, connected-only, first-match, empty id is not a
      wildcard) in the `none` lane.

## Found on the way

**T613** (P1) — closing a remote window while an Activity Monitor panel is open
crashes the app. Section G4 hit it; it is NOT this task's dangler. It
reproduces with `releaseBorrowed` neutered to a no-op (T296-era behavior) and
does not reproduce with no panel open, and the fault lands after
`Window.onDestroy` has fully run, inside `DestroyWindow`'s child-window
destruction with an `OPENGL32` frame on the stack. G4 therefore asserts only
the release notice, and T613 owns the survival assertions.
