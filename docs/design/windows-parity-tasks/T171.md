# T171 - relay-account.ps1 failed once unreproducibly (30 pass / 1 fail, text not captured)

## Summary

Filed so it is not lost, not because the cause is known. During T141's
validation, the FIRST of a three-run loop of `test/win32/relay-account.ps1`
reported `1 FAILURE(S) (pass=30 fail=0... fail=1)` while runs 2 and 3 were
ALL PASS (53). Two more back-to-back runs and a fresh ×3 loop afterwards were
all ALL PASS (53) — **5 consecutive clean runs**, so the shipped state is green
and this is a flake, not a standing red.

The failure text was **not captured**: that loop only printed the last line plus
pass/fail counts. That is the real lesson and the first thing to fix — a
per-run log is worth more than a tidy summary line. Runs after it kept per-run
logs and have shown nothing.

Note the count: 30 passes, i.e. the run stopped producing assertions partway.
A full run is 53. Sections 0+1 are 8 assertions and section 2/3 adds ~22, so 30
lands at the END of the GUI section — the run then produced no section 4-7
assertions at all, without printing their SKIP lines. That shape (assertions
stop, no SKIP) does not match any deliberate skip branch, which is what makes it
worth a task rather than a shrug.

Leading hypotheses, none tested:

1. **Port contention between consecutive runs.** The fake relays bind fixed
   ports (47921/47922/47912). A previous run's `Start-Job` listener can still
   hold them for a moment after its host process is killed, so `Wait-Listening`
   can "succeed" against a DYING listener. Cheap hardening regardless of whether
   it is the cause: derive the ports from `$PID` and assert the port is FREE
   before starting, rather than assert something is listening.
2. **A PowerShell error terminated the script mid-section** (`$ErrorActionPreference`
   is `Continue`, so a non-terminating error prints and moves on — but a
   terminating one from `[AcctDrv]` marshalling or `Invoke-WebRequest` would end
   the run silently from the log's point of view).
3. A GUI from the previous run surviving `Stop-TestProcs` and being found by
   `FindTop`, so the chord went to a window with no fake relay behind it.

*Do:* re-run the script in a tight loop (10+) with per-run logs kept, and
whichever hypothesis the failure text implicates, fix the harness. If 10 clean
runs cannot reproduce it, apply hypothesis 1's hardening anyway (it is a real
latent trap independent of this incident) and close the row.

*Validation:* 10 consecutive `relay-account.ps1` runs ALL PASS with per-run logs
retained, and the port setup no longer depends on a fixed port being free.
