# T884 - Remaining delivery/loop harnesses have no guard-due rows (morning-refresh, deliver-windows-build, agent-upgrade, relaunch-guard) - an edit to their scripts obliges nobody to re-run them

## Summary

Found during T531 (2026-08-16). The delivery pipeline had NO guard-due
coverage at all: `scripts\upgrade-ghoztty-windows.ps1` could be edited and
committed without any gate demanding its harnesses re-run, which is exactly
how `upgrade-no-fork.ps1` sat red at L24 (a T883-class blind capture) with
nobody the wiser - it is not in the P1-P3 floor and nothing tied an edit to a
run. T531 added rows for `upgrade-staleness` (covers
upgrade-ghoztty-windows.ps1, launch-upgrade.ps1, delivery-version.ps1) and
`upgrade-no-fork` (covers upgrade-ghoztty-windows.ps1, loop-session.ps1).

The same gap remains for the neighbouring harnesses:

- `test\win32\morning-refresh.ps1` <- `scripts\morning-refresh.ps1`
- `test\win32\deliver-windows-build.ps1` <- `scripts\deliver-windows-build.ps1`
- `test\win32\agent-upgrade.ps1` <- the agent-refresh arming half it covers
- `test\win32\relaunch-guard.ps1` <- the relaunch-guard spawn/watch code

For each: add a `$GuardTable` row in `scripts\guard-due.ps1` (keep each row to
the family the harness is ABOUT - noise is how a gate gets ignored) and a
green-run stamp block in the harness tail (skip-aware where the harness counts
skips; see go-loop-guard.ps1's block for the pattern). Then run each harness
green once to seed its stamp, and commit the stamps.

## In plain terms

We have automated test suites for the scripts that deliver new builds to the
user's machine, but until recently nothing forced anyone to actually run them
after changing those scripts - one suite was quietly broken for a long time
and nobody noticed. The tracking system that catches this now covers two of
the suites; this task extends it to the remaining four.

## Validation criteria

- [ ] Each of the four harnesses has a guard-due row whose Covers globs name
      the scripts it is about, and a stamp block that only fires on a clean
      green sweep.
- [ ] `scripts\guard-due.ps1 check` reports each new guard CURRENT after one
      green seeding run, and DUE after touching a covered file.
- [ ] `test\win32\guard-due.ps1` still ALL PASS.
