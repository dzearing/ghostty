# T816 - chooser-resume.ps1 cannot build its fixture any more: crash-orphan recovery re-attaches the sessions it tries to orphan

## Summary

The script makes an ORPHANED live session the way it always did - kill the app only, delete session-layout.json, relaunch - and then resumes it from the chooser. Since 80fa0aa12 (2026-08-04, 'A crash no longer loses the windows it left running') the relaunched app recovers that window from the AGENT's layout blobs instead, which is the whole point of that feature: the relaunch log reads 'session-restore: recovered 1 crash-orphaned window(s) from the agent (0 in the local manifest)' and then 'attached 2 pane(s); 0 live agent session(s) unattached'. So there is no row that is alive-and-unattached, the fixture assertion fails at 2 rendered rows instead of 3, and the run exits SETUP FAIL having proved nothing about Resume. Found 2026-08-12 while running the chooser family as T462's regression sweep; it is NOT a T462 regression (the meter touches no restore path) and it has been red since 2026-08-04 - eight days of a P1 acceptance nobody ran, the exact gap T783's guard exists to close. Fix the FIXTURE, not the feature: make an orphan the recovery path will not adopt (e.g. a session whose window blob is dropped from the agent too, or one opened by a second short-lived app instance), and add a chooser-resume row to guard-due.ps1's coverage table so this cannot rot silently again.

## In plain terms

There is a test that proves you can take back a terminal session that is still
running but has no window on screen — the whole reason the machine chooser
lists sessions. That test could not set itself up any more, so it stopped
before checking anything, and it stayed that way for eight days without anyone
noticing. The setup half has since been fixed. What was still missing is the
tripwire: nothing connected this test to the code it covers, so the next time
it rots it would go unnoticed again in exactly the same way. Now the loop is
told to re-run it whenever that code moves.

## Resolution

T816's primary symptom — the fixture — was already fixed by **T620**
(`622cdf9e1`, 2026-08-16), which landed four days AFTER T816 was filed
(2026-08-12) and was not linked to it. This turn verified that on the box
rather than assuming it, and then built the half T620 did not: the
`guard-due.ps1` coverage row T816 explicitly asked for, so the harness cannot
go red for eight days unnoticed again.

`MachineChooser.zig` is deliberately excluded from the row's coverage: it hosts
sixteen chooser features and took 15 commits in the last 14 days, so gating a
four-minute GUI acceptance on it would make this guard due almost daily for
reasons unrelated to resume. That is the same call the `session-layout-preserve`
row already makes about `App.zig`, and the table's comment records it.
