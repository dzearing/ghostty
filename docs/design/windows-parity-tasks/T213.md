# T213 - Migrate the 6 pixel-probe scripts from CopyFromScreen to PrintWindow

## Summary

T207 deliverable 4, and the pleasant surprise of the T207 spike. T207 assumed
the capture scripts might have to stay on the interactive desktop (or move to
a VM) because DWM composes only the input desktop. Half of that is true and
half is not, measured on box 2026-07-30:

- `Graphics.CopyFromScreen` / `BitBlt` off the desktop DC is **dead** on a
  background desktop - `BitBlt` returns false outright, no bitmap at all.
- `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` **works** - it returned real
  content for a `--window-theme=light` window (mean luminance 246, 64 distinct
  colors), against the same OpenGL-rendered terminal surface.

So the capture scripts CAN move; they just cannot screenshot. Rewrite the 6
onto `Get-TestWindowPixels` (T211).

Scripts that capture pixels: `tab-strip.ps1`, `menu-bar.ps1`,
`pane-banner.ps1`, `ipc-machine-chooser.ps1`, `profile-latency.ps1`,
`hero-mode.ps1`, `dark-menus.ps1`, `confirm-dialogs.ps1`, `config-errors.ps1`
(9 files match `CopyFromScreen|PrintWindow`; T207's count of 6 was
`CopyFromScreen` only).

## NARROWED 2026-07-30 by T211 - read this before starting

`PrintWindow` on a background desktop returns the window's GDI-painted
**chrome** only; the OpenGL terminal surface comes back as a flat fill
(measured: the `GhozttyTerminal` child captured meanLum 255 / 1 distinct
color, unchanged after typing into it). The spike's "64 distinct colors" came
from the tab strip it enabled, not from the terminal.

So this task covers the probes that measure NATIVE CHROME - tab strip, menus,
dialogs, titlebar - and those work: a titlebar band separates
`--window-theme=light` from `dark` at 240 vs 34 through `Get-TestWindowPixels`.
Probes that measure rendered TERMINAL content are **T214**, not this task, and
must not be migrated into an assertion that passes against a flat fill.

## Known traps

- **Coordinates change.** `PrintWindow` renders into a window-relative bitmap,
  so every probe currently written in SCREEN coordinates (`GetWindowRect` +
  absolute x/y) must be rebased to client/window-relative. This is where a
  migration silently starts sampling the wrong rectangle and still "passes"
  because the expected color happens to be there.
- **`PW_RENDERFULLCONTENT` has a history here** - T131 already found a trap
  with it. Re-read that task before assuming a clean capture.
- **Menus are separate top-level windows.** `#32768` popups are not children
  of the app window, so they must be `PrintWindow`ed individually rather than
  captured from a screen rect that happens to contain them.

## Validation

- Each migrated script ALL PASS x3 on the test desktop.
- Negative control per script: flip the app to the opposite theme/state and
  confirm the assertion FAILS. A `PrintWindow` that quietly returned a blank
  or stale bitmap must not be able to pass.

### What the verification turned up: the harness's own control was dead

`test/win32/test-desktop-harness.ps1` - the script that proves
`Get-TestWindowPixels` returns real chrome for everything above - compared a
`--window-theme=light` window against a `--window-theme=dark` one. Both now
read the **same** caption band, `rgb 60,64,72`, meanLum 65-71: since T254
client-painted the caption and T205 merged the tabs into it, the band derives
from `background` (+20/channel) and nothing in either painter reads
`window-theme`. Filed as **T273**; the hardcoded light foregrounds that
compound it are **T274**.

The control is now driven by `--background=ffffff` vs `--background=000000`,
the input the band actually derives from: **meanLum 243 vs 24**, and the
harness is ALL PASS (20 assertions).

**The lesson is about the control, not the theme.** It failed HALF green: the
light assertion (`> 150`) went red on 71 while the dark assertion (`< 100`)
stayed PASS on the identical pixels. A two-sided control whose sides are only
ever checked against their own thresholds can sit half-green over a
discriminator that has stopped discriminating entirely - and the green half
reads as evidence. The separation between the two halves is now asserted in
its own right (`light - dark >= 100`), which is the assertion that could not
have survived the regression.
