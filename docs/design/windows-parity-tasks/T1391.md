# T1391 - Find bar's rounded corners paint opaque, showing square dark corners over the terminal

## Summary

The floating find card is drawn with rounded corners, but the four corner
pixels are **opaque**, not transparent: they are filled with the colour the bar
*assumes* is behind it rather than the pixels actually there. Over anything
whose colour differs from that assumption, the rounding stops reading as
rounding and you instead see a square dark plate with lighter rounded inset —
the corners are visible as distinct blocks.

Reported interactively 2026-09-06 with a screenshot: the find bar floating over
a pane, its top-left/top-right corners clearly a different shade than both the
card and the content behind it.

### Where it comes from

`src/apprt/win32/ViewerFindBar.zig` paints the card by blitting the
`banner_card` surface with `SRCCOPY`:

- `ensureCardSurface` renders the rounded card onto a backdrop pre-filled with
  `self.doc_rgb` (`self.doc_rgb = self.pane.bg`, set around line 261).
- `paint` does `BitBlt(hdc, 0, 0, width, height, mem, margin, margin, SRCCOPY)`
  (around line 535), so every pixel of the window rect is written, corners
  included, with that assumed `doc_rgb`.

So the corner colour is only correct when the content directly under the bar
happens to be exactly `pane.bg`. Over a viewer document, a scrollbar, a
selection, a differently-shaded region, or the terminal's own content it is
wrong, and the difference is exactly what the user is seeing.

The same `SRCCOPY`-a-rounded-card-onto-an-assumed-backdrop pattern is used by
other floating chrome (`BannerOverlay.zig`, `banner_card.zig` consumers) — check
whether they have the same defect over non-`pane.bg` content before fixing only
this one. If they share it, fix the shared mechanism, not the call site.

### Fix direction

Stop guessing the backdrop; make the corners genuinely not-there. Either:

1. **Clip the window** — `SetWindowRgn` with `CreateRoundRectRgn` at the card's
   radius, so the corner pixels are never painted and whatever is behind shows
   through unmodified. Simplest, and correct over any content. Remember to
   re-apply on every DPI/scale and size change (`card_scale` already tracks
   this), and that the region is in window coordinates.
2. **Composite instead of copy** — make the card surface carry alpha and blit it
   with `AlphaBlend`/`UpdateLayeredWindow` so the corners blend with the real
   backdrop.

(1) is the smaller change and matches how the rest of win32 chrome handles
rounded plates; prefer it unless the card needs a soft/antialiased edge, which
a hard region cannot give.

Consult `docs/design/win32-design-system.md` for the card radius — do not
hardcode a new one — and `docs/claude/win32-ui.md` before touching chrome.

### Parity note

Per the standing symmetry rule, check whether the macOS find bar has the same
artifact. It almost certainly does not (AppKit composites its rounded card), so
this is expected to be a win-only fix — but confirm rather than assume, and if
the Mac side is also wrong, file the mac seat's half.

## Validation criteria

- [ ] Over content that is NOT `pane.bg` (a viewer document, a light page, a
      selection), the find bar's four corners show the content behind them —
      no square plate, no mismatched corner blocks. Evidence: before/after
      screenshots at the same spot.
- [ ] Corners stay correct after a DPI change and after the pane is resized
      (region re-applied, not stale at the old radius/size).
- [ ] Corners stay correct in both a light and a dark terminal theme.
- [ ] The card's rounding radius still matches the value in
      `docs/design/win32-design-system.md` — no new hardcoded radius.
- [ ] `BannerOverlay` / other `banner_card` consumers checked for the same
      defect; either shown correct, or fixed in the same change.
- [ ] An automated check covers it: a pixel probe in `test/win32/` that puts a
      known non-`pane.bg` colour behind the bar and asserts the corner pixel
      still reads that colour. See the probe recipe notes — the probe process
      must be DPI-aware and use `CopyFromScreen` (`GetPixel` skips layered
      windows).
- [ ] `powershell -NoProfile -File scripts\floor-lane.ps1 -Lane all` green.
