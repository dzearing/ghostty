# T1391 - Find bar's rounded corners paint opaque, showing square dark corners over the terminal

## Summary

The floating find card is drawn with rounded corners, but the four corner
pixels are **opaque**, not transparent: they are filled with the colour the bar
*assumes* is behind it rather than the pixels actually there. Over anything
whose colour differs from that assumption, the rounding stops reading as
rounding and you instead see a square dark plate with lighter rounded inset —
the corners are visible as distinct blocks.

Reported interactively 2026-09-06 with a screenshot: the find bar floating over
a pane, its top-left/top-right corners clearly a different shade than both the
card and the content behind it.

### Where it comes from

`src/apprt/win32/ViewerFindBar.zig` paints the card by blitting the
`banner_card` surface with `SRCCOPY`:

- `ensureCardSurface` renders the rounded card onto a backdrop pre-filled with
  `self.doc_rgb` (`self.doc_rgb = self.pane.bg`, set around line 261).
- `paint` does `BitBlt(hdc, 0, 0, width, height, mem, margin, margin, SRCCOPY)`
  (around line 535), so every pixel of the window rect is written, corners
  included, with that assumed `doc_rgb`.

So the corner colour is only correct when the content directly under the bar
happens to be exactly `pane.bg`. Over a viewer document, a scrollbar, a
selection, a differently-shaded region, or the terminal's own content it is
wrong, and the difference is exactly what the user is seeing.

The same `SRCCOPY`-a-rounded-card-onto-an-assumed-backdrop pattern is used by
other floating chrome (`BannerOverlay.zig`, `banner_card.zig` consumers) — check
whether they have the same defect over non-`pane.bg` content before fixing only
this one. If they share it, fix the shared mechanism, not the call site.

### Fix direction

Stop guessing the backdrop; make the corners genuinely not-there. Either:

1. **Clip the window** — `SetWindowRgn` with `CreateRoundRectRgn` at the card's
   radius, so the corner pixels are never painted and whatever is behind shows
   through unmodified. Simplest, and correct over any content. Remember to
   re-apply on every DPI/scale and size change (`card_scale` already tracks
   this), and that the region is in window coordinates.
2. **Composite instead of copy** — make the card surface carry alpha and blit it
   with `AlphaBlend`/`UpdateLayeredWindow` so the corners blend with the real
   backdrop.

(1) is the smaller change and matches how the rest of win32 chrome handles
rounded plates; prefer it unless the card needs a soft/antialiased edge, which
a hard region cannot give.

Consult `docs/design/win32-design-system.md` for the card radius — do not
hardcode a new one — and `docs/claude/win32-ui.md` before touching chrome.

### Parity note

Per the standing symmetry rule, check whether the macOS find bar has the same
artifact. It almost certainly does not (AppKit composites its rounded card), so
this is expected to be a win-only fix — but confirm rather than assume, and if
the Mac side is also wrong, file the mac seat's half.

## In plain terms

When you search inside a viewer pane, the little search box floats on top of
the page. Its corners are supposed to be rounded, but they were being filled in
with a flat colour guessed from the pane's background instead of letting the
page show through - so on anything that was not exactly that colour you saw a
dark square block at each corner, with the rounded box sitting inside it. After
this the corners are genuinely see-through: the page behind them is what you
see, at any size, any zoom level, and in a light or a dark theme.

## Goals

- [x] The search box's four corners show whatever is behind them, not a guessed
      colour
- [x] They stay right when the pane is resized or the display scale changes
- [x] The other floating chrome is checked for the same problem
- [x] A test proves the corners are cut away, so this cannot come back unnoticed

## Validation criteria

- [x] Over content that is NOT `pane.bg` (a viewer document, a light page, a
      selection), the find bar's four corners show the content behind them -
      no square plate, no mismatched corner blocks. Verified by the WINDOW
      REGION rather than by pixels: `viewer-find.ps1` section B2 asks the
      window manager whether each corner pixel is inside the card's region and
      all four answer no, so nothing the card paints there can reach the
      screen and the content behind it is what shows - whatever colour that
      content happens to be. (A screenshot could not have answered this: the
      suite runs on the background test desktop where `CopyFromScreen` is
      dead, and a `PrintWindow` capture shows what the card DRAWS, which it
      still does in the clipped corners.)
- [x] Corners stay correct after a DPI change and after the pane is resized.
      The region is cut in `place`, which runs on every bounds sync, so it can
      never be stale: B2 grows the window and re-probes the new trailing
      corner. The scale half is the unit test - `cornerRegion` is asserted to
      equal twice the scaled `banner_card.RADIUS` at every scale from 1.0 to
      3.0, and `place` passes it the live `self.scale`. A monitor scale change
      itself is not drivable on the test desktop.
- [x] Corners stay correct in both a light and a dark terminal theme. True by
      construction now: the corner pixels are not painted at all, so there is
      no colour left for a theme to get wrong. This is exactly what the old
      code could not say - its corners were `doc_rgb`, which IS the theme.
- [x] The card's rounding radius still matches the value the card is drawn
      with - `cornerRegion` reads `banner_card.RADIUS` and no new number was
      introduced; the acceptance cross-checks the region's arc against the
      radius the pane logged (`ellipse=36` at 1.25 scale, r=18). The design
      system's 3.1 table says 8 DIP for cards where `banner_card` renders 14,
      which is a real contradiction between the table and every card on
      screen - filed as T1399 rather than resolved here, since making the
      table win moves every card.
- [x] `BannerOverlay` / other `banner_card` consumers checked for the same
      defect. `BannerOverlay`, `ViewerNavBar` and `ViewerFeedbackBar` paint
      RESERVED bands - `ViewerPane.contentTop` adds each one's height, so the
      page is pushed below them and `pane.bg` really is what is behind - and
      `ViewerTOCPanel`'s compact card already clips itself the same way. The
      find card was the only floating card that did not.
- [x] An automated check covers it: `viewer-find.ps1` section B2, on the new
      `Get-TestWindowRegionHits` in `lib\TestDesktop.ps1` (a desktop-bound
      `GetWindowRgn` + `PtInRegion`). It asserts a region exists at all - a
      square-cornered window carries none, which is the defect itself - the
      four corners are outside it, the middle is inside, and the arc starts
      where the logged radius says. The pixel-probe recipe the card was filed
      with was the wrong instrument here for the reason given above.
- [x] `powershell -NoProfile -File scripts\floor-lane.ps1 -Lane all` green -
      lib/none/win32/agent ALL LANES PASS.
