# T345 - next orders by id, so the oldest todos outrank every follow-up the loop files

## In plain terms

Nobody decides by hand what gets worked on next any more - a script does, by
reading the tasks themselves. This checks that the script picks the way a
person would: the most important thing first, and when two things matter
equally, the one that has been waiting longer. It also gives the tracker a way
to say "we looked at this and it can wait", which it could not say before -
those tasks were filed under a label the tooling quietly threw away, so they
looked exactly like tasks nobody had read yet. And it retires a page of
hand-written priorities that every task on it has long since finished, so the
instructions stop pointing somewhere that has nothing left to say.

## Resolution (2026-08-21)

**The premise expired before the task was picked up.** Two things had to be
true for the starvation this task describes: an id-first sort, and an old
backlog to do the starving. Neither survives.

- **The sort changed on 2026-08-12** (D55, on a direct user directive):
  `priority:` decides, `order:` sequences within a band, id is only the last
  tiebreak. A follow-up filed today is therefore reachable the day it is
  filed, with no renumbering and no hand-placement.
- **The old backlog is gone.** Of the 301 open `todo` tasks for this seat on
  2026-08-21, **zero** have an id below 345. Every open task is one the loop
  filed for itself. There is nothing left for a low id to outrank.

So the answer to "what replaces Current priorities" is: **`next` does, and
re-triage is how you change it.** `set-priority` moves the queue head on its
own and journals the transition into the task's progress log - a hand-curated
list in a 1300-line doc could do neither, and every task on that list is now
closed. It is frozen as history, in the three places that still called it the
authority (`go.md` twice, `windows-parity-tasks.md`, and the task-dir README).

**One genuine gap turned up, and it is why this task still had work in it.**
Two tasks (T499 cache-log noise, T551 an intermittent harness flake) carried
`priority: "P3"`. There is no P3, so `parity-tasks.ps1` blanked it on read -
silently, since nothing validated the field - and both rendered on the
dashboard as untriaged, identical to a task nobody had ever looked at. The
sentence their authors wanted was not expressible any other way either:
leaving the field blank means "nobody looked", and `order:` cannot say it,
because an unplaced task ranks last within its band, so *any* number written
pulls a task AHEAD of every unordered one.

Two people independently reaching for the same missing word is the evidence
that the vocabulary was short one, so P3 is now a real band, ranking behind P2
and ahead of untriaged. This is a mechanism call, not an experience one - no
user of the terminal can tell these apart - so it is recorded here rather than
filed as a decision (go.md 5b). The safeguard that makes it safe to have a
closed set at all: an out-of-set value is now an `ODD PRIORITY` **validate
failure** naming the task and the value, exactly like the seat-typo guard, so
the next invented band is loud on the first commit instead of quiet for weeks.

*Not done, deliberately:* nothing was re-ordered or re-prioritised in the real
tracker. The queue is a pure function of the task files and this task did not
touch what is in them, only what the tooling can express.

## Summary

**Current priorities is now empty** - as of 2026-08-02 every named chain in
that section of `windows-parity-tasks.md` is done. That section has been the
ordering authority since 2026-07-15, so this is the first time `next` has
actually decided what the loop works on, and its policy is: **lowest id whose
deps are met.** With T344 in, that answer is T37, filed in the Phase-A era.

That policy has a consequence worth deciding deliberately rather than
inheriting. Every turn ends by filing what it turned up - T338 filed T342 and
T343, T336 filed T339, T319 filed T328 and T329 - so the follow-ups are always
the HIGHEST ids, and a strict id order puts them permanently last. The tasks
most likely to be load-bearing (a flaky positive control, an N+1 dial on the
GUI thread, a hole a shipped feature left) sit behind every survivor of the
original backlog, which is roughly the opposite of the order that a person
would pick.

The inverse policy is not obviously right either: newest-first would starve
the old backlog just as completely, and some of those old rows are real parity
gaps.

## Details

Things to settle, with evidence rather than taste:

- **How many todos are actually left, and what shape are they?** `list -Status
  todo` is the input. Split them: original-backlog parity gaps vs follow-ups
  filed by a completed task. If the old backlog is mostly stale (superseded,
  or answered by a later task that did not know it existed), the ordering
  question is smaller than it looks and the real work is an audit.
- **Does `deps` already express what we want?** A follow-up filed BY a task is
  causally after it, but `deps` records *blocking*, not *priority*. Adding a
  `priority:` field would be a third ordering axis on top of Current
  priorities and id order; prefer making one axis right over adding one.
- **What replaces Current priorities?** The user directive that created it is
  from 2026-07-15 and has been the top-of-file authority since. If `next` is
  the authority now, `go.md` and the tracker's resume protocol should say so
  in those words, rather than pointing at a section that is empty.

Note this is NOT a request to have the loop pick its own favourites. The value
of a deterministic selector is that no turn negotiates with itself about what
to work on; whatever policy wins here must stay a pure function of the task
files.

*Validation:* whatever ordering lands is asserted in
`test\win32\parity-tasks-seat.ps1` (or a sibling) against a fixture with a low
old id and a high follow-up id, so the policy is a test rather than a habit.
Plus a stated, dated line in `go.md` naming the authority the loop obeys.
