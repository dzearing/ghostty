# T345 - next orders by id, so the oldest todos outrank every follow-up the loop files

## Summary

**Current priorities is now empty** - as of 2026-08-02 every named chain in
that section of `windows-parity-tasks.md` is done. That section has been the
ordering authority since 2026-07-15, so this is the first time `next` has
actually decided what the loop works on, and its policy is: **lowest id whose
deps are met.** With T344 in, that answer is T37, filed in the Phase-A era.

That policy has a consequence worth deciding deliberately rather than
inheriting. Every turn ends by filing what it turned up - T338 filed T342 and
T343, T336 filed T339, T319 filed T328 and T329 - so the follow-ups are always
the HIGHEST ids, and a strict id order puts them permanently last. The tasks
most likely to be load-bearing (a flaky positive control, an N+1 dial on the
GUI thread, a hole a shipped feature left) sit behind every survivor of the
original backlog, which is roughly the opposite of the order that a person
would pick.

The inverse policy is not obviously right either: newest-first would starve
the old backlog just as completely, and some of those old rows are real parity
gaps.

## Details

Things to settle, with evidence rather than taste:

- **How many todos are actually left, and what shape are they?** `list -Status
  todo` is the input. Split them: original-backlog parity gaps vs follow-ups
  filed by a completed task. If the old backlog is mostly stale (superseded,
  or answered by a later task that did not know it existed), the ordering
  question is smaller than it looks and the real work is an audit.
- **Does `deps` already express what we want?** A follow-up filed BY a task is
  causally after it, but `deps` records *blocking*, not *priority*. Adding a
  `priority:` field would be a third ordering axis on top of Current
  priorities and id order; prefer making one axis right over adding one.
- **What replaces Current priorities?** The user directive that created it is
  from 2026-07-15 and has been the top-of-file authority since. If `next` is
  the authority now, `go.md` and the tracker's resume protocol should say so
  in those words, rather than pointing at a section that is empty.

Note this is NOT a request to have the loop pick its own favourites. The value
of a deterministic selector is that no turn negotiates with itself about what
to work on; whatever policy wins here must stay a pure function of the task
files.

*Validation:* whatever ordering lands is asserted in
`test\win32\parity-tasks-seat.ps1` (or a sibling) against a fixture with a low
old id and a high follow-up id, so the policy is a test rather than a habit.
Plus a stated, dated line in `go.md` naming the authority the loop obeys.
