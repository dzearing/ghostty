# T338 - The layout blob key is reused across app runs, so a crash makes the previous window unrestorable

Found building T335 (2026-08-02), which is the task that made the consequence
visible: Restore All rebuilds what the agent holds, and for an ordinary window
the agent no longer holds it.

## The defect

A layout blob's key is the manifest window id, which is the window's ipc name
when it has one and `win-{index}` when it does not (`App.captureSessionLayout`,
`App.zig:1325-1328`). Neither is stable ACROSS APP RUNS:

- Every window gets an **auto ipc name** `window-N` allocated from a counter that
  restarts at 1 in each app process, so run 2's first window is `window-1` — the
  same key run 1's first window pushed. (Related: **T121**, auto `window-N` names
  can duplicate after a session restore. Same counter, different symptom.)
- An unnamed window's `win-{index}` is a position in this run's window list, which
  is likewise re-used from 0.

The push is a reconcile, so the first sync of the new run UPSERTS that key with
the new window's bytes — and the previous run's topology is gone from the store
inside the 250ms layout debounce, before a user could possibly press anything.

## Evidence (VERIFIED on the box, 2026-08-02)

Probe: launch the debug build with persistence, read the store; kill the GUI only
(agent and children survive), delete the local manifest, relaunch, read again.

```
run1 alive ids:          361187ea6f05f1e7a7eb57041604e065
run1 <record> key=window-1 session_ids: 361187ea6f05f1e7a7eb57041604e065
run2 alive ids:          ad8fcb1d084e9ef6852339cdd53643dc, 361187ea6f05f1e7a7eb57041604e065
run2 <record> key=window-1 session_ids: ad8fcb1d084e9ef6852339cdd53643dc
run2 keys:               window-1          <- ONE record, not two
```

Run 1's session is still ALIVE in the agent and is no longer claimed by any
blob, so its window cannot be rebuilt by anything. Corroborated from the other
end by `test\win32\chooser-restore-all.ps1`, which restores exactly one window
(the ipc-NAMED one) out of the two the fixture built.

## Why it matters

Restore All's whole reason to exist is the crash-with-no-manifest case. That case
is also the one that destroys the record: the relaunched app opens a blank
startup window, which takes the dead run's key. So the feature reliably loses
the user's FIRST window and silently keeps the rest.

`test\win32\chooser-restore-all.ps1` sidesteps it by naming its fixture window
(`+new-window --target=t335-multi`), because an explicit ipc name IS stable. That
is a test working around a product defect, and the workaround should be deleted
with the fix.

## The fix (proposed)

Give each window a persistent identity and key the blob on it — Mac's shape,
where an entry carries a UUID (`SessionLayoutManifest.Entry.id`) and a restored
window re-adopts it. Concretely:

1. A `uuid` on `session_layout.Window` (additive, optional — an older manifest
   without one falls back to today's derivation, per the file's own contract).
2. Generated when the window is created, re-adopted by `App.restoreWindow` and by
   the T335 rebuild, so a restored window keeps pushing to the same key.
3. `App.pushLayoutBlobs` keys on it. The reconcile is unchanged: within a run the
   stale-key delete still removes a closed window's blob.

Do NOT "fix" it by having a fresh app adopt the agent's keys and reconcile
against them — pass 2 would then DELETE every blob the previous run left, which
is exactly the state Restore All is there to read.

Watch the blast radius: `test\win32\layout-blobs.ps1` asserts the current key
shape in four places, and T121 touches the same auto-name counter.

## Validation

- Unit: the key survives a capture → restore → capture round trip.
- On box: the probe above, inverted — after the relaunch the store holds TWO
  records and the dead run's session is still claimed by its own.
- `test\win32\chooser-restore-all.ps1` extended with an UNNAMED multi-pane
  window, which must also come back; drop the comment that explains why the
  fixture has to be named.

## Done (2026-08-02)

Shipped as proposed. `session_layout.Window` gained an optional `uuid`,
`Window` a fixed-size `layout_uuid` generated in `init` from the same
`pane_id` generator the panes use (no allocation, no failure path — a window
always has one), `Window.InitOptions.layout_uuid` re-adopts a recorded value
the way `Surface.Overrides.pane_id` already did, `captureSessionLayout` records
it, and `pushLayoutBlobs` keys on `win.uuid orelse win.id`. `restoreWindow`
passes it through, which covers BOTH rebuild sources at once — launch-time
restore from the local manifest and the T335/T336 Restore All from an agent
blob — because both arrive there as a `session_layout.Window`.

`orelse win.id` is not defensive padding: it is the only path a blob written by
a pre-T338 build can take, and it keeps that blob's key stable rather than
re-keying it under a uuid the old bytes never carried.

**The fix is what makes the agent's store an ARCHIVE rather than a mirror.**
Old blobs no longer disappear at relaunch, and nothing new bounds them — the
delete pass only reaches keys THIS run pushed, by design (T338's own "do NOT
have a fresh app adopt the agent's keys"). What bounds them is the agent:
`SessionStore.reapLayouts` drops a record once none of its `session_ids` still
exists, so a blob lives exactly as long as something is left to restore. That
was already true; it was just never load-bearing while every key got recycled.

### Evidence

The regression lives in `test\win32\layout-blobs.ps1` as a new section F — the
task's probe, inverted: kill the GUI, delete the local manifest (the case
launch-time restore cannot serve), relaunch, and require TWO records. Plus key-
shape assertions in A and C. 37 assertions ALL PASS.

**Positive control, run before believing any of it.** Reverting only the key
expression to `win.id` and rebuilding turns 9 assertions red, including exactly
the ones this task is about:

```
FAIL F2 the store holds TWO records - the dead run's and the new one's
FAIL F4 it still describes the two-leaf window it always did
FAIL F5 it still claims the sessions the agent kept alive
FAIL F6 the new window took a fresh uuid key of its own
FAIL F7 the new record claims a session the old one does not
```

F3 stayed GREEN there, and that is the interesting part: the key `window-1` was
still present, so an existence check would have reported the record as fine. It
was the CONTENTS that had been overwritten. A test for this defect has to assert
what a record says, not that it is there.

`test\win32\chooser-restore-all.ps1` grew the unnamed fixture: the startup
window (auto `window-N` only) is split, so the crash case now orphans two
multi-pane windows and Restore All must bring back BOTH (1 → 3 windows), with
the agent independently reporting all five sessions attached. The rebuilt
unnamed window is identified by SHAPE, not by name — its `window-N` collides
with the one the relaunched app already gave its own blank window, and which
registration survives that is **T121**'s question, not this one's.

Two follow-ups filed: **T342** (step 4's Tab walk in `chooser-restore-all.ps1`
failed once in two runs — a flaky POSITIVE CONTROL is worse than none) and
**T343** (in-place agent recovery still pairs live windows to captured ones by
POSITION, restating the capture's skip rule by hand; the uuid is now a real key
it could use instead).
