# T214 - Terminal-surface pixel assertions cannot capture on a background desktop

## Summary

Found while building the T211 harness, and it narrows T207's capture answer.
`PrintWindow(PW_RENDERFULLCONTENT)` on a background desktop returns the
window's **GDI-painted chrome only**. The OpenGL terminal surface comes back
as a flat fill, so any probe aimed at rendered terminal content would read a
constant and "pass" against nothing.

## Evidence (measured on box 2026-07-30, debug build)

| probe | result |
|---|---|
| `PrintWindow(GhozttyWindow)` with the tab strip on | meanLum 251, **60 distinct colors** - real chrome |
| `PrintWindow(GhozttyTerminal child)` | meanLum 255, **1 distinct color** |
| same child, after typing `echo XXXXXXXX` into it | meanLum 255, 1 distinct - unchanged |
| whole window, `--background=ffffff` vs `--background=000000` | 255 vs 253 - the background config does not move it |
| titlebar band only, `--window-theme=light` vs `dark` | 240 vs 34 - chrome DOES discriminate |

So the T207 spike's "PrintWindow returns real content (meanLum 246, 64
distinct)" was reading the tab strip it had deliberately enabled with
`--window-show-tab-bar=always`, not the terminal. The conclusion "the pixel
probes can migrate" holds for chrome and NOT for terminal content.

## What this task has to decide

1. Which of the 9 pixel-probe scripts actually assert **terminal content**
   rather than chrome (T213 covers the chrome ones and can proceed). Likely
   candidates: `pane-banner.ps1` (native overlay above the terminal),
   `hero-mode.ps1` (snapshot thumbnails), `profile-latency.ps1`.
2. Then pick a route, and SAY which in the log rather than leaving it silent:
   - an app-side debug capture (read the GL framebuffer and expose it over
     IPC) - the only path that makes terminal pixels assertable anywhere, and
     useful beyond the test desktop;
   - keep those specific assertions on the interactive desktop behind the
     harness's `-Interactive` escape hatch, accepting that they steal focus
     and so must not run in the loop;
   - or drop the pixel assertion for a non-pixel oracle.

T209 (the on-box pixel assertions T204/T206 could not run) depends on the
answer, so it is blocked on this, not on T213 alone.

## Question 1 is now ANSWERED for the two scripts named above (T218 batch 6,
## 2026-08-01)

Measured while migrating them, so this is a narrowing, not a guess:

- **`pane-banner.ps1` is not blocked** (migrated in T217 batch 8). The banner
  is a GDI-painted `WS_EX_LAYERED` popup, and its band corner reads the pane
  background EXACTLY under PrintWindow - it pins `#101014` -> `16,16,20`.
- **`hero-mode.ps1` is not blocked either, and the reason generalises.** Its
  carousel thumbnails ARE terminal content, but the app moves them across the
  boundary itself: each pane's renderer thread captures its GL content into a
  DIB (`Surface.heroSnap*`) and the GUI thread blits it into the PARENT
  window's DC inside BeginPaint, invalidating as it goes. Measured on the test
  desktop: 101 distinct colors in the carousel column, and the signature
  changes while a busy TUI runs in a HIDDEN pane. **Ask which thread painted
  the pixels, not which technology produced them.**
- What IS blocked is **exactly three assertions**, all of them aimed at a
  `GhozttyTerminal` child directly: `hero-mode`'s two `Get-PaneColorCount`
  probes ("hero pane renders content", >= 8 distinct colors) and
  `window-color`'s pane-centre tint probe. All three are dropped in-place with
  the reason in `test/win32/*.ps1` headers, none weakened into an assertion a
  flat fill could pass.
- `window-color` also shows the third route working: its tint probe was
  replaced by the **banner band**, a different painted consumer of the same
  effective background (`Surface.refreshBannerColors`), labeled as NOT covering
  the glass. Where an app-side capture is not worth building, look for another
  consumer of the same value that the app already paints natively.

So this task's remaining scope is smaller than it looked: three assertions and
`profile-latency.ps1`, not "the pixel-probe scripts".

## ANSWER (2026-08-01 — question 1 finished, question 2 decided)

### Question 1, finished: the sweep, and the script it had missed

`grep -l 'PrintWindow|CopyFromScreen|GetPixel|Get-Test(WindowPixels|Pixel|Brightness)'`
over `test/win32/*.ps1` returns **22 files**, and every one of their capture
targets was read rather than inferred. All but two probe CHROME — top-level
windows, dialogs, menus, and the two layered overlays — which the harness
header already says migrates, and which this run re-measures (light caption
243 vs dark 24).

The two exceptions:

- **`profile-latency.ps1`** — one assertion, the scroll-viewport pixel hash
  (`profile-latency.ps1:381`). Already interactive by design for an unrelated
  reason (SendInput timing IS the measurement), so it costs nothing extra.
- **`color-contrast.ps1` (T150) — MISSED by every previous sweep, including
  T272's.** Its whole oracle is terminal content: the derived foreground, the
  regenerated 256-colour palette, and the renderer's draw-time contrast floor,
  none of which exist anywhere but in GL pixels. It escaped T272 because it
  takes no foreground and calls no `SendInput` — it reads `GetDC(NULL)` +
  `GetPixel`, the composited screen, which is dead off the input desktop for a
  different reason. **T276** widens the sweep so "un-runnable in the loop"
  stops being approximated by "steals focus".

### Question 2, decided: routes 1–4, and NOT route 0

Recorded in full in `test/win32/lib/TestDesktop.ps1`'s CAPTURE LIMIT header,
where the next author will actually be standing. In order:

1. **Ask which thread painted the pixels, not which technology produced
   them** — hero-mode's thumbnails are renderer output that the app itself
   moves onto the GDI side (`Surface.heroSnap*` → parent DC inside
   `BeginPaint`), so PrintWindow reads them.
2. **Substitute another native painter of the same value** — window-color's
   tint probe became the banner band, labelled as not covering the glass.
3. **Drop it in place with the measured reason** — hero-mode's two
   `Get-PaneColorCount` probes. Never weaken it into something a flat fill
   passes.
4. **Interactive by design, and DECLARED** — the two scripts above, now named
   in the harness header with why.

**Route 0 (an app-side GL readback over IPC) is deliberately not built**, and
the reason is filed as **T275** rather than left implicit: the measured
population is 3 assertions + 2 scripts, and all five had a cheaper route. What
makes T275 cheap when it comes is that heroSnap already crosses the boundary —
the missing piece is a way to ASK for that snapshot, not a way to take it.

### The enforceable half

A decision recorded in a header is a decision that regrows. `Get-TestWindowPixels`
now **refuses a `GhozttyTerminal` capture by class**, before anything is
measured, pointing at the four routes; `-AllowTerminalSurface` exists only to
measure the limit itself. Refusing by class is the only workable point: a flat
fill is a perfectly valid bitmap, so there is nothing to detect after the fact.
Audited all 29 existing `Get-TestWindowPixels` call sites — none targets a
terminal child, so the guard costs no migration.

## Validation (RUN on the box 2026-08-01, debug build `0783be60f` + this change)

`test-desktop-harness.ps1` — **ALL PASS (23 assertions)**, up from 20. The
three new ones are the guard and its negative control, and they run on a pane
that has just echoed a token, so it is definitely rendering:

```
PASS  Get-TestWindowPixels REFUSES the GhozttyTerminal surface by class
capture: terminal surface distinct=1 meanLum=255
PASS  the terminal surface captures as a FLAT FILL (1 distinct colors on a pane that just echoed 'harness-ok-42')
capture: terminal surface after more output distinct=1 meanLum=255
PASS  the flat fill does not move when the terminal renders (distinct=1 meanLum=255 vs 255)
```

That is this task's required negative control, and it is the stronger form:
rather than flipping the measured thing and watching an assertion fail, the
flat fill is *shown not to move at all* while the pane renders new output —
so a probe there does not fail loudly, it passes against nothing. The positive
control is in the same run and same script: the chrome capture separates light
from dark caption by 219 levels (243 vs 24), so the capture path itself is
provably alive on that desktop.

Floor: `zig build test -Dapp-runtime=none` exit 0, `-Dapp-runtime=win32` exit
0, `zig build test-agent` exit 0, P1/P2/P3 ALL PASS.
