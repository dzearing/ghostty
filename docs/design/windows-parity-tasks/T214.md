# T214 - Terminal-surface pixel assertions cannot capture on a background desktop

## Summary

Found while building the T211 harness, and it narrows T207's capture answer.
`PrintWindow(PW_RENDERFULLCONTENT)` on a background desktop returns the
window's **GDI-painted chrome only**. The OpenGL terminal surface comes back
as a flat fill, so any probe aimed at rendered terminal content would read a
constant and "pass" against nothing.

## Evidence (measured on box 2026-07-30, debug build)

| probe | result |
|---|---|
| `PrintWindow(GhozttyWindow)` with the tab strip on | meanLum 251, **60 distinct colors** - real chrome |
| `PrintWindow(GhozttyTerminal child)` | meanLum 255, **1 distinct color** |
| same child, after typing `echo XXXXXXXX` into it | meanLum 255, 1 distinct - unchanged |
| whole window, `--background=ffffff` vs `--background=000000` | 255 vs 253 - the background config does not move it |
| titlebar band only, `--window-theme=light` vs `dark` | 240 vs 34 - chrome DOES discriminate |

So the T207 spike's "PrintWindow returns real content (meanLum 246, 64
distinct)" was reading the tab strip it had deliberately enabled with
`--window-show-tab-bar=always`, not the terminal. The conclusion "the pixel
probes can migrate" holds for chrome and NOT for terminal content.

## What this task has to decide

1. Which of the 9 pixel-probe scripts actually assert **terminal content**
   rather than chrome (T213 covers the chrome ones and can proceed). Likely
   candidates: `pane-banner.ps1` (native overlay above the terminal),
   `hero-mode.ps1` (snapshot thumbnails), `profile-latency.ps1`.
2. Then pick a route, and SAY which in the log rather than leaving it silent:
   - an app-side debug capture (read the GL framebuffer and expose it over
     IPC) - the only path that makes terminal pixels assertable anywhere, and
     useful beyond the test desktop;
   - keep those specific assertions on the interactive desktop behind the
     harness's `-Interactive` escape hatch, accepting that they steal focus
     and so must not run in the loop;
   - or drop the pixel assertion for a non-pixel oracle.

T209 (the on-box pixel assertions T204/T206 could not run) depends on the
answer, so it is blocked on this, not on T213 alone.

## Validation

- Whatever route is chosen, a negative control proves the capture is real:
  flip the thing being measured and the assertion must FAIL. A flat-fill
  capture must not be able to pass both halves (that is exactly the trap this
  task exists to record).
