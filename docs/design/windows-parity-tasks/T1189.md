# T1189 - The MSI packaging guard is due after every packaging edit and only Docker can clear it

## In plain terms

Nothing a user can see. This is about the safety net around the Windows
installer: the check that says "somebody has actually run the installer tests
against the installer script as it stands now". On this machine that check can
only be satisfied with Docker running, so every time the installer script is
edited the check goes red and the only way past it is the manual override. An
override you press every time stops being a decision.

## Summary

`guard-due.ps1`'s `release-artifacts-packaging` row covers
`dist/windows-installer/build-msi.sh`, and its harness section (B in
`test\win32\release-artifacts.ps1`) needs Docker and the `msitools-local`
image. Without Docker the run is `ALL PASS (1 skipped)` and deliberately does
not stamp, so the row stays due. Docker is down on this box by default and
starting it is a user call (a WSL2 backend that has buried the machine before),
so a packaging edit ends with `parity-tasks.ps1 validate -NoGuardDue` — which
is precisely the "this harness cannot run here" case the hatch exists for, but
used routinely it is indistinguishable from the T1165 misuse.

Worth considering, in preference order:

- CI already builds the MSI on every commit (`fork-ci.yml` → msitools 0.106 →
  `build-release-artifacts.sh`). If a green CI run for a sha could WRITE the
  packaging stamp, the guard would be cleared by the machine that can actually
  answer it, and the on-box hatch would go back to being rare.
- Failing that, split the row: the parts of `build-msi.sh` a Docker-less run
  DOES cover (now including `test\win32\install-launch.ps1`, T1176) stamp
  normally, and only the FILEVERSION half stays Docker-gated.
- Failing that, make the hatch cheaper to read: have `validate -NoGuardDue`
  print WHICH guard was excused and why, so a turn cannot excuse a red harness
  while believing it excused an unrunnable one.

## Validation criteria

- [ ] A `build-msi.sh` edit on a Docker-less box can reach a clean
      `parity-tasks.ps1 validate` without `-NoGuardDue`.
- [ ] The Docker-only assertions are still gated by something — the change
      must not silently stamp coverage that never ran.
- [ ] Demonstrated failing: a deliberately broken packaging surface still
      makes the guard due / the harness red.
