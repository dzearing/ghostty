# T199 - A harness leaks a live GUI ghoztty from a temp install dir for days

## Summary

Found while taking the pre-state for the T196 delivery (2026-07-30): a GUI
`ghoztty.exe` (pid 632) had been running since **2026-07-29 20:43:51** out of
`%TEMP%\gh-dbg2\install\ghoztty.exe` — a scratch install directory created by a
test harness, whose exe is dated 2026-07-29 18:00. Nineteen hours of a stray
app, from a script that finished a day earlier.

That is a live process, not a stray file: it holds windows, a message loop, and
possibly an IPC pipe instance, and it is the kind of thing that makes a later
run's process/pipe assertions ambiguous — "is that ghoztty mine or the leak's?"
Several harness lies already logged on this board (T111b's orphaned CLI child
holding a redirect file, T116's script driving the user's live terminal) are the
same shape.

## Details

- `gh-dbg2` appears in no file in the repo, so the name is composed at runtime
  (e.g. `gh-dbg` + a run index) — start by grepping the win32 scripts for the
  prefix and for `install`/`work` sibling directories, which is the layout on
  disk (`%TEMP%\gh-dbg2\{install,work}`). `upgrade-no-fork.ps1` (T138) and
  `agent-upgrade.ps1` (T147) both build stand-in install dirs and are the prime
  suspects.
- Fix the owning harness to kill what it launched in its teardown, keyed on the
  PID it started or on the exe path under its own temp dir — never on the image
  name, which would kill the user's real Ghoztty (the T116 lesson, and the
  reason `upgrade-ghoztty-windows.ps1` scopes its kill to the install dir).
- Teardown must run on the failure path too; a script that dies mid-way is
  exactly when a leak happens.
- Consider a shared `Stop-HarnessGhoztty` helper in the common test module so
  the next stand-in-install harness inherits the behavior instead of re-writing
  it.

## Validation

- Reproduce: run the owning script to completion, then assert no
  `ghoztty`/`ghoztty-agent` process remains whose `Path` is under the harness's
  temp root.
- Same assertion after forcing a mid-run failure.
- A negative control: with the teardown stubbed out, the assertion fails.
