# T199 - A harness leaks a live GUI ghoztty from a temp install dir for days

## In plain terms

A test that pretends to install Ghoztty into a scratch folder can leave a real
Ghoztty running there after it finishes - one did, for nineteen hours, and it
was noticed by eye. Nobody sees a window, but every later test that asks "which
Ghoztty processes are running?" gets an answer with a stranger in it, and can
report a failure that has nothing to do with the change being tested. After this
lands, a test cleans up what it launched even when it crashes half way through,
and the suite has a check that says out loud when something has been left
behind.

## Goals

- [x] a shared teardown helper for a scratch install dir, with the same
      path-exact safety as the repo-scoped one
- [x] teardown that runs on the failure path, not just at a tidy ending
- [x] a box-wide sweep that names any leaked process (pid, path, age)
- [x] the harnesses that build stand-in install dirs use it
- [x] an acceptance script, with teeth (the leak is provoked, then measured)

## Summary

Found while taking the pre-state for the T196 delivery (2026-07-30): a GUI
`ghoztty.exe` (pid 632) had been running since **2026-07-29 20:43:51** out of
`%TEMP%\gh-dbg2\install\ghoztty.exe` — a scratch install directory created by a
test harness, whose exe is dated 2026-07-29 18:00. Nineteen hours of a stray
app, from a script that finished a day earlier.

That is a live process, not a stray file: it holds windows, a message loop, and
possibly an IPC pipe instance, and it is the kind of thing that makes a later
run's process/pipe assertions ambiguous — "is that ghoztty mine or the leak's?"
Several harness lies already logged on this board (T111b's orphaned CLI child
holding a redirect file, T116's script driving the user's live terminal) are the
same shape.

## Details

- `gh-dbg2` appears in no file in the repo, so the name is composed at runtime
  (e.g. `gh-dbg` + a run index) — start by grepping the win32 scripts for the
  prefix and for `install`/`work` sibling directories, which is the layout on
  disk (`%TEMP%\gh-dbg2\{install,work}`). `upgrade-no-fork.ps1` (T138) and
  `agent-upgrade.ps1` (T147) both build stand-in install dirs and are the prime
  suspects.
- Fix the owning harness to kill what it launched in its teardown, keyed on the
  PID it started or on the exe path under its own temp dir — never on the image
  name, which would kill the user's real Ghoztty (the T116 lesson, and the
  reason `upgrade-ghoztty-windows.ps1` scopes its kill to the install dir).
- Teardown must run on the failure path too; a script that dies mid-way is
  exactly when a leak happens.
- Consider a shared `Stop-HarnessGhoztty` helper in the common test module so
  the next stand-in-install harness inherits the behavior instead of re-writing
  it.

## Validation

- Reproduce: run the owning script to completion, then assert no
  `ghoztty`/`ghoztty-agent` process remains whose `Path` is under the harness's
  temp root.
- Same assertion after forcing a mid-run failure.
- A negative control: with the teardown stubbed out, the assertion fails.

## Evidence (2026-08-10)

- The leak's owner was never a checked-in script: `gh-dbg2` matches no name any
  harness composes, and the directory (still on disk, dated 2026-07-29 20:43)
  has the `{install,work}` layout of a hand-run
  `upgrade-ghoztty-windows.ps1 -InstallDir <scratch>`. Delivering is the job
  that ENDS by launching the app, so pointing it at a scratch dir leaks by
  construction. That is why the fix is a shared helper plus a sweep rather than
  a patch to one script: the next such run will also be ad-hoc.
- Why no existing helper covered it: `lib\CleanSlate.ps1`'s `Stop-RepoGhoztty`
  refuses any exe outside the repo BY DESIGN (a mistyped `-Exe` must never
  reach the user's install), and a stand-in install dir is outside the repo by
  definition. `lib\HarnessLeak.ps1` is the missing counterpart - same
  path-exact discipline, a different sanctioned root, and a root check that
  refuses `%TEMP%` itself so an empty variable can never widen it.
- `agent-upgrade.ps1` had already hand-rolled half of this on 2026-08-03 (its
  `$script:TestProcRoot` filter, after a leftover agent owned the agent pipe
  and turned a passing run into 33 failures on re-run) - the duplication this
  task predicted, now with a shared answer under it.
- **Two silent `PowerShell.Exiting` traps, both measured here**, both of which
  make an exit handler do nothing at all with no error anywhere:
  1. the action resolves NO variable from the registering scope - a `$global:`
     reference never fired, and `.GetNewClosure()` never fired; only an action
     of pure literals fired (on a normal exit AND on an unhandled throw). So
     the teardown is GENERATED with the root baked in, one block per root.
  2. module auto-loading does not work at exit, so `Get-CimInstance` - the
     process query every other helper here uses - is dead there. The block uses
     `Get-Process`/`Stop-Process`, which are core.
  Both were found by probe, not by reading: the first two versions of arm C
  failed with a handler that looked correct.
- `lib\TestDesktop.ps1`'s own exit hook guarded on "is ANY PowerShell.Exiting
  subscriber armed", which this new handler would have satisfied - silently
  disarming the T179 topmost net for any script that dot-sourced HarnessLeak
  first. Its guard is now a flag of its own.
