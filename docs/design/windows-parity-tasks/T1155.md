# T1155 - The fork-identity reproduce count erodes as this branch edits the files it measures

## In plain terms

Nothing a user of the terminal can see. This is one of the checks that has to
be green before the Windows work can become the project's main line, and it is
currently red - so every turn's final check refuses to pass until somebody
looks at it.

## Summary

`test\win32\fork-identity.ps1` section C measures how many of the 52 "U" files
the identity overlay reproduces on its own: it checks the fork point out at
`063ac3ecc`, runs the overlay, and counts the files that come back
byte-identical to HEAD. C4 asserts that count against a hardcoded floor,
`$ReproBaseline = 28` (line 73).

Measured 2026-08-23 on `users/dzearing/windows-amd64` at 155ac6b27:

```
reproduced exactly: 25 of 52
FAIL C4 at least 28 of the U-files reproduce from the fork point reproduced=25 baseline=28
```

Every other section is green, including D (the negative control that fires each
rule at the upstream form) and E (the must-survive fixture). That is the tell:
the RULES are fine. What moved is HEAD. The metric compares the overlay's output
against today's tree, so every legitimate edit this branch makes to one of the
52 files subtracts from it, and the number can only fall over time. A floor that
erodes on its own is a gate that goes red for a reason nobody can act on, which
is the state it is in now.

The question this task has to answer is what C4 should measure instead. Two
shapes worth weighing: compare the overlay's output against the fork point's own
overlaid form (so it measures the RULES and is stable under branch drift), or
keep the HEAD comparison but classify a mismatch as "the file has since been
edited" versus "a rule stopped firing" and assert only the second.

Found while running the harness `guard-due` reported due at the top of T1131's
turn; T1131 committed with `-NoGuardDue` naming this task.
