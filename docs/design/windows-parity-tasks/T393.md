# T393 - Mac viewer-only windows stay pinned at their opening title while Windows now follows the document (T383)

## Summary

A divergence created by T383, in the direction the parity rule still calls a
defect: **Windows is now ahead.**

`docs/design/viewer-panes.md` lists, under "Known v1 gaps (accepted)":

> web page titles don't retitle viewer-only windows (pinned at open)

On win32 they do. A viewer pane's title flows through the ordinary T92 chain -
pane -> tab -> titlebar - so a `+new-window --view=https://…` window's caption
follows `document.title` as the page reports it. There is no separate
"viewer-only window" case on this side: the window title is the active tab's
title, and the active tab's title is its focused pane's, whatever kind of pane
that is.

## Details

CLAUDE.md's standing rule is that a feature living on one platform and not the
other is the divergence this project does not ship - and it does not carve out
an exception for the platform that happens to be behind. So this is a real row,
not a note.

Two ways to close it, and the Mac seat owns the choice:

1. **Follow the document** (what Windows does). `ViewerView` already observes
   `\.title` and updates the pane's `title`; what is missing is the leg that
   pushes it up to a viewer-only window's own title. If the original pin was a
   deliberate anti-flicker decision, that reasoning is not recorded anywhere and
   should be.
2. **Decide the pin is right and put it back on Windows.** Cheap to do - the
   win32 side would have to special-case a single-viewer window in
   `updateWindowTitle`, which is a carve-out where there is none today, so this
   needs a stated reason rather than symmetry for its own sake.

Filed as `seat: mac` because only the Mac seat can see which behaviour reads
better in the real app, and because the evidence for option 1 (is there a
flicker?) can only be gathered there.

*Validation:* whichever way it goes, `docs/design/viewer-panes.md`'s "known v1
gaps" list stops claiming a gap that only one platform has - and the behaviour
is asserted on both seats: on Mac in the viewer tests, on Windows in
`test\win32\viewer-panes.ps1` (which already reads a viewer window's caption
back with `GetWindowTextW`).
