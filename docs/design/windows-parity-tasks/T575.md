# T575 - A keybind on F10 never fires on Windows: the menu system eats the key before keyCallback

## In plain terms

If you bind something to the F10 key on Windows, pressing F10 does nothing —
it opens the menu instead, and it does that even though you told Ghoztty the
key meant something else. There is no error and nothing in the config warns
you; the key simply has no effect. The same binding works on a Mac. Worse, the
menu it opens then takes every key you press next, so the keyboard feels stuck
until you press Escape.

## Goals

- [x] A user-configured F10 binding fires, and does not open the menu
- [x] F10 with NO user binding still opens the menu (the Windows convention
      this rule exists for)
- [x] The same for a sequence or key table whose trigger is F10
- [x] Acceptance coverage on the box

## Validation criteria

- [x] `test\win32\menu-f10-binding.ps1` ALL PASS (14 assertions): a bound F10
      opens a tab and no menu (A), an unbound F10 still opens the menu and no
      tab (B), `f9>f10` completes as a sequence (C), and a key table's `f10`
      fires (D)
- [x] `-NegativeControl` FAILS - it demands that a bound F10 open the menu, and
      the run scores `1 FAILED / 13 passed`
- [x] `menu_activation.zig`'s unit tests cover the predicate itself: the
      binding declines the key, and it never RESURRECTS an F10 the modifier,
      autorepeat or alternate-screen narrowings already declined
- [x] `scripts\floor-lane.ps1 -Lane all` green (lib compile + both zig test
      lanes + test-agent)
- [x] P1-P3 acceptance scripts ALL PASS

## Summary

Found while building T446 (2026-08-07). `Surface.handleKeyEvent`
(`src/apprt/win32/Surface.zig`) runs `trackMenuActivation(vk, lparam, action)`
and **returns** when it claims the key, before `keyCallback` is ever reached:

```zig
// F10 / a lone Alt press open the menu system (T190). Runs before the
// key reaches the terminal so the disarm bookkeeping sees every key.
if (self.trackMenuActivation(vk, lparam, action)) return;
```

So a `--keybind=f10=…`, or a sequence/table whose trigger is F10, silently
never dispatches. The first draft of `test/win32/key-state-pill.ps1` used
`f9>f10` for exactly the reason a user would: F-keys are unmodified and
otherwise inert. The result read as "the pill stops updating after the second
key" for the whole rest of the run — the menu had swallowed everything after
it.

## Details

The menu rule is right by default: F10 opens the menu bar on Windows, and an
app that ignored that would be the odd one out. What is wrong is that it is
UNCONDITIONAL. The precedent for the fix is already in this file — the
viewer's Ctrl+R / Ctrl+D override their global bindings **only while a viewer
pane holds focus** (T161). The same shape applies: let the config win where the
user has stated an intent, and keep the platform default everywhere else.

Sketch: ask the live keybind set whether this event has a binding (the same
`getEvent` lookup `maybeHandleBinding` will do, or `Config.keyboardShortcut`'s
existing reverse lookup) before letting `trackMenuActivation` claim it. The
lookup has to consider the ACTIVE key table and any in-flight sequence, not
just the root set — an F10 that is the second half of a chord is exactly the
case that must not open a menu. Note also that a lone Alt press goes through
the same gate, and Alt is a modifier: whatever is done here must not make
alt-menu access conditional on a binding that does not exist.

Alternative worth weighing in the fix: keep the interception but make it
conditional on `menu-key`-style config rather than on the binding set, if the
lookup turns out to be too hot for the key path.

*Validation:* an acceptance script that binds `f10=clear_screen`, presses it,
and asserts the action dispatched AND no menu opened; plus the inverse (no
binding ⇒ the menu opens), driven the way `test/win32/menu-bar.ps1` drives the
menu. Both `zig build test` lanes, `zig build test-agent`, and P1–P3 stay
green.
