# T292 - Activity Monitor: the gauges and table freeze while a modal action dialog is open

## In plain terms

Open the Activity Monitor, pick a process, hit Kill — and while the "are you
sure?" box is up, the CPU and memory charts stop moving and the process list
stops updating. They only come back once you answer it. Take a moment to read
the confirmation and the panel behind it is quietly stale, which is exactly the
moment you want the numbers to be honest. After this, the panel keeps measuring
and redrawing behind the dialog, the way it does on the Mac.

## Goals

- [x] The Kill confirmation no longer stops the panel from sampling.
- [x] The New Process dialog does not either.
- [x] The process names the confirmation and its failure report quote survive
      the panel refreshing underneath them.
- [x] A refresh behind the dialog cannot steal the keyboard off it.
- [x] Covered by unit tests plus an on-box arm that watches the panel poll with
      the dialog open.

## Summary

A deliberate T286 divergence, filed rather than left implicit.
`ActivityMonitor.modal` suspends snapshot adoption (and `kickSample`) for the
whole life of the Kill confirmation and the New Process dialog, so the CPU/Memory
trend charts stop advancing and the table stops updating while either is up. On
Mac the sheet is presented over a model that keeps polling, so the charts keep
drawing.

## Details

The guard exists for a real hazard, and any fix has to keep solving it: the
confirmation quotes **row names borrowed from the current snapshot**
(`actions.targetsFor` points `Target.name` into `snap.rows`), and the dialogs run
a nested pump — so without the guard a poll landing mid-dialog would `destroy`
the snapshot out from under the string the dialog is displaying. `modal` was the
smallest correct answer; it is not the only one.

The cheaper-to-live-with alternative is to **copy** what the dialog needs instead
of borrowing it: marshal the target names into a fixed stack arena before the
dialog opens, and let adoption continue. Then the only remaining question is
cosmetic — whether a table that re-sorts under an open confirmation is
*desirable*, which Mac answers yes.

Sizing note: the arena has to be bounded (a selection can be up to
`remote_proc.default_limit` = 512 rows), and a name that does not fit must
degrade to `""` — which the failure text already handles, listing such a target
as `PID <n>`.

Low priority: the visible symptom is a chart that pauses for the second or two a
dialog is open.

## Validation criteria

- [x] `ActivityMonitor.modal` is gone — no code path suspends adoption for a
      dialog. Verified by `grep modal src/apprt/win32/ActivityMonitor.zig`: two
      prose mentions remain, no field and no guard.
- [x] `activity_actions.copyNames` unit tests: a copied batch reads back
      correctly after the source buffer is overwritten, an over-long name
      degrades to `""` (never truncated), overflow skips only what did not fit,
      and `name_arena_bytes` holds a full 512-row selection. Five tests, green
      in the `none` lane.
- [x] Both `zig build test` lanes plus `zig build test-agent` green
      (`scripts\floor-lane.ps1`); P1-P3 ALL PASS.
- [x] `test/win32/activity-monitor.ps1` ALL PASS (115 assertions): the new I.1a
      arm watched the panel log two more state lines with the confirmation open
      (`45 -> 47`), and the existing "the confirmation names the process and its
      pid" / "kill result total=1 killed=1 failed=0" / "CONFIRMING really
      terminates the process" assertions still passed with polls deliberately
      landing under the open dialog — those are the proof the batch did not
      dangle.
