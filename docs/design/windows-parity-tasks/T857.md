# T857 - Discriminate hardware from software for the T443 ghost: A/B the crash-prone lane with Turbo Boost disabled during the next active window

## In plain terms

The test suite crashes at random every few days, in a different place every
time, and two weeks of instrumented hunting has not found a software cause.
The 2026-08-15 crash dump shows the processor jumping into the middle of an
instruction in code that could not legally run — which software bugs do not
do, but a known defect in this machine's CPU model (Intel i9-13900K
"Vmin shift" degradation) does. This task is the experiment that tells the two
apart: run the same tests with the CPU's boost clocks disabled, and if the
crashes stop, the machine is the bug, not the code.

## Summary

T443's 2026-08-15 occurrence (deep read in T443.md) shows execution-state
corruption — RIP mid-instruction in a statically unreachable block, rax
inconsistent with the fault site, all memory sane — on an i9-13900K, the SKU
affected by Raptor Lake Vmin-shift degradation. T449 "eliminated" hardware
with a steady all-core SHA stress, but that load shape holds clocks and
voltage flat; the instability manifests during bursty boost/voltage
transitions, i.e. exactly the compile-shaped build-runner condition every
T443 sighting has (and its ~200 standalone clean runs lack). Microcode 0x12F
only prevents further degradation; it does not heal a degraded part.

**The experiment** (only informative while the ghost is ACTIVE — a cluster of
occurrences in one morning, like 2026-08-14's 5-in-21; on a quiet box a
clean run says nothing):

1. Baseline: run `floor-lane.ps1 -Lane agent` (or whichever lane is firing)
   repeatedly via `test-binary-soak.ps1` until ≥2 crashes land; record the
   rate.
2. Disable boost — needs an elevated shell:

   ```powershell
   powercfg /setacvalueindex scheme_current sub_processor PROCTHROTTLEMAX 99
   powercfg /setactive scheme_current
   ```

   (99% max processor state disables Turbo Boost; cores hold base clocks.
   Verify with Task Manager / `Get-Counter '\Processor Information(_Total)\% Processor Performance'` < 100.)
3. Re-run the same lane the same number of times under the same box load.
4. Restore: same commands with `100`.
5. Compare rates. Boost-off collapsing the rate = hardware; the remedy moves
   to BIOS (raise Vcore / Intel Default Settings profile) or RMA, and T443's
   whole software hunt is re-read. Rate surviving boost-off = hardware drops
   back down; resume the software hunt with the page-base sweep.

If elevation is not available to the loop when the window opens, surface the
two powercfg commands to the user via the pane banner and the log rather than
losing the window.

Secondary checks worth doing in the same window (cheap, no reboot):
- `Get-WinEvent` WHEA-Logger for processor/cache/TLB errors (ids other than
  the known corrected-PCIe id 17 noise).
- Note CPU package temps/clocks during a crashing run vs a clean one if a
  sensor CLI is available.

Out of scope: MemTest86 / BIOS changes themselves (need reboot + the user);
this task's deliverable is the measurement and the verdict, plus a decision
filed for the user if the verdict is hardware.

## Validation criteria

- [ ] An active window was caught and both arms (boost on / boost off) ran
      with recorded run counts and crash counts each.
- [ ] The rates and the verdict (hardware / not hardware / inconclusive) are
      appended to T443's ARMED-WATCH LOG with the raw soak summary lines.
- [ ] Power settings restored to 100% afterwards (verified with
      `powercfg /query` output).
- [ ] If the verdict is hardware: a decision filed for the user naming the
      BIOS/RMA options; if not: T443 re-armed with the software sweep as the
      lead instrument.
