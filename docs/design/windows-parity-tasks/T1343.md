# T1343 - Dragging a splitter is slow and steppy - measure the drag frame pipeline, then fix it

## In plain terms

Grab the line between two panes and drag it. On the Mac the panes follow the
mouse; here they lag behind it in visible steps, and the more panes are open
the worse it gets. Nothing is broken - it just feels heavy, and the user said
so directly.

## What the user reported (2026-09-04)

> "the windows version is so much slower than the mac version. like resizing
> panes is janky and slow ... when I resize panes, they're slow to paint. It
> feels so unpolished."

Split out of T1324, which also carried the hero-mode banner artifact (fixed
there) and the banner flicker (T1344) and the layered-popup fan-out (T1345).

## The lead, which is a lead and not a conclusion

`Surface.zig` `setSize`: during a live resize or a live split-layout the UI
thread *blocks* on the renderer presenting a frame at the new size.

```zig
if (self.in_live_resize or self.parent_window.in_live_layout) {
    ...
    _ = w32.WaitForSingleObject(event, 16);
}
```

The reason is real - without it DWM stretches stale framebuffer content and you
see flicker - but the cost is that every mouse-move during a drag serialises
the UI thread against the render thread **once per affected surface**. Four
panes is up to ~64 ms per mouse move, about 15 fps of drag. macOS has no
equivalent stall: CoreAnimation composites the layer tree, so a resize does not
need the app to wait for a frame.

Note the hero path already sidesteps this a different way: `layoutHero` is
called outside `in_live_layout` and its leaf resize is throttled to 80 ms
(`HERO_DRAG_RESIZE_MS`). That is a second data point about what the wait costs,
and a third shape to measure.

## How to approach it

**Measure first, and keep the numbers**, or the work cannot be shown to have
helped:

- Frame time during a splitter drag at 1, 2, 4 and 8 panes. The per-surface
  blocking predicts linear degradation with pane count; if it does not degrade,
  the lead above is wrong and the real cause is elsewhere.
- The same measurement on the Mac build, since "worse than Mac" is the actual
  complaint.

Then fix in the order the numbers say. Unproven candidates: cap or remove the
per-surface wait during drags (and find another answer to the stale-content
flicker it exists to prevent - that is a real problem, not a legacy one);
coalesce mouse-move-driven layout to one update per frame instead of one per
message; wait once for the whole layout pass rather than once per surface.

**Do not regress the flicker the current code prevents.** A change that makes
dragging smooth and brings back stretched stale content is not an improvement.

## What the measurement said (2026-09-04)

Method, so it can be re-run: `test\win32\drag-perf.ps1` launches an isolated
debug build on the background test desktop, splits it to N panes, drives the
root divider with posted mouse messages, and reads the app's own per-drag
summary (`Window.reportDragCost`, gated on `GHOZTTY_PERF`). Both shapes of the
frame wait are measured on ONE build: `GHOZTTY_DRAG_SERIAL_WAIT=1` puts the
per-pane wait back. Numbers are means over ~25 moves, one mouse move end to
end on the UI thread.

| panes | shape | per move | frame wait | placement | overlays | drag fps |
|---|---|---|---|---|---|---|
| 2 | per-pane | 6.2 ms | 1.6 ms | - | 0.5 ms | ~160 |
| 4 | per-pane | 13.5 ms | 4.2 ms | - | 2.0 ms | ~74 |
| 8 | per-pane | 20.0 ms | 8.8 ms | 17.0 ms | 2.9 ms | ~49 |
| 2 | batched | 6.3 ms | 0.6 ms | - | 0.7 ms | ~158 |
| 4 | batched | 12.4 ms | 1.3 ms | - | 2.5 ms | ~80 |
| 8 | batched | 15.8 ms | 2.6 ms | 9.7 ms | 3.3 ms | ~63 |

(Placement is `BeginDeferWindowPos`..`EndDeferWindowPos`, which dispatches every
pane's `WM_SIZE`; on the per-pane shape the waits happen inside it, which is why
its 17.0 ms contains the 8.8 ms. The panes' own `sizeCallback` — grid reflow,
renderer viewport, SIGWINCH — is 0.02 ms and is not where anything goes.)

**The lead was right and incomplete.** The per-surface wait is real, it scales
exactly as predicted (one wait per resized pane, 8 at 8 panes), and removing the
serialization takes a third off the worst case. It is not the majority of the
bill: at 8 panes the batched drag still spends 9.7 ms placing panes and 3.3 ms
re-gluing the dim/banner overlays. That is **T1345's** half of the report — the
layered-popup fan-out — and it now has numbers instead of a hypothesis.

**One caveat, stated rather than buried.** On the background test desktop
presents are not throttled by the compositor, so a wait usually returns in well
under its 16 ms timeout (`timeouts=0` in every run). On a real desktop, where a
present waits for vsync, each of those 8 waits can cost a full frame — 128 ms
per mouse move at 8 panes, against 16 ms flat after the fix. That is why the
harness asserts the wait COUNT and only records the clock: the count is a
property of the code, the clock is a property of the machine.

## What changed

`Window.layoutSplits` opens a frame-wait batch for the pass;
`Surface.handleResize` hands its frame event to the batch instead of waiting for
itself; `Window.endFrameWaitBatch` waits once with
`WaitForMultipleObjects(bWaitAll)` on the same 16 ms budget. The anti-flicker
guarantee is unchanged — the UI thread still does not return to the pump until
the panes have presented at their new size — it just costs one frame for the
pass instead of one per pane. `test\win32esize-flicker.ps1` is the check that
the guarantee survived.

- [x] A perf harness in `test/win32/` holds those numbers, so a later change
      that makes dragging slower again is caught rather than felt —

      drag path makes it due.
- [x] Resizing panes still shows no stale or stretched content -
      `test\win32esize-flicker.ps1` green over this build.
- [x] The remaining gap is stated honestly: at 8 panes a drag still costs

      than guessed at.
