# T1343 - Dragging a splitter is slow and steppy - measure the drag frame pipeline, then fix it

## In plain terms

Grab the line between two panes and drag it. On the Mac the panes follow the
mouse; here they lag behind it in visible steps, and the more panes are open
the worse it gets. Nothing is broken - it just feels heavy, and the user said
so directly.

## What the user reported (2026-09-04)

> "the windows version is so much slower than the mac version. like resizing
> panes is janky and slow ... when I resize panes, they're slow to paint. It
> feels so unpolished."

Split out of T1324, which also carried the hero-mode banner artifact (fixed
there) and the banner flicker (T1344) and the layered-popup fan-out (T1345).

## The lead, which is a lead and not a conclusion

`Surface.zig` `setSize`: during a live resize or a live split-layout the UI
thread *blocks* on the renderer presenting a frame at the new size.

```zig
if (self.in_live_resize or self.parent_window.in_live_layout) {
    ...
    _ = w32.WaitForSingleObject(event, 16);
}
```

The reason is real - without it DWM stretches stale framebuffer content and you
see flicker - but the cost is that every mouse-move during a drag serialises
the UI thread against the render thread **once per affected surface**. Four
panes is up to ~64 ms per mouse move, about 15 fps of drag. macOS has no
equivalent stall: CoreAnimation composites the layer tree, so a resize does not
need the app to wait for a frame.

Note the hero path already sidesteps this a different way: `layoutHero` is
called outside `in_live_layout` and its leaf resize is throttled to 80 ms
(`HERO_DRAG_RESIZE_MS`). That is a second data point about what the wait costs,
and a third shape to measure.

## How to approach it

**Measure first, and keep the numbers**, or the work cannot be shown to have
helped:

- Frame time during a splitter drag at 1, 2, 4 and 8 panes. The per-surface
  blocking predicts linear degradation with pane count; if it does not degrade,
  the lead above is wrong and the real cause is elsewhere.
- The same measurement on the Mac build, since "worse than Mac" is the actual
  complaint.

Then fix in the order the numbers say. Unproven candidates: cap or remove the
per-surface wait during drags (and find another answer to the stale-content
flicker it exists to prevent - that is a real problem, not a legacy one);
coalesce mouse-move-driven layout to one update per frame instead of one per
message; wait once for the whole layout pass rather than once per surface.

**Do not regress the flicker the current code prevents.** A change that makes
dragging smooth and brings back stretched stale content is not an improvement.

## Validation criteria

- [ ] Drag frame time is recorded before and after, at several pane counts,
      with the method written down so it can be re-run.
- [ ] A perf harness in `test/win32/` holds those numbers, so a later change
      that makes dragging slower again is caught rather than felt.
- [ ] Resizing panes still shows no stale or stretched content - the
      regression the current frame wait exists to prevent.
- [ ] The remaining gap to the Mac build is stated honestly rather than left
      as an impression.
