# T469 - An OPEN the agent refuses should fail fast and say why, instead of a blank pane after a 10s timeout

## In plain terms

When the background terminal service cannot start a shell for a new pane, the
pane comes up completely blank and stays that way. Nothing on screen says what
went wrong, and each pane sits for ten seconds before giving up - so restoring a
window full of panes can spend minutes doing nothing visible. It should say what
happened, in the pane, straight away.

## Goals

- [x] A refused OPEN fails in well under a second, not after a 10s timeout
      (measured: 150 ms, arm A of `test/win32/agent-open-refused.ps1`)
- [x] The pane says what happened, in the pane, in plain words (the cap, the
      counts, and what to do about it — and no longer a timeout)
- [x] An older agent and an older app both still work across the change (arm B
      on box: the old road, 10132 ms, link intact; plus both skew directions in
      the `negotiate` and server unit tests)

## Summary

**D8 resolved 2026-08-05: the user picked "Fold T469 back into T278"** — i.e.
the split into a deferred P1 was the wrong call, and this reporting work
carries T278's own P0 urgency. T278 is already shipped, so this task stays the
vehicle, at P0.

The second half of T278. T278 fixed the *cause* the user actually hit (dead
tombstones filling the session cap); this is the *reporting*, which is still
silent for every other reason an `OPEN` can be refused - a genuinely full agent
(256 LIVE sessions), an out-of-memory agent, a spawn that fails.

`Server.handleOpen` (`src/remote/agent/server.zig`) simply `return`s when the
spawn or `SessionTable.create` fails. No reply frame is defined for "I will not
open this", so the client's `rpcCall` for `.opened` parks on
`rpc_open_timeout_ns` (10 s, `src/remote/connection.zig`) and then fails with a
bare `error.Timeout`. Worse, by-type OPEN RPCs are serialized on
`open_rpc_mutex`, so N panes cost 10 s **each, in turn**.

## Evidence (MEASURED on box 2026-08-04, debug build, before the T278 fix)

Seeded 256 dead tombstones into the debug agent's `sessions.json`, launched the
debug app, waited 25 s, then read the pane:

| probe | result |
| --- | --- |
| `+list --json` leaf | `"pid": 0`, `"title": ""`, `"tty": ""` |
| `+read` on that pane | **empty** - not one byte |
| app stderr | `warning(io_thread): error in io thread err=error.Timeout` |
| app stderr | `warning(io_thread): abrupt io thread exit detected` |

So `Thread.zig`'s error-painting `catch` (the `else =>` arm, "error starting IO
thread: {} ... This terminal is non-functional") **did** run, and the pane still
shows nothing. Whatever it printed does not survive to what `+read` sees. That
is a second, independent defect worth pinning down: the generic bring-up error
path is invisible on win32.

T278 already added the agent-side half - `handleOpen` now logs
`OPEN refused: <err> (live=N/256 dead=M/256)`. What is missing is telling the
*client*.

## Approach (worked out under T278, not implemented)

Additive protocol evolution, per the agent-contract rules in CLAUDE.md - a new
opcode is a **fatal framing error** to a peer that does not know it
(`protocol.zig` says so at `session_cpu_sub`), so it MUST be capability-gated:

1. `protocol.zig`: `open_failed = 0x06` (A→C, `{reason, detail}`) +
   `capability.open_failed` + a `Negotiated.open_failed` flag, following exactly
   the `close_session` / `sessions_push` pattern already in that file.
2. `server.zig`: on a refused `OPEN`, send `open_failed` **only when the
   capability was negotiated**; otherwise behave as today (silence → the old
   client times out, which is the graceful degradation the rule asks for).
3. `connection.zig`: `deliverRpcReply` accepts `.open_failed` as a terminal
   reply for a parked `.opened` slot and surfaces a distinguishable error
   (`error.OpenRefused`) carrying the reason.
4. `termio/Remote.zig` + `termio/Thread.zig`: map that error to a real pane
   message. `src/termio/session_notice.zig` is the pattern to copy - a pure,
   unit-testable formatter with both carriers (in-stream text folded into
   scrollback, plus an OSC 7778 banner), already proven to survive a ConPTY
   shell's startup repaint.

Skew matrix to keep honest: new agent + old app (app never advertises the
capability → agent stays silent → today's timeout), old agent + new app (agent
never sends it → same). Neither garbles nor wedges.

## Validation criteria

- [x] An agent forced to refuse brings the pane up with a readable message in
      **under 2 s**, and `+read` returns that message.
      *Verified:* `test/win32/agent-open-refused.ps1` arm A, with the agent
      capped at one live session via `GHOSTTY_AGENT_MAX_SESSIONS=1` so the
      refusal is a genuine `error.TooManySessions` rather than an injected
      fault. Message at **150 ms** (the first poll).
- [x] The message names the CAUSE, not the symptom.
      *Verified:* same arm — it contains "maximum number", "Close some panes"
      and the agent's own `live=1/1` counts, and contains neither "Timeout" nor
      "exhausting a system resource".
- [x] A build with the capability disabled on one side still brings the pane up
      the old way (timeout + non-functional message) - no hang, no garbling.
      *Verified:* arm B, using the new `GHOSTTY_AGENT_SUPPRESS_CAPS=open_failed`
      seam so one binary advertises an older agent's HELLO. Fallback message at
      **10132 ms** (the untouched `rpc_open_timeout_ns`), it is the generic text
      and not the new one, and `+list` still answers afterwards.
- [x] Both skew directions are asserted, not just the one reproduced on box.
      *Verified:* `negotiate: open_failed capability is the intersection of both
      HELLOs` (none lane) and `OPEN refused: a client that did not negotiate
      open_failed gets today's silence` (agent lane), the latter proving silence
      by ordering against a request the agent WILL answer rather than by waiting.
- [x] The zig floor lanes + `test/win32/agent-session-cap.ps1` stay green.
      *Verified:* `scripts\floor-lane.ps1 -Lane all` → none PASS, win32 PASS,
      agent PASS. (The first agent run FAILed on the WebView2 host-floor test at
      342 s, overlapping a process kill I ran mid-lane; the clean re-run passed
      in 190 s.)

## Correction to the Evidence above

The "second, independent defect" this file claims — that the generic bring-up
error path is INVISIBLE on win32 — **does not reproduce** on the current build.
Measured 2026-08-09 against the installed release (28bbcf8ba): a forced spawn
failure (`--shell` pointing at a nonexistent exe) paints `error starting IO
thread: error.Timeout … This terminal is non-functional` and `+read` returns
all 274 bytes of it. The 2026-08-04 observation predates T181/T193, which
changed what `+read` does with a pane in an unusual state.

That is why this task did NOT build a new carrier for the message: the existing
failure paint works, it was simply saying the wrong thing. `Backend.bringUpNotice()`
lets a backend pre-empt it with something true.
