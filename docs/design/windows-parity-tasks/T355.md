# T355 - Agent has no test that a session's reported pid is a real OS pid (Windows returned the HANDLE for years)

## Summary

`test-agent` never checks that a spawned session's reported pid names a real
process, which is how the Windows arm shipped the process HANDLE instead.

## Details

Found while doing T41. `PtySpawner.spawnFn` surfaced
`@intFromPtr(pc.pid)` on Windows — `posix.pid_t` is a HANDLE there — and said
so in a comment (*"the OS process id is not separately tracked"*). That value
travelled the wire as `pid` into `+sessions`, `+list --json`'s `pid`, and
`Remote.child_pid`. It is not a pid in any process: the T41 acceptance script
caught it as `shell pid 492 names a live process -> FAIL`. Fixed in T41 with
`GetProcessId(pc.pid)`.

The gap that let it live: every existing assertion on `pid` checks that it is
non-zero or that it round-trips (`server.zig` `rp.value.pid != 0`,
`expectEqual(1001, op.value.pid)` against a FakeSpawner) — none asks the OS
whether the number means anything. `test-agent` already runs real-pty tests, so
the check is cheap and belongs in that lane rather than only in the on-box
script that happened to find it.

*Validation:* a `test-agent` case that spawns a real pty child and asserts the
reported pid resolves to a live process (Windows: `OpenProcess`/Toolhelp32
lookup; POSIX: `kill(pid, 0)`), and that it is NOT equal to the handle value.
Must fail against the pre-T41 conversion.

## In plain terms

When you ask a persistent session what process is running in it, it tells you a
number. On Windows that number used to be meaningless — it named no program on
the machine at all, so anything that tried to look the session's shell up came
back empty-handed. That was fixed a while ago; what was missing is anything that
would notice if it broke again. This adds the check: spawn a real shell, then ask
Windows itself whether the number we report actually names something that is
running.

## Goals

- [x] The Windows handle-to-pid conversion lives in ONE named place instead of
      being copied inline into two spawn paths
- [x] A test that asks the OS directly whether a reported pid names a live
      process, independent of the process-table walk the existing test uses
- [x] That test demonstrably goes red against the old, broken conversion
