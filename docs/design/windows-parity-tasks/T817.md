# T817 - A win32 diff pane has no next/previous-change or unified-vs-side-by-side controls

## In plain terms

A diff pane on Windows shows the changes, but you read it by scrolling. On the
Mac the pane's toolbar has two things this one does not: buttons that jump to
the next and previous change, and a switch between the stacked view and the
side-by-side one. Both already exist in the page itself — nothing is calling
them from Windows.

## Goals

- [ ] Next / previous change buttons in a diff pane's nav bar, stepping change
      blocks and rolling over into the adjacent file
- [ ] A unified ⇄ side-by-side toggle, with the choice remembered across panes
      and sessions the way Mac's `diffViewStyle` preference is
- [ ] The nav bar stays PINNED OPEN in a diff pane (Mac's rule: it carries the
      controls and shows the revspec)

## Evidence

The page half is already bundled and already reachable: `src/viewer/diff.js`
exposes `setStyle` and `nav`, and `viewer.js` re-exports both as
`window.__viewer.setDiffStyle` / `window.__viewer.diffNav`. T463 wired the
CONTENT path (listing + patch) and deliberately left the chrome: `ViewerPane`
holds `diff_style` as an in-session field with no control that changes it, and
`viewer_nav_layout.zig` lays out back / forward / reload / home / address with
no diff arm.

Mac's counterparts: `ViewerView.diffNav` / `diffViewStyle`, and
`ViewerNavigationBar.swift`'s diff controls. The pinning rule is
`ViewerView.navBarPinned` (`sidePanelLayout == .compact || feedbackOpen ||
isDiffMode`).

## Validation criteria

- [ ] `none`-lane geometry tests for the added nav-bar controls at 1.0/1.25/
      1.5/2.0 (the design-system rule for every win32 chrome number)
- [ ] An acceptance arm in `test/win32/viewer-diff.ps1`: pressing next-change
      moves the page (read back through the pane's own log or the live win32
      lane's DOM probe), and the style toggle survives a new pane
