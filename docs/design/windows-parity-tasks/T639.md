# T639 - Only the viewer nav bar's feedback button has a tooltip; back/forward/reload/home/contents have none

## In plain terms

The little buttons along the top of a viewer pane are icons with no words. On a
Mac, resting the pointer on any of them tells you what it does — and Home even
tells you where it would take you. On Windows only the newest button, the
feedback one, does that; the other five stay silent, so the only way to learn
what an icon means is to press it.

## Summary

T633 gave the win32 viewer nav bar its first tooltip (a `TTF_SUBCLASS` rect
tool on the feedback button, `ViewerNavBar.tipEnsure`/`syncTip`). That leaves
the strip INCONSISTENT: one of six buttons explains itself and five do not,
which is a defect by the design system's "one treatment per control class"
rule even though each button in isolation looks fine.

Mac labels every one of them (`ViewerSplitLeaf.swift`'s `WebChromeBar`):

| Button | Mac `.help(...)` |
|---|---|
| contents | "Show contents" / "Hide contents" (and the diff pane's "Show files" / "Hide files") |
| back | "Back" |
| forward | "Forward" |
| reload | "Reload" |
| home | `"Home — back to \(homeLocation)"` |

Home's is the interesting one: it names the DESTINATION, which is exactly the
question a Home button raises in a pane that has browsed away from where it
started.

## Details

The machinery already exists and is the fifth of a tooltip's worth of work, not
a new subsystem: `ViewerNavBar` owns a `tooltips_class32` popup, a `tip_text`
buffer and `syncTip`, all currently hard-wired to `Button.feedback` and
`tip_id`. What this task changes:

- One tool per PRESENT button rather than one tool for one button — the tool id
  can be the `Button` enum's tag, and `syncTip` becomes a loop that adds,
  re-rects and deletes as the strip's shape changes (the contents toggle and
  the feedback button both come and go, so "delete the tool when the rect is
  empty" is already the established half).
- Each tool's rect is the button's HIT box, as the feedback one already is.
- Text comes from a pure function next to the layout — `label(Button, ...)` —
  so the strings and the contents toggle's open/closed flip are unit-testable
  in the none lane rather than living inside the win32 paint code. Home's
  string needs the pane's `home_location`, which the bar does not hold today;
  push it the way `setWorktree` pushes the worktree.
- A disabled back/forward keeps its tooltip (Mac's `.help` survives
  `.disabled`): "why can I not press this" is the moment a label is worth most.

## Validation criteria

- [ ] Unit tests (none lane): the label for every `Button`, including the

      (and its behavior when the pane has no recorded home).
- [ ] On-box acceptance: each present button has a registered tool whose rect

      the feedback button outside a repo) has none. Extend
      `test\win32\viewer-worktree.ps1`'s existing nav-bar walk rather than
      standing up a second harness.
- [ ] The floor stays green: both zig lanes, `test-agent`, P1-P3,
