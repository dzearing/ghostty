# T250 - Hero/carousel divider ignores design system section 5: still 1 DIP with a bespoke accent hover

## Summary

Found while shipping **T233**, which brought the SPLIT divider into design
system §5 compliance (2 DIP, hover/drag shaded by `±HOVER_DELTA` in the
`icon_button.fillDelta` direction). The hero/carousel divider was not touched
and now disagrees with it on both counts, in the same window.

`src/apprt/win32/HeroCarousel.zig` (~line 137):

```zig
const line_w = @max(@as(i32, @intFromFloat(@round(1.0 * win.scale))), 1);
...
const div_color = if (win.hero_divider_hover or win.hero_divider_drag)
    w32.RGB(106, 106, 255)   // bespoke blue accent
else
    w32.RGB(96, 96, 96);     // bespoke gray, not split-divider-color
```

Three divergences from §5 and from the divider next door:

1. **1 DIP**, so it is the single physical pixel at 100%/125% that T233 exists
   to retire.
2. **A hardcoded accent-blue hover** instead of the shared shade rule. This is
   the "four controls, four answers to the same question" shape that
   `icon_button.zig` was written to end (T204) — a control inventing its own
   hover treatment is a defect even where it looks fine in isolation
   (CLAUDE.md, win32 design system section).
3. **It ignores `split-divider-color`** entirely, so a user who themes their
   dividers gets one themed and one not.

Note the hover MECHANISM here is already right (`hero_divider_hover` /
`hero_divider_drag` + a repaint) — this is about the numbers and the colors,
not about wiring, so it should be a small change.

## The fix

Route it through the same helpers T233 added rather than porting the values by
hand: `split_geometry.bandPx(scale)` for the width and
`split_geometry.dividerColor(rest, dark, hot)` for the color, with `rest` from
`split-divider-color` (same fallback) and `dark` from the pane background.
That is one source of truth for "what a divider looks like", which is the whole
point of putting it in the pure module.

Check whether Mac's hero divider really is accent-blue on hover before
flattening it — if it is, that is a deliberate Mac behavior and the right
answer may be to keep the accent but fix the width and the config plumbing.
Cite the Mac source line either way (the T240 lesson).

## In plain terms

Turn on hero mode and there are two dividers on screen: the thin line between
the big pane and the thumbnail strip, and the ordinary line between split
panes. They did not match. The hero one was half as thick — thin enough at
common display scales to read as a smudge rather than something you can grab —
and it ignored the divider color you set in your config, so theming your
dividers themed one of them and left the other gray. Now both are the same
thickness and both use your color. Grabbing the hero one still lights it up in
the accent color, which is what it does on the Mac too.

## Goals

- [x] Hero divider is `split_geometry.bandPx` wide — the same 2 DIP the split
      divider is, at every scale
- [x] Hero divider honors `split-divider-color`, with the same fallback and the
      same 3:1 contrast floor as a split divider
- [x] Hover/drag keeps the accent (Mac parity), verified against the Mac source
      rather than flattened by assumption
- [x] One source of truth for the configured color, read by both dividers
