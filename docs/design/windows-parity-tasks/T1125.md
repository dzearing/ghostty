# T1125 - soak.ps1 hangs waiting for the app to answer +list and is killed at the 10-minute cap

## In plain terms

The long-running stability check never got started: it waited for the app to respond and it never did, so it was cut off after ten minutes. That check is the one that covers hours-long sessions, which is exactly the way this terminal gets used.

## Summary

`test\win32\soak.ps1` was the only STALL in the T1094 full sweep - killed at the 600-second per-script cap:

```
stall  soak.ps1   Waiting for Ghoztty to answer '+list' (the app may still be starting up)...
```

Two readings, and they need to be told apart before anything is fixed:

1. **The app genuinely never answered.** That is a serious defect and the soak script caught it - the app failed to become addressable at all.
2. **The cap is simply too short for a soak script.** A script whose purpose is to run a long session may legitimately need more than ten minutes, in which case the runner needs a per-script timeout rather than one global cap, and this STALL is a measurement artefact.

The log ends on the waiting message with no further output, which slightly favours reading 1 - a script that was merely slow would normally have progressed past the launch.

Until this is resolved, long-session stability is unmeasured, and that is the property the standing quality bar calls out by name ('reliable and fast under long-context use').

## Where

- `test/win32/soak.ps1`
- `scripts/suite-run.ps1` - the global `-TimeoutSec` and the case for per-script overrides

## Answer: reading 2, and the log was misleading about it

The app answered. `temp\suite-runs\fwd1\soak.log` shows the killed run got past
`+list`, scored `PASS layout: 4 leaves in soak window`, and measured an 88ms
baseline `+read` - then entered its 30-minute sampling loop, which by design
prints nothing at all, and was killed at the 600s cap 20 minutes short of its
verdict.

The `Waiting for Ghoztty to answer '+list'` line that read as the end of the log
is a startup notice from the run's first seconds, printed on STDERR - and
`suite-run.ps1` folds stderr onto the END of the log and then scored the merged
file, so the last stderr line was quoted as the verdict. That is the whole
reason a measurement artefact came out looking like a hung app.

Nothing else in that sweep was close: the next-slowest of the 242 scripts was
under 300 seconds, so the 600s cap has ample headroom everywhere except here.

## Goals

- [x] Run `soak.ps1` alone, with no cap, and watch whether the app ever answers `+list`. - answered; evidence above, plus a full run through the runner
- [x] If it never does, that is the defect - chase it as a launch/addressability failure. - it does, so this arm does not apply
- [x] If it just needs longer, give `suite-run.ps1` a per-script timeout - a `# suite-timeout-sec: N` declaration read out of the script itself, with `-MaxTimeoutSec` to bound declarations for a deliberately quick pass
- [x] Record the soak's real runtime so the suite's total is honest.

## Validation criteria

- [x] which of the two readings it is, recorded here with evidence - reading 2, from the killed run's own log
- [x] `soak.ps1` completes and produces a verdict line - run through `suite-run.ps1 -Include soak.ps1` against the HEAD staging release
- [x] `suite-run.ps1` supports a per-script timeout and uses it - sections N1-N13 of `test\win32\suite-run.ps1`: declaration beats the global cap, the row records which cap it was held to, `-MaxTimeoutSec` bounds it, an undeclared script is unaffected, a garbled declaration falls back rather than becoming unbounded, and N12/N13 read the declaration off the shipping `soak.ps1`
- [x] a stalled script quotes what it SAID, not the stderr folded in after it - sections O1-O4
