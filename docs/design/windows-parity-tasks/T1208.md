# T1208 - Tell the user their terminal is being closed for the update

## In plain terms

When an update needs to close your open terminal, it now does that and opens it
again by itself. What it never does is say so. For a second or two your windows
vanish with no explanation, which reads like a crash rather than an update.

## Where this stands after T1204

The app registers for restart and exits when the Restart Manager asks, so the
mechanism works and needs no user decision. What is missing is the standard
`MsiRMFilesInUse` dialog, which names the applications that must close and
offers to close and restart them. That dialog comes from the package's UI
table, and the package is compiled by wixl (msitools), whose WiX subset does not
carry the standard UI libraries - so this is a real question about how the
installer is built, not a property to set.

## Options to weigh

- Author the minimal UI table by hand (`FilesInUse` / `MsiRMFilesInUse` dialogs)
  and verify it survives wixl, the way T1176's launch actions are read back out
  of the compiled MSI.
- Say it somewhere of ours instead: the in-app updater already owns its own
  dialog and could name what it is about to close, which covers the path most
  upgrades take.
- Decide the silent close is right for a terminal and only make the RETURN
  visible (a first-run line in the reopened window saying what version it is
  now, which pairs with T1205).

## Validation criteria

- [ ] An upgrade over a running Ghoztty tells the user, before or immediately
      after, that the terminal was closed and reopened for the update.
- [ ] Nothing about that message blocks an unattended or silent install.
- [ ] Whatever surface carries it is read back from the shipped artifact rather
      than asserted from its source.
