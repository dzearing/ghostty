# T745 - Banner table columns truncate instead of using full pane width (table appears capped at ~50% width)

## In plain terms

The status banner above a terminal pane showed a line of text that stopped
around the middle of a very wide window, ending in "...", with the whole right
half of the row empty — as if the banner refused to use the space it had. It
turned out the banner was drawing exactly the text it was handed: the script
that keeps that banner up to date was cutting the sentence off at 100
characters before Ghoztty ever saw it. The cut is now made by the banner
itself, which knows how wide the pane is, so a long line fills the row and
wraps instead of stopping halfway. Ghoztty also gained a check that measures
how far a table's text actually reaches, so a future change that really did
squeeze a column to half the pane would be caught.

## Goals

- [x] Reproduce the reported screenshot and find where the truncation is made
- [x] Stop truncating the banner text before the pane's width is known
- [x] Measure — not assume — that a banner table's value column uses the pane
      width, with a control that fails when it does not

## Summary

Reported interactively 2026-08-11 with a screenshot of a pane banner rendering a
markdown pipe table (the tracker session's status banner: rows `Prompt` /
`Status`). The long cell text ("Read C:/Users/David/AppData/Local/Temp/…")
is tail-truncated with an ellipsis while roughly half the pane's width sits
empty to the right of it — the truncation fires long before the content column
has consumed the available width, as if the table's total width were capped at
~50% of the pane rather than derived from the pane's full content width.

Expected per CLAUDE.md's banner contract: "Column widths derive from the pane's
current width" — a cell should word-wrap (up to the 3-wrapped-line cap, then
ellipsize) only after the column has actually been given the pane's available
width. A cell truncated at half-width is neither wrapping nor honoring the
pane width.

Suspect area: the win32 banner table layout in `banner_layout.zig` (column
width distribution vs. `contentWidth`) — check whether the content column's max
width is being computed from the wrong base (e.g. half the pane, a stale width,
or a per-column cap that ignores unused sibling-column slack).

## Finding: the renderer was innocent — the text arrived pre-truncated

The suspected area is correct code. `banner_layout.columnWidths` already hands
every pixel the narrow label column does not need to the wide value column, and
a capture of the exact reported shape proves it end to end: in a 1926px pane,
the same two-row table renders its value across the **full** content width and
wraps, while the reported cell stops near the halfway mark **because the string
itself ends there**. The ellipsis in the screenshot is not Ghoztty's tail
truncation — it is the literal `...` that
`~/.claude/scripts/ghoztty-banner.sh`'s `prompt-hook` appends after cutting the
auto-seeded prompt to 97 characters, before `+set-banner` is ever called.

A character count cannot know how wide a pane is, so it truncates before the
width is used; on a wide pane 97 characters run out around the halfway mark,
which is exactly the symptom. The cap is now 400 characters (a bound on what
goes in the state file, past any width a pane can show), leaving the decision
of where text stops to the renderer — which word-wraps to the pane's content
width and only then ellipsizes, at 3 wrapped lines.

Two side effects of the fix worth naming: a long prompt now costs up to 3
display lines in a narrow pane where it used to cost 2, and — the reason this
was hard to see — nothing in the suite measured a table's HORIZONTAL extent.
Every T123 oracle in `pane-banner.ps1` §6g is a band HEIGHT, which a column
capped at half the pane still satisfies (the value simply wraps one line
later). §6g2 closes that.

## Validation criteria

- [x] A two-column banner table with one short label column and one long text cell in a wide pane (~1900px) uses the full content width: the long cell extends until pane width (minus gutters/chevron reservation) is exhausted before wrapping or ellipsizing. — `test/win32/pane-banner.ps1` §6g2 measures the text's own right edge against the content column: **96.6%** of a 1297px content column on the shipped build. Manual capture at 1926px (`temp` scratch repro) shows the same table full-width with the untruncated string and half-width with the hook-truncated one.
- [x] Column-width distribution asserted in the pure layout module at 1.0/1.25/1.5/2.0 scaling: unused width from narrow columns is granted to the wide column rather than stranded. — two new `columnWidths` tests in `src/apprt/win32/banner_layout.zig` (2-column and 4-column), each asserting `sum(out) + gaps == available` and `out[wide] > 0.9 * available`, run in the `win32` lane.
- [x] Existing banner-table behavior unchanged: 3-wrapped-line cell cap, narrow-pane reflow, and `test/win32/pane-banner.ps1` still ALL PASS. — `ALL PASS (119)`.
- [x] The new assertion can fail: rebuilt with `T123_NEUTERED = true` (the pre-T123 360px fixed cap) it reports **33%** and goes red, while the shipped build reports 96.6%.
