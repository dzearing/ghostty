# T1044 - The upgrade reads the app's job-escape handoff as a dead app, so a slow start becomes RESUME-REUSE FAIL and the loop stalls

## Summary

`upgrade-ghoztty-windows.ps1` brings the app back after the swap with
`Start-Process -PassThru` and then polls `+list` while watching that pid: any
exit was read as "the app is dead", and the reuse path answered with
`RESUME-REUSE FAIL ... the session is alive but headless`, exit 1, without ever
typing the resume prompt.

T675 (1db14f3e2, 2026-08-16) changed what that pid means. The app now notices it
is inside the agent's kill-on-close PTY job, respawns its own command line
outside the job, and **exits 0** - so the process the upgrade started is a
launcher that hands off, and its exit is the expected shape of a healthy start.
The escaped twin answers `+list` a moment later. Whether the run survives is
therefore a race: if the twin answers on the first poll (the box's warm path,
which is why the 08-17..08-20 morning refreshes all logged `RESUME-REUSE OK`)
nothing is noticed; if it takes one poll longer, the upgrade declares the app
dead and the loop is left with no resume prompt typed and nothing to restart it
but the watchdog's ~45 minutes.

Measured in `test\win32\upgrade-no-fork.ps1` section B, which fails exactly this
way against a cold sandbox: `instance probe 1 not ready` -> `the process we
started (pid=37944) EXITED with 0` -> `RESUME-REUSE FAIL`, 6 assertions red
(B4/B15/B15b/B16/B16b and E3).

Fix: in `Wait-Instance`, only a **nonzero** exit is evidence of a dead app. Exit
0 is logged once as a T675 job-escape handoff and the poll continues to the
deadline. Both give-up messages gained the matching third state, so a genuine
"the twin never came up" is still distinguishable from "IPC unreachable" and
from "the process crashed".

## In plain terms

When Ghoztty updates itself it kills the old app, copies the new one in, starts
it, and types the "carry on" prompt back into the window you were working in.
Since a change last week the app restarts itself once during startup as part of
coming up healthy - and the updater mistook that for the app dying. Most
mornings it started fast enough that nobody saw it; a slow morning would have
ended with the update giving up, no prompt typed, and the loop sitting idle for
three quarters of an hour.
