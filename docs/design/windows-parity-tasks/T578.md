# T578 - Nothing builds the Windows target in CI until release time, so a broken cross-compile is only found while shipping

## In plain terms

Every change on this branch gets checked on a Mac in the cloud, and never on
Windows. So the only thing that ever proves the Windows app still compiles for
release is a release — and a release is the worst possible moment to find out
it does not.

## Summary

`.github/workflows/fork-ci.yml` runs `macos-latest` only: a Zig core test, a
debug macOS app build, and the Swift test suite. Nothing anywhere in CI runs
`zig build -Dapp-runtime=win32`, for any target or optimize mode.

T577 exposed what that costs. `release-windows.yml` has existed since T38,
was reviewed, and had static assertions covering its wiring — and the first
time its `zig build -Dapp-runtime=win32 -Dtarget=x86_64-windows-gnu
-Doptimize=ReleaseFast` step ever executed on a Linux runner was during an
actual release, three weeks after it was written. The on-box lanes
(`floor-lane.ps1`) build natively on Windows and so cannot stand in for it:
they exercise a different host toolchain, a different linker path, and never
the `wixl`/`msiinfo` packaging that follows.

## Details

Shape of the fix: a job in `fork-ci.yml` (or a sibling workflow) on
`ubuntu-latest` that cross-compiles the Windows app the same way the release
does, so a commit that breaks it is red on the commit rather than at the tag.

Things worth deciding while doing it:

- **How much to build.** The exe alone is the cheap 90%; running
  `dist/windows-installer/build-release-artifacts.sh` end to end also covers
  the MSI and portable-ZIP packaging, which is where the version-embedding
  check and `wixl` live. The release step is exactly that script, so building
  it is the only thing that fully protects the release path.
- **Which lanes.** `zig build test -Dapp-runtime=win32` is the win32 unit
  lane and would be a real addition to CI coverage, but the tests are built
  for a Windows host and cannot RUN on a Linux runner — building them without
  running them still catches compile breaks.
- **What it must not do.** fork-ci is gated on
  `github.repository == 'dzearing/ghoztty'` and has a 60-minute timeout;
  match both. It must not publish anything.

## Validation criteria

- [ ] A CI job on a push to `users/dzearing/windows-amd64` builds the Windows
      release exe with the same flags `build-release-artifacts.sh` uses, and
      is red when it does not compile.
- [ ] Deliberately breaking the win32 apprt in a scratch commit turns that job
      red (verified once, then reverted) — a green job that would stay green
      through a break is the failure mode being fixed.
- [ ] The job does not publish a release, upload to gh-pages, or move any tag.
- [ ] The runbook (`.claude/commands/release.md`) says a release is expected
      to find the Windows build already green, rather than proving it.
