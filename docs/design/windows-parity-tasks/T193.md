# T193 - +read fails with an unhelpful error on a pane showing the alternate screen

## In plain terms

Asking Ghoztty what is on a terminal's screen used to answer with an error
whenever that terminal was running a full-screen program — a system monitor, a
file viewer, an installer. The error was the same one you get for a terminal
that does not exist, so a script or AI agent watching the pane could conclude
it was broken when it was just showing a full-screen app. Now the answer is
what you would expect: the screen you would see looking at the pane, and the
normal history comes back as soon as the full-screen program exits.

## Goals

- [x] `+read` on an alternate-screen pane succeeds and returns the visible screen
- [x] `+read` recovers the primary screen's scrollback when the program leaves the alt screen
- [x] A regression arm proves both, with a primary-screen control
- [x] The Mac half is covered (T481 updated to include the alt screen in its validation)

## Summary

Found while building `menu-bar.ps1` (T190). A pane running a full-screen TUI -
anything on the ALTERNATE screen - answers `+read` with

```
failed to read terminal content from '<pane-id>'
```

and exit 1, instead of returning what is on screen. Reproduced on this box by
having the pane's shell write `ESC[?1049h`: every `+read` fails until the
terminal returns to the primary screen.

That is a real gap for the agent workflow `+read` exists to serve: an agent
watching a pane that happens to be running `htop`, `mc`, a pager, or a
full-screen installer gets an error it cannot distinguish from "no such pane"
or "the app is wedged".

## Details

Two things to decide and then do:

1. **What should `+read` return on the alternate screen?** The alternate screen
   has no scrollback by design, so "the last N lines of scrollback" is
   genuinely empty. The useful answer is almost certainly *the visible screen*
   - that IS the content a user or agent means when the pane is a TUI. Check
   what the Mac/shared implementation does before diverging: this handler is
   likely shared, in which case the fix is shared too (Mac-seat follow-up like
   T134/T186).
2. **Whatever the answer, the ERROR has to say which.** "failed to read
   terminal content" cannot be told apart from a missing pane, a dead session,
   or a lock timeout by the caller. If reading really is impossible, say
   *why* ("pane is showing the alternate screen; no scrollback").

Note for whoever takes this: a `+read` failure is NOT a usable oracle for "the
pane is on the alternate screen" - it also fires for other reasons, and T190's
harness scored three runs wrong by assuming otherwise. Use a marker printed by
the child after it switches back.

## Resolution (2026-08-06)

**The defect no longer exists at HEAD on win32; the remaining work was
coverage, and it now exists.** Root cause of the filed symptom: the old
`+read` treated an EMPTY screen dump as `failed to read terminal content`
(the T181 defect), and a bare `ESC[?1049h` alternate screen dumps empty —
the alt screen has no scrollback and nothing had painted yet. T181's rework
(2026-08-04) fixed both halves of this task's question in one move:

1. **What does `+read` return on the alt screen? The visible screen.** The
   dump reads `screens.active.pages` (`IpcHandlers.zig` `handleRead`), which
   IS the alternate screen while mode 1049 is set — so a TUI pane answers
   with exactly what a user sees. Verified live: a pane holding
   `T193ALTCONTENT` on the alt screen answers exit 0 with that text and
   WITHOUT the primary screen's marker; after `ESC[?1049l` the primary
   scrollback (both markers) comes back.
2. **No alt-screen-specific error is needed** — reading is always possible,
   so the "say why" half of the task is moot. The distinct-failure contract
   from T181 stands unchanged.

The Mac half is NOT fixed: `IPCServer.swift` still has the `isEmpty →
failure` branch, so a bare alt screen still errors there. That is exactly
T481's defect; T481's file now instructs its taker to include an alt-screen
arm in the macOS validation (edited in this commit), so this task does not
need a separate mac twin.
