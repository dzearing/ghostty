# T588 - Chooser session-card Kill hover sticks when the pointer leaves the dialog

## In plain terms

In the window you open to pick a machine, each running session gets a card with
a small "x" on it that ends that session. Point at the "x" and it lights up, the
way a button should. But if you move the pointer off it and straight out of the
window, the light stays on - the card goes on looking as though your pointer is
still resting on the button long after you have moved away. Nothing is broken
and the button still works; it just keeps advertising itself. After this, the
light goes out as soon as the pointer leaves.

## Goals

- [x] Pointing at a session's "x" still lights it (the affordance is not lost)
- [x] Moving the pointer straight out of the window turns the light off
- [x] It works every time, not just the first
- [x] Ending a session still works after all that pointing
- [x] An automated test that fails on the old behavior

## Summary

Same defect class T315 fixed on the account link, on a sibling control in the same dialog. The session roster's Kill button hover (MachineChooser.zig onSessionHover / setKillHover, roster.hover_kill) is driven ONLY by the dialog's WM_MOUSEMOVE arm; nothing arms a TrackMouseEvent(TME_LEAVE), so a pointer that goes from a Kill button straight out of the chooser leaves the button lit until it comes back. Unlike T315 the tracking belongs on the DIALOG here, because the roster cards are painted on the dialog itself rather than in a child control - and the parent's leave firing when the pointer enters a child (the listbox, the filter, the link) is the CORRECT answer in that case, since the pointer is genuinely off the card. Validation should follow T315's method: test/win32/chooser-link-hover.ps1 measures paint (ink in the control's rect from a PrintWindow capture) and proves it discriminates by building once with the fix disabled.

## Validation criteria

- [x] **The Kill fill clears when the pointer leaves the dialog.** New
  `test/win32/chooser-kill-hover.ps1` measures the first card's Kill box - the
  pixels in it that differ from the card fill beside it - across three states:
  rest **80**, hovered **809** (the rounded fill is +729 px of covered box),
  after a posted `WM_MOUSELEAVE` **80 exactly**.
- [x] **Positive control: entering still lights it.** Same script, asserted
  before the leave (`rest=80 -> hot=809`), and the hot frame comes from
  `Get-TestHoverCapture`, which also answers `Hit=HTCLIENT` (the point routed as
  a client move, so the roster saw it) and `Changed=true`. A leave-on-entry
  regression - the danger of arming the tracker on the DIALOG - fails here
  rather than passing as a "fix".
- [x] **It discriminates.** Built once with both halves of the fix disabled
  (`if (false)` on the arm and on the leave's `setKillHover`): after-leave
  stayed at **809** and the script reported 2 FAILURES. The pre-fix defect is
  what the test measures, not a proxy for it.
- [x] **Repeatable**, not one-shot: a second enter/leave cycle reproduces
  `hot2=809, left2=80`, so the tracker is re-armed per entry.
- [x] **The leave did not break the roster.** Same script: after all the hover
  traffic a click on the Kill button still opens its confirmation dialog, and
  Escape still closes the chooser.
- [x] `-NegativeControl` (inverting "the fill clears") FAILS on the fixed
  build, so the measurement is not scoring a constant.
- [x] Standing floor: `scripts\floor-lane.ps1 -Lane all` and P1-P3.
