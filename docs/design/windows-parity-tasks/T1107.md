# T1107 - The agent never marks a resumed session as attached, so unattached_since is never cleared

## In plain terms

The background session keeper tracks when a session stopped being shown in a window, so it can tell you about sessions left running on their own. When a session is brought back into a window, that clock is supposed to reset.

It turned out it always did. What was broken was the automated check watching it: it drove the session list with the keyboard but never looked at where the highlight went, so when the list took a moment to appear the keys landed on nothing and the check declared the feature broken. The check now watches where the highlight actually lands, and the app's own report of that is shared by every test that drives the list.

## Answer

**The attach path is fine and always was.** Resuming a session marks it attached and clears the clock in about 90 ms, measured on the box. The two sweep failures were a harness defect, now fixed.

## Summary

`test\win32\orphan-notify.ps1` scored `2 FAILURE(S) (11 passed)` in the T1094 sweep:

```
FAIL  the agent reports the resumed session ATTACHED
FAIL  the attach reset unattached_since to null
```

Eleven assertions pass, so detection and notification of genuinely orphaned sessions works; it is the ATTACH transition that does not land. `unattached_since` staying non-null is what keeps the session looking abandoned forever after.

### What actually happens

`git diff 9a764deea..HEAD` - the sweep's commit against the tree that runs this script ALL PASS today - touches no file under `src/` at all, so the code that scored two failures is byte-identical to the code that passes. The failure is in how section 4 drove the chooser:

```
Send-TestKeys Right                      # step into the session roster
Send-TestKeys Down  x targetIdx          # targetIdx counted off `+sessions --json`
Start-Sleep 400ms
Send-TestKeys Return                     # resume "the" row
```

Two assumptions, both false:

1. **The Down count is in the wrong index space.** Since T602 the roster is displayed SORTED (name or CPU, a persisted preference), so an index counted off the agent's reply is not the cursor's index.
2. **Right can silently do nothing.** `MachineChooser.enterSessions` opens `sessionView(&buf) orelse return`, and the roster is fetched asynchronously when the dialog opens. Arrive before it lands and no cursor is ever set - after which `resumeCursor` declines the Return ("No cursor => not ours") and it falls through to the MACHINE row's default action. A window opens, nothing is resumed, and the session the script then reads back is still unattached. That is the failure, and it looks exactly like a broken attach.

The app already says where the cursor lands after every step, precisely so a harness can know - `chooser roster: cursor on session id=... (row N of M)`, added by T602/T620 because an owner-drawn roster has no HWNDs to read back. `chooser-resume.ps1` and `chooser-resume-remote.ps1` use it; the latter by pasting the former's helpers with a different timeout. `orphan-notify.ps1` was never converted.

### The stamp is honest - this is not a guard defect

The green stamp was written at 01:54 and the sweep ran the script red at ~04:00, against identical `src/`. Nothing narrower was stamped: `guard-due.ps1 update` only runs from the bottom of the script after `$script:fail -eq 0`, so the stamped run was the whole script. The stamp says "this harness was run green against the code as it now stands", and that was true. What it cannot say - and does not claim - is that the harness is DETERMINISTIC. A blind keyboard walk is green on an idle box and red on a loaded one, and no stamping scheme can detect that from outside. So there is nothing to file against the guard; the flake was the thing to fix, and it is fixed.

Same two facts fail inside `chooser-orphan-badge.ps1`, which reproduces the mis-navigation deterministically even on an idle box (`index 0 of 3`, Return resumes nothing, empty session id). That is T1106's, and it now has the root cause and the shared helper waiting for it.
