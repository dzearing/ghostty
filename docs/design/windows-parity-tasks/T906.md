# T906 - A starting agent re-adopts live holder sessions with scrollback gap-filled

## Summary

Increment 3 of the T705 split (design:
`docs/design/agent-nondestructive-handoff.md`). On startup the agent reads
`sessions.json`, finds holder-backed sessions whose holder still answers its
pipe, and RE-ADOPTS them: reconnects as owner, gap-fills the output ring from
the holder's offset-acked replay buffer, and serves the session as if it never
left. A holder that does not answer follows the existing dead-session
tombstone path.

This makes the upgrade path and the crash path the same path: the app-side
in-place recovery (T145/T723) already re-dials a replacement agent and
re-attaches panes — with adoption, those panes land on LIVING shells instead
of tombstones.

Skew rule: adoption honors the holder's versioned HELLO. A holder speaking a
newer protocol than this agent degrades additively (unknown fields ignored); a
holder this agent cannot serve at all is left running and reported, never
killed or garbled.

## In plain terms

The previous task lets a session's shell outlive the background manager; this
one teaches a freshly started manager to find those surviving shells and plug
them back in, with no gap in the output history. After this, the manager
crashing or being replaced costs you nothing — your panes reconnect to the
same running programs.

## Goals

- [x] Startup discovery + adoption of live holders; dead holders take the
      existing tombstone path.
- [x] Ring reconciliation via the holder's replay buffer — the resume offset is
      exact, so nothing is duplicated and nothing the holder still retains is
      lost. The one remaining exposure is NOT closed here and is filed as
      **T911**: the owner ACKs on delivery, which is the holder's permission to
      free, so bytes written since the last ring snapshot are no longer in the
      replay buffer after a crash. The gap is reported out loud rather than
      silent, and it is invisible in this increment's acceptance because the app
      never restarts and still holds the grid.
- [x] Pure adoption/reconciliation rules unit-tested in `test-agent`.
- [x] Acceptance proves continuity end to end through an agent kill.
- [x] (added) Orphan sweep: a holder no session record names is shut down at
      startup instead of running until the box reboots — the gap T905's log
      flagged for this increment.

Shape that landed: (a) pty_holder_child.adopt() - an alternate constructor on the existing owner client that dials a RUNNING holder, HELLOs, ATTACHes at the recorded offset and returns the same HolderChild, so an adopted session is indistinguishable from a spawned one; (b) holder_adopt.zig - the startup sweep, called from all three listen paths right after loadPersisted and BEFORE the listener serves anyone (a viewer ATTACHing mid-sweep would see a tombstone and RELAUNCH, spawning a second shell beside the running one); (c) sessions.json gains holder_offset, the SNAPSHOT's watermark, captured beside the ring copy under one lock via a new optional Child.deliveredOffset() read from inside onChildOutput; (d) the restart divider is now DEFERRED for holder-backed records - adoption never draws it, abandonHolder does; (e) the orphan sweep. THE BUG THE ACCEPTANCE CAUGHT, and it would have shipped silently: the first identity check compared the holder's HELLO session_id against the AGENT's session id, but a holder's id is a fresh random value minted before SessionTable.create assigns one - so every adoption was refused, every session was quietly RELAUNCHED with a new shell, and then the orphan sweep killed the abandoned holder. The shared identity is the recorded pipe NAME (pipeNamesHolder, unit-tested). Only an end-to-end script comparing the SHELL PID could see this: the panes all worked.
