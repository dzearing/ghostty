# T1116 - The scrollback holder misses its periodic flush and loses the buffer on a crash

## In plain terms

The part that keeps a copy of your scrollback on disk is supposed to save regularly, so a crash costs you at most a few seconds of history. In the check, the regular save never happens and the history is gone after a simulated crash - which is exactly the situation the feature exists to survive.

## Summary

`test\win32\holder-volume.ps1` scored `HOLDER-VOLUME: 2 FAILURE(S) (14 assertions passed)` in the T1094 sweep:

```
FAIL B4 the marker reached a .ring file inside the periodic interval (the volume trigger fired)
FAIL C3 the marker is still on disk after the crash
```

The two are almost certainly one fault: if the periodic/volume-triggered flush (B4) never fires, then there is nothing on disk to survive the crash (C3). Fourteen other assertions pass, so the holder is running and doing its other work.

The user-visible consequence is real: scrollback written shortly before a crash is lost, and the crash is precisely when you want it.

## Where

- `src/remote/agent/` (or the holder module) - the periodic and volume-triggered flush to `.ring`
- `test/win32/holder-volume.ps1` sections B and C

## Goals

- [ ] Check whether the volume trigger fires at all - a threshold that is never reached, a timer that is not armed, or a flush that writes somewhere else.
- [ ] Fix B4 first and re-run; expect C3 to follow.
- [ ] If C3 stays red with B4 green, that is a separate durability defect (buffered writes not reaching the file) and gets its own investigation.

## Validation criteria

- [ ] the periodic/volume flush fires within its stated interval and the marker is in a `.ring` file
- [ ] the marker survives the simulated crash
- [ ] `test\win32\holder-volume.ps1` is ALL PASS
