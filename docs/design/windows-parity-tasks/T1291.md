# T1291 - Re-running the installer for an already-installed version quits silently

## In plain terms

You run the installer when you already have that exact version. Nothing
happens - the window disappears and you are told nothing. You cannot tell
whether it worked, whether it did nothing on purpose, or whether it broke.

## Goals

- [x] Re-running the installer for the installed version puts a dialog on
      screen offering Repair and Cancel instead of exiting without a word.
- [x] Cancel leaves the existing install exactly as it was, with no error.
- [x] Repair actually repairs - the answer is not just cosmetic.
- [x] A same-version package is no longer announced as a "newer version", and
      the genuinely-newer case explains itself instead of erroring.
- [x] The in-app updater's silent install never sees a dialog.
- [x] An acceptance script drives the whole thing and fails if it goes quiet.

## What the user hit (2026-09-03)

> "I also tried installing the msi with a version already installed and it just
> silently quit. I think this is the case if 1.36 is already installed. there
> should be some message to ask what to do (reinstall, cancel) that's a
> standard dialog to let you know you're already good, not just silently fail."

This is the same-version case, distinct from the two already filed:

- **T1204** is installing over a *running* Ghoztty (no Restart Manager path).
- **T1205** is not being able to tell *which build* is installed.
- **This** is Windows Installer's own already-installed behaviour: with the
  same `ProductCode` and the same `ProductVersion`, a plain `/i` finds nothing
  to do and exits, and in the default UI sequence that can pass without a
  visible word.

## What it should do

Windows already has the convention, and the user named it: when the product is
present at the same version, the installer should offer **Repair** and
**Cancel** (the standard maintenance dialog) rather than vanishing. "You are
already up to date" is a fine answer - being told it is the point.

Worth handling in the same pass, since they are the same branch of the MSI's
UI sequence:

- Same version installed → maintenance dialog (Repair / Cancel).
- Older version installed → upgrade, which already works.
- **Newer** version installed → say so plainly and refuse, rather than a raw
  1638 ("Another version of this product is already installed").

Note this interacts with T1178's in-app updater, which runs the MSI on the
user's behalf: whatever dialog appears must not block a silent/managed install.
Gate the UI on `UILevel` so the updater's quiet path stays quiet.

## Validation criteria

- [x] Running the MSI when the same version is installed shows a maintenance
      dialog offering Repair and Cancel; neither choice leaves the existing
      install damaged. Verified live: `test\win32\install-maintenance.ps1`
      L1/L2 launch the real debug exe as the package's prompt on a background
      desktop, find the `GhozttyConfirmDialog`, and read its two BUTTON
      captions back as exactly `Repair` and `Cancel`.
- [x] Cancel exits without changing anything, and says nothing alarming. L4
      presses the Cancel button and measures the process exit code as 1602
      (`ERROR_INSTALL_USEREXIT`) - the one non-zero value Windows Installer
      ends a transaction on quietly, with no error dialog and nothing written
      (the prompt runs before `InstallValidate`). L3 is its pair: Repair exits
      0, and the package has pre-armed `REINSTALL=ALL` before `CostFinalize`
      so that 0 lets a real repair proceed.
- [x] Running an OLDER MSI over a newer install explains that a newer version
      is present instead of surfacing error 1638. The `Upgrade` table now
      carries three bands instead of two - `SAMEVERSIONFOUND` is detected on
      its own - and each has its own `LaunchCondition` message. Checked at the
      source by A17/A18/A19 and in the compiled package by the new read-back
      block in `build-msi.sh`, whose refusals are demonstrated by E11/E12.
- [x] The in-app updater's install path is unaffected - no dialog appears for a
      silent install. All four maintenance actions are conditioned on
      `UILevel > 3`, and the updater installs with `/qb-!` (UILevel 3). A15
      checks every one of the four rows carries the gate; E6 feeds the
      verifier an unconditional prompt and watches it go red.
- [x] An acceptance script in `test/win32/` drives the same-version case and
      fails if the outcome is silent. `test\win32\install-maintenance.ps1`:
      ALL PASS, 40 assertions, on 2026-09-03. 21 source checks each with a
      `-TeethCheck` mutation (also ALL PASS), 12 build-time-verifier refusals
      including E2 - the silent package itself - and the 6 live checks above.
