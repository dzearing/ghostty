# T1052 - The MSI and portable ZIP ship without ghoztty.com, so the ghoztty command does nothing from PowerShell

## Summary

Both released Windows artifacts package `ghoztty.exe` + `ghoztty-agent.exe` +
the `share/` tree and omit `ghoztty.com`, the console-subsystem twin T245 added.
The MSI also puts its install directory on the user PATH, so a fresh install
answers `ghoztty +list` with silence.

## In plain terms

Someone who installs Ghoztty from the download page gets a working terminal and
a completely dead command line. Typing `ghoztty +list` in PowerShell prints
nothing, `ghoztty +list --json > out.json` leaves a 0-byte file, and there is no
error message anywhere to explain it — PowerShell simply does not wait for a
windowed program. Only the copies this repo's own delivery script installs are
whole; the ones the world downloads are not, and every CLI-driven feature this
project exists for is invisible to them.

## Details

`ghoztty.com` is not an optional extra. `src/cli/com_shim.zig` documents why it
exists: PowerShell and cmd decide whether to WAIT for a native child (and wire
up redirection) by reading the PE subsystem field, and `ghoztty.exe` is a GUI
binary. PATHEXT resolves `.COM` ahead of `.EXE`, so a bare `ghoztty` finds the
console twin, which is the same binary with one word of the PE optional header
flipped (`src/build/patch_subsystem_main.zig`). `zig build` installs it into
`zig-out/bin/` on every Windows target, cross-builds included, and
`scripts/delivery-manifest.ps1` carries it — which is why the loop's own three
install locations behave and the released artifacts do not.

Why nobody noticed: every install on this box has the twin, because
`scripts/deliver-windows-build.ps1` puts it there. Checked 2026-08-21 -
`%LOCALAPPDATA%\Programs\Ghoztty\` and the Desktop portable copy both hold
`ghoztty.com` beside `ghoztty.exe`. The two paths that build the file set for
the outside world are the two that never learned about it, so the defect is
invisible from every seat that could catch it.

Where the file set is decided:

- `dist/windows-installer/build-portable-zip.sh` — copies `ghoztty.exe` and
  `ghoztty-agent.exe` explicitly, then asserts an entry manifest that names both
  and not the twin.
- `dist/windows-installer/build-msi.sh` — same two files into INSTALLDIR, plus
  the File-table version patch (`want = {"ghoztty.exe", "ghoztty-agent.exe"}`)
  that makes Windows Installer treat them as versioned so upgrades replace them.
  The twin needs the same treatment or an MSI upgrade will leave a stale one
  behind.
- `test/win32/release-artifacts.ps1` — section B asserts the ZIP's entry set, so
  it has to learn the twin too, or the gap can reopen silently.

Two details worth getting right rather than fast:

1. The twin doubles the payload of the largest file in the package (~15 MB
   release), so both artifacts grow by roughly that. That is the accepted cost
   of the T245 design — a patched copy of the app rather than a small relay
   shim, because Defender quarantines the shim shape on sight — but the ZIP
   shape check will fail on the changed entry set and needs `-AcceptZipShape`
   for the run that legitimately moves it.
2. The MSI's PATH entry is what makes this user-visible; confirm after the fix
   that a fresh install resolves `ghoztty` to the `.com` and that
   `ghoztty +list --json > out.json` from PowerShell writes real bytes.
