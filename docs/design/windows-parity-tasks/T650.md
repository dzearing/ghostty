# T650 - Viewer feedback: assert that a dev server started AFTER a localhost pane makes the button appear (win32)

## In plain terms

Open a viewer pane on `http://localhost:3000` before your dev server is
running, then start the server. The feedback button should appear on its own
within a few seconds, without you reopening the pane. That is what the
provenance cache's expiry is FOR — but nothing on Windows checks that it
actually happens, so it could quietly stop working and no test would notice.

## Summary

T633's `viewer_worktree.Cache` expires entries after 15s, and both CLAUDE.md
and the module's own comment name the reason: "starting a dev server on :3000
has to make the button appear without reopening the pane". T638 shipped the
port lookup that makes the claim meaningful and asserted the three *steady
state* outcomes (`test\win32\viewer-worktree-port.ps1`) — but not the
TRANSITION, which is the only part that depends on the TTL rather than on the
lookup.

## Details

The gap is only reachable on-box: the pure `Cache` tests already assert that an
entry stops answering at `ttl_ms`, and what is unasserted is that the pane
re-asks when it does. So the arm belongs in the acceptance script, as a fourth
case:

1. Pick a free port, start NO listener, open a pane on it with
   `--working-directory` inside a repo. It resolves leg 3 — the origin.
2. Start a listener from a DIFFERENT working tree on that port.
3. Without touching the pane, wait past the 15s TTL and assert the logged
   worktree moves to the listener's tree.

The honest question this raises, and the reason it is its own task: **what
re-asks?** A pane with no navigation may never call `refreshWorktree` again, in
which case the TTL expiring changes nothing and the button never appears —
which would make this a real defect rather than a missing test, and the fix
(a timer, or a re-resolve on focus/paint) a design choice worth its own pass.
Find out which before writing the assertion; if it is the defect, the arm
still belongs here and the fix rides with it.

## What was found

**Nothing re-asked.** All four `refreshWorktree` call sites in
`ViewerPane.zig` are navigation events — `navigate`, the browser-committed URL,
the page host's commit, and `ensureNav`'s first resolution — and Mac's
`ViewerView` has exactly the same shape (`location`'s `didSet`, plus `init`).
So the cache's TTL expired and nobody asked again: the documented promise was
never true on either platform. This was the defect the task suspected, so the
fix rode with the test.

## The fix

- `ViewerPane` arms a repeating `WM_TIMER` at `Cache.ttl_ms`, and ONLY while
  the pane's location is a loopback URL — a file's directory and a remote
  site's origin cannot move while the location sits still, so no other pane can
  change its answer without navigating. It is armed and disarmed from
  `refreshWorktree` itself, so it follows the location the way the resolution
  does.
- The tick is skipped while the pane's window is not visible, so a stack of
  background tabs costs nothing at all.
- `ViewerWorktreeProbe` memoizes directory → worktree root for five minutes, so
  the steady state of a watched dev server is the two syscalls that establish
  the listener has not moved, and no `git` process. The memo expires rather
  than living for the pane's life, because `git init` under a running server
  does change the answer.

The Mac half is filed as **T1452** (`seat: mac` — the Swift build and its
regression run are the Mac seat's).

## Validation criteria

- [x] Established from the code which event, if any, re-resolves a pane that
      has not navigated — recorded in this file either way. *(Nothing does; see
      "What was found".)*
- [x] On-box acceptance: a pane opened on a dead port picks up a listener
      started afterwards, within a bounded wait, with no navigation and no
      reopen. *(`test\win32\viewer-worktree-port.ps1` case 4 — ALL PASS (23);
      the pane from case 2, already resolved to its origin, moves to the late
      listener's tree on its own.)*
- [x] If nothing re-asks today, the fix that makes it re-ask lands with the
      test, and does not cost a spawn or a syscall per idle pane. *(Only
      loopback panes poll; invisible panes skip the tick; the directory memo
      keeps an unmoved listener process-free — asserted in the win32 lane by
      "a second resolution of the same directory answers from the memo".)*
- [x] Negative control: with the poll disabled the new arm FAILS (the pane
      stays on `D:\git\ghoztty`, its origin), so the arm is load-bearing.
