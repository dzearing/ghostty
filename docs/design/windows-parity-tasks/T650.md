# T650 - Viewer feedback: assert that a dev server started AFTER a localhost pane makes the button appear (win32)

## In plain terms

Open a viewer pane on `http://localhost:3000` before your dev server is
running, then start the server. The feedback button should appear on its own
within a few seconds, without you reopening the pane. That is what the
provenance cache's expiry is FOR — but nothing on Windows checks that it
actually happens, so it could quietly stop working and no test would notice.

## Summary

T633's `viewer_worktree.Cache` expires entries after 15s, and both CLAUDE.md
and the module's own comment name the reason: "starting a dev server on :3000
has to make the button appear without reopening the pane". T638 shipped the
port lookup that makes the claim meaningful and asserted the three *steady
state* outcomes (`test\win32\viewer-worktree-port.ps1`) — but not the
TRANSITION, which is the only part that depends on the TTL rather than on the
lookup.

## Details

The gap is only reachable on-box: the pure `Cache` tests already assert that an
entry stops answering at `ttl_ms`, and what is unasserted is that the pane
re-asks when it does. So the arm belongs in the acceptance script, as a fourth
case:

1. Pick a free port, start NO listener, open a pane on it with
   `--working-directory` inside a repo. It resolves leg 3 — the origin.
2. Start a listener from a DIFFERENT working tree on that port.
3. Without touching the pane, wait past the 15s TTL and assert the logged
   worktree moves to the listener's tree.

The honest question this raises, and the reason it is its own task: **what
re-asks?** A pane with no navigation may never call `refreshWorktree` again, in
which case the TTL expiring changes nothing and the button never appears —
which would make this a real defect rather than a missing test, and the fix
(a timer, or a re-resolve on focus/paint) a design choice worth its own pass.
Find out which before writing the assertion; if it is the defect, the arm
still belongs here and the fix rides with it.

## Validation criteria

- [ ] Established from the code which event, if any, re-resolves a pane that
      has not navigated — recorded in this file either way.
- [ ] On-box acceptance: a pane opened on a dead port picks up a listener
      started afterwards, within a bounded wait, with no navigation and no
      reopen.
- [ ] If nothing re-asks today, the fix that makes it re-ask lands with the
      test, and does not cost a spawn or a syscall per idle pane.
