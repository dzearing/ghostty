# T104 — PARITY GAP: win32 GUI ignores -e <args…>

## Summary

PARITY GAP: win32 GUI ignores `-e <args…>` (Mac/Linux `ghostty -e cmd…` runs the command in the first window; on win32 the args are silently dropped and the pane runs the default shell). Found by T102 validation (2026-07-20) — its harness had to fall back to `--command=…` (which works, incl. spaces when quoted as one argv entry). Implement `-e` arg collection in the win32 CLI/app launch path mapping to the same exec override as `--command`, matching the Mac flavor conventions; add a launch case to an acceptance script

## Root cause (2026-08-03) — not the parser, the AGENT gate

The original framing ("implement `-e` arg collection in the win32 CLI") was
wrong, and it is worth saying why: `-e` was already collected. `Config.
parseManuallyHook` builds `initial-command` from the trailing args on every
platform, and core `Surface.init` already prefers `initial-command` for the
first surface. Nothing needed implementing.

What dropped it was one gate, three files away. **Session persistence is ON by
default on Windows**, so every local pane's IO backend is the LOCAL AGENT, not
exec — and the agent branch of `Surface.init` forwarded a command only when
`config.@"wait-after-command"` was set:

```zig
if (command) |c| {
    if (config.@"wait-after-command") remote_command = try c.string(alloc);
}
```

`wait-after-command` is a flag the APPRT sets when IT built the command — the
embedded `--command` path (`apprt/embedded.zig`) and the win32 IPC override path
(`apprt/win32/Surface.zig`, `+new-window --command`). The app's OWN config never
sets it. So on the GUI launch path the command matched nothing and was never put
in the OPEN. It was not logged, because from the gate's point of view nothing
happened.

The gate is not paranoia: forwarding the LOCAL default shell to a CROSS-MACHINE
agent is the documented stall wedge (a macOS `/bin/zsh` handed to a Windows
ConPTY agent never replies OPENED and the IO thread hangs forever). The gate was
right; its test for "explicit" was the wrong one.

### The proof, on the box

`--session-persistence=false` (see T405 — the documented `off` does not parse)
takes the exec path, and there `-e` worked all along:

| launch | backend | result (pre-fix) |
|---|---|---|
| `ghoztty -e cmd /k echo T104MARKER` | agent (default) | plain `cmd` prompt, no marker |
| `ghoztty --session-persistence=false -e cmd /k echo …` | exec | `T104MARKER` printed |
| `ghoztty "--command=ping -n 30 127.0.0.1"` | agent (default) | plain prompt, no ping |

That table is the whole diagnosis: same command, same parser, two backends, one
of which never received it. `--command=` and a `command` in the config file were
dropped identically — the SAME line, so they are fixed by the same line.

## The fix

`Config` cannot answer "did the user ask for this command?" by nullness:
`finalize()` fills `command` with the default shell (`cmd.exe` on Windows) when
nothing did, so after finalize the field is never null and "the login shell" and
"the user asked for `pwsh`" look identical downstream.

- **`Config._command-explicit`** (new, `src/config/Config.zig`) records
  `self.command != null` at the TOP of `finalize`, before the default-shell
  lookup fills it in. Recomputed on every rebuild, so
  `changeConditionalState`'s replay (which every win32 startup runs to seed
  light/dark) keeps it honest rather than losing it.
- **`Surface.init`** derives `command_explicit` next to the existing `command`
  block — `initial-command` is explicit by construction (only `-e` or the key
  itself sets it), everything else defers to the flag — and the agent gate
  becomes `wait-after-command OR (local_agent AND command_explicit)`.

The second term is **LOCAL-agent only** (`rb.local_shell_integration`), which is
what preserves the stall-fix invariant: a command configured for THIS machine
still never reaches a cross-machine agent.

`-e`'s argv is joined into one command string by `Command.string()` and run by
the agent through the shell's native convention (`cmd /c`, `pwsh -Command`,
`wsl --`). That is not a new decision — it is exactly what `+new-window -e`
already does (`IpcHandlers.joinArgv`), so the two `-e` surfaces now behave the
same.

## Validation (2026-08-03, on the box)

- `test/win32/gui-launch-command.ps1` — **ALL PASS** (new). Hermetic (per-run
  `$env:LOCALAPPDATA` + `GHOSTTY_LOCAL_AGENT_BIN`), so no real session layout
  restores over the window under test, and it only ever kills zig-out processes.
  - **A** `-e <script> alpha beta` → the pane prints `T104ARGS=[alpha][beta][]`,
    with the agent running (i.e. on the backend that dropped it).
  - **B** `"--command=<script> gamma delta"` → same, one argv entry.
  - **C** a plain launch → an interactive shell, no marker, and
    `+sessions --json` shows **no** recorded `argv` — the default shell must not
    be mistaken for a request.
- **Negative control** (the reason to trust it): with the new term forced to
  `false` and rebuilt, exactly A2/A3/B2/B3 fail and C stays green. An acceptance
  script that cannot see the bug validates nothing.
- Three unit tests in the `none` lane cover `_command-explicit`: absent, set,
  and surviving a `changeConditionalState` rebuild.
- Floor: `zig build test -Dapp-runtime=none`, `-Dapp-runtime=win32`,
  `zig build test-agent`, P1–P3 — all green.

## Two traps this turn hit, both worth remembering

- **`Start-Process -ArgumentList` does not quote its elements** (the same trap
  go.md records for the upgrade launcher). `-ArgumentList '--command=cmd /k echo
  X'` reaches the app as FOUR argv entries, so `command` became `cmd` and the
  pane looked like a plain shell — a convincing false "the fix does not work".
  A `--command=` with spaces must carry its own quotes.
- **A leftover session layout restores over the window under test.** Two runs in
  a row read as failures because the app rebuilt the PREVIOUS pane instead of
  honoring the new command line. That confound is real behavior, filed as
  **T406**; the acceptance script sidesteps it by being hermetic.

Follow-ups filed: **T405** (`session-persistence = off|on` is documented but
does not parse), **T406** (restore swallows a launch command).
