# T482 - reset-context's verification has no acceptance script: its three branches are only ever tested by hand

## In plain terms

The step that keeps this project's automation alive — restart the session, hand
it the next instruction, check the instruction arrived — is a shell script that
nobody can test except by running it against a real terminal and watching. When
it was wrong (T261) it stayed wrong for days, because a hand test is one that
gets skipped. A small script that sets up the three panes and asserts the three
outcomes would turn a five-minute manual ritual into one line, and would notice
the next regression the day it lands rather than the day it stalls the loop.

## Goals

- [ ] `test\win32\reset-context-verify.ps1` exercises all three verdicts
- [ ] It runs unattended and prints one `ALL PASS` / `N FAILURE(S)` line
- [ ] It cleans up its panes even when it fails

## Summary

`reset-context.sh`'s read-back decides whether the loop's continuation was
delivered. T261 fixed it to accept two proofs (prompt echoed, or pane
repainting) and to fail only on a pane that shows neither — and validated all
three branches **by hand**, with panes built one command at a time. Nothing
re-runs that. The script also lives in another repo
(`dzearing-claude-marketplace`) and is deployed by copying into the plugin
cache, so there is no CI that would catch a regression either.

That is a bad shape for the one step go.md allows to stop and ask a human: a
false FAILED stalls the loop, and a false PASS hides a dead one.

## The fix

`test\win32\reset-context-verify.ps1`, in the house style (defaults to the
built exe, single `ALL PASS` / `N FAILURE(S)` last line, touches only panes it
made). It does not need a Claude session — T261 showed all three branches can
be driven with ordinary processes:

| Branch | Pane | Expected log line |
|---|---|---|
| prompt echoed | `cmd.exe` (echoes typed input) | `verified: continuation is on screen` |
| pane repainting | `ping -t 127.0.0.1` (paints, ignores input, no echo) | `verified: pane is repainting ...` |
| nothing landed | `ping -t 127.0.0.1 > NUL` (silent, ignores input, no echo) | `RESET-CONTEXT FAILED: ...` |

Run the script from the **active plugin cache** path (resolved out of
`%USERPROFILE%\.claude\plugins\installed_plugins.json`), not the source repo —
the deployed copy is what actually runs, and the two drifting apart is its own
failure mode worth asserting.

Assert on `%TEMP%\reset-context-last.log`, and clean up panes in a `finally`.

## Note for whoever writes it

A tail-based oracle on a TUI is weaker than it looks. `+read --lines=40` on a
live Claude pane can come back as nothing but the two rules and the status bar,
because the TUI paints real blank lines between the transcript and the bottom
chrome — they are interior, so nothing trims them, and they eat the budget. Not
a `+read` defect; a reason to assert on the log's verdict rather than on pane
text.

## Validation

- The new script passes on box, unattended, and leaves no `t261*`/test panes.
- Deliberately reverting the T261 fix in the cache copy makes the "prompt
  echoed" or "repainting" case FAIL — the test can actually catch the bug it
  exists for.
