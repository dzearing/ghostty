# T667 - session-persistence.ps1 cannot be run from inside a Ghoztty pane

## In plain terms

One of the big automated checks refuses to start when it is launched from a
Ghoztty window — which is where every session on this box runs. It stops with
an ABORT that reads like the app is broken, when in fact the check is pointing
at the wrong terminal and (correctly) refusing to touch it.

## Summary

**Already fixed by 328da04b0 (2026-08-09), the same day this was filed.** That
commit — *"The session-persistence harness can be run again, and its 19-day
blocker is gone"* — landed under T89i's banner and never named T667, so the card
stayed open for 30 days describing a defect that was gone within hours of being
written. What it did is exactly what the Details below asked for.

The original report: `test/win32/session-persistence.ps1` guards hermeticity by
running `& $Exe +list` and aborting if anything answers:

```
ABORT: a Ghoztty instance is ALREADY answering on the endpoint '...\zig-out\bin\ghoztty.exe' uses.
```

The guard was RIGHT — but it fired for the wrong reason. Run from inside a
Ghoztty pane, the CLI resolves the pane's baked `$GHOZTTY_IPC_SOCKET` (T118
instance addressability) and dials the USER'S release instance, which answers.
The script never set a `GHOZTTY_PIPE_SUFFIX`, and the suffix is the one thing
that outranks the baked value, so its every CLI call really was aimed at the
user's terminal.

## What the code does now (read, not assumed)

`test/win32/session-persistence.ps1:367-369` dot-sources `lib\BuildMode.ps1` and
`lib\Isolation.ps1` and calls `Set-GhozttyTestIsolation -Tag 'sesspersist'`
**above** the pre-flight guard — the placement the fix turns on, since the
guard's own `+list` is itself a CLI call. `Assert-GhozttyIsolatedBuild` (the
shared T350 gate, adopted at line 375 by T1033) runs first, and
`Assert-GhozttyIsolated` (line 416) proves whose panes are being driven once the
first window is up, before anything is typed or closed.

The Details' last bullet — *"worth checking the same gap in any other script"* —
was answered as a class by **T680**: `test\win32\isolation-meta.ps1` scans every
script in `test/win32/` for a CLI verb without an isolation claim, so the gap
cannot silently reopen in a script written next month. A hand-audit would have
been the wrong deliverable.

## Details

- Fix: `. lib/Isolation.ps1` + `[void](Set-GhozttyTestIsolation -Tag 'sessionpersist')`
  before the existing guard, then assert the endpoint, so the guard measures the
  endpoint the harness will actually use. — **done, as `-Tag 'sesspersist'`.**
- Keep the existing build-mode refusal (T350) exactly as it is — the agent pipe
  is build-mode-derived and no suffix makes a release run safe. — **kept, and
  since T1033 it is the shared gate rather than a local copy.**
- Worth checking the same gap in any other script that guards with a bare
  `+list` rather than through `Isolation.ps1`. — **superseded by T680's scan.**
