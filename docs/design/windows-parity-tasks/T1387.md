# T1387 - A key table you entered by accident can only be explained with the mouse

## In plain terms

When your keyboard suddenly means something else, Ghoztty now shows a small
card at the bottom of the pane naming the key table you are in, and hovering
or clicking that card explains what a key table is (T576). Both of those are
mouse gestures. The person this explanation was written for is mid-typing,
just tripped a chord they did not mean to press, and may never take their
hands off the keyboard — for them the explanation is on screen and out of
reach.

## Goals

- [ ] The explainer is reachable without a mouse
- [ ] Whatever key or affordance that is does not collide with the key table
      itself, which is reinterpreting every key while it is active
- [ ] A screen reader announces the pill and its explanation

## Summary

Filed out of T576, which put Mac's popover text on Windows behind a hover (and
a click, which is Mac's own gesture). Mac has the same limitation, so this is
not a parity gap — it is a gap in the feature on both platforms, and the
Windows seat is where it was noticed.

## Details

Two threads, and the second is the bigger one:

- **A keyboard route.** The obvious candidates all fight the feature: every
  ordinary key is being reinterpreted by the active table, so the route has to
  be something the table cannot swallow (F1 in the pane? a line in the command
  palette? a one-time notice the first time a table is entered, which is the
  option T576's own Details raised and did not take). Worth thinking about
  whether the RIGHT answer is a route to the tooltip at all, rather than
  putting the sentence somewhere a keyboard user already looks.
- **Screen readers.** The pill is a `WS_EX_LAYERED` popup painted with
  `UpdateLayeredWindow` and no UI Automation surface at all, so a screen
  reader says nothing when a key table activates — which is the same
  "something changed and nothing told you" defect T446 existed to fix, for a
  user who cannot see the card. That is likely a `WM_GETOBJECT` /
  `IAccessible` shim on the pill window, and it would be the first one in this
  chrome; the read-only badge and the banner have the same hole.

## Validation criteria

- [ ] An acceptance check drives the keyboard route on a live GUI and asserts
      the explanation is reachable with no mouse input at all
- [ ] The route works while a key table is active (the state it explains)
- [ ] A UIA client (Inspect / a scripted `UIAutomationClient` query) reads the
      pill's name and its explanation back
- [ ] Both `zig build test` lanes, `zig build test-agent`, the `lib` build and
      P1-P3 stay green
