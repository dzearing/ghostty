# T988 - The chooser's focused row fails two acceptance probes that still describe the pre-T828 accent pill

## Summary

Found while converting the chooser probes to the synchronous capture (T942).
Both failures reproduce identically with the default capture and with `-Sync`,
so they are neither new nor a capture artifact — they were red before that work
started and stayed red after it.

Two red assertions, both on the FOCUSED selected row:

1. `test\win32\ipc-machine-chooser.ps1:480` —
   `focused list: the selected row is accent-tinted (b-r = 0 at the pill)`.
   It samples the pill body at `$lr.Left + 14` and demands `b - r >= 25`, which
   is the pre-T828 treatment: an accent-TINTED pill. T828 made the pill a
   neutral wash at two weights and moved the accent onto the 4x16 indicator
   capsule at the leading edge, so a neutral reading here is the shipped
   behavior and the assertion is the thing that is stale. Whatever replaces it
   has to keep the oracle honest — the point of the pair at 479/480 is that a
   region signature alone cannot tell a repaint from a stale capture, so the
   colour half needs a real successor (the indicator's accent), not a deletion.

2. `test\win32\chooser-selection.ps1` section C —
   `focused - the fill IS wash(row bg, 0.16)` reads `#eeeeef` where it wants
   `#51545a`, and then `the selected row is a full row tall (5 px)`. `#eeeeef`
   is a near-white neutral, which is what `chooser_rows.focusRing` derives from
   a dark pill: section C samples the pill's TOP EDGE line
   (`$lr.Top + $fillInsetY`), and that is exactly where §2.2's focus rim lands
   once the list holds keyboard focus. So the probe's chosen sample point
   collides with a treatment that ships on purpose.

   The open question inside this one: section C selects the row with a MOUSE
   click, and `rowPaint` only draws the rim when `focus_visible` is set —
   Windows' own convention is to hide focus visuals while the user is driving
   with the pointer. Either the app is leaving `focus_visible` on after a click
   (a real defect a user would see as a rim appearing on a mouse click), or the
   earlier `ctrl+shift+n` chord legitimately cleared `UISF_HIDEFOCUS` for the
   window and the probe simply has to sample below the rim. Decide from
   evidence before moving either side.

## In plain terms

Two of the tests that check the machine list are still describing the old look
of the selected row — the bright coloured pill that was deliberately replaced
with Windows 11's quiet grey selection. They fail against the app doing the
right thing. One of them may also have caught something real: a focus outline
that shows up when the row is clicked with the mouse, which Windows normally
only shows for keyboard users.
