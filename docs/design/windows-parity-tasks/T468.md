# T468 - A --command= pane dies instead of keeping its shell alive: 'Process exited. Press any key' and +send-keys does nothing

## In plain terms

When you open a terminal and tell it to run something - `--command="tail -f
app.log"`, or the three-pane layout the docs use as their headline example -
the command runs, and then the pane just stops. It shows "Process exited.
Press any key to close the terminal" and nothing you send to it afterwards
does anything. You cannot type in it, and automation cannot drive it. What
should happen is that the command runs and the pane is left at a live shell
prompt, ready for the next thing.

## Goals

- [x] A `--command=` pane is at a live shell prompt after the command finishes
- [x] `+send-keys` into that pane runs what it sends
- [x] The same for `+split --command=` and `--split-command=`
- [x] Covered per shell flavor (cmd, powershell/pwsh, wsl, nu, git-bash), since
      the keep-alive is a per-flavor invocation — cmd, powershell and git-bash
      pass live; pwsh and nu are not installed on this box, so the script runs
      them when they are and prints SKIP when they are not; **wsl is a separate
      defect, filed as T656** (its row of the table is broken identically on
      both paths and was never about the keep-alive being skipped)
- [x] `conformance.ps1` S8.5 goes green without changing what it asserts

## Details

### Measured 2026-08-04, on an isolated instance built from e2787431c

```
ghoztty +new-window --target=ka "--command=echo KA-MARKER"
ghoztty +read --name=ka --lines=12
    KA-MARKER
    Process exited. Press any key to close the terminal.

ghoztty +send-keys --target=ka "echo ALIVE-PROBE" Enter
ghoztty +read --name=ka --lines=12
    KA-MARKER
    Process exited. Press any key to close the terminal.      <- unchanged
```

The pane is inert: the follow-up never runs and leaves no trace. Same shape for
a `+split --command=`-created pane (that is how the conformance failure below
was first seen).

### This contradicts a documented guarantee

CLAUDE.md, `+new-window` / `--shell`:

> On Windows the fallback is `command-shell` then `cmd.exe`, and the invocation
> is per-flavor (**the shell stays alive after the command in every case**):
> `pwsh`/`powershell` -> `-NoExit -Command`, `cmd` -> `/K`, `wsl` -> `-- <cmd>`
> in the default distro, `nu` -> `-e`, anything else (e.g. git-bash) ->
> `-lic "<cmd>; exec shell -li"`.

`cmd /K` does not exit after its command, so a pane that reports "Process
exited" is not going through `/K`. Either the per-flavor keep-alive is not
being applied on this path, or the command is being exec'd directly instead of
through the shell. **Not diagnosed further** - measure which before fixing.

Worth checking as part of that: whether this is a regression. `conformance.ps1`
S8.5 was written against a pane it describes as sitting "at a cmd prompt now",
so the keep-alive worked when that assertion was authored.

### Blast radius

Every `--command=` workflow in the docs. CLAUDE.md's own three-pane example
(`--command="nvim ."`, `--command=zsh`, `--command="tail -f app.log"`) produces
three panes that die as soon as their command returns, and agent panes started
this way cannot be driven with `+send-keys` at all. It is invisible for a
long-running command (`tail -f` never returns) and immediate for anything that
finishes, which is probably why it has gone unnoticed.

### How it surfaced

Found while validating T441 (test isolation). `test/win32/conformance.ps1`
S8.5's last two assertions send an OSC 7777 sequence from inside the `tabchk`
pane, which was created with `--command=powershell -NoProfile -File ...`. The
pane's process exits, so the OSC command line is typed into a dead pane and the
window title never changes:

```
FAIL OSC needs_input set
T25 CONFORMANCE: 1 FAILURE(S)
```

Reproducible: 3/3 runs, on a fresh build of HEAD (e2787431c), against a
T441-isolated instance whose server exe was asserted to be
`zig-out\bin\ghoztty.exe`. **Not caused by T441** - `conformance.ps1` loads
`lib\CleanSlate.ps1`, which has dropped the inherited `$GHOZTTY_IPC_SOCKET`
since T118 (f84754940, 2026-08-03), so it was already driving this same debug
build before the isolation change.

`ipc-p3.ps1` sends the identical OSC line and PASSES, which is the control:
its target pane is a bare `+split` (a live shell), not a `--command=` pane. The
difference is the keep-alive, not the OSC path.

## Root cause (measured 2026-08-09)

**Not a regression, and not the wrap table** — `wrapShellCommandArgv`
(`src/apprt/ipc/args.zig`) was correct and unit-tested the whole time. It was
only ever reached on the plain-ConPTY path, and with `session-persistence` on —
the default since T99 — every local pane is agent-backed instead. Confirmed on
box: the failing pane's `+list --json` leaf carries a `session_id`.

That branch of `IpcHandlers.handleNewWindow` forwarded the command as a RAW
string in `OPEN.command`, with the comment "never locally shell-wrapped — the
agent applies its own shell's convention". The agent then synthesized
`cmd.exe /c <cmd>` (`pty_child.windowsCommandArg`), which exits.

That comment is right for a CROSS-MACHINE agent and wrong for the local one,
and the reason the hole is Windows-shaped is worth writing down: the keep-alive
convention is expressed differently on the two platforms. POSIX folds it into
the command STRING (`<cmd>; exec <shell> -li`), which rides `OPEN.command`
untouched and keeps working through the agent for free — which is why the Mac
seat never saw this. Windows spells it in ARGV (`cmd /K`, `pwsh -NoExit
-Command`), and argv cannot ride a command string.

So the fix does not touch the table or the agent's synthesis: a LOCAL-agent
pane sends the wrapped invocation as `OPEN.argv` — the agent's existing
exec-verbatim seam, already used for the shell-integration argv rewrite (T04c/
T151) — while `OPEN.command` still travels so the agent records the raw command
as the session's human-readable label (`+sessions`, the session-interrupted
notice). New field `command_argv` on `Surface.Overrides.Remote` →
`CoreSurface.RemoteBackend` → `termio.Remote`; it is deliberately NOT the
existing `argv`, because `argv` is replayed on the `notify` fresh-shell OPEN
and re-running the recorded command there is precisely what T230 forbids.
`auto`/`prompt` relaunch DO send it — those paths exist to re-run the command,
so it should come back the way it was opened.

`-e` is left verbatim on both paths (control arm H): `-e` means "exec exactly
this", so its pane exiting with its command is correct, not the same bug.

## Validation

- [x] `test/win32/ipc-command-keepalive.ps1` (new) — ALL PASS. Arms A–E cover
      `--command=` on cmd / powershell / git-bash, `+split --command=`, and
      `--split-command=`; each asserts the command RAN, no `Process exited`
      tombstone, and a follow-up `+send-keys` executes. F runs pwsh/nu when
      installed (SKIP here). Controls: G the pane is agent-backed (so the file
      cannot go vacuous if persistence ever defaults off), H `-e` is still not
      wrapped.

      `KA-MARKER` then a live `D:\git\ghoztty>` prompt, and
      `echo ALIVE-PROBE` runs.
