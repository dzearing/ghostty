# T468 - A --command= pane dies instead of keeping its shell alive: 'Process exited. Press any key' and +send-keys does nothing

## In plain terms

When you open a terminal and tell it to run something - `--command="tail -f
app.log"`, or the three-pane layout the docs use as their headline example -
the command runs, and then the pane just stops. It shows "Process exited.
Press any key to close the terminal" and nothing you send to it afterwards
does anything. You cannot type in it, and automation cannot drive it. What
should happen is that the command runs and the pane is left at a live shell
prompt, ready for the next thing.

## Goals

- [ ] A `--command=` pane is at a live shell prompt after the command finishes
- [ ] `+send-keys` into that pane runs what it sends
- [ ] The same for `+split --command=` and `--split-command=`
- [ ] Covered per shell flavor (cmd, powershell/pwsh, wsl, nu, git-bash), since
      the keep-alive is a per-flavor invocation
- [ ] `conformance.ps1` S8.5 goes green without changing what it asserts

## Details

### Measured 2026-08-04, on an isolated instance built from e2787431c

```
ghoztty +new-window --target=ka "--command=echo KA-MARKER"
ghoztty +read --name=ka --lines=12
    KA-MARKER
    Process exited. Press any key to close the terminal.

ghoztty +send-keys --target=ka "echo ALIVE-PROBE" Enter
ghoztty +read --name=ka --lines=12
    KA-MARKER
    Process exited. Press any key to close the terminal.      <- unchanged
```

The pane is inert: the follow-up never runs and leaves no trace. Same shape for
a `+split --command=`-created pane (that is how the conformance failure below
was first seen).

### This contradicts a documented guarantee

CLAUDE.md, `+new-window` / `--shell`:

> On Windows the fallback is `command-shell` then `cmd.exe`, and the invocation
> is per-flavor (**the shell stays alive after the command in every case**):
> `pwsh`/`powershell` -> `-NoExit -Command`, `cmd` -> `/K`, `wsl` -> `-- <cmd>`
> in the default distro, `nu` -> `-e`, anything else (e.g. git-bash) ->
> `-lic "<cmd>; exec shell -li"`.

`cmd /K` does not exit after its command, so a pane that reports "Process
exited" is not going through `/K`. Either the per-flavor keep-alive is not
being applied on this path, or the command is being exec'd directly instead of
through the shell. **Not diagnosed further** - measure which before fixing.

Worth checking as part of that: whether this is a regression. `conformance.ps1`
S8.5 was written against a pane it describes as sitting "at a cmd prompt now",
so the keep-alive worked when that assertion was authored.

### Blast radius

Every `--command=` workflow in the docs. CLAUDE.md's own three-pane example
(`--command="nvim ."`, `--command=zsh`, `--command="tail -f app.log"`) produces
three panes that die as soon as their command returns, and agent panes started
this way cannot be driven with `+send-keys` at all. It is invisible for a
long-running command (`tail -f` never returns) and immediate for anything that
finishes, which is probably why it has gone unnoticed.

### How it surfaced

Found while validating T441 (test isolation). `test/win32/conformance.ps1`
S8.5's last two assertions send an OSC 7777 sequence from inside the `tabchk`
pane, which was created with `--command=powershell -NoProfile -File ...`. The
pane's process exits, so the OSC command line is typed into a dead pane and the
window title never changes:

```
FAIL OSC needs_input set
T25 CONFORMANCE: 1 FAILURE(S)
```

Reproducible: 3/3 runs, on a fresh build of HEAD (e2787431c), against a
T441-isolated instance whose server exe was asserted to be
`zig-out\bin\ghoztty.exe`. **Not caused by T441** - `conformance.ps1` loads
`lib\CleanSlate.ps1`, which has dropped the inherited `$GHOZTTY_IPC_SOCKET`
since T118 (f84754940, 2026-08-03), so it was already driving this same debug
build before the isolation change.

`ipc-p3.ps1` sends the identical OSC line and PASSES, which is the control:
its target pane is a bare `+split` (a live shell), not a `--command=` pane. The
difference is the keep-alive, not the OSC path.

## Validation

- The measured probe above, as an acceptance script under `test/win32/`: a
  `--command=` pane accepts a follow-up `+send-keys` and runs it. Assert per
  shell flavor.
- `test/win32/conformance.ps1` back to ALL PASS with S8.5 unmodified.
- `test/win32/ipc-p1.ps1` stays ALL PASS (it creates `--command=` panes too,
  but only asserts registration, so it does not currently catch this).
