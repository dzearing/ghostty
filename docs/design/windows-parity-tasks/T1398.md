# T1398 - A busy LOCAL pane closes with no confirmation - Ctrl+Shift+W does not prompt

## Summary

`test\win32\close-confirm-idle.ps1` scores red on the two sections whose subject
is the POSITIVE half of T41: with `ping -n 100 127.0.0.1` demonstrably running
under the pane's shell (asserted from `Win32_Process` in the line immediately
above), Ctrl+Shift+W produces **no confirmation dialog**.

```
  PASS A/exec ping is running under the shell (1 descendants)
  FAIL A/exec busy shell: ctrl+w opens the confirm dialog
  PASS A/exec ctrl+c leaves the shell with no descendants (found 0)
  PASS A/exec idle shell: ctrl+w opens NO confirm dialog
```

Both backends fail the same way (`A/exec` and `B/agent`), and in both the pane
survives the chord - so the close did not merely proceed unconfirmed, the whole
close appears not to have run. The IDLE cases in the same sections pass, which
means the chord IS reaching the app: the difference is entirely the busy branch.

## In plain terms

Hitting the close-pane shortcut while a build, a test run or an install is still
going is supposed to stop and ask. Right now it does not ask - and in the runs
seen so far it does not close either, so the shortcut simply appears dead
whenever anything is running. Either way the guard that stands between a stray
keystroke and a killed build is not doing its job.

## Details

Found on 2026-09-06 while validating T1390 (the remote Disconnect offer), on
commit `4556380e9` plus that change. **It is not T1390's doing**: the busy branch
in `Surface.close` is byte-identical before and after that change, which only
adds a preceding `if (offering)` arm that a LOCAL window never enters
(`Window.remote_machine` is null, and Zig's `and` short-circuits before the pane
facts are read). The same failure reproduces from `remote-disconnect.ps1`'s own
local section, where the pane DID close silently - so the two symptoms (no
dialog + no close, vs no dialog + closed) may not be one bug.

Where to look:

- `Surface.close` (`src/apprt/win32/Surface.zig`) - the `process_active and
  !self.shellIsIdleNow()` gate. `process_active` is the core's `cursorIsAtPrompt`
  verdict; if shell integration now DOES emit OSC 133 for the configured shell,
  a busy shell could be reported as "at the prompt" and skip the confirmation
  entirely. That would explain both symptoms and is the first thing to measure.
- `Surface.shellIsIdleNow` / `ProcessTree.snapshot` - the other half of the gate.
  A snapshot that fails answers "not idle", so this direction cannot suppress a
  dialog on its own.
- Whether `close_surface` reached `Surface.close` at all in the A/exec case,
  where the pane survived.

Start by instrumenting the two inputs to that `if` rather than by changing it:
the two symptoms have to be reconciled before a fix means anything.
