# T463 - ghoztty +split --view=git-diff:<revspec> is accepted by the CLI but renders nothing on Windows

## In plain terms

A viewer pane can now show a git diff — `--view=git-status:` for what you
have changed right now, `--view=git-diff:main...HEAD` for a range — with the
files listed down the side and the changes rendered like a review page. That
shipped for the Mac. On Windows the same command is accepted, the shared
page assets are already in the build, and then nothing usable appears. When
this lands, the command draws a diff here too.

## Goals

- [x] `--view=git-status:` and `--view=git-diff:<revspec>` open a diff viewer
      pane on Windows, from both `+split` and `+new-window`
- [x] The repository is resolved the same way the Mac resolves it — from
      `--working-directory`, else the caller's cwd — and a value that names
      no repo fails with a legible in-page error rather than a blank pane
- [x] A bad revspec is reported, not swallowed
- [x] `+list --json` reports a diff pane's location the way it reports any
      other viewer location

## Evidence

The CLI half already crossed over with the merge. `src/cli/view_arg.zig`
knows the two schemes (`isDiffView`) and deliberately passes them through
path resolution untouched, so a win32 app now receives
`--view=git-diff:main...HEAD` verbatim. Nothing under `src/apprt/win32/`
matches `git-diff`, `git-status` or `isDiffView`, so the win32 viewer
classifies the value by its own rules — which is to say, wrongly.

The page itself is **shared and already present**: `src/viewer/diff.css`
(385 lines) and `src/viewer/diff.js` (925 lines) arrived with the merge, and
`viewer.html`/`viewer.js` already reference them. So this task is not a
rendering project — it is git plumbing plus wiring the win32 viewer to load
the diff page with the data it wants.

## The Mac counterpart

`macos/Sources/Features/Viewer/ViewerGit.swift` (444 lines) runs git and
shapes the payload; `ViewerDiffSpec.swift` (316) parses the scheme —
`view_arg.isDiffView` is documented as mirroring `ViewerDiffSpec.parse`, so
the two must keep agreeing; `ViewerDiffPanel.swift` (296) is the pane.
`ViewerDiffSpecTests.swift` and `ViewerDiffPaneTests.swift` are the
behavior contract worth porting to the `none` lane.

The native **file tree** side panel (`ViewerDiffTree.swift`,
`ViewerSidePanel.swift`) is deliberately NOT in this task — see T464.

## What landed

Three pieces, split the way every other win32 port of a Swift feature is:

- **`src/apprt/win32/viewer_diff.zig`** (pure, asserted in the `none` lane) —
  the spec parse and its canonical location, the table of git invocations
  (`--name-status`/`--numstat`/patch, `git show --format= -m --first-parent`
  for a bare revision), the `-z` output iterators, and the two
  `window.__viewer` calls the page reads. `cli/view_arg.isDiffView` is
  IMPORTED rather than repeated, so the CLI's "do not path-resolve this" test
  and the viewer's "this is a diff" test cannot disagree.
- **`src/apprt/win32/ViewerDiffProbe.zig`** — one worker slot per pane, off the
  message loop: repository root, default base for a bare `git-diff:`, the file
  list, and one file's patch (synthesized for an untracked file, which git will
  not diff). A request arriving while a worker is out is deferred and re-issued
  from the completion, which is what keeps the 2s poll from stacking spawns.
- **`ViewerPane`/`viewer_content`** — `Mode.diff` as a third thing the bundled
  template renders, the canonical location on `navigate`, the first listing
  asked for when the page says it is ready, `WM_APP_VIEWER_DIFF` as the only
  place the answer is read, and a working-tree poll that redraws only when the
  file list actually moved.

`git_run.captureAlloc` is new and load-bearing: the fixed-buffer `capture`
cannot serve a diff, because a `readAll` that stops on a full buffer leaves git
blocked writing into a pipe nobody drains and the `wait` after it never
returns.
