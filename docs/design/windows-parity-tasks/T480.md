# T480 - ProcSampler cpu_pct test fails on a busy box - a floor lane can go red for reasons that have nothing to do with the code

## Summary

Found under **T443** while soaking a test binary under deliberate CPU
contention. `scripts\test-binary-soak.ps1 -Concurrency 32` (32 copies of the
win32 test binary on 32 logical cores) produced **4 failures in 32 runs**, all
of them the same test, and no crashes:

```
3792/3858 remote.agent.proc.test.ProcSampler: a genuinely busy thread reports
          a plausible per-core cpu_pct ... FAIL (TestUnexpectedResult)
          std\testing.zig:607 in expect
          src\remote\agent\proc.zig:956
```

The test starts a thread that spins, samples it, and asserts the reported
per-core `cpu_pct` clears a floor. That is a sound assertion **on an idle
box**: the spinner owns a core, so the sampler must see it near 100%. On a
saturated box the spinner gets a slice of a core like everything else, the
sampled percentage lands under the floor, and the test fails while the code
under test is behaving perfectly.

The same binary, run one process at a time, passes: 10/10 bare and 26/26 in
T473's control arm. So this is purely a function of machine load, at roughly a
**12% failure rate at 32x contention**.

## In plain terms

One of our tests measures how busy a thread is and expects a high number. That
only holds when the machine has a spare core to give it. Run the tests while
the machine is doing anything else demanding and the test fails even though
nothing is broken - so a red test result stops meaning "something is wrong",
which is the one thing a test result has to mean.

## Why it matters beyond the flake

T443 exists because nobody can tell a real failure from noise in these lanes.
A test whose result depends on what else the box is doing is a second source
of exactly that noise, and it is the cheap one to remove. Anyone running
`floor-lane.ps1` while a build, a soak, or the user's own work is in flight can
be handed a red lane with a green codebase.

## Goals

- [x] Make the assertion independent of machine load - measure the sampler
      against a *known* quantity rather than against "a core's worth of work".
      Done by T346 (099bd6b5c, 2026-08-05, one day after this task's failing
      measurement): the test burns a measured amount of actual CPU time via
      `selfCpuNs` and asserts the sampler reports at least half of that burn
      spread over the outer window - proportional, so load shrinks both sides
      together.
- [x] Whatever replaces it must still fail if the sampler reports nonsense
      (zero, negative, or > 100 per core) - the test's purpose is real.
      Zero/negative/undercount were caught by T346's floor; the missing half
      was OVER-reporting (an inverted unit conversion would sail past a floor).
      This task added a ceiling assert: the burn spread over the inner
      between-samples window, doubled for skew, is a hard upper bound a correct
      reading sits under. Load only shrinks a correct reading, so the ceiling
      cannot flake on a busy box.
- [x] Re-soak at `-Concurrency 32` and see 0 failures in 32 runs. Done
      2026-08-15: `-Mode standalone -Runs 32 -Concurrency 32` (the original
      contention condition; `-Concurrency` is standalone-only since T832) -
      **ProcSampler failed 0 of 32** against the pre-fix 4 of 32. A bonus
      build-runner soak (32 sequential lane runs) was also fail=0 crash=0.
