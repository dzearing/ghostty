# T1293 - A UTF-8 BOM in a commit message file lands in the subject and the activity feed

## In plain terms

Commit titles are what the dashboard's activity feed shows as headlines. One of
them now starts with three stray characters that nothing can remove, because
the file the message came from was written with an invisible marker at the
front and git took it as part of the first word. Anyone reading the feed sees
it; nothing warned about it.

## Summary

`9afc60732` has subject `\xEF\xBB\xBFchore(tracker): record the commit that
closed T370`. It was written with PowerShell 5.1's `Set-Content -Encoding utf8`,
which emits a BOM in that edition, and `git-commit-guard.ps1` passed the file
straight to `git commit -F`. Git does not strip a BOM from a message file, so
it is in the subject permanently.

Only 1 of the last 20 subjects has one, so this is not a standing pattern - it
is a trap that catches whoever reaches for `Set-Content` on the message file
instead of a BOM-free writer.

## Details

T1245 already made the guard read the message file (refusing one that is
missing, empty, or already committed). A BOM check is the same read: refuse a
message file whose first bytes are `EF BB BF`, naming the remedy (write it
without a BOM - `[IO.File]::WriteAllText`, or a heredoc). Refusing is better
than silently stripping: a message file with a BOM was written by a tool that
will do it again elsewhere, and the author should see that.

Consider covering the same trap for the OTHER text the loop writes through
PowerShell - task files, log entries, digests - though those are markdown and a
BOM there is cosmetic rather than permanent.

Per go.md's rule, a new refusal in the guard ships with the demonstration that
it can fire: a section in `test\win32\go-loop-guard.ps1` (the guard's harness,
section W is the commit path) that writes a BOM'd message file, runs the guard,
and asserts it is refused and nothing was committed.

## Validation criteria

- [ ] `git-commit-guard.ps1 commit` refuses a `-MessageFile` starting with a
      UTF-8 BOM, names the bytes and the remedy, and commits nothing
- [ ] A BOM-free message file still commits normally (positive control)
- [ ] The refusal is demonstrated in `test\win32\go-loop-guard.ps1` and that
      harness passes
- [ ] `test\win32\gate-negatives.ps1` still passes with the new refusal
      declared
