# T1293 - Defender quarantines Ghoztty as Wacatac.C!ml

## In plain terms

You install Ghoztty on a new machine and Windows Defender decides it is a
trojan, quarantines the program, and takes the files away. Nothing is left to
run. This is worse than the SmartScreen warning, because there is no "run
anyway" - the files are gone.

## What the user hit (2026-09-03)

> "i installed ghoztty on another machine and defender quarantined saying
> ghoztty.com and ghoztty.exe were compromised with Trojan:Script/Wacatac.C!ml"

## Evidence gathered at the time

**Provenance is clean and auditable.** `win-v1.36.2` was built and published by
`github-actions[bot]` in run 33777624339 from `release-windows.yml` on
`ubuntu-latest`, out of this public repository. There is no local packaging
step, no third-party binary drop, and no hand-uploaded asset in that path.

**The same binaries do not trip Defender on the dev box.** Checked directly:
`Get-MpThreatDetection` reports no ghoztty detections, `Get-MpPreference` shows
**no exclusion** covering the install directory or the repo, and cloud
protection is on (`MAPSReporting = 2`, Advanced). Identical files, full
protection, no exclusion, no detection - so the verdict is machine-specific
rather than a property of the bytes.

**The detection name is Microsoft's generic ML bucket.** The `!ml` suffix marks
a machine-learning verdict rather than a signature match, and `Wacatac.*!ml` is
the bucket that fires on low-reputation, unsigned, recently-created
executables. Every one of those describes our release.

**Two of our own choices make us an ideal false-positive candidate:**

1. **The build is unsigned** (D87 - the user chose to stay unsigned and explain
   the SmartScreen warning). An Authenticode signature plus accumulated
   reputation is the single largest input to these ML verdicts. This report is
   new evidence bearing on that decision: D87 weighed a *warning*; quarantine
   is a *deletion*.
2. **`ghoztty.com` is a PE32+ binary with a `.com` extension** (T245 - it is
   the console-subsystem twin, so PowerShell waits for it and wires
   redirection). That shape - an executable whose extension does not match its
   format - is a long-standing heuristic trigger, independent of signing.

**Not yet established:** independent confirmation from a second scanner. That
is the first thing to do, and this task must not assume the answer.

## What to do

1. **Verify rather than assume.** Submit both files to VirusTotal and compare
   engines; a lone Defender ML hit with everything else clean is the signature
   of a false positive, while multiple independent detections would mean
   something else entirely and this task becomes an incident.
2. **Report it to Microsoft.** The Security Intelligence submission portal
   (`microsoft.com/en-us/wdsi/filesubmission`) takes a software-developer
   false-positive report; these are typically corrected within days, and the
   correction reaches every machine. This is the actual remedy and it is free.
3. **Reopen the signing question.** D87 chose unsigned on the strength of "a
   warning most people click through". A quarantine is not clickable-through.
   Re-put the decision to the user with this evidence attached (see T1246,
   which was skipped on that answer).
4. **Consider the `.com` shape.** If submission does not clear it, test whether
   the `.com` twin alone drives the verdict; if so, weigh alternatives that
   keep T245's console behaviour without the extension mismatch.
5. **Tell the user before they meet it.** Until it is cleared, the download
   page should say plainly that Defender may quarantine the files and what to
   do about it - the same honesty the SmartScreen note now has.

## Validation criteria

- [ ] Both binaries are submitted to VirusTotal and the result recorded here -
      engine names and counts, not a summary.
- [ ] A developer false-positive report is filed with Microsoft, with the
      submission ID recorded.
- [ ] A fresh install on a clean machine completes without quarantine, verified
      after Microsoft's correction lands.
- [ ] The signing decision is re-put to the user with this evidence.
- [ ] While the detection stands, the website says so and says what to do.
- [ ] If independent scanners disagree with the false-positive reading, this
      task is escalated as a supply-chain incident and the release is pulled.
