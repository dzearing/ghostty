# T612 - macOS never skips the close confirmation for a cross-machine pane whose remote shell emits no OSC 133

## In plain terms

Close a pane on the Mac that is running a shell on another machine, and Ghoztty
asks "a process is still running, close anyway?" even when nothing is running —
every single time, so the question stops meaning anything. It only happens when
the far machine's shell does not announce where its prompt is, which is exactly
what a Windows machine's `cmd.exe` or PowerShell does not do. The fix is to ask
that machine instead of guessing; it already knows the answer and already sends
it.

## Summary

T356 (win) made the agent sample each bound session's process subtree once a
second and push `META{has_descendants}` on change, gated on the negotiated
`session_busy` capability. The sampling is in shared agent code and works on all
three OSes; the win32 app consumes it in `Surface.shellIsIdle`. The macOS app
does not consume it at all.

## Details

macOS decides "is a process still running in this pane?" from the core's
`cursorIsAtPrompt`, which reads the shell's OSC 133 semantic prompt marks. That
is correct for a local zsh/bash/fish, and for a remote POSIX shell with shell
integration — but a session whose shell is `cmd.exe` or stock PowerShell emits
no marks at all, so the answer is permanently "running" and the confirmation is
permanently shown. This is the same defect T41 fixed on Windows for local panes
and T356 fixed on Windows for cross-machine ones.

The materials are already on the wire and need no protocol work:

- `protocol.capability.session_busy` + `protocol.Meta.has_descendants`
  (`src/remote/protocol.zig`).
- Agent sampling: `SessionStore.sampleDescendants` /
  `sampleDescendantsIn` (`src/remote/agent/session.zig`), over
  `proc.snapshotParents` + `descendants.hasDescendants`. The macOS arm of
  `snapshotParents` is implemented (libproc `proc_listpids` +
  `PROC_PIDTBSDINFO`).
- Client caching: `inbound_ring.Channel.signalHasDescendants` →
  `termio.Remote.busy_state` → `Remote.shellHasDescendants()`, which already
  returns null (⇒ confirm) when the link is not connected.

So the Mac work is the consumer: where the Swift close path asks the core
whether a process is active, prefer `shellHasDescendants()` when it has an
answer, and fall back to `cursorIsAtPrompt` when it does not. Worth deciding at
the same time whether a LOCAL macOS pane should use it too (a local
session-persistence pane is agent-backed, so the same push is available) or
whether OSC 133 remains the better local signal.

## Validation criteria

- [ ] A cross-machine pane attached to a shell that emits no OSC 133, sitting
      idle, closes on the Mac with NO confirmation dialog.
- [ ] The same pane with a long-running command under it still confirms.
- [ ] An agent that does not advertise `session_busy` (older build) still
      confirms both ways — the skew degrades to today's behavior.
- [ ] A pane whose link has dropped confirms, rather than trusting a value
      pushed before the disconnect.
- [ ] macOS regression run green.
