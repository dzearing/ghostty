# T120 — `--color=random` tints are indistinguishable on Windows

## Summary

`--color=random` window tints are indistinguishable on Windows — `color_math.randomDark` uses HSB s `0.2–0.3` / b `0.1–0.15`, the exact ranges main replaced in `45f4f2250` because every window landed on the same near-black (brightest channel ~26–38/255, hue imperceptible). Fix: raise to s `0.33–0.46` / b `0.13–0.18` to match, and keep the doc comment's "IPCServer.randomDarkColor parity" claim true. Trivial, self-contained, has a unit-testable pure function already

## Details

`color_math.randomDark` generates HSB with saturation `0.2–0.3` and brightness
`0.1–0.15`. Those are precisely the ranges main replaced in `45f4f2250`, whose
message records why: every window landed on the same near-black (brightest
channel ~26–38/255) and the hue was imperceptible, so `--color=random` produced
windows you could not tell apart.

Main's replacement is saturation `0.33–0.46`, brightness `0.13–0.18` — still
comfortably dark, but lifted off pure black so the hue reads. Port the same
numbers. The function's own doc comment claims "IPCServer.randomDarkColor
parity", which is currently false; fixing the code makes it true again.

Smallest task in this band: one pure function that already has a unit-test
harness in every app-runtime lane.

## Done 2026-08-03

`color_math.randomDark` now generates saturation `0.33–0.46` / brightness
`0.13–0.18`, Mac's numbers from `IPCServer.swift:2042-2043` (read, not assumed:
the Swift carries the same comment about the old ranges landing every window on
the same near-black). The four bounds are named constants
(`random_dark_sat_min` … `random_dark_bri_max`) so the tests assert the range
they came from rather than restating it, and the doc comment's
"IPCServer.randomDarkColor parity" claim is true again.

**The interesting part is the oracle, not the numbers.** The pre-existing unit
test — `!isLight(c)` and `hsb.b <= 0.16` — was GREEN through the entire defect,
and it would stay green under ranges even darker and duller than the ones being
retired. Darkness was never the complaint; *sameness* was. What a viewer
actually sees between two tints is the **chroma**, `max - min` channel, which
works out to `b * s * 255`:

| | sat | bri | chroma range |
|---|---|---|---|
| retired | 0.20–0.30 | 0.10–0.15 | **5 – 11** (typ. ~8) |
| Mac / now | 0.33–0.46 | 0.13–0.18 | **11 – 21** |

So the regression test asserts `chroma >= 10` and `peak channel >= 32` over
1000 samples — a floor the retired ranges could clear only at the single
extreme corner of their box, and never twice in a row. Brightness alone barely
moved (peak 26–38 → 33–46); it is the saturation lift that does the work, which
is why an assertion about "dark enough" could never have caught this.

The on-box script had the same hole and in a second form: `window-color.ps1`
section 5 opened **one** window and asserted its luminance was low. One sample
cannot show that two windows differ — the same shape as T235's "a one-title
window cannot test a width rule". It now opens three, applies the chroma and
peak floors to each, and asserts the three are not all the same tint.

**The negative control found a second thing, and it is the reason the two
epsilons differ.** Running the new tests against the retired constants failed
*both* of them — `min_chroma >= 10`, as designed, and also the range check,
which should have been range-relative and therefore immune. It isn't, because
saturation is read back as `(peak - trough) / peak` and at the retired
brightness `peak` is only ~26, so one 8-bit rounding of the trough moves the
measured saturation by 1/26 = **0.038**. At the new brightness the peak is ~33
and the step is 0.030. The first draft's `± 0.02` was therefore *smaller than
one quantum* — green on 1000 samples but latently flaky. Widened to `± 0.04`,
with the arithmetic written next to it. Brightness needs no such allowance
(`peak / 255`, one step = 0.004). That colors quantize this coarsely at all is
itself a symptom of the defect being fixed.

*Validation:* `zig build test -Dapp-runtime=win32` exit 0, `-Dapp-runtime=none`
exit 0, `zig build test-agent` exit 0. `test\win32\window-color.ps1`
**ALL PASS (33)**, P1–P3 ALL PASS, against a fresh Debug build.

*Negative control:* reverting the four constants to the retired 0.2–0.3 /
0.1–0.15 fails exactly the two `randomDark` unit tests and nothing else
(3737/3807 passed, 2 failed), so the oracle discriminates rather than merely
being green. The control was run at the unit level, where the floor lives; the
acceptance script applies the same two floors to real `+list` tints, so it is
covered by the same argument rather than by its own separate run.
