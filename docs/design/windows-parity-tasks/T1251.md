# T1251 - The terminal picks its graphics driver when it starts, and falls back when the system one is too old

## In plain terms

Ghoztty draws its terminal with the graphics driver the machine hands it, and
today it binds to that one driver the moment it launches. If the driver is too
old - which is exactly what a remote desktop connection gives you - the app
gives up and shows a dialog.

After this, Ghoztty asks the system driver what it can do, and when the answer
is "not enough", it tries a second one instead of quitting. It also says in its
log which of the two it ended up using, so a session that draws slowly is
explainable rather than mysterious.

## Split from

[[T1250]], which asked for the whole remote-desktop story at once. This is the
code half: runtime selection plus the fallback attempt, all of it provable here.
[[T1252]] ships the second driver's files; [[T1253]] proves the result over a
real remote session.

## What is wrong now

The Win32 GL entry points are bound at build time: `wglCreateContext`,
`wglMakeCurrent`, `wglDeleteContext` are `extern "opengl32"` in
`src/apprt/win32/win32.zig`, `wglMakeCurrent` / `wglGetCurrentDC` again in
`src/renderer/OpenGL.zig`, and glad is loaded with a null loader, which sends it
to its own built-in `opengl32.dll` + `wglGetProcAddress` path. There is exactly
one implementation and no way to reach a second.

That also carries a trap for the fix (noted in T1250): `opengl32.dll` is not a
KnownDLL, so a fallback copy dropped next to `ghoztty.exe` would be loaded by
the static import for **every** launch, silently moving every user with a
perfectly good GPU onto a software renderer. So the entry points have to be
resolved at run time, out of a module this code chose, before any of this is
safe.

## What to build

- A leaf loader module that opens a named GL implementation and resolves the
  WGL entry points plus a glad-compatible `getProcAddress` from it. The system
  one is loaded from System32 explicitly, never by bare name, so an adjacent
  copy cannot pre-empt it.
- `win32.zig`, `Surface.zig` and `OpenGL.zig` call through the loader instead of
  their `extern "opengl32"` declarations, and the static `opengl32` link goes
  away with them - the exe should have no import-table entry for it.
- When the context created from the system module measures below the floor
  (`gl_report.Report.belowFloor()`, T1249), tear that context down and retry
  once against the fallback module. Key off the measurement, never off
  `SM_REMOTESESSION`: a weak GPU or a VM produces the same failure with no RDP
  involved.
- If the fallback is absent or also below the floor, the T1249 dialog stands
  exactly as it is - an honest refusal is still the right ending when nothing
  can draw.
- The log names which module was chosen, its path, and the version/vendor/
  renderer it reported.

## Not in this task

Shipping the fallback binary ([[T1252]]) and About-box reporting - About is
where a user, not a log reader, learns they are on the slow path, and it wants
the fallback to actually exist first.

## What changed

- `src/renderer/gl_loader.zig` (new): opens one named OpenGL implementation and
  resolves the WGL entry points out of it. The system one by EXPLICIT System32
  search (`LOAD_LIBRARY_SEARCH_SYSTEM32`), never by bare name; a fallback by
  full path from `<dir holding ghoztty.exe>\gl\opengl32.dll`, or from
  `GHOZTTY_GL_FALLBACK_DLL` in debug builds. `fallbackRelPath` and `shouldRetry`
  are pure and carry the module's unit tests, so the policy is covered in the
  `none` lane that never touches a Windows API.
- The pixel-format and buffer-swap entry points travel with the implementation
  rather than being taken from gdi32 unconditionally: a standalone GL owns its
  own pixel formats and GDI knows nothing about them. `.system` deliberately
  keeps gdi32's.
- `win32.zig` no longer declares `wglCreateContext` / `wglMakeCurrent` /
  `wglDeleteContext`, `OpenGL.zig` no longer declares its own `wglMakeCurrent` /
  `wglGetCurrentDC` / `SwapBuffers`, `SharedDeps.zig` no longer links
  `opengl32`, and glad is loaded through `gl_loader.gladLoad` instead of null
  (null sends glad to its own `LoadLibraryA("opengl32.dll")`, which would undo
  all of it).
- `Surface.init` splits into a retry wrapper and `initOnce`. On
  `OpenGLOutdated` / `GLInitFailed` from the SYSTEM implementation, with a
  fallback present, it switches and runs `initOnce` again — a WHOLE new window,
  because a pixel format may be set exactly once per device context.
- `GHOZTTY_GL_FORCE_VERSION` (T1249) now applies to the system implementation
  only. That is what makes the fallback observable: a seam that also aged the
  fallback would land the retry on a context reporting 1.1 and the app would
  refuse exactly as if nothing had been tried.

## The design call: fall back on failure, never probe at startup

Deciding up front would mean creating and tearing down a throwaway GL context
on every launch, before the first window — tens to hundreds of milliseconds for
every user, to answer a question that is "system" on essentially every machine.
Taking the fallback on the failure instead costs the 99.9% nothing and costs the
affected machine one extra window creation it was not going to get at all.

The other half of the same call is that the retry is keyed on the MEASURED
context, not on `GetSystemMetrics(SM_REMOTESESSION)`: a weak GPU, a VM and a
stripped-down driver all produce this failure with no Remote Desktop anywhere.

## Validation criteria

- [x] Unit lanes cover the loader's policy — `fallbackRelPath` (subdirectory,
      trailing separator, buffer too small) and `shouldRetry` (retry once, never
      without a fallback, never a second time, never for a non-GL failure).
      Registered in `src/renderer.zig`, so both `-Dapp-runtime=none` and
      `-Dapp-runtime=win32` run them. `floor-lane.ps1 -Lane all`: ALL LANES PASS.
- [x] `dumpbin /imports zig-outin\ghoztty.exe` lists GDI32, USER32, KERNEL32
      and 16 others — and NO `OPENGL32.dll`. An adjacent copy cannot hijack a
      healthy launch, which is what made the fallback safe to ship at all.
- [x] A normal launch still selects the system implementation: arm C of
      `test\win32\startup-failure.ps1` (healthy launch, window, no dialog), and
      arm F5-F7, which is the sharper version — the fallback is IN REACH and
      still not taken, proven by reading `impl=system` back out of the child's
      stderr and asserting `impl=fallback` never appears.
- [x] With the seam forcing the system context below the floor and a fallback
      available, the app starts on the fallback: arm F1-F4. F1/F2 are the
      outcome (window, no dialog); F3/F4 are what stops a build that merely
      dropped the floor check from passing — the log has to name the
      implementation it loaded and the one it drew with.
- [x] With the seam forcing below the floor and NO fallback, the T1249 dialog
      still appears with its wording and a nonzero exit: arm E, unchanged and
      still green.
- [x] Standing floor green: `floor-lane.ps1 -Lane all` (lib, none, win32,
      agent) ALL LANES PASS; ipc-p1 (25), ipc-p2 (20), ipc-p3 (16) ALL PASS;
      `startup-failure.ps1` ALL PASS (34 assertions), which re-stamped its guard.
