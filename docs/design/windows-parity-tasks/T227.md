# T227 - Ctrl+Shift+N surface: pixel-parity and polish pass against the Mac dialog

## Summary

T172/T174/T175/T176 shipped the chooser's structure: owner-drawn rows, a
master-detail layout, a per-row management menu, per-host defaults, and the
account row. Every *control* Mac has now exists on Windows except the two in
T177/T226. **That is not the bar.**

The user restated the bar on 2026-07-31, and it is a correction of what "parity"
has been taken to mean here:

> "Your idea of parity is not the same as mine. I mean, pixel parity, the UX
> looks and feels cohesive and polished and scrubbed, and it isn't just buttons
> that exist in the same place, but it looks like a posh win32 version of the
> MacOS app. The borders look nice. There's a master details view. There are
> ways to get to the activity viewer."

So this task is the finish pass on the whole Ctrl+Shift+N surface: the chooser
(`MachineChooser.zig`, `chooser_layout.zig`, `chooser_rows.zig`,
`chooser_menu.zig`), the Host Settings dialog (`HostSettingsDialog.zig`), and
the relay account row (`RelayAccountRow.zig`) - judged as one cohesive surface,
not as a checklist of controls.

"Posh win32 version" is the operative phrase: **not** a pixel-cloned macOS
dialog on Windows. Native metrics, native focus rings, native accent, native
type - executed to the polish level of the Mac original.

## Details

### Method: measure, do not eyeball

T202 is the precedent and it worked: it read live Windows Terminal pixel by
pixel through `PrintWindow(PW_RENDERFULLCONTENT)`, wrote the findings up as
`docs/design/win32-tab-strip.md`, and every later task painted to that one
agreed target instead of to an opinion. Do the same here.

Two sources for the target, because there is no Mac on this box to screenshot:

1. **The Swift source states its own metrics numerically.**
   `macos/Sources/Features/Remote/MachineChooserView.swift` carries the real
   paddings, corner radii, row heights, font roles, divider treatment, and
   which controls are conditional. Read them out rather than approximating.
2. **Native Windows references for the idiom** - a real Win11 master-detail
   dialog (Settings, Task Manager) captured through `Get-TestWindowPixels`,
   for what a Windows version of the same layout is supposed to look like.

Write the reconciled target up as `docs/design/win32-machine-chooser.md`
(the `win32-tab-strip.md` analog) so this task and any follow-up paint to one
spec.

### The specific things "polished and scrubbed" has to cover

Derive the full list from the measurement above; these are the known suspects,
not the whole set:

- **Borders and rims.** The user called this out directly. The banner card
  (`banner_card.zig`) and the tabs (T206) already share one rim/lift language;
  the chooser predates that work and does not. Import those constants, do not
  re-derive them - the T206 rule.
- **The master-detail seam** - divider weight, gutter widths, and whether the
  detail pane's left edge aligns to anything. `GlassCard.outerMargin` is the
  Mac-side lesson: one margin number everywhere beats per-component fudges.
- **Selection and focus.** Accent-filled pill while key, neutral unemphasized
  when not, a separate hover wash - the same three-state rule the viewer TOC
  follows. Check T203 (system accent + light/dark) is honored here, since the
  chooser is one of the surfaces that breaks in a light theme.
- **Type ramp** - title vs subtitle vs status, one ramp across chooser, Host
  Settings, and the account row.
- **The action row** once T177/T226 land: it becomes a run of up to four
  buttons, which is exactly when uneven gaps and misalignment show.
- **Empty, error, and long-string states.** The cue-banner filter with no
  matches, an unreachable machine, a very long machine name or endpoint.
- **DPI.** Every metric at 100/125/150/200 percent - the tab strip's glyphs
  were sized off an inherited font and broke at scale; assume the same class
  of bug is here.

### Do not re-skin what is about to change

T226 adds the Activity panel and T177 adds its button, both of which change the
detail row's composition. Land those first (they are the deps that matter),
then do this pass across the finished surface - otherwise the polish pass runs
twice. T213 is a dep because the pixel probes need the PrintWindow path.
