# T564 - A task status change leaves no trace, so an un-parked armed watch is indistinguishable from a stray dashboard click

## Summary

set-status rewrites the frontmatter and writes nothing to the task's progress log, and the dashboard's Mark unblocked button flips blocked(reason) to a bare todo. On 2026-08-07 that silently reopened T443 and T474 with no crash occurrence behind it, and the loop spent a turn re-deriving the park for the second time in two days.

## In plain terms

Tasks can be put on hold with a reason attached ("waiting for this crash to
happen again"). Anyone could take one off hold with a single click, and nothing
anywhere recorded that they had done it — or wiped out the reason it was on hold
in the first place. So a stray click looked exactly like a deliberate decision,
and the automated loop kept picking the task back up and spending a whole
session working out that it should still be on hold. After this, every change to
a task's state writes a line into that task's own history saying what it changed
from, what to, and which button or command did it — and taking a task off hold
from the dashboard now asks once, showing you the condition you are overriding.

## Goals

- [x] A status change appends the transition to the task's own `## Progress log`
- [x] The old status is preserved verbatim, so a discarded `blocked(reason)`
      survives somewhere readable
- [x] The dashboard says which button did it, not just that something did
- [x] Taking a task off hold from the dashboard is two clicks, and the second
      one is shown the `unblock:` condition it is overriding
- [x] A no-op status change writes nothing; a bulk pass can opt out on purpose

## Details

Three edits, one behaviour:

- `scripts\parity-tasks.ps1` — `set-status` reads the frontmatter BEFORE
  rewriting it and appends `status: <old> -> <new>` to the task's progress log,
  with `(by <SourceNote>)` when given and `[commit <sha>]` when `-Commit` is
  passed. New `-SourceNote` and `-NoNote` parameters. Nothing is written when the
  status did not actually change, so re-running a command is not an event.
- `scripts\task-dashboard.js` — `/api/status` forwards the page's own button
  label as `-SourceNote "dashboard: <label>"`, sanitised to printable ASCII and
  capped at 120 chars. A request with no label still records
  `dashboard: status button` rather than nothing.
- `scripts\task-dashboard.page.html` — `setStatus()` sends that label; the
  blocked card's **Mark unblocked** button is two-step, re-reading the task's
  `unblock:` condition back at whoever is about to override it (a plain text/
  colour change on the button, deliberately not a `confirm()` — a modal inside
  the viewer pane blocks the whole WebView).

The `-NoNote` hatch exists so a future bulk normalisation does not stamp two
hundred files; it is documented as not-for-ordinary-use, because a status flip
with no receipt is the defect itself.
