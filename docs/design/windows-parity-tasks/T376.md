# T376 - Generic COM callback-object helper: T372 shipped one hand-rolled handler, T373 needs five more

## Summary

T372's summary promised 'a reusable Zig-side callback-object helper with vtable+refcount' and what landed is ONE concrete handler (EnvCompletedHandler in webview2.zig): its QueryInterface/AddRef/Release/free-at-zero body is ~40 lines that every further WebView2 event needs verbatim. T373 alone adds ControllerCompleted, NavigationCompleted, NewWindowRequested and AcceleratorKeyPressed; T375 adds WebMessageReceived. Copy-pasting the refcount five times is five chances to get a lifetime wrong and no way to notice - the same argument T257 made for hoisting the chrome datum. Factor it into a comptime helper parameterized on the interface IID and the Invoke signature, port EnvCompletedHandler onto it (its existing vtable test is the regression oracle), and do it BEFORE the second handler exists rather than after the fifth.

## Details

*Validation:* `zig build test -Dapp-runtime=win32` (the generic's own tests plus
T372's ported handler tests, including the LIVE environment creation, which is
the one test that drives our vtable from the real runtime),
`zig build test -Dapp-runtime=none`, `zig build test-agent`, P1-P3.

### Done 2026-08-02

`src/apprt/win32/com.zig` is the helper; `webview2.zig` lost ~80 lines and its
handler is now an IID plus an `Invoke` body.

**The signature IS the parameterization.** The call site is
`com.Callback(IID_EnvironmentCompletedHandler, onEnvironmentCompleted)` — two
arguments, not five. The context type and both `Invoke` parameter types are read
back off the implementation function with `@typeInfo`, so the vtable slot cannot
disagree with the function it dispatches to; getting that pair out of step by
hand is precisely the bug this task exists to prevent. Every WebView2 handler
interface takes exactly two `Invoke` parameters — `(HRESULT, result)` for the
create-completed pair, `(sender, args)` for the events — so the arity is pinned
at two with a comptime error rather than generalised to a tuple nobody needs;
the test instantiates one of each shape to prove the parameterization actually
varies.

Three things the port settled that the hand-written copy had left open.

**1. The object now carries its own allocator, and that is not a detail.**
`EnvCompletedHandler` freed itself through `self.host.alloc` — fine for exactly
one handler whose context happens to own an allocator. T373's handlers hang off
a `ViewerPane`, which reaches its allocator through its window. `std.mem.Allocator`
**cannot be a field of an `extern struct`** (proven, not assumed: the compiler
says `extern structs cannot contain fields of type 'mem.Allocator'`), so it is
stored as its two words and rebuilt on free. The test for it is a counting
allocator asserting the free lands on the allocator the object was CREATED with —
a leak checker cannot catch freeing through the wrong heap.

**2. The refcount is atomic now.** One interlocked op in one place, versus a
per-handler judgement call about whether a proxy thread can `AddRef` this
particular object. The counts the tests assert are unchanged.

**3. `QueryInterface` answering for another handler's IID is now a tested
failure.** The old test rejected a made-up GUID; the new one rejects the *sibling
handler's* real IID, which is the mistake that actually happens once five
handlers share a file — and it hands the caller a pointer whose `Invoke` has a
different signature.

The regression oracle held: T372's "the completed handler is a well-behaved COM
object", "a failing Invoke reports the failure instead of dereferencing null" and
the live-environment test all pass unmodified except for the `create(alloc, ctx)`
argument. The live one is the strongest evidence — the real runtime called our
generated `Invoke` through our generated vtable and the environment reported
`150.0.4078.105`, so the ABI survived the rewrite.

`com.zig` is listed in `src/apprt/win32.zig`'s test block in its own right rather
than riding in as `webview2.zig`'s import: the lane should name what it checks.
It imports only `std`, but it stays a win32-lane module deliberately —
`callconv(.winapi)` is a Windows concept and the none lane also runs on the Mac
seat, where a compile error would be a floor I cannot reproduce here.

(log line `[webview2] (warn): live environment reports browser version
150.0.4078.105`), `test-agent` exit 0, P2/P3 ALL PASS. P1's first run reported
