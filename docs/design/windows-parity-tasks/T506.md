# T506 - running ghoztty from a terminal on Windows opens in home, never the current directory (probableCliEnvironment hardcoded false)

## In plain terms

On Mac and Linux, typing `ghoztty` in a terminal opens the new window in the
folder you were standing in. On Windows it always opens in your home folder,
no matter where you ran it from. Anyone who navigates to a project folder and
launches the app from there lands somewhere else.

## Summary

`Config.probableCliEnvironment()` (src/config/Config.zig, ~5181) hardcodes
`.windows => return false`, with an upstream comment calling Windows "not a
real supported target". This fork ships win32 as a first-class runtime, so the
consequence is a real parity divergence: the `working-directory` default
resolves to `.home` for EVERY Windows launch, while macOS/Linux CLI launches
resolve `.inherit` and open in the caller's cwd.

Found while fixing T236 (the auto-launch startup window ignoring
`--working-directory`): T236 worked around it for the auto-launch path by
passing the directory explicitly on the spawned instance's command line, but a
human typing `ghoztty.exe` in cmd/PowerShell still gets home.

Detection is genuinely non-trivial for a GUI-subsystem exe (it never attaches
to the parent console, so `GetConsoleWindow()` is null even when launched from
cmd — and debug builds link the Console subsystem, so any console-based probe
would behave differently per build mode). Candidate signals to evaluate:

- `AttachConsole(ATTACH_PARENT_PROCESS)` succeeding (then detach) — the parent
  has a console iff launched from one.
- Argv length > 1 (upstream's own weak signal; `std.os.argv` is POSIX-only, so
  it needs `std.process` on Windows).
- Parent-process inspection (cmd/powershell/pwsh/wt) — fragile, last resort.

Whatever the mechanism, the auto-launched instance must NOT start reading as
"CLI" in a way that breaks T236's B4 (the startup window must not silently
inherit a detached launcher's System32 cwd) — the explicit argv pass from T236
already pins that case, but the negative-control run must confirm it.

## Goals

- [x] Typing `ghoztty` in a shell opens the window in that shell's directory.
- [x] A launch that is not from a shell (double-click, `Start-Process`, a
      service) still opens in home.
- [x] The detection is one documented rule in one module, not a guess spread
      across the win32 layer.
- [x] Nothing else about a Windows launch changes — in particular the default
      shell stays `cmd.exe` and is never taken from a git-bash `$SHELL`.

## What landed

`probableCliEnvironment()` now asks `src/os/cli_launch.zig` on Windows instead
of returning a hardcoded `false`. Three signals, because two different PE
subsystems answer differently:

1. **`GHOZTTY_CLI_LAUNCH=1`** — set by `runComShimGuiRespawn` on the detached
   `ghoztty.exe` it starts. PATHEXT resolves a bare `ghoztty` to the
   `ghoztty.com` twin (T245), whose GUI path respawns DETACHED: the child has
   no console and a parent already exiting, so this launch — the one a human
   actually performs — cannot be probed and is told instead. The child consumes
   the variable and clears it, so no pane's shell inherits it.
2. **A console shared with someone else** (`GetConsoleProcessList() > 1`) — a
   console-subsystem build (every Debug build) launched from a shell inherits
   that shell's console. A console *created for* us — `CREATE_NEW_CONSOLE`,
   `CREATE_NO_WINDOW`, an Explorer double-click — holds exactly one process,
   which is what keeps every harness launch in this suite non-CLI.
3. **No console at all, but a console-owning parent**
   (`AttachConsole(ATTACH_PARENT_PROCESS)`, released immediately) — a
   GUI-subsystem release exe named directly, which is what MSYS/git-bash
   resolves since its `.exe` magic does not cover `.com`.

Two shared-core edits ride along, both Windows-guarded so POSIX is untouched:

- The CLI default resolves to an **explicit cwd path**, not `.inherit`.
  `.inherit` reports `value() == null`, and a null cwd on an agent OPEN means
  *the agent's* directory (`C:\Windows\System32` for the HKCU Run entry) — the
  exact defect T144 fixed.
- The `$SHELL` lookup stays off on Windows. `SHELL` there is an MSYS artifact
  holding `/usr/bin/bash`, which the win32 spawn cannot execute, so honoring it
  would break every pane of a Ghoztty launched from git-bash.
