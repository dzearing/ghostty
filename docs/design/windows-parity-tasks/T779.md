# T779 - persistence-flag.ps1 is RED: four launches in agent-attach-refused.ps1 and url-scheme.ps1 leave session persistence unstated

## In plain terms

A rule the test suite enforces on itself - every test launch has to say whether
it wants saved sessions restored - is currently being broken by four launches,
so the check that guards it is failing. Nothing a user sees is wrong; the guard
is.

## Summary

Found while running the sweeps for T275 (2026-08-11), and PRE-EXISTING - none of
the four sites was touched by that work.

```
FAIL  A1 no launch leaves persistence unstated (undeclared: 4 of 175)
  agent-attach-refused.ps1:276  $app = Start-OnTestDesktop -Exe $Exe -Arguments @() -StdErr ...
  url-scheme.ps1:359 / :368 / :381  $aN = Start-OnTestDesktop -Exe $exe -Arguments @("$debugScheme`://open/urlwin")
```

T158's rule is state-which-you-want: pass the flag, pass something built from
it, have every caller of your helper pass it, or write a
`# persistence: <reason>` marker. The `url-scheme.ps1` launches are activation
processes whose whole job is to hand a URL to the running instance and exit -
plausibly a marker case rather than a flag case; `agent-attach-refused.ps1`
launches with an empty argument list and is a persistence test, so it probably
wants the flag ON, explicitly.

Decide per site rather than by adding four flags: the point of the rule is that
the launch says what it wants, and a wrong flag is worse than a missing one.

## Validation criteria

- [ ] `test\win32\persistence-flag.ps1` is ALL PASS.
- [ ] Each of the four sites either passes a persistence flag or carries a
      `# persistence: <reason>` marker naming why it does not.
- [ ] `agent-attach-refused.ps1` and `url-scheme.ps1` still pass after the
      change (a launch that starts restoring panes it did not create is exactly
      the T248 poisoning this rule exists to prevent).
