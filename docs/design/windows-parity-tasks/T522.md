# T522 - ctrl+insert copy is swallowed on Windows when nothing is selected (missing performable)

## In plain terms

Pressing Ctrl+Insert (the classic Windows "copy" chord) with no text selected
does nothing — and the program running in the terminal never sees the key
either. With a selection it copies fine. After the fix, the no-selection case
lets the keystroke through to the program instead of silently eating it.

## Summary

Found while fixing T156, same defect class as T154. `Config.zig`'s non-darwin
desktop block (`.{ .physical = .insert }` + ctrl, ~line 6592) binds
ctrl+insert -> `copy_to_clipboard = .mixed` with a plain `put()` and no
`performable` flag. `copy_to_clipboard` returns **false when there is no
selection** (`src/Surface.zig` ~6088–6113), and a non-performable binding
consumes the key even when its action declines — so ctrl+insert with nothing
selected is swallowed whole.

Fix shape (mirror T154/T156): re-bind ctrl+insert in the win32 mirror block
with `putFlags(..., .{ .performable = true })`, next to the ctrl+c mirror
(which is already performable for exactly this reason). Note the Linux/generic
binding also lacks the flag; widening to the shared block would change Linux
behavior and should be its own call (check Mac-seat/upstream intent first).

Landed exactly that shape. Follow-up filed: **T1354** - because performable
bindings are deliberately absent from the binding set's reverse map, the Edit
menu labels Copy/Paste from the non-performable `put()`s in the generic block,
so it likely advertises Ctrl+Ins / Shift+Ins rather than Ctrl+C / Ctrl+V.
