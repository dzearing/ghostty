# T206 - Tab chrome does not share the banner card's visual language

## Summary

User directive 2026-07-30, closing the tab-strip review:

> "the tab should have similar borders to the banner. It should feel cohesive"

The app currently has two independently-invented surface treatments. The pane
banner is a designed card with a documented spec ported from Mac's
`GlassCard`; the tab strip is arithmetic over the terminal background. They
share no constants, no rim, no fill model, and no radius relationship, so they
read as two different products in one window.

Filed SEPARATELY from T202 rather than folded into it because T202 was already
in flight when this came in - a cohesion pass that lands after the shape work
cannot be lost this way.

## The banner's language (from `banner_card.zig`, the existing spec)

| Token | Value | Note |
|---|---|---|
| `RADIUS` | 14 px unscaled | Mac `GlassCard.cornerRadius`; squircle on Mac, plain rounded rect in GDI |
| `MARGIN` | 12 px, UNIFORM 4 sides | per-side fudges are what break corner alignment with the viewer TOC card |
| `PADDING` | 12 px uniform | |
| `FILL_LIGHTEN` / `FILL_DARKEN` | white 6% on dark / black 4% on light | a wash over the backdrop, not an opaque color |
| Specular rim | alpha 0.28 top -> 0.10 -> 0.04 bottom | hairline border, brightest at the top, elliptical gradient |
| Shadow | blur 8, dy 4, black 30% | elevation |

The rim is the thing the user is pointing at: a hairline top-lit border is
what makes the banner read as a raised surface, and the tab has nothing
equivalent.

## The trap: do NOT just copy the numbers

Cohesion here is a shared **language**, not shared constants, and the naive
reading would look worse than what we have:

- **Radius.** 14 px on a ~32 px tall tab is nearly half its height - that is a
  pill, not a tab. The in-flight T202 metric is `corner_r = 6`. Keep a
  proportionate radius and make the RELATIONSHIP explicit (a documented small
  vs large surface radius pair), rather than one number used twice.
- **Shadow.** The banner FLOATS (uniform margin, shadow on all sides). A
  selected tab is ATTACHED - it merges into the pane below it, which is why
  T202 rounds only its top corners. So the tab DOES get the banner's
  elevation shadow, but on its top and sides ONLY, stopping where it meets
  its content. Same blur/alpha, three-sided path. (User, 2026-07-30: *"the
  tabs - they don't show shadowing around the active tab"* - the shadow is
  wanted, it is only the bottom edge that must not have one.)
- **Rim.** For the same reason the rim must run the tab's top and sides and
  STOP at the bottom, where the banner's rim wraps all the way round. Same
  gradient, same alphas, different path.
- **Fill.** The 6%-on-dark / 4%-on-light wash model SHOULD carry over
  directly - it is resolution-independent and already theme-aware, which is
  exactly what T203 needs for the strip anyway.

## The active tab is not legible against the strip (same report)

> "i really can't make the tab out on the background"

This is the headline symptom, and it is measurable rather than a matter of
taste. Today the strip is `background + 20` per channel and the active tab is
the raw terminal `background` (`Window.zig:2666-2680`) - a separation of 20/255,
about 8%, with no rim and no shadow to reinforce it. The direction is right
(selected tab darker than the strip, as in the Windows Terminal reference) but
the magnitude is below the threshold where an edge reads at all.

Three fixes compound, and the point of doing them together is that no single
one has to be heavy-handed:

1. Raise the fill separation to a stated minimum perceptual delta rather than
   an invented constant. **Derive the target by measuring the banner card
   against its own pane background** - that surface is already legible and
   already signed off, so it is the honest reference, and using it keeps the
   two surfaces cohesive by construction instead of by coincidence.
2. The specular rim gives the tab a defined top edge, which is most of what
   makes a surface read as separate.
3. The three-sided shadow gives it elevation.

Contrast must hold in BOTH themes and against a light terminal background,
which is where the current `+20` arithmetic collapses entirely (T203).

## Deliverables

1. Extract the shared tokens (rim alphas and gradient rule, fill
   lighten/darken, the radius pair, hairline width) out of `banner_card.zig`
   into a small design-token module both surfaces import. `banner_card.zig`
   keeps its card-specific geometry; only the LANGUAGE moves.
2. Apply to the tab chiclet: top-and-sides specular rim with the banner's
   gradient, the banner's fill model for the selected and hover states, and a
   radius documented as the small-surface counterpart to the card's 14.
3. Audit the other surfaces built since for the same drift, and either align
   them or record why not: the machine chooser's selection pill and detail
   wash (T172/T175), `ConfirmDialog`/`HostSettingsDialog`, the viewer TOC card
   (which on Mac already shares `GlassCardBackground` with the banner). The
   point of a token module is that the NEXT surface inherits it for free.
4. Write the tokens down in the T202 visual spec so this is checkable in
   review rather than re-litigated per surface.

## Validation

- Unit tests on the token module in the none lane, and on the tab's rim and
  shadow paths (top and sides present, bottom absent) the way
  `banner_card.zig` already unit-tests its corners.
- **The legibility assertion is the one that closes the user's report**:
  capture the strip and compute the perceptual delta between the active tab
  fill and the strip background, and between the active and an inactive tab.
  Assert both clear the target derived from the banner card. Run it on a dark
  AND a light terminal background - a pass on dark only is what let the
  current 8% ship.
- Extend `test/win32/tab-strip.ps1`: sample the tab's top edge and assert a
  hairline lighter than the fill, sample the bottom edge and assert there is
  no rim, and assert the tab fill is the documented wash over the strip rather
  than an unrelated color.
- A cohesion check with both surfaces on screen at once: capture a window with
  a banner set and assert the tab rim's top alpha and the banner rim's top
  alpha match within tolerance. This is the assertion that actually encodes
  the user's request - the two surfaces are measured against EACH OTHER, not
  against a constant.
- Negative control mandatory.
- Regressions: `pane-banner.ps1` (this touches banner_card's module
  boundary), both lanes, P1-P3.
