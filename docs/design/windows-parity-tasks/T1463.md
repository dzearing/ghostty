# T1463 - Re-run the T1458 pane-vs-conhost A/B against an optimized build before optimizing the parser

## Summary

Every number in the T1458 → T1460 chain was measured on a **Debug** build. That
build prints, in its own startup log, *"This is a debug build. Performance will
be very poor. You should only use a debug build for developing Ghostty."* The
user's report is against the **installed release**.

T1460's split is sound regardless — lock wait is 0.08% of the drain cost on any
build, and that is a ratio, not a rate. What is NOT established is the
**magnitude**: whether a release build still spends ~500 ms of every second in
`processOutputLocked` at ~50 KB/s, or whether an optimized parser closes most of
the 26x gap on its own. Zig's `Debug` mode leaves every bounds check, every
safety check and no inlining in a byte-at-a-time state machine, which is exactly
the shape that pays the most for it.

Until that is measured, T1461 has no honest baseline to improve on and no way to
tell a real win from recovering Debug overhead.

## In plain terms

The measurements that found the slow part were taken with the terminal built in
its slow "development" mode, which is not the build the reporter is running. The
finding about *where* the time goes still holds; *how much* time it really is
does not. This measures the same thing again on a build shaped like the one
people actually install, so the fix that follows is worth its cost.

## Details

The blocker is the standing safety rule, not the measurement:
`-Doptimize=Debug` is mandatory for on-box dev builds precisely because a
release-mode dev build **derives the same IPC and agent endpoints as the user's
installed release** and would silently drive their terminal (T243, T350).

So this task's first job is to make an optimized measurement build that cannot
reach the user's endpoints, and to prove it cannot:

- `test\win32\lib\Isolation.ps1` already sets `GHOZTTY_PIPE_SUFFIX` and
  `Assert-GhozttyPrivateEndpoint` / `Assert-GhozttyIsolated` already prove the
  answering instance is ours. Establish whether that covers the **agent**
  endpoint and the local-agent port/sessions files as well, not just the app
  pipe — the run in T1460 spawned its own `ghoztty-agent`, so the answer is
  probably yes, but it must be checked rather than assumed.
- Build to a separate `zig-out-*` prefix so nothing overwrites the debug tree the
  rest of the loop uses.
- If isolation genuinely cannot be proven for a release-mode build, that is a
  finding worth its own task, and the fallback is to measure the parse cost in
  isolation (a benchmark that feeds `Termio.processOutputLocked` from a captured
  byte stream, no GUI, no agent) rather than to skip the question.

The workload and A/B runner are in this loop's scratchpad and are described in
T1458's measurement section. T1461 owned folding them into `test\win32\` and
is now superseded, so that obligation moved to **T1464** - and it grew a second
mode there, since the local-vs-agent contrast is the finding.

## MEASURED 2026-09-08 - the optimized numbers

Build: `zig build -Dapp-runtime=win32 -Dtarget=x86_64-windows-gnu
-Doptimize=ReleaseFast --prefix zig-out-t1463` - the SAME mode and target the
shipped installer uses (`dist/windows-installer/build-msi.sh:121`), so this is
the build shape the reporter is running rather than a proxy for it.

Isolation: `Set-GhozttyTestIsolation -ReleaseSandbox` (all three knobs) plus
`Assert-GhozttyPrivateEndpoint -AllowReleaseBuild`. That is not a claim - the
first attempt at this run was **REFUSED** by `Assert-GhozttyIsolatedBuild`
because `Reset-GhozttyTestState` was called without the opt-in, which is the
demonstration that the gate fires. The user's endpoint was snapshotted before and
after every run (`+list --json` pane count plus `+version`'s Running Instance pid
/ commit / mode) and came back identical each time: `4|24300|82b87b0d2|ReleaseFast`.

Same workload, same box, same desktop as T1458 - `workload.ps1` at 400,000
chunks (~9.4 MB as measured at the pane).

### The A/B

| 400k chunks | conhost | **Debug pane (T1458)** | **ReleaseFast pane, agent-held PTY** | **ReleaseFast pane, local ConPTY** |
|---|---|---|---|---|
| writer-clock elapsed | 7,950 / 8,468 / 7,956 ms | 9,088 / 9,104 ms | **12,863 / 12,706 ms** | **6,511 / 6,138 ms** |
| sustained ingest | ~1.2 MB/s | **50-61 KB/s** | **634-696 KB/s** (peak 1.3-1.5 MB/s) | **1.44-1.70 MB/s** |
| `parse_ms_per_s` (median) | - | 460-605 | **41-43** | n/a (Exec path) |
| `lock_ms_per_s` (median) | - | 1 | 1 | n/a |
| lock share of drain | - | 0.08% | 2.6-2.8% | n/a |
| work us/byte | - | **~9.7** | **0.06-0.07** | n/a |
| still draining after the writer was released | - | **20+ s** | no | no |

Two samples of each; the pair agree within 3%.

### What that changes

1. **The 26x deficit was a Debug artifact.** The parse path costs
   **0.06 us/byte** optimized against ~9.7 us/byte in Debug - about 150x - and
   `parse_ms_per_s` falls from ~500-600 to ~41. The pane no longer trails the
   writer by 20 seconds; it finishes with it.
2. **T1460's split survives intact.** Lock wait is 2.6-2.8% of the drain here
   against 0.08% in Debug - a different number, the same verdict: the io thread
   is not starved by the renderer holding the pane mutex.
3. **T1461 has no premise left.** "The parser is the cost" is true only of a
   Debug build. On the shipped build the parser is ~4% of a wall-clock second,
   and optimizing it could not move the user's experience.
4. **A real deficit is still there, and it is somewhere else entirely.** The
   *same optimized build* runs the *same workload* in **6.1-6.5 s with a local
   ConPTY** and **12.7-12.9 s when the PTY is held by `ghoztty-agent`** - 2.1x,
   with the parse cost identical in both. Against conhost that is the difference
   between being **1.3x FASTER** (local) and **1.6x SLOWER** (agent-held), and
   the shipped configuration is the agent-held one. The relay is the cost.
   `feeds_per_s` = `slices_per_s` at 10,000-22,600 per second for 634-696 KB/s
   works out to **~60 bytes per feed**: the relay is carrying the stream one
   ConPTY read at a time. Filed as T1464.
5. **T1462 got much bigger.** Burst fps on the optimized build is **2,905-4,192**
   (Debug: 421-514), with `swap_avg_us` still 56-62 and `swap_max_ms` 0-1. The
   waste that task describes is roughly 8x what it was measured at.

### How the local-vs-agent contrast was obtained

A cold sandbox has no agent, and the app waits only 2,000 ms for the one it
spawns before deciding "no local agent" for the whole session - so the first run
of this harness silently measured the **local** path (`perf pty`, no
`perf agent_feed` samples at all). Bringing the app up once purely to spawn the
agent, waiting for its `port.json`, killing the app only, and relaunching against
a live agent is what puts the pane on the shipped path. That accident is what
produced the two-column contrast above, and it is the most useful number in this
task - keep both modes when this harness is folded into `test\win32\` (T1461).
