# T1086 - No lane runs the DUE acceptance harnesses, so a suite-wide sweep costs a turn or mutes the gate

## In plain terms

There is a rule that says a test has to be re-run after the code it watches
changes, and it is a good rule. But there is no button that runs the tests it
is asking for - each one has to be started by hand, one at a time, and a change
that touches the whole test folder can ask for thirty of them at once. When
that happens the choice is to spend most of a working session babysitting them
or to switch the rule off for that commit, and switching it off is what has
happened before.

## Summary

`scripts\guard-due.ps1 check` answers "which acceptance harnesses have not been
run since the code they cover changed", and `parity-tasks.ps1 validate` fails
while any are DUE (T783). What is missing is the other half: a way to RUN them.

The zig lanes have one - `scripts\floor-lane.ps1 -Lane all` runs four lanes
sequentially with stall detection and one verdict line each. The acceptance
harnesses have nothing equivalent, so draining a DUE list is N hand-typed
commands with N verdicts to read.

Measured on T352, which changed one token (`'-vptest'` -> `"-vptest$PID"`) in
131 scripts: **36 guards went DUE at once**, 30 of them GUI or agent harnesses
of several minutes each. That turn drained them with a throwaway loop written
into a scratch directory - which worked, and is exactly the artifact that
should not be thrown away.

The failure mode when it is not drained is on the record: T1042 found
`-NoGuardDue` had been passed by every turn for a day, because T1039's own
one-line sweep had left ~30 guards due and re-running them by hand was not
something a turn could absorb. The gate was muted as routine for a day.

## What to do

- `scripts\guard-lane.ps1` (name to taste), in the `floor-lane.ps1` shape:
  read the DUE list from `guard-due.ps1 check`, run each harness **sequentially**
  (never overlapped - go.md), one verdict line each, and a final summary plus an
  exit code.
- Per-script wall-clock cap so one wedge cannot eat the batch, reported as
  `STALL`/`TIMEOUT` rather than as a hang - the same distinction `floor-lane.ps1`
  exists to make.
- `-Only <names>` to drain a subset, and `-List` to print what it would run.
- Each harness re-stamps its own guard on green already, so the lane needs no
  stamping logic of its own; it must NOT stamp anything itself.
- Worth considering: a `-Continue` that skips harnesses already known red at
  HEAD (agent-upgrade is red for T1037's reasons and will be until that lands),
  so a permanent red does not make the lane useless.

## Validation criteria

- [ ] The lane drains a real DUE list and `guard-due.ps1 check` exits 0 after it
- [ ] A deliberately wedged fixture harness is reported as a timeout with its log
      named, and the lane carries on to the next one
- [ ] Its own acceptance script exists in `test\win32\` and has a `guard-due` row
- [ ] `-List` prints the queue without running anything
