# T585 - The win32 acceptance harness cannot score any accent-painting CHILD window: the one that exists is foreground-gated and the background desktop has no foreground

## In plain terms

Ghoztty's automated Windows UI tests run on a hidden desktop so they cannot
disturb whoever is using the machine. One consequence, found while proving out
T307: nothing on that hidden desktop is ever the "active" window, and the one
place Ghoztty paints your accent color inside a sub-window - the highlighted
row in a document's contents card - deliberately only uses the accent when its
window is the active one. So that surface can never be photographed in its
accent state by a test, and a real bug in it would go unnoticed.

## Goals

- [ ] An accent-painting child window that a background-desktop capture can
      actually score, or a harness-level way to make a window read as active
- [ ] `chrome-theme.ps1` gains the child-repaint assertion it currently
      documents as unscoreable

## Summary

T307 widened the reaction to a system accent change from "invalidate the chrome
row" to "redraw this window and every child", because a child HWND never
receives `WM_SETTINGCHANGE` / `WM_DWMCOLORIZATIONCOLORCHANGED` - the broadcast
reaches top-level windows only - so its owner is the only place its repaint can
come from. The fix is right by reading, and its top-level half is scored by
`chrome-theme.ps1` B4. Its CHILD half is not scored by anything, and two
candidate oracles were built and measured to be undiscriminating:

- **The hero carousel's accent-outlined selected tile.** Measured PASS with the
  repaint reverted: `Window`'s thumbnail refresh timer repaints the band every
  150ms unprompted, so it picks the new accent up from the cache drop alone.
  A surface that repaints on its own cannot score whether anything invalidated
  it. (It is also not a child - it is painted into the parent's DC.)
- **The viewer's contents card (`GhozttyViewerTOC`).** The right shape - a real
  child HWND whose active row is filled with the raw accent - and it appears
  and captures fine on the test desktop. But the accent fill is gated on
  `ViewerTOCPanel.isEmphasized()`, i.e. on `GetForegroundWindow`, and
  `test/win32/lib/TestDesktop.ps1`'s own header records that a background
  desktop HAS no foreground window at all (`SetForegroundWindow` fails,
  `GetForegroundWindow` returns 0). The pill is therefore always the
  unemphasized gray there. Measured: `E1 the card's selected row is filled with
  #ff0000` FAILS on a correct build.

Both findings are written into `chrome-theme.ps1`'s header under "WHAT THIS
SCRIPT CANNOT CLAIM" so the next attempt does not re-derive them.

## Where

- `test/win32/lib/TestDesktop.ps1` - the desktop harness and its documented
  capability limits.
- `src/apprt/win32/ViewerTOCPanel.zig` `isEmphasized` (~line 851) - the gate.
- `test/win32/chrome-theme.ps1` - where the assertion belongs once there is a
  way to make it.

## Options worth weighing

1. Give the harness a way to make a window read as emphasized on a background
   desktop (the `AttachThreadInput` + `SetActiveWindow` route the harness
   already uses for input may or may not move `GetForegroundWindow`; measure
   before designing around it).
2. Score it under the script's existing `-Interactive` switch, which runs on
   the real desktop - honest, but it never runs in the standing floor, so it
   guards nothing by default.
3. Find or add a child surface that paints the accent ungated.

## Validation criteria

- [ ] An assertion exists that FAILS on a build whose parent does not redraw
      its children on an accent change, and PASSES on one that does - the
      negative control run, not assumed.
- [ ] It runs in the default (non-interactive) invocation of its script.
