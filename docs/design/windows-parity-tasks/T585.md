# T585 - The win32 acceptance harness cannot score any accent-painting CHILD window: the one that exists is foreground-gated and the background desktop has no foreground

## In plain terms

Ghoztty's automated Windows UI tests run on a hidden desktop so they cannot
disturb whoever is using the machine. One consequence, found while proving out
T307: nothing on that hidden desktop is ever the "active" window, and the one
place Ghoztty paints your accent color inside a sub-window - the highlighted
row in a document's contents card - deliberately only uses the accent when its
window is the active one. So that surface can never be photographed in its
accent state by a test, and a real bug in it would go unnoticed.

## Goals

- [x] An accent-painting child window that a background-desktop capture can
      actually score, or a harness-level way to make a window read as active
- [x] `chrome-theme.ps1` gains the child-window assertion it currently
      documents as unscoreable
- [x] Say honestly what that assertion can and cannot claim, and file the half
      it cannot (T1405)

## Summary

**The blocker this card was filed for is gone, and was already gone when it was
filed against.** T215 (2026-08-10, three days after this card) replaced
`isEmphasized()`'s bare `GetForegroundWindow` comparison with
`w32.windowIsActive`, whose off-input-desktop proxy is the queue-scoped
`GetActiveWindow` - and T568 gave the harness `Set-TestActiveWindow`, which
moves exactly that. So the contents card DOES paint its emphasized accent pill
on the background desktop. Measured, not assumed: with the card in its GUTTER
layout (a viewer window resized past `viewer_toc_layout.gutter_min_dip` - the
compact layout hides it behind the nav bar's contents button) the capture holds
64 distinct colors and an exact `#ff0000` hit.

So the deliverable was the TEST, and `chrome-theme.ps1` grew section F:

- **F1/F2, in pixels** - a CHILD window paints the accent, and it paints the
  CURRENT one after a change notified only to its owner.
- **F3, in source** - `repaintForColorChange` still redraws with
  `RDW_ALLCHILDREN`, with the analyzer exercised against a good and a bad
  fixture first (T1133).

**Why the child-repaint half is source and not pixels.** Building the pixel
version turned up something bigger, measured on purpose: cut
`repaintForColorChange` down to a bare cache drop with no `RedrawWindow` at all,
rebuild, and `chrome-theme.ps1` still passes **129 of 129** - B4, the assertion
labelled "the LIVE-UPDATE claim", included. Photographing a window makes it
paint (`-Sync` is `WM_PRINTCLIENT`; the async path is
`PrintWindow(PW_RENDERFULLCONTENT)`), and that fresh frame reads the accent
through the cache the message just dropped. No capture this harness can take
can tell "was invalidated" from "painted for the camera". Filed as **T1405**;
F3 covers the one flag as text in the meantime, and goes red on both controls.

The candidate that failed earlier - the hero carousel's tile, repainted every
150ms by its own timer - was the same blind spot wearing a different hat.

## Where

- `test/win32/chrome-theme.ps1` - section F (F1/F2 pixels, F3 source) and the
  header paragraph "WHAT NO CAPTURE IN THIS SCRIPT CAN CLAIM".
- `scripts/guard-due.ps1` - `system_colors.zig` joins the chrome-theme coverage
  row, so dropping the flag makes the harness due.
- `src/apprt/win32/ViewerTOCPanel.zig` `isEmphasized` - the gate, now
  `w32.windowIsActive`.
- `test/win32/lib/TestDesktop.ps1` - `Set-TestActiveWindow` (T568), the lever
  that makes the pill emphasized off the input desktop.

## Options worth weighing

1. Give the harness a way to make a window read as emphasized on a background
   desktop (the `AttachThreadInput` + `SetActiveWindow` route the harness
   already uses for input may or may not move `GetForegroundWindow`; measure
   before designing around it).
2. Score it under the script's existing `-Interactive` switch, which runs on
   the real desktop - honest, but it never runs in the standing floor, so it
   guards nothing by default.
3. Find or add a child surface that paints the accent ungated.

## Validation criteria

- [x] An assertion exists that FAILS on a build whose parent does not redraw
      its children on an accent change, and PASSES on one that does - the
      negative control run, not assumed. **F3**: with `RDW_ALLCHILDREN` removed
      from `system_colors.zig` and the app rebuilt, `chrome-theme.ps1` reported
      `1 FAILURE(S) of 133`, the failure being F3 and nothing else; restored, it
      reports `ALL PASS (133 assertions)`.
- [x] It runs in the default (non-interactive) invocation of its script. F1-F3
      are all in the default path; the green run above took no switches.
- [x] The pixel half is scored too: F1 `the card's selected row is filled with
      #ff0000` and F2 `the card's pill is #00c000 after the accent changed`,
      which is the assertion this card recorded as failing on a correct build.
