# T1217 - The morning refresh silently turns off the installed terminal's ability to find updates

## In plain terms

You installed Ghoztty from the website this morning. Forty-one minutes later,
without anything on screen, your terminal stopped being able to notice that a
newer version exists, and its About box went back to calling itself 1.4.0
instead of 1.35.0. Nothing warned you; the only way to find out is to ask it
its version. This is the loop's own "here are today's fixes" delivery writing
a development build over the product you installed.

## Goals

- [x] A build delivered into the installed-release folder keeps a truthful
      version number instead of falling back to the repo's 1.4.0.
- [x] That build can still find and take a published update.
- [x] A portable copy and a `zig-out` dev build still never phone home.
- [x] The gap is provable on the box, not just reasoned about.

## Summary

`scripts/morning-refresh.ps1` -> `scripts/launch-upgrade.ps1` builds the
staging release with

```
zig build -Dapp-runtime=win32 -Doptimize=ReleaseFast \
    -Dtarget=x86_64-windows-gnu -Dstrip=false --prefix zig-out-release
```

and delivers it over `%LOCALAPPDATA%\Programs\Ghoztty`. That command line
carries neither `-Dversion-string` nor `-Dwindows-update-check=true` - both of
which the MSI pipeline passes (`dist/windows-installer/build-msi.sh:118`,
`build-release-artifacts.sh:113`). So the delivered exe:

- reports `1.4.0-users-dzearing-windows-amd64-+<sha>` (from `build.zig.zon`),
  not the version of the release it just replaced, and
- reports `update check: off (dev build)`, because `App.zig:7549` gates the
  automatic check on `build_config.windows_update_check` alone.

### Measured

- 2026-08-31 07:08 - the user installed `Ghoztty-1.35.0-x64.msi` from the
  website (T1179). Verified at the time: About and `--version` both
  `1.35.0+890207079`.
- 2026-08-31 07:46-07:49 - `ghoztty-morning-refresh.log`: `DUE: first push
  at/after 5:00 today` -> `LAUNCH OK`. `%LOCALAPPDATA%\Programs\Ghoztty\
  ghoztty.exe` last-write 07:49:13.
- 2026-08-31 11:15 - that exe answers `+version` with
  `1.4.0-users-dzearing-windows-amd64-+db68549df`, `channel: tip`,
  `update check: off (dev build)`.

### Why the obvious one-line fix is wrong

Just adding `-Dwindows-update-check=true` would make the delivered build
compare its `1.4.0` against the newest `win-v` tag and offer 1.35.0 - a
*downgrade* to older code. The version stamp has to be fixed in the same
change, and it has to be `>=` the published baseline. `update_check.isNewer`
already ignores build metadata, so `1.35.0+<sha>` is "up to date" against
`win-v1.35.0` and takes `win-v1.36.0` - which is exactly the behavior the gate
needs.

The same staging prefix is also delivered to the two portable locations, and
"portable builds never phone home" is a deliberate rule (`App.zig:7538-7545`).
So the automatic check is enabled by *where the exe is running from* - the
installed-release folder, and not in a Debug build - rather than by turning the
build flag on for every copy of those bytes.

## Fix

1. `scripts/launch-upgrade.ps1`: stamp the staging build with
   `-Dversion-string="<newest published win-v semver>+<short sha>"`.
2. `src/apprt/win32/install_location.zig` (new, pure): does this exe live in
   `%LOCALAPPDATA%\Programs\Ghoztty`?
3. `src/apprt/win32/App.zig`: the automatic update check runs when the build
   flag is set **or** the exe is the installed release and this is not a Debug
   build.
