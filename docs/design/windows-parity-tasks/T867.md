# T867 - win32 agent integrations (3/8): nothing installs the bundled skills or the banner/activity scripts into an agent's config dir - port SkillComponent and BannerScriptInstaller

## In plain terms

With the safe writer (T865) and the packed files (T866) in place, this task
teaches the Windows app to actually put them where a coding agent looks: the
skill documents into the agent's own folder, and the two helper scripts into
a stable Ghoztty folder. Still no prompts or windows — just the machinery,
fully tested.

## Goals

- [x] The app can install/uninstall the two bundled skills into an agent's
      config folder, refusing to touch anything the user wrote themselves
- [x] The two hook helper scripts install into one stable Ghoztty folder,
      always as a pair — never one without the other
- [x] A failed install cleans up after itself without deleting anything that
      was already installed before the attempt
- [x] All lanes green on the box

## Summary

Third slice of the T598 split. Port `SkillComponent.swift` and
`BannerScriptInstaller.swift`.

- **SkillComponent**: installs `ghoztty` and `process-feedback` SKILL.md into
  `<agent config dir>\skills\<name>\SKILL.md` (`%USERPROFILE%\.claude\...`,
  `%USERPROFILE%\.copilot\...`). Appends the markdown marker line
  (`<!-- ghoztty-managed -->` + trailing newline) to the embedded text — that
  exact composed string is the `expected` for state comparison. Renders ALL
  skills before writing ANY (a missing asset fails before the first write);
  rollback on partial failure removes only what THIS call wrote, via
  `removeIfManaged`, in reverse order. State aggregation: all installed →
  installed; all absent → not_installed; else outdated.
- **BannerScriptInstaller**: both hook scripts (`ghoztty-banner.sh`,
  `ghoztty-activity-state.sh` — or their T866-decided flavor) into ONE
  Ghoztty-owned stable directory; shell marker. They install and uninstall
  together — hooks reference both, a half-pair leaves dangling hook commands.
  The directory path is the hook-ownership signature that T868 keys on, so
  ONE function owns the layout (Mac's `HookScripts`: banner path is the
  anchor, siblings resolve from it).

**Windows path decision** (make it here, record it): Mac uses
`~/.config/ghoztty/hooks`. Windows candidates: `%USERPROFILE%\.config\
ghoztty\hooks` (byte-compatible with Mac hook commands, dotfiles-style) vs
`%LOCALAPPDATA%\ghoztty\hooks` (Windows-native). Weigh: the hook commands
embed this path into agent config files that Git-Bash-based hooks will read
— a `~/.config`-style path spells identically in bash on both platforms,
which keeps the merged-fragment signature logic and any shared tests simple.
Check what the win32 app already uses for its banner STATE dir (the Mac
migration writes `~/.config/ghoztty/banner-state`) and stay consistent with
the T598-era state the box already has.

**RESOLVED (2026-08-15, this turn): `%USERPROFILE%\.config\ghoztty\hooks`.**
Not a taste call — the T866-vendored assets already hardcode the spelling:
`ghoztty-banner.sh` keeps state in `$HOME/.config/ghoztty/banner-state`, and
the bundled `process-feedback` skill invokes
`~/.config/ghoztty/hooks/ghoztty-banner.sh` by that literal path. The hooks
run under Git Bash, where `~/.config/...` resolves to `%USERPROFILE%\.config`
on Windows, so the dotfiles-style path is the only one under which the
shipped assets work unmodified and the hook-ownership signature (T868) spells
identically on both platforms. Recorded in `hook_scripts.zig`'s module doc.
