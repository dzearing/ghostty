# T235 - Tabs size to content, capped by proportion

## Summary

User report with screenshot, 2026-07-31, verbatim: *"in the tab control, you
have tons of horiz realestate, and yet you are truncating the tab text here.
Tabs should only constrict content at a reasonable maximum size, like 50% width
or something."*

The screenshot shows `. Fix background p...` truncated in a single tab on a wide
window with most of the strip empty. That is `max_tab_w = 200 DIP`
(`tab_strip_layout.Metrics.init`) doing exactly what it was written to do, and
what it was written to do is wrong.

## Why it is there, and why that reasoning does not hold

T202 measured Windows Terminal and found `TabWidthMode="Equal"`: every tab gets
an equal share of the strip clamped to a maximum, never the remainder. Two
findings came out of that and **the first one is still right**:

- **Tabs never stretch to fill.** A single tab must not span the window. Keep
  this.
- **The cap is a fixed 200 DIP.** This is the part to replace. Matching a
  platform control's *algorithm* was never the goal - not truncating a title
  while 1000 px of strip sits empty is.

## The rule (design system section 6b)

1. A tab's **preferred width is its measured title width + padding** (leading
   `text_pad`, the close button's box, trailing gap).
2. Cap it at **50% of the available tab run** - a proportion of the container,
   not a DIP constant. Wide window, long title: the tab grows. Narrow window:
   the same tab yields.
3. **Only shrink under pressure.** When the preferred widths do not all fit,
   fall back to today's equal-share clamped to `[min_tab_w, cap]`, and only
   then ellipsize.
4. **Never stretch** a tab beyond its preferred width to fill leftover strip
   (the T202 rule, preserved).

`min_tab_w` (60 DIP) stays as the floor. `max_tab_w` as a constant goes away,
replaced by the proportional cap.

## Implementation note

`tab_strip_layout.zig` deliberately does no text measurement, and that property
is worth keeping - it is why the module is unit-testable with no window, no
font and no DPI. So **the caller measures and passes preferred widths in**:
`layout()` grows one `[]const i32` parameter (preferred width per tab, already
including padding), computed in `paintTabBar` with `GetTextExtentPoint32W`
against the same font the titles are drawn in.

The layout module stays pure; its input grows by one array. Every existing
unit test can pass a uniform preferred width and keep asserting what it asserts
today.

## Validation

- Unit tests at 1.0/1.25/1.5/2.0: a single short title yields a tab exactly its
  preferred width (no truncation, no stretch); a single very long title is
  capped at 50% of the run; N tabs whose preferred widths exceed the run fall
  back to equal-share and every tab is the same width; the floor is respected.
- On box, reproducing the user's screenshot: the same tab title renders in full
  on a wide window.
- `test/win32/tab-strip.ps1` ALL PASS x3 - note its single-tab-width assertion
  currently pins `max_tab_w - tab_gap` and must be rewritten to the new rule
  (and its negative control re-derived, since T202's neuter targets the
  stretch rule, which survives).

## Outcome (done, 2026-07-31)

`max_tab_w` is gone from `Metrics`. In its place:

- `Metrics.preferredWidth(text_w)` - the painted width a `text_w` title needs,
  written as the **exact inverse of `titleRect`**. A unit test pins that
  inverse at five scales over six text widths, because one pixel of
  disagreement means a tab sized to its own stated preference still
  ellipsizes - the bug reappearing through the back door.
- `runWidth(m, client_w)` - the tab run, named because the cap is a fraction
  of it and `layout`, the unit tests and the acceptance script all have to
  mean the same run. `layout` now calls it instead of recomputing it inline.
- `capWidth(m, tabs_avail) = max(tabs_avail / 2, min_tab_w)` - the proportional
  cap, floored so a narrow run still shows one tab.
- `layout(m, client_w, prefer: []const i32, out)` - `tab_count` is gone; the
  preferred-width array's length IS the count, so a caller cannot pass a count
  and an array that disagree. Sums the clamped slots; if they fit, each tab
  gets its own and the leftover strip stays empty. If they do not, it falls
  back to T202's equal share clamped to `[min_tab_w, cap]`.
- `Strip.tab_w` now means "the uniform width used **under pressure**", and is
  **0 when each tab took its own width** - there is no single width to report
  then, and a caller wanting tab `i` reads `out[i]`.

`Window.paintTabBar` measures each title with `GetTextExtentPoint32W` against
`mem_dc`, which already has `tab_font` selected a few lines above - the same
font `DrawTextW` renders with. The layout module still owns no HDC and no font;
its input grew by one array.

### Evidence

- Unit tests, all four/five scales: `preferredWidth is the exact inverse of
  titleRect`; `a tab grows with its title, and is capped at half the run`
  (monotonic growth over 40/80/160/240 DIP titles, past the retired 200 DIP
  constant; a 5000 DIP title lands exactly on `cap - tab_gap`; the SAME title
  on a window a third as wide gets less, which is what "proportional" buys);
  `preferred widths that do not fit fall back to an equal share` (uniform,
  narrower than preferred, never below the floor); `mixed titles each get their
  own width`. The pre-existing suite kept every assertion it had, re-expressed
  against a measured slot instead of `max_tab_w`.
- `zig build test -Dapp-runtime=none` exit 0, `-Dapp-runtime=win32` exit 0,
  `zig build test-agent` exit 0, `zig build -Dapp-runtime=win32
  -Doptimize=Debug` exit 0 (the GUI link, which is the only lane that sees
  lazily-analyzed win32 code).
- `test/win32/tab-strip.ps1` **ALL PASS (35 assertions) x3**. Its new section 7
  is the user's report in pixels: one window, two different titles. At the
  box's 125% the long-titled tab measured **690 px** against the retired cap's
  **245**, and the default-titled tab beside it **344**.
- The measured 344 is worth keeping: **the ordinary default title was already
  ~275 DIP**, so the 200 DIP cap was ellipsizing essentially every tab the user
  had, not merely long ones. The screenshot was the general case.
- **Negative control, source-level**: `T202_NEUTERED = true`, rebuilt, re-run -
  9 FAILED / 26 passed. The failures are exactly the width rules (`does NOT
  span the client width`, `never wider than 50% of the tab run` in both
  sections, both T235 growth assertions, and the "+"-travel/index assertions);
  the accent-rule, seam, glyph-symmetry, right-inset and menu-popup assertions
  all still passed. Restored and rebuilt.
- Standing floor: P1/P2/P3 ACCEPTANCE ALL PASS.

Docs: `win32-tab-strip.md` records `max_tab_w`'s retirement, the new rule 1,
and - explicitly - **why the original reasoning was wrong**: the Windows
Terminal measurement was right, but "it needs no text measurement in the layout
module" was convenience masquerading as a design rule. The module is still
text-free; the caller measures.
