# T235 - Tabs size to content, capped by proportion

## Summary

User report with screenshot, 2026-07-31, verbatim: *"in the tab control, you
have tons of horiz realestate, and yet you are truncating the tab text here.
Tabs should only constrict content at a reasonable maximum size, like 50% width
or something."*

The screenshot shows `. Fix background p...` truncated in a single tab on a wide
window with most of the strip empty. That is `max_tab_w = 200 DIP`
(`tab_strip_layout.Metrics.init`) doing exactly what it was written to do, and
what it was written to do is wrong.

## Why it is there, and why that reasoning does not hold

T202 measured Windows Terminal and found `TabWidthMode="Equal"`: every tab gets
an equal share of the strip clamped to a maximum, never the remainder. Two
findings came out of that and **the first one is still right**:

- **Tabs never stretch to fill.** A single tab must not span the window. Keep
  this.
- **The cap is a fixed 200 DIP.** This is the part to replace. Matching a
  platform control's *algorithm* was never the goal - not truncating a title
  while 1000 px of strip sits empty is.

## The rule (design system section 6b)

1. A tab's **preferred width is its measured title width + padding** (leading
   `text_pad`, the close button's box, trailing gap).
2. Cap it at **50% of the available tab run** - a proportion of the container,
   not a DIP constant. Wide window, long title: the tab grows. Narrow window:
   the same tab yields.
3. **Only shrink under pressure.** When the preferred widths do not all fit,
   fall back to today's equal-share clamped to `[min_tab_w, cap]`, and only
   then ellipsize.
4. **Never stretch** a tab beyond its preferred width to fill leftover strip
   (the T202 rule, preserved).

`min_tab_w` (60 DIP) stays as the floor. `max_tab_w` as a constant goes away,
replaced by the proportional cap.

## Implementation note

`tab_strip_layout.zig` deliberately does no text measurement, and that property
is worth keeping - it is why the module is unit-testable with no window, no
font and no DPI. So **the caller measures and passes preferred widths in**:
`layout()` grows one `[]const i32` parameter (preferred width per tab, already
including padding), computed in `paintTabBar` with `GetTextExtentPoint32W`
against the same font the titles are drawn in.

The layout module stays pure; its input grows by one array. Every existing
unit test can pass a uniform preferred width and keep asserting what it asserts
today.

## Validation

- Unit tests at 1.0/1.25/1.5/2.0: a single short title yields a tab exactly its
  preferred width (no truncation, no stretch); a single very long title is
  capped at 50% of the run; N tabs whose preferred widths exceed the run fall
  back to equal-share and every tab is the same width; the floor is respected.
- On box, reproducing the user's screenshot: the same tab title renders in full
  on a wide window.
- `test/win32/tab-strip.ps1` ALL PASS x3 - note its single-tab-width assertion
  currently pins `max_tab_w - tab_gap` and must be rewritten to the new rule
  (and its negative control re-derived, since T202's neuter targets the
  stretch rule, which survives).
