# T824 - Replayed scrollback no longer leaves a dead TUI's modes armed on Windows

## Summary

Port main's replay_mode_reset + additive RELAUNCH.notice (relaunch_notice HELLO capability) so a Windows pane restored from replay resets mouse tracking/encodings, bracketed paste, focus reporting, cursor keys/keypad, autowrap, cursor visibility and SGR, and shows the 'previous session was lost' notice where the shell prompt cannot blank it. Upstream c76b5c89d.

## In plain terms

When a pane comes back after a reboot, the terminal replays the old text — and
that replay re-arms whatever the dead program had switched on. The result is that
moving the mouse over the pane types gibberish like `35;1;12M` into the shell,
and a hidden cursor or stuck colours make the pane look broken. After this, a
pane that came back by re-running its old command behaves like a normal terminal
again.

## Goals

- [x] a replay resets the modes the dead program armed, so the mouse stops typing into the shell
- [x] the reset lands where the respawned program cannot undo it (the agent puts it in the stream)
- [x] an older agent that does not know about the field still works
- [x] an ordinary re-attach to a live session is left alone

## Details

Upstream `c76b5c89d` (main, 2026-08-12). Two pieces:

- `replay_mode_reset` undoes what the raw replay re-arms: mouse tracking, mouse
  encodings, bracketed paste, focus reporting, cursor keys/keypad, autowrap,
  cursor visibility, SGR. **Mode state only** — no RIS, and deliberately no
  alt-screen/origin/scroll-region, because ghostty applies those
  unconditionally (cursor restore, erase, home) and they would drop the fresh
  prompt on top of the restored output. Not applied on the ordinary alive
  re-attach, where the child still owns those modes.
- `RELAUNCH.notice`, an additive protocol field gated on a `relaunch_notice`
  HELLO capability. A client-side print loses the race with the respawned
  shell's first prompt repaint; the agent instead appends the notice to the
  ring ahead of the replay, landing it in the agent-baked divider's slot. An
  older agent ignores the field and the client prints locally as before — this
  is the wire-protocol compatibility contract, so the capability gate is not
  optional. The mode reset rides the same payload, which also stops a locally
  injected reset from racing ahead of a `rerun` TUI and switching its tracking
  back off.

## What this branch actually needed (findings, 2026-08-17)

Upstream's change is three things; only one of them was still missing here,
because this branch's `restore` policy took a different route (T230).

| Upstream piece | State on this branch |
| --- | --- |
| `session-relaunch=restore\|rerun\|prompt` | landed as T823 (`f5db01f0f`) |
| `Session.setCwd` on `handleOpen` | already present (`server.zig` `handleOpen`) |
| the "previous session was lost" notice surviving the first prompt | already solved differently: `restore` here opens a BRAND-NEW session (T230) and its notice is `termio/session_notice.zig`, folded above the viewport by `armNoticeFold` / `Termio.holdNoticeAboveLocked` (T422/T423/T424) — no wire field involved |
| `replay_mode_reset` + `RELAUNCH.notice` | **missing — this task** |

Because `restore` opens a fresh session, it replays nothing and arms nothing. The
defect therefore lives on the two policies that DO relaunch and replay: `rerun`
and the keystroke-deferred `prompt`. So the `notice` slot carries the mode reset
here rather than a sentence, which is also why the client-side fallback matters
less on this branch than it does on main.

## How the on-box oracle works (and what it cost to build)

DECRQM (`CSI ? Ps $ p`) is the only way to ASK the terminal what a mode's value
is, and the answer arrives as INPUT to the pane's child — so the probe has to be
a program that asks and reads its own answer back. Three things about
`+send-keys` had to be discovered by measurement first, and are now written into
the harness so the next probe does not rediscover them:

- **Adjacent text arguments concatenate with NO separator.** `probe.cmd VTPRE
  1003` arrives as `probe.cmdVTPRE1003`. The first run of this oracle failed for
  exactly that reason and looked like "the mode was never reset". Each probe now
  gets its own generated `.cmd` with the tag and mode baked in, so exactly one
  word is ever sent.
- **`\t` `\n` `\r` `\\` `\e` are escapes in text**, so a path through
  `...\Temp\t824probe\` arrives with a TAB in the middle of it.
- **`[Console]::KeyAvailable` throws** the moment stdin is not a console. The
  reader is `$Host.UI.RawUI` (ReadConsoleInput) instead.

Verified end to end in a scratch pane before wiring it in: armed → `?1003;1$y`,
disarmed → `?1003;2$y`.
