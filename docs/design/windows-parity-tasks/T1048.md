# T1048 - In-place recovery still pairs TABS by index, so a tab closed mid-recovery rebuilds from another tab's tree

## In plain terms

When the background service that holds your shells is restarted, the terminal
rebuilds each window's tabs underneath you. It works out which tab gets which
layout by counting - first tab, second tab - so if a tab is closed during the
few seconds the rebuild takes, the count slips and a tab can come back holding
the tab-next-door's panes. T343 fixed exactly this one level up (windows now
match by name tag); tabs have no name tag yet.

## Summary

`App.rebuildWindowInPlace` walks `for (0..tab_count) |ti|` and hands
`captured.tabs[ti]` to `rebuildTabInPlace`, with
`tab_count = @min(window.tab_count, captured.tabs.len)`. The pairing is correct
only while the live tab list has not moved since `captureSessionLayout` ran -
and the capture is followed by `reconnectForRecovery`, which can block for
seconds. A tab closed (or inserted) in that window shifts every later tab, and
each one is then rebuilt from its neighbour's tree.

`rebuildTabInPlace` cannot catch it: its correspondence check
(`capturedNodeShapes`) compares node SHAPES, so two tabs with the same split
shape - the common case, e.g. two single-pane tabs - pass the check and get each
other's sessions re-ATTACHed. Same latent class T343 removed for windows, and
the same reason it stayed: there is no stable per-tab identity to key on.
Nothing has been observed to misfire; the fix is a tab-level analogue of T338's
`layout_uuid` plus `session_layout.pairWindows`.

Found doing T343 (2026-08-21).

## Goals

- [x] Each tab carries an identity that survives a capture, a rebuild and a
  restore, and that travels with the tab through close/insert/reorder.
- [x] In-place recovery pairs captured tabs to live tabs by that identity, and
  leaves an unmatched tab strictly alone.
- [x] Unit coverage for the pairing in the `none` lane, including a tab list
  reordered between the two walks.
- [x] An on-box arm that drives the real race and fails on the pre-fix build.

## Details

Two plausible shapes were on the table; the FIRST was taken:

- **Chosen.** Give each tab a stable uuid the way T338 gave windows one
  (recorded on `session_layout.Tab`, re-adopted on restore), then reuse the
  pairing - it is already generic over "captured entries keyed by string".
- Rejected: key on something the tab already owns that survives a capture. The
  first leaf's `session_id` is stable and unique per tab in practice, but it is
  empty for a viewer-only tab and for a tab whose OPEN is still in flight - and
  an empty key is exactly the case that must never pair.

What landed:

- `session_layout.Tab.uuid` (additive, optional) + `tabKey` + `pairTabs`.
  `pairWindows` and `pairTabs` now share one `pairByKey` core, which hands each
  captured entry out AT MOST ONCE and treats an EMPTY key as unmatchable on
  either side - so a manifest written by a pre-T1048 build pairs nothing rather
  than falling back to the positional guess.
- `Window.tab_uuid[MAX_TABS]`, generated in `insertPaneAsTab` and carried
  through every shuffle site (`insertPaneAsTab`, `closeTab`,
  `moveTabRelative`'s swap, `moveTabTo`), with `tabUuid()` / `adoptTabUuid()`.
- `captureWindowSessionLayout` records it; `restoreTab` re-adopts it before the
  subtree is rebuilt; `rebuildWindowInPlace` pairs on it.

The Mac owes nothing here: its recovery keys each controller on
`sessionLayoutEntryID` and looks the entry up in a dictionary, and a macOS tab
IS a `TerminalController`, so there is no positional tab walk to fix.

## Validation criteria

- [x] Unit: the tab pairing matches by identity and skips an unmatched tab,
  exercised with a tab list reordered between the two walks (mirror of T343's
  `pairWindows` tests). Six tests in `session_layout.zig`, green in the `none`
  and `win32` lanes.
- [x] On box: `test/win32/agent-recovery.ps1` still ALL PASS (76). The new arm
  is its own harness, `test/win32/agent-recovery-tabs.ps1` (ALL PASS, 18) -
  three tabs on three shells, the agent SUSPENDED until the app commits to
  recovery, tab 0 closed over IPC while the re-dial is still pumping, then
  resumed; the survivors must come back on their own shell pids.
- [x] The arm FAILS on the pre-fix build, measured: with the positional walk
  restored, `after=34788,27180` against `want=27180,35200` - tab 0 came back on
  a brand-new shell (its captured partner's session had just been closed) and
  tab 1 came back holding tab 0's session. D2 rules out the vacuous pass where
  an aborted re-dial re-enters recovery with a fresh capture.
