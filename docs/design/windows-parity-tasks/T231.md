# T231 - Expose tab-strip hit regions to tests instead of re-deriving the layout

## In plain terms

The automated tests that click Ghoztty's tabs had to work out for themselves
where each tab and the "+" button were, by copying the app's own sizing rules
into a script. Every time the tab bar's design changed, that copy went stale
and a pile of tests started failing against a perfectly healthy app — twice
already, once costing a whole session chasing a bug that was not there. Now the
app simply reports where its tabs and buttons are, and the tests ask. Nothing
changes on screen; what changes is that a tab-bar redesign no longer breaks the
tests that are supposed to be watching it.

## Goals

- [x] The app publishes the strip's regions — the band, every tab, the "+" and
      the "≡" — as the rects its own hit tests read, in client coordinates.
- [x] An absent control is unmistakably absent on the wire, not a rect at the
      origin.
- [x] `menu-bar.ps1` no longer models the "+"'s position, a tab width, or where
      the strip starts.
- [x] `tab-strip.ps1` and `tab-color.ps1` click published rects; the pixel scan
      stays only where the claim is that something is PAINTED.
- [x] A unit test pins that what is published is what `layout()` returned.

## Summary

Filed from **T218 batch 4** (2026-07-31). `menu-bar.ps1` had to learn where the
tab strip's "+" button IS, and there is no way to ask the product - so it now
carries `Strip-Geometry`, a PowerShell re-implementation of
`tab_strip_layout.zig`'s `layout()`: the seven scaled metrics
(`strip_pad_l/r`, `group_gap`, `btn_w`, `tab_gap`, `min_tab_w`, `max_tab_w`),
the `plus_limit` arithmetic, the tab-width clamp, and the
`min(tabs_right + group_gap, plus_limit)` rule that makes the "+" travel.

That is a second source of truth for a layout the product owns, in a language
that cannot be type-checked against it. It is tolerable today only because
every consumer asserts an outcome (a wrong model clicks dead space and the
section fails), but it will drift the moment the strip's metrics change - and
it will drift SILENTLY for any future script that copies the helper without
the assertions around it.

## Why it is worth doing

The duplication was introduced to fix a REAL rot bug, which is the argument for
removing the duplication rather than the argument for keeping it. The constant
it replaced (`46px left of the client's right edge`) was written when a single
tab stretched to fill the strip; **T202** stopped the stretch, and at 125% DPI
the offset landed inside the menu button - five `menu-bar` assertions failing
against a completely healthy product, undetected because the script had not been
re-run since. A product-reported region cannot rot that way.

More than one script wants this. `tab-strip.ps1` and `tab-color.ps1` (T218
batch 2) both scan pixels to locate the selected chiclet, and batch 2 found two
stale geometry claims in them for the same reason. All three would be simpler
and non-rotting against a published answer.

## Sketch

Report the resolved strip in `+list --json` (per window: the `menu`, `new_tab`
and per-tab rects in client coordinates), or add a debug-only IPC verb if
polluting `+list` is unattractive. `layout()` already returns exactly this
shape (`Strip { visible, tab_w, tabs_right, new_tab, menu }`), so the work is
plumbing, not geometry.

Then delete `Strip-Geometry` from `menu-bar.ps1` and re-point the pixel scans in
`tab-strip.ps1` / `tab-color.ps1` at the reported tab rects.

## What shipped

`+list --json` reports a per-window `chrome` object (`{"dpi", "tab_strip":
{"band", "tabs", "new_tab", "menu"}}`), every rect in CLIENT coordinates. They
are **the rects the hit tests read** (`Window.stripRegions` returns the cached
`tab_rects`/`new_tab_rect`/`menu_btn_rect` the painter published, moved into
client space), not a fresh `layout()` pass — a re-layout would need an HDC and
the tab font to measure the titles again, so it could answer with geometry the
window is not currently hit-testing, which is the very drift this ends.

**An empty rect goes on the wire as `null`.** That is the rule the whole report
hangs on: absent means the "≡" on a caption window (T260), a tab that did not
fit, or a strip that has not painted yet, and a consumer taking a zero rect's
center would click x = 0 — which is tab 1. `tab_strip: null` (a window with no
strip) is deliberately distinct from the `chrome` key being missing (a server
that cannot say), so a build older than this cannot be mistaken for a window
without tabs; the harness THROWS on that case rather than guessing.

Deciding to put it in `+list --json` rather than behind a debug-only verb is
**D66**; the Mac server half is **T735**.

Harness side: `Get-TestStripRegions` in `test/win32/lib/ChromeGeometry.ps1` is
the one consumer everything else goes through, and that file's header now names
three sources of truth instead of two — PUBLISHED (ask the product; use this
for a click target), DERIVED (a DIP constant restated exactly), MEASURED (a
capture; the only one that can prove something is PAINTED, and now used only
for that). `Strip-Geometry` in `menu-bar.ps1` models nothing any more, and the
`Strip-Top` helper — a datum that moved three times in three tasks — is gone
entirely, because every point is now client-space to begin with.

`tab-strip.ps1` gained the arrangement that makes both sources honest: it still
SCANS for chiclets, because "an inactive tab is visible against the strip" can
only be proved in pixels, and it now checks that scan against the published
rects. That turned a heuristic into a measured one on the first run — the scan
is systematically 1px generous at each end (chiclet antialiasing).
