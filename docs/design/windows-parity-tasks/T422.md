# T422 - Session-interrupted notice REPLACES the pane's restored banner; banners and window titles must rehydrate across an agent restart

## In plain terms

You can pin a note above any pane — what it is working on, a link, a status.
Until now those notes vanished whenever Ghoztty reopened your windows, and on
the restart path every pane came back showing the same "session interrupted"
message where your note used to be. Now the note comes back, and that message
only takes the space when a pane has no note of its own. Anyone who labels their
panes gets their labels back.

## Goals

- [x] A pane's banner survives a restore and comes back with its text intact.
- [x] A restored pane gets its recorded title back.
- [x] The session-interrupted notice never overwrites a banner the pane already
      has — and is still on screen for a pane that has none.
- [x] A banner change alone is enough to reach the manifest on disk.

## Summary

**User report, 2026-08-03**, after the T120 upgrade: *"When windows were
reopened, all the previous banners were replaced with [the session-interrupted
notice]. I expected banners to be rehydrated, window titles too."*

Two carriers of the session-interrupted notice are written on purpose
(`src/termio/session_notice.zig`, `Remote.zig:783-789`): in-stream text plus an
**OSC 7778 sticky banner**. The banner carrier is the problem here. A pane's
banner is persisted per pane in the session-layout manifest and is supposed to
come back with its text intact across a restart (CLAUDE.md, "Banners are
persisted per pane … so a session-persistence restore brings them back with
their text intact — across app quit/relaunch/upgrade re-attach **and** across an
agent-restart relaunch alike"). On the agent-restart path the notice banner
lands on top of it, so the documented behavior and the shipped behavior
disagree: **every** restored pane loses its banner and shows the same notice
instead.

That is a real loss, not a cosmetic one. The user's banners carry live task
state (goal, status, PR links); the notice carries one sentence that is the
same in every pane. Overwriting N distinct banners with N copies of one
sentence is strictly negative.

## Two halves

1. **Banners must rehydrate.** Restore the persisted banner, and find another
   way to carry the notice that does not consume the pane's single banner slot —
   see **T423**, which wants the notice inline in the scrollback anyway. If the
   notice must remain a banner for the reason `session_notice.zig` documents (a
   ConPTY startup repaint erases in-stream text), then the two need a defined
   precedence and a way back: the user must end up with their own banner, not
   have to clear the notice by hand.
2. **Window titles must rehydrate too.** The user expected them and calls them
   out separately. Verify against the manifest what is actually restored on the
   agent-restart path versus the app-restart path — a title that survives a quit
   but not an agent restart is the same class of bug as the banner.

## Read T421's log evidence first

`pre-kill agent sessions: 0` in the 2026-08-03 upgrade log means the agent held
**zero** sessions going into the swap — which would explain a total loss of
banners and titles without any bug in the restore path at all. But the user
still saw the session-interrupted notice, which is only emitted for a
dead-but-relaunchable tombstone, so both cannot be plainly true. Settle that
before writing any code here: if there was genuinely nothing persisted, this
task is about *why persistence was empty*, not about rehydration.

## Validation

An agent-restart relaunch (the T230 `notify` path) where a pane that had a
banner and a pinned title before the restart has **that same banner and title**
after it, asserted on box — `test\win32\session-relaunch-notify.ps1` is the
script that already drives this path.

## Update from T423 (2026-08-03): the premise changed in your favour

The clause above — "the notice must remain a banner for the reason
`session_notice.zig` documents" — no longer holds. T423 landed the in-stream
copy for real: the notice is folded into the SCROLLBACK before the child's first
byte and held there by a tracked pin across every later reflow, so a ConPTY
startup repaint can no longer erase it. `test\win32\session-relaunch-notify.ps1`
asserts it on the pane's own `+read` text (A11/A12/A13), not on the banner.

So the banner is no longer the only carrier, and dropping it is now a live
option rather than a data-loss. It was deliberately KEPT by T423 for one reason
worth weighing here and nowhere else: the in-stream copy lives above the
viewport, so a user who does not scroll never sees it. The real choice is
therefore between:

- **Drop the notice banner.** The pane's own banner is never clobbered, no
  precedence rule is needed, and this whole half of T422 disappears. Cost: the
  notice is only discoverable by scrolling up.
- **Keep it and define precedence.** Costs the design work described above, and
  still owes the user a way back to their own banner.

Whichever way it goes, decide it here — `session_notice.formatBanner` says the
same thing in its doc comment and defers to this task.

## What shipped (2026-08-03)

**The premise held: persistence was not empty.** T421 settled the
`pre-kill agent sessions: 0` lead — the upgrade script had asked a *debug*-lineage
agent; the release agent had 4 sessions (T421, "What actually happened", item 5).
So this really was a rehydration bug.

**The root cause was smaller than the report.** The win32 manifest leaf
(`session_layout.Leaf`) had **no banner field at all** — the Mac leaf has carried
one since it was written (`SessionLayoutManifest.swift:105`, restored at
`SessionLayoutRestore.swift:442`). Windows never persisted a banner, so every
restored pane came up with an empty slot, on the app-restart path as well as the
agent-restart one. The notice was not overwriting anything; it was moving into a
vacancy that a bug had created. The same walk found `Leaf.title` **captured but
never applied** on restore, which is the pane-title half of "window titles too"
(`title_override` and the tab title pin were already restored — verified by
`session-reattach.ps1` F9, which predates this task).

Three changes, in that order of importance:

- **`banner` joins the manifest leaf**, captured in `App.captureLeaf` from
  `Surface.banner_text` (the raw markdown SOURCE, so the restore re-runs the same
  parser the user's `+set-banner` did) and applied by a new
  `App.restoreLeafPresentation`, which also puts back `Leaf.title`. Terminal
  leaves only — `+set-banner` rejects viewers. Additive and optional, so a
  pre-T422 manifest loads unchanged.
- **A banner change now marks the layout dirty.** `Surface.setPaneBanner` calls
  `App.markLayoutDirty`. Nothing in a banner change touches the topology, and
  `markLayoutDirty` is only wired to topology mutations — so without this a
  banner set hours before a crash was never written, and the field above would
  have been dead weight in exactly the case that matters.
- **Precedence, decided here as this task's `Update from T423` asked** (see
  decision **D2**): *the banner slot belongs to the pane.* The notice keeps its
  in-stream scrollback copy unconditionally, and emits the OSC 7778 carrier only
  when the pane has no banner of its own. A pane with a banner keeps it; a pane
  without one still gets the notice on screen without scrolling. Implemented as
  one plumbed signal, `pane_banner_restored`, from
  `App.restoreAttachOverride` → `apprt.win32.Surface.Overrides.Remote` →
  `Surface.Options.Remote` (shared core) → `termio.Remote.Config`, read once at
  the `did_notify` site in `Remote.threadEnter`.

  It sits in the SHARED core deliberately, so the Mac half is one signal away —
  Mac has the same clobber today and never sets the flag. That is **T432**
  (`seat: mac`), filed rather than left undocumented.

### Two unit tests, none-lane

`session_layout.zig`: the banner round-trips with its markdown source intact
(delimiters, a pipe table and escaped newlines all survive the JSON), a pane with
no banner records none, and a pre-T422 manifest still loads with a null banner.

### Not done here

The pane title restored on the **notify** path is overwritten seconds later by
the fresh shell's own OSC 0 (cmd.exe titles itself on startup). That is expected
and matches Mac, whose comment says as much: the restored title is what matters
on the **re-attach** path, where no new OSC arrives — which is where F9b's
sibling assertion runs.
