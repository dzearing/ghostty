# T422 - Session-interrupted notice REPLACES the pane's restored banner; banners and window titles must rehydrate across an agent restart

## Summary

**User report, 2026-08-03**, after the T120 upgrade: *"When windows were
reopened, all the previous banners were replaced with [the session-interrupted
notice]. I expected banners to be rehydrated, window titles too."*

Two carriers of the session-interrupted notice are written on purpose
(`src/termio/session_notice.zig`, `Remote.zig:783-789`): in-stream text plus an
**OSC 7778 sticky banner**. The banner carrier is the problem here. A pane's
banner is persisted per pane in the session-layout manifest and is supposed to
come back with its text intact across a restart (CLAUDE.md, "Banners are
persisted per pane … so a session-persistence restore brings them back with
their text intact — across app quit/relaunch/upgrade re-attach **and** across an
agent-restart relaunch alike"). On the agent-restart path the notice banner
lands on top of it, so the documented behavior and the shipped behavior
disagree: **every** restored pane loses its banner and shows the same notice
instead.

That is a real loss, not a cosmetic one. The user's banners carry live task
state (goal, status, PR links); the notice carries one sentence that is the
same in every pane. Overwriting N distinct banners with N copies of one
sentence is strictly negative.

## Two halves

1. **Banners must rehydrate.** Restore the persisted banner, and find another
   way to carry the notice that does not consume the pane's single banner slot —
   see **T423**, which wants the notice inline in the scrollback anyway. If the
   notice must remain a banner for the reason `session_notice.zig` documents (a
   ConPTY startup repaint erases in-stream text), then the two need a defined
   precedence and a way back: the user must end up with their own banner, not
   have to clear the notice by hand.
2. **Window titles must rehydrate too.** The user expected them and calls them
   out separately. Verify against the manifest what is actually restored on the
   agent-restart path versus the app-restart path — a title that survives a quit
   but not an agent restart is the same class of bug as the banner.

## Read T421's log evidence first

`pre-kill agent sessions: 0` in the 2026-08-03 upgrade log means the agent held
**zero** sessions going into the swap — which would explain a total loss of
banners and titles without any bug in the restore path at all. But the user
still saw the session-interrupted notice, which is only emitted for a
dead-but-relaunchable tombstone, so both cannot be plainly true. Settle that
before writing any code here: if there was genuinely nothing persisted, this
task is about *why persistence was empty*, not about rehydration.

## Validation

An agent-restart relaunch (the T230 `notify` path) where a pane that had a
banner and a pinned title before the restart has **that same banner and title**
after it, asserted on box — `test\win32\session-relaunch-notify.ps1` is the
script that already drives this path.
