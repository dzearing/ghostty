# T1037 - The agent-refresh confirmation no longer appears for a handoff-capable agent, and agent-upgrade.ps1 has been 27-red about it for 12 days

## In plain terms

When the background helper that keeps your sessions alive needs replacing while
you have live sessions, the terminal used to stop and ask. It now hands the
sessions over to the new helper by itself instead - which is the better
behavior, and is what the newer handoff feature is for. Nobody updated the test
that still expects the question, so a whole safety-net test has been failing
since that feature landed, and nothing was obliged to notice.

## Summary

Found while validating T1033 (agent-upgrade.ps1 is one of the scripts it
touched). `test\win32\agent-upgrade.ps1` runs **27 FAILURE(S) / 79 passed** on
this box at 4361b6592. Every failure is downstream of one expectation:

    FAIL C3 the mandatory confirmation appeared
    FAIL D3 the confirmation appeared
    FAIL E3 the confirmation appeared (a session is live)
    FAIL H6 launch-restore found the stale agent and asked

The cause is in the product, and looks deliberate. `agent_upgrade.evaluate`
(src\apprt\win32\agent_upgrade.zig:187) now returns `.handoff_now` - no dialog -
when the running agent is handoff-capable and no legacy session is live; only a
MIXED-generation mix still returns `.confirm_first`. The harness predates that
arm: its C/D/E/H fixtures build a handoff-capable agent with live sessions and
then wait 40s for a `GhozttyConfirmDialog` that the app is correct not to show.
The sections that ARE current all pass (B's no-op arm, E's silent idle refresh,
F's persistence-off control, H's rebuild-survives asserts).

Two things to fix, and they are separable:

1. **The harness.** C/D/H should assert the handoff path for a handoff-capable
   agent (no dialog, sessions carried across, the decision logged as
   `stale_handoff`), and keep the confirmation assertions on the arm that still
   produces one - a mixed/legacy live session, or a protocol skew. The negative
   controls must stay: "no dialog" has to be proved to be the RIGHT no-dialog,
   not the absence of a check that never ran.
2. **Why nobody noticed.** T884 already records that `agent-upgrade.ps1` has no
   `guard-due` row, so an edit to the agent-upgrade code obliges nobody to
   re-run it. Last recorded green: 2026-08-08 in the log (107 assertions,
   commit 629637a39);
   handoff landed after, and 12 days passed with the harness red at HEAD. Give
   it a row covering `src\apprt\win32\agent_upgrade.zig`, `LocalAgent.zig` and
   the App.zig refresh path, so the next change to the decision arm makes the
   harness due.
