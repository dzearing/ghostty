# T528 - Caption close button shows a BLACK X on its red hover; Windows draws white

## User report (2026-08-06)

"the close X button in the top right has black X on hover while normal
windows have white X."

Every native Windows 11 window flips the close glyph to WHITE when the red
hover fill appears. Ours goes black on at least the user's theme, which reads
as broken chrome at the single most-looked-at control on the window.

## In plain terms

Hover the X in the top-right corner of a Ghoztty window and the button turns
red, the way every Windows window does - but the X on it went BLACK instead of
white. It is the one control everybody looks at, and a black X on red looks
like something is broken with the app rather than like a close button. After
this, the X is white on every theme, exactly like the rest of Windows.

## Goals

- [x] The close button's X is white on its red fill, on every background
- [x] The rule is an invariant the palette tests enforce, not a lucky value
- [x] The tab strip's close glyph keeps its own (different) contrast rule
- [x] The connection pill's red "Reconnect" capsule carries the same white

## Lead (? INFERRED from reading the code - verify against the user's theme)

`paintCaptionSlab` (`src/apprt/win32/Window.zig:~3900`) does the right thing
structurally: on a lit close slab it paints `pal.on_danger` over `pal.danger`.
The suspect is the PALETTE (`src/apprt/win32/chrome_theme.zig:245`):

```
.danger    = accentOn(bar, danger_base),                        // adjusts #C42B1C against the bar
.on_danger = color_math.contrastForeground(accentOn(bar, danger_base)),  // picks black or white
```

`accentOn` adjusts the danger red until it clears its 3:1 floor against the
caption bar. On a bar where that adjustment LIGHTENS the red, the lightened
red's luminance crosses `contrastForeground`'s threshold and the foreground
flips to BLACK - WCAG-clean (the palette tests only assert
`ratio(on_danger, danger) >= 4.4`, which black satisfies on a light red) and
visually wrong: black-on-red is not the OS's close button.

## Direction

Windows' convention IS the spec here (same reasoning as T496): the close hover
glyph is WHITE, full stop. Constrain the danger ADJUSTMENT instead of the
foreground - pick/clamp the close-hover red so that WHITE clears >= 4.5:1
against it (i.e. keep the red dark enough), rather than letting the
foreground flip. That keeps the contrast floors AND the convention. Check the
tab strip's close-hover glyph at the same time - it shares
`danger`/`on_danger`, so it likely has the same defect on the same themes.

## What landed

The palette split the one red into two derivations, because it was answering
two different questions with one color (`chrome_theme.zig`):

- `danger` - the destructive FILL (caption close hover, the connection pill's
  Reconnect capsule). Its luminance is CAPPED so white keeps 4.5:1 on it
  (`dangerFillOn` over the new `color_math.cappedLuminance`).
- `on_danger` - white, always. `contrastForeground` no longer decides.
- `danger_ink` - the destructive MARK on the band (the tab strip's close glyph
  on hover), which keeps the 3:1 chrome floor it always had. It is drawn ON the
  bar with nothing on top of it, so it wants the opposite constraint - capping
  it would have dimmed a glyph that was never wrong.

`remote_pill.ink` now takes `pal.on_danger` for the Reconnect capsule instead
of re-searching a foreground per state, and firms its fill DARKER on hover/press
(the caption slab's own convention) rather than lighter toward the cap.

Where the cap and the 3:1 lift off the band cannot both hold - bands around
`#2F2F2F`..`#595959` - the convention wins and the fill sits at the cap; the
sweep asserts exactly that disjunction rather than dropping the floor.
