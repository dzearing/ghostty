# T170 - +list --pid is answered only by the win32 IPC server (Mac has no pid match)

## Summary

Found by T141's CLI parity audit. `+list` takes both `--tty` and `--pid` from
one shared options struct (`src/cli/list.zig`), so *the flags exist on both
platforms*. But only one of them works on each:

- `--tty` is resolved **client-side** out of the returned list JSON
  (`findPaneNameByTty`), so it works wherever the server reports a tty.
- `--pid` is resolved **server-side**: the CLI forwards `--pid=<n>` as an IPC
  argument and expects the reply's `data.match` to be the pane name
  (`src/cli/list.zig`, the `opts.pid != null` branch). The win32 IPC server
  implements that walk; `macos/Sources/Features/IPC/IPCServer.swift` contains no
  `"pid"` at all (verified by grep), so on macOS the flag parses, dials, and
  then silently produces nothing useful.

A flag that parses on both platforms and only answers on one is worse than a
per-platform flag, because nothing tells the user which case they are in.
CLAUDE.md already documents `--pid` as the Windows, tty-less equivalent of
`--tty`, so the *intent* is a per-OS pair — the defect is that the shared
options struct advertises both everywhere.

Mac-seat work. Pick one:

1. **Implement the pid walk on the Mac** (ancestry walk from the given pid to a
   pane's shell, same as win32's), making both flags work on both seats. This is
   the parity-maximal answer and `--pid` is genuinely useful on macOS too (a
   process in a pane with no controlling tty).
2. **Gate the flags per-OS** so `--pid` is rejected with a clear message on
   macOS and `--tty` likewise on Windows. Cheap and honest, but it makes the CLI
   surface differ per platform, which is what T141 just finished removing — so
   only take this if 1 is disproportionate.

*Validation:* on the Mac seat, `ghoztty +list --pid=$$` from inside a pane prints
that pane's name (or, for option 2, a clear rejection); `pane-id.ps1` and
`ipc-p1..p3` stay ALL PASS on Windows.
