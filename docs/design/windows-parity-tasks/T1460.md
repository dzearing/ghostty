# T1460 - Split lock-wait from parse in the agent feed telemetry, so the 500 ms-per-second is attributed

## Summary

T1458's capture put roughly **500 ms of every wall-clock second** inside
`termio/Remote.zig`'s `processOutputTracked` call while the pane moved only
~50 KB - about 10 ms per KB, which no terminal parser is. The clock T1458 added
(`perf agent_feed ... parse_ms_per_s=`) brackets the whole call, and
`processOutputTracked` SELF-LOCKS the renderer mutex, so that number is lock
wait PLUS parse and cannot say which. Until it is split, the leading explanation
of the whole defect is an inference.

The inference is a strong one and worth stating so this task knows what it is
testing: the renderer ran at 12 fps in those same seconds, and 12 frames x ~40 ms
of held mutex is ~480 ms/s, which matches `parse_ms_per_s` almost exactly. If the
split confirms it, the io thread is being starved by the renderer holding the pane
mutex across a slow `drawFrame`, and the work moves to the draw path (T1461). If
it does not, the parser really is the cost and the work moves there instead. Both
are real outcomes; the point is to stop guessing between them.

## In plain terms

We can see that half of every second disappears somewhere between the terminal
receiving text and showing it, but not yet WHICH half - waiting for a turn, or
doing the work. This adds the one measurement that tells them apart, so the fix
that follows is aimed at the thing that is actually slow rather than the thing
that looked slow.

## Details

`src/apprt/win32/IpcHandlers.zig` already does exactly this split for the IPC
handler (T111a/T111b: "LOCK WAIT vs work under the lock") and is the pattern to
copy - including its habit of reporting both numbers on one line so a reader
cannot see one without the other.

Mechanically the awkward part is that `Termio.processOutputTracked` takes the
mutex itself, so the split needs either a variant that reports its own acquire
time or a `GHOZTTY_PERF`-only pre-acquire probe around the call. Prefer whichever
does not change lock ORDER or hold duration when telemetry is off - a measurement
that perturbs the thing it measures is worse than none, and this mutex has three
separate prior tasks (T111b, T114, T115) about starvation under it.

## MEASURED 2026-09-08 - the leading hypothesis is REFUTED

`perf agent_feed` now carries `lock_ms_per_s` and `work_ms_per_s` beside
`parse_ms_per_s`. Same 400,000-chunk workload as T1458, same box, same isolated
Debug build, `GHOZTTY_PERF=1`; artifacts under
`%TEMP%\t1458\gh-20260908-131232\`.

Across the **28 sustained seconds** of the drain:

| | ms/s summed | share of `parse_ms_per_s` |
|---|---|---|
| lock wait | 12 | **0.08%** |
| work under the lock | 14,450 | **99.83%** |
| total, as `parse_ms_per_s` | 14,474 | 100% |

Representative seconds, straight off the line:

```
kb_per_s=56 slices_per_s=14 feeds_per_s=3 parse_ms_per_s=683 lock_ms_per_s=1 work_ms_per_s=682 yield_ms_per_s=0
kb_per_s=61 slices_per_s=15 feeds_per_s=3 parse_ms_per_s=605 lock_ms_per_s=1 work_ms_per_s=604 yield_ms_per_s=0
kb_per_s=50 slices_per_s=12 feeds_per_s=3 parse_ms_per_s=510 lock_ms_per_s=1 work_ms_per_s=509 yield_ms_per_s=0
```

**The io thread is not being starved by the renderer.** Lock wait is one
millisecond per second - noise. The "12 fps x ~40 ms of held mutex = ~480 ms/s"
arithmetic in T1458 matched the total for the reason two unrelated numbers
sometimes do: the drain really does sit in that call for half of every second,
but it is *inside* `processOutputLocked` doing work, not queued outside it
waiting for a turn. Renderer-mutex starvation is now ruled OUT, alongside the
present (T1458) and the T111b handoff (`yield_ms_per_s` is still 0 everywhere).

**A caveat this finding must carry: every number here is off a Debug build**,
whose own startup log says performance will be very poor. The *ratio* is
build-independent - lock wait is 0.08% of the cost whatever the parser costs -
but the ~500 ms/s *rate* is not. Filed as **T1463**, which must land before T1461
optimises anything, or T1461 will be measuring the recovery of Debug overhead.

### Verdict for T1461

Point it at the **parse path**, not the draw path. What has to be explained is
why `processOutputLocked` takes ~40 ms per 4 KiB slice.

## Goals

- [x] `perf agent_feed` reports lock wait and work under the lock as separate
      numbers on the same line. **Done**: `lock_ms_per_s` / `work_ms_per_s`,
      with `parse_ms_per_s` kept on the line as their sum so the partition can
      be checked rather than trusted.
- [x] The 400k-chunk workload from T1458 is re-run and the ~500 ms/s is
      attributed to one of them with a number. **Done**: 99.83% work, 0.08% lock
      wait, over 28 sustained seconds.
- [x] The finding is written into T1458 and this task, and T1461 is pointed at
      whichever path won. **Done**: the parse path.

## Validation criteria

- [x] Telemetry off: no measurable change to the drain rate of the T1458
      workload (compare against the 9,088 ms / ~50 KB/s baseline).
      **Done**: 8,860 ms with `GHOZTTY_PERF` unset - and zero `agent_feed` lines
      emitted, which is the proof it was actually off - against 8,927 ms with it
      on and T1458's 9,088 ms baseline. That 2.5% spread runs the wrong way for
      a telemetry cost. The off path also calls the untouched original function,
      by construction: the timed twin is selected only when the counters are on.
- [x] Telemetry on: the two new numbers sum to approximately the existing
      `parse_ms_per_s`, which is the arithmetic proof they partition it.
      **Done**: worst per-second delta across all 28 busy seconds is **1 ms**,
      which is the whole-millisecond rounding of the three terms.
- [x] `powershell -NoProfile -File scripts\floor-lane.ps1 -Lane all` green.
