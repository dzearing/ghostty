# T1460 - Split lock-wait from parse in the agent feed telemetry, so the 500 ms-per-second is attributed

## Summary

T1458's capture put roughly **500 ms of every wall-clock second** inside
`termio/Remote.zig`'s `processOutputTracked` call while the pane moved only
~50 KB - about 10 ms per KB, which no terminal parser is. The clock T1458 added
(`perf agent_feed ... parse_ms_per_s=`) brackets the whole call, and
`processOutputTracked` SELF-LOCKS the renderer mutex, so that number is lock
wait PLUS parse and cannot say which. Until it is split, the leading explanation
of the whole defect is an inference.

The inference is a strong one and worth stating so this task knows what it is
testing: the renderer ran at 12 fps in those same seconds, and 12 frames x ~40 ms
of held mutex is ~480 ms/s, which matches `parse_ms_per_s` almost exactly. If the
split confirms it, the io thread is being starved by the renderer holding the pane
mutex across a slow `drawFrame`, and the work moves to the draw path (T1461). If
it does not, the parser really is the cost and the work moves there instead. Both
are real outcomes; the point is to stop guessing between them.

## In plain terms

We can see that half of every second disappears somewhere between the terminal
receiving text and showing it, but not yet WHICH half - waiting for a turn, or
doing the work. This adds the one measurement that tells them apart, so the fix
that follows is aimed at the thing that is actually slow rather than the thing
that looked slow.

## Details

`src/apprt/win32/IpcHandlers.zig` already does exactly this split for the IPC
handler (T111a/T111b: "LOCK WAIT vs work under the lock") and is the pattern to
copy - including its habit of reporting both numbers on one line so a reader
cannot see one without the other.

Mechanically the awkward part is that `Termio.processOutputTracked` takes the
mutex itself, so the split needs either a variant that reports its own acquire
time or a `GHOZTTY_PERF`-only pre-acquire probe around the call. Prefer whichever
does not change lock ORDER or hold duration when telemetry is off - a measurement
that perturbs the thing it measures is worse than none, and this mutex has three
separate prior tasks (T111b, T114, T115) about starvation under it.

## Goals

- [ ] `perf agent_feed` reports lock wait and work under the lock as separate
      numbers on the same line.
- [ ] The 400k-chunk workload from T1458 is re-run and the ~500 ms/s is
      attributed to one of them with a number.
- [ ] The finding is written into T1458 and this task, and T1461 is pointed at
      whichever path won.

## Validation criteria

- [ ] Telemetry off: no measurable change to the drain rate of the T1458
      workload (compare against the 9,088 ms / ~50 KB/s baseline).
- [ ] Telemetry on: the two new numbers sum to approximately the existing
      `parse_ms_per_s`, which is the arithmetic proof they partition it.
- [ ] `powershell -NoProfile -File scripts\floor-lane.ps1 -Lane all` green.
