# T419 - Packaging steps are bash scripts: make the build universal from zig build on both platforms

## In plain terms

Nothing about this one is visible in the terminal. It answers a question the user
asked: when we build things, should we be using something that works the same on
any machine? The answer turned out to be that almost everything already does —
one single step, turning the built files into a Windows installer, needs a Linux
tool, and that step now happens on the build machine where the tool is native.
What is left is tidying up so there is one way to make a release rather than two.

## Summary

`dist/windows-installer/*.sh` and `relay/deploy/*.sh` are only runnable on
Windows through the msitools Docker image. Investigate folding packaging into
`zig build` steps so one command works on either platform. Prompted by a
2026-08-03 report of an `.sh` being executed on Windows, plus the user's
question: "when we build things, should we be using something more universal
that can work on any platform?"

## What is true today (verified 2026-08-03)

- **The compile IS already universal.** `zig build` is the single entry point
  on both platforms; the only difference is `-Dapp-runtime` and what comes
  out. Nothing about producing the binaries needs a shell.
- **The PACKAGING is not.** 17 tracked `.sh` files, of which the load-bearing
  ones are `dist/windows-installer/build-msi.sh`, `build-portable-zip.sh`,
  `build-release-artifacts.sh`, `relay/deploy/msi/build-msi.sh`,
  `relay/deploy/publish-agent.sh` and `scripts/deploy-windows-agent.sh`.
  They exist in bash because the MSI is compiled with `wixl` (GNOME
  msitools), which is a Linux/macOS tool.
- **Windows already routes around it with a container, not a native shell.**
  `scripts/publish-windows-release.ps1` runs them as
  `Invoke-InImage bash dist/windows-installer/build-msi.sh ...` inside the
  local msitools Docker image (lines 122, 172). So on Windows these scripts
  are supposed to run in Linux; a native invocation is a mistake, not a
  supported path. Whatever tried to execute an `.sh` directly on Windows was
  bypassing `publish-windows-release.ps1`.
- Consequence: releasing from Windows requires Docker Desktop to be running.
  That is a real dependency and a real failure mode, and it is the thing this
  task is about removing.

## Options to weigh (pick one, write down why)

1. **Fold packaging into `zig build` steps.** Zig is already the universal
   entry point and its build graph can run programs, copy trees, and generate
   files cross-platform. The MSI compile still needs wixl, so this either
   shells out to wixl where it exists and to the container where it does not,
   or moves MSI generation to a Zig implementation. Best long-term fit with
   how the project already works; largest change.
2. **Keep the scripts, make the container the only supported invocation on
   every platform** (including macOS), and add a guard that fails fast with a
   clear message when a script is run outside it. Cheapest; does not remove
   the Docker dependency, only makes it honest.
3. **Rewrite the packaging scripts in a cross-platform language** (Python is
   already a build-time dependency here via `dist/website/update-windows-links.py`
   and `scripts/e2e/*.py`). Middle cost; still needs wixl for the MSI itself.

Whatever is chosen must keep the property `publish-windows-release.ps1`
already protects: the release artifacts and the version stamping come from
ONE definition so they cannot drift between platforms.

## What is true today (re-verified 2026-09-04)

The task was filed on 2026-08-03 and the ground moved under it twice since.

- **The Docker dependency this task exists to remove is already gone from the
  path that matters.** T1292 (2026-09-03) took the daily publish off
  `publish-windows-release.ps1` entirely: `scripts\daily-publish.ps1` now pushes
  a `win-v<X.Y.Z>` tag, and `.github/workflows/release-windows.yml` builds the
  MSI + portable ZIP on `ubuntu-latest` from the same
  `dist/windows-installer/build-release-artifacts.sh`. Releasing from this box no
  longer requires Docker Desktop. The old local path survives only behind
  `daily-publish.ps1 -Local`.
- **Bash on Windows is not the problem, and is already a supported path.**
  `test\win32\release-artifacts.ps1` runs `build-portable-zip.sh` (lines 287-306)
  and `sign-artifacts.sh` (lines 742+) under **Git Bash natively on Windows**,
  and those sections pass here. So the portability line is not "bash vs
  `zig build`" — it is **wixl vs everything else**. Exactly one step in the whole
  packaging chain cannot run on Windows: compiling the MSI with `wixl` (GNOME
  msitools, Linux/macOS only).
- **T417 is done** — the standalone agent MSI is retired and `relay/deploy/msi/`
  is deleted — so the surface this task had to make portable already shrank, as
  the sequencing note below anticipated.
- `relay/deploy/publish-agent.sh` is **not** dead: it still publishes
  `/dl/version.json` and `/dl/ghoztty-agent.exe` for the `--relay` self-updater,
  and retires with that updater under T550. It is blocked on ssh key material
  (T1200, `seat: mac`), not on being a shell script.

## Decision: option 2, refined — bash stays, Linux is the one supported host, and the local Docker path goes

**Chosen: option 2**, with the fence drawn around `wixl` rather than around
"`.sh` files". Concretely: the packaging scripts remain bash, CI on
`ubuntu-latest` is the single supported place the **MSI** is compiled, the
non-wixl scripts keep running anywhere bash runs (including natively on Windows,
as they already do), and the local-Docker publish path is retired rather than
maintained as a second definition of how a release is made.

**Why not option 1 (fold packaging into `zig build`).** It does not remove the
dependency it is meant to remove. A `zig build` step still has to invoke `wixl`
where it exists and a container where it does not, so the graph gains a step and
loses nothing. Option 1's honest form is *write an MSI writer in Zig*, and that
is a large, security-relevant piece of work with zero user-visible payoff — and
an actively bad idea right now, because Defender already flags our unsigned
output as `Wacatac.C!ml` (T1293, D89) and a hand-rolled MSI writer makes that
trust problem worse, not better. The property this task was told to protect —
one definition of the artifact set and the version stamping — is already held by
`build-release-artifacts.sh` being the single script both CI and the on-box path
call.

**Why not option 3 (rewrite in Python).** It moves the same logic to a second
language while keeping the wixl dependency intact. Pure churn: the scripts stop
being bash and still cannot compile an MSI on Windows.

**What option 2 buys.** The one genuinely non-portable step runs where it is
native, on a machine that is always available and is already building it on every
push; the loop keeps its rule that starting Docker Desktop is the user's call;
and the remaining work is deletion and fencing rather than reimplementation.
