# T419 - Packaging steps are bash scripts: make the build universal from zig build on both platforms

## Summary

`dist/windows-installer/*.sh` and `relay/deploy/*.sh` are only runnable on
Windows through the msitools Docker image. Investigate folding packaging into
`zig build` steps so one command works on either platform. Prompted by a
2026-08-03 report of an `.sh` being executed on Windows, plus the user's
question: "when we build things, should we be using something more universal
that can work on any platform?"

## What is true today (verified 2026-08-03)

- **The compile IS already universal.** `zig build` is the single entry point
  on both platforms; the only difference is `-Dapp-runtime` and what comes
  out. Nothing about producing the binaries needs a shell.
- **The PACKAGING is not.** 17 tracked `.sh` files, of which the load-bearing
  ones are `dist/windows-installer/build-msi.sh`, `build-portable-zip.sh`,
  `build-release-artifacts.sh`, `relay/deploy/msi/build-msi.sh`,
  `relay/deploy/publish-agent.sh` and `scripts/deploy-windows-agent.sh`.
  They exist in bash because the MSI is compiled with `wixl` (GNOME
  msitools), which is a Linux/macOS tool.
- **Windows already routes around it with a container, not a native shell.**
  `scripts/publish-windows-release.ps1` runs them as
  `Invoke-InImage bash dist/windows-installer/build-msi.sh ...` inside the
  local msitools Docker image (lines 122, 172). So on Windows these scripts
  are supposed to run in Linux; a native invocation is a mistake, not a
  supported path. Whatever tried to execute an `.sh` directly on Windows was
  bypassing `publish-windows-release.ps1`.
- Consequence: releasing from Windows requires Docker Desktop to be running.
  That is a real dependency and a real failure mode, and it is the thing this
  task is about removing.

## Options to weigh (pick one, write down why)

1. **Fold packaging into `zig build` steps.** Zig is already the universal
   entry point and its build graph can run programs, copy trees, and generate
   files cross-platform. The MSI compile still needs wixl, so this either
   shells out to wixl where it exists and to the container where it does not,
   or moves MSI generation to a Zig implementation. Best long-term fit with
   how the project already works; largest change.
2. **Keep the scripts, make the container the only supported invocation on
   every platform** (including macOS), and add a guard that fails fast with a
   clear message when a script is run outside it. Cheapest; does not remove
   the Docker dependency, only makes it honest.
3. **Rewrite the packaging scripts in a cross-platform language** (Python is
   already a build-time dependency here via `dist/website/update-windows-links.py`
   and `scripts/e2e/*.py`). Middle cost; still needs wixl for the MSI itself.

Whatever is chosen must keep the property `publish-windows-release.ps1`
already protects: the release artifacts and the version stamping come from
ONE definition so they cannot drift between platforms.
