# T1334 - zig-crash-repro.ps1's control arm still cannot run, so its comparison has only one side

## Summary

`scripts\zig-crash-repro.ps1` (T449) replays a lane's exact `zig test` command
standalone and correlates each run against the Windows Application log, to
measure how often `zig.exe` faults on OUR workload. It was built with a CONTROL
arm - the same compiler, a workload that is not ours - because a crash rate
with nothing to compare it against cannot say whether ghoztty's build is
special or the compiler simply crashes.

That arm has never worked. `zig test` on zig's own `std.zig` fails immediately:
several std tests `@embedFile` their data by relative path, so the run needs its
working directory set to the zig lib dir, or a different non-ghoztty workload
picked entirely. Left as it is, the script is an instrument with one probe.

Noted while closing **T451**, which answered the neighbouring question by a
cheaper route (the installed compiler is byte-identical to the official 0.15.2
release, so "a different build of zig" is not a variable) and left this one
untouched.

## In plain terms

We have a tool for measuring how often the compiler crashes while building our
code. It was supposed to compare that against building something else, and the
"something else" half has never run. Until it does, the number it produces
cannot answer the question it was built for.

## Goals

- [ ] The control arm runs to completion against a non-ghoztty workload
- [ ] A run reports both rates side by side, and says plainly whether ours is
      the outlier

## Validation criteria

- [ ] `scripts\zig-crash-repro.ps1` completes its control arm without the
      `@embedFile` failure, on this box.
- [ ] Its output names both arms and their crash counts in the same summary.
