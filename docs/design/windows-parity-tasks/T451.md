# T451 - zig.exe takes access violations at two repeating offsets - the compiler, not our code, and a red lane cannot tell a compiler crash from a test failure

## Summary

Filed out of **T449** (2026-08-04), which set out to decide whether the crashes
plaguing the floor lanes are the machine, a security product, or the toolchain.
The machine came back clean under measurement; the compiler did not.

`zig.exe` — the compiler itself, not any ghoztty binary — has taken **8 fatal
faults in 21 days on this box**, and they are not spread randomly:

```
08-04 04:54:35  c0000005  zig.exe+0x02303d52
08-04 03:39:24  c0000005  unknown+0x8669f77d80     (jump into no loaded module)
08-04 02:43:54  c0000005  zig.exe+0x0230f248
08-04 01:18:58  c0000005  zig.exe+0x037ddea2
08-04 01:17:00  c0000005  unknown+0x10             (null pointer + field offset)
08-03 23:55:01  c0000005  unknown+0x2ac6d5d0000    (executing at a heap address)
08-03 23:51:42  c0000409  ntdll.dll+0x44ffd        (fail-fast: corruption detected)
07-27 22:34:53  c0000005  ntdll.dll+0x4415a
```

**Two of those offsets are 48 KB apart in the same binary** (`0x2303d52` and
`0x230f248`). zig.exe is a ReleaseFast build with ASLR, so the offsets reported
here are module-relative and stable across runs — which means a repeated
offset is a repeated *code path*, not a coincidence. Random memory corruption
from a failing machine does not concentrate like that; a real bug does.

This matters for the lanes as well as for the compiler. Today a `zig.exe` crash
surfaces as `compile test … failure` with `error code 5` and reads exactly like
a broken build (see T444, which decoded the `5`). It is not one, and nothing
distinguishes it from a genuine failure without going to the Windows event log
by hand.

## In plain terms

The compiler we build with occasionally crashes — about eight times in three
weeks, and twice in the very same place. When it does, the build reports a
confusing failure that looks like our code is broken. It is not; it just needs
to be retried and reported as what it is.

## Goals

- [ ] A lane that fails because the *compiler* crashed says so, and is retried,
      rather than being counted as a test failure
- [ ] Establish whether a different zig binary reproduces it (there is only one
      zig on this box — a WinGet 0.15.2 — so nothing has been ruled out yet)
- [ ] If it survives a second binary, it is worth an upstream report with the
      repeated offsets and the crashing command line

## Suggested approach

- `scripts/zig-crash-repro.ps1` (added by T449) already replays the lane's exact
  ~10 KB `zig test` command standalone and correlates each run against the
  Application Error log. Its **control arm is not yet working** — `zig test` on
  zig's own `std.zig` fails immediately because several std tests `@embedFile`
  test data by relative path, so the arm needs its working directory set to the
  zig lib dir (or a different non-ghoztty workload picked).
- Retry policy belongs next to the decode that already exists in
  `scripts/lib/CrashDiag.ps1`: if the crashed process is `zig.exe`, that is a
  toolchain fault, not a result.
- Getting a second 0.15.2 binary is cheap and is the one experiment that cleanly
  separates "this build of zig" from "zig 0.15.2".

## Validation

- A forced compiler crash produces a lane result that names the compiler and
  retries, rather than `N FAILURE(S)`.
- The second-binary experiment is run and its outcome recorded here either way.
