# T451 - zig.exe takes access violations at two repeating offsets - the compiler, not our code, and a red lane cannot tell a compiler crash from a test failure

## Summary

Filed out of **T449** (2026-08-04), which set out to decide whether the crashes
plaguing the floor lanes are the machine, a security product, or the toolchain.
The machine came back clean under measurement; the compiler did not.

`zig.exe` — the compiler itself, not any ghoztty binary — has taken **8 fatal
faults in 21 days on this box**, and they are not spread randomly:

```
08-04 04:54:35  c0000005  zig.exe+0x02303d52
08-04 03:39:24  c0000005  unknown+0x8669f77d80     (jump into no loaded module)
08-04 02:43:54  c0000005  zig.exe+0x0230f248
08-04 01:18:58  c0000005  zig.exe+0x037ddea2
08-04 01:17:00  c0000005  unknown+0x10             (null pointer + field offset)
08-03 23:55:01  c0000005  unknown+0x2ac6d5d0000    (executing at a heap address)
08-03 23:51:42  c0000409  ntdll.dll+0x44ffd        (fail-fast: corruption detected)
07-27 22:34:53  c0000005  ntdll.dll+0x4415a
```

**Two of those offsets are 48 KB apart in the same binary** (`0x2303d52` and
`0x230f248`). zig.exe is a ReleaseFast build with ASLR, so the offsets reported
here are module-relative and stable across runs — which means a repeated
offset is a repeated *code path*, not a coincidence. Random memory corruption
from a failing machine does not concentrate like that; a real bug does.

This matters for the lanes as well as for the compiler. Today a `zig.exe` crash
surfaces as `compile test … failure` with `error code 5` and reads exactly like
a broken build (see T444, which decoded the `5`). It is not one, and nothing
distinguishes it from a genuine failure without going to the Windows event log
by hand.

## In plain terms

The compiler we build with occasionally crashes — about eight times in three
weeks, and twice in the very same place. When it does, the build reports a
confusing failure that looks like our code is broken. It is not; it just needs
to be retried and reported as what it is.

## Goals

- [x] A lane that fails because the *compiler* crashed says so, and is retried,
      rather than being counted as a test failure — `COMPILER CRASH` block +
      one retry per lane, `scripts/lib/CompilerCrash.ps1`
- [x] Establish whether a different zig binary reproduces it — answered without
      the soak: there is no *different* binary. The installed compiler is
      byte-identical to the official release (see **Findings**)
- [x] If it survives a second binary, it is worth an upstream report with the
      repeated offsets and the crashing command line — it does survive, and a
      report needs a stack we cannot yet capture: **T1333**

## Validation criteria

- [x] A forced compiler crash produces a lane result that names the compiler and
      retries — arm 10 of `test/win32/floor-lane-compiler-crash.ps1` drives a
      real access-violating process named `zig.exe` through the wrapper on the
      background test desktop
- [x] A test-binary crash in the same window vetoes the verdict — arms 2, 3, 6
- [x] An ordinary non-zero exit is not relabelled and is not retried — arm 11,
      the negative control
- [x] The second-binary experiment is run and its outcome recorded either way —
      **Findings** below

## Findings (2026-09-04)

**The compiler on this box is the official one, bit for bit.** The WinGet
install at
`...\WinGet\Packages\zig.zig_...\zig-x86_64-windows-0.15.2\zig.exe` hashes to

```
SHA256  D408DD38EED3E5204AF841BCEBF70502A4DBBB8399A3A3262BE55059370BC018
```

which is exactly the `zig.exe` inside a freshly downloaded
`zig-x86_64-windows-0.15.2.zip`, whose own SHA256 matches the shasum ziglang.org
publishes in `download/index.json`. Two things follow, and they are why the
"get a second binary" experiment in the task's original approach is now closed
rather than pending:

- **The on-disk binary is not corrupted.** That was a live hypothesis and it
  would have explained faults recurring at fixed offsets perfectly. It is
  eliminated.
- **There is no second binary to try.** One official build exists for this
  target and this box is running it, so a second copy is the same bytes and
  cannot separate "this build of zig" from "zig 0.15.2". What is left to
  separate is zig 0.15.2 from this machine, and that needs a stack, not another
  download — filed as **T1333**.

**The crashes continue.** Eight more `zig.exe` faults in the 32 days to
2026-09-04, and the concentration the task was filed over holds:

```
09-01 14:20  c0000005  zig.exe+0x394d8     x4, within the same minute
08-17 22:39  c0000409  ucrtbase.dll+0xa527e
08-15 13:49  c0000005  ntdll.dll+0x4415a
08-14 18:27  c0000005  zig.exe+0x1e03070
08-14 18:22  80000003  zig.exe+0x136c17b
```

Four faults at one module-relative offset inside a minute, in a ReleaseFast
binary, is a code path rather than a coincidence — so the report the wrapper
now prints names a repeated fault site when it sees one.

## Suggested approach

- `scripts/zig-crash-repro.ps1` (added by T449) already replays the lane's exact
  ~10 KB `zig test` command standalone and correlates each run against the
  Application Error log. Its **control arm is still not working** (now filed as
  **T1334**) — `zig test` on
  zig's own `std.zig` fails immediately because several std tests `@embedFile`
  test data by relative path, so the arm needs its working directory set to the
  zig lib dir (or a different non-ghoztty workload picked).
- Retry policy belongs next to the decode that already exists in
  `scripts/lib/CrashDiag.ps1`: if the crashed process is `zig.exe`, that is a
  toolchain fault, not a result.
- Getting a second 0.15.2 binary is cheap and is the one experiment that cleanly
  separates "this build of zig" from "zig 0.15.2".

## Recurrences

- 2026-08-04 08:33, during the T377 turn's floor run: `LANE agent FAIL`,
  `CRASH zig.exe pid=0x8BD8 0xc0000005 in zig.exe+0x00000000037ddea2` — the
  **same offset** as the 08-04 01:18 entry above, so the two-offset pattern
  holds. A bare re-run of the same lane, no source change, passed in 186s.
  That is the cost this task is about: a red floor that means nothing, which
  the turn only recognised because T444's decode named `zig.exe`.
