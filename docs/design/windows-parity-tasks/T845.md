# T845 - The chevron hover probe still misses its hovered frame about one run in ten

## Summary

Left over after T835 fixed the capture tearing. In 20 clean runs of test/win32/pane-banner.ps1 the T745/T835 value-column assertions were green 20 times, but one run failed the two T204 chevron-fill assertions: 'hovering the chevron lights a fill (rest=35 hot=35)' and 'that fill is ROUNDED (corner=36 edge=35)'. Both read the SAME numbers as the un-hovered probe, and Get-LastHoverCaptureError was empty, so the app-side capture succeeded and simply was not in hover state when it took the frame. That path is Get-TestHoverCapture / the debug-only capture-hover IPC (lib/HoverCapture.ps1, T282), NOT Get-TestWindowPixels, so -Sync does not reach it. Effect: pane-banner.ps1 goes red about 1 run in 10 on a correct build - and since T835 added it to scripts/guard-due.ps1, a red run leaves the guard due and a turn touching banner sources has to re-run it. Work: find why capture-hover occasionally photographs the rest frame (a WM_MOUSELEAVE drained before the app pins the hover? the hover set after the capture stack is entered?) and make the app hold the hovered state for the capture, or fail the capture loudly instead of returning an un-hovered frame.
