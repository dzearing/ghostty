# T845 - The chevron hover probe still misses its hovered frame about one run in ten

## Summary

Left over after T835 fixed the capture tearing. In 20 clean runs of test/win32/pane-banner.ps1 the T745/T835 value-column assertions were green 20 times, but one run failed the two T204 chevron-fill assertions: 'hovering the chevron lights a fill (rest=35 hot=35)' and 'that fill is ROUNDED (corner=36 edge=35)'. Both read the SAME numbers as the un-hovered probe, and Get-LastHoverCaptureError was empty, so the app-side capture succeeded and simply was not in hover state when it took the frame. That path is Get-TestHoverCapture / the debug-only capture-hover IPC (lib/HoverCapture.ps1, T282), NOT Get-TestWindowPixels, so -Sync does not reach it. Effect: pane-banner.ps1 goes red about 1 run in 10 on a correct build - and since T835 added it to scripts/guard-due.ps1, a red run leaves the guard due and a turn touching banner sources has to re-run it. Work: find why capture-hover occasionally photographs the rest frame (a WM_MOUSELEAVE drained before the app pins the hover? the hover set after the capture stack is entered?) and make the app hold the hovered state for the capture, or fail the capture loudly instead of returning an un-hovered frame.

## In plain terms

The automated tests photograph the banner while the little collapse arrow is lit
up, to prove the arrow responds to the pointer. Occasionally the photograph came
back showing the arrow un-lit, and the test then reported a broken button on a
build where nothing was broken. The app now takes that photograph itself instead
of asking the desktop compositor for a copy, and — the part that matters most —
it also photographs the window a moment BEFORE, so it can say whether hovering
changed anything at all. A photograph of the wrong moment can no longer pass
itself off as a working button: it comes back labelled "this changed nothing",
and the test says so.

## Goals

- [x] Take the DWM copy out of the hovered capture's path
- [x] Make a capture that cannot be taken at all fail loudly instead of
      returning a plausible-looking wrong frame
- [x] Make a capture of the WRONG MOMENT self-identify, so the next occurrence
      names its own cause instead of costing another investigation
- [x] Give the seam's own harness an oracle that one sample cannot satisfy

## What was NOT established

The original miss was **not reproduced**, and the DWM hypothesis is
**unproven**. The reasoning was sound — the capture went through
`PrintWindow(PW_RENDERFULLCONTENT)`, the asynchronous DWM copy T835 measured
tearing on, and the banner overlay is a layered window, the exact case T835
measured — but the experiments do not support it:

- 60 iterations of 6g's whole chevron sequence (posted move, `-Sync` rest
  capture, hovered capture) inside one app launch, against a build **still on
  the old flag**: 0 misses.
- 12 back-to-back hovered captures of the chevron, old flag: all lit, all the
  same value.
- 12 consecutive full `pane-banner.ps1` runs after the switch: green, every one
  reading `rest=35 hot=45`. At the observed 1-in-20 rate that is worth about
  0.28 probability of being luck, so it is corroboration and not proof.

So the fix that carries the task is the SECOND one its own Work statement
allows — "fail the capture loudly instead of returning an un-hovered frame".
Whatever the cause turns out to be, the miss can no longer be silent: see
[[T946]] for the two consumer scripts that still do not ask.

## Progress log

- 2026-08-17 17:03: claimed; work starting.
- 2026-08-17 17:06: root cause: capture-hover's own grab (src/apprt/win32/ipc_hover.zig capture()) still calls PrintWindow(PW_RENDERFULLCONTENT) - the ASYNC DWM copy T835 proved hands back a stale/torn frame. The message ordering guarantee is intact (hover IS set, WM_PAINT does run on the stack); what is flaky is that DWM's composited copy can predate that paint, so the capture is the REST frame with no error - exactly the reported rest=35 hot=35. Fix: take the synchronous WM_PRINT/WM_PRINTCLIENT path (flags=0) that Get-TestWindowPixels -Sync already uses, plus a sentinel pre-fill so a window with no WM_PRINTCLIENT handler fails loudly instead of returning an un-hovered frame.
- 2026-08-17 18:00: hypothesis NOT confirmed: with the app still on PW_RENDERFULLCONTENT, 60 iterations of 6g's whole chevron sequence in one launch produced 0 misses, and 12 back-to-back chevron captures were all lit and identical. So the DWM copy is not a demonstrated cause. Took the second route the task allows instead: capture-hover now photographs the window BEFORE the move too and reports data.changed, so a capture of the un-hovered moment is a named failure rather than a valid PNG. Kept the synchronous WM_PRINTCLIENT capture (T835 precedent, removes DWM from the path) and the sentinel refusal. Assertions added in hover-capture.ps1 and pane-banner.ps1 6g (both polarities); guard-due row added for the seam; filed T946 for the two consumer scripts that still infer instead of asking.
