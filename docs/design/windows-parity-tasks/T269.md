# T269 - A release-lineage acceptance test cannot run beside the user's real agent (SID-keyed single-instance guard, no Windows override)

## In plain terms

Ghoztty's automated tests all run against a developer build. The build people
actually use behaves differently in a few ways that matter, and there was no way
to test it here: a test copy and the real Ghoztty both wanted the same
background process, and only one of them can have it. The test copy either lost
(and then quietly measured the wrong thing) or, in the wrong circumstances,
could have killed the real one and every terminal it was keeping alive. Now a
test run can be given its own private identity, so it runs happily alongside the
terminal you are sitting in and leaves it completely untouched — which the test
itself checks, before and after.

## Goals

- [x] The release lineage is isolatable on every axis it is named on: guard,
      heartbeat, agent pipe, state dir, autostart entry.
- [x] An acceptance script can run release binaries beside the user's own agent
      and prove it left them alone.
- [x] The guard still guards inside a lineage — isolation, never a way to turn
      the single-instance rule off.
- [x] The consumer conversion that needs a second mechanism is filed, not
      silently dropped.

## Summary

**Every acceptance script on this box tests the DEBUG lineage, and there is
currently no way to test the RELEASE one while the user is using their
terminal.** That is a coverage hole with teeth: the user runs ReleaseFast, and
ReleaseFast differs from Debug in ways that matter — safety checks off, GUI
subsystem instead of Console, and a completely different log sink (the
`%LOCALAPPDATA%\ghoztty\ghoztty.log` file, which Debug builds do not write at
all). A defect that only exists in the shipped configuration cannot be
reproduced or regression-tested today.

Found while trying to reproduce T229 in the configuration the user actually
runs.

## Evidence (VERIFIED on box, 2026-08-01)

Two release-lineage identifiers are derived from the USER, not from the run,
and only one of them has an override:

| Resource | Composition | Isolatable? |
|---|---|---|
| app IPC pipe | `\\.\pipe\ghoztty[-debug]-<USERNAME>` | yes — `GHOZTTY_PIPE_SUFFIX` |
| agent state dir | `%LOCALAPPDATA%\ghoztty\local-agent[-debug]\` | yes — `LOCALAPPDATA` |
| agent pipe | `\\.\pipe\ghoztty-agent[-debug]-<USERNAME>` (`LocalAgent.pipeName`) | only by faking `USERNAME` |
| **single-instance guard** | `Global\GhozttyAgentDaemon-local-<user SID>` (`single_instance.zig`) | **no** |

The guard is the blocker. `GHOSTTY_AGENT_LOCK` exists but is **POSIX only** (it
resolves a flock path); the Windows arm is a named mutex whose name has no
override at all. So a test-spawned release agent loses the race against the
user's live agent and exits 183:

```
warning(win32_local_agent): local agent did not become dialable within 2000ms
info(win32): session-restore: no local agent; opening a blank window
```

It yielded rather than killing the holder only because the redirected
`LOCALAPPDATA` also hid the heartbeat file, which the takeover logic reads as
"old-binary holder → yield". **That is luck, not design**: with the heartbeat
visible and stale, a test run would have TERMINATED the user's real agent and
every session on it, including the one the test was launched from.

## Direction

Give the local agent's guard the same test hook its POSIX sibling already has,
keyed so it cannot collide:

- An explicit override for the Windows mutex name (e.g. `GHOSTTY_AGENT_LOCK`
  reused as a *name segment* on Windows rather than a path, or a dedicated
  `GHOSTTY_AGENT_INSTANCE_KEY`), applied to the mutex AND the heartbeat
  filename so a test lineage is isolated on both.
- The same segment should reach `LocalAgent.pipeName`, so a release-lineage
  test does not have to fake `USERNAME` to avoid the user's agent pipe.
- Honour it in release builds (unlike `GHOZTTY_AGENT_BUNDLED_VERSION`, which is
  debug-only by design): the whole point is to test the shipping build. It is
  not dangerous in the way the version hook is — it isolates rather than
  destroys, and the destructive verbs still consult the redirected state.

Then a `-Release` switch on the acceptance scripts that need it (starting with
`agent-upgrade.ps1`, whose arm H is T229's regression guard).

## What landed (2026-08-11)

The OVERRIDE half of the Direction above shipped as **T167**
(`GHOZTTY_AGENT_INSTANCE`, `src/remote/agent_lineage.zig`): one suffix moves the
guard mutex, the lock and heartbeat files, the app's agent state dir, the agent
pipe name, the HKCU Run value and the dir `+sessions` reads. It is honored in
RELEASE builds — deliberately, unlike `GHOZTTY_AGENT_BUNDLED_VERSION` and
`GHOZTTY_AGENT_PROTO_VERSION`, which are debug-only because they DESTROY rather
than isolate. T167's acceptance, though, only ever ran it in the debug lineage,
which is the half T269 is about.

So this task delivered the release-lineage proof:
`test/win32/agent-instance-lineage.ps1 **-Release**` runs the identical arms
against the ReleaseFast staging build in `zig-out-release`. Three knobs isolate
it — `GHOZTTY_AGENT_INSTANCE` (agent half), `GHOZTTY_PIPE_SUFFIX` (app half),
`LOCALAPPDATA` (files) — and the run measures the box it is a guest on rather
than asserting good manners:

- **Bystander agents**: every `ghoztty-agent.exe` this run did not start is
  recorded before and required alive after. In `-Release` that set contains the
  user's own installed agent, holding their live panes — the incumbent whose
  guard is what made this untestable.
- **Autostart Run values**: the user's `GhozttyAgent` value must be byte-for-byte
  unchanged; a release build DOES write the Run key (a debug one does not), and
  the value it writes carries the lineage suffix, so it can only ever be a new
  name beside theirs. It is asserted to be ours, then deleted — a Run entry
  pointing into `%TEMP%` would try to start a deleted agent at every logon.
- **Release-only launch hardening**: `GHOZTTY_URL_SCHEME=0` (a release build
  registers `HKCU\Software\Classes\ghoztty` at its own exe, i.e. it would
  repoint the user's real `ghoztty://` links at `zig-out-release`) and
  `GHOZTTY_PATH_SELFHEAL=0`.

Two things the work turned up, both filed: **T772** (the `-Release` conversion of
`agent-upgrade.ps1`, which needs a genuinely stale agent because its staleness
input is a debug-only hook) and **T773** (a freshly built binary bakes a stale
commit stamp — noticed while checking what the staging build under test was).

Also fixed here, because this task is what made it visible: arm D's agent is
spawned BY THE APP and so was never in the script's own kill list. Both a debug
and a release sandbox agent were found still running after the script exited,
holding a deleted temp state dir and their own image file. Cleanup now also
matches this run's `$root` on the command line — never the image name, which in
the release lineage is the same path the user's agent runs.

## Validation criteria

- [x] With the override set, a release `ghoztty.exe` spawns and dials its OWN
      agent while the user's real agent keeps running — both alive, neither
      disturbed. *Verified: `agent-instance-lineage.ps1 -Release` → `ALL PASS
      (26 checks)`, incl. `D2 the pane is backed by a LIVE session` and
      `bystander agents untouched (before: 1, gone: )`; the user's agent pid
      24620 confirmed alive afterwards, `HKCU\...\Run` back to
      `GhozttyAgent` + `GhozttyGoLoopWatchdog` only, and the `ghoztty` scheme
      still pointing at the installed release.*
- [x] Negative control: within one lineage the guard still refuses the second
      agent (exit 183) rather than taking over. *Verified: arm A2 in the
      `-Release` run, `exit 183`, `A2 published nothing`, `A1 survived`. Run
      against a SANDBOX incumbent rather than the user's real agent on purpose —
      the takeover path kills a holder whose heartbeat has gone stale, and
      pointing that at the user's agent to watch it not happen risks their
      sessions to prove a negative.*
- [x] The switch measures what it claims: a `-Release` run asserts the build
      mode is NOT one of the `-debug`-endpoint modes, so a Debug tree in
      `zig-out-release` cannot pass as a release-lineage run.
- [x] Teeth: `-Release -TeethCheck` (D2 given a lineage another agent holds)
      fails exactly the two D2 assertions and nothing else — `2 FAILURE(S) (23
      passed)`.
- [x] The debug run is unchanged: `ALL PASS (24 checks)`.
- [~] `agent-upgrade.ps1 -Release` reaches at least arm D — **split out as
      T772**. Its staleness input (`GHOZTTY_AGENT_BUNDLED_VERSION`) and its skew
      input (`GHOZTTY_AGENT_PROTO_VERSION`) are debug-only by design, so a
      release-mode run needs a genuinely stale agent (two ReleaseFast agent
      builds with different `-Dagent-version` stamps) rather than the switch this
      task removes the blocker for. Filed with that design rather than shipped
      as a half-mode that would claim more than it tests.
