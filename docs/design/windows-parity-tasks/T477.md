# T477 - ReleaseSafe test binary panics deterministically at renderer.cell test Contents with zero-sized screen - a real defect Debug masks

## Summary

Found under **T473**, which built the test binary at `ReleaseSafe` to see
whether the T443 corruption survived an optimize-mode change. It never got that
far: the ReleaseSafe binary **panics 10 runs out of 10**, always at the same
test, always at the same address, ~11s in.

```
powershell -NoProfile -File scripts\test-binary-soak.ps1 `
    -Exe zig-out-t473\win32-releasesafe\bin\ghostty-test.exe -Runs 10
SOAK: runs=10 pass=0 fail=0 crash=10  crash-rate=10/10 (100%)
  victim: 1401/3878 renderer.cell.test.Contents with zero-sized screen...
  0x80000003 STATUS_BREAKPOINT (Zig panic) ghostty-test.exe+0x00000000004d1a63
```

The same tests at `Debug` pass 3810/3810 in 26 consecutive runs (T473's control
arm), so this is **ReleaseSafe-specific and 100% reproducible** — the opposite
of T443's coin-flip, and much cheaper to chase.

The test is four lines (`src/renderer/cell.zig:498`):

```zig
test "Contents with zero-sized screen" {
    var c: Contents = .{};
    defer c.deinit(alloc);
    c.setCursor(null, null);
    try testing.expect(c.getCursorGlyph() == null);
}
```

**No panic message reaches stderr** — the process just takes the breakpoint.
That is the same silent-death shape T450 recorded for Zig's handler on this box,
so expect to read this from a debugger rather than from the log.

## In plain terms

The project's tests pass when built for debugging and crash when built the way a
shipped build is compiled. Nothing users run is built that way today, so nobody
is hitting it — but "our tests only pass in one build mode" is the kind of gap
that hides a real bug, and this one crashes the same way every single time,
which makes it cheap to find.

## What it turned out to be

Two defects, in series. The second was invisible until the first was fixed,
because the suite never got past test 1954.

**1. `free()` on an `undefined` slice (`src/renderer/cell.zig`).**
`Contents.bg_cells` was declared `= undefined`, but two functions free it
before anything ever assigns it: `deinit()` on a `Contents` that was never
resized (what the zero-sized-screen test does), and the FIRST `resize()`,
which frees the previous buffer before installing the new one — the path the
real renderer takes, since `generic.zig:722` builds its `Contents` with `.{}`.
Freeing `undefined` is UB, and at ReleaseSafe LLVM takes the entitlement: it
compiles the whole tail of the calling function to `unreachable`. cdb shows
the result exactly —

```
ghostty_test!test.Contents with zero-sized screen:
  ...
  call    ghostty_test!setCursor
+0x23:
  cc              int     3          <-- the trap, right after setCursor returns
```

— an `int 3` with no panic message because no panic handler was ever involved;
the test's remaining two lines were simply deleted as unreachable. Debug never
trapped, so 26 consecutive Debug runs said nothing was wrong.

Fix: default `bg_cells` to an empty slice (`&.{}`), which is what its sibling
`fg_rows` already did (`.{ .lists = &.{} }`). Freeing an empty slice is a
defined no-op, so both callers are now well-defined.

**2. A returned pointer into a dead stack frame (`src/apprt/win32/App.zig`).**
With (1) fixed the suite advanced to test 2016,
`restoreWindowHasAttachableLeaf keeps viewer-bearing windows with no agent
(T398)`, which then segfaulted 10 runs out of 10 at a fresh address each time.
Its local `mk.win()` helper built `const tabs = &[_]Tab{...}` from a runtime
`nodes` slice and returned `.{ .tabs = tabs }` — a pointer into `win`'s own
frame. Debug left that memory intact long enough for the assertions to read
it; ReleaseSafe reused the frame. Fix: build the three tab arrays in the test's
own frame, which is the pattern the very next test in the file already used.

Swept the rest of `src/` for the same shape (`const x = &[_]…` whose address
escapes): every other instance is a comptime-constant literal, so there is no
third case.
