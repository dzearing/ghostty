# T1159 - A viewer pane squeezed narrow should look designed, not just trimmed

## Summary

D83 resolution (user, 2026-08-23) accepted option 1 - buttons that do not fit whole are dropped - and added a directive on top of it: the narrow state must look POLISHED AND CONSISTENT, not merely truncated. Two specific things the user asked for. (1) Collapsing the hidden buttons into a '...' overflow menu is explicitly sanctioned ('I would love for it to look designed as you suggest so collapsing them into a ... button is fine'), so the dropped controls become reachable rather than gone. (2) The condensed address bar is unproven and the user is uneasy about it: 'i am quite unsure how an address bar is going to look in a tiny condensed mode. 1 button and 1 tiny input?' - so the narrow layout needs to be designed and looked at, at several widths, rather than falling out of a clamp. T1130 made the strip stop spilling past the pane; this makes what is left look intentional.

## In plain terms

Squeeze a viewer pane - a rendered README next to a terminal - down to a
sliver and its little toolbar has to give something up. Today the buttons
that no longer fit simply disappear, and the address box shrinks to whatever
is left. Nothing is broken and nothing spills over the edge any more, but it
reads as an accident rather than a design: you cannot tell there were more
buttons, you cannot reach them, and the squashed address box has never been
looked at by anyone. After this lands, a narrow pane looks like a deliberate
compact mode - the buttons that do not fit fold into a small "..." menu you
can still open, and the address bar has a designed condensed form instead of
whatever the arithmetic leaves behind.

## Goals

- [x] the buttons dropped by the narrow-pane rule fold into a "..." overflow
      menu instead of vanishing, so every control stays reachable
- [x] the condensed address bar has a designed look at each width band, seen
      and judged on the box rather than derived from a clamp
- [x] the compact state reads as consistent with the rest of the win32 design
      system (spacing on the scale, the same button metrics, no orphan gaps)
- [x] the width bands are covered by the viewer-narrow-pane harness so the
      compact look is asserted, not rediscovered

## Validation criteria

- [x] at a pane width where at least one button is dropped, an overflow
      "..." control is present, is inside the pane, and opens a menu carrying
      exactly the dropped commands. -- `viewer_nav_layout.zig` T1159 tests
      (none + win32 lanes): every wanted command is painted XOR in the menu at
      every width and every variant, the menu never lists itself, and what is
      folded is a suffix of the strip order. On the box, section E of
      `test/win32/viewer-narrow-pane.ps1` measures a control in the leading
      slot at every width down to a 77px pane.
- [x] screenshots at several width bands (wide, one-drop, address-only,
      minimum) reviewed on the box - each looks intentional, with spacing on
      the win32 design scale. -- section E writes a WM_PRINTCLIENT capture per
      band to `%TEMP%/ghoztty-vnp-band-<width>.png`; the four reviewed at
      1.25 scale were 351px (full strip + field), 217px (back, "...", field),
      155px ("..." + field) and 108px ("..." alone). Every control is on the
      shared icon-button metrics with the band's own 4 DIP edge.
- [x] `test/win32/viewer-narrow-pane.ps1` extended to assert the
      overflow control and the condensed address field, ALL PASS, with the
      negative control turning over. -- 56 assertions ALL PASS;
      `-NegativeControl` still turns over with exactly three failures.
- [x] no regression of T1130 - nothing paints outside the pane host at
      any of the tested widths. -- the T1130 containment test is re-asserted
      with the overflow control in the mix, and sections A-D are unchanged and
      green.
