# T560 - Hero carousel strip order is node-array order, not the tree's leaf order

## In plain terms

When one pane is blown up big and the others appear as small previews down
the side, the previews are not in the order the panes appear on screen. Split
a terminal downward into a second pane and the new pane's preview shows up
ABOVE the original's, so the arrow keys walk the strip in an order that does
not match what you are looking at.

## Summary

Found while validating T397 (2026-08-07). `HeroCarousel.geometry`/`paint`
and `Window.leafAt` all walk `SplitTree.iterator()`, which iterates the
`nodes` ARRAY in storage order — not the tree structurally. `+list --json`
walks it structurally (`buildNode`: left, then right), and for a
`+split --direction=down` the two disagree: `+list` reports
`[terminal, viewer]` while the carousel strip and the hero index order them
`[viewer, terminal]`.

Evidence, from the T397 acceptance run: with a terminal focused and hero mode
on, the debug log reported `heroSelect req=2 clamped=1 cur=1 n=2` — the
FOCUSED TERMINAL was leaf index 1 — while `+list --json` put the terminal at
index 0. `test/win32/hero-viewer-tile.ps1` is written selection-relative
specifically so it does not depend on which order wins; that comment in
`Get-TileRects` is the pointer back here.

## Details

Consequences worth weighing:

- **Strip order vs screen order.** Mac's `HeroModeView` builds its strip from
  the tree's leaves, so its strip reads top-to-bottom the way the splits do.
  Node-array order is an implementation detail of how splits were allocated,
  which is why a `down` split can land its new leaf first.
- **Arrow navigation follows the strip**, so `ctrl+alt+down` can move the
  selection UP the visible strip.
- **`+list` and the GUI disagree** about which leaf is which index. Nothing
  in the CLI exposes a leaf INDEX today, so this is not a wire-format break —
  but it is two orders for one tree.

Decide whether the fix is (a) an ordered iterator on `SplitTree` used by the
hero paths (and anything else that means "leaf order"), or (b) making the
node array's order structural on insert. (a) is local; (b) is the one that
makes every future caller correct by default.
