# T263 - Send-TestMouse cannot click caption-band chrome: it posts client mouse messages, not the NC pair

## In plain terms

Our automated tests drive the app by pretending to be a mouse. The pretend
mouse could not press anything in the title bar — the minimize, maximize,
close and "..." buttons — because it always spoke the language Windows uses
for clicks in the main body of a window, and the title bar listens for a
different one. Nothing happened when those tests clicked, which looks exactly
like a broken button: one round of work lost seventeen test results to it while
the buttons were perfectly fine. Now the pretend mouse asks the window which
language a real click at that spot would use, and speaks it. Nobody sees this
in the product; what changes is that a title-bar button which really does break
will now be caught by a test instead of by a user.

## Goals

- [x] The harness routes a click by the window's own hit test, once, for every
      script — client messages where the point is client, the non-client pair
      where it is not.
- [x] An escape hatch (`-Client`) for a test whose subject IS the client path.
- [x] The two scripts that hand-rolled the workaround collapse back to ordinary
      clicks.
- [x] A negative control: an empty title-bar click presses nothing.
- [x] No mouse-driven acceptance script regresses.

## Summary

Found while doing T260, and it will bite T205 much harder than it bit T260.

`Send-TestMouse` (`test/win32/lib/TestDesktop.ps1`, `MouseEvent`) posts
`WM_LBUTTONDOWN`/`WM_LBUTTONUP` to a window at CLIENT coordinates. Since T254
the caption band IS client area, but the window claims it back through
`WM_NCHITTEST` (`HTSYSMENU`/`HTMINBUTTON`/`HTMAXBUTTON`/`HTCLOSE`/`HTCAPTION`),
so a REAL click there is delivered by Windows as `WM_NCLBUTTONDOWN` — a message
`Send-TestMouse` never sends. The app's caption handlers (`handleNcLButtonDown`
/ `handleNcLButtonUp`) therefore never run, and the click silently does
nothing.

## Evidence (VERIFIED on the box, 2026-07-31)

T260 pointed `menu-bar.ps1`'s `Open-Menu` at the caption's "…" via
`Send-TestMouse`. Every menu-open assertion failed while F10 and the lone-Alt
route still passed and the pixel probe found the glyph painted where the
metrics said it was:

```
FAIL  A: clicking the caption menu button opens the menu
FAIL  B: menu opens for the tree walk        (x14 more)
PASS  A: the caption menu button paints a glyph (27 ink pixels)
PASS  G: F10 opens the menu
17 FAILED / 37 passed
```

The workaround now in `menu-bar.ps1`'s `Click-MenuHost`: ask the app
`WM_NCHITTEST` at the button's screen point, then post `WM_NCLBUTTONDOWN` with
the code it answered — the same idiom `caption-bar.ps1` already uses. That
keeps the hit test REAL (the app decides what is under the point) but
synthesizes the delivery, which is T240's "an acceptance script that
synthesizes the trigger cannot validate the trigger" in a milder form.

## Why it matters more for T205

T205 moves the tab run INTO the caption band. Every strip click in every
acceptance script — `tab-strip.ps1`'s `Strip-Click`, `menu-bar.ps1`'s
`Click-Strip`, `tab-color.ps1`, `tab-strip-autohide.ps1` — is a
`Send-TestMouse` at a client point that will, after T205, be inside a band the
window hit-tests as non-client. Unless the harness routes those the way Windows
does, T205 lands with a set of scripts that click nothing and pass nothing.

## The fix

Teach the harness the routing Windows does, once, in `MouseEvent`:

- Send `WM_NCHITTEST` at the target point first. If the answer is anything
  other than `HTCLIENT`, deliver the `WM_NC*` form (`WM_NCMOUSEMOVE`,
  `WM_NCLBUTTONDOWN`/`UP`, `WM_NCRBUTTONDOWN`/`UP`) with the hit code in
  wparam and the SCREEN point in lparam; otherwise deliver today's client
  messages. That is exactly what `DefWindowProc`'s input path does, so a script
  stops having to know which band it is aiming at.
- Keep an explicit escape hatch (`-Client`) for a test that deliberately wants
  the client message regardless of the hit test.
- Then `menu-bar.ps1`'s `Click-MenuHost` collapses back to one
  `Send-TestMouse` call, and `caption-bar.ps1`'s `ClickCaption` becomes a real
  click rather than a synthesized pair.

## What it cost the scripts

Two probes in `tab-strip.ps1` aimed at the window's LAST pixel column to prove
the strip's hit box stops short of the border. In the merged row that column is
the caption's close button, so a routed click there closes the window — which
is correct, and is what a real user's click does. Both now pass `-Client`
(their subject is what the STRIP does with that column, i.e. the message its
own handler reads), and the first gained a `Get-TestMouseRoute` assertion that
the column routes non-client at all — a stronger statement about the inset than
"clicking it did nothing", read from the app rather than from silence.
