# T405 - session-persistence is documented as off|on but parseBool only accepts true/false

## In plain terms

The docs say you can write `session-persistence = off`, but the setting parser
only understood `true`/`false` — so the documented spelling was silently
ignored and persistence stayed on. This exact defect was already fixed under
T137 (2026-08-04, commit 8f7af4466): `off`/`on` and `yes`/`no` now work
everywhere a yes/no setting is accepted, and a genuinely bad value raises the
Configuration Errors dialog instead of being swallowed. Nothing is left to do.

- [x] unit test pins the accepted spellings — `parseBool: the exact accepted set` in `src/cli/args.zig`

## Summary

`session-persistence` is documented as taking `off|on` — in CLAUDE.md ("Session
Persistence": *"`session-persistence = off|on` (macOS + Windows, default
`on`)"*) and in the option's own doc comment — but the field is a plain
`bool` (`src/config/Config.zig`), and `cli.args.parseBool` accepts only
`1/t/T/true` and `0/f/F/false`. `off` and `on` are `error.InvalidValue`.

So the documented spelling does not work, in a config file or on the CLI, and
the failure is quiet: the value is rejected into `_diagnostics` and the option
keeps its default. A user who writes the documented `session-persistence = off`
gets session persistence ON.

## Evidence (2026-08-03, found while working T104)

`--session-persistence=off` on the GUI launch path left the local agent in
charge — the pane was still agent-backed. The same run with
`--session-persistence=false` took the exec path, which is how T104's root cause
was finally isolated. Cost: one wrong conclusion ("the exec path drops the
command too") that had to be re-tested.

`src/cli/args.zig:654` is the whole story:

```zig
pub fn parseBool(v: []const u8) !bool {
    const t = &[_][]const u8{ "1", "t", "T", "true" };
    const f = &[_][]const u8{ "0", "f", "F", "false" };
    ...
```

## Fix

Pick ONE and make the docs and the parser agree:

- Teach `parseBool` `on`/`off` (and `yes`/`no`?) — a change to EVERY bool option
  in the config, so it needs a deliberate decision, not a drive-by. Upstream
  Ghostty's parser is the same one, so this is a divergence to weigh.
- Or correct the docs to `true|false` in CLAUDE.md and the `session-persistence`
  doc comment, and leave the parser alone.

The second is the smaller change and keeps us on upstream's parser; the first is
friendlier to the documented spelling users have already read. Note the *silent*
half is worth fixing either way: a rejected value on the CLI should be visible
(it lands in `_diagnostics` — check whether the win32 startup path surfaces
those the way `config-errors.ps1` expects).

## Validation

- If the docs move instead: grep CLAUDE.md, `go.md`, and
  `docs/design/session-persistence.md` for `off|on` and fix every copy.
