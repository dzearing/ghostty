# T1168 - Soak runs leave agent autostart entries behind in the user's registry

## In plain terms

Running the test suite is quietly adding startup programs to this machine. Four
of them were sitting in the user's "run these at sign-in" list on 2026-08-23,
each one pointing at a throwaway test sandbox from a soak run earlier that day,
and each one will launch a background agent process at the next sign-in for a
sandbox that no longer means anything. Nothing about a test run should still be
running tomorrow morning.

## Summary

Found while measuring T1142. `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`
held, alongside the user's real `GhozttyAgent` entry:

```
GhozttyAgent-soak-47404  "D:\git\ghoztty\zig-out-release\bin\ghoztty-agent.exe"
                         "--listen-pipe=\\.\pipe\ghoztty-agent-soak-47404-David"
                         "--port-file=...\Temp\ghoztty-soak\20260823-093902\sandbox\..."
GhozttyAgent-soak-48720  (same shape, 20260823-094339)
GhozttyAgent-soak-43452  (same shape, 20260823-094639)
GhozttyAgent-soak-47856  (same shape, 20260823-100937)
```

Four in one morning, from four soak runs. The mechanism is T167's per-lineage
autostart: `GHOZTTY_AGENT_INSTANCE=<tag>` correctly gives the sandbox agent its
own Run VALUE name instead of clobbering the user's — which is what stops a test
from breaking their terminal — but nothing removes that value when the run ends,
so each isolated run leaves a permanent one behind. Confirmed the same way from
this seat: a T1142 measurement under `GHOZTTY_AGENT_INSTANCE=ingest48876` left
`GhozttyAgent-ingest48876` behind, and it was removed by hand.

This is squarely the rule in `docs/claude/testing.md` — *tests must never touch
live user state* — and the leak is invisible to every existing sweep, because
`HarnessLeak.ps1` and the clean-slate audits look at processes, windows, pipes
and files, not at the registry.

## Where

- `src/remote/agent/` — whichever autostart install path writes the Run value
  (`enroll.zig` / `keepalive.zig` / the `--listen-pipe` bring-up); the lineage
  suffix is T167's.
- `test\win32\lib\CleanSlate.ps1` — where a per-run teardown would belong.
- `test\win32\lib\HarnessLeak.ps1` — the sweep that should be able to see it.
- `test\win32\soak.ps1`, `test\win32\holder-soak.ps1` — the observed producers.

## Notes

The four existing entries were left in place rather than deleted from under the
user; whoever takes this should confirm with them before removing what is there,
and then make the leak impossible rather than tidying it once.

## What was done

The Run-key WRITE was never the defect: T167's per-lineage value name is what
stops a sandbox clobbering the user's entry, and it does that correctly. What
was missing is that nothing ever removed the value afterwards, so the isolation
that made a run safe also made it permanent. Answered at both ends, in the
harness libraries rather than in the agent:

- `test\win32\lib\HarnessLeak.ps1` grows the REGISTRY half of the leak library
  it already was for processes — `Test-AgentRunValueLeaked`,
  `Get-LeakedAgentRunValue`, `Remove-LeakedAgentRunValue`,
  `Register-AgentRunKeyTeardown`. A lineage suffix can only come from
  `GHOZTTY_AGENT_INSTANCE`, which is unset in every production run, so a
  suffixed name is a harness artifact by construction — and the two unsuffixed
  names (`GhozttyAgent`, `GhozttyAgent-debug`) are the real installs, which the
  remover THROWS on rather than declining quietly.
- `test\win32\lib\Isolation.ps1` arms the exit teardown in the same breath as it
  mints the instance — the one place the suffix exists, rather than the bottom
  of each script that uses one, which is exactly what does not run when a run
  dies half way through.
- `test\win32\lib\CleanSlate.ps1`'s `Reset-GhozttyTestState` sweeps whatever a
  KILLED run left, and reports the count. A crash never reaches an exit handler,
  so the next run's clean slate is the backstop.

The teardown block bakes its instance in as a literal and goes through
`[Microsoft.Win32.Registry]` rather than `Remove-ItemProperty`, for the two
reasons `Get-HarnessTeardownBlock` documents: an exit-time action cannot resolve
the registering scope's variables, and module auto-loading does not work at exit.

## Validation criteria

- [x] a soak/isolated run that finishes normally leaves NO
      `GhozttyAgent-<instance>` value behind in `HKCU\...\Run` — R8 in
      `test\win32\harness-process-leak.ps1` (a child that arms and then THROWS),
      plus an end-to-end run through `Set-GhozttyTestIsolation -ReleaseSandbox`
      itself: instance `t1168e2e-25464`, planted, gone at exit
- [x] a run that is KILLED mid-way is also swept — R10 runs the clean-slate
      sweep against the leak R9 just made; `cleanslate-audit.ps1` C7/C8 hold
      `Reset-GhozttyTestState` to calling it and reporting the count
- [x] the leak sweep can SEE the condition — R4 plants a fake value and requires
      `Get-LeakedAgentRunValue` to report it; R9 is the teeth (without the
      arming the same run leaks one); R12 is the standing arm at zero
- [x] the user's own `GhozttyAgent` entry is never touched — R1/R2 refuse to
      classify either real install as a leak, R7 proves the remover THROWS on
      one, and R11 compares a before/after read of the value in the same run
- [x] the four entries already on this box are resolved — removed 2026-08-31
      after backing up their exact values (see below); the user's `GhozttyAgent`
      was read back unchanged immediately afterwards

## The four entries on this box

Removed rather than left, on the evidence that they were pure litter of ours:
each named a `%TEMP%\ghoztty-soak\2026082x-xxxxxx\sandbox` that had meant
nothing since the morning it was made, and the release agent binary they point
at still exists — so all four would have started an orphan agent at the next
sign-in. Their exact values were written to `%TEMP%\t1168-runkey-backup.json`
before the delete, and the removal ran through the new
`Remove-LeakedAgentRunValue` (4 removed, 0 remaining, user entry byte-identical
after).
