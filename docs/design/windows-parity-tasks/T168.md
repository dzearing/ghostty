# T168 - Converge go-loop-lock.ps1 onto the shared loop-session.ps1 identity helpers

## In plain terms

Two of the scripts that keep the automated work loop running each had their own
copy of the same piece of logic: "which Claude session owns this loop, and is it
still running?" One uses the answer to decide whether a session may start
working; the other uses it to decide whether to relaunch Claude after an
upgrade. They agreed, but only by accident of nobody having touched either -
fix a mistake in one copy and the other keeps making the opposite call, which is
how two sessions once ended up building the same task at the same time. After
this there is one copy, so they cannot disagree.

## Goals

- [x] `go-loop-lock.ps1` uses the shared helpers instead of private copies
- [x] The loop lock behaves identically - no change to who may work
- [x] A test that goes red if a private copy is ever reintroduced

- [x] Standing floor: all three zig lanes green, P1-P3 ALL PASS

## Summary

Two scripts now answer "which claude owns this loop session, and is it still
the same process?" with their own copies of the same logic:

- `scripts/go-loop-lock.ps1` - `Resolve-ClaudePid`, `Get-ProcStamp`,
  `Test-OwnerAlive` (T139).
- `scripts/loop-session.ps1` - `Resolve-LoopClaudePid`, `Get-LoopProcStamp`,
  `Test-LoopProcAlive` (T138), dot-sourced by
  `scripts/upgrade-ghoztty-windows.ps1`.

They agree today (explicit pid -> `$env:CLAUDE_PID` -> ancestry walk; pid +
process start time as the identity, +/-2s tolerance). The risk is drift: these
two decide *the same fact* for the same loop - the lock decides who may work,
the upgrade decides whether to relaunch - and a fix applied to one copy would
leave the other making the opposite call. That is the exact shape of the bug
T138 fixed.

T138 deliberately did NOT fold them together: the loop lock is load-bearing for
the running loop, and re-validating it (`go-loop-guard.ps1`, 78 assertions x3,
sections I-L against a live GUI) had no business riding along with an unrelated
fix.

## Details

Work: delete the private copies in `go-loop-lock.ps1`, dot-source
`loop-session.ps1`, and pass the script's `-ClaudePid` parameter through
`Resolve-LoopClaudePid -Explicit` (the current function closes over script
scope, which a dot-sourced version cannot).

Validation: `go-loop-guard.ps1` ALL PASS x3 (it covers dead-owner takeover,
stale heartbeat, and the pane-keyed ownership that the pid resolver feeds), plus
`upgrade-no-fork.ps1` section A, which asserts the helpers directly.

## What landed

`go-loop-lock.ps1` dot-sources `loop-session.ps1` and its three private
functions are gone:

- `Resolve-ClaudePid` -> `Resolve-LoopClaudePid -Explicit $ClaudePid` (the
  private one closed over the script's `-ClaudePid` parameter, which a
  dot-sourced function cannot see, so the parameter is passed explicitly).
- `Get-ProcStamp` -> `Get-LoopProcStamp`. The shapes differ - a hashtable
  `@{Name; Start}` vs a `pscustomobject` with `Pid` as well - but every use site
  reads `.Name`/`.Start`, so the extra field is additive.
- `Test-OwnerAlive` keeps its name and its signature (it takes a LOCK, not a
  stamp) and is now four lines: rehydrate `claude_pid`/`claude_name`/
  `claude_start` into a stamp and delegate to `Test-LoopProcAlive`. The rule -
  pid alive AND name matches AND start time within 2s - lives in one place.

Two behavior differences, both in the shared version's favour and both
deliberate:

1. The env-var path now accepts a process named `claude*` rather than exactly
   `claude`, which is what the ancestry path in BOTH copies already did. The
   private copy could reject via `$env:CLAUDE_PID` a process the very next
   branch would have accepted.
2. A non-numeric `$env:CLAUDE_PID` no longer takes the script down. The private
   copy cast it with `[int]` unguarded, a TERMINATING error under the script's
   `$ErrorActionPreference = 'Stop'`; the shared resolver `TryParse`s and falls
   through to the ancestry walk. Teeth-checked on box: the old expression exits
   1 with `Cannot convert value "not-a-pid"` and never reaches the walk.

Anti-drift is now a test, not a comment: `go-loop-guard.ps1` section U asserts
the lock dot-sources the shared file and defines neither private function, so
reintroducing a copy goes red.
