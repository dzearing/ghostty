# T168 - Converge go-loop-lock.ps1 onto the shared loop-session.ps1 identity helpers

## Summary

Two scripts now answer "which claude owns this loop session, and is it still
the same process?" with their own copies of the same logic:

- `scripts/go-loop-lock.ps1` - `Resolve-ClaudePid`, `Get-ProcStamp`,
  `Test-OwnerAlive` (T139).
- `scripts/loop-session.ps1` - `Resolve-LoopClaudePid`, `Get-LoopProcStamp`,
  `Test-LoopProcAlive` (T138), dot-sourced by
  `scripts/upgrade-ghoztty-windows.ps1`.

They agree today (explicit pid -> `$env:CLAUDE_PID` -> ancestry walk; pid +
process start time as the identity, +/-2s tolerance). The risk is drift: these
two decide *the same fact* for the same loop - the lock decides who may work,
the upgrade decides whether to relaunch - and a fix applied to one copy would
leave the other making the opposite call. That is the exact shape of the bug
T138 fixed.

T138 deliberately did NOT fold them together: the loop lock is load-bearing for
the running loop, and re-validating it (`go-loop-guard.ps1`, 78 assertions x3,
sections I-L against a live GUI) had no business riding along with an unrelated
fix.

## Details

Work: delete the private copies in `go-loop-lock.ps1`, dot-source
`loop-session.ps1`, and pass the script's `-ClaudePid` parameter through
`Resolve-LoopClaudePid -Explicit` (the current function closes over script
scope, which a dot-sourced version cannot).

Validation: `go-loop-guard.ps1` ALL PASS x3 (it covers dead-owner takeover,
stale heartbeat, and the pane-keyed ownership that the pid resolver feeds), plus
`upgrade-no-fork.ps1` section A, which asserts the helpers directly.
