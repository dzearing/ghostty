# T738 - connection.zig 'inbound DATA routing' flakes on a 100k-spin timeout

## In plain terms

One test in the standing test suite fails at random. It is not finding a bug —
it gives up waiting after a fixed number of tries, and on a busy machine that
number runs out before the answer arrives. A test that cries wolf is worse than
no test: the next person to see it red spends their turn hunting a defect that
is not there.

## Summary

Seen on 2026-08-11 during T249's floor run:

```
error: 'remote.connection.test.inbound DATA routing: bytes land in the right
channel; unknown is dropped' failed: [tripwire] (warn): untripped point=read
src/remote/connection.zig:3772:34: in drainChannel
```

Line 3772 is `if (spins > 100_000) return error.Timeout;` in `drainChannel`,
which busy-spins on `ch.pop()` with a `std.Thread.yield()` between tries while a
reader thread fills the ring. **A spin COUNT is not a timeout** — it measures
how many times this thread got scheduled, not how long it waited, so what it
actually bounds varies with core count, box load and the scheduler's mood. On a
loaded box the reader thread can lose 100 000 yields' worth of races without
anything being wrong.

Re-running `scripts\floor-lane.ps1 -Lane win32` on the identical tree and
build passed (339 s, ALL LANES PASS), which is what makes this a flake rather
than a regression: same inputs, different verdict.

The fix is to bound the wait by the CLOCK — `std.time.Instant` / `Timer`, a
generous wall-clock budget (a second or two is enormous for a loopback ring) —
and, while in there, to sweep for the same shape elsewhere: any `spins >`,
`attempts >` or `for (0..N)` guarding a cross-thread wait is the same bug
waiting for a busy afternoon.

## Where

- `src/remote/connection.zig` — `drainChannel` (the spin guard) and the
  `inbound DATA routing` test that calls it.
- Sweep `src/remote/` and `src/apprt/win32/` for sibling spin-count waits.

## Validation criteria

- [ ] `drainChannel` bounds its wait on wall-clock time, not on a spin count,
      and says so in its error.
- [ ] The sweep is done and every cross-thread wait found is either converted
      or explicitly justified in a comment.
- [ ] `scripts\floor-lane.ps1 -Lane win32 -Repeat 3` PASS — the repeat is the
      point, since one green run is what a flake gives you anyway.
