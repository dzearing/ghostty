# T814 - unsubscribeMetrics/unsubscribeSessionCpu returning does not actually prove no handler is in flight

## Summary

Both unsubscribe paths clear the handler slot under write_mutex, and every caller in the app treats the return as the guarantee that no further callback can fire against its context (ActivityMonitor.dropProbeLink says so in as many words; SessionCpuProbe.stop and the Mac SessionCPUProbe rely on the same claim). The control dispatch does not support it: it takes write_mutex, READS the handler and the ctx, releases the lock, and only then calls - so a handler already past the unlock runs while unsubscribe returns and its ctx is freed. Never observed, and the window is a few instructions wide, but it is a use-after-free by construction and the comments promise it cannot happen. Shape of a fix: an in-flight counter (or a per-handler rwlock) that unsubscribe drains before returning, in connection.zig so every subscription kind gets it at once.
