# T663 - The upgrade resume prompt reaches the pane with its '>' characters stripped - three consecutive RESUME-REUSE FAILs

## Summary

Carved out of **T525**'s Notes, which recorded it and said it "needs its own
look - file separately if not absorbed here". It was not absorbed: T525 built
the morning trigger and the app-only delivery, and left this untouched.

Evidence on the box: `%TEMP%\ghoztty-upgrade.log` shows three consecutive
deliveries ending in `RESUME-REUSE FAIL` — the resume prompt is typed into the
surviving pane, the arrival gate reads the pane back, and the text does not
match because its `>` characters have been stripped somewhere between the
prompt file and the composer. The gate then correctly refuses to submit a
mangled prompt (that refusal is T210 working as designed) and hands off to the
watchdog, so each of those deliveries cost the loop a stall it had to be
rescued from.

This matters more now, not less: T525 makes an unattended delivery a DAILY
event, and the resume is the step that puts the loop back to work afterwards.

## In plain terms

After the terminal updates itself, it has to type a message back into the work
session to get it going again. Some characters go missing on the way, the
safety check spots that the message is wrong, and it correctly refuses to send
it — so the work loop stops until a watchdog notices. It has happened three
deliveries running.

## Where to look

- `Send-LoopPromptVerified` / `New-LoopSendKeysText` / `Get-LoopPromptNeedle` in
  `scripts/loop-session.ps1` — the type-verify-submit cycle and the
  normalization the comparison uses.
- The `--keys-file=` path in `src/cli/send_keys.zig` (byte-exact by contract,
  T210) versus the argv path, and which one the installed exe actually took —
  the log says, via the "does not support --keys-file" warning.
- Whether the `>` loss is on the WRITE (the prompt file / the send) or on the
  READ (`+read` of a composer that renders `>` as part of its own chrome), which
  are different bugs with the same symptom. `Get-LoopPromptNeedle` already
  exists because the composer injects characters of its own.

## Not the same as T562

T562 is "the text arrives intact and Enter never submits it". This is "the text
does not arrive intact, so it is correctly never submitted". Both end the loop
at a stalled composer; the causes are unrelated.

## Validation criteria

- [ ] A prompt containing `>` (the `/reset-context …` shape the loop actually
      uses) round-trips through send + `+read` byte-for-byte, proven by a test
      rather than by a delivery.
- [ ] Whichever side loses the characters is named with evidence, not guessed.
- [ ] A delivery on this box logs `RESUME-REUSE OK` rather than FAIL.
