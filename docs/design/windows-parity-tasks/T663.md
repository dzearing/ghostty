# T663 - The upgrade resume prompt reaches the pane with its '>' characters stripped - three consecutive RESUME-REUSE FAILs

## Summary

Carved out of **T525**'s Notes, which recorded it and said it "needs its own
look - file separately if not absorbed here". It was not absorbed: T525 built
the morning trigger and the app-only delivery, and left this untouched.

Evidence on the box: `%TEMP%\ghoztty-upgrade.log` shows three consecutive
deliveries ending in `RESUME-REUSE FAIL` — the resume prompt is typed into the
surviving pane, the arrival gate reads the pane back, and the text does not
match because its `>` characters have been stripped somewhere between the
prompt file and the composer. The gate then correctly refuses to submit a
mangled prompt (that refusal is T210 working as designed) and hands off to the
watchdog, so each of those deliveries cost the loop a stall it had to be
rescued from.

This matters more now, not less: T525 makes an unattended delivery a DAILY
event, and the resume is the step that puts the loop back to work afterwards.

## In plain terms

After the terminal updates itself, it has to type a message back into the work
session to get it going again. Some characters go missing on the way, the
safety check spots that the message is wrong, and it correctly refuses to send
it — so the work loop stops until a watchdog notices. It has happened three
deliveries running.

## Goals

- [x] Name the side that loses the characters, from a measurement rather than a
      hypothesis
- [x] Make the resume's read of the pane actually work
- [x] Leave an oracle behind so the same silence cannot come back unnoticed
- [x] Sweep the rest of the loop for the same defect
- [ ] Watch the next morning refresh log `RESUME-REUSE OK`

## Where to look

- `Send-LoopPromptVerified` / `New-LoopSendKeysText` / `Get-LoopPromptNeedle` in
  `scripts/loop-session.ps1` — the type-verify-submit cycle and the
  normalization the comparison uses.
- The `--keys-file=` path in `src/cli/send_keys.zig` (byte-exact by contract,
  T210) versus the argv path, and which one the installed exe actually took —
  the log says, via the "does not support --keys-file" warning.
- Whether the `>` loss is on the WRITE (the prompt file / the send) or on the
  READ (`+read` of a composer that renders `>` as part of its own chrome), which
  are different bugs with the same symptom. `Get-LoopPromptNeedle` already
  exists because the composer injects characters of its own.

## Not the same as T562

T562 is "the text arrives intact and Enter never submits it". This is "the text
does not arrive intact, so it is correctly never submitted". Both end the loop
at a stalled composer; the causes are unrelated.

## What it actually was

Not a stripping bug on either side. **The gate was reading nothing at all.**

`ghoztty.exe` is a GUI-subsystem binary, and PowerShell decides from that field
whether to wait for a native command and whether its stdout can be captured. The
readiness gate, the arrival gate and both `+sessions` probes all read through
`$oldExe` — the installed release `ghoztty.exe` — with

```powershell
(& $oldExe +read "--name=$pane" --lines=40 2>$null) | Out-String
```

which returns **zero bytes with an empty `$LASTEXITCODE`**, silently, for every
call. Measured 2026-08-10 against a live pane: 0 characters through
`ghoztty.exe`, 2856 through its `ghoztty.com` sibling, same pane, same second.
So the prompt almost certainly arrived intact every time; the gate simply could
not see it, refused to submit on that basis (T210 working exactly as designed),
and handed off to the watchdog.

That also explains the July half of the log — `RESUME-REUSE SENT: … but was not
seen in the pane tail (the TUI may have consumed it)` — and the standing
`pre-kill agent sessions: 0` on a box with live sessions, which made the
sessions-survive assert a no-op.

The `>` hypothesis is refuted twice: `Get-LoopPromptNeedle` has always stripped
`>` and `|` from **both** sides before comparing, and the last three failures
carried `/reset-context read go.md and go`, which has no `>` in it.

Why `+send-keys` next door worked and the readers did not: `2>&1` forces
PowerShell to build a pipeline and wait, `2>$null` does not. The send calls used
the former, every reader used the latter.

## Fix

`Resolve-GhozttyCliExe` in `scripts/loop-session.ps1` — one place decides which
binary a CLI *answer* is read from. It prefers the sibling `ghoztty.com` (T245's
console-subsystem twin, a required sibling of `ghoztty.exe`) and falls back to
the `.exe` for a pre-T245 install, where the caller's own `2>&1` is all there is.

Wired into `upgrade-ghoztty-windows.ps1` as `$cliExe`, resolved before the swap
and **re-resolved after it** (the twin may only exist in the new build); every
verb whose answer the script reads now goes through it, while `$oldExe` stays
the thing that is copied, verified and launched. Swept the rest of the loop:
`go-loop-pane-probe.ps1` had the identical defect in `Get-PaneShellPid`
(`+list --json 2>$null` captured nothing, so the watchdog's pane probe answered
0 for every pane), and the `Ghoz` / `Invoke-Ghoztty` wrappers in
`go-loop-exec.ps1` and `go-loop-watchdog.ps1` resolve too.

- [x] The pre-fix behaviour is pinned as an oracle rather than merely fixed. —
      G5/G6 above, plus E10 (no reader left on `$oldExe`), teeth-checked by

- [ ] A delivery on this box logs `RESUME-REUSE OK` rather than FAIL. — carried
      by the next morning refresh; this is the one criterion a test cannot
      stand in for, because the failure only exists against a GUI-subsystem
      release build and an acceptance script must never drive one.

## Note on why the tests cannot cover the last line

Debug builds link the **console** subsystem (so `std.log` reaches the shell),
which is why section F passes identically with and without the fix. The defect
only exists against the GUI-subsystem release — exactly what the upgrade script
drives — and the acceptance rules forbid a script from running an installed
release or a release `zig-out` (T350 endpoint isolation). Section G is the
substitute: it measures the property on the release **staging** binary with a
verb that opens no window and dials no pipe.
