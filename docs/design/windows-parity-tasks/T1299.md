# T1299 - Nobody has ever installed the MSI and clicked through it on this box

## In plain terms

Everything the installer does is checked by reading the recipe that builds it,
never by running it. So the way we find out that installing is broken is that
you install it and it breaks - which is how the last three installer bugs were
found. There should be a test that actually installs a throwaway copy, runs
through the cases a person hits, and says so when one of them goes wrong.

## Why it is like this today

Two constraints, both real:

- Building the MSI needs `wixl` (GNOME msitools), which on this box lives only
  inside Docker - and starting Docker is the user's call, not the loop's. So
  `test\win32\release-artifacts.ps1`'s packaging half is permanently advisory
  here (`guard-due.ps1` reports it as `GUARD DUE (advisory)`).
- Installing the real product would replace the user's Ghoztty, which is this
  repo's first non-negotiable.

`scripts\msi-test-identity.ps1` and `build-msi.sh --test-identity` already
solve the second constraint: they mint a THROWAWAY product with its own name,
ProductCode, UpgradeCode, install dir and component GUIDs, so an install and an
uninstall cannot touch anything real. What is missing is a package to feed it
without Docker.

## What to do

- **Get a package without wixl on this box.** `release-windows.yml` already
  builds one on every tag and `fork-ci` compiles one on every push; the
  cheapest route is probably to have CI publish the throwaway-identity MSI as a
  build artifact and have the harness download the one built from the current
  commit (skipping cleanly, the way the advisory guards do, when there is no
  network or no matching run).
- **Then drive the cases a person actually hits**, each with an oracle that is
  the outcome and not an exit code:
  - fresh install → files on disk, PATH entry, Start Menu shortcut, a terminal
    opens (T1176);
  - upgrade over an older version → the exe survives (T23), sessions survive
    (T1207), no reboot is demanded (T1204);
  - **re-run at the same version → the Repair / Cancel dialog appears and
    Cancel leaves the install untouched (T1291)** - the case this task was
    filed from, whose MSI half is currently asserted only at its source and at
    the build-time read-back;
  - older package over a newer install → the plain explanation, not 1638;
  - uninstall → nothing left behind.

## Validation criteria

- [ ] A harness in `test/win32/` installs a throwaway-identity package on this
      box, with no Docker, and skips cleanly (never fails) when it cannot get
      one.
- [ ] It covers fresh install, upgrade, same-version maintenance, older-over-
      newer and uninstall, each asserting the OUTCOME rather than msiexec's
      exit code.
- [ ] It is impossible for it to touch the real product: the assertions name
      the throwaway ProductCode and install dir, and a `-TeethCheck` shows the
      guard that enforces that going red.
- [ ] `guard-due.ps1` carries a row for it, so an edit to `build-msi.sh` asks
      it whether the package still installs.
