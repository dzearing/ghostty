# T432 - Mac: the session-interrupted notice still replaces a restored pane's banner (set pane_banner_restored from the Swift restore)

## In plain terms

On Mac, when the background process that keeps your terminals alive restarts,
every reopened pane loses the sticky banner you put on it and shows the same
"session interrupted" message instead. Windows stopped doing that (T422); Mac
still does. Anyone who uses banners to track what a pane is for loses that
information on every such restart.

## Goals

- [ ] A restored Mac pane that had a banner keeps it across an agent restart.
- [ ] A restored Mac pane that had NO banner still gets the notice banner.
- [ ] A Mac banner change is enough on its own to get into the manifest.

## Summary

T422 fixed this on Windows and put the decision in the SHARED core, so the Mac
half is one signal away. `termio.Remote.Config.pane_banner_restored`
(`src/termio/Remote.zig`) gates the session-interrupted notice's OSC 7778
carrier: true ⇒ the notice keeps only its in-stream scrollback copy (T423) and
leaves the banner slot to the pane's own banner.

`src/Surface.zig`'s `Options.Remote.pane_banner_restored` carries it down.
The win32 apprt sets it in `App.restoreAttachOverride` from the manifest leaf's
`banner`. **The Mac path never sets it**, so it defaults false and
`SessionLayoutRestore.swift:442`'s `view.paneBanner = banner` is overwritten by
the notice moments later — the exact loss the user reported on Windows
(*"When windows were reopened, all the previous banners were replaced with [the
notice]. I expected banners to be rehydrated"*).

## What to do

1. Thread the flag: `Ghostty.SurfaceView` baseConfig → `apprt/embedded.zig`
   (`ghostty_surface_config_s` already carries `restore_snapshot`/
   `restore_snapshot_len`; add the bool the same additive way) → the
   `Options.Remote` literal at `embedded.zig:~1524`.
2. Set it from the restore where `leaf.banner` is applied
   (`SessionLayoutRestore.swift:442`) — non-empty banner ⇒ true.
3. Check the sibling that T422 also had to fix on Windows: a banner change alone
   must mark the session-layout manifest dirty. On win32 `Surface.setPaneBanner`
   now calls `App.markLayoutDirty`, because nothing in a banner change touches
   the topology and the manifest otherwise only learns about it if some
   unrelated mutation happens to write afterwards. Confirm the Mac manifest sync
   observes `paneBanner`; if it does not, a banner set hours before a crash is
   not on disk.

## Validation

An agent-restart relaunch (the `notify` path) on a Mac where a pane that had a
banner before the restart shows THAT banner after it, and a pane that had none
shows the notice banner. The win32 analog is arm E of
`test\win32\session-relaunch-notify.ps1` (E1-E5), which scores the mixed case on
purpose: two panes with banners keep them, the third takes the notice, and all
three still carry the notice in their scrollback.
