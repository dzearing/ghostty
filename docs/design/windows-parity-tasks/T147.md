# T147 — Agent upgrade delivery is destructive on Windows

## Summary

**Agent upgrade delivery is destructive on Windows — 2 Mac commits, ZERO references.** `c6ad0fc07` (non-destructive agent upgrade delivery) and `ae2be57cb` (eliminate tombstone reload + blank re-attach on upgrade). This is the mechanism CLAUDE.md's "Agent contract & upgrade compatibility" section mandates — *"prefer a lazy, non-destructive agent upgrade… carry sessions across… drain/snapshot and resume so no work is lost"* — and the win32 agent (T89h) has none of it, so every agent upgrade is the very silent session reset that contract forbids. Port the drain/snapshot/resume handoff and the upgrade-path re-attach fix, and pair with the T125 update dialog so the mandatory-confirmation fallback exists for the skew case

## Outcome (DONE 2026-07-30)

The filed premise was **half right, and the wrong half was the one it led
with**. Windows' agent upgrade was not destructive — it was *inert*.

**What the audit found before any code was written:**

- `ae2be57cb` needs NO port. Its FIX 2 (the continuous headless emulator +
  self-contained VT repaint on ATTACH, `grid_snapshot.zig`) is **shared Zig in
  the agent**, so the win32 agent has carried it since it first built; FIX 1 is
  `launchctl bootout` logic that has no Windows analog.
- The Windows delivery path was **already non-destructive** in the direction the
  row feared: `scripts/upgrade-ghoztty-windows.ps1` renames the running agent's
  exe aside and copies the new one in, deliberately never killing the agent
  (T89h). Nothing here silently reset sessions.
- The real gap was the OTHER half of `c6ad0fc07`, and it is the more damaging
  one: **nothing ever adopted the new binary.** The running agent keeps every
  PTY and serves forever, so an agent-side fix reached the user only after a
  reboot. A user who upgraded through several releases kept an agent from weeks
  ago — the Mac's exact 1.15.0 incident, one platform later.

**What landed:**

- `src/apprt/win32/agent_upgrade.zig` — the whole decision, pure and
  unit-tested: parse `ghoztty-agent --version`, order stamps by `YYYYMMDD`,
  `isStale` (null ⇒ pre-versioned ⇒ stale; newer ⇒ never downgrade), and
  `decide(running, bundled, live) → none | refresh_now | confirm_first`. Three
  rules it encodes, each destructive to get wrong: unknown never judges, newer
  is never downgraded, live is never silent.
- `LocalAgent`: `bundledVersion()` (probe `--version` once per run, cached
  including the failure), `runningVersion()` (the peer's HELLO stamp, already
  plumbed shared-side), `restartForUpgrade()` (retire the connection FIRST so
  sends fail fast, then TerminateProcess + a bounded wait so a respawn can't
  race the dying agent's pipe), and `sharedConnectionIfWarm()` — the upgrade
  check must never SPAWN an agent to ask whether the running one is old, since a
  fresh agent is by definition current.
- `App`: `refreshLocalAgentIfStale(reason)` at Mac's two safe moments — launch
  restore finished, and (posted, so the close settles first) the last persistent
  window closing. Idle ⇒ silent restart; live ⇒ the mandatory
  `ConfirmDialog` ("Restart the Ghoztty background terminal process?" /
  "Update Now" / "Later"), and a decline defers to the next idle moment rather
  than nagging.

**Three decisions that differ from a literal port, all measured or reasoned
rather than assumed:**

1. **Liveness is asked of the AGENT, not counted from this app's panes.** At app
   quit every window is destroyed while its sessions stay alive on purpose, so a
   pane count reads 0 at exactly the moment a restart destroys the most work.
   `liveAgentSessionCount()` asks the agent (bounded RPC) and counts
   `alive == true`; tombstones don't count, because a restart costs them
   nothing. Unknown liveness ⇒ do nothing at all: "we couldn't ask how much this
   would destroy" is never grounds for destroying it. Plus an explicit
   `quit_requested` guard.
2. **The idle arm re-dials through `recoverLocalAgentInPlace`, not a bare
   re-dial.** "No LIVE sessions" still permits agent-backed windows full of
   TOMBSTONES, and those panes must be re-ATTACHed (RELAUNCHed) onto the new
   agent instead of pointing at a retired connection. With no windows it
   degrades to exactly a re-dial.
3. **A restart cap (2/run).** If a restart doesn't cure staleness — an agent
   from another install holding the single-instance guard, say — retrying on
   every window close would kill an innocent agent over and over.

## Validation

`test/win32/agent-upgrade.ps1` **ALL PASS (38) ×3**, hermetic (per-run
`LOCALAPPDATA` + `GHOSTTY_LOCAL_AGENT_BIN`, only ever touching zig-out
processes). Measured by outcome — agent pids, dialogs on screen, panes that
still answer — never by log scraping:

- **A** premise: `--version` really prints a parseable stamp.
- **B** negative control: a CURRENT agent is never touched (no dialog, same pid,
  pane still responsive after a full check cycle).
- **C** stale + live ⇒ the mandatory dialog, and **the agent pid is unchanged
  while it is up** — consent before destruction, the contract assert. "Later"
  leaves pid and pane exactly as they were.
- **D** stale + "Update Now" ⇒ agent REPLACED (new pid, old gone), app is the
  **same** process (in place, not a relaunch), pane count preserved and the
  rebuilt pane responsive on the new agent.
- **E** the deferral promise kept: after declining, closing the last pane makes
  the agent idle and the refresh happens **silently** (new pid, no second
  dialog).
- **F** negative control: `session-persistence=false` never runs the check and
  never spawns an agent.

**Negative control, run for real:** with `refreshLocalAgentIfStale` stubbed to
return immediately, the script failed **exactly** the six T147 assertions
(C3, D3, D5, D6, E3, E6) and nothing else — B and F still passed, so they are
controls and not filler.

The staleness INPUT is faked with `GHOZTTY_AGENT_BUNDLED_VERSION`, a **debug-only**
hook (`build_config.is_debug`, the `GHOZTTY_AGENT_AUTOSTART=force` pattern): every
stamp in a real build comes from the same binary the agent runs, so there is no
way to fabricate an old agent from a new tree. It overrides the input only —
the decision and the restart it drives are the shipping ones. A stray env var
can never kill a user's agent.

Floor: both test lanes + `zig build test-agent` + P1–P3 green; regressions
`agent-recovery.ps1` (25) and `session-close.ps1` ALL PASS, since this shares
their teardown and rebuild paths.

**The harness lied first, again.** Six assertions failed against a build whose
correct `+list --json` output was sitting complete in the redirect file: a timed
`WaitForExit(ms)` leaves `$p.ExitCode` empty unless `.Handle` was cached
*before* the child exited. Fixed here, and filed as **T197** because the same
idiom is copied across the suite and some scripts only pass by timing luck.

Left open: **T125** (the "What's new" notes accessory on this same dialog, and
protocol-SKEW gating — this task detects a stale BUILD, not an incompatible
protocol) and **T196** (deliver this and T145 to all three install locations —
until then the mechanism exists only in `zig-out`, which is the T49 lesson
applied to the very feature that makes future agent fixes reach users).
