# T333 - A roster refetch resets the scroll under a parked session cursor

## Summary

`SessionRoster.adopt` ends with `self.scroll = 0` (`src/apprt/win32/SessionRoster.zig`).
That was harmless while the roster was read-only: a refetch happened on a
machine change, which resets everything anyway.

T320 added a keyboard cursor that can be parked several rows down a long
roster, and `refresh_in_place` (T319) re-fetches the SAME machine without
resetting anything else — that is the whole point of it, "a re-selection must
not flash the region back to Loading". So a refresh now jumps the region back to
the top while the cursor stays where it was: the highlighted row is off screen
until the next keystroke scrolls it back.

Nothing on box catches it today because the Windows chooser only refetches on
selection change; Mac polls its rosters every 2s (`rosterRefreshTimer`,
`MachineChooserView.swift`), and if/when Windows takes that poll the defect
becomes continuous rather than occasional.

## The fix

`adopt` should not reset the scroll for a refresh that KEPT its rows — clamp it
to the new content height instead (`chooser_sessions.clampScroll`, already
there), and let `clear()` keep owning the reset for a real machine change. The
cursor's own `scrollToCursor` then does the rest.

Care: the rows can shrink under the offset, which is exactly what `clampScroll`
is for, and the cursor is already clamped at the point of use
(`cursorIndex`).

## Validation

- Unit: a scroll offset survives an adopt that replaced the rows in place and is
  clamped when the new content is shorter.
- On box: extend `test/win32/chooser-resume.ps1` with a roster long enough to
  scroll, park the cursor low, force a refetch (re-select the same machine), and
  assert the cursored card is still painted inside the region.
