# T333 - A roster refetch resets the scroll under a parked session cursor

## In plain terms

The machine chooser lists the terminal sessions a machine is running, and you
can walk that list with the arrow keys. If there are more sessions than fit, the
list scrolls to follow you. But whenever the app quietly re-checks the list —
which it does while you are looking at it — the list jumped back to the top,
leaving your highlighted row somewhere off screen. You had to press an arrow key
to find it again. After this, the list stays exactly where you left it.

## Goals

- [x] A re-check of the machine you are already looking at keeps the list where
      it is, instead of snapping to the top.
- [x] A re-check that comes back with FEWER sessions still lands somewhere real
      — no scrolling past the end into an empty pane.
- [x] Switching to a different machine still resets everything, as it must.
- [x] A regression test that fails without the fix.

## Summary

`SessionRoster.adopt` ends with `self.scroll = 0` (`src/apprt/win32/SessionRoster.zig`).
That was harmless while the roster was read-only: a refetch happened on a
machine change, which resets everything anyway.

T320 added a keyboard cursor that can be parked several rows down a long
roster, and `refresh_in_place` (T319) re-fetches the SAME machine without
resetting anything else — that is the whole point of it, "a re-selection must
not flash the region back to Loading". So a refresh now jumps the region back to
the top while the cursor stays where it was: the highlighted row is off screen
until the next keystroke scrolls it back.

Nothing on box catches it today because the Windows chooser only refetches on
selection change; Mac polls its rosters every 2s (`rosterRefreshTimer`,
`MachineChooserView.swift`), and if/when Windows takes that poll the defect
becomes continuous rather than occasional.

## The fix

`adopt` should not reset the scroll for a refresh that KEPT its rows — clamp it
to the new content height instead (`chooser_sessions.clampScroll`, already
there), and let `clear()` keep owning the reset for a real machine change. The
cursor's own `scrollToCursor` then does the rest.

Care: the rows can shrink under the offset, which is exactly what `clampScroll`
is for, and the cursor is already clamped at the point of use
(`cursorIndex`).

## What landed

`adopt` no longer touches `scroll`. `clear()` still owns the reset, so a real
machine change is unchanged; a `refresh_in_place` refetch keeps the offset the
user scrolled to.

`adopt` has no geometry to clamp against, so the clamp happens at the point of
use — the same rule `cursorIndex` already follows. `SessionRoster.clampScrollTo`
re-clamps against the rows as they are now, and `MachineChooser.onSessions`
calls it (via `clampRosterScroll`) between the adopt and the repaint, where the
region IS known. A refetch that comes back shorter therefore lands on the last
legal offset rather than painting an empty region.

## Validation criteria

- [x] A scroll offset survives an adopt that replaced the rows in place.
      Unit: `adopt keeps the offset a refetch was parked at (T333)` in
      `src/apprt/win32/SessionRoster.zig`, win32 lane.
- [x] A stale reply still changes nothing, offset included. Unit:
      `a stale reply changes nothing, offset included`.
- [x] A real machine change still resets the offset (and the cursor, and the
      hover). Unit: `a machine change still resets the offset`.
- [x] The offset is clamped when the new content is shorter. Unit:
      `clampScrollTo pulls a parked offset back into a roster that shrank`.
- [x] On box: a roster long enough to scroll, the cursor parked on its last row,
      a refetch of the SAME machine forced through the chooser's own filter-edit
      path, and the cursored card still painted inside the region.
      `test\win32\chooser-roster-refetch.ps1` ALL PASS (8 assertions).
- [x] That script FAILS without the fix — the negative control. With
      `self.scroll = 0` put back in `adopt` and the app rebuilt, the same run
      reports `FAIL the cursored card is STILL painted in the region after the
      refetch (B +0)` where the fixed build reports `B +26`.

### Where the on-box test lives (deviation, deliberate)

The plan said to extend `test/win32/chooser-resume.ps1`. That script cannot run
at all today: its fixture builds an ORPHANED session by deleting the layout
manifest, and launch-time restore has since learned to recover such a window
from the agent's own layout store, so it exits at `SETUP FAIL: no orphaned live
session` before any section executes. Filed as **T620**. This property needs no
orphan, so it shipped as its own script rather than as a section of a red one.
