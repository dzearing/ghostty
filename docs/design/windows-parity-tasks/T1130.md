# T1130 - A viewer pane squeezed narrow on Windows spills its chrome outside the pane

## In plain terms

Drag a viewer pane (a rendered README, a diff, a web page) narrow enough and the
little table-of-contents card inside it stops fitting: the card is built at a
fixed minimum size, wider than the pane holding it, so its right-hand side is
simply cut off - no rounded corner, no scrollbar, and its rows laid out for a
width the card never gets. The pane's toolbar does the same thing with its
buttons, running off the edge mid-icon. After this, both compress to the pane
they are in, the way the pane's text already does.

## Summary

Main intake, 2026-08-22 (range `22c9c6d8a..origin/main`). Upstream commit
**463dcb0b4** *"fix(viewer): a squeezed viewer pane stays inside its pane"* is
the Mac half; its contract, from `macos/Tests/Ghostty/ViewerNarrowPaneTests.swift`,
is that *a viewer is a leaf in the split tree exactly like a terminal: the tree
decides the width and the leaf does not get a vote.*

**What Windows actually does, measured before the fix.** An 800px window with the
viewer squeezed to 77px (`+rearrange` at ratio 90): the `GhozttyViewerTOC` card
window measured 150px wide starting 15px into the pane - its right edge 88px
past the pane. Root cause `viewer_toc_layout.compactCardWidth`:

```zig
return @min(pref_dip, @max(compact_floor_dip, pane_w_dip - margin_dip * 2));
```

a hard 120 DIP floor the pane cannot veto. Mac has the identical expression and
relies on `ViewerView.clipsToBounds` to hide the overflow, so the Mac build has
the same defect one control further in - filed as **T1154** under the
platform-symmetry rule.

**The symptom differs from Mac's, and the difference matters.** Every piece of
viewer chrome on win32 is a `WS_CHILD` of the pane host, so Windows CLIPS it
rather than painting it over the pane next door. Nothing ever spilled past the
divider here; what the user sees instead is chrome sliced by the pane edge, and
rows measured for a width the card does not have.

**Second site: the nav bar strip.** `viewer_nav_layout.Layout.init` laid every
button out from the strip's own natural width (five buttons = 200px at this
box's 1.25 scale) and let the bar's right edge cut through them. At 77px that is
one whole button, a sliced second, and a trailing feedback button placed
entirely outside the band, where it painted nothing and answered no click. The
strip now ends on the last button that fits WHOLE - **D83** carries that choice
for the user, since it is the half of this they can see.

**Third site, filed not fixed:** `viewer_feedback_layout` pins its action
buttons to the pill's right and walks left with no floor, so a narrow pane puts
them outside the pane - **T1153**.

**The fix.** `compactCardWidth` caps the floor by what the pane has; `Layout.init`
re-clamps in pixels as well, because the pane rounds into DIP and the card
rounds back into pixels and either can round up. `viewer_nav_layout` drops a
button that does not fit and never places the trailing one outside the band, and
the address field is clamped to the band as well as floored.

## Validation criteria

- [x] A viewer pane dragged to its minimum width draws entirely inside the pane
      rect - nothing overlaps the divider or the neighbouring pane.
      **How:** `test\win32\viewer-narrow-pane.ps1` section B measures every
      chrome child window against the pane host at three widths (77px, 155px,
      272px) and scores zero outside; before the fix the same probe reported the
      card 88px past the pane. Window-rect comparison rather than a pixel probe
      because the chrome is child windows, which is also what lets it run on the
      background test desktop.
- [x] The same holds for each viewer flavor Windows ships.
      **How:** the chrome is flavor-independent by construction - one
      `GhozttyViewer` host, one nav bar, one TOC panel, with the flavor deciding
      only what the WebView2 renders. Section D spot-checks that claim on a code
      file (no headings, therefore no card) and asserts both the containment and
      the card's ABSENCE, so the sweep cannot be measuring only section B's one
      control.
- [x] Navigation chrome degrades rather than being clipped mid-control.
      **How:** `viewer_nav_layout.zig`, the two `T1130:` tests - every painted
      rect inside the band at every width from 0 up, at all four scales; buttons
      drop from the trailing end; widening never takes one away. Both
      teeth-checked (reverting the fit test scores 2 failures). Note the
      criterion as originally written said "the way the Mac build does" - reading
      463dcb0b4 shows Mac CLIPS rather than degrading, so there was no Mac
      behaviour to copy and D83 records the choice instead.
- [x] An on-box acceptance script in `test/win32/` covers the narrow case.
      **How:** `test\win32\viewer-narrow-pane.ps1`, ALL PASS; `-NegativeControl`
      scores exactly the three inverted assertions. It has a `guard-due` row so
      an edit to either layout module or either native panel makes it due.
- [x] Floor lanes green (`scripts\floor-lane.ps1 -Lane all`) plus P1-P3.
      **How:** `floor-lane.ps1 -Lane all` ALL LANES PASS (lib, none 292s, win32
      366s, agent 379s); P1/P2/P3 25/20/16; `viewer-panes.ps1` ALL PASS (195).
      The eight audit harnesses these edits made due re-ran green and re-stamped
      (viewer-narrow-pane, printclient-audit, isolation-meta, launch-preflight,
      verdict-exit, cleanslate, body-complete, stderr-capture - the last under a
      real console, per T1144). `fork-identity` stays red for T1134's reason and
      nothing to do with this turn.
