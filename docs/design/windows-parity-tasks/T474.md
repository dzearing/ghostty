## Summary

Split out of **T443** on 2026-08-04, and the direct complement of **T473**.
If the compiler is not truncating the pointer (T473's verdict), then
something is writing 4 bytes over a live stack slot, and the way to see the
writer is a **hardware write breakpoint** — the one tool that names the
instruction that did it rather than the instruction that later tripped over
it.

## In plain terms

Half of a memory address keeps getting overwritten while a test runs. Rather
than guessing what does it, this puts a hardware watch on the exact bytes and
lets the debugger stop the moment anything touches them, which points straight
at the culprit.

## Goals

- [x] A cdb script that breaks after the page is created, reads the page's
      memory pointer, and arms on the slot that later holds the truncated copy —
      `crash-databreak.ps1 -WatchPages`. `ba w8` on the whole pointer rather than
      `ba w4` on the high half: an 8-byte watch catches any write overlapping it,
      including the 4-byte one, and the reports are gated on the T443 signature
      instead of on the width

      is the point: it is what produced the shape guard

- [x] The T443 corrupter itself caught — **not by this instrument, and that is

## Details

**Most of the machinery now exists (T458, 2026-08-06).**
`scripts/lib/DataBreak.ps1` + `scripts/crash-databreak.ps1` already do the
cdb-side heavy lifting this task needs: non-interactive arming of `ba w8`
breakpoints from a computed address at a code breakpoint, `$$<file` includes
for breakpoint commands that set further breakpoints, module+rva addressing
across ASLR, hit reporting (writing instruction + all-thread stacks + full
dump), and the T450 crash filters kept alive alongside. What T458 arms is the
target function's own *stack* slots per call; this task's delta is arming a
*heap* slot (the page's map pointer) from a breakpoint on the code that
creates the page — reuse the lib rather than re-deriving the cdb mechanics.

- The addresses move every run (ASLR + heap), so the breakpoint must be armed
  from a *computed* address, not a literal — break on the function that
  produces the page, then compute.
- `scripts\crash-catch.ps1` already knows how to find `cdbX64.exe` and drive
  it non-interactively; extend that rather than starting a new harness. Its
  header documents the three cdb traps (backslashes eaten inside quoted
  commands, filters armed at the loader break, cdb echoing its own commands)
  that each cost an experiment last time.
- x64 supports four hardware breakpoints and `ba w4` is per-thread; arm it on
  the test thread.
- **There is no small repro.** The terminal-only binary ran 20/20 green (T443,
  2026-08-04), so the breakpoint has to be armed against a full lane run.
  Budget for that: a full lane is ~2-3 minutes and fails about half the time.

## THE INSTRUMENT LANDED, THE HUNT DID NOT END (2026-08-14)

What is in the tree after this turn, so the next reader does not rebuild it:

```
crash-databreak.ps1 -Lane agent -AttachName core \
    -Symbol verifyIntegrity -SignatureFilter page.Page -WatchPages
```

arms four hardware write breakpoints on live `Page` structs and then removes
itself from the hot path. Read T443's "THE WATCH CAN FINISH A LANE NOW" for the
four facts that cost this turn: which spill slot holds `self` (the second, not
the first), why a hit can be recycled memory, why a stray single-step used to
end a run silently, and what the four-address coverage does and does not prove.

The remaining work looked like repetition against a signal that fires ~19% of
the time. It is not: the next turn ran the instrument against a real lane and
measured that no watched address survives one (see DISPOSITION).

## DISPOSITION (2026-08-14): closed on the instrument, residual re-homed

This task is closed as **done for what it can be done for**, and the remaining
line of the title is deliberately NOT left hanging as an open P0:

- **What shipped**: `crash-databreak.ps1 -WatchPages` arms `ba w8` on live
  `Page` structs from a computed heap address, removes itself from the hot path
  (335,878 entry breakpoints → 4), gates hits on the T443 signature plus a shape
  guard, survives a hot address, and reports coverage honestly. Fixture-proven
  end to end in `test\win32\crash-databreak.ps1`.
- **What was measured and closes the rest**: the instrument was run against the
  real thing and reported `2 armed, 2 dropped after going hot, 0 watched to the
  end` over a 183s lane. Pages live in a `MemoryPool` and mostly die young, so a
  watched address is freed and recycled into hot memory within seconds. Four
  debug registers cannot cover that population — this is structural, not a
  tuning gap, so more soak time against this shape buys nothing.
- **Where the work went**: detection is now the software sweep in
  `PageList.verifyIntegrity` (T443, `995711884`), which checks every live page's
  base on a walk already paid for. Naming the writing instruction — the one
  thing a data breakpoint does that a sweep cannot — is **T839**, re-scoped from
  "aim the four registers at the victim tests' pages" to "arm at a code path the
  sweep names". The hunt itself stays with T443, blocked on a live occurrence.
- **The condition that produces occurrences** is being restored under **T840**:
  every sighting had another compile+test running on the box, and the soak can
  only hold CPU spinners today.
