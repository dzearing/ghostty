# T474 - Catch the T443 pointer being truncated with a hardware write breakpoint on the stack slot, armed from cdb

## BLOCKED (2026-08-04) — there is nothing to arm a breakpoint against

**Do not pick this up yet.** T473 measured the crash 26 consecutive times at
HEAD across three harnesses — bare, under cdb, and a full lane — and got **zero
occurrences**, including from the exact binary and debugger that caught three
crashes the same morning. A hardware write breakpoint needs a live occurrence to
arm against and a known page to point at; with the signal quiet, arming one
costs a whole context and observes nothing.

Unblock it by getting the crash back first — see **T443 § T473 VERDICT** and

## Summary

Split out of **T443** on 2026-08-04, and the direct complement of **T473**.
If the compiler is not truncating the pointer (T473's verdict), then
something is writing 4 bytes over a live stack slot, and the way to see the
writer is a **hardware write breakpoint** — the one tool that names the
instruction that did it rather than the instruction that later tripped over
it.

## In plain terms

Half of a memory address keeps getting overwritten while a test runs. Rather
than guessing what does it, this puts a hardware watch on the exact bytes and
lets the debugger stop the moment anything touches them, which points straight
at the culprit.

## Goals

- [ ] A cdb script that breaks after the page is created, reads the page's
      memory pointer, and arms `ba w4` on the slot that later holds the
      truncated copy
- [ ] The writing instruction captured, with its stack
- [ ] The mechanism written into T443 with the cite

## Details

**Most of the machinery now exists (T458, 2026-08-06).**
`scripts/lib/DataBreak.ps1` + `scripts/crash-databreak.ps1` already do the
cdb-side heavy lifting this task needs: non-interactive arming of `ba w8`
breakpoints from a computed address at a code breakpoint, `$$<file` includes
for breakpoint commands that set further breakpoints, module+rva addressing
across ASLR, hit reporting (writing instruction + all-thread stacks + full
dump), and the T450 crash filters kept alive alongside. What T458 arms is the
target function's own *stack* slots per call; this task's delta is arming a
*heap* slot (the page's map pointer) from a breakpoint on the code that
creates the page — reuse the lib rather than re-deriving the cdb mechanics.

- The addresses move every run (ASLR + heap), so the breakpoint must be armed
  from a *computed* address, not a literal — break on the function that
  produces the page, then compute.
- `scripts\crash-catch.ps1` already knows how to find `cdbX64.exe` and drive
  it non-interactively; extend that rather than starting a new harness. Its
  header documents the three cdb traps (backslashes eaten inside quoted
  commands, filters armed at the loader break, cdb echoing its own commands)
  that each cost an experiment last time.
- x64 supports four hardware breakpoints and `ba w4` is per-thread; arm it on
  the test thread.
- **There is no small repro.** The terminal-only binary ran 20/20 green (T443,
  2026-08-04), so the breakpoint has to be armed against a full lane run.
  Budget for that: a full lane is ~2-3 minutes and fails about half the time.
