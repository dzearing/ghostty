# T696 - The queue starves priorities one tier below D49: an ordered P2 band outranks 107 unordered P1s

## Summary

next sorts by order, then priority, then id. Yesterday's D49 fixed the P0 case by hand (five P0s given positions 1-5). Today every one of those is closed, and the win-seat queue head is an ordered run of P2 harness tasks at order 312-319 while 107 open P1s - including every M1 promotion made this morning - carry no order at all and therefore sort last. The hand-pull was applied again today (14 tasks given fractional front positions), which is the second consecutive morning a human ordering pass was the only thing standing between the tracker and working on the wrong thing. The fix belongs in the tool: either sort priority before order, or make order a within-priority key, or have new/triage assign an order at write time so unordered is never a state. See D55.

## In plain terms

The list of work has a "what next" button, and it has been handing out the wrong
answer. It reads a hand-written position number before it reads how important a
task is, and most tasks have no position number at all - so a batch of minor
cleanup jobs that happen to be numbered keeps beating the serious ones that are
not. Someone has had to re-sort the list by hand two mornings in a row. This
makes the rule part of the tool instead.

## Goals

- [x] An important task can never be handed out after a less important one just
      because the less important one carries a number
- [x] A task filed today is reachable today, without a manual ordering pass
- [x] Whatever hand-curated sequencing is still wanted keeps working, inside its
      own priority band
