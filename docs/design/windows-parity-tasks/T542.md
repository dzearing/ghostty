# T542 - viewer-panes.ps1 T395 regression: split off a web viewer lands in the repo cwd, not the last-focused terminal's

## In plain terms

One of the viewer acceptance checks is failing on the current build, before
any new work: open a terminal in directory A, open a browser-style viewer
pane, then split a new terminal off that viewer — the new terminal is
supposed to open in directory A (the last real terminal the user was in),
but it opens in the repository directory instead. Either the app lost that
"fall back to the last terminal's directory" behavior, or the test's setup
stopped focusing the terminal it thinks it focused. Until this is fixed the
viewer test suite is permanently red, which hides any new breakage.

## Summary

Found 2026-08-06 while validating T160. `test\win32\viewer-panes.ps1` fails
one assertion — `a web viewer contributes no cwd, so the fallback stands
(got 'D:\git\ghoztty\')` (the T395 section, ~line 667) — **on clean HEAD
b8b45a77a with a freshly built debug exe**, reproduced twice, so it is not a
T160 regression (T160's runs failed the same single assertion; a stash +
rebuild + rerun on HEAD failed it identically with 151 passing).

The section's chain: `+split --target=vp --name=t395base
--working-directory=<other>` (passes, terminal lands in `<other>`), `+split
--view=about:blank --name=t395web`, then `+split --pane=t395web
--name=t395webterm`. The final terminal should inherit the last-focused
core surface's cwd (`<other>`) because a WEB viewer contributes no file
directory; it actually gets the app's own launch cwd (`D:\git\ghoztty\`),
i.e. the ORIGINAL `vp` pane's cwd — so the "last focused core surface"
bookkeeping (or the test's assumption about which split holds focus) is off.

## Where

- `test\win32\viewer-panes.ps1` T395 section (`contributes no cwd`).
- The fallback implementation T395 added (viewer split cwd inheritance) —
  likely `Window.zig`/`PaneView` split-cwd resolution; git-log the T395/T396
  commits for the exact site.
