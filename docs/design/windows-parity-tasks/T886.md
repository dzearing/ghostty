# T886 - crash-catch reports a clean exit as UNCAUGHT when the debuggee's last stdout write has no trailing newline

## Summary

`Read-CrashCatchLog`'s `Test-Marker` matched the cdb `.echo` markers
(`GHOZTTY-EXIT-BEGIN` etc.) with a start-of-line anchor. cdb interleaves the
debuggee's stdout with its own output on the same stream, so when the
debuggee's LAST write before the marker has no trailing newline — WebView2's
`AddWebResourceRequestedFilter` deprecation warnings are exactly that shape —
the marker lands glued onto the end of the debuggee's text
(`...linkid=2286319GHOZTTY-EXIT-BEGIN`) and the anchor misses it. The parser
then finds no exit block and calls the run UNCAUGHT (exit 3).

Seen live 2026-08-16 during T536's validation: `crash-catch.ps1 -Lane win32
-Attempts 6` reported attempt 1 `UNCAUGHT in 221s` while its own transcript
(`.dumps/ghostty-test-20260816-051608-1.log`) plainly contained
`Last event: … Exit process 0:d730, code 0` — a clean, fully-passed
4927/4927 run. A false UNCAUGHT is the same instrument lie T877 covered for
the soak, in the opposite direction: on a box with an armed T443 watch it
reads exactly like the corruption ghost firing, and it aborts a multi-attempt
catch series on its first occurrence.

## In plain terms

The tool that watches test programs for crashes was sometimes declaring a
perfectly healthy run "unexplained" — because the program's last printed line
didn't end with a newline, and the tool's end-of-run bookmark got stuck to it.
On this machine, where a real intermittent crash bug is being hunted, a false
alarm from the watcher is indistinguishable from the bug itself, so the
watcher has to be exact.

## Fix

`Test-Marker` (scripts/lib/CrashCatch.ps1) now matches the marker anywhere in
the line but still end-anchored — anything may precede it, only whitespace may
follow. The end anchor is what keeps cdb's `Reading initial command
'...GHOZTTY-EXIT-BEGIN; ...'` echo (markers mid-string, always followed by
`; …`) a non-match.
