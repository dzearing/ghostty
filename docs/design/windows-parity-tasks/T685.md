# T685 - The parity sweep watches only macos/ and src/viewer/, so main's changes to shared src/ are ungated

## Summary

scripts\parity-sweep.ps1 (T152) enumerates commits touching macos/ or src/viewer/, which is what the 2026-07-29 audit measured and therefore what the gate inherited. But parity obligations also arrive through the SHARED core: T604 exists precisely because main rewrote src/cli/send_keys.zig while this branch built bracketed-paste framing on top of it, and nothing flagged the divergence - a shared-path sweep would have. The reason it is not simply a wider -Paths default is that this branch's own win32 work lives in src/ too, so a naive sweep would report several hundred of our own commits as unmapped and the gate would be ignored within a day. Evaluate the shape that works: probably restricting the enumeration to commits reachable from origin/main but not from the merge-base (the incoming side only), which is well-defined for the intake range and is what the intake actually cares about. Then decide which shared subtrees are worth watching (src/cli/, src/termio/, src/apprt/ipc/ are high-signal; src/apprt/win32/ is ours). Ship it with acceptance arms in test\win32\parity-sweep.ps1 proving our own commits are not reported.

## In plain terms

We keep a checklist of every change the Mac side makes, so a feature Mac users
got can never quietly fail to arrive on Windows. That checklist was only
watching the Mac app's own folder — but plenty of the terminal's behaviour
lives in shared code underneath both apps, and changes there were invisible to
it. This widens the checklist to cover the shared code as well, while making
sure our own Windows work doesn't flood it. Nobody sees a new button; what
they get is that the "we've covered everything" number is now telling the
truth.

## Goals

- [x] The gate watches shared `src/`, not just `macos/` + `src/viewer/`
- [x] The Windows frontend (`src/apprt/win32/`) and Linux's (`src/apprt/gtk/`)
      are excluded — neither owes Windows a port
- [x] This branch's own commits are never reported as unmapped Mac changes
- [x] The exclusion is visible in the report, not silent
- [x] Acceptance arms prove each half separately, each with a control
- [x] `go.md`'s description of the gate matches what it now does

## Decision on the shape

Two ways to widen, filed as **D60**: an allowlist of high-signal subtrees, or
all of `src/` minus what cannot owe Windows anything. Shipped the second.

An allowlist is quiet today and blind to whatever main adds next month — which
is this very defect, re-committed. Subtracting is complete by construction, and
the noise objection turned out to be bounded: the daily intake range is the
watermark, which evaluates 0–2 commits a day.

The measurement that settled it: since 2026-06-01, main has **152 commits
touching `src/`, 87 of which touch no `macos/` path at all**. That is the size
of the blind spot, and 81 of those are cited by no Windows work item anywhere.

## Why the guard is topological, not another path exclusion

Widening the paths puts our own work in scope: 187 of this branch's commits
since the merge-base touch shared `src/`, and no path rule separates them from
main's — we edit `src/cli/`, `src/termio/` and `src/remote/` too. So the sweep
now enumerates only the **incoming side**: a commit in the range that is not
reachable from `-IncomingRef` (`origin/main`, else `main`) is branch-local,
dropped, and counted separately.

For the daily intake range (`<watermark>..origin/main`) that is a no-op. For
`-Range <merge-base>..HEAD` it is the difference between a usable report and
187 lines of our own history. Measured on `680a07ed3..HEAD`: 481 commits raw →
**294 enumerated + 187 excluded**.
