# T576 - The key-state pill has no explainer popover on Windows: Mac's says what a key table is

## In plain terms

When a key table is active, Ghoztty shows a small card at the bottom of the
pane naming it. On a Mac you can click that card and get a sentence explaining
what a key table actually IS — which matters, because the most likely way to
end up in one is by accident, and the name alone ("resize", "vim") does not
tell you what has happened to your keyboard or how to get out. On Windows the
card is there but there is nothing to click.

## Goals

- [x] The pill explains itself on Windows, in a way that reaches someone who
      did not mean to enter the mode - resting the pointer on the card shows
      the explainer, and so does clicking it (Mac's own gesture)
- [x] Whatever is added does not cost the pill its click-through behavior for
      ordinary terminal input (see decision D31) - the card takes the pointer
      and nothing else does
- [x] Geometry asserted at 1.0 / 1.25 / 1.5 / 2.0, plus acceptance coverage

## Summary

Filed out of T446 (2026-08-07), which shipped the pill itself. Mac's
`KeyStateIndicator` carries a popover (`macos/Sources/Ghostty/Surface
View/SurfaceView.swift`, the `.popover` at the end of `indicatorContent`) with
a "Key Table" heading and the sentence *"A key table is a named set of
keybindings, activated by some other key. Keys are interpreted using this table
until it is deactivated."* The win32 pill (`KeyStateIndicator.zig`) has no
counterpart.

## Details

The obstacle is not the popover, it is the trigger. The win32 pill is
`WS_EX_TRANSPARENT` on purpose: it floats over the bottom-center of live
terminal content, which is where a selection drag ends, so it must not eat
mouse input. Making it clickable to open a popover gives that back. Options
worth weighing before building:

- **A tooltip on hover** rather than a click target. `tab_tooltip.zig` is the
  existing pattern, and a hover tooltip needs `WM_MOUSEMOVE`, which is the same
  problem in a smaller form.
- **Hit-test only the card**, passing everything else through — the pill's
  window is the card plus a shadow allowance, and `key_state_pill.Layout.card`
  already names the exact rect, so `WM_NCHITTEST` returning `HTTRANSPARENT`
  outside it is a small amount of machinery.
- **Put the explanation somewhere that is not the pill at all** — a one-time
  notice the first time a key table is entered, which reaches the accidental
  case better than a control you have to already suspect the answer to click.

The last is worth taking seriously: the user this is for does not know the
thing on their screen is explainable.

Decision D31 (should the pill be draggable) covers the adjacent
clickable-vs-click-through question and should be read first; if it resolves
toward a clickable pill, this becomes much cheaper.

*Validation:* an acceptance script that enters a key table and asserts the
explanation is reachable and that ordinary mouse input at the pill's location
still reaches the terminal underneath (the regression the click-through rule
exists to prevent). Both `zig build test` lanes, `zig build test-agent`, and
P1–P3 stay green.

## What landed

The trigger, which was the whole obstacle, is **the card and only the card**.
The pill's window is the card plus a shadow allowance, and it drops
`WS_EX_TRANSPARENT` for a `WM_NCHITTEST` that answers `HTTRANSPARENT`
everywhere `key_state_pill.hitsCard` says no - so the shadow band, which is
decoration over live terminal content, still falls through to the terminal,
while the card can be hovered. The ex-style could not make that distinction:
it is all or nothing, and it would have made the card unhoverable too.

The explanation is Mac's popover text, verbatim (`EXPLAINER_TITLE` /
`EXPLAINER_BODY`), in the control the Windows shell uses to answer "what is
this thing": a comctl32 tooltip with a bold heading. It shows on hover after
the system's own double-click-time delay, and immediately on a click, which is
the gesture Mac uses - hover is the one that reaches the accidental case,
because someone who did not mean to be in a key table does not know the card
is clickable.

Three things measured rather than assumed, each of which was wrong on the
first cut:

- **Subclass mode does not work here.** `TTF_SUBCLASS` lets comctl32 watch the
  tool window's own mouse messages, and a pointer that arrives on the card and
  rests - which is what a hover IS - produces exactly ONE `WM_MOUSEMOVE` and
  never trips the relay. Nothing ever showed. It is track mode now, with this
  file owning the hover timer, the way the tab strip's tooltip already did.
- **The bubble is placed above the card.** The pill hugs the pane's bottom
  edge, so the control's default placement hangs the explanation off the pane.
  Track mode positions by the top-left corner, so the height has to come
  first - and `TTM_GETBUBBLESIZE` answers for a bubble that has not been laid
  out with this control's title and wrap width (it reported 81x27 for one that
  drew 332x69). It is shown, measured with `GetWindowRect`, then placed.
- **`TTM_TRACKACTIVATE FALSE` does not take the bubble off the screen** when
  its tool window is a layered popup hiding in the same breath - the window
  stayed `WS_VISIBLE` with the explanation floating over the terminal after
  the key table ended. Both states are set now: the control's, so its next
  show is clean, and the window's.

## Validation criteria

- [x] Only the card takes the pointer, asserted at the exact boundary pixel on
      each of its four edges, computed from the window's real DPI - section G2
      of `test\win32\key-state-pill.ps1`, which asks the window the same
      `WM_NCHITTEST` question Windows asks before it delivers a click
- [x] The pill is no longer `WS_EX_TRANSPARENT`, asserted (inverted, not
      deleted, so re-adding the style cannot silently take the explainer away)
      - section D of the same script
- [x] The explainer reaches the screen: clicking the card shows the bubble,
      centered on the card, above it, wider than the pill - section G2
- [x] It leaves with the card: deactivating the key table takes the bubble off
      the screen - section G2
- [x] The hover path shows it on a real pointer, verified by hand on the
      interactive desktop (the background test desktop has no pointer to hold
      a hover with - T233): tooltip visible, 332x69, centered on the card and
      just above it
