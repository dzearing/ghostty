# T98 — FIX: local-agent session pid reads as a system pid on Windows

## Summary

FIX: local-agent session pid reads as a system pid on Windows — `+sessions`/`+list` report a bogus child pid (428 "Secure System" observed) for a LOCAL agent-backed ConPTY session instead of the shell pid; ConPTY reparents the child, so the agent's recorded pid does not track the real shell. Found by T89d (2026-07-20; worked around there by proving agent-ownership via survives-app-quit instead of pid ancestry). Impact: `+list --pid` self-ID and any pid-based tooling on agent-backed panes. Pre-existing agent behavior (T89b/T89c pty pid capture), not introduced by T89d; NOT in the parity validation lanes. Investigate the agent's ConPTY child-pid capture (PROCESS_INFORMATION.dwProcessId vs the pseudoconsole host)

## Details

Found by T89d (2026-07-20). For a LOCAL session-persistence pane, both
`+sessions` and (presumably) `+list` report a bogus child pid — a probe of the
initial agent-backed window showed `sess.pid = 428` ("Secure System", a
low system pid), not the ConPTY shell's pid. Walking `ParentProcessId` from 428
reaches only `System`(4)→(0), never the agent. So the agent's recorded
per-session child pid does NOT track the real shell process.

Likely cause: the agent captures a wrong/uninitialized pid for a ConPTY child
(ConPTY reparents the child under an OpenConsole/conhost host, and
`PROCESS_INFORMATION.dwProcessId` vs the pseudoconsole host pid may be confused
in the agent's `pty_child` spawn path). This is PRE-EXISTING agent behavior
(T89b/T89c), NOT introduced by T89d — T89d merely surfaced it and worked around
it in `session-open.ps1` by proving agent-ownership via **survives-app-quit**
(kill the GUI, the agent still lists the session alive) instead of pid ancestry,
which is a stronger claim anyway.

Impact: `+list --pid` self-identification on agent-backed panes (a process
inside the pane can't find its pane by pid), and any pid-based tooling. Bounded:
does not affect the session's function, typing, or persistence. Not in the
parity validation lanes.

*Fix (candidate):* audit the agent's ConPTY child-pid capture — record the real
`PROCESS_INFORMATION.dwProcessId` of the spawned shell and thread it through the
session roster's pid field; add a `+sessions --json` pid assertion once fixed.

*Validation:* extend `session-open.ps1` to assert the session pid is a live,
agent-descended process once the capture is fixed (the assertion T89d dropped).

## Outcome (2026-08-03)

**The capture was already fixed — by T41 (`1968b0581`, 2026-08-02), a day before
this task was picked up.** T41 needed a real shell pid for its close-confirmation
idle check, found the same root cause, and fixed it at the source:

- `pty_child.zig` `spawnFn` — on Windows `posix.pid_t` IS the process HANDLE, so
  the spawner now asks `GetProcessId` for the pid behind it before putting it in
  `Spawner.Result.pid`. The old code surfaced the HANDLE's integer value, which
  is what made `sess.pid` read as `428`: a small even number that happens to name
  "Secure System", so it looked like a plausible pid and walked to `System(4)→0`.
  The suspected cause in the Summary above (confusion with the pseudoconsole
  host) was wrong — the child IS created by the agent and IS parented by it.
- `Surface.shellPid` — the app-side half. `IpcHandlers` had a private copy that
  returned 0 for EVERY remote-backed pane, which with `session-persistence` on
  (the default) is every local pane, so `+list --pid` could not find the pane it
  was run from inside.

Measured on box, hermetic debug build: session pid `44396` = `cmd.exe`, parent
`40636` = `ghoztty-agent.exe`; `+list --json` reports the same `44396` for the
pane; `+list --pid=44396` answers with the pane id.

So what this task actually delivered is **the validation it always named as its
own second half**, in both places the loop keeps evidence:

- `session-open.ps1` A7–A10 (the assertion T89d dropped, restored): the session
  pid names a live process, that process is a strict descendant of the agent
  (`Is-DescendantOf`, which stops at the system pids so `428` can never pass),
  `+list` agrees with `+sessions` about the pid, and `+list --pid` resolves back
  to the pane. A8–A14 renumbered.
- `pty_child.zig` — an agent-lane test, `PtySpawner: the reported pid is a real
  process parented by the agent (T98)`. It goes through the `Spawner` vtable, not
  `spawnChild`, because the conversion under test lives in `spawnFn`; the oracle
  is `ProcSampler` (pid → ppid, already cross-platform), so it guards the POSIX
  arm too. Confirmed to actually execute by breaking it deliberately
  (`expected 46273, found 46272`) before landing it green — `test-agent` runs
  3852 tests and a silently-skipped one would have looked identical.
  `proc.freeProc` became `pub` for the row cleanup.
