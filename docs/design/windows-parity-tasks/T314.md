# T314 - ipc-machine-chooser.ps1 keeps a private banker's-rounding Dip - the T257 divergence, in the one script T257 did not sweep

## In plain terms

Nothing a user of the terminal can see is wrong. This is about the test that
checks the "New Remote Window" picker looks right. It was doing its own
pixel arithmetic with a rounding rule that disagrees with the app's on a
112.5%-scaled screen, and it was rebuilding one measurement (where a row's
text starts) by a shortcut the app does not take. Both made the test measure
approximately instead of exactly, so it could only assert the text landed
"somewhere in a nine-pixel window". After this it asserts the exact pixel.

## Goals

- [x] the private `Dip` helper is gone; every DIP measurement goes through the
      shared `Get-TestChromeDip`
- [x] `text_x` is composed from the module's own terms instead of re-derived
      from their total
- [x] the row-geometry probe is anchored on that exact value
- [x] 112.5% - the only scale where the rounding modes disagree - is pinned
      somewhere it can actually be exercised

## Summary

**Exactly the defect T257 found, still live in a fifth script.** T257 hoisted
the chrome datum into `test/win32/lib/ChromeGeometry.ps1` and its lesson was
not "less duplication": the layout modules round with Zig's `@round` (half away
from zero) and PowerShell's `[math]::Round()` is BANKER'S rounding, so private
copies carry a latent DPI bug that agrees at 100/125/150/200% and diverges at
112.5%.

`ChromeGeometry.ps1:98` gets it right:

```powershell
return [int][Math]::Round($Dip * $Scale, [MidpointRounding]::AwayFromZero)
```

`test/win32/ipc-machine-chooser.ps1:131` does not:

```powershell
function Dip($scale, $v) { return [int][Math]::Round($v * $scale) }
```

T257 swept the four scripts that measured the tab strip; the chooser measures
its own dialog through its own helper, so it was never in that sweep.

## Why it matters now (T310 hit it)

T310 added a row-geometry pixel probe and could not state an exact expected
value because of this. The row's `text_x` at 1.25 is 85 physical px, built by
the layout module as a SUM of individually-`@round`ed components; `Dip 1.25 68`
returns 85 by luck, and `Dip 1.25 44` returns 55 where the module's row height
is 56. So the probe had to be written as a band (`>= 65 DIP`, `<= 74 DIP`)
rather than an equality, and its discrimination margin against the retired
geometry is ~9 px instead of exact.

Two separate things are wrong and both should be fixed:

1. **The rounding mode.** Use `ChromeGeometry.ps1`'s helper (the script already
   dot-sources `TestDesktop.ps1`, which dot-sources it) instead of a private
   `Dip`.
2. **Component-wise vs whole rounding.** A metric the module builds by summing
   rounded parts cannot be reproduced by rounding the total, at ANY rounding
   mode. Either expose the composed metric so the script reads it rather than
   rebuilds it, or state in the script which values are safe to `Dip` (single
   terms: 840, 540, 260, 16) and which are not (row height, `text_x`).

The second is the more interesting half and is the same rule T235/T257 keep
arriving at from different directions: **a script must not re-derive a number
the module composes.**
