# T821 - A Mac window attached to a Windows agent keeps its scrollback when grown

## In plain terms

Dragging a terminal window taller used to quietly delete some of the output you
had already scrolled past. That is fixed everywhere now, including for a Mac
window showing a shell that actually lives on a Windows machine — but only the
Windows half of that pair has been watched happening. This is somebody sitting
in front of a Mac, making the window taller, and confirming nothing disappears.

## Summary

T471 moved the scrollback guard (`src/termio/history_guard.zig`) off
`builtin.os.tag` and onto the child's pty flavour, which the agent now reports in
its HELLO (`Hello.pty_flavor`). That fixes both cross-OS directions in one place,
because the guard lives in the shared Zig core:

- **macOS app + Windows agent** — the child is a ConPTY and repaints after every
  resize, so the guard is now ARMED where it used to be compiled out. This was
  the direction that genuinely lost data.
- **Windows app + POSIX agent** — the guard is now OFF, so a taller pane pulls
  previously-scrolled output down instead of showing blank rows.

The second direction is measured end to end on the Windows box
(`test\win32\history-guard-flavor.ps1`, section B, using the
`GHOZTTY_AGENT_PTY_FLAVOR` test seam to make one machine answer as the other).
The FIRST one cannot be: it needs a Mac window driving a Windows agent, which is
two machines and only the Mac seat has the near half.

## What to do

Open a remote window from macOS against this box's `ghoztty-agent`
(`+new-remote-window`), fill the pane with `line 1`..`line 500`, then grow the
window's height by ~18 rows and read the scrollback back. No `line <N>` that was
present before the resize may be missing after it — the T431 oracle, unchanged.
Worth running the negative control the same way T471's section B does: with an
agent forced to report `posix` (`GHOZTTY_AGENT_PTY_FLAVOR=posix`, Debug/
ReleaseSafe only) the same gesture SHOULD eat exactly the rows the viewport
gained, which is what proves the Mac side is reading the flavour off the wire
rather than assuming POSIX because it is a Mac.

## Validation criteria

- [ ] A macOS window on a Windows agent's ConPTY session loses no scrollback
      when the window is made taller (numbered-line oracle, ~500 lines)
- [ ] Negative control: the same pane against an agent reporting `posix` DOES
      lose the rows the taller viewport gained — so the Mac client is reading
      the reported flavour, not its own OS
- [ ] Whatever is run is left behind as a script or a documented recipe, so the
      next protocol change to this field can be re-measured
