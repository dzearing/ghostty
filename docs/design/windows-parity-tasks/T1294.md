# T1294 - One publish per day strands the fixes that land after it

## In plain terms

The loop publishes once a day. Anything fixed after that publish sits on the
shelf until tomorrow, even when someone is waiting on it right now. So you can
report a bug, watch it get fixed, download the installer an hour later, and
still hit the same bug.

## What happened (2026-09-03)

| | |
|---|---|
| 09:28 | `win-v1.36.2` published |
| 11:01 | T1291 fixed and committed (`65da707e5`) - the silently-dying same-version install |
| 18:19 | `daily-publish.ps1 -Check` → `NOT DUE: already published today` |
| | The user installs, hits the *same* bug, reports it again |

`git merge-base --is-ancestor 65da707e5 win-v1.36.2` → **not an ancestor**. The
fix was never in the build the user had. At the time of writing there were
**24 commits** on the branch behind that one-per-day rule.

The user's words, on hitting it the second time:

> "again, i click on the msi to install (it's already installed.) I don't get
> an option to repair or reinstall or anything, it just silently dies."

The word that matters is *again*.

## The defect

T1292 fixed *whether* a publish can happen (it no longer needs Docker). This is
about *when*. The watermark is a **date**, so the second publish of a day is
refused by design - which is a sensible guard against publish-per-commit noise
and a bad answer when someone is actively waiting.

Note also the interaction with the T1178 in-app updater: the user is supposed
to receive fixes by update, not by re-downloading. A fix that is not published
is not offered by the updater either, so the whole delivery story stalls on the
same watermark.

## What to build

- **Let a publish be requested when work is waiting on it.** A second publish
  in a day should be possible - on demand, or when a task the user reported is
  the thing that just landed. The daily cadence stays the floor, not the
  ceiling.
- **Keep the noise guard.** The reason for one-a-day is not to spam releases
  per commit; preserve that default while allowing an explicit "ship this now".
- **Say what is stranded.** The health line reports `publish=ok` once a day has
  published, which was true today and still left 24 commits unshipped. It
  should distinguish "published, and nothing is waiting" from "published, but N
  commits have landed since" - the second is the state that misleads.
- **Close the loop on a user report.** When a fix lands for a task filed from a
  user report, the publish that carries it is part of the fix. A task marked
  done whose fix has not shipped is not done from where the user stands.

## Validation criteria

- [x] A fix landing after the day's publish can reach a release the same day
      without a hand-cut tag. `daily-publish.ps1 -Request -Reason "<why>"`
      records it; the next task-boundary run publishes past the date rule.
      Verified by section L of `test\win32\daily-publish.ps1` (L3 -> L4).
- [x] The default cadence is unchanged for ordinary work - no publish-per-commit.
      L2 and L7 of the same section (a fix landing with no request is still
      stranded; an ordinary evening push after today's publish is still a no-op),
      plus J2, and the whole of A/G unchanged and green.
- [x] The health line distinguishes "published and current" from "published but
      N commits behind HEAD": `publish=ok+<n>` vs `publish=ok`. Verified by Z8/Z9
      of `test\win32\go-loop-guard.ps1` (a release three commits back reads
      ok+3; one carrying HEAD reads plain ok), and observed live as `ok+31`.
- [x] The digest names the commits that landed after the day's release.
      `daily-publish.ps1 -Status` prints them (section M); go.md step 0.5 now
      requires the Commentary to name them.
- [x] A test drives the exact 2026-09-03 shape - publish at T, fix at T+90m -
      and proves the fix can ship that day: section L, end to end through the
      real script with a sentinel publisher.
- [x] The new refusals can score red: `-NegativeControl` on
      `test\win32\daily-publish.ps1` reports 130 FAILURE(S), and L8/J3 construct
      the empty-release state and prove the request is cleared, not honoured.
