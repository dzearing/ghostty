# T323 - No build lane on this box actually compiles the libghostty C API (embedded.zig CAPI)

Found 2026-08-01 during T322, by a positive control. A C API edit can ship from
the Windows seat with **zero compile coverage**, and every lane reports green.

## Evidence (VERIFIED on the box, both directions)

T322 added one field to `SessionJsonRow` inside
`ghostty_remote_connection_list_sessions` (`src/apprt/embedded.zig`). Before
believing the green, the line was deliberately broken to
`.relaunchable = s.T322_POSITIVE_CONTROL,` and every lane re-run:

| lane | with the bogus field | analyzes CAPI? |
|---|---|---|
| `zig build test -Dapp-runtime=none` | exit 0 | no |
| `zig build test -Dapp-runtime=win32` | exit 0 | no |
| `zig build test-agent` | exit 0 | no |
| `zig build -Dapp-runtime=win32 -Doptimize=Debug` | exit 0 | no |
| `zig build -Dapp-runtime=none -Dtarget=aarch64-macos -Demit-lib-vt=false` | **exit 0** | **no** |
| `zig build -Dapp-runtime=none -Demit-lib-vt=false` (windows target) | exit 1, names the field | yes |

Two independent reasons, and they cover each other:

1. **The exe lanes never reference it.** `apprt.runtime` resolves to `embedded`
   only for `build_config.artifact == .lib` (`src/apprt.zig:43-49`), and `CAPI`
   is reached solely from `src/main_c.zig:41`
   (`if (@hasDecl(apprt.runtime, "CAPI")) _ = apprt.runtime.CAPI;`). An `export
   fn` in an unreferenced container is never analyzed.
2. **The macOS-target lib is built and then thrown away.** `build.zig:315-329`
   constructs `GhosttyLib.initShared/initStatic`, then installs them only
   `if (!config.target.result.os.tag.isDarwin())` — the comment there already
   admits the guard is wrong ("We shouldn't have this guard"). For a Darwin
   target nothing depends on the compile step, so it never runs, and the build
   exits 0 having compiled none of it.
3. The one lane that DOES analyze it — a **windows-target** lib — cannot
   complete for an unrelated reason: `src/remote/ssh_transport.zig` is
   POSIX-only (`posix.pipe2` at `:64`, `posix.kill` at `:698`) and fails with 2
   errors on a Windows target regardless of this change (confirmed: the two
   errors are identical with and without the T322 edit, in a file `git status`
   shows unmodified).

So the only way to type-check a C API edit from this seat today is to
deliberately break it against a lane that cannot otherwise build, and read the
error out of the wreckage. That is what T322 had to do.

## Why it matters here

The C API is the Mac seat's entire view of the Zig core, and the Windows seat
edits it (T322 did; the T146 children touch the same roster path). A change that
compiles nowhere is a change the Mac seat discovers at *its* next build — the
opposite of the "make a lie loud" discipline the rest of this loop runs on.

## Fix (sketch — decide during the task)

Add a compile-only check step that analyzes `main_c.zig` for a Darwin target,
so it is exercised without needing the Darwin link/install to succeed:

- Preferred: a `zig build check-capi` step wired to the `GhosttyLib` compile
  (a `Compile` step added to a check step compiles without emitting a binary),
  targeting `aarch64-macos`, and added to the standing floor in `go.md`.
- Alternative: drop the `isDarwin()` install guard at `build.zig:320` if the
  Darwin lib can actually link when cross-compiled from here (unproven —
  measure before choosing).

Either way the acceptance is the positive control above: with a bogus field in
`SessionJsonRow`, the new step must FAIL, and pass once reverted. A step that
goes green on the broken tree is the failure this task exists to remove.

## Validation

- `zig build check-capi` (or whatever it lands as) fails on a deliberately
  broken `embedded.zig` CAPI body and passes on HEAD.
- The existing five lanes stay green.
- `go.md`'s standing floor lists the new step.

## Resolution (2026-08-14, under T475)

Point 3 above turned out to be the whole task. The lane this file already
identified as the one that DOES analyze `CAPI` — a **windows-target**
`zig build -Dapp-runtime=none` — could not build only because of the four
POSIX-only call sites in `src/remote/ssh_transport.zig`. T475 guarded them, so
that lane now completes, and it is wired into the standing floor as
`scripts\floor-lane.ps1 -Lane lib` (first in `-Lane all`, ~1s cached).

No new `check-capi` step was needed: the sketch above proposed one because the
existing lane was unusable, not because it was the wrong lane. Using the lane
the build already has avoids a second, parallel definition of "compile the C
API" that could drift from it.

Acceptance is this file's own positive control, run both directions:

| tree | `floor-lane.ps1 -Lane lib` |
|---|---|
| `.relaunchable = s.T323_POSITIVE_CONTROL` | `FAIL` — `embedded.zig:2926:35: error: no field named 'T323_POSITIVE_CONTROL' in struct 'remote.connection.OwnedSession'` |
| reverted (HEAD) | `PASS` in 5s |

`go.md` step 3 now names four lanes and says what the `lib` one is for.
