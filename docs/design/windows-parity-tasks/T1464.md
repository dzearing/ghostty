# T1464 - The agent relay, not the parser, is what makes a pane slower than conhost

## Summary

Measured on an optimized (ReleaseFast, `x86_64-windows-gnu`) build under T1463,
same box, same desktop, same byte-identical 400k-chunk workload, two samples of
each:

| 400k chunks (~9.4 MB) | writer-clock elapsed | sustained ingest |
|---|---|---|
| conhost | 7,950 / 8,468 / 7,956 ms | ~1.2 MB/s |
| Ghoztty pane, **local ConPTY** (`termio/Exec.zig`) | **6,511 / 6,138 ms** | 1.44-1.70 MB/s |
| Ghoztty pane, **agent-held ConPTY** (`termio/Remote.zig`) | **12,863 / 12,706 ms** | 634-696 KB/s |

The same build, on the same workload, is **2.1x slower when the PTY is held by
`ghoztty-agent`** than when the pane owns it directly - and the shipped
configuration is the agent-held one. Against conhost that is the difference
between being 1.3x FASTER and 1.6x SLOWER.

The parse cost is the same in both and is not the difference: `parse_ms_per_s`
runs 41-43 on the agent path, ~4% of a wall-clock second, at 0.06-0.07 us/byte.
Lock wait is 2.6-2.8% of the drain. So the ~6.5 seconds the agent path adds is
neither parsing nor the renderer mutex - it is the relay.

The shape of the relay is the leading suspect and is right there in the numbers:
`feeds_per_s` equals `slices_per_s` at **10,000-22,600 per second** for 634-696
KB/s, which is **~60 bytes per feed**. That is one feed per ConPTY read. The
local path reads the same ~60-byte chunks (`perf pty reads_per_s=24,841-29,304
kb_per_s=1,442-1,701`) but has no wire between the read and the parser.

## In plain terms

When a program prints a lot of text quickly, a Ghoztty pane falls behind - it
takes about twice as long to catch up as the terminal Windows ships with. The
surprising part is that the *same* Ghoztty is faster than that terminal when it
runs the program itself. The slowdown comes from the piece that keeps your
sessions alive across restarts: it hands the text over about sixty bytes at a
time, thousands of times a second, and that hand-off is where the time goes.
When this lands, a pane should be at least as quick as conhost whether or not
its session is being kept alive.

## What is already ruled out - do not re-investigate

All measured, all with numbers in T1458 and T1463:

- **The present.** `swapBuffers` costs 15-194 us; `swap_max_ms` was 0 across
  1,240 Debug samples and 0-1 across the optimized runs. The virtual/streamed
  display theory is dead.
- **The parser.** 0.06-0.07 us/byte on the shipped build shape; ~41 ms of a
  wall-clock second. Optimizing it cannot move this.
- **Renderer-mutex starvation.** Lock wait is 2.6-2.8% of the drain (0.08% in
  Debug). T1460 settled this.
- **The T111b priority handoff.** `yield_ms_per_s` = 0 in every sample on both
  builds.
- **Software OpenGL.** T1458 measured the loaded module list: NVIDIA
  `nvoglv64.dll`, Mesa fallback not loaded.

## Details

Where to look, in the order the evidence justifies:

1. **Measure the relay itself before changing it.** `perf agent_feed` today
   instruments what happens *after* the bytes arrive
   (`Remote.feedSliced` - parse, lock, yield). What has no instrument at all is
   the trip: agent ConPTY read -> agent-side framing -> named pipe -> app-side
   read -> `feedSliced`. Add the analog on that path (bytes and messages per
   second at each end, and the app-side wait) the way T1458 added `agent_feed`
   in the first place. Without it this task would be guessing between framing
   overhead, pipe round-trips, and a thread hop.
2. **Then look at batching.** ~60 bytes per feed at 10-22k feeds/s is the number
   to attack if step 1 confirms per-message cost dominates: the agent can
   coalesce consecutive ConPTY reads into one wire message the way the app
   already coalesces renders, bounded by a small latency budget so an
   interactive keystroke echo is not delayed to serve a bulk stream. Note that
   the LOCAL path reads the same ~60-byte chunks and is fast, which is the
   evidence that the read size is not itself the problem - the wire is.
3. **Only then consider the pipe.** Message-mode vs byte-mode, buffer sizes, and
   whether each feed costs a round-trip rather than a one-way write.

**Do not "fix" this by taking panes off the agent.** The agent holding the PTY
is what makes a session survive closing the window, which is a shipped feature
(`docs/claude/sessions.md`). The local-ConPTY column is a control that isolates
the cost, not a proposed configuration.

## Parity note

Standing symmetry rule. The relay is `src/remote/agent/` plus
`termio/Remote.zig`, which are shared, and the Mac seat has the same agent-held
session design - so a win from step 2 is likely to be cross-platform. Measure
there rather than assuming: file the Mac half if the same deficit shows up.

## What this task turned out to be, and where the rest went

Step 1 of the Details above - *measure the relay itself before changing it* -
is what this task delivered, and it moved the answer somewhere the plan did not
predict. The framing hypothesis in step 2 was **tested and disproved**, so the
throughput half of the work is now **T1465**, which starts from a measured cause
rather than a suspicion. T1458 waits on that instead.

## MEASURED 2026-09-08 - before and after, and what the instrument said

Both columns: `test\win32\pane-ingest-ab.ps1 -ReleaseSandbox`, 400,000 chunks
(7.7 MB as the workload counts it), ReleaseFast `x86_64-windows-gnu`, same box,
same background test desktop. The BEFORE column is `zig-out-t1463` - the build
T1463 measured - through the same harness, so the two differ only in this
task's code.

| 400k chunks | conhost | local ConPTY | agent-held, BEFORE | agent-held, AFTER |
|---|---|---|---|---|
| writer-clock elapsed | 5,915-6,078 ms | 5,542-5,985 ms | **12,528 ms** | **11,760 ms** |
| sustained ingest | ~1.3 MB/s | ~1.3-1.4 MB/s | **631 KB/s** | **672 KB/s** |
| agent / local | - | 1.00x | **2.25x** | **2.12x** |

So: ~6% better, and the deficit stands. What the instrument said is worth more
than the 6%:

```
perf holder_read  frames_per_s=8408  kb_per_s=600  bytes_per_frame=73  io_ms_per_s=0
perf holder_out   frames_per_s=8399  kb_per_s=600  bytes_per_frame=73  io_ms_per_s=55
perf holder_in    frames_per_s=8399  kb_per_s=600  bytes_per_frame=73  io_ms_per_s=890
perf relay_out    frames_per_s=8306  kb_per_s=664  bytes_per_frame=81  io_ms_per_s=54
```

Every leg carries the SAME ~8,400 messages a second and every leg's own pipe
syscalls cost under 7 us. `holder_in`'s 890 ms is a reader WAITING for bytes
that have not arrived, not an expensive read. And `holder_read` - the holder's
own ConPTY - delivers ~8,400 reads a second of 73 bytes where the app's local
ConPTY does ~19,000 of the identical size. **The source is the ceiling and the
relay merely follows it**, which is why merging messages could not help.

### What landed

- **`src/remote/agent/relay_perf.zig`** - the meter, the four call sites, and
  the file sink. The sink is not incidental: the app's stderr is redirected by
  whoever launched it, nothing redirects the agent's, and nothing at all
  launches a pty holder except the agent, so two thirds of this relay were
  unmeasurable in principle before it.
- **One pipe write per OUTPUT frame** in the holder (`pty_host.zig`), against
  three (header, offset header, payload) - the peer reassembles them into one
  message anyway.
- **The agent's writer coalesces contiguous DATA** on one channel and writes a
  whole batch with one `writeAll` (`server.zig`, `coalesceRun`). Backlog-only by
  construction: a batch of one - an idle pane's keystroke echo - takes exactly
  the path it took before, so there is no latency trade. `.data_repaint` never
  merges (it anchors rather than advances the stream) and a gap in `byte_offset`
  ends a run; both are unit tested.
- **ACKs batch to 64 KiB / 200 ms** (`pty_holder_child.zig`, `ackDue`), against
  one per read batch, which under a burst was 16,000 pipe writes a second from
  the agent's reader thread. Measured no throughput change; kept because it is
  strictly less work across two processes, and said plainly here rather than
  claimed as a win.
- **`test\win32\pane-ingest-ab.ps1`** - and it REPRODUCES the defect (2.25x on
  the pre-change build), which is the property that makes it a regression test.
  Three things it had to learn the hard way, all now comments in the script: a
  cold sandbox has no agent so the agent section silently measured the LOCAL
  path; a `+new-window` that lands during the app's own startup resolve gets a
  plain local shell; and `+list`'s `session_id` - the oracle for "is this pane
  really agent-held" - is null until the OPEN completes, so the pane has to be
  re-read after its shell answers.

### Tested and DISPROVED

Recorded so T1465 does not pay for them again:

- **Message count.** A 1 ms coalescing wait in the holder's writer halved the
  frame count (8,294 -> 4,378 frames/s at 146 bytes) and moved throughput not at
  all (626 KB/s against 594). Reverted; `pty_host.zig` carries the finding where
  the next person will look for it.
- **The ACK storm.** Batched as above; no throughput change.
