# T1194 - Prove the in-app update end to end against a real published win-v release (msiexec exit 0)

## Summary

T1178 proves the whole in-app update path except its last inch: msiexec
SUCCEEDING. `test\win32\update-apply.ps1` drives the applier end to end
against a package msiexec REJECTS, because a real install would replace the
user's installed Ghoztty and that is this repo's first non-negotiable. So
"the new version is actually on disk and running afterwards" is the one
claim the harness cannot make.

Close it at the next published `win-v` release: from a throwaway install
(a copy of the install directory, or a VM), let a real notification lead to
a real msiexec run, and check the version the app reports afterwards.

## In plain terms

The update works right up to the moment the installer runs; that final step
has only been tested with an installer that is designed to fail. Somebody
has to watch it succeed once, on a machine where being wrong costs nothing.

## Goals

- [x] A published `win-v` MSI can be installed on this box without touching the user's Ghoztty
- [x] The app finds, downloads and stages a real published package
- [x] msiexec is observed SUCCEEDING, and the version on disk moves
- [x] The whole walk is an acceptance script, wired to the staleness guard

## Validation criteria

- [x] A build older than the newest published win-v release offers the update, installs it, and reopens
      - `test\win32\update-real-msi.ps1` sections C/D: the app stages the
      published `win-v1.36.0` package while running the published
      `win-v1.35.0`, and the applier exits 0, which it only does when msiexec
      returned 0 AND the terminal relaunched.
- [x] `+version` afterwards reports the published version
      - section D: `1.35.0` before, `1.36.0` after, read from the installed
      `ghoztty.com`; and Apps & Features moves `26.8.3108` to `26.8.3110` with
      still exactly ONE registered product, so it was an upgrade rather than a
      second install.
- [x] Open terminal sessions survive it (the PTY holders were the whole reason for the rename-aside design)
      - section D: the app is closed but the agent and its per-session
      pty-host holder are deliberately left running, and every holder is still
      alive after msiexec finishes (`1 of 1`).
- [x] Nothing is left behind: no staged package, no `.old-<stamp>` image after the holders restart
      - section E: the staged package is deleted on success; the sidelined
      agent image is EXPECTED while a holder still has it mapped, and the next
      launch sweeps it and the applier copy.
- [x] Run somewhere that is NOT the user's daily-driver install
      - `scripts\msi-test-identity.ps1` rewrites each published package to a
      throwaway product (own ProductCode, UpgradeCode, INSTALLDIR, component
      GUIDs, registry key, Start Menu name), so the install lands in
      `%LOCALAPPDATA%\Programs\GhozttyT1194Test`. Section E measures the
      user's install directory across the whole run: file count and
      `ghoztty.exe` mtime unchanged.
