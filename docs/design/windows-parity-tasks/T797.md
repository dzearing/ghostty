# T797 - persistence-flag.ps1 is red: 4 acceptance launches state no session persistence

## Summary

Found while validating T748 (2026-08-12), and NOT caused by it - all four sites
are in files that change did not touch. `test\win32\persistence-flag.ps1` fails
its own sweep:

```
FAIL  A1 no launch leaves persistence unstated (undeclared: 4 of 180)
      declared by: literal=83, marker=62, =4, var=26, callers=5
```

The four:

- `agent-attach-refused.ps1:276` - `Start-OnTestDesktop -Exe $Exe -Arguments @()`,
  the section C control whose subject IS a live restore, so it wants persistence
  ON and needs a `# persistence:` marker (or the explicit `=true`) saying so.
- `url-scheme.ps1:359, 368, 381` - the three `ghoztty-debug://open/...`
  activation launches. An activation is answered and the process exits without
  opening a terminal, which is exactly the "forward-and-exit second instance"
  case T158 names as marker-worthy.

Neither looks like a real isolation bug; both look like the stated-intent marker
never being written. The value of fixing it is the sweep: a red audit cannot
tell anyone that a NEW launch forgot the flag, which is the failure T158 was
built to make impossible (T131/T155 both cost a turn to a script poisoned by the
previous one's restored panes).

## In plain terms

One of the self-checks that keeps the Windows test suite honest is currently
failing, so it has stopped being able to catch the mistake it exists to catch.
Nothing a user sees is broken; the risk is a future test quietly restoring the
previous test's windows and reporting nonsense.

## Validation criteria

- [ ] Each of the four sites either passes an explicit
      `--session-persistence=<bool>` or carries a `# persistence: <reason>`
      marker stating which it wants and why.
- [ ] `test\win32\persistence-flag.ps1` is ALL PASS again (it re-runs the sweep
      plus its own live control that the flag really stops a restore).
- [ ] The two edited scripts still pass: `agent-attach-refused.ps1`,
      `url-scheme.ps1`.
