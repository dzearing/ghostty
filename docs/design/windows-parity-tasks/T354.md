# T354 - win-v1.4.1 has no portable ZIP asset, so the site's ZIP link points at the release page

## Summary

The landing page's portable-ZIP link points at the **release page**
(`.../releases/tag/win-v1.4.1`) rather than at a `.zip` asset, because
`win-v1.4.1` — the only published Windows release — predates the portable
ZIP and contains the MSI alone. Verified: `gh api
repos/dzearing/ghoztty/releases/tags/win-v1.4.1` lists exactly one asset,
`Ghoztty-1.4.1-x64.msi`.

## Details

This is a **state** problem, not a code problem, and it self-heals: the
release-time rewrite (`dist/website/update-windows-links.py`, T39) writes
the direct asset URL `Ghoztty-portable-<version>-x64.zip` for whatever
release publishes next, and `release-windows.yml` has produced both
artifacts since T38.

Until then the link is honest rather than broken: a GitHub release page
always lists whatever assets exist, so it is never a 404 (asserted live,
E2 in `test/win32/website-windows-download.ps1`), and A6 asserts it points
at the *same* `win-v` release as the MSI card so the two can never drift
apart.

Two things to check when the next Windows release lands:

1. The rewrite promoted the link to the direct `.zip` asset URL — the
   `id="win-zip-link"` href rule replaces the whole href, so the tag-page
   form does not survive a rewrite. C3 asserts exactly this transition on
   a copy of the real page.
2. `test/win32/website-windows-download.ps1` A6 still passes. Its comment
   documents the tag-page form as *allowed*; once every published release
   carries a ZIP, that allowance could be tightened to require the direct
   asset URL.

*Validation:* after the next `win-v` release, the live page's
`win-zip-link` is a `.../releases/download/win-v<V>/Ghoztty-portable-<V>-x64.zip`
URL that answers 200, and the acceptance script is still ALL PASS.
