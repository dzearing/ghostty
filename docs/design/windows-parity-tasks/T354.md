# T354 - win-v1.4.1 has no portable ZIP asset, so the site's ZIP link points at the release page

## In plain terms

The download page offers Windows users a portable ZIP. Until today that link
did not hand them a file: it dropped them on the release page and left them to
find the ZIP themselves, because the only Windows release published back then
shipped the installer alone. Now that a Windows release with a portable ZIP
has gone out, the link is a real download again, and the check that watches it
no longer accepts the old landing-page form.

## Goals

- [x] Confirm the release-time rewrite promoted `win-zip-link` to a direct
      `.zip` asset URL on the live page
- [x] Confirm that URL answers 200
- [x] Confirm `test\win32\website-windows-download.ps1` is still ALL PASS
- [x] Tighten A6 so a tag-page link is a failure rather than an allowance

## Summary

The landing page's portable-ZIP link points at the **release page**
(`.../releases/tag/win-v1.4.1`) rather than at a `.zip` asset, because
`win-v1.4.1` — the only published Windows release — predates the portable
ZIP and contains the MSI alone. Verified: `gh api
repos/dzearing/ghoztty/releases/tags/win-v1.4.1` lists exactly one asset,
`Ghoztty-1.4.1-x64.msi`.

## Details

This is a **state** problem, not a code problem, and it self-heals: the
release-time rewrite (`dist/website/update-windows-links.py`, T39) writes
the direct asset URL `Ghoztty-portable-<version>-x64.zip` for whatever
release publishes next, and `release-windows.yml` has produced both
artifacts since T38.

Until then the link is honest rather than broken: a GitHub release page
always lists whatever assets exist, so it is never a 404 (asserted live,
E2 in `test/win32/website-windows-download.ps1`), and A6 asserts it points
at the *same* `win-v` release as the MSI card so the two can never drift
apart.

Two things to check when the next Windows release lands:

1. The rewrite promoted the link to the direct `.zip` asset URL — the
   `id="win-zip-link"` href rule replaces the whole href, so the tag-page
   form does not survive a rewrite. C3 asserts exactly this transition on
   a copy of the real page.
2. `test/win32/website-windows-download.ps1` A6 still passes. Its comment
   documents the tag-page form as *allowed*; once every published release
   carries a ZIP, that allowance could be tightened to require the direct
   asset URL.

*Validation:* after the next `win-v` release, the live page's
`win-zip-link` is a `.../releases/download/win-v<V>/Ghoztty-portable-<V>-x64.zip`
URL that answers 200, and the acceptance script is still ALL PASS.

## Resolution (2026-08-21)

`win-v1.34.0` published today with `Ghoztty-1.34.0-x64.msi` **and**
`Ghoztty-portable-1.34.0-x64.zip`, so both checks above came due at once.

1. The rewrite promoted the link: gh-pages `index.html` and the in-repo mirror
   both carry
   `https://github.com/dzearing/ghoztty/releases/download/win-v1.34.0/Ghoztty-portable-1.34.0-x64.zip`,
   and it answers 200.
2. The harness is ALL PASS, and A6's allowance is now **tightened** rather than
   left documented: the ZIP href must be a direct asset URL whose tag and
   filename versions agree (A6b) and whose release matches the MSI card (A6c).
   The tag-page form is a failure from here on, because every release since
   `win-v1.31.0` publishes the ZIP - the allowance could no longer protect a
   real release and could only hide a rewrite that ran without promoting the
   link. The else-branch fails both follow-up assertions explicitly, so an href
   that never matched cannot pass by comparing two empty strings.
