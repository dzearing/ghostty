# T855 - crash-catch and soak lane resolution can silently pick the OTHER lane's test binary (none/win32 both map to ghostty-test.exe, newest-mtime wins)

## In plain terms

The crash-diagnosis tools take a lane name ("none", "win32") and promise to run
or read that lane's test program. But the two lanes' programs share a filename,
and the tools just grab whichever was built most recently — so asking about one
lane can silently give you answers about the other. A crash investigation can
end up soaking, re-running, or reading dumps from the wrong program and
reporting confident numbers about the wrong thing.

## Goals

- [x] A lane name resolves to a binary that has been CHECKED to be that lane's
      full build, never to whichever build was linked last
- [x] The tools say which cache directory they picked and what it passed
- [x] A `-Dtest-filter` build can never stand in for the full lane
- [x] A dump is attributed to the build that actually died, and its symbols come
      from that build
- [x] Acceptance coverage that fails if any of the above regresses

## Summary

`$script:LANE_TEST_EXES` in `scripts/lib/CrashCatch.ps1` maps BOTH `none` and
`win32` to `ghostty-test.exe`, and `Get-NewestBuiltBinary` resolves purely by
newest `LastWriteTime` under `.zig-cache\o\`. Whenever the other lane built
more recently, `-Lane none` resolves to the win32 binary (and vice versa), with
nothing in the output saying so.

Observed during T504 triage (2026-08-15): `crash-catch.ps1 -Lane none` and a
standalone soak both ran the **win32** lane's `ghostty-test.exe` (it contains
`apprt.win32.*` tests; the none binary does not) because the win32 lane had
built last. The same defect affects `-Last` dump attribution: a WER dump for
`ghostty-test.exe` cannot be told apart by name, so a none-lane crash can be
"explained" with a win32-lane stack. A filtered `-Dtest-filter` build also
produces a `ghostty-test.exe` that then wins newest-mtime and gets soaked as
if it were the full lane.

Fix directions (implementer's call): resolve the binary through the lane's own
build manifest / floor-lane marker instead of newest-mtime; or verify the
picked exe's lane by probing for a lane-distinguishing embedded test name and
refuse ambiguity loudly; and have crash-catch print which cache dir it picked
plus the lane check it passed.

## What landed

`Resolve-LaneTestBinary` (scripts/lib/CrashCatch.ps1) replaces "newest wins".
Candidates are still gathered newest-first, but each one is READ before it is
accepted: zig embeds every test's fully-qualified name in the binary, so the
names answer both questions the resolution has to ask.

- **Which lane is this?** The win32 apprt is not in the none lane's module graph
  at all, so its GUI tests (`apprt.win32.Window.test.`, `.Scrollbar.`,
  `.IpcRegistry.`) are present in one binary and absent in the other. Measured
  on the two builds on disk at the time: present in the 96 MB win32 build,
  absent in the 89 MB none build. (Pure-logic win32 files like `layout_blobs`
  compile in BOTH lanes, which is why the markers are deliberately ones that
  touch HWNDs.)
- **Is this the whole lane?** `-Dtest-filter` leaves the excluded tests out of
  the binary, so six core names spread across `terminal`, `input`, `config`,
  `cli` and `datastruct` separate a full build from a filtered cut.

A candidate that fails is REJECTED WITH A REASON rather than skipped silently,
and `Write-LaneResolution` prints the cache directory that was picked plus the
check it passed — the thing that was missing when `-Lane none` ran the win32
binary during T504 triage. `Get-LaneTestBinary` now returns verified paths only,
so a caller that just counts results cannot end up on the wrong program.
`crash-catch.ps1`, `crash-databreak.ps1` and `test-binary-soak.ps1` all resolve
through it and exit 2, loudly, when nothing verifies.

Dump attribution is fixed at the same root: `Get-MinidumpMainModulePath`
(scripts/lib/CrashDump.ps1) reads MINIDUMP_MODULE_LIST and returns the full path
of the exe the dump was taken of — `.zig-cache\o\<hash>\ghostty-test.exe`, which
the `<exe>.<pid>.dmp` file name cannot carry. `crash-catch -Last/-FromDump`
prints it, REFUSES a dump whose build is positively another lane's, and takes
its symbols from that build's own directory instead of from whatever the lane
linked most recently.

Out of scope, deliberately: build MODE is not part of the identity, so a
ReleaseFast test build of the right lane still verifies. Nothing in the crash
tooling claims an optimize mode today; if that changes, the same marker table is
where it would go.

## Validation criteria

- [x] With the win32 binary newer on disk, `crash-catch.ps1 -Lane none`
      runs/reads the none lane's binary (or fails loudly), never the win32 one.
      Verified twice: against the REAL cache (the 20:23 win32 build was skipped
      and the 20:17 none build picked, with the reason printed), and by
      `test\win32\crash-stacks.ps1` section 7c, whose fixture repo writes the
      win32 binary last on purpose -- "lane none resolves past the newer win32
      binary", "crash-catch exits 2 rather than run the other lane".
- [x] Same for `test-binary-soak.ps1` standalone lane resolution.
      `test\win32\test-binary-soak.ps1` section 6: a repo holding only a
      win32-marked `ghostty-test.exe` makes `-Lane none` exit 2 saying the
      binary is another lane's, and soak NOTHING -- while `-Lane win32` against
      that same repo resolves it.
- [x] A filtered (`-Dtest-filter`) build cannot be silently picked as the full
      lane binary. crash-stacks 7c: a filtered fixture written newest is skipped
      for the full build, and its verdict reads "a partial build -- N expected
      test name(s) missing ... (a -Dtest-filter build is not the lane)".
- [x] Acceptance coverage in the crash tooling harness.
      `test\win32\crash-stacks.ps1` sections 7c (resolution) and 7d (dump
      attribution: a synthetic minidump proves the module reader, and a
      win32-lane dump under `-Lane none` is REFUSED while the same dump under
      its own lane is read). ALL PASS with the stamp taken; the soak, databreak
      and first-chance harnesses are green on the same code.
