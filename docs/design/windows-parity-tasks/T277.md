# T277 - toggle_window_float_on_top does not stick: a ghoztty window loses WS_EX_TOPMOST while a plain Win32 window keeps it

## Summary

Found while migrating `overlay-zorder.ps1` (T224). Its section E needs a
window that is LEGITIMATELY topmost - the `toggle_window_float_on_top` /
quick-terminal case the T142 heal is deliberately owner-relative to protect.
On this box a ghoztty window cannot be put in that state at all: neither the
product's own action nor an external `SetWindowPos(HWND_TOPMOST)` leaves
`WS_EX_TOPMOST` set, while a plain Win32 window in the SAME process, desktop
and harness keeps it in every condition.

So `float_window` (`--keybind=...=toggle_window_float_on_top`, the command
palette entry, and the quick terminal's own topmosting) is a user-visible
feature that does nothing. Section E of `overlay-zorder.ps1` currently SKIPs
with a pointer here rather than asserting against a state the app cannot
reach.

## Evidence (MEASURED on box 2026-08-01, debug build, background test desktop)

`toggle_window_float_on_top` bound at launch and pressed inside the pane, with
a control keybind to prove the keybind path works at all:

| step | result |
|---|---|
| `ctrl+shift+F8` = `new_window` (control) | windows 1 -> 2, so the keybind path WORKS |
| `ctrl+shift+F9` = `toggle_window_float_on_top` | `WS_EX_TOPMOST` False for 2000ms, z unchanged (1) |
| pressed a SECOND time (in case the first toggled it off) | still False for 1000ms |
| harness `SetWindowPos(HWND_TOPMOST)` on the same window | returns TRUE, bit False on the very next read |

Same harness, same desktop, subject = a plain Win32 window (`charmap.exe`,
class `#32770`), three conditions - no focus call, another window active, the
subject itself active:

| condition | result |
|---|---|
| inject topmost, no focus call first | topmost TRUE, z 1 -> 0, held 1000ms |
| focus the OTHER window, then inject | topmost TRUE, z 0, held |
| focus the SUBJECT, then inject | topmost TRUE, z 0, held |

So it is not the background desktop, and not the harness: **a ghoztty window
specifically does not keep the bit.** A ghoztty window sometimes DOES keep an
injected bit (measured: 3 of 5 conditions in the T224 probes), so the clearing
is conditional, not absolute - which is why it reads as flakiness.

The banner OVERLAY popup, by contrast, keeps an injected topmost reliably -
that is what `overlay-zorder.ps1` section B depends on, and it still passes.

## Prime suspect (NOT yet verified - do not fix from this)

MSDN, `SetWindowPos`: *"When a topmost window is made non-topmost, its owner
and its owned windows are also made non-topmost windows."* Every ghoztty
window OWNS popups (banner overlay, dim overlay, scrollbar, resize overlay),
so any code path that seats one of them after a NON-topmost window drags the
OWNER out of the topmost band with it. `healOverlayZOrder`
(`src/apprt/win32/win32.zig`) does exactly that at its reseat, and guards it
with an early return when the root is topmost - so the question is whether
some path reaches the reseat with a stale/racing view of the root's ex-style,
or whether another popup path (creation, show, DPI change) reorders without
`SWP_NOZORDER`.

`charmap` owns no popups, which fits.

## In plain terms

There is a way to tell a terminal window "stay in front of everything else" —
handy when you are watching a build in one window while working in another. It
worked if you picked it from the Window menu and did nothing at all if you
pressed the keyboard shortcut for it, which is the way anyone would actually
use it. It turned out Windows was accepting the request and quietly not doing
it; asking a second time works. Now the app checks that the window really did
move to the front instead of trusting the answer it got — and a status banner on
a pinned window no longer ends up hidden behind the window it belongs to.

## What this task must do

1. **Reproduce on the INTERACTIVE desktop first.** Everything above is on the
   background test desktop. If float-on-top works on the user's desktop, this
   is an environment-conditional defect and section E is a T207 option-B gap
   instead of a product bug. That check decides which.
2. Instrument the clearing: log every `SetWindowPos` on the window and its
   owned popups (insert-after + flags) around a float toggle, and identify the
   call that drops the bit.
3. Fix it, and make the fix hold with a live banner up (owned popups present)
   and with the quick terminal, which topmosts on its own path
   (`QuickTerminal.zig`).
4. Then restore `overlay-zorder.ps1` section E to a real assertion (it is
   written to skip loudly, so it will start asserting again as soon as the
   float sticks) and drop the skip note from its header.
