# T994 - The shared-index commit guard is armed only on the Windows box

## Summary

T948 landed the commit guard: a versioned `pre-commit` hook
(`scripts/githooks/pre-commit`, plain POSIX sh) that refuses a commit from a
session which is not holding the repo's advisory commit lock, plus
`scripts/git-commit-guard.ps1` which holds the lock, commits an explicit
pathspec, and reads the commit back.

What arms it is `core.hooksPath`, which is **local config**: it cannot arrive by
`git pull`, so every clone must run `install` once. On Windows that is covered —
`scripts\go-loop-exec.ps1 claim` re-asserts it at the top of every turn — and
nothing does the equivalent on the Mac seat.

The hook itself is portable (sh, LF-pinned in `.gitattributes`); the arming and
the commit helper are PowerShell. The Mac seat needs either pwsh, or a small
sh sibling of the `install` verb, whichever fits how that seat actually works.

## In plain terms

The safeguard that stops two assistant windows from committing over each other
is switched on automatically on the Windows machine and not on the Mac one. The
code for it is already there on both; on the Mac it is just never turned on.

## Validation criteria

- [ ] A Mac-seat clone has `core.hooksPath` pointed at `scripts/githooks`, set
      by something that runs on its own rather than by hand.
- [ ] The reproduction from T948 (one session holds, another commits) is
      refused on the Mac seat too.
- [ ] Whatever arms it is idempotent and never fatal — a repo that cannot take
      the config must still be workable.
