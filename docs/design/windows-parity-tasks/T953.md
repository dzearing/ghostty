# T953 - The release-artifacts guard can never clear on this box: its Docker sections always skip, and a skipped run does not stamp

## Summary

guard-due has held release-artifacts DUE since the workflow files last changed, and running the harness does not clear it: sections A/C/E/F pass, but section B needs Docker + the msitools-local image, Docker is deliberately kept down on this box (its WSL2 backend has buried the machine at 28 GB before), and release-artifacts.ps1 only stamps when failures AND skips are both zero. So every validate from here on needs -NoGuardDue, which is exactly the hatch that must stay rare or the gate stops meaning anything for the other 50 harnesses. Options worth weighing: stamp per-section (each section covers the files it actually asserts, so the pure sections can clear their own coverage while B stays due); or split the Docker-only assertions into their own guard row that is explicitly box-conditional; or teach guard-due a per-row 'needs docker' flag that reports UNAVAILABLE rather than DUE. Do NOT fix it by starting Docker in the harness.

## In plain terms

Nothing a user can see. This is a broken smoke alarm in the workshop: one of
the automatic "has anybody tested this since it changed?" checks got stuck in
the alarm state and cannot be reset on this machine, so every piece of work now
has to walk past a red light and switch the whole alarm system off to get by. A
red light nobody can turn off is one everybody stops reading.
