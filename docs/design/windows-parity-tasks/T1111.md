# T1111 - The tab strip's '...' button reports itself as minimize to Windows

## In plain terms

The little '...' button on the tab strip tells Windows it is the minimize button. Windows then treats it as one, which can make it behave oddly with window snapping and the right-click window menu instead of opening the overflow it is supposed to open.

## Summary

`test\win32\tab-strip-autohide.ps1` scored `1 FAILURE(S) (14 passed)` in the T1094 sweep:

```
FAIL  the '...' button hit-tests as HTSYSMENU, Windows' own code for the window menu (got 8)
```

`8` is `HTMINBUTTON`; the expected value is `HTSYSMENU` (`3`). So the non-client hit test is returning the minimize-button code for the region occupied by the overflow button.

Note that `caption-bar.ps1` asserts the OPPOSITE mapping and PASSES it (`hit test over the '...' -> HTSYSMENU (got 3)`, `hit test over minimize -> HTMINBUTTON (got 8)`). Two scripts measuring the same button disagree, which means the geometry differs between them - most likely the autohide state changes where the button sits, and the hit test is computed against the non-autohidden layout. That is the thing to chase: the bug is probably positional, not a wrong constant.

## Where

- `src/apprt/win32/` - `WM_NCHITTEST` for the caption/tab-strip band
- `test/win32/tab-strip-autohide.ps1`, `test/win32/caption-bar.ps1` (the passing counter-example)

## Goals

- [ ] Reproduce with the tab strip in its autohidden state and compare the button rects against the hit-test regions.
- [ ] Fix the hit test to follow the actual laid-out position in both states.
- [ ] Add the autohidden state to whichever script does not currently cover it, so the two cannot disagree again.

## Validation criteria

- [ ] the '...' button hit-tests as HTSYSMENU in BOTH the autohidden and normal tab-strip states
- [ ] `test\win32\tab-strip-autohide.ps1` is ALL PASS
