# T366 - T56b: win32 remote-reconnect DRIVER - link observer, off-thread redial, ATTACH-then-DETACH swap

## Summary

Split out of T56 (WP-D1 remote reconnect on win32), 2026-08-02. The moving
half: drive T365's policy against a real transport.

## Details

Today a cross-machine window whose agent dies degrades to a clean dead pane
(`ipc-relay.ps1` sections 6/7 prove no hang and no crash) and stays that way.
The driver to build:

- A link-state OBSERVER on `window.remote_dialed.conn()`. There is no
  notification centre here; the win32 analog is the App's existing local-agent
  poller (`agent_recovery.zig` + its `App.zig` watcher, `poll_ms = 250`).
  Rebind on every swap so a dead connection stops being listened to.
- The redial loop OFF the GUI thread: `tcp_dial` / `relay_dial` per the
  window's `RemoteMachine`, bounded handshake (`waitHandshake` already takes a
  deadline), backoff from T365's schedule, generation cancellation.
- **ATTACH-then-DETACH swap ordering**: re-ATTACH the recorded session id on
  the NEW connection before tearing the old one down, then swap
  `window.remote_dialed` and re-point every surface. Getting the order wrong
  ends the session it is trying to save (the `sessionSpared` invariant in
  `agent_recovery.zig` is the same hazard).
- No orphan threads: the redial loop must be joinable and must not outlive
  the window (`Window.deinit` already tears `remote_dialed` down).
- Local-agent windows are explicitly OUT of scope — they recover through
  `agent_recovery.zig` / in-place rebuild, exactly as Mac excludes
  `isLocalMachine` from this ladder.

*Validation:* T368's acceptance script, plus whatever of the swap ordering can
be asserted headlessly.
