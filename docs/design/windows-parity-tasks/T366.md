# T366 - T56b: win32 remote-reconnect DRIVER - link observer, off-thread redial, ATTACH-then-DETACH swap

## Summary

Split out of T56 (WP-D1 remote reconnect on win32), 2026-08-02. The moving
half: drive T365's policy against a real transport.

## Details

Today a cross-machine window whose agent dies degrades to a clean dead pane
(`ipc-relay.ps1` sections 6/7 prove no hang and no crash) and stays that way.
The driver to build:

- A link-state OBSERVER on `window.remote_dialed.conn()`. There is no
  notification centre here; the win32 analog is the App's existing local-agent
  poller (`agent_recovery.zig` + its `App.zig` watcher, `poll_ms = 250`).
  Rebind on every swap so a dead connection stops being listened to.
- The redial loop OFF the GUI thread: `tcp_dial` / `relay_dial` per the
  window's `RemoteMachine`, bounded handshake (`waitHandshake` already takes a
  deadline), backoff from T365's schedule, generation cancellation.
- **ATTACH-then-DETACH swap ordering**: re-ATTACH the recorded session id on
  the NEW connection before tearing the old one down, then swap
  `window.remote_dialed` and re-point every surface. Getting the order wrong
  ends the session it is trying to save (the `sessionSpared` invariant in
  `agent_recovery.zig` is the same hazard).
- No orphan threads: the redial loop must be joinable and must not outlive
  the window (`Window.deinit` already tears `remote_dialed` down).
- Local-agent windows are explicitly OUT of scope — they recover through
  `agent_recovery.zig` / in-place rebuild, exactly as Mac excludes
  `isLocalMachine` from this ladder.

*Validation:* T368's acceptance script, plus whatever of the swap ordering can
be asserted headlessly.

## In plain terms

If you have a Ghoztty window running a shell on another machine and that
machine's connection drops — the network blips, the far end restarts — the
window on Windows goes quiet and stays quiet. Nothing you type does anything,
nothing tells you why, and the only way out is to close the window and lose
whatever was running. On the Mac the same window quietly re-dials and picks the
session straight back up. After this, Windows does too: the window notices the
drop, retries on its own for about thirty seconds, and when it gets through it
reconnects your panes to the very same programs that were running, still
running. If it cannot get through it keeps trying slowly in the background, so a
machine that comes back an hour later brings your window back with it.

## Goals

- [x] The window NOTICES its connection dropping (link observer on the
      transport, re-bound on every swap)
- [x] It re-dials on its own, off the UI thread, with the backoff and budget
      T365 decided
- [x] A successful re-dial re-ATTACHes the same sessions, so the panes come
      back with their programs still running
- [x] The old connection is only torn down AFTER that, never before
- [x] A dial that outlives its window cannot touch it, and no thread is left
      wedging teardown

## Evidence

New file `src/apprt/win32/RemoteReconnect.zig` — the driver. Four steps, each
where it is for a reason:

1. **Notice.** `install()` puts a state handler on `window.remote_dialed.conn()`;
   it runs on the connection's READER thread under `state_mutex`, so it does one
   thing — `PostMessageW(WM_APP_REMOTE_LINK)` — and every decision happens on the
   GUI thread. Re-installed on every swap, and cleared on both window teardown
   paths, so a retired transport stops being listened to.
2. **Drive.** A 250ms poller on `App.msg_hwnd` (timer id 6; `agent_recovery`'s
   cadence and reason), armed ONLY while some remote window is mid-ladder,
   waiting on a background re-dial, or has a dial outstanding. It folds the
   transport state through T365's `classify`/`onLinkChange` and runs whatever has
   come due.
3. **Dial.** A DETACHED worker per attempt: `tcp_dial`/`relay_dial` per the
   window's `RemoteMachine`, the transport's own bounded handshake, then
   `requestSessions` — the liveness probe rides the worker so the GUI never
   blocks on a machine that may be gone. Relay credentials resolve on the GUI
   thread (the account store is its) and travel in the request.
4. **Swap.** `applySwap` captures the live topology, points `window.remote_dialed`
   at the fresh transport, rebuilds every terminal leaf ATTACHed on it, and only
   then retires the old one.

Decisions worth naming:

- **The worker holds no window pointer.** It carries `Window.layout_uuid` (T338)
  and a generation; the reply resolves both on the GUI thread. A window that
  closed mid-dial cannot be written through — the reply frees the connection it
  brought. The reply also lands on the APP's message-only window, not the
  terminal's, because `DestroyWindow` discards a window's queued messages and a
  discarded reply would leak a whole connection (T295/T318).
- **A replaced transport is RETIRED, never destroyed.** `Surface.remote_conn` and
  each pane's `termio.Remote` hold the connection borrowed and nothing refcounts
  it. It is shut down off the GUI thread (`shutdown` joins four threads; inline
  on the GUI thread is the T229 wedge shape) and freed at window teardown, after
  `cleanupAllSurfaces`. Exactly `LocalAgent.retire`'s bargain.
- **A swap that attached nothing keeps the old transport.** `SwapGuard.abandoned`
  — the dead old connection is still the only thing that knows the session, and
  the ladder counts the attempt as failed. This forced a fix one level down:
  `rebuildTabRootInPlace` used to propagate a subtree-walk error AFTER the root
  had already been replaced, reporting "nothing happened" while a live surface
  rode the new transport — which would have had this caller free it.
- **A failed BACKGROUND re-dial does not restart the fast ladder.** Exhausted is
  sticky: re-arm the 45s re-dial, keep the truthful `disconnected(self_healable)`
  state, rather than telling the pill "reconnecting 1/5" every 45 seconds.
- **`dead` really is terminal.** The transport FSM only reaches it via
  `onSessionGone` (eviction / session gone); a socket dying lands in
  `reconnecting`. So the ladder cannot be killed by the very drop it is there to
  survive.

Shared rather than copied, in `App.zig`:

- `captureWindow` / `captureOneWindow` split out of `captureSessionLayout`, whose
  walk deliberately SKIPS cross-machine windows — the only ones this needs.
- `rebuildWindowInPlace` / `rebuildTabInPlace` now take a `RestoreTransport`
  instead of a bare local-agent connection, and return how many terminal leaves
  re-attached. One walk now serves the local crash recovery (T145) and this swap.
- `AttachProbe.fromRoster` / `.owns`, because the probe happens on the worker.

`Window` gains `reconnect: RemoteReconnect.State` and `setRemoteDialed()` — every
site that installs a dial goes through it, so none can forget the observer.

`manualReconnect(app, window)` is the seam T367's Reconnect button calls; it has
no caller yet by design.
