# T1134 - fork-identity C4 decays with every main intake: the reproduce-from-fork-point baseline is a moving target nobody moves

## In plain terms

One of the automated checks has started failing for a reason that is not a bug:
it counts how many files a rewriting script can reproduce from scratch, and that
number naturally goes down every time we pull real changes in from the main
project. Nobody updates the count, so the check is now permanently red - and a
check that is always red is one people learn to ignore.

## Summary

`test\win32\fork-identity.ps1` section C measures the fork-identity overlay
honestly: it checks the 52 U-files out at the fork point `063ac3ecc`, runs the
overlay, and counts how many come back byte-identical to HEAD. `$ReproBaseline
= 28` asserts the count does not regress, which is the right shape for catching
a rule that quietly stopped matching.

It is not the right shape for the number it is measuring. Every real edit that
lands on a U-file - ours or one arriving through the daily main intake - makes
that file irreproducible from a 2026-05-07 tree, so the count only ever falls.
Measured 2026-08-22 during T1097:

```
FAIL C4 at least 28 of the U-files reproduce from the fork point
        reproduced=27 baseline=28
```

The cause is benign and identified: T1073's main merge (`8cc25838a`,
2026-08-21) added 45 lines to `HACKING.md`, a U-file. Nothing about the overlay
regressed - `residual` lists 25 files, all of them real work.

## Where

- `test/win32/fork-identity.ps1` - `$ReproBaseline` (line ~73), section C
- `scripts/guard-due.ps1` - the `fork-identity` guard row

## The work

Separate the two questions section C currently asks with one number:

1. **Did a rule regress?** That is what the baseline is for, and it should be
   measured against a set that does not decay - e.g. count reproduction only
   over U-files unchanged since the last stamp, or assert the overlay's rule
   HIT COUNT rather than the byte-identical file count.
2. **How far has the tree drifted from the fork point?** Worth reporting, but as
   a number in the output, not an assertion - or as an assertion with an
   explicitly dated baseline that the daily intake is expected to move.

Whatever the shape, the guard has to be able to be green on a tree that is
absorbing main, because that is the tree we always have.
