# T176 - Machine chooser: per-row management menu + relay Rename/Remove (T173 split 2/2)

## Summary

The behavioral half of T173: the machine chooser's management `...` menu and
the two relay account operations behind it. Mac's `managementActions`
(`MachineChooserView.swift:1114-1123`) is:

| Machine kind | Menu |
|---|---|
| direct-TCP | `Host Settings...` |
| relay | `Host Settings...` - sep - `Rename...` - sep - `Remove from Account...` (destructive) |

Nothing is ever greyed; items are conditionally absent. The Local row has no
menu at all. The same menu is reachable two ways: the `...` button in the
detail header, and right-click on a master-list row.

`Host Settings...` is **T174's** (the per-host defaults store does not exist on
Windows yet). This task lands the menu plumbing plus `Rename...` and
`Remove from Account...`.

## Details

Needed pieces:

- A pure menu model (its own small module, per the no-mega-files rule) that
  maps a chooser row to menu items, unit-tested. `TrackPopupMenuEx` with
  `TPM_RETURNCMD` following `src/apprt/win32/context_menu.zig` +
  `Surface.openContextMenu` (dark menus are already app-wide via `DarkMode`).
- Relay HTTP verbs in `src/remote/relay_directory.zig`, matching Mac's
  `RelayDirectoryClient`: `PATCH v1/client/devices/<id>` with `{"name": "..."}`
  (rename, returns the device) and `DELETE v1/client/devices/<id>` (remove).
  `src/remote/http_client.zig` currently exposes only GET/POST helpers - add a
  method-generic authenticated request rather than one helper per verb.
- A modal text prompt for `Rename...`. Follow the modeless-with-owner-disabled
  pattern the app already uses (`RenameDialog.zig`, `MachineChooser.zig`) and
  route its keys through the App message loop - do NOT spin a nested
  `GetMessage` loop inside the chooser (T48's deadlock class).

  **Superseded when built** (see Outcome): the prompt is `ConfirmDialog` with
  an optional field, which DOES run a nested pump. That was a deliberate
  reversal, not an oversight - reasoning recorded below.
- `Remove from Account...` confirms first (Mac: *"This deletes the device from
  the relay and revokes its credential..."*, buttons Remove / Cancel,
  destructive), then deletes and refreshes the list in place. A 404 still drops
  the local row.
- Failures surface in the chooser's status strip, not silently.

## Validation

- Unit tests: the pure menu model per row kind; URL/body construction and
  status classification for rename/delete.
- `test/win32/ipc-machine-chooser.ps1` (or a sibling script) drives the `...`
  button and a right-click against the fake relay used by the existing test:
  menu appears with the expected items, `Rename...` PATCHes and the row
  relabels, `Remove from Account...` confirms + DELETEs and the row disappears.
- Both `zig build test` lanes + `zig build test-agent` green; P1-P3 ALL PASS.

## Outcome

Built. New pure module `src/apprt/win32/chooser_menu.zig` (item model per row
kind + `newName` trimming); relay verbs `renameDevice`/`deleteDevice` in
`relay_directory.zig` over a new method-generic `http_client.requestAuth`;
`chooser_layout` gained the `menu_btn` slot; `MachineChooser` grew the `...`
button, the right-click/`VK_APPS` path, and the two action handlers.

### The nested-loop question, reversed on purpose

The task file said to build the rename prompt modeless and route its keys
through the App loop, and NOT to spin a nested `GetMessage`. That was written
before checking what the app already had. `ConfirmDialog.zig` (T80) is exactly
this dialog minus the field, and it already runs a nested pump - its own
comments cite the T48 analysis, which found the deadlock was a
**non-pumping** `Condition.wait()` inside a WndProc, not nesting as such. A
pump that pumps is the safe case; `MessageBoxW` does the same thing
internally.

Weighed against that, a modeless prompt would need a second routing hook in
`App.run` and a completion callback, for a dialog that must hand a string back
to a modal parent synchronously. So `Rename...` is `ConfirmDialog` with an
optional single-line field (`Options.input` + `prompt()`), which is also what
Mac does - `NSAlert` with an `accessoryView`, the same alert class as the
remove confirmation. One dialog class, one pump, one dark palette.

Two behaviors fall out of having a field: it takes initial focus with its seed
text selected, and it forces the Enter default onto OK (`default_cancel and
!has_input`) - a prompt's Enter must commit. The destructive remove
confirmation keeps `MB_DEFBUTTON2`, and the script asserts that Enter on it
CANCELS with no DELETE sent.

### Re-anchoring: found by the test, not by reading

After a successful rename the chooser re-lists, and `refilter` selects row 0 -
so renaming a machine threw the selection back to **Local**, taking the detail
pane and the `...` button with it. The script found this by accident: with the
rename fixed, the whole remove block stopped running because the button was
no longer visible. Mac has `reanchorSelection()` for exactly this.
`reloadDevices` now copies the selected device id (the refetch frees the arena
it points into) and re-selects it by id after the refilter - by ID, not index,
because a refetch may reorder. Pure helper `rowForDeviceId`, unit-tested
including the reorder and stale-index cases.

### Host Settings is absent, not greyed

`chooser_menu.State.host_settings` is a bool, `HOST_SETTINGS_AVAILABLE = false`
in `MachineChooser`. T174 flips it and adds a handler; nothing about the menu
reshapes. `hasMenu` is derived from `build` rather than from the row kind, so
a row whose only item is gated away gets no menu at all instead of an empty
popup - and `build` never emits a leading separator when the first group is
absent. Both are unit-tested.

### Evidence

`test/win32/chooser-menu.ps1` (new): a stateful fake relay that actually
renames and deletes, so the chooser's re-list shows the consequence. ALL PASS
(33) x3. It reads the live popup's items through `MN_GETHMENU` +
`GetMenuStringW` - asserting the exact list `Rename... | sep | Remove from
Account...`, and that `Host Settings...` is ABSENT - drives both entry points
(a real click on the button, a real right-click on the row), and proves the
wire from the relay's side (method, path, and the PATCH body).

One test-harness trap worth keeping: **a cross-process `SetWindowTextW` on an
EDIT is not a way to type into it.** It updated USER32's cached window text -
so the script's `GetWindowTextW` read back the new name and passed - while the
control's own buffer kept the old one, and the app (reading in-process, via
`WM_GETTEXT`) saw the OLD name, making the rename a silent no-op that looked
like a product bug. The script now types real keystrokes and reads the field
back with `WM_GETTEXT`. That also makes the assertion honest: it proves the
seed is pre-selected, because typing replaces it.

Standing floor: both `zig build test` lanes + `zig build test-agent` exit 0;
P1-P3 ALL PASS; `ipc-machine-chooser.ps1` and `relay-account.ps1` (the two
scripts that share this dialog) re-run green.
