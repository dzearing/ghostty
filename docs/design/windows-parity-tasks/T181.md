# T181 - +read transiently fails on a pane that +list already reports

## Summary

Filed 2026-07-30 by T133. Building `test/win32/reset-context.ps1` hit this
twice: a pane that `+list --json` already reports as a leaf (with an id, a
title and a pid) can still answer `+read --name=<id>` with

    ghoztty.exe : failed to read terminal content from '<pane-id>'

for a short window right after its window is created — the window is
registered before its terminal is attached/readable. It is transient (a retry
200ms later succeeds), which is precisely what makes it dangerous: a caller
that reads once gets an EMPTY tail, and "the pane has no output" reads exactly
like a product verdict rather than a race. The harness now retries an empty
read (an unidentified single-assertion flake in one of six runs is the likely
same cause), but the CLI should not need that.

**Work:** decide the contract and make it true. Either `+list` should not
report a pane before `+read` can serve it, or `+read` should wait briefly for
the surface to become readable instead of failing (and, either way, its error
should distinguish "no such pane" from "pane not readable yet" — today's one
message covers both). Check the same window on `+send-keys`, which the
`/reset-context` helper aims at a freshly created pane in exactly this state.

**Validation:** a script that creates a window and immediately (no sleep)
`+read`s the pane id returned by `+list --json`, run enough times to catch the
race; pre-fix it must reproduce the failure.
