# T181 - +read transiently fails on a pane that +list already reports

## In plain terms

Asking Ghoztty what a terminal has printed used to answer with an error when the
terminal had printed nothing yet — and every terminal looks like that for the
first moment after you open it, plus permanently if whatever is running in it is
quiet. The error was word-for-word the one you get for a terminal that does not
exist, so a script or an AI agent watching a pane could decide the pane was
broken, or that a command had produced no output, when the truth was "it is new
and has not spoken yet".

Afterwards, reading a pane that has printed nothing succeeds and prints nothing
— the way `tail` of an empty file does — and each remaining failure says which
different thing went wrong.

## Goals

- [x] Reproduce it deterministically on the box, not as a timing race
- [x] An empty pane reads back as success with empty output
- [x] Each remaining `+read` failure names a DIFFERENT state
- [x] `+send-keys` at a freshly created pane gets the same treatment
- [x] Pure unit tests in the `none` lane + an on-box acceptance script
- [x] The macOS half filed, since this seat cannot compile Swift (T481)

## Summary

Filed 2026-07-30 by T133. Building `test/win32/reset-context.ps1` hit this
twice: a pane that `+list --json` already reports as a leaf (with an id, a
title and a pid) can still answer `+read --name=<id>` with

    ghoztty.exe : failed to read terminal content from '<pane-id>'

for a short window right after its window is created — the window is
registered before its terminal is attached/readable. It is transient (a retry
200ms later succeeds), which is precisely what makes it dangerous: a caller
that reads once gets an EMPTY tail, and "the pane has no output" reads exactly
like a product verdict rather than a race. The harness now retries an empty
read (an unidentified single-assertion flake in one of six runs is the likely
same cause), but the CLI should not need that.

**Work:** decide the contract and make it true. Either `+list` should not
report a pane before `+read` can serve it, or `+read` should wait briefly for
the surface to become readable instead of failing (and, either way, its error
should distinguish "no such pane" from "pane not readable yet" — today's one
message covers both). Check the same window on `+send-keys`, which the
`/reset-context` helper aims at a freshly created pane in exactly this state.

**Validation:** a script that creates a window and immediately (no sleep)
`+read`s the pane id returned by `+list --json`, run enough times to catch the
race; pre-fix it must reproduce the failure.

## Root cause (MEASURED 2026-08-04, debug build)

It is not a registration race and nothing needs to wait. **The pane is fully
readable the whole time; its SCREEN is empty**, and `+read` reported an empty
screen as a failure.

`handleRead` in `src/apprt/win32/IpcHandlers.zig` ended with

```zig
const result = full[start..];
if (result.len == 0)
    return try errorResponse(ctx.alloc, "failed to read terminal content from '{s}'", .{name});
```

and `Screen.selectionString` emits nothing at all for a screen with no content,
so a blank pane took that branch. That makes the failure *transient by
coincidence*: a CLI process launch is normally long enough for `cmd.exe` to
paint its prompt, which is why the "create, `+list`, `+read`, no sleep" loop the
task asked for does **not** reproduce it on this box (6/6 rounds pass pre-fix)
while the same defect is trivially reproducible on demand:

```
+new-window --target=silent -e cmd /c "timeout /t 20 /nobreak > nul"
+list --json  ->  pane id 8B3FF204-..., pid 4604   (a real, live child)
+read --name=<id> --lines=5  ->  exit 1, "failed to read terminal content"  (x3, 400ms apart)
```

That also explains T133's flake and is the same symptom T278 saw for a
different reason (a pane the agent refused a shell to is blank forever), which
is exactly why the message had to stop covering several unrelated states.

Two smaller findings from the same read of the code:

- `getBottomRight(.screen)` can never return null (`PageList.zig`), so the
  *other* `failed to read terminal content` branch — `dump == null` — is
  reachable only on a real serialization failure. It keeps the message.
- `core_surface_ready` false covers **two** states: a surface being torn down,
  and one whose `core_surface.init` never completed (both flags are set together
  at the end of init, so `core_surface_initialized` separates them). `+read` and
  `+send-keys` both reported the second as "no longer alive".

## What landed (2026-08-04)

**An empty pane is an answer.** `+read` returns success with empty text. `tail`
of an empty file exits 0; so does this. (Contract call recorded as **D13** — the
alternative was a distinct nonzero error for "empty", which keeps every
exit-code-only caller treating a brand-new pane as broken.)

**Every remaining failure names a distinct state**, so no two can be confused:

| state | message |
| --- | --- |
| unknown name | `pane '<n>' not found in registry` |
| pane gone | `pane '<n>' is no longer alive` |
| viewer pane | `<n> is a viewer pane, not a terminal` |
| terminal never came up | `pane '<n>' is not readable: its terminal never finished starting up` |
| screen could not be serialized | `failed to read terminal content from '<n>'` |

`+send-keys` gets the same liveness split (`is not writable: its terminal never
finished starting up`) because the `/reset-context` helper aims it at a freshly
created pane.

**The "last N lines" rule is now shared, pure and tested.**
`src/apprt/ipc/read_tail.zig` (new) holds it, `apprt.ipc.read_tail` exposes it,
and its tests run in the `-Dapp-runtime=none` lane — including the empty case,
which is the contract. The Swift handler applies the same rule with
`components(separatedBy:)` + `suffix(n)`, so the two now agree by description
rather than by coincidence.

One knock-on, deliberate: `+send-keys --when-idle` polls with
`read.queryPaneText` and used to `catch return` (send immediately) when the read
FAILED. A blank pane now answers "" instead, so it takes the normal
unchanged-across-1s path — one second slower at a brand-new pane, and no longer
printing an IPC error to stderr on the way.

**No wait, no retry, nowhere.** The task's other candidate fix — have `+read`
wait for the surface — would have been wrong twice over: there is nothing to
wait for (the pane is readable), and IPC handlers run ON the GUI thread, so a
handler that waits for the GUI thread to make progress cannot get it.

### macOS

`IPCServer.swift` has its own copy of the `resultText.isEmpty` branch and the
same hazard. Filed as **T481** (`seat: mac`) rather than edited blind: the Swift
`guard let surface … else { return }` above it funnels into the same empty
string, so deleting the branch alone would swallow a real failure into a silent
empty success. That is a restructure worth compiling and running, which this
seat cannot do.

## Evidence (MEASURED on box 2026-08-04, debug build)

`test/win32/ipc-read-race.ps1` (new) runs on a background desktop and covers
arm A (a silent pane reads back empty), arms B/C (the create→`+list`→`+read`/
`+send-keys` race as filed, no sleep), and controls D/E/F (a pane with real
output still reads; an unknown name still says `not found in registry`; a
viewer pane still says it is a viewer).

Run against the pre-fix behaviour — the fix reverted with the one branch put
back, rebuilt — arm A reproduces and the controls hold:

```
== A: a silent pane is readable, and reads back empty
  PASS A +list reports the silent pane
  PASS A the silent pane has a real child (pid != 0)
  FAIL A +read of a silent pane exits 0 (was: failed to read terminal content)
  FAIL A +read of a silent pane says nothing rather than failing
...
2 FAILURE(S)
```

| lane / script | result |
| --- | --- |
| `test\win32\ipc-read-race.ps1` | ALL PASS (13 checks) |
| `scripts\floor-lane.ps1 -Lane all` | `ALL LANES PASS` (none 288s, win32 298s, agent 293s) |
| `ipc-p1` / `ipc-p2` / `ipc-p3` | ALL PASS |

New unit tests in the `none` lane (`src/apprt/ipc/read_tail.zig`): empty input
gives empty output rather than an error, a lone `"\n"` likewise, fewer lines
than asked for returns everything, interior blank lines count as lines, a single
line with no newline, and `lines == 0` means everything.
