# T513 - Shell detection never strips .exe for bash/nu/zsh/fish, so git-bash and nushell panes named by Windows path get no integration

## Summary

`detectShell` (`src/termio/shell_integration.zig:146`) compares the argv0
basename exactly (`bash`, `nu`, `zsh`, `fish`, `elvish`) and only strips a
`.exe` extension — case-insensitively — inside the pwsh/powershell block
(T27). On Windows a shell is routinely named WITH the extension or by full
path: `--shell=bash.exe`, `--shell="C:\Program Files\Git\bin\bash.exe"`,
`--shell=nu.exe`, and the `command-shell` config takes the same forms. All of
those return null from detection today, so a git-bash or nushell pane gets no
shell integration (no OSC 7 cwd, no prompt marks) even though T151 made the
agent path deliver the argv rewrite end-to-end.

Fix shape: hoist the `.exe`-strip + lowercase normalization above ALL the
name checks (Windows filenames are case-insensitive, so `Bash.EXE` should
detect too). Keep the Darwin `/bin/bash` special case keyed on the original
arg0. Unit tests in the same file cover the table; extend them with
`bash.exe`, `nu.exe`, a full `C:\...\bash.exe` path, and a mixed-case name.

## In plain terms

If you ask for a Git Bash or Nushell pane the way Windows users naturally
write it — `bash.exe`, or the full path to the program — the terminal doesn't
recognize the shell, so the quality-of-life features (the terminal knowing
your current folder, prompt navigation) silently don't turn on. Asking for
`bash` with no extension works. The fix makes both spellings work.

## Goals

- [x] `bash.exe`, `nu.exe`, `zsh.exe`, `fish.exe` (any case) detect their shells
- [x] A full Windows path to the shell (`C:\...\bash.exe`) detects too
- [x] An agent-backed git-bash pane actually receives the integration rewrite end-to-end
