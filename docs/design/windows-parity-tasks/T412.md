# T412 - Measure the WP-D3 snapshot capture cost on high-frequency layout syncs (window drag/resize)

## In plain terms

Every time you finish dragging or resizing a Ghoztty window, the terminal writes
down what all your panes look like so a crash or a reboot can bring them back.
Doing that means reading each pane's screen, and reading a screen means waiting
for the pane to stop printing for a moment. With eight panes all busy that wait
was a full second - so letting go of a window edge froze the window for about a
second, and it happened again on a timer while anything was printing.

Now the drag just says "the shape moved, the content did not" and reuses the
screens it already has. The same gesture costs a few milliseconds. Nothing about
what a restore brings back changes: the screens are still refreshed on their own
schedule, and the last write before the app quits is still a fresh one.

## Goals

- [x] Measure one `captureSessionLayout` at 2 / 3 / 8 panes, idle and flooded,
      with the capture, write and blob-push halves separated
- [x] Answer whether a sustained drag stutters at 8 panes
- [x] Make the snapshot conditional on the TRIGGER rather than dropping it
- [x] Leave the measurement standing as a harness, not a one-off number

## Summary

T109 made `App.captureSessionLayout` do a per-pane structured VT dump (up to 600
rows, under the pane's renderer mutex) on EVERY layout sync, on the UI thread.

**The premise this card was filed on was already stale.** It assumed a window
drag re-armed the 250 ms debounce over and over; T220 had moved the frame path
off that debounce months earlier, so a drag is ONE capture, taken synchronously
at `WM_EXITSIZEMOVE` (the manifest is written before the placement memory, so a
kill between the two cannot strand the frame). The question narrowed rather than
went away: one synchronous whole-app capture at the end of every gesture, on the
thread that has to repaint.

**Measured** (`test\win32\layout-capture-cost.ps1`, this box, Debug build, six
real drag gestures per arm):

| arm | max sync | mean | of which capture | snapshot |
|---|---|---|---|---|
| 2 panes idle | 13.9 ms | 7.6 ms | 1.4 ms | 15 KB |
| 3 panes idle | 15.4 ms | 8.5 ms | 2.7 ms | 22 KB |
| 3 panes flooded | 45.5 ms | 27.9 ms | 37.6 ms | 74 KB |
| 8 panes idle | 19.1 ms | 11.6 ms | 10.2 ms | 86 KB |
| **8 panes flooded** | **1001 ms** | **593 ms** | **991 ms** | 151 KB |

So: over budget, badly. And almost none of it is the dump - the flooded arm
encodes twice the bytes of the idle one and costs ninety-seven times as much. It
is lock wait: `sessionSnapshot` takes `renderer_state.mutex` and the IO thread
holds it while feeding output.

**Fixed** the way this card proposed: the snapshot is now conditional on the
TRIGGER. `App.ScreenCapture` is `.fresh` or `.reuse`; a `.reuse` capture carries
`Surface.last_snapshot` forward instead of re-dumping.

- `.reuse` - the drag/frame sync (T220) and the debounced topology sync (tab,
  split, rename, banner, tab colour, divider drag). The topology moved, the
  content did not.
- `.fresh` - the T922 refresh, whose whole job is the screens and which waits
  for the panes to go quiet before it asks, and the quit / `WM_ENDSESSION`
  flush, which is the authoritative last write.

The card's own warning is respected: the snapshot is never DROPPED on a frame
sync, only carried. A pane with nothing cached - one created since the last full
capture - still captures fresh, so reuse can never mean "restores blank".

**After**: 8 panes flooded, max 8.7 ms per sync, 0.14 ms of it capture. Every
arm is inside the 16.67 ms frame budget.

## Details

- `src\apprt\win32\layout_cost.zig` (new) - the `Sample` and the frame budget,
  unit-tested in the win32 lane.
- `src\apprt\win32\App.zig` - `reportLayoutCost` emits one machine-readable line
  per sync at **debug** (stderr in a Debug build: the measurement channel) and
  at **info** only when the sync missed the frame budget, so a field report of
  "dragging hitches" has the number in the log the user already has and a
  healthy app writes nothing. Plus `ScreenCapture` and the reuse path.
- `src\apprt\win32\Surface.zig` - `last_snapshot` / `last_snapshot_offset`,
  gpa-owned, freed with the pane.
- `src\apprt\win32\session_layout.zig` - `File.paneCount`, so a cost sample can
  be read against the pane count it was paid at.
- `test\win32\layout-capture-cost.ps1` (new) plus a `guard-due.ps1` row, so the
  measurement is re-run whenever the code it covers moves.

What is left is filed as **T1311**: the T922 refresh's 30-second ceiling means a
pane that never goes quiet still buys one `.fresh` capture at the flooded price
every 30 s. That ceiling is not removable (a permanently-busy pane must still get
its screen recorded for D78), so the fix has to be on the cost side.

## Validation

A timing harness in the none/win32 lane cannot reach this (it needs live panes),
so the deliverable is the on-box script, kept.

## Validation criteria

- [x] An on-box script drives N panes, forces M syncs through the real
      `WM_ENTERSIZEMOVE`/`WM_EXITSIZEMOVE` path, and reports per-sync
      milliseconds - `test\win32\layout-capture-cost.ps1`, sections B/C/D.
- [x] The flooded-pane arm is measured, and it is a real flood rather than a
      second idle arm: the control reads a pane back and requires the flood's
      own text on its screen (C1/D3). That matters more after the fix than
      before it, because a reused snapshot's byte count no longer says anything
      about how busy the panes were.
- [x] Every arm's worst sync is inside the frame budget (section E), and the
      budget is READ from `layout_cost.zig` rather than hand-copied.
- [x] No drag-triggered sync re-dumps the screens (section F) - the fix stated
      as a measurement rather than a claim.
- [x] The instrumentation is proved wired rather than assumed: an arm with zero
      samples fails (B1), and the sample's pane count must match the live one
      (B2, D1).
- [x] Floor green (`floor-lane.ps1 -Lane all`), plus every harness `guard-due`
      named as due over these edits.
