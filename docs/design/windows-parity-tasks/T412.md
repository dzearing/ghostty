# T412 - Measure the WP-D3 snapshot capture cost on high-frequency layout syncs (window drag/resize)

## Summary

T109 made `App.captureSessionLayout` do a per-pane structured VT dump (up to 600
rows, under the pane's renderer mutex) on EVERY layout sync. Most sync triggers
are rare - add/close a tab or split, rename, tab color. One is not: a **window
frame change** marks the layout dirty, so dragging or resizing a window re-arms
the 250 ms debounce over and over. Nothing measured says that is a problem;
nothing measured says it is not, and the standing bar is explicitly "reliable
and fast under long-context use" (T53).

## Details

What to measure, on box, at the sizes the user actually runs:

- Wall time of one `captureSessionLayout` with N agent-backed panes (N = 1, 3,
  8), split into the VT dump and the rest - and the same with the panes
  FLOODED. The dump takes `renderer_state.mutex`, which the IO thread holds
  while feeding output, so a flooded pane is the worst case, not an idle one.
- Whether a sustained window drag produces a visible stutter at 8 panes.

If it costs more than a frame, the cheap fix is to make the snapshot conditional
on the TRIGGER rather than on the capture: a frame-only sync does not need a
fresh screen (the topology moved, the content did not), so `markLayoutDirty`
could carry a "content unchanged" hint and `captureLeaf` reuse the leaf's
previous snapshot. Do NOT simply drop the snapshot on frame syncs - the last
write before an abrupt kill decides what the next restore paints, and a drag is
as likely to be the last write as anything else.

## Validation

A timing harness in the none/win32 lane cannot reach this (it needs live panes),
so: an on-box script that drives N panes, forces M syncs, and reports the
per-sync milliseconds, with the flooded-pane arm as the interesting one. Then
either "measured X ms, under budget, closing" or the conditional-capture fix
with the same script as its before/after.
