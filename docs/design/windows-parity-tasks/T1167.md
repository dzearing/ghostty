# T1167 - A pane ingests output at about half the rate the plain Windows console does

## In plain terms

Dumping a big file or a long build log into a Ghoztty pane takes about twice as
long as dumping the same thing into a plain Windows console window. Nothing
looks broken — the text scrolls the whole time and the pane never falls behind
itself — it just finishes later than it needs to. Whether anyone would notice
without a stopwatch is the open question; the number is what makes it worth
looking at.

## Summary

Measured under T1142 with the same 4.5 MB payload (`type` of 500000 numbered
lines), release builds throughout:

| host | wall clock | rate |
|---|---|---|
| conhost (control) | 2.34 s | ~1.92 MB/s |
| Ghoztty pane, agent-backed | 4.52 s | ~1.0 MB/s |
| Ghoztty pane, local (`termio.Exec`) | 7.17 s | ~0.63 MB/s end-to-end, ~1.0 MB/s steady |

The app is never *behind* — its terminal state reaches the last line in the same
100 ms poll sample the child finishes in — so this is a throughput gap, not the
lag T1142 was filed for. The child is paced by the pipeline, which is correct
terminal behavior; the question is why the pipeline paces it at half conhost's
rate.

## Where to look

T1142's ingest-path map turned up these, none of them yet attributed to a
measured share of the gap — that attribution is the first job here, since fixing
an un-measured candidate is how a perf task turns into churn:

- `src/pty.zig:417` — `CreatePipe(&pty.out_pipe, &pty.out_pipe_pty, null, 0)`
  takes the **system-default 4 KiB** pipe buffer on the ConPTY output side, so
  conhost can never stage more than ~4 KiB and every reader above sees ~4 KiB
  granularity. This one is upstream of everything else in the list.
- `src/remote/agent/pty_child.zig:293` — the agent's ConPTY reader has a 64 KiB
  buffer but **no `PeekNamedPipe` top-up**, unlike Exec's win32 reader
  (`src/termio/Exec.zig:1578`), so it emits one DATA frame per ~4 KiB read.
- `src/remote/pipe_stream.zig:177` — `CreateEventExW` + `CloseHandle` per read
  AND per write, i.e. four kernel handle operations per frame across the two
  processes.
- `src/remote/client_mux.zig:209` — every frame is parsed and then
  **re-serialized** purely to sort it onto a lane, and copied into a `Fifo`
  (`:257`) that is an unbounded `ArrayList` compacting only when fully drained.
- `src/remote/connection.zig:3604` — parses every frame a **second** time out of
  that Fifo, 16 KiB at a time.
- `src/remote/agent/session.zig:1322` — `onChildOutput` holds a **store-wide**
  mutex across record + bridge, so all sessions on the box serialize their
  output through it.
- `src/termio/Remote.zig:1863` — one renderer-mutex cycle, one `SwitchToThread`
  and one IOCP post per 4 KiB `max_parse_slice`, with a 2 ms handoff budget
  (`src/renderer/State.zig:65`) whenever the renderer is contending. Deliberate
  (T111/T114/T115 bought GUI latency with it) — so any change here must re-run
  those harnesses, not just this one.

The local path is SLOWER than the agent path in the measurement above, which
rules out "the agent transport is the gap" as the whole story and points at the
shared core.
