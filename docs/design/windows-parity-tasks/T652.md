# T652 - Sweep the restore scripts for the "attached is not alive" gap

## In plain terms

The automated checks that prove your windows come back after a restart all
check that the panes *look* right. None of them checked that the panes still
*work* — that you can type in one and get an answer. A pane that came back as
a frozen picture passed every one of them. Two of those checks now type into
the pane; the rest still do not.

## Goals

- [x] Every script that restores or re-attaches a pane proves the pane is live,
      not merely painted.
- [x] Each new arm is teeth-checked: it must be seen to go red when the pane
      produces no new output.
- [x] The rule is written down somewhere a future restore test will find it.

## Summary

Landed with T532's investigation, and the reason this task exists:

- `test/win32/session-reattach.ps1` — **F8b** added (full-ring re-attach).
- `test/win32/session-snapshot-reattach.ps1` — **C6d** added (the WP-D3 delta
  path: `offset > 0` with a grid snapshot).

Both plant a marker AFTER the restore and require it to come back, which
exercises input reaching the child and the child's output reaching the pane.
Both were teeth-checked by sending a different token than the one matched: the
arm goes red and every other assertion in the script stays green.

Still unswept, and all of them restore or re-attach panes:

- `test/win32/chooser-restore-all.ps1` and `chooser-restore-all-remote.ps1`
- `test/win32/session-persistence.ps1`
- `test/win32/session-crash-recover.ps1`
- `test/win32/session-relaunch.ps1` and `session-relaunch-notify.ps1`
- `test/win32/viewer-restore.ps1` (viewer panes have no PTY — the equivalent
  claim is that the page still responds, e.g. a reload or a navigation lands)
- `test/win32/window-name-restore.ps1`

## The sweep (2026-08-09)

The probe was written three times in three scripts before this task, so it is
now written once: `test/win32/lib/PaneLiveness.ps1`. `Test-PaneLive` types
`echo Space <token> Enter` at a target and polls `+read` until the token comes
back **twice** — once as the echoed input line, once as the command's output.
The two-hit rule is T230's, and it is the sharp part: one occurrence is only
keystrokes landing in a line editor, which a pane whose child is gone can still
show you. (The separator is the `Space` KEY, not a space in a quoted argument:
adjacent text positionals merge with no separator, so `echo` and the token as
two arguments arrive as `echoGLIVE…`.)

`GHOZTTY_TEST_LIVENESS_BREAK=1` makes every arm match a token that was never
sent, so the teeth-check is a switch anyone can flip rather than a hand edit
nobody repeats.

| Script | Arm |
|---|---|
| `window-name-restore.ps1` | B4 — a restored window answers |
| `session-crash-recover.ps1` | C5/C6 — one pane in EACH recovered window |
| `session-persistence.ps1` | B.10 (the other window, every cycle); `Test-RoundTrip` delegated to the shared oracle |
| `session-relaunch.ps1` | A12 (auto RELAUNCH), B8 (keystroke RELAUNCH) |
| `session-relaunch-notify.ps1` | E5b (banner restore); `Test-PaneResponsive` delegated; section B carries the why-not comment |
| `chooser-restore-all.ps1` | the recovered named window answers |
| `chooser-restore-all-remote.ps1` | K — across the relay: keystroke → agent → child → back |
| `viewer-restore.ps1` | H2 (the re-attached terminal) + L1–L3/J7 (the viewer half) |

Two arms are deliberately NOT the echo probe:

- `session-relaunch-notify.ps1` section B (auto policy) — those panes are not
  at a prompt, they are running the respawned command. B2/B3 are the liveness
  claim in the form the policy allows (marker pings a frozen pane cannot
  produce), and the input direction is covered on the same restore path by A9,
  C4 and E5b.
- Viewer panes have no shell. `viewer-restore.ps1` gains a raw-TCP page server
  whose every response carries its own ordinal in `<title>`; `+list --json`
  reports a viewer leaf's title, so the restore must report a HIGHER ordinal
  than before the app died (it re-navigated) and a following `+reload` must
  raise it again (fetched from origin, ran, reported back). A pane holding a
  last painted frame keeps its number.

## Details

The generalisable defect is that a **replayed** pane and a **live** pane are
byte-identical to every assertion that reads the screen. `session-snapshot-
reattach.ps1`'s C5 is the sharpest example: it proves the painted bytes match
the recorded snapshot byte for byte — which a frozen pane proves equally well.
An oracle that a broken build satisfies is not an oracle.

The cheap arm is the one used twice already: `+send-keys` a run-unique
space-free token, then poll `+read` until it appears, whitespace-stripped. It
costs one CLI round trip and a few seconds of polling, and it fails on exactly
the symptom the user reported.

Where a pane has no shell (viewer restore), the equivalent is any interaction
that requires the pane to still be servicing its own message loop rather than
holding a last painted frame.
