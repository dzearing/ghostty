# T826 - Viewer: right-clicking a link offers Ghoztty's link menu on any page

## Summary

The second half of main 18acc4f6f: a right-click on a link in ANY viewer (not just the bundled template) shows the same menu a banner link shows - open, open in browser, copy - by re-anchoring the banner link opener on a link-anchor protocol instead of a surface view. On Windows a viewer link has no context menu at all, so there is no way to copy a link target or force it into the browser.

## In plain terms

Right-click a link in a viewer pane today and nothing useful happens - there is
no way to copy where it points, open it in your browser, or put it in a pane
beside this one. Terminal banner links have offered exactly that menu for months;
the pages a viewer shows did not. After this, a right-click on any link - in a
rendered doc, in a local HTML page, on a website - offers the same short menu,
and it acts on the real thing behind the link: copying a link to a doc gives you
the file's path, not an internal address that means nothing outside Ghoztty.

## Goals

- [x] Right-clicking a link in any viewer page shows Ghoztty's link menu
- [x] The menu is the SAME one banner links show - same rows, order and verbs
- [x] Links to documents and local pages act on the file, not the internal URL
- [x] `mailto:`, `javascript:` and same-page `#anchor` links keep the page's own menu
- [x] A `ghoztty://` link offers Focus in Ghoztty, and nothing that "opens" it

      link resolves to its file - including one that does not exist, which still
      opens a menu on the path the link meant.

## Where it landed

- `src/viewer/links.js` - the shared decider, taken from main verbatim.
- `src/apprt/win32/viewer_bridge.zig` - embeds it in the injected blob after the
  shim, and parses the `linkMenu` message it posts.
- `src/apprt/win32/viewer_content.zig` - `linkMenuTarget`: what a right-clicked
  href IS (command / web / file URL / viewer-relative / page-relative / none).
- `src/apprt/win32/ViewerPane.zig` - `armLinkMenu` resolves it, a posted
  `WM_APP_VIEWER_LINK_MENU` pops the menu one hop out of the web view's callback
  (it is modal), and `performLinkMenuAction` runs the verb on the viewer's own
  plumbing. Rows, order and ids come from `banner_link.zig` unchanged.

## Known divergence

A link inside an IFRAME keeps WebView2's own menu: a subframe's `postMessage`
goes to `ICoreWebView2Frame`'s event rather than the web view's, so running the
script there would suppress the page's menu with nowhere to send the href. Filed
as T928.
