# T210 - A slash-command resume prompt is mangled on the way into the pane, so /reset-context silently never fires

## Summary

Hit for real on 2026-07-30 delivering T204+T206. The turn ended the way go.md
step 7 mandates: `launch-upgrade.ps1` with a resume prompt that begins
`/reset-context <verification instructions> Then read go.md and go`.

Everything reported success. `LAUNCH OK`, `exe swapped`, `UPGRADE OK (reused
claude pid=37708 ...)`, and the delivery itself was genuinely correct
(`+version` = `28b76b6c5` = HEAD). **But the context was never reset.** What
arrived in the pane was the TAIL of the prompt as plain prose:

> ` the DWM/PrintWindow capture question first, it decides the shape of the
> whole task. T208 (stale delivery) and T209 (on-box pixel assertions for the
> tab strip, blocked on T207) come after.read go.md and go`

The leading `/reset-context` and most of the body were gone, the remainder was
submitted as an ordinary message, and the session carried on at ~250k tokens -
exactly the runaway context the go.md CONTEXT RULE exists to prevent.

The upgrade log had already flagged it, in a line written to be ignorable:

```
RESUME-REUSE SENT: prompt '...' sent to pane ... but was not seen in the pane
tail (the TUI may have consumed it); no second session was started
```

That branch treats "the echo check failed" as benign - "the TUI may have
consumed it". Here it was the actual symptom, and the run still ended
`UPGRADE OK`.

## Why this matters more than it looks

This is the third variant of the same failure class the loop keeps hitting:
**a delivery step that reports OK while its real effect did not happen.**
T200 fixed it at the launch boundary, T208 files it at the build boundary,
and this is the same defect at the *resume* boundary. The cost here is
specific: the loop's one context-hygiene mechanism is the reset, and a reset
that silently no-ops turns every subsequent turn into a longer one.

## Suspects, in order

1. **Slash-command mangling through `+send-keys`.** Already a known trap on
   this box: a `/`-prefixed argument sent from a Bash-tool shell is rewritten
   by MSYS path conversion (`/clear` arrived as
   `C:/Program Files/Git/clear`). `upgrade-ghoztty-windows.ps1` sends from
   PowerShell, so MSYS is not obviously in play - but the prompt is passed as
   a single positional argument to `& $oldExe +send-keys ... $prompt Enter`,
   and it is 1222 chars with quotes, `%LOCALAPPDATA%`, `+`, `-` and `"` in
   it. Any one of those could be the culprit; find out WHICH rather than
   guessing.
2. **Length.** 1222 characters typed into a TUI prompt box. The surviving
   fragment is the tail, which is consistent with a buffer that dropped the
   head, or with the TUI's own paste/submit handling truncating.
3. **`--when-idle` racing the submit.** The send used
   `--when-idle --idle-timeout=60` against a session that was mid-turn. If
   the pane accepted input while Claude Code was still rendering, a leading
   `/` may have been eaten by the slash-command autocomplete popup rather
   than starting a command.

## Deliverables

1. Reproduce deterministically: send prompts of increasing length, with and
   without a leading `/`, with and without quotes/percent signs, into a live
   pane and diff what arrives. This is a pure `+send-keys` question and needs
   no GUI focus, so it is NOT blocked on T207.
2. Fix the transport for the case that fails. If long prompts are the issue,
   the resume should type a SHORT prompt (`/reset-context read go.md and go`)
   and leave the long verification text in a file the fresh session reads -
   the prompt does not need to carry the whole briefing.
3. **Make the echo check a gate, not a shrug.** `RESUME-REUSE SENT ... but was
   not seen in the pane tail` must not end in `UPGRADE OK`. Either assert the
   prompt arrived intact (compare the pane tail against what was sent) and
   fail loudly, or retry. The whole point of T200's wrapper was that a
   silent-success delivery step is the expensive kind.
4. Consider whether a resume prompt should be allowed to start with a slash
   command at all, given the loop depends on exactly that.

## Validation

- Negative control: with the fix in place, a deliberately mangled/short send
  must FAIL the run rather than log `UPGRADE OK`.
- Positive control: a real `launch-upgrade.ps1` cycle whose resume prompt is
  `/reset-context read go.md and go` demonstrably clears the session - check
  the pane shows a fresh context, not just that the text appeared.
- Extend `test/win32/upgrade-no-fork.ps1` (it already drives the resume paths
  with stand-in processes) or `ipc-when-idle.ps1`.

## ROOT CAUSE (measured on the box, 2026-08-01)

**Suspect 1 was right, and it is narrower and nastier than "slash-command
mangling": PowerShell 5.1 does not escape an embedded `"` when it builds a
native command line.** MSYS was never involved. The prompt travelled fine
through every hop T200 hardened and died at the LAST one — the positional
`+send-keys` argument.

Argv oracle (`python -c` printing `sys.argv`, called the same way the upgrade
script calls `ghoztty.exe`):

| payload | what the child received |
|---|---|
| `pct %LOCALAPPDATA% and plus + and dash -Flag` | intact |
| `single 'quotes' inside` | intact |
| `has a " quote in it` | **child never ran** |
| `a "quoted phrase" mid string` | **child never ran** |
| `trailing backslash dir\` | **child never ran** |

The "child never ran" rows are the loud half. The quiet half is what the child
DOES receive, and the probe printed it by accident — the mangled argv made
python write its output to a file named from a fragment, in the repo root:

```
has a " quote in it   ->  argv = ['has a ', 'quote', 'in', 'it', <outpath>]
a "quoted phrase" ...  ->  argv = ['a quoted', 'phrase mid string', <outpath>]
```

One argument became four, and the spaces between them are GONE. Hand that to
`resolveArgument`, which joins positional arguments with no separator, and
`has a " quote in it` arrives as `has a quoteinit`. That is the field
signature — `come after.read go.md and go` — reproduced from first principles.

End to end through `+send-keys` into a pane running a raw-console capture
(`[Console]::ReadKey($true)`, so nothing echoes or normalizes):

```
sent 130: /reset-context settle the "DWM/PrintWindow" capture question first, it decides the shape of the whole task. Then read go.md and go
got  128: /reset-context settle the DWM/PrintWindow capture question first, it decides the shape of the whole task. Then read go.md and go
```

Both quotes gone, exit 0, no diagnostic. With several quoted runs the same send
exits 1. And because `resolveArgument` concatenates positional arguments with
**no separator**, a re-tokenized prompt arrives as run-together prose — which is
exactly the field signature, `come after.read go.md and go`.

**Suspect 2 (length) is DEAD.** Byte-exact capture at four sizes, all `exact=True`:

```
L1 sent=1222  got=1222  exact=True
L2 sent=2500  got=2500  exact=True
L3 sent=5000  got=5000  exact=True
L4 sent=10000 got=10000 exact=True
```

So the tracker's "keep resume prompts SHORT" mitigation was aimed at the wrong
suspect; it is withdrawn. **Suspect 3 (`--when-idle` racing the submit) is
unnecessary as an explanation** and there is no evidence for it: the fragment
arrived AND was submitted, so input was accepted normally.

**Deliverable 4 answered: yes, a resume prompt may start with a slash command.**
A leading `/reset-context ` transports byte-exact at every length tested. The
loop depends on it and nothing about it is fragile.

## What shipped (2026-08-01)

- **`src/cli/send_keys.zig` — new `--keys-file=<path>`.** The file's bytes are
  sent **verbatim**: no key notation, no `\n` escape processing, no shell in the
  way. It keeps its POSITION among the positional arguments, so
  `--keys-file=p.txt Enter` sends the file and then the CR — order matters, or
  the prompt is submitted before its own text arrives. Zero protocol change: the
  CLI still resolves everything into one `--keys=` IPC argument. An unreadable
  path names itself and exits 1 rather than sending nothing.
  `resolveArguments` was extracted so the ordering and the file handling are
  unit-testable.
- **`scripts/loop-session.ps1` — `New-LoopPromptFile`, `Get-LoopPromptNeedle`,
  `Test-LoopPromptArrived`.** One copy of the transport and one copy of the
  comparison, dot-sourced by the upgrade script, the watchdog and
  `go-loop-exec.ps1`. Box glyphs are matched by RANGE, never by literal
  character: PS 5.1 mojibakes non-ASCII in a BOM-less script (T241).
- **`scripts/upgrade-ghoztty-windows.ps1` — the prompt goes by file, and the
  echo check is a GATE.** It now types the prompt, VERIFIES it in the pane, and
  only then sends Enter. Checking before the submit is what makes the gate
  trustworthy: `/reset-context` clears the pane on purpose, so a post-submit
  check would fail a *correct* delivery. A prompt that did not arrive is not
  submitted (Escape clears the box, so no fragment concatenates with the
  watchdog's next nudge) and the run exits 1 — `RESUME-REUSE SENT` is gone.
- **The comparison is whitespace-collapsed on BOTH sides.** The old check did an
  exact `IndexOf` against the pane tail, which a wrapped input box can never
  satisfy — so it failed on healthy deliveries too, which is *why* it had been
  written as a shrug rather than a gate. Fixing the oracle is what made the gate
  possible.
- **`go-loop-watchdog.ps1` and `go-loop-exec.ps1`** send their prompt/note the
  same way. Neither had failed yet (their text has no quotes), but the watchdog
  is the loop's safety net and `-ResumePrompt` is caller text.
- **A RUNTIME capability probe, `Test-LoopKeysFileSupported` /
  `New-LoopSendKeysText`** — and it is load-bearing on day one, not
  future-proofing. These scripts drive whichever ghoztty is **installed**, and an
  exe that predates the flag treats `--keys-file=C:\...` as ordinary TEXT and
  types the PATH into the pane: the T241 failure, recreated by its own fix, in
  the watchdog that exists to catch it. Verified at the moment of writing:
  ```
  installed +96fbe40c7 : +send-keys --help does NOT mention keys-file
  built     (this tree): MATCH keys-file
  ```
  So the transport is probed per exe (`+send-keys --help` exits 0 and touches no
  pane, so it is side-effect-free), cached, and falls back to argv with a
  `WARNING:` line naming the degradation. Same rule as CLAUDE.md's app/agent
  HELLO handshake: detect capability at runtime, never at compile time, and
  degrade rather than corrupt. The reuse path's exe is the one the swap just
  installed so it normally has the flag — but "normally" is precisely what T208
  is about.

## Evidence (2026-08-01)

**`test/win32/ipc-send-keys-fidelity.ps1` (new) ALL PASS, 19 assertions, exit
0.** Byte-exact capture, not a screen read, and **every keys-file case has a
positional-argument negative control with the same payload** — live, in the same
run:

```
1  field payload byte-exact via --keys-file        130 of 130
2  NEGATIVE CONTROL: same payload via argv         128 of 130  <- quotes gone
3  quotes/%VARS%/+/-Flag/trailing backslash         97 of 97
4  NEGATIVE CONTROL: same payload via argv          91 of 97
5  1400 chars with quotes                         1400 of 1400
6  file bytes then CR, in that order                PASS
7  unreadable --keys-file exits nonzero + names it  PASS
8  the gate's own oracle, against a real pane tail  PASS
```

Without the controls a green run could not tell "the fix works" from "this
payload was never broken" — which is exactly how the length theory survived.

**`test/win32/upgrade-no-fork.ps1` ALL PASS, 126 assertions, exit 0.** New
section **M** (25 pure cases: the file transport, the wrapped-tail oracle with
its pre-fix `IndexOf` oracle, the mangled field text failing the check, and the
capability probe in both directions — a supporting exe gets the file, a
non-answering one falls back to argv and reports itself degraded) and
new section **E** — the end-to-end gate control. E puts the pane in the exact
state the field failure produced: a swallow process
(`[Console]::ReadKey($true)`, consumes without echoing) so the send succeeds and
the text never appears. The script must exit nonzero, log `RESUME-REUSE FAIL:
the prompt did not arrive intact`, and **not** log `UPGRADE OK (` — that last
one is the assert the whole task is for. Section B's E2E prompt is now HOSTILE
(`T210-REUSE settle the "capture" question, ...`); the old
`T138-REUSE-PROMPT` was a single quoteless token that argv could not break, so
the E2E was blind to the defect that mattered.

Two process notes from building it. **E4 first passed for the wrong reason**: the
new FAIL message contained the words "NOT UPGRADE OK", which a grep for
`UPGRADE OK` matched — the message no longer spells the success tag, and the
assert keys on `UPGRADE OK (`. **M14 did the same in reverse**: a grep for the
removed shrug's prose matched the comment documenting its removal, so it keys on
the log TAG instead.

**Standing floor:** `zig build test -Dapp-runtime=none` exit 0, `zig build test
-Dapp-runtime=win32` exit 0, `zig build test-agent` exit 0, P1/P2/P3
ACCEPTANCE: ALL PASS, `go-loop-guard.ps1` ALL PASS.

## Still open

The positive control T210 asked for — a real `launch-upgrade.ps1` cycle whose
resume prompt demonstrably clears the session — is observed by the NEXT
delivery, not by this turn; section E's swallow-pane control is the automated
stand-in for its failing half. Two follow-ups: **T279** (the same argv hazard at
every other PowerShell → CLI call site: `+rename --title`, `+set-banner`,
`--command`) and **T280** (`ConvertTo-SendKeysLiteral` is now redundant — the
escaper existed only because the text was on argv).

## Priority note

Rank alongside T208 - they are the same class and the same delivery pipeline.
T207 still comes first (it is what unblocks the visual tasks and it is what
the user asked for by name), but T210 should be taken before any further
long-prompt resumes, because until it is fixed every turn boundary silently
risks skipping its reset.
