### The regression guards exist and are GREEN today

`test\win32\session-reattach.ps1`, run 2026-08-03 — **34 passed / 2 failed**,
and the 2 are the documented T223 reds (F10/F11), not these anomalies:

```

PASS F3 manifest holds the full 2-window / 3-session layout pre-quit
PASS F4 the agent kept all 3 sessions alive after the app died
```

A4/B6 are anomaly (a)'s oracle, F3 is anomaly (b)'s, and **F7 is the leak's** —
a restore that re-OPENed instead of attaching would leave 6 sessions alive, not
3, and F7 counts them. So the mechanism cannot return silently.

### Mechanism, for the record

A leaf with a null `session_id` is not re-attachable, so restore OPENs a fresh
session for that pane; local panes are opened `pinned`, and `pinned` is exactly
what exempts a session from the agent's idle-TTL reaper
(`server.zig`: *"Pin persistent local sessions so the idle-TTL reaper never
evicts them while orphaned"*). Each such restore therefore ratchets the live
count up by one per pane, permanently. T89f2's bounded retry
(`LAYOUT_SYNC_RETRY_MS` 400 ms × `LAYOUT_SYNC_MAX_RETRIES` 40 ≈ 16 s, `App.zig`)
closed the source; F7 keeps it closed.

### Prune: deliberately NOT done

T108 says "close leaked ids". Declined, and this is the reasoning, not an
omission: there is one orphan, its child is a live shell sitting in the repo
directory, and it is **resumable** from the chooser roster (T318/T320) — killing
it would destroy a session the user may still want, to tidy a number that is no
longer growing. The runaway condition the instruction was written for is gone.
The unbounded-accumulation problem itself is real but general, and now belongs
to its own task (below), not to a one-off prune.

degrading to one stale field rather than to breakage.
