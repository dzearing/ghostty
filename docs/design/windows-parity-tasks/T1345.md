# T1345 - The app paints heavier than the Mac build because every piece of chrome is its own layered popup

## In plain terms

Everything the app draws on top of the terminal - the banner strip, the dimming
over unfocused panes, the scrollbar, the read-only badge, the key-state pill -
is its own separate little window that Windows has to composite and that
repaints itself independently. The Mac draws all of that into one layer tree.
That difference is the likeliest reason the whole app feels heavier, and it is
a redesign rather than a fix.


## Background

Split out of T1324. `WS_EX_LAYERED` popups are created by `BannerOverlay`,
`DimOverlay`, `Scrollbar`, `KeyStateIndicator`, `ReadonlyBadge`,
`RegionSelector`, `ViewerPane`, `App` and `Window`. The design is deliberate -
a plain child window cannot reliably sit above the OpenGL surface, which is why
the chrome works at all - but a layout change fans out into many window
repositions and many independent GDI paints.

The repositions are already batched (`BeginDeferWindowPos` in `Window.zig`,
T1031). The **paints** are not, and every one of these popups is re-glued on
every layout pass through `updateDimOverlays`.

## Why this is behind T1343

Nothing here should be attempted until T1343 has numbers. If the drag cost is
dominated by the per-surface frame wait, this fan-out may be a small term and a
large rewrite. If it is not, this is where the time goes. Deciding that from a
reading of the code is exactly the guessing T1324 was filed to stop.

## Candidate directions, all unproven

- Batch the overlay paints the way the repositions already are.
- Ask whether the overlays that do not need per-pixel alpha could be plain
  child windows, or drawn by the owner instead of owning a window.
- Collapse several per-pane popups into one per-pane chrome window.

## What the second measurement said (2026-09-04)

T1343 timed the blocks a motion tick is made of; nothing had ever counted the
individual window operations inside them, so "the placement costs 9.7 ms" still
did not say what the placement was DOING. `chrome_fanout.zig` counts them, the
drag line reports them, and `test\win32\drag-perf.ps1` asserts them.

The count at 8 panes, per single mouse move, before this task:

| | moves | layered blits | z-order walks |
|---|---|---|---|
| chrome popups | 22 | 15 | 22 |

Three things that count is made of, all of them invisible until it existed:

- **Every pane's scrollbar was repositioned TWICE.** A moved pane sends its
  surface both `WM_MOVE` and `WM_SIZE`, and both arms called
  `Scrollbar.repositionAndResize`. 15 moves at 8 panes where 8 is the honest
  number — and each redundant one carried a z-order walk and a layered blit
  behind it.
- **Every reposition walked the desktop z-order.** `healOverlayZOrder`
  (`seatedAboveOwner`) walks up to 64 windows with three `GetWindow` calls a
  step, and a live layout pass moves already-visible popups with
  `SWP_NOZORDER` — so the walk could only ever confirm what it found last
  time. 22 of them per mouse move.
- **Every scrollbar reposition re-blitted its layered surface.**
  `UpdateLayeredWindow` hands the compositor a whole new bitmap; dragging a
  VERTICAL divider changes the scrollbar's x and not one of its pixels.

## What changed

Four changes, none of them a rewrite of the popup design:

1. `Scrollbar.repositionAndResize` remembers where it placed the popup and
   answers the second of the `WM_MOVE`/`WM_SIZE` pair from that cache — the
   same argument `dim_math.needsReposition` already made for the dim wash
   (T1295).
2. A live layout pass suppresses the z-order walk for popups that were already
   on screen (`chrome_fanout.shouldHeal`). A hidden→shown transition still
   heals, because `SWP_SHOWWINDOW` is the lift the heal exists for, and
   `WM_ACTIVATE` still heals every overlay a window owns.
3. `Scrollbar.repaint` compares a content signature (size, fill, thumb colour,
   thumb rect) against what the layered surface already holds and skips the
   blit when they match. Size is load-bearing on the must-blit side: a resized
   popup keeps its old surface, and leaving that stale is the stretched-content
   defect T1343 was told not to reintroduce.
4. The unfocused-split washes move through ONE `BeginDeferWindowPos` batch
   instead of one `SetWindowPos` each — the same thing T1031 did for the panes,
   one level up.

Measured on ONE build, same box, same minute, via `GHOZTTY_CHROME_FANOUT_LEGACY`
(the control switch, exactly as `GHOZTTY_DRAG_SERIAL_WAIT` is for T1343's half):

| panes | shape | per move | overlay term | chrome moves | blits | z-order walks | verdict |
|---|---|---|---|---|---|---|---|
| 2 | legacy | 6.3 ms | 0.68 ms | 4 | 3 | 4 | smooth |
| 2 | now | 5.8 ms | 0.72 ms | 2 | 0 | 0 | smooth |
| 4 | legacy | 11.9 ms | 2.42 ms | 10 | 7 | 10 | smooth |
| 4 | now | 11.2 ms | 2.08 ms | 5 | 0 | 0 | smooth |
| 8 | legacy | 19.3 ms | 4.03 ms | 22 | 15 | 22 | steppy |
| 8 | now | 15.5 ms | 2.72 ms | 11 | 0 | 0 | **smooth** |

At 8 panes that is 59 window-manager operations per mouse move reduced to 11,
about 20% off the tick, and the 8-pane drag crosses from `steppy` to `smooth`.

## What this did NOT do, stated plainly

The popups are still one popup each. The remaining bill at 8 panes is 9.1 ms of
pane placement and 2.7 ms of wash repositioning, and those are the window
manager actually moving 19 windows — not redundant work this task could delete.
Collapsing several per-pane popups into one per-pane chrome window (the third
candidate direction above) is the next honest step and is filed separately
rather than attempted here.

## Validation criteria

- [x] The cost of the fan-out is measured (paint count and time per layout
      pass) before any structural change is made — `chrome_fanout.zig` counts
      moves, layered blits and z-order walks; the drag line reports them; the
      table above is the reading, and `GHOZTTY_CHROME_FANOUT_LEGACY` makes the
      before/after comparable on one build.
- [x] If the answer is "this is not where the time goes", that is recorded and
      the task is closed as such - a measured no is a result. It was a
      qualified YES: half the operations were redundant and are gone; the
      other half is the window manager moving windows, which is stated above
      rather than claimed away.
- [x] Any change keeps every overlay above the GL surface in the cases the
      current design was built for: z-order healing (T142), hero mode, tab
      switches, DPI changes and window moves — `overlay-zorder.ps1` ALL PASS
      (34) is the T142 case directly, `hero-mode.ps1` ALL PASS (72) the hero
      one. Tab switches and window hides go through `setOwnerVisible`, which
      clears `shown` so the popup coming back heals as a hidden→shown
      transition; a DPI change moves and resizes the popup, so it is a
      placement change and heals on the same path. The suppression is scoped
      to `layoutSplitsLive` alone, so nothing outside a live drag skips
      anything.
- [x] The existing overlay acceptance scripts stay green — `overlay-zorder`
      (34), `split-dim` (29), `split-dim-viewer` (29), `pane-banner` (132),
      `readonly-badge` (28), `key-state-pill` (53), `hero-mode` (72),
      `viewer-nav-pin` (24) and `scrollback-narrow` (11), all ALL PASS on the
      box, plus `drag-perf.ps1` ALL PASS (12), four floor lanes PASS and
      P1–P3 ALL PASS.
