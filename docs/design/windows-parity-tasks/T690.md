# T690 - The host-floor t400 arm compares a warm-cache measurement against a cold-cache expectation, so it goes red at random

## In plain terms

One of the automated checks that runs before every change fails about one time
in three, without anything being broken. That is worse than it sounds: a check
that cries wolf teaches whoever is watching to ignore it, so the next time it
goes red for a real reason nobody believes it.

## Summary

`ViewerPane.zig`'s live "host floor" test (win32 lane) has a T400 arm that
measures how many HTTP fetches a navigation costs, then re-measures the same
navigation after cancelling a stale reload debounce and asserts the two numbers
match (`ViewerPane.zig:5010`, `try testing.expectEqual(nav_cost, after_nav)`).

`nav_cost` is measured FIRST, against a browser cache that has never seen the
page; `after_nav` is measured second, against one that now has. The second
number is therefore stably 0 and the first is not — measured over four
consecutive runs of `zig build test -Dapp-runtime=win32 -Dtest-filter="host
floor"` on 2026-08-10, with no source change between them:

| run | `nav_cost` | `after_nav` | result |
|---|---|---|---|
| 1 | 1 | 0 | FAIL |
| 2 | 0 | 0 | pass |
| 3 | 1 | 0 | FAIL |
| 4 | 0 | 0 | pass |

So the *expectation* is the unstable side, not the thing under test. The arm's
own comment already says the fetch count "is invisible at the server in both
cache states" and that the real oracle is the `KillTimer` line above it
(`expectEqual(0, KillTimer(...))`), which is deterministic and stays green.

Found while landing T163 (popup adoption), where it read as a regression in a
change that touches nothing on this path.

## Details

Where: `src/apprt/win32/ViewerPane.zig`, the `t400` section of
`test "host floor: a real controller on a real window, on this box"` — roughly
lines 4990–5010.

Two candidate fixes, in preference order:

1. **Assert the invariant that is actually stable**: the end-to-end companion
   claim is "the destination is not fetched an EXTRA time because of the stale
   debounce", i.e. `after_nav <= nav_cost`, or simply that the fetch count did
   not grow while pumping past the debounce window. Compare against a
   re-measured warm-cache baseline rather than the cold-cache one.
2. **Prime the cache before measuring `nav_cost`** — navigate to `reload_url`
   once and discard the count, so both numbers describe the same cache state.

Do NOT simply delete the arm: the `KillTimer` oracle above it covers the race,
but the fetch count is the user-visible half ("the page you opened is loaded
once") and is worth keeping in a form that means something.

## Validation criteria

- [x] The arm passes 5 consecutive runs of `zig build test -Dapp-runtime=win32
      -Dtest-filter="host floor"`, with the `t400:` log lines recorded for each
      so the cache state is visible rather than assumed. **4 filtered runs, all
      `costs 0` / `expected 0`, plus the full-lane run below** — and the point is
      that the calibration now reads the SAME number every time, where before it
      alternated 1,0,1,0.
- [x] Re-introducing the T400 bug (drop the `KillTimer` from `syncWatcher`)
      still turns the section red — the fix must not have removed the teeth
      along with the flake. Verified: `expected 0, found 1`.
- [x] `zig build test -Dapp-runtime=win32` green end to end (and `test-agent`,
      which compiles the same win32 apprt tests and is where this last failed).

## The fix

`ViewerPane.zig`'s t400 section now runs its calibration round trip **twice**
and keeps the second number, so `nav_cost` and `after_nav` describe the same
cache state. Option 2 of the two candidates below; option 1 (`after_nav <=
nav_cost`) was rejected on inspection: with a cold `nav_cost` of 1 and a true
warm cost of 0, a bug that adds exactly one fetch lands on `1 <= 1` and passes.
