# T942 - The machine chooser probes still take the torn photo - convert the chooser scripts to the synchronous capture

## Summary

T843's second half for `MachineChooser`, unblocked by T940's `WM_PRINTCLIENT`
handler. Switch the chooser probes to `-Sync` and re-run each script several
times.

Scripts, from the T843 survey: `chooser-selection.ps1`, `chooser-sessions.ps1`,
`chooser-session-sort.ps1`, `chooser-session-cpu.ps1`,
`chooser-roster-refetch.ps1`, `chooser-resume.ps1`, `chooser-link-hover.ps1`,
and the `$h` site in `ipc-machine-chooser.ps1` if it targets the chooser rather
than the window behind it.

These assertions are the ones most exposed to a torn frame: they read a row's
text extent and a selection highlight, which is exactly the measurement T835
found reading 1062/1283/1179 px for one unchanged frame.

## In plain terms

The tests that check the machine list — which row is selected, what order the
sessions are in, what the hover looks like — are reading a photograph that can
come out half-taken. This points them at the steady one.

## The one guard this leaves due, and why

`chooser-selection`'s guard row cannot re-stamp: only a clean green run stamps,
and that script is red on T988's two assertions. It was RUN — three times, plus
a control run of the un-converted script — so the question the guard asks ("has
anybody run this against the code as it now stands?") is answered; what it
cannot do is write the stamp. This commit therefore takes the `-NoGuardDue`
hatch, which is the intended way for that to be explainable rather than silent.
It re-stamps itself the moment T988 turns the script green, and stays due until
then, which is the guard working rather than failing.

## What the flake actually measured

Two purpose-built probes on 2026-08-19, both against the debug build on the
background test desktop, with the chooser opened by the real `ctrl+shift+n`
chord.

- **Back-to-back captures of a steady chooser.** 20 default and 20 sync
  captures, 64 sample points over the client area: **0 of 19 later frames
  disagreed with the first, in either mode.** Like the main window (T941) and
  unlike `BannerOverlay` (T835), the chooser is not layered — `WS_EX_DLGMODALFRAME`
  and nothing else — so DWM hands back its redirection surface without the
  mid-row tear T835 measured at 1062 / 1283 / 1179 px.
- **A capture taken right after a change.** Focus was driven between the filter
  field and the list (which repaints the selected row between the unemphasized
  and the emphasized wash), photographed immediately, then photographed again
  after a 1.2 s settle; the settled frame is ground truth for whatever state the
  dialog is actually in. 100 sample points, 30 changes per mode, two runs:
  **default 3 of 60 frames disagreed with the settled frame** (worst case 8 of
  100 points wrong), **sync 0 of 60.**

So the chooser's before-rate is ~5% of post-change captures, not the 0% the main
window measured and not the one-run-in-three of the banner. That is the number
the conversion removes, and it is a real one: a probe that captures within a few
hundred ms of driving the dialog — which every one of these scripts does — was
reading the previous frame about one time in twenty.

One methodology note worth keeping, because the first version of the second
probe was wrong. It scored each frame against a FIXED per-mode reference of the
two focus states, and the chooser's Tab ring has more than two stops, so a
single dropped keystroke shifted the phase permanently and every later frame
scored as a capture fault — one run reported 30 of 30 sync frames "wrong" when
nothing was wrong with the capture at all. Comparing each frame against its own
settled successor has no phase to lose.
