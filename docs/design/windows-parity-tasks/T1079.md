# T1079 - A Windows +split from inside a pane still lands in the last-focused window

## Summary

The merge of `origin/main` (T1073) brought **caller anchoring**: a `+split` or
`+rearrange` that names no target now anchors at the pane it was invoked from
rather than at whatever window is focused when the app gets around to the
message. The CLI half is in shared `src/` and therefore already ships on
Windows — `apprt.ipc.seedCallerPane()` (`src/apprt/ipc.zig`) inserts
`--caller-pane=$GHOZTTY_PANE_ID` ahead of anything from `-e` on, for both
`src/cli/split.zig` and `src/cli/rearrange.zig`.

The app half is macOS-only. `IPCServer.callerAnchorPane` (Swift) prefers the
flag over `TerminalController.preferredParent`; `src/apprt/win32/IpcHandlers.zig`
has no `--caller-pane=` case at all. Its argument loops are if/else-if chains
that ignore anything they do not recognize, so the flag is silently dropped and
Windows keeps the old focused-window fallback.

## In plain terms

Ask for a side pane from a script running in one window, click another window
while it works, and the pane opens in the window you clicked. On the Mac that
was just fixed — the pane now opens next to the script that asked for it. On
Windows it still lands wherever the mouse went. The command already carries the
answer; the Windows app is not reading it.

## Goals

- [x] `src/apprt/win32/IpcHandlers.zig` reads `--caller-pane=<id>` on `+split`
      and `+rearrange` and prefers it over the focused-window fallback
- [x] Anything explicit still wins: `--target`, `--pane`, `--from-focused`
- [x] A `--caller-pane=` naming a pane that no longer resolves FALLS BACK to
      the focused window (it is a default, not an assertion) while an explicit
      `--pane=` naming nothing stays a hard error
- [x] Absent or empty behaves exactly as today
- [x] The known-gap note in `docs/claude/cli.md` (Caller anchoring) is removed
