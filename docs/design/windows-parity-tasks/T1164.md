# T1164 - The suite runner's own acceptance is red in two sections, and its per-script timeout feature never proved it works

## Summary

Found while doing T1158. 	est\win32\suite-run.ps1 scores 7-9 FAILURE(S) on HEAD, in two clusters. Section N (per-script declared timeout, the feature T1125 added in 9d445b377) is red end to end: N1 a fixture declaring # suite-timeout-sec: 40 under a 5s global cap is killed and scored stall instead of passing; N4 reports declared 0; N5/N8 the header never says any script declared a cap; N13 the runner does not read the declaration off the shipping soak.ps1 either (suite-run.ps1 list -Include soak.ps1 prints a bare cli  soak.ps1). Section M (the between-script modal sweep) is FLAKY rather than steady - M1 a script that leaves a dialog up is scored a FAILURE passed on one run of this turn and failed on the very next with nothing changed in between, along with M2/M3/M4. NOT caused by T1158, and that is checked rather than asserted: the only file T1158 changed that this harness covers is test\win32\soak.ps1, its first 35 lines (the declaration region) are byte-identical to HEAD, and N12 - which parses the declaration out of that same edited file - PASSES while N13 - which asks the RUNNER to do it - fails. The difference is scripts\suite-run.ps1, which T1158 did not touch. Worth noting how it stayed hidden: the guard-due row for suite-run lists scripts\suite-run.ps1 in Covers, yet the 2026-08-23 claim reported GUARD CURRENT suite-run (5 files, stamped 2026-08-23 from 820193367) even though 9d445b377 changed that file AFTER 820193367. So a second question to answer here is whether guard-due mis-scored that row, because a stamp that survives a change to a covered file is the T783 defect itself.

## In plain terms

Nobody here notices a broken test unless the tests that watch the tests are
themselves trustworthy. The tool that runs the whole Windows acceptance suite
has its own test, and that test was scoring failures for two different reasons
that had nothing to do with each other - one a real bug that has since been
fixed, one a stopwatch in the test itself that was too short whenever the
machine was busy. A test that goes red when the box is busy trains everyone to
shrug at red, which is how a real failure gets shrugged at too.

## Findings

**Section N was already fixed, by 6dc4708ed.** The declaration regex anchored
`[ \t]*$`, and .NET's multiline `$` matches BEFORE the `\n`, so a CRLF file's
`\r` sat inside the line and `# suite-timeout-sec: 2400` in `soak.ps1` read as
no declaration at all. `soak.ps1` became CRLF in ce943e238 - the commit this
task was filed from - which is why the cluster appeared then and why N12 (parse
the file directly) passed while N13 (ask the runner) failed. That commit's
message names the same root cause and adds N14 as its regression check. Five
full runs of the harness on HEAD score N green.

**Section M was a race in the fixture, not in the runner.** `h-modal.ps1`
raised its dialog from a detached process, slept a flat three seconds and
exited; the sweep runs AFTER the script exits, so on a box slow enough that
WinForms had not finished painting, the sweep found nothing and M1-M4 all went
red at once with no defect behind them. Measured: 0.23s to paint on an idle
box, unbounded on a loaded one - and this task was filed during the soak work,
which is exactly the load. The fixture now waits on the sweep's own predicate
instead, and M5 was rewritten to be a real positive control (the dialog was
seen on screen, not merely a pid written), so if this ever does fail again the
four checks above it are explained rather than mysterious.

**guard-due did not mis-score anything.** The gate compares content hashes and
always did. The 2026-08-23 stamp was written at 01:59 over a working tree that
was committed seven minutes later as 9d445b377 - its recorded
`scripts/suite-run.ps1` hash (`b490824...`) is 9d445b377's content, not
820193367's. What misled was the sentence: `stamped 2026-08-23 from 820193367`
names where the stamp was TAKEN, and reads like a claim about what it HOLDS. A
`CURRENT` line now says `+N uncommitted` when the stamp was taken over work
that had not been committed yet, and the stamp records which files those were.
