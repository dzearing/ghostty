# T43 — Proper visual debug banner on win32 (Phase I, lower priority)

## Summary

A debug build's whole caption/tab band is now tinted **warning amber**, so the
window cannot be mistaken for the user's installed release at a glance. The
`" [DEBUG]"` title suffix stays as the second half of the marker — it is the
one that reaches the taskbar and Alt-Tab, where the app paints no pixel of its
own. Both are gated on `Window.debug_build` (`Debug` or `ReleaseSafe`, the same
pair Mac gates its banner on; what ships is `ReleaseFast` and is unmarked).

Measured on box, caption band mode color, debug build vs the same background's
release band:

| `--background` | release band | debug band |
|---|---|---|
| `#f3f3f3` | `#e0e0e0` | **`#e3ca91`** |
| `#ffffff` | `#ebebeb` | **`#ebd199`** |
| `#1e1e1e` | `#303030` | **`#795f27`** |

## Details

### A tint, not the Mac banner row

Mac stacks a full-width warning strip above the terminal
(`TerminalView.swift:81`, `DebugBuildWarningView`). Translated literally that
row comes straight out of the design system's §6 budget — and T234 and T205 had
just spent two tasks giving 95 physical px of it back. So the marker had to
live in chrome the window already pays for. A tint costs zero rows and zero
geometry: **no rect moves**, so no layout module, hit test, or
`ChromeGeometry.ps1` datum changes with it. T43's own Details named "a tinted
tab bar" as one of its two candidate vehicles; this is that one.

### The tint goes into the BASE

`chrome_theme.debugChromeBase(base)` is applied to the chrome background
*before* `resolve` derives anything from it, so the text ramp, the accent and
the danger red all recompute their §2.3 contrast floors against the band that
is really painted. A tint applied to `Palette.bar` afterwards would leave every
floor measured against a surface no longer on screen. Asserted by a sweep over
the background × accent space, not by one hand-picked pair.

### Two marker hues, because one cannot mark itself

A fixed hue cannot mark a background that already IS that hue: on an amber
terminal background `mix(base, amber)` is the base again and the debug build
looks exactly like the release one. Below `debug_min_delta` (48) the tint falls
back to violet. Amber and violet are 508 apart in channel distance, so by the
triangle inequality no background can defeat both — asserted
(`no background can defeat both marker hues`), not argued.

### `GHOZTTY_DEBUG_MARKER=0`, and why it is not a convenience

The win32 GUI acceptance suite runs a **debug** build and reads its chrome
pixels *as the proxy for what ships*. A marker that recolors the band silently
moves every one of those claims onto a surface no user ever sees.

That is measured, not feared. A baseline run with the tint compiled out was
fully green; with it live `tab-strip.ps1` went **8 red** on a build that was
painting exactly what it was told to — including *"an inactive tab is invisible
against the strip"* and *"dead space right of the tab is bar background (R=102)"*
— and `tab-color.ps1` could only measure 1 of its 2 chiclets. Root cause:
every chrome surface is a fixed-FRACTION wash of the bar, and a tinted bar is a
lighter bar, so each wash steps less far (inactive-tab step 14 → 9 on black).

So the harness sets `GHOZTTY_DEBUG_MARKER=0` **once**, in
`test/win32/lib/TestDesktop.ps1` — a script must control the inputs its
conditions are a function of (the T267 rule), and a new script gets it for
free. `chrome-theme.ps1` re-enables it and is the one script that owns the
marker, the same opt-out shape `-KeepWindowPlacement` uses for the two scripts
that own the placement memory.

Follow-ups: **T363** (`tab-strip.ps1`'s hardcoded bar R range, which only
survives because the marker is off there) and **T364** (the compressed wash
steps themselves, which a dev running a debug build still sees).

## Validation

Run on box, 2026-08-02, all against `zig-out\bin\ghoztty.exe` (Debug):

- `zig build test -Dapp-runtime=none` — exit 0. The three new `chrome_theme`
  tests were proven to actually RUN, not merely to not fail: `-Dtest-filter=
  debugChromeBase` reports 77 tests against a 74-test baseline with a
  no-match filter, a delta of exactly 3.
- `zig build test -Dapp-runtime=win32` — exit 0.
- `zig build test-agent` — exit 0.
- `ipc-p1/p2/p3.ps1` — ALL PASS.
- `chrome-theme.ps1` — **ALL PASS (38)**, including the four T43 assertions:
  the band equals `wash(debugChromeBase(bg), bar_wash)` EXACTLY on all three
  backgrounds, the marker's presence matches the build's own `+version` "build
  mode" line, and the title carries `" [DEBUG]"` iff the build marks itself.
  Both halves are two-directional, so *"release build unaffected"* is a real
  check rather than an untested half — and that also defuses T350 here.
- `chrome-theme.ps1 -NegativeControl` — **2 FAILURE(S) of 38**, as designed:
  the pre-existing direction claim *and* the new marker claim both flip and
  both go red, which is what proves the marker probe can see the tint at all.
- `tab-strip.ps1` ALL PASS (56), `tab-color.ps1` ALL PASS (16),
  `color-contrast.ps1` ALL PASS (14) — the neighbours the marker perturbed
  before the harness default landed.
