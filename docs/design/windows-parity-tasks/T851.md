# T851 - A second same-lineage app launch silently adopts the running instance's sessions: launch restore ignores the attached flag, the agent rebinds to the newest attach, and the first app's panes freeze

## In plain terms

If Ghoztty is already running and you start a second copy of it (say the
portable one from the Desktop while the installed one is open), the new copy
comes up showing YOUR windows - and the copy you were working in freezes: its
panes still show their last picture, but typing into them goes nowhere. The
new copy stole the running one's terminals. When this lands, starting a second
copy gives you a fresh window and leaves the running one alone.

## Goals

- [x] A second same-lineage launch never adopts a session that a live viewer
      holds - it comes up with a fresh startup window
- [x] Crash recovery is NOT weakened: a relaunch seconds after a crash still
      re-attaches everything (the attach flags the dead app left behind must
      not read as "a live viewer holds this")
- [x] `test\win32\chooser-restore-all-adopt.ps1` (T486) runs end to end with
      0 skipped - its skip gate names this task while the defect exists

## Summary

User-facing freeze in a real configuration: the installed release and the Desktop
portable copy are same-lineage instances sharing one agent and one session-layout
manifest; launching the second hijacks every window of the first. Measured on-box
2026-08-15 building T486's fixture.

## Details

Mechanism, measured with two debug instances (`GHOZTTY_PIPE_SUFFIX` -t486a/-t486b,
one shared debug agent):

- Instance B up first, one pane (session `c501...`, ATTACHED to B).
- Instance A launches. `restoreSessionLayout` (App.zig) unions the shared
  manifest with the agent's layout blobs and gates each window on
  `restoreWindowHasAttachableLeaf` - whose attach set (`AttachProbe.take`) is
  "alive OR relaunchable tombstone". **Currently-attached-to-a-live-viewer is
  not excluded**, so B's window passed the gate. A's log:
  `attach: session=c501... offset=481` then `session-restore: restored 1
  window(s)` - A restored B's window, the agent rebound the session to the
  newest attach, and B's pane became a frozen picture (attached-is-not-alive,
  the T652 phrase in its purest form).
- The steal also suppressed A's default blank startup window, so A LOOKED
  normal - nothing anywhere said a running app just lost its terminal.

Why the fix is not just "skip attached sessions": after a CRASH the dead app's
attach flags can linger until the agent notices the broken pipes (measured to
clear within ~1s on this box, but the race is real for an immediate relaunch).
Blindly skipping attached sessions would make crash recovery restore nothing on
that race. The design question is how launch restore tells "attached to a LIVE
viewer" from "attached-flag left by a dead one" - e.g. the agent clearing
attach state on pipe break (already happens; maybe enough), a short retry when
everything reads attached, or the agent reporting attach-pipe liveness
explicitly. Pick what is robust, not what is quick.

Related product question, noted here rather than decided: whether a second
same-lineage launch should even be an independent instance (Windows Terminal
opens a new window in the running instance; Mac's app bundle single-instances
via LaunchServices). Whoever fixes this should consider whether the experience
answer changes the mechanism, and file the experience decision if both
directions are genuinely viable.

Found building T486's already-running-viewer fixture: the fixture launches B
then A, and A's launch stole B's session before the fixture could build A's
topology. `test\win32\chooser-restore-all-adopt.ps1` carries a skip gate that
detects the steal and names this task; once this lands the gate passes and the
script's sections 2-5 become the regression coverage (including the assertion
that A's session ids are disjoint from B's).

- 2026-08-17 19:15: root cause + design settled: AttachProbe treated 'alive or relaunchable' as attachable with no regard for the roster's ttached flag, so a second same-lineage launch adopted a running instance's window and the agent rebound the session to the newest attach. Fix: AttachProbe.Policy - LOCAL launch restore and local Restore All use .skip_live_holders (withhold sessions the agent reports attached, recorded in a new held set); the two REMOTE arms keep .attachable, because across a relay an attached flag can be our own un-reaped connection. The crash race is closed by a bounded settle loop in restoreSessionLayout (re-probe every 200ms up to 2s, only while a window this launch would restore reads held) - a dead holder's flag clears in ms, a live holder's never does, and the budget-exhausted fallback is the safe one. A held window is carried forward, never forgotten, and says so in the log.
