# T1255 - Ghoztty over Remote Desktop has an acceptance harness that can only pass from inside a remote session

## In plain terms

Everything we know about Ghoztty over Remote Desktop, we know by pretending:
a debug switch makes the graphics driver claim to be older than it is. Nobody
has ever watched the terminal start inside a real remote session. This is the
checklist for when somebody does - a script that launches the terminal, reads
back which graphics driver it ended up on, measures how smoothly it draws, and
checks that the window list and session restore still work. Run it anywhere
else and it refuses to give an answer at all.

## Split from

[[T1253]]. Its sibling is [[T1256]], which is the run itself.

## What lands here

- `test\win32\rdp-session.ps1`, six arms: the session's own identity (A), a
  launch with no startup-failure dialog (B), the renderer's account of the
  OpenGL context and implementation it drew with (C), `+list` over the remote
  session (D), frame pacing under a sustained stream (E), and a named window
  surviving a kill-and-relaunch restore (F).
- The refusal is the design, not a skip branch: outside a remote session it
  prints `ASSERTED NOTHING` and exits 2, so a console run can never be mistaken
  for evidence.
- `-SelfTest` runs the body on whatever desktop it finds so the harness can be
  proved to work without a second machine, and is deliberately incapable of
  scoring green: it prints `SELF-TEST`, exits 2, writes its numbers to a
  separate gitignored artifact, and never stamps the guard.
- An **advisory** `rdp-session` row in `scripts\guard-due.ps1`, covering
  `src\renderer\gl_loader.zig` and `src\renderer\gl_report.zig` only. Advisory
  because this box is physically unable to answer the question and there is no
  CI job that can either; narrow because a row that is always due is a row
  nobody reads.

## Why it runs on the interactive desktop

Every other GUI script in this suite runs on a background desktop so acceptance
never takes the user's foreground. A background desktop is never composited and
never presented, so its frames are not shipped over the RDP wire - arm E would
be measuring a renderer talking to nothing, which is the exact number this
exists to get right. `-BackgroundDesktop` is there for the arms that do not
care.

## Validation criteria

- [x] The script exits 2 with `ASSERTED NOTHING` when run outside a remote
      session, demonstrated on this box: `rdp-session: ASSERTED NOTHING
      (0 assertions) - this run proved nothing; it is not a pass`, exit 2.
- [x] `-SelfTest` executes all six arms and cannot score green: `SELF-TEST
      (13 passed, 1 failed)`, exit 2. The one failure is A1 (SM_REMOTESESSION),
      which is the assertion that cannot hold on a console desktop - the rest
      of the run is the proof that B through F execute. The self-test earned
      its keep immediately: it found `+list --json` being parsed at the wrong
      depth (`.windows` rather than `.data.windows`), which had silently
      failed D2, E2 and F2.
- [x] `stderr-capture-audit`, `verdict-exit-audit` and `body-complete-audit`
      pass with the new script in the swept directory. `stderr-capture-audit`
      caught a real violation first (arm D piped a merged stream to
      `Out-String` unstringified); after the fix, `ALL PASS (25 assertions)`.
      `verdict-exit-audit`: `ALL PASS`. `body-complete-audit`: `ALL PASS
      (40 assertions)`.
- [x] `guard-due.ps1 check` lists `rdp-session` as advisory and never counts it
      against `validate`.

`asserted-nothing.ps1` and `skip-visibility.ps1` are red at HEAD for reasons
