# T243 - zig build panics opaquely unless ZIG_GLOBAL_CACHE_DIR is on the repo drive

## In plain terms

Building this project on a fresh terminal window used to blow up with a crash
report that had nothing to do with the code you were changing - no error
message, just a stack trace from deep inside the build tool. The real cause was
a setting: the build tool keeps a scratch folder on the C: drive by default,
and the project lives on D:, and it cannot cope with that. Anyone who hit it
lost a build or two guessing, and at least one person assumed it was a random
blip and simply ran the same command again.

Now the build stops on its own and says so in one sentence, with the exact line
to paste to fix it. Nobody has to recognise the crash any more.

## Goals

- [x] Building with the scratch folder on the wrong drive prints a real,
      actionable error instead of crashing
- [x] The suggested fix is a line you can paste, not just a diagnosis
- [x] The check is invisible when nothing is wrong - other machines and other
      operating systems build exactly as before
- [x] The rule is written down where someone hitting it would already be looking

## Validation criteria

- [x] With `ZIG_GLOBAL_CACHE_DIR` unset (default C: cache) on this box,
      `zig build test -Dapp-runtime=none` prints the new diagnostic and exits
      non-zero **without a panic** - run on the box at this HEAD: exit 1,
      `error: the zig global cache is on drive C: but this repo is on drive D:`
      followed by the `$env:`/`set` lines and `error:
      GlobalCacheOnDifferentDrive`. No `panic:` anywhere in the output.
- [x] With it set to `D:\zig-global-cache`, the three zig lanes are green -
      `scripts\floor-lane.ps1 -Lane all`: `none#1=PASS win32#1=PASS
      agent#1=PASS`, `ALL LANES PASS`.
- [x] The pure decision logic is asserted in the `none` lane, and the assertions
      actually run there - `zig build test -Dapp-runtime=none --summary all`
      reports `run test ghoztty-build-helpers-test 9 passed` (8 test blocks in
      `drive_check.zig` + the aggregator's own import block).
- [x] Same-drive and drive-less (POSIX/UNC) inputs are proven no-ops - three
      test blocks cover it: matching drives in either case, POSIX pairs, both
      UNC positions, and a null `Cache.Directory.path`.
- [x] P1-P3 stay ALL PASS - `P1 ACCEPTANCE: ALL PASS`, `P2 ACCEPTANCE: ALL
      PASS`, `P3 ACCEPTANCE: ALL PASS`, run sequentially after the lanes.

## Summary

On this box a fresh shell that runs `zig build test` with no
`ZIG_GLOBAL_CACHE_DIR` set does not fail with a diagnostic - it **panics inside
the build runner**:

```
thread NNNNN panic: reached unreachable code
  std/Build/Step/Run.zig:662  assert(!std.fs.path.isAbsolute(child_cwd_rel));
error: unable to read results of configure phase from '.zig-cache\tmp\...': FileNotFound
```

Cause (already known, recorded only in a session memory): zig 0.15.2's build
runner asserts when a dependency `Run` step sets a cwd on a **different drive**
than the build root. The repo is on `D:`, the default global cache is on `C:`,
and uucode's `setCwd(b.path(""))` trips it. Setting
`ZIG_GLOBAL_CACHE_DIR=D:\zig-global-cache` is the fix, and it must be set in
every build/test shell.

This cost time again on 2026-07-31 (the T242 turn): the first test lane came
back "exit 1" with a stack trace and no `error:` line pointing at anything in
this repo, which is exactly the shape of a false failure the go.md rules warn
about.

**Bitten at least four times now**, each in a different turn, each costing a
build or two before the environment was suspected: T242 (2026-07-31), T257
(2026-07-31, filed separately as **T262** because the previous filing was not
findable from a fresh session either), and T225 (2026-08-01) - where the FIRST
`zig build` of the turn panicked, was re-run verbatim on the assumption of a
transient, and panicked identically. That re-run is the tell: the failure looks
enough like a flake to earn a retry, which is the exact behaviour go.md's
`-First N` rule exists to stop.

**T262 is a DUPLICATE of this task** (marked `skipped(duplicate -> T243)`), and
that duplication is itself evidence for the fix below: two independent turns hit
the wall, searched, did not find each other's task, and filed. Documentation
that has to be *found* keeps failing here; a diagnostic that fires at the moment
of the panic cannot be missed. T262's own contributions are folded in:

- Reproduced deliberately in BOTH directions at one HEAD (`5ad81a99e`), only the
  variable changing: unset -> exit 1 + panic; `D:\zig-global-cache` -> exit 0.
  Confirmed unset twice with a fresh `.zig-cache\tmp\<hash>` each run, so it is
  not one poisoned cache entry.
- `zig build --help` exits 0 with it unset - the panic needs the real configure
  phase, which is why a quick sanity check misses it.
- `D:\zig-global-cache` already exists on the box: this was solved once and then
  never written anywhere a turn would read it.
- Alongside the diagnostic, put the one-line workaround in `go.md` next to the
  `Select-Object -First N` warning - same shape of trap (a scary failure with
  nothing to do with the change under test), same place a turn is already
  reading when a build fails oddly.

## Why this is a repo task and not just a note

The knowledge lives only outside the repo (a private session memory). A fresh
agent, a fresh clone, or the user on a second machine hits the same wall with
nothing in the tree to explain it.

## What landed

- **`src/build/drive_check.zig`** - the whole decision, pure and std-only.
  `driveLetter` uppercases a leading Windows drive and sees through a `\\?\`
  verbatim prefix (the shape a `realpath`-resolved path arrives in) but not
  through `\\?\UNC\`; `check` returns a `Mismatch` only when both sides yield a
  letter and the letters differ. **"Cannot tell" is always answered as "no
  mismatch"** - a POSIX path, a UNC share, a relative path, or a null
  `Cache.Directory.path` all mean silence, which is why this is inherently a
  no-op on the Mac seat rather than something gated off by OS.
  `suggestedCacheDir` builds the concrete path to export, because "put it on
  the same drive" is a diagnosis and what a stuck shell needs is a line to
  paste.
- **`build.zig`** - `checkGlobalCacheDrive(b)` is the first statement in
  `build()`, ahead of anything that could reach the assert. It resolves each
  root through `absoluteRootPath`, which falls back to the open handle's
  `realpathAlloc` when `Cache.Directory.path` is null or relative (otherwise
  the guard would silently no-op in exactly the shell it exists for). One
  `std.log.err` carries the whole message, so the failure has the `error:` line
  whose absence go.md teaches you to distrust, then
  `error.GlobalCacheOnDifferentDrive`.
- **`src/build/build_test.zig`** - a new aggregator wired into `test_step`,
  outside the `emit_lib_vt` guard since it depends on nothing. The main test
  binary roots at `src/main.zig` and therefore reaches **no** build logic, so a
  `test` block written next to a build helper used to run in no step at all
  (`wasm_patch_growable_table.zig` still has one, and it has never run). This
  is the seam that makes any future pure build helper testable.
- **Docs** - the CLAUDE.md Windows build bullet and go.md, the latter beside
  the `Select-Object -First N` rule, since it is the same trap shape: a scary
  failure with nothing to do with the change under test.

Deliberately **not** done: setting the variable from inside `build.zig`. A
build script that silently relocates a user's global cache is its own surprise,
and removing surprises is the entire point.

## Proposed fix

In `build.zig`, before anything else: if the build root's drive letter differs
from the resolved global cache directory's drive letter, **fail with a real
diagnostic** naming `ZIG_GLOBAL_CACHE_DIR` and the value to use. A `std.log.err`
+ `return error.` beats a runner assert. (Do not silently *set* it - mutating a
user's cache location from inside build.zig is a surprise; telling them exactly
what to export is not.)

Cheap belt-and-braces alongside it: a line in the Windows build section of the
docs, so the answer is greppable even if the check regresses.

## Validation

- With `ZIG_GLOBAL_CACHE_DIR` unset (or pointed at a `C:` path) on this box,
  `zig build test -Dapp-runtime=none` prints the new diagnostic and exits
  non-zero **without a panic**.
- With it set to `D:\zig-global-cache`, both test lanes are unchanged and green.
- The check is a no-op when the drives match (e.g. a same-drive CI checkout),
  so it cannot break the Mac seat or a normal Linux build.
