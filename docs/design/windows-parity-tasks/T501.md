# T501 - The loop resumes crashed work instead of orphaning it: stale in-progress detection, progress journaling

## In plain terms

When the computer crashed mid-task, the work simply vanished from view: the
task stayed marked "in progress" with nobody on it, half the fix sat
uncommitted, and the next session started fresh work on top. Now every task
keeps a running journal of steps taken, and when the loop restarts it is
handed the abandoned task first - with that journal and the uncommitted
files as the trail - instead of new work.

## Goals

- [x] `next -Claim` detects a stale in-progress task (one agent runs at a
      time, so any in-progress claim at turn start is stale) and hands it
      back as `RESUME:` with reassessment instructions, instead of new work
- [x] `note <id> -Text ... [-Session <id>]` appends timestamped entries to a
      `## Progress log`; a claim seeds the first entry automatically
- [x] `validate` fails an in-progress task with no progress log
- [x] go.md's step 1 teaches the RESUME path and the journaling cadence
- [x] The three tasks stranded by the 2026-08-05 bluescreens (T183, T496,
      T497) got seeded progress logs with evidence-based assessments

## Summary

Two bluescreens on 2026-08-05 (00:23 and 08:23) killed loop turns mid-task.
The 08:23 one left T496/T497 in-progress with no agent, ~600 lines of
uncommitted chrome work in the tree, and nothing telling the next turn - the
user found them by noticing "3 tasks in flight" on the dashboard hours later.

The fix closes the loop's crash hole at three layers (`parity-tasks.ps1`,
`go.md` step 1, `docs/design/windows-parity-tasks/README.md`):

- **Detection**: this queue runs ONE agent, so `in-progress` + a new turn =
  stale by definition. No heartbeat or agent-assignment field needed.
- **Context**: the progress log is the journal a dead turn leaves behind;
  `-Session` stamps which conversation wrote each entry.
- **Resume**: `RESUME:` output routes the new turn through reassessment
  (read the log, `git status`/`git diff` the task's files, keep-or-restart)
  rather than silently re-claiming or orphaning.
