# T1290 - A nudged-but-idle loop reports HEALTHY

## In plain terms

The loop stopped doing any work for over fourteen hours. The health check kept
saying everything was fine, because something had typed into the window
recently - not because the loop had actually done anything.

## What happened (2026-09-03)

The ledger's last event is `turn=66 acquire` at **2026-09-02 14:29**. Nothing
after it: no heartbeat, no acquire, and `git log --since` over the same window
returns **zero commits**. The loop was inert from 14:29 to at least 05:07 the
next morning.

Across that whole window the health line read:

```
HEALTHY uptime=2d 21h 54m turn=66 state=held ... windows=1 watchdog=True
```

The watchdog found `state=stale-heartbeat` at 04:59:44, nudged the pane, and
logged `NUDGE SUBMITTED: the pane moved`. Six minutes later the health check
reported `HEALTHY` with `age=5.17m(by=transcript)` - measuring the nudge
itself. The pane moved; the loop did not.

## The defect

Two clocks, and the verdict keys off the wrong one:

- **Transcript activity** - "something happened in this pane". Refreshed by the
  watchdog's own nudge, by a login prompt redraw, by anything at all.
- **The lock heartbeat / turn counter** - "the loop completed work". This was
  14.5 hours stale and is the number that describes the thing being supervised.

This is the same family as the mismatch noted on 2026-09-02, where the health
script called a stall DOWN at 76 minutes while the watchdog still read healthy
by transcript. Then the two disagreed; here they agree on the wrong answer,
which is worse - a green line with no work behind it.

**Trigger CONFIRMED 2026-09-03, and it is not what this task first guessed.**
Reading the loop's own pane (`ghoztty +read --name=<pane>`) shows the cause
directly:

```
API Error: 529 Overloaded. This is a server-side issue, usually temporary.
  Sauteed for 16m 20s - done 6:28 AM
API Error: 529 Overloaded.
  Churned for 3m 23s - done 8:00 AM
```

The loop is not logged out and is not wedged: it is being turned away by
server-side overload, sitting idle, and a watchdog nudge re-submits straight
into another 529. The earlier note in this file blamed an expired login,
inferred from a `/login` and a batch of queued ticks; that was circumstantial
and wrong. **Read the pane before theorising** - the answer was one command
away for three stalls running.

This changes what the fix must handle: a 529 is transient and expected, so the
loop needs to retry with backoff rather than stop, and the supervisor needs to
distinguish "waiting on an overloaded API" from "broken". Nudging into an
overloaded API just burns another request.

## What to build

- **Report progress, not liveness.** A `turn=` that has not advanced and a lock
  heartbeat older than the stale threshold must not produce HEALTHY, whatever
  the transcript says. Consider a `stalled=` or `last_turn_age=` field so the
  supervisor reads work done rather than keystrokes seen.
- **A nudge is a treatment, not evidence.** After the watchdog nudges, the
  verdict should stay degraded until a turn actually completes - otherwise the
  cure manufactures the symptom of health.
- **Name the auth case if it is confirmed.** A loop that cannot authenticate
  should say so, rather than presenting as a live pane doing nothing.

## What landed

A third clock, kept deliberately apart from the two liveness ones:

- `go-loop-lock.ps1` writes **`turn_started`** on every `acquire` and nothing
  else. Only a completed turn reaches go.md step 0 again, so only a completed
  turn moves it. `status` exposes `turn_age_minutes` (and `turn_age=` on its
  plain line); a lock written before the field existed falls back to the
  HEARTBEAT, never to the transcript pulse - otherwise the upgrade would have
  re-introduced the bug for every lock already on disk.
- `go-loop-health.ps1` reports `turn_age=` beside `uptime=`, and reddens the
  verdict past `-TurnStaleMinutes` (default 180 - generous, because this clock
  only moves at turn boundaries and a long acceptance sweep is legitimate; the
  shape being caught was 14.5 HOURS). The note names the turn and when it
  started, and sends the reader to the pane, because three stalls running were
  theorised about from the ledger while `ghoztty +read` had the answer.
  `-Postmortem` now prints that pane tail without being asked.
- A loop stopped ON PURPOSE is not turning by design, so the note is dropped
  from the `stopped` verdict with the other two that would be noise there.

Not built: the auth line. The trigger was confirmed as `API Error: 529
Overloaded`, not an expired login, so there is no auth case to name - the note
points at the pane where a 529 is legible instead.
