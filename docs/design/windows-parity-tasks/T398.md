# T398 - Viewer-only windows do not restore without a local agent: restoreSessionLayout bails before reaching them

## In plain terms

If the piece of Ghoztty that keeps your shells running in the background can't
start — a broken or missing install of it, say — then reopening the app threw
away your whole layout and gave you one empty window. That is fair enough for
your terminals, whose processes really are gone. But it also threw away the
panes that were just showing a file, a web page or a diff, and those never
needed that background piece at all: reopening what they were showing IS how
they come back.

Now they come back. A window made only of viewer panes reopens exactly where it
was, and a window that mixed a viewer with a terminal reopens too, with the
viewer at its old page and the terminal as a fresh shell in the same spot. A
window that was nothing but dead terminals is still dropped, as it always was.

## Goals

- [x] a viewer-only window restores when no local agent can be resolved
- [x] a mixed window restores, its terminal degrading to a plain local pane
- [x] a terminal-only window is still dropped (the never-all-dead rule holds)
- [x] the log says which case happened instead of claiming a failed probe
- [x] a negative control proves the new assertions fail without the fix

## Summary

`App.restoreSessionLayout` resolves the local agent connection FIRST and returns
false when there is none ("no local agent; opening a blank window"). That gate
predates viewer panes and is correct for terminals — without a connection there
is nothing to ATTACH to. A VIEWER rides no agent at all (T90h: re-opening its
recorded location IS its restore), so a manifest whose windows are all viewers
is dropped for a reason that does not apply to any leaf in it.

## Details

Found while landing T90h, which added the viewer arms of the restore walk. The
never-all-dead rule now keeps a viewer-only window in
`restoreWindowHasAttachableLeaf`, but that function is never reached: the
connection `orelse return false` above it exits first.

Reproduces when the agent is unspawnable / unreachable — a broken or missing
`ghoztty-agent.exe`, or `session-persistence` turned off between runs — with a
manifest holding a `--view` window. The user's terminals genuinely cannot come
back; their viewer panes could, and silently do not.

The shape of the fix: build a null-transport `RestoreTransport` for windows with
no session-backed leaf and restore those, keeping the existing early return for
the rest (or, equivalently, move the connection resolution to the first window
that needs one). Terminal leaves inside a partially-restorable window then open
as plain local ConPTY panes, which is what a no-agent window does anyway.

*Validation:* extend `test/win32/viewer-restore.ps1` with a run whose
`GHOSTTY_LOCAL_AGENT_BIN` points at a path that does not exist: the mixed window
degrades (its terminal opens fresh) and the viewer-only window still comes back
with its recorded location. The existing agent-present run is the control.

## What landed

`src/apprt/win32/App.zig`, three coupled changes:

1. `RestoreTransport.conn` is now **optional**, with an `agentless()`
   constructor. `restoreAttachOverride` returns a plain override — recorded
   pane id, no `.remote` — when it is null, so the leaf opens as a local ConPTY
   pane. The pane id is still adopted: it is ghoztty's own, and dropping it
   would break every `--target=$GHOZTTY_PANE_ID` the pane's processes were
   baked with.
2. `restoreSessionLayout` no longer returns false on a missing connection. It
   skips `GET_LAYOUTS` (nobody to ask) and probes with a new
   `AttachProbe.agentless` — an **EMPTY** attach set, deliberately not a null
   one. That distinction is the whole liveness tri-state: null means "probe
   failed, attempt every leaf" and would have rebuilt terminal-only windows as
   walls of fresh shells. Empty means "known: nothing is attachable", which is
   exactly how the never-all-dead rule already reads an agent that knows none
   of the recorded sessions.
3. The T411 gap report gets its own no-agent branch, so the log says "no local
   agent, so every restored terminal pane is a fresh local shell" instead of
   claiming the probe failed.

Net behavior with no agent: a viewer-only window restores, a mixed window
restores with its terminal degraded in place, a terminal-only window is still
dropped.

## Filed while here

- **T589** (`seat: mac`) — the same gate exists in Swift
  (`SessionLayoutRestore.swift:53-64`, read directly), so the Mac drops
  viewer-only windows too.
- **T590** — a launch that restores nothing then OVERWRITES the manifest with
  the blank window it opened (`syncSessionLayout` regenerates wholesale), so
  the recorded layout is lost for good. Mac explicitly does not do this
  ("keeping N manifest entries for next launch"). Adjacent to this fix, and
  total loss in precisely the no-agent case.
