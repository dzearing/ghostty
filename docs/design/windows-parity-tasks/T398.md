# T398 - Viewer-only windows do not restore without a local agent: restoreSessionLayout bails before reaching them

## Summary

`App.restoreSessionLayout` resolves the local agent connection FIRST and returns
false when there is none ("no local agent; opening a blank window"). That gate
predates viewer panes and is correct for terminals — without a connection there
is nothing to ATTACH to. A VIEWER rides no agent at all (T90h: re-opening its
recorded location IS its restore), so a manifest whose windows are all viewers
is dropped for a reason that does not apply to any leaf in it.

## Details

Found while landing T90h, which added the viewer arms of the restore walk. The
never-all-dead rule now keeps a viewer-only window in
`restoreWindowHasAttachableLeaf`, but that function is never reached: the
connection `orelse return false` above it exits first.

Reproduces when the agent is unspawnable / unreachable — a broken or missing
`ghoztty-agent.exe`, or `session-persistence` turned off between runs — with a
manifest holding a `--view` window. The user's terminals genuinely cannot come
back; their viewer panes could, and silently do not.

The shape of the fix: build a null-transport `RestoreTransport` for windows with
no session-backed leaf and restore those, keeping the existing early return for
the rest (or, equivalently, move the connection resolution to the first window
that needs one). Terminal leaves inside a partially-restorable window then open
as plain local ConPTY panes, which is what a no-agent window does anyway.

*Validation:* extend `test/win32/viewer-restore.ps1` with a run whose
`GHOSTTY_LOCAL_AGENT_BIN` points at a path that does not exist: the mixed window
degrades (its terminal opens fresh) and the viewer-only window still comes back
with its recorded location. The existing agent-present run is the control.
