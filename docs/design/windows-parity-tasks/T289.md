# T289 - Activity Monitor: no visible keyboard focus anywhere in the panel (design system 2.2)

## In plain terms

Open the Activity Monitor and there is no way to tell where the keyboard is.
Tab does not move between the filter box, the checkbox, the buttons and the
process list, and the list itself never shows which row the arrow keys will
move from — so someone working without a mouse (or just working fast) is typing
into a window that never says what is listening. Worse, the arrow keys moved
the list's selection even while the cursor was in the filter box, so pressing
Down while typing a filter quietly picked a process somewhere off screen.

After this, Tab walks the panel in the order the eye reads it, every stop shows
where it is, and the process list draws a ring on the row it will act from —
which appears when the list has the keyboard and goes away when it does not.

## Goals

- [x] Tab (and Shift-Tab) cycle every control in the panel, skipping the ones
      that are not on screen
- [x] The process table shows a visible focus indicator when it has the keyboard
- [x] Arrow / Page / Home / End reach the table only while the table has focus
- [x] Row focus and row selection are two distinct signals, and it is written
      down which is which

## Summary

T285's panel is keyboard-**operable** — Escape closes it, and Up/Down/PageUp/
PageDown/Home/End move the table's selection through `ActivityMonitor.handleKey`
— but nothing on screen says where the keyboard is. The design system is
explicit about this (§2.2): *"Keyboard focus is always visible. If a control can
be tabbed to, it draws the ring. Missing focus rings are an accessibility
defect, not a polish item."*

Three concrete gaps:

1. **No Tab order.** Tab does not cycle filter -> Show all -> New Process ->
   table the way `MachineChooser.nextFocus` (a pure, unit-tested cycle) does for
   the chooser. The panel has the same shape and should reuse that pattern.
2. **The table has no focus indicator.** Selection is painted (`COLOR_SELECT`),
   but selection is not focus, and nothing on screen says which of the two the
   arrow keys will move.

   The *routing* half of this already landed with T285 and does not need
   redoing: `handleKey` refuses the navigation keys while the caret is in the
   filter EDIT, because Home/End/arrows inside a text box belong to the text
   box. The consequence is that the table is reachable by keyboard only after a
   click — which is precisely what a Tab order plus a visible ring fixes.
3. The native EDIT/BUTTONs draw the theme's own ring, so they are fine; the
   owner-drawn table region is the hole.

## Scope

- A pure `Focusable` cycle + `nextFocus` in `ActivityMonitor.zig`, mirroring
  `MachineChooser.Focusable` (:1624-1655), unit-tested.
- Route Tab/Shift-Tab through `handleKey`.
- Paint a focus ring on the table region when it holds focus, and make the
  keyboard row-movement keys apply only then (today they apply unconditionally,
  which is why the missing indicator is confusing rather than merely plain).
- Decide the row-focus vs row-selection distinction and record it: Windows list
  views draw a focus rect on the focused row separately from the selection fill.

## What landed

**The cycle.** `ActivityMonitor.Focusable` is `carousel, filter, show_all,
kill, new_proc, table` — top to bottom down the panel, then left to right along
the control bar, which is `activity_layout`'s own order. `nextFocus` is the
pure ring and `nextVisibleFocus` is the step that walks OVER a stop that is not
on screen (no carousel on a single-source panel, no Kill without a selection);
both are unit-tested, including that every stop is reached exactly once.

**Focus is now KNOWN before it can be VISIBLE.** The four native children carry
real Win32 focus and `self.focus` mirrors them (`syncFocus`, so a mouse click on
a child cannot leave the field stale). The carousel and the table are
owner-drawn regions of the panel's own window, so for those two Win32 knows only
"the panel" and the field is the only thing that says which — `WM_LBUTTONDOWN`
records the region the click landed in. `panel_focused` comes from
`WM_SETFOCUS`/`WM_KILLFOCUS` rather than from asking `GetFocus` at paint time:
`GetFocus` answers for whichever window is active, so a deactivated panel would
keep painting a ring over nothing.

**Routing.** Every key is dispatched by the focus stop. The row keys reach the
table only while the table has focus, the carousel's arrows only while the
carousel does, and a focused button keeps Space and Enter. Escape still closes
from anywhere.

**Row focus vs row selection** (the decision this task asked for, filed as
`D28`): the panel now has a CARET — `caret_pid`, keyed by pid for the same
reason the selection is, since a re-sort or a re-poll moves rows underneath it.
The ring goes on the caret row; the selection stays a fill. A row that is both
wears both, which is the split T312 already made for the chooser's rows.
Tabbing into the table establishes a caret at the first VISIBLE row and selects
nothing, so focus becomes visible without a Tab silently popping the Kill
button. What is deliberately NOT built: a gesture that decouples the two
(Ctrl+Arrow moving the caret without the selection). A plain arrow key moves
both, because this panel has no way to express the difference and a caret that
lagged behind would signal a distinction that does not exist.

**Geometry** lives in `activity_layout.zig` and is asserted at 1.0/1.25/1.5/2.0:
`focusRing` (§2.2's 2 DIP ring inset 1 DIP, both floored at a physical pixel,
with the half-pen-width correction GDI needs), `focusRingPath`, `rowRect`, and
`tableFocusFallback` — where the ring goes when no row can carry it (an empty
or fully filtered table that still holds focus), inset by the panel's own
margin because there it is a standalone element rather than a rim on a
full-bleed row.

**One thing fixed on the way:** the carousel used to paint its focus ring
unconditionally, so a card wore a ring while the caret sat in the filter box.
It is now drawn only while the carousel really holds focus.

- [x] Both `zig build test` lanes plus `zig build test-agent` green —
      `scripts\floor-lane.ps1` run per lane: `none` PASS (308s), `win32` PASS
      (345s), `agent` PASS (315s).
- [x] P1-P3 ALL PASS — `ipc-p1.ps1` / `ipc-p2.ps1` / `ipc-p3.ps1`, each ending
      `ALL PASS`.
- [x] `test\win32\activity-monitor.ps1` grows section L and the whole script is
      **ALL PASS (114 assertions)**. L asserts, on the running panel: Tab from
      the filter reaches "Show all", STEPS OVER a hidden Kill to "New
      Process...", and then reaches the table (all four read back with
      `Get-TestFocusedWindow`); a selection puts Kill BACK into the cycle, so
      the skip is dynamic; Down in the filter field selects nothing while Down
      with the table focused selects exactly one row (the panel's own state
      line is the oracle); and the caret row's left rim is bare background in a
      `Get-TestWindowPixels` capture while the filter has focus, painted once
      the table does, bare again when Tab moves focus away — with the empty
      table area below it bare throughout, so what was measured is a rim and
      not a panel-wide repaint.
- [x] A `-NegativeControl` inversion for the new load-bearing claim — L's ring
      probe is inverted (the rim is asserted painted while the FILTER holds
      focus) and that run FAILS, alongside D's existing inversion.
- [x] Unit tests for the pure halves: the cycle is a ring and backwards undoes
      forwards, every stop is reached exactly once, the visible-skip steps over
      a hidden carousel and a hidden Kill, and a cycle with nothing visible
      terminates rather than hanging the message pump.
- [x] No regression in the sibling script: `activity-monitor-remote.ps1` ALL
      PASS (33 assertions). Its E1 needed updating rather than merely
      re-running — a click below the carousel now focuses the TABLE, so it Tabs
      once to reach the carousel before arrowing.

**Not asserted, and why:** that the ring disappears when the whole panel is
deactivated. Posted input cannot activate a window off the input desktop
(activation comes from `WM_MOUSEACTIVATE` on real input), so there is no honest
oracle for it in this harness — filed as T568 rather than faked. The code path
is `WM_KILLFOCUS`, and the adjacent claim that the ring follows focus BETWEEN
stops is asserted.
