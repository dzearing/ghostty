# T1283 - The split-dim checks measure an empty colour off the dim overlay, so the dim feature has no working oracle on the test desktop

## In plain terms

When you split a pane, the one you are not using is dimmed. The checks that
prove the dimming happens read back no colour at all on the hidden test desktop,
so they fail without ever measuring anything - which means nobody is actually
watching that the dimming still works. This settles whether the checks or the
dimming is at fault, and leaves a check that can tell the difference.

## Goals

- [x] the overlay's painted fill is measurable on the background desktop, or the reason it is not is named
- [x] `split-dim.ps1` and `split-dim-viewer.ps1` are green there, or skip with a named capability
- [x] each red is re-attributed in writing: harness or product

## Summary

split-dim.ps1 and split-dim-viewer.ps1 fail with an EMPTY measured colour (got ''). The overlay is a GDI-painted top-level window, which T1115 says IS capturable on a background desktop, so this is either a helper reaching for a dead route or the overlay not being captured at all. Re-attribute it: harness or product.

## Attribution: the HARNESS, and the dim overlay was working the whole time

The overlay was captured fine. What refused it was `Get-TestWindowPixels`'
bitmap-level uniform guard (T303), which throws on a capture that is one colour
over its whole interior - the signature of a WinUI window that never GDI-paints.
The dim overlay is a single `FillRect`, so one colour is its CORRECT output, and
no reading of the finished bitmap can separate the two. The probe caught the
throw, returned `$null`, and the assertion reported `got ''`.

Reproduced before the fix: `the capture is UNIFORM - 782x274, one color over its
whole interior, still uniform after 14 attempt(s) across 2000ms`, twice per run.

Fixed by taking the opt-out T303 already provides, at the probe rather than in
the library: `Get-TestWindowPixels -Sync -AllowUniform`. What keeps the probe
honest without the guard is that it pins an EXACT colour which tracks the config
- 16,16,20 under a defaulted fill, 255,0,0 under `--unfocused-split-fill` - so a
dead capture (black, or the sentinel) fails it instead of passing for free.

Not taken, and why: making `-Sync` exempt from the uniform guard library-wide.
The justification would have been that the synchronous route already answers the
same question exactly - it prefills the DC with a sentinel and fails a window
that leaves it untouched - but a window built to paint nothing under
WM_PRINTCLIENT captured as solid BLACK rather than sentinel, so that guard did
not fire when asked to. Relaxing every `-Sync` caller on a promise that could not
be demonstrated was the wrong trade; the promise itself is now T1287.
