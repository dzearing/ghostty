# T182 - reset-context verification false-alarms once the prompt is accepted

## Summary

USER-REPORTED 2026-07-30, live: *"why did reset context fail? did it actually
fail? the banner says so but your context is reasonable."* It did NOT fail. The
continuation-verification T133 added the same morning declares failure on a
**successful** reset, then shouts about it in the log AND on a pane banner the
user then has to reason about. A verifier that cries wolf on the happy path is
worse than no verifier: the loud path is now the common path, so the one time it
means something nobody will believe it.

## Details

Evidence, straight out of `%TEMP%\reset-context-last.log` for the run the user
asked about (session `2D1184AD-5A46-411F-9C3A-C808F72E8EA8`):

```
06:47:36 verified: /clear landed (nothing left on screen)
06:47:37 typed continuation (17 chars) rc=0
06:47:38 submitted continuation rc=0
06:47:40 !!! RESET-CONTEXT FAILED: the continuation text never appeared in the pane
    | (blank lines)
    | * Photosynthesizing...
    | ctx: 0k/1000k (0%) | files: clean | v2.1.220 (Opus 5)
06:47:40 banner set rc=0
```

The clear landed, the continuation was typed AND submitted, and the resumed
session went on to work the whole turn (this is how T123 got picked up) — so
every step succeeded and the verdict is wrong.

**Mechanism.** The check searches the pane tail for the literal continuation
text. Submitting a prompt in Claude Code EMPTIES the composer and replaces it
with the working spinner, so the moment the continuation is accepted — the
success we are trying to confirm — the string we are looking for is gone. The
tail in the log proves it: `Photosynthesizing...` and `ctx: 0k/1000k` are the
resumed session already running. The verifier is looking for evidence that
success itself destroys, inside a ~2s window.

**Fix direction.** Treat "a turn is underway" as the positive signal, not the
echoed text. In the pane tail, ANY of these means the continuation was accepted:
a working/spinner indicator, a non-empty transcript above the composer, or the
literal text still sitting in the composer (the not-yet-submitted case). Only an
IDLE pane with an empty composer and no transcript is a genuine miss. Keep the
`/clear`-landed check as-is — that one is sound and it is the half that actually
detects the T133 defect. Also widen the window: 2s after submit is inside the
race, and the check costs one `+read`.

Watch for the neighbouring trap while re-testing: **T181** (`+read` transiently
returns an empty tail for a pane `+list` already reports) produces the same
empty-tail input, so the two must be told apart — a failed read is not a failed
reset, and neither should shout.

**Validation:** extend `test/win32/reset-context.ps1`. A positive control must
cover the ACCEPTED-prompt case (submit, let the pane start working, assert the
helper reports success and sets NO failure banner), and the existing negative
control (the `C-u` composer wipe deleted) must still trip the loud path — so the
run proves the alarm still fires when the thing it watches for really happens.
