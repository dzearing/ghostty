# T373 - T90d2: ViewerPane host window + controller lifecycle + native error card

### Done 2026-08-02

Four files: `webview2_iface.zig` (the vtables Microsoft hands us),
`viewer_error_card.zig` (pure, none lane), `ViewerPane.zig` (the host window,
the chain, the card), and the `App` wiring (class atom + the one shared
`webview2.Host`).

**The vtables were transcribed, not remembered.** Order is the whole contract —
a slot in the wrong position calls a different function with the wrong
arguments, in someone else's process — and this box has no WebView2 SDK on it.
So the SDK's own `WebView2.h` (`Microsoft.Web.WebView2` 1.0.3485.44) was
downloaded to a scratchpad and read: its `DECLSPEC_XFGVIRT(Interface, method)`
annotations state, per slot, which interface in the derivation chain
contributed it. Nothing is vendored; what survived is the declarations and the
slot counts, which are asserted with `@sizeOf`/`@offsetOf` in the module
itself. That was not a formality: `IID_ICoreWebView2Profile` is
`{79110AD3-CD5D-4373-8BC3-C60658F17A5F}`, and the value this session would have
written from memory differed in three places. A wrong IID does not crash — the
`QueryInterface` just fails, dark mode silently stays AUTO, and nothing ever
says so.

**`ICoreWebView2_13` is declared as 105 slots we never call, then
`get_Profile`.** Naming the 102 middle ones would be 102 chances to typo a name
that is never used; the block is one `[102]*const anyopaque` whose only
contract is its LENGTH. That is safe against a runtime NEWER than the header
because of the COM versioning rule that makes each revision its own IID: a QI
for `_13` returns a pointer whose first 106 slots are `_13`'s, whatever the
runtime's latest revision is. The live test reads a value back through
`get_Profile`, which is what proves the count.

**The live test is the ABI oracle, and it says what it proved.** It registers
the class, creates a host window under a bare hidden parent, waits out both
async hops against the real runtime, and then round-trips every slot the pane
depends on: bounds set to 640x480 and read back, resized to 320x200 and read
back, visibility toggled and read back, `ShouldDetectMonitorScaleChanges` read
back FALSE, `RasterizationScale` equal to what the pane pushed, and
`PreferredColorScheme` set dark then light and read back each time. A
transposed parameter or a shifted slot cannot survive that. It logs
`live controller ready ...` at **warn** on the success path for the same reason
T372's does: "78 tests passed" cannot tell you whether it talked to a browser
process or took the no-runtime skip, and the difference is the entire value of
the test. Measured here: it runs, and the run was confirmed by filtering the
lane down to it (78 tests vs a 77-test baseline) rather than assumed from a
green summary.

**A pane can be closed mid-creation, so neither hop carries the pane
pointer.** Creation is two asynchronous hops — wait for the shared
environment, then wait for the controller — and closing a viewer in the first
second of its life is exactly what a user does when they open one by mistake.
Both hops carry a heap `Pending` token instead: the pane clears `Pending.pane`
on the way out, and a callback that arrives late finds a null, closes the
controller it was handed (or a renderer process outlives the pane that asked
for it) and drops the last reference. Two references, never three: one the pane
holds for its whole life, one that MOVES from the environment waiter to the
controller handler without being dropped in between — so there is exactly one
place a hop can lose track of it, and it is the same place the hop ends. Both
the survive-the-close path and the environment-failure path are unit tests, with
the testing allocator as the oracle for the reference counting.

**DPI is pushed, not detected.** `ShouldDetectMonitorScaleChanges` is FALSE and
the pane pushes `RasterizationScale` itself (design §4), because the window
already tracks its own DPI and lays panes out in physical pixels under
per-monitor-v2 — two sources of truth for scale is how a pane renders at 1.25
inside bounds computed for 1.0. The wrinkle worth writing down: **a child
window never receives `WM_DPICHANGED`**, the top-level does. So the scale is
re-read from the host window on every bounds sync, which a DPI change always
causes. No new plumbing from `Window`, and no way for the two to drift.

**The pane does not reach through `parent_window`.** The colors and the scale
are snapshotted onto the pane at construction, so the whole host floor is
drivable from a test against a bare parent HWND without standing up an `App`
and a `Window` first. That is what made the live test possible at this stage at
all, given that nothing constructs a viewer from IPC until T374.
