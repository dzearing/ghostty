# T670 - Screenshot capture: Space captures a whole WINDOW, the way Mac's screencapture -i does

## In plain terms

When you take a screenshot for a feedback report you have to drag a rectangle
by hand, even when what you want is obviously one window. On the Mac the same
tool lets you hit Space and click the window instead, and it comes out
perfectly cropped. This adds that here.

**Space is reserved for this task** (T671, 2026-08-10). T671 gave the selector
a full keyboard path — arrows aim, Ctrl+arrow steps coarsely, Enter pins a
corner and Enter captures — and deliberately did NOT alias Space onto Enter,
even though the overlay is a button-shaped thing, because Space is the key Mac
uses for exactly the mode below. So it is free, and this task should take it.
The other half of that note: window-picking with Tab/Space would be a much
better keyboard answer than nudging a rectangle 32 px at a time, so the
keyboard path here matters even though T671 shipped one.

## Goals

- [x] Space toggles the selector between dragging a region and picking a window
- [x] Aiming — with the pointer or with the arrows — highlights the window
      under it, and the overlay says which window and how big it is
- [x] A click (or Enter) captures exactly that window's drawn frame, with no
      rim of desktop from the invisible resize border around it
- [x] A second Space goes back to region mode, where a drag still works
- [x] The clipboard is untouched, as it is for every other capture path

## Summary

Noticed while building T647. Mac's capture primitive is `screencapture -i -o`,
and `-i` has two modes: drag a region, or press **Space** to switch to a
window picker where hovering highlights a window and a click captures exactly
it. T647 built the region half only, which is the half a drag needs; the
window half is the one a user reaching for "a picture of THIS dialog" wants,
and it is strictly more accurate than any rectangle they could drag.

## Details

- The overlay already owns a photograph of the whole virtual screen, so the
  capture itself is the same crop it already does — what is new is picking the
  RECT from a window rather than from a drag.
- `WindowFromPoint` on the pointer, then `GetAncestor(GA_ROOT)` so a child
  control resolves to its top-level window, then `DwmGetWindowAttribute`'s
  `DWMWA_EXTENDED_FRAME_BOUNDS` rather than `GetWindowRect` — the latter
  includes the invisible resize border DWM leaves around a window, so a naive
  window capture comes out with a rim of desktop around it.
- The overlay itself must be excluded from the pick (it is the window under
  the pointer, always). It is `WS_EX_TOOLWINDOW` and ours, so skipping it by
  handle is enough.
- **As built, the walk is `EnumWindows` rather than the `WindowFromPoint` +
  `GetAncestor` pair above.** They answer the same question, but
  `WindowFromPoint` cannot be told to skip a window, and the one window that
  must be skipped is under the pointer at every point of the desktop.
  `EnumWindows` enumerates top-level windows front-to-back, so the pick is
  "the first candidate containing the point" — which is where the z-order
  rule, and the exclusion, both live, and both are unit-testable because the
  decision is a pure function over a list.
- Hover feedback: the picked window's rect is what the region rect already
  draws — bright inside, dimmed outside, same outline. So the paint path is
  unchanged; only where the rect comes from changes.
- Space TOGGLES: a second press goes back to region mode, because a mode with
  no way out is worse than no mode.

## Validation criteria

- [x] Unit tests (none lane): the mode's rect selection is pure given a
      "window rect" input — the pick clips to the desktop, and the overlay's
      own handle is never a candidate. `region_select.zig` gained eight tests
      (`toggleMode` both ways, the overlay excluded by handle, invisible /
      minimized / cloaked / empty windows unpickable and not shadowing what is
      behind them, topmost-wins, the clip on both a positive- and a
      negative-origin desktop, the window status line, and every line of
      either mode fitting the one card the template measures). Green in the
      `none` lane via `scripts\floor-lane.ps1 -Lane all`.
- [x] On-box acceptance: with the selector up, Space then a click over a
      known-geometry window captures a PNG of exactly that window's extended
      frame bounds. Section I of `test\win32\viewer-feedback-capture.ps1`
      aims at the viewer's own top-level window, reads its frame with
      `DwmGetWindowAttribute` and asserts the capture against THAT, not
      against a number the script chose: `102,94 784x592` announced, captured
      and cropped. DWM composes the background test desktop, so the
      non-circular half is live too — the capture is strictly inside the
      `GetWindowRect` rect (`800x600` outer vs `784x592` captured), which is
      the invisible resize border this mode exists to leave out.
- [x] On-box acceptance: Space toggles back to region mode, and a drag still
      works after the round trip — same section, a 140x100 drag after
      Space-Space.
- [x] On-box acceptance: the clipboard is still untouched. The existing arm
      covers the earlier captures; a second read after the window picks covers
      these (`ALL PASS (83)`).
