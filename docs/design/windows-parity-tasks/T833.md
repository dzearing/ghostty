# T833 - Banner does not repaint after collapse then expand

## Summary

Reported interactively 2026-08-14: collapsing a multi-line banner and then expanding it leaves the card unpainted/stale - the expand does not trigger a repaint. User flagged HIGH priority. User notes they may be on an older build, so FIRST verify against current HEAD zig-out debug build before root-causing; if unreproducible on HEAD, identify the fixing commit and confirm the installed build predates it. Likely area: src/apprt/win32/BannerOverlay.zig collapse/expand animation path (T149 - collapse_anim, COLLAPSE_TIMER_ID heartbeat, paintedCardHeight) and banner_layout.zig collapseHeight; suspect the expand branch fails to invalidate/repaint when the animation completes or never starts. Validation: on-box acceptance - set a multi-line banner via pane-banner.ps1, click chevron to collapse, click to expand, assert the card repaints to full height with content visible (pixel probe or WM-based check per test/win32 harness rules).

## In plain terms

A banner with several lines can be folded away with the little chevron and
unfolded again by clicking it. Folding worked; unfolding did not - the banner
made room for itself again, but the card inside it stayed stuck part-open, so
the user was left with a stale sliver of text floating in an empty gap until
something else forced it to redraw. Now the unfold animates open the same way
the fold animates shut, and finishes showing every line.

## Goals

- [x] Unfolding a banner really repaints, all the way to its full height.
- [x] The suite can tell a frame that was *drawn* from a frame that was merely
      computed, so this cannot come back silently.

## Validation criteria

- [x] Reproduced (or ruled out) on a current HEAD `zig-out` debug build; if HEAD is clean, the fixing commit is named and the report is attributed to a stale build. **Reproduced on HEAD's behavior** (a debug build with `T833_NEUTERED = true`, which restores exactly the pre-fix path): the expand painted `68, 68` - the COLLAPSED card - inside a 160px band and never again, while the animation heartbeat logged all eleven frames. The user's build was not stale.
- [x] After collapse then expand of a multi-line banner, the card repaints to full expanded height with all lines visible - no stale collapsed pixels. Measured by the new `banner paint h=` oracle, which records what a WM_PAINT actually drew: expand now paints `68,68,70,83,117,149,159,160` and ends on the settled 160.
- [x] On-box acceptance script in `test/win32/` covers the collapse -> expand -> repaint cycle with a positive control, green through the watchdog. `test\win32\pane-banner.ps1` section 6f2 gained four T833 assertions (intermediate frames painted + settled final paint, in BOTH directions); whole script **ALL PASS (123)**. Negative control `T833_NEUTERED = true` fails exactly the two expand assertions and nothing else (2 FAILURE(S), 121 passed).
- [x] Floor lane green on Windows. `scripts\floor-lane.ps1 -Lane all`, plus a new win32-lane unit test (`an expanding card repaints while the window keeps its size`) that asserts the painted height moves while the window height does not.

## Notes
