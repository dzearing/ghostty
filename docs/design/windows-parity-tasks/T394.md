# T394 - Viewer panes: forward app keybind chords out of a focused viewer (add_AcceleratorKeyPressed)

## Summary

Split out of T90g (2026-08-02). A focused viewer pane swallows EVERY app
keybind: `ViewerPane.zig` registers no key handler at all (`grep -n 'WM_KEY\|
Accelerator' src/apprt/win32/ViewerPane.zig` is empty), and WebView2 renders
into Chromium child HWNDs that never reach our WndProc. So with a viewer
focused, ctrl+shift+p opens no palette, ctrl+t opens no tab, ctrl+shift+w
closes nothing.

## Details

`docs/design/viewer-panes-windows.md` P7 pins the mechanism:
`add_AcceleratorKeyPressed` on the controller sees Ctrl/Alt/F-key combos
before the page. It checks the pane-scoped table first (T161's chords — NOT
this task), then the app keybind table, then lets the page have it.

**This task is the app-keybind leg only.** The pane-scoped chords (ctrl+r
reload, ctrl+d/ctrl+l/alt+d address bar, ctrl+plus/minus/0 zoom) belong to
T161 and land with the address bar; this one puts the dispatch spine in
place so T161 is a table, not a mechanism.

What exists to build on:

- `com.Callback` / `com.CallbackOwning` (`src/apprt/win32/com.zig`, T376) is
  the generic COM callback object — a new handler is its `Invoke` body and
  nothing else.
- `add_AcceleratorKeyPressed` / `remove_AcceleratorKeyPressed` are already
  vtable slots on the controller (`webview2_iface.zig:817-818`), typed
  `*const anyopaque`. Both need real signatures, plus
  `ICoreWebView2AcceleratorKeyPressedEventArgs`
  (`get_KeyEventKind`, `get_VirtualKey`, `get_KeyEventLParam`,
  `get_PhysicalKeyStatus`, `put_Handled`).
- The app's own chord dispatch is in `App.zig`/`Surface.zig`; the handler
  must reach the same `performBindingAction` path a terminal keypress does,
  addressed at the viewer's OWN pane (so "close surface" closes the viewer).

Care: the handler runs on the browser-process callback and must stay
non-blocking (T90a §11). Modifier state comes from `GetKeyState` at Invoke
time, not from the args.

with the viewer focused, ctrl+w and ctrl+f4 did nothing, and there is no other
keyboard path out — the user could not close the pane at all without the CLI.
Bumped P1 → P0: this is the blocking half of the viewer keyboard story.

*Validation:* `test/win32/viewer-panes.ps1` grown — with a viewer pane
focused, ctrl+shift+p opens the command palette and ctrl+t adds a tab, and
the same chords still work from a terminal pane (positive control, T157's
lesson: a keybind script that cannot prove it delivered the chord proves
nothing). Pure half: the vkey+modifier → `input.Binding.Trigger` mapping is
unit-tested in the none lane.

## In plain terms

Ghoztty windows can hold "viewer" panes — a rendered markdown file, a web
page, the task dashboard — next to normal terminal panes. Today, while your
keyboard focus is inside one of those viewer panes, every app shortcut is
dead: Ctrl+W won't close the pane, Ctrl+T won't open a tab, Ctrl+Shift+P
won't open the command palette. The web content eats every key, and there is
no keyboard way out of the pane at all. After this lands, the app's
shortcuts work the same whether you're focused on a terminal or a viewer —
close, new tab, palette, split navigation, all of it — while keys the app
has no claim on still reach the page normally.

## Goals

- [x] The WebView2 accelerator event is wired: a focused viewer hands
      Ctrl/Alt/F-key chords to the app before the page sees them.
- [x] Chords that match an app keybind perform their action, addressed at
      the viewer's own pane (Ctrl+W closes the viewer, not some other pane).
- [x] Chords that match nothing (or match terminal-content actions like
      copy/scroll/font-size) stay with the page.
- [x] The vkey+modifier → binding lookup mapping is pure and unit-tested in
      the none lane.

## Implementation notes (2026-08-06)

- Pure half: `src/apprt/win32/viewer_accel.zig` — `keyFromVk` (VK literal
  table; `Surface.zig` holds an exhaustive drift-guard test against its own
  `mapVirtualKey`), `keyEventFor` (the KeyEvent that `Binding.Set.getEvent`
  resolves — physical key first, unshifted codepoint second, which is how
  the default `ctrl+shift+p`-style unicode triggers are stored), and
  `forwards` (the window/app-scoped action subset a viewer may perform).
- `webview2_iface.zig`: typed `add/remove_AcceleratorKeyPressed` controller
  slots (19/20, offset-asserted), `ICoreWebView2AcceleratorKeyPressedEventArgs`
  (IID `9F760F8A-…`, slots offset-asserted), `KeyEventKind`,
  `PhysicalKeyStatus` (size-asserted 24 bytes), handler IID `B29C7E28-…` —
  all transcribed from WebView2.idl 1.0.2903.40.
- `ViewerPane.zig`: `subscribeAcceleratorKey` in `adoptController` (same
  Pending-token pattern as every other subscription). The Invoke resolves
  the chord against `config.keybind.set` and — only if the action is in the
  `forwards` subset — claims the key with `put_Handled(TRUE)` and POSTS
  `WM_APP_VIEWER_ACCEL` (WM_APP+21) to the pane's host window. The action
  runs from the message loop, never from inside the controller's callback:
  `close_surface` tears the controller down, and WebView2 must not be
  closed from within its own event handler. The chord is re-resolved at
  dispatch time so a config reload landing between post and dispatch wins.
- **Deviation from the task's Details, deliberate**: the handler does NOT go
  through `performBindingAction` — that is a method on a core Surface, and a
  viewer pane has no core surface at all. Instead
  `Window.performViewerBindingAction` dispatches the matched action onto the
  same Window/App machinery the core path reaches (`closeSplitPane`,
  `addTab`, `newSplitAt`, `selectTab`, `gotoSplit`, …), addressed at the
  viewer's own PaneView — which is the intent the Details sentence was
  naming ("close surface closes the viewer").
- `toggle_command_palette` from a viewer opens the palette on the window's
  first terminal surface (active tab preferred) — the palette UI is
  Surface-owned. A viewer-only window logs and does nothing; filed as an
  acceptable degradation rather than hidden.
- Binding sequences (`leader`) and `leaf_chained` bindings stay with the
  page for now: a viewer has no UI for a pending sequence prefix.
