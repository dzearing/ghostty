# T830 - Rebuild the viewer feedback composer on a WebView2 contenteditable, per D43's answer

## Summary

D43 asked which text control the win32 feedback composer should be built on and was answered on 2026-08-13 with option 2 - a second WebView2 controller hosting a contenteditable composer - NOT the recommended RichEdit. T635 had already shipped the RichEdit version while the decision sat open, so the answer is a rebuild rather than a green light: the composer moves to the existing viewer bridge, the quote block and accent bar become CSS, image chips become DOM nodes, and clipboard image paste, IME and accessibility come from the browser engine instead of being hand-carried. The decision's own mitigation is the design: create the controller lazily on first open and destroy it on close with composer state kept on the pane, and mirror the design-system numbers into the CSS from one shared source. T637's chips and T636's report writer both sit on top of the control that is being replaced, so their behaviour is the regression surface.

## In plain terms

When you report something from a viewer pane, you type into a little composer
that slides in under the toolbar. Today that box is a plain Windows text
control we drive by hand, and the things a text box is supposed to do for free
— pasting a screenshot straight in, typing Japanese or Chinese through an input
method, a screen reader reading what you wrote — are either missing or
hand-carried. The user picked the other foundation: build the composer out of
the same web view the page beside it already uses, so all of that comes from
the browser engine instead of from us. Nothing about how the composer looks or
where it sits should change; what changes is that it stops being the one part
of the app that has to reinvent typing.

This task is now the PLAN for that rebuild rather than the rebuild itself — see
the split below.

## Split

The rebuild is four coherent pieces and one turn cannot hold them, so T830 is
`skipped(split)` and the work continues in:

- **T934** — the composer web host. The text surface becomes a second,
  lazily-created `ICoreWebView2Controller` filling the pill's text rect,
  hosting an embedded contenteditable page. Plain-text parity only.
- **T935** — quotes as CSS blocks with a real per-quote id.
- **T936** — image chips as DOM nodes; paste from the engine.
- **T937** — retire the RichEdit machinery and re-point the harness.

T935 and T936 both depend on T934; T937 depends on all three.

## Design (recorded here so the children are not hollow)

**What already exists to build on.** `ViewerPane` gets its
`ICoreWebView2Environment` from `webview2.Host` (`host.request` →
`onEnvironmentReady` → `env.createController(hwnd, handler)`,
`ViewerPane.zig:3953-4035`) and keeps its own reference in `self.env` for the
life of the pane. A second controller for the composer is that same three-step
dance against the bar's own HWND — no new environment, no new user-data
folder. `viewer_bridge.zig` already defines the one message channel
(`handler_name = "viewerTOC"`) and the shim that makes `chrome.webview` look
like `webkit.messageHandlers`; the composer gets its own channel name rather
than sharing that one, because the composer is our page and the viewer's is
arbitrary third-party content.

**No fallback path is owed.** A viewer pane cannot exist without WebView2 in
the first place, so "what if the second controller fails" degrades to the same
place a failed pane already does. That is what makes replacing the RichEdit
outright acceptable rather than a second code path forever.

**The shape change that is the real work: synchronous → asynchronous.** Today
`caret()`, `readBack()`, `lineCount()` and `quoteSpans()` ask the control and
get an answer on the same stack. A WebView2 answers through `ExecuteScript`
callbacks and `WebMessageReceived`. So the ownership flips: the PAGE owns the
live document and pushes a state snapshot up on every input (text, wrapped
line count, live quote ids, live image numbers), and native keeps that
snapshot as the truth it lays out and serializes from. Everything that reads
the control becomes a read of the last snapshot; everything that writes it
becomes a message posted down. `pane.feedbackText()` stays exactly where it
is — the pane still owns what has to outlive the window, which is why the
controller can be destroyed on close without losing what was typed.

**Where the design-system numbers live.** D43's mitigation asks for one shared
source. `viewer_feedback_layout.zig` already computes the pill's text rect and
asserts at 1.0/1.25/1.5/2.0; the CSS gets its numbers from that module at
composition time (custom properties written into the page from the layout
result on each `place`), not from a second hand-maintained copy in a
stylesheet. The bar keeps painting the pill, the accent, the carousel and the
send row; only the text rect's interior becomes web content.

**Regression surface.** T637's chips and T636's report writer sit on top of the
control being replaced, and `test\win32\viewer-feedback.ps1` is the only thing
that proves the composer's undo, quote formatting and send path. Its arms are
part of each child's validation, not an afterthought in T937.
