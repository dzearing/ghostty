# T242 - The selected tab's rim traces its baseline

## Summary

User report with screenshot, 2026-07-31: *"the active tab seems to have a
horizontal line at the bottom, making it feel disconnected from the pane
below."*

Correct, and it defeats the single most important thing the strip does. The
whole selection idiom (T202, from measuring Windows Terminal) is that **the
selected chiclet is filled with the CONTENT background and merges into the pane
below it** - that merge is what marks selection, which is why there is no
underline and no accent bar. A line across its baseline re-introduces exactly
the separation the design removed.

## Root cause (VERIFIED by reading the math, not inferred)

`tab_shape.zig` composites each tab from a signed distance field. Two lines
combine to produce the artifact:

**1. The silhouette has a hard, artificial bottom edge.** `sdTab` builds the
body by extending a top-rounded rect *below* the baseline and then clipping it
square with a half-plane:

```zig
const body_round = card.sdRoundRect(x, y, .{ ..., .bottom = b + rt }, rt);
const body = @max(body_round, y - b);   // <-- half-plane clip at the baseline
```

That clip is right for COVERAGE (the tab must not paint past `bar_h`), but it
makes `y - b` the nearest "edge" for every pixel within a hairline of the
baseline.

**2. The rim is derived from that same field**, in `renderTab`:

```zig
const sd  = sdTab(fx, fy, t, m);
const rim = (cov - coverage(sd + m.rim_w)) * rim_a;
```

The rim is by definition "the ring just inside the silhouette" - so it faithfully
traces the baseline, because the SDF says there is an edge there. There isn't
one; it is where the tab meets the pane.

**The arithmetic at the bottom row** (`y = bar_h - 1`, scale 1.25, `corner_top`
6 DIP): `body_round` is about `-(rt+1) = -8.5`, the half-plane is `-1`, so
`sd = max(-8.5, -1) = -1`. Then `coverage(-1) = 1` and
`coverage(-1 + rim_w) = coverage(0.25) = 0`, giving `rim = 1.0 * rim_a`.
`rimAlpha` at `k = 1` returns `card.RIM_BOT = 0.04`, and `rim_toward` is 255 on
a dark theme - so the bottom row is lightened by about
`0.04 * (255 - 30) ~= 9` levels across the tab's full width, with a fainter
partial row above it.

A 1-2 px, ~9-level-brighter line spanning exactly the tab's width, sitting
exactly on the seam. That is the screenshot.

## The fix

**The baseline is not a silhouette edge, so it must not contribute a rim.**
Keep coverage as it is (the half-plane clip is load-bearing - without it the
tab paints past `bar_h`), and derive the RIM from the un-clipped shape:

- Add `sdTabRim()` = `min(body_round, flares)` - the same field WITHOUT the
  `y - b` half-plane - and feed the rim term from it while `cov` keeps using
  `sdTab`.
- The rim then appears only where there is a real edge: the rounded top
  corners, the two sides, and the outboard curve of each bottom flare. Along
  the baseline the rim ring falls below the drawn area and vanishes, which is
  what it should always have done.

Do **not** "fix" this by setting `RIM_BOT` to 0. That dims the rim up the whole
height of the tab to hide one row of it, trading a correct highlight for a
missing one - and it would leave the same artifact at any future
`RIM_BOT > 0`.

Check the inactive tabs in the same pass. Their baseline is also not an edge
(they meet the pane too), so they get the same treatment; the difference
between selected and unselected stays the FILL, as designed.

## Secondary check while in here

If a seam is still visible after the rim fix, the remaining suspect is a fill
mismatch: `renderTab` is handed `content_rgb` from the window's configured
background, while the pane may paint a slightly different background (T67 tint,
`background-opacity`, or a runtime background change - see **T150**). The
selected tab's fill must be **byte-identical** to the pixel the pane paints in
its top row, or the merge shows a seam no rim change can hide.

## What shipped

`sdTab` was split in two. `sdTabRim()` is the silhouette with **no baseline
clip** - the body's rounded rect runs below the baseline as before, and each
flare's box now runs to `b + rb` instead of stopping at `b`. `sdTab` is then
*defined as* `@max(sdTabRim(...), y - b)`, so the clipped and un-clipped fields
cannot drift apart: they are the same shape, differing only in whether the seam
counts as an edge. `renderTab` keeps taking coverage from `sdTab` and now takes
the rim ring from `sdTabRim`.

Both halves of the artifact needed the un-clip. The tab body's baseline was the
obvious one; the flares' box bottom was the second, and it is why the line ran
the full *flared* width rather than stopping at the tab's sides.

`RIM_BOT` was deliberately left at 0.04 (see above).

## Validation - all run on the box, 2026-07-31

- `tab_shape.zig`, new unit tests:
  - *"the selected tab's baseline carries NO rim"* - renders a selected tab and
    asserts every pixel of the seam row (clear of the side rims) is **exactly**
    `fillColor(.active, ...)`, at 1.0, 1.25, 1.5 and 2.0.
  - *"an unselected tab's baseline carries no rim either"* - same for
    `.inactive`; the selected/unselected difference stays the FILL.
  - *"the rim field keeps the tab's real edges and drops its baseline"* - the
    mechanism directly: the two fields disagree only on the seam row (tab body
    AND inside a flare), and agree to 0.001 on the top edge and the sides.
  - Negative control: reverting `renderTab` to `sd` fails exactly the two
    render tests (`3240/3310 passed, 2 failed`), and correctly leaves the
    field-level test passing.
- `zig build test -Dapp-runtime=none` exit 0; `-Dapp-runtime=win32` exit 0;
  `zig build test-agent` exit 0; `zig build -Dapp-runtime=win32
  -Doptimize=Debug` exit 0.
- `test/win32/tab-strip.ps1` gained section **2c**, an on-box pixel oracle: the
  strip's last row inside the chiclet must be no brighter than an interior row
  of the same fill. **ALL PASS (26 assertions) x3**, and `-NegativeControl`
  still fails 1/26.
  - Its own positive control, measured: rebuilt with the old rim math, the same
    assertion reports `seam=33 interior=0` and FAILS - i.e. (11,11,11) over a
    (0,0,0) fill, matching the predicted `0.04 * 255 ~= 10` levels per channel
    to within rounding. With the fix it reports `seam=0 interior=0`.
- P1 / P2 / P3 acceptance: ALL PASS.

## Secondary check: not triggered

The fill-mismatch suspect did not need chasing. After the rim fix the seam row
is byte-identical to the chiclet's interior, and that interior is
`fillColor(.active, ...)` = the configured background by construction (asserted
in `tab_shape.zig`). A runtime background change diverging from
`config.background` remains **T150**'s territory, not this one's.
