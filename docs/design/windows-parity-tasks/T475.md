# T475 - Plain `zig build` is red on Windows: libghostty pulls ssh_transport's unguarded posix.pipe2/posix.kill into an msvc-target compile

## Summary

Found while doing T473, which needed `zig build -Demit-test-exe` to get a test
binary without running it. The **default `build` step fails on Windows**, and
has nothing to do with the test exes:

```
error: the following command failed with 2 compilation errors:
  +- compile lib ghostty Debug native-native-msvc 2 errors
src\remote\ssh_transport.zig:64:25: error: type 'void' does not support struct initialization syntax
    return posix.pipe2(.{ .CLOEXEC = true });
src\remote\ssh_transport.zig:698:17: error: incompatible types: '*anyopaque' and 'comptime_int'
    if (pid > 0) posix.kill(pid, posix.SIG.TERM) catch {};
```

On Windows `posix.pipe2` is `void` and `posix.SIG` has no `TERM`, so those two
call sites only compile on a POSIX target. `ssh_transport.zig` already guards
elsewhere (`builtin.os.tag` switches at lines 142/204/209, and its tests
`SkipZigTest` on Windows) — these two were missed, and nothing on the Windows
side compiles the shared `lib ghostty` artifact, so nobody noticed.

## In plain terms

One of the ways to build this project on Windows stops with a compile error,
and has for weeks. Nobody hits it during a normal day, because the commands
people actually run skip the piece that breaks — which is the real problem:
Windows-hostile code can land in the shared engine and every check stays green.
When this lands, that build works again and a fourth check runs on every task
so the same thing cannot creep back in unnoticed.

## Goals

- [x] `zig build -Dapp-runtime=none` completes on Windows (this, not the
      argument-less `zig build`, is the command that was red — see Details)
- [x] Guard the POSIX-only call sites rather than dropping the artifact, and
      say in the code why that is the right one of the two
- [x] A standing-floor lane compiles `lib ghostty` on Windows, so the next
      POSIX-only call site is caught the day it lands

## Details

Two candidate fixes, and they are not equivalent:

1. **Guard the call sites** (`comptime builtin.os.tag == .windows` →
   `error.Unsupported`), matching what the rest of the file already does. Keeps
   the artifact building everywhere, which is the honest state if libghostty is
   meant to be buildable on Windows at all.
2. **Drop `lib ghostty` from the default step on Windows.** It exists for the
   macOS XCFramework; if it is not a Windows deliverable, building it here is
   the actual mistake and guarding the code only hides it.

Decide which by asking whether libghostty is a Windows deliverable — do not
just make the error go away.

### What the reproduction actually is (measured 2026-08-14)

The title says "plain `zig build`", and that command is **green** on this box:
`ApprtRuntime.default` is `win32` on Windows, so the default step builds the
exe and never reaches the lib branch. The red command is
**`zig build -Dapp-runtime=none`** — the same config the report's error text
names (`compile lib ghostty Debug native-native-msvc`), and the one T473 would
have been in when it went looking for a test exe.

### Which fix, and why

**Option 1, guard the call sites.** Two pieces of evidence decide it:

- `src/remote/ssh_transport.zig` was *deliberately* made Windows-compilable in
  `67892b1f6` ("compile core tests natively on Windows x86_64"), which branched
  `controlPath` per-OS for exactly this reason. The two — then four — bad call
  sites are omissions in that work, not a statement that the file is POSIX-only.
- `build.zig`'s lib branch installs `ghostty-internal.dll` /
  `ghostty-internal-static.lib` on Windows on purpose. Carving Windows out of it
  would diverge from upstream in the file main touches most, and would throw
  away the only thing on this box that compiles the shared core for the msvc
  target.

Four sites, not the two in the report — each was masking the next:

| Site | Why it only compiles on POSIX |
|---|---|
| `pipe()` → `posix.pipe2(.{ .CLOEXEC = true })` | `posix.pipe2` is `void` on Windows |
| `reapChild` → `posix.kill(pid, posix.SIG.TERM)` | no `SIG.TERM`; pid is a HANDLE |
| `closeFn` → `if (self.write_fd >= 0)` | `fd_t` is `*anyopaque`, not an int |
| `spawnChannel` → `log.debug("… pid={?d}", …)` | `{d}` cannot format a pointer |

The guards are all the comptime-early-return shape this file already uses, which
is load-bearing: a comptime-known `return` stops Zig analyzing the rest of the
body. That is also *why the test lanes never caught this* — the three tests that
reach `pipe()` open with `if (builtin.os.tag == .windows) return
error.SkipZigTest;`, so their bodies are never analyzed on Windows.

### The regression guard

Because of that, no test lane can be the guard here — only a build can.
`scripts\floor-lane.ps1` gains a fourth lane, `lib` (`zig build
-Dapp-runtime=none`), and it runs FIRST in `-Lane all`: it is a pure compile,
costs ~1s cached, and only does real work when the shared core moved.

## Validation criteria

- [x] `zig build -Dapp-runtime=none` exits 0 on Windows — run directly, exit 0
      (it was exit 1 with 2 compilation errors before the change).
- [x] Argument-less `zig build` still exits 0 on Windows — run directly.
- [x] `none`, `win32` and `agent` lanes stay green — `scripts\floor-lane.ps1
      -Lane all`.
- [x] The new `lib` lane runs inside `-Lane all` and reports PASS.
- [x] The POSIX path is unchanged in behaviour — every guard is a comptime
      Windows-only branch; `zig test src\remote\ssh_transport.zig` still runs
      its 8 non-skipped tests.
- [x] **Negative control**: with the `pipe()` guard neutered (`… and false`),
      `-Lane lib` reports `FAIL` and prints
      `src\remote\ssh_transport.zig:73:25: error: type 'void' does not support
      struct initialization syntax`. Restored → `PASS`.
- [x] **T323's positive control passes on this lane**: with
      `.relaunchable = s.T323_POSITIVE_CONTROL` in `embedded.zig`'s CAPI,
      `-Lane lib` fails naming the field; reverted → `PASS`. That closes T323,
      which named this task as the reason its only C-API-analyzing lane could
      not build.
- [x] P1 / P2 / P3 acceptance ALL PASS (25 / 20 / 16).
