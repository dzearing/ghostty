# T475 - Plain `zig build` is red on Windows: libghostty pulls ssh_transport's unguarded posix.pipe2/posix.kill into an msvc-target compile

## Summary

Found while doing T473, which needed `zig build -Demit-test-exe` to get a test
binary without running it. The **default `build` step fails on Windows**, and
has nothing to do with the test exes:

```
error: the following command failed with 2 compilation errors:
  +- compile lib ghostty Debug native-native-msvc 2 errors
src\remote\ssh_transport.zig:64:25: error: type 'void' does not support struct initialization syntax
    return posix.pipe2(.{ .CLOEXEC = true });
src\remote\ssh_transport.zig:698:17: error: incompatible types: '*anyopaque' and 'comptime_int'
    if (pid > 0) posix.kill(pid, posix.SIG.TERM) catch {};
```

On Windows `posix.pipe2` is `void` and `posix.SIG` has no `TERM`, so those two
call sites only compile on a POSIX target. `ssh_transport.zig` already guards
elsewhere (`builtin.os.tag` switches at lines 142/204/209, and its tests
`SkipZigTest` on Windows) — these two were missed, and nothing on the Windows
side compiles the shared `lib ghostty` artifact, so nobody noticed.

## In plain terms

Running the project's plain build command on Windows stops with an error. It
does not stop anyone today, because every lane people actually run names a
specific target and skips the part that breaks — but a newcomer who types the
obvious command gets a compile error and no way to tell it is harmless.

## Goals

- [ ] `zig build` with no arguments completes on Windows
- [ ] Either guard the two POSIX-only call sites, or stop building the
      msvc-target `lib ghostty` on Windows — whichever is right, not whichever
      is quicker

## Details

Two candidate fixes, and they are not equivalent:

1. **Guard the call sites** (`comptime builtin.os.tag == .windows` →
   `error.Unsupported`), matching what the rest of the file already does. Keeps
   the artifact building everywhere, which is the honest state if libghostty is
   meant to be buildable on Windows at all.
2. **Drop `lib ghostty` from the default step on Windows.** It exists for the
   macOS XCFramework; if it is not a Windows deliverable, building it here is
   the actual mistake and guarding the code only hides it.

Decide which by asking whether libghostty is a Windows deliverable — do not
just make the error go away.

## Validation

- `zig build` (no arguments) on Windows exits 0.
- Both test lanes and `test-agent` stay green (the guards must not change
  behaviour on the POSIX path).
