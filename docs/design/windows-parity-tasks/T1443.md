# T1443 - A session the agent restored from disk comes back with no scrollback until it produces output again

## In plain terms

If the background session daemon restarts - after a reboot, or when it upgrades
itself - the sessions it brings back have their recent output, but a pane you
re-open shows only the current screen with nothing above it until the program
prints something new. The history is not lost; the part of the daemon that serves
it starts empty and has no way to catch up.

## Goals

- [ ] confirm the gap on box before building anything
- [ ] a session restored from disk can serve a scrollback-bearing repaint
- [ ] and reports its alt-screen state correctly, which it also cannot today
- [ ] the catch-up cost is bounded and never paid for a session nobody attaches

## Summary

Suspected, not yet reproduced. `Session.emulator` is created lazily on the first
output the agent RECORDS (`feedEmulator`, called from `recordOutput`), so it only
ever sees bytes that arrive while this agent process is running. The raw ring, by
contrast, is snapshotted to disk and restored (T13, §5.4) - so after an agent
restart a session can hold a full ring and an EMPTY emulator.

T621 handles that safely rather than well: `handleAttach` takes the snapshot
before deciding what to replay, so no emulator means no repaint and the ring
replay stands, exactly as before T621. The pane is correct. What it does not get
is the thing T621 added - a reflowed, scrollback-bearing repaint - for as long as
the emulator stays behind, which for a quiet session is indefinitely.

## Details

First, CONFIRM it: restart the agent with a session holding deep scrollback, then
attach fresh and check whether the app logs `scrollback=true` with a non-empty
repaint, or falls back (`grid snapshot 0 byte(s)` in the agent's own log). It is
possible some restore path already re-feeds the ring; nothing found in
`session.zig` does, but this was reasoned from the code rather than run - so the
first deliverable is the reproduction, and if it does not reproduce, the finding
itself closes the card.

If confirmed, the natural fix is to REPLAY THE RESTORED RING INTO A FRESH
EMULATOR - the ring is already in memory, the emulator is side-effect-free, and
the cost is one VT parse per session bounded by the ring size. That also gives
the restored session a correct alt-screen determination, which `gridOnAltScreen`
currently answers `false` for on the same path.

Where to do it matters. At agent startup, an agent holding many sessions parses
every ring at once, and tombstones (which never attach) pay too. Deferring to the
FIRST ATTACH of each session is probably the better shape: it is exactly where
the result is needed, and an idle session never pays. Record which was chosen and
why.

## Validation criteria

- [ ] reproduce: after an agent restart, a fresh attach to a restored session is
      shown to fall back to ring replay with no scrollback-bearing repaint
      (or the reproduction fails and the card closes with that evidence)
- [ ] unit: a Session whose ring was restored from disk yields a snapshot
      carrying that history, and reports its alt-screen state correctly
- [ ] the parse is bounded and never runs for a tombstone; the choice between
      restore-time and first-attach is recorded with its reason
- [ ] on-box: `test\win32\session-snapshot-reattach.ps1` (or the agent-restart
      arm nearest it) asserts the scrollback survives an agent restart
- [ ] floor: all four lanes green
