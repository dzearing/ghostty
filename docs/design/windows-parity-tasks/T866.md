# T866 - win32 agent integrations (2/8): the hardened skills and hook scripts are not bundled in the Windows build, and the hook payload parsing still assumes jq

## In plain terms

The Mac app carries the Ghoztty skill files and the two helper scripts (the
banner updater and the busy/idle tracker) inside itself, so it can install
them for a coding agent with one click. The Windows app carries none of them,
and the scripts as written need a unix tool (`jq`) that a normal Windows
machine does not have. This task packs the up-to-date files into the Windows
build and settles how the scripts read their input without jq.

## Summary

Second slice of the T598 split. Two halves:

**1. Vendor the assets.** On `origin/main` they live at
`macos/Resources/Ghoztty/`: `hooks/ghoztty-banner.sh`,
`hooks/ghoztty-activity-state.sh`, `skills/ghoztty/SKILL.md`,
`skills/process-feedback/SKILL.md`. Take the tip-of-main copies — T598's
"vendor the HARDENED copies" table (06d50037a mkdir-mutex + mktemp +
self-heal + markdown-escaping, 1b632b812, 4b07859e4, 4df779938) is already
folded into them. Windows equivalent of the Mac app bundle: `@embedFile` into
the exe (a `GhosttyAssets`-shaped Zig module returning the text), which beats
loose files beside the exe — nothing to go missing or stale, and the
portable-zip manifest stays untouched. Keep the assets as repo files under a
shared path (e.g. `src/apprt/win32/assets/` or a platform-neutral
`resources/ghoztty/`) so the Mac and Windows builds can converge on one copy
later; note whatever you choose in the file header.

**2. The jq problem.** The scripts parse hook payloads (stdin JSON) with jq.
On-box facts measured 2026-08-15: `jq` exists here only via winget (not
guaranteed); `bash` resolves to WSL's `System32\bash.exe` on PATH, though
Claude Code on Windows ships/requires Git-for-Windows bash for its own hook
execution; Copilot CLI is absent entirely. Options to settle EMPIRICALLY
(check what the currently-working 0.8.0 plugin banner script does on this
box, measure `powershell -NoProfile` cold-start against a tool-tick hook's
budget):

- (a) Keep bash scripts, replace jq with a `ghoztty +hook-payload`-style
  native parse (the app's own JSON, per T598's guidance) — hooks stay
  one-liner `bash` commands, parsing is native and fast.
- (b) Rewrite the scripts in PowerShell (`ConvertFrom-Json` is built in) —
  no bash dependency at all, but measure startup latency: tool-tick hooks
  fire on every tool call and a 300-800ms `powershell.exe` spawn per tick is
  user-visible in agent responsiveness.
- (c) Keep bash + require jq — REJECTED already: a clean box lacks jq, and
  the Mac flow's "install jq with brew" nag is exactly the manual wiring
  this feature exists to remove.

This is a mechanism call (D46: decide, record in this file, do not file a
decision). Whichever lands, the choice must serve BOTH hook consumers the
same way (Claude today, Copilot when present), and the scripts' behavior
must stay byte-compatible with the Mac state files where the formats are
shared (banner state JSON under the app state dir).

## Validation criteria
