# T894 - ipc-p1 can fail all 21 assertions on a cold start right after the floor lanes, then pass clean on rerun

## In plain terms

The first acceptance script run after a heavy build/test session sometimes
reports everything broken when nothing is. Whoever is watching has to notice
the failure pattern, rerun it, and see it pass — time lost and trust in the
test's word eroded.

## Summary

Observed 2026-08-16 (T578 turn): `test\win32\ipc-p1.ps1` run immediately
after `floor-lane.ps1 -Lane all` finished (four lanes, ~18 min of build/test
churn) failed 21 of 23 assertions, with `Cannot index into a null array` at
the `+list --json` shape checks — the app either never came up or never
answered IPC in time, so every downstream assertion cascaded. An immediate
rerun with no changes passed 25/25. Suspicion: cold-start latency (first
launch after cache churn, AV scan of a fresh exe, or the pipe not yet
listening) exceeding the script's launch/connect wait.

Worth doing: make the P1 launch wait tolerant of a slow first start (poll
the endpoint with a generous cold-start budget before the first assertion,
and make assertion 1 fail with "app never answered within Ns" instead of a
null-array cascade), and check whether P2/P3 share the same shape.

## Validation criteria

- [ ] The root cause of the null-array cascade is identified from a repro or
      from instrumentation added to the script's launch path.
- [ ] A cold start after heavy churn (or a simulated slow launch) no longer
      fails wholesale: either the wait absorbs it or the script reports a
      single clear "app did not answer" failure instead of 21 cascaded ones.
- [ ] P2/P3 checked for the same launch-wait shape; fixed or noted why not
      applicable.
