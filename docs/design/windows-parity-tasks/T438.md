# T438 - upgrade-ghoztty-windows.ps1 resume types the prompt and Enters in two calls, so the framing that fixes T428 can never apply to it

## Summary

T428 made `+send-keys` frame a text run as a bracketed paste so the key run
after it submits — but only when ONE invocation carries both. The upgrade
script's RESUME-REUSE path deliberately splits them (type, verify arrival,
then Enter), so its Enter is still the bare unframed CR that failed on
2026-08-03. Every delivery goes through this path.

## In plain terms

When the app upgrades itself it has to hand the running session a prompt and
press Enter for it. It types the prompt, checks the prompt really arrived, and
only then presses Enter — a good habit that exists because a half-arrived
prompt once turned into a chat message. The fix that made Enter reliable
everywhere else cannot reach this path, because it works by delivering the
prompt and the Enter together, and this path deliberately delivers them apart.

## Goals

- [x] The upgrade resume both VERIFIES the prompt arrived and SUBMITS reliably
- [x] No regression to the arrival gate — a fragment must still never be
      submitted

## Details

`scripts/upgrade-ghoztty-windows.ps1:586` sends the prompt (via
`--keys-file=`, from `New-LoopSendKeysText`), then polls the pane up to ~8s for
`Test-LoopPromptArrived`, then sends `Enter` on its own at line 619. The gate
between the two is load-bearing and documented at length: checking BEFORE the
Enter is what makes it trustworthy, because `/reset-context` clears the pane
and a post-submit check would race its own success (T210, T200).

So this cannot be fixed by merging the two calls without losing the gate.
Options, none free:

1. **Frame a lone `--keys-file=` text run** even with no key run after it.
   Principled — `--keys-file` means "content the caller did not type", which is
   paste semantics — and it fixes this path with the gate intact. The cost is a
   behaviour change for anyone using `--keys-file` to feed a shell commands to
   EXECUTE: inside a frame, a trailing newline pastes instead of running.
   Filed as a decision on T428 rather than assumed.
2. **Re-type after the gate**: verify, clear the composer, then re-send prompt
   and Enter as one call. Doubles the typing and the failure surface.
3. **A distinct "submit" verb** that is unambiguously a keypress. Largest
   change; also the only one that helps callers who cannot batch.

## Exposure

Mitigated, not absent: if the Enter is swallowed the prompt sits in the
composer and the watchdog re-enters after up to ~45 min of dead time (T139).
That is the slow-death shape the loop-reliability tasks exist to remove, so it
is worth closing — but it is not the same severity as the reported T428 stall,
which had no automatic recovery at all.

## Resolution (2026-08-07)

Option 1 was ruled out by **decision D4** (a lone `--keys-file=` run stays
unframed), and options 2 and 3 both trade away something real — re-typing after
the gate submits text nobody verified, and a "submit" verb would have to emit
the *same* bytes to be any different, i.e. a frame.

So the fix is on the submit side, and it is the smallest thing that can work:
**the submitting call brings its own text run.**
`Get-LoopSubmitArgs` (`scripts/loop-session.ps1`) returns `' ' Enter` instead of
a bare `Enter`, which makes that call a mixed text+key send — the one shape the
CLI frames. The pane therefore receives a closing fencepost immediately before
the CR, which is exactly what makes the CR a keypress rather than a newline
inside pasted text.

The gate is untouched: the prompt is still typed, read back intact, and only
then submitted. And a space is the payload that cannot cost anything — every
failure mode degrades to at worst a trailing space on the prompt:

| what happens | result |
|---|---|
| frame honoured | space appended, CR is a keypress, prompt submitted |
| pane has mode 2004 off | ` ` `\r` unframed — today's bytes plus a space |
| paste ignored by the TUI | the verified prompt is submitted unchanged |

That is the property the rejected alternatives lack. Holding back the prompt's
last character (gate the head, frame the tail) submits a **truncated** prompt if
the tail is dropped, and backspace-then-retype eats a real character if the
retype is — both re-open the fragment hole the gate exists to close.

**This closes T438, not the family.** T562 (P0, filed the same morning) is the
other half: `reset-context.sh` already sends its continuation and Enter in ONE
framed call and the loop was still found sitting at a full composer, so framing
is necessary and demonstrably not sufficient — a submission GATE (verify the
composer emptied, re-send bounded) is what T562 adds, and its own validation
list already names the upgrade's reuse path as a consumer of that helper. What
T438 removes is the one path where the framing could never even be attempted.

Measured, not reasoned: round 6 of `send-keys-bracketed.ps1` captures the
two-call shape as `68656c6c6f20776f726c64` + `0d` with no fencepost anywhere
even with mode 2004 on (the pre-fix oracle — no CLI change could have reached
it), and round 7 captures the new submit as
`…1b5b3230307e` `20` `1b5b3230317e` `0d`.
