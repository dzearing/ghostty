# T1209 - Prove the in-app update takes the graceful route end to end

## In plain terms

Ghoztty can now update itself, and the app now knows how to be closed and
reopened by an installer. Nobody has yet watched those two things happen
together, so "click the notification and it just works" is still a claim rather
than a measurement.

## What exists and what is missing

- T1178's `test\win32\update-apply.ps1` drives the applier end to end against a
  package msiexec rejects: 36 assertions, all of them up to and through
  msiexec's verdict. It never observes a SUCCESSFUL replacement, because that
  needs a signed, versioned MSI and would replace the user's installed Ghoztty.
- T1204's `test\win32\install-restart.ps1` measures the app half live - the
  registration Windows reports, the agreement to close, the exit - but drives it
  with the messages an installer would send, not with an installer.

The gap is the join: an actual replacement of a running build by the updater,
with the sessions and the reopen observed. The honest place for that is a
THROWAWAY product identity (`build-msi.sh --test-identity`), which is exactly
what that flag exists for.

## Goals

- [x] The whole sequence a user actually sees - running terminal, close,
      replace, reopen - is measured as ONE run rather than three halves.
- [x] The close is the one an installer performs, not a kill a test can do and
      an installer cannot.
- [x] A live session is open across it, and answers afterwards.
- [x] Windows Installer's own account of the install is the evidence for "no
      reboot", not our applier's summary of it.

## Validation criteria

- [x] A throwaway-identity package is installed over a running throwaway build
      by the in-app update path, and the app comes back on its own -
      `test\win32\update-graceful.ps1` sections D and E: the applier is armed
      on the LIVE app's pid (D1), waits instead of installing over it (D3), the
      app is closed with the Restart Manager's own messages and exits (D4/D5),
      msiexec succeeds (D7), and a terminal nobody started is running again on
      the far side (E1/E2).
- [x] No reboot is requested at any point - section F, from Windows Installer's
      own event 1033 (`success or error status: 0`, so not the 3010 the applier
      would have folded into success) plus an empty
      `PendingFileRenameOperations` for the product.
- [x] A pinned session opened before the update is still attachable after it -
      section G: the holder that owned the session before the install is still
      running (G1), the reopened terminal has a pane (G2), and that pane answers
      a typed command (G3, `Test-PaneLive`). B6 is its control: the same probe
      passed before the update, so G3 cannot be green for a trivial reason.
- [x] The user's installed Ghoztty is provably untouched by the run - section H
      and the cleanup, measured on every run against the file count and the
      exe's timestamp captured before anything started.

## What was done

`test\win32\update-graceful.ps1` (42 assertions, ALL PASS 2026-09-01) - the
join, plus two pieces of machinery it needed:

- `test\win32\lib\ThrowawayProduct.ps1`, the throwaway product identity
  lifted out of `update-real-msi.ps1` and shared with it: packages, processes,
  install directory, uninstall entries and version read-back. It also gained the
  refusal the private copy never had - `Stop-ThrowawayInstances` and
  `Remove-ThrowawayProduct` REFUSE a directory that is the user's install rather
  than merely filtering away from it.
- `scripts\msi-test-identity.ps1 -ProductVersion`, which mints a synthetic
  PREDECESSOR of a published package.

## The finding that shaped it

The obvious pair - install win-v1.35.0, upgrade to win-v1.36.0 - cannot measure
this at all, and the first run said so: `D5 and it exits, instead of leaving its
files locked` FAILED, the applier refused to install over a live app, and its
exit code was 1. That is correct behaviour end to end. **The build being
REPLACED is the one that has to know how to close, and win-v1.35.0 predates
T1204.** The first graceful update the fork ever performs will therefore not be
graceful; every one after it will.

So both sides of the test are the SAME published package (win-v1.36.0), with the
older side registered at a lower ProductVersion. The install is a real major
upgrade between two real products and both builds carry the shipping
close-and-reopen code. That failing first run is also this harness's teeth
check: the assertions that matter have been observed going red against a build
that genuinely lacks the feature.

`-ProductVersion` turned up a latent defect in the identity rewriter on the way
in. Writing `Property.ProductVersion` frees a string-pool entry it SHARES with
`Upgrade.VersionMin`/`VersionMax` (all three spelled `26.8.3110` in the
published package), and both Upgrade cells read back empty. Neither the repair
pass nor the verification could see it: `Property|Value` is on the intended-cell
list and `Upgrade` is in `$skipTables`. A blank `NEWERVERSIONFOUND.VersionMin`
is unbounded, which makes every install of that package abort with "a newer
version is already installed" - a package broken in a way nobody finds until
they try to use it. Fixed with a fourth session that re-asserts the identity
cells and the version bounds after the repair pass, and a verification for the
bounds so it cannot regress silently.
