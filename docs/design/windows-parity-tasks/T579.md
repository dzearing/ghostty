# T579 - A release can still ship macOS-only, because nothing notices when the newest v tag has no matching win-v release

## In plain terms

Windows downloads went three weeks stale and nobody found out from a red
build, an alert, or a broken link — every link kept working, it just handed
people an old build. T577 made a Windows release possible again, but the way
it goes wrong is unchanged: someone forgets a step and everything looks fine.

## Summary

Until the Windows branch merges back into `main`, a full release is TWO tag
pushes: `vX.Y.Z` on main for macOS, and `win-vX.Y.Z` on
`users/dzearing/windows-amd64` for Windows (T577 explains why one tag cannot
do both — a workflow runs from the tree of the ref that triggered it, and main
has no `src/apprt/win32`).

The runbook now says so. Nothing enforces it. Skipping the second push
produces no error anywhere: the macOS release succeeds, the website's Windows
card keeps pointing at the previous `win-v` release, every link answers 200,
and `update_check.zig` correctly reports "no update" to installed builds
because there genuinely is none. That is precisely the shape of the original
failure — the system is silent when it is behind, and the only signal is a
person noticing a date.

## Details

The check itself is small: the newest `vX.Y.Z` release and the newest
`win-vX.Y.Z` release should carry the same version, and a gap older than one
release is a problem. What needs deciding is where it lives, since each place
catches a different mistake:

- **In `release.yml`, as a final non-blocking step** — catches it minutes
  after the macOS release, while the person who cut it is still there. Cannot
  block the DMG (a Windows failure must never interrupt notarization), so it
  has to be a warning or an issue, not a red job.
- **As a scheduled workflow** — catches it even when the second tag was pushed
  and its run then failed, which the release-time check would miss. Costs a
  recurring run and a place for its output to be seen.
- **In the existing acceptance script** (`website-windows-download.ps1`, which
  already talks to the live site under `-RequireNetwork`) — catches it on this
  box, in the loop, with no new CI surface, but only when someone runs it.

Whichever, the assertion is about **version drift**, not link liveness: the
existing checks already prove the links resolve, and they resolved throughout
the three weeks the page was stale.

This becomes much simpler at merge-back, when one tag fires both workflows —
but it does not become unnecessary: a Windows run that fails after a
successful macOS run leaves exactly the same silent gap.

## Validation criteria

- [x] Something reports when the newest `vX.Y.Z` release has no `win-vX.Y.Z`
      release at the same version, and names both versions in its output —
      `scripts\check-release-parity.ps1`, run live 2026-08-16: `GAP: newest
      macOS release v1.33.0 has no matching win-v1.33.0 release / newest
      Windows release: win-v1.31.0 (2 release(s) behind)`, exit 1. CI runs it
      via fork-ci.yml's `release-parity` job on every push to this branch.
- [x] It is proven against the real failure: harness section A1 feeds it the
      pre-T577 state (newest `v1.31.0`, newest `win-v1.4.1`) and asserts exit
      1 with both versions named (`test\win32\release-parity.ps1`, ALL PASS).
- [x] It reports nothing when the two are in step — harness A2 (matched pair,
      exit 0), A3 (drafts/prereleases ignored), A4 (tip/rc tags ignored), A5
      (Windows ahead is not a gap).
- [x] It cannot fail the macOS release — the check lives in fork-ci.yml
      (this branch) only; harness B4 asserts release.yml never references the
      checker, so signing/notarization is structurally out of reach.

## Resolution (2026-08-16)

Mechanism call (fails the experience test, so decided here, not filed): one
PowerShell implementation, `scripts\check-release-parity.ps1`, used by both
CI and the on-box harness so the two cannot drift. Detection lives in
fork-ci.yml as its own `release-parity` job on every push to the Windows
branch — the parity loop pushes many times a day, so a forgotten win-v tag is
a red job within hours; a scheduled workflow was rejected because schedules
only fire from the default branch (main), and a release.yml step because this
branch cannot edit what a v tag runs (the workflow runs from main's tree).
Guard row `release-parity` ties the checker + fork-ci.yml to the harness.

The check immediately caught a real live gap: v1.32.0 and v1.33.0 shipped
macOS-only. Filed T895 (P1) to publish win-v1.33.0; fork-ci's release-parity
job stays red until it closes, which is the intended loudness.
