# T123 — banner table columns use a fixed 360pt cap

## Summary

Banner table columns use a FIXED 360pt cap on Windows — `BannerOverlay.MAX_CELL_W = 360.0` is the exact constant main replaced in `1d56c6948`+`c94a8158a`; CLAUDE.md (now merged) documents the post-fix contract: column widths derive from the pane's CURRENT width so the banner reflows live on resize and never blocks the pane from shrinking (even a long unbroken token breaks mid-string), and a cell is capped at 3 wrapped lines with a tail ellipsis so one nasty cell can't blow up banner height. Windows currently satisfies none of that, so the merged CLAUDE.md now over-promises for win32 — fix the code, don't weaken the doc. **RE-REPORTED BY THE USER 2026-07-29** — *"Even the banner has the same stupid bugs i fixed in the mac client a week or 2 ago! The text in the table has fixed width and doesn't use available space."* Still unfixed and still verifiable by inspection: `src/apprt/win32/BannerOverlay.zig:68` `const MAX_CELL_W: f32 = 360.0`, consumed at `:605`. PRIORITY RAISED — this is a user-visible regression against a bug already fixed on the Mac, and it is cheap: the Mac fix (`1d56c6948`) replaced the constant with a pane-width-derived budget, so this is a port of known-good logic, not a design task

## Details

`BannerOverlay.MAX_CELL_W = 360.0` is the exact constant main replaced across
`1d56c6948` and `c94a8158a`. The merged CLAUDE.md now documents the post-fix
contract:

- Column widths derive from the pane's **current** width, so the banner reflows
  live as the pane resizes and can never block the pane from shrinking — even a
  long unbroken token breaks mid-string.
- A cell is capped at **3 wrapped lines**; beyond that it tail-truncates with an
  ellipsis, so one nasty cell cannot blow up the banner height.

Windows satisfies none of this today, which means the merge left CLAUDE.md
**over-promising for win32**. Fix the code rather than weakening the doc — the
resize-blocking half is a real usability bug (a banner can currently pin a
minimum pane width), not a cosmetic one.

**Validation:** a banner with a wide table must let the pane shrink to its
normal minimum; a cell with a long unbroken string must break rather than
overflow; a very long cell must stop at 3 lines with an ellipsis.

## Outcome (2026-07-30) — DONE

The Mac fix ported, and the row's "port of known-good logic" framing held: the
algorithm is Mac's `columnWidths(natural:available:)` line for line. What did
NOT port was the delivery mechanism — Mac feeds the pane width down through a
SwiftUI `GeometryReader`; win32 has no such thing, so the width is fed
top-down through the layout call that already runs on every resize:
`Window.layoutNode` → `Surface.bannerLayoutInset(slot_w, slot_h)` →
`BannerOverlay.insetHeight(scale, pane_w)`. One-way, no feedback loop possible
(the loop is exactly what `c94a8158a` had to break on the Mac).

What landed:

- **`banner_layout.zig`** grew the pure math: `columnWidths` (fits → exact
  natural widths; overflows → max-min fair share, narrowest first; width
  unknown → the old 360 cap, so the first paint is never absurd; width known
  but tiny → bounded equal shares, which is what stops a banner from ever
  being a minimum pane width), `fitWithEllipsis`, and `utf16PrefixBytes` (the
  bridge from what GDI counts to the byte slices tokens hold, so a mid-string
  break can never land inside a codepoint or split a surrogate pair).
- **`BannerOverlay.zig`**: `MAX_CELL_W` is gone. `renderTable` takes the
  available width; `breakWideTokens` + `prefixFitting` (one
  `GetTextExtentExPointW` per chunk, not a measure-per-prefix loop) break a
  long unbroken token mid-string; cells cap at `MAX_CELL_LINES` = 3 with a
  tail ellipsis whose fit is computed by `fitWithEllipsis`.
- **`ensureContentHeight` measures at the REAL content width** — it used to
  measure at `1 << 20`, i.e. infinity, so the reserved band was computed from
  a layout that could never be the one painted. Measure and paint now go
  through the same width, which is what makes the band track a rewrap.

**The band height IS the oracle.** Every new assertion in `pane-banner.ps1`
section 6g counts display rows via the overlay's height — self-relative, so it
needs no pixel constants and survives any DPI. `ALL PASS (54)` ×3.

**Negative control** (`T123_NEUTERED`, kept in the source so it can be re-run):
flipping it restores the pre-fix sizing and fails **exactly the 6 section-6g
assertions, nothing else** — and the numbers are the user's complaint, measured:

| assertion | fixed | pre-fix |
|---|---|---|
| wide pane, >360px value must not wrap | 121 px (== short) | **146 px** (wrapped with room to spare) |
| narrowing 1400 → 520 px must reflow | 121 → 146 px | **146 → 146** (never moved) |
| 90-char unbroken token must break | 171 px (2 lines) | **121 px** (one clipped line) |
| 4× the text must not grow a capped cell | 171 == 171 px | **196 vs 446 px** |

The pane itself measured 1382 → 502 px across that resize, so the "a banner can
pin a minimum pane width" half is proven closed by measurement, not assertion.

**T184** (text/heading/list blocks still clip instead of wrapping; same user
complaint, one block type over) and **T183** (a non-hermetic agent-server test
that panics on a null when its temp dir vanishes, which took the none lane red
