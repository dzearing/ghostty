# T493 - macOS: a pane named window-N can still collide with a later minted window name

## In plain terms

Panes and windows share one namespace for names. You can name a pane anything,
including something that looks like an automatic window name - "window-9". Open
enough windows after that and one of them is handed the same name, so two
different things answer to it and commands aimed at one can hit the other. On
Windows a window in that position now quietly takes a different name instead;
macOS still lets the clash happen.

## Summary

`565b77a58` (Mac) reserves adopted **window** names against the auto allocator,
which is the common case and the one that mattered. It does not cover a name
adopted by a **pane**: `+split --name=window-9` registers `window-9` to a pane,
the allocator knows nothing about it, and the ninth window of that run mints
`window-9`. The registry keeps the incumbent (the pane), but the controller
still calls itself `window-9` - so `+list` advertises a window `target` that
`+close`/`+rename`/`+set-banner` route to a pane.

win32 closed this in T121 with the second half of the same fix: `register`
reports whether the caller actually holds the name, and a window that lost the
race mints a fresh one rather than recording a name that routes elsewhere
(`IpcRegistry.RegisterResult`, `Window.init`). Mac's
`registerRestoredRemoteWindow` has the live-window check but the ordinary
`windowName` assignment path does not.

## Details

Two candidate shapes, either fine:

1. Reserve pane names too - `IPCServer.register` calls
   `BaseTerminalController.reserveWindowName(name)` for every registered name,
   not just window ones. Cheapest, and symmetric with the existing reservation.
2. Mirror win32: make registration report whether the target holds the name and
   have the controller re-mint on a loss. More code, but it also covers a name
   taken by anything else in future.

Note this is a much narrower hole than the restore duplicate T121/`565b77a58`
fixed - it needs a deliberately window-N-shaped pane name - which is why it is
P2 rather than P0.

## Validation

- Unit: `+split --name=window-9` (or the registry equivalent), then mint nine
  window names and assert the ninth window does not report `window-9` as its
  target.
- E2E: with a pane named `window-9` live, open windows until the counter
  reaches 9 and assert `+list` has no duplicate `target`, and that
  `+send-keys --target=window-9` still reaches the PANE.
