# T1427 - A pending revocation only completes if the APP is launched again - the agent keeps the machine online meanwhile

## Summary

T1424 arms a pending revocation and retries it from the app: at launch and on a backoff while the app runs. The agent is not in that loop, and it is the process that actually keeps this machine online - it holds the same relay.env credential and keeps its control link up. So between a Sign Out Anyway and the next time the user opens Ghoztty, the machine is still listed and still reachable, and if they never open it again (they signed out because they are done with this box) it stays that way forever. The agent should complete an armed revocation itself - it is already long-lived, already reads the same directory, and already knows when the relay came back, which is the signal the app has to approximate with a backoff. Watch the ordering: whichever side wins must clear the record and the credential exactly once, and a 401 must stay as narrow as it is in relay_revoke_pending.nextAfter.

## In plain terms

You told Ghoztty this computer is not yours any more, it could not reach your
account to say so, and you signed out anyway. The window you were looking at
remembered that and kept trying — but the background service that is what
actually puts this computer on your account carried on as if nothing had
happened. So the machine stayed in your list, and stayed reachable from your
other computers, until the next time you happened to open Ghoztty here. If you
signed out because you were done with this box, that was never.

Now the background service handles it: within a few seconds it takes this
computer off your account's network, and it keeps asking to be removed properly
until your account answers — with no window open anywhere. Your local terminal
sessions keep running the whole time; only the sharing goes away. If it turns
out you were not leaving after all, signing back in here brings it straight
back.

## Goals

- [x] The agent takes the relay uplink DOWN as soon as a revocation is armed,
      without needing a network, so the disowned-machine window is seconds
      rather than "until the app is launched again"
- [x] The agent completes the revocation itself, on T1424's existing rules —
      no second opinion about what a 401 means
- [x] Signing back in on this machine (or re-enrolling it) brings the uplink
      back, so the hold is never a one-way trip
- [x] The two reconcilers that can write the desired link state do not fight:
      one veto, checked first, and only one of them resumes
- [x] Local sessions are untouched by the park

## Validation criteria

- [x] **The agent parks the uplink when a revocation is armed** — section 5 of
      `test\win32\agent-sharing-uplink.ps1`: a live sharing-enabled agent stops
      dialing `GET /v1/agent/control` within one tick of `pending-revoke.json`
      appearing, and stays stopped well past its 3s base backoff. ALL PASS (25).
- [x] **The agent completes the revocation itself, with no app running** — same
      section: `POST /v1/agent/deenroll` arrives at the loopback relay from the
      agent process. This is the deliverable, and nothing else on the box
      observes it.
- [x] **A relay that gives no answer does not strand the machine** — same
      section: the record survives the 404, which is what keeps the uplink down.
- [x] **The hold releases when the machine is on an account again** — same
      section: clearing the record (the sign-back-in path) is announced and the
      uplink dials again.
- [x] **The rules are pure and unit-tested** — `verdict` and the `apply` state
      machine over a real `LinkControl` in `src\remote\agent\revoke_watch.zig`;
      `zig build test-agent` PASS (floor-lane agent, 418s).
