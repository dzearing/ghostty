# T1183 - An image opened in a Windows viewer pane shows as text instead of a picture

## In plain terms

Open a screenshot or a PNG in a side pane today on Windows and you get a wall
of garbled characters, because the pane treats every file as source code. It
should show the picture, let you zoom and pan it, and snap between "fit the
pane" and "actual size" the way any image viewer does.

## Summary

Main intake 2026-08-30 (range `772e4fc3a..origin/main`). Upstream commit
**fc7e36356** *"feat(viewer): native image panes, and an always-pinned nav
bar"* added `macos/Sources/Features/Viewer/ViewerImageView.swift` (+581) plus
`ViewerSplitLeaf.swift` / `ViewerView.swift` wiring, with
`macos/Tests/Ghostty/ViewerImageTests.swift` (+429) as proof.

The Mac behavior to carry across, from that commit's own reasoning:

- A dedicated image surface, NOT an `<img>` in the web view - the Mac chose
  native because trackpad feel was the requirement and WebKit's magnification
  has no notion of the image's natural size. On Windows the equivalent
  question is GDI+/Direct2D in the pane vs. a WebView2 document; read the
  Swift diff before deciding, and record the call in this file (mechanism, so
  it is this seat's decision, not a D-decision).
- **100% means one image pixel per DEVICE pixel** - the only definition where
  nothing is resampled, and most of what these panes show is screen capture.
- **Best-fit never upscales**, so a small icon stays crisp at its real size;
  when fit and 100% coincide the first double-click goes to 200% so the toggle
  always toggles.
- Zoom is anchored at the gesture centroid; pan has elastic edges and
  momentum; double-click (or two-finger double-tap) toggles fit vs 100%.
- The pane keeps a real history entry, its address, Home, `+list`'s url,
  session restore, and the same in-page error card every other file mode uses.

The Windows split half of the nav-bar change in the same commit is T1185.

## Goals

- [x] A picture opens as a picture, fitted to the pane, in every format the Mac
      extension table names.
- [x] The three contested rules (100% = one image pixel per device pixel,
      best-fit never upscales, the double-click always toggles) live in ONE
      place and are asserted without a browser.
- [x] Zoom and pan feel like an image viewer, not like page zoom.
- [x] Nothing else about the pane changes: history, address, Home, `+list`,
      session restore and the error card all still work.

## Validation criteria

- [x] `+split --view=<file>.png` (and .jpg/.gif/.webp/.svg) shows the image,
      not text. Verified: `test\win32\viewer-image.ps1` sections A, D, E - the
      picture is fetched through the pane's own origin with an image MIME type,
      which a source view never does, and the `.txt` control in section I
      produces neither line.
- [x] Zoom anchors where the gesture is; pan is bounded. Verified: the anchor
      arithmetic is `src\viewer\image.js`'s `setTransform`, and panning is the
      scroll container's own - which is what buys precision-touchpad panning,
      inertia and overlay scrollbars instead of a hand-rolled win32 scroller.
      Chromium's ctrl+wheel PAGE zoom is taken (`preventDefault` on a
      non-passive listener) so the picture zooms rather than the document.
- [x] Double-click toggles best-fit and 100%; 100% is one image pixel per
      device pixel at every display scale; best-fit never upscales; the
      fit==100% case toggles to 200%. Verified two ways: the arithmetic in the
      none lane (`viewer_image.zig` - "double-click toggles fit and 100%, and
      still toggles when they coincide", "fitZoom shrinks a large image and
      never enlarges a small one", "cssScale turns a zoom into the transform
      the page applies"), and that those numbers reach the picture in
      `viewer-image.ps1` section B, which recomputes the fit from the pane's
      reported viewport and asserts the pushed scale is `zoom/dpr` at this
      box's real dpr of 1.25 - plus section C, where a 16px icon opens at
      fit=1 rather than blown up.
- [x] The pane still reports its url in `+list --json`, restores with the
      session, and shows the standard error card for a missing/corrupt file.
      Verified: `viewer-image.ps1` section F (`type: viewer`, `url` = the file's
      own path), section H (a `.png` that is not one gets "Cannot display this
      image" naming the file), and section G (`+reload` re-fetches under a new
      revision). Session restore needs no new code: `Mode.image.isFile()` is
      true, so the location round-trips exactly as markdown's does.
- [x] An on-box acceptance script in `test/win32/` covers the above, with a
      `-NegativeControl` arm that scores red. Verified: `viewer-image.ps1` ALL
      PASS (40 assertions); `-NegativeControl` scores exactly the 2 failures its
      header declares.
- [x] Floor lanes green (`scripts\floor-lane.ps1 -Lane all`) plus P1-P3.
