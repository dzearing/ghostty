# T617 - An acceptance script can go silently red for days when another task changes what it reads

## In plain terms

The Windows test scripts are only run when someone touches the thing they test.
So when a change alters something a *different* script was checking, that script
quietly starts failing and nobody finds out — in one case for six days, until a
later task happened to run it. A test that has stopped testing is worse than no
test, because the tracker records it as green.

## Summary

Found while validating T339 (2026-08-08). `test/win32/chooser-restore-all-remote
.ps1` had been failing assertions A and G since **2026-08-02**, and the tracker
recorded it as ALL PASS (32) from a run 72 minutes before the change that broke
it:

- T336 landed 02:46 and its script passed at ~02:22.
- **T338 landed 03:58** and re-keyed the agent's layout blobs from the window's
  IPC name onto its stable UUID.
- The script's fixture oracle looked the blob up by `key -eq 't336-multi'`,
  which from then on matched nothing.

The failure then MASQUERADED as a product defect rather than reading as a broken
oracle, because of a PowerShell trap: `$rec` was `$null`, and
`@($null.session_ids).Count` is **1**, so "no record at all" printed as "the
window's blob claims 1 session id" — a plausible-looking capture bug. (The oracle
is fixed in T339's commit; the store had a correct 3-id blob the whole time.)

## Details

Two separable gaps:

1. **Nothing re-runs a script whose SUBJECT was not touched.** The floor is
   P1–P3 plus the task's own script. A change to the agent's on-disk keying,
   the manifest schema, a log line's wording, or an IPC field can invalidate any
   of the 80+ scripts, and only the ones the author thinks of get re-run.
2. **A red script is indistinguishable from a red product.** Every script ends
   in one `ALL PASS` / `N FAILURE(S)` line, which is what makes a sweep cheap —
   but nothing records that a script WAS green on a given commit, so a
   regression has no "since when".

Worth considering, cheapest first:

- A **sweep runner** (`scripts/acceptance-sweep.ps1`) that runs the whole
  `test/win32/*.ps1` suite sequentially (they must not overlap — T401) and
  writes a per-script PASS/FAIL row plus the commit, so a red script has a first
  bad day. Long, but it is a background/overnight job, not a per-turn cost.
- A **staleness surface**: the dashboard already knows task dates; a script's
  last-known-green commit could sit beside it, so "green as of 6 days and 40
  commits ago" is visible.
- The **PS5.1 null trap** itself is worth one shared helper: every fixture that
  counts a JSON array off a possibly-absent record can print 1 for "absent".
  `test/win32/lib/` has no `Count-Or-Zero`; it should.

## Validation criteria

- [ ] A sweep can be run with one command, ends with a per-script table, and
      exits non-zero if any script is red.
- [ ] The sweep's own result is recorded somewhere durable (a JSON under
      `docs/design/` or `temp/`) with the commit it ran at, so "since when" is
      answerable.
- [ ] The scripts it flags red on its first run are triaged into tasks (or
      fixed), so the baseline it establishes is a true one rather than a wall of
      known-red.
- [ ] Whatever the sweep costs, it does NOT run scripts concurrently (T401).
