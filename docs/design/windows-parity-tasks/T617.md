# T617 - An acceptance script can go silently red for days when another task changes what it reads

## In plain terms

The Windows test scripts are only run when someone touches the thing they test.
So when a change alters something a *different* script was checking, that script
quietly starts failing and nobody finds out — in one case for six days, until a
later task happened to run it. A test that has stopped testing is worse than no
test, because the tracker records it as green.

## Goals

- [x] One command runs the whole acceptance suite and reports a table
- [x] A run says which commit it measured, not just when it happened
- [x] A verdict that changed is attributable to a range of history
- [x] The null-count trap that made a dead oracle look like a product bug has one shared fix

## Summary

Found while validating T339 (2026-08-08). `test/win32/chooser-restore-all-remote
.ps1` had been failing assertions A and G since **2026-08-02**, and the tracker
recorded it as ALL PASS (32) from a run 72 minutes before the change that broke
it:

- T336 landed 02:46 and its script passed at ~02:22.
- **T338 landed 03:58** and re-keyed the agent's layout blobs from the window's
  IPC name onto its stable UUID.
- The script's fixture oracle looked the blob up by `key -eq 't336-multi'`,
  which from then on matched nothing.

The failure then MASQUERADED as a product defect rather than reading as a broken
oracle, because of a PowerShell trap: `$rec` was `$null`, and
`@($null.session_ids).Count` is **1**, so "no record at all" printed as "the
window's blob claims 1 session id" — a plausible-looking capture bug. (The oracle
is fixed in T339's commit; the store had a correct 3-id blob the whole time.)

## Details

Two separable gaps were named when this was filed. **Gap 1 - nothing re-runs a
script whose subject was not touched - has since been closed elsewhere**, and
this task only had to finish gap 2:

- `scripts\suite-run.ps1` (T361) is the sweep runner: one command, a per-script
  verdict table printed as it goes, exit 1 if anything is red, serial by
  construction and documented as to why (T401), a durable
  `temp\suite-runs\<stamp>\summary.json`, and a re-run-alone pass that separates
  a broken product from a broken harness (T1137). Its first sweep's reds were
  triaged into tasks on 2026-08-22.
- `scripts\guard-due.ps1` (T783) is the staleness surface for the per-harness
  case: a stamp records that harness X was green over the exact files it covers,
  step 0's claim reports every stale one, and `parity-tasks.ps1 validate`
  refuses a commit while one is due.

**What was still missing** (verified against the code on 2026-09-07):

1. **A sweep's summary said WHEN it ran, never WHAT it ran over.** The meta was
   `started`/`set`/`order`/`timeout`/`repo` and no commit, so two summaries a
   week apart still could not name the change that turned a script red - which
   is the entire question this task was filed about.
2. **`test\win32\lib\` still had no shared helper for the PS 5.1 null-array
   trap.** `@($null.session_ids).Count` is **1**, which is why the original
   failure printed "the window's blob claims 1 session id" and read as a
   product capture bug rather than as a dead oracle.

## What landed

- `scripts\suite-run.ps1` records `commit`, `branch` and `dirty` in
  `summary.json`, prints them in the run header, and `compare` now names each
  run by its commit in the same left-to-right order as the verdict columns - so
  a `DIFFER` row is a range of history rather than two timestamps. A **resumed**
  run keeps the commit its rows were measured at (and says so when HEAD has
  moved underneath it), and `confirm` carries that commit through unchanged:
  both report on a run that already happened, so re-reading HEAD would
  re-anchor old verdicts onto today's code.
- `test\win32\lib\CountOrZero.ps1` - `Get-CountOrZero` (absent is 0, a
  collection is its count, anything else is 1, and a string is one value not
  five) and `Format-CountOrAbsent` (prints `<absent>` rather than a number, so
  "there were none" and "there was no record" stop looking identical in an
  assertion message).
- `test\win32\chooser-restore-all-remote.ps1` - the script the trap was found
  in - uses both. Its assertion A still guarded correctly after T339, but its
  MESSAGE went on printing `1` for a missing record, which is the half that did
  the damage.

## Validation criteria

- [x] A sweep can be run with one command, ends with a per-script table, and
      exits non-zero if any script is red. `scripts\suite-run.ps1` (T361);
      sections A, B and S of `test\win32\suite-run.ps1` cover the table and the
      exit code (B7 red, B10 green).
- [x] The sweep's own result is recorded somewhere durable with the commit it
      ran at, so "since when" is answerable.
      `temp\suite-runs\<stamp>\summary.json` now carries `commit`/`branch`/
      `dirty`. Section V of `test\win32\suite-run.ps1` (V1-V11) builds a real
      one-commit fixture repository, turns a green script red in a second
      commit, and asserts that `compare` names both shas and attributes the
      changed verdict to that range.
- [x] The scripts it flags red on its first run are triaged into tasks (or
      fixed). Done by the 2026-08-22 sweep, whose eight P1s are what T1137 was
      written from.
- [x] Whatever the sweep costs, it does NOT run scripts concurrently (T401).
      Serial by construction, with the per-worker exe and LOCALAPPDATA that
      parallelism would need named in the runner's header as a separate task
      rather than smuggled in.
- [x] The PS 5.1 null trap has one shared helper rather than a fix per fixture.
      `test\win32\lib\CountOrZero.ps1`, covered by `test\win32\count-or-zero.ps1`
      (24 assertions, ALL PASS) - whose section A is a NEGATIVE CONTROL proving
      the naive idiom really does answer 1 on this interpreter, so the rest of
      the file cannot pass by testing nothing.
- [x] Both harnesses green on the box, and stamped: `suite-run` ALL PASS (108
      assertions), `count-or-zero` ALL PASS (24), `restore-all-remote` re-run
      because its file changed.
