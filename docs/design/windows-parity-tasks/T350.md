# T350 - A non-Debug zig-out silently aims every acceptance script at the user's INSTALLED Ghoztty

## In plain terms

The automated tests are supposed to drive the copy of the terminal we just
built, in a sandbox of its own. If that copy happens to be built the "fast"
way instead of the "debug" way, it stops being separate: the tests start
opening windows in the terminal the user is actually sitting in, typing into
it, and reporting a clean pass about a program nobody here built. It has
happened for real - stray test windows were found in the user's terminal.
After this lands, a test run that would do that stops with an explanation
instead of quietly doing it.

## Goals

- [x] A test run can tell, before it launches or types anything, whether the
      binary it was handed is the isolated kind or the shared kind.
- [x] A shared-endpoint binary aborts the run with a message that says what to
      do about it, instead of driving the user's terminal.
- [x] A script that deliberately tests a release build can still say so.
- [x] Debug runs are completely unchanged (P1-P3 still ALL PASS).
- [x] The reason `-Doptimize=Debug` is not optional is written down next to the
      build command, in both `go.md` and `CLAUDE.md`.

## Summary

An acceptance script picks its subject with `-Exe zig-out\bin\ghoztty.exe`.
That only chooses which CLI **binary** runs. Which **app** that CLI reaches is
decided by the IPC endpoint, and the endpoint is derived from the BUILD MODE:
`\\.\pipe\ghoztty-debug-<USER>` for a Debug build, `\\.\pipe\ghoztty-<USER>`
for a release one - the same pipe the user's installed Ghoztty listens on.

So a `zig build -Dapp-runtime=win32` run WITHOUT `-Doptimize=Debug` leaves a
release build in `zig-out`, and from that moment the whole suite drives the
user's terminal: `+new-window` opens windows in it, the path-filtered kills
match nothing (different ExecutablePath), and every assertion measures a
binary nobody here built. Nothing reports an error; the scripts pass.

Observed for real on 2026-08-02 during T248, before anything was changed:

    D:\git\ghoztty\zig-out\bin\ghoztty.exe +list --json
    ... "exe":"C:\\Users\\David\\AppData\\Local\\Programs\\Ghoztty\\ghoztty.exe"

and the same install was holding a window `[target: p1win] P1Title` plus a
`window-1` - `ipc-p1.ps1` fixtures, leaked into the user's running terminal by
an earlier run. Rebuilding zig-out as Debug made the same command answer "No
running Ghoztty instance found."

T248 landed half the answer: `Assert-GhozttyUnderTest`
(`test\win32\lib\CleanSlate.ps1`) compares `+list --json`'s `build.exe`
against `$Exe` and throws, and `Reset-GhozttyTestState` runs it as a
pre-flight. That catches the case where the foreign app is ALREADY up - the
common one, since the user's terminal is always running - but not a cold box,
where nothing answers and the script proceeds to auto-launch the release build
onto the shared endpoint.

## What is left

- Detect the build mode of `$Exe` itself, before anything is launched. `+list
  --json` reports `build.mode` but only from a RUNNING server; find the local
  equivalent (extend `+version` output if there is none) and have
  `CleanSlate.ps1` refuse a non-Debug exe unless the caller opts in - the
  upgrade/soak scripts legitimately test a release build, and those pass
  `GHOZTTY_PIPE_SUFFIX` to keep off the installed instance.
- Consider making the suffix override the DEFAULT for acceptance runs: a
  run-unique `GHOZTTY_PIPE_SUFFIX` gives the script a private endpoint that no
  installed release can answer, which makes the whole class impossible rather
  than detectable. Weigh against auto-launch (the app inherits the env, so it
  should work) and against scripts that dial the agent.
- Note the trap in `go.md`/CLAUDE.md next to the build incantation: the reason
  `-Doptimize=Debug` is not optional is not speed, it is endpoint isolation.

## Validation

- With a release build staged in `zig-out`, `test\win32\ipc-p1.ps1` must ABORT
  with a clear message instead of running against the installed Ghoztty.
- With a Debug build, every P1-P3 run is unchanged (ALL PASS).

## Resolution (2026-08-04)

**The gate is the BUILD MODE, not "is a pipe suffix set".** That is the one
finding that shaped the fix: `GHOZTTY_PIPE_SUFFIX` moves the app endpoint and
nothing else - `LocalAgent.pipeName` (`src\apprt\win32\LocalAgent.zig:855`)
derives the local agent's pipe from `build_config.is_debug` with **no env
override**, and the agent's state directory follows the same rule. So a release
build under a private suffix still dials the agent that owns the user's live
sessions, and the task's second bullet ("make the suffix the default") cannot
close the class on its own. Build mode is the single thing that moves all three
endpoints together, so it is what the guard reads and why a suffix is *not*
accepted as the opt-in.

`is_debug` is `Debug` **or** `ReleaseSafe` (`src\build_config.zig:109`), so the
predicate is "isolated / shared", not "Debug / non-Debug".

- **`test\win32\lib\BuildMode.ps1`** (new). `Get-GhozttyBuildMode` reads the
  `build mode` line `+version` already prints from `builtin.mode` - local,
  offline, and therefore an answer on a COLD box, which is the half T248 could
  not reach. `Test-GhozttyIsolatedBuildMode` is the pure predicate;
  `Assert-GhozttyIsolatedBuild` throws with the mode it found, the exe it was
  handed, the rebuild command, why a suffix does not help, and the opt-in. An
  exe whose mode cannot be read at all is refused the same way an unknown mode
  is - a run we cannot vouch for is exactly the run that leaks.
  No zig change was needed: `+version` already prints the line (`- build mode
  : .Debug`), and the match is anchored on `build mode` because the `Running
  Instance` section carries its own `- mode` line.
- **Wired into both pre-flight paths**, so it fires ahead of every other check:
  `Reset-GhozttyTestState` (`CleanSlate.ps1`, 24 scripts) and
  `Assert-GhozttyPrivateEndpoint` (`Isolation.ps1`, which covers the scripts
  that set a suffix by hand and never load CleanSlate). Both take
  `-AllowReleaseBuild`; `GHOZTTY_TEST_ALLOW_RELEASE=1` does the same per run.
- **`session-persistence.ps1`** got the cold-box complement of the guard its own
  2026-07-21 incident note describes: that one only fires when something is
  already listening, which is the warm case.
- **`soak.ps1`** passes `-AllowReleaseBuild` - it is the one caller whose
  SUBJECT is the release build. Its remaining agent-side exposure is filed as
  **T490**.
- Docs: the trap is now stated next to the build incantation in `CLAUDE.md`
  (Build, run & debug -> Windows) and in `go.md` ("What to do" 3).

### Evidence

- `test\win32\build-mode-guard.ps1` (new, 39 assertions): **ALL PASS**. Covers
  the predicate at all four modes, parsing (including an exe that prints no
  mode line and one that does not exist), the refusal message's content, both
  opt-ins, that a private suffix is *not* one, that both pre-flight paths
  refuse and that `-AllowReleaseBuild` reaches them, a positive control against
  the real `zig-out` exe, and the doc notes. Release builds are played by a stub
  exe that prints a `+version` banner - a real ReleaseFast build would
  contribute one line of text for ten minutes of wall clock.
- Task Validation 1, end to end: `ipc-p1.ps1 -Exe <ReleaseFast stub>` aborts
  with `REFUSING TO RUN ...` and exit 1 **before opening a window**.
- Task Validation 2: `ipc-p1/p2/p3` all `ALL PASS` unchanged.
- Floor: `scripts\floor-lane.ps1 -Lane all` -> `ALL LANES PASS`
  (none 166s, win32 187s, agent 198s).
