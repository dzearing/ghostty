# T350 - A non-Debug zig-out silently aims every acceptance script at the user's INSTALLED Ghoztty

## Summary

An acceptance script picks its subject with `-Exe zig-out\bin\ghoztty.exe`.
That only chooses which CLI **binary** runs. Which **app** that CLI reaches is
decided by the IPC endpoint, and the endpoint is derived from the BUILD MODE:
`\\.\pipe\ghoztty-debug-<USER>` for a Debug build, `\\.\pipe\ghoztty-<USER>`
for a release one - the same pipe the user's installed Ghoztty listens on.

So a `zig build -Dapp-runtime=win32` run WITHOUT `-Doptimize=Debug` leaves a
release build in `zig-out`, and from that moment the whole suite drives the
user's terminal: `+new-window` opens windows in it, the path-filtered kills
match nothing (different ExecutablePath), and every assertion measures a
binary nobody here built. Nothing reports an error; the scripts pass.

Observed for real on 2026-08-02 during T248, before anything was changed:

    D:\git\ghoztty\zig-out\bin\ghoztty.exe +list --json
    ... "exe":"C:\\Users\\David\\AppData\\Local\\Programs\\Ghoztty\\ghoztty.exe"

and the same install was holding a window `[target: p1win] P1Title` plus a
`window-1` - `ipc-p1.ps1` fixtures, leaked into the user's running terminal by
an earlier run. Rebuilding zig-out as Debug made the same command answer "No
running Ghoztty instance found."

T248 landed half the answer: `Assert-GhozttyUnderTest`
(`test\win32\lib\CleanSlate.ps1`) compares `+list --json`'s `build.exe`
against `$Exe` and throws, and `Reset-GhozttyTestState` runs it as a
pre-flight. That catches the case where the foreign app is ALREADY up - the
common one, since the user's terminal is always running - but not a cold box,
where nothing answers and the script proceeds to auto-launch the release build
onto the shared endpoint.

## What is left

- Detect the build mode of `$Exe` itself, before anything is launched. `+list
  --json` reports `build.mode` but only from a RUNNING server; find the local
  equivalent (extend `+version` output if there is none) and have
  `CleanSlate.ps1` refuse a non-Debug exe unless the caller opts in - the
  upgrade/soak scripts legitimately test a release build, and those pass
  `GHOZTTY_PIPE_SUFFIX` to keep off the installed instance.
- Consider making the suffix override the DEFAULT for acceptance runs: a
  run-unique `GHOZTTY_PIPE_SUFFIX` gives the script a private endpoint that no
  installed release can answer, which makes the whole class impossible rather
  than detectable. Weigh against auto-launch (the app inherits the env, so it
  should work) and against scripts that dial the agent.
- Note the trap in `go.md`/CLAUDE.md next to the build incantation: the reason
  `-Doptimize=Debug` is not optional is not speed, it is endpoint isolation.

## Validation

- With a release build staged in `zig-out`, `test\win32\ipc-p1.ps1` must ABORT
  with a clear message instead of running against the installed Ghoztty.
- With a Debug build, every P1-P3 run is unchanged (ALL PASS).
