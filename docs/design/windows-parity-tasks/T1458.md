# T1458 - Claude Code in a Ghoztty pane lags versus native conhost on a streamed desktop

## Summary

Running Claude Code inside a Ghoztty pane feels **laggy**; the same workload in
a native `cmd` / conhost window on the same machine feels markedly faster.
Reported interactively 2026-09-08 on the installed release (build 2026-09-05),
Windows 11 26100.9278.

P0 because this is the user's primary terminal and the defect is in the
interaction they spend all day in, not in a corner of the chrome.

## In plain terms

Type into Claude Code inside Ghoztty and the screen does not keep up the way a
plain `cmd` window does - text arrives in visible lurches instead of flowing.
Nothing is broken and nothing is lost; it just feels heavy, and it feels lighter
in the terminal Windows ships with. When this lands, a Ghoztty pane should feel
at least as immediate as conhost for the same output.

## What was already RULED OUT - do not re-investigate

The reporter's own hypothesis was that Ghoztty had fallen back to software
OpenGL. **It has not.** Measured on the live process (pid 24300) 2026-09-08:

```
opengl32.dll   C:\WINDOWS\SYSTEM32\opengl32.dll                  10.0.26100.9278
nvoglv64.dll   ...DriverStore\...\nv_dispi.inf_amd64...\nvoglv64.dll  32.0.15.9649
```

- The loaded GL is the **NVIDIA hardware driver**, reached through System32's
  real `opengl32.dll`.
- The shipped Mesa fallback (`<install>\gl\opengl32.dll`, 17 MB, from T1252) is
  present on disk but **is not loaded into the process**.
- The box has an RTX 4090. `gl_loader`'s fallback path (T1251) did not trigger.

So this is NOT llvmpipe, and any work that starts from "we are on the software
rasterizer" is starting from a false premise. Method worth reusing: the loaded
module list is the decisive oracle here, and it is one PowerShell call -
`(Get-Process ghoztty).Modules | Where-Object ModuleName -match 'opengl|nvoglv'`.
It beats reading the log, which on this build carries
`renderer=renderer.generic.Renderer(renderer.OpenGL)` but no vendor/renderer
string.

## The environment, which is probably load-bearing

`Get-CimInstance Win32_VideoController` on the reporting box returns THREE
adapters:

```
Virtual Desktop Monitor           10.54.50.446
Parsec Virtual Display Adapter    0.45.0.0
NVIDIA GeForce RTX 4090           32.0.15.9649
```

`SESSIONNAME=Console` and no `mstsc`/`msrdc`/`rdpclip` is running, so this is
not classic RDP - it is a **streamed console session** (Parsec and/or Virtual
Desktop). That matters because it changes what "presenting a frame" costs:

- An OpenGL window renders on the NVIDIA adapter and then has to reach a
  **virtual display** owned by a different driver. If the compositor is doing a
  cross-adapter copy per frame, every frame pays a GPU→CPU→GPU trip that a
  native desktop never pays.
- The streamer then has to **capture and encode** whatever changed. A
  GL-composited window and a GDI/DirectWrite window (conhost) are not equally
  cheap to capture, and conhost's damage rectangles are far smaller than a
  full-surface GL swap.

That is a hypothesis, not a finding. **Establish it or kill it first**, because
it decides whether the fix is in Ghoztty's frame pacing or in how Ghoztty
presents on a virtual display.

## Investigation order

Measure before changing anything. The instrumentation already exists.

1. **Get the numbers with `GHOZTTY_PERF` set.** `renderer/OpenGL.zig`'s `perf`
   struct (T40/T48/T1147) logs, once per second per pane:
   `fps`, the longest inter-frame gap, and the **max SwapBuffers-to-SwapBuffers
   stall**, each tagged `pane=<uuid>`. Group by pane and read only the pane the
   load is in - the median across panes is meaningless when idle panes sit at
   1 fps (that mistake is documented in the same comment block).
   `renderer/Thread.zig` adds `wakeups_per_s`.
   **A long SwapBuffers stall is the direct signature of the present being the
   bottleneck**, which is what the virtual-display theory predicts.
2. **Compare against conhost on the same desktop**, same output, same window
   size. Without that control the numbers say nothing - the reporter's whole
   claim is relative.
3. **Find out which monitor the pane is on.** Move the Ghoztty window to the
   physical 4090-attached display (if one is attached) and to the virtual
   display, and take the same measurement on each. If the stall follows the
   virtual display, the theory above is confirmed and the work is about
   presentation, not about the terminal.
4. **Characterise Claude Code's output shape.** It is not a `cat` of a big
   file: it is a spinner ticking several times a second, streaming tokens, and
   frequent full-width repaints of a status area. That is many small ConPTY
   reads, each of which can wake the renderer. Count `wakeups_per_s` against
   frames actually presented - if wakeups vastly exceed useful frames, the
   renderer is being asked to draw far more often than the display can show,
   and coalescing is the lever.
5. **Only then look at the ANSI/parse path.** `termio/Exec.zig`'s `ReadFile`
   loop (around lines 1558-1585) already does a fill-then-parse; confirm with
   numbers that parsing is or is not on the critical path before touching it.
   The reporter named "ansi support that claude code uses" as a suspect, and it
   may well be innocent - do not optimise it on suspicion.

## Fix directions, in the order the evidence would justify them

None of these should be started before step 1-3 above name a cause.

- **If the present is stalling on a virtual display:** consider whether the
  win32 surface should present differently when the window is on an adapter
  that is not the rendering one - fewer, larger presents; or an explicit
  damage-limited blit rather than a full-surface swap.
- **If wakeups vastly exceed presented frames:** coalesce. The renderer thread
  already distinguishes `wakeup` (coalescing) from `draw_now` (not) - see the
  comment at `renderer/Thread.zig:66`. Make sure a burst of small ConPTY reads
  rides the coalescing path and cannot force a present each.
- **If frames are cheap but latency is high:** the problem is scheduling, not
  throughput. Look at how a PTY read gets from `termio` to a present, and how
  much of that is a thread hop.

## Parity note

Standing symmetry rule. The macOS build uses Metal and has no equivalent of
either the WGL present path or a Parsec virtual display, so a fix here is
expected to be win-only. **Confirm rather than assume**, and if the Mac seat
shows the same lag under screen sharing, file its half.
