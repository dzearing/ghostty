# T969 - A busy pane can still outrun what a crash can recover: snapshot on volume, not only on a 30-second timer

## In plain terms

If the session manager crashes, you now get back everything printed since the
last time your scrollback was saved (T911). But scrollback is only saved every
30 seconds, and a session can only hold about a megabyte of unsaved output — so
a pane in the middle of a noisy build can print more than that between two
saves, and the oldest of it is dropped to make room. The pane you are watching
is fine; what a crash could hand back is not. The fix is to save when enough has
been printed, not only when enough time has passed.

## Summary

The recoverable window is `min(snapshot interval, holder replay capacity)`. The
interval is `snapshot_every_ticks = 30` reaper ticks (`session.zig`), and the
capacity is `pty_holder_child.Options.replay_bytes = 1 MB`. A shell writing
faster than ~35 KB/s therefore reaches the ring's capacity before the timer
fires, and `ReplayBuffer.append` drops oldest — which is correct behavior for a
buffer that must never stall the pty reader, and still a loss of exactly the
bytes T911 exists to keep.

Shape of the fix: make the store snapshot a session whose unsaved byte count
crosses a threshold, in addition to the periodic pass — the threshold sized off
the holder's replay capacity (e.g. half of it) so the buffer is refilled before
it wraps. `Session` already knows its unsaved volume (`out_offset.value -
last_snapshot_offset`), so the trigger is a comparison, not new bookkeeping. The
cost to weigh is disk churn on a noisy pane: a bounded minimum interval between
volume-triggered writes belongs in the design, and the existing atomic write is
already a whole-ring rewrite, so the write cost scales with ring size rather
than with the delta.

Deliberately NOT "make the replay buffer bigger": that spends per-session memory
on every box to buy the same window, and the number that actually decides what
survives is how stale the file on disk is.

## What landed

The reaper's snapshot pass now fires on BYTES as well as on the clock. Each
tick, `SessionStore.volumeSnapshotDue` reads the busiest alive session's
`out_offset - last_snapshot_offset`; at or past `snapshot_volume_bytes`
(default `default_snapshot_volume_bytes` = half the holder's replay capacity)
the whole pass runs, exactly as the 30-tick timer would have run it. The
decision itself is `volumeSnapshotFires`, a pure function of (unsaved,
threshold, elapsed, floor), so the boundary is unit-tested rather than asserted.

Three calls worth naming, all mechanism (no user-visible fork, so no decision
was filed):

- **Checked on the reaper tick, not on the output path.** The pty reader thread
  is parked inside `onChildOutput` when the counters move, so testing there
  would be free of a scan — but it would also put a branch (and, if it ever
  wanted to act rather than flag, disk I/O) on the hot path that serializes
  child output. The cost of checking on the tick is up to one second of extra
  latency, which is the granularity every other sampler in that loop already
  runs at, and the extra second is bounded by the same holder ring.
- **The busiest session decides for the whole pass.** `snapshotRings` already
  flushes every dirty session; a per-session decision would write the same
  files and cost another lock round-trip.
- **A floor (`snapshot_volume_min_interval_ms`, 1 s) between passes.** A
  snapshot rewrites each dirty ring WHOLE, so the write amplification is
  `ring size / max(threshold, rate x floor)` — bounded at 2x of what the pane
  prints at the shipped numbers, and falling as the pane gets noisier.

What is still bounded, honestly: the guarantee now holds for a pane printing up
to roughly `threshold / floor` — about 500 KB/s at the shipped numbers, against
the ~35 KB/s the timer alone covered. A pane printing tens of megabytes a second
still outruns it, because at that rate the unsaved delta passes the holder's
whole ring inside one floor interval, and no snapshot cadence short of writing
faster than the shell prints can close that. The remaining lever there is making
a snapshot cost proportional to the delta rather than to the ring (T997), not a
shorter floor.

Two env knobs came with it, both defaulting to the shipped numbers and both
ignoring anything unparseable (a typo must not silently shrink what a crash can
recover): `GHOZTTY_AGENT_SNAPSHOT_VOLUME_BYTES` (0 = trigger off) and
`GHOZTTY_AGENT_HOLDER_REPLAY_BYTES`. The second exists because the acceptance
harness needs to overrun a holder's ring in a second rather than printing a
megabyte through a ConPTY and racing the 30-second timer while it does.

## Goals

- [x] A pane printing fast has the same crash-recovery guarantee as a quiet one.
- [x] The extra writes are bounded — a noisy pane cannot turn this into a disk
      hammer.

## Validation criteria

- [x] Unit: the volume trigger fires at the threshold and not before, and the
      minimum-interval bound suppresses a second write. — three tests in
      `session.zig` (the pure boundary table; a busy session going due, being
      cleared by the pass, and being suppressed at 999 ms then due at 1000 ms;
      both off switches) plus `replayBytesFor` in `pty_holder_child.zig`, which
      also pins `default_snapshot_volume_bytes * 2 == default_holder_replay_bytes`
      so the ratio the design rests on cannot drift. `zig build test-agent` green.
- [x] Acceptance: an extension of `test\win32\holder-durable.ps1` (or a sibling)
      where the marker is followed by MORE than the replay capacity of output
      before the manager is killed — the marker still reaches a `.ring` file.
      Negative control: the same run with the volume trigger disabled loses it.
      — `test\win32\holder-volume.ps1`, ALL PASS (16 assertions) on both arms:
      the marker reaches a `.ring` 1 s after a ~256 KB flood through a 64 KB
      holder ring and survives the hard kill, and with the trigger off the same
      run finds it neither on disk nor after recovery.
- [x] Floor lanes + `holder-adopt.ps1`, `pty-holder.ps1`, `holder-durable.ps1`
      stay ALL PASS.
