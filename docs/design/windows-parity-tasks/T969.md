# T969 - A busy pane can still outrun what a crash can recover: snapshot on volume, not only on a 30-second timer

## In plain terms

If the session manager crashes, you now get back everything printed since the
last time your scrollback was saved (T911). But scrollback is only saved every
30 seconds, and a session can only hold about a megabyte of unsaved output — so
a pane in the middle of a noisy build can print more than that between two
saves, and the oldest of it is dropped to make room. The pane you are watching
is fine; what a crash could hand back is not. The fix is to save when enough has
been printed, not only when enough time has passed.

## Summary

The recoverable window is `min(snapshot interval, holder replay capacity)`. The
interval is `snapshot_every_ticks = 30` reaper ticks (`session.zig`), and the
capacity is `pty_holder_child.Options.replay_bytes = 1 MB`. A shell writing
faster than ~35 KB/s therefore reaches the ring's capacity before the timer
fires, and `ReplayBuffer.append` drops oldest — which is correct behavior for a
buffer that must never stall the pty reader, and still a loss of exactly the
bytes T911 exists to keep.

Shape of the fix: make the store snapshot a session whose unsaved byte count
crosses a threshold, in addition to the periodic pass — the threshold sized off
the holder's replay capacity (e.g. half of it) so the buffer is refilled before
it wraps. `Session` already knows its unsaved volume (`out_offset.value -
last_snapshot_offset`), so the trigger is a comparison, not new bookkeeping. The
cost to weigh is disk churn on a noisy pane: a bounded minimum interval between
volume-triggered writes belongs in the design, and the existing atomic write is
already a whole-ring rewrite, so the write cost scales with ring size rather
than with the delta.

Deliberately NOT "make the replay buffer bigger": that spends per-session memory
on every box to buy the same window, and the number that actually decides what
survives is how stale the file on disk is.

## Goals

- [ ] A pane printing fast has the same crash-recovery guarantee as a quiet one.
- [ ] The extra writes are bounded — a noisy pane cannot turn this into a disk
      hammer.

## Validation criteria

- [ ] Unit: the volume trigger fires at the threshold and not before, and the
      minimum-interval bound suppresses a second write.
- [ ] Acceptance: an extension of `test\win32\holder-durable.ps1` (or a sibling)
      where the marker is followed by MORE than the replay capacity of output
      before the manager is killed — the marker still reaches a `.ring` file.
      Negative control: the same run with the volume trigger disabled loses it.
- [ ] Floor lanes + `holder-adopt.ps1`, `pty-holder.ps1`, `holder-durable.ps1`
      stay ALL PASS.
