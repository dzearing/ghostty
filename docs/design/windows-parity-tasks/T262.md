# T262 - zig build panics with 'reached unreachable code' when ZIG_GLOBAL_CACHE_DIR is unset

## DUPLICATE of T243 (marked 2026-08-01, during T225)

**T243 is the canonical task** - same defect, same box, filed 2026-07-31 with
the same reproduction and a stronger fix (a real diagnostic emitted from
`build.zig` when the build root and the resolved global cache are on different
drives, so the knowledge does not have to be found at all). Everything below is
folded into T243; nothing is lost by closing this one.

That two turns filed this independently is not noise, it is the argument for
T243's fix: a documented workaround only helps a session that goes looking, and
neither of these two did - both were mid-floor-run with a build that looked like
it had failed on the change under test. Recorded in T243.

## Summary

On this box the standing floor's first lane does not fail — it **panics**, and
the panic reads like a compiler bug or a source error rather than the box-state
trap it is. Hit 2026-07-31 running the T257 floor.

```
zig : thread 31740 panic: reached unreachable code
  ...\lib\std\debug.zig:559:14: 0x7ff65c1192ad in assert (build_zcu.obj)
error: unable to read results of configure phase from '.zig-cache\tmp\<hash>': FileNotFound
```

Nothing in `go.md` or the tracker mentions `ZIG_GLOBAL_CACHE_DIR`, so a fresh
session has no reason to suspect the environment. The obvious readings are all
wrong: a broken toolchain, a corrupt `.zig-cache`, or — worst — the source
change under test.

## Evidence (reproduced deliberately, both directions)

Same repo, same HEAD (`5ad81a99e`), same command, only the variable changing:

| `ZIG_GLOBAL_CACHE_DIR` | `zig build test -Dapp-runtime=none` |
|---|---|
| unset | **exit 1**, `panic: reached unreachable code` |
| `D:\zig-global-cache` | **exit 0** |

Confirmed with it unset twice (a fresh `.zig-cache\tmp\<hash>` each run, so it
is not one poisoned cache entry) and with it set on the none lane, the win32
lane and `test-agent`. `zig build --help` with it unset exits 0 — the panic
needs the real configure phase, which is why a quick sanity check misses it.

`D:\zig-global-cache` already exists on the box, i.e. this was known and set up
at some point, and then never written down where a turn would read it.

## Root cause (as far as it matters here)

Unset, zig puts the global cache under `%LOCALAPPDATA%` on **C:**, while the
repo is on **D:**. The build then panics in its own configure phase. Whether
the underlying bug is zig 0.15.2's cross-volume handling or something specific
to this box is not worth chasing — the fix is one line of documentation and
the workaround is already proven.

## Why this is a task and not just a note

This is the same shape as go.md's `Select-Object -First N` warning: a build
reporting a scary failure for a reason that has nothing to do with the change
under test. That one was **mis-filed twice** as a transient flake (T89h, then
T89i) before it was written down. This one is currently undocumented and will
be misread the same way.

## The fix

- Add it to `go.md` next to the `-First N` warning: what the panic looks like,
  that it is environmental, and the one-line fix
  (`$env:ZIG_GLOBAL_CACHE_DIR = 'D:\zig-global-cache'`).
- Prefer making it not need saying: have the build/test helper scripts set it
  when unset, so a session that never reads that paragraph is still fine.
  `scripts/` already owns the upgrade/launch wrappers; a floor-lane wrapper is
  the natural home.

## Validation

- With the variable unset in a fresh shell, the documented workaround takes the
  none lane, the win32 lane and `test-agent` to exit 0.
- If a wrapper is added: running it with `ZIG_GLOBAL_CACHE_DIR` unset succeeds,
  and it does NOT override an operator-set value.
