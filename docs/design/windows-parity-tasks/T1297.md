# T1297 - Tunnel viewer panes between machines

## In plain terms

When you open a terminal on another machine, you get the terminal. But if
something over there opens a preview - a rendered document, a web page, a diff
- you cannot see it. You would have to go to that machine. The ask is that a
viewer opened on the remote machine simply appears in your window, as if it had
been opened locally.

## What the user asked for (2026-09-03)

> "i would loveeeee to have the ability to tunnel the web page content. E.g. if
> the other machine has a viewer open, we can stream the results over to the
> remote machine as if it were local."

## Why it matters

The remote-machines feature exists so an agent working on another box is
usable from here. Today that means **terminals only**. Viewer panes - the
markdown, HTML, code and git-diff previews - are the half that makes an agent's
output readable rather than a wall of scrollback, and they stop at the machine
boundary. So the remote experience is strictly worse than the local one in
exactly the place the product is trying to be better.

## Where network requests originate - the user named this specifically

> "network requests from within the remote web window didn't fire from the
> local machine but rather sent to remote"

This is the sharp edge of the whole feature and it deserves deciding on its own
rather than falling out of the implementation. A page shown in a tunnelled
viewer can issue requests, and *which machine makes them* changes what the page
can reach:

- **From the remote machine** - the page sees the remote machine's network:
  its localhost, its private hosts, its VPN. That is usually what you want when
  the page IS the remote machine's work (a dev server on that box, an internal
  dashboard), and it is what the user observed.
- **From the local machine** - the page sees what your laptop sees. Right for
  content that is merely *displayed* remotely but belongs to you.

They are not interchangeable and the wrong default is either useless (a preview
of a remote dev server that cannot reach it) or surprising (a remote page
quietly reaching into your local network). Whichever is chosen, the pane should
be able to say which machine its requests go out from, for the same reason it
should say where its content came from.

## The design question this needs

There is a real fork here, and it should be settled before anyone builds:

- **Tunnel the content** - the remote side sends the document (HTML, markdown,
  the diff text) and the *local* viewer renders it. Crisp at any size, cheap on
  bandwidth, and it reuses the viewer that already exists. But local rendering
  of remote content raises the questions that always follow: what can that
  content reach, what does it do about relative links and local assets, and
  what is the trust boundary when the remote machine is one the user merely has
  access to.
- **Tunnel the pixels** - the remote side renders and streams frames. Perfectly
  faithful to what the other machine shows, and sidesteps the content-trust
  question, but it is a video pipeline with the cost and latency that implies,
  and text stops being selectable or searchable unless that is tunnelled too.

The first is almost certainly right for documents and the second for anything
genuinely interactive, but that is a judgement worth writing down with the
reasoning rather than assuming.

Note it interacts with the viewer feedback and quoting features - a tunnelled
viewer that cannot be quoted or fed back is only half the pane.

## Validation criteria

- [ ] The approach is chosen and recorded, with the trust boundary for remote
      content stated explicitly.
- [ ] A viewer opened on a remote machine appears in the local window without
      the user asking for it separately.
- [ ] Markdown, HTML, code and git-diff viewers all tunnel, or the ones that do
      not are named and explained.
- [ ] Navigation, scrolling and selection behave as they do locally, or the
      differences are documented.
- [ ] The pane says which machine its content came from - a viewer that looks
      local but is not should not be able to mislead.
- [ ] Mac and Windows both get it, per the platform-symmetry rule.
