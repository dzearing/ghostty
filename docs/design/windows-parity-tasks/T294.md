# T294 - Hoist the chooser control locators: three scripts each keep a private copy of 'find the management button'

## In plain terms

Nothing a user can see changes here. This is about the tests that drive the
"New Remote Window" chooser: seven of them each had their own private way of
answering "which button is the management menu" or "which one is the account
control", and each of those ways was a guess from the button's caption or from
where it sat in a row. Add one button to that row - which has now happened
twice - and some of those tests quietly start clicking the wrong control while
still reporting a pass. They ask the app which control is which now, so a new
neighbour, a moved button or a renamed label cannot mislead them.

## Goals

- [x] One module owns the chooser's control vocabulary, dot-sourced everywhere
- [x] Controls are identified by something the app itself defines, not by a
      caption or a position
- [x] Every private copy is deleted - no locator left in any script
- [x] The claims the old locators used as PREMISES become real assertions
- [x] The new module has its own acceptance script, including a drift check
      against the app's source

## Summary

**T257's finding, in a different subsystem.** Four acceptance scripts drive the
machine chooser, and each one re-implements how to FIND its controls:

- `test/win32/chooser-menu.ps1` - `Get-Controls` + `Get-MenuButton`
- `test/win32/host-settings.ps1` - its own `Get-Controls` + `Get-MenuButton`
- `test/win32/relay-account.ps1` - `Get-ChooserControls` + `Get-AccountButton`
- `test/win32/ipc-machine-chooser.ps1` - inline button lookups

T177 added an **Activity** button to the detail pane's action row and broke two
of them at once, in the quietest possible way: both `Get-MenuButton` copies
were "the first button to the right of New Window", which is Activity now, so
`host-settings.ps1` would have CLICKED Activity - opening an Activity Monitor
panel - while asserting about a management menu. `relay-account.ps1` identified
the account button by *excluding* the labels it is not (`New Window`, `Open`,
`Cancel`), an exclusion list that grows silently and had just gained a fourth
member.

Both were repaired in T177 against something the design system fixes rather
than against a label (the menu button is the SQUARE button in the action row;
the account button is the TOPMOST button in the dialog), so the scripts are
green. What is NOT fixed is the shape of the problem: the next control added to
that row gets the same three chances to be wrong.

## What landed

### The scope was seven scripts, not four - the regrowth had already happened

Before this was picked up, the prediction in the Details section below came true
twice over. `Restore All` (T335) landed in that same action row and grew **two**
more private locators (`chooser-restore-all.ps1`,
`chooser-restore-all-remote.ps1`, identical copies keyed on the caption
`Restore All`), and `chooser-link-hover.ps1` grew a **fifth** copy of "the
topmost visible button is the account control". Three more scripts
(`chooser-resume.ps1`, `chooser-roster-refetch.ps1`, `chooser-close-chord.ps1`)
reached the filter field as "the chooser's first visible EDIT". All of them are
converted.

### Identification is by the app's own control ID

Rather than by shape (T177's repair) or by label. `MachineChooser.zig` creates
every one of these controls with an explicit id - its `hMenu` argument - because
that is how `WM_COMMAND` is routed back to the right handler, so the id is the
app's OWN name for the control rather than a second description of it invented
in the harness. `GetDlgCtrlID` reads it off the HWND, needing neither the app's
message loop nor a pixel.

That kills every failure mode of the private copies at once: a RELABELED control
is still found; a control that MOVES or gains a neighbour is still found; a
HIDDEN control is still found with `Visible` reporting the state (rather than
the lookup answering "absent", which is what a caption lookup does and what
T335's Restore All specifically needs to read); and an id that is RENUMBERED
fails LOUDLY - `$null`, red script - instead of silently returning the wrong
control.

### Two assertions became real

Both were circular before, and neither could have failed:

- `ipc-machine-chooser.ps1` found the primary action BY the caption `New Window`
  and then asserted the caption was `New Window`. It is found by id now.
- Its T311 section identified the account row's two controls as "every button
  above the header rule" and asserted there were two of them. They come by id
  now, and where they SIT is a separate assertion.

The same is true of the SHAPE rules the T177 repair used as lookups (the menu
button is square; the account control is the visible one of two): section B of
the new acceptance script states each of them as a claim.

## Details

Do for the chooser what `test/win32/lib/ChromeGeometry.ps1` did for chrome
geometry (T257): one module, dot-sourced from `TestDesktop.ps1` (which every
script already loads), owning the chooser's control vocabulary -

- `Get-ChooserControls`, one implementation (the three today differ in which
  fields they project: Left/Right/Bottom, Visible, Enabled - the union is
  cheap).
- `Get-ChooserActionRow` (the packed run, left to right), `Get-ChooserMenuButton`
  (the square one), `Get-ChooserActivityButton`, `Get-ChooserPrimaryButton`,
  `Get-ChooserAccountButton`, `Get-ChooserCancelButton`.
- The split T257 named: what is DERIVED from the layout rule (positions, the
  gap, the square) versus what must be MEASURED off the live window (button
  widths, which come from text metrics and cannot be re-derived - T235).

Then delete the private copies. Four scripts, mechanical, and the win is that
the NEXT change to the action row (T146's Restore All) touches one file.

**How it was actually resolved**: by asking the app for the control's id, which
is neither derived nor measured but PUBLISHED - the tier `ChromeGeometry.ps1`
prefers and reaches for `Get-TestStripRegions` (T231). The one lookup still
measured is the pair of STATICs (account status / footer hint), because both are
created with a null id and there is nothing to ask for; that rule is written
once now instead of three times.

The cost of the new approach is a coupling: the ids are restated in the harness.
Section A of the acceptance script parses `MachineChooser.zig` and fails if the
two tables disagree - in BOTH directions, so an id the app grows and the harness
never learns is a failure too.
