# T1243 - A download cut off mid-transfer can still be staged and handed to msiexec

## Summary

`update_install.fetch` stops its read loop on `bytes_read == 0` and never
compares what it got against the `Content-Length` it now knows (T1195 added
the header read). A connection that dies half way through therefore returns a
SHORT body, and `update_apply.looksLikeMsi` only inspects the leading OLE
compound-file signature - so a truncated package passes the check, gets
staged, and is what the applier hands msiexec after the app quits.

Found while building T1195's progress panel: the panel makes the truncation
visible for the first time (the bar stops part way and the download still
reports success), which is what turned an invisible failure mode into an
observable one.

The fix is to treat a body shorter than a known `Content-Length` as
`error.Truncated` rather than a complete download. Where the server sent no
length there is nothing to compare against and today's behavior stands.

## In plain terms

If the network drops in the middle of downloading an update, Ghoztty can
believe it got the whole thing. It then quits and hands a half-finished
installer to Windows. The user sees their terminal close for an update that
cannot install.

## Validation criteria

- [x] A transfer cut short of its Content-Length fails instead of staging - `fetch()` now returns `error.Truncated`; section 4 of `test\win32\update-progress.ps1` sees `update download failed: error.Truncated` and no `update download: staged` line
- [x] The progress panel reports that failure rather than "Download complete." - the same section asserts `update progress: The download failed`
- [x] A server that sends no Content-Length still downloads as it does today - section 5 serves a length-less body and it fails the PACKAGE check, never the length check

## Evidence

- `src/apprt/win32/update_install.zig`: `fetch()` compares the body it read
  against the `Content-Length` it already knew and returns `error.Truncated`
  when it is short. `isTruncated(received, total)` is the whole rule and treats
  `total == 0` as "the server would not say", so a length-less transfer is
  unchanged. Three unit tests cover the short body, the complete one, and the
  unknown length.
- `test/win32/update-progress.ps1`: the asset server learned a `-NoLength`
  mode; section 4 cuts a 12 MB promise off after 2 MB and asserts the failure
  is `Truncated`, nothing was staged, and the panel said the download failed;
  section 5 serves a length-less 4 MB body and asserts it ran to completion and
  failed the PACKAGE check instead. ALL PASS, 42 assertions.

  update-apply, update-failure-visible, update-graceful, update-real-msi and
