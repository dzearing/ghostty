# T860 - The agent lane intermittently fails benchmark.OscParser.decltest.OscParser with a leak through an async WebView2 popup callback - build-runner mode only, ~13 percent under load

## Summary

Caught red-handed by the 2026-08-15 T443 active-window probe: 2 of 15 loaded build-runner agent-lane runs failed the same way (soak label boost-on-baseline, logs in %TEMP%\ghoztty-soak and %TEMP%\floor-lane-agent-20260815-130157-606.log / -131348-619.log). Shape, identical both times: test 'benchmark.OscParser.decltest.OscParser' fails, stderr carries '[terminal_apc] (warn): kitty graphics protocol error: error.InvalidFormat', and the run reports 1 leaked with the trace ViewerPane.ensureNav <- ViewerPane.start <- testPopupOpen <- adoptPopup <- onNewWindowRequested <- comInvoke2 <- EmbeddedBrowserWebView.dll. That trace is an ASYNC WebView2 COM callback from a ViewerPane popup test landing while a LATER test is running and allocating with the current test's std.testing allocator - cross-test contamination, with OscParser as the bystander victim. Consistent with that: the failing seed replays clean standalone (ghoztty-agent-core-test.exe --seed=0xa9d599b3 direct = exit 0, all pass), so the failure needs mainServer()'s one-test-per-pipe-message timing, the same build-runner-only signature T832 measured for T443. Fix direction: make the ViewerPane popup test (testPopupOpen / adoptPopup path) drain or cancel its WebView2 async callbacks before the test returns, so nothing fires into a later test's allocator; then soak the agent lane in build-runner mode to confirm the rate drops to 0. This is the same defect T776 could not read the text of - it now has a face.

## In plain terms

When a web page open in a viewer pane pops a window open by itself, Ghoztty had
to decide whether to hand that page to your default browser or keep it in a
Ghoztty window. Holding **Ctrl** is the way you ask for the second — but Windows
was reading the Ctrl key off the whole desktop, so a Ctrl you were holding for
something else entirely, in another app, could grab a popup you never asked
about and open it here instead of in your browser. macOS never had that problem:
there the modifier belongs to the click. After this, the Ctrl shortcut only
counts when *you* clicked; a page opening a window on its own goes where it
would have gone anyway. The same bug was also making the test lane fail about
one run in eight, which is how it was found.

## Goals

- [x] The Ctrl escape hatch only applies to a popup a user gesture asked for
- [x] A page's own `window.open()` routes the same however the desktop keyboard
      looks at that instant
- [x] The live popup test states the Ctrl state instead of sampling it, so it
      cannot be failed by what someone is typing in another app
- [x] The Ctrl escape hatch gets live coverage it never had: the same URL,
      routed both ways, one run apart
- [x] A test wait that runs out says so, rather than failing an unrelated
      assertion thirty seconds later
- [x] An unexpected second popup adoption cannot show up as a memory leak

## Validation criteria

- [x] `viewer_popup.destination` routes a Ctrl-held **scripted** popup to the
      browser and a Ctrl-held **user-initiated** one to a Ghoztty window — new
      test "a Ctrl the user is holding for something else does not reroute a
      scripted popup", plus the `ctrlEscape` truth table. `none` lane PASS.
- [x] The live T163 popup test asserts the runtime reports the opener page's own
      load-time `window.open()` as not user-initiated — the gate's premise,
      measured rather than assumed. Lane log: `gesture flags: page's own
      window.open()=false, ExecuteScript's=true`.
- [x] The live T163 popup test STATES the Ctrl state through the `ctrl_probe`
      seam instead of sampling the desktop keyboard, so its routing assertions
      cannot be decided by what is being typed in another app.
- [x] **The mechanism, executable.** T163 now has a live Ctrl leg: the SAME http
      URL that leaves for the browser with no Ctrl is adopted as a pane with
      Ctrl held. Lane log, one run apart: `an http popup still reached the
      default browser` then `popup adoption #2 at
      'http://127.0.0.1:58282/elsewhere.html'` / `with Ctrl held, the same http
      popup stayed in ghoztty`. That is exactly what a stray desktop Ctrl did to
      the browser leg before this task, and the Ctrl escape hatch had no live
      coverage at all before it.
- [x] `waitFor` returns `error.WaitForTimeout` instead of falling through
      silently, and the whole win32 lane is still green under that (407s PASS).
- [x] The popup test sink holds every adopted pane, so a second adoption fails
      the routing assertion rather than leaking a `ViewerPane` — proven by the
      Ctrl leg above, which adopts twice in one run with 0 leaks reported.
- [x] Floor green: lib PASS, none PASS, win32 PASS (407s), agent PASS (383s).
- [ ] **NOT DONE: the loaded build-runner soak.** Two attempts (12 runs and 6
      runs, 8 `build` load workers) were killed by the environment inside their
      first lane run, ~3 min in, with no partial verdict. Recorded rather than
      quietly dropped — but note it would have been weak evidence either way:
      the baseline condition is *a human pressing Ctrl*, and an unattended soak
      does not reproduce it, so a green soak cannot tell the fix from an idle
      keyboard. The live Ctrl leg above is the decisive evidence instead: it
      demonstrates the causal chain rather than sampling for its absence.
      Follow-up on the killed-soak tooling: T954.
