# T224 - Decide the off-input-desktop oracle for overlay-zorder and profile-latency

## Summary

Two of T217's remaining scripts cannot be *mechanically* converted the way the
first 18 were, because the quantity they measure does not exist off the input
desktop. Neither is blocked on T214 (that is the terminal-surface CAPTURE
limit, which blocks `split-dim`); both are blocked on a decision about what the
assertion should measure instead. Filed out of T217 batch 7 so the decision is
not made accidentally inside a migration turn.

Do NOT migrate either script until this task has answered its question. A
port that quietly substitutes a different quantity is the vacuous-assertion
failure mode T217 batch 3 and batch 4 both warn about - worse here, because
`overlay-zorder`'s assertions would *invert* rather than merely weaken.

## Details

### `overlay-zorder` - "the foreground window" has no meaning here

The whole T142 oracle is expressed against the FOREGROUND window: the banner
overlay must sit above its own window and BELOW whichever window holds the
foreground (section A), topmosting it must put it above that window (B), and a
reposition (C) or an ACTIVATION CHANGE (D) must heal it. On a background
desktop `GetForegroundWindow` returns 0 for every window
(`lib/TestDesktop.ps1` header; measured again in T217 batch 6, where
`session-reattach`'s foreground assertion had to be deleted rather than
relabelled because it scored zero and passed).

What is already fine: the z-order half. `EnumWindows` index, `WS_EX_TOPMOST`
(now readable through batch 7's `Get-TestWindowStyle`), the owner-relative
"nothing foreign is sandwiched between the overlay and its owner" test, and
`WindowFromPoint` are all per-desktop and only need marshalling onto the
harness worker thread.

The question to MEASURE before writing any assertion:

- Does `Focus-TestWindow` (AttachThreadInput + SetActiveWindow + SetFocus)
  raise a window inside the non-topmost band the way real activation does? If
  it does, "the ACTIVE window" is a faithful stand-in for "the foreground
  window" throughout, and the script ports with a rename.
- Does it deliver WM_ACTIVATE to the app? Section D's entire claim is that
  activation alone heals a stray topmost bit - the case a window nobody
  resizes depends on - so if no WM_ACTIVATE arrives, D is not portable and
  must be marked as such rather than dropped silently.
- Does `SWP_SHOWWINDOW` still lift a freshly shown popup to the top of the
  band on a desktop with no foreground? That behaviour is the SECOND half of
  the filed defect (section A's discovery), and if it does not reproduce here
  then section A proves nothing on the test desktop.

Whatever the answers, record them in this file with the measurement, and only
then migrate. If the answer is "no faithful stand-in", the right outcome is a
split: migrate the z-order/topmost half and leave the activation half as an
explicitly-named gap (the T207 option-B bucket), not a quietly weakened
assertion.

### `profile-latency` - it measures a different quantity

Two independent problems, already noted in T217 batch 6 and repeated here so
the decision has one home:

1. Its section-3 positive control is a `PrintWindow` pixel hash of the
   **terminal surface** before/after `ctrl+home`. That is the CAPTURE LIMIT
   case: PrintWindow returns a flat fill there, so the two hashes are EQUAL
   and the assertion inverts (it asserts they differ). This half is blocked
   on **T214**.
2. It measures input LATENCY through `SendInput`. A posted `WM_KEYDOWN`
   bypasses the raw-input/queue path a real keystroke takes, so a posted-key
   port measures a different number - not a slower or noisier version of the
   same one. Decide deliberately whether this script keeps an interactive-
   desktop carve-out (with the T207 rule making that explicit and rare), moves
   to a latency oracle the app can report about itself, or is retired.

## THE ANSWERS (measured on box 2026-08-01, debug build, background test desktop)

Probes: `Get-TestZIndex` / `Get-TestActiveWindow` / `Get-TestOverlaySandwich` /
`Get-TestWindowAt` / `Set-TestWindowTopmost` / `Set-TestWindowShown`, all added
to `lib\TestDesktop.ps1` for this task (EnumWindows walks the CALLING thread's
desktop, so every one of them had to be marshalled onto the worker thread).
Two windows in one process, oz2 parked exactly over oz1, banner on oz1.

### `overlay-zorder` - the three questions, answered

1. **Does `Focus-TestWindow` raise the window inside the band, the way real
   activation does? YES.** With oz2 active: `ov=3 A=4 B=1`. Activate oz1
   instead: `ov=1 A=2 B=4` - the activated window moves above the other and
   drags its owned overlay with it. Reproduced across two runs, and again in
   the migrated script's three green runs. So **"the ACTIVE window"
   (`GetGUIThreadInfo.hwndActive`) is a faithful stand-in** for the foreground
   window in this oracle.

   Corollary that would have silently killed the port: **`Focus-TestWindow`'s
   boolean return is not the activation oracle.** Called without `-Child` it
   returns False on a ghoztty window (measured: `returned=False
   focused=<pane> active=<top>`), because the app moves keyboard focus to the
   GhozttyTerminal child, so `GetFocus()` is never the top-level. The old
   script aborted the whole run on `GrabForeground`'s return; a mechanical
   port of that gate aborts every run and prints no verdict. Gate on
   `Get-TestActiveWindow` (or pass `-Child`, which does return True).

2. **Does it deliver WM_ACTIVATE? YES.** An injected stray topmost cleared
   after nothing but an activation switch, with no layout event, in every run.
   That is a sound proof rather than an inference: `Window.healOverlayZOrders`
   has exactly ONE caller in the tree, the `WM_ACTIVATE` handler
   (`src/apprt/win32/Window.zig`, verified by grep over `src/`). **Section D
   is portable, and it doubles as the harness's own activation proof.**

3. **Does `SWP_SHOWWINDOW` still lift a freshly shown popup to the top of the
   band? NO.** Hiding the overlay and re-showing it with
   `SWP_SHOWWINDOW|SWP_NOZORDER|SWP_NOACTIVATE` - the product's own flag set -
   put it back at the SAME index (2), still below the active window, where on
   the input desktop it goes to the top of the band. So **section A's original
   discovery mode does not reproduce off the input desktop**; section A is a
   healthy-state baseline there and the stray-bit half carries the repro. Named
   in the script header rather than left as a silent gap.

### What had to change rather than port

- **The SANDWICH is no longer the section-B repro.** Measured: topmosting the
  overlay also raises its OWNER to the top of the band - unopposed where no
  window holds the foreground - so nothing foreign ends up between overlay and
  owner, and `Sandwich` reads `0:` in the healthy AND the injected state. It
  stays as the healthy-state invariant (A and C). The two measures that DID
  discriminate replace it: z-index against the ACTIVE window (healthy `ov=3 >
  B=1`; injected `ov=0 < B=4`) and `WindowFromPoint` over the banner band
  (healthy: oz2's terminal; injected: `GhozttyBannerOverlay`). Both statements
  are equally true on the interactive desktop, so `-Interactive` scores the
  same assertions - the port did not fork the oracle.

- **Section E is SKIPPED, and that is a product finding, not a harness one.**
  E needs a legitimately-topmost owner (`toggle_window_float_on_top`). On this
  box a ghoztty window cannot reach that state: the bound action leaves
  `WS_EX_TOPMOST` clear (twice, with a `new_window` control keybind proving
  the keybind path works), and an injected `HWND_TOPMOST` does not stick
  either - while a plain Win32 window (`charmap`, class `#32770`) in the SAME
  harness and desktop keeps it in all three conditions tested. So float-on-top
  itself is broken: **T277**. E announces the skip, names T277, and starts
  asserting again with no edit the moment the float sticks.

### `profile-latency` - the decision

**Interactive by design, declared - not migrated.** Both halves of the
question are already settled and the answer is the same:

- Its section-3 pixel hash is a TERMINAL-SURFACE probe, and T214 decided that
  case: it is declared in `lib\TestDesktop.ps1`'s "terminal-content probes
  that stay on the input desktop" list, which is the mechanism that keeps an
  exception from being indistinguishable from an oversight.
- The latency number IS `SendInput` timing. A posted `WM_KEYDOWN` skips the
  raw-input/queue path, so a posted-key port measures a DIFFERENT quantity,
  not a noisier version of the same one - the substitution T217 batches 3 and
  4 warn about. Retiring it would delete the only latency oracle; moving it to
  an app-reported number is a different task, not a migration.

`test/win32/profile-latency.ps1` and `context-menu-real-input.ps1` are
therefore the two standing interactive-by-design scripts, both listed in T272.
