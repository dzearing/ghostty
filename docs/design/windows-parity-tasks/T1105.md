# T1105 - Every relay path fails end to end: ipc-relay.ps1 is red on 14 of its assertions

## In plain terms

Opening a terminal on another machine through the relay does not work in the automated end-to-end check - not the connection, not typing into it, not running a command, and not the error messages you should get when you are signed out or use a bad token. Fourteen separate checks fail, starting with the very first plain local window the test opens.

## Summary

`test\win32\ipc-relay.ps1` scored `14 FAILURE(S)` in the T1094 sweep - the largest red in the suite.

Setup is HEALTHY, which is what makes this interesting:

```
PASS relay builds
PASS relay is healthy
PASS device enrolled (id + token)
PASS agent is running
```

Then the first thing that opens a window fails, before any relay behaviour is exercised at all:

```
== 0c: base local window
  FAIL base window exit 0
  PASS [isolation] the answering instance is ours, not the caller's own app
```

and from there everything downstream fails, including the negative cases:

```
FAIL exit 0 / FAIL relay window registered under --name
FAIL send-keys exit 0 / FAIL remote output visible via +read
FAIL error says not signed in
FAIL exit nonzero / FAIL error names device via relay
FAIL +list still answers after agent death / FAIL app still alive
FAIL close exit 0 within timeout / FAIL app survived the teardown
```

**The base-window failure is the thread to pull.** `0c` opens an ordinary local window with no relay involved; if that returns nonzero, the other thirteen assertions never had a chance and this is one fault, not fourteen. Note the isolation assertion immediately after it passes, so an app IS answering on the private endpoint - the launch returned nonzero while apparently working, or returned nonzero for a reason the script does not print.

Do not fix thirteen symptoms. Get `0c` green first and re-measure.

## Where

- the relay dial path and `+new-remote-window`, only after 0c is understood

## What it turned out to be

**Not fourteen defects, and not a product defect.** `git diff 9a764deea..HEAD`
- the sweep's commit against today's HEAD - touches **no file under `src/` at
all**. The code under test is byte-identical to the code that scored
`14 FAILURE(S)`, and the script is **ALL PASS in ~35s** on that same code. So
there was never a relay bug to find: the run died on its setup for a reason the
box did not keep, and no repro survives.

What IS a defect, and what this task fixed, is that the failure was
**unreadable and self-multiplying**:

1. **0c did not gate.** Sections 0a (relay) and 0b (agent) both `exit 1` when
   their setup fails; 0c - the live app every later section opens its relay
   windows in - did not. One dead app therefore printed thirteen more failures,
   and the count sent triage looking for fourteen faults.
2. **The log could not tell a refusal from a hang.** `Run-Cli` returns `$null`
   on timeout, and `$null -eq 0` is false, so `FAIL base window exit 0` covered
   both "the CLI refused with 3" and "the CLI never came back". The 4m41s the
   runner recorded was the only surviving hint, and it is not in the log.
3. **The CLI's own output was thrown away.** `base.txt` had whatever the CLI
   said on the way out and nothing ever printed it.
4. **The isolation assertion passed vacuously.** `Assert-GhozttyIsolated` looks
   for a foreign `"exe"` and the caller's pane id; `No running Ghoztty instance
   found.` contains neither, so it prints PASS against a dead endpoint. In the
   sweep it did that one line under the 0c failure, which reads as "an app is up,
   the launch just returned nonzero" - the opposite of what had happened, and
   the reading this task was filed on.

Also fixed while here: the harness agent had **no lineage of its own**. Every
sibling relay harness forks `GHOZTTY_AGENT_INSTANCE`; this one did not, so its
agent claimed the legacy relay singleton `Global\GhozttyAgentDaemon-<SID>` -
the name the box's own relay agent and every other relay harness compete for.
That is a live cross-contamination vector during a 242-script sweep, and it is
the kind of thing that produces exactly this shape of one-shot failure.
