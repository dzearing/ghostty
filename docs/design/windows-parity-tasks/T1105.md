# T1105 - Every relay path fails end to end: ipc-relay.ps1 is red on 14 of its assertions

## In plain terms

Opening a terminal on another machine through the relay does not work in the automated end-to-end check - not the connection, not typing into it, not running a command, and not the error messages you should get when you are signed out or use a bad token. Fourteen separate checks fail, starting with the very first plain local window the test opens.

## Summary

`test\win32\ipc-relay.ps1` scored `14 FAILURE(S)` in the T1094 sweep - the largest red in the suite.

Setup is HEALTHY, which is what makes this interesting:

```
PASS relay builds
PASS relay is healthy
PASS device enrolled (id + token)
PASS agent is running
```

Then the first thing that opens a window fails, before any relay behaviour is exercised at all:

```
== 0c: base local window
  FAIL base window exit 0
  PASS [isolation] the answering instance is ours, not the caller's own app
```

and from there everything downstream fails, including the negative cases:

```
FAIL exit 0 / FAIL relay window registered under --name
FAIL send-keys exit 0 / FAIL remote output visible via +read
FAIL error says not signed in
FAIL exit nonzero / FAIL error names device via relay
FAIL +list still answers after agent death / FAIL app still alive
FAIL close exit 0 within timeout / FAIL app survived the teardown
```

**The base-window failure is the thread to pull.** `0c` opens an ordinary local window with no relay involved; if that returns nonzero, the other thirteen assertions never had a chance and this is one fault, not fourteen. Note the isolation assertion immediately after it passes, so an app IS answering on the private endpoint - the launch returned nonzero while apparently working, or returned nonzero for a reason the script does not print.

Do not fix thirteen symptoms. Get `0c` green first and re-measure.

## Where

- `test/win32/ipc-relay.ps1` - section 0c first
- the relay dial path and `+new-remote-window`, only after 0c is understood
