# T1158 - morning-refresh restarts the user's primary terminal unattended into a growing pinned-session set

## Summary

Reported by the user 2026-08-23: "you left some insane window spamming what
looked like stress spam open. I think it's been crashing explorer ... not even
dev window, looked like our release window."

It was not a stress script. No soak ran that day - the newest directory under
`%TEMP%/ghoztty-soak/` was 2026-08-17, and `soak.ps1` (whose subject legitimately
IS the release build, per T350) was never invoked. The storm came from the loop's
own daily delivery job, and it landed on the installed app because that is what
the job is for.

Timeline, from `%TEMP%/ghoztty-morning-refresh.log` and process start times:

- `05:05:15` morning-refresh scores DUE ("first push at/after 5:00 today")
- `05:10:21` it logs `LAUNCH OK` for `scripts/launch-upgrade.ps1`, having built
  `zig-out-release/bin/ghoztty.exe` (mtime 05:10) and delivered it
- `05:10:31` the installed `ghoztty.exe` under
  `%LOCALAPPDATA%/Programs/Ghoztty/` starts - ten seconds later, the same event
- `05:35:51` a cluster of BlueScreen / LiveKernelEvent entries in the
  Application log
- `08:43:44` explorer `AppHangTransient`; explorer's live pid dates from 08:43

The restart on its own is by design. What turns it into a window storm is what
it restarts INTO. The installed agent (`ghoztty-agent.exe`, running since 08-18)
was holding **12 pinned sessions, 6 of them `detached`**, with 24 child
processes (12 `cmd.exe` + 12 `conhost.exe`). Every one is `pinned`, so none of
them ages out. A detached pinned session is one no window is attached to and
nothing will ever close - it is a leak, and the population only grows across
loop runs. Each morning's unattended relaunch therefore restores a bigger burst
of windows than the one before.

The daily relaunch itself is NOT the defect, and a fix that removes it would be
regressing a feature the user asked for. Step 6.5 of `go.md` exists because
"the user works all day inside one Ghoztty, which keeps running whatever exe it
was launched with, so work that shipped days ago reads to them as a missing
feature" - measured twice, 2026-08-06 and 2026-08-07. One restart per day is the
agreed price and the watermark already holds it to exactly one.

What was never part of that bargain is what the restart restores INTO. The
defect is the pinned-session leak in the INSTALLED agent:

- Six detached pinned sessions with no window is not a state any user action
  produced. Something in the loop - acceptance runs, `/reset-context` cycles, or
  both - is seeding the installed (release-endpoint) agent rather than only the
  `-debug` one, and leaving pins behind that nothing reaps.
- Because they are `pinned`, they never age out, so the population is monotonic.
  A restart that was meant to bring back the user's real windows brings back
  every abandoned one as well, and the burst grows every day the loop runs.

Same family as T108's session leak, but against the release endpoint, and this
time with the daily restart to amplify it.

Whether the BlueScreen cluster at 05:35 and the 08:43 explorer hang are caused
by the burst or merely downstream of it is unproven and should not be assumed -
but a shell that is handed a dozen restoring top-level windows at once is a
plausible enough trigger to be worth ruling in or out with evidence.

Note the ping-pong storm of T105 is NOT this - that was fixed 2026-07-20 and the
installed build long postdates it. This storm is window COUNT at restore, not
foreground flipping.

## In plain terms

Every night the loop restarts your terminal once, on purpose, so the morning's
build is the one you are using. What nobody meant to happen is what it was
restarting INTO. The automated stability soak was opening its test panes inside
*your* terminal's session keeper instead of its own, and those panes are marked
"keep this alive even after the window closes" - which is exactly right for a
real pane you want back tomorrow, and exactly wrong for a test fixture. So every
soak run quietly left a few more abandoned shells behind, they could never age
out, and the pile only ever grew. After this, the soak runs in a sandbox of its
own and proves, every single run, that it added nothing to your terminal.

## What it was

Not the restore, and not a stress script. `test\win32\soak.ps1`.

The evidence is exact. The six detached pinned sessions were created in two
bursts - 2026-08-22 05:19:33 (x2) and 2026-08-23 01:05:08 (x4) - and
`%TEMP%\ghoztty-soak\` holds run directories `20260822-051928` and
`20260823-010503`, five seconds before each burst. All six `cmd.exe` children
had the INSTALLED agent as their parent, and none carried an argv or an
`fg_cmd`: bare shells nobody ever typed in. (The task text above says no soak
ran that day; that was wrong, and the run directories are why.)

The mechanism was a half-isolated harness. Isolating a release-lineage run takes
three knobs, and `test\win32\lib\BuildMode.ps1`'s own header already named the
failure: *"One or two of the three is the dangerous state, not a partial win: a
release build under a private pipe suffix alone still dials the agent that owns
the user's live sessions."* The soak set `GHOZTTY_PIPE_SUFFIX` and nothing else,
then passed `-AllowReleaseBuild`. Its app pipe was private while every pane it
opened became a PINNED session in the user's real roster. Its teardown closes
the window, and a pinned session surviving a window close *is* the persistence
feature (`session.zig:1729`, `if (s.pinned and s.alive) continue`), so nothing
reaped them.

The reason a documented rule did not stop it: `-Allow` **returned
unconditionally**. The gate took the caller's word. It now verifies.

Two things were found on the way and are NOT fixed here, each filed:

- **T1162** - the deeper half. Killing those six shells did not free their
  sessions: sixty seconds on, the agent still reported all six `alive` against
  dead pids. `markExited` is reachable from exactly one place, `onChildOutput`,
  so exit detection rides the child's output path and needs a live reader; the
  `--pty-host` holders were long gone, so no EOF, no nudge, no reap, ever.
- **T1160** - the soak's `median fps >= 20` bar was graded from the USER'S
  `ghoztty.log`, because LOCALAPPDATA was not isolated either. It was passing on
  the frames of the terminal the user was working in.
