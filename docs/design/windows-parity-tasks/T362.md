# T362 - win32 test lane is flaky: font.Collection 'add full' crashes with exit code 5 on some runs and passes on the next

## In plain terms

One of the standing test suites sometimes dies instead of finishing: a font
test crashes the whole test process, and running the exact same suite again
immediately passes. A test suite that cries wolf like this teaches everyone to
just re-run until it goes green - which is how a real bug slips through one
day. This task finds out whether the crash is its own bug or another sighting
of the known intermittent memory corruption already being tracked (T443), and
either fixes it or records it on that watch.

## Goals

- [x] Rule out (or find) a real defect in the font-collection code the test exercises
- [x] Measure whether the crash reproduces at today's code (soak runs, not a single run)
- [x] Disposition: either a fix, or fold into the T443 armed watch with the evidence

## Validation criteria

- [x] Font code reviewed for a use-after-free / overflow in the 'collection full' path
      (read `Collection.add` + the test: CollectionFull returns before the face is
      touched, the test deinits the extra face manually; no local change to
      src/font since 2026-07-05, Collection.zig since 2026-01-20)
- [x] Soak of the win32 test binary at HEAD (filtered + full, incl. recorded seed 0x6e8a8aaf)

## Result (2026-08-06)

**This is the T443 ghost, not a font bug - closed as duplicate -> T443.**
Fourth victim-test fold-in (after T317, T369, T238). The `add full` test is the
win32 lane's largest heap workload (~16k FreeType Face.inits), which is the
profile of a corruption victim. No repro at HEAD in 210 runs of this victim
(10 loaded full-binary runs with the red seed + 200 filtered), consistent with
every post-2026-08-04 attempt on this class. The armed watch (T444 exit-code
decode + T450 auto cdb capture, both wired into floor-lane.ps1) captures the
next natural occurrence with a full all-thread stack. Do not reopen this file;
a new occurrence belongs in T443's ARMED-WATCH LOG.

## Summary

`zig build test -Dapp-runtime=win32` - one of the two standing floor lanes -
fails intermittently in `font.Collection.test.add full`. The test binary does not
report a failed assertion; it **exits with code 5**, i.e. the process died. The
very next run of the same unchanged tree is green.

This is the T258 shape in a second lane. A floor lane that is green on the retry
trains every turn to re-run until green, which is precisely how a real regression
gets waved through.

## Evidence (VERIFIED on the box, 2026-08-02, during T267)

No `src/` file had been modified - the turn's whole diff was `test\win32\` -
so nothing in the product changed between the red run and the green one.

Red run:

```
error: while executing test 'font.Collection.test.add full', the following
command exited with code 5 (expected exited with code 0):
".\.zig-cache\o\f8d3ef870d388c9a8fe7c5d73b1b25fd\ghostty-test.exe"
    "--cache-dir=.\.zig-cache" --seed=0x6e8a8aaf --listen=-

Build Summary: 48/50 steps succeeded; 1 failed; 3644/3662 tests passed; 18 skipped
```

Immediate re-run, same command, same tree: `exit 0`.

Two lines printed just above the failure are worth keeping in view, since they
show what else the shared test binary was doing at the time:
`[tripwire] (warn): untripped point=read` and
`[relay_directory] (warn): device rename: relay returned HTTP 500`.

## Notes for whoever takes it

- Exit code 5 with no assertion text means a crash/abort, not a failed
  `expectEqual` - look for a use-after-free, a leaked handle, or an OOM path in
  the font discovery/collection code rather than for a wrong number.
- `add full` suggests the collection-is-full branch, which is the one that runs
  rarely and is therefore the one least likely to be exercised elsewhere.
- The zig test runner shares one process across the lane's tests, so a crash
  attributed to this test may have been *caused* by a neighbour. Re-run the
  single test in isolation (and repeatedly) before concluding it is the culprit.
- `--seed` is printed on every run; capture the seed from a red run, since the
  runner may be ordering tests by it.

## Validation

- Run `zig build test -Dapp-runtime=win32` 20 times back to back: 20 green.
- If the cause is a neighbouring test, the fix is still measured that way -
  a lane that needs a retry is not a passing lane.
