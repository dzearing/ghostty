# T858 - test-binary-soak teardown kills the load worker's children before the worker - the still-alive loop logs a phantom exit=-1 iteration and spawns a new command mid-teardown

## In plain terms

The crash-soak tool holds "load" programs busy on the machine while it runs a
test, and when the soak ends it shuts them down. The shutdown killed each
worker's children before the worker itself, so in the fraction of a second it
stayed alive the worker wrote a bogus "my command finished" record and even
started a brand-new command. The soak's report then claimed load work
completed that never really did — the exact kind of mismeasurement the tool
exists to prevent.

## Summary

`Stop-SoakProcessTree` in `scripts\test-binary-soak.ps1` recursed depth-first
(children before root) with one CIM query per level. Each query takes long
enough that after the worker's in-flight command was killed, the still-alive
worker loop recorded `exit=-1` as a completed iteration and spawned the next
command inside the teardown window. Observed 2026-08-15 while validating T509:
`test\win32\test-binary-soak.ps1` section 3c failed twice reproducibly — the
45s-ping fixture reported `1 iteration(s) completed of 2 started` instead of
`0 completed, 1 in flight`, and the summary carried `load-iters=1 started=2`.

Fix: kill the ROOT first (nothing can respawn once the worker is dead), then
sweep descendants by walking the stale-`ParentProcessId` closure over fresh
`Win32_Process` snapshots until no family member is left alive.
