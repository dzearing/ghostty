# T795 - Bake the Google OAuth client id into delivered Windows builds

## Summary

T747 made an unconfigured build honest - the machine chooser now says sign-in is not set up instead of offering a button that cannot work - but relay sign-in is still UNAVAILABLE in every delivered Windows build, because the delivery scripts pass no -Dgoogle-client-id and no google-client-id.txt exists on this box. Blocked on D72, which asks the user where the id should come from (repo-root git-ignored file / explicit -Dgoogle-client-id in the delivery scripts / hardcoded in the repo). When D72 is answered: wire that source, rebuild, and verify against a real relay that the chooser's button appears and a browser sign-in completes end to end. Acceptance today only proves the UNCONFIGURED presentation plus a fake-relay flow under GHOSTTY_GOOGLE_CLIENT_ID=cid-e2e; a real signed-in delivered build has never been observed on this seat.

## In plain terms

Signing in to a remote-machine account needs a credential that gets stamped into
the terminal when it is built. Every Windows copy we have ever published was
built without one, so the sign-in row in the machine chooser said "not set up" no
matter what the user did - while the Mac download from the very same release
worked. Nothing anywhere reported this: the terminal never mentioned which
credential it carried, and the scripts that deliver new builds checked the
version, the build type and the helper program, but never this. Now the terminal
says which credential it holds (or that it holds none), the release pipeline
stamps in the same one the Mac build uses, and a delivery shouts when it is about
to ship a build that cannot sign in.

## Goals

- [x] a built binary can be ASKED whether it can sign in, and with which id
- [x] the published Windows artifacts bake the same credential the Mac ones do
- [x] a delivery says, up front, when the build it is shipping cannot sign in
- [x] and reads the state back out of every location it delivered to
- [x] the on-box source (a git-ignored file at the repo root, per D72) is proven
      to actually bake, which had never been observed
- [ ] a real signed-in delivered build, against a real relay - needs the user's
      credential, so it is T915's

## Validation criteria

- [x] a build with a repo-root `google-client-id.txt` reports
      `relay sign-in : configured (<id>)` from `ghoztty +version` - measured on
      the box: a synthetic `795-onbox-proof.apps.googleusercontent.com` in that
      file, `zig build -Dapp-runtime=win32 -Doptimize=Debug`, then
      `ghoztty.exe +version` printed exactly that. First end-to-end proof that
      D72's chosen mechanism bakes at all.
- [x] the same tree with the file removed and rebuilt reports
      `relay sign-in : not configured (no google client id baked in)` - measured
      the same way, and it is the state `zig-out` was left in so no fake id can
      resurrect T747's dead button.
- [x] the reader that a delivery uses agrees with the printer, against a real
      binary rather than a fixture - `test\win32\upgrade-staleness.ps1` arms
      A36-A48 (pure: configured / unconfigured / pre-T795 / unrecognised /
      wrong-id oracle) and B1b (live: the built exe's own payload).
- [x] a delivery whose staged build cannot sign in WARNS in words that name the
      fix, and one that can names the id in every verified location -
      `test\win32\deliver-windows-build.ps1` section F.
- [x] the release pipeline bakes the SAME repository secret on both seats, and
      only passes the flag when it is non-empty (an explicit
      `-Dgoogle-client-id=""` would satisfy the build option and kill the
      repo-root fallback) - `test\win32\release-artifacts.ps1` section F.
- [x] the standing floor: `scripts\floor-lane.ps1 -Lane all`, plus P1-P3.
