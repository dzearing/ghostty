# T552 - +sessions --json could report the pane id a session is bound to (symmetry with T332)

## In plain terms

T332 made `+list --json` say which background session each pane is showing.
The reverse direction — asking the session list which pane each session lives
in — still has no answer. That matters because `+sessions` works even when the
Ghoztty app is closed, so it is the only view a script has in that state.

## Summary

T332 added `session_id` to `+list --json`'s terminal panes, so the pane→session
join is answerable while the app is up. The reverse join from `+sessions
--json` (which dials the agent directly and works with the app closed) still
is not: a session row says `attached` but never WHICH pane took it.

The agent already stores each session's baked spawn env for RELAUNCH, and that
env carries `GHOZTTY_PANE_ID` (`src/remote/agent/server.zig` replays it; pane
ids are stable across restore, so the stored id IS the pane the session
belongs to for local panes). So the agent could surface a `pane_id` field on
its LIST response rows without the app's help.

Caveats to design around:

- **Additive protocol only** (agent contract): new field on the agent's LIST
  response; old app/CLI ignore it, old agent omits it — degrade to absent.
- **Cross-machine sessions**: the viewing pane lives on another machine; the
  stored env's pane id (if any) describes the machine the session runs on, not
  the viewer. Decide whether to omit the field there or document the meaning.
- A session opened by an older app may have no `GHOZTTY_PANE_ID` in its env —
  the field must be optional per row, not per build.

## Validation criteria

- [ ] Agent LIST response carries `pane_id` for sessions whose stored env has
      `GHOZTTY_PANE_ID`; omitted otherwise (unit test in the agent lane)
- [ ] `+sessions --json` prints the field; the human tree is unchanged
- [ ] On box: the `pane_id` on an attached session's row matches the pane
      whose `+list --json` `session_id` names that session (round trip)
- [ ] Old-agent skew: `+sessions` against an agent without the field still
      renders every row (absent, not error)
