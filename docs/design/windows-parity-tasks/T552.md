# T552 - +sessions --json could report the pane id a session is bound to (symmetry with T332)

## In plain terms

T332 made `+list --json` say which background session each pane is showing.
The reverse direction — asking the session list which pane each session lives
in — still has no answer. That matters because `+sessions` works even when the
Ghoztty app is closed, so it is the only view a script has in that state.

## Summary

T332 added `session_id` to `+list --json`'s terminal panes, so the pane→session
join is answerable while the app is up. The reverse join from `+sessions
--json` (which dials the agent directly and works with the app closed) still
is not: a session row says `attached` but never WHICH pane took it.

**Corrected on 2026-09-05 (the CHECK FIRST re-verification):** the agent does
NOT store a session's spawn env. `protocol.Relaunch` says so outright — "the
agent's on-disk session record keeps only argv-label/cwd" — which is exactly why
RELAUNCH has to carry env from the viewer (wp3). What IS true is that
`GHOZTTY_PANE_ID` ARRIVES at the agent, in the OPEN's env (the win32 surface
bakes it into `config.env`, which is forwarded verbatim) and again in the
RELAUNCH's. So the agent can record that one key at spawn — an identity rather
than an environment detail — and surface it on its LIST rows without the app's
help. Pane ids are stable across restore, so the recorded id stays the right
answer, which makes it worth persisting beside `fg_cmd`.

Caveats to design around:

- **Additive protocol only** (agent contract): new field on the agent's LIST
  response; old app/CLI ignore it, old agent omits it — degrade to absent.
- **Cross-machine sessions**: the viewing pane lives on another machine; the
  stored env's pane id (if any) describes the machine the session runs on, not
  the viewer. Decide whether to omit the field there or document the meaning.
- A session opened by an older app may have no `GHOZTTY_PANE_ID` in its env —
  the field must be optional per row, not per build.

      `+list --json` `session_id` names that session (round trip) — arm D of
      `test\win32\sessions-running-cmd.ps1`, `ALL PASS (16 checks)` on
      2026-09-05 with `pane_id = 6AD668C9-A110-4AFA-8AA0-3524D17FB46D` naming the
      pane whose leaf named that session back
- [x] Old-agent skew: absent, not error — the field is optional/defaulted on
      `protocol.SessionInfo`, `connection.OwnedSession` and the CLI row, and the
      second row of the CLI test above is exactly this case (renders, reads null).
      The reverse skew (old CLI, new agent) is the parser's `ignore_unknown_fields`
- [x] The pane id survives the reboot floor — `SessionTable.materialize: pane_id
      survives the reboot floor round-trip (T552)` plus the `session_meta`
      round-trip, so a relaunchable tombstone still names its pane after a restart
