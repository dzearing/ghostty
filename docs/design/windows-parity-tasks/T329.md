# T329 - The chooser's Activity button over a relay is now testable (FakeRelay.ps1) - close T295's uncovered DIALED entry

## Summary

`test/win32/activity-monitor-remote.ps1` says so in its own header:

> NOT COVERED HERE: the DIALED entry (the chooser's Activity button) needs a
> relay device, which needs a signed-in account; `chooser-menu.ps1` covers the
> button and this covers the data plane it lands on.

That was true until T319: the button and the data plane were each validated, and
the path between them — `App.openRelayWindow`'s token/base resolution,
`relay_dial.dial`, `ActivityMonitor.adoptDial`, and the panel sampling a machine
it reached through a relay — was validated by nobody.

`test/win32/lib/FakeRelay.ps1` removes the blocker. It serves the device
directory AND bridges `ws://…/v1/client/connect` to a real
`ghoztty-agent --listen`, so a relay device with live sessions is now a fixture
any script can stand up in a few lines (`chooser-sessions-remote.ps1` is the
worked example, and its `-UnauthorizedDevice` / `-UnreachableDevice` /
`-TripFile` verbs cover the sad paths).

## In plain terms

When you pick another machine from the machine list and press **Activity**, you
get a window showing what that machine is busy with. That window opens its own
private link to the machine. Nothing on this box ever checked what happens to
that link when you close the window while you also have a terminal open on the
same machine - and the way that goes wrong is not subtle: the wrong link gets
hung up, and the terminal you were working in goes dead. After this, a test on
this box opens both at once, closes the Activity window, and types into the
terminal to prove it is still there.

## Goals

- [x] a live remote window and a dialed Activity panel coexist in one fixture
- [x] the panel opens its OWN link rather than riding the window's
- [x] closing the panel gives back only its own link
- [x] the window keeps working afterwards, proved by typing into it
- [x] the stale "NOT COVERED HERE" note on the sibling harness is retired
- [x] the guard row that claims to cover the dial code names the file that code
      actually lives in

## Validation criteria

- [x] `test\win32\activity-monitor-dialed.ps1` ALL PASS on box, zero skips
- [x] `-NegativeControl` FAILS (the inverted root-pid oracle, in section 4 as
      well as section 1)
- [x] the floor lanes and P1-P3 stay green
- [x] no duplicate coverage filed: `+new-remote-window` with no `--token` is
      already proven end to end by `relay-account.ps1` section 7

## The work

Extend `activity-monitor-remote.ps1` (or add a sibling) with the third entry
style: open the chooser, select a relay device, press **Activity**, and assert
the panel comes up titled for THAT machine and sampling it — the same `root=`
pid oracle the existing script uses, which distinguishes a remote sample from a
local one. The ownership half matters as much: a DIALED panel owns its
connection (unlike the BORROWED one), so closing it must free the connection and
must not disturb any other window's session.

Also worth covering with the same fixture, since it is one line of setup away:
`+new-remote-window --relay/--device` with **no** `--token`, resolving the
signed-in account.

## Validation

On-box ALL PASS, plus a negative control (the relay's `-TripFile` inverts the
"the panel reached the machine" assertion without breaking the fixture's setup).
