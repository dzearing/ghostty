# T420 - Agent metrics pump: stopMetricsPump touches metrics_thread outside the mutex, so a concurrent UNSUB and shutdown double-join and crash

## Summary

Found by T118 (2026-08-03) on a floor run. `zig build test -Dapp-runtime=none`
died with **exit code 3** in
`remote.agent.server.test."METRICS_SUB pushes metrics frames; METRICS_UNSUB
stops the pump cleanly"` — not an assertion failure, a **crash in std**:

```
assert(ntdll.NtClose(hObject) == .SUCCESS)     std/os/windows.zig:596 CloseHandle
                                               std/Thread.zig:679     join
src/remote/agent/server.zig:1560               stopMetricsPump   -> t.join()
src/remote/agent/server.zig:394                shutdown
src/remote/agent/server.zig:2181               deinit
```

i.e. a thread handle was closed twice: the thread had already been joined.

## The race

`stopMetricsPump` (`server.zig:1553`) takes `metrics_mutex` only for the STOP
FLAG, then reads and clears `self.metrics_thread` **outside** it:

```zig
self.metrics_mutex.lock();
self.metrics_stop = true; ... self.metrics_cond.signal();
self.metrics_mutex.unlock();
if (self.metrics_thread) |t| {   // <- unsynchronized read
    t.join();                    // <- two callers can both get here
    self.metrics_thread = null;  // <- and the second join is a use-after-close
}
```

It has two callers on different threads — `handleMetricsUnsub` (control
channel) and `shutdown` (deinit) — and its doc comment claims it is
"idempotent and safe to call with no pump running", which is true only
sequentially. The spawn side (`:1536-1542`) reads `metrics_thread == null` and
assigns it around the same window, so the pairing is not clean there either,
and `:447` asserts `metrics_thread == null` — an assert that a losing race can
also trip.

This is a **product** bug, not a test bug: it crashes the agent's shutdown
path, and the agent is the process that owns every persistent PTY.

## Fix

Move the whole thread handoff under `metrics_mutex` (or an atomic swap): take
the thread OUT of the field while holding the lock, then join the local copy
outside it — so exactly one caller ever owns the join and a second caller sees
null. Do not join while holding the lock (the pump takes the same mutex).

## Validation

- The existing test, run in a loop (it is the one that caught it); it is
  intermittent, so a bare pass proves little — drive UNSUB and shutdown
  concurrently in a new test instead.
- `zig build test -Dapp-runtime=none` and `test-agent` green.

Related but distinct: **T416** (a test binary that HANGS at frozen CPU in the
WebView2 host-floor test) and **T258**/**T401** (agent-lane flakiness filed
earlier). This one has a stack and a named race, so it should be fixed on its
own evidence rather than folded into "the agent tests are flaky".
