# T346 - test-agent flake: server.zig spin-waits a fixed 10k yields, so DATA/detach tests fail under CPU load

## In plain terms

Some of the automated tests that gate every change occasionally report a
failure when nothing is actually broken — it only happens when the computer is
busy doing something else at the same time, because those tests give up after
"trying a number of times" instead of waiting a fixed amount of time. Once
fixed, a test failure will mean something is genuinely wrong, and nobody wastes
a work cycle re-running a red result to see if it was real.

## Goals

- [x] All the "try 10,000 times" waits in the agent's test suite are replaced
      with a shared wait-up-to-a-deadline helper (all 11 sites in server.zig).
- [x] The agent test lane passes repeatedly, including while the box is fully
      loaded (the exact condition that produced the false failure): 3 green
      runs of the final state, one of them under a 100% all-core load. The
      loaded runs surfaced and fixed two MORE load-sensitive tests beyond the
      spin waits — keepalive's live-link test (25ms stale window measured
      scheduler latency, not link health) and ProcSampler's busy test (asserted
      >= 50% CPU while the load generator was eating the core).
- [x] A deliberately broken wait times out with a clear failure instead of
      hanging (verified: disabled the server's DATA→child write; the test
      reported "slices differ" after the 10s bound instead of wedging).

## Summary

`zig build test-agent` failed on 2026-08-02 with
`remote.agent.server.test.unknown channel DATA is ignored (no crash, no child
write)`: expected `real`, found a zero-length slice. Nothing was wrong with the
code under test — the same test passed 3/3 in isolation
(`-Dtest-filter="unknown channel DATA"`) minutes later. The lane was running
while a `zig build -Doptimize=Debug` and two other test lanes had just churned
the box.

## Details

The tests wait for a cross-thread effect with a **fixed iteration count**, not a
deadline:

```zig
var spins: usize = 0;
while (spins < 10_000) : (spins += 1) {
    const got = try fc.inputCopy(alloc);
    defer alloc.free(got);
    if (std.mem.eql(u8, got, "real")) break;
    std.Thread.yield() catch {};
}
```

`src/remote/agent/server.zig:3627` (the DATA test) and `:3591` (the preceding
detach test) both use this shape. 10,000 `Thread.yield()` calls is a duration
only if the scheduler cooperates: on a loaded box every yield returns almost
immediately, so the budget can burn through in well under the time the server
thread needs to be scheduled at all. `got` came back **empty**, not partial —
the reader thread had not run once.

That makes the agent floor (`test-agent` green, per go.md step 3)
load-sensitive, which is exactly the wrong property for a gate every turn has
to pass. It has already cost one turn a re-run.

Fix: replace the spin budget with a wall-clock deadline (e.g. a 5s
`std.time.Timer` loop with a short `std.Thread.sleep` between polls) so the test
fails on "never happened" and not on "the box was busy". Audit the file for the
other `while (spins < …)` waiters and convert them the same way; a shared
`waitUntil(pred, timeout)` helper in the test harness is preferable to N copies
of the loop.

*Validation:* `zig build test-agent` green x3, including one run started while a
full `zig build -Dapp-runtime=win32 -Doptimize=Debug` is in flight (that is the
condition that produced the failure). Confirm the new waiters actually fail —
temporarily break the code path and check the test reports a timeout rather than
hanging.

## Evidence (2026-08-05)

**What landed.** All 11 `while (spins < 10_000) : Thread.yield()` waiters in
`src/remote/agent/server.zig` replaced with `waitUntil(pred, args)` — a shared
wall-clock waiter (10s liveness bound, 1ms poll) in the new
`src/remote/agent/test_util.zig`. Predicates that error (allocating readers)
count as "not yet"; every caller keeps its authoritative assert after the wait.
The loaded validation runs then surfaced two more load-sensitive shapes in the
same lane, fixed the same way:

- `keepalive.zig` "live link keeps getting pinged": the 25ms `stale_after_ms`
  window measured *keepalive-thread scheduling latency* (the refresh only
  happens when that thread runs), and the fixed 120ms sleep undercounted pings
  exactly when the tick thread was the starved one. Now: 60s stale window (the
  stale/fresh arithmetic has its own pure `evaluate` unit test) and a
  `waitUntil` on pings >= 3.
- `proc.zig` ProcSampler busy test: asserted an absolute >= 50% CPU, i.e.
  assumed the test thread would GET a full core. Now burns ~300ms of measured
  CPU time (via `selfCpuNs` — GetProcessTimes on Windows, `clock_gettime
  (PROCESS_CPUTIME_ID)` on macOS/Linux, an API independent of the sampler's
  mach-units reading where the guarded bug lives) and asserts the sampler
  reports at least half of burned/wall — proportional, so decisive at any load
  (the unit bug undercounts ~24x).

**Runs.** Isolated worktree at HEAD + this diff only (a second session was
actively editing win32 chrome in the main tree; its in-flight duplicate `px`
in `caption_layout.zig` broke compilation there — unrelated to this task).
Load generator: 32 hidden powershell busy-loop processes (one per core,
9-minute self-cap), confirmed 100% CPU. Final state: agent lane PASS under
100% load (620s), then PASS x2 clean (154s each); `-Lane none` PASS; `-Lane
win32` PASS.

**Negative proof.** With the server's DATA→child write disabled, the DATA test
reported `slices differ` after the 10s bound — a clean failure, not a hang.
With only the predicate broken (waiting for bytes that never match), the wait
timed out at 10s and the authoritative assert still judged the real bytes.

**P1–P3 disposition.** Not run for this change: the diff is test-only
(`test_util.zig` is imported only from test sections; the one product-file
touch is an extern *declaration* in `proc.zig`'s windows struct), so
`ghoztty.exe` is unaffected — and the main tree could not produce a
representative build while the concurrent chrome work is mid-edit.

**Follow-up filed.** T498: the same yield-spin / fixed-sleep audit for the
non-agent lanes (`connection.zig`, `inbound_ring.zig`, `tcp_dial.zig`,
`client_mux.zig`, `socket_stream.zig`, `wp4_e2e.zig`, `renderer/State.zig`).
