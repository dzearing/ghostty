# T305 - T203b: wire every win32 chrome surface to chrome_theme + repaint on accent/theme change

## Summary

The wiring half of **T203**. T304 lands the module; this task makes every
win32 chrome surface consume it, retires the invented literals, and makes the
chrome repaint when the user changes their accent or flips light/dark —
without a restart.

## Call sites to convert (VERIFIED by reading at HEAD)

- `Window.paintTabBar` — `bar_r/g/b = bg + 20`, `hover = +15`, text
  `RGB(230,230,230)` / `RGB(150,150,150)`, close hover `RGB(232,65,65)`.
- `Window.paintCaption` — `SetTextColor(RGB(230,230,230))`, glyph
  `RGB(230,230,230)` / `RGB(255,255,255)`.
- `chooser_rows.zig:232` — `pub const accent = #3D8EF8`, feeding
  `selectionFill` (accent at 0.25) and `selectionBorder` (0.7).
- `ActivityMonitor.zig:214` — `COLOR_ACCENT = RGB(80,160,235)`, a second
  invented blue, used for the active card fill and its ring.
- `HeroCarousel.zig` — hover/selected accent blue.
- `Window.zig:5029` — `SetTextColor(220,220,220)` / `SetBkColor(45,45,45)` on
  a static control, hardcoded dark.

## Live updates

- `WM_SETTINGCHANGE` already reaches `App.zig:4189` and `Window.zig:4965`
  (which calls `applyChromeTheme`). Extend, do not add a second path.
- Accent changes arrive as `WM_DWMCOLORIZATIONCOLORCHANGED` — add it, and

- Both test lanes, `test-agent`, P1-P3, and the T202 regression set.

## What landed (2026-08-01)

Every call site above converted, plus one this task's own list missed.

- **`Window.chromePalette()`** — the single resolution site: `chrome_theme.
  resolve(chromeBase(window-theme, background, systemUsesLightTheme()),
  system_colors.accentCached())`. `paintTabBar` and `paintCaption` both consume
  it, so the band, its hover, both text ramps and the close red come from one
  `Palette` instead of eight literals across two functions.
- **`paintCaptionRedFill` takes the red as an argument.** The caption's fill
  was `#C42B1C` and the tab strip's close-hover glyph was `RGB(232,65,65)`;
  both are `palette.danger` now, which is what `chrome_theme`'s doc comment
  already promised.
- **`chooser_rows.accent` is deleted.** `selectionFill`/`selectionBorder` take
  the accent as a parameter; `MachineChooser` passes
  `chrome_theme.accentOn(ROW_BG, system_colors.accentCached())`.
- **`ActivityMonitor.COLOR_ACCENT` → `accentColor()`**, a function because the
  value is a registry read and a container-level `const` is comptime.
- **`HeroCarousel`**: `bandBackdrop()` + `bandAccent()`. Selected is the
  accent; hovered is the accent stepped toward the band and re-floored, which
  replaces a second HUE (`RGB(139,92,246)`, ported off Mac as a raw literal and
  reading as an unrelated purple the moment the accent stopped being blue).
- **`WM_CTLCOLORSTATIC`** (not on the list above, found while converting): the
  hovered-URL preview and the resize overlay set `RGB(220,220,220)` on
  `RGB(45,45,45)` while RETURNING the terminal background brush — a background
  that disagreed with the fill actually painted. Both come from
  `chrome_theme.textOn(background)` and the background itself now.
- **Live updates**: `WM_SETTINGCHANGE` (extended, not duplicated) and the new
  `WM_DWMCOLORIZATIONCOLORCHANGED` both drop `system_colors`' accent cache and
  `invalidateChrome()`. DWM's `wparam` is the COMPOSED colorization color, not
  the accent, so the message is used as a signal and the registry stays
  authoritative.
- Two hoists, both because a second caller appeared: **`color_math.mix`** (out
  of `chooser_rows.blend`, which now delegates) and **`chrome_theme.textOn` /
  `accentOn`**, so a surface that is not the bar still gets its floor applied
  in this module rather than by the caller.

### T274 is discharged by this

T274 asks for exactly this — "one resolver, not five edits", a pure module
taking the band color and returning every foreground derived to clear its
floor. `chrome_theme.zig` IS that module, and T274's own named failure case
(`background = ffffff`, where a per-channel add cannot move at all and the
frozen `RGB(230,230,230)` title measured **1.25:1**) is scored in the
acceptance script: the band lands at `#EBEBEB` and the title at **14.89:1**.
Marked done with this commit.

### The validation's premise was wrong, and the correction is the finding

This task asked for the **active-tab indicator** to be sampled and asserted to
track the accent. **There is no such pixel.** The tab strip paints no accent at
all — a tab's fill comes from `tab_shape.fillColor` (strip and content
backgrounds) — and that is deliberate: it matches WinUI's TabView, and adding
an accent element is exactly what T304's "the dark strip must not visibly move"
note forbids. Writing the assertion as specified would have meant inventing the
pixel to satisfy it.

The accent's real surfaces are the chooser row, the Activity Monitor's active
card and the carousel border, so the tracking claim is scored on one of those.
Recorded rather than quietly reinterpreted, because a validation step that
cannot be satisfied by a correct build is a defect in the task.

## Notes / follow-ups

- **T307** — only `Window` handles `WM_DWMCOLORIZATIONCOLORCHANGED`, so a panel
  that is already OPEN when the accent changes keeps painting the old one. The
  acceptance script closes and reopens around the notification, which is the
  workaround standing in for that task.
- **T308** — the panels themselves are still hardcoded dark. This task took the
  invented accents out of them; their thirty-odd remaining `COLOR_*` literals
  are the panel-scale version of the same defect.
- **T309** — `applyChromeTheme` and `chrome_theme.chromeBase` now both answer
  "which side of light/dark is this window on", with different luminance
  weightings. They agree today and nothing asserts that they must.
- The dark look moved by two levels, as T304 predicted (`bg + 20` → `wash` at
  0.08: `#323232` → `#303030`). The one deliberate improvement: the inactive
  tab label went `RGB(150,150,150)` → `#A2A2A2`, because 150 measured 4.4:1
  against the bar and the text floor is 4.5.
