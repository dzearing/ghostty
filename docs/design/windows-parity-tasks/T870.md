# T870 - win32 agent integrations (6/8): first-run still offers the OLD marketplace plugin and nothing migrates plugin users - rewire first-run to the new installer and port ClaudePluginMigration

## In plain terms

This is the slice the user actually feels first. Today the Windows app still
offers the OLD way of wiring up Claude Code (a separately-installed plugin
that has fallen out of date — the "still has the old skill loaded" complaint
that made this a P0). After this task, a first launch offers the NEW built-in
setup for every agent it finds, and anyone still on the old plugin gets a
one-time offer to switch over without losing their banners.

## Goals

- [x] First launch offers the new built-in setup (checkbox per detected
      agent) instead of the old plugin install
- [x] Old-plugin boxes get a one-time switch-over offer that uninstalls via
      Claude's own CLI and keeps banners working
- [x] The old marketplace/plugin-install flow is fully retired
- [x] This box's real 0.8.0 plugin migrated with evidence

## Summary

Sixth slice of the T598 split. Two halves, mirroring `AppDelegate+Setup.swift`
(new-flow first-run) and `ClaudePluginMigration.swift`.

- **Rewire first-run**: `ClaudeIntegration.zig`'s prompt currently runs
  `claude plugin marketplace add` + `claude plugin install` (the T71 flow —
  the thing this replaces). New flow: detect available agents (T869 probe),
  one-time prompt offering integration setup per detected agent (win32
  ConfirmDialog, checkbox-per-agent or the closest native equivalent this
  side already has; the Mac couples it with CLI/PATH setup — Windows' PATH
  story is PathInstaller/T70, keep the analogous coupling), then
  `Service.install` per accepted agent off-thread, outcomes marshalled back
  WM_APP-style. First-launch success stays SILENT (Mac parity); failures
  report once, actionably. Keep the existing gating pattern: only the
  canonical install (`%LOCALAPPDATA%\Programs\Ghoztty`) prompts; debug/dev
  builds never nag (GHOZTTY_CLAUDE_SETUP-style env overrides for tests).
  Preserve the answered-state file semantics (declined is remembered;
  crash mid-dialog never re-nags). Palette entries move to the new flow.
- **ClaudePluginMigration**: for a box where the old plugin IS registered
  (this box: plugin cache 0.8.0 vs main's 0.10.0 skills — the user's
  complaint). One-time prompt ("switch over / keep plugin"), answer recorded
  BEFORE the work. On accept: `claude plugin uninstall <registration>` per
  registration via Claude's OWN CLI (never delete from
  `.claude\plugins\cache` — package-manager state, sentinels, lockfile);
  then copy (never move, never overwrite) per-pane banner state JSONs from
  the plugin's state dir to the app's; then remove the plugin's stale
  banner-script link/copy ONLY if it provably points into the plugin cache
  — on Windows check where the plugin actually put it
  (`%USERPROFILE%\.claude\scripts\ghoztty-banner.sh` exists on this box,
  2026-08-15; it may be a real file rather than a Mac-style symlink — if a
  real file, the marker/content decides ownership); then install the app's
  Claude integration and report only failure. Gated on the first-run prompt
  having been answered so a fresh install never stacks two modals.

## On-box migration evidence (2026-08-15, the real 0.8.0 plugin)

Driver: zig-out debug build + `GHOZTTY_CLAUDE_SETUP=force`, Enter posted to
the dialog (title verified `Ghoztty Now Manages Its Claude Integration`
before any key was sent).

| Check | Before | After |
|---|---|---|
| `installed_plugins.json` has `ghoztty@dzearing-claude-marketplace` | yes (0.8.0) | **no** (removed via `claude plugin uninstall`) |
| `~\.claude\scripts\ghoztty-banner.sh` | real file, byte-identical to plugin cache (hash C51AECFE5907…) | **removed** (ownership proven by byte-compare) |
| `~\.claude\ghoztty-banner\*.json` (plugin originals) | 30 | 30 (untouched) |
| `~\.config\ghoztty\banner-state\*.json` (carried) | 0 | **30** |
| `~\.claude\skills\ghoztty\SKILL.md` + `process-feedback` | absent | **installed** (app copy, current with this build) |
| `~\.config\ghoztty\hooks\ghoztty-banner.sh` + activity-state | absent | **installed** |
| `~\.claude\settings.json` ghoztty hook fragment (`.config/ghoztty/hooks`) | absent | **merged in** |
| `%LOCALAPPDATA%\ghoztty\claude_plugin_migration` | absent | `accepted` |

The user-facing payoff landed immediately: the very next Claude session on
this box listed the app-shipped `ghoztty` / `process-feedback` skills from
`~\.claude\skills` — the "still has the old skill loaded" complaint that
made this a P0 is closed at the root, since the skills now ship with (and
version with) the installed app.
