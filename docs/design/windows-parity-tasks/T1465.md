# T1465 - A pane whose PTY the agent holds is capped at ~8,400 ConPTY reads a second, half the local path's

## Summary

T1464 built the relay's missing instrument and the answer is not where anyone
was looking. Measured on an optimized build with `test\win32\pane-ingest-ab.ps1`
(the median busy second of a 7.7 MB burst):

```
perf holder_read  frames_per_s=8408  kb_per_s=600  bytes_per_frame=73  io_ms_per_s=0
perf holder_out   frames_per_s=8399  kb_per_s=600  bytes_per_frame=73  io_ms_per_s=55
perf holder_in    frames_per_s=8399  kb_per_s=600  bytes_per_frame=73  io_ms_per_s=890
perf relay_out    frames_per_s=8306  kb_per_s=664  bytes_per_frame=81  io_ms_per_s=54
```

Every leg carries the **same** ~8,400 messages a second, and every leg's own
pipe syscalls cost **under 7 us** (55 ms of a second over 8,400 writes). The one
leg with a large number is `holder_in`, the agent's reader, and its 890 ms is
time spent *waiting for bytes that have not arrived* — the signature of a
consumer that is faster than its producer, not of an expensive read.

So the ceiling is the SOURCE. `perf holder_read` is the holder's own ConPTY
read loop, and it delivers **~8,400 reads a second of 73 bytes** — where the
app's local ConPTY, on the identical workload with the identical read size,
does **~19,000** (`perf pty reads_per_s=19,079 kb_per_s=1,369`). Same code
(`pty_child.zig`), same ConPTY API, half the rate. Everything downstream simply
follows it, which is why the agent-held pane finishes in 11,760 ms against the
local pane's 5,542 ms and conhost's 5,915 ms.

## In plain terms

When a program prints a lot of text fast, a Ghoztty pane takes about twice as
long to catch up as the terminal Windows ships with — but only when the piece
that keeps sessions alive across restarts is the one running the program. We now
know exactly where the time goes, and it is not the hand-off we suspected: the
text comes out of the operating system half as fast in that process as it does
in the app itself. When this lands, a pane keeps up whether or not its session
is being kept alive.

## What is already ruled out — do not re-investigate

Each of these was MEASURED under T1464, not reasoned about:

- **The relay's framing.** Every leg's pipe syscalls are under 7 us, and the
  legs already carry the same rate as the source, so no wire cost is being paid
  on top of it.
- **Message COUNT.** A 1 ms coalescing wait in the holder's writer halved the
  frame count (8,294 -> 4,378 frames/s at 146 bytes) and moved throughput not at
  all (626 KB/s against 594). It was reverted rather than shipping echo latency
  for nothing; `pty_host.zig` carries the finding as a comment so it is not
  re-tried.
- **The ACK storm.** One ACK per read batch was 16,000 pipe writes a second from
  the agent's reader thread; batching them to 64 KiB / 200 ms (T1464, kept —
  it is strictly less work) changed the throughput by nothing.
- **The parser, the renderer mutex, the present, the priority handoff, software
  OpenGL.** T1458, T1460 and T1463 between them.

## Details

The question this task has to answer first: **why does the same `pty_child.zig`
read loop run at half the rate inside a holder process?** Candidates, cheapest
first — and each one is a measurement, not a change:

1. **Time the ConPTY read itself.** `perf holder_read`'s `io_ms_per_s` is 0
   today because `sinkFn` cannot see the read — the meter counts chunks after
   the fact. Bracket the `ReadFile` inside `pty_child.zig`'s reader thread (the
   same `relay_perf.Meter` shape) and the answer is immediate: a read that is
   WAITING says the shell is being paced by something else, a read that is SLOW
   says the cost is in the holder's own ConPTY.
2. **What the holder's process does per chunk that the app's does not.**
   `sinkFn` takes `state.mutex` and calls `cond.broadcast()` on every 73-byte
   chunk — 8,400 kernel wakes a second, contending with the writer thread and
   (before the ACK batching) the frame reader. The app's reader hands off
   without a broadcast. Measure the mutex, then try a wake only when the writer
   is actually parked.
3. **The holder's job object.** The measured runs logged `job escape=IN-JOB
   (degraded)` — the holder is inside the APP's job object rather than its own.
   A job can carry CPU rate control and scheduling-class limits; check what this
   one carries before assuming it carries none. (This is also a correctness
   smell in its own right — `docs/claude/build.md` and T1464's runs both hit
   `breakaway spawn refused err=.ACCESS_DENIED`.)
4. **ConPTY buffer geometry.** Whether the holder's ConPTY is created with the
   same size and mode as the app's, and whether the 73-byte read size is the
   pty's choice or ours.

## Parity note

Standing symmetry rule. `pty_child.zig`, `pty_host.zig` and `relay_perf.zig` are
shared with the Mac seat, which has the same agent-held session design. The
ConPTY specifics are Windows', so the *cause* may not be, but the harness
question is: file the Mac half if the same deficit shows up on a POSIX pty.

## Goals

- [x] Why the holder's ConPTY read rate is half the app's is a MEASURED cause,
      not a hypothesis. **It is core placement**: the holder's process tree runs
      on the CPU's efficiency cores, where the shell->conhost round trip behind
      every ~73-byte chunk costs ~122 us against ~55 us on a performance core.
      Established by elimination and then by construction - see the log below.
- [ ] The agent-held pane's sustained ingest is at least conhost's on the same
      workload, and its writer-clock elapsed is no worse than conhost's.
      **PART WAY**: 1.94x -> 1.55x of the local pane. The rest needs the USER's
      shell subtree on the performance cores too, which costs a build in a
      persisted pane half the machine - filed as **D94** rather than taken
      quietly.
- [x] Interactive latency does not regress in exchange: a single keystroke's
      echo is not delayed by whatever lands. Nothing added to the per-chunk
      path; the two calls are at holder startup, before the shell exists.

## Result

Same box, same 7.7 MB burst, optimized build, release sandbox. `A` is a
local-ConPTY pane, `B` the shipped agent-held one, `D` conhost.

```
BEFORE (5 runs)   B = 11588 / 11639 / 11688 / 11742 / 11964 ms   B/A = 1.84 - 2.02
AFTER  (3 runs)   B =  8990 /  9032 /  9909 ms                   B/A = 1.51 - 1.58
                  A = 5800 - 6269 ms      D (conhost) = 6318 - 6372 ms
```

The ceiling the task title names was never a cap on the source: pinning the
whole holder tree (holder + conhost + the shell) to the performance cores as a
one-off experiment measured **1.05x and 1.14x** - level with conhost. That is
the number D94 is about; what shipped is the part of it that costs nothing.
