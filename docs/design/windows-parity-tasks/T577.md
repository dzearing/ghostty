# T577 - release-windows.yml is not on main, so no Windows release has ever been published automatically

## In plain terms

Windows users who click Download on the website get a build from July 19th.
Mac users get today's. Every piece of machinery that was supposed to fix
that got built and tested — it just lives on a branch that releases are not
cut from, so it has never actually run. Nothing is broken; nothing is
plugged in.

## Summary

T38 built the automated Windows release: `.github/workflows/release-windows.yml`
fires on the same `vX.Y.Z` tag push as the macOS release, cross-compiles on
`ubuntu-latest`, publishes `Ghoztty-<version>-x64.msi` +
`Ghoztty-portable-<version>-x64.zip` to a `win-v<version>` release, and then
runs `dist/website/update-windows-links.py` to retarget the landing page at
what it just published (T39).

**None of it has ever executed.** The workflow file exists only on
`users/dzearing/windows-amd64`; `origin/main` does not have it, and release
tags are cut from `main`. Evidence gathered 2026-08-07 while working T349:

```
$ git ls-tree --name-only origin/main .github/workflows/ | grep windows
(nothing)

$ gh run list --repo dzearing/ghoztty --workflow release-windows.yml
HTTP 404: workflow release-windows.yml not found on the default branch

$ gh release list --repo dzearing/ghoztty --limit 200 | grep win-v
Ghoztty for Windows v1.4.1    win-v1.4.1    2026-07-19T22:30:23Z
```

So the newest Windows release is still the hand-published `win-v1.4.1` from
before T38 landed, while macOS is at `v1.31.0` (2026-08-07) — the exact
27-releases-behind gap T38 was written to close, still open, for a different
reason than the one T38 fixed. The website is honest about what exists
(T39's rewrite only runs when a release is published, and T349 added the
unsigned/SmartScreen caveat), which is why this has stayed invisible: every
link answers 200, it just answers with a three-week-old build.

## Details

The fix is not code — the workflow is written and its wiring is asserted by
`test/win32/website-windows-download.ps1` section D. It is a delivery
question, and the honest options differ in how much they front-run the
merge-back:

- **Cherry-pick the release path onto `main`** — the workflow plus the
  scripts it calls (`dist/windows-installer/build-release-artifacts.sh`,
  `build-portable-zip.sh`, `dist/website/update-windows-links.py`). Smallest
  surface that makes the next tag publish Windows artifacts, and it does not
  wait on the whole branch being merge-ready. The artifacts it would build
  come from `main`'s source, which is the honest thing to ship anyway.
- **Wait for the branch merge-back**, and accept that Windows publishes
  nothing until then. Fewest moving parts, but the lag is unbounded and the
  download page keeps offering July's build.
- **Run `scripts/publish-windows-release.ps1` on this box per release** as a
  stopgap. It is the on-box path T38 kept working and it defaults `-Version`
  to the newest `vX.Y.Z` tag. This is precisely the "needs a human to
  remember" process T38 replaced, so it is a bridge, not an answer.

Whichever is chosen, verify it by *observation* rather than by the workflow
file existing: a `win-v<version>` release with both assets, and a gh-pages
commit from the workflow moving `win-msi-link` / `win-zip-link` /
`win-version`.

Note that a Windows build published off `main` today would be missing every
parity feature on this branch. That is a reason to hurry the merge-back, not
a reason to keep shipping a build from July — but it should be a conscious
call, so file it as a decision if the answer is not obvious when this is
picked up.
