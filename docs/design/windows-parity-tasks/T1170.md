# T1170 - The git-diff viewer test times out in the full agent lane and passes on its own

## In plain terms

One of the automated checks fails whenever it is run alongside all the others,
and passes every time it is run by itself. Nothing is actually broken — the
check simply gives itself thirty seconds to see a result, and thirty seconds is
not enough when a few thousand other checks are competing for the same machine.
Until it is fixed, every piece of work has to stop and prove that this
particular red light is not its fault.

## Summary

Found by T1142's floor run on 2026-08-23, at HEAD `1cf251aa4` with a working
tree carrying only `.ps1` and `.md` edits — so nothing in the change could
touch it.

```
error: 'apprt.win32.ViewerPane.test.host floor: a real controller on a real
        window, on this box' failed: ...
[viewer_pane] (err): waitFor: nothing satisfied the wait within 30s (pane state ready)
D:\git\ghoztty\src\apprt\win32\ViewerPane.zig:8018:5  in waitFor
D:\git\ghoztty\src\apprt\win32\ViewerPane.zig:7625:13 in test.host floor: ...
```

Three runs, and the discriminator is clean:

| run | command | result |
|---|---|---|
| 1 | `floor-lane.ps1 -Lane all` | agent **FAIL**, 246 s |
| 2 | `floor-lane.ps1 -Lane agent` (alone, T1137 rule) | **FAIL**, 246 s |
| 3 | `floor-lane.ps1 -Lane agent -Filter "host floor"` | **PASS**, 130 s |
| 4 | `floor-lane.ps1 -Lane agent` again | **FAIL** |

Three full-lane runs, three reds, on the same arm; the only green is the
filtered one. So this is not an intermittent flake to re-roll - the full lane is
reliably over the bound on this box today.

The waiting arm is the `git-status:` leg at `ViewerPane.zig:7625`: two worker
round trips (a `git status` listing, then a patch) each landing as a posted
message, behind `try waitFor(&msg, 30, …)`. In a binary that runs 5314 tests
and drives a live WebView2, 30 s of wall clock is not 30 s of progress for this
pane. Ruled out as causes: leaked WebView2 hosts (the lane sweeps and reported
0; the 14 `msedgewebview2.exe` on the box at the time all parent to the user's
own Ghoztty and to SearchHost) and leaked repo agents (none running).

The confusing top line — `error: while executing test
'benchmark.OscParser.decltest.OscParser', the following test command failed` —
is the build runner naming the test command, not a second failure. Anyone
reading the tail of a lane log will chase that name first; worth a line in the
fix.

## Where

- `src/apprt/win32/ViewerPane.zig:7625` — the `waitFor(&msg, 30, …)` under test
- `src/apprt/win32/ViewerPane.zig:8018` — `waitFor` itself, which returns
  `error.WaitForTimeout` with no note of how far the predicate had got
- `scripts/floor-lane.ps1` — where a "this failed under load, passes alone"
  re-run would belong, the same shape `suite-run.ps1` grew in T1137

## Validation criteria

- [ ] the full agent lane is green in three consecutive runs on a loaded box
- [ ] the fix is not just a bigger number: a wait that gives up says WHICH part
      of its predicate was unsatisfied, so the next timeout is diagnosable
- [ ] `floor-lane.ps1 -Lane agent -Filter "host floor"` still passes
- [ ] a lane failure that a solo re-run does not reproduce is REPORTED as such
      rather than left for each turn to discover (the T1137 rule, applied to
      lanes as well as to the suite)
