# T1170 - The git-diff viewer test times out in the full agent lane and passes on its own

## In plain terms

One of the automated checks fails whenever it is run alongside all the others,
and passes every time it is run by itself. Nothing is actually broken — the
check simply gives itself thirty seconds to see a result, and thirty seconds is
not enough when a few thousand other checks are competing for the same machine.
Until it is fixed, every piece of work has to stop and prove that this
particular red light is not its fault.

## Goals

- [x] a wait that runs out of time under load is no longer scored the same as a
      wait that is genuinely stuck
- [x] a timeout says enough for the next reader to diagnose it without a re-run
- [x] a red lane answers "is this the code or the box?" in the run itself
- [x] and the answer never turns a red lane green

## Summary

Found by T1142's floor run on 2026-08-23, at HEAD `1cf251aa4` with a working
tree carrying only `.ps1` and `.md` edits — so nothing in the change could
touch it.

```
error: 'apprt.win32.ViewerPane.test.host floor: a real controller on a real
        window, on this box' failed: ...
[viewer_pane] (err): waitFor: nothing satisfied the wait within 30s (pane state ready)
D:\git\ghoztty\src\apprt\win32\ViewerPane.zig:8018:5  in waitFor
D:\git\ghoztty\src\apprt\win32\ViewerPane.zig:7625:13 in test.host floor: ...
```

Three runs, and the discriminator is clean:

| run | command | result |
|---|---|---|
| 1 | `floor-lane.ps1 -Lane all` | agent **FAIL**, 246 s |
| 2 | `floor-lane.ps1 -Lane agent` (alone, T1137 rule) | **FAIL**, 246 s |
| 3 | `floor-lane.ps1 -Lane agent -Filter "host floor"` | **PASS**, 130 s |
| 4 | `floor-lane.ps1 -Lane agent` again | **FAIL** |

Three full-lane runs, three reds, on the same arm; the only green is the
filtered one. So this is not an intermittent flake to re-roll - the full lane is
reliably over the bound on this box today.

The waiting arm is the `git-status:` leg at `ViewerPane.zig:7625`: two worker
round trips (a `git status` listing, then a patch) each landing as a posted
message, behind `try waitFor(&msg, 30, …)`. In a binary that runs 5314 tests
and drives a live WebView2, 30 s of wall clock is not 30 s of progress for this
pane. Ruled out as causes: leaked WebView2 hosts (the lane sweeps and reported
0; the 14 `msedgewebview2.exe` on the box at the time all parent to the user's
own Ghoztty and to SearchHost) and leaked repo agents (none running).

The confusing top line — `error: while executing test
'benchmark.OscParser.decltest.OscParser', the following test command failed` —
is the build runner naming the test command, not a second failure. Anyone
reading the tail of a lane log will chase that name first; worth a line in the
fix.

## Where

## Progress log

- 2026-08-31 20:21: claimed; work starting.
- 2026-08-31 20:28: baseline: agent lane PASSES today (floor-lane.ps1 -Lane agent = PASS in 363s). So this is not a hard red now, but the bound is still fragile - a 363s lane against a 30s per-wait bound is the shape that went red three times on 2026-08-23. Fix stands: make waitFor deadline progress-based rather than wall-clock, dump the pane state on timeout, and teach floor-lane to re-run a red lane solo and report load-only failures.
- 2026-08-31 20:58: fix landed in three parts. (1) waitFor's deadline is now STILLNESS, not wall clock: every observable change to the pane resets the count, with a hard ceiling of 8x the bound so a livelock still fails - that is why it is not just a bigger number. (2) A timeout now prints the whole observable pane state (state/mode/page_loaded/diff_pushed/controller/failure/title/location/diff{repo,files,patch,busy}) plus how long the pane had been still, so the next one is diagnosable from the log; it logs at warn rather than err because an err from the same event makes the runner report a second differently-worded failure - the extra top line the report says everyone chases. (3) floor-lane.ps1 grew a solo confirm pass (the T1137 rule applied to lanes): a red lane is re-run narrowed to the tests it blamed and the summary carries [alone: ...]. A green solo run does NOT change the verdict - red stays red and the exit stays non-zero. New lib scripts/lib/LaneSolo.ps1 + harness test/win32/floor-lane-solo-confirm.ps1 (14 assertions, ALL PASS) + guard row lane-solo-confirm. Demonstrated end to end on a real red win32 lane: 414s loaded run, 36s narrowed re-run, 'FAIL alone - reproduced', exit 1.
- 2026-08-31 21:02: side finding, filed as T1231: repairing scripts/guard-due.ps1 exposed that TWO guard rows (install-prepare, release-artifacts-packaging) carried control characters inside their Covers paths, so those files could never resolve and neither guard has ever been able to report itself due. Both went DUE the moment the paths were repaired. Thirteen more repo files carry the same damage, two of them live .ps1 scripts.
- 2026-08-31 21:15: the loaded agent lane went red again mid-validation (self-inflicted: seven corpus audits running beside it), and the new diagnostic paid for itself immediately - it named a DIFFERENT wait than the report did (ViewerPane.zig:7066, the quote.md navigation, not the git-status leg at 7625) and printed 'state=ready mode=markdown page_loaded=false ... still for 30013ms'. That exposed a real hole in the first fix: a single-step wait on page_loaded moves NO other observable field while it waits, so the stillness bound collapsed back to a wall-clock bound for exactly the hardest wait to bound. Added pane.wait_progress, a monotonic counter bumped by every WebView2 callback into the pane (navigation completed, resource requested, page message), folded into the signature and printed as callbacks=N. The solo confirm pass meanwhile scored the run correctly with no human involved: 'LANE agent FAILED UNDER LOAD, PASSES ALONE - not reproduced on its own', 237s loaded vs 101s alone, exit still 1.
