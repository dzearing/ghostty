# T259 - tab-color.ps1 re-derives BOTH the strip origin and the tab width, and has been red since T254/T235

## Summary

`test/win32/tab-color.ps1` fails at its first right-click:

```
PASS  positive control: the tab bar is visible with a single tab (barH=45)
PASS  positive control: ctrl+t made a 2nd tab
INFO  scale=1.125 tabW=225 stripeH=3 stripeTop=68 tab0x=189 tab1x=414
PASS  baseline: tab 0 has no red stripe
FAIL  context menu: menu window (#32768) opened on tab right-click
```

It is the SAME defect T256 fixed in `tab-strip.ps1` and `menu-bar.ps1`, in the
one script T256 did not cover, and it has both halves of it at once.

**Half 1 - the origin moved (T254).** Line ~170 measures the strip as
`panes[0].Top - clientRect.Top`. Since T254 the caption band is CLIENT area, so
that expression is `caption_h + bar_h`, not `bar_h`. The run above reports
`barH=45`, which at this box's 1.25 scale is exactly `caption_h`
(5 + 35 + 5) - the strip is 50 px and was not measured at all. (Before T234 the
same expression returned 95 = 45 + 50; both are wrong, which is why this is
**pre-existing and not T234's doing** - T234 only changed which wrong number
comes out.)

**Half 2 - the width is not derivable (T235).** Lines ~197-209 then compute
`$scale = $barH / 40.0` (1.125 instead of 1.25) and rebuild the tab width from
T202's retired rule: equal share of the run, clamped to [60, 200] DIP. T235
retired that - a tab is now its measured title plus padding, floored at 60 DIP
and capped at 50% of the run, and a script cannot re-derive a width that comes
from text metrics. So `tab0x`/`tab1x` point at the wrong columns and the
right-click lands on empty strip.

## The fix

Both halves already have a written answer; this is applying it, not inventing
it:

- Take the scale from `Get-TestWindowDpi`, never from a chrome height.
- Take the strip's origin from the caption height (`4 + 28 + 4` DIP), the same
  datum `caption-bar.ps1` and `tab-strip-autohide.ps1` restate - **or better,
  from the hoisted helper T257 exists to create**, since this is now the third
  script keeping a private copy.
- Measure the tab RUN off a capture, the way T256 taught `Strip-Geometry` to,
  instead of recomputing a width from a rule.

`--window-show-tab-bar=always` is also now required for its single-tab positive
control ("the tab bar is visible with a single tab"): T234 made `auto` hide the
strip at one tab, so that control currently passes by measuring the caption.

Strongly prefer doing this **with T257** (hoist the shared chrome geometry into
`test/win32/lib/`), so the count of private copies goes to zero rather than
from three to two.

## Validation

- `powershell -NoProfile -File test\win32\tab-color.ps1` ALL PASS x3.
- Its `-NegativeControl` run still fails.
- The INFO line's `scale` equals `Get-TestWindowDpi / 96`.

## Outcome (2026-07-31)

Done with **T257**, as this task asked, so the count of private copies went to
zero rather than three to two.

**Half 1 (origin).** `$barH = $panes1[0].Top - $clientTop` now subtracts the
caption band, and the loose `20..80` plausibility band became an exact check
against the derived `bar_h`:

```
before:  INFO  scale=1.125 tabW=225 stripeH=3 stripeTop=68 tab0x=189 tab1x=414
after:   PASS  positive control: the tab bar is visible with a single tab (capH=45 barH=50, expected 50)
```

`barH=45` was `caption_h` at this box's 1.25 scale — the strip (50) was never
measured at all.

**Half 2 (width).** Deleted, not repaired. The equal-share-clamped-to-[60,200]
model, the `$scale = $barH / 40.0` derivation and every DIP constant behind
them are gone; the two chiclets are MEASURED with T257's new
`Get-TestTabExtents`, which returns each painted chiclet's `{Left, Right,
Center}` off a capture. The measurement is its own positive control ("both tab
chiclets are measurable off the strip"), so a strip that stops painting fails
loudly instead of silently clicking empty space.

The measured widths are what settle that the old model was wrong rather than
merely differently rounded:

```
INFO  scale=1.25 stripeH=4 stripeTop=114 tab0=[5,351) tab1=[357,701) tab0x=251 tab1x=602
```

346 and 344 px wide — matching the "~344px real tab" T256 recorded — against
the retired model's 225. That ~120px error is exactly why the right-click
landed on empty strip and the first context-menu assertion failed.

Also added `--window-show-tab-bar=always` to the launch, required since T234
made `auto` hide the strip at one tab; without it the single-tab positive
control passes by measuring the caption band. Autohide behavior stays
`tab-strip-autohide.ps1`'s to assert.

`$scale` now comes from `Get-TestWindowDpi` via the shared helper and reads
**1.25**, matching the box's 120 DPI (it reported 1.125 before, the tell that
it was derived from a chrome height).

### Evidence

Three consecutive clean runs, ALL PASS (16 assertions) each:

```
run 1: ALL PASS (16 assertions)  | INFO scale=1.25 ... tab0=[5,351) tab1=[357,701)

```

Client-relative extents are identical across runs while the screen-relative

accidentally passing. `-NegativeControl` still fails (1 FAILED / 15 passed).
