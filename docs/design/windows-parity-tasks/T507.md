# T507 - Validate the T166 attach-cwd reporting on macOS (shared-core change in termio.Remote.threadEnter)

## Summary

T166 (fixed on the Windows seat, 2026-08-05) changed SHARED core:
`src/termio/Remote.zig` `threadEnter` now captures the agent-reported `cwd`
from the attach-family replies (ATTACHED alive + the dead-tombstone
notify/auto/prompt branches), sets the terminal pwd, and pushes a `pwd_change`
surface message with timed retries so the apprt's cached pwd — what `+list`
reports — follows. macOS runs this exact code on every session-persistence
re-attach, so the Mac seat should confirm the fix behaves there and nothing
regressed.

## In plain terms

After restarting the app, each restored terminal used to report the wrong
folder (the default one) when scripts asked where it was. The fix lives in
code both platforms share; Windows verified its half on-box, and this task is
the Mac half of that verification.

## What to check

- `ghoztty +list --json` after an app quit + relaunch (sessions re-attached):
  each restored pane's `working_directory` is the session's real cwd, not the
  config default. Before the fix the Mac symptom may have been masked by OSC 7
  (shell integration re-reports pwd on the next prompt), so check a pane whose
  shell has NOT emitted a fresh prompt since re-attach, e.g. one running a
  long-lived TUI.
- The relaunch-notice path (agent restarted): the fresh shell's pane reports
  the recorded cwd immediately.
- No regression in the Mac `+list` path or restore bring-up (the pwd_change
  retry loop must never stall an attach; it aborts on the RPC canceller).

## Validation criteria

- [ ] Re-attach on macOS: restored panes report their real cwd in
      `+list --json` (name the manual or scripted check used)
- [ ] Relaunch-notice path reports the recorded cwd
- [ ] macOS test suite / smoke unaffected
