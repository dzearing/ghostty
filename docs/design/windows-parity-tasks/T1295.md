# T1295 - A viewer pane keeps darkening over Remote Desktop

## In plain terms

You open an HTML pane over a remote desktop connection and the white gets
dimmer and dimmer the longer it sits there. Closing the pane and opening it
again makes it look right, and then it starts fading again.

## What the user reported (2026-09-03)

> "i made an html pane, and it kept dimming ... the white became dim. if i
> closed and reopened it was better. i don't know whose fault that is, but it
> was over a remote desktop connection."

Two parts to separate:

- **Some dimming is by design.** `DimOverlay.zig` (T74) implements the Mac/GTK
  `unfocused-split-opacity` behaviour: an unfocused pane of a split gets a
  uniform semi-transparent rectangle. An HTML viewer sitting unfocused beside
  the terminal is *supposed* to look dimmer.
- **Progressive darkening is not.** "Kept dimming" and "closing and reopening
  was better" describe an effect that compounds, which no fixed alpha does.

## What was checked, and what it rules out (2026-09-03)

Every layered-alpha site in `src/apprt/win32` was read, not grepped:
`App.zig` (`toggle_background_opacity`), `Window.zig` (`background-opacity`
at creation), `BannerOverlay`, `Scrollbar`, `ReadonlyBadge`,
`KeyStateIndicator` and `DimOverlay`. None of them accumulates:

- **One overlay per pane, for the life of the pane.** `showDimOverlay`
  creates at most one and `hide()` never destroys it, so overlays cannot
  stack.
- **Alpha is applied only when it changes.** `SetLayeredWindowAttributes` is
  guarded on `alpha != self.alpha`, and the brush is recreated only on a
  colour change.
- **Nothing re-blends on a timer.** `updateDimOverlays` is reached from focus
  changes, `layoutSplits`, `WM_MOVE`, a tab switch and a config reload;
  `healOverlayZOrders` from `WM_ACTIVATE` and the topmost action. There is no
  paint-rate or interval caller.

So **app-side alpha accumulation is ruled out by construction**, and the
compounding lives in composition — which is why it shows up over Remote
Desktop and not locally.

## What was changed

The app's one lever over a blend it does not control is *how often it asks
for one*. `DimOverlay.show()` used to issue `SetWindowPos(...
SWP_SHOWWINDOW)` plus a z-order heal on **every** one of the events above,
even when the pane had not moved and neither the alpha nor the fill had
changed. On a composited desktop that is free and invisible. In an RDP
session, where the layered blend is not reliably idempotent, each redundant
re-blend is another wash of `unfocused-split-fill` over pixels that already
carry one — which is exactly "it kept dimming, and closing the pane fixed
it".

- `show()` is now genuinely idempotent: it tracks the placement it last
  applied and returns early, having touched nothing, when placement, alpha,
  colour and visibility are all unchanged. It returns `bool` so a unit test
  can ask "did this re-blend?" without a composited screen.
- When a re-blend IS unavoidable **and the process is in a remote session**
  (`GetSystemMetrics(SM_REMOTESESSION)`), the overlay drops itself and forces
  the owner — including WebView2's own child windows, via `RDW_ALLCHILDREN`
  — to repaint underneath first, so the blend starts from clean pixels
  instead of from the previous blend's output. Local sessions are untouched.

Pure logic (`dim_math.needsReposition`, `dim_math.Placement`) is unit tested
in every lane; the windowing behaviour is covered by
`T1295: a redundant dim-overlay show does not re-blend` in `ViewerPane.zig`
(win32 lane), which drives a real overlay over a real host window and asserts
that three identical `show()` calls in a row touch nothing while a move, an
opacity change, a fill change and a hide/show flip each get through.

## What is still open

Confirmation over RDP. The remedy above is the app's whole contribution to a
compounding blend, but it cannot be *proved* to be the cause from this seat:
there is no Remote Desktop session here, and off the input desktop there is no
composited screen to photograph (the reason `split-dim-viewer.ps1` asserts on
the overlay's own `PrintWindow` fill rather than on composited pixels). If the
fade survives this change, the remaining suspect is the composition path
itself — the Mesa d3d12 fallback renderer (T1251/T1252) under RDP's
redirection — and the next step is item 4 of the investigation list below.

## What to investigate (if it survives the fix)

1. Reproduce over RDP and sample the pane's actual pixels over time - is the
   overlay's alpha compounding, or is the *surface underneath* getting darker?
   Those are different bugs and the fix differs.
2. Test with the dim overlay disabled (`unfocused-split-opacity = 1`) over RDP.
   If the darkening stops, it is the overlay; if it continues, it is the
   renderer or RDP redirection.
3. Test the same viewer pane **focused**, where no overlay is shown at all.
4. Check whether a local session with the fallback renderer forced
   (`GHOSTTY_*` override) reproduces it without RDP, which would separate the
   renderer from the remote-desktop path.

## Validation criteria

- [x] Overlay alpha compounding **inside the app** is ruled out by
      construction - every layered-alpha site read, one overlay per pane,
      alpha applied only on change, no periodic re-blend caller. (Reading, not
      pixels: pixels of a composited screen are not obtainable from this seat.)
- [ ] The surviving cause is named with pixel evidence - needs an RDP session.
- [ ] A viewer pane over RDP holds a steady brightness over several minutes.
- [ ] Closing and reopening the pane is no longer a workaround anybody needs.
- [x] A test covers the layer the fix landed in: `dim_math` reposition logic
      (every lane) plus `T1295: a redundant dim-overlay show does not re-blend`
      in `ViewerPane.zig` (win32 lane).
