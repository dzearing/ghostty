# T1295 - A viewer pane keeps darkening over Remote Desktop

## In plain terms

You open an HTML pane over a remote desktop connection and the white gets
dimmer and dimmer the longer it sits there. Closing the pane and opening it
again makes it look right, and then it starts fading again.

## What the user reported (2026-09-03)

> "i made an html pane, and it kept dimming ... the white became dim. if i
> closed and reopened it was better. i don't know whose fault that is, but it
> was over a remote desktop connection."

Two parts to separate:

- **Some dimming is by design.** `DimOverlay.zig` (T74) implements the Mac/GTK
  `unfocused-split-opacity` behaviour: an unfocused pane of a split gets a
  uniform semi-transparent rectangle. An HTML viewer sitting unfocused beside
  the terminal is *supposed* to look dimmer.
- **Progressive darkening is not.** "Kept dimming" and "closing and reopening
  was better" describe an effect that compounds, which no fixed alpha does.

## What was checked, and what it rules out

`DimOverlay.show()` is idempotent by construction: the brush is recreated only
when the colour changes, and `SetLayeredWindowAttributes` is called **only when
`alpha != self.alpha`**, with the last value cached on the struct. One overlay
exists per surface and it is repositioned rather than re-created. So the app's
own alpha bookkeeping does not accumulate, and stacked overlays are unlikely.

That moves suspicion to composition rather than logic. The overlay is a
`WS_EX_LAYERED` popup composited by DWM **above the surface's OpenGL content**
(the header says a plain child window cannot reliably do this). Layered windows
over a GL surface are already known-fragile on this box - a prior finding
records that `GetDC` on a `SetLayeredWindowAttributes` window kills the
composite until a repaint.

**Prime suspect, untested:** this is an RDP session, which means the pane is
being drawn by the **Mesa d3d12 fallback renderer shipped days ago** in
T1251/T1252 - brand new, and never exercised together with the dim overlay.
The combination of a layered popup over a fallback-rendered GL surface under
RDP's redirection is the interaction to test first.

## What to investigate

1. Reproduce over RDP and sample the pane's actual pixels over time - is the
   overlay's alpha compounding, or is the *surface underneath* getting darker?
   Those are different bugs and the fix differs.
2. Test with the dim overlay disabled (`unfocused-split-opacity = 1`) over RDP.
   If the darkening stops, it is the overlay; if it continues, it is the
   renderer or RDP redirection.
3. Test the same viewer pane **focused**, where no overlay is shown at all.
4. Check whether a local session with the fallback renderer forced
   (`GHOSTTY_*` override) reproduces it without RDP, which would separate the
   renderer from the remote-desktop path.

## Validation criteria

- [ ] The cause is named as one of: overlay alpha compounding, surface content
      darkening, or RDP/DWM redirection - with pixel evidence, not inference.
- [ ] A viewer pane over RDP holds a steady brightness over several minutes.
- [ ] Closing and reopening the pane is no longer a workaround anybody needs.
- [ ] A test covers the regression in whatever layer the cause turns out to be.
