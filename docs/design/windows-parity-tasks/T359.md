# T359 - remote-test-client is an on-demand build target, but two acceptance scripts require it - a clean tree fails them for a reason that reads like a product bug

## Summary

`remote-test-client.exe` is built **on demand only** (`build.zig:171-175`, its
own `zig build remote-test-client` step), but two acceptance scripts require it
as a prerequisite: `test/win32/agent-pipe.ps1` (T89c) and
`test/win32/agent-user-env.ps1` (T42). A tree that has only ever run
`zig build -Dapp-runtime=win32` does not have the binary, so both scripts fail
at their first assertion — and the failure names a missing exe, which reads
like the agent failed to build rather than "this lane was never asked for".

## Evidence

- `build.zig:168-175`: `remote_test_client_step.dependOn(...)` only — nothing in
  the default install step reaches it. Same shape for `wp4-e2e`.
- `test/win32/agent-pipe.ps1:18` and `test/win32/agent-user-env.ps1` default
  `-ClientExe` to `zig-out\bin\remote-test-client.exe` and assert existence.
- Observed 2026-08-02 doing T42: the client had to be built with an explicit
  extra `zig build remote-test-client` before the new script could run.

## The fix (pick one, then write it down)

Either make the scripts self-sufficient — build the client themselves when it
is missing (a `zig build remote-test-client` shell-out, the way the delivery
launcher builds the staging release rather than assuming it) — or add it to
whatever the standing "test binaries" target is so the floor produces it.
Prefer the former: it keeps the default build lean and makes the script's
prerequisite explicit at the point of use.

Whichever way it goes, the `-ClientExe` assertion message should say **how** to
produce the binary; a precondition that cannot be acted on is half a failure
message. Check `wp4-e2e` for the same trap while here.

## Validation

Delete `zig-out\bin\remote-test-client.exe`, run both scripts, and get ALL PASS
without a manual build step (or a failure line that states the exact command).
