# T1323 - The exit-code audit's spot-check names a line T1285 legitimately deleted

## In plain terms

One of the self-checks that guards the test suite is failing, and nothing is
actually broken - it is looking for a line of code that was correctly removed
weeks ago. A check that is red for no reason teaches everyone to ignore it,
which is the whole reason it stops working.

## Summary

`test\win32\harness-exitcode-audit.ps1` fails B3:

```
FAIL B3 P1's second-instance probe caches the handle
```

The audit's subject is the PS 5.1 trap where `$p.ExitCode` reads empty unless
`$p.Handle` was touched before the child exited. Section B has two halves:

- **B1, the analyzer sweep** over `test\win32` and `scripts` - it PASSES, so
  there is no unguarded `ExitCode` read anywhere in the suite.
- **B3, a spot-check by name**, asserting the literal text
  `$null = $second.Handle` still appears in `test\win32\ipc-p1.ps1`. Its stated
  purpose is that "a later edit that drops the line is caught by name, not only
  by the analyzer".

T1285 (`6d4587f1f`) rewrote P1's step 9 to run the second GUI launch through
`Invoke-OnTestDesktop`, which returns an `ExitCode` parsed out of the native
`RunProcess` helper's own result string - there is no PowerShell `Process`
object in that path, so there is no handle to cache and the trap cannot arise.
`ipc-p1.ps1:177-179` is correct as it stands; the assertion looking for the old
spelling is what is stale.

The fix is not to re-add the line. Either the spot-check moves to the shape the
code now takes, or it is retired in favour of the analyzer sweep that already
covers it - and whichever way, the reason the by-name check existed (an edit
silently dropping the guard) has to still be covered, since B1 alone would pass
a file that had never had the guard at all.

## Where

- `test\win32\harness-exitcode-audit.ps1` (section B, the B3 assertion)
- `test\win32\ipc-p1.ps1` step 9 (the site it names)
- `test\win32\lib\TestDesktop.ps1` `Invoke-OnTestDesktop` (the path that
  replaced it)
