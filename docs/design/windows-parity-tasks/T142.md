# T142 — The banner overlay does not defend its z-order

## Summary

**The banner overlay does not defend its z-order** — user-reported 2026-07-28 as *"windows in the background have banners that overlap windows in the foreground"*. ROOT CAUSE THIS TIME WAS NOT THE PRODUCT: a T131 verification probe (`raiseshot.ps1`) called `SetWindowPos(banner, HWND_TOPMOST)` to beat occlusion and never restored `HWND_NOTOPMOST`, so both overlays stayed topmost for the rest of the day; clearing the bit restored correct ordering (banner directly above its own window, both below whatever is foreground) and the symptom went away. But the product made it possible and could not recover from it: `updatePosition` passes `SWP_NOZORDER`, so once anything — a probe, a screen recorder, another app's stray `SetWindowPos` — leaves the bit set, nothing ever clears it. Fix: place the overlay explicitly on every reposition (just above its owner, `HWND_NOTOPMOST`) instead of `SWP_NOZORDER`, so the z-order is re-asserted continuously and is self-healing; same for the scrollbar/dim overlays if they share the pattern. Validation: an on-box case that sets `HWND_TOPMOST` on a live overlay, triggers a reposition, and asserts `WS_EX_TOPMOST` is gone and the overlay sits directly above its owner

## Details

**DONE 2026-07-30.** The filed mechanism was real and is fixed — but writing
the baseline assertion first turned up a SECOND, product-only cause of the
exact same user-visible symptom, with no stray probe involved at all. Both are
fixed by one helper.

### What the measurement found

The very first run of the new acceptance script failed its *healthy baseline*
(before any injection): with window B holding the foreground directly on top of
window A, A's banner overlay indexed **above** B, and `WindowFromPoint` over
A's banner band returned the banner overlay. Pre-fix z-order was literally
`[overlay(A), … , B, … , A]` — the `Between(overlay, A)` probe named the
sandwiched windows: `GhozttyScrollbar, GhozttyWindow`.

Mechanism: `SWP_SHOWWINDOW` lifts a popup to the top of the non-topmost band,
and window ownership only guarantees a popup stays above **its own owner** —
nothing keeps it below unrelated windows. So any banner set (or overlay first
shown) while its window was not in front left that overlay floating over other
apps until something re-placed it, which nothing ever did. That is the user's
report, reachable without any probe.

### The fix

`win32.healOverlayZOrder(hwnd, owner)` (`src/apprt/win32/win32.zig`), called
after every overlay reposition, plus `Surface.healOverlayZOrders` /
`Window.healOverlayZOrders` wired into **`WM_ACTIVATE`** — because the moment
the defect becomes visible is an activation change, and a window nobody resizes
would otherwise stay broken forever. It does two things, both no-ops when
nothing is wrong:

1. clears a **stray `WS_EX_TOPMOST`** (the filed cause), and
2. **re-seats** the popup directly above its owner when a foreign VISIBLE
   window has got between them (the cause above).

Policy lives in a new pure `src/apprt/win32/overlay_zorder.zig` (`isStray`,
`walkStep`), unit-tested in the none-runtime lane; the z-order walk
(`seatedAboveOwner`) is in `win32.zig`. Call sites: `BannerOverlay.updatePosition`,
`DimOverlay.show`, `Scrollbar.repositionAndResize`, `Window.showResizeOverlay`.

Three things the implementation had to get right, each of which was wrong in a
first draft and caught by the harness:

- **The check must be owner-RELATIVE.** `toggle_window_float_on_top`
  (`App.zig:2465`) and the quick terminal make a window topmost, and Windows
  propagates the bit to its owned popups. "Clear the bit whenever we see it"
  would drop the banner out of the topmost band and hide it behind its own
  floating window. So a topmost owner is left entirely alone (section E asserts
  the propagated bit SURVIVES a reposition, with a positive control that the
  propagation happens at all).
- **`SetWindowPos(overlay, owner)` puts the overlay BEHIND its owner.** The
  first draft used it on the theory that an owned window cannot sink below its
  owner; measured, the explicit call is honored as given and the overlay landed
  directly *under* A (`ov=6, A=5`). The seat is
  `SetWindowPos(overlay, GetWindow(root, GW_HWNDPREV))` — insert after whatever
  is directly above the owner.
- **Don't re-place on every reposition.** Unconditional placement churns the
  z-order of sibling overlays against each other on every layout pass, so the
  walk short-circuits when already seated (hidden windows and sibling overlays
  of the same window don't count as occluders).

### Validation

`test/win32/overlay-zorder.ps1` — **ALL PASS (24) ×3**. Sections: A healthy
baseline (+ the `Between` sandwich probe and a `WindowFromPoint` front-most
control), B stray-topmost repro, C heal on reposition, D heal on activation,
E float-on-top preserved, F the dim overlay and the scrollbar popup.

**Negative control** (the fix neutered with an early `return`, same binary
otherwise): **9 FAILED / 13 passed** — the baseline trio, C, D and both F cases
all fail pre-fix, so every assertion that matters is proven to distinguish the
builds. E passes either way (nothing to preserve when nothing heals), which is
noted deliberately: it is a regression guard, not a repro.

Standing floor at the same commit: `zig build test` both lanes + `zig build
test-agent` green, P1–P3 ALL PASS, and the two overlay-adjacent standing
scripts re-run green (`pane-banner.ps1`, `split-dim.ps1`).

Harness trap worth remembering (cost ~2 runs): **PowerShell variables are
case-insensitive**, so `$OV = Hwnd-Of $ov` silently destroyed the rect row it
was derived from. Every geometry probe then sampled `(6685007, …)` and
`WindowFromPoint` answered "nothing there" — which reads exactly like a product
verdict. The script now uses `$ovHwnd`/`$dimHwnd`/`$sbHwnd` and says why.
