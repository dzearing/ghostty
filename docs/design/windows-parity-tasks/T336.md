# T336 - T146d-3: cross-machine Restore All over the relay (per-window transport ownership)

Third child of the **T321 split (2026-08-02)**, and the one that closes T146.
Mac commit `43bfb8e4a`.

## Summary

T335 restores a machine's whole topology from the LOCAL agent's blobs. This is
the same thing pointed at a REMOTE machine over the relay - and it is separated
because of one structural difference that has no Mac analog:

**Mac hands every rebuilt window ONE `RemoteConnection`
(`SessionLayoutRestore.swift:659-675`, `presentResumedTopology(connection:)`).
win32 windows each OWN their transport** - `openDialedWindow` stores
`window.remote_dialed = dialed` (`App.zig:2202`) and `openRemoteWindowFrom`
re-dials the same machine for a new window from a remote one (T68). So
restoring N windows from a relay machine is N dials, or a deliberate decision to
share one - and whichever it is, the ownership/free rule has to be stated and
tested, not inherited by accident. T295's dial-off-thread + ownership discipline
is the pattern to reuse.

Everything else is T335's machinery pointed at a dialed connection: the same
`requestLayouts` decode, the same `requestSessions` attach set, the same
`App.restoreWindow`. The double-attach guard does NOT apply (the entry ids
belong to the other machine - Mac says so at
`SessionLayoutRestore.swift:696-698`), and frames should be re-clamped onto a
visible LOCAL monitor (Mac's `reanchor`), since a frame authored on a
4K portrait monitor can otherwise restore off-screen here.

Also owns:

- The relay token resolution + "not signed in" messaging the T320 remote resume
  already shapes (`MachineChooser.resumeRow`'s `.remote` arm).
- Retiring the "local-only" caveat T335 puts in CLAUDE.md, in the commit that
  makes the cross-machine statement true.

## Outcome (2026-08-02)

Done. `restoreAllRelaySessions` dials the machine, pulls ITS blobs, and replays
each decoded window through the same helpers launch-time restore uses.

**Ownership, settled: one dial per window, plus one for the pull.** The shared
alternative was rejected on the mechanism, not on taste - `Window.deinit` tears
its transport down, so a shared connection dies with whichever rebuilt window the
user closes first and leaves the rest attached to a corpse. The decision is a
value, not a convention: `RestoreTransport` carries the connection, the
`local_agent` flag, the dial the window will own, the machine identity (T68) and
the reanchor bit as ONE thing, so a caller cannot set the connection and forget
the ownership that goes with it. The acceptance script counts relay connects and
asserts `>= 1 + N`, which is the only way this property is visible from outside.

**The double-attach guard was KEPT, against this task's own prediction.** Mac
skips it cross-machine because its ids come from the LOCAL manifest and cannot
match; ours are read off the LIVE panes, so the same walk keeps working over the
relay - and pressing Restore All twice on a remote machine without it would tear
apart the windows the first press just built (the agent rebinds a session to the
newest ATTACH). What it needed was SCOPING: `paneForSession` now takes the
machine, because a session id means nothing without the machine that owns it.

**Frames re-anchor** (`restore_frame.zig`, pure, 9 unit tests): a frame that
intersects any visible area is left exactly where it was - a half-off-screen
window is still grabbable, and moving it would be the app second-guessing the
user - and one that intersects nothing is re-centered on the primary work area,
shrunk to fit. `MonitorFromRect(MONITOR_DEFAULTTONULL)` IS the intersection
query, so the win32 side asks the OS once rather than deriving a second answer
that could disagree with the first.

**The composition rule lost its `row == .local` clause**, which is the visible
half of the task: >= 2 live sessions is now the whole condition, matching Mac
(`MachineChooserView.swift:145-155`).

### The fixture is the interesting part

T319's "other machine" - a bare `ghoztty-agent --listen` - **cannot test this at
all**, and the reason is a real product property rather than a test
inconvenience: the only thing that pushes a layout blob is an APP pushing to ITS
OWN local agent (T334). An agent with no app holds no layouts, so a correct
cross-machine Restore All against it returns zero, and the test would pass while
proving nothing.

The only machine on this box an app has lived on is this one, and its agent
listens on a NAMED PIPE while the relay speaks TCP. `test/win32/lib/PipeBridge.ps1`
is that adapter (a TCP listener forwarding to the pipe, one outstanding
`ReadAsync` per pair because a pipe has no `DataAvailable` to poll), so the
fixture becomes *this box's own agent, reached the way a remote machine is
reached* - and every line of app code on that path is the real cross-machine one.

Deleting the agent's `port.json` after the fixture is built is what makes the
discrimination real rather than assumed: the app and the CLI both find the local
agent through that file, so with it gone the Local row can only resolve to
`failed`, and everything the app under test can see, it saw through the relay.
The bridge does not need the file (it knows the pipe name), so the agent keeps
serving and its children stay alive.

`FakeRelay.ps1` gained `-TripUnauthorizedFile`, the 401 twin of `-TripFile`, for
the same reason its sibling exists: a PERMANENTLY unauthorized device can never
get a roster loaded, so it can never reach a button that is gated on having one.
Expiring the bearer *after* the roster loaded is both the reachable path and the
honest one - tokens go stale between one click and the next.
