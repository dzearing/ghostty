# T233 - Split dividers: 2 DIP band with a real hover color change

## Summary

User directive, 2026-07-31, verbatim: *"I think the splitter lines should be 2px
and have a hover color that emphasizes it. 'lights it up in dark' or 'darkens
it' in light modes."*

Today the divider is **1 DIP** (`split_geometry.bandPx`, matching Mac's 1 pt
`SplitView.swift`) and has **no hover treatment at all** - hovering the grab
band changes only the mouse cursor (T94). Two consequences:

- At 100% and 125% the band rounds to a **single physical pixel**
  (`bandPx` unit test: `1.0 -> 1`, `1.25 -> 1`, `1.5 -> 2`, `2.0 -> 2`), which
  against a dark pane reads as a rendering artifact rather than a control.
- A user looking at the divider rather than at the pointer gets no feedback
  that it is grabbable, and a screenshot shows none either.

## The fix

Per `docs/design/win32-design-system.md` section 5:

| Property | Value |
|---|---|
| Visible band | **2 DIP** (`bandPx` becomes `max(round(2 * scale), 2)`) |
| Grab band | +-4 DIP either side, invisible (unchanged, T94) |
| Rest color | must clear **3:1** against both panes it separates |
| **Hover** | lighten by 25/channel in dark themes, **darken by 25** in light |
| Drag | same as hover, held for the whole drag |
| Cursor | SIZEWE / SIZENS over the grab band (unchanged) |

Reuse `icon_button.fillDelta`'s sign convention (positive in dark, negative in
light) rather than inventing a second one - the magnitude differs (25 vs 15)
because a divider is a thin mark that needs more delta to read, and that is
worth a comment where the constant lives.

**This is a deliberate divergence from Mac** (1 pt), justified by Windows'
fractional scaling rounding a 1 DIP band down to an invisible hairline. Record
it in the divergence list so a later parity sweep does not "fix" it back.

Hover state needs a `WM_MOUSEMOVE`/`TrackMouseEvent` path on the divider band
that repaints just the band - the pattern already exists for the hero divider
(`Window.zig`, `hero_divider_hover`), so this is extending an established
mechanism to the ordinary split divider, not inventing one.

## Blast radius

`split-divider.ps1` asserts `gap == bandPx` and counts divider-colored runs in
the parent-visible strip between the two pane rects (see **T228**, which
narrowed those probes onto the test desktop). Doubling the band changes both
the expected gap and the run width; update the script in the same commit.

## Validation

- `split_geometry.zig` unit tests: `bandPx` >= 2 at every scale 1.0-3.0, and
  panes+divider still tile the rect with no leftover pixel (the existing
  no-gap/no-overlap test must still pass, since a stale-pixel gap is exactly
  what it guards).
- Contrast: rest and hover divider colors both clear 3:1 against the pane
  background in dark AND light themes, asserted in `color_math`-style unit
  tests rather than eyeballed.
- On box: hover the divider and confirm the band visibly changes (screenshot
  diff of the band rows, not a cursor check), in both themes.
- `test/win32/split-divider.ps1` ALL PASS x3 with its negative control failing.

## What shipped (2026-07-31)

**`src/apprt/win32/split_geometry.zig`** — `bandPx` is `max(round(2 * scale), 2)`,
and the module gained the color half beside the geometry it already owned:
`HOVER_DELTA` (25), `hoverDelta(dark)` and `dividerColor(rest, dark, hot)`.
The sign convention is `icon_button.fillDelta`'s and is asserted against it
rather than restated, so the divider can never drift out of step with the rest
of the chrome; only the magnitude differs (25 vs 15), because a 2 DIP mark
needs more delta to read than a 28 DIP button fill.

**`src/apprt/win32/Window.zig`** — `hover_split` holds the split whose grab
band the pointer is in; `paintDividers` resolves ONE hot color and
`paintDividerNode` picks the hot brush for that handle. Which way to shade is
decided by the PANE background (`!color_math.isLight(bg)`), not the OS theme —
a light terminal under a dark Windows theme is an ordinary setup, and the
divider has to read against the panes it separates. A drag outranks hover
(`dragging_split` -> `drag_split_handle`) because the pointer routinely leaves
the band mid-drag and the mark must not flicker back to rest under the hand
that grabbed it. `heroResetTransients` is now `resetPointerTransients` and
drops `hover_split` too — the handle is active-tab state and goes stale on a
tab switch or tree change exactly like the hero indices did.

Hover arrives via the parent's `WM_MOUSEMOVE`: the band's outer edges lie over
the pane children, which answer `HTTRANSPARENT` there (T94), so this is the
same fall-through the resize cursor already rode on. Un-hover is
`WM_MOUSELEAVE` plus an explicit clear when the pointer crosses up into the
tab bar (which never generates a leave).

**A second, less obvious defect found while validating it.** The first
implementation repainted through `layoutSplits`' `GetDC` + `paintDividers`
shortcut, and the hover was correct on screen but INVISIBLE to a `PrintWindow`
capture: that path draws straight to the window DC and never marks the region
dirty, so the pixels never reach the backing store. It is right for its own
job — a band that MOVED has no dirty region to mark, because a child already
covers its old spot — and wrong for a band that only changed color. Replaced
with `refreshDividerBand`: `dividerBandRect` walks the tree for the one band's
rect, then `InvalidateRect` + `UpdateWindow` repaints it through the normal
cycle. Only the band rect is invalidated, so the panes never repaint.

## Evidence (2026-07-31, on the box)

`test/win32/split-divider.ps1` **ALL PASS (38 assertions)**, from 30 before.
`-NegativeControl` still fails (`1 FAILED / 37 passed`), and the new
assertions are not rubber stamps — an earlier run of this same script against
the half-finished build reported `FAIL T233 hover` twice while everything
around it passed.

Measured at the user's 125% (120 dpi): the band is **3px**, where the retired
1 DIP formula gave **1px**. `Get-ExpectedBandPx` mirrors `bandPx` in
PowerShell and must pass `[MidpointRounding]::AwayFromZero` — .NET's default
is BANKER'S rounding and 125% lands exactly on the midpoint (2 * 120/96 =
2.5), so the naive form expects 2px where the product correctly paints 3 and
fails against a healthy build at the one scale that matters most here.

**A POSTED HOVER CANNOT SURVIVE TO A PIXEL CAPTURE, and it took a debug log on
both sides to know that rather than guess it.** The posted move DOES set the
state — the log reads `divider hover=0` — and then the OS posts
`WM_MOUSELEAVE` within one frame and it reads `divider hover=null`, because
`TrackMouseEvent` watches the REAL cursor and there is none over the window on
a background desktop (`SetCursorPos` fails off the input desktop). The band is
back to rest before the first capture 60ms later:

```
debug(win32): divider hover=0
debug(win32): WM_MOUSELEAVE (diag)
debug(win32): divider hover=null
```

That is a harness limit, not a product defect: on a real desktop the leave
arrives when the real pointer leaves, which is precisely the un-hover. So the
claim is proved in two halves that together cover it — the COLOR by pixels
mid-DRAG (`dragging_split` does not depend on the cursor, and it runs through
the same one hot color as hover), read as rest -> hot -> rest from the same
probe at three moments; and the TRIGGER by the debug-log oracle, degrading to
a skip on a release build.

**Standing floor:** `zig build test -Dapp-runtime=none` exit 0, `zig build
test -Dapp-runtime=win32` exit 0, `zig build test-agent` exit 0, full GUI
build (`-Dapp-runtime=win32 -Doptimize=Debug`) exit 0, P1/P2/P3 ACCEPTANCE:
ALL PASS.

**Blast radius, checked not assumed:** `split-divider.ps1` was the only script
that pinned the band width. `hero-mode.ps1`'s divider is the hero/carousel
line (`HeroCarousel.zig`, still 1 DIP — a different control, out of scope);
`focus-follows-mouse.ps1` only skips sample points that land in the gap, which
a wider gap still satisfies; `pane-banner.ps1` and `session-relaunch.ps1` say
"divider" about text separators.
