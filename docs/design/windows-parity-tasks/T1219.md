# T1219 - The loop pushes every turn and never looks at CI, so a red build sits unnoticed until a release fails

## Summary

fork-ci's windows-cross job has been failing on every push since e2a706dc4 and no turn noticed. It was failing for the exact reason the win-v1.36.0 release later failed (T1218) - so CI had the answer hours before the gate task hit it, and the only thing missing was somebody reading it. Nothing in the turn (claim, validate, commit guard) asks GitHub whether the commit it just pushed is green.

## In plain terms

Every time the loop finishes a piece of work it pushes it, and a build machine
immediately tries to build it. Nobody ever looks at the answer. Today that
build had been failing for ten hours with the message that later stopped a
release dead, and the first thing to notice was the release itself.

## Goals

- [ ] A turn cannot end believing it shipped something green when the build
      says otherwise.
- [ ] The answer arrives where the turn already looks, rather than as one more
      thing to remember.
- [ ] Demonstrated red, not just green (go.md's rule for a new gate).

## What to work out

The turn already has two places that ask a question of the outside world and
refuse on the answer: `go-loop-exec.ps1 claim` (which reports stranded work,
guard staleness and an unpushed HEAD) and `parity-tasks.ps1 validate` (which
FAILS on those). CI status belongs in the same pair:

- The claim reports the conclusion of the newest completed run for the branch,
  and names the failing job when it is red.
- `validate` fails when the commit at the branch head has a completed FAILING
  run - with a hatch, since a run can be red for reasons that are not this
  turn's (and the hatch prints that it was used, per go.md).
- The in-progress case is not a failure: a run still going is reported as
  in-progress, and the next turn's claim is what catches it. That keeps the
  gate from blocking on a ten-minute build every turn.

Cost: one `gh run list --repo dzearing/ghoztty --branch <branch> --limit 1`
per turn boundary, which is a second and needs no new dependency.

## Validation criteria

- [ ] The claim report names the CI conclusion for the branch head, with the
      failing job when there is one.
- [ ] `validate` fails against a red run and says which job and which run.
- [ ] The refusal is demonstrated red in `test\win32\gate-negatives.ps1`,
      which is the registry for exactly these two gates' conditions.
- [ ] An in-progress run is reported and does not fail the gate.
