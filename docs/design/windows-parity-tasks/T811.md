# T811 - The agent lane intermittently panics in Connection.destroy at the end of T739's repaint test (DebugAllocator free)

## Summary

One run in a handful of `zig build test-agent` dies instead of finishing: 9432/9512 tests pass and then ghoztty-agent-core-test aborts. T460's first-chance capture got the stack on the occurrence that failed, so this is not a suspicion - .dumps/ghoztty-agent-core-test-20260812-182923-0.log names the faulting thread: std.heap.debug_allocator's `free` PANICS (abort via defaultPanic) under `Allocator.destroy` under `Connection.destroy` (src/remote/connection.zig:1603), called from `test 'T739: an injected repaint is rendered like DATA but advances no offset'` (connection.zig:4004). The args register row is 0xaaaa..., zig's undefined fill, so the shape is a free of memory the connection had already released or overwritten - i.e. a double free or a destroy racing one of the connection's own threads, not a leak. Reproduction is intermittent: the identical lane passed on the immediately following run (221s) and was green earlier the same day, which is why this needs the dump rather than a re-run to diagnose. Found while validating T461 (whose diff touches no shared or agent code: src/apprt/win32 only), so it is neither caused nor masked there. Next step is the dump, not a guess: `scripts\crash-catch.ps1 -FromDump .dumps\ghoztty-agent-core-test-20260812-182923-0.dmp` and the other threads' stacks in the same transcript, which is what will say WHICH thread was still inside the connection when destroy ran.

## In plain terms

Every so often the whole test run for the remote-session code would die halfway
instead of finishing, so nobody could see which check had actually gone wrong —
one bad check took the entire run down with it. The cause turned out to be a
teardown mistake in the test itself, already corrected by a later audit; this
task proves that, and fixes a related memory leak the same teardown code had
been quietly carrying. Nothing a user of the terminal sees changes, but a leak
in a long-running session is gone and a red test run now tells you what failed
instead of just collapsing.

## Root cause

The T739 repaint test tracks a `Pane` whose `ring` is `&ch` — a **stack**
`ring.Channel`. `Connection.destroy` frees any pane still tracked when the
connection goes away, and it frees the pane's ring with
`alloc.destroy(pane.ring)` because in production that ring is always heap.
Before T536's audit, the test untracked its pane on the last line of the body,
so **any** early `return error` (a `try` failing anywhere after `trackPane`)
left the pane tracked, `destroy` ran `alloc.destroy(&ch)` on a stack address,
and `std.heap.DebugAllocator.free` panicked `Invalid free` — aborting the
process with exit 3 *before* the test's real failure message was printed.
That is exactly the 2026-08-12 dump: `free` → `defaultPanic` under
`Allocator.destroy` under `Connection.destroy`, from this test.

So the flake was never "a crash in shipped agent code": it was a genuine
intermittent test failure whose error path detonated. The escalation is what
made it look like corruption, and what hid the underlying failure.
