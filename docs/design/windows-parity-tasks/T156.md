# T156 - shift+insert is swallowed on Windows (paste_from_selection can never perform)

## Summary

Found by T154's audit of the Windows keybind blocks, same defect class, one
block over. `Config.zig` (non-darwin block, `.{ .physical = .insert }` +
shift) binds **shift+insert -> `paste_from_selection`** with a plain `put()`
and no `performable` flag. On win32 `Surface.clipboardRequest`
(`src/apprt/win32/Surface.zig:1199`) returns **false immediately** for any
`clipboard_type != .standard` — Windows has no selection clipboard — so the
action can NEVER perform. Combined with the missing flag, the chord is
swallowed: shift+insert does nothing at all, and the pane never sees the key
either. Windows users expect shift+insert to paste (it is Windows Terminal's
and conhost's paste chord), so today's behavior is worse than either
alternative.

## Details

Two candidate fixes, pick one after checking Mac/Linux parity intent:

1. **Make it performable** (minimal, matches T154): the chord falls through
   to the shell, which is what a Linux user gets when the selection
   clipboard is empty. Does not give Windows users a working paste.
2. **Bind shift+insert to `paste_from_clipboard` on Windows** (Windows
   Terminal parity, likely what the user actually wants), performable, in
   the same win32 mirror block that owns ctrl+v. The generic non-darwin
   `paste_from_selection` binding stays for Linux.

Recommended: (2) plus performable, since (1) alone leaves a documented
binding that visibly does nothing. Check first whether the Mac seat has an
opinion — this is a Windows-only divergence in a shared block.

## Validation

Extend `test/win32/clipboard-paste.ps1` (T154's script — its in-pane
`[Console]::ReadKey` probe is exactly the oracle needed): with text on the
clipboard, shift+insert must paste it; with an image-only clipboard, the
chord must reach the pane rather than being swallowed. Plus the standing
floor.
