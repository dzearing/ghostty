# T1324 - Painting and resize feel sluggish next to the Mac build

## In plain terms

Dragging a splitter is slow and steppy. Banners flicker when they open and
close. Drag a splitter left with a banner showing and the banner does not keep
up - it stays the old size and leaves smeared artifacts behind. The whole app
feels heavier than the Mac one doing the same things.

## What the user reported (2026-09-04)

> "the windows version is so much slower than the mac version. like resizing
> panes is janky and slow and things flicker ... when i expand/contract
> banners, they flicker. when I resize panes, they're slow to paint. It feels
> so unpolished. ... i have a pane with a banner, in hero mode, i drag the
> splitter leftwards and the banner doesn't resize and i get artifacts."

## Three findings from a first read of the code

These are starting points with evidence, not conclusions. **Measure before
changing any of them** - the whole point of this task is to stop guessing about
performance.

### 1. The splitter drag blocks the UI thread on the renderer, once per surface

`Surface.zig` (~3280): during a live resize or a live split-layout,
`setSize` calls `WaitForSingleObject(frame_event, 16)` - it *blocks* until the
renderer presents a frame at the new size.

```zig
if (self.in_live_resize or self.parent_window.in_live_layout) {
    ...
    _ = w32.WaitForSingleObject(event, 16);
}
```

The comment explains why, and the reason is real: without it DWM stretches
stale framebuffer content and you see flicker. But the cost is that **every
mouse-move during a drag serialises the UI thread against the render thread,
once per affected surface**. Four panes means up to ~64 ms of blocking per
mouse move - about 15 fps of drag, which is exactly "janky and slow to paint".

macOS has no equivalent stall: CoreAnimation composites the layer tree, so a
resize does not need the app to wait for a frame.

### 2. Nine different kinds of layered popup, each its own HWND and paint cycle

`WS_EX_LAYERED` popups are created by `BannerOverlay`, `DimOverlay`,
`Scrollbar`, `KeyStateIndicator`, `ReadonlyBadge`, `RegionSelector`,
`ViewerPane`, `App` and `Window`. Each is a separate top-level window that DWM
composites above the OpenGL surface, and each has its own `WM_PAINT`.

That is a deliberate design (the headers explain that a plain child window
cannot reliably sit above GL content), and it is why the chrome works at all -
but it means a layout change fans out into many window repositions and many
independent GDI paints, where the Mac has one layer tree. It is the likeliest
structural reason the whole app feels heavier.

`BeginDeferWindowPos` batching already exists in `Window.zig`, so the
repositioning is at least batched; the paints are not.

### 3. The banner is not part of the live layout - which is the artifact bug

`layoutSplits` ends with `defer self.updateDimOverlays()`, so **dim overlays**
track pane rects during a drag. Nothing in that path repositions the
**banner**. That matches the report exactly: the pane moves under the drag, the
banner does not, and what is left behind is the artifact. This one is a
concrete bug rather than a performance question and can probably be fixed
first, on its own.

## How to approach it

**Measure first, and keep the numbers.** "Feels slow" has to become a number
before anything is optimised, or the work cannot be shown to have helped:

- Frame time during a splitter drag, at 1, 2, 4 and 8 panes - the per-surface
  blocking predicts this should degrade linearly with pane count, and if it
  does not, finding 1 is wrong.
- Time from banner-toggle to a stable frame.
- The same measurements on the Mac build where the comparison is meaningful,
  since "worse than Mac" is the actual complaint.

**Then fix in order of what the numbers say**, not in the order above.
Candidate directions, all unproven: cap or remove the per-surface frame wait
during drags (and find another answer to the stale-content flicker it exists to
prevent - it is a real problem); coalesce mouse-move-driven layout to one
update per frame rather than one per message; batch the overlay paints the way
the repositions are already batched; and consider whether the overlays that do
not need per-pixel alpha could be plain children.

**Do not regress the flicker the current code prevents.** The frame wait was
added deliberately. A change that makes dragging smooth and brings back
stretched stale content is not an improvement.

## Validation criteria

- [ ] Drag frame time is recorded before and after, at several pane counts,
      with the method written down so it can be re-run.
- [ ] Dragging a splitter with a banner showing keeps the banner in step -
      no lag, no artifacts. (The user's exact case: hero mode, drag left.)
- [ ] Expanding and contracting a banner does not flicker.
- [ ] Resizing panes does not show stale or stretched content - the regression
      the current frame wait exists to prevent.
- [ ] A perf harness in `test/win32/` holds the numbers, so a later change that
      makes painting slower again is caught rather than felt.
- [ ] The remaining gap to the Mac build is stated honestly - if some of it is
      structural (one layer tree vs many layered HWNDs), say so rather than
      leaving it as an open impression.
