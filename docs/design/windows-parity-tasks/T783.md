# T783 - Nothing runs go-loop-guard.ps1 when the go-loop scripts change, so the loop's own harness went 26-red for a day

## Summary

b64c3e8aa (2026-08-11) prefixed every go-loop-lock.ps1 message with an ISO timestamp for the uptime report. 26 assertions in test\win32\go-loop-guard.ps1 anchor on the answer's first word (^ACQUIRED, ^held, ^stale-dead), so the whole guard went red against a lock script that was working perfectly - and nobody noticed until T280 ran it the next day. The guard is not in the P1-P3 floor and no gate ties a scripts\go-loop-*.ps1 edit to it. The loop's supervisor is the one thing whose failure nothing else can catch, so its harness going quietly red is the worst place for this gap.

## In plain terms

Some of our test scripts are only run when somebody remembers to run them. One
of those covers the machinery that keeps the overnight work loop alive, and last
week a one-line change to a timestamp quietly broke 26 of its checks - the loop
itself was fine, but its safety net had been torn for a day and nothing said so.
Now every test script that matters carries a receipt of the last time it was run
and what the code looked like then. If the code has moved since, the loop says
so when it starts up, and refuses to record a finished task until that script
has been run again.

## Goals

- [x] a `guard-due` command that answers "has this harness been run against the
      code as it now stands?" from a committed receipt, not from a timestamp
- [x] the go-loop harness stamps that receipt on a clean green run - and only
      on a clean green run
- [x] the loop's first command of every turn reports staleness, and can never
      fail over it
- [x] the pre-commit gate FAILS over it, with a stated-intent hatch
- [x] the whole thing is measured by its own acceptance script
