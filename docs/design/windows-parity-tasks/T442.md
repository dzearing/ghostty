# T442 - test-agent lane is red: 'PageList resize (no reflow) more cols remaps pins in backfill path' panics with reached-unreachable, but only in the agent lane and only for some seeds

## Summary

Found 2026-08-04 running the standing floor for T439. `zig build test-agent`
fails with `thread NNNNN panic: reached unreachable code` in
`terminal.PageList.test.PageList resize (no reflow) more cols remaps pins in
backfill path`. The **same test passes in the `none` lane**, both filtered and
in a full unfiltered run minutes earlier, and the agent lane's own exit code
differs run to run - which points at a seed/order-dependent interaction inside
the agent test binary rather than at the test itself.

No Zig changed in the turn that found this: T439's diff is PowerShell and
markdown only.

## In plain terms

One of the three test suites has started failing, and it fails in a way that
does not look like an ordinary broken test: the same check passes when run by
itself and in the other suite, and the failure moves around between runs. Until
this is understood, that suite cannot be used as evidence that anything else
works - the same reason T430 was ranked ahead of feature work.

## Goals

- [ ] The failure is reproducible on demand (a seed, or a named ordering)
- [ ] Root cause: whether the defect is in the resize backfill path itself or in
      state another test leaves behind
- [ ] `zig build test-agent` is green again, and the floor means something

## Details

### What was observed

Three runs of the agent lane, one after another, on `1e1f9002a` with a clean
`git status` apart from T439's `.ps1`/`.md` edits:

| run | via | result |
|---|---|---|
| 1 | `floor-lane.ps1 -Lane all` | `agent FAIL in 180s`, `exited with error code 9` |
| 2 | `floor-lane.ps1 -Lane agent` | `agent FAIL in 155s`, `exited with error code 5` |
| 3 | bare `zig build test-agent` | exit 1, `7731/7742 tests passed`, the panic below |
| 4 | bare, `--seed 0x9655fdff` (run 3's seed) | exit 1, `7722/7742`, **`Segmentation fault at address 0x1b830c9de28`** in two *different* tests |

**Run 4 is the one that settles the shape.** Re-running with run 3's own seed did
not reproduce run 3's failure - it failed in
`terminal.formatter.test.PageList soft-wrapped line spanning two pages`
(with and without unwrap) instead, and this time with an outright segfault
rather than an `unreachable`. A crash whose location moves between runs, in a
binary whose other two lanes are green, is **memory corruption**, not a wrong
assertion in any of the tests it lands on. Run 3's
`Unable to dump stack trace: InvalidBlockIndex` says the same thing from the
other end - the stack was already unwalkable.

So the tests it names are victims, and chasing `PageList resize ... backfill`
specifically would be chasing a symptom. Find what corrupts the heap in the
agent test binary.

Only run 3 named the test. Runs 1 and 2 attributed the failure to
`compile test ghoztty-agent-test` with no diagnostic at all - see "The wrapper
hid the failure" below. That attribution sent the first two investigations at
the build instead of at a test.

```
thread 33236 panic: reached unreachable code
Unable to dump stack trace: InvalidBlockIndex
error: while executing test 'terminal.PageList.test.PageList resize (no reflow)
more cols remaps pins in backfill path', the following command exited with code
3 (expected exited with code 0):
".\.zig-cache\o\...\ghoztty-agent-core-test.exe" "--cache-dir=.\.zig-cache"
--seed=0x9655fdff --listen=-
```

Both `ghoztty-agent-test` and `ghoztty-agent-core-test` failed, on the same test.

### Why it is probably not the test

- **The `none` lane is green.** `zig build test -Dapp-runtime=none` passed
  unfiltered (160s) minutes before, and
  `-Dtest-filter="remaps pins in backfill"` passes on its own (exit 0). The
  `win32` lane is green too (176s).
- **The exit code and the failing test both move** (9, then 5, then
  `PageList resize ... backfill`, then two `formatter` tests on the SAME seed),
  and one run segfaults outright. That is memory corruption in the agent test
  binary, and it is why re-running "to see if it is a flake" answers nothing.
- The test is upstream and old - `d67dd08a2`, 2026-01-19, 3338 commits back - so
  this is not a newly written assertion.

What is NOT yet known is where the corruption comes from. The agent binary is
the only one of the three that links the agent's own code alongside the terminal
(root `src/agent_main.zig`, terminal through `terminal_options`), so the first
place to look is what the agent tests do that the other lanes never run - the
real-pty tests and the relay/self-update tests are both visible in the log
immediately before the failures. Start by bisecting with `-Dtest-filter` to find
the smallest set that still crashes, rather than reading the named victim test.

### The wrapper hid the failure

`floor-lane.ps1` reported `compile test ghoztty-agent-test ... failure` with a
bare exit code and no compiler diagnostic, twice. Running the same lane bare
immediately produced a normal, named test failure. Whatever the root cause of
the panic, a wrapper that reports a *run* failure as a *compile* failure is a
second defect: T430 exists so that a red lane is legible, and this made a real
test failure look like a broken build for two runs. Fix it here or split it.

## Outcome (2026-08-04) - split

Worked for a full context. It **reproduced on demand**, one real
use-after-free was found and fixed on the way, and the rest is split out
because the hunt had not converged by the context budget:

- **Reproduction, and it is not the seed.** The built test exe run directly
  (`ghoztty-agent-test.exe --seed=0x87af847b`) fails ~2 of every 3 passes, at a
  different test each time *with the same seed*. Test ORDER is deterministic
  (index 2192 is always `terminal.search.screen.test.simple search with
  history`); the crash point is not. So the variable is asynchronous, not the
  RNG.
- **Every crash is inside `Page.assertIntegrity`,** in whatever `terminal.*`
  test happens to be running, with fault addresses spread across `0x0`,
  `0xffffffffffffffff` and live-looking heap pointers. Confirms T442's reading
  that the named test is a victim.
- **One real UAF found and fixed: T420.** The agent server's three push pumps
  (metrics, session-cpu, roster) assigned their `std.Thread` handle OUTSIDE the
  mutex that guards their stop flag, and `stop*Pump` read it outside the mutex
  too. A `*_sub` on the control reader racing `shutdown()` could therefore
  leave a pump running past the `Server` (it then writes into freed memory
  forever) or let two callers join the same handle (T420's `NtClose` crash).
  Fixed by taking the handle under the lock and latching `pumps_closed` before
  shutdown stops them. This did NOT fix the lane.
- **Eliminated:** native-CPU codegen (`-Dcpu=baseline` fails identically),
  terminal tests alone (`-Dtest-filter="terminal."` passes), thread-count
  growth (2-5 threads all run), memory exhaustion (6-26 MB private bytes).

- **And the premise of this task is wrong.** The closing floor run came out
  `none=PASS win32=FAIL agent=PASS` - the **win32** lane crashed in
  `terminal.search.screen.test.reloadActive partial history cleanup on loop
  append error`, a member of the same victim set, while the agent lane passed
  that round. The agent binary is not special; the two lanes that fail are the
  two that run the `apprt.win32`/WebView2 tests. T443 leads with that.

The remaining hunt is **T443**, which carries the full reproduction recipe and
the eliminated-hypothesis list. The wrapper's mis-attribution of a failure -
which turned out not to be the wrapper's fault at all - is **T444**.

## Validation

- Reproduce on demand, then `zig build test-agent` green.
- `floor-lane.ps1 -Lane agent` must name the failing TEST when a test fails,
