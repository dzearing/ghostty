# T1222 - The packaging guard is due and cannot re-stamp without Docker

## In plain terms

There is a check that proves the Windows installer and the downloadable ZIP are
packaged correctly. It has not been run since the packaging code last changed,
so nothing currently vouches for the artifacts a new user would install. It is
not broken - it just needs a machine with Docker running, and Docker is down on
this box.

## The evidence

`scripts\guard-due.ps1 check` reports:

    GUARD DUE release-artifacts-packaging: test\win32\release-artifacts.ps1 has
    not been run since these changed:
        changed  dist/windows-installer/build-msi.sh

Observed on 2026-08-31 during T1218, and it predates that turn - the packaging
commit that changed `build-msi.sh` did not re-stamp this row. The harness's
Docker-dependent sections SKIP when Docker is unavailable, and a run with
skipped sections deliberately does not stamp, so the row cannot go green on a
box with the daemon down. `docker ps` on 2026-08-31 answered: *cannot find
`//./pipe/dockerDesktopLinuxEngine`*.

## What has to change

- Run `powershell -NoProfile -File test\win32\release-artifacts.ps1
  -RequireDocker` with Docker Desktop up, read the verdict, fix whatever it
  catches, and let the clean run re-stamp the row.
- Starting Docker Desktop is the user's call on this box (it has buried the
  machine before), so this task waits for a turn where it is already running, or
  for the user to start it.
- While it is due, `parity-tasks.ps1 validate` fails on it and turns have to use
  the `-NoGuardDue` hatch with a reason. That hatch existing for a KNOWN,
  filed reason is the intended use; leaving it due indefinitely is not.

## Validation criteria

- [ ] `scripts\guard-due.ps1 check` reports `release-artifacts-packaging` as
      CURRENT.
- [ ] The run that stamped it was a full one (no skipped sections), i.e. Docker
      was actually up.
- [ ] Any defect the run surfaced in the MSI/ZIP is fixed or filed.
