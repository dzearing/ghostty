# T499 - Every zig build logs 'Invalid timestamp in cache entry ... error.Overflow' from a poisoned global-cache entry

## In plain terms

Every time the project builds, one meaningless warning line appears in the
output. Nothing is broken — but a warning that fires on every single run
teaches everyone to skim past warnings, which is how a real one eventually
gets missed.

## Goals

- [ ] A clean `zig build test-agent` run emits no cache-timestamp warning
- [ ] Root cause recorded: what wrote the absurd timestamp, so it does not
      come back

## Summary

Observed 2026-08-05 during T437's validation: all 10 agent-lane runs (fresh
worktree, shared `D:\zig-global-cache`) surfaced

```
[default] (warn): Invalid timestamp in cache entry: 999999999999999999999999999999999999999999999999 err=error.Overflow
```

once per `zig build test-agent` invocation. The message is zig's build cache
(`std.Build.Cache`) failing to parse a stored file timestamp — the value is a
literal run of 9s far beyond any i128 nanosecond clock, so some entry in the
shared global cache directory carries a corrupt manifest line. The build
falls back gracefully (treats the entry as stale), so nothing fails; the
cost is one line of noise on every build and lane log on this box.

## Where to look

- `D:\zig-global-cache` manifest files (`h\*.txt`): find the entry whose
  mtime field is the 9-run, note which artifact it belongs to, then delete
  that one manifest (NOT the whole cache — a full clear costs the next build
  several minutes for no diagnostic gain).
- Worth a quick thought on origin before deleting: a tool writing a
  sentinel/max timestamp into a tracked file (an archive extractor writing
  no-mtime entries?), or a crashed write interleaving a manifest. If a repro
  is identifiable, note it; if not, delete the entry and watch whether it
  returns.
- If it returns, this stops being cosmetic and becomes "something in this
  repo's build writes files with garbage mtimes" — re-triage then.

## Validation

`zig build test-agent` (any lane) twice after the cleanup: the warning is
absent from both logs.
