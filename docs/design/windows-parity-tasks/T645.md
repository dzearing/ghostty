# T645 - Viewer feedback: the draft's staging folder, its footer link, and stale-draft pruning

## In plain terms

On the Mac you can open the folder your half-written feedback report is being
assembled in and drop extra files into it — a log, a crash dump, a recording —
and they ride along when you send. Windows has no way to do that: its staging
folder is created at the moment you press send and is gone a moment later.

## Summary

T636 shipped the win32 report writer with the atomicity property (build under
`temp/feedback/.staging/<stem>`, publish with one rename) but NOT the
long-lived DRAFT folder Mac keeps around it. Mac's half is
`ViewerFeedbackReport.stage` + `pruneStaleStaging` +
`ViewerView.revealFeedbackStagingFolder` + `feedbackDraftStem`.

## Details

What Mac has and win32 does not:

- **A stem that is stable for the draft's whole life**, minted when the
  composer opens, so the folder the user is shown is the folder that gets
  published.
- **`stage()`**: (over)write `report.json` and the draft's own `images/` IN
  PLACE on each change, leaving every other file in the folder untouched — that
  is what makes dragged-in files survive to the published report.
- **A footer link** showing `temp/feedback/.staging/<stem>`, which reveals the
  folder in File Explorer (Mac: `NSWorkspace.activateFileViewerSelecting`),
  materializing it first so it is never empty or stale.
- **`pruneStaleStaging`**: drafts composed but never sent would otherwise leave
  their folders forever; sweep entries older than 24h, never the current draft
  and never a recent one another pane may still be composing into.

Win32 today mints its stem inside `write`, so there is nothing to link to until
the report is already filed. The pieces that already exist and should be reused:
`viewer_feedback_report.makeStem` / the `.staging` constants, and the composer
footer that currently shows the destination (`ViewerFeedbackBar.paintFooter`).

Note the interaction with T637 (screenshots/image chips): the images a draft
holds are what makes the folder worth opening, so land these in whichever order
suits, but the footer link is worth more once there are images in it.

## Validation criteria

- [ ] Opening the composer creates nothing; typing into it materializes
      `temp/feedback/.staging/<stem>/report.json`, and the stem does not change
      as the draft is edited.
- [ ] A file dropped into that folder by hand is present in the PUBLISHED
      folder after a send (the publish is still one rename).
- [ ] The footer names the staging path and clicking it opens that folder in
      File Explorer.
- [ ] A staging folder older than 24h is swept on the next draft's write; the
      current draft's folder never is (unit tests, injected clock).
- [ ] `test\win32\viewer-feedback.ps1` stays ALL PASS.
