# T628 - a REMOTE machine on an incompatible protocol reads as merely unreachable

## Summary

Found while building T125. The skew handling landed for the LOCAL agent only.
Every other dial — the machine chooser's session roster, `+new-remote-window`,
the per-window reconnect ladder — still collapses `error.ProtocolIncompatible`
into "could not reach that machine", so a remote box running an incompatible
Ghoztty version is indistinguishable from one that is off.

## In plain terms

If a machine you connect to is running a version of Ghoztty that no longer
matches yours, Ghoztty tells you it could not reach the machine. So you check
whether the machine is awake, whether the network is up, whether the agent is
running — and all of those are fine. The real answer, that the two versions no
longer speak to each other, is the one thing it does not say. The connection
pill turns red and the reconnect ladder retries forever against something that
cannot succeed.

## Goals

- [x] A remote dial that fails on an incompatible handshake says so, in the
      chooser and on the connection pill, rather than "unreachable".
- [x] The reconnect ladder stops retrying a skew (retrying cannot fix it) while
      still retrying every transient failure exactly as it does now.
- [x] Nothing on a remote machine is ever restarted from here — a remote agent
      is not ours to kill; the answer is to update one side.

## Details

`error.ProtocolIncompatible` and `tcp_dial.DialReport` already exist (T125); the
missing part is threading them through `relay_dial.zig` / `RemoteReconnect.zig`
/ `MachineChooser` and giving the pill a distinct state or message. Care: the
pill's three states are already load-bearing for WCAG 1.4.1 (they differ in
whether there is text, not only in hue) — a fourth must not break that.

## Validation criteria

- [x] An acceptance script dials a local agent forced to a different
      `GHOZTTY_AGENT_PROTO_VERSION` over the remote path and asserts the message
      names a version mismatch, not unreachability.
      — `test\win32\ipc-remote.ps1` section 4b, ALL PASS. A real second
      `ghoztty-agent` on `GHOZTTY_AGENT_PROTO_VERSION=0`, dialed with
      `+new-remote-window --host --port`: names an incompatible version, names
      the endpoint, does NOT say "failed to reach", opens no window. Its own
      negative control is the first run of that section, which went red on
      exactly those three asserts when the agent was not listening.
- [x] The reconnect ladder does not spin on it.
      — `remote_reconnect.zig` "a protocol skew is terminal, named, and never
      retried (T628)" in the `none` lane: `.incompatible` collapses to
      `ProbeOutcome.incompatible_agent` for all three liveness answers, and
      `decideAttempt` returns `.terminal` for BOTH the automatic and the manual
      ladder. The state it lands in is `self_healable = false`, so
      `needsTick` is false and no slow background re-dial is armed either.
- [x] Both zig test lanes, `test-agent`, and P1-P3 stay green.
      — `scripts\floor-lane.ps1 -Lane all`: `lib#1=PASS none#1=PASS
      win32#1=PASS agent#1=PASS`. `ipc-p1` 25 / `ipc-p2` 20 / `ipc-p3` 16
      assertions, ALL PASS.

## Validation evidence

Beyond the criteria above, the 24 acceptance guards these edits made due were
all run green and re-stamped (`scripts\guard-due.ps1 check` now reports zero
non-advisory rows due). The two that actually watch this code:

- `test\win32\remote-pill.ps1` — drives a real remote window against a loopback
  agent and reads the capsule's painted pixels, its `WM_NCHITTEST` answer and
  what a click does. Green with the fourth mode in place, which is the evidence
  that the new state did not disturb the three that were already load-bearing.
- `test\win32\remote-reconnect-relay.ps1` and
  `test\win32\chooser-resume-remote.ps1` — the two remote paths whose failure
  vocabulary grew a member.

Unit coverage added in the `none` lane: `tcp_dial.classifyHandshakeError` (the
shared rule, with the "a peer version on a non-disagreement error changes
nothing" case), `dial_failure` (the three-way split, the retryability question
and the assertion that the three sentences are distinct and that only the
unreachable one blames the agent), `remote_pill` (the fourth label, its
distinctness from `Reconnect`, the tooltip contents, and that the status still
fits `status_cap` under a long machine name), and `list.zig` (the `reason` key,
present only when it is the interesting answer).

## Harness note

The agent's single-instance guard is a NAMED MUTEX, so `GHOSTTY_AGENT_LOCK`
alone does not let a second agent coexist — it exits 183 before it ever
listens, which reads downstream as an unreachable port. `GHOZTTY_AGENT_INSTANCE`
(T167) is the knob that forks the whole guard identity; section 4b sets a
per-PID suffix. Without it the section silently degrades into a second copy of
section 4, which is how the first run of it passed the two asserts that were
not about the skew at all.
