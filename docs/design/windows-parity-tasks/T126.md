# T126 — hero-mode key navigation audit vs main's `HeroKeyNavigator`

## In plain terms

Hero mode gives one pane the big stage on the left and puts thumbnails of the
others in a strip down the right; the arrow chords walk that strip. On the Mac
those chords went wrong three ways — they walked a stale copy of the layout, so
a pane you opened after entering hero mode was unreachable; they moved *every*
open window at once instead of the one you were typing into; and from a web
pane one press jumped two thumbnails. This task measures whether the Windows
build has any of those problems.

It does not — but it turned up one of its own: with a web or document pane on
the stage, the shortcut that leaves hero mode did nothing. The keystroke went
to the page instead of the app, so you could step onto such a pane and then
had no way back out except stepping onto a terminal first. That is fixed, and
the strip's slide animation, which also quietly gave up whenever a web pane was
involved, now runs for those panes too.

## Goals

- [x] Prove key navigation reads the LIVE split tree: a pane added after hero
      mode is on is reachable, and one closed while it is on does not strand
      the selection past the end
- [x] Prove one press moves exactly one tile and skips nothing
- [x] Prove one press moves only the window it was aimed at, with two windows

- [x] Fix: hero mode can be entered and left from a focused viewer pane
- [x] Fix: the selection slide animates for viewer panes too, instead of

- [x] Land it as a repeatable acceptance script, teeth-checked against the

## Details

Main's `280f2449e` extracted hero navigation into a dedicated `HeroKeyNavigator`
because the Mac was navigating a **stale snapshot** of the split tree and could
act on a window other than the aimed-at one; `4eb13a651` then fixed an arrow-nav
beep and a skipped pane.

win32 has its own hero implementation (`HeroCarousel.zig` + `hero_math.zig`), so
this is an **audit, not a port**. Confirm on the box that win32 navigates the
LIVE tree — it does call `heroOnTreeChanged` on rearrange, which is a good sign
but not proof that key navigation reads current state — and that arrow
navigation skips no pane and never beeps.

The viewer half of `1e0cf5484` / `4eb13a651` (viewer panes participating in hero
mode, viewer-pane beep) is moot until T90 lands viewer panes.

## Findings (2026-08-09)

**The two Mac hazards are absent by construction, and now measured.**

- *Stale tree.* Mac's key monitor closed over the `tree` of the SwiftUI struct
  it was installed from. win32 has nothing to capture: `Window.gotoSplit`,
  `Window.swapSplit` and `Window.heroSelect` all read `tab_trees[tab]` and
  `leafCount(tab)` at the instant the key lands, and `heroOnTreeChanged` clamps
  the index whenever the tree moves under them. Arms B and C of the new script
  are the evidence: the debug log's `n=` (the live leaf count at the keystroke)
  reads 5 after a mid-hero split and 4 after a mid-hero close.
- *Wrong window.* Mac's monitor was app-wide. win32 has no monitor at all — a
  bound action rides its surface (`core_surface.rt_surface.parent_window`), and
  the viewer accelerator path dispatches on the pane's own `Window`. Arm D puts
  two windows in hero mode and shows each press moving exactly one of them.
- *Double-step / beep.* Mac's viewer re-injected the "unhandled" chord, so one
  press stepped twice. win32's `ViewerPane.onAcceleratorKeyPressed` calls
  `setHandled(true)` before posting a single `WM_APP_VIEWER_ACCEL`, so the
  chord is consumed once. Arm A counts `heroSelect` log lines per press: one,
  every time. (There is no Windows beep to suppress — that is an NSBeep
  behavior with no win32 analog.)

**Two real defects, both fixed here.**

1. `viewer_accel.forwards()` did not admit `toggle_hero_mode`, so a focused
   viewer swallowed ctrl+shift+space into the page. T397 had already made a
   viewer a full carousel citizen (own tile, selectable, navigable), which is
   exactly what turns this from a curiosity into a one-way door: step onto a
   viewer tile and there was no keyboard way back out of hero mode.
   Fix: the action joins the forwarded set, with a matching arm in
   `Window.performViewerBindingAction`.
2. `Window.heroStartAnims` gated the selection slide on
   `view.surface().snap_dib`, narrowing to terminals — the same shape as the
   T397 tile bug, one level up. `PaneView.heroSnapshot()` and
   `HeroCarousel.paintSlideSnap` are both already kind-generic, so the gate was
   the only thing left refusing a viewer a slide. Fix: the gate asks
   `heroSnapshot()`, the accessor the painter itself uses.

**Out of scope, filed as T681.** Probing arm C turned up that a closed
split pane's `GhozttyTerminal` child window is never destroyed —
`Surface.deinit` says so deliberately (OPENGL32.dll hooks window destruction
and segfaults after WGL teardown), so the HWND survives hidden for the app's
life. Measured: 10s after `+close`, the corpse is still enumerable at its old
size. It is why this script counts leaves from `+list --json` rather than from
child windows.
