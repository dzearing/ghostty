# T508 - atomic_write's 'concurrent writers never error' guarantee flakes under box load - the T183 test failed with TestUnexpectedResult in a 5-way soak

## In plain terms

We recently fixed file-saving so that two parts of the program saving the same
file at the same instant can never corrupt it or fail (T183), and a test
guards that promise. Under heavy machine load that test just failed once: one
of the simultaneous savers reported an error. Nobody's file was corrupted, but
the promise was "never errors", and a promise that breaks under load will
eventually break in real use — the agent really does save its session roster
from several threads at once. This finds the exact error and makes the save
retry it away.

## Goals

- [x] Capture the swallowed error: which call fails, and with what
- [x] Confirm the root cause with measurement, not a guess
- [x] Make the save out-wait the transient failure so concurrent saves never error
- [x] Deterministic unit tests for the retry path (no load required)
- [x] Soak + floor green

## Root cause (confirmed 2026-08-15)

The failing call is the **rename** (`NtSetInformationFile` /
`FileRenameInformation` + `ReplaceIfExists`), and the error is
**`error.AccessDenied`** (`STATUS_ACCESS_DENIED`). An instrumented copy of
`writeChunks` with per-call-site tagging reproduced it on demand: 4 threads x
200 rounds on one path, 10 processes at once, under 16 CPU-spinner jobs —
6 of 10 processes failed, every one at `site=rename err=AccessDenied`.

The mechanism is NOT two renames colliding for a microsecond. A probe that
retried the rename unbounded (1ms sleeps) and timed each outage showed the
real shape: when it hits, **all four threads block at once and the outage
lasts 440–786ms**, then clears completely. That is an on-access scanner
(Defender) opening the file the previous writer just published — without
`FILE_SHARE_DELETE`, which makes every replace-rename of that target fail
AccessDenied until the scan completes — with the scan stretched from
sub-millisecond (idle box, never noticed) to ~800ms by CPU starvation.

That sizing datum is the whole fix: a first attempt with a 95ms retry budget
still failed 37 of 120 runs, because the budget sat inside the outage. The
landed fix retries the transient errors (`AccessDenied`,
`PathAlreadyExists`) with 1..50ms exponential backoff under a **5s time
budget** (~6x the worst observed hold) — after which 120 of 120 runs passed
under the same harness. Retrying is safe by construction: the staging file is
unique-named, complete, and synced before the rename, so whichever attempt
lands publishes a whole file. A genuine permission failure still surfaces,
~5s later.

## Summary

During the T317 close-out soak (10 runs of the win32 test binary, 5 concurrent,
2026-08-06), run 7 went red — not a crash, one failed test:

```
3639/3907 remote.agent.atomic_write.test.writeChunks: concurrent writers to ONE
          path never error or tear (T183)...FAIL (TestUnexpectedResult)
    src\remote\agent\atomic_write.zig:151: try testing.expect(!failed.load(.seq_cst));
```

`failed` is set only when a writer thread's `writeChunks` call returns an
error — i.e. the T183 guarantee ("with unique staging names every call must
SUCCEED") did not hold. 4 in-process threads × 25 rounds contend on one path,
and the box was running 5 copies of the test binary at once, so this is the
guarantee failing under load, at ~1/10 whole-binary runs at 5× concurrency
(log: `%TEMP%\ghoztty-soak\t317-seed-0xefa4b814-20260806-010926-07.log`).

Two things worth knowing before fixing:

- **The error is swallowed.** The test's writer catch block records only a
  bool, so which error occurred (and from which call — `createFile`, `sync`,
  `rename`, or the staging `deleteFile` cleanup) is unknown. Step 1 is making
  the test record the actual error value; guessing ahead of that datum is how
  wrong fixes happen.
- **The likely suspect is the rename.** `writeChunks` ends in
  `std.fs.cwd().rename(tmp_path, path)` — on Windows that is
  `FileRenameInformation` with `ReplaceIfExists`, and two of those replacing
  the SAME target concurrently can transiently collide (sharing/access
  violation shapes, surfacing as `error.AccessDenied` or similar) even though
  each staging file is unique. If that is confirmed, the fix shape is a small
  bounded retry on the transient error set around the rename — the unique
  staging name already guarantees whichever rename lands publishes a complete
  file, so retrying the loser is safe by construction.

This matters beyond the test: the agent's `session_meta` persists
`sessions.json` from the control thread, the child-exit watcher, and shutdown
concurrently — a transient error there is a dropped roster persist with a
warn nobody reads. Related but distinct: T480 (a load-sensitive *assertion*
that is environmentally wrong), T500 (consolidating the remaining fixed-name
copies onto this helper — a fix here strengthens all of them at once).
