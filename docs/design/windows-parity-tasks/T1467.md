# T1467 - A test teardown that kills the app reports it as CRASHED - 0xFFFFFFFF is Stop-Process, not an NTSTATUS

## In plain terms

When one of our automated checks finishes, it kills the app windows it opened
and then prints a short report on how each one ended. For one of them it says
the app CRASHED, with an unrecognised error code - but nothing crashed: that
code is simply what Windows leaves behind when something is force-killed, which
is what the check itself just did. A green run that ends with the word CRASHED
in it is how a real crash line stops being read.

## Summary

`ConvertTo-GuiExitVerdict` (`test\win32\lib\GuiPostmortem.ps1`) decides crash
vs clean exit structurally: any exit code with the high bit set is a crash, and
one the name table has never seen is reported as `unnamed NTSTATUS`. That rule
is right for real exception codes and wrong for exactly one value.

`0xFFFFFFFF` (-1) is what `Stop-Process -Force` and `TerminateProcess(h, -1)`
leave as the exit code. It is not an NTSTATUS at all - a real status with the
severity bits set starts `0x8`, `0xC` or `0xE` and carries a facility - so it
can never arrive from an unhandled exception. Observed on 2026-09-08 in a
green `test\win32\session-persistence.ps1` run (77 PASS / 0 FAIL), whose
teardown printed:

```
  GUI POSTMORTEM ghoztty.exe pid 42620
    verdict : CRASHED - 0xFFFFFFFF unnamed NTSTATUS
    WER     : no Application Error record found for it
```

The missing WER record is the corroboration: nothing crashed, so Windows filed
nothing.

## Details

- The fix is a named entry rather than a hole in the rule: add `0xFFFFFFFF` to
  `$script:GUIPM_STATUS_NAME` AND return `IsCrash = $false` for it, so the
  verdict line says what actually happened ("force-terminated - the exit code
  `Stop-Process -Force` / `TerminateProcess(h, -1)` leaves") instead of naming
  a status that does not exist. Keep every other high-bit code a crash.
- `0x40010004 DBG_TERMINATE_PROCESS` is already in the table and has the same
  shape of cause, so the wording should match it.
- The same run's other seven `exited with 1` lines are the app's own deliberate
  exit and read correctly, so they are NOT this bug.
- `TestDesktop.ps1` keeps a `Killed` flag per launch precisely so "the teardown
  report does not present a deliberate Stop-Process as a mystery" (T527) - work
  out why this corpse was reported anyway, since that flag not being set may be
  the more general defect.

## Validation criteria

- [ ] `ConvertTo-GuiExitVerdict -ExitCode -1` returns `IsCrash = $false` with a
      name that says force-terminated.
- [ ] Every code already in the name table still verdicts as a crash.
- [ ] `test\win32\gui-postmortem.ps1` covers both, and its negative control
      still scores red.
