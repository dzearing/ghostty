# T1099 - The merge-back plan's eight staged commits are unreferenced, and the loop's own claim reports UPSTREAM OK over it

## In plain terms

The plan for merging this Windows work back into the main project points at eight specific save-points in git history. Nothing is currently holding on to those save-points, so a routine git cleanup could delete them and the plan would point at nothing. On top of that, the check built to warn about exactly this says everything is fine every single morning.

## Summary

`test\win32\upstream-remote.ps1` scored `UPSTREAM-REMOTE: 5 FAILURE(S) / 18 passed` in the T1094 full sweep:

```
FAIL A3 upstream/main resolves (the ref that keeps the objects alive) (got '')
FAIL A6 every one is an ancestor of upstream/main, so the ref keeps it alive
        (dangling: 063ac3ecc, 74d0c72fd, ad6e72ddc, c4c9e945a,
                   c6b0c0dcb, e6605009b, e8525c0fd, ec5b36961)
FAIL A7 `upstream-remote.ps1 check` scores this repo green (exit 1)
FAIL A8 ...and says so in one readable line
        (got: UPSTREAM PROBLEM / upstream/main does not resolve (never fetched?))
FAIL setup: a merge base with upstream exists
```

This reproduces against the LIVE repo, not a sandbox - `git rev-parse --verify upstream/main` answers `fatal: Needed a single revision` right now. A1/A2 pass, so the `upstream` remote is configured and points at ghostty-org/ghostty; what is missing is the fetched ref.

Two consequences, and the second is the one that let this sit:

1. **The eight commits are reachable from nothing.** A5 passes, so they still resolve today - they have simply not been collected yet. `git gc` (which runs automatically) is entitled to prune them, and the merge-back plan would then cite shas that no longer exist.
2. **Step 0's claim reports the opposite.** `scripts\go-loop-exec.ps1 claim` printed `UPSTREAM OK (upstream/main a88ad03e6, fetched 16h ago)` on the very turn that found this. Whatever it reads is not `upstream/main` as git resolves it - a cached stamp, a config value, or a reflog entry. A gate that cannot go red is not a gate.

## Where

## Goals

- [x] Re-fetch the ref and confirm all eight shas become ancestors again: `powershell -NoProfile -File scripts\upstream-remote.ps1 ensure -Force`.
- [x] Work out HOW the ref went away while the claim kept saying OK - most likely a `git remote prune`, a refspec that stopped writing `refs/remotes/upstream/main`, or a fetch that only ever wrote FETCH_HEAD. Fix the cause, not the symptom.
- [x] Make the claim's `UPSTREAM OK` line derive from `git rev-parse --verify upstream/main` (and the ancestry of the cited shas), so it is the same question the acceptance script asks. It must be capable of printing UPSTREAM PROBLEM on this box today, before the fix.
- [x] Consider a durable anchor for the merge-back points that does not depend on a remote-tracking ref at all - a local tag per staged sha is cheap and cannot be pruned.

## What was found

The ref did not decay - it was **deleted**. The 2026-08-22 05:14 hard-fork turn
ran `git remote remove upstream` by hand, which takes `refs/remotes/upstream/*`
with it; the 05:26 correction re-added the remote fetch-only, and a re-add does
not restore a tracking ref. Nothing fetched again until this morning's claim, so
for that window all eight shas were reachable from nothing. That is not a bug in
any script - it is the anchor being the wrong kind of ref. A remote-tracking ref
also vanishes on a refspec change, on a fresh clone, and on the Mac seat, which
has never fetched this remote at all.

The false green is the separate half, and it is a real defect: `ensure` printed
`UPSTREAM OK` from `upstream/main` resolving **alone**. It never asked the
plan-sha question `check` asks, so the one line the loop prints every turn could
not go red for the thing the script exists to protect.

## What changed

- **A durable anchor**: `scripts\upstream-remote.ps1 ensure` now writes a local
  lightweight tag `refs/tags/upstream-anchor/<sha>` for every sha the plan cites.
  A tag is a ref this repo owns - no remote operation prunes it, it survives the
  remote being removed outright, and lightweight means neither `git push` nor
  `push.followTags` can leak it into `origin`.
- **One verdict, two callers**: `Get-Problems` is now the single place the
  verdict is computed, so `ensure` and `check` cannot answer different questions.
  `ensure` prints `UPSTREAM PROBLEM` and the offending shas when the assertion
  fails - and still exits 0, because a claim that wedges on an unreachable GitHub
  is a worse failure than an unanchored sha. The teeth are the acceptance script
  via `guard-due`.
- **`check` no longer hides the sha question behind a missing ref.** It used to
  skip the sha rows entirely when `upstream/main` did not resolve; the whole
  point of the tag is that a sha stays alive with the remote gone, so the rows are
  evaluated either way.
- **The plan doc is in the guard's coverage list**, because it is the input: a
  re-cut stage introduces a sha nothing has anchored yet, and editing the doc now
  makes the harness due.
