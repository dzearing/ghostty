# T1218 - Retire the morning swap

## In plain terms

You install Ghoztty from the website and get a real release. Until now, a
background job on this machine quietly replaced that program with a build
straight out of the source tree every morning - so the terminal you installed
was, by lunchtime, something that had never been released. You asked for the
opposite: your terminal should only ever run something that was actually
published, and it should update itself the way every other app does. After this
lands, nothing in the repo can overwrite your installed Ghoztty; new work
reaches you as a published release that your terminal offers you.

## Goals

- [x] Nothing in the repo can replace the installed app - it refuses, rather
      than merely not doing it by default
- [x] The retired morning job is gone: script, harness, guard row and the
      instruction that ran it
- [x] Building and running a dev build still works, on a copy the loop owns
- [x] The rule is written where the next turn reads it, and a test proves the
      refusal actually fires

## The call being executed

D85 asked whether the user's terminal should keep being swapped every morning
by a repo build, or update itself from published releases like any other app.
The user chose **option 2 - update itself from published releases only**, which
is **not** the option the loop assumed. Their reasoning, recorded on the
decision: fewer surprise restarts, and a terminal whose version always
describes real published bytes.

> "the terminal should only ever run something that was actually published"

T1217 implemented the *assumption* (keep the swap, make it honest) and is
`done`. The resolution note landed on that closed task, where nothing would
ever act on it - which is why this task exists. **Until this lands, the shipped
behaviour is the one the user rejected.**

## What has to change

- **The morning swap stops owning the installed terminal.** Whatever job
  replaces `%LOCALAPPDATA%\Programs\Ghoztty\ghoztty.exe` from `zig-out` each
  morning must no longer do so. The installed terminal is the product, and the
  only thing that may replace it is the updater (T1178) taking a published
  release.
- **Dev builds stay available, just not by overwriting the install.** The loop
  still needs to run what it just built - from `zig-out`, a portable copy, or
  an explicitly-invoked path. This task removes the *silent overwrite of the
  user's install*, not the ability to test a dev build.
- **Publishing becomes the delivery path.** The loop publishes at the end of a
  day's work so same-day fixes still arrive the same day; the user then takes
  them through the updater like any other user. That is also, usefully, the
  T1179 second half being exercised continuously rather than once.
- **Audit what the swap left behind.** Anything that assumed the install would
  be refreshed out of band - version stamping in `launch-upgrade.ps1`, the
  `-Dversion-string=<newest win-v>+<HEAD sha>` stamping T1217 added, and any
  doc telling a human to run an upgrade script - needs revisiting now that the
  install is only ever a published build.

## Validation criteria

- [x] No scheduled job, hook, or script replaces the installed
      `ghoztty.exe` / `ghoztty-agent.exe` from a repo build. A test asserts it,
      so the swap cannot come back quietly.
      *How: `scripts\morning-refresh.ps1` (the only such job) is deleted, and
      `test\win32\install-ownership.ps1` sections B and C RUN the two delivery
      scripts against the real install path and observe exit 3 with the refusal
      text; sections D/E assert the retirement across guard-due, go.md and the
      scripts themselves, each with a `-TeethCheck` mutation proving it can
      score red. ALL PASS both ways.*
- [x] After a day of loop work with no publish, the installed terminal still
      reports the release the user installed - unchanged bytes.
      *How: structurally, since nothing can write it any more; the baseline for
      the observation is recorded below. Note what the baseline SHOWS: the
      install is currently a repo build (`1.4.0-...+db68549df`, swapped at
      07:49 today by the job this task retires), which is exactly the state D85
      rejected. Getting it back onto published bytes is T1179's walk, already
      waiting on the user to install win-v1.36.0 from the website.*
- [ ] A published release is picked up and applied by the in-app updater, and
      the version afterwards matches the release.
      *Not this turn: needs a publish (Docker is down on this box) and the
      user's own install action. It is T1179's criterion and T1179 is open and
      blocked on exactly that; T1220 covers the loop's end-of-day publish.*
- [x] The loop can still build and run a dev build without touching the
      installed one.
      *How: the four floor lanes build and run from `zig-out`, and the upgrade
      script's swap path is intact - only its target moved to
      `%LOCALAPPDATA%\ghoztty\dev-install`, which section A8 asserts is NOT
      treated as the user's.*
- [x] `docs/claude/build.md` states the rule: the installed app is the user's,
      and only the updater may replace it.
      *How: the "installed app is the user's" bullet, checked by section F.*
- [x] Any upgrade script still referenced as a user-facing path is removed or
      re-scoped to dev builds only.
      *How: `morning-refresh.ps1` removed; `upgrade-ghoztty-windows.ps1` and
      `launch-upgrade.ps1` re-scoped to the dev install in their headers,
      defaults and behaviour; go.md step 6.5 now says publish instead of swap.*

updater is a regression of this task.
