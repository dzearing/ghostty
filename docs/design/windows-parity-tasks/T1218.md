# T1218 - Retire the morning swap

## The call being executed

D85 asked whether the user's terminal should keep being swapped every morning
by a repo build, or update itself from published releases like any other app.
The user chose **option 2 - update itself from published releases only**, which
is **not** the option the loop assumed. Their reasoning, recorded on the
decision: fewer surprise restarts, and a terminal whose version always
describes real published bytes.

> "the terminal should only ever run something that was actually published"

T1217 implemented the *assumption* (keep the swap, make it honest) and is
`done`. The resolution note landed on that closed task, where nothing would
ever act on it - which is why this task exists. **Until this lands, the shipped
behaviour is the one the user rejected.**

## What has to change

- **The morning swap stops owning the installed terminal.** Whatever job
  replaces `%LOCALAPPDATA%\Programs\Ghoztty\ghoztty.exe` from `zig-out` each
  morning must no longer do so. The installed terminal is the product, and the
  only thing that may replace it is the updater (T1178) taking a published
  release.
- **Dev builds stay available, just not by overwriting the install.** The loop
  still needs to run what it just built - from `zig-out`, a portable copy, or
  an explicitly-invoked path. This task removes the *silent overwrite of the
  user's install*, not the ability to test a dev build.
- **Publishing becomes the delivery path.** The loop publishes at the end of a
  day's work so same-day fixes still arrive the same day; the user then takes
  them through the updater like any other user. That is also, usefully, the
  T1179 second half being exercised continuously rather than once.
- **Audit what the swap left behind.** Anything that assumed the install would
  be refreshed out of band - version stamping in `launch-upgrade.ps1`, the
  `-Dversion-string=<newest win-v>+<HEAD sha>` stamping T1217 added, and any
  doc telling a human to run an upgrade script - needs revisiting now that the
  install is only ever a published build.

## Validation criteria

- [ ] No scheduled job, hook, or script replaces the installed
      `ghoztty.exe` / `ghoztty-agent.exe` from a repo build. A test asserts it,
      so the swap cannot come back quietly.
- [ ] After a day of loop work with no publish, the installed terminal still
      reports the release the user installed - unchanged bytes.
- [ ] A published release is picked up and applied by the in-app updater, and
      the version afterwards matches the release.
- [ ] The loop can still build and run a dev build without touching the
      installed one.
- [ ] `docs/claude/build.md` states the rule: the installed app is the user's,
      and only the updater may replace it.
- [ ] Any upgrade script still referenced as a user-facing path is removed or
      re-scoped to dev builds only.
