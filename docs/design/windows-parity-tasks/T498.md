# T498 - load-flake audit: yield-spin and fixed-sleep test waits outside the agent lane (connection.zig, inbound_ring.zig, tcp_dial.zig, client_mux.zig, socket_stream.zig, wp4_e2e.zig)

## In plain terms

T346 fixed the agent test suite so a busy computer can no longer make its
tests report false failures. The same weakness exists in other test files that
the other two test lanes run: they wait for background work by "trying N
times" or "sleeping a fixed spell" instead of waiting up to a wall-clock
deadline. Until they are converted the same way, a busy box can still turn
those lanes red when nothing is broken.

## Goals

- [x] Every cross-thread test wait in the non-agent remote code uses the T346
      `waitUntil` deadline helper (move it somewhere both lanes can import).
- [x] Both `zig build test` lanes pass while the box is fully loaded.

      2026-08-15: lib 47s, none 321s, win32 384s, agent 353s, ALL PASS.
- [x] Both `zig build test` lanes green x3 including a run started under an
      all-core CPU load — none: clean 321s, LOADED 353s, clean again; win32:
      clean 384s, LOADED 407s, clean again (all via floor-lane.ps1, ALL PASS).

      untouched by design.

## Summary

T346 converted the agent lane's cross-thread test waits from yield counts /
fixed sleeps to wall-clock-deadline waits (`src/remote/agent/test_util.zig:
waitUntil`), after loaded runs produced false failures in three different
shapes: 10k-yield spin budgets (server.zig), a tight staleness window that
measured scheduler latency (keepalive.zig), and an absolute >=50% CPU assert
that assumed the test thread would get a whole core (proc.zig).

The same shapes exist outside the agent lane and are load-sensitive in the
same way:

- `src/remote/connection.zig:3514,4031,5700,5720` — `Thread.yield()` waiters
- `src/remote/inbound_ring.zig:748,770,932` — yield waiters
- `src/remote/tcp_dial.zig:415,476,535` — yield waiters
- `src/remote/client_mux.zig:586`, `src/remote/socket_stream.zig:250` — same
- `src/remote/wp4_e2e.zig` — many fixed `Thread.sleep` waits (lines ~243-730);
  each needs a look: some are poll intervals inside bounded loops (fine), some
  are "sleep then assert" (the flaky shape)
- `src/renderer/State.zig:102-116` — yield loop (check whether it is test-only
  or product code before touching)

Line numbers are as of 2026-08-05; re-grep `Thread\.yield\(` and
`Thread\.sleep\(` under `src/` when picking this up.

**Also audit the second T258 shape: unbounded test-harness reads.** T258 found
that the agent lane's wedge (11 min flat CPU, no failure text) was a test
loopback fifo whose `read` blocks on an untimed `cond.wait` — when the awaited
frame never arrives, the lane hangs instead of failing. The fix was a
`read_deadline_ns` on the client-read direction (`server.zig` ByteFifo, 30s
liveness bound → `error.LoopbackReadTimeout`). The SAME untimed-fifo pattern
exists in the non-agent test harnesses: `src/remote/connection.zig` (test
ByteFifo, ~line 3260) and `src/remote/client_mux.zig` (`TestFifo`, ~line 337);
check `socket_stream.zig` and `wp4_e2e.zig` for the same shape. Bound only the
direction the TEST reads from — a product/server side idling between frames is
the normal state. Also convert unbounded `ResetEvent.wait()` calls in test
bodies to `timedWait` (the WEDGE test's `gate_entered.wait()` was one).

Fix pattern (from T346): wait on the EFFECT with `waitUntil(pred, args)`
(10s liveness bound, 1ms poll), keep the authoritative assert after the wait,
and never assert absolute timing/CPU numbers that assume a quiet scheduler —
assert proportionally to something measured, or against a generous bound.

*Validation:* both `zig build test` lanes (none + win32) green x3 through
`scripts\floor-lane.ps1`, including runs started while an all-core CPU load is
running (T346 used 32 hidden powershell busy-loop processes with a 9-minute
self-cap; see T346's evidence for the incantation).
