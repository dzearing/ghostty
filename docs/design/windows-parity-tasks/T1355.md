# T1355 - The Windows app writes no crash report of its own - a user whose terminal vanishes has nothing to send

## In plain terms

If the terminal disappears on a Mac, it leaves a crash report behind that
someone can look at. On Windows it leaves nothing: the window is gone, the
work in it is gone, and there is no file anywhere that says what happened.
The only person who can currently diagnose one of these is somebody running
the test harness, which is nobody outside this repo.

## Summary

`crash.init` (`src/global.zig`) is called on both platforms and does nothing
on Windows: `src/crash/sentry.zig` opens both `init` and `deinit` with

```zig
if (comptime builtin.os.tag == .windows) return;
```

so the macOS build gets the Sentry native handler writing local reports under
the crash dir (`src/crash/dir.zig`, which the app can already iterate), and
the Windows build gets no handler at all. Platform symmetry says the concept
travels even though the mechanism cannot: the Windows-native equivalent of a
signal-handler crash reporter is `SetUnhandledExceptionFilter` plus
`MiniDumpWriteDump` out of `dbghelp.dll`, writing into the same crash dir.

T527 built the harness-side half of this - `test\win32\lib\GuiPostmortem.ps1`
names a dead process's exit code, correlates the Windows `Application Error`
record, and points at any minidump WER kept. That covers an acceptance run.
It covers nothing a user experiences, because it lives in the test harness and
depends on a process handle the harness held from launch.

## Details

- Where: `src/crash/main.zig` dispatches; add `src/crash/windows.zig` beside
  `sentry.zig` and give `init` a Windows arm rather than an early return.
- The handler must be allocation-free at crash time: resolve and create the
  crash directory during `init` and keep the path in a static UTF-16 buffer,
  then format only a timestamp and a pid at the point of the crash.
- Return `EXCEPTION_CONTINUE_SEARCH` after writing so Windows still applies
  its own default handling and the process still exits with the exception
  code - the number T527's postmortem reads.
- Note the interaction with Zig's own segfault handler: in Debug and
  ReleaseSafe, `std.debug` installs a vectored handler that panics, and a
  vectored handler runs BEFORE the unhandled-exception filter. So this is the
  net for the case that reaches Windows unannounced, which is exactly the
  T527 shape, and it must be tested against a build with no segfault handler.
- WER LocalDumps happens to be armed on the loop's box (confirmed
  2026-09-05), which is why T527's acceptance can assert a dump exists. That
  is a property of this machine and not something a user has, so it is not a
  substitute for the app writing its own.

## Validation criteria

- [ ] A build with no Zig segfault handler, crashed on purpose, leaves a
      minidump and a text report in the crash dir
- [ ] The report names the exception code, the faulting address and the
      thread, and the process still exits with the exception code afterwards
- [ ] The handler costs nothing measurable at startup and allocates nothing
      on the crash path
- [ ] `zig build test -Dapp-runtime=win32` and the `lib` build are green with
      it wired in
