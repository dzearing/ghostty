# T446 - No pending-key-sequence / key-table indicator on Windows: port Mac's KeyStateIndicator pill

## In plain terms

Ghoztty lets you bind multi-key shortcuts - press one combination, then a
second key finishes the command - and lets a binding switch you into a named
"key table" where the keyboard temporarily means something else. On Windows
neither of those states shows up anywhere. You press the first half of a
shortcut and the terminal looks exactly as it did a second ago, so there is
no way to tell whether it is waiting for you, or whether you are stuck in a
mode you did not mean to enter. On a Mac a small floating pill appears over
the pane showing which keys you have pressed so far and which table you are
in.

## Goals

- [x] A pending multi-key sequence is visible while the terminal waits for
      the next key, and clears when the sequence completes or is abandoned
- [x] An active key table is named on screen for as long as it is active,
      including nested tables
- [x] Geometry asserted at 1.0 / 1.25 / 1.5 / 2.0 scaling, plus an on-box
      acceptance script

## Validation criteria

- [x] A pending sequence shows a pill, and it clears both when the sequence
      COMPLETES and when it is abandoned — sections B/E/F of
      `test/win32/key-state-pill.ps1`, ALL PASS (53 assertions)
- [x] An active key table is named for as long as it is active; nesting adds
      to the pill rather than replacing it, and ONE deactivation leaves the
      outer table still named — sections G/H, same script
- [x] Tables and a pending sequence coexist in one pill (each addition makes
      it strictly wider: 106 → 164 → 238 px measured) — section H
- [x] Per pane, not per window: the pill follows its own pane across a split,
      two panes can each have one, and clearing one leaves the other —
      sections I/J/K/L
- [x] The anchor is the computed one at the window's real DPI
      (`inset - shadowPad`, bottom-centered), and a `-NegativeControl` run
      fails exactly that assertion and nothing else (1 FAILED / 52 passed)
- [x] Card pixels, key caps, divider, dots, and the 4.5:1 / 3:1 contrast
      floors swept over the whole background ramp at 1.0/1.25/1.5/2.0 —
      `key_state_pill.zig` unit tests, `none` lane
- [x] Key-table stack push/pop/clear semantics, including depth past the
      displayable cap and UTF-8-safe name elision — `key_state.zig` unit
      tests, `none` lane
- [x] Standing floor: both `zig build test` lanes, `zig build test-agent`,
      and P1–P3 green

## Summary

Split out of T28 (2026-08-04). The core's `.key_sequence` and `.key_table`
apprt actions are acknowledged no-ops on win32 (`App.zig:4037-4049`), so
both states are invisible here.

## Details

**Mac's version** is `Ghostty.SurfaceView.KeyStateIndicator`
(`macos/Sources/Ghostty/Surface View/SurfaceView.swift:958-1090`), fed from
`SurfaceView_AppKit.swift:828-849`:

- `.key_sequence` appends a `KeyboardShortcut` per pending key and clears
  the array when the sequence resolves (`:828`, `:834`).
- `.key_table` pushes a name, pops one, or clears all (`:845-849`) - so the
  model is a STACK, not a single value, and the pill renders the whole stack
  with chevrons between entries (`SurfaceView.swift:1041-1049`).
- Rendered as a capsule with `.regularMaterial` fill and a 1pt
  `Color.primary.opacity(0.15)` border, 12pt horizontal / 6pt vertical
  padding, positioned at the pane's bottom by default.
- The keyboard glyph is `keyboard.badge.ellipsis`; pending keys render as
  `KeyCap` views followed by an animated `PendingIndicator` ellipsis.
- It is DRAGGABLE between the pane's top and bottom edge (50pt threshold,
  `SurfaceView.swift:1008-1027`), and the position is view state - it does
  not persist.

**Scope call to make and record.** The drag-to-reposition and the spring
animations are the parts most likely not to earn their keep on Windows. The
information (which table, which keys, still waiting) is the feature; the
draggability is a Mac interaction habit. Recommend shipping a fixed
bottom-centered pill first and filing a decision
(`parity-decisions.ps1`) on whether drag-to-top follows, rather than
skipping it silently - a flag that exists on one platform and not the other
is the divergence this project does not ship, but an *interaction* with no
Windows idiom is a legitimate translation.

**Design system is mandatory** (`docs/design/win32-design-system.md`): the
pill is a card (radius 8, elevation rules), spacing on the 4 DIP scale,
>= 4 DIP off the pane edge, 3:1 for the border and any glyph, 4.5:1 for the
key text. Numbers go in a pure geometry module and are asserted at 1.0,
1.25, 1.5 and 2.0. Glyphs are filled shapes, never `LineTo` strokes.

**Landmarks.** `BannerOverlay.zig` is the closest existing per-pane overlay
and `banner_card.zig` its paint; `overlay_zorder.zig` owns stacking and the
pill must be slotted in relative to the banner (they can be on screen at the
same time). The keycap rendering has no win32 counterpart yet - expect a
small `key_cap.zig` paint helper. State lands on `Surface.zig` (a key-table
stack plus a pending-sequence list), driven from the `.key_sequence` /
`.key_table` arms in `App.zig` that currently fall through to `return true`.

*Validation:* unit tests for the geometry module and for the key-table
stack's push/pop/clear semantics at the four scales; an on-box acceptance
script in `test/win32/` that configures a two-key binding, presses the first
half, and asserts the pill appears and then clears. Both `zig build test`
lanes, `zig build test-agent`, and P1-P3 stay green.

## What landed

Three new files, split the way the design system asks (numbers in a pure
module, asserted at four scales; the OS half owns only the window):

- `src/apprt/win32/key_state.zig` — the MODEL. The key-table stack (push /
  pop / clear-all) and the pending-key list, fixed-capacity and allocator-free
  because it is driven from the key handler. Key labels go through
  `menu_label.formatTrigger`, the same formatter the menus use, so a chord
  reads identically wherever the app prints it. Two details worth keeping: the
  stack's true DEPTH is counted past the names it retains (a pop after an
  overflowing push has to land back where it came from), and a name too long
  for its slot is elided at a UTF-8 boundary rather than sliced mid-codepoint.
- `src/apprt/win32/key_state_pill.zig` — geometry, colors and card pixels.
  Bottom-centered card, radius 8, everything on the 4 DIP scale, WCAG 4.5:1 on
  every label and 3:1 on the border, the divider, the chevrons and the dots,
  swept over the whole background ramp. When the content will not fit, the KEY
  section keeps its natural size and the table names shrink proportionally —
  a chord you are halfway through is the urgent half of the message.
- `src/apprt/win32/KeyStateIndicator.zig` — a `WS_EX_LAYERED` popup on the
  read-only badge's `UpdateLayeredWindow` per-pixel-alpha path, but
  `WS_EX_TRANSPARENT` (unlike the badge): the pill is pure information sitting
  where a selection drag ends, so it must not eat mouse input. The waiting
  dots animate off a `WM_TIMER` that is alive only while a sequence is
  actually pending.

Wiring: the `.key_sequence` / `.key_table` arms in `App.zig` (which were a
bare `return true`), `Surface.updateKeyStateIndicator` driven from the STATE
rather than the action, and `Window.updateKeyStateIndicators` on the layout
pass — the same triple the read-only badge uses, which is what keeps the pill
glued to its pane across a divider drag, a tab switch and a DPI change.

**Scope call, filed as D31:** shipped fixed at the pane's bottom, not
draggable. Mac's pill can be flung to the top edge; that position is view
state that does not persist even there, the Windows shell has no vocabulary
for a chrome control the user repositions by hand, and making it draggable
means making it clickable — which costs the click-through behavior above.
Everything else is at parity, animation included.

**Two bugs the box found, both invisible to unit tests:**

1. `for (1..l.table_count)` in the text pass **underflowed** when a pending
   sequence had no key table — Zig lowers a for-range to a counted loop over
   `end - start`, so `for (1..0)` panics with "integer overflow". That is the
   single most common state this feature has, and it crashed the app on the
   first key of every chord. Now an explicit `while`, with the reason written
   next to it.
2. **F10 never reaches the core on Windows** — `handleKeyEvent` claims it for
   the menu system before `keyCallback`. The first draft of the acceptance
   script used `f9>f10` for exactly the reason a user would, and the menu then
   swallowed every key after it. Filed as **T575**; the script uses `f5>f6`
   and names the trap.

Also filed: **T576** (Mac's pill has a popover explaining what a key table
is; ours has nothing to click).
