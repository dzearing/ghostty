# T446 - No pending-key-sequence / key-table indicator on Windows: port Mac's KeyStateIndicator pill

## In plain terms

Ghoztty lets you bind multi-key shortcuts - press one combination, then a
second key finishes the command - and lets a binding switch you into a named
"key table" where the keyboard temporarily means something else. On Windows
neither of those states shows up anywhere. You press the first half of a
shortcut and the terminal looks exactly as it did a second ago, so there is
no way to tell whether it is waiting for you, or whether you are stuck in a
mode you did not mean to enter. On a Mac a small floating pill appears over
the pane showing which keys you have pressed so far and which table you are
in.

## Goals

- [ ] A pending multi-key sequence is visible while the terminal waits for
      the next key, and clears when the sequence completes or is abandoned
- [ ] An active key table is named on screen for as long as it is active,
      including nested tables
- [ ] Geometry asserted at 1.0 / 1.25 / 1.5 / 2.0 scaling, plus an on-box
      acceptance script

## Summary

Split out of T28 (2026-08-04). The core's `.key_sequence` and `.key_table`
apprt actions are acknowledged no-ops on win32 (`App.zig:4037-4049`), so
both states are invisible here.

## Details

**Mac's version** is `Ghostty.SurfaceView.KeyStateIndicator`
(`macos/Sources/Ghostty/Surface View/SurfaceView.swift:958-1090`), fed from
`SurfaceView_AppKit.swift:828-849`:

- `.key_sequence` appends a `KeyboardShortcut` per pending key and clears
  the array when the sequence resolves (`:828`, `:834`).
- `.key_table` pushes a name, pops one, or clears all (`:845-849`) - so the
  model is a STACK, not a single value, and the pill renders the whole stack
  with chevrons between entries (`SurfaceView.swift:1041-1049`).
- Rendered as a capsule with `.regularMaterial` fill and a 1pt
  `Color.primary.opacity(0.15)` border, 12pt horizontal / 6pt vertical
  padding, positioned at the pane's bottom by default.
- The keyboard glyph is `keyboard.badge.ellipsis`; pending keys render as
  `KeyCap` views followed by an animated `PendingIndicator` ellipsis.
- It is DRAGGABLE between the pane's top and bottom edge (50pt threshold,
  `SurfaceView.swift:1008-1027`), and the position is view state - it does
  not persist.

**Scope call to make and record.** The drag-to-reposition and the spring
animations are the parts most likely not to earn their keep on Windows. The
information (which table, which keys, still waiting) is the feature; the
draggability is a Mac interaction habit. Recommend shipping a fixed
bottom-centered pill first and filing a decision
(`parity-decisions.ps1`) on whether drag-to-top follows, rather than
skipping it silently - a flag that exists on one platform and not the other
is the divergence this project does not ship, but an *interaction* with no
Windows idiom is a legitimate translation.

**Design system is mandatory** (`docs/design/win32-design-system.md`): the
pill is a card (radius 8, elevation rules), spacing on the 4 DIP scale,
>= 4 DIP off the pane edge, 3:1 for the border and any glyph, 4.5:1 for the
key text. Numbers go in a pure geometry module and are asserted at 1.0,
1.25, 1.5 and 2.0. Glyphs are filled shapes, never `LineTo` strokes.

**Landmarks.** `BannerOverlay.zig` is the closest existing per-pane overlay
and `banner_card.zig` its paint; `overlay_zorder.zig` owns stacking and the
pill must be slotted in relative to the banner (they can be on screen at the
same time). The keycap rendering has no win32 counterpart yet - expect a
small `key_cap.zig` paint helper. State lands on `Surface.zig` (a key-table
stack plus a pending-sequence list), driven from the `.key_sequence` /
`.key_table` arms in `App.zig` that currently fall through to `return true`.

*Validation:* unit tests for the geometry module and for the key-table
stack's push/pop/clear semantics at the four scales; an on-box acceptance
script in `test/win32/` that configures a two-key binding, presses the first
half, and asserts the pill appears and then clears. Both `zig build test`
lanes, `zig build test-agent`, and P1-P3 stay green.
