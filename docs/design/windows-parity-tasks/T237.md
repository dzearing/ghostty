# T237 - CLOSE_SESSION RPC times out against the local agent (1.5s, no reply) even though both peers negotiate the capability

## Summary

Found 2026-07-31 while building T230. The first implementation of the `notify`
relaunch policy retired the dead tombstone it was replacing with the BOUNDED
RPC `Connection.closeSession(sid, 1500ms)`. On box, against the local
`ghoztty-agent`, it timed out **every time**:

```
info(io_remote): notify policy: could not retire dead session err=error.Timeout (harmless)
info(io_remote): notify policy: could not retire dead session err=error.Timeout (harmless)
```

(two panes, two timeouts, same run — `src/termio/Remote.zig`, since replaced by
the fire-and-forget `closeSessionNoWait`).

`error.Timeout` — not `error.Unsupported` — means the capability gate
(`supportsCloseSession`) said **yes**: both HELLOs advertised `close_session`,
the frame went out, and no `CLOSE_SESSION_RESULT` came back within 1.5 s. So
either the agent is not replying, is replying on a channel the client is not
correlating on, or the reply is slower than 1.5 s.

T230 does not need the answer (it now sends the request fire-and-forget, which
is the right shape for housekeeping on a pane's bring-up path either way), so
this is filed rather than fixed. But it matters on its own: the same RPC is what
the machine chooser's session **Kill** is built on (T146), and there it IS
load-bearing — a Kill that hangs for its whole timeout, or reports failure while
the session actually dies, is a bad affordance.

## What to check

1. Does the agent even reach `handleCloseSession`?
   (`src/remote/agent/server.zig`) It looks correct on inspection — it answers on
   `frame.channel` in every arm, including the malformed-payload one — so
   instrument the agent and confirm the frame ARRIVES.
2. Channel correlation. `closeSession` picks a random `req_channel` and
   `rpcCall`s `.close_session` → `.close_session_result`
   (`src/remote/connection.zig`). Confirm the agent's reply channel is the
   REQUEST channel and that the client's pending-RPC table is keyed the same
   way (`requestSessions`/`relaunch` use the same shape and do work).
3. Timing. `handleCloseSession` does `freeUnlinked` + `persistMeta` +
   `reapLayouts`/`persistLayouts` before replying — all synchronous, all under
   or around the store lock. Measure it; if a sessions.json write can exceed
   1.5 s the fix is to reply first and persist after.
4. Whether the tombstone is nevertheless being freed (i.e. the request works and
   only the REPLY is lost). That distinction decides whether this is a wire bug
   or a liveness bug.

## Validation

- A test that drives `closeSession` against a real agent and asserts it returns
  `ok` within a sane bound, in the none-runtime or agent lane — the existing
  coverage clearly does not exercise the local-agent transport this way.
- On box: after a `notify` restore, `ghoztty +sessions --json` must NOT
  accumulate one dead tombstone per pane per agent restart.
