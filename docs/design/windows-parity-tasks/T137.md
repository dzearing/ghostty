# T137 — --session-persistence=off is silently rejected on the CLI

## In plain terms

The docs tell you to turn session persistence off by writing
`session-persistence = off`. Write exactly that and Ghoztty ignores it and
leaves persistence **on** — no message, no warning, the opposite of what you
asked for. Only the undocumented spelling `false` actually works. After this
lands, `off` and `on` (and `yes`/`no`) mean what they look like everywhere a
setting takes a yes/no answer, and a value Ghoztty genuinely cannot understand
says so in a dialog instead of quietly keeping the old setting.

## Goals

- [x] `off`/`on` and `no`/`yes` are accepted anywhere a true/false setting is
      accepted, on both platforms
- [x] a genuinely bad value for a real setting is surfaced at startup, not
      swallowed
- [x] unit tests pin exactly which spellings are accepted and which are errors
- [x] `config-errors.ps1` covers both the accepted spelling and the rejected
      value
- [x] T414 (the duplicate filed from T118) is closed against this work

## Resolution (2026-08-04) — option (a), in the shared parser

`cli/args.zig` `parseBool` now accepts `on`/`off` and `yes`/`no` alongside
`1 t T true` / `0 f F false`. It lives in the Zig core, so this is one change
for both seats — the platform-symmetric answer, and the one that makes the
documented spelling true rather than rewriting the docs to match an
implementation accident.

Option (b) — fix every doc to say `true`/`false` — was rejected. `off`/`on` is
the vocabulary the docs, the tracker and the user all reach for on a switch,
and a parser that rejects it will be tripped over again by the next person who
writes what reads naturally. The change is **purely additive**: no spelling
that parsed before changes meaning.

Checked before widening it:

- No config `packed struct` has a field named `on`, `off`, `yes` or `no`
  (`FontSyntheticStyle`, `ShellIntegrationFeatures`, `AppNotifications`,
  `FreetypeLoadFlags`, `ScrollToBottom`, …), so `= off` on one of those now
  clears the whole set instead of being `error.InvalidField` — strictly more
  sensible, and nothing that parsed before moved.
- The two `parseBool`-then-enum fallbacks (`BackgroundBlur`,
  `WindowDecoration`) have no `on`/`off`/`yes`/`no` tag either.
- The parser stays case-sensitive apart from the pre-existing `T`/`F`. `On`,
  `OFF`, `True` are still errors; widening that is a separate decision and is
  pinned as such by the new test.

### The second half: a bad value was already loud on Windows

The task asked whether an invalid value for a *known* key surfaces. It does —
`args.parse` records it in `_diagnostics` (`args.zig:174`) whether it came from
a file or the command line, `Config.load` runs both through the same list, and
win32's `showConfigErrorsIfAny` (T69) raises the Configuration Errors dialog at
startup. That was never pinned by a test for the **CLI** path, which is where
this defect bit; it is now.

### Evidence, on the box

`zig-out\bin\ghoztty.exe`, Debug, win32, built from this change:

```
session-persistence = off    -> no diagnostic
session-persistence = on     -> no diagnostic
session-persistence = no     -> no diagnostic
session-persistence = yes    -> no diagnostic
session-persistence = nope   -> probe.conf:1:session-persistence: invalid value "nope"
```

`--session-persistence=off` starts with no dialog; `--session-persistence=nope`
raises the Configuration Errors dialog and the app stays up.

- `test\win32\config-errors.ps1` — **ALL PASS (27 assertions)**, up from 19;
  the eight new ones are case 4. Oracle is the diagnostic TEXT, never the exit
  code: `$LASTEXITCODE` after a native command in a PS 5.1 pipeline reported 1
  for a clean `+validate-config` that exits 0 through `cmd.exe`.
- `none` lane: two new tests — `parseBool: the exact accepted set` (the whole
  contract, accepted and rejected) and the `on`/`off` additions to
  `parseIntoField: bool` and `parseIntoField: packed struct true/false`.

## Summary

**`--session-persistence=off` is silently rejected on the CLI** (doc/impl mismatch). CLAUDE.md and the tracker both document the setting as `session-persistence = off\|on`, but the config bool parser takes `true`/`false` only: `ghoztty --session-persistence=off` produces a config error that is swallowed at startup and the default `true` stays in force — the app restores the previous layout anyway. Found 2026-07-28 in T131 (the pane-banner harness used `=off`, saw restore happen regardless, and only worked once switched to `=false`). A user following the documented spelling gets the opposite of what they asked for, silently, which is the worst failure mode for a persistence switch. Decide and implement one of: (a) accept `on`/`off` (and `yes`/`no`) in the bool parser — check what Mac's parser accepts first, since config syntax is shared, (b) keep the parser and fix every doc to say `true`/`false`. Either way a bad config VALUE for a known key should surface (startup config-error dialog, like `config-errors.ps1` covers) rather than being swallowed. Validation: extend `config-errors.ps1` with the rejected-value case + whichever spelling is chosen

## Second sighting, 2026-07-31 (T234) — it costs an hour every time

`test/win32/tab-strip-autohide.ps1` launched with `--session-persistence=off`
and `Focus-TestWindow` then returned **false forever**: 5 attempts, 2 s apart,
against a window with a perfectly good visible pane. Every keyboard-driven
assertion in the script was unrunnable. Switching the one flag to
`--session-persistence=false` made it pass first try — no other change.

So the symptom is not only "the layout gets restored anyway". Persistence
staying on silently routes the pane's shell through the local agent, and on the
background test desktop that window never becomes focusable. **A swallowed bad
value for a known key turns into a completely unrelated-looking harness
failure**, which is the second time this exact flag has burned a session
(T131 was the first).

`caption-bar.ps1` was still passing `=off` in two places and has been corrected
to `=false` as part of T234. Worth grepping the whole `test/win32/` tree for
`=off` when this task is picked up.
