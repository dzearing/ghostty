# T400 - Viewer: a pending live-reload debounce timer survives navigation and re-fetches the new page

## In plain terms

A viewer pane watches the file it is showing and re-renders it a fraction of a
second after you save. If you save and then immediately open something else in
that pane — a website, another document — the pending re-render used to go
ahead anyway, aimed at whatever you just opened. You would see the new page
load, and then load a second time on its own. Nothing was lost, but the pane
did work nobody asked for on a page that had nothing to do with the file you
saved. After this, leaving a document cancels its pending re-render.

## Goals

- [x] Navigating a viewer pane away from a file cancels any debounce that
      file's watcher already armed.
- [x] The same holds for leaving a document by following an in-page link to a
      website, not just by typing in the address bar.
- [x] Covered by the real-WebView2 host-floor test, with the fix's removal
      verified to turn it red.

## Validation criteria

- [x] Host-floor test asserts nothing is armed on the pane's window the instant
      a navigation away returns, with a positive control proving the watcher's
      message does arm one — `zig build test -Dapp-runtime=win32
      -Dtest-filter="host floor"`, exit 0.
- [x] Mutation (drop the `KillTimer` from `syncWatcher`) turns that assertion
      red — run twice, `expected 0, found 1` both times.
- [x] Standing floor green: all three zig lanes via `scripts\floor-lane.ps1
      -Lane all`, and `test\win32\ipc-p1/p2/p3.ps1` ALL PASS.

## Summary

Found while building T391, not by it: `syncWatcher` stops the WATCHER on every
navigation but nothing kills the debounce `WM_TIMER` the watcher may already
have started. A save that lands within ~100ms of the user navigating away
leaves a timer armed on the pane's host window, and when it fires
`reloadContent` runs against wherever the pane went — for a web destination
that is `refetchFromOrigin`, an unrequested cache-bypassing re-fetch of a page
the user just opened.

Small and narrow (a 100ms window, and the worst case is one redundant load),
which is why it is a task rather than a hold on T391. The fix is one line in
`ViewerPane.syncWatcher`: `_ = w32.KillTimer(hwnd, reload_timer_id)` alongside
the `watcher.stop()`, so leaving a document cancels its pending render the same
way Mac's `reloadDebounce?.cancel()` does.

## Validation

Unit lane, in the real-WebView2 `host floor` test: arm the timer by posting
`WM_APP_VIEWER_RELOAD` at the pane, navigate to the loopback page WITHOUT
pumping, then pump past the debounce and assert `ReloadPage.requests` did not
advance beyond the navigation's own fetch. The mutation is removing the
`KillTimer` again.
