# T425 - The dead session's recorded command and cwd never reach the fresh shell: no 'Previous command' line and the pane opens in the wrong directory

## SPLIT (2026-08-03) - read this first

This task was filed with **two** symptoms of one user report, and with an
explicit instruction: *"Split this task the moment the two stop sharing a
cause."* They stopped. Measured on box, they are different mechanisms:

| symptom | recorded? | cause | owner |
|---|---|---|---|
| last known **cwd** not restored | YES, at spawn | never refreshed afterwards | **T425** (this file) |
| no **previous command** line | NO, never, for any session | the label is recorded only from `OPEN.command`/`OPEN.shell`, and a plain win32 GUI pane sends neither | **T429** |

What separates them is one file — the live agent's `sessions.json`, where every
session carries a `cwd` and **not one carries an `argv`**. A single shared cause
does not produce that asymmetry.

So T425 keeps the cwd half and is **done**; **T429** carries the command half,
which also needs a design decision (recording the resolved shell would print
`previous command: C:\WINDOWS\system32\cmd.exe` — worse than silence) and an
additive change to the app<->agent wire.

The section below is the ORIGINAL filing, kept for its reasoning. Its
"suspected root cause" (that `outcome.argv` and `outcome.cwd` are both null) is
half right: argv is null, cwd is not.

## Summary

**User report, 2026-08-03**: *"I expected 'Previous prompt:' to be preserved
and the last known CWD to be restored in the shell."*

Both symptoms, one suspected root cause, which is why they are one task: the
notify path reads **both** values off the same tombstone, at
`src/termio/Remote.zig:568-572`:

```zig
notice_command = if (outcome.argv) |v| aa.dupe(u8, v) catch null else null;
const cwd: ?[]const u8 = if (outcome.cwd) |c| ... else self.working_directory;
```

The code is already written to do what the user expects — the notice names the
command when there is one (`session_notice.format`, "previous command:") and
the fresh shell is placed in the dead session's recorded directory. CLAUDE.md
documents exactly that. The user's screenshot shows the notice with **no
previous-command line at all**, and reports the shell came up in the wrong
directory. So the likely failure is upstream of this file: `outcome.argv` and
`outcome.cwd` are both null.

**Split this task the moment the two stop sharing a cause.** They are filed
together only because one `outcome` feeds both; if argv is present and cwd is
not (or vice versa) they are separate bugs and deserve separate files.

## Where to look

- `src/remote/agent/server.zig:757` already comments on a case where cwd was
  *"never written to `sessions.json`"* — start there.
- `server.zig:3395`, `test "RELAUNCH respawns in the RECORDED cwd, not the
  agent's (T132)"`, proves the RELAUNCH verb honors a recorded cwd. **Notify is
  not relaunch** — it opens a brand-new session — so that test passing tells us
  nothing about this path, and the gap between them may be the bug.
- Whether the agent that served this upgrade was an OLDER build than the app
  (the standing agent-contract hazard): an agent too old to report argv/cwd
  degrades to null here, which would be correct-by-design rather than a bug,
  and would change the fix to "make the app say so" instead.

## Read T421's log evidence first

The 2026-08-03 upgrade log records `pre-kill agent sessions: 0` and
`SESSIONS-SURVIVE SKIP: no agent sessions before the kill`. A null argv and a
null cwd are the *expected* output of a restore with nothing persisted behind
it — so this may not be a bug in `Remote.zig` at all, but the downstream
symptom of an agent that held no sessions. Establish which before touching the
notice path; **T422** carries the same caveat and the same contradiction (the
notice only fires for a tombstone, so something was there).

## On the wording

The user wrote *"Previous prompt:"*; the code writes `previous command:`. Treat
that as the user naming the field loosely rather than a rename request — but
the label is user-visible text on the same surface **T424** is rewording, so
settle it there in one pass rather than twice.

## Validation

`test\win32\session-relaunch-notify.ps1` extended: a pane whose session had a

come back with the command named in the notice and the shell's `cd`/`pwd`

## Root cause (2026-08-03, VERIFIED by reading the code and the box)

The recorded cwd was **write-once**. `handleOpen` (`server.zig:762`) does
`if (open.cwd) |c| s.setCwd(c)` at spawn and nothing ever writes it again —
`handleGetCwd` (`server.zig:1156-1187`) reads the child's *live* directory on
demand for new splits, replies with it, and **discards it**. So a pane the user
had `cd`'d out of came back where the shell STARTED.

That the value was recorded at all is why this reads as "the wrong directory"
rather than "no directory": `D:\git\ghoztty` is a perfectly plausible answer,
just not the user's answer. The one session on this box that had been opened
from the GUI with no explicit directory recorded `C:\Users\David` — home — and
would restore there no matter where its user had worked.

The `pre-kill agent sessions: 0` lead from the filing turn is a dead end, as
T421 established: the upgrade script was asking a **debug**-lineage agent; the
release agent held four sessions, all with a cwd.

## What shipped (2026-08-03)

- **`SessionStore.refreshCwds()`** (`session.zig`) — samples every LIVE session's
  current directory from its child and updates the record, so the value that
  outlives the agent is where the user IS, not where the shell was spawned.
  Wired into the existing reaper tick on its own **10-second cadence**
  (`cwd_every_ticks`), separate from the 30s ring snapshot because it is a
  different kind of cost (an OS query per session vs. a disk write) and wants
  its own dial. `persistMeta` runs only when something actually changed, so an
  idle box does no periodic writing.
- **The OS query runs OUTSIDE the store mutex**, unlike the neighbouring
  foreground-pid sampler. That sampler's vtable contract is explicitly "a cheap
  single non-blocking syscall"; a cwd read is not one (a cross-process PEB read
  on Windows), and holding the lock across it would stall every OPEN/ATTACH/DATA
  frame behind a directory read. Same collect-then-act shape `handleGetCwd` and
  `reapIdle` already use: snapshot `(id, child)` locked, query unlocked,
  re-look-up **by id** before writing — a concurrent CLOSE can free the session
  while we are unlocked, so the pointer we started from must not be reused.
- **A failed query keeps the last known value.** Forgetting it is strictly worse
  than a stale one: with no recorded cwd the respawn inherits the AGENT's
  directory — `C:\WINDOWS\system32` on the win32 autostart path, which is the
  T132 failure this record exists to prevent. Dead sessions are skipped
  entirely, not queried: their child is gone and their recorded cwd is exactly
  what the notify restore is about to use.

## Evidence (2026-08-03)

- **`test\win32\session-relaunch-notify.ps1` arm D (new) — ALL PASS (56), exit 0.**
  A pane is opened in one directory, the shell is driven into a deeper one, and
  the arm asserts on the two things that matter: **D5**, the agent's own

  restart works from, so it is the thing that was broken); and **D9**, after the
  app AND agent are killed and the app relaunched, the restored fresh shell

- **Unit tests** (`session.zig`, agent lane): the recorded cwd follows the child
  and reaches `sessions.json`; a dead session is never queried and keeps its

## Still open, deliberately

The refresh tracks the **shell's** directory. A pane sitting inside a
long-running foreground program that changed its own cwd is not represented —
the shell is where a fresh shell should land, so that is the right answer here,
but it is an assumption worth naming rather than discovering later.
