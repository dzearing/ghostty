# T298 - Activity Monitor: per-card live metrics for INACTIVE machines (Mac's MachineMetricsProbe)

## Summary

**The deliberately deferred half of T296**, named here rather than left as a
silent scope cut. T296 shipped the carousel — Local first, every registered
machine after it, one click to switch, arrows that never dial. What it did NOT
ship is what Mac paints on the cards it is not currently showing: a live status
dot, uptime, and a `CPU n% · Mem n%` readout for EVERY registered machine at
once.

Mac gets that from `MachineMetricsProbe`
(`RemoteActivityMonitorView.swift:153-155`, wired at :227-262): it **dials every
registered machine** and subscribes each one's metrics stream for the panel's
whole lifetime. Windows has no equivalent anywhere — verified by reading
`src/apprt/win32/`: no probe exists, and the chooser's rows carry no metrics
either.

## What T296 does instead, and why it is not a lie

An inactive card reports the relay directory's own `online` flag and says
exactly that — `online` / `offline`, with a neutral dot for offline. It does not
print a CPU or memory number it does not have. `activity_cards.State` has a
fourth state, `.idle`, for precisely this: "we are not connected to this
machine". The ACTIVE card is live (it is the panel's own source).

So the gap is missing INFORMATION, not wrong information — which is the only
form of gap worth shipping.

## Why it is its own task

It is a connection-budget design, not a paint pass. N registered machines means
N relay dials (TCP + TLS + WebSocket upgrade + HELLO) plus N metrics
subscriptions, held open for as long as the panel is open, on a **non-modal**
window the user may leave up for hours. Every one of them is a thread, a
teardown path, and a failure mode. Questions this task has to answer, none of
which T296 needed:

- What is the cap, and what happens past it (Mac probes all of them)?
- Do probes stop when the panel is minimized? (T290 asks the same question about
  the process enumerator — the answers should agree.)
- Does a probe dial share anything with the panel's own dial, or is the active
  machine simply excluded from the probe (Mac excludes it by preferring `host`)?
- What does a probe failure do to the card — `unreachable` forever, or a retry
  with backoff?
- Teardown ordering against `close`/`switchTo`, which already has the
  unsubscribe-then-join-then-free rule for ONE connection and would now need it
  for N.

## Details

Land it behind the existing model: `activity_cards.Summary` already carries
`state`/`uptime_s`/`cpu_pct`/`mem_used`/`mem_total`, and
`ActivityMonitor.cardSummary` already picks live-for-active vs directory-flag
for the rest. The probe fills in the non-active branch; nothing in the painter
or the layout has to change.

## Validation

- Both `zig build test` lanes plus `zig build test-agent` green; P1-P3 ALL PASS.
- `test/win32/activity-monitor-remote.ps1`: an inactive card shows a live
  uptime/CPU readout for a machine the panel is NOT showing (assert on the
  carousel log line, which already reports per-card state).
- Closing or switching the panel tears down every probe connection — assert on
  the agent's connection count, not on pixels.
- A machine that refuses the dial paints `unreachable` and does not retry in a
  tight loop.
