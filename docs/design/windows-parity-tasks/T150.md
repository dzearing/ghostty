# T150 — Runtime background-color changes are not accessibility-safe on Windows

## Summary

**Runtime background-color changes are not accessibility-safe on Windows.** `c3e9999e7` (single-pass, accessible runtime background changes) and `752f3178a` (stop the background-color picker flipping panes to white) have ZERO references. Win32 got the T67 tint and the T120 random-tint fix but not the single-pass accessible recompute, so a live background change can leave foreground/selection/cursor contrast below the WCAG 4.5 floor the Mac now guarantees. Port the single-pass recompute and add a contrast assertion to the T67 validation

## User directive, 2026-07-31 (raises this task's priority)

Verbatim, in the context of the right-click context menu (**T240**): *"within
that i should be able to change the bg color, which involves color picker as
well, plus a bunch of logic for remapping foreground colors to adapt"*

This names the exact deliverable and confirms it is user-facing, not internal
hygiene. Three parts, and the third is the one with no Windows implementation:

1. **The menu row exists.** `context_menu.zig` ships `Background Color...`
   (`Id.bg_color`), handled locally in `Surface.zig:3006` rather than through a
   binding.
2. **The picker exists** on that path (win32 `ChooseColor`).
3. **The adaptation does not.** Mac's `c3e9999e7` recomputes the derived colors
   — foreground, selection, cursor, and the tinted chrome — in a SINGLE pass
   from the new background, so contrast floors hold at the moment the color
   changes. Windows just sets the background. Pick a dark blue and the
   foreground can land below 4.5:1 with no correction; `752f3178a` (the Mac fix
   for the picker flipping panes to white) has no Windows analog either.

So the user's *"a bunch of logic for remapping foreground colors to adapt"* is
precisely the missing `c3e9999e7` port. Note the menu row makes this reachable
in one click from every pane, which is why an unadapted recompute is a visible
defect rather than a theoretical one.

**Contrast floors** now live in `docs/design/win32-design-system.md` §2.3 and
apply here: 4.5:1 for text, 3:1 for chrome glyphs and meaningful boundaries,
re-checked after every runtime color change rather than assumed.

## Validation

- Port the single-pass recompute; a background change updates foreground,
  selection, cursor and chrome tint in ONE pass (no intermediate frame where
  the pane is white or the text is unreadable — that is `752f3178a`'s bug).
- Unit tests over the recompute (pure color math, `color_math.zig` lane): for a
  spread of backgrounds across the whole lightness range, every derived color
  clears its floor from §2.3.
- On box: open the picker from the right-click menu (needs **T240** for the
  menu to be reachable under mouse reporting), pick several extreme colors
  including near-black, near-white and a saturated mid-tone, and assert the
  measured on-screen contrast for text, selection and cursor in each.

## Outcome

Done. `applyBackgroundTint` already did bg + contrast foreground + ANSI 0–15
under one mutex hold, so the single-pass property held; three things were
missing or wrong underneath it.

1. **Palette 16–255 was never revisited**, so 256-color content kept the old
   background's lightness. Regenerated in the same hold via
   `terminal.color.generate256Color(..., harmonious)`, base 16 kept as
   adjusted (Mac `ghostty_surface_regenerate_palette`). Measured: index 250
   on `#f0f0f0` goes 1.67:1 → **10.6:1**.
2. **Truecolor was beyond every palette.** Push `min_contrast = 3.0` to the
   renderer (`color_math.runtime_min_contrast`) so the shader adjusts per
   cell at draw time; the hue-preserving `contrasted_color` was already
   shared. Measured: `230,230,230` renders as `138,138,138` = **3.03:1**,
   against a `minimum-contrast` default of 1.
3. **Two sub-floor holes in the color math itself**, both found by sweeping
   the whole lightness range rather than handpicking themes:
   `contrastForeground` chose its side by Rec.601 lightness, which put
   `#777777` on white at 4.42:1 (black gives 4.76:1) — now chosen by
   contrast, worst case 4.58:1 for any background; and `contrastAdjusted`
   only ever searched away from the background, returning a still-failing
   color when a saturated entry clamps against the gamut — now tries the
   other side, then falls back to black/white. Both holes exist in the Mac
   code this was ported from: **T247**.

Selection and cursor are covered by the fg/bg pair rather than separately:
with nothing configured the renderer derives selection as a straight fg/bg
swap and the cursor as the foreground (`renderer/generic.zig:2892`, `:2590`),
so both move in the same pass — asserted, not assumed, in the scheme test.

Evidence:

- `zig build test -Dapp-runtime=none` / `-Dapp-runtime=win32` / `test-agent`
  green; `zig build -Dapp-runtime=win32 -Doptimize=Debug` links.
- New `test/win32/color-contrast.ps1` (+ `lib/paint-blocks.ps1`): **ALL PASS
  (14)**. Screen-pixel oracle — none of this shows in `+list --json`.
- `test/win32/window-color.ps1` (T67) still ALL PASS (14); P1–P3 ALL PASS.

Three false-green traps found and fixed inside that new script, each of which
had it passing while proving nothing: a **block glyph cannot test minimum
contrast** (`renderer/cell.zig:noMinContrast` exempts graphics elements on
purpose); **ConPTY reports a row count the app does not render** (66 vs ~53),
so band arithmetic aimed the probe into the neighbouring band; and
**`+new-window --target=` is idempotent against a PERSISTED session**, so from
the second run on it focused the previous run's pane and read its pixels —
**T248** spreads that last fix to the other acceptance scripts.
