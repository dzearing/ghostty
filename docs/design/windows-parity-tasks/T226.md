## Summary

**Windows has no Activity Monitor at all.** Mac has a whole feature; win32 has
zero lines of it. T177 files the missing *button* in the chooser's detail row;
this task is the *panel that button opens*, which was never filed anywhere.

Filed 2026-07-31 from a user directive, verbatim intent: *"prioritize the new
window parity and activity viewer immediately next ... If you haven't even
built the activity monitor, then you don't have parity with the dialogue in the
MacOS app."*

T177 said to trace the Mac side first and fold this into T146 if it turned out
to depend on cross-machine session browsing. **That tracing is done and it does
NOT** - the panel is process/metrics monitoring, structurally independent of
T146's session browse/resume. So it is its own task, T177 becomes its entry
point, and T146 stays about sessions.

## What Mac actually has

`macos/Sources/Features/Remote/RemoteActivityMonitor.swift` (presentation +
window registry) and `RemoteActivityMonitorView.swift` (model + view):

- **One non-modal window per source**, keyed by `MonitorSource` (`.local` or
  `.remote(Machine)`) in a registry, so a second open FOCUSES the existing
  panel instead of duplicating it. Close always calls `model.stop()` exactly
  once, so connections never leak.
- **Three entry styles.** `presentReusing` (rides a remote window's existing
  `RemoteConnection`, does not own it), `presentDialing` (dials a fresh
  connection off-main and owns it - this is what the chooser's Activity button
  calls, `MachineChooserView.swift:1488`), `presentLocal` (in-process, no
  connection).
- **An in-panel machine switcher** (the card carousel): once open, the panel
  can move to any other source, dialing/freeing owned connections, WITHOUT
  opening a second window. The registry governs only the initial open.
- **Header gauges**: CPU and memory trend charts (`TrendGaugeView`, Swift
  Charts, with a non-Charts fallback path).
- **A selectable process table**: pid, name, CPU% per core, memory, command.
- **A control bar**: filter field at the top, plus actions.
- **Process control**: Kill (with a confirm sheet, multi-select aware) and a
  "New Process" sheet (command + optional working directory).
- **Failure states**: a "Couldn't connect" card and an error banner.
- Also reachable from the Mac command palette
  (`TerminalCommandPalette.swift:188`, `openFromPalette`).

## The good news: the data plane is already cross-platform

This is not a from-scratch port. The backend is shared Zig and **already has
Windows implementations** - verified by reading the source, not assumed:

| module | Windows path |
|---|---|
| `src/remote/agent/metrics.zig` | `sampleWindows` - `GetSystemTimes` + `GetSystemInfo` |
| `src/remote/agent/proc.zig` | `sampleWindows` - `CreateToolhelp32Snapshot` |
| `src/remote/agent/proc_control.zig` | `killWindows` - `OpenProcess(PROCESS_TERMINATE)` (note the documented TERM==KILL caveat) |
| `src/remote/agent/proc_spawn.zig` | `spawnDetached` has a windows branch |

`src/remote/protocol.zig` already carries `HostMetrics` and the proc list over
the wire, so the REMOTE source works the moment a UI asks for it. The
`ghostty_local_proc_list` / `_free` / `_kill` / `_spawn` exports in
`src/apprt/embedded.zig` are the macOS embedding shim; the win32 apprt calls
the Zig modules directly and does not need them.

**So the gap is the win32 UI and its wiring, not the data.** Budget the work
accordingly: this is a chrome/layout task in the shape of `MachineChooser.zig`,
not a systems task.

## Details

Build it the way the chooser was built (T172/T175/T176), because that is the
pattern this codebase has already validated for a complex win32 dialog:

- A pure, unit-tested layout module (`activity_layout.zig`) in the none lane -
  gauge row, table columns, control bar, card carousel - the way
  `chooser_layout.zig` and `chooser_rows.zig` are pure and fully tested.
- An owner-drawn window (`ActivityMonitor.zig`) for the paint, sharing
  `icon_button.zig`, `banner_card.zig` rim constants and the T206 visual
  language so it does not read as a different app.
- The window registry keyed by source, matching Mac's focus-don't-duplicate
  rule and its exactly-once teardown.
- The trend gauges are the one genuinely new drawing problem (no Charts on
  win32). A pure `trend_gauge.zig` that maps samples to a polyline plus a
  fill, unit-tested on the mapping, is the shape.

Sequencing note: T177 (the chooser's Activity button) is this task's entry
point, and the command-palette entry is the second one (T189 gave win32 one
command list, so it is one row there).
