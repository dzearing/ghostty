# T328 - Kill on a REMOTE roster row loses its refetch: CLOSE_SESSION and the LIST behind it both fail on the relay connection

## Summary

Found while validating T319, on the box, on every run. Killing a session from
the chooser's roster works **locally** (T318's `chooser-sessions.ps1` proves the
agent really ends it and stops listing it). Over a **relay** connection the same
worker's two RPCs both fail:

```
info(win32):    chooser roster: loaded 2 session(s) target=remote device=dev-remote
info(win32):    chooser roster: ending session id=52184a6228108267a2d3be0131af6130
info(win32):    chooser roster: relay dialled device=dev-remote
warning(win32): chooser roster: close session failed err=error.ConnectionClosed
warning(win32): chooser roster: LIST_SESSIONS failed err=error.ConnectionClosed
```

The error is **not stable across runs**: `error.ConnectionClosed` on four runs,
`error.Timeout` on the fifth. Both are the same event seen from two sides of a
race, and `error.Timeout` is precisely **T326** — the agent terminates the child
and persists to disk BEFORE replying, so a Kill that plainly worked reports a
timeout. On a relay-bridged link that window is evidently long enough that the
connection sometimes dies inside it.

## Why it matters

The refetch is the roster's only source of truth. Losing it means the row the
user just killed is only hidden by the **optimistic hide** (`markKilled`), and
the count in the detail subtitle — and `owned.sessions.len` behind it — stays at
the pre-kill number until the user leaves the machine and comes back. The user
is looking at a machine's roster that disagrees with the machine.

## What has already been ruled out

- **Not the fake relay's bridge lifecycle.** `BRIDGE down` is never logged at
  the time of the failure; the bridge for the Kill's dial comes up and stays up.
- **Not stale bridges piling up.** Reaping them made no difference. (Two reaping
  probes were tried and BOTH are wrong, which is worth keeping: `TcpClient.Connected`
  reports the state as of the last I/O, and `Poll(SelectRead) && Available == 0`
  races the loop's own reads — it tore down healthy bridges ~30 ms after the
  upgrade. `lib\FakeRelay.ps1` carries that note.)
- **Not the 8-byte WebSocket length.** It WAS broken (`[int] -shr 56` is
  silently `-shr 24` in .NET) and is fixed, and the failure survived the fix.
- **Not the dial.** `chooser roster: relay dialled device=…` is logged, so the
  WebSocket upgraded and the HELLO handshake completed. The connection dies
  after that and before (or during) the first RPC.

## What was tried and must NOT be shipped as-is

A retry on a fresh dial — `if (roster == null and conn != null) re-dial, list
again` — **wedged the worker thread**: no `re-dialled` line, no `re-dial failed`
line, no reply ever posted. Blocking in `relay_dial.dial` (the WebSocket upgrade
read has no deadline) or in the previous `Dialed.deinit` are the two candidates.
That is a worse failure than the stale count and it was reverted; the comment in
`SessionRoster.worker` points here.

## The work

1. Decide WHO closes the connection — instrument both sides. The agent's own
   log during `CLOSE_SESSION` is the first place to look, then the client's
   reader/heartbeat threads, then the relay bridge.
2. Settle whether this is relay-specific or just SLOWER on a relay (T326 says
   the same window exists locally). If it is T326's window, fixing T326 — reply
   before persisting — may close this too.
3. Make the roster truthful after a Kill whatever the answer is: either the RPC
   survives, or the refetch happens on a connection that does. Any retry needs a
   BOUNDED dial (see above).
4. Re-enable the assertion that is deliberately not asserted today:
   `test/win32/chooser-sessions-remote.ps1` prints
   `NOTE T328: the post-Kill refetch does not land - …` where it should assert
   `the refetched remote roster is down to 1`.
