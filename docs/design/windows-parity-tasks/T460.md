# T460 - Crash details still cost a whole red lane to obtain: nothing captures a stack on the FIRST crash, so every intermittent crash is diagnosed by re-running it

## Summary

D6 follow-up (user, 2026-08-04): make crash details easy and fast to get. Today a crash is diagnosed by re-running the binary under cdb after the fact, which only works if the crash reproduces. Investigate always-on first-chance capture (AeDebug/WER LocalDumps scoped to our test binaries, or launching every lane's test binary under cdb from the start) so the first crash is the one that yields the stack.

## In plain terms

When the test suite crashes, the only way to find out *why* has been to run the
crashing program again under a debugger and hope it crashes the same way twice.
Half the time it does not, so the crash that actually broke the build tells us
nothing and somebody spends an afternoon trying to provoke it again. It turns
out Windows has been quietly saving a full record of every crash all along, at
the moment it happens, and nobody was reading the file. Now a failed test run
opens that record and prints the answer in about a second — including for the
crashes that never happen twice.

## Goals

- [x] Find out whether a crash can be captured on its FIRST occurrence, with no
      cost to a run that does not crash
- [x] Read the evidence instead of re-creating it, and prove it holds the same
      facts the re-run produced (every thread, the fault site, source lines)
- [x] A failed lane takes that path first and only re-runs when there is nothing
      to read
- [x] Make it available by hand, and able to say whether the box is armed at all
- [x] Refuse to invent evidence: never report an older crash, or a dump of a
      healthy process, as the crash being asked about

## Validation criteria

- [x] A single run of a crashing binary leaves a dump that yields both threads,
      the faulting frame and source lines — verified by section 3 of
      `test\win32\crash-first-chance.ps1` (`avthread!boom` and `avthread!main`
      both present, 2 threads, source lines >= 2)
- [x] Reading it costs seconds rather than a re-run — asserted at <= 60s in the
      same section; measured at ~1s
- [x] `floor-lane.ps1` reads the dump and does NOT reach the cdb re-run, and
      with `GHOZTTY_CRASH_NO_WER=1` falls back to it — section 6, both arms
- [x] A dump older than the asking run, a binary that never crashed, and a dump
      of a live process are all refused — section 4
- [x] `crash-catch.ps1 -FromDump` exits 1 with the block, a missing dump exits 2,
      `-Status` exits 0 and names the dump folder — section 5
- [x] `test\win32\crash-first-chance.ps1` ALL PASS (49 assertions, 0 skipped)
- [x] `test\win32\crash-stacks.ps1` still ALL PASS (the T450 path is untouched)
- [x] Floor green: `scripts\floor-lane.ps1 -Lane all`, plus P1-P3
