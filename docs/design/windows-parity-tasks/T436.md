# T436 - An assertion inside a hand-locked store.mutex turns a test flake into a Deadlock panic (11 sites in server.zig)

## In plain terms

When one of the agent's automated checks fails, it is supposed to say what it
expected and what it got. Instead, eleven of them will report something else
entirely — a crash blaming a completely different part of the program — because
of how they hold an internal lock while checking. Whoever hits it spends their
time chasing the wrong thing.

## Goals

- [ ] A failing assertion in these tests reports the assertion, not a deadlock
- [ ] The spin-until-gone loop below reports what it was still waiting for

## Summary

Eleven test sites in `src/remote/agent/server.zig` are shaped like this:

```zig
h.server.store.mutex.lock();
try testing.expect(h.server.store.table.getByChannel(o.channel) == null);
h.server.store.mutex.unlock();   // <- never reached when the expect fails
```

When the assertion fails, `try` returns out of the function **still holding the
store lock**. The test's own `defer h.deinit()` then runs
`Server.shutdown()` → `detachAll()` → `store.mutex.lock()` on that same thread,
and zig's Debug `Mutex` reports:

```
thread 44780 panic: Deadlock detected
  ...\std\Thread\Mutex.zig:34:19  in lock
  src\remote\agent\server.zig:421 in detachAll
  src\remote\agent\server.zig:383 in shutdown
  src\remote\agent\server.zig:2181 in deinit
  src\remote\agent\server.zig:3041 in test."child exit emits EXIT after final
                                        DATA; reattach -> dead+exit_code; CLOSE frees"
```

So a plain "the session was still in the table" reads as a mutex deadlock in
the shutdown path — a part of the code that is working correctly. Measured live
on 2026-08-03 during T430's validation.

## Sites

`src/remote/agent/server.zig` lines 3088, 3139, 3226, 3378, 3491, 3600, 3722,
3793, 3849, 3913, 3970 (the `try` sits between a hand-written `lock()` and its
`unlock()`).

## Fix

Compute under the lock, assert after it — or scope the section and `defer` the
unlock. Do **not** blanket-convert to `defer` at function scope without reading
each site: some of these are followed by code that takes the same lock again,
and holding it to end-of-scope would produce the very deadlock being removed.

## The flake underneath it

The run that exposed this failed because the session was still in the table
after the test's 10,000-spin wait for `CLOSE` to land — twice green before and
after on the same source, so it is a timing flake and not a regression. The
spin loop exits silently on exhaustion and leaves the assertion to report it;
it should say that it timed out, and how long it waited.

## Validation

- Force one of the eleven assertions to fail (flip the expectation locally) and
  confirm the output names the assertion rather than a deadlock.
- `powershell -NoProfile -File scripts\floor-lane.ps1 -Lane agent -Repeat 5`.
