# T1405 - Nothing scores the accent REPAINT: chrome-theme.ps1 passes 129 of 129 with the color-change redraw removed entirely

## In plain terms

When you change your accent colour in Windows settings, Ghoztty is supposed to
recolour whatever is already on screen there and then. There is a test that
claims to check exactly that. It does not: the test takes its photograph by
asking the window to draw a fresh picture, so the picture is always up to date
whether or not the app would have redrawn anything by itself. The app could
stop repainting entirely and every check would still be green, which is what a
measurement proved.

## Summary

Measured while validating T585, not reasoned: `system_colors.repaintForColorChange`
was cut down to a bare cache drop —

```zig
pub fn repaintForColorChange(hwnd: w32.HWND) void {
    invalidate();
    _ = hwnd;   // no RedrawWindow at all
}
```

— the win32 app was rebuilt, and `test\win32\chrome-theme.ps1` still reported
`ALL PASS (129 assertions)`, B4 (labelled "the LIVE-UPDATE claim") included.
An intermediate control — the same function keeping `RedrawWindow` but losing
`RDW_ALLCHILDREN` — also passed everything.

Root cause: **photographing a window makes it paint.** `Get-TestWindowPixels
-Sync` is `WM_PRINTCLIENT`, and the default path is
`PrintWindow(PW_RENDERFULLCONTENT)`; both hand the window a DC and ask for a
frame. That frame reads the accent through the process-global cache the
message has just dropped, so the new colour appears in the capture whether or
not anything invalidated the window. Every accent assertion in the script —
B3, B4, F1, F2 — therefore scores the CACHE and its drop, and the repaint a
user actually sees is scored by nothing.

The same shape defeated the earlier candidate oracle for T307's child half (the
hero carousel repaints itself on a 150ms timer), so this is a class of blind
spot, not one bad assertion.

What T585 landed meanwhile: `chrome-theme.ps1` F3 asserts `RDW_ALLCHILDREN` as
SOURCE TEXT, which does go red on both controls above. That covers the specific
flag; it does not cover "the window redraws when the accent changes" in
general.

## Where

- `test/win32/chrome-theme.ps1` — B3/B4 and the new F1/F2/F3; its header
  records the measurement under "WHAT NO CAPTURE IN THIS SCRIPT CAN CLAIM".
- `test/win32/lib/TestDesktop.ps1` — `Get-TestWindowPixels`, both capture
  paths.
- `src/apprt/win32/system_colors.zig` — `repaintForColorChange`, the code the
  claim is about.

## Options worth weighing

1. Find a read of the on-screen pixels that does NOT ask the window to draw —
   e.g. a BitBlt of the desktop DC on the background desktop (measure it: the
   harness header records `CopyFromScreen` as dead there, and a `CreateDesktopW`
   desktop may have no composited surface to read at all).
2. Count paints instead of reading pixels: a debug-only counter, or an existing
   log line, and assert it advances on the notification and not otherwise. Cheap
   and exact, at the cost of test-only instrumentation in the app.
3. Keep the pixel oracle but remove the cache from under it — e.g. capture,
   then assert against a window that is NOT notified, so the two windows must
   disagree. (Does not work as stated: the cache is process-global, so the
   un-notified window also paints the new accent when photographed. Written
   down so it is not re-derived.)

## Validation criteria

- [ ] An assertion that FAILS on a build whose `repaintForColorChange` does not
      redraw, and PASSES on one that does — the negative control run, not
      assumed, on a build made for the purpose.
- [ ] It runs in the default (non-interactive) invocation of its script.
- [ ] `chrome-theme.ps1`'s header stops saying the repaint is unscoreable, and
      B4's label matches what it measures.
