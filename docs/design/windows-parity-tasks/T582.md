# T582 - Mac's hero divider ignores split-divider-color too (win32 fixed it in T250)

## Summary

Found while fixing T250 on win32, by reading the Mac source it was supposed to
port. Mac has the SAME defect win32 just fixed, in the same place: a hero
divider that ignores the divider color the user configured, sitting next to a
split divider that honors it.

VERIFIED by reading, 2026-08-07:

- `macos/Sources/Features/HeroMode/HeroModeView.swift:117-121` —
  ```swift
  private var dividerColor: Color {
      (isHovering || isDragging)
          ? Color(red: 0.416, green: 0.416, blue: 1.0)
          : Color.gray.opacity(0.3)
  }
  ```
  The rest color is a literal gray. `split-divider-color` is nowhere in this
  file.
- `Ghostty.Config.swift`'s `splitDividerColor` IS what
  `SplitView.Divider.swift` fills the ordinary split divider with. So on Mac,
  as on win32 before T250, theming your dividers themes one of them.

The hover/drag accent is NOT the defect and must survive: it is deliberate
hero-mode behavior on both platforms now (win32 derives the user's accent for
it since T305, rather than porting the 0.416/0.416/1.0 literal).

## The fix

Read `splitDividerColor` for the rest state, the way `SplitView.Divider` does.
Whether Mac also adopts win32's 3:1 contrast floor (`split_geometry
.dividerPaint`, T251) is a separate call — it is already recorded as a
deliberate win32 divergence in `docs/design/win32-design-system.md` §5, and
this task is only about the config plumbing.

Note the WIDTH divergence is deliberate and stays: Mac's 1 pt is right on macOS
and 2 DIP is right on Windows (T233, §5). Do not "fix" Mac to 2 pt.

## In plain terms

On the Mac, the divider between the big pane and the thumbnail strip stays gray
no matter what divider color you set in your config — while the divider between
ordinary split panes changes. Windows had the same problem and no longer does.

- [ ] Hovering/dragging it still paints the accent, unchanged
- [ ] macOS test suite green
