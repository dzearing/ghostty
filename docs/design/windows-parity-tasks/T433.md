# T433 - session-relaunch.ps1 sets no GHOZTTY_PIPE_SUFFIX, so run from a Ghoztty pane it drives the USER'S terminal

## In plain terms

An automated test that is supposed to exercise a throwaway copy of the terminal
instead reached into the real one the user is working in, and opened two panes
there. Nothing was lost and the panes were closed again, but a test that can
touch the user's own windows is a test nobody can safely run. After this, it
runs entirely to itself, like the rest of the suite already does.

## Goals

- [ ] `session-relaunch.ps1` talks only to the instance it launched.
- [ ] Any other `test/win32/*.ps1` with the same gap is fixed with it.
- [ ] Something fails loudly if a future script forgets, rather than silently
      driving whatever terminal happens to be listening.

## Evidence (2026-08-03, measured during T424 — ✓ VERIFIED)

Run from inside a Ghoztty pane, `test\win32\session-relaunch.ps1` reported
**13 FAILURE(S)**, starting at setup:

```
  PASS A1 startup pane came up under the local agent
  FAIL A2 +split opened a second agent-backed session (2 alive)
```

The cause is not the code under test. `Launch` (line ~205) is hermetic on state
(`$env:LOCALAPPDATA`, `$env:GHOSTTY_LOCAL_AGENT_BIN`) but sets **no
`GHOZTTY_PIPE_SUFFIX`**, and its `Run-Cli` helper shells out through `cmd.exe`,
inheriting the calling pane's environment. Per CLAUDE.md → *Instance
addressability*, the CLI's precedence is **suffix → baked → derivation**, so
with no suffix every `+split` / `+list` / `+send-keys` in the script resolved
the pane's baked `GHOZTTY_IPC_SOCKET` — `\\.\pipe\ghoztty-David`, the **user's
installed release**.

`+sessions`, meanwhile, dials the agent found under the *redirected*
`LOCALAPPDATA`, i.e. the test agent. So the script split the user's real
terminal and then counted sessions on a different instance — hence "2 alive"
never arriving. Confirmed by `+list --json` against the release app immediately
afterwards, which showed the script's own panes in a user window:

```
WINDOW: C:\WINDOWS\system32\cmd.exe
   pane name=AAE528DA-…   (pre-existing)
   pane name=relp         <- created by the test
   pane name=prp          <- created by the test
```

Both were closed by hand. The script's `Stop-TestProcs` filters on
`CommandLine -like '*zig-out*'`, so it correctly never killed the release
processes — the damage was confined to the two panes it opened.

**Proof it is the harness and not the product:** the identical script, same
build, re-run with `$env:GHOZTTY_PIPE_SUFFIX` set, is **ALL PASS**.

CLAUDE.md already names this exact hazard — *"a script inherits the environment
of the pane it was started from — without this rule every `test\win32\*.ps1`
run from one of the user's panes would drive the user's terminal"* — so this is
a script that never adopted a rule the project had already written down.

## The fix

1. Give `Launch` a per-run `$env:GHOZTTY_PIPE_SUFFIX` (the pattern
   `session-relaunch-notify.ps1` already uses), and restore it in `cleanup`
   alongside `LOCALAPPDATA` / `GHOSTTY_LOCAL_AGENT_BIN`.
2. **Audit the rest of `test/win32/`** for the same gap — grep for scripts that
   set `LOCALAPPDATA` or launch `$Exe` but never mention `GHOZTTY_PIPE_SUFFIX`.
   The two-arm shape here (state redirected, IPC not) is the one that hides.
3. Make the omission loud rather than silent. Cheapest credible guard: a shared
   preflight in `test/win32/lib/` that refuses to run when the effective IPC
   endpoint is one the script did not launch — a test that silently retargets
   is worse than one that fails.

## Validation

- `session-relaunch.ps1` ALL PASS with **no** `GHOZTTY_PIPE_SUFFIX` exported by
  the caller, run from inside a Ghoztty pane.
- During that run, `+list --json` against
  `%LOCALAPPDATA%\Programs\Ghoztty\ghoztty.exe` shows **no** new panes in any
  user window.
