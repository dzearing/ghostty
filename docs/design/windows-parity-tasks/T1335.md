# T1335 - An UNCORRECTED hardware error on this box should reach the turn that follows it, not wait to be asked

## Summary

Filed out of **T452** (2026-09-04). That task built `scripts\whea-report.ps1`,
which reads the Windows hardware error log correctly - no level filter, and a
hard split between CORRECTED (recovered, nothing lost, ~267 a day here) and
UNCORRECTED (the fault reached the machine). It exits 8 on the second class.

Nothing runs it. So today an uncorrected hardware error - the single most
decisive piece of evidence the T443/T449 crash hunt could possibly receive -
lands in the event log and waits for a human to think of asking. T449 shows what
that costs: it asked once, asked wrongly, and wrote the wrong answer down.

The asymmetry is the whole design here. **Corrected errors must never reach the
turn**: 267 a day is noise, it gates nothing, and a claim that reports it every
turn trains the reader to skip the block. **An uncorrected error must reach it
once**, named, with the device resolved, and never again for the same event -
so it reads as news rather than as a standing condition.

## In plain terms

The computer keeps a log of hardware faults. The harmless kind happen hundreds
of times a day here and are not worth mentioning. The serious kind - where the
machine actually lost something - has never happened on this box, and if it ever
does, nobody will find out until somebody happens to go looking. This makes the
serious kind announce itself, once, the next time the loop starts a turn.

## Goals

- [ ] `go-loop-exec.ps1 claim` reports an UNCORRECTED WHEA event once, with the
      device resolved the way `whea-report.ps1` resolves it
- [ ] It is informational, never a refusal - a claim that can fail over the
      state of the hardware log wedges the loop, which is the disease not the cure
- [ ] Corrected errors produce NO line at all, however many there are
- [ ] A reported event is watermarked so the next turn does not repeat it

## Suggested approach

`scripts\whea-report.ps1 -Json -Days 1` already returns everything needed
(`Counts.UNCORRECTED`, `Sources` with the resolved device and drive letters).
The claim's other reporters - stranded work (T847), CI verdict (T1219), boot
outage (T829) - are the shape to copy, watermark included. Cost matters: the
claim runs every turn, so scope the query to a short window and skip the PnP
resolution walk unless there is something to resolve.

Per T1133, ship it with the demonstration that it can fire: an arm in
`test\win32\gate-negatives.ps1` that plants an uncorrected event (the fixture
path `whea-report.ps1 -InputPath` already exists for exactly this) and requires
the claim to name it - and a companion arm requiring a corrected-only window to
produce silence.

## Validation criteria

- [ ] A synthetic uncorrected event makes `claim` print a block naming the
      device; a corrected-only window prints nothing.
- [ ] The claim still exits 0 in both cases.
- [ ] The same event does not reappear on the following turn.
- [ ] `test\win32\gate-negatives.ps1` carries both arms and is ALL PASS.
