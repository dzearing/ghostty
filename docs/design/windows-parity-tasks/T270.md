# T270 - ghoztty.log has no timestamps, so ordering across concurrent processes is unknowable

## In plain terms

When something goes wrong in the Windows build, the log file it leaves behind is
the only record of what happened — and until now that record could not say WHEN
anything happened or WHICH program wrote it. Everything Ghoztty runs writes into
the same file at once, so it read as one jumbled stream with no way to pull one
program's story out of it, and no way to tell a crash from a twenty-minute wait.
Every line now starts with the time and the writing program's id, so the file can
be sorted, filtered, and read as a sequence of events. Nobody sees this while the
terminal is working; it is what makes a bad day diagnosable instead of guesswork.

## Goals

- [x] Every line in the shared log carries a millisecond UTC timestamp and the
      writing process's id
- [x] The prefix rides the same single write as its message, so it cannot split
      a line the way the pre-T229 writer did
- [x] The timestamp/pid formatting is pure and unit-tested, including a wrong
      system clock at both extremes
- [x] `test\win32\log-append.ps1` measures the new shape on the real binary:
      shape on every line, each writer's own pid present, per-pid monotonic time

## Summary

`%LOCALAPPDATA%\ghoztty\ghoztty.log` carries a level, a scope and a message —
and **no timestamp and no pid**. It is a SHARED sink: the GUI app, the agent and
every one-shot `ghoztty +...` CLI invocation append to it, and on this box there
are several a second. So the file is an interleaving of many processes' output
with nothing to tell them apart or place them in time.

T229 lost real time to this. Reconstructing what happened around the three
`user confirmed destructive agent refresh` lines meant guessing which of nine
identical `ghoztty version=...` banners belonged to a GUI and which to a
`+list`, and the pairing of a confirmation to the `showing mandatory restart
confirmation` line that preceded it was **~6,500 lines away** in the file with no
way to prove they belonged to the same process. A question as basic as "did the
app die, or did it sit there for twenty minutes?" is not answerable from this
log.

Sibling of the loss defect T229 fixed (concurrent `seek`+`write` was silently
clobbering lines; now `FILE_APPEND_DATA`). That one made lines vanish; this one
makes the surviving lines unreadable.

## Direction

Prefix every line written to the FILE sink with a timestamp and the pid:

```
2026-08-01T14:22:31.104Z 13060 warning(win32): user confirmed destructive agent refresh (...)
```

- File sink only. stderr (Debug) and the macOS unified log both already have
  their own timestamping, and duplicating it there would be noise.
- The pid is what makes the sink demultiplexable — `Select-String ' 13060 '`
  becomes a single process's log.
- Keep it one `bufPrint` into the existing 2 KB buffer and one `write`: the
  append is atomic per write, so the prefix must not become a second write or
  it can interleave inside a line.
- Cheap: `std.time.milliTimestamp` + `GetCurrentProcessId`, both already
  reachable.

Worth considering alongside: a size cap / rotation. The file is 8.6 MB today
with no bound.

## Validation criteria

- [x] Every line in the file matches
      `^\d{4}-\d\d-\d\dT[\d:.]+Z \d+ (debug|info|warning|error)` — assertion L2
      of `test\win32\log-append.ps1`, over all 216 lines of a 24-writer run.
- [x] Two concurrent processes' lines can be separated by pid — L4/L5/L6: all 24
      launched writers' pids appear, no pid appears that did not write the file,
      and the distinct-pid count equals the writer count.
- [x] Each pid's lines are monotonically ordered in time — L7 (per-pid, not
      global: two processes genuinely interleave, so a global claim would be
      false). L3 proves every stamp is a real UTC instant and L8 that it is this
      run's rather than a constant.
- [x] `test/win32/log-append.ps1` extended and ALL PASS (12) against
      `zig-out-release\bin\ghoztty.exe`.
- [x] Teeth check: the same script against the pre-T270 installed release fails
      L2, L3, L4 and L6 (`-Exe %LOCALAPPDATA%\Programs\Ghoztty\ghoztty.exe`,
      hermetic — its own LOCALAPPDATA and pipe suffix, `+list` only).
- [x] Unit tests in `src/os/log_stamp.zig` run in the `none` lane — verified by
      breaking one deliberately and watching the lane go red, then reverting.
- [x] Standing floor: `scripts\floor-lane.ps1 -Lane all`, P1-P3.

## Not done here: the size cap

The Summary's "worth considering alongside" — the file is 8.6 MB with no bound,
and the prefix adds ~30 bytes to every line — is deliberately NOT in this change.
Rotation is a different mechanism with its own failure mode (a rotating writer
must not lose the atomic-append property T229 established), and folding it into
a formatting change would make one commit answer for two contracts. Filed as its
own task; see the Progress log.
