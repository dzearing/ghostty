# T668 - Viewer feedback carousel: an overflowing strip gives no sign there are more pictures, and no way to reach them from the keyboard

## In plain terms

If you attach more pictures to a feedback report than fit across the box, the
extra ones are simply off the edge with nothing on screen saying so. The mouse
wheel scrolls to them, but nobody would guess that, and someone working from the
keyboard cannot get to them at all.

## Summary

Filed out of T646, which built the strip. The scroll mechanism is there and
tested (`Layout.maxScroll` / `clampScroll` / `scrollToShow`, wheel over the
band, and an automatic scroll when the caret enters a chip or a paste lands) —
what is missing is the two ways a person finds out about it.

- **No overflow cue.** A ribbon longer than its viewport looks identical to one
  that fits: the last visible tile is simply cut off at the clip edge, which
  reads as a rendering glitch rather than as "there is more this way". Mac's
  carousel is an `NSScrollView` and gets the platform's own scroller. Candidates
  here: a fade/gradient at whichever end has content past it, small chevron
  affordances, or a thin indicator under the strip. Whatever it is has to obey
  the design system's contrast floor for a meaningful boundary (3:1) and must
  not appear when there is nothing to scroll.
- **No keyboard path.** The tiles are reachable only by clicking. There is no
  focus ring, no Tab stop, no arrow-key walk. The composer's own keyboard model
  is the constraint to design within: Tab inside a RichEdit is a character, and
  the band's chords already carry Ctrl+Enter/Escape.

Note that the chip↔tile sync gives the keyboard an INDIRECT path already —
arrowing the caret into a chip rings and scrolls to its tile — so the gap is
about acting ON a tile, not about seeing it.

## Validation criteria

- [x] Unit tests (none lane): the cue's geometry asserted at 1.0/1.25/1.5/2.0,
      present only when `maxScroll() > 0` and on the end(s) that actually have
      content past them — `viewer_feedback_layout.zig`, "the overflow cue
      appears only on the end that has pictures past it" and "a strip that fits
      has no cue at either end".
- [x] Unit tests (none lane): the keyboard walk's index arithmetic as a pure
      function — `moveTile` clamps at both ends, skips nothing between them and
      answers inside a strip that shrank under it ("moveTile clamps at both ends
      and skips nothing in between"), plus the Tab ring with the strip in it
      ("with pictures attached the strip is a Tab stop between the text and the
      actions").
- [x] On-box acceptance: with more tiles than fit, the app reports the cue on
      the end that has more and drops it at each end it reaches; with a strip
      that fits, it reports none — `test/win32/viewer-feedback-carousel.ps1`
      sections F and H, ALL PASS (60).
- [x] On-box acceptance: Tab stops on the strip, End reaches the last picture
      (which is off-screen at that width) by scrolling to it, Left steps back
      into full view, and Enter selects that picture's chip — the same
      observable outcome the click in section C has. Section G of the same
      script.
