# T1127 - Seven acceptance scripts leave a live app process behind when they finish

## In plain terms

Seven of the automated checks finish without shutting down the copy of the app they started. The leftover copy then interferes with the next check in line, so failures can appear in checks that are perfectly fine. Five of the seven otherwise pass, so nothing would ever have noticed on its own.

## Summary

The T1094 full sweep reports `leaked procs : 7 script(s) left a zig-out process running`. The runner's between-script sweep is the ONLY reason these are visible - before it existed, each leak silently poisoned whichever script ran next.

| script | own verdict | leaked |
|---|---|---|
| `agent-instance-lineage.ps1` | pass | 1 |
| `agent-relay-session-e2e.ps1` | pass | 1 |
| `ipc-under-load.ps1` | pass | 1 |
| `menu-bar.ps1` | fail | 1 |
| `remote-pill.ps1` | pass | 1 |
| `remote-reconnect-fresh.ps1` | pass | 2 |
| `test-desktop-spike.ps1` | fail | 1 |

Five of the seven PASS, which is the point: a leak is a harness defect regardless of the script's own verdict, and a passing script has no reason to be looked at.

Filed as one task with a checklist rather than seven near-identical files, because the fix is expected to be one shape (a teardown path that misses a spawned instance) repeated seven times; if any one turns out to have a genuinely different cause, split it out then.

## Where

- the seven scripts' teardown/cleanup paths
- `test/win32/lib/CleanSlate.ps1`
- `scripts/suite-run.ps1` - the between-script leak sweep that detects this

## Goals

- [x] Take each script in turn: run it alone, confirm the leak, find which spawned instance escapes teardown.
- [x] Look for the common shape first - a second window, a detached child, or an instance started before the cleanup handler is installed.
- [x] Fix the teardown at the shared helper level if the cause is shared; per-script only if it is genuinely per-script.
- [x] `remote-reconnect-fresh.ps1` leaks TWO, so it may be the clearest specimen to start from.

## What it was

Every leak was the same process: a detached `ghoztty-agent --pty-host` HOLDER.
The holder owns the ConPTY and is spawned through the shell-parent hop
**precisely so it outlives its agent** (T904/T906 - that is what makes a
session survive an agent restart), so it is neither a child of the agent nor a
member of any job that dies with it. Every teardown in these scripts is by PID
(`Stop-Process -Id $agent.Id`) or app-only, and none of them can reach it.

`menu-bar.ps1` was the odd one out: run alone it leaks nothing and passes (its
`finally` is a full `Stop-RepoGhoztty`, which reaps holders by path). Its sweep
leak was collateral from the script before it - which is exactly the poisoning
this task is about.

## What landed

- `Register-RepoBuildTeardown -Exe <exe>` in `test\win32\lib\HarnessLeak.ps1`: arms a
  `PowerShell.Exiting` reap of everything under the directory of the build under
  test. One line per script, and it covers the failure path - a
  `SETUP FAIL ...; exit 1` walks past a `finally`, and that is when a leak
  actually happens. An exe outside the repo and `%TEMP%` arms nothing and says
  so, so a run pointed at a delivered install can never reap the user's app.
- Armed in the six leaking scripts, plus `menu-bar.ps1` for its setup-guard
  exits.
- Section F of `test\win32\harness-process-leak.ps1` is its acceptance, with teeth
  (F4: the same run without it leaks), and a new `harness-leak` row in the
  `guard-due` coverage table so the leak library cannot drift unwatched.
