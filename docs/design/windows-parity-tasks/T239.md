# T239 - Chevron glyph reads ~30% lighter than the + and x at the same stroke width

## In plain terms

The little collapse arrow on a pane banner is drawn with thinner lines than the
"+", the "x" and the menu button sitting next to it in the same chrome, so on a
high-DPI screen it looks faded next to its neighbours — as if it were disabled.
Nothing changes about what it does; it just stops being the odd one out.

Who actually sees it, stated honestly: this task was filed before T497, which
made Windows' own icon font the normal way these buttons are drawn. So on a
stock Windows 10/11 machine the arrow now comes from Microsoft's font and this
was never visible there. What is fixed is the **fallback** Ghoztty falls back to
when a machine is missing both icon faces — plus, more importantly, the rule
itself, so the next hand-drawn glyph does not repeat the mistake.

## Goals

- [x] The chevron's arms paint at the same weight the eye reads as every other
      mark in the chrome, at every display scale.
- [x] The same correction covers the other sloped marks (the back/forward
      arrows, the home icon's roof), so no glyph is left disagreeing.
- [x] A test that fails if any glyph in the set drifts off the shared weight
      again — not just the one this task was about.

## Summary

Surfaced while landing T232. The banner's collapse chevron is built from two
arms whose thickness is measured **vertically** (`b.bottom - t` .. `b.bottom`
at the outer end), while the "+" and the hamburger are built from bars whose
thickness is measured **perpendicular** to the mark, and the "x" was explicitly
corrected to perpendicular in T232 (design system §4.3).

The chevron's arms are at 45° (`mark_chevron_w` 12, `mark_chevron_h` 6 → 6
across and 6 of rise per half), so a vertical thickness of `stroke_w` paints a
perpendicular thickness of `stroke_w / sqrt2` ≈ **0.71 × stroke_w**. Three of
the four chrome glyphs land at `t`; the chevron lands at `0.71t`. That is the
same class of defect as the hamburger's optical width — one control quietly
disagreeing with the set — and the design system's own §4.2/§4.3 already say it
is a defect.

`? INFERRED` on the visual severity: this is arithmetic off the source, not a
user report, and 0.71t on a 2 DIP stroke is a sub-pixel difference at 100%. It
is most visible at 1.5x and above, where `stroke_w` is 4 px and the chevron
paints ~3.

## The fix

Either give the chevron a perpendicular-corrected vertical thickness
(`tv ≈ 1.4 * stroke_w`, which needs `mark_chevron_h` to grow so the rise is
not eaten by the thickness), or make the arms genuinely shallower than 45° —
which is what "shallower than a caret" in the design system was asking for
anyway — so vertical thickness and perpendicular thickness converge. Prefer
the second: it fixes the weight AND makes the glyph match its own spec.

## What the numbers actually were

The Summary's arithmetic assumed the arms sit at 45°. They do not — the arm
rises `mark_chevron_h - stroke_w` over a run of `mark_chevron_w / 2`, i.e. 4
over 6, which is 33.7°. So the real shortfall is `cos 33.7° = 0.83t`, not
`0.71t`. Two other premises in the Summary were also off: `stroke_w` at 1.5x is
**2** px, not 4 (the parity fit in `markPx` rounds it down), and the arms were
already "shallower than a caret", so the Summary's preferred fix — make them
shallower still — would not have closed the gap on its own.

Measured `min` perpendicular thickness per glyph, from the quads themselves:

| scale | `stroke_w` | `+` | `×` | `≡` | chevron before | chevron after | home roof after |
|---|---|---|---|---|---|---|---|
| 1.0 | 2 | 2.00 | 1.41 | 2.00 | 1.66 | 1.66 | 1.74 |
| 1.25 | 3 | 3.00 | 2.83 | 3.00 | 2.68 | 2.68 | 2.62 |
| 1.5 | 2 | 2.00 | 1.41 | 2.00 | 1.66 | 1.66 | 1.71 |
| 2.0 | 4 | 4.00 | 4.24 | 4.00 | 3.33 | **4.32** | 4.00 |
| 3.0 | 6 | 6.00 | 5.66 | 6.00 | 4.99 | **5.97** | 5.82 |

The correction is deliberately a no-op at 1.0–1.5: it adds a sub-pixel amount
there, and a mark cannot be painted in fractions of a pixel. It bites at exactly
the scales where the deficit had grown past a pixel — 2.0 and 3.0 — which is
where the glyph was visibly the odd one out.

## Validation criteria

- [x] `icon_button.zig` unit test asserting **every** open glyph's PERPENDICULAR
      mark thickness lands within 1 px of `stroke_w` at every scale 1.0–3.0
      (step 0.05) — T232's `close`-only assertion generalised to the whole set.
      Verified: `zig build test -Dapp-runtime=win32`, and proven to be a real
      test by temporarily reverting the correction, which fails it with
      `scale 2.999998: chevron_up paints a 4.99px mark, want 6.00`.
- [x] The correction is shared, not chevron-local: `slopedStroke()` is applied
      to `chevron_up`/`chevron_down` (so `back`/`forward`, which transpose the
      chevron, inherit it) and to the `home` roof, which had the same defect
      (4.99px against a 6px stroke at 3.0).
- [x] Both `zig build test` lanes + `zig build test-agent` green via
      `scripts\floor-lane.ps1 -Lane all`.
- [x] `test/win32/pane-banner.ps1` ALL PASS (it covers the chevron's box and
      hover).

Note on scope, checked while working this: `glyphQuads` has been the FALLBACK
since T497 — `icon_button_paint.glyph` draws Segoe Fluent Icons / Segoe MDL2
Assets first, and only a machine missing both faces lands on these quads. The
fix is still correct and still worth having (the fallback has to look like the
product, and the shared `slopedStroke` + the generalised test are what stop the
next hand-drawn glyph repeating it), but it does not change what a stock
Windows 10/11 box paints. The task predates T497 and its Summary does not know
that.

Note on the Summary's second validation bullet: an on-screen capture at 125% is
not evidence here, because the correction is a **no-op at 1.25** (see the table)
— a capture would show exactly what it showed before the fix and prove nothing.
The measurement is taken off the quads instead, which is where the defect lives
and where it is checkable at every scale rather than at whatever DPI this box
happens to run.
