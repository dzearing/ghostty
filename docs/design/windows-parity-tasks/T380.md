# T380 - Viewer panes get no unfocused-split dim overlay (T74) now that they own a host window

## In plain terms

Ghoztty can show a web page, a document, or a diff in one half of a split
window. When you click away from a pane, the pane you left is supposed to
darken slightly so your eye can always find the active one. Terminal panes
darkened correctly, but viewer panes never did — a viewer always looked like
the pane you were working in, even when you weren't. Now viewers dim and
undim exactly like terminals as focus moves around.

## Goals

- [x] An unfocused viewer pane in a split shows the same dim overlay a
      terminal does (same color, same strength).
- [x] The dim follows focus in both directions: focusing the viewer undims it
      and dims the terminal, and vice versa.
- [x] No stale overlay after the window is resized, a pane is zoomed, or the
      tab is switched.

## Validation criteria

- [x] Unit test: the overlay glues to the viewer host window, is
      layered/click-through/no-activate, tracks a host move, hides and
      survives a heal pass — `ViewerPane.zig` test "T380: the dim overlay
      glues to the host window and follows it", win32 lane (77→78 tests with

- [x] Acceptance: `test\win32\split-dim-viewer.ps1` ALL PASS (29 assertions)

## Summary

`PaneView.showDimOverlay`/`hideDimOverlay` are no-ops on the `.viewer` arm.
That was correct while a viewer had no window to dim; T373 gave it one, so the
gap is now visible: in a split with one terminal and one viewer, the terminal
dims when unfocused and the viewer does not, which reads as "the viewer is
always the active pane".

## Details

Not a straight copy of the terminal path. T74's dim is a layered popup window
positioned over the pane (`Surface.showDimOverlay`, with the T142
`healOverlayZOrders` pass keeping it above the surface). A viewer's host window
contains WebView2's OWN Chromium child windows, which are created by the
browser process and re-parented as it likes, so the z-order rules the overlay
relies on need re-checking against them — and a layered window over a
DirectComposition-painted child is exactly the class of composite that T252's
`GetDC` finding says to measure rather than assume.

*Validation:* a split with one terminal and one viewer; focus each in turn and
probe pixels in both panes (the `win32 screen-pixel probes` recipe: DPI-aware
probe process, `CopyFromScreen`, topmost). Both panes must dim by the same
delta when unfocused, and neither may keep a stale overlay after the split is
resized or the tab switched.
