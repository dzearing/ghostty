# T630 - win32 startup still goes deaf for one agent handshake timeout (~1.2s) inside dialExisting

## Summary

T188 closed the 10.7 s startup blackout by pumping IPC from the points where
startup blocks. What is left is one of them: `LocalAgent.dialExisting` is a
single blocking call bounded by `probe_handshake_ns` (1200 ms), and against a
wedged agent it spends all of it. The pump brackets that call but cannot reach
inside it, which is exactly why `test\win32\ipc-startup-latency.ps1` measures
the suspended-agent first answer at ~1330 ms rather than the ~250 ms a healthy
restore gets.

Options, none of them investigated yet: thread a pump callback through
`tcp_dial.dialPipeTimeoutReport`'s wait (it is shared cross-platform code, so
this must not become a win32-shaped hook in `src/remote/`); do the dial on a
worker thread and post the result back (the `RestoreAllRelay` pattern, but
`LocalAgent`'s resolve mutates app-owned state and is not thread-safe today —
see D42's third option); or shorten the handshake budget for the STARTUP dial
specifically, on the grounds that an agent that has not answered in a few
hundred milliseconds is not going to.

## In plain terms

Commands now get answered while Ghoztty restores your windows, except for one
stretch of about a second when the background agent is wedged. Nobody has
reported noticing it; this is about closing the last of the gap.
