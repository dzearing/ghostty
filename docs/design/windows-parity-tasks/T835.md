# T835 - A banner table sometimes renders with a stunted value column - the T745 symptom is back, intermittently

## Summary

Measured 2026-08-14 while validating T833. The banner table probe that T745 added to test/win32/pane-banner.ps1 is not deterministic: the same banner, same pane width, same build renders the long value cell at the full content column most of the time and at 55-85 percent of it the rest. Eight renders on a clean build: 96.6, 96.6, 96.6, 96.6, 96.6, 82.4, 96.6, 96.6 percent - and on a build with T833 neutered, 79.6, 55.3, 96.6, 96.6, 96.6, 96.6, 96.6, 82.4. Both directions of that flake predate T833 (both builds show it), so this is NOT a T833 regression - it is the ORIGINAL user-reported symptom (2026-08-11, with a screenshot: a two-column banner table whose long cell stopped near the halfway mark) surviving T745 intermittently. The user's own loop banner hook is a table, so they see this. What is known: the card height is IDENTICAL between a good and a bad render (h=110), the paint happens at the right client width (cw=1382 pw=1382 in the debug oracle), and the difference is where the value text stops - 1283 px vs 1099 or 747. That points at the column-share math or the natural-width measurement, not at a stale pane width, and rules out a capture race (the bad values are stable wrap positions, not noise). Repro harness: the probe in the T833 turn (scratchpad t833-probe.ps1) measures ink-right N times in one instance; port it into test/win32/ as a repeat-count assertion so ONE good render can no longer pass the suite. Note pane-banner.ps1 currently fails about 1 run in 3 because of this.

## In plain terms

When the banner shows a two-column table - a label on the left, a long value on
the right - the value usually fills the pane, but sometimes it stops around the
middle and leaves the rest of the row empty. It is the same banner and the same
window either way; it just depends on the render. This was reported once with a
screenshot and fixed, and the fix only holds most of the time.

## Goals

- [ ] The stunted render is reproduced deliberately, not by luck, and the cause
      is named (column shares vs natural-width measurement).
- [ ] A table value fills its column on EVERY render, not most of them.
- [ ] The acceptance suite measures many renders, so one good one cannot pass it.
- [ ] Once it is deterministic, `scripts\guard-due.ps1` gains a row mapping the
      banner sources to `pane-banner.ps1` - deliberately NOT added while the
      script is 1-in-3 red, since a guard that cannot go green wedges the loop.

## Validation criteria

- [ ] `test/win32/pane-banner.ps1` measures the value column over N repeated
      renders (N >= 8) and every one of them is at the full width - the current
      single-shot assertion cannot fail reliably.
- [ ] 10 consecutive runs of `pane-banner.ps1` are ALL PASS (today ~1 in 3 goes
      red purely on this assertion).
- [ ] The root cause is written down in this file - which value differs between
      a good and a bad render, and why it changes.
