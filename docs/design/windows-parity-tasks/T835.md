# T835 - A banner table sometimes renders with a stunted value column - the T745 symptom is back, intermittently

## Summary

Measured 2026-08-14 while validating T833. The banner table probe that T745 added to test/win32/pane-banner.ps1 is not deterministic: the same banner, same pane width, same build renders the long value cell at the full content column most of the time and at 55-85 percent of it the rest. Eight renders on a clean build: 96.6, 96.6, 96.6, 96.6, 96.6, 82.4, 96.6, 96.6 percent - and on a build with T833 neutered, 79.6, 55.3, 96.6, 96.6, 96.6, 96.6, 96.6, 82.4. Both directions of that flake predate T833 (both builds show it), so this is NOT a T833 regression - it is the ORIGINAL user-reported symptom (2026-08-11, with a screenshot: a two-column banner table whose long cell stopped near the halfway mark) surviving T745 intermittently. The user's own loop banner hook is a table, so they see this. What is known: the card height is IDENTICAL between a good and a bad render (h=110), the paint happens at the right client width (cw=1382 pw=1382 in the debug oracle), and the difference is where the value text stops - 1283 px vs 1099 or 747. That points at the column-share math or the natural-width measurement, not at a stale pane width, and rules out a capture race (the bad values are stable wrap positions, not noise). Repro harness: the probe in the T833 turn (scratchpad t833-probe.ps1) measures ink-right N times in one instance; port it into test/win32/ as a repeat-count assertion so ONE good render can no longer pass the suite. Note pane-banner.ps1 currently fails about 1 run in 3 because of this.

## In plain terms

The banner was never drawing the stunted column - the TEST's camera was. When
the suite photographed the banner to check that a long value fills the row, it
sometimes got a half-finished photo, and the half-finished photo looked exactly
like the bug the user reported in August. The banner itself painted the same
correct row every single time. Now the suite photographs the banner in a way
that always waits for the whole picture, and it takes eight photos instead of
one, so a lucky shot can no longer stand in for a good render.

## Root cause

Not the column-share math and not the natural-width measurement: both are
deterministic and both were right every time. Instrumenting the app showed
`avail=1297 natural={71,2266} widths={71,1203}` and the value's first wrapped
line ending at `x=1290` on all ten renders, good and bad alike.

The variance is in `Get-TestWindowPixels`. It captures through
`PrintWindow(PW_RENDERFULLCONTENT)`, which asks DWM for a copy of the
composited surface of this `WS_EX_LAYERED` overlay - and that copy is
ASYNCHRONOUS. Three back-to-back captures of one UNCHANGED overlay, with no
repaint in between, measured the same row's rightmost ink at 1062, 1283 and
1179 px; six captures ranged from 388 to 1283. The torn frame stops mid-text at
a glyph boundary, which is precisely why the bad values looked like "stable
wrap positions" rather than noise and sent T835 hunting in the layout code.

The fix is a capture that cannot tear: `BannerOverlay` answers `WM_PRINTCLIENT`
by painting into the caller's DC, and `Get-TestWindowPixels -Sync` uses
`PrintWindow` with no flags so the window draws the frame itself, synchronously,
before the call returns. The bitmap is pre-filled with a sentinel colour and a
capture that comes back entirely sentinel FAILS - a window with no handler can
never quietly return a blank frame for an assertion to score against.

## Goals

- [x] The stunted render is reproduced deliberately, not by luck, and the cause
      is named - the DWM capture, not the column shares or the natural widths.
- [x] A table value fills its column on EVERY render, not most of them
      (60/60 captures at 96.6% after the fix; 8/8 in the suite).
- [x] The acceptance suite measures many renders, so one good one cannot pass it.
- [x] Once it is deterministic, `scripts\guard-due.ps1` gains a row mapping the
      banner sources to `pane-banner.ps1` - deliberately NOT added while the
      script is 1-in-3 red, since a guard that cannot go green wedges the loop.
      Added, with the residual ~1-in-10 flake (T845) known: that rate costs a
      re-run, not a wedge, and the alternative was leaving the banner's
      HORIZONTAL regressions - the only kind these pixel probes can see -
      ungated until an unrelated task closes. The script now stamps itself on a
      clean green sweep and refuses to stamp a run with skipped sections.

## Validation criteria

- [x] `test/win32/pane-banner.ps1` measures the value column over N repeated
      renders (N >= 8) and every one of them is at the full width - the current
      single-shot assertion cannot fail reliably. Section 6g2 now loops 8
      rounds, re-rendering from a different banner each round, and asserts the
      WORST round; it prints all eight percentages on failure.
- [x] 10 consecutive runs of `pane-banner.ps1` are ALL PASS (today ~1 in 3 goes
      red purely on this assertion). Measured over TWO batches of 10: this
      assertion was green 20 times out of 20. The script itself was 9/10 in
      each batch, on a DIFFERENT and unrelated assertion each time - one round
      that did not wait for the overlay (fixed here), and the T204 chevron
      hover reading its un-hovered frame, which comes through the `capture-hover`
      IPC rather than `Get-TestWindowPixels` and is filed as T845.
- [x] The root cause is written down in this file - which value differs between
      a good and a bad render, and why it changes. See `## Root cause`.
