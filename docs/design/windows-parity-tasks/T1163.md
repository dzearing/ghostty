# T1163 - Restoring a terminal with many saved panes opens them all at once, with no pacing and no way to say 'not now'

## Summary

Split out of T1158 rather than asserted there. T1158 closed the SOURCE of the window storm the user hit on 2026-08-23 (a half-isolated soak seeding the installed agent with pinned sessions), so the pile no longer grows on its own. What it did not address is the shape of restore itself when the pile is legitimate. Two facts, both read from the code. (1) App.restoreSessionLayout unions TWO sources - the app-local session-layout manifest AND the layout blobs the AGENT holds (src/apprt/win32/App.zig:2820, mirroring Mac's 20e505aaf) - so a window can be restored from the agent even when no manifest names it. That is deliberate and is what makes a crash survivable. (2) Nothing paces or caps the result: every restorable window is rebuilt in one burst at launch. A user who has accumulated a dozen persistent panes over a few weeks - which the persistence feature actively encourages - gets a dozen top-level windows appearing at once, and on 2026-08-23 that coincided with a BlueScreen cluster and an explorer AppHangTransient (causation unproven, and it should stay unproven until someone measures it). Worth considering: restore the focused window first and the rest lazily or on demand, cap the burst, or offer the chooser instead of opening everything. NOT a defect with a proven user report behind it yet - this is the exposure that remains once T1158's leak is gone.
