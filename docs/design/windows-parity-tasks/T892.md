# T892 - Flipping a blocked task to todo from the CLI needs evidence: set-status must require a source note and restate the unblock condition when it un-blocks

## Summary

On 2026-08-16 09:26 a turn folding decision D76 also ran bare 'set-status T443/T857 -Status todo' with no source note and no check of either task's unblock condition (T857's is machine-checkable: powercfg PROCTHROTTLEMAX must read 99, and it read 100). The next turn spent its context re-verifying and re-parking - the second no-evidence reopen of T443's armed watch (D27 was the first). T564 closed this hole for the dashboard by stamping 'dashboard: <button>' into the progress log; the CLI path still journals a naked transition. Fix: when set-status moves a task OUT of any blocked(...) state, require -SourceNote (or an explicit -NoNote-style opt-out for bulk passes), and echo the task's unblock: text in the command output so the caller sees the condition they are claiming is satisfied. Acceptance: a section in test\\win32\\parity-tasks-seat.ps1.

## In plain terms

A task can be parked with a note saying what has to happen before anyone picks
it up again ("wait until the crash happens again"). Right now anything can flip
that task back into the queue with a single command and leave no word about
whether that condition was ever met - so the board says a task is ready when
nobody checked. Twice now the next person spent their whole session
re-discovering that nothing had actually changed. After this, un-parking a task
makes you say what you checked, and it prints the park condition back at you
while you do it.

## Goals

- [x] `set-status` refuses to move a task out of `blocked(...)` without a
      `-SourceNote` saying what was checked
- [x] the same command prints the task's `unblock:` condition, so the caller
      sees the condition they are claiming is satisfied
- [x] a bulk normalisation pass can still get through, and says out loud that
      it bypassed the gate
- [x] acceptance section in `test\win32\parity-tasks-seat.ps1`
