# T554 - Mac: manifest frame can go stale vs a crash right after a resize (T220's Mac half)

## In plain terms

On Windows, a crash or force-kill shortly after resizing a window could bring
the window back at its OLD size on the next launch, because the restore
manifest was written on a 250ms delay and the crash caught it stale. T220
fixed that on Windows by writing the manifest at the instant the resize
gesture ends. The Mac app appears to have the same delayed write, so the same
crash timing may forget a resize there too. This task is to confirm it on a
Mac and apply the same rule.

## Summary

Win32's `Window.savePlacement` used to arm the debounced manifest write
(`markLayoutDirty`, 250ms) at drag-end; a kill inside the debounce stranded
`session-layout.json` (and the agent's layout blobs) at the pre-resize frame,
which restore then replayed over the newer T85 placement memory. T220 made
user geometry gestures sync the manifest IMMEDIATELY (manifest first, then
the placement memory) — the gesture end is already the coalescing point, so
there is no write-storm concern.

The Mac side syncs frame changes through the same-shaped 250ms debounce
(`SessionLayoutManifest.scheduleSync`, "window move/resize (debounced)" per
its own header comment), with `syncNow` flushing only on QUIT — not on a
crash. So the same sequence — live-resize ends, crash within the debounce,
relaunch — plausibly re-attaches at the pre-resize frame there too, racing
whatever AppKit frame autosave remembered.

## What to do

1. Reproduce on a Mac: resize, `kill -9` the app within ~250ms of the
   live-resize ending, relaunch, and check the re-attached window's frame.
2. If confirmed, mirror T220's rule: `windowDidEndLiveResize` (and the
   zoom/unzoom transitions) should run the manifest sync synchronously for
   that window rather than only arming the debounce. The gesture end is the
   coalescing point, so this adds one small file write per completed gesture.
3. State the precedence rule in the Mac code the way
   `docs/design/session-persistence.md` §5.3 now states it (manifest
   authoritative for a RESTORED window's frame; autosave/placement memory
   for a NEW window's size; the manifest must never be the staler of the
   two).

## Validation criteria

- [ ] Repro attempted on a Mac (resize → kill -9 inside the debounce →
      relaunch) and the result recorded here, whether or not it reproduces.
- [ ] If confirmed: fix applied at the live-resize-end / zoom-transition
      sites, and the repro sequence restores the post-resize frame x3.
- [ ] `docs/design/session-persistence.md` §5.3 updated if the Mac rule
      lands differently.
