# T304 - T203a: pure chrome_theme.zig - resolve the system accent + a luminance-aware chrome palette

## Summary

The derivation half of **T203**. One pure module that answers, in one place,
every color question the win32 chrome currently answers with invented
arithmetic: what the user's accent is, and what the bar / hover / text colors
are for a given chrome background under a given light-dark setting.

No surface is rewired here — that is T305. This task lands the module, its
system-accent reader, and the unit tests, so the wiring pass has one agreed
source to consume (the T206 rule: import the constants, do not re-derive
them).

## Why it is split out

T203 carries four deliverables and an acceptance script that mutates system
state (the accent registry + the apps theme) and must restore it. Landing the
derivation first means the wiring pass is a mechanical substitution against a
module that is already asserted at every luminance, instead of a colour
redesign and a five-file edit in one turn.

## What the code does today (VERIFIED by reading at HEAD)

- `Window.paintTabBar` (`src/apprt/win32/Window.zig`) derives the bar as
  `bg + 20` per channel, hover as `+15` more, and hardcodes text at
  `RGB(230,230,230)` / `RGB(150,150,150)` and the close hover at
  `RGB(232,65,65)`. A per-channel add clamps toward white on a light
  background and skews hue on any non-gray one.
- `chooser_rows.zig:232` holds `pub const accent: Rgb = .{ 0x3D, 0x8E, 0xF8 }`
  — the literal T203 names — and `ActivityMonitor.zig:214` holds a SECOND
  invented accent, `RGB(80, 160, 235)`. Two files, two different blues,
  neither the user's.
- `banner_card.fillColor` already does this correctly (composite white at 6%
  on a dark backdrop, black at 4% on a light one, chosen by
  `color_math.isLight`). That is the pattern to generalize, not to reinvent.
- `Window.systemUsesLightTheme()` already reads
  `HKCU\...\Themes\Personalize\AppsUseLightTheme`, so the light/dark SIGNAL
  exists; nothing consumes it for chrome colors.

## The accent source (MEASURED on the box, 2026-08-01)

| key | value | decoded |
|---|---|---|
| `HKCU\Software\Microsoft\Windows\DWM\AccentColor` | `4286644328` = `0xFF810068` | ABGR -> **`#680081`** |
| `HKCU\...\Explorer\Accent\AccentColorMenu` | `4286644328` | same value |
| `HKCU\...\Explorer\Accent\AccentPalette[3]` | `#A94DC1` | **not** the picked accent |

`#680081` is exactly the accent T302 recorded as this box's real one, so
`DWM\AccentColor` (a DWORD stored **ABGR**, not ARGB) is the authoritative
read; `Explorer\Accent\AccentColorMenu` is the fallback and agrees here.

**`AccentPalette` is deliberately NOT used for the light/dark variants.** Its
index semantics are reverse-engineered, and on this box index 3 — the index
usually claimed to be "the accent" — is `#A94DC1`, a color the user never
picked. Variants are derived instead, which is deterministic and testable in
the none lane. Record that as the rejected alternative, with this evidence.

## Deliverables

1. `src/apprt/win32/chrome_theme.zig` — pure, no `win32.zig` import, unit
   tested in the none lane:
   - `accentFromDword(u32) Rgb` — the ABGR decode (pure, so the registry
     encoding is asserted without a registry).
   - A `Palette` resolved from (chrome background, accent, is_dark) carrying
     bar fill, hover fill, primary/secondary text, the accent as drawn, and
     the on-accent foreground.
   - Washes composite toward white or black by `color_math.isLight`, never by
     per-channel addition (the `banner_card.fillColor` rule, generalized).
   - Text meets **4.5:1** against the surface it lands on and the accent as
     drawn meets **3:1** against the chrome background (WCAG 1.4.11, the
     design system's floor for chrome glyphs and meaningful boundaries),
     using `color_math`'s existing WCAG + CIELAB search rather than a new one.
2. A thin win32-side reader for the live system accent (registry, with the
   documented fallback chain and a final fallback that is *stated* rather than
   another invented blue).

## Validation

- Unit tests in the `-Dapp-runtime=none` lane, including a **sweep**: for a
  representative set of backgrounds across the luminance range x a set of
  accents, assert every text color clears 4.5:1 and the accent clears 3:1, and
  that bar / hover / active are mutually distinguishable. A single hand-picked
  pair proves nothing here — that is how `bg + 20` survived.
- `accentFromDword` asserted against the measured `0xFF810068 -> #680081`.
- Both `zig build test` lanes green, `zig build test-agent` green, P1-P3
  ALL PASS.

## What landed (2026-08-01)

- **`src/apprt/win32/chrome_theme.zig`** (new, pure, in the none lane via
  `apprt.zig`): `default_accent` (`#0078D4`, Windows' own), the Fluent surface
  pair, `accentFromDword` (ABGR), `chromeBase(theme, terminal_bg,
  system_light)`, and `Palette`/`resolve` — bar, hover, text, text_secondary,
  accent, on_accent, danger, on_danger, resolved together because each is only
  correct RELATIVE to the others.
- **`src/apprt/win32/system_colors.zig`** (new): the live accent read, DWM key
  first, Explorer's copy as fallback, `accentOrDefault()` for callers that
  just want a color. Referenced from `apprt/win32.zig`'s test block so the
  win32 lane compiles it before T305 has a caller.
- **`color_math.wash(bg, a)`** — the composite hoisted out of THREE private
  copies (`banner_card.fillColor`, `tab_shape.lift`, and `bg + 20` in
  `Window.paintTabBar`), the third of which was the wrong one. Both remaining
  copies now call it.
- **`color_math.contrastAdjustedTo(base, bg, target)`** — the existing CIELAB
  search parameterized by floor; `contrastAdjusted` delegates at 4.5, the
  accent and danger use 3.0.

## Notes for T305

- Two floors, not one: text at 4.5, accent/danger/glyphs at 3.0. `resolve`
  already applies both; a caller re-clamping is a caller re-deriving.
- The sweep found nothing that needed a special case, including pure black and
  pure white backgrounds and a very light saturated accent — the clamp
  fallback (`contrastForeground`) covers the backgrounds where a
  hue-preserving move has no room on either side.
- One number to carry across deliberately: `bar_wash = 0.08` reproduces the
  retired `bg + 20` on a dark background to within a few levels, so T305 is a
  light-theme fix and should NOT visibly move the dark look. If the dark strip
  changes, something else changed with it.
