# T490 - The local agent's pipe has no test-isolation hook, so an acceptance run always shares the user's agent

## Summary

GHOZTTY_PIPE_SUFFIX (T441) moves the APP endpoint only. LocalAgent.pipeName (src/apprt/win32/LocalAgent.zig) derives the agent pipe from build_config.is_debug with no env override, and the agent state dir follows the same rule. Consequence 1: soak.ps1 legitimately runs a ReleaseFast exe under a '-soak' suffix, but session-persistence is on by default, so its panes are owned by the agent that owns the USER'S live sessions. Consequence 2: agent-autostart/agent-pipe/agent-user-env set no suffix at all and lean entirely on the build being Debug. Found while landing T350, whose gate refuses a non-debug exe precisely because the agent half cannot be isolated any other way. Give the agent pipe + state dir the same suffix hook the app endpoint has, then let a release-subject script isolate BOTH halves instead of opting out.

**Verdict on re-verification (2026-09-04): the code half was already done, twice
over, and what survived was the WRONG SENTENCE that filed this task.** The hook
landed as `GHOZTTY_AGENT_INSTANCE` rather than as a second
`GHOZTTY_PIPE_SUFFIX` (T167, `60bb1e9c9`): `src/remote/agent_lineage.zig` forks
the agent pipe, the state dir, the single-instance guard and the autostart value
together. The release-subject half landed with T1158 (`ce943e238`):
`Set-GhozttyTestIsolation -ReleaseSandbox` sets all three knobs in one call,
`soak.ps1` uses it, and `BuildMode.ps1` now REFUSES a partial sandbox instead of
taking the caller's word. Consequence 2's three scripts are isolated too, by a
different route: `agent-autostart` takes `Set-GhozttyTestIsolation`, while
`agent-pipe` and `agent-user-env` bind their own `--listen-pipe` under a
redirected `LOCALAPPDATA` (T680), so no app suffix would have isolated anything
they dial.

What was left was the claim itself, still written down in the two places the
next author reads before touching this: `docs/claude/build.md` ("the agent pipe
has no env override") and the header of `test\win32\lib\Isolation.ps1` ("the
local agent's pipe is build-mode derived with no env override"). That is the
same stale sentence T1158 found in `BuildMode.ps1` and called out as *plausibly
how the soak's author concluded the pipe suffix was all that was available* —
left in two more files, it rebuilds the belief that cost the user a monotonic
pile of pinned sessions. Both now state the three-knob rule and name
`-ReleaseSandbox`.

## In plain terms

When we run the test suite against a build that behaves like the shipping one,
the tests have to talk to their own private copy of Ghoztty — otherwise they
open panes and kill processes inside the terminal you are actually sitting in.
That isolation has worked for a while now. What had not been fixed was the
documentation: two files still told the next person it was impossible, which is
exactly the misunderstanding that once left a growing pile of stray panes in the
user's session list. Nothing you can see changes; the next test that gets
written is less likely to break your terminal.
