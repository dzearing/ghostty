# T1038 - Turning the agent handoff off with the kill switch leaves the app waiting for a handoff that will never come

## In plain terms

There is an off switch for the feature that lets the background session helper
replace itself. Flipping it stops the helper from replacing itself, but it
still tells the terminal that it will — so the terminal politely stands back
and waits, and the helper is then never updated by anyone. A box put on the old
behavior to work around a problem quietly stops getting session-manager fixes
altogether.

## Summary

Found while writing T1037's arm M. `GHOZTTY_AGENT_NO_HANDOFF`
(`handoff.env_disable`, `src\remote\agent\handoff.zig:78`) is documented as the
kill switch that "puts a box back on the pre-T907 behavior without a
downgrade". It only stops the SUPERVISOR from starting
(`Supervisor.start` -> `disabled(alloc)` -> return, handoff.zig:390).

The HELLO capability list is untouched by it:
`Server.default_capabilities` appends `capability.agent_handoff` at comptime on
Windows (`src\remote\agent\server.zig:391`), and the only thing that removes a
capability at runtime is `GHOSTTY_AGENT_SUPPRESS_CAPS`. So the agent keeps
advertising a promise it has just been told not to keep, and the app's policy
believes it: `agent_upgrade.evaluate` returns `.handoff_now` for a stale,
handoff-capable agent with only holder-backed sessions
(`src\apprt\win32\agent_upgrade.zig:189`), which is a deliberate stand-down —
no dialog, no restart, nothing. Pre-T907 behavior is the opposite: that same
state used to raise the mandatory confirmation and refresh.

Net effect of flipping the kill switch on a real box: the agent never replaces
itself, the app never restarts it, and the only remaining path to a newer agent
is a reboot — the exact defect T147 exists to close, reintroduced by the
control that claims to restore the old behavior.

The fix is one line of intent: when the supervisor is disabled, do not
advertise `agent_handoff`. `Server.suppressCapabilities` already exists for
exactly this and is called from `main.zig:207`, so the disable check can feed
it at startup rather than a second mechanism being invented.

## Validation criteria

- [ ] with `GHOZTTY_AGENT_NO_HANDOFF=1`, the agent's HELLO does NOT carry
      `agent_handoff`, and the app's decision line reports
      `handoff-capable=false`
- [ ] a stale agent under that switch takes the mandatory-confirmation path
      again (the pre-T907 behavior the switch promises), not the stand-down
- [ ] the negative control holds: with the switch unset, the stand-down arm is
      unchanged (`test\win32\agent-upgrade.ps1` arm M stays green)
- [ ] a unit test in the `none` lane pins "disabled => not advertised", so the
      two halves cannot drift apart again
