# T879 - Merge-back plan from the divergence inventory: group the 131-file risk set and sequence the merge

## Summary

T516 turned the merge-back risk into data: `docs/design/windows-parity-divergence.md`
lists the 131 files both this fork and upstream ghostty changed since the
fork point (`063ac3ecc`, 2026-05-07), with per-side status and commit counts.
The next step is the plan that data was bought for: group the risk set into
coherent conflict domains (build system, shared core `src/`, macOS app files
we carry patches in, CI/workflow files, docs), decide per group whether the
merge direction is ours-wins / upstream-wins / real three-way work, and
sequence the merge into stages small enough to validate — with the floor
lanes and P1–P3 as the gate after each stage. The plan is a committed doc
under `docs/design/`, and it should also say what to do about the 616
changed-only-upstream files (they arrive clean but still need a post-merge
build+test pass) and whether any upstream change obsoletes open parity tasks.

## In plain terms

We now know exactly which files both we and the original project edited —
those are the places a future merge can go wrong. This task turns that list
into an actual plan: which chunks to merge in what order, what each chunk
risks, and how we prove each chunk landed safely before taking the next.

## Goals

- [x] Group the 131-file risk set into disjoint domains with a per-file merge
      direction derived from data, not from reading 131 diffs
- [x] Sequence the merge into stages small enough to validate, each with a gate
- [x] Say what happens to the 616 changed-only-upstream files
- [x] Answer whether any upstream change supersedes an open parity task
- [x] File the go/no-go as a decision so it reaches the user without blocking

## Validation criteria

- [x] A committed merge-back plan doc under `docs/design/` that accounts for
      every file in the risk set (each is in exactly one group, and every
      group has a merge strategy and a validation gate).
      **How verified:** `docs/design/windows-parity-merge-back-plan.md`. A
      script re-parsed the risk-set table out of
      `windows-parity-divergence.md` and the per-group tables out of the plan
      and diffed the two path sets: 131 risk paths, 131 appendix paths, 131
      unique, 0 missing, 0 extra. Group assignment is first-match-wins by
      path, and the generator reported `UNGROUPED: 0`. All ten groups carry a
      merge direction and a named gate in "Group summary".
- [x] The plan sequences the groups and names the first mergeable stage.
      **How verified:** the "Merge shape" table stages the merge by upstream
      commit range (S1-S6) with per-stage risk-set intersections computed from
      `git diff --name-only <from> <to>`. **S1 (`063ac3ecc..c4c9e945a`) is
      named as the first mergeable stage**, preceded by a Stage 0 of
      preparation that merges no upstream code.
- [x] Open parity tasks that an upstream change supersedes (if any) are
      listed with their ids, or the plan states none were found.
      **How verified:** the plan states **none found**, on two pieces of
      evidence: `git ls-tree -d --name-only ad6e72ddc src/apprt/` returns only
      `src/apprt/gtk` (upstream has no win32 apprt and no `src/apprt/ipc`), and
      a keyword sweep of all 353 open `todo` tasks for shared-core subjects
      returned 15, every one of them win32-frontend / viewer / agent work or
      `seat: mac`. All 15 ids are listed in the plan.
