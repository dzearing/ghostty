# T879 - Merge-back plan from the divergence inventory: group the 131-file risk set and sequence the merge

## Summary

T516 turned the merge-back risk into data: `docs/design/windows-parity-divergence.md`
lists the 131 files both this fork and upstream ghostty changed since the
fork point (`063ac3ecc`, 2026-05-07), with per-side status and commit counts.
The next step is the plan that data was bought for: group the risk set into
coherent conflict domains (build system, shared core `src/`, macOS app files
we carry patches in, CI/workflow files, docs), decide per group whether the
merge direction is ours-wins / upstream-wins / real three-way work, and
sequence the merge into stages small enough to validate — with the floor
lanes and P1–P3 as the gate after each stage. The plan is a committed doc
under `docs/design/`, and it should also say what to do about the 616
changed-only-upstream files (they arrive clean but still need a post-merge
build+test pass) and whether any upstream change obsoletes open parity tasks.

## In plain terms

We now know exactly which files both we and the original project edited —
those are the places a future merge can go wrong. This task turns that list
into an actual plan: which chunks to merge in what order, what each chunk
risks, and how we prove each chunk landed safely before taking the next.

## Validation criteria

- [ ] A committed merge-back plan doc under `docs/design/` that accounts for
      every file in the risk set (each is in exactly one group, and every
      group has a merge strategy and a validation gate).
- [ ] The plan sequences the groups and names the first mergeable stage.
- [ ] Open parity tasks that an upstream change supersedes (if any) are
      listed with their ids, or the plan states none were found.
