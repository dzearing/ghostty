# T417 - One installer: Ghoztty makes any machine session-transferable, retire the standalone agent MSI

## Summary

Investigate, plan, then implement folding the standalone ghoztty-agent
installer into the Ghoztty app install on both platforms, so installing
Ghoztty is all it takes to move sessions between machines. User directive,
2026-08-03: "you install ghoztty on any machine, you can transfer sessions
across machines. Then we can remove the standalone agent."

This task is deliberately an INVESTIGATE -> PLAN -> SPLIT task. Do not start
by editing a .wxs. The first deliverable is a written plan plus the split
tasks it implies; the implementation lands under those.

## What is true today (verified 2026-08-03)

Two agent roles exist, and only one of them ships with the app.

1. LOCAL role - session persistence. The Ghoztty app spawns
   `ghoztty-agent` itself with a local-only transport and never with
   `--relay`: `--listen-pipe=` on Windows (`src/apprt/win32/LocalAgent.zig`
   ~line 755) and `--listen-unix=<dir>/agent.sock` on macOS
   (`macos/Sources/Features/Remote/LocalAgentManager.swift` ~line 25). The
   Windows app MSI already CARRIES `ghoztty-agent.exe` as a required sibling
   of `ghoztty.exe` (T89h; `dist/windows-installer/build-msi.sh` lines
   125-132, 253-257 - the build hard-fails if the agent exe is missing).
   So the app install already ships the binary; what it never does is run it
   in a mode another machine can reach.

2. RELAY role - being reachable from another machine. That is
   `ghoztty-agent --relay=<base>`, which is the ONLY authenticated way a
   machine serves itself (`src/remote/agent/main.zig` lines 37-76), and it
   needs a per-device credential written to `relay.env` by
   `ghoztty-agent --enroll --relay=<base>` (`src/remote/agent/enroll.zig`).
   Getting that on a box today means running the SEPARATE per-user MSI:
   `relay/deploy/msi/ghoztty-agent.wxs` + `relay/deploy/install.ps1`
   (`irm https://<relay>/dl/install.ps1 | iex`), published by
   `relay/deploy/publish-agent.sh` / `scripts/deploy-windows-agent.sh`. It
   installs to `%LOCALAPPDATA%\Programs\Ghoztty Agent\`, writes its own HKCU
   Run key `GhozttyAgent` carrying `--relay=<url>`, adds a Start Menu
   shortcut, and self-enrolls via a browser Google sign-in when no
   DEVICE_TOKEN is present.

Consequences worth naming before designing anything:

- The two roles are two PROCESSES today, on purpose - the local single
  instance guard is written to coexist with a relay agent
  (`src/remote/agent/main.zig` ~line 231, `src/apprt/win32/LocalAgent.zig`
  ~line 25). Whether consolidation means one process serving both transports
  or one INSTALL managing two processes is the first design decision, and it
  is not obvious: one process is simpler to install and reason about, two
  keeps the local session path insulated from relay churn.
- Two HKCU Run keys both named `GhozttyAgent` are in play (app-written for
  persistence per CLAUDE.md; MSI-written with `--relay`). Any consolidation
  has to define one owner of that key, and migrate boxes that have the other.
- Two install dirs and two ARP entries exist on a box that has both
  (`%LOCALAPPDATA%\Programs\Ghoztty` and `...\Ghoztty Agent`), each with its
  own self-update path and its own UpgradeCode. Retiring the standalone one
  means an UNINSTALL/adopt path, not just deleting the .wxs - existing boxes
  (including this dev box and the user's) are already enrolled through it,
  and their `relay.env` credential must survive.
- macOS cannot serve AT ALL right now. There is no Mac equivalent of the
  agent MSI and `LocalAgentManager` never passes `--relay`. So "install
  Ghoztty on any machine and transfer sessions" is a strictly bigger ask on
  the Mac than on Windows: Windows has the capability behind a second
  installer, the Mac does not have the capability. Per the standing platform
  symmetry rule this task is not done when Windows is done.

## Questions the investigation must answer

- One process or two? If one, how does a relay-serving agent avoid dragging
  local session PTYs down with a relay reconnect storm; if two, what owns the
  lifecycle of the second one.
- Where does enrollment live in the product? The relay account sign-in is
  already GUI-only by decision (T141 removed the `+relay-login` CLI verb), and
  the machine chooser already has an account row - so "share this machine"
  most likely belongs there as a toggle, on both platforms, rather than as a
  new CLI verb. Confirm against `src/remote/relay_signin.zig` and
  `src/apprt/win32/RelayAccountRow.zig`.
- Is serving opt-in or on by default once signed in? Default-on makes the
  user's sentence literally true; opt-in is the safer default for a terminal
  that may sit on a machine the user does not want exposed. Pick one, write
  down why.
- Migration: what happens on a box with the standalone agent already
  installed and enrolled. The credential in `%LOCALAPPDATA%\ghoztty\relay.env`
  is shared state the MSI deliberately preserves; adoption should reuse it
  rather than force a re-enroll.
- What actually gets deleted at the end, and what has to stay: `install.ps1`
  is HOSTED at `<relay>/dl/install.ps1` and referenced from the relay README
  and several design docs, so the URL must keep working (or redirect to the
  Ghoztty download) after the MSI stops being published.

## Deliverables

1. A design note (`docs/design/`) answering the questions above, with the
   one-process-vs-two decision and the migration story written down.
2. Split tasks filed for the implementation, at minimum: Windows app-managed
   relay serving + enrollment UI; macOS app-managed relay serving +
   enrollment UI (`seat: mac`); adoption/uninstall of the standalone install;
   retirement of `relay/deploy/msi/`, `relay/deploy/install.ps1`,
   `relay/deploy/publish-agent.sh`, `scripts/deploy-windows-agent.sh` and the
   docs that point at them.
3. Nothing ships in this task itself except the note and the split tasks.
