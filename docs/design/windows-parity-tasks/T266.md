# T266 - In a merged row the top resize edge sits ON the tabs, so a click near a tab's top resizes instead of selecting

## In plain terms

Since the tabs moved up into the window's title bar, the thin strip at the
very top of each tab grabbed the window-resize arrow instead of selecting the
tab. Windows Terminal — measured, not guessed — gives its tabs their whole
height: clicking anywhere on a tab selects it, and you resize the window from
the empty area beside the tabs or from the corners. Ghoztty now does the
same: a tab is never a resize target, and the resize edge still works
everywhere it visibly should.

## Goals

- [x] Measure how much of a tab's top Windows Terminal gives to the resize
      edge, empirically, not from a model of the framework
- [x] If ours is materially thicker, cap it over the tab run (it was: WT
      gives tabs their FULL height — ours now does too, keeping the corners
      and the empty band at full frame thickness)
- [x] Pin the boundary in unit tests at all four scales and probe it live in
      the acceptance suite

## Summary

`caption_layout.ncHitTest` answers `HTTOP`/`HTTOPLEFT`/`HTTOPRIGHT` for the
first `resizeBorder(m, sys_frame)` rows of the band on a restored window, and
that check deliberately comes FIRST - before any button and, since T205, before
the tab run. It has to: a control that answered before the top border would
make a restored window un-resizable from the top in three places, and the user
would just find that the window "sometimes" cannot be resized.

Before T205 that band was pure chrome, so it cost nothing. Now it lands on the
TABS. `sys_frame` is `SM_CYSIZEFRAME + SM_CXPADDEDBORDER`, about 8-9 px at
100% and ~10 px at this box's 125%, against a chiclet whose painted top is
`tab_top_pad` (4 DIP) below the band top. So roughly the top fifth of every
tab resizes the window instead of selecting the tab.

## Why it is filed rather than fixed

Every custom-frame app on Windows has this, Windows Terminal included - the
resize edge has to live somewhere and the window's top row is where Windows
trained users to look for it. The behavior is very likely CORRECT. What is not
established is the SIZE: nobody has measured how much of a tab WT actually
gives to its resize edge, and 10 px out of a 45 px chiclet is enough to be
felt when aiming at a tab's title.

## What to do

1. **Measure the reference.** How many px at the top of a WT tab answer
   `HTTOP`? `WM_NCHITTEST` against a live `WindowsTerminal.exe` answers this in
   minutes and settles it empirically, which is the T240/T246 lesson: a parity
   claim about another app's behavior must cite a measurement, not a model of
   the framework.
2. If ours is materially thicker, cap the band over the TAB RUN specifically
   (leaving it full thickness over the empty drag region and the corners, which
   is where a user actually reaches for a resize), and assert the cap in
   `caption_layout`'s tests at 1.0/1.25/1.5/2.0.
3. If it matches, record the measurement in
   `docs/design/win32-design-system.md` beside the T205 section so the next
   reader does not re-litigate it.

## Resolution (2026-08-06, revised): a tab owns its full height — the frame stops at the strip, like Windows Terminal's actually does

The first resolution written for this task (same day, earlier session)
concluded "we match WT exactly, 9 px of HTTOP over a tab, no code change" from
`WM_NCHITTEST` probes against WT's **top-level** window. That probe answers a
question no user's mouse ever asks: WT 1.24's tab **island child** covers the
tab run from the window's very top row (child rect probed at topOffset=0), it
answers `HTCLIENT` at every row (never `HTTRANSPARENT`), and Windows routes
input to the child under the cursor — so the top-level's `HTTOP` over the tab
run is unreachable. Probing the windows the mouse actually lands on:

- **Over a WT tab: `HTCLIENT` from row 0.** A tab owns its full height; there
  is no resize edge over it at all.
- **Over WT's empty drag band** (its drag-bar child, which starts right of the
  tab run): `HTTOP` for 7 rows at 120 dpi, then `HTCAPTION`. (Slightly under
  the 9-row `SM_CYSIZEFRAME + SM_CXPADDEDBORDER` metric — WT's private
  formula; we keep the stock metric over our own empty band.)

So ours WAS materially thicker over the tabs — 9 rows vs WT's zero — and per
step 2 the band is now capped over the strip: `caption_layout.ncHitTest`
answers the corners first, then hands `x < min(client_right, band_left)` to
the strip at every row. Clicking anywhere on a tab (including its top rows)
selects it — `handleTabBarClick` gates on `y < tabBarHeight()` and hit-tests
by x, so the newly-client rows already route to the tab. The resize edge
keeps full `sys_frame` thickness over the empty band, the caption's own
controls (native Win11 behavior), and both corners (which outrank the strip,
so a tab at the window's edge never blocks the diagonal grab).

Measurement probes are reproducible from the session scratchpad scripts
(`wt-probe*.ps1`): child-window enumeration + `SendMessageTimeout`
`WM_NCHITTEST`, read-only, against live `WindowsTerminal.exe` 1.24.11911.0 at
120 dpi.

## Validation criteria

- [x] Measure WT's resize edge over a tab empirically — done twice: the
      parent-window probe (misleading, see Resolution) and the corrected
      child-window probe: island answers HTCLIENT from row 0 over a tab;
      drag-bar child answers HTTOP only over the empty band.
- [x] `caption_layout` unit tests pin the new boundary at all four scales
      with measured per-dpi frame values (96→8, 120→9, 144→11, 192→13):
      over a tab .client from row 0, corners .top_left, empty band .top at
      the frame's last row and .caption one below, maximized all client —
      tests "over a TAB there is NO top resize edge" and "over the strip the
      TAB wins the top rows"; win32 lane PASS via floor-lane.ps1 (all three
      lanes green).
- [x] `test/win32/chrome-merged-row.ps1` §4 probes the live window: HTCLIENT
      at tab 1's top row and at the old boundary row, HTTOP/HTCAPTION on both
      sides of the frame boundary over the empty band
      (`Get-TestResizeBorder` in `lib/ChromeGeometry.ps1` derives the
      expected thickness the way `caption_layout.resizeBorder` does) —
      ALL PASS.
- [x] Negative control: the pre-fix build passed the OLD §4 assertions
      (HTTOP over a tab), and the unit test "the resize edge still wins over
      a tab" pinned .top at a strip x — both had to be inverted for the new
      behavior, so the probes demonstrably distinguish the two worlds; and
      the empty-band boundary pair (HTTOP then HTCAPTION on adjacent rows)
      proves the live probe can tell adjacent rows apart.
