# T869 - win32 agent integrations (5/8): no runtime registry or aggregate install flow - port RuntimeAgent probe, RuntimeIntegration rollback, refcounted banner and the factory/service layer

## In plain terms

This task ties the earlier pieces into one switch: "set up Claude Code" or
"set up Copilot" as a single action that either fully succeeds or cleanly
undoes itself. It also teaches Ghoztty to notice which agents are installed
on the machine, and to share the helper scripts between agents so removing
one agent's setup never breaks the other's.

## Goals

- [x] Ghoztty can tell which agent CLIs are installed by probing for their
      binaries (never their config folders), with a test seam
- [x] "Set up" for an agent is one action that fully succeeds or cleanly
      undoes only what it created — retries never delete working pieces
- [x] Removing one agent's setup leaves the shared helper scripts in place
      while the other agent still uses them
- [x] When Claude's own plugin already owns the setup, Ghoztty steps aside
      instead of double-installing
- [x] A service layer reports install/uninstall outcomes and per-agent
      status in the same vocabulary the Mac app uses

## Summary

Fifth slice of the T598 split. Port `RuntimeAgent.swift` (+ `RuntimeProbe`),
`RuntimeIntegration.swift`, `RuntimeIntegrationFactory.swift`,
`AgentIntegrationService.swift`.

- **RuntimeAgent**: `claude` / `copilot`; config dirs `.claude` / `.copilot`
  under `%USERPROFILE%`; display names "Claude Code" / "Copilot CLI".
- **RuntimeProbe — Windows translation**: detection is the BINARY, never the
  config dir (Ghoztty writes into that dir; leftovers must not report a
  removed CLI, and a never-run CLI must still detect). Windows probe: PATH
  search for `claude.exe`/`claude.cmd`/`copilot.*` (SearchPathW or `where`-
  equivalent walking PATHEXT), then fallback locations:
  `%USERPROFILE%\.local\bin\`, `%USERPROFILE%\.claude\local\`, npm global
  prefix (`%APPDATA%\npm\`), winget links dir
  (`%LOCALAPPDATA%\Microsoft\WinGet\Links\`). Measured on this box
  2026-08-15: claude at `C:\Users\David\.local\bin\claude.exe`, copilot
  absent. NO login-shell spawn (Mac's zsh -lic probe is the Mac mechanism;
  Windows PATH is process-env + registry, read it directly). Struct-of-
  function-pointers seam so tests stub "exactly these agents installed".
- **RuntimeIntegration**: components in FIXED order banner → skills → hooks
  (hooks LAST — the banner refcount depends on reverse-order processing
  removing hooks first). `install()` gates on `isAvailable`, records which
  components did not exist before, and on failure rolls back ONLY those
  (pre-existing/outdated components are refreshed, never deleted — Mac's
  retry-wipe lesson, spelled out in RuntimeIntegration.swift's comment).
  `uninstall()` reverse order, best-effort, first error rethrown at the end.
  Aggregate state: any not_installed → not_installed; any outdated →
  outdated; else installed.
- **Factory**: plugin-managed gate — when Claude's external `ghoztty` plugin
  is registered (parse `%USERPROFILE%\.claude\plugins\installed_plugins.json`:
  v2 object keyed `name@marketplace`, older array-of-entries shape, unknown
  shape → absent; match plugin NAME only, any marketplace; NEVER substring-
  match the whole file — installPath poisoning), Ghoztty must not own skills
  OR hooks (nil components) — half-gating recreates the split-state bug
  through the other component. Shared-banner refcount:
  `anyHooksReferenceBanner(excluding:)` — banner uninstall is a no-op while
  any OTHER agent's Ghoztty hooks still reference the scripts.
- **Service**: `install`/`uninstall`/`allAgentStatuses` returning the Mac
  outcome vocabulary (installed / upToDate / upgraded / notFound /
  pluginPresent / uninstalled / failed(detail)) for the UI slices. Statuses
  carry detected / state / pluginManaged / bannerSharedWithOther. Blocking
  probes stay off the GUI thread (the ClaudeIntegration.zig detached-thread
  + WM_APP marshal pattern already in the tree).
