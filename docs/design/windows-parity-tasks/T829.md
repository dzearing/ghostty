# T829 - The go-loop cannot come back from an unattended reboot until a human logs in

## Summary

Measured 2026-08-14: the box rebooted at 08:07 on 08-13, minutes after that morning's triage commit, and the loop did not run again until 09:16 on 08-14 - 25 hours, zero tasks closed, M1 unchanged at 119 of 206. The watchdog did its job the moment it existed: its process start time is 09:16:44, i.e. it was not running at all during the outage. Both of its revival paths are user-session-bound - the HKCU Run entry fires at logon, and GhozttyGoLoopWatchdog's principal is logonType=Interactive - so an unattended restart (Windows Update) leaves nothing alive to notice, and T440's 'supervisor has its own supervision' does not cover the case where the supervisor's own session is gone. Wanted: a revival path that survives a reboot with no interactive logon, or, if a GUI loop genuinely requires a session, a loud out-of-band signal that the loop is down rather than silence.

## In plain terms

When Windows restarts this machine on its own - an update at three in the
morning - it comes back to the lock screen and stops there. Nothing else on the
box can run until somebody walks over and signs in, so the automation that works
through the task list simply stops, and nothing anywhere says it stopped. Last
time that cost a full day of work and the only way anyone found out was by
noticing the board had not moved.

After this, the machine says so. The moment work resumes, the first thing
printed is how long the machine sat there with nobody signed in, measured rather
than guessed, and the one Windows setting that would have prevented it. The
parts that are ours to fix are fixed outright: work restarts the instant anyone
signs in instead of up to ten minutes later, it is no longer skipped when the
machine is on battery, and it can no longer be killed off after three days by a
timer nobody knew was set.

## Goals

- [x] measure the real gap between power-on and a usable desktop, instead of
      inferring it from settings that lie
- [x] say it out loud on the way back, once per restart, with the fix a person
      can act on
- [x] restart the supervisor the instant a session exists, not minutes later
- [x] stop the supervisor being skipped on battery or killed by a hidden
      72-hour limit
- [x] one owner for the scheduled task's shape, so the flags cannot drift apart
      again
- [x] acceptance coverage that does not require rebooting the box

## Validation criteria

- [x] `go-loop-boot.ps1 check` reproduces the measured outage on this box from
      evidence alone - it reports `waited-for-human (this boot: desktop 1d 1h 9m
      after power-on)` against the 2026-08-13 08:07 boot, which is the 25 hours
      the summary describes, read off `LastBootUpTime` and explorer.exe's start
      time in this session.
- [x] `record` writes one row per boot and is silent on every later call:
      verified live (second call printed nothing, ledger stayed at one row) and
      by V6/V7 in `test\win32\go-loop-guard.ps1`.
- [x] `go-loop-exec.ps1 claim` prints the outage block - verified by running
      claim after the wiring (see the log entry) and by section V's fixture
      arms.
- [x] the revive task now fires AT LOGON, is not battery-gated, and has no
      execution time limit - read back out of `schtasks /query /xml` after
      `install` (`<LogonTrigger>`, `DisallowStartIfOnBatteries=false`,
      `StopIfGoingOnBatteries=false`, `ExecutionTimeLimit=PT0S`) and asserted
      read-only against the REAL task by V16-V18.
- [x] `install` is idempotent and verifies its own write (V12-V14); the
      watchdog's `-Install` delegates to it rather than registering a second
      shape (V19).
- [x] `test\win32\go-loop-guard.ps1` ALL PASS with zero skips, stamp updated
      (19 new assertions in section V; the guard's existing `scripts\go-loop-*`
      glob covers the new script automatically).
- [ ] link 1 itself - the box signing in without a human - is a one-time Windows
      setting and is left to the user by design; `check` exits 1 and names it
      until it is on. Once it is, the next reboot's record will say
      `signed in by itself`, and that is the proof.
