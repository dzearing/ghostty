# T829 - The go-loop cannot come back from an unattended reboot until a human logs in

## Summary

Measured 2026-08-14: the box rebooted at 08:07 on 08-13, minutes after that morning's triage commit, and the loop did not run again until 09:16 on 08-14 - 25 hours, zero tasks closed, M1 unchanged at 119 of 206. The watchdog did its job the moment it existed: its process start time is 09:16:44, i.e. it was not running at all during the outage. Both of its revival paths are user-session-bound - the HKCU Run entry fires at logon, and GhozttyGoLoopWatchdog's principal is logonType=Interactive - so an unattended restart (Windows Update) leaves nothing alive to notice, and T440's 'supervisor has its own supervision' does not cover the case where the supervisor's own session is gone. Wanted: a revival path that survives a reboot with no interactive logon, or, if a GUI loop genuinely requires a session, a loud out-of-band signal that the loop is down rather than silence.
