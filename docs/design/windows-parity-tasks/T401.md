# T401 - A win32 acceptance script run concurrently with zig build test-agent wedges the test lane

## In plain terms

Running the automated test suite at the same time as one of the hands-on
Windows check scripts used to freeze the test suite for over ten minutes with
no output — it looked like the tests were broken when really the two jobs were
tripping over each other. That freeze has since been fixed at the root (a wait
inside the test harness that could sleep forever is now given a deadline, so
the worst case is a clearly named test failure in about 30 seconds). This task
verified the fix holds under the exact original collision and wrote the
"don't run these two things at once" rule where the next person will read it.

## Goals

- [x] Reproduce the original collision (test lane running while the two
      acceptance scripts run against it) and see whether it still wedges.
- [x] Identify what actually caused the wedge, from evidence.
- [x] Make sure the failure mode can never again be a silent 11-minute hang.
- [x] Write the no-overlap rule into go.md step 3 where turns will read it.

## Validation criteria

- [x] `zig build test-agent` finishes green while `agent-pipe.ps1` runs
      against it — verified twice on box, 2026-08-05 (lane exit 0 in 110s and
      105s; scripts ALL PASS both times; per-30s CPU sampling of both test
      binaries showed steady progress, no wedge, clean exit).
- [x] The wedge mechanism itself is bounded — verified by reading
      23d13c7f8 (T258): the test loopback's untimed `cond.wait` now fails
      with `error.LoopbackReadTimeout` after 30s, naming the waiting test;
      that commit's own negative proof recreated the hang shape and got a
      red failure in ~30s instead of a wedge.
- [x] go.md step 3 carries the sequential-not-overlapped rule (this commit).

## Summary

Observed on box during T96 (2026-08-02). `zig build test-agent` was started in
the background; while it ran, `test\win32\agent-pipe.ps1` and
`test\win32\chooser-sessions.ps1` were run in the foreground. Both agent test
binaries **spun at 100% CPU for 11+ minutes** with no output and never
finished:

```
40308 ghoztty-agent-core-test  CPU 108s  running 11 min
45772 ghoztty-agent-test       CPU 108s  running 11 min
```

Killed and re-run **alone**, with nothing else touching agents, the same lane
was green in a few minutes (exit 0). So the lane is not flaky here — it was
wedged by the concurrent scripts.

## Why this matters more than one lost run

The turn read this as "test-agent is flaky again" (T258, T346 have trained
exactly that reflex) and nearly filed a third flake task over a
self-inflicted collision. A lane that hangs because of *what else the box is
doing* is worse than a lane that fails: it burns 10+ minutes before anyone
suspects it, and the natural response is to re-run rather than investigate.

## Suspected cause (NOT verified — verify before fixing)

Both scripts deliberately reach for per-user agent state:

- `agent-pipe.ps1` starts an agent with `--force-replace`, which exists
  precisely to **win the per-user single-instance guard** away from whoever
  holds it.
- Both scripts `Stop-Process` every `ghoztty-agent.exe` whose path is under
  `zig-out`. The agent TEST binaries run from `.zig-cache\o\...`, so they are
  not matched by that filter — but they may still be contending for the same
  per-user guard / pipe namespace that `--force-replace` takes.

That is a hypothesis with one supporting observation, not a diagnosis. Confirm
by reproducing (start `test-agent`, then run `agent-pipe.ps1`) and by finding
what the test binaries are actually spinning on — a stack sample of the two
wedged processes is the direct evidence, and this box has the cdb recipe.

## Root cause (verified 2026-08-05)

The per-user guard hypothesis was wrong, and so was the "100% CPU" reading of
the original evidence. 108s of CPU over 11+ minutes is ~16% of one core — and
108s is almost exactly what each test binary consumes in a NORMAL full run
(measured: the lane finishes in ~110s with both binaries near one core the
whole way). The binaries had done essentially all their work and were
**blocked**, not spinning.

What they were blocked on is named by commit 23d13c7f8 (T258, 2026-08-05):
the agent test loopback's client-read direction waited in an **untimed
`cond.wait`** for a frame that would never be framed — "the ~11-minute
flat-CPU hang T205/T311 hit in the win32 lane". The trigger chain: box load
from the concurrent acceptance scripts let the pre-T346 iteration-count spin
waits expire before the server thread ever ran, one face of that raced into
the loopback's untimed wait, and the lane froze with no output. So the
concurrency was the *load trigger*, not a namespace collision — consistent
with the earlier finding that neither script's kill filters nor the per-user
mutex reach the test binaries (`remote-test-client.exe` is spawned only by
acceptance scripts, never by the test lane; nothing under `src/remote/agent`
references it).

Fixed at the root by the T346 → T258 → T183 sequence: deadline waits instead
of spin budgets, a 30s liveness deadline (`error.LoopbackReadTimeout`) on the
loopback itself, and timed-out waits failing red at the wait instead of
panicking on a null. Verified here by running the exact T401 collision twice
(lane green both times, scripts ALL PASS both times). Residual risk of
overlap is now a red flake that names its wait, not a silent wedge — and the
no-overlap rule is written into go.md step 3 so turns stop inviting it.
Belt-and-braces mutual exclusion in the suite runner remains with T361.

## Fix directions (pick after the cause is known)

- Give the agent unit tests a **per-run-unique** single-instance/pipe
  namespace (they already take `--port-file`/`--sessions-file` overrides for
  exactly this reason), so no acceptance script can collide with them.
- And/or a **mutual exclusion** in the suite runner (T361) so the zig test
  lanes and the on-box acceptance scripts never overlap, with the rule written
  where a turn will read it — `go.md` step 3 currently invites running them
  together.

## Validation

Start `zig build test-agent`, run `agent-pipe.ps1` against it, and have the
lane still finish green. Today that combination hangs.
