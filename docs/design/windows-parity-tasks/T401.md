# T401 - A win32 acceptance script run concurrently with zig build test-agent wedges the test lane

## Summary

Observed on box during T96 (2026-08-02). `zig build test-agent` was started in
the background; while it ran, `test\win32\agent-pipe.ps1` and
`test\win32\chooser-sessions.ps1` were run in the foreground. Both agent test
binaries **spun at 100% CPU for 11+ minutes** with no output and never
finished:

```
40308 ghoztty-agent-core-test  CPU 108s  running 11 min
45772 ghoztty-agent-test       CPU 108s  running 11 min
```

Killed and re-run **alone**, with nothing else touching agents, the same lane
was green in a few minutes (exit 0). So the lane is not flaky here — it was
wedged by the concurrent scripts.

## Why this matters more than one lost run

The turn read this as "test-agent is flaky again" (T258, T346 have trained
exactly that reflex) and nearly filed a third flake task over a
self-inflicted collision. A lane that hangs because of *what else the box is
doing* is worse than a lane that fails: it burns 10+ minutes before anyone
suspects it, and the natural response is to re-run rather than investigate.

## Suspected cause (NOT verified — verify before fixing)

Both scripts deliberately reach for per-user agent state:

- `agent-pipe.ps1` starts an agent with `--force-replace`, which exists
  precisely to **win the per-user single-instance guard** away from whoever
  holds it.
- Both scripts `Stop-Process` every `ghoztty-agent.exe` whose path is under
  `zig-out`. The agent TEST binaries run from `.zig-cache\o\...`, so they are
  not matched by that filter — but they may still be contending for the same
  per-user guard / pipe namespace that `--force-replace` takes.

That is a hypothesis with one supporting observation, not a diagnosis. Confirm
by reproducing (start `test-agent`, then run `agent-pipe.ps1`) and by finding
what the test binaries are actually spinning on — a stack sample of the two
wedged processes is the direct evidence, and this box has the cdb recipe.

## Fix directions (pick after the cause is known)

- Give the agent unit tests a **per-run-unique** single-instance/pipe
  namespace (they already take `--port-file`/`--sessions-file` overrides for
  exactly this reason), so no acceptance script can collide with them.
- And/or a **mutual exclusion** in the suite runner (T361) so the zig test
  lanes and the on-box acceptance scripts never overlap, with the rule written
  where a turn will read it — `go.md` step 3 currently invites running them
  together.

## Validation

Start `zig build test-agent`, run `agent-pipe.ps1` against it, and have the
lane still finish green. Today that combination hangs.
