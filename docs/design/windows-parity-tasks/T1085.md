# T1085 - session-open A9 failed once in a batch run and passed five times alone: the pane pid and the session pid disagreed

## In plain terms

A test that checks two different parts of Ghoztty agree about which process is
running inside a pane failed once, in the middle of a long batch of tests, and
then passed every time it was run on its own. Either something the previous test
left behind confused it, or there is a timing window where the two answers are
briefly different. Recorded so the next sighting is a pattern instead of a
surprise.

## Summary

`test\win32\session-open.ps1` A9 - *"+list reports the same pid for the pane"* -
compares the pid `+sessions --json` reports (answered by the agent) with the pid
`+list` reports (answered by the app). They disagreed on ONE run.

Circumstances (T351, 2026-08-21): the failing run was the second of two
consecutive runs inside a 32-run batch, immediately after `chooser-sessions.ps1`.
Investigated at once because it looked like fallout from that task's CleanSlate
conversion, and ruled out:

- the file as it stands at `HEAD` (pre-sweep) passed twice consecutively;
- the converted file then passed **five** consecutive runs, four of them
  back-to-back in one shell;
- after a clean run, the only ghoztty processes on the box were the user's
  installed release - no repo-build leftovers for a following run to attach to.

So it is neither a leftover the sweep stopped killing nor a deterministic
regression. What remains is a cross-script interaction (state from the preceding
harness) or a genuine race between the agent's view and the app's view of a
freshly-created pane. The second would be a real product bug, not a harness one.

## What to do

- Re-run the exact batch order (`chooser-sessions.ps1` then `session-open.ps1`,
  twice) and see whether it reproduces; that separates the two hypotheses.
- If it is a race, A9 should say WHICH pid each side gave, so one sighting is
  enough to tell a stale pid from an unrelated one.

## Validation criteria

- [ ] either a reproduction with a named cause, or A9 reporting both pids so the
      next occurrence is diagnosable from its log alone
