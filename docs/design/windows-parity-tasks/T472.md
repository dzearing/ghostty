# T472 - Flaky win32 lane: remote.connection 'inbound DATA routing' drainChannel spins out under load, then panics in destroy

## In plain terms

One of the automated tests fails at random — not because anything is broken,
but because it gives up waiting after a fixed number of tries, and on a busy
machine that runs out before the data it is waiting for arrives. When it gives
up it does not fail cleanly either: it crashes the whole test run with a
confusing message that looks like a serious defect.

The cost is trust. A test that cries wolf trains whoever is watching to shrug
at a red run, which is exactly when a real failure slips through. Every red run
also costs about ten extra minutes, because the crash catcher re-runs the whole
binary under a debugger trying to capture a stack for a crash that was never
real.

## Goals

- [x] Make the drain wait on a deadline (wall clock), not a spin count, so a
      loaded machine cannot manufacture a timeout
- [x] Make the timeout fail the test cleanly instead of panicking in `destroy`
      (already true: closed by T693, verified rather than rebuilt — see below)
- [x] Re-run the lane enough times to show it stable (`floor-lane.ps1 -Lane
      win32 -Repeat 5`)

## Validation criteria

- [x] Every spin-count oracle in `src/remote/connection.zig`'s tests is a
      wall-clock deadline instead — five sites: `drainChannel`, `spinUntil`, the
      two T739 `streamPos` waits, and the metrics-unsub wait. `grep` for
      `spins` in the file returns nothing.
- [x] A spent budget is a `error.Timeout`, and no number of yields can spend a
      budget that has not elapsed — unit test `T472: a test wait is bounded by
      the wall clock, not by a spin count`, green in the `none` and `win32`
      lanes. Its second half is the property the old oracle lacked: 200 000
      yields against a ten-minute budget, still not expired.
- [x] A `drainChannel` timeout names how far it got — prints the budget, the
      collected/wanted byte counts and the bytes themselves before returning
      `error.Timeout`.
- [x] The reported failure mode (`inbound DATA routing` timing out, then
      panicking in `destroy`) does not recur — 15 win32-lane runs and 5 agent
      runs on 2026-08-14, zero occurrences; `-Lane win32 -Repeat 5` is 5/5.
- [x] Floor: `none` PASS, `win32` PASS (5/5 on `-Repeat 5`), `agent` PASS on 2

## Summary

Seen during T431's floor run, on an otherwise green tree, in code T431 does not
touch:

```
error: while executing test 'remote.connection.test.inbound DATA routing:
bytes land in the right channel; unknown is dropped', the following command
exited with code 3
thread 42120 panic: reached unreachable code
  src/remote/connection.zig:3513  if (spins > 100_000) return error.Timeout;
  src/remote/connection.zig:1462  assert(self.writer_thread == null);   <- destroy
```

`FLOOR SUMMARY: none#1=PASS win32#1=FAIL agent#1=PASS`, and then — the tell —
the crash-catch pass re-ran the very same binary and reported *"no crash in 1
attempt(s) — the program ran to completion (exit 0)"*. Same bits, same box,
opposite result: a timing flake, not a defect.

## Two separate faults, and the second is the expensive one

1. **The oracle is a spin count, not a deadline.** `drainChannel`
   (`src/remote/connection.zig:3505`) polls `ch.pop` and gives up after 100 000
   fruitless spins with `error.Timeout`. A spin count measures *scheduler
   contention*, not elapsed time — on a box running three test lanes and a
   WebView2 host, 100 000 yields can pass in well under the time the writer
   thread needs. A wall-clock deadline (generous — seconds) cannot be starved
   this way, and says what it means.

2. **The timeout does not fail, it panics.** The `try drainChannel(...)`
   propagates the error out of the test body, which runs `defer
   conn.destroy(alloc)` while the writer thread is still alive, and
   `destroy`'s `assert(self.writer_thread == null)` reaches unreachable code.
   So a soft timeout is laundered into `0x80000003 STATUS_BREAKPOINT`, which
   `floor-lane.ps1` correctly reports as a crash and then spends ~2.5 minutes
   chasing under cdb. The test should shut the connection down on the error
   path before destroying it, so a timeout reads as a failed assertion with the
   byte counts in it rather than as a segfault.

Fixing (2) is worth doing even if (1) never fires again: it is the difference
between a red run you can read and one you have to excavate.
