# T278 - The agent wedges at max_sessions: dead pinned tombstones are never reaped, so every new pane comes up with no shell and nothing says so

## In plain terms

Ghoztty remembers your terminal panes so they survive closing the app. Each one
it remembers takes a slot, and there are 256 slots - but slots were never given
back when a pane's program had already ended. After enough weeks of use every
slot was held by a pane that no longer existed, and from that point on every NEW
terminal you opened came up completely blank: no prompt, no cursor, typing did
nothing, and no message anywhere said why. It looked exactly like a hung
terminal, and the only cure was to find and delete a file by hand.

Afterwards, a remembered-but-finished pane no longer holds a slot, so opening a
terminal keeps working no matter how long the app has been in use.

## Goals

- [x] Reproduce the wedge on the box with an automated script
- [x] A finished (dead) session never denies a new pane its shell
- [x] A genuinely full agent still refuses, and says so in its log
- [x] Remembered sessions are still restorable - the reboot floor is unchanged
- [x] Unit tests in the agent lane + an on-box acceptance script

## Summary

Found while validating T224: **P2 and P3 acceptance failed on the box with a
clean tree and no product change.** The cause is not in the IPC verbs they
test - the local agent had reached its 256-session cap entirely with DEAD
tombstones, so every new pane was created with no child process. `+read`
returns "failed to read terminal content", `+send-keys` goes nowhere, and
`+list` shows the pane as `running` with `pid:0` and an empty command.

Nothing anywhere reports the refusal. The pane simply comes up empty and stays
that way, which is indistinguishable from a hung shell.

## Evidence (MEASURED on box 2026-08-01, debug build, clean tree)

| probe | result |
| --- | --- |
| `ipc-p1.ps1` | ALL PASS |
| `ipc-p2.ps1` | 2-5 FAILURE(S) (varies: leaf counts, "command ran in pane", "tab title tracks shell") |
| `ipc-p3.ps1` | 3 FAILURE(S) ("read exit 0", "marker line exact", "OSC busy set") |
| launch with `--session-persistence=false`, `+send-keys` then `+read` | **exit 0, marker present, pid populated** |
| launch with persistence ON (default), same probe | `+read` exit 1, "failed to read terminal content" |
| `+sessions --json` count | **256** - every one `alive=False`, `pid=0`, `pinned=True`, empty `argv` |
| `%LOCALAPPDATA%\ghoztty\local-agent-debug\sessions.json` | 256 records, 26451 bytes |
| `%LOCALAPPDATA%\ghoztty\local-agent\sessions.json` (the USER's release agent) | 2 records - not affected yet |

`src/remote/agent/session.zig`:

```zig
pub const max_sessions: usize = 256;
...
if (self.by_id.count() >= max_sessions) return error.TooManySessions;   // create
if (self.by_id.count() >= max_sessions) return error.TooManySessions;   // adopt/load
```

So the cap counts DEAD sessions, and dead sessions are `pinned` (local panes
are pinned so they survive the viewer quitting), which is exactly what exempts
them from the agent's idle-TTL reaper. The set only ever grows. On this box it
took some weeks of acceptance runs to fill; a user with long-lived panes gets
there more slowly but by the same one-way ratchet.

## The two defects

1. **A dead session holds a slot forever.** `pinned` exists to stop the
   idle-TTL reaper from killing a session whose viewer went away - a claim
   about a LIVE child. A tombstone with `pid=0` and no argv has nothing to
   protect. Reap dead sessions (with whatever grace the relaunch flow needs -
   `session-relaunch` materializes a tombstone deliberately, so the rule is
   "dead AND not awaiting relaunch", not "dead"), and/or exclude dead
   sessions from the cap check.
2. **`error.TooManySessions` is silent at the pane.** The pane is created,
   reports `running`, and has no child. Surface the failure where the user is
   looking: a pane notice + banner (the T230 `notify` path already has exactly
   this shape), and a log line on the app side.

## Repro / recovery on the box

The debug agent's state is sidelined, not deleted:

```
%LOCALAPPDATA%\ghoztty\local-agent-debug\sessions.json
  -> sessions.json.bak-t278-<stamp>
```

Kill `zig-out\bin\ghoztty-agent.exe` first, or it rewrites the file on exit.
After that P1-P3 pass again. **The acceptance suite will refill it** - which is
the second reason to fix the reaper rather than to keep sidelining the file.

## Validation

- With 256 dead tombstones in `sessions.json`, a fresh agent still creates a
  working pane (the reaper drops them), and `+sessions` reports the live set.
- A genuinely-at-capacity agent (256 LIVE sessions) still refuses, and the
  refusal is visible in the pane and in the log - not an empty pane.
- P1-P3 green across a full acceptance-suite run followed immediately by a
  second one (the run that used to push the count up).
- A `session-relaunch` tombstone still survives long enough to be relaunched
  (`test/win32/session-relaunch-notify.ps1` stays green).

## What landed (2026-08-04)

**The cap counts LIVE sessions.** `session.max_sessions` (256) now bounds only
sessions that own a child process; `SessionTable.create` gates on the new
`liveCount()`. A tombstone owns no process and can no longer be the reason a
user is denied a shell. Tombstones get their own bound, `max_dead_sessions`,
deliberately set to the SAME 256 rather than something smaller - trimming harder
would trade this wedge for a quieter regression (a restore that silently drops
somebody's sessions), and it keeps the split caps at the total the single cap
already allowed. `SessionTable.materialize` enforces it with a distinct
`error.TooManyTombstones`.

**An over-full file keeps the NEWEST.** `loadPersisted` sorts records by
`created_ms` descending before materializing, so which sessions survive an
over-full file is an answer rather than a coin toss (`persistMeta` writes in
hash-map iteration order). One summary warn line names how many were dropped
instead of a wall of per-record warnings.

**The agent says no out loud.** `Server.handleOpen` logs
`OPEN refused: <err> (live=N/256 dead=M/256) - the pane will come up with no
shell`. Counts, not just the error name: "at the live cap" and "out of memory"
are different problems with the same symptom.

The other half of defect 2 - telling the CLIENT, so the pane says why instead of
timing out blank after 10 s - is split out as **T469**, with the
capability-gated `open_failed` design worked out there (see D8 for why).
**T470** carries a related find: a materialized tombstone eagerly allocates a
full 2 MB output ring it never uses.

### Evidence (MEASURED on box 2026-08-04, debug build)

`test/win32/agent-session-cap.ps1` (new) seeds 256 dead tombstones into a
private per-run `LOCALAPPDATA`, brings the GUI up on a background desktop, and
demands a working pane. Run against the build BEFORE the fix, it reproduced the
wedge exactly:

```
== C: control - a clean agent opens a working pane
  PASS C the pane has a real child (pid != 0), not a refused OPEN
  PASS C the pane takes input and echoes it back
== A: 256 dead tombstones must not cost the user a pane
  FAIL A the pane has a real child (pid != 0), not a refused OPEN
  FAIL A the pane takes input and echoes it back
```

After the fix, `ALL PASS (14 checks)` - and the roster oracle is real: 257 rows
total, 1 alive, so the tombstones are still there (the reboot floor is intact)
and simply no longer deny anyone a shell.

| lane / script | result |
| --- | --- |
| `scripts\floor-lane.ps1 -Lane all` | `ALL LANES PASS` (none 286s, win32 297s, agent 136s) |
| `test\win32\agent-session-cap.ps1` | ALL PASS (14) |
| `ipc-p1` / `ipc-p2` / `ipc-p3` | ALL PASS - and again immediately after, with the debug agent's `sessions.json` steady at 5 records across both runs |

New unit tests in the agent lane (`src/remote/agent/session.zig`): a table full

refuses and gives the slot back when a session dies; an over-full file keeps the
newest.
