# T975 - After a reboot nothing comes back: the panes that were open are replaced by one empty window

## Summary

Found 2026-08-18 validating T922, and reproduced twice outside the acceptance harness. Shape: build a 2-window / 3-pane layout with persistent sessions, then kill the app, the session manager AND every --pty-host holder (what a reboot does since T909 put each session's ConPTY in a holder that outlives its manager). Relaunch the app against that state: it opens ONE fresh default window with a brand-new pane - a new pane id, cwd C:\Users\David, no notice - and the second window with its two commanded panes never returns. Both windows and all three sessions are present in session-layout-debug.json and in the agent's sessions.json (each with a holder_pid whose process is gone). Evidence: test\win32\session-relaunch-notify.ps1 arm A now scores 'A2 the layout restored (3 panes)' FAIL with 1 leaf; its app stderr shows 'local agent did not become dialable within 2000ms' then repeated ConnectionRefused, yet a hand-started ghoztty-agent.exe with the SAME --listen-pipe/--port-file/--sessions-file against that exact state dir is listening in 0.3s - so the agent binary handles dead holder_pids fine and the failure is on the app side (or in what the app spawns). Not caused by T922: its code only runs inside the did_notify branch of an attach that never happens here. Until this is fixed a reboot loses the user's whole layout, and every restore-path acceptance arm is unscoreable.

## In plain terms

Restart the machine and your terminal comes back empty. Every window you had
open, every split, every shell you left running is replaced by a single blank
window in your home directory — the panes are still recorded on disk, they just
never come back, and nothing on screen says why. After this lands, a reboot
brings the windows and panes back the way it always should have: same layout,
same directories, with the "session interrupted" notice above each pane that
lost its program.

## Goals

- [x] After a full kill of the app, the session manager and every PTY holder,
      the next launch restores every recorded window and pane
- [x] The freshly spawned session manager is reachable within the app's launch
      budget even when nothing it recorded is still alive
- [x] A client that gives up on a connection can never leave the session
      manager unable to serve anybody again
- [x] Both defects have regression tests with a negative control

## Root cause

Two defects, chained. The visible failure needed both.

1. **The listener wedged permanently on an abandoned connection**
   (`src/remote/pipe_stream.zig`). `PipeListener.accept` created the next pipe
   instance ahead of time; when a client OPENED that instance and then went
   away before the server called `ConnectNamedPipe`, the call failed, `accept`
   returned `AcceptFailed` — and left the dead instance in `next`. Every later
   accept retried the same corpse with the same result: ten
   `ghoztty-agent: pipe accept error: AcceptFailed` lines a second, forever,
   and not one connection served for the life of the process.

2. **Startup adoption held the listener shut for 2s per dead holder**
   (`src/remote/agent/pty_holder_child.zig`). Holder adoption deliberately runs
   before the agent serves anybody, and it dialed each recorded holder for
   `dial_timeout_ms` (2000ms) — serially. After a reboot every recorded holder
   is dead, so three sessions cost six seconds of silence.

Together: the app spawns the agent, waits `spawn_deadline_ms` (2000ms), and
gives up while adoption is still running — and its abandoned dial is exactly
the poison in (1), so the agent it just started never serves anyone again. The
app then restores "only windows that need no agent", which is one empty window.

That is also why the T975 report's hand-started agent looked healthy: nothing
had aborted a dial on it yet.

## Fix

- `PipeListener.accept` now drops a pending instance whose `ConnectNamedPipe`
  failed and replaces it (`dropPending`), creating the replacement BEFORE
  closing the broken one so the pipe name never goes unbound. The caller still
  sees `AcceptFailed` and still backs off; the difference is that the next
  accept waits on a healthy instance. This covers the agent's listener, the
  holder's own control pipe and the handoff listener — all three share it.
- `adopt` asks the process table before it dials: a recorded holder whose pid
  is gone returns `error.HolderProcessGone` immediately. One-directional on
  purpose — anything unanswerable reads as "still there", so the dial stays the
  authority and a permission hiccup can never abandon a live holder.

## Validation criteria

- [x] A client that opens a pipe instance and vanishes before `accept()` does
      not stop the listener serving later clients — unit test
      `PipeListener: a client that vanishes before accept() does not wedge the
      listener` (`zig build test-agent`), with the negative control run: with
      `dropPending` reverted the test FAILS at the `served` assertion.
- [x] A recorded holder whose process is gone is abandoned in well under the
      dial timeout — unit test `adopt: a recorded holder whose process is gone
      is abandoned without paying the dial timeout` asserts
      `error.HolderProcessGone` in <500ms against a pid it watched exit.
- [x] End-to-end reboot shape (2 windows / 3 panes, app + agent + every holder
      killed, app relaunched): the app log reports
      `shared local-agent connection ready`, `session-restore: restored 2
      window(s)` and `attached 3 pane(s)`, and three `--pty-host` holders are
      running again. Before the fix the same script produced `local agent did
      not become dialable within 2000ms` and one empty window.
- [x] `test\win32\session-relaunch-notify.ps1` scores the reported failure —
      arm A's **A2 "the layout restored (3 panes)" PASSES**, as do B2/B3, C, D,
      E0b and every F arm: 98 passed / 6 failed, from a run where arm A used to
      be unscoreable. The six reds are other tasks' arms and are named in the
      progress log (A12/A15/A16/A17 → T922, E3/E4 → T977); the harness stamp
      therefore stays due, which is why this commit takes `-NoGuardDue`.
- [x] Floor green: `scripts\floor-lane.ps1 -Lane all`.
