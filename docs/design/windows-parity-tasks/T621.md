# T621 - Agent grid snapshot carries no scrollback, so every snapshot-less attach still replays the whole ring

## In plain terms

When you take over terminal sessions that are running on another machine — or
resume one you have never had open here — every pane has to re-send its whole
recent history over the network before it is usable, and the history above the
visible screen can come back looking mangled. The screen itself is already
correct; it is the scrollback, and the wait, that are not. This makes those
panes come up immediately and with clean history.

## Goals

- [x] the agent's per-session emulator retains bounded scrollback
      (`grid_snapshot.max_scrollback_bytes`, 1 MiB)
- [x] the attach snapshot it sends includes that scrollback, at the attaching
      client's geometry (`ensureSize` reflows before `snapshotAlloc` serializes)
- [x] a snapshot-less attach can skip the raw ring replay entirely
- [x] the agent's memory ceiling per session is stated and bounded (~3 MB:
      the 2 MB raw ring plus this 1 MiB of grid)
- [x] skew-safe: negotiated, so an older peer keeps today's behavior
      (`capability.grid_scrollback`)

## Summary

`grid_snapshot.GridEmulator` runs with `max_scrollback = 0`
(`src/remote/agent/grid_snapshot.zig`), so the repaint the agent appends after a
gap-fill covers only the VISIBLE screen. That is why a snapshot-less ATTACH
(`last_byte_offset == 0`) must still replay the whole raw ring first: the ring is
the only source of scrollback the client has.

T413 established that this — not the layout blob — is where the remaining loss
on the cross-machine paths lives. Two paths take it today:

- **"Restore All" from an agent-held layout blob** (T335/T336). Blobs carry no
  WP-D3 snapshot by design (see `layout_blobs.serializeWindow` and design
  §5.4.1), so every rebuilt pane attaches at `offset=0`.
- **Resume-one from the chooser's roster** — a session this viewer has never had
  open has no local manifest entry either, so it can never have a WP-D3 snapshot
  regardless of what blobs carry.

Cost per pane: up to the ring size (2 MB default) on the wire, over a relay for
the cross-machine case, plus a client-side parse of geometry-bound VT. T106's
capture-geometry reflow makes the recent segments faithful, but the ring is a
concatenation of segments drawn at different geometries and only one of them can
be replayed at its own size.

## Details

The shape to build:

- Give `GridEmulator` a bounded `max_scrollback` (a real number, chosen against
  the agent's per-session memory budget — the raw ring is already 2 MB/session,
  so this is a second, comparable allocation and the ceiling must be deliberate).
- Have `snapshotAlloc` serialize that scrollback ahead of the visible screen, so
  one payload carries both. `ensureSize` already reflows to the attaching
  client's geometry before the snapshot is taken, which is exactly the property
  a stored app-side snapshot cannot have.
- Then `handleAttach` can extend today's `skip_replay` (currently
  `want_snapshot and s.gridOnAltScreen()`) to the fresh-attach case, so a pane
  that is getting a full scrollback-bearing repaint does not also get the raw
  ring.
- Negotiate it: a new HELLO capability, so an older app attached to a newer
  agent (and vice versa) keeps today's ring replay rather than losing scrollback
  silently. The agent↔app contract is a compatibility boundary (CLAUDE.md).

Not in scope: putting snapshots into layout blobs. T413 closed that.

## Validation criteria

- [x] unit: the emulator retains and serializes N rows of scrollback, and the
      snapshot reflows to a different attach geometry — `grid_snapshot.zig`,
      "retains scrollback and serializes it only when asked" and "a scrollback
      snapshot reflows to the ATTACH geometry" (agent lane)
- [x] unit: the negotiated capability gates it — an un-negotiated peer gets
      today's payload byte-for-byte — `server.zig`, "T621: without
      grid_scrollback an older peer gets today's payload byte-for-byte" (the
      ring replay is still sent AND the repaint is screen-only), plus
      `protocol.zig` "T621: grid_scrollback is the intersection, and never
      outruns grid_snapshot" for the negotiation itself
- [x] unit: the skip is proven end-to-end at the server — `server.zig`, "T621: a
      snapshot-less ATTACH gets scrollback in the repaint and no ring replay"
      (the repaint is the FIRST post-attach frame, anchored at S; a replay would
      have preceded it anchored below S) and its delta twin, "a DELTA re-attach
      keeps its gap-fill and gets no duplicate scrollback"
- [x] on-box: section J of `test/win32/chooser-restore-all-remote.ps1` extended
      (J2) — each rebuilt pane logs `attach: requested=0 … scrollback=true`
      across the RELAY, so the capability is asserted over the hop and not as a
      same-process handshake, and the existing marker read-back still passes
- [x] on-box: `test/win32/session-snapshot-reattach.ps1` green — the local WP-D3
      delta path did not regress
- [x] floor: `scripts\floor-lane.ps1 -Lane all` (lib + none + win32 + agent) green

**One criterion was met differently than written.** The card asked for "the
replay byte count drops" as the on-box measurement. The app exposes no such
counter, and adding one to the pane's inbound data path — a hot path, on the
thread the user's output flows through — to satisfy a test would be the wrong
trade. The byte drop is instead asserted where it is exact and free: at the
server, where the test reads the actual frames and proves the repaint is the
first one (a ring replay would necessarily arrive ahead of it, anchored below
S). On box, J2 asserts the negotiated PATH over the relay, which is the thing
the acceptance script is uniquely able to say.
