# T739 - The persisted resume offset overshoots the agent's stream head

## In plain terms

Every time a terminal reconnects to its background session, it writes down "I
have read this many bytes" — and the number is too big, by however much the
reconnect itself painted on screen. The next reconnect then asks to carry on
from a point the session never reached, gets pulled back to the end, and
whatever the program printed in between is skipped. Today the damage is usually
hidden because the reconnect repaints the visible screen anyway; on a busy pane
it is silently lost output.

## The evidence

Measured while landing T666, in the app's own log, on every single re-attach:

```
attach: recorded offset 1883 is ahead of the agent's stream head 1714;
        resuming from the head (the session's stream restarted under this id)
```

169 bytes of overshoot, which is exactly the size of the repaint the agent
appended on the PREVIOUS attach. With the agent's `grid_snapshot` capability
suppressed the warning does not appear at all — the overshoot IS the injected
repaint.

## Why it happens

`Remote.appliedOffset()` is `attach_offset + applied_bytes`, and
`applied_bytes` counts **every byte fed to the terminal** (`drainRing` →
`processOutputTracked`). Two of the things the agent sends are NOT stream bytes:

- the grid snapshot, sent as DATA anchored at `snapshot_at` — a repaint of the
  current screen that advances nothing (`agent/server.zig`, `sendData(...,
  snapshot_at, snap)`), and
- the `[ghoztty: N bytes of scrollback lost during disconnect]` marker, sent at
  `att.last_byte_offset`.

Both are counted, so the recorded offset drifts forward by their length on every
attach. The T532 clamp (`connection.resumeOffset`) catches the result and pulls
the resume point back to the agent's head — which is the safe direction, but it
means the bytes between the true applied position and the head are never
replayed.

## The fix

Track the absolute position from the DATA frames' own `byte_offset` rather than
by accumulating parsed bytes: a frame anchored at or below the position we have
already reached does not advance it. The inbound ring already carries byte
offsets (`Pane.discard_below` is anchored in them), so the information is
present; what is missing is using it as the position of record.

Note the clamp must STAY — it is the reader's defence against a resume point
from a stream that no longer exists (T532), which is a different fault.

## Validation criteria

- [ ] Across three kill/restore cycles the app logs no "recorded offset … is
      ahead of the agent's stream head" warning at all.
- [ ] The offset the manifest records equals the agent's head for a quiet pane,
      exactly, rather than head + repaint size.
- [ ] A pane producing output continuously across the kill loses none of it on
      restore (extend the `session-persistence.ps1` section D flood arm to a
      SECOND cycle, which is where the skip would land).
- [ ] `session-persistence.ps1`, `session-snapshot-reattach.ps1` and
      `session-reattach.ps1` stay ALL PASS.
