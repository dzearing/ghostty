# T739 - The persisted resume offset overshoots the agent's stream head

## Goals

- [x] The position a pane records on re-attach is the position its session
      actually reached — not that plus the size of the repaint the reconnect
      itself painted.
- [x] A reconnect after that one replays everything the program printed in
      between, instead of being pulled back to the end and skipping it.
- [x] An older agent, and a newer agent talking to an older app, keep working
      exactly as they do today.

## In plain terms

Every time a terminal reconnects to its background session, it writes down "I
have read this many bytes" — and the number is too big, by however much the
reconnect itself painted on screen. The next reconnect then asks to carry on
from a point the session never reached, gets pulled back to the end, and
whatever the program printed in between is skipped. Today the damage is usually
hidden because the reconnect repaints the visible screen anyway; on a busy pane
it is silently lost output.

## The evidence

Measured while landing T666, in the app's own log, on every single re-attach:

```
attach: recorded offset 1883 is ahead of the agent's stream head 1714;
        resuming from the head (the session's stream restarted under this id)
```

169 bytes of overshoot, which is exactly the size of the repaint the agent
appended on the PREVIOUS attach. With the agent's `grid_snapshot` capability
suppressed the warning does not appear at all — the overshoot IS the injected
repaint.

## Why it happens

`Remote.appliedOffset()` is `attach_offset + applied_bytes`, and
`applied_bytes` counts **every byte fed to the terminal** (`drainRing` →
`processOutputTracked`). Two of the things the agent sends are NOT stream bytes:

- the grid snapshot, sent as DATA anchored at `snapshot_at` — a repaint of the
  current screen that advances nothing (`agent/server.zig`, `sendData(...,
  snapshot_at, snap)`), and
- the `[ghoztty: N bytes of scrollback lost during disconnect]` marker, sent at
  `att.last_byte_offset`.

Both are counted, so the recorded offset drifts forward by their length on every
attach. The T532 clamp (`connection.resumeOffset`) catches the result and pulls
the resume point back to the agent's head — which is the safe direction, but it
means the bytes between the true applied position and the head are never
replayed.

## The fix

Two halves, because the anchor alone cannot answer it.

**The wire must SAY which bytes are a repaint.** The proposal above — "a frame
anchored at or below the position we have already reached does not advance it" —
cannot work, and the reason is worth writing down: the grid snapshot is anchored
at the head S, and so is the FIRST LIVE FRAME after it. Same anchor, same shape,
same payload type; no arithmetic over (anchor, length) can separate them. Only
the sender knows. So the agent frames its two injections as **`DATA_REPAINT`
(0x15)**, same `DataPayload`, gated on the new `repaint_data` capability (a new
opcode is a fatal framing error to a peer that does not know it — the same rule
`open_failed`/`attach_failed` follow). Semantics: *feed these bytes to the
terminal; the stream position after them is `byte_offset`, not `byte_offset +
len`.*

**The client tracks position by anchor, not by counting.** `Pane.stream_pos` is
advanced by the connection from each frame's own offset (`streamPosAfter`, pure)
and the pane's IO thread ADOPTS it in `drainRing` when a pre-pop read is followed
by an empty pop — which proves every byte the connection had handed over is
parsed, so the adoption is exact with no window in which it could claim bytes it
has not applied. That half also fixes the eviction case for free: the
scrollback-lost marker no longer advances anything, and the replay that follows
re-anchors at the ring's base, so the position jumps the hole instead of counting
bytes across it.

The clamp STAYS — it is the reader's defence against a resume point from a stream
that no longer exists (T532), which is a different fault.

## What validating it turned up

A new data-lane opcode was **silently swallowed**. Both muxes fold one transport
back into two logical lanes with `frame.type == .data`, so `DATA_REPAINT` was
routed to the CONTROL lane, where the control reader ignores what it does not
recognize. The agent sent a 197-byte grid snapshot, the client had negotiated it,
and nothing arrived — no crash, no log, just a pane that never repainted. The
fold rule is now one shared predicate, `protocol.onDataLane`, used by
`client_mux`, the agent's `mux`, and the mock that exists to mirror the rule.

That is why the on-box arms matter here: every unit test passed while the frame
was vanishing on the real transport.

## Validation criteria

- [x] Across three kill/restore cycles the app logs no "recorded offset … is
      ahead of the agent's stream head" warning at all. — arm A of
      `test\win32\session-resume-offset.ps1`, ALL PASS (68 assertions).
- [x] The offset the manifest records equals the agent's head for a quiet pane,
      exactly, rather than head + repaint size. — the same arm asserts
      `requested == head` per cycle (539/1467/2572), and arm B (the pre-T739
      accounting, from the same tree via `GHOZTTY_RESUME_COUNT_BYTES=1`) shows
      the overshoot returning and the clamp firing on every cycle after the
      first, so the green is evidence rather than an absence.
- [x] A pane producing output continuously across the kill loses none of it on
      restore — `session-persistence.ps1` section D now runs a SECOND
      kill/restore cycle (D8–D11), which is the cycle whose resume point the
      previous attach wrote.
- [x] `session-persistence.ps1`, `session-snapshot-reattach.ps1` and
      `session-reattach.ps1` stay ALL PASS.
- [x] Skew, both directions: an agent with `repaint_data` suppressed still
      restores a live, unclamped pane (arm C), and the framing itself is
      asserted in the agent lane (`data_repaint` iff the peer asked).
