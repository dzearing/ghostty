## THE HARDWARE WATCH IS THE WRONG INSTRUMENT, AND THE SWEEP REPLACES IT (2026-08-14, turn 5)

Turn 4 handed this turn a page-watch that finishes a lane. It was run against
the real thing, and the run is the most useful negative in the file:

```
crash-databreak.ps1 -Lane agent -Symbol verifyIntegrity -SignatureFilter page.Page
    -WatchPages -AttachName core -TimeoutSeconds 2400
-> no implausible write observed (mode=build-runner, page-watch)
   2 address(es) armed, program ran 183s (cdb exit 0)
   COVERAGE: 2 armed, 2 dropped after going hot, so 0 watched to the end.
```

**Zero addresses were watched to the end**, and turn 4's own instrumentation is
what says so. The reason is structural, not a tuning problem: a `Page` lives in
a `MemoryPool` slot, most pages are short-lived, and nothing disarms — so within
seconds of arming, the watched address has been freed, recycled, and handed to
something that writes it constantly, and `-HotLimit` drops the breakpoint. It
armed 2 rather than 4 because the arm gates (rightly) reject slots that do not
hold a plausible `*Page`, which also means the entry breakpoint never got
disabled and the per-call cost was still being paid.

This retires the premise of **T839** ("aim the four registers at the pages the
known victim tests use"): the victim's page dies and recycles exactly like any
other. Four debug registers cannot cover a pool that churns. T839 stays open
only for what the sweep below genuinely cannot do — name the writing
instruction — and it should be armed at a code path, once there is one.

### What landed instead: sweep every live page, on a walk we already pay for

`PageList.verifyIntegrity` already walks every node in the list (to total the
rows and check page serials). That walk now also checks each page's
`memory.ptr` with `Page.memoryPtrPlausible`, returning the new
`IntegrityError.PageMemoryPtrCorrupted` and logging the page's serial, struct
address, base and length.

Why this is the instrument this hunt actually needed, stated as the thing it
changes: turn 3's `assertMemoryPtrPlausible` reports damage the next time **that
one page** is verified, which can be an arbitrarily long time after the write —
which is precisely why every abort so far has landed in an unrelated later test.
The sweep reports it at the next PageList assertion on **any** page, and
`assertIntegrity` is deferred on every structural mutation. So the next
occurrence should panic inside the test that CORRUPTED, not the test that
tripped over it. That is the single missing fact in this hunt: the victim has
been known for two weeks and the culprit has never been.

It costs nothing extra — no debug registers, no address limit, no recycling
blind spot, and no additional traversal.

Unit test: `PageList verifyIntegrity catches a corrupted page base anywhere in
the list`, which grows past the first page, clobbers the FIRST page's base with
the exact recorded signature (low 32 bits exact, high half `0x11a60` from the
2026-08-14 dump), and expects the error — i.e. it proves the sweep catches a
page nobody is operating on. Verified firing:

```

                    serial=0 page=0x213fafa01b8 memory.ptr=0x11a60fb4ef000 memory.len=0x6f000
```

## THE WATCH CAN FINISH A LANE NOW (2026-08-14, turn 4 — T474/T838)

`crash-databreak.ps1 -WatchPages` arms the heap field instead of the stack
slots: it reads `self` out of `verifyIntegrity`'s spill slots, arms `ba w8` on
`&page.memory.ptr`, and then **disables the entry breakpoint**. Turn 3's shape
paid one break-into-debugger round trip per call — 335,878 of them at ~2 ms,
which is why it timed out mid-lane having measured nothing. This one pays four,
total, and the lane then runs at full speed. The per-call bottleneck is gone.

Four facts this turn established, all of them cheaper to have written down than
to re-derive:

1. **`self` is the SECOND spill slot, not the first.** The probe finds
   `@rbp+0x4e0 <- r8`, `@rbp+0x4e8 <- rdx`, `@rbp+0x4f0 <- rcx`, and the obvious
   reading (first spill = first parameter) is wrong here. `dv` at the arm point
   names `@rbp+0x4e0` as **`alloc_gpa`**, and `@rbp+0x4e8` dereferences to
   `{000001d3`39220000, 0006f000}` — a page-aligned base and the familiar
   `0x6f000` length. So `self` arrives in **rdx**. (The fixture's
   `check(self, a, b)` spills in parameter order, which is exactly how a
   one-fixture rule gets adopted and then quietly aims the instrument at an
   allocator.) The tool no longer guesses: it tries every candidate slot and the
   arm gates pick — a slot only arms if it holds a plausible aligned pointer
   whose own first field is a plausible pointer aligned to 0x1000.

2. **The first armed run reported a hit, and it was NOT the bug.** Writer:
   `memcpy` from `hyperlink.zig:108` (`dupe`) under
   `clonePartialRowFrom` (`page.zig:962`), copying `https://example.com`
   (19 bytes) into `dst_page.string_alloc`, during
   `test.Page exactRowCapacity hyperlink map capacity for many cells`. The
   watched page had been freed, its pool region returned to the GPA and handed
   out again as a later page's backing buffer; ASCII (`2e656c70`6d617865` =
   "example.") reads as an implausible pointer. **Nothing disarms in this mode,
   so a recycled address stays watched.** The remedy is the **shape guard**: the
   qword after the watched pointer — `memory.len` — must be UNCHANGED between
   the arm and the report. T443's damage leaves it alone (every dump printed
   `page_len=0x6f000` intact); recycling does not survive it. Proven both ways in
   `test\win32\crash-databreak.ps1`.

3. **A break nobody routes ends the session and reads as a clean run.** A
   hardware data breakpoint arrives as a single-step exception; one that matches
   no registered `ba` (a thread created after the arm does not inherit the debug
   registers) falls through to the `sse` filter, returns from `g`, and drops into
   the script's closing `q` — cdb quits, the debuggee dies mid-lane at exit 84,
   and the verdict says "no implausible write observed". That is what the first
   guarded run did at 110 s, inside `remote.connection`. Fixed with `sxi sse`,
   plus an `EndedEarly` check that now exits **4** and refuses to call a partial
   run clean.

4. **A watched address that goes hot will starve the run.** Same root as (2) —
   nothing disarms, so a recycled address can land in memory something writes
   constantly, and then every write is a ~2 ms break. One did: thirteen minutes
   and a **335 MB transcript** with the lane nowhere near done. Two fixes, both
   in: the report moved out of the breakpoint command into its own `$$<` include
   (cdb echoes every command it runs, so an inline report was being echoed on
   every ordinary write too), and after `-HotLimit` waved-through writes the
   breakpoint is DROPPED and counted. The verdict now reads "4 armed, 1 of which
   went hot, so 3 watched to the end" — which is the honest number.

5. **Coverage is four addresses, and that is the remaining weakness.** It is an
   ADDRESS that is watched, not a page, so every later page landing on the same
   pool slot is covered too — but a lane touches thousands, and (4) can take some
   of the four away mid-run. A clean armed run rules out a corrupting write to
   those addresses and nothing more, and the verdict now says so in its own
   output rather than leaving a reader to infer it. Aiming the watch at the pages
   the known victim tests use is **T839**.

## THE DAMAGED VALUE IS THE FIELD, NOT A COPY (2026-08-14, turn 3) — the target moves again, and gets cheaper

Turn 2 ended pointing the next armed run at "a 4-byte write landing on the high
half of a `Page.memory.ptr` copy (stack spill **or** the `Page` struct itself)".
That ambiguity is now resolved **statically, without a repro**, by disassembling
`verifyIntegrity` in the lane's own binary
(`.zig-cache\o\b4a902e9…\ghoztty-agent-core-test.exe`, built 13:40 today):

```
verifyIntegrity+0xf37   mov   rcx,[rbp+4F8h]      ; rcx = self  (*Page)
                        mov   [rbp+2D8h],rcx      ; the ONLY write to this slot
                        mov   [rbp+718h],rcx
                        mov   rax,[rcx]           ; a copy of self.memory.ptr -> [rbp+720h]
...
verifyIntegrity+0xfb8   mov   rax,[rbp+2D8h]      ; rax = self, again
                        mov   r9,[rax]            ; <-- THE BAD VALUE ENTERS HERE
                        mov   rcx,[rax+8]
                        call  map__anon_52937
```

`memory` is `Page`'s **first field**, so `[self]` *is* `self.memory.ptr` — the
disassembly confirms the layout (`[rcx]`/`[rcx+8]` are ptr/len,
`[rcx+160h]` is `hyperlink_map`). Turn 2 read the equivalent instruction pair in
the crashing binary as "`[rbp+188h]` is a pointer to the page's memory slice"
and inferred a stack temporary. It is not a temporary: the slot is written once,
from `self`, and never again.

**So the load that produced the half-clobbered base read the `Page` struct's own
`memory.ptr` field, on the heap.** There is no stack copy in that path to blame.
That is the sharpest statement this hunt has: the corrupted 4 bytes are at
`&page.memory.ptr + 4`, a heap address.

It also sharpens the paradox rather than dissolving it, and the next turn should
hold both halves in view: the diagnostic printed `page_base=0x1c9cb22f000`
(correct) from a re-read of that same field a few instructions later. Two reads
of one address, different values. Either something writes the field and it is
later restored, or the two reads are not as close together as the source
suggests (the `lookupGrapheme`/`lookupHyperlink` calls sit inside the per-cell
loop, so the "earlier" copy can be from a previous iteration — that is the
likelier reading and it makes the write ordinary rather than magical).

### What this buys the instrument

`crash-databreak.ps1` timed out on turn 2 because it arms per `verifyIntegrity`
call: 335,878 arm/disarm cycles at ~2 ms each, and the lane never finished.
A heap field does not need that. `&page.memory.ptr` is **stable for the life of
the page**, so the armed window can be per-PAGE (armed in `Page.init`, disarmed
in `Page.deinit`) instead of per-check — orders of magnitude fewer cycles. The
constraint to design around is that x86 has only 4 debug registers, so at most
4 pages can be watched at once; picking the page a lane's known victims use
(`terminal.PageList resize reflow …`) is the obvious first cut.

### Landed this turn: a detector that does not need a debugger at all

`Page.memoryPtrPlausible` + `assertMemoryPtrPlausible`, called at the top of
`verifyIntegrity` under `slow_runtime_safety`. The T443 damage keeps the pointer
**non-null and page-aligned** — which is why every null/alignment check in this
codebase has waved it through for two weeks — but it pushes the address above
`0x0000_8000_0000_0000`, which no user-mode pointer can reach. Checking the
field itself means the next occurrence is reported **against the page that owns
the damage, at the next integrity check on it**, instead of ten frames deep in
whichever map happened to reify a pointer from it. Unit test: `Page
memoryPtrPlausible rejects a half-clobbered base`, which uses the exact high
halves from both recorded dumps (`0x11a60`, `0x3d3d0`).

Why this matters beyond legibility: the existing `assertMapPtrInPage` only fires
when a lookup reifies a pointer whose damage happens to push it out of the
page's range. This one fires on the *page*, so any check on a damaged page
reports it. If the corrupter damages pages more often than the crash rate
suggests, this raises the observed rate — and a higher rate is the single thing
this hunt needs most.

memory bug: a scheduling window between every single test, and a completely
different set of leftovers under the test's stack frame.

### The damage, measured exactly, for the first time

`210c763f4`'s diagnostic fired (`assertMapPtrInPage`), so the 10:22 dump is a
clean panic with a message rather than a wild fault ten frames deep:

```
[page] (err): page hyperlink_map metadata pointer outside page memory
              ptr=0x11a60cb29de28 page_base=0x1c9cb22f000 page_len=0x6f000
thread 17804 panic: page map metadata pointer corrupted
```

| quantity | value |
|---|---|
| page base | `0x0000_01c9_cb22_f000` |
| page len | `0x6_f000` |
| bad pointer | `0x0001_1a60_cb29_de28` |
| implied offset from the LOW half | `0xcb29de28 - 0xcb22f000` = `0x6e_e28` — inside the page, exact |
| high half, correct | `0x0000_01c9` |
| high half, actual | `0x0001_1a60` — page-offset-shaped again (`< 0x6f000`) |

`offset` is a `u32`, so `base + offset` can move the high half by **at most 1**.
`0x1c9 → 0x11a60` is therefore **arithmetically impossible from the addition** —
the high half was not computed, it was inherited. Same signature as the
2026-08-04 dump, now with the numbers to prove it rather than infer it.

Adjacent stack, in `verifyIntegrity`'s frame (`dq 000000ad`f6bed530`):

```
f6bed540  000001c9`cb29e000  <- page_base + page_len, correct
f6bed550  00011a60`cb29de28  <- the bad pointer
f6bed558  00011a60`cb29de28
f6bed568  000001c9`cb22f000  <- page_base, correct, in the SAME frame
f6bed570  00000000`00011a68  <- an OffsetBuf offset
f6bed578  00011a68`00011a68  <- two u32 offsets packed
```

The stale high half `0x11a60` sits eight bytes from two live `0x11a68` offsets.

### Where it is NOT: the arithmetic and the store are clean

`OffsetHashMap.map` was disassembled **in the crashing binary** (`uf
map__anon_53065`), and it is correct code:

```
mov ecx,[rbp-2Ch]      ; the u32 offset
mov rax,[rbp-28h]      ; base.ptr, 8 bytes
add rax,rcx            ; full 64-bit add, zero-extended offset
...
mov [rax],rcx          ; full 8-byte store through the sret pointer
```

and the caller reads it back with a full `mov rax,qword ptr [rbp+0AD8h]`.

**So the 2026-08-04 conclusion — "the truncation happens across three by-value
copies through `get` → `getContext` → `getAdapted`" — is wrong.** The pointer is
already bad when `map()` returns, before the hash map is ever entered. Working
backwards through the caller:

```
mov rax,qword ptr [rbp+188h]   ; a pointer to the page's memory slice
mov r9, qword ptr [rax]        ; r9 = base.ptr   <-- THE BAD VALUE ENTERS HERE
mov rcx,qword ptr [rax+8]      ; base.len
call map__anon_53065
```

`base + offset` produced `0x11a60cb29de28` from an exact low half, so **`r9` was
already `0x11a60cb22f000`** — i.e. the `Page.memory.ptr` value *as loaded at this
call site* had a clobbered high half, while another copy of it, in the same stack
frame, was intact when the diagnostic read it back a few instructions later.

The target is therefore one level up from where this file has been looking: **a
4-byte write landing on the high half of a `Page.memory.ptr` copy** (stack spill
or the `Page` struct itself), with an offset-shaped value.

## START HERE (2026-08-04, second pass) — the damage is HALF A POINTER

The three dumps `scripts\crash-catch.ps1` left in `.dumps\` were read back with
cdb, disassembled, and the faulting value traced. The result is the first datum
in this hunt that is a *shape* rather than a symptom, and it overturns most of
what is written below.

**One pointer arrives at the hash map with its low 32 bits exactly right and
its high 32 bits replaced.**

From `.dumps\ghostty-test-20260804-071353-2.dmp` (victim:
`terminal.PageList.test.PageList compact oversized page`):

| thing | value |
|---|---|
| page memory base (`Page.memory.ptr`) | `0x0000_0216_cca6_0000` |
| page memory length | `0x0007_2000` |
| `hyperlink_map` metadata offset | `0x0007_0f40` |
| correct metadata pointer (seen on the stack) | `0x0000_0216_ccad_0f40` |
| pointer `header()` actually received | `0x0003_d3d0_ccad_0f40` |

`0xcca60000 + 0x70f40 = 0xccad0f40` — the low half is not approximately right,
it is arithmetically exact. Only `0x00000216` → `0x0003d3d0` changed. And
`0x0003d3d0` is itself page-offset-shaped (`< 0x72000`), as are the other
mangled high halves littering the same frames (`0x0003d3d8`, `0x0005b990`,
`0x0005ba98`, `0x00070f40` — that last one *is* the map offset).

**Why this explains the intermittency, which nothing before it did.** A page
pointer's high half is the same for every page in the process. So a slot that
keeps its stale high half is *usually still correct by accident* — it only
faults when the stale bytes happen to be one of these offsets instead of a
previous pointer's high half. That is a coin flip per run, victim wherever the
walk happens to be. "Different victim every run, ~50% of runs" is what a
half-written pointer looks like, not what a wild write looks like.

**What this rules out.** Not a use-after-free (a freed block does not preserve
32 bits of a pointer verbatim). Not a wild write of garbage. Not "something
zeroes memory" — the T454 reading of `self = 0`, `trace = 0` was reading debug
stack slots that had simply never been written in this path, which a Debug
frame is full of. Not a leaked thread (T450's capture already showed only idle
pool workers).

**Where it happens, narrowed to three instructions.** In the same dump,
`verifyIntegrity` computes the pointer correctly:

```
81d68f85  mov  r9,[rax]              ; page.memory.ptr   -> 0x00000216cca60000
81d68f98  call OffsetHashMap.map     ; add rax,rcx  (full 64-bit add), 8-byte store
81d68fab  mov  rax,[rbp+850h]        ; the map, still correct
81d68fb2  mov  [rbp+858h],rax
81d68fc7  call get                   ; -> getContext -> getAdapted -> getIndex
```

`map()` disassembles clean: a zero-extended `add rax,rcx` and a full
`mov [rax],rcx`. Yet by the time `getAdapted` spills its copy at
`0x2f21df9838`, the high half is gone — and `header()` faults reading
`[rax+0Ch]` at `0x0003d3d0ccad0f3c`. So the truncation happens across three
by-value copies of an 8-byte struct through `get` → `getContext` →
`getAdapted`, all of which are `-O0` code doing nothing but moving the value.

That leaves two candidates, and they are cheap to separate:

1. **A codegen bug** (a 4-byte store where an 8-byte one belongs, or two
   stack slots overlapping). Discriminator: build the same lane with the
   self-hosted x86_64 backend (`-fno-llvm`) or at `ReleaseSafe` and see
   whether the signature survives. Note T451 already has `zig.exe` itself
   taking access violations on this box, so a toolchain fault is not exotic
   here. Filed as **T473**.
2. **Something else writing 4 bytes over that stack slot.** Discriminator: a
   hardware write breakpoint on the slot, armed from cdb once the page is
   known. Filed as **T474**.

**Floor after the change:** `floor-lane.ps1 -Lane all` →
`none#1=PASS win32#1=PASS agent#1=PASS`; P1/P2/P3 all `ALL PASS`. Read that as
"the diagnostic did not break anything", **not** as evidence the crash is
gone — one green round of a coin-flip signal is exactly what you expect half
the time, and nothing here fixed the truncation.

**Landed this turn:** `Page.ptrInPage` plus `assertMapPtrInPage`, called from
`lookupHyperlink` and `lookupGrapheme` under `slow_runtime_safety`. The next
occurrence stops being a wild fault ten frames deep in the hash map and
becomes one line naming the page, its range and the bad pointer — including
the half-clobbered case, which is exactly what a null/alignment check would
wave through. Unit test: `Page ptrInPage bounds`.

**A measurement, so it is not re-run, and it says DON'T iterate there.** The
`none` lane's terminal-only binary
(`zig build test -Dapp-runtime=none -Dtest-filter=terminal.`) was run **20
consecutive times, 0 failures, 39 minutes**. This file previously recorded
