# T443 - The agent test binary still segfaults intermittently inside Page.assertIntegrity - the corrupter is upstream of the pump-lifetime UAF fixed in T420

## Summary

Split out of **T442** on 2026-08-04 after that turn used its whole context
narrowing the failure. T442 found one real use-after-free on the way (the
agent server's three push pumps could outlive the `Server`; fixed as **T420**)
but the lane is still red: `zig build test-agent` segfaults on roughly half of
its runs, always in an unrelated `terminal.*` test, always inside
`Page.assertIntegrity`.

## In plain terms

One of the three test suites still crashes about half the time, and it crashes
in a different place every run. The crash is not in the test it lands on -
something else has already scribbled over memory by the time that test runs, so
the named test is a victim, not the culprit. Until this is understood, that
suite cannot be used as evidence that anything else works.

## Goals

- [ ] Identify what writes into memory it does not own (the win32 lane fails
      the same way, so this is NOT specific to the agent binary - see below)
- [ ] `zig build test-agent` AND `zig build test -Dapp-runtime=win32` green over
      5 consecutive runs each
- [ ] A regression test or an assertion that would catch the same class again

## IT IS NOT THE AGENT LANE (2026-08-04, the last datum of the T442 turn)

T442 was scoped to the agent binary because the agent lane was the only one
seen failing. The closing floor run of that turn broke that assumption:

```
FLOOR SUMMARY: none#1=PASS win32#1=FAIL agent#1=PASS
```

The **win32** lane crashed in `terminal.search.screen.test.reloadActive partial
history cleanup on loop append error` - a member of the same victim set - while
the agent lane passed that same round. So:

- The corrupter is in code the **win32 and agent** lanes share and the `none`
  lane does not. The obvious candidate is the `apprt.win32` block (real
  windows, WebView2 hosts, COM apartments, message loops) - which is also where
  **T430** found the two lanes hanging, and **T434** notes those tests get built
  and run twice concurrently.
- Any bisect must therefore be run in the **win32** lane too, and a green agent
  lane on a single run means nothing (it passed once here while win32 failed).
- Read T430 first: it fought the same two lanes and its `floor-lane.ps1`
  already sweeps leaked WebView2 hosts between lanes (it reported "swept: 0"
  on all three runs, so nothing leaked ACROSS lanes - but that says nothing
  about what happens within one).

Everything below was measured on the agent lane and still holds; just do not
assume the agent binary is special.

## What is already known (do not re-derive)

**Reproduction.** `zig build test-agent`, unfiltered, on this box. Roughly 4
failures in 6 full runs. Running the built test exe directly is faster to
iterate on (~100 s per pass, no rebuild):

```powershell
$e = Get-ChildItem .zig-cache\o -Recurse -Filter ghoztty-agent-test.exe |
     Sort-Object LastWriteTime -Descending | Select-Object -First 1
& $e.FullName --seed=0x87af847b *> $env:TEMP\run.log
```

The Zig segfault handler prints a full, symbolised stack for the FAULTING
frame, which is where every datum below came from.

**Test order is deterministic; the crash is not.** Three runs of the same exe
with the *same* seed crashed at test 2191, 2207 and 1095 of 3911 (and a fourth
passed outright). So `--seed` is not the variable - something asynchronous is.
Test *indices*, though, are stable across runs (index 2192 is
`terminal.search.screen.test.simple search with history` in every run), which
makes indices usable as landmarks.

**Every crash lands inside `Page.assertIntegrity`.** Observed victims:

| test | faulting frame |
|---|---|
| `terminal.PageList ... more cols forces less rows per page` | `clonePartialRowFrom` -> `assertIntegrity` -> `verifyIntegrity` -> `lookupHyperlink` -> `hash_map.getContext` |
| `terminal.Terminal: deleteLines across page boundary ...` | `PageList.grow` -> `last.data.assertIntegrity()` |
| `terminal.search.screen`, `terminal.search.sliding_window`, `terminal.formatter` | page paths, traces truncated |

Fault addresses are all over the map - `0x0`, `0xffffffffffffffff`, and heap-ish
values like `0x27481050e5dc`. One run reported `Unable to dump stack trace:
InvalidBlockIndex`, i.e. the stack was already unwalkable. That spread is what
says *corruption* rather than a wrong assertion.

**Hypotheses already eliminated, with the experiment that killed each:**

- *A SIMD / native-CPU codegen bug* (the agent tests build for
  `config.target` = native CPU, while `zig build test` builds
  `config.baselineTarget()`). Killed: `zig build test-agent -Dcpu=baseline`
  segfaults the same way.
- *A bug in the terminal code itself under the agent build config.* Killed:
  `zig build test-agent -Dtest-filter="terminal."` passes.
- *Something in the `remote.*` tests corrupting the following terminal tests.*
  Weakened: `-Dtest-filter="remote." -Dtest-filter="terminal.PageList"` passes.
  (Not fully excluded - that build reaches PageList seconds sooner, so a
  timer-driven corrupter would have less runway.)
- *Leaked threads accumulating.* Killed as a bulk effect: sampling
  `Process.Threads.Count` across a whole run shows 2-5 threads throughout, with
  a brief spike to 12 during the WebView2 host tests. No monotonic growth.
- *Memory / address-space exhaustion.* Killed: private bytes stay at 6-26 MB
  for the whole run (peak 156 MB during the font tests).
- *The push-pump use-after-free.* Fixed (T420) and it did **not** fix this:
  three full runs after the fix still failed twice.

**Still open, ranked:**

1. A single leaked or dangling background thread from the `remote.agent.*`
   tests (indices 1-223, and a second block around 2099-2131:
   `keepalive`, `ws_client`, `ssh_transport`). One thread writing through a
   stale pointer on a timer explains every property observed: only this binary,
   nondeterministic, victims spread across whatever allocated next.
2. An overlapped/async Windows read (ConPTY, socket, or pipe) completing into a
   buffer whose owner has already gone away. `pty_child.zig`'s reader join was
   read carefully and looks correct; `conpty_smoke.zig` has five reader-thread
   sites that were NOT audited.
3. Something in the agent binary's *own* allocation path corrupting the heap
   that `PageList`'s pool later hands out.

**Tooling note.** `cdb` is NOT installed on this box, so there is no
just-in-time debugger to catch the AV with all thread stacks. Installing the
Windows Debugging Tools (or shipping a `MiniDumpWriteDump` handler in the test
binary) is probably the cheapest way to get the culprit's stack rather than the
victim's, and is worth doing FIRST rather than continuing to bisect a
50%-flaky signal.

## Validation

- Five consecutive green `zig build test-agent` runs.
- The mechanism is named in this file with a stack or a code cite - not
  "it stopped reproducing".
