# T1245 - git-commit-guard silently reuses a stale message file when -MessageFile does not exist

## Summary

`scripts\git-commit-guard.ps1 commit -MessageFile temp\msg2.txt` was run on
2026-09-01 with no such file written for that turn. It did not refuse: it
committed and PUSHED using a leftover `temp\msg2.txt` from an earlier turn, so
e4824918e - which records the sha that closed T1195 - is titled "record the
commit that closed T1170".

That is the exact failure mode T948 built this guard to prevent, from the
message side rather than the pathspec side: the guard reads the commit back and
verifies the PATHS, and nothing at all checks that the SUBJECT was written for
this commit. A stale file is worse than a missing one, because a missing file
would at least have produced an empty message somebody noticed.

The commit message is the dashboard's activity feed (go.md step 6), so a stale
subject is not cosmetic - it is a feed item describing work that is not in the
commit.

Fix: refuse when `-MessageFile` names a path that does not exist, and refuse an
empty one. Consider having the guard DELETE the message file after a successful
commit, so a stale one cannot exist to be picked up.


## Validation criteria

- [ ] A `-MessageFile` that does not exist is refused, with the path named
- [ ] An empty or whitespace-only message file is refused
- [ ] The message file is consumed (deleted) after a successful commit
- [ ] Demonstrated red in section W of test\win32\go-loop-guard.ps1 before it is demonstrated green


## In plain terms

When the loop commits its work, the commit's description can silently be an old
one left over from a previous piece of work. The dashboard shows that
description as what happened, so the feed can end up describing the wrong
thing.
