# T662 - On a box whose panes never all close, the local agent can now go indefinitely without ever adopting a newer build

## Summary

Surfaced by **T525** (the morning app-only refresh), which deliberately stops
swapping `ghoztty-agent.exe` on disk. That closes an unattended dialog, and it
has a consequence worth tracking honestly: on this box the agent now has only
two ways to advance, and both can go unreached indefinitely.

- The **on-disk** agent only moves on a deliberate, attended full delivery.
  App-only mornings skip it (by design — see T525).
- The **running** agent only moves when the app's check finds it stale AND
  there are zero live sessions (`refresh_now`), or when the user answers the
  confirmation. A box where the go loop keeps a persistent pane open all day
  never reaches zero live sessions, and the confirmation is exactly what T525
  is suppressing during the unattended restart.

So a machine could sit for weeks on an old agent while the app advances daily.
Nothing is broken — the agent contract is explicitly forward-compatible in both
skew directions (CLAUDE.md, "Agent contract & upgrade compatibility") — but an
agent-side fix reaching a user only when they happen to close everything is the
same defect T147 was written to end, arrived at from a different direction.

## In plain terms

The background process that keeps your terminal sessions alive updates only
when every session is closed, or when you answer a prompt. Since the morning
refresh now (correctly) never asks you that at 5am, and your work sessions are
never all closed, that process can stay on an old version indefinitely while
everything else gets newer. Nothing misbehaves today; the risk is a fix landing
in it that never reaches you.

## What to work out

- Is a periodic **attended** full delivery enough (i.e. the answer is a policy,
  not code)? The dialog is honest and the user is present; it may just need a
  cadence and a way to see how far behind the running agent is.
- Or does the agent need a genuinely non-destructive handoff — drain, snapshot,
  re-exec, re-attach — which is what CLAUDE.md calls the "lazy, non-destructive
  agent upgrade" and describes as the preferred path for a breaking change.
- Either way, the staleness should be VISIBLE rather than inferred: `+sessions`
  or `+version` naming the running agent's build next to the bundled one.

## Validation criteria

- [ ] It is answerable from the CLI how far behind the running agent is.
- [ ] There is a documented path by which a long-lived box adopts a newer agent
      without the user having to close every session, or a written decision
      that the attended confirmation IS that path and what its cadence is.
- [ ] Whatever lands does not reintroduce an unattended dialog (T525) and does
      not kill sessions silently (rule 3 of `agent_upgrade.zig`).
