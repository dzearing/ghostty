# T662 - On a box whose panes never all close, the local agent can now go indefinitely without ever adopting a newer build

## Summary

Surfaced by **T525** (the morning app-only refresh), which deliberately stops
swapping `ghoztty-agent.exe` on disk. That closes an unattended dialog, and it
has a consequence worth tracking honestly: on this box the agent now has only
two ways to advance, and both can go unreached indefinitely.

- The **on-disk** agent only moves on a deliberate, attended full delivery.
  App-only mornings skip it (by design — see T525).
- The **running** agent only moves when the app's check finds it stale AND
  there are zero live sessions (`refresh_now`), or when the user answers the
  confirmation. A box where the go loop keeps a persistent pane open all day
  never reaches zero live sessions, and the confirmation is exactly what T525
  is suppressing during the unattended restart.

So a machine could sit for weeks on an old agent while the app advances daily.
Nothing is broken — the agent contract is explicitly forward-compatible in both
skew directions (CLAUDE.md, "Agent contract & upgrade compatibility") — but an
agent-side fix reaching a user only when they happen to close everything is the
same defect T147 was written to end, arrived at from a different direction.

## In plain terms

The background process that keeps your terminal sessions alive updates only
when every session is closed, or when you answer a prompt. Since the morning
refresh now (correctly) never asks you that at 5am, and your work sessions are
never all closed, that process can stay on an old version indefinitely while
everything else gets newer. Nothing misbehaves today; the risk is a fix landing
in it that never reaches you.

## Goals

- [x] The running agent's build is answerable from the CLI, with the app closed.
- [x] The answer names the DISTANCE (how far behind), not just "old".
- [x] "Stale" has exactly one definition, shared by the CLI and the app's policy.
- [x] The current adoption path is written down where someone will find it.
- [x] The non-destructive alternative is filed rather than left as a maybe.

## What landed

- **`ghoztty +sessions --agent [--json]`**, on both platforms — the running
  agent's stamp next to the bundled one, the calendar days between them, the
  live-session count that decides which arm the app's policy would take, and
  the agent's pid. `status` is a machine token (`current` / `stale` / `newer` /
  `unknown` / `not_running`). No agent running exits 0 with `not_running`: it
  is an answer, not a failure, and the next persistent session simply starts
  the bundled build.
- **`src/remote/agent_build.zig`** — the stamp primitives, the calendar
  distance, the status classification and the report rendering, all pure. The
  win32 policy (`agent_upgrade.zig`) now RE-EXPORTS them rather than holding a
  second copy, so the number a user reads and the decision the app acts on
  cannot drift apart.
- `days_behind` is absent rather than 0 or negative whenever there is no honest
  number: a `dev` stamp, a pre-versioned agent, a same-day rebuild, or a
  running agent that is newer.
- Docs: the `+sessions` section of CLAUDE.md now states the two ways a running
  agent advances and why a long-lived box reaches neither.
- **D59** asks the user which path to take; **T705** is the non-destructive
  handoff (drain / snapshot / re-exec / re-attach) the agent contract already
  calls preferred.

## What to work out

- Is a periodic **attended** full delivery enough (i.e. the answer is a policy,
  not code)? The dialog is honest and the user is present; it may just need a
  cadence and a way to see how far behind the running agent is.
- Or does the agent need a genuinely non-destructive handoff — drain, snapshot,
  re-exec, re-attach — which is what CLAUDE.md calls the "lazy, non-destructive
  agent upgrade" and describes as the preferred path for a breaking change.
- Either way, the staleness should be VISIBLE rather than inferred: `+sessions`
  or `+version` naming the running agent's build next to the bundled one.

## Validation criteria

- [x] It is answerable from the CLI how far behind the running agent is.
      `ghoztty +sessions --agent` prints both stamps, the status token and the
      calendar days between them; `--json` carries the same as keys. Verified
      on the box by `test/win32/sessions-agent-build.ps1` (ALL PASS, 38
      checks): arm B against a real agent this tree just started, arms C/D
      against fabricated newer/older bundled stamps, arm E on the JSON keys.
      Teeth-checked with `-TeethCheck`, which collapses the fabrications onto
      the running stamp and turns exactly the C/D/E status arms red (8
      failures, nothing else moves).
- [x] There is a documented path by which a long-lived box adopts a newer agent
      without the user having to close every session, or a written decision
      that the attended confirmation IS that path and what its cadence is.
      CLAUDE.md's `+sessions` section now states both existing exits
      (`refresh_now` at zero live sessions, or the mandatory confirmation), why
      a never-idle box reaches neither, and that the path today is an attended
      full delivery. **D59** puts the choice in front of the user; **T705** is
      the non-destructive handoff.
- [x] Whatever lands does not reintroduce an unattended dialog (T525) and does
      not kill sessions silently (rule 3 of `agent_upgrade.zig`). Everything
      here is read-only: one new CLI verb flag that dials and prints, plus a
      pure module. No policy branch, no dialog and no restart path was touched
      — `agent_upgrade.zig`'s own tests (win32 lane) still pass unchanged, and
      the moved primitives are pinned by a re-export test there.
