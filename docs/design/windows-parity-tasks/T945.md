# T945 - A harness whose stamp needs Docker can never go green on this box, so validate stays red until somebody reaches for the hatch

## Summary

Observed 2026-08-17 (the T940 turn). `guard-due` reported `release-artifacts`
DUE at claim time; the harness was run and reported **ALL PASS (2 skipped)** —
and it stayed DUE, because only a clean run with NO skipped sections stamps
(T783, deliberately: a run that skipped the section covering the change proves
nothing about it).

The two skips are `B1 FILEVERSION single source` and `B2 portable ZIP layout`,
both `SKIP … (Docker is not running)`. Docker is deliberately NOT started on
this box — the WSL2 backend has taken it to 28 GB of RAM and buried it, so
"Docker down" is a supported state, not a fault to fix. So this guard cannot
reach a stamp here at all: `parity-tasks.ps1 validate` fails on it every turn,
forever, and the only way past is `-NoGuardDue`.

That is the failure the guard system was built to prevent, arriving from the
other side. A hatch reached for once is an explained exception; a hatch reached
for every turn is a disabled gate, and the next genuinely stale harness rides
through under the same flag with nobody looking.

## In plain terms

The project has a rule that you cannot commit while a test that covers your
change has not been run since the change. One of those tests can only finish if
a piece of software that is deliberately kept switched off is running. So the
rule now fails every single time, and the way past it is a flag that also
switches off the checking for everything else.

## What to weigh

- **Stamp what actually ran.** Record the stamp per SECTION rather than per
  harness, so a Docker-gated section stays due while the sections that did run
  go green. Most faithful; the most work.
- **Let a harness declare an environment-gated section.** A skip whose reason
  is a declared unavailable dependency does not block the stamp, but the stamp
  records that it was partial and `guard-due check` says so on every report —
  so the gap stays visible instead of being either invisible or fatal.
- **Split the harness** so the Docker-dependent assertions live in their own
  script with its own guard row, which is then legitimately due-and-unrunnable
  in one narrow place rather than blocking the whole coverage.
- Whatever is chosen, `-NoGuardDue` should stay rare enough to mean something.
  Consider making its use loud in the COMMIT (it already prints), and counting
  it, so a turn that reaches for it is visible in the tracker.

## Validation criteria

- [ ] `parity-tasks.ps1 validate` passes on this box with Docker stopped, with
      no `-NoGuardDue`
- [ ] The Docker-gated coverage is still reported as NOT proven — the fix must
      not turn "we could not check" into "we checked"
- [ ] A genuinely stale harness still fails `validate`, proven by a negative
      control
