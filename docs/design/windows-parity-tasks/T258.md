# T258 - test-agent is flaky: remote.agent.server PTY round-trip tests fail a different assertion on ~2 of 3 runs

## Summary

**`zig build test-agent` — a standing-floor lane since T89b — is flaky on this
box, and it fails a DIFFERENT assertion each time.** Found while running the
floor for T256, whose diff is two `.ps1` files and cannot touch a zig test.

Three consecutive runs at `1f21e9891` + T256's script edits, nothing else
running on the box:

| Run | Result | Failure |
| --- | --- | --- |
| 1 | exit 1 | `remote.agent.server.test.FLOW pause halts streaming; resume continues from buffered offset` — `expected 6, found 0` (`src/remote/agent/server.zig:3552`) |
| 2 | exit 1 | `remote.agent.server.test.client DATA reaches the child (input round-trip)` — slices differ at index 0 |
| 3 | exit 0 | — |

Both failures are in `src/remote/agent/server.zig`'s live-ConPTY round-trip
tests, and both have the shape of a race with the child: the expected bytes
had not arrived yet, so the assertion read an empty or short buffer rather than
a wrong one. Run 3 passing on the same binary is the tell.

### It also HANGS, not only fails — and it is not confined to `test-agent`

New evidence, 2026-07-31 during T205 (`zig build test **-Dapp-runtime=win32**`,
whose diff was `caption_layout.zig` + `Window.zig` and cannot reach an agent
test):

```
error: while executing test 'remote.agent.server.test.FLOW pause halts
streaming; resume continues from buffered offset'
Build Summary: 48/50 steps succeeded; 1 failed; 3400/3467 tests passed
```

The run did not fail — it **stopped**. `ghostty-test.exe` sat at a flat
119.20s of CPU for six minutes with 4 threads, no child processes and no
ConPTY, until it was killed; the "1 failed" line is the kill. So the same test
that fails a short read in `test-agent` can instead block forever, and it does
it in the `-Dapp-runtime=win32` floor lane too.

That widens the cost in the way the section below describes: a hang has no
failure text at all, so a turn that hits it has nothing to attribute and no
signal that its own change is innocent. Whatever wait this test performs, it
can clearly wait unbounded — which points at the same missing wall-clock
deadline, and makes "add a deadline" the fix for both symptoms.

This is the same class of defect T89b already recorded once for this lane —
*"`Thread.sleep(100us)` rounds to the ~15.6ms tick on Windows; use wall-clock
`milliTimestamp()` deadlines in polling tests, never spin counts"* — so the
first thing to check is whether these two tests wait on a spin count, a fixed
sleep, or a single read rather than a deadline loop.

### Reproduced again, identically (2026-08-01, T218 batch 6)

Third independent turn, third diff that cannot reach a zig test (two `.ps1`
files), same 2-of-3 and **the same two assertions in the same order**: run 1
`FLOW pause halts streaming...` (`expected 6, found 0`), run 2 `client DATA
reaches the child (input round-trip)` (slices differ), run 3 exit 0. Nothing
else was running on the box. The failure set is not drifting - it is these two
tests, and the ordering suggests they poison each other rather than failing
independently.

### The hang reproduced identically (2026-08-01, T311)

Fourth turn, same story, and this one matches the T205 hang datapoint to the
detail: `-Dapp-runtime=win32`, `FLOW pause halts streaming; resume continues
from buffered offset`, `ghostty-test.exe` sitting at a **flat 123.02s of CPU**
across two samples two minutes apart, 4 threads all in `Wait`, no window, no
child. Killed at ~11 minutes; the resulting "1 failed / exit 255" is the kill,
not a result. The immediately preceding run of the SAME lane on the SAME source
was exit 0, and T311's diff is the chooser's account row — it cannot reach an
agent test.

So the hang is now 2 of 2 observed occurrences in the **win32** lane rather than
`test-agent`, both on `FLOW pause`. That is worth stating because the task title
still says `test-agent`: the lane is not the variable, the test is.

### Third occurrence, 2026-08-02 (T29's floor)

`zig build test -Dapp-runtime=win32` exit 1 —
`remote.agent.server.test "client DATA reaches the child (input round-trip)"`,
`server.zig:2684`: `expectEqualSlices` got **len 0** where `"ls -la\n"` was
expected. 3582/3651 passed, 1 failed. The identical re-run on the same source
was exit 0, and `test-agent` and the `none` lane were both green in the same
session. T29's diff is one Swift file in `macos/` — it cannot reach a Zig test.

Two things this adds:

- It is the **input** round-trip this time, not `FLOW pause` — so three
  distinct assertions across three occurrences, all in the same file, all with
  the "expected bytes had not arrived yet" shape (empty buffer, not a wrong
  one). That strengthens the shared-cause reading.
- It is a **failure**, not the ~11-minute hang the second occurrence was, and
  it happened in the **win32** lane. So the win32 lane can produce either mode.

## Why it matters beyond the flake

A floor lane that fails ~2 runs in 3 stops being a floor. Every turn that hits
it has to decide whether the red is its own work, and the honest answer costs
two extra ~6-minute runs. Worse, the next turn that sees red on a lane it
*cannot* have broken has been trained to re-run until green — which is exactly
how a real regression gets waved through.

## The fix

- Read both tests; replace whatever timing primitive they use to wait for the
  child with a wall-clock deadline loop that drains until the expected bytes
  arrive or the deadline expires.
- Audit the other `remote.agent.server` tests that drive a real ConPTY for the
  same pattern — two failed independently, so it is unlikely to be only two.

## Validation

- `zig build test-agent` green **10 consecutive runs** (a lane that fails 2 in 3
  is not proved by 3 greens).
- The other two lanes unaffected.
