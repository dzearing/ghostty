# T818 - A diff pane's git calls have no timeout on Windows, so a wedged git would hang the pane's teardown

## In plain terms

When a diff pane asks git what changed, it waits for git to answer. If git
never answers — a credential helper waiting on something, a filesystem that
has stopped responding — the pane waits forever, and closing that pane (or
quitting Ghoztty) waits with it, because the close has to collect the worker
before it can free what the worker is writing into. Nothing recovers; the app
has to be killed.

## Goals

- [ ] A bounded wait on every `git` invocation a diff pane makes, after which
      the pane reports that git did not answer rather than hanging
- [ ] Closing a pane whose git is wedged still closes it

## Evidence

`src/apprt/win32/git_run.zig`'s `captureAlloc` reads the child's stdout to EOF
with no deadline, and `ViewerDiffProbe.deinit` JOINS the worker (it must — the
worker writes into a `Job` the deinit then frees). Mac's `ViewerProcess.run`
has the deadline this lacks: a 15 s `DispatchWorkItem` that calls
`process.terminate()`.

What is already in place, and why this is P2 rather than P1: `captureAlloc`
sets `GIT_TERMINAL_PROMPT=0` and `GIT_OPTIONAL_LOCKS=0`, which are the two
documented ways a read-only `git diff` blocks indefinitely. No hang has been
observed on this box.

The shape to port is a watchdog thread (or a `WaitForSingleObject` on the
child's handle with a timeout, then `TerminateProcess`) — with the same
"stdout is drained to EOF" property `captureAlloc` documents, since a
terminate that leaves a full pipe still deadlocks the reader.

## Validation criteria

- [ ] A unit test in the win32 lane: a child that never exits is given up on
      within the deadline and the capture returns
- [ ] `test/win32/viewer-diff.ps1` still ALL PASS (the deadline must not turn
      a slow first `git diff` on a cold repository into a failure)
