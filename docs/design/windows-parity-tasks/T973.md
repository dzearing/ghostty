# T973 - A half-written build cache reads as a code failure when the compiler blames a source file

## Summary

After the 2026-08-18 reboot the win32 and agent lanes failed with 'root source file struct options has no member named app_version' pointing at src/build/Config.zig - intact source. The torn artifact was a ZIR entry under .zig-cache/z, named only in the compiler's 'note: struct declared here' line, so Get-TornCacheEntry (which matches the FILE LOCATION of an 'error:' line) could not name it and floor-lane reported a code failure. The corroborating 'Invalid timestamp in cache entry' warning was present in the same log. Teach the heal to read the note: line (and the /z ZIR store) so a torn cache heals itself instead of costing a turn a diagnosis.

**Correction (2026-08-19, from the surviving logs).** Two details above were written from memory and are wrong: the torn artifact was `.zig-cache\c\0b3c0f31d02be43a2a65f80447be46bd\options.zig` - a truncated generated build_options file in the `c` bucket, not a `/z` ZIR entry - and no `Invalid timestamp in cache entry` warning appears anywhere in those logs. What IS exactly as described, and is the whole defect, is that the cache path was named only on a `note:` line. The `/z` store is covered anyway, since resolving a hash-FILE entry costs one condition.

## In plain terms

Every so often the machine loses power part-way through a build, and one of
the files the compiler keeps in its scratch folder is left half written. The
next build then complains about a source file that is perfectly fine, and
whoever is at the keyboard spends the next hour debugging code that was never
broken. The build wrapper already knows how to spot this and quietly throw the
bad scratch file away, but only when the compiler points straight at it. Last
time it pointed at it sideways -- in the follow-up "declared here" line -- and
the whole trick missed. After this, that shape gets thrown away and retried
too, so a half-written cache costs a rebuild instead of a diagnosis.

## Goals

- [x] A cache path named only on the compiler's `note: ... declared here` line
      is recognised as a heal target
- [x] Any cache-named file that is torn ON DISK (missing, empty, zero-filled,
      truncated mid-write) heals whatever line named it
- [x] Notes that merely pass through intact generated code still heal nothing
- [x] Hash-FILE entries (the `/z` ZIR store) resolve and delete like hash dirs
- [x] The 2026-08-18 log, replayed verbatim, names exactly the entry a human
      deleted by hand
