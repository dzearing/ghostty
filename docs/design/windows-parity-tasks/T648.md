# T648 - Composer offsets assume ASCII: a non-ASCII report inserts quotes and image chips at the wrong place

## In plain terms

Write feedback with an accent, an emoji, or any non-English text in it, then
quote a passage or paste a picture: the quote or the picture lands in the wrong
spot — further left the more non-English text is above it. Typing plain English
is unaffected, which is why nobody has hit it yet.

## Goals

- [x] One pure, tested conversion between the two ways of counting a position
- [x] Every place the composer hands the control a position goes through it
- [x] Check whether the address bar and the banner editor need it too
- [x] A test that fails if the conversion is taken back out

## Summary

Found while building T637 (image chips). The win32 feedback composer treats a
byte offset into the pane's UTF-8 buffer and a character index into the
RichEdit as the same number. They are the same number **only for ASCII**:
RichEdit counts UTF-16 code units, so `é` is 2 bytes and 1 unit, and an emoji
is 4 bytes and 2 units. Every offset the composer computes purely and then
hands to `EM_EXSETSEL` is therefore short by the difference.

Pre-existing, not introduced by T637 — `viewer_feedback_doc.insertion` (T641)
has the same contract, and `readBack`'s comment states the assumption
explicitly while explaining a DIFFERENT hazard (`WM_GETTEXT`'s CR→CRLF
expansion, which it does fix).

## Details

- Sites: `ViewerFeedbackBar.caret`/`setCaret`/`insertQuote`/`attachImage`/
  `selectChipForDelete`/`formatRange`/`applyQuoteFormatting` — everywhere a
  `CHARRANGE` is filled from a number that came out of a pure module.
- The pure modules are right to work in bytes: they operate on the pane's UTF-8
  buffer, which is also what the report is written from. What is missing is a
  CONVERSION at the boundary, in both directions:
  `utf16UnitsBeforeByte(text, byte_offset)` and its inverse. Both are pure and
  belong beside the buffer, with unit tests over ASCII, Latin-1, CJK and
  astral-plane input.
- Cheap to verify by hand today: open the composer, type `héllo héllo`, quote a
  passage from the page, and watch the block land two characters early.
- Worth checking whether the ADDRESS bar and the banner editor share the
  assumption; if so, the conversion has one home rather than three.

## What landed

- **`src/apprt/win32/utf16_offset.zig`** — pure, none-lane tested:
  `unitsBeforeByte` / `byteForUnits` / `unitLen`. Malformed input is clamped
  rather than fatal (an invalid lead byte counts as one byte and one unit; an
  offset landing mid-sequence or past the end answers the nearest boundary at
  or before it), so a composer cannot be crashed by a stray byte.
- **`ViewerFeedbackBar.charIndex` / `.byteOffset`** — the two-line boundary the
  whole file now goes through. Every `CHARRANGE`, and every `EM_POSFROMCHAR`
  index, is converted; the buffer converted against is always the pane's, which
  `readBack` keeps in step with the control.
- `paintQuoteBars` steps back a CODE UNIT rather than a byte for a block's last
  character — `s.end - 1` can land inside a multi-byte character, and a byte is
  not a position there.
- **The conversion has ONE home, as hoped.** The other two suspects were
  checked and neither shares the assumption: `ViewerNavBar` (the address bar)
  and `BannerDialog` (the banner editor) only ever `EM_SETSEL(0, -1)` — select
  all — so they compute no offset at all.
- Line endings needed nothing: `readBack` already reads with
  `EM_GETTEXTEX`/`GT_DEFAULT`, so a paragraph mark is one byte here and one
  character there. The conversion is about the ENCODING only.

### The first acceptance draft had no teeth

Worth recording, because it passed against a deliberately broken build. Two
mistakes, both the same shape — an assertion narrower than the corruption:

- The Backspace arm asked for "no `[Image` left". The unconverted build deletes
  one character and leaves **`[Imag`**, which does not match that needle
  either. Every arm now compares the WHOLE composer text.
- The caret was parked where BOTH readings of the offset happen to sit just
  after a space, so the leading-space decision agreed by accident. The fixture
  now parks it where the correct byte follows a space and the unconverted one
  lands inside a multi-byte character.

Re-checked by stubbing `charIndex`/`byteOffset` back to identity: 4 arms go
red (doubled space, caret 16 vs 15, a chip eaten into `[Im` taking the emoji
with it, and a mangled report body). With the conversion in: ALL PASS.

## Validation criteria

- [x] Unit tests (none lane): byte offset ⇄ UTF-16 unit index round-trips for
      ASCII, 2-byte, 3-byte and 4-byte (surrogate-pair) sequences. —
      `src/apprt/win32/utf16_offset.zig`, 10 tests (ASCII, Latin-1, CJK,
      astral, a surrogate half, a whole-string round trip over every boundary,
      past-the-end clamping, mid-sequence offsets, malformed bytes, line
      breaks); `zig build test -Dapp-runtime=none` green.
- [x] On-box acceptance: with non-ASCII already in the composer, a quote
      inserted at the caret lands exactly at the caret, and a pasted image's
      chip does too. — the chip half is arms B and C of
      `test\win32\viewer-feedback-utf16.ps1` (whole-text compare plus the
      caret position, ALL PASS 29); the quote half is the T648 arm added to
      the live win32-lane test in `ViewerPane.zig` (a composer seeded with
      `ééééé\n\nTAIL`, caret at unit 7, and an exact-text assertion that the
      block gets no extra blank lines), `zig build test -Dapp-runtime=win32`.
- [x] On-box acceptance: Backspace against a chip that follows non-ASCII text
      still removes the whole chip. — arm D of the same script, compared
      against the whole expected text rather than a `[Image` needle.
- [x] The assertions have TEETH: stubbing the conversion back to identity
      turns 4 of them red (see "What landed").
