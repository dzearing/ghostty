# T1400 - viewer-narrow-pane.ps1 fails in the repo working directory but passes in a fresh worktree on identical code

## Summary

`test\win32\viewer-narrow-pane.ps1` fails its assertion

```
FAIL  E: narrowing never ADDS ink to the strip
```

when run from `D:\git\ghoztty`, and passes (`ALL PASS (63 assertions)`) when the
SAME COMMIT is checked out into a fresh worktree and run from there. Measured
2026-09-06 during T1392, repeatedly, both ways.

The control that makes this a finding rather than a suspicion: the repo's own
source files were reverted to HEAD, rebuilt in place, and the script re-run from
`D:\git\ghoztty` — still red. So it is not the code under test, and it is not
whatever change happened to be in the tree. Something about *where the run
happens* decides the verdict.

`test\win32\viewer-feedback.ps1` showed the same split on the same day (red in
the repo, green in the worktree, identical code). That one had a second,
independent defect underneath — a window lookup with no wait loop — which T1392
fixed, and it is green in both places now. This card is the half of the symptom
that survived that fix, and the shared shape is what suggests one cause rather
than two coincidences.

## In plain terms

A test that checks how the viewer's toolbar shrinks says "broken" when you run it
from the main folder and "fine" when you run the exact same code from a copy of
that folder. Until we know why, neither answer can be trusted — and the check
that is supposed to say "somebody verified this" can never go green.

## Why it matters now

The harness guard `viewer-narrow-pane` clears only on a clean green run, and the
seat that changes viewer chrome works in `D:\git\ghoztty`. So this makes a guard
permanently unclearable from the only place the work is done — which is worse
than a red test, because the next turn's honest options are to leave a guard red
indefinitely or to reach for the `-NoGuardDue` hatch.

## Leads, in the order worth trying

1. **A live repo-built ghoztty.** `Stop-RepoInstances` kills instances running
   from THIS repo's `zig-out`. In a fresh worktree that matches nothing; in the
   main repo it may be racing something the go-loop or the session itself has
   open. Check what `Stop-RepoGhoztty -Exe <repo>\zig-out\bin\ghoztty.exe`
   actually killed in each case.
2. **Window geometry.** The pane geometry differed noticeably between the two
   locations in the sibling script (`page top` 275 in the worktree vs 658 in the
   repo on adjacent runs), and this assertion is about ink across five WIDTH
   bands. A window that opens at a different size measures different bands.
3. **Per-exe-path app state** under `%LOCALAPPDATA%\ghoztty` — a saved layout or
   config keyed on the executable path would differ between the two locations.
