# T249 - Content-sized tabs reflow the strip on every title change

## In plain terms

Each tab is as wide as its own label. A shell rewrites that label every time you
run a command — Windows' own Command Prompt renames itself to the command it is
running and back again when it finishes — so the tabs kept growing and shrinking
all day, sliding each other sideways and dragging the "+" button along with
them. Measured: one ordinary command shoved the next tab 186 pixels across and
186 pixels back, and while it ran, the spot where that tab used to be belonged
to its neighbour, so a click there opened the wrong tab.

Now a tab widens when its label needs the room and simply stays put when the
label gets shorter again. It re-fits itself the next time the strip has a reason
to move anyway — you open or close a tab, or resize the window. The strip stops
twitching, nothing gets truncated that would have fitted, and a tab is where it
was a second ago.

## Summary

T235 made a tab's width its title's width. That is what the user asked for, and
it has a consequence nobody has looked at yet: **a tab's width is now a
function of a string the shell rewrites constantly.** A shell that sets its
title to the running command (which is the normal configuration, and is what
Claude Code does) changes that string on every command — so the tab grows or
shrinks, its neighbours slide sideways, and the "+" walks with them. Under the
old fixed 200 DIP cap none of that could happen: every tab was the same width
until the count changed.

Nobody has reported this, and it may well read as fine (a tab that fits its
label is the point). But it was introduced deliberately and unobserved, which
is exactly the kind of loose thread this tracker exists to hold.

## What to establish first

Watch a real session before changing anything:

1. A pane running a shell that titles itself per command — does the strip
   visibly jump, and is it distracting or is it invisible?
2. Two or more tabs, one of them busy. A width change in tab 1 moves tab 2's
   chiclet under a stationary cursor: does a click ever land on the wrong tab?
   The hit rects are republished in the same paint that moves them
   (`Window.paintTabBar` writes `self.tab_rects` from the same layout it
   draws), so a *stale* rect is not the hazard — a moving target under a
   stationary finger is.
3. Does the strip repaint more than it used to? Title changes already
   invalidated the tab bar (`onTabTitleChanged` → `invalidateTabBar`), so the
   repaint count should be unchanged; only the layout inside it now varies.

If it does not jump, close this as observed-and-fine with the evidence. Do not
add machinery to fix a problem that is not there.

## If it does need fixing

Options, cheapest first:

- **Grow-only hysteresis within a tab's life**: a tab never narrows on a title
  change, only on a count change or a window resize. One `i32` per tab.
- **Quantise** the preferred width to a step (say 40 DIP) so small title edits
  do not move anything.
- **Debounce** the relayout, not the repaint.

## While in there: measurement cost

`paintTabBar` now calls `GetTextExtentPoint32W` once per tab per repaint (up to
64). That is a cheap GDI call and the strip repaints rarely, so it is almost
certainly noise — but if any of the fixes above lands, the natural place to
cache the measurement is the same per-tab state, keyed on (title, font). Measure
before caching; T53's soak lane is the instrument.

**Not done, deliberately.** The ratchet gave the per-tab state a home, so the
cache would now be easy — which is exactly the reason to say no without a
measurement. Nothing in the observation runs showed a repaint cost at all, and
`GetTextExtentPoint32W` on up to 64 short strings is not a plausible hotspot
next to the composite the same paint does. It stays a hypothesis for T53's soak
lane to confirm or kill.

## What was observed (2026-08-11)

Instrument: the app's OWN published tab rects — T231's `chrome.tab_strip` in
`+list --json`, which are the rects its hit tests read — so "how far did tab 2
move" and "would a click have landed on the wrong tab" are answered exactly
rather than scanned for. Fixture: debug build, 3 tabs, 1400x800 window, 125%
DPI, default `cmd.exe` shell, `--config-default-files=false`.

**1. It jumps, and nobody has to configure anything for it to.** With no
synthetic titles at all, one ordinary `ping -n 6 127.0.0.1` in tab 1:

```
idle       t1w=346  t2.left=356  plus.left=709   "C:\WINDOWS\system32\cmd.exe"
running    t1w=532  t2.left=542  plus.left=895   "C:\WINDOWS\system32\cmd.exe - ping  -n 6 127.0.0.1"
finished   t1w=346  t2.left=356  plus.left=709   "C:\WINDOWS\system32\cmd.exe"
```

Tab 2 and the "+" move **+186 px on start and −186 px on finish**. cmd.exe
retitles itself to `<cmd.exe path> - <command>` for the duration of every
command; that is stock Windows behaviour, not a setting.

**2. A click can land on the wrong tab.** The point that had been tab 2's centre
was, mid-command, **inside tab 1**. Across a sweep of six realistic shell titles
the per-command deltas were **+152, −363, +46, +365, −423 px** (up to 30% of the
window width); of the five transitions, two put tab 2's old centre inside tab 1
and two more put it on empty strip, where a click does nothing.

**3. The repaint count is unchanged.** `onPaneTitleChanged` invalidated the
whole strip band before T235 and still does (`Window.zig`, → `invalidateTabBar`,
which dirties the full band). Only the layout inside that repaint now varies.

## What was done

`tab_strip_layout.applySticky` — a grow-only ratchet, pure and asserted at
1.0/1.25/1.5/2.0. A tab widens the instant its title needs the room; it narrows
only when `Window.tab_sticky_key` says the strip was re-fitted, which is any
structural relayout: a tab opened or closed, the window resized, the DPI
changed, a tab reordered. The ratchet is **released** rather than allowed to
truncate — once the high-water marks no longer fit, every tab drops back to what
its own title needs, so grow-only can never be the reason a title ellipsizes or
the strip goes under pressure.

The split is by who caused the motion. The grow happens as the user submits a
command, and refusing it would ellipsize a title with strip to spare — the whole
of T235. The shrink fires minutes later, attributable to nothing, which is
exactly when a moving click target is a hazard.

Same fixture, after:

```
one ordinary command moved tab 2 by 186 px on start and 0 px on finish
```

and over the six-title sweep the deltas became **+152, 0, 0, +48, 0** — total
strip motion **1349 px → 200 px**, with the wrong-tab hit gone from every
transition. (The one non-zero shrink is the release path working: the strip was
at capacity, so the marks were dropped and all three tabs re-fitted at once.)

Alternatives weighed and rejected in **D67**; the residual — a first-ever-longer
title still moves the strip once — is **T737**.
