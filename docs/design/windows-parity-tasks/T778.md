# T778 - A composited window capture, so a probe can assert what is BETWEEN two panes off the input desktop

## In plain terms

The test suite can now take a picture of what one terminal pane is showing.
What it still cannot do is take a picture of a whole WINDOW - panes, the strip
of background between them, and the chrome on top - so any check about how
those pieces sit together has to be run by a human sitting at the machine.

## Summary

T275 built route 0: the `capture-pane` IPC action has ONE pane's renderer read
back its own offscreen target. That answers "what is this pane showing" exactly
and needs no desktop, no composite and no visibility - but by construction it
can say nothing about anything OUTSIDE a pane.

The concrete claim still without an oracle is in `test/win32/split-divider.ps1`
(see its `Measure-GapSolid` header): the divider band between two panes is
painted by the PARENT window, and a `PrintWindow` of the parent shows that band
over a flat-fill terminal - so a stale line UNDER a pane and a correctly
repainted band are indistinguishable in the capture. The script works around it
by asserting the band at three points and by proving the panes TILE the split,
which makes an under-pane line unreachable on screen. That is a real argument,
not a pixel measurement.

## What it has to do

1. Produce a capture of a whole window that is composed the way the screen
   composes it: the parent's GDI paint, plus each pane's rendered content in
   its own rect, in z-order.
2. Reuse route 0's readback per pane rather than adding a third capture path
   (T275 reused hero mode's for the same reason).
3. Decide where the composition happens - in the app (one image out) or in the
   harness (parent PrintWindow + per-pane captures, blitted together in
   PowerShell). The harness side needs no new product code and no new IPC
   shape, which is the argument for it; the app side is the only one that can
   get z-order and clipping right without restating the layout.

## Validation criteria

- [ ] `split-divider.ps1`'s band assertion becomes a pixel measurement of the
      composited strip, with a negative control that goes red against a build
      that paints the band in the wrong place.
- [ ] The composition is asserted against a fixture whose expected image is
      known (e.g. two panes with different tints and a known divider color), so
      a mis-composed capture fails rather than being averaged away.
- [ ] `test/win32/lib/TestDesktop.ps1`'s CAPTURE LIMIT header gains the new
      route, in the same "first one that applies wins" list.
