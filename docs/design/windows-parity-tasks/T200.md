# T200 - A detached upgrade launch fails silently: Start-Process argv shreds the resume prompt

## Summary

The T196 turn (2026-07-30) launched `upgrade-ghoztty-windows.ps1` detached, at
the task boundary, exactly the way every delivery since T89h has, reported the
installed release as "upgrading now", and ended. **It never ran.** No line was
appended to `%TEMP%\ghoztty-upgrade.log`, the installed app and agent pids were
unchanged 45 minutes later, and the only thing that noticed was the T139
watchdog re-entering the loop.

The launch failed in PowerShell **parameter binding**, before line 1 of the
script executed, so the script's own logging could not possibly record it — and
because the child is started `-WindowStyle Hidden` and detached, its stderr went
nowhere. A delivery mechanism that can fail with zero evidence anywhere is the
same defect class as T187 (`RESUME-REUSE FAIL` from an unbounded probe) and T112
(the loop's own continuation breaking): fix the mechanism before the feature.

## Root cause (measured, with a negative control)

`Start-Process -ArgumentList @(...)` does **not** quote its array elements. Every
element is concatenated with spaces, so a multi-word `-ResumePrompt` value is
re-tokenized by the child's own command-line parser and each word becomes a
separate argument.

Reproduced against the real script with the exact failing argument vector:

| run | prompt text | outcome |
|---|---|---|
| A | `…did not take - investigate…` (contains a bare `-`) | exit 1, `PSArgumentException: Cannot process argument because the value of argument "name" is not valid`, **nothing logged** |
| B | same, hyphen removed | binding succeeds, script runs — and logs `pane=did`, `ResumeCommand ('It')`, `ABORT: staging exe not found: Verify\bin\ghoztty.exe` |

Run A is the silent failure: a lone `-` token is an empty parameter name, which
PowerShell rejects at bind time.

Run B is the *worse* finding, and it is the one that generalizes: binding
"succeeded" while assigning **prose to three separate parameters** —
`$Staging = 'Verify'`, `$ResumeCommand = 'It'`, `$LoopPaneId = 'did'`. The
script has no defense against that. It aborted only by luck, because a staging
directory named `Verify` does not exist. A different sentence could have bound a
real-looking value to `-InstallDir` and pointed the kill/swap at the wrong tree.

A standalone probe script confirmed the mechanism independently: passing
`-ResumePrompt '/reset-context First verify the …'` bound `ResumePrompt` =
`/reset-context`, `Staging` = `First`, and dumped the remaining 13 words into
`$args`.

## Fix

Three layers, because any one of them alone still leaves a silent path:

1. **Get the free text out of argv.** Add `-ResumePromptFile <path>` to
   `upgrade-ghoztty-windows.ps1` (keep `-ResumePrompt` for short values, prefer
   the file when both are given). A file cannot be re-tokenized, so no prompt
   content — quotes, hyphens, `%VARS%`, newlines — can ever reach the parser.
2. **Make stray arguments loud instead of silently binding.** Add
   `[CmdletBinding()]` to the param block so an unexpected positional is a hard
   error rather than something that lands in `$Staging`/`$LoopPaneId`. Also
   validate the resolved `$Staging`/`$InstallDir` are real directories before
   anything destructive, and log the FULL resolved parameter set as the first
   line after `=== upgrade start`, so a future mis-bind is visible in the log
   rather than inferred from a weird `pane=` value.
3. **Gate the launch on OUTPUT, not on "Start-Process returned".** New
   `scripts/launch-upgrade.ps1`: write the prompt to a temp file, record the
   current length of `ghoztty-upgrade.log`, start the child detached with its
   stderr redirected to a file, then WAIT for a new `=== upgrade start` line to
   appear (a few seconds is plenty — it is the script's first statement). If it
   does not appear, print the captured stderr and fail loudly **in the launching
   turn**, which is the only moment anyone is still watching. `go.md` and the
   delivery notes should point at this launcher instead of an open-coded
   `Start-Process` incantation that each session retypes from prose.

Layer 3 is the one that matters most: layers 1 and 2 fix the bug that happened,
layer 3 is what makes the *next* unknown failure in a detached launch visible
instead of costing another watchdog cycle.

## Validation

- `test/win32/upgrade-no-fork.ps1` gains:
  - a round-trip assertion that a hostile prompt (spaces, a bare `-`, an
    apostrophe, `%TEMP%`, parentheses) arrives at the pane **byte-identical** to
    what the caller passed;
  - an assertion that a stray positional argument is REJECTED (non-zero exit, an
    error naming the argument) rather than binding to `$Staging`;
  - an assertion that `$Staging`/`$InstallDir` pointing at a non-directory aborts
    before the kill.
- A launcher test: with the script replaced by a stub that exits before logging,
  `launch-upgrade.ps1` must fail loudly and surface the stub's stderr — the
  negative control for layer 3. With the real script, it must report success and
  the log must show the new `=== upgrade start`.
- End-to-end: the next real delivery uses the launcher, and its own boundary is
  the proof (the T112 precedent — the loop's continuation mechanism validates
  itself by continuing).

### What the tests caught in the fix itself

Every one of these was a real defect in my own first cut, found by an assertion
rather than by review:

1. **`[CmdletBinding()]` alone did not stop the mis-bind.** Every `[string]`
   parameter is positional by default, so `-Staging x -NoResume aStrayWord`
   still bound `aStrayWord` to `$InstallDir` and *ran*. Only
   `PositionalBinding = $false` refuses it. (L9–L11)
2. **The launcher declared every healthy launch a failure.** Its marker search
   regex-escaped the pattern and then passed `-SimpleMatch`, which takes the
   pattern literally — so it hunted for `===\ upgrade\ start`, a string in no
   log ever written. The stub logged its start, the launcher denied it. (L19)
3. **The test was itself passing free text through argv** to the launcher's own
   `-Prompt`, and the shredding bound `arg` to `-LoopClaudePid`. That is the
   disease reproducing inside its own cure, and it forced the right shape:
   `-Prompt` is for IN-PROCESS calls (`& launch-upgrade.ps1 -Prompt '…'`, what
   `go.md` now documents), `-PromptFile` is for command-line callers, and the
   launcher gets `PositionalBinding = $false` too so a shredded call is refused
   instead of half-bound. (L23–L26)
4. **`Write-Error` under `$ErrorActionPreference = 'Stop'` throws**, so the
   `exit 2` after it never ran and "you called it wrong" came back as exit 1,
   indistinguishable from "the launch failed". Replaced with an explicit
   `Fail-Launch`.
5. **`.ExitCode` read back empty** in the failure message — the same
   `Start-Process` trap this repo has been bitten by twice (T197). The handle is
   now cached before the child can exit.
