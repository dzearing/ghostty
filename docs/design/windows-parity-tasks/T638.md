# T638 - Viewer feedback: localhost port to working-directory provenance leg on Windows

## In plain terms

When a viewer pane is pointed at a dev server running on your own machine —
`http://localhost:3000` — the feedback button should know which checkout that
server was started from, so feedback lands in the right place. On a Mac it
works this out from the port. Windows has no equivalent of the tool the Mac
uses, so until this lands a localhost pane falls back to the folder the pane
was opened from, which is usually right but not always.

## Goals

- [x] Find the process listening on a loopback port, without elevation
- [x] Read that process's working directory, or honestly report nothing
- [x] Keep both lookups off the UI thread, behind T633's 15s cache
- [x] Prove on the box that the listener's checkout beats the pane's origin

## Summary

Leg 2 of the strategy-D provenance chain, split out of T633 because Windows has
no `lsof` and the mechanism is a genuine choice rather than a translation.
Mac's chain is `lsof -iTCP:<port> -sTCP:LISTEN -t` for the pid, then
`lsof -p <pid> -d cwd -Fn` for that pid's working directory.

## Details

The pid half is settled: `GetExtendedTcpTable` with
`TCP_TABLE_OWNER_PID_LISTENER` gives the listening pid for a port, for both
IPv4 and IPv6, with no elevation. `127.0.0.1`, `0.0.0.0` and `localhost` all
have to map to the same lookup, matching Mac's `loopbackPort` classification.

The cwd half is the open question. Another process's current directory is not
exposed by a documented API on Windows:

- `NtQueryInformationProcess(ProcessBasicInformation)` + a `ReadProcessMemory`
  walk of the PEB's `RTL_USER_PROCESS_PARAMETERS.CurrentDirectory` works, is
  what every tool that does this uses, and is undocumented and
  bitness-sensitive (a 32-bit target from a 64-bit process needs the WOW64 PEB).
  It also needs `PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_VM_READ`, which is
  available for the user's own processes without elevation.
- WMI's `Win32_Process` exposes `ExecutablePath` and `CommandLine` but **not**
  the working directory, so it can only be a heuristic (guess from the command
  line), which is exactly the confidently-wrong answer the report format works
  hard to avoid elsewhere.
- Asking the pane's own shell does not generalize — the listener is usually a
  different process in a different pane, or no pane at all.

Recommended shape when this is taken: the PEB read, guarded so that every
failure mode (access denied, bitness mismatch, process exited between the two
calls) degrades to **null**, which falls through to leg 3 exactly as today. A
provenance leg that returns the wrong repo is worse than one that returns
nothing.

Whatever lands, it runs off the UI thread and behind T633's 15s cache, and a
dev server started *after* the pane was opened still makes the button appear
within the TTL.

## What landed

The PEB read was the recommended shape and it is what shipped — except that
half of it already existed: `src/os/process_cwd.zig` has done exactly this walk
since T185 (for a pane's own shell) using the std ABI types rather than
hand-rolled offsets, so leg 2's second half was a call, not a build. What is
new is `src/os/listening_pid.zig`, the port→pid half:
`GetExtendedTcpTable(TCP_TABLE_OWNER_PID_LISTENER)` over both address families,
v4 first.

The structural part was keeping it off the message loop. Leg 2 used to be a
hook inside `candidateDirectory`, which `ViewerWorktreeProbe.kick` calls on the
**GUI thread** — fine while the hook was absent, a machine-wide TCP table fetch
plus a cross-process PEB read once it is not. So `viewer_worktree` gained a
pure `plan()`: legs 1 and 3 are string work and still settle on the message
loop, and a `.port` plan rides the worker the pane was going to spawn for `git`
anyway. Nothing new is spawned and nothing new blocks.

**Correction to criterion 3 below.** It asked for a listener in no repo to fall
through to the origin. Mac does not do that — `ViewerWorktree.swift`'s
`candidateDirectory` returns the listener's cwd and lets `git` decide, so a
server running out of nowhere yields NO worktree rather than borrowing the
pane's origin. Platform symmetry decides it: the criterion was wrong and the
acceptance script asserts Mac's answer. The fall-through to the origin is what
a port with **no listener at all** does, which is a different case and is
asserted separately.

## Validation criteria

- [x] Unit tests (none lane): port classification — `localhost:3000`,
      `127.0.0.1:3000`, `0.0.0.0:3000` all yield port 3000; a remote host and a
      non-loopback address yield none. *(`viewer_worktree.zig`'s "loopback
      classification" test, plus new "the plan says which leg applies" and
      "resolvePort prefers the listener…" tests. `src/os/listening_pid.zig`
      additionally asserts the two row ABIs, the network-byte-order port read,
      and — against a real socket it opens itself — that `forPort` finds this
      process, and finds nobody once the socket is released.)*
- [x] On-box acceptance: start a throwaway HTTP listener from a known
      directory inside a git worktree, open a viewer pane on its
      `http://localhost:<port>`, and confirm the resolved worktree is that one
      and not the pane's origin directory (make them different, or the test
      proves nothing). *(`test\win32\viewer-worktree-port.ps1` case 1: the
      scratch repo is created under `%TEMP%` and the pane is opened with
      `--working-directory=D:\git\ghoztty`, so the two answers differ; the
      script asserts BOTH that the answer is the listener's tree and that it is
      not the origin. ALL PASS (20).)*
- [x] On-box acceptance: a port with no listener falls through to the
      origin-directory leg rather than erroring or hanging, and a listener in
      no repo resolves to no worktree (Mac's shape — see the correction above).
      *(Same script, cases 2 and 3. Three different outcomes from the same URL
      shape in one run, which is what makes a green-and-empty pass impossible.)*
- [x] The lookup never blocks the UI thread and never leaves a handle open.
      *(It runs in `ViewerWorktreeProbe.work`, i.e. the worker thread, reached
      only from there; case 4 of the script confirms the app still answers
      `+list` after all three lookups. Handles: `process_cwd.fromPid` closes
      its process handle on every path via `defer`, and `listening_pid` opens
      none — it only allocates a buffer it frees on every path.)*
