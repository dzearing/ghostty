# T409 - zig build test-agent hangs: its two test binaries deadlock when run concurrently, each passes alone

## Summary

Found by T107 (2026-08-03) while running the standing floor. `zig build
test-agent` **hangs indefinitely** on this box. Both of its test binaries sit
at **zero CPU** — blocked, not spinning — and never exit. Reproduced twice,
~2 minutes into the run each time; killed at 30 min and 20 min.

This is almost certainly the real root cause of **T401**, which recorded the
same lane wedging and blamed a concurrently-run acceptance script. Nothing
was running concurrently here: the second reproduction was `zig build
test-agent` alone on an otherwise idle box.

## The evidence that names it

`test-agent` builds TWO test binaries (`build.zig:105` `ghoztty-agent-test`,
rooted at `src/agent_main.zig`; `build.zig:138` `ghoztty-agent-core-test`,
rooted at `src/agent_core_test.zig`) and `zig build` runs both **at the same
time** — they start one second apart.

Run each one **directly and sequentially**, no build runner, and both pass
completely:

| binary | result | how |
|---|---|---|
| `ghoztty-agent-core-test.exe` | **3707 passed, 68 skipped, 0 failed** | direct, < 180s |
| `ghoztty-agent-test.exe` | **3779 passed, 76 skipped, 0 failed** | direct, < 240s |

So the tests are fine; the *concurrency* is not. Two candidates, and the
task is to tell them apart:

1. **Shared fixed-name resources.** Both binaries are near-identical suites
   exercising real ConPTYs, sockets and (in `ghoztty-agent-test`) a real
   WebView2. Any fixture at a FIXED path — a named pipe, a port file, a temp
   directory, the `EBWebView-debug` user-data-dir — is contended when two
   copies run at once. The WebView2 one is the loudest suspect: the hung
   `ghoztty-agent-test` had spawned a live `msedgewebview2.exe` tree against
   `%LOCALAPPDATA%\ghoztty\EBWebView-debug\EBWebView` and then stopped
   consuming CPU entirely.
2. **The build runner's `--listen=-` plumbing.** Both children were invoked
   with `--listen=-` (stdout/stdin protocol to `build.exe`). A child that
   spawns a grandchild inheriting the pipe handles — which the WebView2 host
   does — is the classic way for that channel to stall. Note the direct runs
   above did NOT use `--listen`, so this has not been ruled out.

## A workaround, and what it narrows (T109, 2026-08-03)

**`zig build test-agent -j1` serializes the two run steps and the lane
completes.** Observed directly: with `-j1` only ONE agent test binary is ever
resident, where the plain lane runs both. That is worth two things.

As a WORKAROUND it unblocks the floor today - a turn that needs the agent gate
can run `-j1` instead of hand-picking two content-hashed exes out of
`.zig-cache\o\`, which is the only other documented route and is unpleasant
(272 candidate paths on this box).

As EVIDENCE it does not settle the question, and should not be read as if it
did. `-j1` changes concurrency only; both candidate causes above are
concurrency-dependent, so it eliminates neither. It does raise the odds on
cause 1 slightly - the `--listen=-` channel is per-child and would be no less
stalled by a single child - but the discriminator in "The fix" is still the
experiment to run.

## Why it matters more than one lane

`zig build test-agent` is one of the four standing floor gates in `go.md`, so
a hang there stalls **every turn**, and it stalls it in the worst way: no
output, no failure, just a turn that looks busy. T107 lost roughly 50 minutes
of wall clock to it before the shape was clear. It also trains exactly the
habit T258 warned about — re-running a floor lane until it behaves.

## The fix

Identify which of the two causes it is (the cheap discriminator: run the two
binaries concurrently WITHOUT `--listen`, and separately run them one at a
time WITH it), then either give each binary its own instance of whatever
fixture is shared, or serialize the two steps in `build.zig`. Prefer
isolation over serialization — the lane is already minutes long.

Grab a native stack while it is hung if the discriminator is not decisive;
note `cdb.exe` is NOT at the usual Windows Kits path on this box.

## Validation

`zig build test-agent` green ×3 consecutively (it hangs, not fails, so a
single green run proves less than usual), plus whatever unit-level assertion
the chosen fix admits. Fold T401 into this task or close it against the
finding.
