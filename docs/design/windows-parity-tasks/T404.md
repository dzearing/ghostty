# T404 - Sweep the todo list for tasks whose defect was already fixed incidentally by another task

## Summary

**T98 turned up green before a line of it was written.** Its defect — the local
agent reporting the ConPTY child's HANDLE value where a pid belongs, observed as
`428` ("Secure System") — was fixed on 2026-08-02 by **T41**, which needed a real
shell pid for its close-confirmation idle check and fixed the capture at the
source (`pty_child.zig` `spawnFn` → `GetProcessId`, plus `Surface.shellPid` for
the app side). T41's task file never mentions T98, T98's file never learned it
was fixed, and `parity-tasks.ps1 next` handed it out 14 days later as if it were
open work.

That is cheap when the task turns out to be already-done (T98 cost one build and
became the validation it was always missing). It is expensive the other way: a
todo whose defect is gone still gets a full context, and a todo that a later task
*half* fixed is worse — the next agent implements over a fix it never read.

## In plain terms

Cards in the queue describe problems as they were on the day somebody wrote
them down. Nothing ever re-checks that. So an agent can pick up a card, spend
its whole turn building context, and find the problem was quietly fixed weeks
ago under a different card - or, worse, half-fixed, and build over the half
that already exists. After this, the queue tells you how old a card's claim is
and whether anything has moved underneath it before you start.

## Goals

- [x] Picking up a task says how old its claim is and what has touched the
      files it names since
- [x] The same question can be asked of the whole queue in one command
- [x] The strongest signal is surfaced first: a later commit that named the
      task by id
- [x] A pass over the top of that report, with each card closed, rewritten or
      re-verified

## Validation criteria

- [x] `next` prints the filing date, the count of commits that have since
      touched the files the task names, and `CHECK FIRST` when there are any.
      (Section Q1/Q1a/Q1b of `test\win32\parity-tasks-seat.ps1`.)
- [x] `stale-scan` ranks the queue by later commits naming the task, then
      oldest first, and says out loud that it is a prompt rather than a
      verdict. (Q2, Q3, Q3b, Q4c.)
- [x] A task naming only a DIRECTORY is not counted, so a hub file cannot make
      every card that mentions its area look busy. (Q4b - this was the first
      cut's actual failure mode: seventeen cards naming `test\win32` at the top
      with 300+ "touches" each.)
- [x] Outside a git repository the whole signal degrades to silence rather than
      guessing. (Q5, Q5b.)
- [x] The sweep produced all three outcomes on real cards: T606 closed against
      the commit that actually fixed it (`e2d48ac08`, arrived with a main
      intake), T726 rewritten to what is left, T767 and T670 re-verified as
      still entirely real.
- [x] `parity-tasks.ps1 validate` green afterwards.

## Details

The gap is structural, not a T98 accident: a task fixing a defect at the SOURCE
frequently repairs symptoms filed as their own tasks elsewhere, and nothing in
the tracker links them. `parity-tasks.ps1` has no notion of "verify this is still
broken", and the pick step (`next`) trusts `status: todo` completely.

Scope of the sweep:

1. Enumerate every `status: todo` task.
2. For each, ask the cheap question first: does its stated symptom still
   reproduce, or does the code it names still look the way the task describes?
   Most answer from a grep + one file read; only ambiguous ones need a build.
3. For a task already fixed: set it `done` with the commit that ACTUALLY fixed it
   (not a new one), and — the part that matters — record what its validation
   should have been, then land that validation if it is missing. T98's shape:
   the fix was elsewhere, the *test* was the deliverable.
4. For a task PARTLY fixed: rewrite its Summary to what is left, so the next
   agent does not re-derive the whole thing.

Worth considering as a durable fix rather than a one-off sweep: have
`parity-tasks.ps1 next` print the task's age and any commits since that touched
the files it names, so the "is this still true?" question is asked at pick time
instead of after the work.

*Validation:* the sweep's own output — every todo either confirmed still broken,
or closed with the commit that fixed it plus its missing validation landed.
`parity-tasks.ps1 validate` green afterwards.
