# T920 - The release-artifacts guard can never clear itself on this box, so every turn's validate needs the -NoGuardDue hatch

## In plain terms

There is a safety check that refuses to let work be committed until every test
covering the changed code has actually been run. One of those tests can never
finish here, because two of its checks need a container runtime that this box
is under standing orders not to start. So the safety check stays permanently
unhappy, and every turn has to wave it through with an override flag — which is
exactly how a real warning gets ignored later.

## Goals

- [ ] the release-artifacts guard reaches a satisfied state on this box without
      an override
- [ ] a check that genuinely cannot run here is visibly accounted for rather
      than silently blocking the stamp
- [ ] no turn needs `-NoGuardDue` for this guard again

## Summary

`test\win32\release-artifacts.ps1` stamps its guard only when
`$script:failures -eq 0 -and $script:skipped -eq 0` (release-artifacts.ps1:301).
Sections B1 (FILEVERSION single source) and B2 (portable ZIP layout) SKIP when
Docker is not running — and Docker on this box is a standing "never start it
unasked" (a WSL2 backend once took 28 GB and buried the machine). So the run is
`ALL PASS (2 skipped)`, no stamp is written, and `guard-due.ps1 check` keeps
reporting the guard DUE forever.

Observed 2026-08-17 during T816: the guard was already DUE at the turn's claim
(from `.github/workflows/fork-ci.yml`, `release-windows.yml`,
`dist/windows-installer/build-release-artifacts.sh` and the harness itself),
the harness was run and passed every runnable assertion, and the guard was
STILL due afterwards. Step 6's `parity-tasks.ps1 validate` fails on that, so
the commit had to use `-NoGuardDue`.

The distinction the stamp gate is missing is the same one
`deliver-windows-build.ps1` already makes about an unreachable NAS: a check
that is ABSENT because its prerequisite is not here is not the same as a check
that FAILED. Candidate shapes (whichever survives design):

- the harness records which sections were skipped *and why* into the stamp, and
  `guard-due.ps1` treats a stamp with a declared environment-gated skip set as
  current for the files those sections do not read;
- or B1/B2's coverage is split into its own guard row whose `Covers` are only
  the files those two sections actually read, so the Docker-gated half is due
  on its own and the rest of the harness clears normally.

Do NOT "fix" this by starting Docker; the directive is the constraint, not the
bug.

## Validation criteria

- [ ] `test\win32\release-artifacts.ps1` runs with Docker down and leaves
      `guard-due.ps1 check -Guard release-artifacts` reporting CURRENT
- [ ] a genuine failure in any runnable section still leaves the guard DUE
      (negative control)
- [ ] the Docker-gated coverage is still gated on something, not dropped
- [ ] `scripts\parity-tasks.ps1 validate` passes without `-NoGuardDue`
