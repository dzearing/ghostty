# T211 - Shared test-desktop harness: run GUI acceptance scripts off the interactive desktop

## Summary

T207 deliverable 2. The T207 spike (`test/win32/test-desktop-spike.ps1`, ALL
PASS x3) proved a background `CreateDesktopW` desktop gives total foreground
isolation AND can still be driven and measured - but only with two mechanism
swaps, because `SendInput` and `CopyFromScreen` both die there. Build the
shared helper that encapsulates those swaps once, so scripts opt in with a
line instead of each re-deriving them.

## What the spike established (all verified on box, 2026-07-30)

| Capability on a background desktop | Result |
|---|---|
| Window created there, enumerable there | works |
| Window enumerable on the interactive desktop | NO - fully isolated |
| App ever becomes foreground on the interactive desktop | NEVER (watched, 150ms sampling) |
| `SetForegroundWindow` / `GetForegroundWindow` | fail / return 0 - a background desktop is not the INPUT desktop, so it has no foreground window |
| `AttachThreadInput` + `SetFocus` | works - `GetFocus` returns the target |
| `SendInput` | **BLOCKED**, returns 0 events accepted, `GetLastError` = 5 ACCESS_DENIED |
| Posted `WM_KEYDOWN`/`WM_KEYUP` | **works** - lands as terminal input |
| Posted modifier chord (`ctrl+shift+t`) | **works** - fired its keybind, tab count 1 -> 2 |
| `BitBlt` off the desktop DC (== `Graphics.CopyFromScreen`) | **BLOCKED** - `BitBlt` returns false outright; DWM composes only the input desktop |
| `PrintWindow(PW_RENDERFULLCONTENT)` | **partly** - the spike read meanLum 246 / 64 distinct colors and called it "real content"; T211 measured that this is the GDI-painted CHROME only, and the OpenGL terminal surface comes back as a flat fill (see the DONE section and T214) |

## The harness

`test/win32/lib/TestDesktop.ps1` (dot-sourced; a `.psm1` module would need
`Import-Module` plumbing the scripts do not have today), exposing:

- `New-TestDesktop [-Name]` - `CreateDesktopW`, plus a **persistent worker
  thread** bound to it with `SetThreadDesktop`. It must be a long-lived
  thread with a command queue: `SetThreadDesktop` is per-thread and cannot be
  done on the PowerShell host thread (it fails on a thread that owns windows
  or hooks), so every desktop-side call has to be marshalled onto that one
  thread. The spike does the single-shot version of this and is the reference.
- `Start-OnTestDesktop -Exe -Args` - `CreateProcessW` with
  `STARTUPINFO.lpDesktop = "WinSta0\<name>"` and `CREATE_NO_WINDOW` (without
  it the child's log floods the harness's stdout).
- `Focus-TestWindow` - `AttachThreadInput` onto the app's GUI thread, then
  `SetActiveWindow`/`SetFocus`. This REPLACES `GrabForeground`; the 30 scripts
  that define their own copy of the T86 `GrabForeground` should end up calling
  this instead.
- `Send-TestKeys` - posted `WM_KEYDOWN`/`WM_KEYUP`, with modifiers applied via
  `SetKeyboardState` on the (attached, therefore shared) input queue. Post
  `WM_KEYDOWN` only, never `WM_CHAR` as well: the terminal window class skips
  `TranslateMessage` (`App.run`) and calls `ToUnicode` itself, so posting both
  doubles every character - the spike hit exactly that (`sSpPiIkKeEbB`).
- `Get-TestWindowPixels` - `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` into
  a memory DC, sampled with GDI `GetPixel`. Same shape as the existing
  `Get-RectBrightness` helpers so migration is mechanical.
- `Remove-TestDesktop` - kill the app, `CloseDesktop`, join the worker thread.

Also needed: a documented escape hatch (`-InteractiveDesktop` switch or
`GHOZTTY_TEST_INTERACTIVE=1`) that runs a script the old way for debugging,
since nobody can watch a window on a desktop they cannot see.

## Validation

- The spike script keeps passing (it is the harness's own reference test).
- One real script migrated onto the helper as the proof-of-concept, ALL PASS
  x3, with its negative control still failing.
- `GetForegroundWindow` polled on the interactive desktop for the whole run
  never returns a harness-launched pid.

Two things the work turned up, both material:

1. **A product bug, fixed here.** `App.performDeferredFocus` bailed unless
   `GetForegroundWindow() == root` (the T89f2 ping-pong guard). A background
   desktop has NO foreground window, so every deferred focus was dropped and
   keyboard focus could never move - the first POC run failed exactly there.
   Fixed by routing the decision through the new pure
   `shouldPerformDeferredFocus(on_input_desktop, foreground, root)` (unit
   tested both ways) and a cached `onInputDesktop()` that compares the
   thread desktop's name with `OpenInputDesktop`'s. The interactive path is
   unchanged; failure to query reports "on the input desktop", so it degrades
   to today's behavior. Sweep for more of these: **T215**.
2. **T207's capture answer is narrower than the spike concluded** -
   `PrintWindow` returns GDI chrome, not the OpenGL terminal surface. Full
   measurements and the routing decision: **T214**. T213 (chrome probes) is
   unaffected and can proceed.

Two PowerShell traps cost real time here and are documented in the harness
so the T212/T213 migrations do not re-pay them:

- In an array literal the comma binds tighter than `+`, so
  `@($a, $b, $c + $d)` CONCATENATES arrays instead of adding. Every probe
  built that way silently read `-1`.
- PowerShell's .NET method binder converts `$null` to `""` for a `string`
  parameter, and win32 reads `""` as "match a window whose class/text IS
  empty". That made "any class" enumerations return nothing and
  `FindWindowEx(..., "EDIT", null)` miss an EDIT that had text in it.
  Normalised in one place (`NoFilter`) inside the harness.

Also measured, and recorded in the harness header: a modifier chord does NOT
survive into a standard control (the app TranslateMessage's dialog messages,
and translation reads the queue's own key state, so ctrl+a arrives as a
literal 'a'). Terminal surfaces take chords fine; dialogs take plain keys and
text.
