# T897 - Audit the Mac test suite for the T594 leak class: a viewer test handing a URL to NSWorkspace opens the user's real browser

## In plain terms

On Windows, test runs sometimes opened the user's real Edge browser on pages
the tests serve to themselves, and the windows piled up until closed by hand
(T594). The Mac app has the same "hand this URL to the system browser" moves
— an http(s) popup goes to the default browser by design
(`ViewerView.popupDestination`), and link routing can shell out too. This
task checks whether any Mac test can reach those moves for real, and closes
the hole the same way Windows did if so.

## Summary

Windows' fix (T594) is structural: in test builds, every viewer shell-open
path short-circuits before `ShellExecuteW` (`builtin.is_test`), recording to
the test's link sink when one is installed and logging loudly otherwise. The
acceptance harness additionally runs a browser-process tripwire around the
viewer suite (`test\win32\lib\BrowserLeak.ps1`).

For the Mac seat:

1. Find every path in the macOS app that hands a URL to
   `NSWorkspace.shared.open` (or equivalent) on behalf of a viewer —
   popupDestination's default-browser arm, link routing's browser arm, any
   help/release-page openers reachable from tests.
2. Determine whether any XCTest / test harness can reach them with a live
   WKWebView (the Windows leak came from the live host-floor test's pages).
3. If reachable: add the equivalent structural guard for test runs and, if
   the Mac acceptance flow can leak a browser, an equivalent tripwire.

## Validation criteria

- [ ] Every NSWorkspace-open path reachable from a viewer is enumerated
- [ ] Each is either proven unreachable from tests or guarded in test runs
- [ ] Mac test suite green after any guard lands
