# T672 - The composer acceptance scripts' chip-deletion arms pass over a PARTIALLY eaten chip

## In plain terms

Two of our own tests claim to prove that deleting an attached picture removes
the whole thing. They do not. If the code left half of it behind, both tests
would still say PASS — which is exactly what happened while T648 was being
written. The tests need to compare what is in the box against what should be in
the box, instead of looking for one phrase.

## Summary

Found during T648, by measurement rather than by review: the acceptance script
being written passed against a build with the offset conversion deliberately
stubbed out, because its Backspace arm asked for "no `[Image` left" and the
corruption leaves **`[Imag`** — which does not match that needle either.

The same weak needle is in two shipped scripts:

- `test\win32\viewer-feedback-images.ps1:335` — `$afterDelete -notmatch
  '\[Image'`. Satisfied by `[Imag`, by `[Ima`, by any prefix short of `[Image`.
- `test\win32\viewer-feedback-carousel.ps1:418` — `$afterDelete -notmatch
  '\[Image #1\]'`. Weaker still: satisfied by `[Image #1` with only the closing
  bracket eaten, which is precisely the failure the chip-atomicity code
  (`selectChipForDelete`) exists to prevent and precisely what it produces when
  it misses.

A chip that no longer parses still LOOKS attached and silently drops its
picture from the report. That is the defect these arms are named after, and
neither can currently see it.

## Details

- The fix is the rule T648 landed on: compare the WHOLE composer text against
  the exact expected string, the way
  `test\win32\viewer-feedback-utf16.ps1` now does in every arm. A substring
  needle cannot distinguish "correct" from "damaged in a way the author did not
  picture", and the damage is never the shape you pictured.
- `viewer-feedback-utf16.ps1` also has a `Show-Text` helper that escapes
  non-printing and non-ASCII characters for the failure message, so a mismatch
  is readable on a console that cannot render the text. Worth sharing rather
  than copying a third time — `test\win32\lib\` is where it belongs.
- While in there, audit the other composer arms for the same shape: any
  `-match`/`-notmatch` where the whole expected text is known and could be
  compared instead.
- Teeth check whatever lands: stub `ViewerFeedbackBar.charIndex`/`.byteOffset`
  back to identity, rebuild, and require the tightened arms to go red. An
  untested tightening of an untested assertion is the same bug one level up.
  (T673 proposes a seam that makes this one command instead of a source edit.)

## Validation criteria

- [ ] `viewer-feedback-images.ps1`'s chip-deletion arm compares the whole
      composer text, not a `[Image` needle.
- [ ] `viewer-feedback-carousel.ps1`'s chip-deletion arm does the same.
- [ ] Both go RED against a build whose chip lookup misses (the T648 stub), and
      the failure message names the actual text.
- [ ] Both stay ALL PASS against HEAD.
