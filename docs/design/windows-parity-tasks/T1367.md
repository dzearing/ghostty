# T1367 - The installer's maintenance prompt may be sequenced after everything is installed

## In plain terms

Running the installer when Ghoztty is already installed is supposed to stop and
ask whether to repair it, with Cancel leaving the machine untouched. There is
reason to think the question is being asked at the very END of the install
instead — after the files have been written — which would make Cancel a
formality. Nobody has watched it happen yet; this is to find out and fix it if
it is true.

## Summary

While fixing the fork-CI red on `baa842241` (T1364's turn) the cause turned out
to be that **wixl resolves `After="<a custom action>"` by appending to the end
of `InstallExecuteSequence`**, not by placing the action next to the one it
names: `SetRepairModeFlags After="SetRepairMode"` landed at **6605**, past the
`CostFinalize` at 1000, and the build's own check caught it. That arm is fixed
(both anchor on `Before="CostFinalize"` now).

The same construct is used twice more in the maintenance block, and nothing
checks where THOSE land:

```xml
<Custom Action="SetMaintenancePromptCmd" After="CostFinalize">...
<Custom Action="MaintenancePrompt" After="SetMaintenancePromptCmd">...
```

If the theory holds, `MaintenancePrompt` is appended to the end of the sequence
— after `InstallFinalize` — so the Repair/Cancel dialog appears once the install
has already run, and its `Return="check"` 1602 ends a transaction that has
nothing left to undo. The existing assertions cannot see it: they only require
`MaintenancePrompt` to be sequenced AFTER `CostFinalize`, which the end of the
table satisfies.

The evidence needed is one line, and it is already wired: `build-msi.sh` now
prints the resolved `sequence: ...` numbers for all of these on every build, so
the next fork-CI run over this commit answers the question without a local
Docker/wixl setup.

      it (an explicit `Sequence=` number, or an anchor on a standard action) so

      and `InstallValidate`, so the hole that let this through is closed
      - plus `MaintenancePrompt < PrepareInstallDir`, because that step renames

## Progress log

- 2026-09-05 08:54: claimed; work starting.
- 2026-09-05 08:56: root cause found by reading wixl's source (msitools tools/wixl/builder.vala + msi.vala): visit_action turns Before=X into 'X depends on me' and After=X into 'I depend on X'. add_sorted_actions only uses actions WITHOUT incoming deps as topological entry points, and assigns an unsequenced custom action the running counter+1 at the point it is emitted. So a custom action reachable only through After= has no incoming dep, is visited at the END of the entry-point loop, and lands past InstallFinalize(6600) - exactly the 6605 T1364 saw. Consequence here: SetMaintenancePromptCmd After=CostFinalize and MaintenancePrompt After=SetMaintenancePromptCmd BOTH append to the end, so the Repair/Cancel question is asked after the install has already run. Second finding: PrepareInstallDir (Before=InstallValidate) renames ghoztty-agent.exe aside, so if it ran before the prompt a Cancel would leave the existing install with no agent exe - the prompt must sequence before it. Fix going in: explicit Sequence= numbers (wixl honours them and add_implicit_deps chains explicitly-sequenced actions into the standard chain) so the ordering cannot depend on hash iteration order.
- 2026-09-05 09:12: CONFIRMED off fork-ci run 33976131310 (windows-cross, commit 2686b4fa5): 'sequence: CostFinalize=1000 SetRepairMode=5 SetRepairModeFlags=4 SetMaintenancePromptCmd=6604 MaintenancePrompt=6605 InstallValidate=1400 InstallFinalize=6600'. The Repair/Cancel question was being asked at 6605 - five past InstallFinalize - so the whole install had already run and Cancel had nothing to cancel. Fix landed: the six immediate actions in that band now carry explicit Sequence numbers (SetRepairMode 990, SetRepairModeFlags 991, SetMaintenancePromptCmd 1010, MaintenancePrompt 1020, SetPrepareInstallDirCmd 1030, PrepareInstallDir 1040) and none anchors on another custom action. The build's check gained the upper bound it never had (prompt < InstallValidate) plus prompt < PrepareInstallDir, and prints the two new numbers.
