# T1418 - win32 machine pill names a relay machine by device id, not the friendly name the chooser shows

## In plain terms

A remote window's titlebar now says which machine it is running on. When you
reached that machine by hostname it says something you recognise
(`build-agent-1`). When you reached it through the relay it says the device id
— a long stable string nobody picked — even though the machine chooser you
opened it from listed it as "MaximusHome" two seconds earlier. The same box
should have the same name everywhere in the app.

## Summary

Filed out of T610 (2026-09-07). `Window.machineDisplayName` returns
`RemoteMachine.displayName()`, which is the hostname for `.tcp` and the DEVICE
ID for `.relay`. That is the app's single naming derivation (T1390) and the
close confirmation and the pill tooltip speak it too — so this is one fix in
one place, not three.

The friendly name exists only in the relay directory
(`relay_directory.Device.name`, `GET /v1/client/devices`), which the machine
chooser fetches and the Activity Monitor's carousel fetches again. A window
holds no copy: nothing records `dev.name` at dial time, and nothing caches an
id -> name map, so a window that was restored at startup — or opened by
`+new-remote-window --device=…` — has never seen the directory at all.

## Details

Two candidate shapes, and the second is probably right:

1. **Record the name at dial time.** `MachineChooser.openRelayWindow` has
   `dev.name` in hand; carry it into `setRemoteMachine` and own it like the
   other strings. Cheap, and wrong on its own: it answers for windows the
   chooser opened and for no others, so the same machine would be named two
   ways depending on how the window was born.
2. **A small persisted id -> name map**, written whenever a directory listing
   is parsed (the chooser and the Activity Monitor both already do it), read by
   `displayName`. That makes the name available to a restored window, to a
   window opened from the CLI, and to the close confirmation, from one store.
   `host_defaults.zig` is the precedent for a per-machine store keyed on the
   device id, and `RemoteMachine.hostDefaultsKey` already computes that key.

Whichever shape: `displayName` stays the ONE derivation. A rename on the relay
should reach the pill at the next listing rather than pinning whatever the name
was when the window opened, and a machine we have never listed must still be
namable — falling back to the device id, which is what happens today.

Mind the borrow contract: `displayName` currently returns a slice of the
window's own strings and its doc says so. A map-backed name changes who owns
that memory.

## Validation criteria

- [ ] A window opened on a relay device shows that device's friendly name in
      the pill, on both a chooser-opened and a CLI-opened window.
- [ ] A window restored at startup, whose session predates any directory
      fetch, shows the friendly name once a listing has happened.
- [ ] A device with no known name still shows its id, never a blank pill.
- [ ] The close confirmation (T1390) and the pill tooltip name the machine the
      same way, from the same call.
- [ ] Floor green: both zig test lanes, `test-agent`, P1-P3.
