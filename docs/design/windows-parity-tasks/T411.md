# T411 - Nothing ever reports a LIVE pinned agent session that no restored pane attached to: it holds a slot and a real shell forever (sibling of T278)

## Summary

Found by T108 (2026-08-03) on the user's release install. The agent holds **4
live pinned sessions; the restored layout references 3**. The fourth
(`d30c78af…`, a real `cmd.exe` started 2026-08-02 05:29:02 in `D:\git\ghoztty`)
is attached to nothing and will stay that way forever:

- `pinned` is precisely what exempts a session from the agent's idle-TTL reaper
  — `server.zig`: *"Pin persistent local sessions so the idle-TTL reaper never
  evicts them while orphaned (§7.1, T11)"*. That is correct on its own terms: a
  session must survive its viewer quitting.
- Nothing anywhere compares the agent's live session set against the set the
  restore actually attached. `App.captureSessionLayout` writes the manifest FROM
  the live windows; there is no read in the other direction.
- So the orphan is invisible unless the user opens the chooser roster and reads
  it, and it costs a session slot (cap 256) and a real shell process, forever.

**This is the LIVE sibling of T278.** T278 is the same one-way ratchet with dead
tombstones and has already been observed wedging the agent at the 256 cap; this
is the alive-child case, which the reaper is *intentionally* not allowed to
touch. Fixing T278 does not fix this, and the two want different answers.

## In plain terms

When the app starts, it reconnects to terminal sessions that kept running in
the background while it was closed. Sometimes the background service is holding
a live session that no window picks up — it just sits there invisibly, using
memory and one of a limited number of session slots, forever. Nothing ever
told anyone. Now the app prints one clear line at every startup saying how
many such leftover sessions exist (including "0" when everything is
accounted for), so a leak is noticed the day it happens instead of during a
forensic investigation weeks later.

## Goals

- [x] The launch restore logs, in the same breath as "restored N window(s)",
      how many live agent sessions no restored pane attached to.
- [x] The zero case logs too — a counter that only appears when nonzero cannot
      be told from a counter that never runs.
- [x] The counting rule is the SAME rule restore uses to attach (one shared
      function, so the two cannot drift).
- [x] The orphan itself is untouched — reporting, never reaping (the pin's
      guarantee stands).
- [x] Follow-ups filed for the ambitious halves: chooser marking (T520),
      opt-in aging (T521 + decision D18), and the Mac sibling (T519).

## Evidence (2026-08-03, user's release agent, measured)

```
ghoztty +sessions
6a46bb99…  alive  attached  idle  pid=472  pinned  cwd=D:\git\ghoztty\
05710eba…  alive  attached  idle  pid=896  pinned  cwd=C:\Users\David
d30c78af…  alive  DETACHED  idle  pid=596  pinned  cwd=D:\git\ghoztty   <-- orphan
e901d928…  alive  attached  idle  pid=556  pinned  cwd=D:\git\ghoztty\
```

`session-layout.json` holds 3 leaves, all with `session_id`, all matching the
three attached rows. The app log's last launch says
`session-restore: restored 2 window(s)` and, one line later,
`agent upgrade check: … 4 live session(s)` — **the app had both numbers in hand,
in the same second, and said nothing about the gap.**

## Fix — surface it, do not reap it (shipped 2026-08-06)

Item (1) of the original plan, implemented in `src/apprt/win32/App.zig`:

- `leafAttachSessionId` — THE attach rule (recorded id iff alive/relaunchable
  in the roster, or roster unknown; null for viewers/id-less/gone), now shared
  by `restoreAttachOverride` and the new counter so they cannot drift.
- `collectAttachedLeaves` — records the session ids each restored window's
  leaves attach to, and counts the attaching panes.
- `countUnattachedLive` — live roster sessions outside the attached set.
  ALIVE only: tombstones are T278's problem.
- `restoreSessionLayout` logs after `restored N window(s)`:
  `session-restore: attached N pane(s); M live agent session(s) unattached` —
  `warn` when M > 0, `info` when 0; a failed roster probe logs
  `unattached live session count unknown (probe failed)` instead of omitting
  the line. Release builds write info+ to `%LOCALAPPDATA%\ghoztty\ghoztty.log`,
  so the line lands on the user's install too.

Items (2)/(3) are deliberately NOT here: chooser marking is T520, aging is
T521 gated on decision D18 (the user's call on whether pinned sessions may
ever expire). The Mac sibling of this log line is T519 (`seat: mac`).

The chooser "Restore All" path also probes the roster but deliberately does
NOT log the gap: after launch, other open windows legitimately hold sessions,
so "unattached to what I just rebuilt" would not mean "orphaned" there.
