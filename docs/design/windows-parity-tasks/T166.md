# T166 - +list --json reports an empty working_directory for agent-backed local panes

## In plain terms

Scripts and agents ask Ghoztty "which folder is this terminal sitting in?"
through the window-listing command. For any window that came back after
restarting the app, the answer was wrong — it named the user's home folder no
matter where the terminal really was, because the app answered from its own
startup guess instead of asking the session manager, which knew. Now the
session manager's answer is threaded through, so the listing tells the truth
for fresh windows, restored windows, and windows revived after a reboot alike.

## Goals

- [x] A pane opened without an explicit directory reports its real cwd (was
      already fixed by T144/T236 — measured before touching anything)
- [x] A pane RE-ATTACHED after an app restart reports the session's real cwd,
      not the config default
- [x] A pane revived across an AGENT restart (relaunch notice) reports the
      recorded cwd
- [x] The T138 `+sessions` fallback in `upgrade-ghoztty-windows.ps1` is
      retired; the RELAUNCH-CWD guard reads the relaunched window's own pane

## Validation criteria

- [x] `test\win32\auto-launch-cwd.ps1` extended and ALL PASS (30 asserts):
      new C7 (relaunch-notice path reports recorded cwd) and section D
      (app-only restart → re-ATTACH reports recorded cwd, pid preserved)
- [x] `test\win32\upgrade-no-fork.ps1` ALL PASS with the rewritten

- [x] Floor: `floor-lane.ps1 -Lane all` → none/win32/agent all PASS;

## Summary

`+list --json` reports `"working_directory": ""` (and `"pid": 0`) for every
LOCAL session-persistence pane on Windows, so nothing can ask "where is this
pane?" through the documented interface. Sibling of T98 (bogus pid); this row
is the **cwd** half, which T98 does not cover.

Evidence (2026-07-29, live release instance, four agent-backed panes):

```
{"id":"2D1184AD-...","title":"...","working_directory":"","pid":0,"tty":"","name":"..."}
```

while the agent's own view has the real answer:

```
ghoztty +sessions --json
  { "id": "95718f13...", "pid": 792, "cwd": "D:\\git\\ghoztty", ... }
```

A non-persistent (Exec) pane reports its cwd correctly - `auto-launch-cwd.ps1`
section A asserts exactly that and passes - so the gap is specific to the
agent-backed path: the app never learns the cwd it handed to the agent, and
nothing reads it back from the session record.

Impact, measured rather than assumed: `upgrade-ghoztty-windows.ps1`'s
RELAUNCH-CWD guard (the T132 belt-and-braces that exists so a pane landing in
`C:\Windows\System32` can never again cost 7h20m of dead loop) matched on this
field, so on a persistence box - i.e. the default - it could only ever log
`RELAUNCH-CWD UNKNOWN`. T138 worked around it by falling back to `+sessions
--json` filtered to sessions created in the last two minutes; that workaround
should come out once this is fixed.

## Details

Likely fix: thread the session's recorded cwd (the agent already stores it -
T132 made `OPEN.cwd` durable in `sessions.json`) back into the surface's
reported working directory, so `+list` answers from the same source `+sessions`
does. Watch the additive-evolution rule: an older agent may not report cwd, and
the reader must degrade to "" rather than fail.

Validation: extend `auto-launch-cwd.ps1` (it already proves the Exec case) with
an agent-backed pane whose `+list --json` working_directory equals the
requested directory, cross-checked against the shell's own `cd` output; then
drop T138's `+sessions` fallback in `upgrade-ghoztty-windows.ps1` and re-run
`upgrade-no-fork.ps1` (its section C asserts RELAUNCH-CWD OK).

## Resolution (2026-08-05)

The evidence predated T144/T236: measured at HEAD with a hermetic probe, OPEN
panes (with and without an explicit `--working-directory`) already reported the
right cwd and a real pid. The surviving defect was the **re-attach family**:
after an app restart every restored pane reported the config-resolved default
(`C:\Users\David`) — the `initTerminal` seed from the restore path — while the
agent's ATTACHED reply was already carrying the session's real cwd, unread.

Fix, in shared core (`src/termio/Remote.zig` `threadEnter`, so macOS gets it
too): capture `outcome.cwd` from the attach-family replies (ATTACHED alive,
and the dead-tombstone notify/auto/prompt branches, which respawn in the
RECORDED cwd), set the terminal pwd under the renderer mutex, and push a
`pwd_change` surface message so the apprt's cached copy — the value `+list`
actually reports (T111b) — follows. The push uses stream_handler-style timed
retries with the RPC canceller as the teardown escape: the surface mailbox is
the SHARED app mailbox, drained only by the GUI thread, which during a restore
rebuild is busy building windows — an instant push was measured dropping 2 of
3 restored panes' updates. An older agent that omits `cwd` leaves the seeded
value standing (additive evolution: degrade, never fail).

Also retired the T138 workaround in `upgrade-ghoztty-windows.ps1`: the
RELAUNCH-CWD guard now parses `+list --json` and reads the relaunched window's
own pane by name, instead of regex-grabbing the first non-empty
working_directory anywhere in the list (post-T144 that could be a DIFFERENT
window's pane and mis-grade the guard in either direction) and falling back to
`+sessions --json` recency filtering.

Chosen design: thread the agent's wire-truth (ATTACHED.cwd) rather than
persisting each pane's pwd in the session-layout manifest — the agent's answer
is live, already on the wire, and survives the manifest being lost (the same
reason Restore All reads agent blobs).

Evidence: `auto-launch-cwd.ps1` 30/30 PASS (new C7 + section D);
`upgrade-no-fork.ps1` ALL PASS; floor none/win32/agent PASS; P1–P3 ALL PASS.
Mac-side validation of the shared-core change: T507.
