# T166 - +list --json reports an empty working_directory for agent-backed local panes

## Summary

`+list --json` reports `"working_directory": ""` (and `"pid": 0`) for every
LOCAL session-persistence pane on Windows, so nothing can ask "where is this
pane?" through the documented interface. Sibling of T98 (bogus pid); this row
is the **cwd** half, which T98 does not cover.

Evidence (2026-07-29, live release instance, four agent-backed panes):

```
{"id":"2D1184AD-...","title":"...","working_directory":"","pid":0,"tty":"","name":"..."}
```

while the agent's own view has the real answer:

```
ghoztty +sessions --json
  { "id": "95718f13...", "pid": 792, "cwd": "D:\\git\\ghoztty", ... }
```

A non-persistent (Exec) pane reports its cwd correctly - `auto-launch-cwd.ps1`
section A asserts exactly that and passes - so the gap is specific to the
agent-backed path: the app never learns the cwd it handed to the agent, and
nothing reads it back from the session record.

Impact, measured rather than assumed: `upgrade-ghoztty-windows.ps1`'s
RELAUNCH-CWD guard (the T132 belt-and-braces that exists so a pane landing in
`C:\Windows\System32` can never again cost 7h20m of dead loop) matched on this
field, so on a persistence box - i.e. the default - it could only ever log
`RELAUNCH-CWD UNKNOWN`. T138 worked around it by falling back to `+sessions
--json` filtered to sessions created in the last two minutes; that workaround
should come out once this is fixed.

## Details

Likely fix: thread the session's recorded cwd (the agent already stores it -
T132 made `OPEN.cwd` durable in `sessions.json`) back into the surface's
reported working directory, so `+list` answers from the same source `+sessions`
does. Watch the additive-evolution rule: an older agent may not report cwd, and
the reader must degrade to "" rather than fail.

Validation: extend `auto-launch-cwd.ps1` (it already proves the Exec case) with
an agent-backed pane whose `+list --json` working_directory equals the
requested directory, cross-checked against the shell's own `cd` output; then
drop T138's `+sessions` fallback in `upgrade-ghoztty-windows.ps1` and re-run
`upgrade-no-fork.ps1` (its section C asserts RELAUNCH-CWD OK).
