# T951 - The release-artifacts guard can never clear on this box, so every turn's validate needs a hatch

## In plain terms

One of the automatic checks that runs before every commit is stuck on
permanently red, for a reason nobody can fix from the keyboard: part of it
needs a tool that is not running and must not be started here. So every turn
has to wave it through by hand, and a check that is always waved through stops
being a check — the day it goes red for a REAL reason, nothing will look
different.

## Summary

`scripts\guard-due.ps1` reports `release-artifacts` DUE, and running
`test\win32\release-artifacts.ps1` does not clear it. The harness is green
(`ALL PASS (2 skipped)`) but sections B1/B2 need Docker (the msitools image),
and by design a run with ANY skip does not stamp — "a Docker-less run never
looked at the packaging sections it would be vouching for"
(`release-artifacts.ps1:296-304`). Docker is not running on this box and
starting it is ruled out (the WSL2 backend has buried the box before), so the
stamp can never be written from this seat and step 6's `validate` fails on it
every turn until `-NoGuardDue` is passed.

That hatch exists for exactly this, and it is loud, but a hatch used every
turn is indistinguishable from no gate at all.

Options worth weighing (mechanism, so this is the seat's call — record which
one and why):

- **Split the row**: the workflow/script wiring sections (A, C-F) cover
  `.github/workflows/*` and `build-release-artifacts.sh` and run fine
  Docker-less; the packaging sections cover the MSI/ZIP shape. Two guard rows
  with two stamps means the always-runnable half actually gates, and only the
  packaging half sits idle.
- **Stamp what was actually run**: record the covered files PER SECTION so a
  partial run stamps its own half honestly.
- **Mark the guard Docker-gated** in `guard-due.ps1` so it reports
  `GUARD BLOCKED (docker down)` rather than `DUE`, and does not fail
  `validate` — visible, but not a wolf cry.

Whatever is chosen, the property to keep is the T783 one: the report must
distinguish "nobody ran this" from "this cannot run here", because today they
look identical.

## Validation criteria

- [ ] with Docker down, `guard-due.ps1 check` no longer reports
      `release-artifacts` as plain DUE
- [ ] `parity-tasks.ps1 validate` passes with no `-NoGuardDue` on a clean tree
- [ ] an edit to the release WIRING (a workflow file) still arms a gate that
      a Docker-less run can clear
- [ ] an edit to the PACKAGING inputs is still reported as unverified here
- [ ] acceptance: a section in `test\win32\go-loop-guard.ps1` (or the
      guard-due harness) pinning both halves
