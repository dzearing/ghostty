# T633 - Viewer feedback: worktree provenance + the nav-bar feedback button (win32)

## In plain terms

On a Mac, when a viewer pane is showing something that belongs to one of your
checked-out copies of a repo, its navigation bar grows a small button that lets
you file feedback straight into that copy. On Windows there is no such button,
because nothing here works out which checkout the pane's content belongs to.
This task teaches Windows that question and puts the button on screen when the
answer is yes — pressing it does nothing yet, that is the next task.

## Goals

- [x] A pure `viewer_worktree.zig`: strategy D's classification (legs 1 and 3,
      plus the loopback-port classification leg 2 will plug into), the repo-root
      argv/parse, and the 15s (location, origin) cache — all asserted in the
      none lane.
- [x] `ViewerWorktreeProbe.zig` runs `git rev-parse --show-toplevel` on a worker
      thread and posts `WM_APP_VIEWER_WORKTREE` back; the pane never blocks its
      message loop on a process spawn.
- [x] The nav bar grows a TRAILING, icon-only feedback button that exists if and
      only if the pane's content resolves to a working tree, with the full path
      on its tooltip. Geometry asserted at 1.0/1.25/1.5/2.0.
- [x] Re-resolved on every location change — `navigate` and the browser's own
      `syncCommitted` alike.
- [x] An on-box acceptance script covers the shown and hidden cases against one
      running app, so neither can pass while the other is broken.

## Summary

First of the T384 split (the win32 half of CLAUDE.md's "Worktree feedback
capture"); it inherits T384's own dependency on T375 rather than depending on
the split parent, which would deadlock the queue. Two pieces, deliberately together because neither is testable

is this pane's content attributable to", and the **feedback button** in the
viewer nav bar, which exists if and only if that question has an answer.

`ViewerWorktreeCache`), plus `ViewerView.refreshWorktree` and the button half
of `ViewerFeedbackBar.swift`.

## Details

**Provenance is strategy D**, re-resolved on every navigation because a pane
moves between a file, a dev server and a remote site — each a different
worktree or none. This task lands legs 1 and 3, which are fully portable:

1. **File viewers** -> the viewed file's own directory.
3. **Fallback** (remote site, blank pane) -> the pane's origin directory. That
   value already exists on win32 and is already persisted:
   `ViewerPane.origin_directory` (`ViewerPane.zig:188`), written from
   `--working-directory` by `IpcHandlers.zig:252/668` and restored through
   `session_layout.viewer_origin_directory`. Nothing new has to be captured.

Leg 2 — `http://localhost:PORT` -> the listening pid's cwd — is **T638**, a
separate task because Windows has no `lsof` and the mechanism is a real choice.
Until it lands a localhost pane falls through to leg 3, which is the pane's
origin directory and is usually the right answer anyway.

Whatever directory results is resolved to a repo root with
`git -C <dir> rev-parse --show-toplevel` (**any** working tree counts — a
linked worktree or the main checkout), and the branch/commit are read the same
way for the report's `worktree` block later. No repo => no button. Resolutions
are cached per `(location, origin)` for 15s so navigation never stutters and a
dev server started later still makes the button appear.

**All git work runs off the UI thread** — this is a process spawn on every
navigation, and the win32 viewer's message loop is the same one the terminal
draws on.

**The button** is icon-only, in the same 24pt/28 DIP square as the other nav
chrome, labeled by tooltip with the worktree's basename and full path
(Mac shows the basename as text; win32 nav-bar space is tighter — decide and
state which, and keep the full path on the tooltip either way). Geometry goes
in `viewer_nav_layout.zig` next to the existing controls and is asserted at
1.0, 1.25, 1.5 and 2.0 per the win32 design system; the >= 4 DIP gap rule and
the one-icon-button-size rule are not negotiable here.

## What was decided

- **The button is ICON-ONLY on win32 too**, with the full worktree path on its
  tooltip (`Send feedback to <path>`). The task left the label open; the tighter
  nav strip settles it the same way Mac's own note does — a text label there
  reads as a heading rather than a button and breaks the row's rhythm — and the
  CLI surface and the design system both want one icon-button size, not a
  special wide one.
- **It TRAILS the address field**, alone on the far side of it, matching Mac's
  HStack order. The layout measures it in from the band's own trailing 4 DIP
  edge and never lets it cross the leading cluster, so a violently narrow pane
  squeezes the FIELD rather than overlapping two painted controls.
- **The tooltip is a `TTF_SUBCLASS` rect tool**, not the track-mode tip the tab
  strip drives by hand: the strip already tracks hover to paint tabs, while this
  is one rect whose delay, placement and dismissal are exactly what comctl32
  does for free.
- **Absent, never disabled.** With nowhere to file, the button would be a lie —
  so it takes no room at all (an empty rect that answers no hit), which is also
  how the existing contents toggle expresses its own absence.

## Validation criteria

- [x] Unit tests (none lane): worktree resolution classifies a file location,
      a `file://` URL, an http location and a blank pane to the right candidate
      directory; a directory in no repo resolves to null; the cache returns a
      hit inside the TTL and re-resolves after it.
      — `src/apprt/win32/viewer_worktree.zig`'s eight tests (legs 1/2/3, the
      loopback table, `parseRoot`, the name/tooltip, and two cache tests
      covering TTL expiry, the negative answer, in-place refresh and eviction),
      registered in `src/apprt.zig` and green in `zig build test
      -Dapp-runtime=none`. Leg 2's probe is injected, so it is asserted here
      before T638 supplies a real one.
- [x] Unit tests (none lane): nav-bar geometry with and without the feedback
      button asserted at 1.0/1.25/1.5/2.0 — no overlap, >= 4 DIP gaps, the
      button is the standard icon-button square.
      — `viewer_nav_layout.zig`: the design-system sweep now walks all four
      `Shown` combinations, plus "the feedback button trails the field, and is
      absent when not asked for" and "a narrow pane squeezes the field, never
      overlaps two painted buttons". The glyph itself is asserted by
      `icon_button.zig`'s all-glyph symmetry and clearance sweeps, which
      `.feedback` was added to.
- [x] On-box acceptance script: a viewer pane opened on a file inside this repo
      shows the feedback button; the same pane navigated to a remote URL with no
      origin directory does not; a pane opened with
      `--working-directory` outside any repo does not.
      — `test\win32\viewer-worktree.ps1`, **ALL PASS (25)**. Four provenance
      cases against one running app (file-in-repo → shown at `D:\git\ghoztty`;
      `%TEMP%` origin → hidden; repo origin with a website → shown; file
      outside any repo → hidden), the click reaching the pane, and the address
      field still readable beside the new button. The script REFUSES to run if
      `%TEMP%` is itself inside a working tree, so the negative cases can never
      be vacuous.
- [x] The git calls never run on the UI thread (assert by construction: the
      call site is the worker, and the pane is repainted from the completion).
      — `ViewerWorktreeProbe.work` is the only caller of `repositoryRoot`, and
      it is only ever reached through `std.Thread.spawn`; the GUI thread's only
      contact with the answer is `complete()`, called from
      `WM_APP_VIEWER_WORKTREE`. `deinit` joins the worker before freeing what
      it writes into.
