# T1169 - Every acceptance script pays a 12 KB/s pane because the test build parses unoptimized

## In plain terms

Everything we test against on this machine is the developer build, and a pane in
that build swallows terminal output about sixty-five times slower than the one
we ship. Every test that prints anything substantial into a pane waits for that,
which makes the suite slower than it needs to be and — worse — makes tests get
written around the slowness instead of around the feature.

## Summary

T1142 measured the app-side ingest rate at **12–15 KB/s on a Debug build** and
**~1 MB/s on ReleaseFast**, on both the agent-backed and the local pane paths.
The gap is Debug codegen of the terminal parse path, not a throttle: the local
path has no ring, no `feedSliced` and no priority handoff, and measures the same
rate.

Two costs, and the second is the reason this is filed rather than accepted:

1. **Wall clock.** 180 KB costs ~18 s of Debug catch-up. Any script that floods
   a pane pays proportionally, on a suite that is deliberately serial (T361).
2. **Harness distortion.** T1116 sized a flood in typed bytes, waited on the
   APP's screen for its marker, and the marker was evicted from the agent's ring
   long before the screen ever showed it — three defects (T1142, T1143 and the
   rebuilt section B) traceable to a pane that could not keep up with its own
   child. `docs/claude/testing.md` now warns about this, but a warning is a tax
   on every future author.

## Options to weigh

The obvious lever is Zig's per-MODULE optimize setting: build the terminal parse
path (`src/terminal/`) at `ReleaseFast` even inside a `-Doptimize=Debug` app, so
the suite gets a realistic pane without giving up debug info or safety checks
anywhere else. That is not free and the trade wants stating before it is taken:

- safety checks in the terminal module stop firing in the build every acceptance
  script runs, which is precisely where a grid/scrollback bounds bug would
  otherwise be caught first;
- a debugger stepping into the parser stops being useful in the default build;
- the app under test diverges, in one module, from the app a `-Doptimize=Debug`
  build claims to be — which is the sort of divergence this project treats as a
  defect elsewhere.

An alternative that keeps the build honest: leave the build alone and make the
harness LIBRARY carry the cost model — a shared "flood this pane and wait" helper
that sizes and times itself off the measured rate, so no individual script has to
know. Cheaper to reason about, does nothing for wall clock.

Whichever way it goes, the decision belongs in the task file and the log — it is
a mechanism call, not an experience one.

## Validation criteria

- [ ] the chosen approach is recorded with its trade-off, not just implemented
- [ ] if the build changes: `test\win32\pane-ingest-lag.ps1` shows a materially
      higher Debug ingest rate, and its bounds are re-calibrated with the new
      numbers in the header table
- [ ] if the build changes: the safety-check loss is answered — the terminal
      module's own coverage still runs checked somewhere in the floor
- [ ] the four floor lanes are green, and a full suite run is no slower
