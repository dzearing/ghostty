# T118 — Instance addressability on Windows

## Summary

Instance addressability on Windows — main's `ab3c1e25d` bakes `$GHOZTTY_IPC_SOCKET` into every pane's env so an IPC command run inside a pane drives THAT pane's app instead of whatever `ghoztty` on `$PATH` resolves to; on Windows NEITHER half exists (grep: no `GHOZTTY_IPC_SOCKET` anywhere in `src/apprt/win32/` or `src/os/ipc_client.zig`). `ipc_client.endpointPath` derives the pipe name from build mode + `USERNAME` alone, so a `+split` run from a Debug pane silently drives the installed RELEASE app — the exact confusion class that burned T116, and unlike Mac there is no escape hatch. Fix: bake the resolved endpoint into the pane env on all three win32 spawn paths (plain exec, agent-backed OPEN incl. the agent's RELAUNCH replay, remote), and have `endpointPath` prefer it; keep `GHOZTTY_PIPE_SUFFIX` working for the harnesses. Note the Windows analog is a PIPE NAME, not a socket path — decide whether to reuse the documented `GHOZTTY_IPC_SOCKET` name (CLAUDE.md's "Instance addressability" says socket) or add a sibling, and write the choice down

## Details

Main's `ab3c1e25d` makes an IPC command run inside a pane target **the app
instance that owns that pane**: every pane's env is baked with
`$GHOZTTY_IPC_SOCKET` (the absolute path of its own app's IPC socket) and the
CLI prefers it over the compile-time derivation. CLAUDE.md now documents this
under "Instance addressability".

On Windows **neither half exists.** Grep for `GHOZTTY_IPC_SOCKET` across
`src/apprt/win32/` and `src/os/ipc_client.zig`: zero hits. `endpointPath`
derives the pipe name from build mode + `USERNAME` alone, so a `+split` run
from inside a **Debug** pane silently drives the installed **release** app. That
is the same class of confusion that produced T116 (a harness aimed at a release
endpoint closed the user's real windows), and unlike Mac there is currently no
per-pane escape hatch — only the global `GHOZTTY_PIPE_SUFFIX` test hook.

**Fix:** bake the resolved endpoint into the pane env on all three win32 spawn
paths — plain exec, agent-backed OPEN (and the agent's RELAUNCH replay, which
must carry it like it carries the rest of the pane env), and remote panes (whose
IPC still belongs to the *local* app). Then have `endpointPath` prefer the baked
value, keeping `GHOZTTY_PIPE_SUFFIX` working for the harnesses.

**Decision to make and write down:** the Windows endpoint is a PIPE NAME, not a
socket path. Either reuse the documented `GHOZTTY_IPC_SOCKET` name (simplest;
CLAUDE.md's wording says "socket", so the doc needs a Windows clause) or add a
sibling var. Pick one explicitly — a silent divergence here is exactly what
CLAUDE.md's agent-contract section warns about, and the var is baked into
long-lived panes that outlive the app.

**Validation:** from a Debug-build pane with a release app also running,
`ghoztty +list` and `ghoztty +split` must hit the DEBUG instance; overriding the
var for one command must aim it elsewhere; a pane baked by an older
app/agent (no var) must still work via today's derivation.

## What landed (2026-08-03)

Half of the CLI side turned out to be there already and was simply not on the
path Windows takes: `apprt.ipc.socketPath` had a Windows branch that read the
var, but every win32 CLI verb dials through `ipc_client.connect` /
`connectWithReset` (`+list`, `+read`, `+version`, `+rearrange`,
`+new-remote-window` directly; every other verb via `App.performIpc` →
`sendAction`), and those called `endpointPath` — the derivation — so the var
was dead code on this platform. The fix therefore splits the two questions
that had been one function:

- **`ipc_client.endpointPath`** stays the pure DERIVATION (build flavor +
  `GHOZTTY_PIPE_SUFFIX` + `USERNAME`). The IPC **server** binds this.
- **`ipc_client.clientEndpointPath`** is new: baked value if non-empty, else
  the derivation. `connect`/`connectWithReset` use it, so every verb that
  dials the app inherits it at once, and `apprt.ipc.socketPath` delegates on Windows
  rather than keeping a second copy of the rule.

**The name decision: reuse `GHOZTTY_IPC_SOCKET`, one spelling on both
platforms**, even though the Windows value is a pipe name. `apprt.ipc.socket_env`
is now an alias of `ipc_client.endpoint_env` so the two cannot drift, and
CLAUDE.md carries the Windows clause. A sibling var was rejected for the reason
the task itself names: the var is baked into panes that outlive the app, so a
second name would have to be understood by every future reader of an old pane's
env for a value neither side ever parses.

**The bake** rides the same `config.env` seam as `GHOZTTY_PANE_ID` (T113), one
block below it in `Surface.init`, which is what gets all three spawn paths for
one edit: exec applies it last as `env_override`, the agent forwards it in the
OPEN (and replays it on RELAUNCH), and `Surface.zig`'s remote branch forwards
`config.env` too. The value is `App.ipcEndpoint()` — the endpoint the server
**actually bound**, kept on `IpcServer.path`, not a re-derivation. No server ⇒
no bake ⇒ the pane is on the CLI's own derivation, which is the pre-T118
behavior and the only honest answer when this app owns no endpoint to name.

Two things fell out of "who may read the var", and both are the same bug from
different ends: **an app launched from another instance's pane inherits that
instance's endpoint.**

- The **server** must never bind it (it would try to own the other app's pipe),
  so `IpcServer.init` keeps using `endpointPath`, and `App.init` drops the
  inherited value from its own environment before the bind — which also covers
  the `AlreadyRunning` **forward**, where an inherited value would send the
  startup `new-window` to a completely different instance than the one we
  collided with.
- The `+new-window` **auto-launch retry** drops it too: the instance we just
  spawned is our own exe and binds the derivation, so retrying against a baked
  endpoint would spend the whole 10 s backoff dialing a pipe nothing will
  answer on again. This is not hypothetical — session-persistence panes outlive
  their app by design, so "run `ghoztty +new-window` from a pane whose app is
  gone" is a normal thing to do.

### The rule that keeps the fix from breaking the test suite

An explicit **`GHOZTTY_PIPE_SUFFIX` outranks the baked endpoint.** This was not
in the task and it is the most consequential decision here. An acceptance script
aims by ENDPOINT (`Assert-GhozttyUnderTest` in `lib\CleanSlate.ps1` exists
because of it) and it inherits the environment of the pane it was started from
— which on this box is one of the user's own panes. The moment the installed
release bakes an endpoint, `test\win32\*.ps1` would inherit the USER'S endpoint,
the CLI would prefer it over the derivation, and the whole suite would drive the
user's terminal: 32 of the 96 scripts set no suffix at all, and the ones that do
would have been overridden by the bake. That is the T116 accident arriving
through the fix for T116.

So precedence is **suffix → baked → derivation**: the suffix is set by a
caller who is aiming on purpose, the baked value by the app. Belt and braces on
top of it, because a rule only protects the scripts that use the hook: both
`lib\CleanSlate.ps1` and `lib\TestDesktop.ps1` now drop
`$GHOZTTY_IPC_SOCKET` at dot-source time — a test never wants to inherit an
endpoint.

`internal_os.unsetenv` had to grow a second half for that: on Windows it only
called the CRT's `_putenv_s`, while `std.process.getEnvVarOwned` reads the PEB
environment block, which only `SetEnvironmentVariableW` touches. Clearing just
the CRT copy would have left every Zig-side reader still seeing the variable —
i.e. the App.init drop would have silently done nothing. Pinned by a round-trip
test rather than trusted.

### Validation (on box, 2026-08-03)

`test/win32/ipc-instance-addressability.ps1` — **ALL PASS (16 assertions)**. Two
instances of the same exe with different `GHOZTTY_PIPE_SUFFIX` values stand in
for "debug build vs installed release": that is the real bug's shape (two live
instances whose endpoints differ) without needing two builds on disk. Instance A
runs with session persistence ON (agent-backed panes, the OPEN env path) and
instance B with it OFF (plain exec panes) — both local bake paths, and it also
stops B restoring A's panes out from under it through the shared debug manifest.

1. A's pane is baked with A's own pipe.
2. From inside that pane, with the suffix removed from the child's env, `+list`
   still reaches A and sees A's window.
3. **Negative control**: clear the baked var in the SAME pane and the SAME
   command fails and sees nothing. Without this, check 2 is equally consistent
   with "the CLI happened to work".
4. An explicit bogus override fails instead of falling back — the documented
   escape hatch aims, it does not merely hint.
5. B, launched with A's pipe in its environment, still binds its OWN endpoint,
   and its panes are baked with B's pipe.
6. A third instance, launched with B's suffix (so its bind loses) and A's pipe
   in its env, forwards its window to **B** and leaves A untouched.

Unit lanes cover the pure halves: the baked-beats-derived rule, absent == empty,
and suffix-beats-baked (`ipc_client`), plus the `unsetenv` PEB round trip
(`os/env.zig`, Windows-only). Floor: `-Dapp-runtime=none` exit 0; P1-P3 ALL
PASS; the agent binaries run directly (T409's route) at **3787/76/0** and
**3715/68/0**. The full `-Dapp-runtime=win32` lane could not be completed on
this box today — it wedged three times in the `ViewerPane` WebView2 host-floor
test, including with no build runner at all, which is filed with that evidence
as **T416**; the lane filtered to this change's tests
(`-Dtest-filter=ipc -Dtest-filter=env -Dtest-filter=endpoint
-Dtest-filter=unsetenv`) is exit 0.

Three test-side traps cost a run each, and all three produced a confident wrong
reading rather than an error:

- `echo %ERRORLEVEL%> file` is `echo 0> file` — cmd reads the digit
  immediately before a redirection operator as a HANDLE, so it redirects stdin
  and leaves the file empty. Every probe reported "never ran" while running
  perfectly.
- A `[string]` parameter joins a multi-line `[string[]]` body with spaces, so
  `set X=` + `set Y=` + a command became ONE assignment that ran nothing: exit
  0 and an empty capture, which is indistinguishable from a product failure.
- `--session-persistence=off` is not a valid bool (**T414**): the flag was
  ignored, the second instance restored the first's manifest and attached its
  panes, and `+list` against B returned A's windows.

The shared-Zig half of the change moves macOS too (`+list`/`+read`/`+version`/
`+rearrange`/`+new-remote-window` now prefer the baked socket, converging with
what every other verb already did) — filed for that seat as **T415**.
