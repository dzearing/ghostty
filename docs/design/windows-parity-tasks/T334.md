# T334 - T146d-1: win32 mirrors its layout blobs to the agent (SET_LAYOUT) and can pull them back (GET_LAYOUTS)

First child of the **T321 split (2026-08-02)**. Mac commit `43bfb8e4a`.

## Summary

**Restore All rebuilds a machine's topology from blobs the AGENT holds - and
win32 pushes none.** Verified: `grep -rn "setLayout|requestLayouts" src/apprt/win32/`
returns only doc-comment mentions of `layout_meta.zig`; the only caller of
`Connection.setLayout` in the tree is `embedded.zig:2909`, the C API Mac uses
(`LocalAgentManager.pushLayout`, `LocalAgentManager.swift:410-445`).

So today a Windows machine is invisible to Restore All from anywhere -
including from itself - because the agent's `layouts.json` is always empty. The
button (T335) has nothing to rebuild until this lands. This is the plumbing
half, deliberately separated so the UI half is one context:

1. **Push.** Mirror each window's layout blob to the local agent on the same
   trigger that writes `session-layout.json` (`App.syncSessionLayout`,
   `App.zig:1051`): one `SET_LAYOUT{key, blob, session_ids}` per window, with
   `key` = the manifest window id, `blob` = that window's
   `session_layout.Window` JSON, `session_ids` = every leaf's session id.
   Best-effort and NON-spawning (an app with no agent pushes nothing), and off
   the UI thread - `setLayout` blocks through its ack.
2. **Delete.** A clean window close removes its blob (`delete = true`), the
   mirror of `LocalAgentManager.deleteLayout`. The agent also reaps a blob once
   none of its sessions exist (`session.zig` `reapLayouts`), so this is the
   prompt path, not the only one.
3. **Pull + decode.** `Connection.requestLayouts(timeout_ns) ![]u8`
   (`connection.zig:1693`) returns the RAW `LAYOUTS{layouts:[{key, blob}]}`
   reply. Decode it to a list of `session_layout.Window` - each `blob` is an
   opaque JSON STRING that parses as one window. A malformed blob is SKIPPED,
   never fatal: one bad window must not cost the user the other five.

## Why the blob is a `session_layout.Window` and not Mac's shape

`session_layout.zig`'s header already says the file is "the win32 app's private
local-restore state ... never decoded by the macOS app", so win32 pushing
win32-shaped blobs is the only self-consistent choice available here. It does
mean a Mac viewer cannot restore a Windows machine's topology and vice versa -
that cross-lineage gap is **T337**, filed separately because it is a schema
decision, not plumbing.

## What landed

- **`Connection.setLayoutNoWait`** (`src/remote/connection.zig`) - the
  fire-and-forget `SET_LAYOUT`, mirroring `closeSessionNoWait`. `enqueue` only
  appends to the writer thread's queue, so the push never touches the socket on
  the calling thread and the UI thread can mirror a topology between a split
  drag and its repaint. Ungated on purpose, and the comment says why: the
  `SET_LAYOUT`/`GET_LAYOUTS` opcodes shipped in the SAME commit as the agent
  handler that answers them (`43bfb8e4a`, 2026-07-16), which predates every
  `ghoztty-agent.exe` that has ever existed, so unlike `close_session` there is
  no skew window in which a peer could see the opcode as unknown.
- **`src/apprt/win32/layout_blobs.zig`** (new, pure, in the every-lane test
  block): `serializeWindow`, `sessionIds` (tree order, deduped, id-less leaves
  skipped), `blobHash`, and `decodeLayouts` for the `LAYOUTS` reply. A malformed
  INNER blob is skipped and counted; a malformed OUTER payload is an error -
  answering "this machine has no windows" over a transport fault would send the
  caller down the "nothing to restore" path.
- **`App.pushLayoutBlobs`** on the existing `syncSessionLayout` trigger, plus
  `pushed_layouts` / `pushed_layouts_conn` state.

## The push is a RECONCILE, and that is what removes a closed window's blob

There is no close hook. Every sync computes the live key set, re-pushes only the
windows whose bytes changed (`blobHash` against `pushed_layouts`), and DELETES
every tracked key that is no longer live. That one property also makes the
manifest's index-derived key (`win-0`, `win-1`) safe: closing window 0 renames
window 1 to `win-0`, and the same pass pushes `win-0`'s new bytes and deletes
the now-absent `win-1`. A connection identity change (agent restart, link
recovery) drops the map so the whole topology is re-pushed rather than assumed
present.

## Validation (VERIFIED on the box, 2026-08-02)

- `zig build test -Dapp-runtime=none` exit 0, `-Dapp-runtime=win32` exit 0,
  `zig build test-agent` exit 0, `zig build -Dapp-runtime=win32
  -Doptimize=Debug` exit 0. P1/P2/P3 ALL PASS.
- **`test\win32\layout-blobs.ps1` - ALL PASS, twice.** Hermetic (per-run
  `LOCALAPPDATA` + `GHOSTTY_LOCAL_AGENT_BIN`, kills only zig-out processes,
  T248) and headless-safe: no foreground grab and no synthetic input, so it
  needs no background desktop. Five sections: a startup window mirrors as one
  single-leaf record claiming its live session id; a `+split` UPSERTS the same
  record to 3 nodes / 2 ids rather than adding a second; `+new-window
  --target=` adds a record keyed by the ipc name; `+close` DELETES it and leaves
  the survivor; and a GUI-only kill leaves the blobs in the store, which is the
  whole point of the thing.

## Two things it turned up

1. **The `session_id` a record claims is not there on the first push.** An
   agent-backed pane publishes its id asynchronously, and `syncSessionLayout`
   already re-arms a bounded retry for exactly this. So the script waits for the
   record to SETTLE (`Wait-RecordIds`), not merely to exist - an assertion on
   first sight fails on a correct implementation.
2. **PS 5.1 unrolled a one-element array and only the SIMPLE case failed.** The
   single-leaf window in section A came back from `Nodes $rec` as a bare
   `PSCustomObject` whose `.Count` is `$null` and whose `[0]` is not an element,
   while the three-node split tree in section B survived intact - so the trap
   passed the interesting case and failed the trivial one, which reads like a
   product bug in the single-pane path. Every call site wraps in `@(...)` now
   and the helper's doc comment says why.
