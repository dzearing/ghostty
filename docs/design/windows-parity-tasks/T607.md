# T607 - A second ghoztty window on the test desktop makes the first refuse WS_EX_TOPMOST from any process

## In plain terms

There is one situation in the automated test environment where a Ghoztty window
simply cannot be pinned in front of other windows — and it is not the app's
doing: a completely separate program asking Windows to pin that same window is
refused too, while an unrelated app's window in the same place pins fine. Until
somebody explains it, one z-order test stays switched off.

## Summary

Found while fixing T277. On the **background test desktop**, once a SECOND
ghoztty window exists, the FIRST window will not take `WS_EX_TOPMOST`:

| condition (background test desktop, debug build) | result |
|---|---|
| one window, `toggle_window_float_on_top` from the keybind | pins, unpins, and re-pins (`float-on-top.ps1`, 12 assertions) |
| one window, banner up, pin + banner reposition | pin propagates to the overlay and survives |
| **second window created (IPC or keybind), then pin window A** | `SetWindowPos(HWND_TOPMOST)` x3 back to back, all `ok=1 lasterr=0`, ex-style stays `0x100` |
| **same state, external `SetWindowPos` from the harness on A** | also fails |
| same state, external `SetWindowPos` on `charmap.exe` | succeeds, every time |

So it is not the app's call site (three consecutive identical calls, no message
pump between them, no heal in the trace), not the harness, and not the desktop
in general — the ghoztty window specifically, and only once a second one exists.
A second window created and left un-repositioned reproduces it, so the harness's
`Set-TestWindowPos` is not the trigger either.

## What this task must do

1. Decide whether this reproduces on the INTERACTIVE desktop, which T277's step 1
   asked for and this box has never run (running acceptance windows on the user's
   own desktop was not something to do unattended). If it does not reproduce
   there, this is an environment-conditional harness gap (a T207 option-B case)
   and section E should say so permanently rather than pointing at a bug.
2. If it DOES reproduce interactively, find what about a second ghoztty window
   makes the first un-pinnable — start from what a second window changes in the
   process: another top-level in the same thread group, another message window,
   the window-placement/restore path, or a hidden owner relationship
   (`GetWindow(GW_OWNER)` was 0 in the single-window case; re-read it here).
3. Restore `overlay-zorder.ps1` section E to a real assertion, or replace its
   skip text with the permanent explanation.

## Validation criteria

- [ ] The interactive-desktop question is answered with a measurement, not an
      assumption.
- [ ] `overlay-zorder.ps1` section E either asserts or carries a skip that names
      the settled reason rather than a suspected product bug.
- [ ] If it is a product defect, a regression arm covers the two-window case in
      `test/win32/float-on-top.ps1`.
