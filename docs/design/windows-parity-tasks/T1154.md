# T1154 - A squeezed viewer pane on the Mac still lays its contents card out wider than the pane

## In plain terms

Squeeze a viewer pane narrow on the Mac and its table-of-contents card is still
built at a fixed minimum width, wider than the pane it is in. The pane hides the
overflow, so what you see is a card with its right-hand side sliced off - no
rounded corner, no scrollbar, and rows laid out for a width the card does not
have.

## Summary

The Windows half of this is T1130. `ViewerView.updateSidePanelLayout` computes:

```swift
let cardWidth = layout == .gutter
    ? sidePanelWidth
    : min(sidePanelWidth, max(120, bounds.width - GlassCard.outerMargin * 2))
```

The `max(120, ...)` is a floor the pane cannot veto, so a pane below
`120 + 2 * outerMargin` gets a card wider than itself and `clipsToBounds` hides
the difference. That is the same shape as the defect 463dcb0b4 fixed one level
up - chrome insisting on a minimum the pane cannot pay - applied to the card
instead of the nav bar.

Windows now caps the floor by what the pane actually has
(`viewer_toc_layout.compactCardWidth`):

```zig
const avail = pane_w_dip - margin_dip * 2;
const wanted = @min(pref_dip, @max(compact_floor_dip, avail));
return @max(@min(wanted, avail), 1.0);
```

A pane wide enough to pay the floor is unaffected, which is every pane above
`120 + 2 * margin`.

## Goals

- [ ] The compact card's width never exceeds the pane's own available width.
- [ ] A pane wide enough for the floor is unchanged.

## Validation criteria

- [ ] A test in `macos/Tests/Ghostty/` mounts a viewer at a pane width below the
      floor and asserts the card's frame fits the pane (the shape
      `ViewerNarrowPaneTests.swift` already uses for the nav bar).
- [ ] The Mac regression build is green.
