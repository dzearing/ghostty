# T1110 - The menu bar disables Close Tab and tab cycling while two tabs are open, and leaks a process

## In plain terms

With two tabs open, the menu still shows 'Close Tab' and the tab-switching commands as unavailable, greyed out, even though there are clearly tabs to close and cycle. The check that measures it also leaves a copy of the app running when it finishes.

## Summary

`test\win32\menu-bar.ps1` scored `3 FAILED / 75 passed` in the T1094 sweep, and left one process behind:

```
FAIL  A: the rect after the last tab is the + (tabs 1 -> 1)
FAIL  D: Close Tab is enabled with two tabs
FAIL  D: tab cycling is enabled with two tabs
```

Assertion A is the tell for the other two: the script tried to open a second tab and the tab count stayed at 1 (`tabs 1 -> 1`). If the second tab never opened, then Close Tab and tab cycling being disabled is CORRECT behaviour being measured against a wrong premise - the defect would be that the `+` button rect was not found, not the menu state.

So attribute A first. If clicking `+` genuinely does not add a tab, that is a bigger user-facing defect than the menu greying and this task's title should change.

Separately: `[leaked 1]` - see the leak task.

## Verdict

**The menu was right; the script was wrong.** Nothing in the product needed
fixing. See the progress log for the measurements: the `+` rect was correct and
never moves, the tab genuinely never opened, and the two menu rows were grayed
because there really was only one tab. The lost click came from the harness -
the two probes that click bare strip immediately before it are HTCAPTION
clicks, which can leave the window inside DefWindowProc's modal move loop, and
that loop eats what is queued behind it.

## Where

- `test/win32/menu-bar.ps1` sections A and D, and its final teardown
