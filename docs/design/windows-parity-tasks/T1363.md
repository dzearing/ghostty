## In plain terms

Every acceptance script closes by killing the app it started. Windows records a
forced kill with the same kind of exit code an actual crash produces, so the
post-run report at the bottom of a perfectly good run says `CRASHED` in capital
letters, complete with a stack-less "no WER record found" note. It is wrong every
single time, on every clean run, which is the worst possible place for a false
alarm: the block it appears in is the only thing that would tell you about a real
crash, and it has already taught everyone to scroll past it.

## Summary

`ConvertTo-GuiExitVerdict` (`test/win32/lib/GuiPostmortem.ps1:86`) classifies an
exit code structurally: high bit set == crash. That is the right default for an
unhandled exception, and it is also true of `0xFFFFFFFF`, which is what
`TerminateProcess` writes — and `Stop-RepoGhoztty`
(`test/win32/lib/CleanSlate.ps1:129`) tears every run down with
`Stop-Process -Force`. So the harness reports its own teardown as a crash.

Observed on the T552 run of `test\win32\sessions-running-cmd.ps1`, which scored
`ALL PASS (16 checks)` and still printed:

```
  GUI POSTMORTEM ghoztty.exe pid 18744
    verdict : CRASHED - 0xFFFFFFFF unnamed NTSTATUS
```

The fix is not to widen the "not a crash" range — `0xFFFFFFFF` really is
indistinguishable from an exception code by value alone. It is to let the killer
say so: the teardown knows it terminated the process, so it should mark that pid
as deliberately killed (a script-scoped set, or a flag on the postmortem call),
and the verdict should read `killed by the harness` for those and stay `CRASHED`
for everybody else. A process that vanished on its own with `0xFFFFFFFF` must
still report as a crash.
