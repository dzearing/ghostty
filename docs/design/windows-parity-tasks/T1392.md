# T1392 - Viewer address bar repaints a frame late during live resize; banner is smooth

## Summary

Dragging a split/window edge to **give the viewer more width** shows the address
bar visibly *painting* — you watch it redraw into the newly revealed space
instead of the bar simply being the new width every frame. The banner used to do
this and no longer does, which is the user's own A/B: "I see it painting rather
than a smooth transition whereas I don't see this with the banner anymore."

Reported interactively 2026-09-06.

## In plain terms

Drag the edge of a viewer pane to make it wider and you can WATCH the toolbar at
the top redraw itself into the space you just opened, a beat behind your mouse.
The status banner above panes used to do the same thing and was fixed months
ago; the toolbar never got that fix. When this lands the toolbar is simply the
new width on every frame, the way the banner already is — and the find card, the
feedback composer and the contents card come along, because they were all
positioned the same unfixed way.

## Goals

- [x] The address bar repositions on the banner's proven path, not a second one
- [x] That path is ONE shared helper, so the next overlay inherits it
- [x] The other viewer chrome positioned the same way is moved onto it too
- [x] The move-vs-resize decision is a tested pure function with a negative control
- [x] The rule is written into the win32 design system, not just the code

### Root cause (verified by reading the code)

The two overlays position themselves differently, and only the banner got the
fix:

- **Banner** — `BannerOverlay.updatePosition` (`src/apprt/win32/BannerOverlay.zig`
  ~line 467) explicitly detects a resize vs a move, adds **`SWP_NOCOPYBITS`** on
  a resize so Windows does not blit stale bits into the new rect, and then calls
  **`UpdateWindow`** to force the `WM_PAINT` **synchronously, in the same
  frame**. That is the T456 work.
- **Address bar** — `ViewerNavBar.place` (`src/apprt/win32/ViewerNavBar.zig`
  line 326) resizes with **`MoveWindow(hwnd, 0, 0, width, l.bar_h, 1)`**. The
  `TRUE` only *invalidates*; the repaint is deferred to the next idle. During a
  live drag the message loop is busy pumping `WM_MOUSEMOVE`/sizing messages, so
  the paint lands a frame (or more) after the move — and with the class's
  `CS_HREDRAW | CS_VREDRAW` (line 138) invalidating the *whole* bar, that late
  frame is a full redraw of everything, which is what makes it so visible.

There is a comment at line 135/915 that already reasons about `place()` using
`MoveWindow(.., TRUE)` — read it before changing, and update it to match
whatever lands.

### Fix direction

Bring `place()` onto the banner's proven path rather than inventing a second
one:

1. Replace the `MoveWindow` calls with `SetWindowPos`, computing `resized` the
   same way `updatePosition` does (compare against the current window rect).
2. On a resize, add `SWP_NOCOPYBITS` — the class already invalidates everything,
   so copying the old bits is pure cost and is what produces the smeared
   intermediate frame.
3. Follow with `UpdateWindow(hwnd)` on the resize path so the repaint is in the
   same frame as the move.

Consider factoring the banner's resize-aware reposition into a small shared
helper so the third overlay that needs it does not have to rediscover this.
Check the other floating chrome (`ViewerFindBar`, the TOC card, any other
`MoveWindow`-positioned overlay) for the same defect while in here — if they
share it, fix the shared mechanism.

Read `docs/claude/win32-ui.md` and `docs/design/win32-design-system.md` before
touching chrome.

### Parity note

Standing symmetry rule: this is a win32-only paint-path defect (AppKit
composites and has no `MoveWindow` equivalent), so no mac half is expected —
but confirm the macOS viewer's address bar is genuinely smooth on live resize
rather than assuming it.

      verified:** the decision is on the extents changing at all, in either

- [ ] Holds at 200% DPI. **NOT VERIFIED** — see below.

      synchronous paint are both gated on `d.resized`, with the move case
      asserted negatively in `chrome_reposition.zig` and a negative control that
      fails if the two branches ever agree.
- [x] A unit test for the nav bar's reposition DECISION. **How verified:** five

      `win32.zig` and `none` does not compile win32 chrome. The `none` lane is
      green regardless.

### What was NOT measured, and why that matters

The criterion asked for a screen recording of the drag, before and after. This
box runs acceptance scripts on a background desktop where `CopyFromScreen` and
`SendInput` are dead (T233), so a live divider drag cannot be driven or captured
here at all — the 200% DPI check has the same blocker. What IS established is
that the address bar now takes the identical code path as the banner, which is
the control the user's own report supplies ("I don't see this with the banner
anymore"). The remaining gap is confirmation by eye, and it is the user's to
give or a mac-seat/interactive-desktop run to take.
