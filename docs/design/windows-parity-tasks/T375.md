# T375 - T90d4: window.webkit.messageHandlers shim + one-blob document-created injection

## Summary

P1/P2 of docs/design/viewer-panes-windows.md. Define window.webkit.messageHandlers.<name>.postMessage in terms of window.chrome.webview.postMessage so the shared viewer JS (viewer.js:115-127, selection.js:132-146) is NOT forked, and add shim + selection.js as ONE AddScriptToExecuteOnDocumentCreated blob so injection order is not a question. Native side: add_WebMessageReceived + get_WebMessageAsJson sees the same JSON shape the Mac WKWebView proxy does. Verify on a real http:// page, not just the bundled template.

## What landed

`src/apprt/win32/viewer_bridge.zig` (new, pure, none lane) owns both halves:

- **P1, the shim.** Ten lines that define
  `window.webkit.messageHandlers.viewerTOC.postMessage` in terms of
  `window.chrome.webview.postMessage`. No shared JS is forked — the test
  "selection.js is embedded VERBATIM" asserts that byte-for-byte, by LENGTH as
  well as substring, so a patched copy cannot pass it.
- **P2, one blob.** `injected_js` = wrapper + shim + `@embedFile`'d
  `selection.js`, handed to `AddScriptToExecuteOnDocumentCreated`. The
  outermost statement is `if (window.top !== window) return;` — WebView2
  injects into every frame where Mac's `WKUserScript` is `forMainFrameOnly`.
- **The messages back up.** `parse` turns one `get_WebMessageAsJson` payload
  into a typed `headings` / `active` / `quote`, with Mac's own normalization
  ported field by field: `compactMap` on headings (one malformed entry does not
  blank the list), trimmed quote text, empty strings and negative offsets to
  null, and "ignore anything else" as the default — the blob runs on arbitrary
  websites, so a page can post whatever it likes through this bridge.

`webview2_iface.zig` gained three IIDs, `ICoreWebView2WebMessageReceivedEventArgs`
(6 slots), and the two `ICoreWebView2` slots the bridge calls. What used to be
one 38-slot opaque block is now three shorter ones, so
`AddScriptToExecuteOnDocumentCreated` sits at 27 and `add_WebMessageReceived` at
34 — with `add_NewWindowRequested` still asserted at 44, which is the check that
says the split moved nothing.

`ViewerPane.zig` installs the blob and subscribes **before the first
navigation** (a script registered after a page starts loading does not reach
that page), owns the parsed `headings` / `active_heading` in its own memory, and
carries both handlers on the `Pending` token like the new-window handler does.

## Evidence

Every lane run on the box, 2026-08-02:

- `zig build test -Dapp-runtime=none` — exit 0 (the 11 `viewer_bridge` tests).
- `zig build test -Dapp-runtime=win32` — exit 0.
- `zig build test-agent` — exit 0.
- `test\win32\ipc-p1/p2/p3.ps1` — `ALL PASS` each.
- `test\win32\viewer-panes.ps1` — `ALL PASS (71)`.

The oracle that matters is the live one, in the win32 lane's
"host floor: a real controller on a real window, on this box" — extended with a
**loopback HTTP server** and a page that posts through the WebKit path the
shared JS uses. It logged:

```
[viewer_pane] (warn): bridge: headings=2 active=toolbar-ran
```

That single line is three undocumented slot indices and two design pins at once:
slot 27 ran our blob in a page we did not author, the shim turned a WebKit
`postMessage` into a WebView2 one, slot 34 delivered it, args slot 4 returned
the JSON the parser expects — and `toolbar-ran` is the page reading back
`window.__ghozttySelection`, i.e. `selection.js` ran from the SAME blob.
`toolbar-missing` there would mean the shim was injected and the toolbar was
not: exactly the split P2's single-blob rule exists to make impossible.

It is `http://`, not `file://` or the bundled template, because that is the
task's own requirement and P2's whole claim is about pages we do not render. A
socket on 127.0.0.1 gives a real origin on a box with no route out.

There is no new IPC acceptance assertion, and that is deliberate rather than
skipped: nothing the bridge does is observable from `+list` or any other verb
until T160 draws the TOC card. The live win32-lane test IS the on-box
validation, and it is loud on both the success and the skip path.

## What it cost, and what to remember

`std.net.Stream.read`/`writeAll` **cannot be used on a Windows socket**: they go
through `ReadFile`/`WriteFile` with a null `OVERLAPPED` and zig creates its
sockets with `WSA_FLAG_OVERLAPPED`, so every call fails with
`ERROR_INVALID_PARAMETER (87)`. The loopback server hit that on its first run.
The house answer already existed — `src/remote/socket_rw.zig`'s `readStream` /
`writeAllStream`, with the identical diagnosis written down at T89b — so the
test uses those rather than growing a fourth private copy of `recv`.

The IIDs were **not** written from memory. Two of the three recalled values were
right and one (`AddScriptToExecuteOnDocumentCreatedCompletedHandler`) was
plausible and WRONG; all three were checked against a published transcription of
the SDK's own interface declarations before being committed, and the vtable
ORDER was re-derived the same way. The cross-check that made it cheap:
`add_NewWindowRequested` was already pinned at slot 44 by T374, so an ordering
that puts it anywhere else is wrong by construction.
