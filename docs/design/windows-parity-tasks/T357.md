# T357 - No coverage for the FORCED close-confirm paths (confirm-close-surface = always, read-only surface) now that idle can suppress the dialog

## In plain terms

Closing a terminal tab used to always ask "a process is still running — close
anyway?", even when nothing was. That nagging is gone now, and closing an idle
tab just closes it. But there are two cases where the question is still the
right one: when you have told Ghoztty to always ask, and when you have marked
the pane read-only. Nothing on the box checked that those two still ask — and
now that a missing dialog is the normal, expected outcome, a bug that stopped
asking would look exactly like the feature working.

## Goals

- [x] `confirm-close-surface = always` + an idle shell still opens the dialog — asserted on box
- [x] A read-only pane + an idle shell still opens the dialog — asserted on box
- [x] Each new section discriminates: it fails when the verdict is inverted
- [x] Read-only is confirmed reachable on win32 (it is: `toggle_readonly`, no default chord)

## Summary

Nothing on box asserts that `confirm-close-surface = always` and a read-only
surface still confirm — the two cases T41's idle rule is explicitly forbidden
to suppress.

## Details

`Surface.shellIsIdle` returns false for `readonly` and for
`confirm_close_surface == .always` before it ever looks at the process table,
because a confirmation the user configured unconditionally is not a question
about the shell. Both branches are asserted by nothing: `close-confirm-idle.ps1`
runs the default config, and `confirm-dialogs.ps1` (T80) is about the dialog's
rendering and key semantics, not the policy that opens it.

That matters more after T41 than before it: until now every close confirmed, so
a regression in these branches was invisible. Now the *absence* of a dialog is a
normal outcome, and a bug that suppressed `always` would look exactly like the
feature working.

*Validation:* a section in `close-confirm-idle.ps1` launching with
`--confirm-close-surface=always` — an IDLE shell must still open the dialog —
plus the read-only surface path (`+new-window --readonly`, or whatever sets
`Surface.readonly` on win32; check that it is reachable here at all before
scripting it, and file the gap if it is not).

## Validation criteria

- [x] A section launching with `--confirm-close-surface=always`: an IDLE shell still opens the confirm dialog — `test\win32\close-confirm-idle.ps1`, section D, both the Ctrl+W and the WM_CLOSE call site
- [x] A read-only surface with an IDLE shell still opens the confirm dialog — same script, section E, with the `GhozttyReadonlyBadge` window as the independent oracle that the pane really is read-only
- [x] Read-only confirmed REACHABLE on win32 before scripting it: `toggle_readonly` (context menu, command palette, or a bound chord) — no gap to file
- [x] Both new sections discriminate: `-NegativeControl` → `6 FAILURE(S) (50 passed)`, and D's two and E's inverted verdicts are among them
- [x] The whole script green: `ALL PASS (56 checks)`

## What landed

`test\win32\close-confirm-idle.ps1` grew two sections. Both run an **idle**
shell — descendant-free, asserted straight out of `Win32_Process` exactly as
A–C do — because idle is the only state in which the forced branch is the sole
reason a dialog can appear; a busy shell confirms anyway and would prove
nothing.

- **D/always** — launched with `--confirm-close-surface=always`. Both consumers
  of the branch are exercised, because they are separate call sites: Ctrl+W is
  `Surface.close` → `shellIsIdleNow`, and WM_CLOSE (the title-bar X / Alt+F4
  path, driven here with `Send-TestWindowClose`) is
  `Window.confirmCloseIfNeeded`, which asks `shellIsIdle` once per pane against
  one shared snapshot. The discriminator is section A rather than a toggle
  inside the section: nothing in a running app can turn `always` off, and A is
  the same harness, the same chord and the same idle oracle under the default
  config, where the idle close does *not* confirm.
- **E/readonly** — read-only turned out to be reachable on win32 only through a
  binding action (`toggle_readonly`: no default chord, no CLI verb, reachable
  by hand from the context menu and the command palette), so the window is
  launched with `--keybind=ctrl+shift+o=toggle_readonly`, the route
  `test\win32\readonly-badge.ps1` established. The `GhozttyReadonlyBadge`
  window is the independent oracle that the toggle actually landed, and doubles
  as the section's positive control — it proves chords reach this window, so a
  later "no dialog" cannot be "no keystroke". Unlike `always`, read-only *can*
  be turned back off, so the section carries its own discriminator: same pane,
  same chord, read-only off, and the dialog must be gone and the pane must
  close.

Deliberately NOT done: a `scripts\guard-due.ps1` coverage row for this harness.
The file it is about is `src\apprt\win32\Surface.zig`, which moves for a hundred
reasons that have nothing to do with the close confirmation — a row for it would
leave this 5-minute GUI harness permanently due, and a gate that is always red
is a gate nobody reads. That is the same call the table already records for
`src\Surface.zig` elsewhere.

Found and fixed along the way: **T1090** — section C could no longer find the
remote shell, because the pty holder (T905/T909) escapes the agent's process
tree. The script was red before this task touched it.
