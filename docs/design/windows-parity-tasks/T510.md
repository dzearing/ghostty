# T510 - relay_dial.dial's WebSocket upgrade read has no deadline: a silent endpoint wedges the caller's thread forever

## In plain terms

If the machine your terminal is dialling accepts the network connection but
then never answers, the part of the app doing the dialling can get stuck
waiting forever instead of giving up after a few seconds. Today the places
that dial mostly get lucky (the machine answers, or refuses outright, and
both resolve quickly); this makes the unlucky case — a machine that answers
nothing at all — time out cleanly like the others.

## Summary

Found twice from T328. The chooser roster's worker once grew a
retry-on-fresh-dial and it **wedged the worker thread permanently** — no
log line after the redial attempt, no reply ever posted — and the prime
suspect was `relay_dial.dial`: its WebSocket **upgrade read has no
deadline**, so an endpoint that completes TCP connect but never answers the
HTTP upgrade blocks the calling thread forever. (The other candidate was the
previous `Dialed.deinit`; whoever fixes this should settle which it was, or
bound both.)

The acceptance runs only survive because their failure modes are fast: a 502
(`WebSocketUpgradeFailed`) and a 401 (`WebSocketUnauthorized`) both come back
immediately. A machine that goes silent mid-upgrade — a firewalled port that
accepts, a hung relay — is the untested shape, and it turns any caller of
`dial` (SessionRoster worker, `+new-remote-window`, Restore All) into a
permanently stuck thread. The roster worker is serialized, so one stuck dial
means the chooser never loads another roster until app restart.

Fix shape: a receive timeout on the socket for the upgrade+HELLO phase (or a
deadline loop), long enough for a slow relay hop (seconds, not the connect
default), cleared or re-armed appropriately once the connection is
established and handed to `Connection` (whose heartbeat then owns liveness).
Both the upgrade read AND `Dialed.deinit` need to be provably bounded before
a retry-on-fresh-dial (the thing T328 reverted) is safe to reintroduce
anywhere.

## Goals

- [x] A dial against a machine that accepts the connection but never answers
      gives up within a deadline instead of hanging the app's worker forever
- [x] Established connections are untouched: the deadline only covers the
      handshake phase, and idle long-lived connections stay open
- [x] Every caller of the relay dial (chooser, new remote window, Restore All,
      the agent's own relay links) inherits the bound with no code changes

## Validation criteria

- [x] A unit or acceptance test dials an endpoint that accepts TCP and never
      answers the upgrade, and `dial` returns an error within its deadline
      instead of blocking (the test itself must be bounded) — VERIFIED by
      three new bounded unit tests (silent-accept listener, 500ms deadline,
      elapsed asserted < 10s): `relay_dial` "accepts TCP and never answers the
      upgrade" (drives `dialUpgradeTimeout`, the same core as `dial`),
      `ws_client` "never answers the upgrade", and `socket_rw`
      "setIoTimeout … fires as ConnectionTimedOut". All ran green in the
      `none`, `win32`, and `agent` lanes (floor-lane 2026-08-15, 4/4 PASS).
- [x] `chooser-sessions-remote.ps1` (incl. `-NegativeControl`) still ALL PASS
      — VERIFIED on-box 2026-08-15 after the Debug build: ALL PASS (20) and
      `-NegativeControl` ALL PASS (13). P1–P3 floor also ALL PASS (25/20/16).
- [x] `Dialed.deinit` on a half-dead connection is shown bounded (test or
      reasoned evidence recorded here) — REASONED EVIDENCE, now recorded on
      `Dialed.deinit`'s doc comment: the only waits in `deinit` are thread
      joins, and every joined thread's exit is forced — `conn.shutdown()`
      closes the lane streams → mux closes the transport WebSocket →
      `ws.close` does `shutdown(.both)` on the raw socket, which errors out
      any blocked recv/send through `socket_rw`'s mapped errors (the T81 suite
      proves both directions on-box: "flush after shutdown(.both) is an
      error, not a panic" and "recv after local shutdown is EOF or a mapped
      error"). No step in `deinit` performs a network wait of its own. The
      T328 wedge suspect is therefore settled as the UPGRADE READ, not
      `deinit`; a retry-on-fresh-dial is now safe to reintroduce (filed as
      T859).
