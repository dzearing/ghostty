# T1103 - A viewer page's window.open() popup is never adopted into a Ghoztty window

## In plain terms

A web page shown in a viewer pane is allowed to open a second window - a preview, a sign-in step, a details view. That second window is supposed to appear as another Ghoztty window. It does not appear at all, so any page that relies on opening a window simply stops working with no message.

## Summary

`test\win32\viewer-popup.ps1` scored `5 FAILURE(S) of 19` in the T1094 sweep:

```
FAIL  a second window appeared for the popup (it was NOT handed to the browser)
FAIL  the popup window has exactly one pane (got 0)
FAIL  the popup's pane is a viewer (got 'none')
FAIL  the popup pane is at about:blank (got '')
FAIL  what the opener wrote through its window.open() handle landed in the popup pane
      (title '', wanted 't163-adopted')
```

The first assertion carries the important detail: the popup was NOT handed off to the system browser either. So it is not a case of the window opening in the wrong place - nothing opens anywhere. The remaining four are consequences of the first.

T163 is the feature; this is its acceptance script reporting it gone.

## Where

- the viewer's WebView2 `NewWindowRequested` handling (T163 adoption path)
- `test/win32/viewer-popup.ps1`

## What it turned out to be

The feature was never broken. `viewer-popup.ps1` decided which window was the
popup by "the window that was not already open", and it took that snapshot of
"already open" AFTER waiting for the opener's pane to appear. The opener's page
calls `window.open()` the moment it loads, so on a loaded box the popup was
already registered by then and got captured into the set of windows to ignore —
after which the script could never find it again.

The same run proves the popup was real: section D located it by its window
title, at the portrait size the page had asked for, and closed it in section E.
Only the assertions that went through `+list --json` were blind to it, and
section E's "the popup is gone" passed for free because it had never been found.

The fix is in the harness: snapshot before the opener exists (the popup cannot
be created before its own opener), exclude the opener by the name this script
gives it, and make the close assertion name the window it expects to lose.

## Goals

- [x] Fix so the popup becomes a viewer pane in a new window, with the opener's handle still usable (that is what assertion 5 measures).
- [x] Confirm the fallback is still correct: what SHOULD go to the system browser still does.

- [x] the opener can still drive the popup through its returned handle — section C: the title the opener wrote through its handle (`t163-adopted`) is the title `+list --json` reports for the popup's pane

- [x] `test\win32\viewer-popup.ps1` is ALL PASS (20) — two consecutive runs
- [x] the browser fallback is untouched — the http(s) leg is decided in `viewer_popup.destination` and asserted by the win32 unit lane's live T163 test; no product code changed in this task
