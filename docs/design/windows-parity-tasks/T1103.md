# T1103 - A viewer page's window.open() popup is never adopted into a Ghoztty window

## In plain terms

A web page shown in a viewer pane is allowed to open a second window - a preview, a sign-in step, a details view. That second window is supposed to appear as another Ghoztty window. It does not appear at all, so any page that relies on opening a window simply stops working with no message.

## Summary

`test\win32\viewer-popup.ps1` scored `5 FAILURE(S) of 19` in the T1094 sweep:

```
FAIL  a second window appeared for the popup (it was NOT handed to the browser)
FAIL  the popup window has exactly one pane (got 0)
FAIL  the popup's pane is a viewer (got 'none')
FAIL  the popup pane is at about:blank (got '')
FAIL  what the opener wrote through its window.open() handle landed in the popup pane
      (title '', wanted 't163-adopted')
```

The first assertion carries the important detail: the popup was NOT handed off to the system browser either. So it is not a case of the window opening in the wrong place - nothing opens anywhere. The remaining four are consequences of the first.

T163 is the feature; this is its acceptance script reporting it gone.

## Where

- the viewer's WebView2 `NewWindowRequested` handling (T163 adoption path)
- `test/win32/viewer-popup.ps1`

## Goals

- [ ] Reproduce by hand with a page that calls `window.open()` from a viewer pane.
- [ ] Check whether the new-window event is being received at all, and whether the deferral/adoption handshake still completes.
- [ ] Fix so the popup becomes a viewer pane in a new window, with the opener's handle still usable (that is what assertion 5 measures).
- [ ] Confirm the fallback is still correct: what SHOULD go to the system browser still does.

## Validation criteria

- [ ] a `window.open()` from a viewer pane produces a new Ghoztty window holding a viewer pane, verified by hand
- [ ] the opener can still drive the popup through its returned handle
- [ ] `test\win32\viewer-popup.ps1` is ALL PASS
