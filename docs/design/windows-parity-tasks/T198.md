# T198 - Delivery to the 3 install locations is hand-run every time (script it)

## In plain terms

When a fix is ready, it has to reach three places: the copy of the terminal the
user actually launches, the portable copy on their Desktop, and the copy on the
network share that other machines download. Only the first was ever automated.
The other two were done by hand every time, from instructions written in prose,
by a session that had never done it before - and twice now that has quietly
shipped the wrong thing while every message said it worked. After this, the
other two are scripted, and the script reads back what it wrote instead of
trusting that a file copy returning success means the right bytes arrived.

## Goals

- [x] One script owns install locations 2 and 3, including the share's loose
      agent and the portable ZIP.
- [x] The ZIP is built from an explicit rule, not from whatever is in the
      folder, and its contents are compared with the ZIP it replaces.
- [x] Every delivered file is read back and every delivered binary is asked what
      build it is; a wrong answer fails the run.
- [x] An unreachable location is skipped, not a failure.
- [x] The pile of dated backups can be trimmed, but only when asked.
- [x] The delivery runs where someone is still watching, before the detached
      upgrade takes over.

## Summary

The standing bar says a user-facing fix must reach all three install locations,
and every delivery since T49 has done locations 2 and 3 by hand: rename each
file to a dated `.bak-*`, copy six binaries, mirror `share\`, refresh the share's
loose `ghoztty-agent.exe`, rebuild `Ghoztty-portable-x64.zip`, then launch
`upgrade-ghoztty-windows.ps1` for the installed release. Only the LAST step is
scripted. The other two locations are re-derived from prose in the log every
time, by a session that has never done it before.

T196 (2026-07-30) is the evidence that this costs correctness, not just time:
its hand-built zip exited 0 and was wrong twice over - rooted at
`Ghoztty-portable-x64\Ghoztty\...` instead of `Ghoztty\...` (extracting it the
documented way would have double-nested the app dir) and carrying both `.pdb`
files, doubling a network-share download from 20.3 MB to 41.9 MB. Both were
caught only because that session diffed the new artifact's entry list against
the one it replaced. The next session has no reason to think of that.

**Second measurement, found on the box while implementing this**: both portable
install locations were holding a **Debug** `ghoztty.exe` (`+edc526574`, PE
subsystem 3 = console) beside a **release** `ghoztty.com` (`+213a21f0d`) - an
hour after the morning refresh logged `extra install '...': ghoztty.exe,
ghoztty.com, ghoztty.pdb, ghostty-vt.dll, share\(robocopy 1)` for both of them.
The copy reported success and the bytes on disk were from another build
entirely. Nothing anywhere read the result back. That is the defect this task
names, caught in the act.

## Details

`scripts/deliver-windows-build.ps1` (plus the pure `scripts/delivery-manifest.ps1`)
covers locations 2 and 3 and is invoked by `launch-upgrade.ps1` in-process,
after the staging build and before the detached upgrade - so a failure over
there happens while someone is still watching, which is the same reason T200
gates the launch at all. On success the child upgrade is passed
`-NoExtraInstalls`, so the verified path and the old best-effort mirror never
both copy; on failure the mirror stays as the fallback it has always been.

What it does:

- source of truth is the staging prefix (`zig-out-release` by default), and a
  staging prefix whose `ghoztty.exe` is console-subsystem (i.e. a Debug build)
  is REFUSED before anything is written;
- backs up what it replaces with a `-Suffix`-dated `.bak-*`, for the five files
  you RUN and not the two `.pdb` files (see D64);
- copies the shipped set plus the `share\` tree (robocopy `/MIR`);
- refreshes the share's loose `ghoztty-agent.exe`;
- rebuilds `Ghoztty-portable-x64.zip` **from an explicit manifest** - root entry
  `Ghoztty\`, no `.pdb`, no `.bak*` - rather than "whatever is in the portable
  dir right now";
- and then PROVES the delivery instead of asserting it: every file is compared
  against its staging source (length + mtime, SHA-256 under `-DeepVerify`),
  every `ghoztty.exe`/`ghoztty.com` is asked `+version` and must answer the
  commit being shipped, their PE subsystems must be GUI/console, and the new
  zip's entry set is diffed against the artifact it replaces - an unannounced
  shape change fails the run and the zip is NOT published (`-AcceptZipShape` is
  how a deliberate change ships).

Reachability is not failure: an absent or unreachable location is SKIPPED and
named in the verdict, because a sleeping NAS must not hold up the install the
user is sitting in front of. A location that is present and WRONG is a failure -
the distinction the old best-effort mirror could not make.

Retention: the `.bak-*` files had reached 62 in the Desktop portable dir. The
script REPORTS the count, the generation count and the megabytes on every run
and prints the command to trim them; `-PruneBackups <keep>` actually deletes,
keeping whole generations rather than individual files. Deleting is user-gated,
so it is offered, never done.

## Validation criteria

- [x] A dry-run mode that prints what it would replace and writes nothing -
      `-DryRun`, plus a hand run against a sandbox.
- [x] A real run whose output is the delivered `+version` lines and the zip
      diff - hand run against both real install locations, see the Progress log.
- [x] Re-run twice in a row: the second run is a no-op apart from new `.bak-*`
      files and the `+version` assertions still pass - arms E1-E4 of
      `test\win32\deliver-windows-build.ps1`.
- [x] The zip it builds is rooted at `Ghoztty\`, carries no `.pdb` and no
      `.bak*` - arms C8-C11.
- [x] An entry-set change fails the run and leaves the published zip untouched -
      arms D7-D9; `-AcceptZipShape` ships it - D10-D11.
- [x] A Debug staging prefix is refused before anything is written - arms D1-D3.
- [x] A delivery whose binaries report another commit FAILS - arms D4-D6.
- [x] An unreachable location exits 0 but never claims OK - arms D12-D13.
- [x] `test\win32\deliver-windows-build.ps1` prints ALL PASS.
- [x] `test\win32\upgrade-staleness.ps1` still prints ALL PASS with the new
      delivery step wired into `launch-upgrade.ps1`.
- [x] Floor: `scripts\floor-lane.ps1 -Lane all` PASS, P1-P3 ALL PASS.
