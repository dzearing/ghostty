# T198 - Delivery to the 3 install locations is hand-run every time (script it)

## Summary

The standing bar says a user-facing fix must reach all three install locations,
and every delivery since T49 has done it by hand: rename each file to a dated
`.bak-*`, copy six binaries, mirror `share\`, refresh the share's loose
`ghoztty-agent.exe`, rebuild `Ghoztty-portable-x64.zip`, then launch
`upgrade-ghoztty-windows.ps1` for the installed release. Only the LAST step is
scripted. The other two locations are re-derived from prose in the log every
time, by a session that has never done it before.

T196 (2026-07-30) is the evidence that this costs correctness, not just time:
its hand-built zip exited 0 and was wrong twice over — rooted at
`Ghoztty-portable-x64\Ghoztty\…` instead of `Ghoztty\…` (extracting it the
documented way would have double-nested the app dir) and carrying both `.pdb`
files, doubling a network-share download from 20.3 MB to 41.9 MB. Both were
caught only because that session diffed the new artifact's entry list against
the one it replaced. The next session has no reason to think of that.

## Details

Add `scripts/deliver-windows-build.ps1` covering locations 2 and 3, invoked
after staging and before the detached upgrade script:

- source of truth is the staging prefix (`zig-out-release` by default),
- back up what it replaces with a `-Suffix`-dated `.bak-*` (today's convention),
- copy the six shipped files (`ghoztty.exe`, `ghoztty-agent.exe`, both `.pdb`,
  `ghostty-vt.dll`, `ghoztty-agent-ca.dll`) plus the `share\` tree,
- refresh the share's loose `ghoztty-agent.exe`,
- rebuild `Ghoztty-portable-x64.zip` **from an explicit manifest** — root entry
  `Ghoztty\`, no `.pdb`, no `.bak*` — rather than "whatever is in the portable
  dir right now",
- and then PROVE the delivery instead of asserting it: run each delivered
  `ghoztty.exe +version` and require the staged commit, and diff the new zip's
  entry list/size against the artifact it replaced, failing loudly on a shape
  change that was not asked for.

That last bullet is the point of the task. A copy loop is easy; the reason this
keeps being a source of bugs is that nothing checks the RESULT.

Worth folding in while there: the `.bak-*` files now number ~50 in the Desktop
portable dir (every delivery since 2026-07-15). A retention policy (keep the
last N) belongs in the same script — but deleting anything is a user-gated
action, so the script should offer it, not do it.

## Validation

- A dry-run mode that prints what it would replace, and a real run whose output
  is the three `+version` lines and the zip diff.
- Re-run it twice in a row: the second run is a no-op apart from new `.bak-*`
  files, and the `+version` assertions still pass.
