# T531 - `-NoResume` also skips relaunching the app

## In plain terms

Updating Ghoztty means briefly closing the running terminal and swapping in
the new program. One delivery option ("don't type anything afterwards") was
accidentally also skipping the step that reopens the terminal - so after one
update the terminal window simply vanished and stayed gone until the user
opened it by hand. Now the terminal always comes back after an update; that
option only controls whether text gets typed into it.

## Goals

- [x] A `-NoResume` delivery that killed a running app restarts the freshly
      installed exe and verifies it answers IPC before claiming success.
- [x] The resume-prompt typing is still skipped under `-NoResume`.
- [x] The upgrade log states the restart explicitly (`relaunched app pid N`).
- [x] The delivery scripts are wired into the guard-due staleness gate, so
      editing them without re-running their harnesses fails `validate`.

## What happened (2026-08-06 09:19, from `%TEMP%\ghoztty-upgrade.log`)

The interactive session delivered T524/T495 via `launch-upgrade.ps1
-ExtraArgs @('-NoResume')` - `-NoResume` chosen for exactly what its name
says: do not type a resume prompt into the (busy, mid-task) loop pane. The
run killed the 2 release ghoztty processes, swapped all three installs,
logged `POST-SWAP VERIFY OK` ... and then `resume decision: none` /
`UPGRADE OK (no-resume)` - **no app restart**. The user's terminal
disappeared and stayed gone until they reopened it by hand at 09:19:53
(which then hit T529's frozen re-attach).

## The defect

One flag conflates two independent things:

- "do not TYPE the resume prompt into the loop pane" (what the caller wanted)
- "do not RESTART the app" (what the user must never get - an upgrade's
  contract is that the terminal comes back; see T421/T524, where exactly
  this outcome from a different cause was called the worst possible shape)

`upgrade-ghoztty-windows.ps1` should ALWAYS restart the freshly installed
exe after the swap when it killed a running app - `-NoResume` should only
suppress the pane-resume typing. If a true no-restart mode is ever needed,
it must be its own explicitly named flag (e.g. `-NoRelaunch`), never the
default reading of `-NoResume`.

## Validation criteria

- [x] A delivery run with `-NoResume` against a running app ends with a live
      app answering `+list` (asserted in the script's own log flow AND in an
      acceptance arm - upgrade-staleness.ps1's neighbourhood).
      *Verified: `upgrade-ghoztty-windows.ps1` restart-only path calls
      `Wait-Instance 180` and exits 1 on `NO-RESUME RELAUNCH FAIL`; section G
      of `test\win32\upgrade-staleness.ps1` (G2-G6) runs a real hermetic
      delivery that kills a decoy release process and proves a live app came
      back from the installed exe - ALL PASS (108 assertions).*
- [x] The resume-prompt typing is still skipped with `-NoResume` (that half
      keeps working).
      *Verified: G7 asserts no `upgrade-resume` send-keys in the run's log;
      pure decision table A12b-A12d in `test\win32\upgrade-no-fork.ps1` -
      ALL PASS (131 assertions).*
- [x] The upgrade log states the restart explicitly (`relaunched app pid N`)
      so the next incident is diagnosable from one file.
      *Verified: G5 matches `relaunched app pid \d+` in the sandbox upgrade
      log.*

## Resolution (2026-08-16)

The one flag conflated two things; they are now separate. The resume decision
(`Resolve-LoopResumeAction`, scripts\loop-session.ps1) takes a `-KilledApps`
count and answers `restart-only` for `-NoResume` over a killed app: the
upgrade script then starts the freshly installed exe, waits for it to answer
`+list`, and logs `relaunched app pid N` - typing nothing. `-NoResume` with
nothing killed still completes as `no-resume` with no launch (all existing
sandboxed -NoResume acceptance runs keep their behavior). No `-NoRelaunch`
flag was added: no caller has ever wanted a no-restart mode, and the task
names it as an explicit future flag if one ever does.

Also landed with this task:

- guard-due rows for `upgrade-staleness` and `upgrade-no-fork` (the delivery
  pipeline had NO staleness gate - an edit to `upgrade-ghoztty-windows.ps1`
  obliged nobody to re-run its harnesses, which is the exact T783 gap), plus
  green-run stamp blocks in both harnesses.
- fixed `upgrade-no-fork.ps1` L23/L24's capture: `*> file` of the in-process
  launcher call loses Fail-Launch's refusal text on this host (T883's class),
  so L24 was red against a launcher that was refusing correctly. Now merges
  all streams record-by-record.
