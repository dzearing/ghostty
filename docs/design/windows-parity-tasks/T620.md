# T620 - chooser-resume.ps1 can no longer build an orphaned session, so it fails at setup

## In plain terms

There is a test that proves you can take over a terminal session that is still
running but has no window on screen — the whole point of the machine chooser's
session list. That test can no longer set itself up, so it stops before it
checks anything, and nobody would notice if the feature broke. Nothing is wrong
with the feature itself as far as we know; the test's way of *creating* a
window-less session stopped working.

## Summary

`test/win32/chooser-resume.ps1` builds its fixture the way the comment says a
user does: run panes under the agent, kill the APP (not the agent), delete the
local layout manifest so nothing auto-restores, and relaunch. The agent then
holds live children with no viewer.

That no longer produces an orphan. Launch-time restore has a SECOND source since
T194 — the agent's own layout-blob store (`local-agent-debug\layouts.json`, read
live over `GET_LAYOUTS`) — so the relaunched app rebuilds the fixture window from
the agent and re-attaches both sessions. Observed 2026-08-08 against
`89eb3857a` + the T333 change (which cannot touch this path):

```
info(win32): session-restore: recovered 1 crash-orphaned window(s) from the agent (0 in the local manifest)
info(win32): session-restore: attached 2 pane(s); 0 live agent session(s) unattached
```

and the script's own output:

```
  PASS the sessions outlived the app (2 alive)
  FAIL the roster has the orphans plus the new pane (2 rows)
  FAIL a live row with no viewer is rendered (index -1 of 2)
SETUP FAIL: no orphaned live session
```

`exit 1` at that point, so sections 2, 3 and 4 — the cursor paint, the resume
itself, the tombstone refusal and its positive control — have not run since. The
log records the script ALL PASS (21) on 2026-08-02, so the break is somewhere
after that.

Deleting `layouts.json` in the fixture does NOT fix it: the agent is deliberately
kept alive across the app kill, it owns that file, and `GET_LAYOUTS` answers from
memory (`lib/CleanSlate.ps1` says as much — "callers that keep the agent ALIVE
must not use this").

## The fix

Find a fixture that still yields a live session with no viewer. The candidate
that needs no product change: build the orphan with a SECOND app instance on its
own `GHOZTTY_PIPE_SUFFIX` (both instances share the one `-debug` agent), then
kill only that instance. The first app never relaunches, so launch-time restore
never runs, and its chooser sees the dead instance's session as alive and
unattached — which is also closer to what a user hits than a manifest delete.

Whatever shape it takes, keep the section-4 positive control: "nothing happened"
must stay distinguishable from "the keys never arrived".

While in there, check whether the same assumption is baked into any sibling
script (`chooser-sessions.ps1`, `chooser-restore-all.ps1` reset `layouts.json`
with the agent already dead, so they look safe — confirm rather than assume).

## Validation criteria

- [ ] `test\win32\chooser-resume.ps1` reaches section 4 and ends ALL PASS, twice
      in a row.
- [ ] The orphan the fixture builds is verified from OUTSIDE the app:
      `ghoztty +sessions --json` reports it `alive` and not `attached` before the
      chooser is opened.
- [ ] The section-4 positive control still fails when the keys are not delivered
      (prove it once by pointing the send at the wrong window).
- [ ] Any sibling script relying on "delete the manifest ⇒ no restore" is either
      confirmed safe or fixed in the same change.
