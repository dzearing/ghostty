# T369 - FLAKE: terminal.search.screen 'simple search with history' aborted with a recursive panic in the win32 lane

## In plain terms

One of the automated test suites crashed once, in a part of the code the change
being tested never touched, and passed when run again. This is another sighting
of the same rare, untraceable crash already tracked in T443 — the one the user
decided to stop hunting and instead watch with tripwires armed. The concern
this task raised separately (the crash "ate its own diagnostic", so nobody
could see what really failed) has since been fixed by other work: a crashed
test run now gets its exit code decoded and is automatically re-run under a
debugger that captures a full crash report. What was left to do here was the
measurement: run the suite enough times to say whether this crash can be
brought back on demand, and add the count to the standing watch.

## Summary

`zig build test -Dapp-runtime=win32` failed once during T60's floor run
(2026-08-02) in a test that has nothing to do with the change under test, and
passed on an immediate re-run with no edits in between.

## Details

Observed output:

```
aborting due to recursive panic
error: while executing test 'terminal.search.screen.test.simple search with history',
the following command exited with code 5 (expected exited with code 0)
Build Summary: 48/50 steps succeeded; 1 failed; 3659/3696 tests passed; 37 skipped
```

The same lane had passed earlier in the same session and passed again
immediately afterwards (exit 0), so this is intermittent rather than a
regression from the T60 change (which touches only
`src/apprt/win32/title_spinner.zig` and the two title paint sites in
`Window.zig` — nothing reachable from `terminal.search`).

"aborting due to recursive panic" is a panic raised while another panic was
already unwinding, so the reported test name may be the victim rather than the
cause: the real failure's message was swallowed. That is the first thing to
recover — a lane that can eat its own diagnostic is worse than the flake.

This is the same class as T136 (`zig build test-agent` flaked once on
`remote.agent.server.test "RESIZE ..."`), and the two should probably be
investigated together: both are intermittent aborts in a test lane rather than
in shipped code.

## Validation

the full log of any failing run — the recursive-panic text plus whatever
preceded it. A run that cannot reproduce it in 20 tries should say so and raise
the count rather than close the task on one clean pass.

## Result (2026-08-06) — no repro in 20+3 runs; folded into the T443 armed watch

This sighting is the T443 crash class, and the measurement is done:

- **Signature match.** Exit code 5 is the T444 truncation of 0xC0000005 (an
  access violation); the recursive panic is Zig's panic handler dying while
  reporting it, which is why the diagnostic was eaten. An intermittent AV in
  core terminal code during a floor-lane run, gone on an immediate re-run, is
  exactly the T443/T317 shape — `terminal.search.screen` walks the same
  PageList/page memory the T317 sighting crashed in (`page.verifyIntegrity`),
  and the recursive panic means the named test may be the victim anyway.
- **Measurement.** At HEAD: `floor-lane.ps1 -Lane all` → ALL LANES PASS
  (none 159s / win32 190s / agent 185s), P1–P3 ALL PASS, then
  `test-binary-soak.ps1 -Lane win32 -Runs 20 -Concurrency 5` →
  **20/20 PASS, 0 crashes**. No repro, consistent with every other
  post-2026-08-04 attempt on this class (now 110+ cumulative crash-free runs).
- **The diagnostic-eating concern is already fixed** by T444 (exit-code
  decode + Application Error log correlation) and T450 (auto re-run of a
  crashed test binary under cdb with all-thread stacks) — both verified wired
  into `floor-lane.ps1`. A future occurrence captures itself.
- **Disposition:** closed as duplicate → T443, per the D10/D12 armed-watch
  decision. The data point is appended to T443's ARMED-WATCH LOG. Do not
  reopen this file; a new occurrence belongs in T443.
