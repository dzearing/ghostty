# T320 - T146c: resume ONE browsed session on this machine

Third child of the **T146 split (2026-08-01)**. Mac commit `236a217ca`.

## Summary

T318/T319 make sessions *visible*. This task makes one of them **openable**:
picking a session row (or pressing Return on it) dismisses the chooser and
opens a local window attached to that session - the local agent's or a remote
machine's.

Mac models this as a new chooser RESULT, not a new code path inside the
chooser: `WindowTarget.resumeSession(machine:session:)`
(`MachineChooserView.swift:20`), built by `resumeTarget`
(`:127-133`) and handed to `onSelect` by `resume` (`:167-170`). The chooser
does not attach anything itself - it returns a target and closes. Windows
should keep that separation; `MachineChooser.zig` is already big enough
(108 KB) without owning attach.

## Two rules Mac states and both are load-bearing

- **Only ALIVE sessions are resumable.** `resume` guards on `session.alive`
  (`:167-168`) and a dead row renders disabled. A *relaunchable* tombstone is
  connectable-for-listing but not attachable - it needs `RELAUNCH`
  (`protocol.zig:800`), which is a different verb and is **not** in this task.
  Do not collapse `isConnectable` and `alive` into one predicate.
- **The keyboard sub-cursor's index space must match the rendered list.**
  `highlightedSessions` filters to `isConnectable` precisely so that Return
  resumes the row the highlight is on (`:114-122`). Any Windows list that
  renders a filtered view and navigates an unfiltered one has this bug by
  construction - and T312 just finished proving that this chooser's list is
  where focus/selection state gets miscounted.

## What shipped

**The keyboard model is Mac's, verbatim, because Windows' `handleKey` already
intercepts arrows and Return before any control sees them.** `MachineChooser`
grew no focus plumbing at all: Right steps the cursor INTO the roster
(`enterSessions`), Left steps out, Up/Down walk it and stepping above the first
row hands navigation back to the machine list, and Return resumes the cursored
row instead of firing the machine's primary action - Mac's `move` / `submit` /
`enterSessions` (`:1309-1322`, `:1373-1381`, `:815-823`) one for one.

Left/Right are consumed **only when the filter cannot use them**
(`horizontalIsNav`, unit-tested): in a field with text they are caret keys, and
taking those would make the filter uneditable. Mac has the same conflict and
ignores it; Windows' filter is a real EDIT and cannot.

**The index-space rule is structural here rather than duplicated.** Mac needs
`highlightedSessions` because its rendered list and its cursor are two computed
properties; on Windows the painter, the hit test, `killAt`, `rowAt` and the
cursor all take the SAME `[]const VisibleRow` that `visible()` returned, so
there is no second list to disagree with. The cursor is clamped where it is
USED (`cursorIndex`), not kept in sync, so a roster that shrank under a parked
cursor can never resume the row that slid into the index.

**The alive guard lives in one place**: `chooser_sessions.resumeTarget`, which
returns `.none` for a tombstone, for a row with no id, and for no machine
selected. Callers cannot forget it because they have nothing to forget - they
switch on what they were handed.

**One deliberate divergence, filed as T330.** A row already open in one of our
own panes is FOCUSED, not attached a second time: the agent rebinds a session to
its newest ATTACH (`remote/agent/server.zig:1026-1067`), so Mac's unconditional
resume takes the pane away from the window that has it. "Show me that session"
is satisfied either way, and only one of the two can strand a pane.

**The attach itself is `App`'s**, as Mac's separation demands:
`resumeLocalSession` (the same override shape launch-time restore builds - a
resume IS a restore of one leaf, on demand, including the manifest's recorded
`pane_id` so the pane keeps the `$GHOZTTY_PANE_ID` its running shell was baked
with, T113) and `resumeRelaySession` (one dial, then the shared open tail).
`RemoteOpenOptions.session_id` also SUPPRESSES the per-host cwd/shell defaults:
an ATTACH's shell and directory were fixed when the session was first opened,
and sending them would describe a spawn that is not happening.

## Evidence (VERIFIED on the box, 2026-08-02)

Unit (none-runtime lane): `resumable is alive only`, `resumeTarget names the
machine the roster is pointed at`, `the cursor's index space is the RENDERED
list, with a dead row planted mid-roster` (the one the task asked for - the
second rendered row is the THIRD raw session, and both the walk and the resume
agree on it), the enter/leave/clamp cases, and that the cursor card wears the
chooser's own `selectionFill`/`selectionBorder` rather than a second selection
language.

On box: **`test/win32/chooser-resume.ps1` - ALL PASS (21 assertions)**.

The fixture is the interesting half. A session that is merely *listed* is not
enough: every session the app has open takes the focus short-circuit, so the
test needs a live session with **no viewer**, built the way a user gets one -
run panes under the agent, kill the APP only, drop the layout manifest so
nothing auto-restores, relaunch. What it then asserts:

- Right paints the cursor: the first card's blue channel lifts by 27 over the
  same point one keystroke earlier (the plain card is its own control);
- Return resumes THAT row - the app logs the id, and it equals the id of the
  row the cursor walked to;
- the agent, dialled directly by `+sessions --json` (nothing about that reading
  goes through the app), reports the session `attached` when it was not a
  moment before;
- a relaunchable tombstone refuses: no attach, and the chooser stays open;
- **positive control**, mandatory after that negative: the same chooser and the
  same keys act on a live row (its pane is focused, T330).

**The first run of the script failed 6 assertions and every one was the test's
fault, in the same way**: it assumed the agent lists sessions in creation order
and picked row 0. The agent's order is its store's - the app's own session came
first - so the "orphan" it resumed was a pane it already had open, and the focus
short-circuit fired instead. Rows are now chosen by what they ARE (alive, no
viewer) and the cursor is walked to that index, which is also a stronger test of
the index space than a fixed 0 would have been.

Floor: `zig build test -Dapp-runtime=none`, `-Dapp-runtime=win32`, the full
`-Doptimize=Debug` GUI link, `zig build test-agent`, P1-P3 and
`chooser-sessions.ps1` (T318's own script, since this touched the roster's
paint and hit testing) all green.
