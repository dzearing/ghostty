# T386 - selection.js's toolbar font stack has no Windows entry, so the viewer selection popover renders in Arial

## Summary

`src/viewer/selection.js:40` sets the Quote/Copy toolbar's font to
`-apple-system, BlinkMacSystemFont, sans-serif`. Neither of the first two
resolves on Windows, so the toolbar falls through to the generic `sans-serif`
family — Arial — while every other piece of win32 chrome is Segoe UI Variable
(`type_ramp.zig`, `title_font.zig`). T375 made this visible for the first time
by injecting the toolbar into real pages on Windows.

Its colors are NOT part of this: the file already has a
`@media (prefers-color-scheme: dark)` block (`selection.js:61`), and T373's
`put_PreferredColorScheme` drives it, so the popover already follows the window
appearance on Windows.

## Details

The fix belongs in the SHARED file, not a Windows copy — P1's rule is that
`selection.js` stays a single copy, and T375's
"selection.js is embedded VERBATIM" test enforces it byte-for-byte. Putting
`system-ui` at the head of the stack resolves to San Francisco on macOS and
Segoe UI Variable on Windows, so one edit is right on both platforms and
nothing forks:

```css
font-family: system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif;
```

Check the same line in `viewer.css` while there — T90e renders the document
body through it, and CLAUDE.md pins body text to "the system font (SF Pro via
`-apple-system`)", which has the identical hole on Windows. If it does, this
task covers both or files the second.

*Validation:* a win32 GUI probe is overkill for a font family; read it back
from the page instead. Once T90e/T160 land, `getComputedStyle` on the toolbar
button through an `ExecuteScript` round trip is the honest oracle. Until then,
a unit test on the shared CSS text (the stack begins with `system-ui`) plus a
screenshot in the task file.
