# T395 - Viewer panes: a terminal split created FROM a viewer inherits the viewed file's directory as cwd

## Summary

Split out of T90g (2026-08-02). T90a §15 pins it: "Terminal splits created
FROM a viewer inherit the viewed file's directory as cwd (Mac
`splitConfigFromViewer` parity)." On win32 `Window.newSplitAt` inherits cwd
from the parent SURFACE, and a viewer pane has none — so `+split` (or
ctrl+d) off a viewer lands the new shell wherever the app was started.

## Details

Mac's `splitConfigFromViewer` derives the directory from the viewed
location: a file viewer contributes the file's own directory; a web viewer
contributes nothing (fall back to the existing default). Port that.

Related but NOT this task: `viewer_origin_directory` (P12's manifest field,
the provenance fallback that T164 needs). This task only needs "what
directory does a terminal split off this viewer start in".

*Validation:* `test/win32/viewer-panes.ps1` grown — `+split --view=<a file
in a known dir>`, then `+split` off that viewer with no
`--working-directory`, and the new pane's shell reports that directory. A
web viewer split falls back to today's behavior.

## Done 2026-08-02

**What it was.** `Window.newSplitAt` had two ways to give a new pane a cwd and
neither could see a viewer: `buildRemoteInherit` asks the split-parent
SURFACE (`at.surface()` is null for a viewer), and the plain local path has no
cwd machinery at all. So a `+split` off a file viewer landed wherever the
fallback pointed.

**The fallback is not "nothing", which is what made the test interesting.**
The core already seeds a new surface from the last focused TERMINAL's pwd
(`apprt/surface.zig:194-201`), and focusing a viewer does not change that — a
viewer is not a core surface. A first cut of the negative control asserted
"a web viewer split does not land in the file's directory" and FAILED, because
the last focused terminal happened to BE the pane the file case had just
created there. That is pre-existing core behavior, not a leak. The control was
rewritten to make the fallback a known third directory, so the two cases are
told apart by which of two real answers wins:

- file viewer → the file's directory, and explicitly NOT the fallback;
- web viewer → the fallback, unchanged.

**The fix.**

- `viewer_content.splitWorkingDirectory(?file_path)` — pure, `dirname` of the
  viewed file, null for a website / no usable path / a bare name with no
  directory part. Unit tested in the none lane.
- `Window.newSplitAt` derives it from `at.viewer()` and fills it in wherever
  the cwd would otherwise be silent, on all three paths: an existing IPC baton
  (a `+split` always carries one for the pane/window-name env, so this is the
  common case), the `RemoteInherit` baton (remote window or local persistence
  agent), and the bare local path. An explicit `--working-directory` always
  wins — a null one is the same "nothing said" the no-baton path already
  treats as inheritable. The baton is `*const`, so the value goes into a copy
  that outlives the synchronous surface init rather than into the IPC
  handler's own struct.

**Evidence.**

- `zig build test -Dapp-runtime=none` exit 0, with a positive control: the new
  test was made to fail on purpose and the run reported it by name
  (`apprt.win32.viewer_content.test.splitWorkingDirectory: ...`), so it is
  discovered rather than silently absent.
- `zig build test -Dapp-runtime=win32` exit 0; `zig build test-agent` exit 0.
- `test\win32\viewer-panes.ps1` **ALL PASS (111)**, up from 96 — 15 new
