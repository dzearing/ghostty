# T290 - Activity Monitor keeps enumerating every process while minimized or hidden

## In plain terms

The Activity Monitor panel takes a full inventory of every process on the
machine every second and a half — about 300 of them — and it kept doing that
while it was minimized, hidden, or parked on another virtual desktop, where
nobody could see a single one of those readings. Leave the panel open for an
afternoon and it quietly burns CPU all afternoon. After this, a panel you
cannot see does no work at all, and the moment you bring it back it refreshes
straight away rather than showing you a stale table until the next tick.

## Goals

- [x] A minimized or hidden panel stops enumerating entirely
- [x] A panel on another virtual desktop does too (it gets no window message,
      so the poll tick has to notice it)
- [x] Restoring it shows fresh numbers immediately, not one interval later
- [x] The trend charts do not lie about the gap
- [x] The "it stopped" assertion has a control proving it was ever moving

## Summary

T285's panel polls on a `SetTimer` every `trend_gauge.sample_interval_ms`
(1500 ms) for as long as it is open, and each poll is a **full process
enumeration**: `CreateToolhelp32Snapshot` plus an `OpenProcess` and two
`QueryFullProcessImageName`/times calls per pid. Measured on this box that is
**~300 processes every 1.5 s, forever** — including while the panel is
minimized, fully occluded, or on another virtual desktop, where not one of those
samples can be seen.

The work is off the GUI thread (a worker per sample, joined on close), so it
never stalls the UI. What it does spend is CPU and process-handle churn, on a
panel a user is likely to leave open for hours. That collides directly with the
standing bar for this fork: *"Reliable and fast under long-context use ... no
slowdowns, tuned for hours-long Claude Code sessions."*

Mac has the same shape (a `Timer` that runs while the window is open), so this
is a Windows-side improvement rather than a parity gap — worth doing anyway, and
worth recording as a deliberate divergence if it lands.

## Scope

- Suspend the sample timer when the panel is minimized (`WM_SIZE` /
  `SIZE_MINIMIZED`) or hidden, and resume — with an immediate catch-up sample —
  when it is restored, so the table is never stale on the frame the user sees it.
- Decide what happens to the trend ring across a suspension: a gap in a chart
  whose X axis is "sample index" would silently misrepresent time. Either clear
  the ring on resume (the honest, cheap answer, and what a source switch already
  does on Mac) or carry a gap marker. Record the decision.
- Consider the same treatment for full occlusion; `WM_SIZE` alone does not
  cover a window buried behind another. Do NOT guess — measure whether
  `DwmGetWindowAttribute(DWMWA_CLOAKED)` / `IsIconic` is enough before adding
  anything more exotic.

- `test\win32\activity-monitor.ps1` grows a section: minimize the panel

- That assertion needs its own negative control: the counter must be proven to
  grow while the panel is open, or "it stopped" is true of a dead oracle.

## What was built

`src/apprt/win32/sample_gate.zig` — a pure two-state machine (running /
suspended) that answers one question per tick: `.sample`, `.skip`, or
`.resume_fresh`. It has no OS imports, so its 11 unit tests run in the `none`
lane with no window to minimize. `ActivityMonitor.zig` supplies the OS answers
and carries out the action.

**Both a message path and a polled path, deliberately.** `WM_SIZE` /
`SIZE_MINIMIZED` and `WM_SHOWWINDOW` suspend and resume on the message, so a
minimize does not spend up to a full interval still enumerating. But a
**virtual-desktop switch produces no window message at all**, so every tick
re-asks the OS (`IsWindowVisible` / `IsIconic` / `DWMWA_CLOAKED`) — three cheap
queries next to the enumeration they can save. `WM_PAINT` calls the same resume
path, which is what makes a return from another desktop refresh on the frame it
reappears; it is a no-op unless the gate is suspended, so it costs a branch per
paint.

**Occlusion was measured, not guessed** (the task's own instruction).
`DWMWA_CLOAKED` covers the virtual-desktop case and does NOT false-positive on
the background test desktop — the whole acceptance script samples normally
there, which is the measurement. Full occlusion (a window buried behind
another) is deliberately NOT attempted: Windows has no cheap reliable answer,
and guessing would freeze a panel someone is watching, which is a worse failure
than sampling one they are not. Recorded in the module's doc comment.

**The trend rings are cleared on resume**, not stitched — they are indexed by
sample, not by time, so carrying them across a ten-minute suspension would draw
those ten minutes as one pixel. Same thing `switchSource` already does. Filed
as D26 in case the gap marker is wanted instead.
