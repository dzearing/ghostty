# T155 — Split dividers render as double/triple lines instead of one solid line

## Summary

**Split dividers render as double/triple lines instead of one solid line.** User-reported 2026-07-29 with a screenshot showing two parallel verticals and a 3-line stack near the top. ROOT-CAUSED BY INSPECTION (no build needed), two compounding defects. **(a) Stale lines are never erased — this is the double/triple.** `Window.zig:3839` handles the parent's `WM_ERASEBKGND => return 1`, i.e. it claims the background is erased and paints nothing (the surface CHILD class *does* fill, `App.zig:3443`, so panes are fine — only the inter-pane gap, which the parent owns, is never cleared). Divider lines are then stroked OUTSIDE the paint cycle via a raw `GetDC` right after layout (`layoutSplits:1707-1714`, again in `onConfigChange:451`), with the code's own comment conceding WM_PAINT "misses the content area gaps". So nothing ever clears the gap: every ratio change (divider drag, window resize, pane add/remove, DPI change, tab switch) strokes a NEW line at the new `split_x` and leaves the OLD one on screen. They accumulate — two lines after one drag, three after two. **(b) Even a correctly-painted divider reads as 3 edges.** `paintDividerNode:1830-1844` leaves a 5-DIP gap (left pane ends `split_x - gap/2`, right starts `split_x + (gap+1)/2`) and strokes a hairline at `split_x`, so the render is *pane bg | 2px parent bg | 1px line | 2px parent bg | pane bg* — and with T67 per-pane tints the parent bg is a different color than either pane, making all three boundaries visible. Mac draws a solid filled divider with no gap. **(c) Width is not 2px and not constant.** `line_w = @max(@round(1.0 * scale), 1)` → 1px at 100%/125%, 2px at 150%/200%. Fix: paint the divider as part of the parent's WM_PAINT (fill the whole gap rect with the divider color via `FillRect`, one solid band, no `GetDC` side-channel) and give the parent a real `WM_ERASEBKGND` so no region can hold stale pixels; match the Mac's divider thickness and treat `split-divider-color` (T73) as the fill, not a stroke. Validation: extend the T73/T94 on-box script with pixel oracles that drag a divider N times and assert exactly ONE band of divider-colored pixels on the scanline, at 100/125/150/200% DPI, for both split axes

## Resolution (2026-07-29)

Defects (b) and (c) were exactly as filed. **Defect (a)'s mechanism was
filed WRONG, and the first version of the oracle proved it** — worth
recording, because the wrong mechanism produced a test that passed on a
broken build.

The row claimed "every ratio change strokes a NEW line and leaves the OLD
one on screen". Dragging a divider does NOT do that: a big ratio change
moves the line clear of the old 5 DIP gap, the growing pane's child window
covers the stale pixels, and the count stays at 1. Measured on the pre-fix
build — the drag-based oracle reported `exactly ONE divider band after 3
drags (got 1)` **before the fix**, i.e. it was insensitive and would have
shipped a green test over a live bug.

The real trigger is **repeated SMALL window resizes**. Each drifts the split
position by ~2px — less than the gap was wide — so the previous hairline
survived *inside* the never-erased gap. Found by sweeping shrink steps
against the pre-fix build: 3x 4px shrink gave **2 runs** (offsets 973,975 /
984,986 — the user's "two parallel verticals"), while 6/8/10/14px steps gave
1, because a bigger drift pushes the old line out of the gap where a child
covers it. That is why the user saw it while resizing a window and nobody saw
it while dragging dividers.

**Fix**, all three defects at once, via a new pure module
`src/apprt/win32/split_geometry.zig` (the hero_math/dim_math pattern) that
replaces the arithmetic triplicated across `layoutNode`, `paintDividerNode`
and `hitTestDividerNode`:

- Gap == band == `max(round(1.0 * scale), 1)` px — Mac's
  `splitterVisibleSize = 1`pt. Panes and the band now **TILE** the split
  rect, so there is no parent-owned pixel between them for a stale line to
  live in, and a moved band's old pixels are covered by a child window.
- The band is **FillRect'd** with the divider color (Mac fills a Rectangle),
  not a hairline stroked down the middle of a wider gap — that was the
  3-edge render, and with T67 per-pane tints all three edges were visible.
- Dividers are painted in the parent's `WM_PAINT` as well as after layout.

**`WM_ERASEBKGND` was tried and REVERTED.** The row asked for "a real
WM_ERASEBKGND so no region can hold stale pixels"; painting the bands from
the erase handler regressed `pane-banner.ps1` (the banner overlay is a
layered window above that area and erase-time painting into the parent DC
disturbs its composite). Proven by comparison, not assumed: pane-banner
failed on the build WITH the hook and gave `ALL PASS (45)` both on the
pre-fix build and on the final build with the hook removed. It is also
unnecessary once the panes and band tile, so the handler keeps returning 1
with a comment recording why.

**Evidence.** `split-divider.ps1` grown from 15 to 25 assertions (both axes ×
{3 drags, 3 small resizes} × {one band, solid Npx fill}), plus a screen-pixel
control: every count comes from `GetPixel` on the composited screen, so a
pixel deep inside a pane must read near-black or the axis SKIPs — without it
an occluded window read as "0 divider pixels" and looked like a product
failure (it did, twice, before the control was added). Red/green on the same
box: pre-fix `2 FAILED / 23 passed`, both failures being `still ONE band
after 3 small window resizes (got 2)` on down AND right; post-fix `ALL PASS
(25)` ×3. The DPI sweep the row asked for is covered deterministically by
`split_geometry.zig`'s unit tests (scales 1.0/1.25/1.5/2.0/3.0 assert the
tiling property and band width) rather than by re-scaling the monitor.

Floor: `zig build test -Dapp-runtime=none` + `-Dapp-runtime=win32` +
`test-agent` exit 0, P1–P3 ALL PASS, and the split/banner regressions
`split-dim` (23), `split-zoom-nav` (16), `pane-banner` (45) all ALL PASS.

Two of those regressions were red for a reason that was NOT this change:
`split-dim.ps1` and `split-zoom-nav.ps1` launch a GUI per section without
`--session-persistence=false`, so each section restored the previous
section's panes. Fixed in both (the T131 trap); the general sweep is filed as
**T158**.
