# T484 - Re-attach scrollback loses older cycles' history: session-persistence.ps1 B2.7/B3.7 are RED and were green on 2026-07-21

## In plain terms

Ghoztty on Windows keeps your terminals running when the app dies and hands
them back when it restarts, scrollback and all. But if it dies more than once,
only the most recent session's output comes back — everything you had scrolled
through before the previous crash is gone. Anyone who has to restart the app
twice in a day loses the history they were relying on.

## Goals

- [x] Find out where the older output goes: pane scrollback eviction, a
      truncated ring replay, or a replay that starts from the wrong offset
      (suspect 2 was right — see Close-out: the T109 snapshot attach let the
      agent's screen-only repaint erase the painted history; T666 root-caused
      and fixed it)
- [x] Restore comes back with the FULL cumulative history across repeated
      crashes, not just the last cycle's (fixed by T666, commit `3bbf0eefb`)
- [x] `session-persistence.ps1` B2.7 and B3.7 are green again and stay that way
      (verified 2026-08-15: three consecutive full runs at HEAD, ALL PASS)

## Summary

Found 2026-08-04 while validating T194. `test\win32\session-persistence.ps1`
section B crash-kills the app and relaunches three times, planting a distinct
marker in pane `spB` before each kill and asserting after every restore that
EVERY marker planted so far is still readable (`Read-Pane 'spB' 4000`). Only
the first cycle passes now:

```
PASS B1.7 replayed scrollback holds all 1 cycle marker(s)
FAIL B2.7 replayed scrollback holds all 2 cycle marker(s)
FAIL B3.7 replayed scrollback holds all 3 cycle marker(s)
```

**NOT caused by T194** — measured, not assumed. The same two assertions fail
identically on a clean build of `368b7a11b` (HEAD before T194) in a scratch
worktree, so the cumulative-scrollback contract broke somewhere between
2026-07-21 (T89i: "cumulative scrollback" green, ALL PASS x3) and now. Bisecting
that window is the first job.

The other 27 assertions in section B are green, including B*.5 (the SAME five
sessions re-ATTACH, no re-OPEN) and B*.6 (exact split ratios), so this is
specifically about REPLAYED CONTENT, not about the restore finding the right
sessions.

## Details

Suspects, in the order they are cheap to rule out:

1. **Scrollback eviction.** Each re-attach replays the agent's whole ring, so
   three cycles may push the pane past its scrollback limit and evict cycle 1's
   marker. If so the fix is in what gets replayed (dedupe/offset), not in the
   limit — `Read-Pane 4000` is already generous.
2. **Replay offset.** T109's WP-D3 snapshot path attaches at
   `attach_offset = snapshot offset`, which is deliberately NOT a full-ring
   replay. A snapshot captured after cycle N would legitimately contain only
   cycle N's screen — which is the exact symptom. Check whether the restored
   pane is being seeded from the snapshot and then NOT gap-filled backwards.
3. **Ring truncation in the agent** (2 MB default, snapshotted to disk across a
   crash): if the snapshot restore drops everything before the last attach, the
   history is gone before the app ever asks for it.

## Re-reproduced 2026-08-09 against `343c470f0` (T89i close-out)

Three consecutive full runs, 112s each. Deterministic and unchanged: B1.7
PASS, **B2.7 and B3.7 FAIL every time**, with all 27 other section-B
assertions green (including B*.5 same-sessions-re-ATTACH, B*.6 exact ratios,
and B*.9/B*.10 liveness round-trips in both windows). Sections A, C, D and
**all twelve of E** are green, so this is now the ONLY red in the harness.

The artifacts sharpen suspect 2 (replay offset) and argue against suspect 1
(scrollback eviction). What the pane holds is not "too much history, oldest
evicted" — it is **exactly the last command block and nothing else**, ~144
bytes:

```
--- before cycle-2's kill (read-b2-pre) : the pane holds C1, the liveness
    echo, and C2 -- nine lines, all of it live
--- after cycle-2's restore (read-b2-mk):
D:\git\ghoztty>SPMK16444C2
'SPMK16444C2' is not recognized as an internal or external command,
operable program or batch file.

D:\git\ghoztty>
```

Cycle 1 loses history the same way and nobody noticed, because B1.7 only
requires ONE marker: `read-b1-pre` contains the `Microsoft Windows [Version
...]` shell banner above C1, and `read-b1-mk` after the restore does not.
So the rule is not "older cycles are dropped" but "**a restore seeds the pane
with one screen's worth and never reaches further back**" — which is what a
snapshot-seeded attach with no backward gap-fill looks like. Start there.

## Close-out (2026-08-15): duplicate of T666, fix verified on box

**This defect was independently re-found, root-caused and fixed under T666**
("The second re-attach in a row replays only the last screen", filed 2026-08-11
from T652's restore-script sweep, fixed the same day by `3bbf0eefb`). T666
never cited T484, so this task sat open four days after its own fix landed.

What the investigation here confirmed before finding the duplicate — kept
because it documents WHY suspect 2 was the right one:

- The agent's grid snapshot (`src/remote/agent/grid_snapshot.zig`) is
  visible-screen-only **by design** (`max_scrollback = 0`; "the ring owns
  scrollback replay"), so on a snapshot attach the agent's repaint homes to
  row 1 and paints one screen.
- The app's own persisted snapshot (`Surface.sessionSnapshot`,
  `session_snapshot_max_rows = 600`) DOES carry viewport + bounded scrollback
  — the history was being painted, then **erased** by that agent repaint,
  which is exactly the "one command block, ~144 bytes" artifact this task
  recorded on 2026-08-09.
- T666's fix (now in `src/termio/Remote.zig` threadEnter): park the painted
  snapshot into scrollback at the repaint boundary (`park_target =
  attach_snapshot_at`, gated on `peerRepaintsOnAttach()`), and extend T106's
  geometry-faithful replay to the snapshot path (`attach_reflow_target`), so
  the gap-fill lands unsmeared and the parked history survives.
- Timeline check: harness green 2026-07-21 (pre-T109) → T109's snapshot
  attach landed 2026-08-03 (`aa09d03e4`) → red found 2026-08-04 (this task)
  → re-red 3x 2026-08-09 → T666 fix 2026-08-11 → green today.

**Verification 2026-08-15 at HEAD (`e39c01027`), Debug build, isolated
endpoints:** three consecutive full `session-persistence.ps1` runs, ALL PASS
