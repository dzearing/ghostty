# T682 - a focused viewer still cannot reach reset_window_size or the tab-overview chord

## Summary

T126 found toggle_hero_mode missing from viewer_accel.forwards() and added it; the same sweep shows two more window-scoped actions win32 IMPLEMENTS that a focused viewer pane cannot reach, because the chord is not in the forwarded set and WebView2 keeps it: reset_window_size and toggle_tab_overview (both have App.zig arms). The rule the list is meant to encode is 'window- or app-scoped, and meaningful with no terminal underneath', and both qualify - a viewer-only window has no terminal to press them from at all. Wanted: add them to forwards(), give each an arm in Window.performViewerBindingAction (the else arm logs a drift warning today, which is how this class of gap stays quiet), and extend the unit test in viewer_accel.zig so the list and the switch are asserted together. Not in scope for T126: neither is hero navigation, and shipping them under a hero-mode task would hide them.

## In plain terms

Ghoztty panes can show a web page or a document instead of a terminal. While
one of those panes had the keyboard, two window shortcuts stopped working: the
one that returns the window to its normal size, and the tab-overview one. The
keypress fell through into the page instead of reaching the app — and in a
window made entirely of document panes there was no terminal left to press them
from at all. Now they work from any pane, and the two lists that have to agree
about which shortcuts a document pane hands back are checked against each other
when the app is built, so the next shortcut cannot go missing quietly.

## Goals

- [x] `reset_window_size` resizes the window when pressed from a focused viewer
- [x] `toggle_tab_overview` is claimed by the app instead of leaking into the page
- [x] the forwarded list and the dispatch switch are asserted together, not by a log line
- [x] `reset_window_size`'s default-size rule is spelled in exactly one place

## Validation criteria

- [x] `forwards()` admits both actions — unit test `forwards: window/app commands
      yes, terminal-content commands no` in `src/apprt/win32/viewer_accel.zig`
      (none + win32 lanes).
- [x] The forwarded set and `Window.performViewerBindingAction` cannot drift —
      comptime block over `Window.viewer_dispatch_tags`. Teeth-checked by removing
      `.reset_window_size` from the list: the win32 lane fails with
      `... disagree about .reset_window_size`.
- [x] `forwards()` is payload-independent, which is what licenses the tag-level
      check — new unit test `forwards is decided by the tag, not the payload`.
- [x] On the box: `test\win32\viewer-window-chords.ps1` — **ALL PASS (23
      assertions)**. `reset_window_size` pressed at a focused viewer returns the
      window to its configured default (1158,422), and neither it nor
      `toggle_tab_overview` reaches the page's own keydown log.
- [x] The script discriminates: `-NegativeControl` fails 3 assertions on a
      healthy build, and a rebuild with both entries removed from `forwards()`
      fails exactly the 3 subject arms (no resize; f9 and ctrl+shift+f8 both
      recorded by the page) with every control still green.
- [x] Floor: `zig build test -Dapp-runtime=none`, `-Dapp-runtime=win32`,
      `zig build test-agent` (via `scripts\floor-lane.ps1 -Lane all`), and
      P1–P3 acceptance scripts.
