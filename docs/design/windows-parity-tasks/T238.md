# T238 - FLAKY: terminal.PageList 'resize (no reflow) less rows trims blank lines erases pages' fails intermittently (exit 3)

## In plain terms

One of the project's automated self-tests sometimes crashes for no visible
reason, even when nobody changed the code it tests. Every time that happens,
the person (or agent) who just made an unrelated change has to waste time
figuring out whether they broke something — and the habit of "just re-run it"
could one day hide a real bug. This task pins down whether that crash is its
own bug or another sighting of an already-tracked phantom crash, and records
the evidence either way.

## Outcome (2026-08-06): another sighting of the T443 ghost — folded in, closed as duplicate

The evidence matches T317 (PageList segfault, win32 lane) and T369
(terminal.search panic, win32 lane), both already folded into T443:

- **Exit code 3 is the segfault-handler abort, not a plain test panic.** Per
  the T444 decode, `0x80000003` (Zig's segfault handler dying in its
  recursive panic, T450) truncates to exit 3 through `std.process.Child` —
  the same wrapped-crash shape as every other T443 sighting.
- **The neighbourhood is the same**: PageList / page-integrity, with the
  adjacent `style ref count mismatch` integrity warn.
- **The code is not the variable**: PageList.zig has no local changes since
  April, and the sighting's own task file records that an immediate re-run at
  the identical tree passed.
- **It will not reproduce, exactly like the others**: 260 runs today
  (200 filtered + 60 full-binary, 20 of them 5-way concurrent — the loaded
  condition every real occurrence came from), 0 crashes.

The "1 run in 4" rate in this task's triage line was an impression from one
red run on 2026-07-31, not a measurement; today's measurement is 0/260.
Nothing was fixed, so this is NOT evidence the defect is gone — it is
evidence that hunting from this sighting has nothing to bite on. T443's
armed watch (T444 exit-code decode + T450 cdb crash-catch in
`floor-lane.ps1`) captures the next natural occurrence with a full stack;
this sighting adds its data point to that log and stands down.

Filed along the way: **T509** — `test-binary-soak.ps1` overwrites the first
binary's per-run logs when a lane soaks two binaries, which cost an extra
20-run soak here to re-identify a lost FAIL.

## Summary

Observed 2026-07-31 during the T230 floor run. `zig build test-agent` failed:

```
error: while executing test 'terminal.PageList.test.PageList resize (no reflow)
less rows trims blank lines erases pages', the following command exited with
code 3 (expected exited with code 0)
```

An IMMEDIATE re-run of the identical command at the identical tree passed
(`agent: 0`), and the same lane had passed twice earlier in the same session at
the same commit. So it is intermittent, not a real regression from the change
under test — the T230 diff touches `termio`, `remote`, `config` and the agent's
pty spawn, none of which `terminal.PageList` imports.

Exit code **3** on Windows is what Zig's panic path produces
(`std.posix.abort` → `ExitProcess(3)`), so this is a panic inside the test, not
a plain assertion mismatch. A nearby log line in the same run —
`[page] (warn): page integrity violation style ref count mismatch id=1
expected=10 actual=9` — is suggestive but belongs to a DIFFERENT test's output
in the same lane, so treat it as a lead, not evidence.

## Why it matters

The loop's standing floor is "both lanes + `test-agent` + P1–P3 green". A lane
that fails ~1 run in 4 for reasons unrelated to the change under test is
directly corrosive to that: every turn has to decide whether it broke something
or drew the short straw, and the safe habit ("re-run it") is the same habit that
lets a REAL intermittent regression through.

## What to check

- Reproduce in a loop: run just this test 50–100× (`zig build test-agent
  -Dtest-filter="less rows trims blank lines"`) and capture the panic message —
  the failing run's stderr was consumed by the build's summary, so the actual
  panic text is not yet known. That text is the whole investigation.
- Whether it is order/allocator dependent (the lane runs tests in one process;
  a page-pool or ref-count leak from an earlier test would explain both the
  intermittency and the ref-count warning).
- Whether it also flakes in the `none` / `win32` lanes, or only under
  `test-agent`'s module graph.
- Upstream: if `terminal/PageList.zig` is unmodified from Ghostty here, this may
  be an upstream flake worth reporting rather than a fork bug — check
  `git log --oneline src/terminal/PageList.zig` for local changes first.

## Validation

- The test passes 100 consecutive runs.
- If the root cause is a leak in a NEIGHBOURING test, that test is fixed too and
  named in this file.
