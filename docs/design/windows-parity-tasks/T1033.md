# T1033 - A GUI acceptance script can still launch the app without the build-mode pre-flight, and banner-resize-repaint.ps1 does

## In plain terms

The test suite is supposed to drive its own private copy of the terminal, never
the one the user is typing in. There is a gate that checks that before anything
is launched - but only the tests that remember to ask it get it. One test that
opens the app never asked, and nothing anywhere could list who else was in that
position. When the check is skipped and the app was built the wrong way, a test
run silently opens windows in the user's real terminal, types into it, and then
reports a pass about a build nobody here made.

## Goals

- [x] the pre-flight rides the launch instead of being remembered: the shared
      test-desktop launcher asks it for every `ghoztty.exe` it starts
- [x] a sweep that fails on any script launching the app without the pre-flight
- [x] every script that sweep named is fixed, and still passes
- [x] the sweep is stamped as a guard, so an edit to the test tree makes it due

## Summary

Found while writing T1031's harness. Assert-GhozttyIsolatedBuild is what stops an acceptance run driving the user's OWN terminal - a non-Debug zig-out derives the same IPC/agent endpoints as the installed release. 49 scripts call it; banner-resize-repaint.ps1 launches the app and does not, and nothing enumerates which scripts skip it. Wanted: a sweep audit (the isolation-meta/verdict-exit shape) that fails on any script which launches ghoztty.exe without the pre-flight, plus the fix for every script it names.

## What was built

**The gate rides the launch.** `Start-OnTestDesktop` (lib\TestDesktop.ps1) now
calls `Assert-GhozttyIsolatedBuild` for any exe named `ghoztty.exe`, before the
desktop is even resolved, with the same `-AllowReleaseBuild` opt-in
`Reset-GhozttyTestState` takes. That is how ~80 GUI scripts - banner-resize-
repaint.ps1 among them - get the pre-flight without 80 copies of one line. The
sweep below measured the split: of 96 scripts that launch the app with no
claim, 80 reach it through that one helper.

**The sweep.** `test\win32\launch-preflight-audit.ps1`, in the
isolation-meta/verdict-exit shape: section A feeds the scanner eight synthetic
fixtures so a green run proves it still bites, section B EXERCISES the helper's
new pre-flight against stub exes (refused when the mode is unreadable, refused
when it reads ReleaseFast, passed through under `-AllowReleaseBuild`, not
applied to a non-app launch), and section C sweeps the real tree. The trigger is
a raw `Start-Process` of a variable the script itself binds to a `ghoztty.exe`;
the claim is any call reaching the gate, or an explicit `# preflight: none -
<why>`.

**The 10 scripts it named**, each fixed and re-run: agent-session-cap,
agent-upgrade, context-menu-real-input, log-append, pane-id, path-selfheal,
session-persistence, session-relaunch-notify, update-check, window-name-env.
Two were not one-liners:

- `session-persistence.ps1` hand-rolled the same predicate (and so had missed
  the freshness half the shared gate grew in T1028); it now calls the shared
  assert and keeps its own exit-2 contract in the catch.
- `log-append.ps1` is the one script whose SUBJECT is a release build (the file
  sink is compiled out of Debug), so it answers with `-Allow` and a note on what
  makes that safe. Its own oracle then caught the pre-flight: `+version` is
  itself a writer to the log being counted, which inflated the per-process
  baseline and read as "23 lines lost". The measurement now starts from empty.

Agent-only launchers are deliberately out of scope - `ghoztty-agent.exe` prints
a build stamp rather than a mode, so this assert cannot speak for it. T1036.
