# T538 - Terminal split off a viewer pane loses cwd inheritance: falls to home/caller cwd instead of the last-focused terminal's

## Summary

A terminal split created off a VIEWER pane no longer inherits its working
directory correctly. Two consistent observations at HEAD 10f10a582
(2026-08-06, T392's changes reverted — this is not a T392 regression):

- `test\win32\viewer-panes.ps1` fails `a web viewer contributes no cwd, so
  the fallback stands (got 'D:\git\ghoztty\')` (script ~line 638, 3/3 runs):
  the split off a web viewer was expected to fall back to the last-focused
  terminal's directory (`$t395other`) and instead landed in the SCRIPT's own
  cwd — which smells like the CLI's implicit `--cwd-implicit` caller-cwd
  being applied to a split whose target pane is a viewer, instead of being
  outranked by surface inheritance.
- A manual repro (fresh debug instance, `+split --target=vpterms --name=w1
  --view=about:blank`, then `+split --pane=w1 --name=w2`): w2 reported
  `working_directory: C:\Users\David\` (home) even though the window's other
  terminal — the last-focused one — sat in `D:\git\ghoztty`. Inheritance fell
  through to the shell default instead.

Note the file-viewer half still passes (a split off a FILE viewer starts in
the viewed file's directory — T395's main path). What is broken is the
no-contribution fallback chain for viewers without a file (web/blank panes).

**Root cause (2026-08-11).** The fallback was never a *window* answer. A
viewer with no file contributes nothing, and the pane's directory then comes
from the core's `apprt/surface.zig` `newConfig` — plus `Surface.init`'s T185
live-pwd override — both of which read `app.focusedSurface`, an APP-GLOBAL
value. So the new terminal inherited from whichever window last held focus
(the script's own `D:\git\ghoztty` pane, in the acceptance run) or, with
nothing focused at all, from the shell's home default (the manual repro). The
same sequence run in isolation PASSED, because there the focused pane happened
to be in the window being split — which is why this read as flaky.

**Fix.** `SplitTree.nearestLeaf` (pure, `src/datastruct/split_tree.zig`,
asserted in the none lane) finds the leaf nearest a given one, entering each
sibling subtree from the side facing it — the pane the viewer shares a divider
with, which is almost always the pane it was split off.
`Window.viewerSplitFallbackCwd` uses it: the focused surface when it belongs to
THIS window (the ordinary case, unchanged, and what macOS does), else the
nearest terminal pane in the viewer's own tab. The directory itself follows
T185's rule (the shell's real cwd when the shell reports none). Both backends
inherit it, since the value rides the existing `viewer_cwd` seam that already
feeds the exec baton and the agent OPEN.

## In plain terms

Open a website or blank browser pane, then split a terminal off it: the new
terminal should open in the folder you were last working in, but it now opens
in your home folder (or wherever the command was issued from). The same split
off a markdown/code viewer still lands in the right place; it is only the
"viewer with no file" case that forgets where you were.

## Goals

- [x] A terminal split off a website or blank browser pane opens in the
      directory of a terminal in THAT window.
- [x] A split off a file viewer still opens where the file is (unchanged).
- [x] The acceptance script proves it with the focus deliberately parked in
      another window, so it cannot pass by luck.
