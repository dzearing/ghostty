# T141 — +relay-login / +relay-logout are Windows-only commands the Mac client never had

## Summary

**`+relay-login` / `+relay-logout` are Windows-only commands the Mac client never had — remove them.** User directive 2026-07-28: *"What is +relay-login? This is a command I NEVER ADDED to the mac client. I don't want commands that only exist on one platform."* T21a invented the pair as the Windows analog of the macOS Keychain-backed `RelayAccount` (Mac signs in from the GUI, so it needed no CLI verb), and the chooser now instructs the user to run one — the divergence is not just present, it is being advertised in the UI. This overrides the "build the native equivalent where the concept has no analog" clause: the concept HAS an analog (GUI sign-in), so the CLI surface must not diverge. Do: move sign-in/sign-out into the GUI (the chooser's own affordance, DPAPI store unchanged), delete both CLI verbs and their docs from CLAUDE.md, and keep the stored-credential reader. Then AUDIT the whole win32 CLI for other one-platform verbs and report them in this row — the same rule applies to every one of them. Validation: `ipc-relay-login.ps1` reworked to drive the GUI path; a diff of the win32 command list against the Mac one with every remaining difference justified in the row

### What shipped

- **Deleted** `src/cli/relay_login.zig` + `src/cli/relay_logout.zig` and their
  four sites in the shared `Action` enum (`src/cli/ghostty.zig`: import, member,
  description, `run`, `options`). A comment stands where the members were,
  saying why nothing may be added back there — the enum is shared by every
  apprt, so a verb added for one platform's convenience IS a cross-platform
  divergence.
- **New shared flow** `src/remote/relay_signin.zig`: `signIn` (PKCE + loopback +
  brokered `/oauth/exchange` + store), `signOut` (best-effort revoke + delete),
  `signedInEmail`, `resolveClientId`, and a pure `errorMessage` the UI renders
  verbatim. Registered in `main_ghostty.zig` so its unit tests run in BOTH
  lanes — the CLI files used to be what pulled `relay_account` into the `none`
  lane, so deleting them without this would have quietly dropped that coverage.
- **New win32 UI** `src/apprt/win32/RelayAccountRow.zig` (the async half) +
  an account row in `MachineChooser.zig` (status text + Sign In / Sign Out
  button, above the filter, right-aligned to the same margin, DPI-scaled). This
  mirrors `MachineChooserView.accountRow` on the Mac: email + "Sign Out", or
  "Sign in with Google…" when signed out.
- **Off the GUI thread, by construction.** `signIn` blocks for as long as a
  consent screen takes; running it inline would freeze every window. A detached
  thread posts `WM_APP_RELAY_ACCOUNT` (WM_APP+9) to `App.msg_hwnd` —
  `ClaudeIntegration`'s pattern — and the GUI-thread landing routes the outcome
  to whichever chooser is open, or to nobody if the user closed it (the store is
  the state, not the dialog). On success the row relabels AND the device list is
  re-fetched in place, so the user's machines appear without reopening.
- Every string that told the user to run the deleted verb now points at the
  chooser: the two `IpcHandlers` refusals, the chooser's own three hints, and
  the doc comments in `relay_account.zig` / `google_oauth.zig` /
  `build_config.zig` / `build/Config.zig`.
- CLAUDE.md's `+relay-login` section is replaced by **"Relay account sign-in
  (GUI only — there is no CLI verb)"**, written so a future agent looking for a
  CLI way to sign in is told there deliberately isn't one.
- `test/win32/ipc-relay-login.ps1` → **`test/win32/relay-account.ps1`** (the old
  name advertised a verb that no longer exists — a trap for the next agent).

### One real defect the validation caught, measured not guessed

The first full run failed `Escape closed the chooser`. The mechanism was NOT
"Escape is mis-routed": **disabling the focused button drops the thread's
keyboard focus entirely**, and with no focus window `WM_KEYDOWN` arrives with
`msg.hwnd == null`, which `App.run`'s dialog-key routing (`if (msg.message ==
WM_KEYDOWN and msg.hwnd != null)`) cannot attribute to the chooser. So the whole
dialog went deaf — Enter, Escape and Tab — for as long as the sign-in ran.

That was proven before it was fixed, with a cross-process oracle rather than an
inference: a new `GetGUIThreadInfo` probe in the harness asserts keyboard focus
stays inside the chooser while busy. Pre-fix it FAILED alongside the Escape
assertion; post-fix both pass. Fix: `refreshAccountRow` hands focus to the
filter EDIT **before** disabling the button.

Also fixed while extracting the flow: the CLI's `openBrowser` claimed in its
comment to honor `GHOZTTY_ENROLL_NO_OPEN` and did not (only `enroll.zig`'s copy
did). The shared version honors it, which is what lets the E2E drive the
redirect without a browser opening on the box.

### The audit — every remaining CLI difference, justified

The `Action` enum in `src/cli/ghostty.zig` is **one shared source with no
`builtin.os.tag` branch anywhere in it**, so after this change a one-platform
verb cannot exist without someone adding a comptime branch. That is the
structural guarantee, not a spot check. Full list, identical on both seats:
`version help list-fonts list-keybinds list-themes list-colors list-actions
ssh-cache edit-config show-config explain-config validate-config show-face
crash-report boo new-window split close rename rearrange list sessions read
send-keys set-state set-banner reload new-remote-window`.

Per-OS *implementations* of a shared verb are fine and intended (the "native
equivalent" clause): `boo`, `edit-config`, `sessions` (named pipe vs unix
socket), `list-colors`/`list-keybinds` winsize, `version`'s linux branch. None
of these change the surface.

What the audit DID find is the same divergence one level down — verbs that exist
on both seats but only one can answer. Both filed:

| Difference | Verdict | Row |
|---|---|---|
| `+version`'s "Running Instance" section | Windows-only: Mac `IPCServer.swift` has **no `case "version"`** (grep: 0 hits), so the IPC query cannot be answered there | **T169** |
| `+list --pid` | Windows-only ANSWER: the flag parses everywhere (shared options struct) but is resolved server-side, and Mac `IPCServer.swift` contains no `"pid"` at all | **T170** |
| `+reload` | Missing on Windows (win32 IPC dispatch has no `reload`) — viewer panes are not built yet; already tracked, no new row | T127 / T90b–T90h |
| `+list --tty` vs `--pid` | Intended per-OS pair (CLAUDE.md documents it) — but see T170: advertising both flags on both platforms is the actual defect | T170 |
