# T215 - Audit product code for input-desktop assumptions (GetForegroundWindow guards)

## In plain terms

Ghoztty has a handful of places that ask Windows "is this window the one the
user is looking at right now?" — to decide whether to flash the taskbar for a
bell, which window an untargeted `ghoztty +split` should open in, whether a
document's contents card paints its selected row in the accent colour, and
whether the hovered pointer should slide a viewer's toolbar in. On the hidden
desktop the automated tests run on, Windows answers that question with
"nothing is", for every window, forever. So those features quietly stopped
working there — not with an error, just with a permanent "no".

Nobody using Ghoztty normally was affected: on a real screen the answer is
right. What was affected is every test that tried to check those features,
which got an answer that looked like a broken product. After this, the app
asks the question a different way — one Windows can still answer on a hidden
desktop — and the answer on a real screen is unchanged, to the byte.

## Goals

- [x] Enumerate every place the win32 app reads "am I the foreground window?"
      and say, for each, what it does off the input desktop
- [x] Fix the ones that silently answer "no" forever
- [x] Put the rule in ONE place, so a new site cannot get it wrong again
- [x] Unit-test the decision, and prove on the box that the fixed behaviour is
      really reachable from a background desktop

## Summary

T211 found the app carrying a guard that is silently always-false on a
background desktop, and there may be more. A background desktop has **no
foreground window at all** - `GetForegroundWindow` returns null for every
window on it - so any product code that gates behavior on "am I the
foreground window?" turns into a permanent no-op there.

The instance already found and fixed (T211): `App.performDeferredFocus`
dropped every queued WM_APP_SETFOCUS, so keyboard focus could never move
between panes, tabs, or dialogs on a test desktop. The fix routes the
decision through `shouldPerformDeferredFocus`, which keeps the T89f2
ping-pong guard on the input desktop and skips it off one.

## Why it is worth a sweep rather than fixing them as they bite

Each of these presents as a *test* failure on the test desktop, which invites
the wrong diagnosis ("the harness cannot deliver input") and, worse, invites
someone to weaken a real assertion to make it pass. Knowing the list up front
makes T212's migration read correctly.

## What to do

1. Grep the win32 apprt for `GetForegroundWindow`, `SetForegroundWindow`,
   `GetActiveWindow`, and any "is foreground" state, and classify each: does
   the behavior it guards still make sense with no foreground window?
2. Fix the ones that would no-op, using the same shape as T211's - keep the
   interactive path byte-identical, branch only on `onInputDesktop()`.

   **But do not simply skip the guard on the off-desktop branch** (T223,
   2026-08-04). T211 (`713815f63`) waved `performDeferredFocus` through
   unconditionally
   there, and that restored the *entire* T105 focus live-lock on every
   non-Default input desktop - measured at 43 focus flips in 3s. The guard was
   using `GetForegroundWindow` as a **proxy** for "has activation moved since
   this was queued?", and the correct fix was to find the proxy that still
   carries information off the input desktop (`GetActiveWindow`, which is
   scoped to the thread's message queue rather than the input desktop) rather
   than to conclude there isn't one. So for each site, ask what the foreground
   check was really standing in for, and whether the reason it exists is
   genuinely moot off-desktop or merely unmeasurable with that particular API.
3. Unit-test each decision as a pure function (that is why T211 split
   `shouldPerformDeferredFocus` out).

## The audit (2026-08-10)

Every read of activation in the win32 apprt and the agent, and what it does
with no foreground window. Writes (`SetForegroundWindow`) are not in the table:
they are actions, and one that cannot take effect on a background desktop
simply does nothing there — no guard turns into a lie.

| Site | Off the input desktop | Verdict |
|---|---|---|
| `App.performDeferredFocus` | already branches on the desktop | fixed by T211/T223; now delegates to `window_active.shouldForwardFocus` |
| `IpcHandlers.frontWindow` | matches no window ⇒ falls through to "most recently created" | **FIXED** — a default-target verb was landing in the wrong window |
| `IpcHandlers` `+list --json` `focused` | false for every window, always | **FIXED** — indistinguishable from "the app is in the background" |
| `ViewerTOCPanel.isEmphasized` | false ⇒ the selection pill never paints accent | **FIXED** — a pixel probe could never see the emphasized state |
| `ViewerPane.navHoverTick` | false ⇒ `in_pane` false ⇒ the nav bar never reveals on hover | **FIXED** — the reveal was unreachable from any script on that desktop |
| `App` `ring_bell` taskbar flash | inverted polarity: always flashes | **FIXED** for consistency; no user-visible change (there is no taskbar to flash there) |
| `App` `command_finished` taskbar flash | same | **FIXED**, same |
| `QuickTerminal.forceForeground` | null foreground ⇒ plain `SetForegroundWindow`, then the (guarded) deferred focus | benign — the focus half already survives |
| `Surface.focusFollowsMouse` | reads `GetActiveWindow` | already correct, and the shape everything above now follows |
| `w32.setTopmost` | re-reads the ex-style rather than trusting `SetWindowPos` | already fixed by T277 — the same class, a different API |
| `remote/agent/tray.zig` | `SetForegroundWindow` before a popup menu | benign action; the agent has no window on a test desktop anyway |

The rule now has ONE home, `src/apprt/win32/window_active.zig`, with two
decisions that differ only in what "nothing known" means: `isActive` (unknown
⇒ false, never claim focus we cannot prove) and `shouldForwardFocus` (unknown
⇒ true, T211's rule). `w32.activation()` is the single place the OS is asked.
