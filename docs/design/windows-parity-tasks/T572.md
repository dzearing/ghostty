# T572 - The real balloon click has never been driven end to end - only the routing and the registration are measured

## In plain terms

Clicking a Ghoztty notification is supposed to jump you to the pane that
raised it. We now have proof of everything on either side of the click - the
notification is registered correctly with Windows, and once a click arrives
the right pane gets focused - but nobody has yet had a machine actually click
a real notification and watched the window come forward. It almost certainly
works; it has simply never been seen to.

## Goals

- [ ] A real notification is clicked, by a person or by real input, and the
      raising window is observed coming to the foreground
- [ ] However it is driven, the recipe is written down where the next person
      will find it

## Summary

Split out of T448 (2026-08-07), which fixed the actual defect: the balloon
icons were never registered with `NIM_SETVERSION`, so the shell kept them on
its pre-5.0 default behavior and `NIN_BALLOONUSERCLICK` was never sent at all.

What T448 left measured:

- **Routing** — `test/win32/notification-click-focus.ps1`, 38 assertions:
  the right pane in the right window is focused, the last raiser wins, a
  timed-out balloon does not steal focus, a closed pane does not crash it.
  It posts `WM_APP_TRAY` itself, so by T240's rule it proves nothing about
  delivery.
- **Registration** — the app logs a warning when the shell refuses
  `NIM_SETVERSION`, and an interactive run on 2026-08-07 produced none, so
  this box accepts `NOTIFYICON_VERSION` against the real notification area.
  (On the background test desktop there is no notification area at all, so
  both `NIM_ADD` and `NIM_SETVERSION` fail there and the script asserts only
  that the failure has that shape.)

What is left is the join between them: that Windows really does deliver
`NIN_BALLOONUSERCLICK` to us when a human clicks the toast. MSDN says it does
for a version-3 icon; nobody here has watched it.

## Details

**Why it is not just a lane.** Balloons render on the interactive desktop, so
`test/win32/lib/TestDesktop.ps1` cannot host this — `SendInput` and screen
reads are dead off the input desktop, and there is no toast there to click.
Any automated version has to take the user's foreground for a few seconds,
which is why T448 filed this rather than wiring it into the floor.

**A first attempt and where it stalled.** T448 wrote a one-off probe
(launch a debug build under a private pipe suffix → two windows → raise OSC
777 from one → focus the other → find the toast → click it → poll
`GetForegroundWindow`). It hung before reporting, most likely in the
`EnumWindows` callback: PowerShell 5.1's scriptblock→delegate conversion is
the usual suspect for that shape. Whoever picks this up should either do the
enumeration in a compiled `Add-Type` class (the way
`test/win32/lib/TestDesktop.ps1` does everything) or skip enumeration and
click by coordinate.

**Where the toast is.** Windows 11 renders a `Shell_NotifyIcon` balloon as a
banner notification, hosted by the shell, class `Windows.UI.Core.CoreWindow`,
near the notification area. A click on its body is what produces
`NIN_BALLOONUSERCLICK`; a click on its dismiss button produces
`NIN_BALLOONHIDE` and must NOT move focus (which is worth asserting too — the
handler already distinguishes them, `tray_notify.classify`).

**The oracle.** The raising window coming to the foreground is enough and
needs no code change: raise from window A, make window B foreground, click the
toast, poll `GetForegroundWindow()` for A. The `--session-persistence=false`
+ `GHOZTTY_PIPE_SUFFIX` isolation from the T448 probe applies unchanged, and
the app must be killed by exact `ExecutablePath` afterwards.

*Validation:* the observation itself, recorded here with the date and the
build; plus whatever script drove it checked in (under `test/win32/` with a
header saying it is interactive-only and not part of the floor) or, if it
stays a human step, written into
`test/win32/notification-click-focus.ps1`'s header where the recipe already
lives.

## Validation criteria

- [ ] A real click on a real Ghoztty notification is performed on the
      interactive desktop and the raising window is observed becoming
      foreground; the date, build commit and method are recorded here.
- [ ] A dismiss (rather than a body click) is confirmed NOT to move focus.
- [ ] The method is checked in or written into the acceptance script's header,
      so the next person does not re-derive it.
