# T167 - A debug-lineage agent already on the box blocks every hermetic test sandbox (single-instance mutex)

## In plain terms

Ghoztty keeps your terminal sessions alive with a background helper, and only
one of those helpers is allowed to run at a time. That rule is right for you and
wrong for our test runs: a test that wanted its own private helper could not
have one, so it quietly ran without session persistence and then reported on
persistence anyway — a test that passes while measuring nothing. Worse, the only
way around it was for a test to kill the helper that was holding the developer's
own real terminal windows. After this change a test can ask for a helper of its
own by name, so tests stop lying and stop trampling live sessions. Nobody using
the terminal sees a difference; what changes is how much we can trust a green
test run.

## Goals

- [x] One env knob (`GHOZTTY_AGENT_INSTANCE`) forks the WHOLE lineage, not just
      the guard — a half-isolated sandbox is the bug, so half a fix is not one
- [x] Unset (every production run) reproduces every existing name byte for byte
- [x] Two sandboxes coexist with each other AND with the user's real agents
- [x] A hostile/over-long value can never smuggle a path separator, and can
      never silently merge two sandboxes into one lineage
- [x] Acceptance script proves it end to end, and has a self-test for its teeth

## Summary

The local agent takes a **per-user, per-lineage** single-instance guard (a
named mutex; `acquireDaemonLockOrExit` in `src/remote/agent/main.zig:325`), so
a second debug agent exits 183 - "another instance is already running" - no
matter how isolated its state is. A test sandbox with its own `LOCALAPPDATA`,
its own agent binary, and even its own `USERNAME`-derived pipe name still gets
**no agent at all**, and the app then silently falls back to non-persistent
Exec panes (`sharedConnection` returns null on a failed resolve, by design).

Measured 2026-07-29 while building `upgrade-no-fork.ps1` (T138): every sandbox
run came up with an empty `local-agent-debug\` and `pre-kill agent sessions: 0`
until the box's leftover zig-out agent (pid 11008) was killed. Running the
sandbox agent by hand reproduced it exactly:

```
ghoztty-agent: another instance is already running; exiting   (exit 183)
```

Why it matters beyond the harness: **the failure is silent**. A suite that
does not kill the incumbent does not fail loudly - it quietly tests the
non-persistent path while claiming to test persistence. `upgrade-no-fork.ps1`
now guards against that with an explicit "the sandbox pane really is
agent-backed (port.json written)" assert, which every persistence-touching
suite arguably wants.

## Details

Options, cheapest first:

1. **Document + assert.** A note in the `test/win32` suite-header convention
   that persistence sandboxes must clear the debug lineage first, plus the
   port.json assert copied into the suites that need it. Cheap, but leaves the
   trap armed for the next author.
2. **A test-only instance override.** The agent already models an `instance`
   (`single_instance.Instance`) - give it an env override (e.g.
   `GHOZTTY_AGENT_INSTANCE=<suffix>`) so a sandbox names its own guard, mutex,
   and heartbeat. Then a sandbox agent coexists with the box's, and suites stop
   killing each other's agents (today's convention, which also means two
   suites cannot run at once).
3. **`--force-replace` from the app's spawn.** Already implemented in the
   agent; wrong default for the product (it would evict a healthy agent) but
   worth exposing to the harness.

Preference: (2), with (1) landing alongside it. Validation: two sandboxes with
different instance suffixes, each with its own live agent and sessions, neither
disturbing the other or the user's release agent; then re-run
`upgrade-no-fork.ps1` and `session-open.ps1` back-to-back without the
kill-the-lineage step.

## What landed

Option (2), widened: `GHOZTTY_AGENT_INSTANCE=<suffix>` names a whole distinct
LINEAGE rather than only a distinct guard. The trap being closed is precisely a
sandbox that is *half* isolated, so every derivation that spells the lineage out
moves on the one knob:

| Derivation | Where | Unset | `=sbx1` |
|---|---|---|---|
| single-instance mutex | `single_instance.instanceWithSuffix` | `…Daemon-local-debug-<sid>` | `…Daemon-local-debug-sbx1-<sid>` |
| lock + heartbeat files | same key | `agent-local-debug.heartbeat` | `agent-local-debug-sbx1.heartbeat` |
| app state dir | `LocalAgent.agentDir` | `…\local-agent-debug` | `…\local-agent-debug-sbx1` |
| agent pipe | `LocalAgent.pipeName` | `…\ghoztty-agent-debug-<user>` | `…\ghoztty-agent-debug-sbx1-<user>` |
| HKCU Run value | `LocalAgent.autostartValueName` | `GhozttyAgent-debug` | `GhozttyAgent-debug-sbx1` |
| `+sessions` dir | `cli/sessions.agentInfoPath` | `…\local-agent-debug` | `…\local-agent-debug-sbx1` |

The naming itself is pure and shared: `src/remote/agent_lineage.zig`
(whitelist sanitize — a value can never smuggle `\`, `/` or `:` into a filename
or a mutex name; 24-char cap; an over-long value is REJECTED rather than
truncated, because truncation would silently merge two sandboxes into one
lineage, which is the very bug being fixed). Unset — every production run —
reproduces each legacy name byte for byte, asserted directly.

Not done here, deliberately: converting the existing suites off their
kill-the-lineage step (T691) and the macOS half (T692). The knob has to exist
and be trusted before ~40 suites are rewritten on top of it.
