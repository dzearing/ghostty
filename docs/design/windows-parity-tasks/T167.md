# T167 - A debug-lineage agent already on the box blocks every hermetic test sandbox (single-instance mutex)

## Summary

The local agent takes a **per-user, per-lineage** single-instance guard (a
named mutex; `acquireDaemonLockOrExit` in `src/remote/agent/main.zig:325`), so
a second debug agent exits 183 - "another instance is already running" - no
matter how isolated its state is. A test sandbox with its own `LOCALAPPDATA`,
its own agent binary, and even its own `USERNAME`-derived pipe name still gets
**no agent at all**, and the app then silently falls back to non-persistent
Exec panes (`sharedConnection` returns null on a failed resolve, by design).

Measured 2026-07-29 while building `upgrade-no-fork.ps1` (T138): every sandbox
run came up with an empty `local-agent-debug\` and `pre-kill agent sessions: 0`
until the box's leftover zig-out agent (pid 11008) was killed. Running the
sandbox agent by hand reproduced it exactly:

```
ghoztty-agent: another instance is already running; exiting   (exit 183)
```

Why it matters beyond the harness: **the failure is silent**. A suite that
does not kill the incumbent does not fail loudly - it quietly tests the
non-persistent path while claiming to test persistence. `upgrade-no-fork.ps1`
now guards against that with an explicit "the sandbox pane really is
agent-backed (port.json written)" assert, which every persistence-touching
suite arguably wants.

## Details

Options, cheapest first:

1. **Document + assert.** A note in the `test/win32` suite-header convention
   that persistence sandboxes must clear the debug lineage first, plus the
   port.json assert copied into the suites that need it. Cheap, but leaves the
   trap armed for the next author.
2. **A test-only instance override.** The agent already models an `instance`
   (`single_instance.Instance`) - give it an env override (e.g.
   `GHOZTTY_AGENT_INSTANCE=<suffix>`) so a sandbox names its own guard, mutex,
   and heartbeat. Then a sandbox agent coexists with the box's, and suites stop
   killing each other's agents (today's convention, which also means two
   suites cannot run at once).
3. **`--force-replace` from the app's spawn.** Already implemented in the
   agent; wrong default for the product (it would evict a healthy agent) but
   worth exposing to the harness.

Preference: (2), with (1) landing alongside it. Validation: two sandboxes with
different instance suffixes, each with its own live agent and sessions, neither
disturbing the other or the user's release agent; then re-run
`upgrade-no-fork.ps1` and `session-open.ps1` back-to-back without the
kill-the-lineage step.
