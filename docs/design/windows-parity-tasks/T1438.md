# T1438 - The cache integrity scan only recognises two shapes of a torn package, and cannot answer for the rest

## Summary

T1436 gave the claim a cache integrity scan (Get-TornPackage in scripts\lib\CacheHeal.ps1). It is cheap - 88ms over 1,513 packages - because it asks only two questions that a correct extraction can never answer yes to: the package directory is empty, or it holds a macOS AppleDouble sidecar with no companion file. The 2026-09-07 tear answered yes to the second, which is why it is there. A package torn in a way that leaves neither tell reads as healthy and is still only caught when a build trips over it. The honest check is to re-hash the extracted tree against the package hash the directory is named for, which is minutes rather than milliseconds, so it does not belong in the claim - it belongs behind a flag (say `build-cache.ps1 check -Deep`) that a turn runs when something smells wrong, or on a weekly cadence. Filed as P3 because the cheap scan plus the heal-on-failure path together cover the observed failure end to end; this is the residual.
