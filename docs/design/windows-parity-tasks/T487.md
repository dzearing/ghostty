# T487 - A second launch of ghoztty -e <cmd> against an already-running instance drops the command

## In plain terms

If Ghoztty is already open and you run `ghoztty -e some-command`, you get a new
empty window and your command never runs. Nothing tells you it was ignored. The
same line typed when Ghoztty is *closed* works fine, so it looks random.

## Goals

- [ ] A launch command reaches the running instance's new window
- [ ] `--working-directory` on the same launch reaches it too
- [ ] An acceptance section that fails without the fix

## Summary

Sibling of T406, different code path. When another process already owns the IPC
pipe, win32 `App.init` forwards a bare `new-window` and exits:

```zig
// src/apprt/win32/App.zig — the AlreadyRunning arm
const ok = internal_os.ipc_client.sendAction(alloc, "new-window", null) catch false;
std.process.exit(if (ok) 0 else 1);
```

The payload is `null`, so `initial-command` (`-e …`, `--command=…`) and
`--working-directory` are parsed, then thrown away. Exit code 0, nothing logged
— the same silent-drop shape T406 fixed for the restore path, which is why it is
worth fixing in the same family.

Verified by reading the code (2026-08-04, while landing T406), not yet
reproduced on the box.

## Fix sketch

Build the forwarded `new-window` payload from the parsed config rather than
passing `null`: `command` from `initial-command` (joined the way
`IpcHandlers.joinArgv` already joins `+new-window -e`), plus
`working-directory`. The IPC verb already accepts both, so this is a payload,
not a new protocol.

Check the Mac seat's behaviour before deciding whether a second launch should
also *activate* the existing app — file the Mac half if it diverges.

## Validation

A section E in `test/win32/gui-launch-command.ps1`: launch once, then launch
again with `-e <marker>` at the same private endpoint, and assert the marker
runs in the second window. Must fail with the payload left as `null`.
