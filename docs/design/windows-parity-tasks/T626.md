# T626 - a protocol skew where the APP is the older side tells the user nothing

## Summary

Found while building T125. `agent_upgrade.evaluateSkew` returns `.none` /
`skew_app_older` when the running agent speaks a NEWER protocol than the app —
correctly, because restarting it would be a downgrade AND would end sessions a
newer app could still attach to. But the only trace of that decision is a log
line. The user gets new windows with no session persistence and no explanation,
which is the same invisible degradation T125 fixed for the other direction.

## In plain terms

If you roll Ghoztty back to an older version, the background process that holds
your terminal sessions stays on the newer one, and the two can no longer talk.
Ghoztty is right not to kill it — that would destroy your sessions to install
something older — but it says nothing at all. Windows just quietly stop keeping
their sessions, and there is no way to find out why short of reading a log file.
It should say: this copy of Ghoztty is older than its background process, update
Ghoztty.

## Goals

- [ ] The `skew_app_older` decision produces something the user can see, once
      per run, not a modal that blocks work (there is nothing to consent to).
- [ ] It names the actionable step — update Ghoztty — rather than describing the
      protocol.
- [ ] Nothing is restarted or killed on this path, ever (assert it stays that
      way).

## Details

The decision already exists and is unit-tested (`agent_upgrade.evaluateSkew` →
`Reason.skew_app_older`); this is purely the notification. Candidate surfaces,
in rough order of fit: the existing update balloon path
(`App.showUpdateNotification` / `tray_notify.zig`), an `ok_only` `ConfirmDialog`
(what `showAgentRefreshFailed` uses), or a pane banner. A modal is probably
wrong — the user cannot fix it from inside the dialog.

Symmetric work for the Mac seat rides with T627.
