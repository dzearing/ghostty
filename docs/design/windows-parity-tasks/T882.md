# T882 - chooser-resume.ps1's orphan fixture rotted: T194 agent-blob restore re-attaches the sessions the kill+drop-manifest trick needs orphaned

## Summary

`test/win32/chooser-resume.ps1` (T320) manufactures its "orphaned live
session" fixture the pre-T194 way: run panes under the agent, hard-kill the
APP only, delete `session-layout-debug.json`, relaunch — then expects the
relaunched app NOT to re-attach those sessions. Since T194
(`App.restoreSessionLayout` unions the local manifest with the layout blobs
the AGENT itself holds, served from its in-memory store), that relaunch
recovers the windows and re-attaches every session even with the manifest
gone. The fixture yields zero orphans, so the script's step-1 setup assertions
("the roster has the orphans plus the new pane", "a live row with no viewer is
rendered") cannot hold.

Evidence (2026-08-16, T520 turn): a new acceptance script that copied this
exact fixture measured, after kill+manifest-drop+relaunch, 2 rendered sessions
with BOTH attached — the T194 recovery in action — and had to be rewritten.
The working replacement shape (already proven in `session-reattach.ps1` F9d
and now `chooser-orphan-badge.ps1`): OPEN a session directly against the agent
with `remote-test-client --pipe=<agent pipe> --hold=1`; the client detaches
and the session stays alive with no pane, orphaned by construction, immune to
launch restore.

The script is not in the guard-due coverage table, so nothing flags the rot —
it stays red (or silently mis-fixtured) until someone runs it by hand. Fix the
fixture; while in there, consider whether the chooser scripts deserve a
guard-due row.

## In plain terms

One of our automated tests sets up its scenario using a trick that a later
feature deliberately made impossible (the app now recovers windows on its own
after a crash — good for users, fatal for the trick). The test can no longer
create the situation it wants to test, so it fails at setup. It needs the
newer, supported way of creating that situation.
