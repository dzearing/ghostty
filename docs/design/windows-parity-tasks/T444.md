# T444 - A test-binary RUN failure is reported as 'compile test ... failure' with exit code 5 and no diagnostic, by zig build itself as well as floor-lane.ps1

## Summary

> **The title above is the symptom as it was reported, and it is wrong.** There
> is no mis-attribution: the step really is a compile step, and its child
> process *crashed*. `5` is `0xC0000005 STATUS_ACCESS_VIOLATION` with its top
> three bytes cut off. See "Answer" below. The title is kept because other files
> cite it.

Split out of **T442**, which recorded it as "the wrapper hid the failure" and
said to fix it there or split it. Splitting it: the mis-attribution is not
`floor-lane.ps1`'s doing. Bare `zig build test-agent` produces it too.

## In plain terms

When the agent test suite fails, the report sometimes says the code failed to
*build* rather than that a *test* crashed - and prints no compiler error to go
with it. Two investigations went looking at the build for a problem that was
never there. Whatever the underlying flake is, the reporting has to name the
right thing.

## Goals

- [x] A run failure is never reported as a compile failure — **and it never
      was**: the exit-5 step really is a compile step, whose child process
      *crashed*. See "Answer" below; the task's founding premise was wrong.
- [x] Whatever the exit-code-5 step actually is, it prints a diagnostic

## Answer (2026-08-04): exit code 5 IS the crash, truncated to a byte

`std.process.Child` keeps only the **low byte** of a Windows exit code
(`lib/std/process/Child.zig:462`, verified in the installed zig 0.15.2:
`break :x Term{ .Exited = @as(u8, @truncate(exit_code)) };`). So an NTSTATUS
arrives at `zig build` as `NTSTATUS & 0xFF`:

| real exit code | meaning | what zig prints |
|---|---|---|
| `0xC0000005` | STATUS_ACCESS_VIOLATION | `error code 5` |
| `0x80000003` | STATUS_BREAKPOINT (a Zig panic / segfault-handler abort) | `code 3` |
| `0xC00000FD` | STATUS_STACK_OVERFLOW | `code 253` |

Measured directly rather than inferred: a ReleaseFast Zig program that writes
through `0x10` returns `-1073741819` = `0xC0000005`, and `0xC0000005 & 0xFF` is
`5`.

**So the exit-5 step is a genuine compile step, and the compiler crashed.** The
Windows Application log names it — three separate `zig.exe` access violations on
this box in two days, at three different fault offsets:

```
08/04 03:39:24  zig.exe  0xc0000005  module=unknown   +0x8669f77d80   (WER bucket type BEX64)
08/04 02:43:54  zig.exe  0xc0000005  module=zig.exe   +0x0230f248
08/04 01:18:58  zig.exe  0xc0000005  module=zig.exe   +0x037ddea2
```

The 02:43:54 crash falls inside `%TEMP%\floor-lane-agent-20260804-024251-510.log`
— the exact run this task was filed from. The 03:39:24 crash is run 1 of the
2026-08-04 repro loop below, which failed the same way.

There is no diagnostic because there is nothing to print: a process killed by an
unhandled access violation writes nothing to stderr, and the shipped `zig.exe`
is ReleaseFast, so it has no segfault handler to print a trace. `zig build` and
`floor-lane.ps1` were both reporting faithfully — the exit code simply had its
meaning shredded on the way through.

**This reframes T443 rather than only serving it.** The corrupter is not
confined to the ghoztty test binaries: the *compiler* is crashing too, in
three different places, on the same box, in the same window. See T447.

## What shipped

- **`scripts/lib/CrashDiag.ps1`** (new) — decodes a truncated exit code back to
  the NTSTATUS values whose low byte matches, reads `Application Error` (id 1000)
  records for the run's time window, and prints them together. The decode alone
  is a *suspicion* (a program really can call `exit(5)`); the event log is what
  makes it evidence, and when there is no record the diagnostic says so out loud
  instead of letting the decode read as a confirmation.
- **`scripts/floor-lane.ps1`** — a FAIL now ends with a `-- crash diagnostics --`
  block. Real output from an agent-lane run on 2026-08-04:

  ```
  -- crash diagnostics --
    exit code 3 is the low byte of 0x80000003 STATUS_BREAKPOINT (Zig panic / segfault handler abort)
    (std.process.Child truncates the Windows exit code to a byte, so a
     crashed child arrives as NTSTATUS & 0xFF -- see scripts/lib/CrashDiag.ps1)
    CRASH 03:51:21 ghoztty-agent-test.exe pid=0xBCF4 0x80000003 STATUS_BREAKPOINT ... in ghoztty-agent-test.exe+0x00000000001cb84e
  ```

  It only waits on Windows Error Reporting (which writes its record a beat after
  the process dies) when the exit code already looks like a crash, so an ordinary
  red lane is not slowed down.
- **`test/win32/crash-diagnostics.ps1`** (new) — 21 checks, `ALL PASS`. It
  proves the decode, both of zig's exit-code phrasings, and the whole correlation
  against a **real** access violation it compiles and runs, not a mocked one.
  Plus the two negative controls that matter: an ordinary compile error prints no
  crash block at all, and a crash-shaped exit code with no matching Application
  Error record is reported as unconfirmed.

## Evidence

T442 saw it twice through `floor-lane.ps1` and concluded the wrapper was at
fault. On 2026-08-04 the same shape came out of `zig build` directly:

```
Build Summary: 53/56 steps succeeded; 1 failed; 3836/3912 tests passed; 76 skipped
test-agent transitive failure
+- run test ghoztty-agent-core-test transitive failure
   +- compile test ghoztty-agent-core-test Debug native-native-msvc failure

error: the following command exited with error code 5:
```

with the full `zig test-obj ...` command line echoed and **no `error:` line
from the compiler**. Re-running the identical command immediately afterwards
compiled and passed. So the compile step really is exiting non-zero
(5 = the compiler process dying, not a normal diagnostic exit), and both
`zig build` and the wrapper faithfully report "compile ... failure" for it.

Two things to settle:

1. **Why is the compile step exiting 5 with no output?** A crashing
   `zig test-obj` child would do it. Capture the step's stderr (it is being
   swallowed somewhere - the `--listen=-` protocol carries it) and see.
   Suspect a compiler crash under the concurrent-build load of `test-agent`,
   which builds and runs two large test binaries at once (see **T434**).
2. **Make the report legible either way.** If the step is a compile, say so
   with the compiler's own words. `floor-lane.ps1` should surface the step's
   stderr rather than only its exit code - T430 exists so a red lane is
   legible, and this is the same requirement one level down.

## Validation

- Force a compile failure and a run failure in the agent lane and confirm each
  is reported as what it is, with a diagnostic, both bare and through
  `floor-lane.ps1`.

### Validation results, 2026-08-04 — all three shapes are now distinguishable

Each injected into `src/agent_core_test.zig` and run with
`-Dtest-filter="t444 injected"`, then reverted.

| injected | bare `zig build test-agent` | through `floor-lane.ps1` |
|---|---|---|
| a failing test | `error: 'agent_core_test.test.t444 injected run failure' failed` | same, named, **no** crash block |
| a compile error | — | `src\agent_core_test.zig:14:19: error: expected type 'u8', found '*const [16:0]u8'`, **no** crash block |
| a real crash (the lane's own) | `exited with code 3` and nothing else | the `-- crash diagnostics --` block above, naming the process, exception and fault offset |

One wrinkle worth recording for whoever repeats this: a compile error parked in
an **unreferenced container-level decl** does not fail the build at all (the
lane went green with `const t444_bad: u8 = "…";` sitting in the file) — Zig
never analyses it. The error has to live inside a test the filter selects.

## Another instance, 2026-08-04 (T28-split turn, docs-only working tree)

`zig build test-agent` FAIL in 180s, seed `0x1a4bf15a`, 3837/3913 tests passed,
76 skipped. Reported as:

```
+- run test ghoztty-agent-core-test
   +- compile test ghoztty-agent-core-test Debug native-native-msvc failure
error: the following command exited with error code 5:
"...\zig.exe" test -fllvm ... --listen=-
```

No diagnostic, no test name, nothing on stderr from the step itself - exactly
the shape this task describes, so the behavior is reproducible rather than a
one-off.

Worth noting for prioritization: in the same floor run the `win32` lane failed
too, and it reported *legibly* - a named victim test and
`Segmentation fault at address 0xffffffffffffffff`. Same tree, same wrapper,
one lane readable and one silent. That is a useful contrast to debug against:
whatever the `win32` lane's run step does to surface the crash, the agent
lane's step is not doing. It also means T443 currently cannot tell whether the
agent lane is failing for the same reason as `win32` or a different one, so
this task gates evidence quality for that one.
