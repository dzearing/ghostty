# T247 - Mac seat: the background picker's foreground/palette contrast has the same sub-floor holes T150 fixed on Windows

## Summary

T150 ported Mac's `c3e9999e7` to Windows and, doing it, found two contrast
holes that are in the MAC code the port came from. Neither is a Windows
divergence: they are shared logic that Windows now handles and Mac does not.

1. **The picked foreground can land under the 4.5:1 text floor.**
   `applyBackgroundForColor` chooses black or white by a Rec.601-style
   lightness test (`isLightColor`), which disagrees with WCAG contrast across
   a band of mid-tones. `#777777` reads "dark", so it picks white at
   **4.42:1**, while black gives 4.76:1. Choosing the side by contrast
   instead is self-correcting for every color the picker accepts: the worst
   case is the crossover background, and there both sides are 4.58:1.
   Windows fix: `color_math.contrastForeground` (see its sweep test).

2. **`adjustPaletteForContrast` can return a still-failing color.** Its
   hue-preserving L* search only moves AWAY from the background. A saturated
   color clamps against the sRGB gamut before reaching the luminance it
   needs, so against a mid-tone background neither side has the room, and the
   loop returns its best effort — which still fails the target — as if it had
   succeeded. Windows fix: try the opposite side, then fall back to
   black/white, the same order of preference `contrasted_color` already uses
   in the shaders.

Found by a sweep test over the whole lightness range rather than by
inspection; handpicked themes miss both.

## Validation

- Port both fixes to the Swift picker path.
- A sweep assertion (all greys + saturated hues at every lightness) that the
  chosen foreground and every adjusted palette entry clear 4.5:1.
- Windows reference: `src/apprt/win32/color_math.zig` (`contrastForeground`,
  `contrastAdjusted`/`searchLightness`) and its tests.
