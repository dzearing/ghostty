# T464 - A diff viewer pane has no file-tree side panel on Windows

## In plain terms

Once a diff renders in a pane, a change touching thirty files is one very
long scroll. On the Mac the pane has a file tree down its side: the changed
files nested by folder, click one to jump to it, and it tracks where you are
as you scroll. Windows needs the same panel. It is the same card the table
of contents already uses for markdown, pointed at files instead of headings.

## Goals

- [x] A diff viewer pane shows a file tree of the changed files, nested by
      directory, with a chain of single-child folders collapsed into one row
- [x] Clicking a file OPENS it (the page shows one patch at a time, so
      selecting and opening are one act); the selection follows whichever file
      the pane has open, including across a working-tree poll
- [x] Clicking a folder shuts it and its files leave the list; clicking it
      again brings them back, and the list does not jump under the pointer
- [x] A `git-status:` diff groups its files under working-tree section
      headers; a commit's diff has none
- [x] Wide pane: the panel sits in a gutter with the document reflowing
      beside it, and its right edge is draggable; narrow pane (< 720 DIP): it
      becomes an overlay behind a chrome button. The switch follows the PANE
      width live, so dragging a split divider reflows it
- [x] The margin rule holds: one `outerMargin`, all four sides, no
      per-component fudges, asserted

## Evidence

Nothing under `src/apprt/win32/` renders a viewer side panel of any kind.
On the Mac this landed as `ViewerDiffTree.swift` (190 lines) and
`ViewerSidePanel.swift` (223) in 69eb4aeb0 — and note the same commit
**refactored `ViewerTOC.swift` down by 217 lines**, because the table of
contents and the diff tree are the same panel with different rows. Whatever
Windows builds here should factor the same way rather than growing a second
card implementation; if win32 has no TOC panel yet, that is the shared piece
this task creates.

## What this turn actually built

One card, two subjects - the factoring Mac arrived at, and the one this task
asked for. `ViewerTOCPanel` already owned the glass card, the gutter/overlay
switch, the drag handle, the scroll, the hover and the selection pill; all of
that is now shared, and the only thing that differs between a table of contents
and a file tree is which list the rows come from and what a click means.

- **`src/apprt/win32/viewer_file_tree.zig`** (new) - the pure transform from
  git's flat list of changed paths to the rows on screen. The Windows port of
  `ViewerDiffTree.swift`, including the single-child chain collapsing and the
  per-origin sections, plus the git-status-to-tone mapping the badge colors
  come from.
- **`viewer_toc_layout.zig`** - `treeRowBoxes` and `badgeWidth`: the x extents
  of a tree row's three parts, composed from the SAME insets the heading rows
  use so the two subjects line up on the same edges.
- **`ViewerTOCPanel.zig`** - a row kind, the two extra owned labels a file row
  carries (the status letter, the `+12 -3` counts), the painter for them, the
  `FILES` caption with its file count, and the click routing.
- **`ViewerPane.zig`** - owns the tree, the collapsed-folder set (which
  survives every poll on purpose), and the two click handlers.
- **`chrome_theme.zig`** - a fourth `Tone`, `info`, for the rename/copy badge.
  Mac paints that one blue and the three existing tones had no meaning for it;
  a private RGB beside the shared tones is exactly the divergence that module
  exists to stop.

### Decisions taken here (mechanism, not experience - go.md step 5b)

- **The selection does not track a scroll position**, because there is nothing
  to track: the win32 diff page renders ONE file's patch at a time
  (`setDiffFile`), so the open file IS the selection and a scroll spy would
  have nothing to say. The TOC's pin rule is therefore not needed on this card;
  the goal's wording was written from the heading card's contract.
- **The two-item floor is shared.** A one-file diff draws no card, the same way
  a one-heading document does not - a card listing a single row costs a strip
  of the pane and answers nothing.
- **The name truncates through the middle** (`DT_PATH_ELLIPSIS`). Mac truncates
  at the head for the stated reason that the tail identifies the file; win32
  has no head-ellipsis flag, and the middle ellipsis keeps the same tail and
  extension. It is also exactly right for a folder row, whose title is a
  joined path.
- **The filter field is NOT part of this task.** Mac pins a search box under
  the header; it is a real text input inside an owner-painted card, with its
  own focus yield, and it is filed separately (see below) rather than smuggled
  in here.
