# T933 - The floor run takes three times longer than its lanes because the agent lane leaks its test binaries

## Summary

Measured 2026-08-17 during T829: floor-lane.ps1 -Lane all reported lib 52s + none 282s + win32 361s + agent 363s = 17.6 minutes of lanes, and took 61 minutes of wall clock. The agent lane printed PASS at 13:55:31, and at 14:37 ghoztty-agent-test.exe and ghoztty-agent-core-test.exe (spawned 13:52:04) were STILL alive and burning about 38 percent of a core each, having spawned and outlived a tree of msedgewebview2.exe children; the wrapper blocked until they finally died, then exited 0. So every turn on this box pays roughly 40 minutes of dead time per floor run, the loop's single most-run command, and the run looks like a slow lane rather than a leak - the summary even says 'leaked webview hosts swept: 0' while the leak is the TEST BINARIES, not the webview hosts. Wanted: the agent test binaries exit when their lane does, the wrapper reports and reaps anything still alive at lane end (naming it, so a leak reads as a leak), and the stall detector is not fooled by a leaked child still burning CPU.

## In plain terms

Running the project's standard test sweep used to tie the machine up for an
hour even though the tests themselves finished in under twenty minutes. The
reason was that the tests were accidentally launching copies of themselves:
one of them asks the code to "start a background process", and inside a test
run the only program it knows how to start is the test program itself. Those
copies were started in a way designed to survive being killed, so nothing
cleaned them up - they sat there churning through a CPU core long after the
sweep said it had passed, and the sweep's own hang detector saw that churn and
concluded everything was still working fine.

After this change a test run cannot launch itself, the sweep says out loud when
something like it happens again, and a run whose only activity is a stray copy
is correctly reported as stuck instead of busy.

## Goals

- [x] a test binary can never be spawned as if it were the product executable
- [x] the agent lane leaves no test binaries behind when it prints its verdict
- [x] a leak report names how the process was launched, and says SELF-SPAWN when
      the code under test launched its own image
- [x] the stall detector ignores a self-spawned copy's CPU, so a wedged lane
      reads as wedged

## Validation criteria

- [x] `src/os/self_exe.zig` refuses to hand a test build its own path to spawn -
      three unit tests in the `none` and `agent` lanes (`zig build test-agent
      --summary all`).
- [x] `pty_holder_child.open` returns `SelfSpawnFromTestBinary` instead of
      spawning, asserted by "open: a test binary is never spawned as its own
      holder (T933)" in the agent lane.
- [x] the agent lane spawns NO copy of itself: a WMI command-line watcher over a
      full `zig build test-agent` recorded `ghoztty-agent-test.exe --pty-host
      --spec ...` (pid 8524, reparented to explorer.exe) BEFORE the fix and only
      the two build-runner `--listen=-` launches after it.
- [x] the stall detector is not fooled: the same staged lane (a nested fixture
      spinning while the lane itself does nothing) run through a pre-T933 copy of
      the wrapper reports `LANE command TIMEOUT in 46s` - it never called a stall
      - and through HEAD reports `LANE command STALL in 25s`.
- [x] `test\win32\floor-lane-leak-sweep.ps1` ALL PASS (arms 11-14 are this
      task's: nested-pid identity, launcher recognition, the SELF-SPAWN line, and
      the wedged-lane verdict end to end).
- [x] the standing floor is green: `scripts\floor-lane.ps1 -Lane all`.
