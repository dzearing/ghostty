# T264 - caption-bar.ps1 keeps a private copy of the caption button arithmetic ChromeGeometry now derives

## Summary

T257 hoisted the chrome datum into `test/win32/lib/ChromeGeometry.ps1` because
four scripts each carried their own copy and only one got Zig's
half-away-from-zero rounding right. T260 added the caption's own right-anchored
run to that module (`CaptionOverflowLeft`/`CaptionOverflowX`, plus
`HasCaption`), because `menu-bar.ps1` needed to click the "..." host.

`caption-bar.ps1` still derives the same four rects itself
(`caption-bar.ps1:172-183`: `$step`, `$closeL`, `$maxL`, `$minL`, `$overL`).
Its header calls that deliberate - "restated here from the DIP constants rather
than read out of the binary" - and as a cross-check of ONE script against the
module that is defensible. What is not defensible is that it is now the second
derivation of the same numbers in the same test tree, and **T205 moves them**:
the caption run has to make room for the tab strip, and a script that
re-derives the old anchoring fails in the T256 way (measuring last release's
layout and reporting it as a defect).

## The decision to make

Either:

1. **Read them from `Get-TestChromeMetrics`** like `menu-bar.ps1` does, and
   keep exactly one assertion in `caption-bar.ps1` that restates the DIP
   arithmetic from scratch as the cross-check the header wants - one place, not
   five rects; or
2. **Keep the restatement** and add an assertion that it AGREES with
   `Get-TestChromeMetrics` (`$overL -eq $m.CaptionOverflowLeft`, and so on),
   which turns the duplicate into a real oracle instead of a latent divergence.

(2) is probably better: the cross-check is the reason the copy exists, and
making it explicit costs four lines. Record which, and why, in the script.

## In plain terms

Nothing a user of the terminal can see changes here. One of the automated
checks that guards the window's titlebar had its own private copy of "where the
minimize, maximize, close and '...' buttons sit", separate from the shared copy
every other check reads. Two copies of one measurement drift apart eventually,
and when they do the check starts failing against a perfectly healthy build —
which costs a day of hunting a defect that does not exist. The copy now has to
agree with the shared one, out loud, every run.

## Goals

- [x] Decide which way the duplicate goes, and write the reasoning into the
      script where the next reader will meet it
- [x] The two derivations are compared on every run, not just co-existing
- [x] A one-pixel disagreement fails the script, and fails ONLY the new
      assertions — so a red run names the divergence instead of scattering

## Resolution

**Option 2: the restatement is KEPT and asserted to agree**, and the reasoning
is in `CaptionGeom`'s header in the script (the task asked for it to be
recorded there).

What settled it: section 2 measures PAINTED pixels against `CaptionGeom`'s
numbers. If those numbers were read out of `Get-TestChromeMetrics`, a module
that drifted would move the probe points along with it and the section would
keep passing — the derivation would no longer be checked by anything, in the
one script whose whole job is checking it against reality. Option 1's "keep one
assertion that restates the arithmetic" is the same duplicate wearing a smaller
hat, and it would only cover one rect out of four.

New section **2b** compares all four x's plus the band height against
`$geo.M` — the metrics `CaptionGeom` itself read, so same call and same window
rect, and a difference can only be the arithmetic.

`GHOZTTY_TEST_CAPTION_SKEW=<n>` is the teeth-check: it shifts the restatement
by n px, which is the same observable state as the module drifting by n. One
pixel inside a 46 DIP slab still hit-tests, clicks and paints identically, so a
skewed run goes red in 2b and nowhere else. Unset in every real run.

## Validation criteria

- [x] `caption-bar.ps1` ALL PASS — **32 assertions** (was 27), run 2026-08-11

- [x] A deliberate one-pixel divergence FAILS rather than passing silently —
