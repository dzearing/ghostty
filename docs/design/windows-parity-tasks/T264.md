# T264 - caption-bar.ps1 keeps a private copy of the caption button arithmetic ChromeGeometry now derives

## Summary

T257 hoisted the chrome datum into `test/win32/lib/ChromeGeometry.ps1` because
four scripts each carried their own copy and only one got Zig's
half-away-from-zero rounding right. T260 added the caption's own right-anchored
run to that module (`CaptionOverflowLeft`/`CaptionOverflowX`, plus
`HasCaption`), because `menu-bar.ps1` needed to click the "..." host.

`caption-bar.ps1` still derives the same four rects itself
(`caption-bar.ps1:172-183`: `$step`, `$closeL`, `$maxL`, `$minL`, `$overL`).
Its header calls that deliberate - "restated here from the DIP constants rather
than read out of the binary" - and as a cross-check of ONE script against the
module that is defensible. What is not defensible is that it is now the second
derivation of the same numbers in the same test tree, and **T205 moves them**:
the caption run has to make room for the tab strip, and a script that
re-derives the old anchoring fails in the T256 way (measuring last release's
layout and reporting it as a defect).

## The decision to make

Either:

1. **Read them from `Get-TestChromeMetrics`** like `menu-bar.ps1` does, and
   keep exactly one assertion in `caption-bar.ps1` that restates the DIP
   arithmetic from scratch as the cross-check the header wants - one place, not
   five rects; or
2. **Keep the restatement** and add an assertion that it AGREES with
   `Get-TestChromeMetrics` (`$overL -eq $m.CaptionOverflowLeft`, and so on),
   which turns the duplicate into a real oracle instead of a latent divergence.

(2) is probably better: the cross-check is the reason the copy exists, and
making it explicit costs four lines. Record which, and why, in the script.

## Validation

- `caption-bar.ps1` ALL PASS.
- A deliberate one-pixel change to the module's derivation makes the chosen
  form FAIL rather than silently disagree.
