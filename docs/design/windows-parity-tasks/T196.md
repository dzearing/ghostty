# T196 - Deliver the T145 + T147 agent fixes to all 3 install locations

## Summary

Two agent-lifecycle fixes have landed on the branch and neither has reached the
user's installed build: **T145** (a dead agent no longer freezes every
persistent pane until the app is relaunched) and **T147** (the app adopts a
newer bundled agent build instead of running an old agent until the next
reboot). Both are exactly the class of fix the T49 lesson is about — a fix that
only lives in `zig-out` does not exist as far as the user can tell — and T147 in
particular is *worth less the later it ships*, because it is the mechanism that
makes every FUTURE agent-side fix reach the user without a reboot.

## Details

Deliver HEAD to all three locations per the standing bar:

1. installed release (`%LOCALAPPDATA%\Programs\Ghoztty`) — via the detached
   `scripts/upgrade-ghoztty-windows.ps1` at a task boundary, never with a
   `-ResumeCommand` override (2026-07-18 rule),
2. Desktop portable (`D:\Users\David\Desktop\Ghoztty-portable-x64`),
3. the share copy (`\\homeassistant\share\ghoztty-windows`).

Note the ordering subtlety this delivery is itself a test of: the upgrade script
swaps `ghoztty-agent.exe` WITHOUT killing the running agent (T89h), so after the
swap the app relaunches beside a NEW agent binary while the OLD agent process is
still serving. That is precisely the state T147 was built for, so the resumed
session should see one of two outcomes in the app log and should record which:

- the agent was idle ⇒ a silent refresh (`local agent refreshed to bundled
  build …`), or
- sessions were live ⇒ the mandatory "Restart the Ghoztty background terminal
  process?" confirmation.

Either is correct; a THIRD outcome (neither, and the agent stays on the old
build) means the delivered build is not actually running the T147 code and the
delivery is not done.

### What the delivery turned out to be a live test of

The box was already sitting in the exact state T147 was written for, so this is
a field run rather than a contrived one. Measured before launching:

- installed agent **pid 27568, started 2026-07-29 17:21:04** — a *yesterday*
  build, still serving after four same-day binary swaps (T144, T190, and the two
  T196 stagings). That is precisely the "an agent-side fix reaches the user only
  when they next reboot" gap T147 closes.
- installed app pid 13572, started 2026-07-30 13:11:36 (the T190 upgrade).
- `ghoztty +sessions` against that agent: **4 alive / attached / pinned**
  sessions, one of them this loop's own Claude pane
  (`cmd=…\ghoztty-go-loop-resume.cmd`).

So `agent_upgrade.decide(running, bundled, live=4)` must return `confirm_first`,
and the expected outcome here is the **mandatory confirmation dialog**, not the
silent refresh. That is the CLAUDE.md contract working as designed: four live
PTYs are never reset behind the user's back.

Two properties were verified by reading the code before launching, because an
unattended boundary cannot afford to guess whether a modal dialog would wedge
the loop:

- `ConfirmDialog.runModal` (`src/apprt/win32/ConfirmDialog.zig:530`) pumps the
  normal message loop, and IPC is handled in window procs — so the upgrade
  script's `+send-keys` resume still lands while the dialog is up.
- The dialog disables only its OWNER window (`EnableWindow(o, 0)`), and
  `+send-keys` writes to the PTY over IPC rather than through the keyboard, so
  the resumed session can still drive its own pane.

The correct answer to the dialog on THIS box is **"Later"**: confirming would
restart the agent, relaunching all four sessions as tombstones — including the
pane running the loop. Declining sets `agent_upgrade_declined` for the run and
the refresh happens at the next idle moment (last persistent window closed),
which is the designed deferral, not a failure.

### A shape regression the artifact diff caught

The first zip rebuild exited 0 and was wrong in two ways, both found by diffing
its entries against the artifact it was replacing rather than trusting the exit
code:

- root entries came out `Ghoztty-portable-x64\Ghoztty\…` instead of `Ghoztty\…`,
  so extracting it the documented way would have double-nested the app
  directory, and
- it carried both `.pdb` files, doubling the download (41,858,780 bytes vs
  20,272,204) for a share whose consumers only run the exe.

Rebuilt to the previous shape: 572 entries / 20,299,310 bytes against the old
571 / 20,272,204. The general lesson: a generated artifact that REPLACES an
existing one should be diffed against it, because "the command exited 0" says
nothing about shape. Filed as **T198** so the next delivery does not re-derive
it by hand.
