# T431 - Narrowing a pane can DESTROY scrollback under ConPTY: the reflow pulls history into the viewport and conhost's post-resize repaint erases it

## In plain terms

Scrolled-off output in a terminal pane is supposed to stay there — you can
always scroll up and find it again. On Windows there is reason to think that
making a pane narrower can permanently delete some of it: the lines nearest the
bottom of your history get pulled onto the visible screen by the re-wrap, and
the program running in the pane repaints over them a moment later. They are then
gone from the history too.

Dragging a divider or opening a split next to a pane makes it narrower, so this
would be an ordinary thing to do and lose work over. It has been demonstrated
for one specific block of text; the first job here is to find out whether it
really happens to a user's own scrollback, because that determines whether this
is urgent or a curiosity.

## Goals

- [x] Establish on box whether real scrollback is actually lost when a pane is
      narrowed, with numbered lines so missing ones are countable
- [x] Check it under every shell flavor, and on both local and persisted panes
- [x] If it does not reproduce, record why and close it — the negative result is
      worth as much as the positive one
- [x] If it does, fix it so narrowing a pane never destroys history

## What actually happened — the trigger is the OTHER axis

Measured on box with `test\win32\scrollback-narrow.ps1` (fill a pane with
`line 1`..`line 500`, then read the scrollback back after each gesture; a
number that was there and is not is destroyed history):

| gesture | before the fix |
|---|---|
| narrow 1400 → 700 px | **no loss** |
| divider-style drag, 700 → 460 in 20px steps | **no loss** |
| widen back to 1400 | **no loss** |
| **grow the height 820 → 1300 px** | **LOST 18 lines** (456–473) |
| shrink the height back | no loss |
| **grow height while narrowing** | **LOST 27 more** (438–455, 474–475) |

So the task's premise was half right and pointed at the wrong axis.
**Narrowing a pane destroys nothing.** What destroys scrollback is *growing
the pane's row count* — making the window taller, maximizing it, un-zooming,
closing a split below, dragging a horizontal divider down. The number of lines
lost is exactly the number of rows the viewport gained.

Why width is innocent and height is not: the "pull history down" behaviour
lives in `PageList.resizeWithoutReflow`, the `.gt` rows branch, and it fires
when the cursor is on the bottom row — which is where a shell prompt always
is. A width change alone never takes that branch. The reflow path *can* import
history too, but only over a viewport with trailing blank rows, and a pane
whose viewport is full (the state a 500-line fill leaves it in) has none.

Two adjacent findings worth recording:

- **`cls` (cmd) and `Clear-Host` (Windows PowerShell) destroy the whole
  scrollback**, not just the viewport — they emit `ESC[3J`. That is conhost's
  own behaviour and matches Windows Terminal, so it is native, not a bug. It
  does mean neither flavor can reach the blank-viewport-over-deep-history state
  at all. git-bash's `clear` (terminfo, no `ESC[3J`) does, and that
  configuration is now covered.
- **`pwsh` is not installed on this box.** The script SKIPs a missing flavor
  rather than failing, so its absence never reads as a scrollback bug.

## The fix

`src/termio/history_guard.zig` (new). Pin the first row of the active area
before a resize; afterwards ask where that pin ended up. If it is `k` rows down
the active area, the resize imported `k` rows of history — so scroll exactly
those `k` rows straight back out. The viewport ends up the same height with `k`
blank rows at the bottom, which is *precisely* what conhost's own buffer looks
like after the same resize, so the two models stay in step and the child's
repaint has nothing of ours to erase.

A tracked pin is the only handle that survives a reflow, which is why T423's
`session_notice.trackFold` uses one. This generalises that single-block guard
to the whole boundary: with the first active row held, nothing above it can be
dragged in — the notice included.

Deliberately NOT a terminal-core change. The task's own candidate directions
both proposed changing `PageList`/`Screen` resize semantics, which reaches every
platform for a bug only ConPTY can have. This sits in `src/termio`, is gated on
`history_guard.enabled` (`builtin.os.tag == .windows`), and compiles to nothing
on macOS — where pulling history down on a taller window is correct behaviour
and must stay.

Wired into both paths that reflow the local grid: `Termio.resize` and
`Termio.reflowLocalGrid` (the reboot-scrollback replay, which reflows to the
live width and could eat history the same way).

## Validation

- `src/termio/history_guard.zig` — 5 unit tests in the `none` lane: growing rows
  (the measured bug, asserted against a following `eraseDisplay` so the test
  encodes "history survived the repaint", not just "rows moved"), a narrowing
  reflow over a blank viewport, a shrink (must cost nothing and move nothing),
  cursor-follows-its-content, and the alternate screen having nothing to guard.
  Registered in `src/termio.zig` — without that line the tests silently do not
  run, which was verified with a deliberate canary failure before trusting the
  green.
- `test\win32\scrollback-narrow.ps1` — on-box, background test desktop.
  ALL PASS in four configurations: `cmd`, `powershell`, `bash`, and a
  session-persistence (agent-owned ConPTY) pane. The same script FAILED two
  assertions before the fix, on the same box, at the same geometries.
- Floor: `none` PASS, `agent` PASS, P1–P3 ALL PASS. `win32` failed once and
  passed on re-run, in `remote.connection` — unreachable from this change, and
  filed as **T472**.

## Known gap, filed rather than left undocumented

The guard is chosen by the LOCAL os, not by the child's pty flavour. A macOS app
attached to a **Windows agent's** ConPTY still loses history on a taller window;
a Windows app attached to a POSIX agent gets a guard it does not need (harmless
— blank rows instead of pulled-down ones). Closing that properly means the
child's pty flavour riding the agent HELLO handshake, i.e. a protocol change.

## Summary

Found while fixing T423, which hit this mechanism as a special case. The general
form is a scrollback-integrity bug and is very likely user-visible: **narrowing a
Windows pane appears to be able to eat scrollback lines outright.**

## The mechanism, measured

Two facts that are each fine alone and destructive together:

1. **Ghostty's reflow refills a blank-bottomed viewport out of the scrollback.**
   Measured in a unit test (`session_notice.zig`, the `holdAbove` test): four
   lines of content folded into history, viewport blank, resize 64x20 -> 31x20,
   and the last two lines are back on the ACTIVE screen. That is reasonable
   terminal behaviour on its own — a narrower window shows more wrapped rows, so
   the viewport pulls content down to fill.
2. **A ConPTY child owns the viewport absolutely, and repaints all of it after
   every resize.** conhost re-renders its own screen buffer as absolutely
   positioned VT, opening with `ESC[H ESC[2J`. Anything sitting on the active
   screen that conhost does not know about is erased.

So rows that reflow moves history -> active are then erased by the child's
repaint. It is a MOVE, not a copy: those rows are gone from the scrollback too.

A ConPTY pane's viewport is mostly trailing blank rows almost all the time (a
shell paints a few lines into twenty), so condition 1 is not an edge case — it
is the normal state of every idle pane.

## Why T423 does not already cover it

T423 protects exactly one thing: the session-interrupted notice, via a tracked
pin on the row below it (`session_notice.holdAbove`, called from `Termio`'s
resize paths). A pin is the only handle that survives a reflow, which is why the
fix works — but it is a targeted guard for one block of text, not a general
answer. Ordinary scrollback has no pin.

## What to establish first

Do NOT start by writing a fix. Establish, on box, whether a user actually loses
scrollback:

- Fill a pane's scrollback with numbered lines (`for /l %i in (1,1,500) do @echo
  line %i`), scroll back and record what is there, drag the split divider to
  narrow the pane hard (or `+split` a sibling off it), then read the scrollback
  again with `+read --lines=600` and diff. Missing line numbers are the bug.
- Repeat under a shell that is NOT `cmd.exe` (pwsh, wsl, git-bash): the repaint
  behaviour is conhost's, so it should reproduce for all of them, but the
  measurement in `session_notice.zig` is cmd-specific and should not be
  generalised without checking.
- Try it on the local (Exec/ConPTY) path AND on a session-persistence pane
  (agent-owned ConPTY, `src/termio/Remote.zig`), which resizes over the wire.
- If it does NOT reproduce, say why in this file and close it — a mechanism that
  cannot be shown to hurt a user is not worth a fix, and the negative result is
  worth as much as the positive one.

## Candidate directions, if it does reproduce

- Do not refill the active area from history for a pane whose child owns the
  screen (the ConPTY case), i.e. treat "trailing blank rows" as the child's
  space rather than as reclaimable padding.
- Or defer/suppress the refill across a resize that the child is about to
  repaint anyway.

Both are terminal-core changes with reach well beyond Windows, so this needs a
design pass before code. Mac uses the same `Terminal`/`PageList` but a POSIX pty
whose child does NOT repaint on resize, which is likely why the Mac seat has
never seen it — worth confirming rather than assuming.
