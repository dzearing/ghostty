# T421 - Upgrade confirm shuts Ghoztty down and never brings it back - the user has to relaunch by hand

## Summary

**User report, 2026-08-03**, delivering T120: *"when i clicked upgrade, it shut
down. It did not reopen ghoztty like i expected. i had to manually rerun it."*

The upgrade's whole promise is that it swaps the binary and the user keeps
working. Shutting down and not coming back is worse than not upgrading: the
user is left staring at an empty desktop with no indication anything is
supposed to happen next, and no reason to believe the upgrade succeeded.

## Why this outranks the polish items filed alongside it

The four sibling tasks (T422–T425) are all about what the restored windows
*look like*. This one is about whether they come back at all. Nothing in
T422–T425 is observable if the app does not restart, so this is the first of
the five to fix.

It is also the second time this exact shape has cost the loop: T229 was
"confirming the mandatory upgrade dialog **kills the app**: the windows never
come back and the log stops mid-path". T229 is marked done. **Start by reading
T229 and establishing whether this is a regression of it, a second path to the
same end, or a different failure that merely looks the same** — the user's
click here went through the upgrade delivery (`scripts/upgrade-ghoztty-windows.ps1`
via `launch-upgrade.ps1`), which is not necessarily T229's in-app dialog path.

tombstone, so "zero sessions" and "tombstones exist" cannot both be simply
true. Resolve that contradiction before assuming either task's cause.

## What shipped (2026-08-03)

T229 attacked the CAUSE and could not reproduce it in four shapes; it has now
recurred. So this task takes the half the user actually feels — **the app comes
back** — and adds the one cause-side gate the evidence supports.

- **`relaunch_guard.zig` (new): the destructive window is supervised.** Before
  `restartForUpgrade`, the app writes
  `%LOCALAPPDATA%\ghoztty\agent-refresh[-debug].marker` and spawns a detached
  copy of itself carrying `GHOZTTY_RELAUNCH_GUARD=<pid>|<marker>|<exe>`. That
  copy is not a terminal: `main` asks `runRelaunchGuard` before any window, IPC
  endpoint or single-instance guard exists, so it can never be mistaken for a
  second instance. It holds the app's process handle; if the app ENDS while the
  marker is still there it starts the app again and removes the marker. A
  refresh that finishes (however it finishes) clears the marker and the guard
  exits quietly. Armed on **both** destructive callers — the confirmed one and
  the silent idle one — the same way T229 applied `beginAgentRefresh` to all of
  them.
  - Deliberate: the window is seconds wide (a user quitting deliberately is not
    fighting a relaunch); it relaunches **at most once** and the child does not
    inherit the variable, so no crash loop; a 10-minute cap means a guard whose
    app hangs still goes away; and **no `CREATE_NEW_PROCESS_GROUP`**, which is
    inherited by every descendant and would disable Ctrl-C in every pane of the
    relaunched app (T84).
  - An **environment variable, not a `+verb`**: the CLI surface stays identical
    on both platforms (CLAUDE.md's standing rule). The Mac half is **T427**.
- **The kill target is VERIFIED before it is killed** (`LocalAgent.terminateAgent`,
  was `terminateProcess`). The pid comes out of `port.json` — a FILE — and
  nothing gated it: not our own pid, not the image. Now it refuses its own pid
  outright, resolves the target's image with `QueryFullProcessImageNameW`, and
  refuses a pid that is not the agent. Unverifiable (query denied) proceeds out
  loud rather than breaking the refresh. Each step logs, so the next occurrence
  says which call it stopped in.
- **The match is on the STEM, as a prefix — and that is load-bearing.** A
  full-name match compiled, passed its unit tests, and **broke the shipping
  feature**: `upgrade-ghoztty-windows.ps1` cannot delete a running exe, so every
  delivery does `Move-Item ghoztty-agent.exe ghoztty-agent.exe.bak`, and by the
  time the app judges that agent stale its image path IS the `.bak`. A strict
  gate would have refused to replace any agent that had ever been upgraded past
  — i.e. all of them. **`agent-upgrade.ps1` arm I caught it** (it reproduces the
  same rename), which is the whole argument for keeping negative controls that
  model the delivery rather than the happy path.

## Evidence (2026-08-03)

- **`test\win32\relaunch-guard.ps1` (new) — ALL PASS, 18 assertions, exit 0.**
  Arm A is the user's report inverted: the app is killed with the marker present
  and a NEW app appears from the same exe and **answers `+list`** — measured as a
  terminal that exists, not as a spawn that returned success. Three negative
  controls guard against an always-relaunch bug: a cleared marker relaunches
  nothing (B), a disarm while the app lives ends the guard instead of leaving it
  to fire later (C), and a malformed spec starts nothing (D). Arm E asserts a
  guard binds no IPC endpoint.
- **`test\win32\agent-upgrade.ps1` — ALL PASS, 87 assertions, exit 0** (was 82),
  with arm H gaining H16–H20 — the only end-to-end coverage of the ARMING half:
  a real destructive refresh logs `relaunch guard: ARMED`, then `disarmed`,
  leaves no marker behind, and reports `pid N verified as '…ghoztty-agent.exe'`
  before terminating.
- **A harness leak fixed on the way past, and it is worth knowing about.** The
  same script, unchanged, went 85-passed/2-failed and then 49-passed/**33-failed**
  on the next run. Nothing about the code differed: arm I runs its agent from a
  COPY under the script's temp root, so its command line never says `zig-out` and
  `Stop-TestProcs`'s `*zig-out*` filter left it alive at exit. The agent pipe name
  is NOT namespaced by `GHOZTTY_PIPE_SUFFIX`, so the next run's app dialed that
  corpse instead of spawning its own and cascaded. `Stop-TestProcs` now matches
  the temp root as well. **A script that only passes on a clean box is not
  passing** — and the 33-failure run would have read as "T421 broke everything".
- **Unit tests** (win32 lane): `imageIsAgent` accepts the agent, its renamed
  `.bak`, and a relocated `GHOSTTY_LOCAL_AGENT_BIN`; refuses `ghoztty.exe`,
  `svchost.exe` and a name that merely ends in the agent's; `parseSpec` refuses
  every malformed spec; `shouldRelaunch` fires only on exited-with-marker.
- **Standing floor:** `zig build test -Dapp-runtime=none` exit 0, `zig build test
  -Dapp-runtime=win32` exit 0, `zig build test-agent` exit 0, P1/P2/P3
  ACCEPTANCE: ALL PASS.

## What is NOT fixed — read this before closing it out

**The cause of the death is still unknown.** The app exits inside a call that
cannot kill its caller unless the pid is wrong, and the pid-is-wrong hypothesis
is now blocked rather than confirmed: `port.json` on this box currently holds the
correct pid, so nothing shows it was ever stale. What this task guarantees is
that the user gets their terminal back, and that the NEXT occurrence names the
step it died in — `verified as`, `terminate returned` and the guard's own lines
now bracket every call in that window. **T426** carries the root cause.
