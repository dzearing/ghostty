# T421 - Upgrade confirm shuts Ghoztty down and never brings it back - the user has to relaunch by hand

## Summary

**User report, 2026-08-03**, delivering T120: *"when i clicked upgrade, it shut
down. It did not reopen ghoztty like i expected. i had to manually rerun it."*

The upgrade's whole promise is that it swaps the binary and the user keeps
working. Shutting down and not coming back is worse than not upgrading: the
user is left staring at an empty desktop with no indication anything is
supposed to happen next, and no reason to believe the upgrade succeeded.

## Why this outranks the polish items filed alongside it

The four sibling tasks (T422–T425) are all about what the restored windows
*look like*. This one is about whether they come back at all. Nothing in
T422–T425 is observable if the app does not restart, so this is the first of
the five to fix.

It is also the second time this exact shape has cost the loop: T229 was
"confirming the mandatory upgrade dialog **kills the app**: the windows never
come back and the log stops mid-path". T229 is marked done. **Start by reading
T229 and establishing whether this is a regression of it, a second path to the
same end, or a different failure that merely looks the same** — the user's
click here went through the upgrade delivery (`scripts/upgrade-ghoztty-windows.ps1`
via `launch-upgrade.ps1`), which is not necessarily T229's in-app dialog path.

## The log, read (2026-08-03 09:03:57 – 09:04:13) — this is NOT T229

Gathered in the filing turn, so start from here rather than from scratch:

```
09:03:57 pre-kill agent sessions: 0 ()
09:03:57 killing 2 release ghoztty process(es): 20552, 24484
09:03:57 swap attempt 1: ... being used by another process
09:03:58 exe swapped
09:03:58 SESSIONS-SURVIVE SKIP: no agent sessions before the kill
09:03:58 POST-SWAP VERIFY OK: ... now reports '4e5d62463'
09:04:00 resume decision: reuse (loop claude pid=13060 alive=True ...)
09:04:00 reuse: no running instance; starting the freshly installed exe
09:04:00 reuse: pane 6C13A7F3-... re-attached
09:04:13 RESUME-REUSE FAIL: the prompt did not arrive intact in pane ...
```

Three findings, and they point in different directions:

1. **The swap itself is fine.** `POST-SWAP VERIFY OK` at `4e5d62463`, confirmed
   independently afterwards — `ghoztty +version` on the installed release
   reports `4e5d62463`. The user's build IS current. So the failure is
   entirely in the come-back-afterwards half, not the delivery half. That
   already distinguishes this from **T229**, where the app died on a confirm.
2. **The script believed it restarted the app**: `starting the freshly
   installed exe`, then `pane … re-attached`. The user says it did not come
   back and they launched it by hand. So either it started and exited, or
   "re-attached" is reporting success on something weaker than a visible
   window. **That gap is the task**: `reuse:` logs an intent, and nothing
   verifies a window actually exists afterwards — the same
   *empty-rather-than-absent* failure shape this repo has hit repeatedly
   (T302's `PrintWindow`, T218's green-and-empty probes).
3. **`RESUME-REUSE FAIL` — the resume prompt never landed**, and this is the
   SECOND consecutive delivery to end that way (the same line at
   2026-08-02 11:30:01, for T60). Two in a row is not a flake. Note this is a
   *separate* failure from (2): it is about re-entering the loop, not about the
   app. It may deserve its own task once (2) is understood — the watchdog is
   the only thing that recovered either run.

**`pre-kill agent sessions: 0` is a lead for the siblings, not for this task.**
The agent held zero sessions going in, which would explain why the restored
panes had no banners, no recorded command and no cwd (**T422**, **T425**) —
there was nothing persisted to rehydrate FROM. But the user still saw the
"Session interrupted" notice, which is emitted only for a dead-but-relaunchable
tombstone, so "zero sessions" and "tombstones exist" cannot both be simply
true. Resolve that contradiction before assuming either task's cause.

## Evidence to gather first

- `%TEMP%\ghoztty-upgrade.log` for this delivery (2026-08-03 ~09:03, staging
  `4e5d62463`, pid 41416). The upgrade script logs each step; find where it
  stopped, and whether `UPGRADE OK` and the post-swap relaunch both ran.
- Whether the relaunch is the script's job or the app's, and what it does when
  the app it killed was the user's own foreground session.
- Whether the app came back and then exited, versus never starting — these have
  different causes and the log distinguishes them.

## Validation

An upgrade run end-to-end on this box that leaves the user's windows back on
screen without a manual launch, plus whatever assertion in
`test\win32\upgrade-staleness.ps1`'s neighbourhood can cover "the app is
running again after the swap" non-interactively.
