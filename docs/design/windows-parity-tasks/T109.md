# T109 — mixed-geometry ring replay / WP-D3 persisted snapshots on Windows

## Summary

Mixed-geometry ring replay → WP-D3 persisted snapshots on Windows — filed from T106 (2026-07-20). The ring concatenates segments drawn at different geometries (each attach resize appends a conhost fresh-paint at the new size); single-geometry replay is only faithful for its own segments (T106 anchors to the agent's last-drawn geometry — right for the stable common case). Endgame: persist a WP-D3 structured snapshot per pane (debounced, beside the T89f manifest) and attach at `attach_offset = snapshot offset` so no full-ring raw replay happens; folds in T106's evicted-head completion-lag caveat. T89i (2026-07-21) measured the user-visible cost: at the junction where the replayed block starts overwriting the restored pane's existing screen content, exactly ONE already-seen row is clobbered before it can scroll into scrollback (seq 6 lost in one run, seq 2 in another, none in a third — always inside the replayed pre-kill block, never in the dead-gap; the same junction truncates the replayed cmd banner mid-line). `session-persistence.ps1` D5 bounds it at one row and D5b guarantees zero loss in the dead-gap/post-attach region, so this fix's win is that last row. After publish readiness

## Details

Filed from T106 (2026-07-20). The agent's per-session ring is a
concatenation of segments drawn at DIFFERENT geometries: every ATTACH
applies the client's seed size to the ConPTY, and conhost appends a fresh
`ESC[H ESC[2J` + viewport repaint at each new size. A full-ring replay
parsed at any single geometry is faithful only for the segments drawn at
that geometry — content from other-geometry segments can fail to reach
scrollback before a later in-ring ED2 erases it. T106 anchors the replay to
the agent's LAST-drawn geometry (`Attached.replay_rows/cols`) — right for
the stable-geometry common case and proven by the visible-relaunch oracle —
but a ring spanning geometry changes (e.g. repeated relaunches at different
window sizes) remains lossy for its older segments (demonstrated by the
T106 repro's phase-B chain: visible-capture → minimized relaunch lost a
marker recorded two geometries earlier).

## What landed (2026-08-03)

The Mac WP-D3 design, on Windows, using the machinery that was already there.
Almost none of this was new logic — `Surface.sessionSnapshot` (the 600-row
structured VT repaint), `CoreSurface.RemoteBackend.restore_snapshot/offset`, and
the whole client side of `termio/Remote.zig` (paint-then-delta-attach,
`applied_bytes` tracking, the discard watermark) are platform-agnostic and were
built with the Mac apprt. Windows was simply not wired to any of it. The work
was the two ends:

- **Capture.** `session_layout.Leaf` gains `screen_snapshot` (base64) +
  `screen_snapshot_offset`. `App.captureLeaf` fills them from
  `core_surface.sessionSnapshot`, which already answers null for an exec pane, a
  surface that is not up yet, and a pane that has applied nothing — so that stays
  the one place that decides. The quit path already does a final full sync while
  every window is alive, so no Mac-style `syncAllTrackedNow` was needed.
- **Restore.** `App.restoreAttachOverride` base64-decodes the pair into a single
  App-owned scratch buffer and hands it down through
  `Surface.Overrides.Remote.restore_snapshot/offset` →
  `Surface.remoteBackend()`. One buffer, not one per leaf: the override is
  consumed synchronously by the surface construction that follows it, so the
  peak cost is one pane's screen no matter how many windows are rebuilt.

Two decisions worth keeping:

- **A budget, in the schema.** `SnapshotBudget` caps a pane at 256 KiB encoded
  and the whole file at 3 MiB, well under the 8 MiB `max_file_bytes` read
  ceiling. Without it a wide, heavily-styled pane could push the manifest past
  that ceiling, and the failure mode there is not "no snapshot" — it is a
  manifest that will not load at all, costing the user every window. A refused
  claim spends nothing, so one huge pane cannot starve the panes behind it.
  Asserted in the none lane (`SnapshotBudget` is pure arithmetic).
- **Snapshots are STRIPPED from the agent layout blobs.** A blob is a topology
  record, re-serialized and pushed on every layout mutation, and `blobHash`
  skipping unchanged windows is what keeps that mirror cheap — a snapshot
  changes on every capture, so every window would re-upload forever, at a
  hundred times the size. Cross-machine "Restore All" therefore still takes the
  full-ring path; that asymmetry is deliberate and is filed as **T413** rather
  than left looking accidental. **T412** carries the unmeasured half: a window
  frame change marks the layout dirty, so a drag now re-arms a per-pane VT dump
  every 250 ms and nobody has timed it.

An `attach: session=<sid> offset=<N> snapshot=<M>` line at info is part of the
change, not decoration. The two re-attach paths are indistinguishable from
outside — both end with a pane full of the right text — so without it the only
on-box way to tell a delta attach from a full-ring replay is to eyeball the
pane, and the acceptance script would have no oracle at all.

### Validation (on box, 2026-08-03)

`test/win32/session-snapshot-reattach.ps1` — **ALL PASS (27 assertions)**.
Hermetic (per-run `LOCALAPPDATA`, per-run agent bin, private pipe suffix), on a
background test desktop, and it only ever kills zig-out processes.

- A: a live agent-backed pane's manifest leaf carries a nonzero offset and a
  base64 blob that decodes to a real VT repaint **containing the marker the pane
  had just printed** (matched with CSI/OSC and whitespace stripped — a per-cell
  repaint shoots SGR through the middle of any word).
- B: the manifest still parses, still declares version 1, stays under 8 MiB, and
  the leaf still carries its session id and pane id.
- C: kill the app only (the agent keeps the PTY), relaunch, and the app's own
  log says `offset=N snapshot=M` with N equal to the offset the final on-disk
  manifest recorded and M equal to its decoded byte length — the delta path,
  proven against the exact bytes restore consumed. The pre-quit marker is still
  on the restored pane, and the restored pane goes on snapshotting at a
  non-decreasing offset.

`-NegativeControl` inverts C3 and scores **exactly one failure** on this build,
so the oracle discriminates: a build that silently fell back to the full ring
would still pass every content assertion.

`session-reattach.ps1` is the regression check for the restore path this
touches: unchanged at its documented **34 passed / 2 failed** baseline, both
failures the known T223 reds.

Floor: `zig build test -Dapp-runtime=none` exit 0, `-Dapp-runtime=win32` exit 0,
`zig build test-agent -j1` exit 0 (the plain lane still deadlocks — T409, which
now records `-j1` as a workaround), P1–P3 ALL PASS.

## Original analysis

The principled fix is the Mac WP-D3 design on Windows: the app persists a
structured screen+scrollback snapshot per pane (debounced, alongside the
T89f manifest) and re-attaches at `attach_offset = snapshot offset`, so the
agent gap-fills only the small `(offset, S]` tail and no full-ring raw
replay happens at all. The client-side machinery (restore_snapshot paint,
`applied_bytes` tracking, discard watermark) already exists in
`Remote.zig`/`connection.zig` — the Windows work is capturing/persisting
the snapshot + threading it through the restore Overrides. Also folds in
T106's completion-lag caveat (evicted ring head ⇒ late reflow-to-live).
Priority: after publish readiness — T106 covers the user-visible loss.
