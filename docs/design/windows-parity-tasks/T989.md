# T989 - Typing a long filter into the Activity Monitor panics the app

## In plain terms

Open the Activity Monitor, type a long line into its filter box, and the whole
terminal dies — every pane in every window, not just the panel. It takes about
130 typed characters, or fewer if you are typing a language whose characters
are not ASCII; a paste of a path or a pid list gets there in one action. Nothing
warns you and nothing is saved.

## Summary

`ActivityMonitor.onFilterChanged` (`src/apprt/win32/ActivityMonitor.zig:4254`)
reads the filter EDIT into a **256-unit UTF-16** buffer and converts it into a
**128-byte** destination:

```zig
var wbuf: [256]u16 = undefined;
const wlen: usize = @intCast(w32.GetWindowTextW(self.filter, &wbuf, wbuf.len));
const n = std.unicode.utf16LeToUtf8(&self.needle_buf, wbuf[0..wlen]) catch 0;
self.needle_len = @min(n, self.needle_buf.len);
```

`needle_buf` is `[128]u8` (line 760). The `catch 0` looks like it covers the
overflow and does not: `utf16LeToUtf8` does not RETURN an error for an
undersized destination, it `assert`s inside `utf8Encode`
(`std/unicode.zig:55`), which is `unreachable` in a Debug build and a silent
buffer overrun in a release one. The `@min` on the NEXT line is the clamp
somebody expected to be enough, and it runs after the write that already went
past the end.

So the destination has to be sized for what the source can hold, not for what
the author expected a filter to be: 256 UTF-16 units convert to as many as 768
UTF-8 bytes. Either the destination grows to match, or the source is truncated
to what fits (on a codepoint boundary, not a byte one) before the conversion.

## Evidence

Found while measuring capture flake for T943, on the Debug build at
c69c3ca4b. The panel's own stack, from the app's stderr:

```
thread 28056 panic: reached unreachable code
  std/debug.zig:559  assert
  std/unicode.zig:55  utf8EncodeImpl   <- assert(out.len >= length)
  std/unicode.zig:1030 utf16LeToUtf8Impl
  src/apprt/win32/ActivityMonitor.zig:4256  onFilterChanged
  src/apprt/win32/ActivityMonitor.zig:4567  wndProc
```

Reproduced deliberately afterwards: open the panel, post 130 `a` characters to
the filter EDIT, and the panic lands within two seconds. Below 128 bytes of
converted text nothing happens, which is what makes it look like a filter the
app simply does not like rather than a crash with a threshold.

Repro script kept out of the repo (it is one screen and this task's fix should
land its own acceptance arm instead):
`scratchpad/t943-crash-repro.ps1` in the T943 turn.

## Goals

- [x] A filter of any length the EDIT can hold leaves the app running —
      `needle_buf` is derived from the wide buffer now (`(filter_wide_cap - 1)
      * 3`), so nothing `GetWindowTextW` can hand back is even truncated, and
      the conversion is bounded whatever those two sizes become later
- [x] Non-ASCII text is truncated on a codepoint boundary, never mid-sequence —
      `utf16_text.toUtf8Truncating`, with unit tests over the two-byte,
      three-byte and surrogate-pair cases
- [x] `activity-monitor.ps1` gains an arm that types past the limit and asserts
      the app is still alive and the table still filters — section D2

## Validation criteria

- [x] The repro above (130+ characters into the filter) leaves the process
      alive with no `panic:` in stderr — D2 types 140 characters one WM_CHAR at
      a time and then asserts both, and the same arm run against the restored
      bug goes red on exactly those assertions
- [x] An arm in `test\win32\activity-monitor.ps1` covers the over-long filter,
      including a non-ASCII case, and is ALL PASS — `ACTIVITY MONITOR
      ACCEPTANCE: ALL PASS (157 assertions)`; the non-ASCII case pastes 300
      three-byte characters, the exact worst case the buffer is sized for
- [x] `zig build test -Dapp-runtime=win32` covers the truncation as pure logic
      (a unit test over the needle conversion, not through the window) — 9
      tests in `src/apprt/win32/utf16_text.zig`, proven to run in that lane by
      breaking one expectation and watching the lane report
      `apprt.win32.utf16_text.test.…` red
- [x] Floor lanes lib/none/win32/agent ALL PASS — `scripts\floor-lane.ps1
      -Lane all`
