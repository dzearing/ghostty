# T162 - Viewer selection toolbar (Copy) via shared selection.js on every page

## In plain terms

On the Mac, selecting text in one of Ghoztty's viewer panes (a rendered
document, or a website open in a pane) pops up a small floating toolbar with a
Copy button. On Windows that toolbar was already being delivered to every page
but nothing proved its Copy actually worked, and it also showed a Quote button
that had nowhere to send a quote yet. Now: select text in any viewer pane on
Windows, press the toolbar's Copy, and the text is on your clipboard — and the
dead Quote button stays hidden until the feedback feature it needs arrives.

## Goals

- [x] Copy from the selection toolbar lands the selected text on the system
      clipboard — on the bundled markdown/code template AND on a real website.
- [x] The Quote button is hidden on Windows v1 (nowhere to put a quote until
      T164), without forking the shared `selection.js`.
- [x] The proof runs on-box against a live WebView2, reading the clipboard
      back natively.

## Validation criteria

- [x] Shared-file discipline: `selection.js` stays a single copy — the
      hide-quote guard is additive and inert unless a host sets
      `window.__ghozttyHideQuote`; the win32 blob sets it and Mac does not.
      Verified by `viewer_bridge.zig` tests ("embedded VERBATIM" length check,
      new "T162: the hide-quote flag is set before the toolbar reads it") in
      the none lane — PASS 2026-08-07.
- [x] Select + Copy on the markdown template puts the exact passage on the
      system clipboard. Verified in the live win32-lane test ("host floor"),
      log: `copy[md]: toolbar report=copybar-md:1` then
      `copy[md]: clipboard=ghoztty copied this passage`.
- [x] Select + Copy on a REAL `http://127.0.0.1` page (not the template) does
      the same — the exact gap the user-script injection exists to close.
      Log: `copy[web]: toolbar report=copybar-web:1` then
      `copy[web]: clipboard=the quick brown fox`.
- [x] Quote is hidden: the live toolbar has exactly ONE button on both pages
      (the `:1` in both reports is the button count read from the real shadow
      DOM).
- [x] Standing floor: none lane PASS, win32 lane PASS, agent lane PASS
      (all via `floor-lane.ps1`, 2026-08-07), P1–P3 ALL PASS,
      `viewer-panes.ps1` 152 PASS + only the known pre-existing T538 failure
      (web-viewer cwd fallback; proven pre-existing 2026-08-06 by a
      reverted-sources control build, unrelated to this change).

## Details

The toolbar must work on ARBITRARY web pages, not just the bundled template.
Mac records why in a comment at `ViewerView.swift:429-439`: shipping it inside
`viewer.js` made it a `<script src>` in `viewer.html`, so it only ever ran on
the render template -- quoting worked on markdown and silently did nothing on a
website. It ships as a `WKUserScript` injected into every page, and its UI
lives in a shadow root so page CSS cannot restyle or hide it.

Scope (the injection plumbing itself lands in T90d; this task is the toolbar
and the proof it works off-template):

- `AddScriptToExecuteOnDocumentCreated` with ONE blob = the
  `window.webkit.messageHandlers` shim (P1) + `selection.js`, so their relative
  order is not a question.
- WebView2 injects into all frames; `selection.js` positions itself in viewport
  coordinates, so it must no-op unless `window.top === window` (Mac gets this
  from `forMainFrameOnly: true`).
- Copy puts the passage on the clipboard and flashes confirmation
  (`copySelection`, `flashCopied`).
- Quote: hide the button in v1 rather than wire a dead one. T164 un-hides it.
  Do NOT edit `selection.js` to delete it -- the shared file stays a single
  copy; suppress from the host side (or via a documented flag the shim sets).

*Validation:* `viewer-panes.ps1` grown -- select text in a markdown viewer and
in a REAL `http://localhost` page served by the test, press Copy, and read the
clipboard back both times. The website case is the whole point: it is the exact
gap the Mac user-script fix closed, so a script that only tests the template
would pass on the broken build.

## What landed (2026-08-07)

- `src/viewer/selection.js`: the Quote button is appended only when
  `window.__ghozttyHideQuote` is unset — additive, documented in-file, single
  copy preserved (Mac never sets the flag and keeps both buttons).
- `src/apprt/win32/viewer_bridge.zig`: new `hide_quote_js` line in the
  injected blob (set before `selection.js` runs); the verbatim-length test now
  includes it, and a new test pins the flag-name agreement + ordering so a
  drift on either side is loud. T164 removes this line to un-hide Quote.
- `src/apprt/win32/ViewerPane.zig`: the live "host floor" test grew a T162
  section — drives the REAL toolbar (selection → `mouseup` → press the last
  bar button through the open shadow root) on the template and on the loopback
  `http://` page, and reads the SYSTEM clipboard back natively
  (`GetClipboardData`). Two CDP calls (`Emulation.setFocusEmulationEnabled`,
  `Browser.grantPermissions` for clipboard-write) stand in for the focus and
  user-activation a real click brings and a hidden test window cannot; the
  user's clipboard is saved and restored around the section.

**Validation-home deviation, on purpose:** the original *Validation:* line
asked for `viewer-panes.ps1` growth, but an acceptance script can only drive
the CLI — it cannot select text in a page or press an in-page button, and the
GUI acceptance harness runs on a background desktop where real input is dead.
The T375 precedent already moved in-page bridge proofs into the live win32-lane
test; the Copy proof lives there for the same reason, with the clipboard as the
native oracle.
