# T732 - The four harness-rule audits have no single entry point, so a new acceptance script meets them one red run at a time

## In plain terms

The Windows test suite has four house rules about how a test script must report
itself. Each is enforced by its own analyzer and its own separate check, and
none of them runs as part of the normal test floor. So somebody adding a test
script today learns the rules by tripping over them one at a time, weeks apart,
if anyone happens to run the right check. This gathers them behind one command
that runs with everything else.

## Summary

Four harness-rule analyzers now live in `test\win32\lib\`, each with its own
acceptance script and its own stated-intent marker:

| Rule | Analyzer | Acceptance | Marker |
|---|---|---|---|
| Every launch declares its session persistence (T158) | `PersistenceSweep.ps1` | `persistence-flag.ps1` | `# persistence:` |
| No `Start-Process -PassThru` exit code read without caching `.Handle` (T197) | `ExitCodeAudit.ps1` | `harness-exitcode-audit.ps1` | `# exitcode-audit:` |
| A SKIP is named in the verdict line (T219) | `SkipAudit.ps1` | `skip-visibility.ps1` | `# skip-audit:` |
| A script that prints failure exits nonzero (T221) | `VerdictExitAudit.ps1` | `verdict-exit-audit.ps1` | `# verdict-audit:` |

Two problems, both discovered while adding the fourth (T221, 2026-08-11):

1. **No entry point.** The rules are documented as four separate paragraphs of
   CLAUDE.md prose. There is no README in `test\win32\`, and nothing that says
   "these are the rules a script in this directory follows". A new script
   author has to have read all four paragraphs to write a compliant script.
2. **None of them is in the floor.** The standing floor is the three zig lanes
   plus P1-P3. All four of these audits are pure, non-interactive and take a
   few seconds each - and none runs unless somebody remembers it by name. A
   rule whose check nobody runs is a rule only until the next script.

## Details

The likely shape is a single `test\win32\harness-audit.ps1` that runs all four
sweeps and prints one verdict, listing every finding grouped by rule - so the
answer to "does my new script follow the house rules" is one command. The four
existing acceptance scripts stay: each also self-tests its own analyzer against
fixtures and proves its own teeth, which a combined runner should not absorb.

Then wire it into the floor. `scripts\floor-lane.ps1` is about the zig lanes,
so the natural home is either a `-Lane harness` there or a line in go.md step 3
next to P1-P3. Prefer whichever makes it run without being remembered.

While there, consider a short `test\win32\README.md`: the four rules with one
sentence and one marker each, plus the two conventions every script in the
directory already follows (single ALL PASS / N FAILURE(S) last line; only ever
touch ghoztty processes running from the `-Exe` path).

## Validation criteria

- [ ] One command reports all four rules, with a single verdict line.
- [ ] It goes red when any one of the four is violated - one planted violator
      per rule, in the shape each analyzer's own teeth check already uses.
- [ ] It runs as part of the standing floor without being named by hand, and
      go.md step 3 says so.
- [ ] The four existing acceptance scripts still pass on their own.
