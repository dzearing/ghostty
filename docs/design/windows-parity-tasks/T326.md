# T326 - CLOSE_SESSION_RESULT can miss the 5s RPC budget: the agent terminates the child BEFORE it replies

Found 2026-08-01 by T318's Kill path, on box, against a real agent.

## The evidence (from the acceptance run's own log)

```
info(win32):    chooser roster: ending session id=49b8b0192b24b11ed4ccbfe96c1be060
warning(win32): chooser roster: close session failed err=error.Timeout
info(win32):    chooser roster: loaded 1 session(s)
info(win32):    chooser roster: close session confirmed=false
```

The close **worked** - the roster went 2 -> 1 and `ghoztty +sessions` stopped
listing that id - but `Connection.closeSession` (`connection.zig:2114`, bounded
at 5s by its caller) returned `error.Timeout`. The very next RPC on the same
connection (`requestSessions`) completed normally, so this is not a wedged link
or a correlation bug: the reply was simply LATE.

## Root cause (read, both ends)

`Server.handleCloseSession` (`src/remote/agent/server.zig:1102-1143`) does its
work in two phases and sends the reply LAST:

1. UNLINK under `store.mutex` (correct - it mirrors `handleClose`);
2. `freeUnlinked` OUTSIDE the lock: terminate the child, `persistMeta`,
   `reapLayouts` + `persistLayouts`;
3. only then `sendJson(.close_session_result, ...)`.

For a session with a LIVE child, step 2 is a process termination plus two disk
writes. On this box that exceeded 5s often enough that T318's acceptance had to
stop asserting on the confirmed answer at all.

## Why it matters beyond a log line

Today the only casualty is cosmetic (`killed_ok` is reported false in a log
line; the UI is driven by the refetch, deliberately). But `closeSession`'s
contract is *"returns the agent's ok (true => the session was closed)"* and
callers are entitled to believe it. Any future caller that gates behavior on the
answer - a Kill that reports failure to the user, a retry, a confirmation - will
be wrong on exactly the sessions that matter most (the ones with a live child).

## The fix (decide between two, do not do both by accident)

- **Reply first, reap after.** Send `CLOSE_SESSION_RESULT` as soon as the UNLINK
  makes the outcome KNOWN (`found`/`ok` are both decided by then), and do the
  terminate/persist afterwards. This is the honest fix: the answer does not
  depend on the teardown's duration. Check `handleClose`'s ordering at the same
  time - it has the same shape and may have the same latency.
- **Or budget for it**: raise the client timeout for this one RPC and document
  why. Weaker - it turns a correctness question into a tuning question - but it
  is a one-line change if the reordering turns out to be unsafe.

## Validation

- Agent unit (`zig build test-agent`): a close of a session with a live child
  replies within a bounded time that does NOT include the child's teardown -
  assert on ordering (reply observed before the child is reaped), not on a
  wall-clock number.
- On box: re-enable the assertion T318's `test/win32/chooser-sessions.ps1`
  dropped (`close session confirmed=true` after a Kill) and keep it green.
