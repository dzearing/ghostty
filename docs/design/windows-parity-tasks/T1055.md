# T1055 - A restored pane can hand a dead TUI's mouse-tracking agreement to a plain shell, so moving the mouse types garbage at your prompt

## Summary

Main intake of b723409c4 (upstream fix on origin/main, shared core). The persisted screen snapshot is serialized with every DEC mode that differs from default - mouse tracking and its SGR encoding included - but that snapshot is a picture of the PREVIOUS app run's grid. Between runs an agent restart can relaunch a session as a plain login shell, so repainting the snapshot hands a dead TUI's 'keep sending me motion reports' agreement to a shell, which reads every pointer move as typed input (35;106;15M... at the prompt, and 'command not found' when one carries a newline). Main's fix: the snapshot stops recording the INPUT-REPORTING modes (modes.isInputReporting: mouse tracking + encoding, focus events, bracketed paste, DECCKM/DECNKM, colour-scheme and in-band size reports) because those are an agreement with a process, not part of the frame; snapshots already on disk are neutralised with input_mode_reset right after they paint, gated on the grid_snapshot capability. Files: src/Surface.zig, src/remote/connection.zig, src/terminal/formatter.zig, src/terminal/modes.zig, src/termio/Remote.zig - all shared core, so this branch ships the defect. PARTIAL COVERAGE HERE: T824 already emits replay_mode_reset on the .rerun/.prompt relaunch paths (src/termio/Remote.zig:477), so the relaunch case is disarmed; the gap is the ALIVE RE-ATTACH path and the snapshot itself carrying the modes. Work: port the upstream change onto this branch, reconcile it with T824's replay_mode_reset so the two mechanisms do not double up, and add a win32 acceptance arm that restores a snapshot taken while a TUI had mouse tracking on and proves a pointer move produces no bytes at the prompt. Raise to P0 if the alive re-attach path reproduces on the box.
