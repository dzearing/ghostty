# T1338 - The download page's in-repo mirror goes stale after every release, so its harness is red until somebody notices

## In plain terms

The Ghoztty download page is published from a branch that the release job
edits directly: every release rewrites the three version numbers on the live
page so the download buttons point at the new build. The copy of that page
kept in this repo is not edited by anything, so the moment a release ships the
two disagree - and the test that exists to catch a hand-edit going unpublished
starts failing for a reason that is nobody's mistake. Nobody sees a broken
page; what breaks is the alarm.

## Goals

- [ ] A release leaves the in-repo mirror and the deployed page agreeing
- [ ] F1 of the download-page harness is red only for real drift

## Summary

`test\win32\website-windows-download.ps1` section F compares
`relay\deploy\ghpages\index.html` against `origin/gh-pages:index.html`. The
release path updates only the latter, so F1 goes red on every publish and
stays red until a turn happens to run that harness and re-sync by hand - which
is exactly what happened on 2026-09-04 during T1246, where the mirror was three
releases behind (1.36.3 against the deployed 1.36.6) in the version strings and
nothing else.

That makes a drift gate that cries wolf, which is the T1133 failure in
reverse: a check whose red is routine teaches every turn to clear it without
reading it, and the unpublished hand-edit it exists to catch would be cleared
the same way.

Two shapes worth weighing when this is picked up (mechanism, so this seat's
call rather than a decision): have the release job commit the same version
rewrite back to the mirror in the same run, or have the page derive its
version strings at load time from the GitHub releases API so neither copy
carries a version at all.

gap in the other direction).
