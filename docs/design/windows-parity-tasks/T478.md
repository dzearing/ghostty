# T478 - crash-catch reports ran clean for a binary that dies every run: its cdb filters are blind to STATUS_BREAKPOINT, the Zig panic exception

## Summary

Found under **T473**. `scripts/crash-catch.ps1` was pointed at the ReleaseSafe
test binary from **T477**, which panics on 10 runs out of 10 in ~11 seconds. It
reported:

```
crash-catch: attempt 1 ran clean in 17s
-- crash stack --
  no crash in 1 attempt(s) -- the program ran to completion (exit 0)
```

Run bare, the same binary exits `0x80000003` (`STATUS_BREAKPOINT`) every time.

**Cause:** `$script:FATAL_FILTERS` in `scripts/lib/CrashCatch.ps1` arms cdb on
`av`, `sov`, `ii`, `dz`, `c0000374` and `c0000409` — every access-violation-class
exception and nothing else. A Zig panic raises `int3`, which cdb *owns*: the
debugger consumes the breakpoint as its own, the script's `g` continues past it,
and the process is reported as having run to completion.

This is worse than a missing feature. A **false negative in the crash detector**
reads exactly like evidence of a fix — the failure mode T443's history is
already littered with — and any future turn that runs `crash-catch` against a
panicking binary will be told it is healthy.

## In plain terms

The tool the team uses to catch crashes has a blind spot: it recognises one
family of crashes and silently calls everything else a clean run. A program that
died every time it was tried was reported as having finished successfully. That
is the most expensive kind of bug in a diagnostic — it does not fail, it lies.

## Goals

- [x] `crash-catch` catches a Zig panic and produces a stack for it
- [x] When it genuinely cannot catch something, it says so — a run that ends
      with a nonzero exit code must never be reported as "ran clean"
- [x] A regression test proves both, using a deliberately panicking program

## Details

- The second goal is the important one and is the cheap one: whatever cdb can or
  cannot filter, `Invoke-CrashCatch` already knows the debuggee's exit code. Any
  nonzero exit with no captured exception should be reported as
  `UNCAUGHT (exit <code> -> <NTSTATUS decode>)`, not as clean. `CrashDiag.ps1`'s
  `Get-NtStatusCandidate` already decodes `0x80000003` and names it "Zig panic /
  segfault handler abort", so the decode exists and is simply not consulted here.
- For the first goal: cdb can be told to stop on a breakpoint exception it did
  not plant (`sxe bpe`, or arming `80000003` numerically), but it interacts with
  how the debugger plants its own breakpoints — treat "get a stack" as the
  research half and "never lie" as the shippable half.
- A related instance of the same class was fixed in `test-binary-soak.ps1` this
  turn: a single-candidate NTSTATUS decode was unrolled by PowerShell 5.1 into a
  bare object whose `.Count` is `$null`, so `$cand.Count -gt 0` was false and
  ten crashes in a row were filed as red tests. `[array]$cand = ...` fixes it.
  Check `CrashCatch.ps1`/`CrashDiag.ps1` for the same shape.

## Validation criteria

- [x] A tiny program that panics is caught by `crash-catch` with a symbolised
      stack — never reported as "ran clean". Verified: `test\win32\crash-stacks.ps1`
      section 4c builds `panic.zig`, checks the bare binary really does die with
      `0x80000003` first, then asserts `crash-catch` exits 1, names the exception,
      resolves `panic!inner` at `panic.zig @ 3`, and writes a dump.
- [x] A death the debugger cannot explain is reported as `UNCAUGHT` with the
      decoded exit code, and exits 3. Verified: section 5- against `exit26.zig`
      (`UNCAUGHT (exit 0x0000001A)`), plus the assertion that the text never says
      "ran clean" or "ran to completion".
- [x] "Ran clean" survives only as a positive observation of exit 0. Verified:
      section 4e's synthetic transcripts cover watched-exit-0, nonzero exit, a
      break nothing claimed, a truncated transcript and a missing one.
- [x] Arming `bpe` does not disarm the planted breakpoints DataBreak.ps1 depends
      on. Verified: section 4d runs a `bp0` command file and the panic capture in
      the SAME cdb session, and `test\win32\crash-databreak.ps1` ALL PASS.
- [x] `test\win32\crash-stacks.ps1` still passes: ALL PASS (54 assertions).
- [x] Floor green: `scripts\floor-lane.ps1 -Lane all`, P1-P3.

## What landed

- `scripts/lib/CrashCatch.ps1`
  - `bpe` joins `$FATAL_FILTERS`. That is the whole first goal: cdb owns `int3`,
    so with no filter registered for it the debugger consumed the Zig panic as
    its own break, `g` returned, and the script's next command (`q`) quit — a
    transcript with no crash block, which parsed as a clean run.
  - The cdb script now ends `g; .echo GHOZTTY-EXIT-BEGIN; .lastevent; …; q`.
    `.lastevent` is the only place the DEBUGGEE's real exit code exists: cdb's
    own exit code is 0 whenever `q` killed a still-live debuggee, which is
    exactly the number that made a panicking binary look healthy.
  - `Read-CrashCatchLog` gained `ExitObserved` / `DebuggeeExitCode` / `LastEvent`
    / `Uncaught` / `UncaughtDetail`. "Ran clean" is now a positive observation —
    it requires having WATCHED the debuggee exit 0 — and everything else
    (nonzero exit, unclaimed break, transcript truncated by a timeout kill, no
    transcript at all) is `Uncaught`.
  - `Format-DebuggeeExitCode` decodes the full 32-bit code EXACTLY, so a plain
    `exit(5)` is not announced as an access violation the way CrashDiag's
    low-byte table would have to (through `zig build` the top bits are already
    gone, so that table has no choice; here they survive).
  - An uncaught attempt keeps its transcript and stops the attempt loop, the
    same way a caught crash does.
- `scripts/crash-catch.ps1`: new exit **3** = UNCAUGHT, distinct from 0 (clean)
  and 1 (crash captured).
- `scripts/guard-due.ps1`: a `crash-stacks` row (nothing tied a `CrashCatch.ps1`
  edit to the harness that tests it — which is how this blind spot lived a
  month), and `CrashCatch.ps1` added to `crash-databreak`'s coverage, since
  DataBreak plants its breakpoints through `New-CdbScript`.
- `test/win32/crash-databreak.ps1` now stamps its own guard. It had a row and no
  stamp, so it could only ever go green by somebody running `guard-due update`
  by hand — the remembering T783 exists to remove.

## Measured before/after

Same binary (`@panic("deliberate boom")`, dies `0x80000003` on every run):

```
before:  crash-catch: attempt 1 ran clean in 0s
         no crash in 1 attempt(s) -- the program ran to completion (exit 0)

after:   0x80000003 Break instruction exception at panic!abort+0xe
         | panic!inner+0x23 [panic.zig @ 3]
         | panic!main+0xf   [panic.zig @ 6]
```
