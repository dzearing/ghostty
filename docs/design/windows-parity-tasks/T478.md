# T478 - crash-catch reports ran clean for a binary that dies every run: its cdb filters are blind to STATUS_BREAKPOINT, the Zig panic exception

## Summary

Found under **T473**. `scripts/crash-catch.ps1` was pointed at the ReleaseSafe
test binary from **T477**, which panics on 10 runs out of 10 in ~11 seconds. It
reported:

```
crash-catch: attempt 1 ran clean in 17s
-- crash stack --
  no crash in 1 attempt(s) -- the program ran to completion (exit 0)
```

Run bare, the same binary exits `0x80000003` (`STATUS_BREAKPOINT`) every time.

**Cause:** `$script:FATAL_FILTERS` in `scripts/lib/CrashCatch.ps1` arms cdb on
`av`, `sov`, `ii`, `dz`, `c0000374` and `c0000409` — every access-violation-class
exception and nothing else. A Zig panic raises `int3`, which cdb *owns*: the
debugger consumes the breakpoint as its own, the script's `g` continues past it,
and the process is reported as having run to completion.

This is worse than a missing feature. A **false negative in the crash detector**
reads exactly like evidence of a fix — the failure mode T443's history is
already littered with — and any future turn that runs `crash-catch` against a
panicking binary will be told it is healthy.

## In plain terms

The tool the team uses to catch crashes has a blind spot: it recognises one
family of crashes and silently calls everything else a clean run. A program that
died every time it was tried was reported as having finished successfully. That
is the most expensive kind of bug in a diagnostic — it does not fail, it lies.

## Goals

- [ ] `crash-catch` catches a Zig panic and produces a stack for it
- [ ] When it genuinely cannot catch something, it says so — a run that ends
      with a nonzero exit code must never be reported as "ran clean"
- [ ] A regression test proves both, using a deliberately panicking program

## Details

- The second goal is the important one and is the cheap one: whatever cdb can or
  cannot filter, `Invoke-CrashCatch` already knows the debuggee's exit code. Any
  nonzero exit with no captured exception should be reported as
  `UNCAUGHT (exit <code> -> <NTSTATUS decode>)`, not as clean. `CrashDiag.ps1`'s
  `Get-NtStatusCandidate` already decodes `0x80000003` and names it "Zig panic /
  segfault handler abort", so the decode exists and is simply not consulted here.
- For the first goal: cdb can be told to stop on a breakpoint exception it did
  not plant (`sxe bpe`, or arming `80000003` numerically), but it interacts with
  how the debugger plants its own breakpoints — treat "get a stack" as the
  research half and "never lie" as the shippable half.
- A related instance of the same class was fixed in `test-binary-soak.ps1` this
  turn: a single-candidate NTSTATUS decode was unrolled by PowerShell 5.1 into a
  bare object whose `.Count` is `$null`, so `$cand.Count -gt 0` was false and
  ten crashes in a row were filed as red tests. `[array]$cand = ...` fixes it.
  Check `CrashCatch.ps1`/`CrashDiag.ps1` for the same shape.

## Validation

- A tiny program that panics is caught by `crash-catch` (or, failing that, is
  reported as `UNCAUGHT` with the decoded NTSTATUS) — never as "ran clean".
- `test\win32\crash-stacks.ps1` still passes.
