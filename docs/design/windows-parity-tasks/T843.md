# T843 - Every other pixel probe still photographs chrome through the capture that tears

## Summary

T835 proved the harness's default capture is the problem, not the banner: PrintWindow(PW_RENDERFULLCONTENT) asks DWM for an asynchronous copy of a layered window's composited surface, and three back-to-back captures of one unchanged overlay put the same row's ink at 1062, 1283 and 1179 px. Only pane-banner.ps1 was converted (BannerOverlay answers WM_PRINTCLIENT, its probes pass -Sync). 65 other Get-TestWindowPixels call sites across 34 acceptance scripts - tab strip, caption bar, menus, chooser, split dim, remote pill, hero mode - still take the torn photo, so every one of them can go red on a correct build or, worse, green against a frame that was never painted. Work: give each probed chrome window a WM_PRINTCLIENT handler that calls its existing paint, switch its probes to -Sync, and re-run each script several times to confirm the flake is gone. Where a window cannot answer (a control we do not own, e.g. the RichEdit composer in ViewerFeedbackBar), say so in the script rather than leaving the default capture unremarked.
