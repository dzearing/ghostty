# T877 - test-binary-soak counts a CrashDiag-confirmed test-binary crash as a plain FAIL (crash=0) when the lane dies by exit code alone

## In plain terms

The test-repeat harness is the instrument we use to measure how often the
intermittent "ghost" crash fires. On 2026-08-15 it watched a run crash — its
own log even printed a crash-diagnostics block naming the dead test process —
and then reported "0 crashes" in its summary line. An instrument that
undercounts the one thing it exists to count silently biases every rate the
crash hunt records.

## Goals

- [x] A run whose log carries floor-lane's own decoded crash verdict counts as
      a crash, not a red test
- [x] A crash in one of the background load workers is counted and named
- [x] A soak no longer destroys the previous soak's worker evidence
- [x] A genuinely red test still reads as a red test

## Summary

During the T857 boost-on baseline (`test-binary-soak.ps1 -Lane none -Runs 15
-LoadWorkers 4 -LoadKind build -NoCatch -Label t857-boost-on-eve`, 2026-08-15
22:07), run 4 died in 5s: `ghostty-test.exe` exited with code 3 while executing
`font.Collection.test.add full`, and the per-run soak log
(`%TEMP%\ghoztty-soak\t857-boost-on-eve-20260815-215634-04.log`) contains the
full floor-lane crash-diagnostics block — `CRASH 22:07:14 ghostty-test.exe
pid=0xE570 0x80000003 STATUS_BREAKPOINT ... in ghostty-test.exe+0x2a896c0`
(= `TT_Load_Simple_Glyph+0x510`). The soak's verdict line still said
`pass=14 fail=1 crash=0  crash-rate=0/15 (0%)`.

So the soak's crash classifier does not recognize this occurrence shape: a
test binary killed by exit code alone (zig's `exited with code 3`, no
`Segmentation fault`/`panic:` text in the lane output — the handler abort text
was absent this time), even though floor-lane's own CrashDiag block already
decoded it as a crash. T443's unblock rule explicitly names "a red lane whose
CrashDiag block names one of our test binaries" as an occurrence; the
instrument built to count occurrences must use the same definition.

Fix direction: classify a run as `crash` when the floor-lane output contains a
`-- crash diagnostics --` block whose CRASH line names a test binary (or when
zig reports one of our test exes exiting with a code that decodes to an
NTSTATUS abort: 3 = 0x80000003, 5 = 0xC0000005), not only when handler text
appears. Keep plain assertion-failure reds (runner reports `N failed`, process
exits cleanly) as `fail`.

**Second gap, same instrument, found the same night**: `-LoadKind build`
workers each run a full `zig build test` lane, so a worker iteration can BE an
occurrence — and one was (2026-08-15 22:41:46, worker w3, segfault + recursive
panic in `terminal.formatter.test.PageList plain spanning two pages`, exit 5).
Worker logs are never crash-scanned, worker crashes appear in no verdict line,
and each new soak deletes and recreates `D:\ghoztty-soak-load\w*`, destroying
the previous soak's worker evidence — block 1's 32 iterations and the midday
probe's 41 are now unscannable. Fix: scan worker logs for the same crash
signatures at soak end, report `worker-crash=N` in the summary line, and
timestamp the worker dirs (or move logs aside) so a later soak does not
destroy an earlier soak's evidence.

## Validation criteria

- [x] A soak run whose lane log carries a CrashDiag CRASH line naming a test
      binary is counted in `crash=` (unit/acceptance coverage in
      `test\win32\test-binary-soak.ps1` with a fixture log).
      *How: section 3a of `test\win32\test-binary-soak.ps1` -- fixture lane
      `diagcrash.cmd` reproduces the block; "a CrashDiag-confirmed death with no
      handler text is CRASH, not FAIL" asserts `crash=1` in the summary line.
      Negative control in the same section: a CRASH line naming
      `SomeOtherApp.exe` leaves the round `fail=1 crash=0`, because
      `Write-CrashDiagnostic` reports every crash in the window, not only ours.*
- [x] A load-worker iteration that crashes is scanned, counted, and named in
      the summary (`worker-crash=N`), and a following soak no longer destroys
      the previous soak's worker logs.
      *How: section 3d of the same script -- a crashing `-LoadCommand` fixture
      gives `worker-crash=1` plus a `w0: <evidence>` + log-path line; a clean
      one gives `worker-crash=0` (the field is never omitted); and the second
      soak's `wclean-*` directory leaves the first soak's `wcrash-*\w0\worker.log`
      readable, still holding its `Segmentation fault` line.*
- [x] A plain red test (runner-reported failure, clean process exit) still
      counts as `fail=`, not `crash=` (negative control in the same script).
      *How: the pre-existing `brfail` fixture still asserts `pass=0 fail=1
      crash=0`, and the classifier unit checks assert that `exited with code 1`
      and `(expected exited with code 0)` are not occurrences.*
- [x] The 2026-08-15 22:07 occurrence shape (exit 3, no handler text,
      CrashDiag block present) reproduced against the classifier as a fixture
      and classified `crash`.
      *How: twice. As a fixture lane (`brdiag`, above), and against the REAL
      artifact -- all 15 logs of
      `%TEMP%\ghoztty-soak\t857-boost-on-eve-20260815-215634-*.log` run through
      `Get-CrashOccurrenceLine`: run 04 classifies CRASH (`error: while
      executing test 'font.Collection.test.add full', the following command
      exited with code 3`), the other 14 classify clean. So that soak's true
      verdict was `pass=14 fail=0 crash=1  crash-rate=1/15 (7%)`, not
      `crash=0`.*
