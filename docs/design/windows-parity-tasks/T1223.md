# T1223 - A build that goes red and is pushed past before it finishes is never asked about again

## Summary

T1219 made the turn read CI, but it asks exactly one question: what did the
build machine conclude about the commit this branch is sitting on? A run that
is still in progress at claim time is reported and passed, on the reasoning
that the NEXT turn's claim will ask about it. That holds only while the head
sha stops moving - and it does not stop moving. A short turn (a tracker-only
commit, a doc fix) pushes a new sha before the previous run finishes, and the
older run's conclusion is then the answer to a question nobody asks again.

## In plain terms

The loop now notices when the build says the branch is broken. It only asks
about the very latest commit, though - so if a build fails a few minutes after
the next piece of work has already been pushed, the failure is quietly skipped
over, which is the same silence this was supposed to end.

## Goals

- [ ] A red run is noticed even if the branch head moved past it before it
      finished.
- [ ] No new noise: a red run that a later green run on the same code has
      already answered stays quiet.
- [ ] Demonstrated red (go.md's rule), in section E of
      `test\win32\gate-negatives.ps1` alongside the T1219 assertions.

## What to work out

The shape that probably fits: ask about the head sha as now, and ALSO about
any completed red run on this branch newer than the last one the loop
acknowledged - a small watermark next to the lock (`temp\go-loop.ci.json`),
holding the newest run id already reported. A red run below the watermark is
history; a red one above it is news exactly once. That keeps the gate from
re-reporting the same failure every turn while closing the skip-over hole.

Open questions worth settling with evidence rather than taste:

- Does a red run on a sha that a LATER sha's run then passed still deserve to
  fail the gate? (Probably reported, not failed - the code it condemned is no
  longer what the branch has.)
- Does the watermark belong next to the lock, where a fixture `-Repo` run
  cannot touch the real one, like the stranded snapshot does?

## Validation criteria

- [ ] With a fixture payload where the head sha's run is green and an older
      sha's run is red, the gate reports the older failure once.
- [ ] ...and does not report it a second time on the following claim.
- [ ] A red run already superseded by a green run on later code does not fail
      the commit gate.
- [ ] Section E of `test\win32\gate-negatives.ps1` demonstrates each of the
      above red, and `-NegativeControl` still scores exactly one failure.
