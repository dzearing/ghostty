# T1173 - A running watchdog never re-read its own source, so the stop check added yesterday sat inert for a day while it kept reviving the loop

## Summary

User report 2026-08-24: 'something keeps restarting the go loop, can you stop that'. Measured: the graceful stop was armed 2026-08-23 15:26 and the loop itself obeyed it - the last turn commit is 2026-08-23 15:57 and nothing has run since. What did not obey it was the watchdog. %TEMP%\ghoztty-go-loop-watchdog.log shows 're-entering: no live loop pane, opening a new window (state=free, remaining=370)' every 20 minutes for a full day, and the cause is that the watchdog PROCESS had been running since 2026-08-18 18:16. PowerShell reads a script once at start, so the stop check added to Invoke-Tick the previous afternoon was on disk and not in that process. Nothing anywhere reported that the running copy was stale - the log looked like a healthy watchdog doing its job. Fixed by making the supervisor watch its own source: it hashes go-loop-watchdog.ps1 and loop-session.ps1 at start (SHA256, not mtime, because git pull rewrites mtimes on unchanged files) and re-execs when the bytes change, releasing the single-instance mutex first so the replacement can take it. The mutex wait now retries for five seconds instead of failing instantly, so the parent-to-child handoff cannot leave the box with no watchdog at all. Verified live: the running watchdog picked up an edit at 16:09:38 and re-executed itself. Also covered by test\win32\go-loop-guard.ps1 section X (X1-X11): stop/claim exit 4/resume, health reporting STOPPED with exit 3 rather than DOWN, the watchdog refusing to re-enter while a stop is pending, and a running watchdog re-execing on a source change with the replacement process proven alive.
