# T1425 - Sign-out discards the machine instead of suspending it

## In plain terms

Signing out now correctly takes this machine off your account (T1421). Signing
back in with the same account does not put it back. Your own computer vanishes
from the machine list on all your other devices and stays gone until you go and
re-enroll it by hand — which most people will not know is a thing they can do.
Signing out and back in should leave you where you started.

## Goals

- [x] Sign-out remembers the machine's name and relay (no secret — the credential is dead by then)
- [x] Signing back in with the SAME account re-enrolls the machine and writes the fresh credential to relay.env
- [x] A running `ghoztty-agent` adopts the new credential without a restart (the relay.env watcher already does this — verify it)
- [x] A DIFFERENT account never inherits the suspended machine
- [x] Restore is refused across relays
- [x] A transient re-enroll failure is retried at the next launch while signed in, not stranded until another sign-out/in

## Summary

Split out of T1421. This is the "suspends rather than discards" half of main's
`0c3a19764`, plus two of `f3b1e5fb5`'s corrections:

- **Signing back in must not cancel a pending revocation on an email match
  alone.** If the revocation had in fact landed, that leaves a dead token in
  relay.env, the machine out of the account, and nothing left to notice. The
  cancel re-checks the credential: confirmed alive cancels, confirmed dead drops
  the file and re-enrolls, and an unanswerable relay stays armed rather than
  guessing.
- **The restore is retried at every launch while signed in**, not only at
  sign-in (the Mac renamed `restoreForSignIn` to `restoreEnrollment` for exactly
  this reason).

Depends on T1424 because the pending-revocation record and the suspension record
are the same state machine seen from two ends, and getting them right separately
is how the Mac seat produced the bug where a machine was discarded outright.

Relevant Windows pieces: `src/remote/relay_signin.zig` (`signOut`,
`signIn`), `src/remote/relay_revoke.zig` (the pure rule), the enroll driver in
`src/remote/agent/enroll.zig`, and `src/remote/agent/relay_creds.zig`'s watcher,
which is what adopts a rewritten relay.env within one tick.

## Validation criteria

- [x] A unit test: same account restores, different account does not, different relay is refused — `restoreAction` / `pendingAction` / `enrollName` in `src\remote\relay_suspend.zig`, green in both lanes
- [x] Sign out then back in on this box, and the machine reappears in another client's list under its old name — section 10 of `test\win32\relay-account.ps1`: the record keeps `E2E-Box`, the sign-in POSTs `/v1/client/devices`, relay.env comes back with the FRESH token
- [x] The running agent adopts the fresh credential without a restart — `relay_creds.zig`'s own `watcher: relay.env token change is adopted and bounces the link`, green in the agent lane
- [x] A restore that fails transiently is retried at the next launch — section 10b: dead port leaves the record ARMED and enrolls nothing; the next launch with the port answering completes it
- [x] `scripts\floor-lane.ps1 -Lane all` green — lib/none/win32/agent all PASS
