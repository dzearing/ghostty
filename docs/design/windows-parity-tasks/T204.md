# T204 - Tab strip glyphs are text characters in left-aligned boxes, not icon buttons

## Summary

Third part of the user's 2026-07-30 report (geometry **T202**, color **T203**).
Directly names this:

> "a weird hamburger button which is misaligned from the x button"

The observation is exact. The three strip controls - close, new-tab, menu -
are drawn as **text characters**, each `DT_LEFT` inside a differently-sized
box, with no shared button model. They cannot line up, because nothing in the
code ever asks them to.

## Root causes (verified by reading, line numbers at HEAD)

All in `drawTabBar`, `src/apprt/win32/Window.zig`:

1. **Every glyph is horizontally LEFT-aligned in its own box.** The close "x"
   uses `DT_LEFT` (line 2842), the "+" uses `DT_LEFT` (line 2902), and the
   menu glyph follows the same pattern. `DT_CENTER` is used nowhere. Each
   glyph therefore sits against the left edge of its box, and since the boxes
   differ in width (close 20 DIP, new-tab 36 DIP, menu `menuButtonWidth()`),
   the glyphs land at three unrelated x positions. This is the misalignment.

2. **The vertical boxes disagree too.** The close button is boxed to
   `close_y_center +/- close_btn_w/2` - a 20 DIP tall box centered in the bar
   (lines 2831-2836) - then `DT_VCENTER`'d inside THAT. The "+" and menu glyph
   are `DT_VCENTER`'d inside the FULL bar height (lines 2891-2896). Two
   different vertical reference frames for controls sitting side by side.

3. **They are literal text, not icons.** Line 2830 uses U+00D7 MULTIPLICATION
   SIGN as the close glyph and line 2890 an ASCII "+". These are text
   characters from the UI text font: wrong weight, wrong optical size, and
   wrong metrics next to real system chrome. Windows draws these from **Segoe
   Fluent Icons** (Windows 11) / **Segoe MDL2 Assets** (Windows 10):
   ChromeClose `U+E8BB`, Add `U+E710`, GlobalNavButton `U+E700`.
   CAVEAT, and the reason this is not a one-line change: T172 deliberately
   chose GDI-DRAWN glyphs for the chooser's machine icons because a missing
   symbol font renders as tofu. Segoe Fluent Icons ships with Windows 11 and
   MDL2 with Windows 10, so an icon font is defensible here - but it needs a
   real presence check with a drawn fallback, and the decision should be
   recorded alongside T172's so the two are consistent rather than accidental.

4. **There is no shared icon-button abstraction.** Each control open-codes its
   own rect, hover fill, glyph and hit test, and the close button's hover fill
   is missing entirely (only its glyph changes color, to red - lines
   2824-2827). Windows chrome buttons show a rounded ~4 DIP fill on hover and
   a distinct pressed state; ours have neither shape nor press feedback.

## Sizing (user follow-up, 2026-07-30, with a Windows Terminal reference shot)

> "the hamburger icon is too small and doesn't horizontally align under the X
> above it, icons still feel too small"

Two separate things, and only the first belongs to this task:

- **Too small** is this task. The glyphs are rendered in the TAB TITLE font
  (T78's `window-title-font-family`, ~9pt => ~12 px), so they are text-sized,
  not chrome-sized, and `close_btn_w` is a 20 DIP box that constrains the
  close glyph further. Windows chrome draws these at a **16 DIP glyph in a
  square target of at least 32 DIP**, with all three controls the SAME target
  size. Decouple glyph size from the title font entirely - the icon font is
  selected and sized independently of whatever the user set the tab font to.
  Revisit `close_btn_w` (20) against the "+"/menu `btn_w` (36) in
  `tab_strip_layout.zig`: they should not differ.
- **Does not align under the X above it** is NOT this task and cannot be
  fixed here - that X is the WINDOW's caption close button, on a separate
  titlebar row above the strip. Filed as **T205** (integrated titlebar).
  Aligning a strip button under a caption button by hand would be a fudge
  that breaks at the next DPI or caption-width change; T205 removes the
  second row instead, which is what the reference screenshot actually shows.

Verify all numbers on the box against live Windows Terminal rather than
trusting the ones written here.

## Deliverables

1. One small icon-button helper (rect, glyph, hover/pressed fill, hit test)
   used by all three controls, so alignment is structural instead of
   coincidental. This is what makes the user's complaint un-reproducible by
   construction.
2. Square hit targets of the same size, glyphs CENTERED on both axes in a
   single shared vertical frame.
3. Segoe Fluent Icons with an MDL2 fallback and a drawn last resort; record
   the decision against T172's.
4. Rounded hover fill plus a pressed state for all three.
5. Verify hit rects still match the painted rects - `tab_rects`,
   `new_tab_rect` and `menu_btn_rect` feed the mouse handlers at
   `Window.zig:3146+`, `3263+` and `3474+`, and moving the paint without
   moving those is exactly how a button becomes visually right and
   unclickable.

## Validation

- Extend `test/win32/tab-strip.ps1`: assert the three glyph bounding boxes
  share a common vertical center within 1 px, that each glyph is centered in
  its own box, and that hover produces a fill (not only a color change) on
  each of the three.
- Click-through test at the painted center of each control, proving paint and
  hit test still agree - the specific regression this change risks.
- Negative control mandatory.
- Regressions: `keybinds-t01.ps1`, `menu-bar.ps1` (T190's script, if that is
  its name - the menu button is its entry point), both lanes, P1-P3.

## What T202 already landed (read before starting)

T202 shipped before this task, so some of the ground here is already prepared:

- The geometry is a pure module, src/apprt/win32/tab_strip_layout.zig, with
  `Metrics` (every DIP constant), `closeRect`/`titleRect` (the close box
  is now ONE definition shared by the painter and both hit tests, not three
  copies), `buttonFillRegion` (the rounded hover fill, already inset and
  already used by both the "+" and the menu button), and `chicletRegion`.
  Deliverable 1's "one icon-button helper" should extend that module rather
  than start a new one.
- The **right-edge padding defect is already fixed** — `strip_pad_r` exists,
  the menu button is inset from the client edge by the same 4 DIP the first
  tab gets on the left, and both the layout unit tests and
  `test/win32/tab-strip.ps1` assert it. Do not redo it here.
- What is still open and IS this task: all three glyphs are still drawn with
  `DT_LEFT` in `paintTabBar` (the close "×" and the "+"; only "≡" uses
  `DT_CENTER`), which is the visible misalignment the user named. The boxes
  are correct now; the text inside them is not.
- `test/win32/tab-strip.ps1` exists with 18 assertions and a working
  negative control (`T202_NEUTERED` in the layout module) — extend it.
- The measured visual target is `docs/design/win32-tab-strip.md`.
