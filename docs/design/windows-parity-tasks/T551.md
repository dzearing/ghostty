# T551 - activity-monitor.ps1 section I: row click occasionally selects nothing (selected=0)

## Summary

During T291 validation (2026-08-06), one run of `test/win32/activity-monitor.ps1`
failed `I clicking a row selects exactly one (selected=0)` while the other three
runs that day passed it. The failing run was the negative-control build, which
had just spawned a delegated Windows Terminal host — so extra processes were
appearing in the table around the time of the click.

## In plain terms

The automated test for the Activity Monitor sometimes fails at the step where
it clicks a row in the process table: the click lands, but nothing ends up
selected. It is rare, and it is a test problem, not something a user has
reported — but a test that cries wolf once in a while trains people to re-run
it instead of trusting it.

## Details

Likely mechanism: section I locates the first row's Y coordinate by probing
pixels (`Get-TestFirstRowY`), then clicks it. The table live-polls and
re-sorts every ~1s, so a row list that changes between the probe and the click
can move a row boundary under the click point — clicking a divider or a
different row's edge could yield no selection change. The T291 negative run
made this worse (a new OpenConsole process entering/leaving the table while
sorted by pid ascending), which supports the moving-table theory.

Candidate fix: after sorting by pid ascending, re-probe the row Y immediately
before the click (single atomic probe+click), or retry the click once when
`selected=0` comes back, or pause the panel's polling during the click (if a
test hook exists).
