# T842 - zig build against a FRESH private global cache is unreliable on this box - one run died 0xC0000005 in 4s, another failed in zig rc

## Summary

Filed from T840, where a load worker was first designed to build with a FULLY
private cache (`--cache-dir` + `--global-cache-dir` + `--prefix` all its own).
Two attempts, two different failures, on a box where the same command against
the shared global cache builds fine:

- `zig build test -Dapp-runtime=none --cache-dir <priv> --global-cache-dir
  D:\ghoztty-soak-load-test\probe\zg --prefix <priv>` → `error: zig rc exited
  with code 3` compiling
  `…\zg\p\N-V-…\src\base\ftver.rc:1:1` (freetype's resource script), reported
  as `error(compilation): zig rc failed with stderr:` with the stderr body
  empty.
- The same shape at a shorter path (`D:\zsl\g3`) → the process died with
  **0xC0000005 after 4 seconds and an empty log**; an immediate re-run of the
  identical command then compiled normally for 180s+.

Neither is on the critical path today — T840's build load shares the populated
global cache deliberately, which is both more representative and reliable — so
this is recorded rather than chased. It matters if anything later needs a truly
isolated build (a second seat on this box, a clean-room reproduction, a bisect
harness), because "build it somewhere private" is the obvious tool and it is
not currently trustworthy here.

## Details

Worth checking before spending real time: whether a fresh global cache forces
the third-party deps (freetype, harfbuzz, dcimgui) to be rebuilt from fetched
sources — the shared cache never does, which is exactly why the failure is
invisible in normal use — and whether the `zig rc` step is path-length or
antivirus sensitive. The 4-second access violation with no output smells like a
crash inside zig's own cache setup rather than a compile error, and would want a
`crash-catch.ps1` run to say anything more.
