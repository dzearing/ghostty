# T561 - activity-monitor.ps1 section J: the banner dismiss-glyph click is a pixel-timing flake (failed once, passed on re-run)

## In plain terms

One of the automated checks for the Activity Monitor is unreliable: it clicks
the little "x" that closes the error strip along the bottom of the panel and
then looks to see the strip is gone. Roughly half the time it reports a
failure even though a person doing the same thing sees the strip close. The
feature works; the check does not, and a check that cries wolf is worse than
no check, because the next real failure gets waved through as "that one is
flaky".

## Goals

- [x] Establish whether the click is landing at all, or landing and being
      out-raced by the screen capture - it LANDS: a 26-height sweep found no
      rival pixel in the strip the old search box overreached into
- [x] Replace or shore up the oracle so the assertion is deterministic: the
      band is derived from the capture, the click goes to the glyph's centroid,
      the assert waits for the condition, and a control click beside the glyph
      proves the band does not clear itself
- [x] Prove it with several consecutive runs, not one - 5 consecutive ALL PASS

## Summary

Observed on 2026-08-07 during T290: `test\win32\activity-monitor.ps1` failed
`J clicking the glyph DISMISSES the banner` on one run and passed the same
assertion on an immediate re-run of the unchanged binary (`ALL PASS (92)`).
Nothing in T290's diff touches the banner, the error model, or painting.

## Where to look

- `test\win32\activity-monitor.ps1`, section J: `Find-ExactPixel` locates the
  dismiss glyph by its exact `COLOR_SECONDARY` (150,150,150) pixel, posts a
  left click at that coordinate, sleeps 600 ms, then re-captures and asserts
  the `COLOR_BANNER_BG` band is gone.
- Three candidate mechanisms, in order of suspicion:
  1. **The 600 ms sleep races the repaint.** The click posts; dismissal
     invalidates; the capture can beat the `WM_PAINT`. A wait-for-condition
     loop instead of a fixed sleep would fix it outright.
  2. **The click misses.** `Find-ExactPixel` returns the FIRST matching pixel
     scanning top-to-bottom, which may be a glyph antialias edge or another
     `COLOR_SECONDARY` element in the search box rather than the glyph's
     centre.
  3. **The banner is genuinely still up** because a sample adopted between
     the click and the capture re-raised it — check whether `adoptPending`
     can resurrect `err_len`.

## Validation criteria

- [x] The mechanism is identified from evidence (a log line or a capture),
      not guessed - two of the three candidates are disproved by measurement
      and by reading; the run now prints band top, click target and dismissal
      latency on every pass
- [x] Section J passes 5 consecutive runs (ALL PASS (159 assertions) x5,
      2026-09-05) of `test\win32\activity-monitor.ps1`
- [x] If the oracle changed, its negative control still fails when the
      dismissal is disabled - `if (false) self.clearError();` in
      activity_input.zig turned J red (FAIL J clicking the glyph DISMISSES the
      banner, 7 FAILURE(S)); the patch was reverted and the tree rebuilt
