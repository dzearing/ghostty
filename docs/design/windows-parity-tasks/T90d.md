## Re-scoped 2026-07-29 (T127)

Grown by two items of host plumbing that everything downstream needs, per
`docs/design/viewer-panes-windows.md` P1/P2:

- **The `window.webkit.messageHandlers` shim.** The shared viewer JS is
  WebKit-shaped: `viewer.js:115-127` and `selection.js:132-146` both post
  through `window.webkit.messageHandlers.viewerTOC.postMessage(obj)`. Define
  that object in terms of `window.chrome.webview.postMessage` and change NO
  shared JS -- forking it is rejected, it is the one part of the viewer that
  came free with T117 and must stay a single copy. Native side:
  `add_WebMessageReceived` + `get_WebMessageAsJson` sees the same JSON shape the
  Mac proxy does.
- **`AddScriptToExecuteOnDocumentCreated` with ONE blob** (shim +
  `selection.js`) so injection order is not a question. The toolbar itself is
  T162.

Also: do not consume `NewWindowRequested` in a way that discards the deferral --
T163 needs it.

## Split 2026-08-02 -> T372 -> T373 -> T374 -> T375

Split **before it was started**, per the context rule, on the same evidence
T321 used: reading the task against the code turned up more distinct
mechanisms than one context can carry.

The decisive fact is what this codebase's one existing piece of COM does and
does not do. `win32.zig:2059` declares `ITaskbarList3` -- a vtable struct,
`GUID`s, `CoCreateInstance`, `CoInitializeEx` -- so the *consuming* half is
precedented and cheap. But every COM object in this repo today is one somebody
else implemented and we only call. T90d needs the other direction: WebView2's
environment and controller creation, and every one of its events, are delivered
through **callback objects the app itself implements** -- our own vtable, our
own `QueryInterface`/`AddRef`/`Release`, our own lifetime, invoked by a browser
process on our message loop. Nothing in `src/apprt/win32/` has ever done that.
On top of it T90d asks for an undocumented loader-less runtime probe, a child
window class, an async controller lifecycle, an owner-painted error card, the
IPC/`+list` surface, the verb rejections, an E2E script, AND the JS bridge.
That is four commits behind one title.

The boundaries are drawn where the *state* changes hands:

- **T372** ends when the app can hold an `ICoreWebView2Environment*` (or a
  typed error). No window, no controller, no IPC. Its pure parts -- version
  parse/compare, install-dir join, UDF derivation -- are unit-testable in the
  none lane, and the probe itself is testable for real in the win32 lane, which
  runs on this box.
- **T373** ends when a viewer HWND exists, hosts a controller, resizes,
  focuses, follows DPI/dark mode, and degrades to the error card. Still nothing
  constructs one from IPC.
- **T374** is the user-visible flip: `--view=<url>` builds a real viewer leaf,
  `+list` reports it, terminal-only verbs reject it, and `viewer-panes.ps1`
  proves it on the box.
- **T375** is the JS bridge (P1/P2), which is only *verifiable* once a real page
  loads in a real pane -- so it cannot precede T374 even though it is host
  plumbing.

`--view` keeps T90b's explicit `viewers are not yet supported on Windows` error
until T374 flips it, so the interim behavior stays honest through the whole
band.
