# T1156 - P3 acceptance scored two failures once and then passed twice with nothing changed

## In plain terms

One of the checks that has to pass before any change ships reported a problem
once, then reported none twice in a row with nothing altered in between. A check
that answers differently to the same question is a check nobody will believe the
next time it says something is broken.

## Summary

Observed 2026-08-23 during T1131's turn, on the debug build at 155ac6b27 plus
T1131's viewer changes (which touch no IPC path P3 exercises):

```
run 1: P3 ACCEPTANCE: 2 FAILURE(S) (14 assertions passed)
run 2: P3 ACCEPTANCE: ALL PASS (16 assertions)
run 3: P3 ACCEPTANCE: ALL PASS (16 assertions)
```

Run 1 was started immediately after `ipc-p2.ps1` finished, and its output was
piped to `tail -3`, so WHICH two assertions failed was not captured - that is
the first thing this task has to recover, and the reason it is filed rather
than dismissed. The 14-vs-16 count says the run got all the way to the end and
two named assertions went red, not that it aborted early.

The leading hypothesis is teardown overlap: P2 kills agents and takes the
per-user pipe, and P3 launched about a second behind it. `go.md` already warns
that a concurrent lane starves test waits badly enough to wedge one; a
still-settling teardown is the same shape one notch smaller. If that is it, the
fix belongs in the script's own setup (wait for the endpoint to be free rather
than for a fixed sleep), not in the caller's discipline.

## Validation criteria

- [ ] The two failing assertions are identified by name, from a reproduction
      that captures full output (run P3 back-to-back after P2, N times, logging
      each run).
- [ ] The root cause is named - either the settling window above or something
      else - with the evidence that distinguishes them.
- [ ] `test\win32\ipc-p3.ps1` run 20 times back-to-back after P2 is ALL PASS
      every time.
- [ ] Whatever the fix is, it is in the harness setup and not a longer sleep at
      a call site.
