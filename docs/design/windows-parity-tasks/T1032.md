# T1032 - Nothing catches a test that clicks in the wrong coordinate space

Filed 2026-08-20 out of T327, which fixed the documentation and audited every
existing call site but deliberately left the enforcement unbuilt.

## In plain terms

The automated tests click things by measuring from the corner of the screen. A
test written from the wrong assumption measures from the corner of the window
instead, and then clicks in a place nothing is. The click reports success, so
the test fails and the feature looks broken when it is not - and whoever reads
that failure goes hunting through the app for a bug that was never there. It
happened once (T318), it is now written down in three places, and writing it
down is the only thing stopping it happening again.

## Why a checker rather than more prose

T327's audit found all 147 call sites correct, so this is not a cleanup - it is
a ratchet. The suite gains click sites constantly and the failure is SILENT at
the point it is made: the post succeeds, the helper returns `$true`, and the
cost lands on a later reader in a different session. `harness-exitcode-audit.ps1`
exists for the identical reason ("a rule nobody can forget is a rule a script
checks"), and it is the pattern to copy - analyzer in `test\win32\lib\`,
fixtures that give it teeth, a suite sweep that must stay at zero.

## The rule, and the part that makes it work

Decidable and with real teeth: **every `-X`/`-Y` argument to `Send-TestMouse`
must show screen evidence** - the expression references a rect or point origin
(`.Left`/`.Top`/`.Right`/`.Bottom`, a `To-Screen` call, a pixel probe's `.X`/`.Y`)
or resolves, through same-file assignments, to one that does.

That catches the shape that actually failed: T318 passed `-X $geo.KillX`, a
property carrying no origin term and no local definition, which the rule rejects.

The hard part is the shape it must NOT reject. Half the suite clicks through a
local wrapper - `Open-TabMenu $top $x $y`, `Send-PaneRight`, `Click-Thumb`,
`Glide-TestPointer`, `Click-TestPosted`, `Invoke-ChooserClick` - where the point
arrives as a PARAMETER and the screen evidence is at the wrapper's call sites,
one level up. Resolving those needs a small in-file call graph (which functions
forward a parameter into `Send-TestMouse -X`, then audit their callers the same
way). Without it the sweep reports a pile of findings that are all correct code,
which is how a checker gets switched off.

## Validation criteria

- [ ] Section A: fixtures the analyzer must catch, including T318's exact shape
      (`-X $geo.KillX`), and fixtures it must NOT flag, including a parameter
      forwarded through a local wrapper whose callers are screen-derived.
- [ ] Section B: the sweep over `test\win32\**\*.ps1` reports ZERO findings
      against the suite as it stands (T327 established that this is true today,
      so a non-zero result is a bug in the analyzer, not in the suite).
- [ ] `Send-TestClickStorm` is exempt by name - it genuinely takes CLIENT
      coordinates - and the exemption is asserted, not implicit.
- [ ] Wired into `scripts\guard-due.ps1` with its own row, so an edit to the
      analyzer obliges a run.
