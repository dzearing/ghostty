# T1325 - The vendored asset mirror is stale against origin/main and nothing reopens the check when main moves

## Summary

Found while landing T1321. `test\win32\hook-json.ps1` section A asserts that
`src\apprt\win32\assets\ghoztty\upstream\` is a byte-for-byte mirror of
tip-of-main's `macos/Resources/Ghoztty/`. Two of those assertions are RED right
now, and were red before this turn touched anything:

```
FAIL upstream mirror of skills/ghoztty/SKILL.md is byte-identical to origin/main
FAIL upstream mirror of skills/process-feedback/SKILL.md is byte-identical to origin/main
```

`origin/main` has moved on (`fc7e36356 feat(viewer): native image panes, and an
always-pinned nav bar` and friends touch `macos/Resources/Ghoztty/skills/`);
our mirror still reflects an older main, and the live `skills/ghoztty/SKILL.md`
tracks the mirror, so the skill document the Windows app EMBEDS is missing
whatever main has since said.

The failure mode is the interesting half. `scripts\guard-due.ps1` reopens a
harness when the files it COVERS change - all of them in our tree. Nothing in
our tree changes when `origin/main` advances, so this check goes red silently
and stays that way until an unrelated edit happens to reopen the guard. That is
the T1099 shape (a verdict that can only ever say "fine" until something else
pokes it), and it is why nobody noticed.

Two halves to fix:

1. Re-vendor the mirror from `origin/main` and bring the live unforked copy
   with it, taking whatever main has said about the `ghoztty` skill since. The
   three deliberate forks (`ghoztty-banner.sh`, `ghoztty-activity-state.sh`,
   `skills/process-feedback/SKILL.md`) must survive the re-vendor - hook-json's
   fork assertions are what prove that.
2. Make main's advance REOPEN the question, so this cannot go silently red
   again: the `hook-json` guard row (or a sibling) needs to key on the
   `origin/main` sha as well as on our covered files, the same way the main
   intake watermark does.

## In plain terms

The Windows app carries a copy of the instruction document that teaches an AI
agent how to drive the terminal, and that copy had fallen two days behind the
one the Mac app ships - so an agent on Windows did not know the terminal can
open a picture, and would hand you a file path instead of showing you the
screenshot you asked about. Worse, nothing was ever going to notice: the check
that compares the two copies only wakes up when somebody edits OUR side, and
this went stale because THEIR side moved. Both halves are fixed: the copy is
current, and the check now wakes up when the other side moves too.

## What was decided

**The `Upstream` watch keys on the mirrored files' BLOB shas, not on main's
head sha.** A head sha would reopen the guard on every unrelated main commit -
several a day - and a guard that is due constantly is a guard nobody reads. The
blob shas are read out of `origin/main` at check time and recorded in the stamp
beside the covered files' content hashes, so the question "has main changed
anything we mirror?" is answered exactly. A tree with no `origin/main` (a fresh
clone, a fixture repo) returns "cannot answer" and contributes no finding -
never "everything moved" - and stamping there carries the previous stamp's
upstream shas forward rather than erasing the key.

**The Mac-only wording was NOT corrected here.** The fourth criterion below
asked for it, and doing it in this task would have meant forking
`skills/ghoztty/SKILL.md` for one paragraph. The document is Mac-worded
throughout - `Cmd+R`, `Cmd+Z`, `Cmd`/`Cmd-Shift` banner modifiers, `-lic`,
`/bin/zsh`, `--command=zsh` - so a one-paragraph fork would be an inconsistent
divergence in a file main edits weekly, which is the exact shape that rots
silently. The whole pass, and the mechanism question it needs first (fork the
file vs. a build-time platform substitution over the mirror), is **T1327**.
Criterion 4 is therefore recorded as deferred with its evidence, not ticked.
