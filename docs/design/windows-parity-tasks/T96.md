# T96 — FIX: a session-scoped CLOSE never returns — `close_session_result` had no client dispatch arm

## Summary

`Connection.closeSession` (CLOSE_SESSION by id) **always** burned its full RPC
timeout and then reported failure, over a session the agent had already killed.
`close_session_result` was the one A→C reply frame type with no arm in the
client's `handleControlInternal` (`src/remote/connection.zig`), so the reply
reached the control reader and stopped there: `deliverRpcReply` was never
called, the parked slot never woke, and the caller got `error.Timeout`.

Fix: one arm, delivering it the same same-channel way as `cwd` / `sessions` /
`layouts` / `proc_kill_result`. No wire change, no protocol version bump — the
agent had been sending a correct reply the whole time.

## The filed diagnosis was wrong, and that is the lesson

This task shipped (from T89c, 2026-07-20) as *"the pty teardown hangs the
serving thread; the T89b two-phase `closeConsole` fix was applied to the TEST
teardown, the PRODUCTION close path still uses the untouched `Pty.deinit`."*
Every part of that is false:

- `terminateFn` (`src/remote/agent/pty_child.zig`) — the production path — has
  had the two-phase Windows teardown since **ec8796d8f (T89b, 2026-07-19)**, a
  day *before* T96 was filed. There was nothing left to port.
- The serving thread never wedged. Instrumented on box, the entire
  `handleCloseSession` — unlink, terminate the live ConPTY child, join the
  reader, free, `persistMeta`, `reapLayouts`, `sendJson` — ran in **30 ms**:

  ```
  close: unlinked                    t=...056512
  terminate: after kill              t=...056513
  terminate: after closeConsole      t=...056518
  terminate: after join              t=...056523
  terminate: after deinitAfterReader t=...056526
  terminate: after reap              t=...056529
  close: freed                       t=...056532
  close: persistMeta                 t=...056539
  close: before sendJson             t=...056542
  ```

The tell was in the original report and was read as corroboration instead of a
clue: *"transport-independent (repro'd over TCP too, **exactly 10s**)"*. A pty
teardown does not take the same 10.000 s over two different transports. 10 s was
`remote-test-client`'s own RPC budget — the number belonged to the **client**,
not the agent, and it pointed at the client the whole time.

Two habits would have caught it a week earlier: **a diagnosis inherited from
another task is a hypothesis, not evidence** (T254 already wrote this down about
load-bearing claims in task summaries), and **when a duration equals a timeout
you configured, suspect the waiter before the worker.**

## Evidence (VERIFIED on box, both directions)

`remote-test-client --pipe=… --close-session=<id>` against a real
`ghoztty-agent` holding a live ConPTY session (the holder client still
attached):

| | elapsed | exit | client output |
|---|---|---|---|
| before | **10054 ms** | 1 | `close-session failed: Timeout` |
| after | **59 ms** | 0 | `close-session <id>: ok=true` |

The session was removed from `sessions.json` in both runs — the close always
worked; only the answer was lost.

Negative control on the unit test: with the new arm commented out,
`closeSession: the agent's CLOSE_SESSION_RESULT wakes the RPC (T96)` fails with
`error.Timeout`. With it, green.

## Blast radius (this was user-facing, not just a test annoyance)

- **The chooser's Kill**, on both platforms. `SessionRoster.zig:375` and Mac's
  `embedded.zig:3145` both call `closeSession`, so every Kill stalled for the
  RPC budget and then reported failure over a session it had just killed.
  `chooser-sessions.ps1` had a comment declaring `confirmed=true` unassertable
  and blaming a slow agent teardown — the same wrong diagnosis, propagated into
  a deliberately weakened oracle. Both are fixed; the script asserts it now.
- **`agent-pipe.ps1` step 5** carried the same workaround, waiting out ~10 s and
  asserting only that the session vanished.
- Mac is fixed by the same shared-Zig change and needs its own verification —
  **T402**.
- `closeSessionNoWait` (the T230 relaunch-notify path) was unaffected: it never
  parks an RPC, and its reply landing unclaimed is by design.

## Changes

- `src/remote/connection.zig` — the `.close_session_result` dispatch arm; a
  `MockAgent.handshakeCaps` so a mock can advertise capability-gated opcodes
  (`handshake` delegates with an empty set, so every existing test is
  unchanged); a `.close_session` arm + config on `LifecycleAgent`; three tests
  (reply wakes the RPC, silent agent times out instead of wedging, an agent that
  never advertised the capability is refused instantly).
- `test/win32/agent-pipe.ps1` — step 5 asserts the client exits, reports
  `ok=true`, and gets its reply **well inside** the RPC timeout. The latency
  bound is the point: a re-broken dispatch fails by taking the timeout, and only
  a bound catches that.
- `test/win32/chooser-sessions.ps1` — asserts
  `chooser roster: close session confirmed=true`.
