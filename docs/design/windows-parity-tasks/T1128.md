# T1128 - hero-mode.ps1 overwrites a tracked screenshot artifact on every run, and the new one looks blank

## In plain terms

One of the automated checks takes a photo of a window and saves it into the
project as a reference image. It overwrites that image every single time it
runs, so the project always looks like it has unsaved changes after a test run.
Worse, the new photo is a third the size of the old one - which is what happens
when a photo is mostly one flat colour - and the check still reports success.

## Summary

Found during T1094's full suite sweep. `test\win32\hero-mode.ps1` scored
**`pass` in 36.3 s**, and left this behind:

```
 M test/win32/artifacts/hero-mode-t59b.png
   Bin 133921 -> 41165 bytes
```

The file is TRACKED (not gitignored - `git check-ignore` says nothing), last
changed deliberately in `4312d369b` ("The main-window chrome tests now
photograph a window that poses for the camera", T941). The write is
unconditional:

```
test\win32\hero-mode.ps1:780:
    Save-WindowShot $top (Join-Path $artifacts 'hero-mode-t59b.png')
```

Two separate defects, and the second is why this is P1 rather than tidy-up.

**1. A test mutates tracked state.** Every suite run leaves the working tree
dirty. The go-loop treats a dirty tree at claim time as STRANDED WORK from a
dead turn and fails `validate` on it, so a routine test run now manufactures a
false stranded-work report for the NEXT turn. It also means an artifact could
be committed by accident, replacing a deliberate reference with whatever the
last run happened to capture.

**2. The replacement is 31% of the original's size, and nothing checked.**
133921 -> 41165 bytes on a PNG of the same dimensions is a large drop in visual
content - which is exactly what a near-uniform image compresses to. That is the
same signature `caption-bar.ps1` reports outright (`the capture is UNIFORM`) and
`test-desktop-spike.ps1` measures directly (`PrintWindow(PW_RENDERFULLCONTENT)
returns real content` FAILS) - see [[T1100]].

So this script is very likely photographing a blank window, saving it over the
good reference, and passing. A green verdict over a blank picture is worse than
a red one, because it actively destroys the evidence that would have shown the
problem.

## Reproduced alone

Not applicable, and recorded so the answer is not merely missing (T1137):
`hero-mode.ps1` PASSED the sweep. What this task is about is what the script
writes over while passing, which a re-run cannot discriminate - the artifact is
rewritten on every run, green or red.

## Where

- `test/win32/hero-mode.ps1` - `-ShotDir` / `-UpdateBaseline`, the
  `Save-WindowShot` / `Assert-ShotHasContent` pair, and the WHERE THE
  SCREENSHOTS GO header
- `test/win32/artifacts/hero-mode-t59b.png` - the committed screenshot
- `test/win32/lib/TestDesktop.ps1` - `Get-TestCaptureContent`
- `test/win32/test-desktop-harness.ps1` - section C, the floor's demonstration

## The finding: NOT blank. The hero pane's glass is, and only that

Measured 2026-09-02, both images 1400x900, whole-image sample every 2px:

| | committed (4312d369b) | fresh run |
|---|---|---|
| bytes | 133921 | 41165 |
| distinct colors | 2495 | 681 |
| Shannon entropy | 2.661 | 2.150 |
| most common color's share | 55.6% | 59.2% |

681 distinct colors is not a blank window, so the P1 fear - a green verdict
over a picture of nothing - does not hold. Put the two side by side and the
difference is confined to ONE region: the hero pane's terminal glass, which is
real `cmd.exe` text in the committed shot and a flat fill in the fresh one.
Window chrome, the divider, the carousel column and every thumbnail in it are
pixel-identical.

That is the chrome/surface split [[T1115]] measured and wrote into
`test-desktop-spike.ps1`: on the background test desktop `PrintWindow` returns
the OpenGL terminal surface as a flat fill, and hero-mode.ps1's own header has
warned about it since T214. The committed screenshot predates the effect
reaching this script. So the size collapse is the DOCUMENTED capture limit
showing up in a file nobody was reading - not a regression, and not the blank
capture the filing suspected.

Which leaves defect 1 as the whole of this task, plus the missing floor that
would have answered the question in the run instead of a month later.

## What changed

- **The run no longer writes anything tracked.** `hero-mode.ps1` takes
  `-ShotDir` (default `$TEMP`) and writes both of its shots there. The
  committed screenshot is refreshed only under `-UpdateBaseline`, and only when
  that capture clears the content floor.
- **The screenshot stays in git, as documentation.** It is not a reference the
  script compares against and it cannot become one: a pixel diff would be
  permanently red for the desktop the run happened on rather than for the app.
  It IS cited as the layout evidence for T59b (`T59b.md`,
  `windows-parity-details.md`), so deleting it would break two live citations.
  The header now says which of the two it is, so nobody re-derives this.
- **The floor the byte drop went past.** `Get-TestCaptureContent`
  (`lib\TestDesktop.ps1`) scores a capture as distinct-color count plus the
  most-common color's share; `hero-mode.ps1` asserts both shots clear 8 distinct
  / 90% top share. `Test-TestCaptureUniform` next to it answers only the binary
  question - is EVERY sample the same - and a capture keeping three stray blocks
  slips past it, which is the case section C constructs.
- **Calibration, so the floor separates the right two things.** Dead capture
  scores 1 / 100%; this window with its glass flat-filled scores 23 / 60%; the
  committed screenshot scores 87 / 57%. The floor catches the capture dying,
  and deliberately does not police the known surface limit.
