# T587 - Chrome stroke width is NON-MONOTONIC in DPI: thinner at 150% than at 125%

## In plain terms

Windows' display scaling has a 150% setting, and it is a common one on laptops.
At that setting every icon line in Ghoztty's own chrome — the "+", the tab close
"x", the menu button, the window buttons — is drawn at the same physical
thickness it uses at 100%, so the whole toolbar looks spindly on a screen where
everything else got bigger. Stranger still, it is drawn *thinner* at 150% than
at 125%: turning scaling UP makes the icons lighter. Nothing is broken, but the
chrome stops looking like it was built for the display it is on.

## Goals

- [x] Icon stroke weight grows with display scaling, never shrinks — 3 px at
      150% where it painted 2 px before.
- [x] The "+", the dots, and every other glyph stay internally symmetric at
      every scaling step.
- [x] The whole icon set moves together — no glyph left at the old weight.
- [x] The design rule is written down so the parity fit is never re-applied to
      stroke weight.

## Summary

`✓ VERIFIED` — measured off `Metrics.init(scale).stroke_w` while working T239:

| scale | expected (2 DIP × scale) | actual `stroke_w` |
|---|---|---|
| 1.0 | 2 | 2 |
| 1.25 | 2.5 | **3** |
| 1.5 | 3 | **2** |
| 2.0 | 4 | 4 |
| 3.0 | 6 | 6 |

The cause is `Metrics.markPx` (`src/apprt/win32/icon_button.zig`), which forces
a value to the same parity as the 28 DIP button side and **rounds DOWN on a
mismatch, never up**. At 1.5 the side is 42 (even) and the stroke rounds to 3
(odd), so the parity fit knocks it to 2 — a 33% loss. At 1.25 the side is 35
(odd) and 3 is odd, so it survives. Hence the inversion.

That down-rounding rule is right, and design system §4.2 explains why: for a
mark EXTENT, rounding up collapses the optical order (`close < add < menu`) at
half the scales, and a mark one pixel under its nominal DIP is invisible. But
`stroke_w` is not an extent — it is the mark's WEIGHT, it is small enough that
one pixel is a third of it, and it does not need to share the container's parity
at all (a bar is centered by `centered()`, which does its own parity fit on the
bar's own box). The extent rule was applied to a number it was never argued for.

Surfaced by T239, which corrected the chevron's sloped arms to paint at
`stroke_w` perpendicular. That fix is right and independent of this one — but it
means the chevron now faithfully reproduces a `stroke_w` that is itself wrong at
1.5.

## The fix

Resolve `stroke_w` (and `stroke_outline`) with plain rounding rather than
`markPx`'s parity fit, and let `centered()` handle the parity of the bar box it
is placed in — which it already does. Check the "+" stays symmetric at 1.5 after
the change (the existing `the plus is exactly as long as it is tall` test
asserts the two halves of each bar match, which is the property parity was
protecting).

Watch for knock-ons: `restore_off` is floored at `stroke_w + 1`, the close
glyph's `k` is `3·stroke_w/4`, and T239's `slopedStroke` corrections all scale
off `stroke_w`, so all of them move at 1.5. The T239 test
(`every open glyph paints at the same PERPENDICULAR thickness`) covers the set
and will catch a glyph that falls out of band.

## Evidence

New `stroke_w` by scale: 1.0→2, 1.25→3, **1.5→3** (was 2), 2.0→4, 3.0→6 —
monotonic, always within half a pixel of `2·scale`. The mechanism, as
implemented:

- `Metrics.init` resolves `stroke_w = max(round(2·scale), 1)` — `markPx`'s
  parity fit no longer touches it (`markPx` doc now says extents only).
- `centeredExact` (new) places a box at its exact size; glyph cases whose bar
  short-axis is the stroke (`add`, `menu`/`contents`, `minimize`, `send`'s
  shaft, `overflow`'s dots) use it so the stroke can never be trimmed. The odd
  half-pixel of an odd gap truncates up/left, deterministically.
- `strokeFit` (new): the "+" and the "…" genuinely need extent ≡ stroke
  (mod 2) — bars splitting evenly around a crossing member; three dots plus
  two equal gaps — so there the EXTENT gives up one pixel, never the stroke.
  At 1.5 the "+" paints 17 px wide with a 3 px stroke instead of 18 px wide
  with a 2 px stroke.
- Tests updated where they encoded the old scheme: the extent-parity sweep no
  longer lists `stroke_w`; the both-axes symmetry sweep asserts exact-equal
  clearance on even gaps and exactly-one-pixel up/left bias on odd ones (a
  bias that flipped with scale would be the pen-stroke defect back). Added
  `stroke weight tracks the scale monotonically` (0.05-step sweep, 1.0–3.0).
- Design system §4.2 gained a paragraph: the parity fit governs extents and
  explicitly NOT stroke weight, with the 125%→150% inversion as the reason.

Not filed as a follow-up, deliberately: `send`'s shaft center can sit half a
pixel off its apex at parity-mismatch scales (pre-existing, sub-pixel, and the
quad path is the no-icon-font FALLBACK — T497's font path renders on normal
machines); the T239 thickness sweep bounds it.
