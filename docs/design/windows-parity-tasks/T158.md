# T158 - Sweep test/win32 for scripts that launch without --session-persistence=false

## Summary

A standing script that launches a GUI **without** `--session-persistence=false`
restores whatever panes the last launch left behind, so its own setup
assertions describe someone else's layout. T131 fixed this for
`pane-banner.ps1`; T155 hit it again in `split-dim.ps1` and
`split-zoom-nav.ps1` and fixed those two. Nobody has checked the other ~28
scripts, and the failure mode is expensive: it presents as a product
regression in whatever change happens to be in flight.

Measured during T155 (2026-07-29), in order:

1. Both scripts failed `default setup: 2 visible panes` on a build whose
   pane geometry was independently verified correct (2 panes tiling with a
   1px band, enumerated by hand).
2. `%LOCALAPPDATA%\ghoztty\session-layout-debug.json` held **15 windows** of
   1-3 panes accumulated from earlier runs. Sidelining it moved the failure
   from the FIRST section to the SECOND — proving each section's own launch
   writes the manifest the next section restores. Self-poisoning, so it does
   not even need a dirty box to trigger.
3. Adding the flag to both launchers: `split-dim` ALL PASS (23),
   `split-zoom-nav` ALL PASS (16).

## Details

`grep -n 'Start-Process' test/win32/*.ps1` and check each launch for the
flag. Scripts whose subject IS session persistence
(`session-*.ps1`, `agent-*.ps1`) must obviously keep it on — they are the
exception, not oversights, so read each one rather than bulk-editing.

Two adjacent hazards found in the same pass, worth folding in:

- **Stray instance ⇒ "GUI died at launch".** A second `ghoztty.exe` launch
  finds the pipe owned, forwards `new-window`, and exits, so `$proc.HasExited`
  is true 3s later and the script reports `SETUP FAIL: GUI died at launch` —
  which reads like a crash and is not one (log line: `another instance owns
  the IPC pipe; forwarding new-window`). `Kill-RepoInstances` kills once and
  sleeps 500ms without verifying; it should loop until zero remain.
  Note `ghoztty +list`/`+split` AUTO-LAUNCH an instance when none is
  running, so a stray CLI call between kill and launch re-creates the very
  process the kill removed.
- **No stderr capture.** `pane-banner.ps1` redirects nothing, so when its
  instance disappeared mid-run there was no log to diagnose from and the
  Windows event log had no crash record either. Every script should
  `-RedirectStandardError` to a named temp log.

## Validation

Each edited script ALL PASS x3 on the box. Plus a negative control that
would have caught this class: launch, create a split, kill the GUI, launch
again with the flag, and assert the second launch comes up with ONE pane.
