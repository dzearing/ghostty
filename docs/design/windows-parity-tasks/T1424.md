# T1424 - A failed revocation is never retried

## In plain terms

If the relay cannot be reached when you sign out, Ghoztty now tells you so and
keeps you signed in (T1421), and you can choose "Sign Out Anyway". What it does
not do is finish the job later. That machine stays registered to the account —
listed, reachable and streamable from your other computers — until you go to
another computer and remove it by hand. Nobody thinks to do that. The app should
remember the unfinished revocation and complete it the moment it can reach the
relay again.

## Goals

- [x] "Sign Out Anyway" records a pending revocation rather than only warning about one
- [x] The pending revocation is retried at every app launch while it is armed
- [x] It is retried when the network comes back, without waiting for a relaunch
- [x] The retry authenticates as the DEVICE, so it needs no account session (the user is signed out by then)
- [x] A revocation the relay confirms clears the pending record; an unanswerable relay leaves it armed
- [x] A 401 on the retry does NOT clear the machine's suspension record (see T1425) — a landed POST with a lost response reads identically

## Summary

Split out of T1421, which landed the revocation itself and the refusal to report
a sign-out that did not happen. This is the recovery half of main's
`0c3a19764` plus the edge cases `f3b1e5fb5` closed.

The Mac shape: sign-out arms a pending revocation with relay.env kept as the
retry's own record, retried at every launch and on every network-came-back
transition until the relay confirms it. Two of `f3b1e5fb5`'s bugs live here and
should be designed in from the start rather than rediscovered:

1. **A POST that landed with a lost response.** The retry sees a bare 401, reads
   it as "already revoked", and (on the Mac's first cut) cleared the machine's
   suspension — so the user signed back in and the machine was simply gone, with
   no name left to re-enroll under. Record the suspension BEFORE the de-enroll
   POST; the 401 branch leaves it alone.
2. **A transient re-enroll failure** (relay 5xx, device quota, offline right
   then) must not strand the machine until an explicit sign-out/in cycle.

The primitives are in place from T1421: `relay_revoke.decide`,
`relay_revoke.revocationBase` / `normalizeBase`, `enroll.whoami`,
`enroll.deEnroll`, and `relay_signin.SignOutMode.force`, which is currently the
"tell them and give up" path this task turns into "tell them and finish later".

## Validation criteria

- [x] A unit test of the pending record's state machine: armed, confirmed, 401-with-suspension-intact, unanswerable-stays-armed
- [x] An acceptance check that a forced sign-out leaves an armed record on disk
- [x] A relaunch with the relay reachable clears it and the device is gone from another client's list
- [x] `scripts\floor-lane.ps1 -Lane all` green

## What landed

`src/remote/relay_revoke_pending.zig` (new): the armed record, its pure rules and
the retry driver. A forced sign-out writes `pending-revoke.json` beside
relay.env (device token, normalized relay base, account, armed_at; atomic,
owner-only DACL) and keeps the local credential, because the retry authenticates
as the DEVICE and that credential is the only thing that can ever revoke this
machine. `retryAsync` runs from `App.startup` and again the moment a record is
armed, on 0s/5s/15s/60s/5min then every 15min. `nextAfter` decides: 204/200
clears it revoked, 401 clears it and concludes NOTHING else (T1425's suspension
record is not this branch's business), anything else stays armed.
`enroll.deEnrollStatus` splits the two success answers apart for that reason.
Signing back in cancels an armed record, so re-adopting this machine wins over
the retry. Dialog and footer wording now promise the retry instead of asking the
user to remember a chore.
