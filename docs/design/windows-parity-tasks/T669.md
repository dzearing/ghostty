# T669 - Viewer feedback carousel: a transparent PNG is flattened onto black instead of the tile's own fill

## In plain terms

Paste a picture with transparency — a logo, a cropped screenshot with rounded
corners — into a feedback report and its thumbnail shows the see-through parts
as solid black. It should show the tile's own background there, the way every
other app does.

## Summary

Filed out of T646. The tile decode goes through `gdiplus_decode.decodeBytes` →
`decodeScaled`, which calls `GdipCreateHBITMAPFromBitmap(bitmap, &hbm,
0xFF000000)` — the third argument is the background the alpha channel is
composited against, and it is opaque BLACK. That was the right answer for the
call site the function was written for (T397's hero thumbnail of a web page,
which has no transparency), and it is the wrong one for a tile sitting on the
composer's pill fill, especially in light theme.

The fix is to composite against the surface the picture will actually sit on
rather than a constant. Two shapes worth weighing before building:

- Pass the background colour down to `decodeScaled`/`decodeBytes` and hand it to
  `GdipCreateHBITMAPFromBitmap`. Cheap, but it bakes a theme colour into the
  CACHED bitmap, so a light/dark switch has to invalidate the cache — which is
  keyed by (number, tile size) today and would need the colour in the key.
- Keep the decode alpha-preserving and composite at paint time with
  `AlphaBlend`. The cache stays theme-independent, which also means a theme
  change costs no re-decode, at the cost of a per-paint blend.

The second is likely right for the same reason the tile's fill is derived and
not stored — but that is a judgement to make with the code open, not here.

Note the same constant is used by the hero-thumbnail path; whatever changes must
leave that path's behaviour alone or account for it.

## Goals

- [x] A transparent PNG's see-through parts show the tile's own fill.
- [x] The cached tile bitmap carries no theme colour, so a light/dark switch
      costs no re-decode.
- [x] The hero thumbnail's decode is left exactly as it was.
- [x] Both halves are pinned by tests that fail without the fix.

## What landed

The second shape in the Summary, for the reason it predicted. `decodeBytes` now
routes to a new `decodeAlpha`, which asks GDI+ to scale straight into a
premultiplied 32-bit DIB section of ours (`GdipCreateBitmapFromScan0` +
`GdipDrawImageRectI` at high-quality bicubic) instead of going through
`GdipCreateHBITMAPFromBitmap` and a `StretchBlt`. There is no way to keep an
alpha channel through the old route: the HBITMAP call composites it away by
contract, and a GDI blit treats the fourth byte as padding. `blitThumb` then
paints with `AlphaBlend` (`AC_SRC_ALPHA`, constant alpha 255) over the fill
`paintTileFrame` has already laid down.

`decodeScaled` — the hero thumbnail's path (T397) — is untouched and still
flattens onto black, which is the right answer for a capture of a web page that
has no transparency. The two are now documented as two decodes for two kinds of
picture rather than one call with a colour threaded through it.

One thing found on the way: **`gdiplus_decode.zig`'s tests ran in no lane at
all.** The module was imported and compiled, but it was missing from the
`test { _ = @import(...) }` list in `src\apprt\win32.zig`, which is what
actually pulls a win32 module's tests into the lane (the exact T1177 shape
`test\win32\test-reach-audit.ps1` exists to catch). The first version of the
regression test below went green against a build that never executed it. It is
registered now.

## Validation criteria

- [x] Unit tests in the win32 lane over the real decode:
      `decode: a transparent PNG keeps its alpha instead of being flattened onto
      black` asserts the transparent half comes back alpha 0 with zeroed
      premultiplied colour (i.e. no background was composited in), and
      `decode: an opaque PNG survives the alpha path unchanged` asserts an
      ordinary screenshot is byte-identical through the new path.
      **Negative control run:** with `decodeBytes` pointed back at
      `decodeScaled`, both go red; restored, both pass
      (`floor-lane.ps1 -Lane win32 -Filter "PNG"`).
- [x] On-box acceptance: `test\win32\viewer-feedback-alpha.ps1` — 47 assertions,
      ALL PASS. It pastes a half-transparent PNG, reads the strip's geometry and
      the `thumb=#1 box=B decoded=WxH` line off stderr, and takes a synchronous
      `WM_PRINTCLIENT` capture of the composer band (a GDI-painted native
      window, so it survives the background test desktop). The transparent half
      measures equal to the tile fill sampled from the same capture — light
      `255,255,255` vs fill `255,255,255`, dark `30,35,46` vs fill `30,35,46` —
      and both are far from black. Run in **both themes**, since the whole
      argument for blending at paint time is that the cache holds no theme
      colour.
- [x] The hero thumbnail (T397) still renders as it did:
      `test\win32\hero-viewer-tile.ps1` reports `viewer tile carries the PAGE,
      not just a placeholder (128 distinct colors, floor 4)`. That script has one
      unrelated pre-existing failure on the TERMINAL tile's border, filed as
      T1469 — it is red on the same assertion twice in a row and touches nothing
      this task changed.
- [x] Floor: `floor-lane.ps1 -Lane all` — lib/none/win32/agent ALL PASS.
      Regression: `viewer-feedback.ps1` (96), `viewer-feedback-carousel.ps1`
      (60), plus the nine harness audits `guard-due` marked due.
