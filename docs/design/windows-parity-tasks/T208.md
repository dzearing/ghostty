## Summary

Hit for real on 2026-07-30 delivering **T202**. The turn ran
`scripts/launch-upgrade.ps1`, the launcher reported `LAUNCH OK`, the
upgrade log reported `exe swapped` and `UPGRADE OK`, and the turn reported
the delivery as done. **The installed release was never updated.**

`ghoztty +version` afterwards: `1.4.0-users-dzearing-windows-amd64-+9968a62d9`
— the T196-era commit from that afternoon. T202 (`f1a1c4a24`) was not in it.

## Root cause

`scripts/upgrade-ghoztty-windows.ps1` has **no build step**, by design — its
own header says so: *"kill release ghoztty processes -> swap exe + share\ from
the staging prefix -> RESUME"*. It copies whatever is sitting in
`D:\git\ghoztty\zig-out-release`. `scripts/launch-upgrade.ps1` only checks
that the staging DIRECTORY exists (`Test-Path -PathType Container`, line 69);
it never looks at what is in it.

So the contract is "the caller builds the release into `zig-out-release`
first" — and that contract is written down nowhere the caller reads. go.md's
delivery section documents the *launch* invocation in detail (T200) and says
nothing about building first. A turn that follows go.md exactly therefore
ships whatever binary the LAST delivery happened to leave behind, and every
signal it gets back says success.

This is the same class of failure T200 fixed at the launch boundary — a
delivery that reports OK without having happened — one step earlier in the
pipeline.

## Deliverables

1. **Make the staging build part of the delivery, not a remembered
   precondition.** Either `launch-upgrade.ps1` builds
   (`-Doptimize=ReleaseFast -Dtarget=x86_64-windows-gnu -Dstrip=false
   --prefix zig-out-release`) before launching, or it refuses to launch
   without `-SkipBuild`. Building is the better default: it is the step the
   caller forgets, and it is idempotent when the tree has not changed.
2. **Verify the staged binary against the tree, and fail loudly.** Before the
   swap, compare the staged exe's `+version` commit against `git rev-parse
   --short HEAD`. A mismatch must be a hard error, not a log line — the whole
   failure mode here is that every status signal said OK.
3. **Verify AFTER the swap too.** `upgrade-ghoztty-windows.ps1` should run
   the installed `ghoztty.exe +version` after swapping and log the commit it
   actually got, so `UPGRADE OK` means "the right bits are installed" rather
   than "a file copy returned success".
4. Update go.md's delivery section so the documented invocation is the whole
   procedure. Right now it documents the launch and omits the build.
5. Consider the other two install locations (Desktop portable, the
   `\\homeassistant\share` copy) — the log shows those swapped by hand each
   time, which is the same staleness risk with no automation at all.

## Validation

- Negative control that matters here: with the tree at commit X and
  `zig-out-release` holding a binary from an older commit Y, the delivery
  must **fail** rather than report OK. Assert on the exit code and on the
  installed `+version` still being Y.
- Positive control: a clean run leaves the installed `+version` equal to
  `git rev-parse --short HEAD`.
- Extend or add a script under `test/win32/` (`upgrade-no-fork.ps1` and
  `msi-upgrade.ps1` are the neighbours) so this is checkable without a real
  delivery.

## Priority note

Rank this ABOVE further cosmetics (T203/T204/T206). Those tasks exist because
the user cannot see the fixes; a delivery path that silently ships stale bits
is the mechanism that keeps them from seeing any fix at all, and it produces
turns that honestly believe they delivered.
