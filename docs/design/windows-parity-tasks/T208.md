# T208 - Delivery can silently ship a stale binary: the upgrade path never builds and never checks the staging commit

## Summary

Hit for real on 2026-07-30 delivering **T202**. The turn ran
`scripts/launch-upgrade.ps1`, the launcher reported `LAUNCH OK`, the
upgrade log reported `exe swapped` and `UPGRADE OK`, and the turn reported
the delivery as done. **The installed release was never updated.**

`ghoztty +version` afterwards: `1.4.0-users-dzearing-windows-amd64-+9968a62d9`
— the T196-era commit from that afternoon. T202 (`f1a1c4a24`) was not in it.

## Root cause

`scripts/upgrade-ghoztty-windows.ps1` has **no build step**, by design — its
own header says so: *"kill release ghoztty processes -> swap exe + share\ from
the staging prefix -> RESUME"*. It copies whatever is sitting in
`D:\git\ghoztty\zig-out-release`. `scripts/launch-upgrade.ps1` only checks
that the staging DIRECTORY exists (`Test-Path -PathType Container`, line 69);
it never looks at what is in it.

So the contract is "the caller builds the release into `zig-out-release`
first" — and that contract is written down nowhere the caller reads. go.md's
delivery section documents the *launch* invocation in detail (T200) and says
nothing about building first. A turn that follows go.md exactly therefore
ships whatever binary the LAST delivery happened to leave behind, and every
signal it gets back says success.

This is the same class of failure T200 fixed at the launch boundary — a
delivery that reports OK without having happened — one step earlier in the
pipeline.

## Deliverables

1. **Make the staging build part of the delivery, not a remembered
   precondition.** Either `launch-upgrade.ps1` builds
   (`-Doptimize=ReleaseFast -Dtarget=x86_64-windows-gnu -Dstrip=false
   --prefix zig-out-release`) before launching, or it refuses to launch
   without `-SkipBuild`. Building is the better default: it is the step the
   caller forgets, and it is idempotent when the tree has not changed.
2. **Verify the staged binary against the tree, and fail loudly.** Before the
   swap, compare the staged exe's `+version` commit against `git rev-parse
   --short HEAD`. A mismatch must be a hard error, not a log line — the whole
   failure mode here is that every status signal said OK.
3. **Verify AFTER the swap too.** `upgrade-ghoztty-windows.ps1` should run
   the installed `ghoztty.exe +version` after swapping and log the commit it
   actually got, so `UPGRADE OK` means "the right bits are installed" rather
   than "a file copy returned success".
4. Update go.md's delivery section so the documented invocation is the whole
   procedure. Right now it documents the launch and omits the build.
5. Consider the other two install locations (Desktop portable, the
   `\\homeassistant\share` copy) — the log shows those swapped by hand each
   time, which is the same staleness risk with no automation at all.

## Validation

- Negative control that matters here: with the tree at commit X and
  `zig-out-release` holding a binary from an older commit Y, the delivery
  must **fail** rather than report OK. Assert on the exit code and on the
  installed `+version` still being Y.
- Positive control: a clean run leaves the installed `+version` equal to
  `git rev-parse --short HEAD`.
- Extend or add a script under `test/win32/` (`upgrade-no-fork.ps1` and
  `msi-upgrade.ps1` are the neighbours) so this is checkable without a real
  delivery.

## Priority note

Rank this ABOVE further cosmetics (T203/T204/T206). Those tasks exist because
the user cannot see the fixes; a delivery path that silently ships stale bits
is the mechanism that keeps them from seeing any fix at all, and it produces
turns that honestly believe they delivered.

## What shipped (2026-08-01)

The delivery now carries a **number both ends can compare**: the short commit
`src/build/GitVersion.zig` bakes into the exe as semver build metadata (so it is
whatever follows the last `+` in `+version`). Reading it and comparing two
abbreviations lives once, in **`scripts/delivery-version.ps1`**, so the three
gates cannot drift apart. Two Windows traps are handled there once rather than
at each call site: every probe goes through `cmd.exe /c ... > file` because a
GUI-subsystem exe's stdout does NOT survive PowerShell's redirection (T245), and
every probe is a child with a hard deadline (T187).

1. **`launch-upgrade.ps1` BUILDS** (deliverable 1). Default, with `-SkipBuild`
   for "I already built it" - which still runs the gate, so it is never "ship
   whatever is there". The build is `zig build -Dapp-runtime=win32
   -Doptimize=ReleaseFast -Dtarget=x86_64-windows-gnu -Dstrip=false --prefix
   zig-out-release`, captured to `%TEMP%\ghoztty-staging-build-<stamp>.log`, and
   a failure prints the first ten `error:` lines and exits 3.
2. **The gate, before the launch** (deliverable 2): staged commit vs `git
   rev-parse --short HEAD`. Mismatch = `STALE STAGING`, exit 3, **nothing is
   launched**. `-AllowStaleStaging` ships it anyway and says so; `-ExpectedCommit`
   names the target commit explicitly (and is what lets the acceptance script
   drive both sides of the gate without a build). The resolved commit is handed
   DOWN to the child, so both ends measure the same number even on a box where
   the detached child cannot reach git.
3. **The gate again, before the kill** (deliverable 2, belt to those braces and
   the direct-invocation path). A stale prefix **skips the whole destructive
   region** - no kill, no swap - and the installed release is left untouched.
   Deliberately it does NOT abort the script: the resume still runs, because a
   silently stalled loop is the more expensive failure (T200/T241) and the exit
   code plus `UPGRADE FAILED` already make the delivery unmistakably not-OK.
4. **Post-swap verification** (deliverable 3): the installed exe is read back and
   the commit it reports is logged. Every exit now goes through one
   `Complete-Upgrade` verdict, so `UPGRADE OK` means "the installed exe answers
   with the commit this delivery was for" rather than "a file copy returned
   success".
5. **go.md** (deliverable 4): the delivery bullet is now the whole procedure -
   the build, the gate, both escape hatches, and the acceptance script.
6. **The other two install locations** (deliverable 5) are mirrored
   automatically after a verified swap: the Desktop portable and the
   `\\homeassistant\share` copy, both `...\Ghoztty-portable-x64\Ghoztty` (the
   exe-bearing directory, one level in). Best-effort by construction - a
   sleeping NAS or a portable instance holding its own exe open is logged and
   skipped, never fatal - and **skipped entirely when the primary install did
   not verify**, since propagating unverified bits is the same defect with more
   copies.

## Validation (VERIFIED on the box, 2026-08-01)

`test\win32\upgrade-staleness.ps1` - **ALL PASS**, 49 assertions:

- **A** (pure, 19): the commit parser, the abbreviation comparison and the zig
  cache-drive default (see the section below). Includes
  the 2026-07-30 incident as a permanent oracle (installed `9968a62d9` vs
  delivered `f1a1c4a24` is a mismatch), that a `+hex`-shaped token in the Build
  Config section cannot impersonate the version line, and that an UNREADABLE
  version is never a match - unverified must not read as OK, which is the whole
  disease.
- **B** (6): the probe against a real binary, plus both of its failure modes
  (missing exe; output with no version line) reported distinguishably.
- **C** (14): `launch-upgrade.ps1`. The negative control is the headline - a
  stale prefix exits **3** and **starts no upgrade at all** (asserted on the
  `=== upgrade start` marker count, not on the message). Then
  `-AllowStaleStaging` ships it, the expectation is verified to be handed down
  to the child, a fresh prefix launches, and an exe-less prefix cannot pass.
- **D** (17): `upgrade-ghoztty-windows.ps1` end to end against a sandbox
  install. Stale: exit 1, `STALE STAGING`, **no `exe swapped`**, the installed
  file byte-identical to its sentinel, `UPGRADE FAILED` and never `UPGRADE OK`.
  Fresh: the swap happens, `POST-SWAP VERIFY OK` names the commit, and the
  installed exe hashes equal to the staged one. Then the post-swap gate is
  exercised **live** via `-AllowStaleStaging` - the bits land fine, the post-swap
  read catches that they are not the delivery, and the run is a FAILURE despite a
  successful copy.
- **E** (4): go.md documents the build, the gate's failure word, the incantation
  and the acceptance script - because the omission in go.md is what made the
  defect reachable by a turn following instructions exactly.

Every run is hermetic: sandbox install/staging dirs, `TEMP` redirected for every
child so the box's real upgrade log is untouched, no build ever run, and
`-NoExtraInstalls` on every D case so an acceptance script never writes to the
user's desktop or NAS.

## The defect the acceptance suite could not see

The suite never builds - that is what makes it hermetic and fast - so the build
step went in untested by it. Running the launcher for real against the repo
caught it immediately: with `ZIG_GLOBAL_CACHE_DIR` unset, zig puts its global
cache under `%LOCALAPPDATA%` on **C:** while the repo is on **D:**, a `Run` step
cannot express a cross-drive absolute path relative to its child cwd, and the
build panics:

```
thread N panic: reached unreachable code
  std\Build\Step\Run.zig:662 in convertPathArg
    assert(!std.fs.path.isAbsolute(child_cwd_rel));
error: unable to read results of configure phase from '.zig-cache\tmp\...'
```

Every hand-run build on this box exports the variable first, which is exactly
why it was invisible: **a habit of the operator is not a property of the
script**, and a detached delivery child inherits the launching tool shell's
environment, where it is normally absent. The launcher now fills the default in
itself, on the repo's own drive, and never overrides an explicit setting
(`Get-ZigGlobalCacheDir`, A16-A19).

The failure would have been loud, not silent - exit 3, `staging build FAILED`,
nothing delivered - which is the design working. It would also have blocked
every delivery until someone read the stack trace.

## The lesson: the answer already existed one script over

`scripts/publish-windows-release.ps1` - the MSI/GitHub release path - has
**always** built first and then thrown unless the built exe reported
`$Version+$hash` (lines 74-104). The loop's own delivery path, which runs far
more often and is the one the user actually sees, had neither. The gap was not a
missing idea; it was a second pipeline that never inherited the first one's
discipline. Worth checking for the same shape whenever two paths do the same job
and only one of them is exercised by a human watching.

Regression floor: `zig build test` (`-Dapp-runtime=none` and `-Dapp-runtime=win32`),
`zig build test-agent`, `test\win32\upgrade-no-fork.ps1`, and P1-P3.

`upgrade-no-fork.ps1` needed one real change, and it is the interesting one: its
**L** section drove the launcher at an EMPTY staging directory, which is now
refused before the launch mechanics it is testing are ever reached. It stages a
copy of the built exe instead and passes `-SkipBuild -ExpectedCommit`. The
whitespace guard moved with it: `L23` proves an argv element containing a space
is refused with exit 2, and that check now runs BEFORE the build, so a
mis-quoted path costs zero minutes instead of a full ReleaseFast build.
