# T230 - Never re-execute a dead session command after an agent reset: land on a fresh shell with a notice naming the old command

## Summary

User directive, 2026-07-31, verbatim: *"When the agent resets, resuming
sessions won't work, and yet we try? My preference after an agent reset is to
not try to open previously existing windows. OR, have a message in the console
which says the agent was reset, and land on an open default shell prompt,
allowing the user to choose how to resume. We should not ever re-execute the
commands which were previously ran, but, the console message which says the
session was closed could list the previous command executed so the user can
choose to copy/paste it."*

Today the app does the opposite. `session-relaunch` defaults to `auto`
(`src/config/Config.zig:1238`), so when the agent restarts and materializes its
recorded sessions as dead-but-relaunchable tombstones, each pane RELAUNCHes the
**recorded command** and prints `--- session restarted ---` above the new
output (`src/termio/Remote.zig:934`, policy chosen at
`src/Surface.zig:1067`).

Re-executing a recorded command is unsafe as a default. The command was
recorded in a world that no longer exists (different cwd state, different
files, a build or a migration or an agent loop that must not run twice), and
the user did not ask for it to run again. It is also the behavior the user has
now explicitly rejected.

VERIFIED on box: `grep -c "relaunched dead session"` over
`%LOCALAPPDATA%\ghoztty\ghoztty.log` returns **15**, e.g.
`info(io_remote): relaunched dead session pid=532 ok=true found=true
replayed=true` - three of them in the single boot that followed the
2026-07-31 agent upgrade.

## What to build

A third `session-relaunch` mode - call it `notify` - and **make it the
default**:

- Do **not** respawn the recorded command. Ever.
- Bring the pane up on a **fresh default shell prompt**, in the pane's recorded
  working directory if it still exists (a cwd is not a command; it re-creates
  no side effects).
- Print a notice above the prompt, in the dim divider idiom already used by
  `--- session restarted ---`, that says the agent was reset and the session
  was closed, and **lists the previous command verbatim so it can be copied**.
  Something in the shape of:

  ```
  --- background process was restarted; this session was closed ---
  previous command:  zig build -Doptimize=Debug
  ```

- The old scrollback is not the issue here (the ring/snapshot replay is
  separate and still welcome); the rule is only that no recorded *process* is
  started on the user's behalf.

Keep `auto` and `prompt` as opt-ins so nobody's existing config breaks, but
`notify` is what a fresh install gets, and the docstring must say why.

Applies to BOTH agent-reset paths, which currently share the RELAUNCH:

1. Launch-time restore after the agent restarted (reboot, agent upgrade).
2. The in-place rebuild after a confirmed upgrade (**T229**) - the comment at
   `App.zig:1608` currently states the RELAUNCH-with-divider outcome as the
   promised behavior, and must be updated with it.

Also on the table, and worth deciding explicitly in the task: the user offered
"do not try to open previously existing windows" as an alternative. Prefer the
notice-plus-fresh-shell, because it preserves the layout the user built (which
is real work) while destroying none of their state - but record the choice.

## Validation

- Kill the agent under >= 2 live panes running distinguishable long-lived
  commands, relaunch the app, and assert on box: **no** recorded command ran
  (check pids/process list and the panes' own output), each pane shows the
  notice with its own previous command text, and each pane has an interactive
  prompt that accepts input.
- `session-relaunch = auto` still respawns (the opt-in path is not broken).
- A pane whose recorded cwd no longer exists still comes up on a working
  prompt (fall back to the default working directory, do not fail the pane).
- Unit-level: the notice formatter is pure (command text -> notice bytes) and
  covered in the none-runtime lane, including a session with no recorded
  command and one whose command contains newlines/quotes.

## DONE 2026-07-31

`notify` is implemented and is the default. What landed:

- **`src/termio/session_notice.zig`** (new, pure, 11 unit tests in the
  none-runtime lane): renders the notice. The recorded command is DATA from a
  disk file about to be written into a VT parser, so every C0/C1 control byte
  and DEL becomes a space, the text is truncated at 240 bytes on a UTF-8
  boundary, and the banner variant additionally escapes the markdown
  metacharacters that would let it break out of its code span. Covered:
  control-byte injection, OSC/BEL injection, quotes/backslashes, over-long and
  multi-byte truncation, no-command, whitespace-only-command, short buffer.
- **`src/termio/Remote.zig`** — `RelaunchPolicy.notify`. On a dead+relaunchable
  ATTACH it OPENs a brand-new session (no command) in the tombstone's recorded
  cwd, retires the tombstone, and prints the notice. The snapshot/attach-replay
  blocks are suppressed for it (a fresh session shares no byte stream with the
  old snapshot).
- **Protocol (additive)** — `Attached.argv`, and the agent now sends `cwd`/
  `argv` on the DEAD reply too (`server.zig`). Old agent ⇒ fields absent ⇒ the
  notice omits the command line and the shell opens in the default directory.
  Old app ⇒ ignores the new fields. No version bump; no skew behavior change.
- **`src/config/Config.zig`** — `SessionRelaunch` gained `notify`; it is the
  default; `auto`/`prompt` remain as opt-ins.
- **`PtySpawner.resolveSpawnCwd`** (`agent/pty_child.zig`) — a requested cwd
  that no longer exists falls back to `$HOME`/`%USERPROFILE%` instead of failing
  the spawn. This was a REAL BUG the new test found: deleting a 3-pane layout's
  working directory left every restored pane un-interactive (0/3), because
  `CreateProcessW` fails outright on a missing `lpCurrentDirectory`. It affects
  `auto` (RELAUNCH) just as much as `notify`.

### The notice is written TWICE, on purpose

Measured on box: printing it into the pane's stream is not enough. A fresh
`cmd.exe` under ConPTY opens with its copyright banner and a full-screen
repaint (`ESC[H ESC[2J`) that erases everything already on the pane — the
notice included. Printing it AFTER the shell's paint would instead put it
*below* the prompt the user is typing at. So the same notice also goes up as an
**OSC 7778 sticky pane banner**, a native overlay a screen clear cannot reach.
The two carriers are complementary: the stream text is selectable scrollback
the old command can be COPIED out of (the point of naming it), the banner is
the copy guaranteed to still be on screen.

### Decision recorded (the task asked for it)

The user offered "do not try to open previously existing windows" as an
alternative. **Rejected in favor of notice-plus-fresh-shell**: the layout is
real work the user did, and reopening it destroys nothing as long as no process
is started. Confirmed by the user mid-turn: *"the app can reboot, that's fine,
but windows reopened should not try to rerun commands. they should have some
sort of session was interrupted by an upgrade message, and should leave the
user at a shell prompt for them to decide how to proceed. the message can
contain the last known prompt entered."*
