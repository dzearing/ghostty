# T657 - A refused ATTACH is still silent, so a resumed pane blames a timeout the way a refused OPEN used to

## In plain terms

T469 fixed the case where the background terminal service refuses to start a
NEW pane: it now says why, straight away. Taking over an EXISTING session -
resuming one from the machine chooser, or a window coming back after a restart -
still has the old behaviour. If that is refused, the pane sits blank for ten
seconds and then says a timeout happened, which tells the user nothing about
what went wrong or what to do.

## Goals

- [x] A refused ATTACH fails in well under a second, not after a 10s timeout
- [x] The pane names the reason (session gone, held by another viewer, ...)
- [x] An older agent and an older app both still work across the change

## Summary

Found while landing T469. `OPEN` now has a negative reply (`OPEN_FAILED` 0x06,
capability-gated); `ATTACH` does not.

**Correction, made while building this (2026-08-10).** The premise above was
half right, and the half it got wrong changed the design. Reading
`Server.handleAttach`: it already ANSWERS the refusals that matter, at once —
`ATTACHED{status: not_found}` on the control channel, `ATTACHED{status: dead}`
on the session channel — and has on every agent that ever shipped. The only
genuinely silent ATTACH path is the malformed-payload parse
(`protocol.parseJson(...) catch return`), which really does cost the client the
full `rpc_open_timeout_ns`.

So the 10 s timeout was the small half. The USER-VISIBLE half is entirely
client-side, and it is the second paragraph of the original summary:
`Remote.threadEnter` turns every one of those answered refusals into a bare
`error.RemoteAttachFailed`, so `termio.Thread` paints "The underlying shell or
command was unable to be started… exhausting a system resource" — the exact
text a teeth-check reproduced, and a sentence true of none of these failures.

## Approach

Two halves, deliberately split by what each can carry:

1. **`ATTACH_FAILED` (0x07) covers only what `ATTACHED` cannot express** —
   today a payload the agent could not parse, tomorrow any hard refusal with no
   `Attached` to fill in. `protocol.zig` gains the opcode,
   `capability.attach_failed`, `Negotiated.attach_failed` and the `AttachFailed`
   payload; `server.zig` gains `sendAttachFailed` on the parse path;
   `connection.zig` accepts it as the `.attached` slot's terminal reply and
   surfaces `error.AttachRefused` via `attachChannelRefusable`.
   `OpenFailedCopy` became `RefusalCopy` (verb-neutral now it has two users; the
   old name is kept as an alias).

   It is deliberately NOT a second vocabulary for `not_found`/`dead`/
   `attached_elsewhere`. Saying those a second way would be two spellings of one
   fact across a compatibility boundary, and it would strand every caller that
   reads `AttachOutcome.status` (the chooser, Restore All) behind a new error.

2. **The user-facing sentence is derived CLIENT-side from the status the agent
   already sent** — new pure `src/termio/attach_failed_notice.zig`, out through
   the existing `Backend.bringUpNotice()` seam. This is the load-bearing half:
   it needs no capability and therefore works against an agent of ANY age, which
   arm B of the acceptance script asserts directly.

**Reachability, and the seam it needed.** The win32 launch restore asks the
agent for its roster first and gives a leaf whose session is not listed a null
id, so it OPENs fresh rather than ATTACHing (T89g) — a good rule that leaves
this failure to the case where the probe DID NOT LAND (a slow or wedged agent
past `restore_probe_timeout_ns`). That is a real production branch but a racy
one to hit from a script, so `AttachProbe.take` gained the test seam
`GHOZTTY_RESTORE_PROBE_UNKNOWN=1`, which forces the liveness tri-state to
UNKNOWN and nothing else. Same justification as T469's two agent seams: without
it this path stays unobservable on box, which is why it shipped silent.

## Validation criteria

- [x] A refused ATTACH brings the pane up with a readable message in under 2 s,
      and `+read` returns that message. — `test/win32/agent-attach-refused.ps1`
      arm A: measured **314 ms**, message read back via `+read`.
- [x] The message names the reason and not a timeout. — same arm: matches
      "no longer has the session" and "open a new one", and asserts the absence
      of both `Timeout` and "exhausting a system resource".
- [x] With `GHOSTTY_AGENT_SUPPRESS_CAPS=attach_failed` the pane still comes up.
      — arm B, and the criterion CHANGED with the design: it comes up with the
      SAME message in 274 ms, not the old timeout, because the `not_found`
      sentence never needed the new frame. That equivalence is the assertion.
      The frame's own skew (silence ⇒ the client's timeout) is asserted in the
      server + connection unit tests, where the malformed ATTACH can be built.
- [x] Both skew directions asserted in the `negotiate` and server unit tests. —
      `protocol.zig` "negotiate: attach_failed capability is the intersection…",
      `server.zig` "ATTACH the agent cannot parse…" / "…gets today's silence…",
      `connection.zig` "attachChannelRefusable…" ×2 + "an agent too old to
      refuse out loud still just times out" + "acceptsReply: each negative reply
      answers its own request".
- [x] The zig floor lanes and `test/win32/agent-open-refused.ps1` stay green.
- [x] Teeth-checked twice: disabling `acceptsReply`'s new arm reddens 3 unit
      tests; disabling `recordAttachFailure` reddens arms A and B with the exact
      pre-fix text ("error.RemoteAttachFailed … exhausting a system resource").
