# T657 - A refused ATTACH is still silent, so a resumed pane blames a timeout the way a refused OPEN used to

## In plain terms

T469 fixed the case where the background terminal service refuses to start a
NEW pane: it now says why, straight away. Taking over an EXISTING session -
resuming one from the machine chooser, or a window coming back after a restart -
still has the old behaviour. If that is refused, the pane sits blank for ten
seconds and then says a timeout happened, which tells the user nothing about
what went wrong or what to do.

## Goals

- [ ] A refused ATTACH fails in well under a second, not after a 10s timeout
- [ ] The pane names the reason (session gone, held by another viewer, ...)
- [ ] An older agent and an older app both still work across the change

## Summary

Found while landing T469. `OPEN` now has a negative reply (`OPEN_FAILED` 0x06,
capability-gated); `ATTACH` does not. `Server.handleAttach` still `return`s on
the paths where it will not attach, so the client's parked `.attached` slot
waits out the full `rpc_open_timeout_ns` (10 s, `src/remote/connection.zig`) and
fails with a bare `error.Timeout` - and by-type RPCs serialize on
`open_rpc_mutex`, so a Restore All of N panes pays that 10 s N times, in turn.

`Remote.threadEnter` has its own sibling of the same hole: the
`.dead(!relaunchable)` / `.not_found` / `attached_elsewhere(!force)` arm logs
`attach did not yield a live pane status=... ` and returns
`error.RemoteAttachFailed`, so even when the agent DID answer, the reason it
gave never reaches the pane.

## Approach

Everything T469 built is reusable; this is the second half of the same shape.

1. `protocol.zig`: `attach_failed = 0x07` (A->C, `{reason, detail}`) +
   `capability.attach_failed` + a `Negotiated.attach_failed` flag, following
   `open_failed` exactly. Reason tokens are the ATTACH vocabulary
   (`session_not_found`, `attached_elsewhere`, `not_relaunchable`, ...), not
   OPEN's.
2. `server.zig`: reply on the refusal paths of `handleAttach`, gated on the
   negotiated capability; silence otherwise (an unknown opcode is a fatal
   framing error to an older app).
3. `connection.zig`: extend `acceptsReply` so `.attach_failed` is a terminal
   reply for a parked `.attached` slot, and surface `error.AttachRefused` with
   an `OpenFailedCopy`-shaped carrier. (Consider renaming that type to something
   verb-neutral when the second user lands.)
4. `Remote.zig`: `recordOpenRefusal`'s sibling, plus the same treatment for the
   already-answered-but-unreported arm above. The pane message goes through
   `open_failed_notice`'s sibling and out via the existing
   `Backend.bringUpNotice()` seam - no new carrier needed.

## Validation criteria

- [ ] A refused ATTACH brings the pane up with a readable message in under 2 s,
      and `+read` returns that message. (`GHOSTTY_AGENT_MAX_SESSIONS` will not
      produce this one - attach against a session id the agent does not have
      will.)
- [ ] The message names the reason and not a timeout.
- [ ] With `GHOSTTY_AGENT_SUPPRESS_CAPS=attach_failed` the pane still comes up
      the old way - timeout, generic message, no hang, link intact.
- [ ] Both skew directions asserted in the `negotiate` and server unit tests.
- [ ] The zig floor lanes and `test/win32/agent-open-refused.ps1` stay green.
