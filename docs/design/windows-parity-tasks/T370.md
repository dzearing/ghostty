# T370 - The +list golden tests claim to match the Mac Swift encoder but nothing enforces it

## Summary

`src/apprt/ipc/list.zig` opens with *"shape-matched to the Mac server's Swift
encoder (IPCMessage.swift) ... The golden tests below pin the shape; keep them
in sync with any Mac change."* The second sentence is a request, not a
mechanism, and it had already been missed: Mac's `TerminalData` has encoded
`type` and `url` **unconditionally** (`IPCMessage.swift:103-104`) since the
viewer work landed, and the Zig encoder emitted neither. Four golden tests
asserted the drifted shape as correct.

T90b closed that instance. Nothing stops the next one.

## Details

This is T257's lesson in a second subsystem: two independent copies of one
datum, and no way to notice when they disagree. There it was the chrome
geometry across five scripts; here it is the `+list` wire shape across a Swift
encoder and a Zig encoder that must produce **byte-identical** JSON, because
one client (`src/cli/list.zig`, the `ghoztty` skill, every `+list --json`
consumer) reads both.

The drift is silent in both directions and neither lane can see it:

- A Mac-seat commit adds a field to `TerminalData`. The win32 lane stays
  green, and a Windows client that reads the new field sees it absent.
- A win32 commit adds a field to `List.Terminal`. The Mac build never
  compiles that file's tests as a shape check, so the Mac server keeps
  omitting it.

What made this one recoverable was luck: T90b happened to touch the very
fields that had drifted.

Decide the mechanism, then build it. Candidates, cheapest first:

1. **A field-name manifest checked from the Zig test** - read
   `macos/Sources/Features/IPC/IPCMessage.swift` from the repo (it is checked
   in and reachable from both seats), extract `TerminalData`'s `CodingKeys` +
   the `encode(to:)` call order, and assert it equals the Zig writer's field
   order. Catches added/removed/reordered fields; does not catch a changed
   value shape.
2. **A committed golden JSON fixture** both sides assert against - the Swift
   side gets an encoder test, the Zig side keeps `expectEqualStrings`. Strong,
   but it needs a Mac-seat commit to add the Swift half, so it is a two-seat
   task.
3. **A `seat: mac` companion task** that only adds the Swift encoder test,
   with this task owning the Zig half.

Weigh (1) against (2) rather than defaulting: a name/order check that runs in
the `none` lane on both seats is worth more than a stronger check only one
seat runs. Whatever lands, delete the "keep them in sync" comment - a rule
with an enforcer does not need to ask.

Note the one deliberate divergence to encode rather than flag: `background_tint`
is win32-only (T67) and has no Mac counterpart, so the check needs a way to
say "extra on purpose" without weakening to a subset test.

*Validation:* the check FAILS when a field is added to one encoder and not
the other (prove it by adding one, running the lane, and reverting - a drift
detector that has never detected a drift is an assertion about nothing); both
test lanes green.
