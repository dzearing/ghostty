# T42 — Remote sessions drop the user's env/PATH (Phase G)

## Summary

Remote sessions: user env/PATH missing

## Details

User report 2026-07-13: a remote Windows session opened from the Mac had
none of the user's PATH entries. Likely cause: `ghoztty-agent` runs as a
service/background process whose environment block lacks the interactive
user's registry env (HKCU Environment), and the ConPTY shell inherits the
agent's env. Investigate: agent should build the user token environment
(CreateEnvironmentBlock / reading HKCU+HKLM Environment and merging, as
Windows logon does) for spawned sessions.

*Validation:* remote session's `echo %PATH%` matches an interactive local
shell's PATH (including user-scope entries like the Ghoztty install dir).

## Root cause (VERIFIED by reading the code)

The hypothesis in the Details above was right, and it is not specific to how
the agent was started. `PtySpawner.init` captures `std.process.getEnvMap` ONCE
(`pty_child.zig:799`) and every child's environment is a clone of it
(`:914`). So a session's environment is a snapshot of **whoever started the
agent** — an HKCU `Run` entry, a scheduled task, an SSH bridge, an MSI custom
action, a self-update relaunch — and nothing ever reconciles it with the
user's own registry environment.

The local agent papers over part of this: `OPEN.env` (T04a) forwards an
allowlist from the app, which has a real user environment because Explorer
launched it. **`open.env` is empty for a cross-machine window** by design (the
far machine may be a different OS), which is exactly why the Mac→Windows
remote session was the case the user hit.

This is the same class of defect as the working directory, already written
down in `termio/Remote.zig:openWorkingDirectory`: *"an agent started by the
HKCU `Run` autostart entry inherits `C:\WINDOWS\system32`"*. That comment was
about the cwd; this task is the environment block.

## What shipped (2026-08-02)

**`src/os/user_env.zig` (new)** reads the two keys Windows composes a logon
environment from — HKLM `…\Session Manager\Environment` and HKCU
`Environment` — expands `REG_EXPAND_SZ` values, and overlays them onto the
child's environment. Applied per spawn in `pty_child.zig:spawnChild`, before
TERM/COLORTERM and before `OPEN.env`, so forwarded vars still win.

**The rule is ADDITIVE ONLY**, and that is the load-bearing decision:

- `Path` is MERGED — the process's own value first, then the registry entries
  it is missing (deduped case-insensitively through `path_env.normalize`).
  Existing entries keep their POSITION, so a harness that deliberately
  prepends a shim directory still shadows what it meant to shadow. Faithful
  logon order would have been `system;user` with the inherited value
  discarded; that would have silently re-ordered PATH resolution under every
  test harness on the box for no gain.
- Every other registry variable is applied **only if the environment does not
  already define it** (user key before system key, matching logon precedence).

The defect is *absence*, not staleness, and the agent's own environment is
authoritative for anything it already carries. Being additive is also what
makes it safe to run on **every spawn**, which is what keeps it fresh: a PATH
edit made after the agent started reaches the next session, where a
once-at-startup overlay would have inherited the very staleness it fixes.

`GHOZTTY_USER_ENV=0`/`=off` disables it — an escape hatch, and the negative
control the acceptance script needs.

**`src/apprt/win32/path_env.zig` → `src/os/path_env.zig`.** The PATH-entry
normalization T70 wrote for the self-heal is exactly what the merge needs, and
a second copy of `normalize`/`eqlDir` is the four-copies-four-chances-to-be-
wrong trap T257 wrote down. Moved rather than copied; three import lines
changed, and its unit tests now run in **every** lane (via `os/main.zig`'s test
block) instead of only the win32 one.

POSIX is untouched by design: it has no registry, and a POSIX agent spawns its
shell login+interactive (`-lic`), which is that platform's way of getting the
user's real environment.

## Evidence (2026-08-02, on the box)

**`test/win32/agent-user-env.ps1` (new) — ALL PASS.** It reproduces the
condition without a second machine: a real `ghoztty-agent` started with its
PATH **stripped** to `%SystemRoot%\system32;%SystemRoot%`, driven over a named
pipe by `remote-test-client`, with the spawned `cmd.exe` dumping its whole
environment via `set > <file>`. A file, not the PTY — an 80-column ConPTY wraps
a long PATH mid-entry, and the assertion would have been measuring the terminal
instead of the environment.

```
  marker (user PATH entry): C:\Users\David\AppData\Local\Programs\Python\Python312\Scripts
== 1: overlay ON  ... PASS dumped PATH contains the user entry
== 2: negative control (GHOZTTY_USER_ENV=off)
                  ... PASS dumped PATH does NOT contain the marker
== 3: system32 is still the FIRST entry; no entry appears twice
ALL PASS
```

Section 2 is what makes section 1 mean anything: the same run with the overlay
off leaves the stripped PATH stripped, so the marker's presence is the fix and
not a PATH that was never stripped.

**Standing floor:** `zig build test -Dapp-runtime=none` exit 0, `zig build test
-Dapp-runtime=win32` exit 0, `zig build test-agent` exit 0, P1/P2/P3
ACCEPTANCE: ALL PASS, and `path-selfheal.ps1` ALL PASS (13 assertions) because
the file move touched its module.

10 pure unit tests in `os/user_env.zig` cover the merge (order, empties,
case/trailing-separator dedupe), the additive rules (existing var untouched,
missing var added, user key beating system key, PATH key keeping the spelling
the environment already used so the child never gets two), the empty-key guard,
and the `GHOZTTY_USER_ENV` spelling.
