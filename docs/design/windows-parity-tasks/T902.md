# T902 - Startup job-escape detection is heuristic (first-job flags OR pane lineage); an exact agent-job membership probe would close the nested-killer blind spot

## In plain terms

Ghoztty now moves itself out of a process group that would take it down with
the background service. It decides whether it is in danger from two clues —
what Windows reports about the first group it joined, and whether it was
started from inside a Ghoztty pane. Those clues cover every case seen so far,
but a case is constructible where both clues miss and the app would still die.
This task replaces the clues with a direct question: "am I inside the
service's group, yes or no."

## Summary

T675's `job_escape.shouldEscape` fires on `in_job AND (first-job flags carry
KILL_ON_JOB_CLOSE OR pane lineage via $GHOZTTY_PANE_ID)`. Two soft spots,
both documented in `job_escape.zig`:

- **Nested-killer blind spot**: with nested jobs the NULL-handle
  `QueryInformationJobObject` answers only the FIRST job a process joined. A
  kill-on-close job behind a limitless compat job, on a launch with no pane
  lineage (e.g. from another terminal whose own job sits first), is invisible.
  Measured while building T675's harness: a real pane chain answered `0x0`
  while genuinely inside the agent's `0x2000` job.
- **Lineage over-fire**: a pane-launched app escapes even if the agent's job
  is somehow absent from its chain — harmless (one wasted re-exec) but
  imprecise.

The exact probe: get a handle to the AGENT's PTY job and ask
`IsProcessInJob(self, that_job)` directly. There is no public enumerate-my-jobs
API, so the handle has to come from the agent. Candidate mechanisms, none
validated:

- **Named job object** — `pty_child.zig` creates the job with a lineage-derived
  name; the app opens it by name. MUST incorporate the same per-instance
  isolation as the agent pipe (`GHOZTTY_AGENT_INSTANCE`), because
  `CreateJobObjectW` with an existing name OPENS the existing job — a harness
  agent sharing the dev agent's job name would merge their kill domains, which
  is worse than the blind spot.
- **Handle duplication** — the agent advertises its job handle value in
  `port.json`; the app opens the agent with `PROCESS_DUP_HANDLE` and
  duplicates it. No namespace risk, but the info file is a compatibility
  surface (docs/claude/sessions.md rules apply) and a stale file must degrade
  to the current heuristic, never to a wrong answer.

Whichever lands, the heuristic stays as the fallback for an old agent that
does not expose its job.

## Validation criteria

- [ ] The app's startup probe answers membership against the agent's actual
      job, not a heuristic, when a current agent is running
- [ ] A harness agent's job can never merge with the dev/installed agent's
      (negative test on the naming/duplication path)
- [ ] Old-agent fallback: with the exposure absent, behavior is exactly
      T675's heuristic (acceptance re-run green)
- [ ] `test\win32\job-escape-startup.ps1` extended or joined by a harness for
      the exact probe; floor green
