# T1051 - ipc-p3.ps1 failed 9 of 15 assertions once, then passed four consecutive runs including the same back-to-back shape

## Summary

During the T345 turn on 2026-08-21 the P3 acceptance floor reported '9 FAILURE(S) (6 assertions passed)' on the run immediately after ipc-p2.ps1. Four subsequent runs were ALL PASS (16 assertions), including a deliberate reproduction of the exact back-to-back p2-then-p3 sequence. A good run has 16 assertions and the bad one totalled 15, so it did not merely fail checks - it got partway through setup and cascaded, which points at the launch or the isolation preflight rather than at any of +read / +set-state / +rearrange / OSC 7777. Nothing in the T345 change is in P3's path (it touched only the tracker CLI, the dashboard payload and docs), and the floor's four zig lanes were green in the same turn. The failing run's detail was lost: it was piped to a grep that matched nothing rather than redirected to a file, so there is no log to read - which is itself the first thing to fix. What to do: teach the script to write its own timestamped transcript on every run the way floor-lane.ps1 does, so the next occurrence is diagnosable instead of a number; then look at what a partial setup leaves behind, since a launch that half-succeeds is the shape that fits 15-of-16.
