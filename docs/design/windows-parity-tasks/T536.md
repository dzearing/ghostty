# T536 - Flaky crash: 'inbound DATA routing' test panics in inbound_ring.push with undefined-memory index

## Summary

The win32 test lane intermittently crashes in
`test "inbound DATA routing: bytes land in the right channel; unknown is
dropped"` (`src/remote/connection.zig:3522`): a panic inside
`inbound_ring.zig:138` `push` —

```
thread 36184 panic: index out of bounds: index 12297829382473034411, len 12297829382473034410
D:\git\ghoztty\src\remote\inbound_ring.zig:138:34: in push
        @memcpy(self.buf[start..][0..first], bytes[0..first]);
```

Both numbers are the `0xAAAA…` undefined-memory fill pattern (0xAAAAAAAAAAAAAAAB / …AA), so
some field of the ring (its length or write index) is being READ WHILE STILL
UNDEFINED — either an init path that skips a field, a use-after-free, or a
race with another thread still pushing while the ring is torn down. That
shape is a real bug wearing a test flake's clothes: the same undefined read
can happen in production attach/replay.

## In plain terms

One of the automated tests for remote sessions crashes once in a while, and
the crash pattern says some memory is being read before anything was ever
written to it. Today that shows up as a test lane going red for no visible
reason; the same underlying mistake could corrupt or crash a real remote
terminal session, so it needs a root cause, not a retry.

What the investigation found: the remote-session plumbing itself follows its
teardown rules correctly everywhere — but this machine has a separately
tracked gremlin (T443) that randomly corrupts running test programs under
load, and this crash matches that gremlin's fingerprint. So the fix here is
threefold: a tripwire in the exact spot that crashed, which from now on says
*by name* whether the code misused freed memory or the gremlin struck; repairs
for three real (if latent) cleanup mistakes in the test scaffolding that the
audit turned up; and the evidence trail linking the incidents to T443.

## Goals

- [x] Account for every way the crashing code path can touch freed memory,
      and either find the bug or prove the teardown rules hold.
- [x] Make the next occurrence self-diagnosing (the liveness tripwire in the
      ring's push/pop).
- [x] Fix the latent cleanup bugs the audit found in the test scaffolding
      (stack ring freed as heap; leaked helper threads writing into dead
      stack frames).
- [x] Full floor green + repeated-run confidence, with run counts recorded.
