# T665 - the ViewerPane host-floor test fails the win32 lane when the WebView2 runtime is replaced under it

## Summary

2026-08-09: 'apprt.win32.ViewerPane.test.host floor: a real controller on a real window, on this box' failed with [webview2] (warn): environment creation failed hr=0x80004005 env=null, and the same lane passed on an immediate re-run. Two WebView2 runtime versions were resident on the box at the time (151.0.4129.59 and .72), i.e. the runtime was being replaced mid-run. A live-runtime test that cannot tell 'the feature is broken' from 'the OS component was mid-upgrade' spends a whole floor run to say nothing - it should retry the environment creation (or skip with a named reason) rather than report a red lane. Found while validating T562, whose change touched no Zig at all.

## In plain terms

One of our automated checks opens a real browser view, the same one the viewer
panes use. When Windows happens to be replacing that browser component in the
background, the check could not tell "our viewer is broken" from "Windows is
mid-upgrade", so it reported a failure and a whole test run was spent saying
nothing. It now asks again a couple of times, and if the component still will
not start, it says so by name and steps aside instead of crying wolf.

Nobody using the terminal sees this directly - what they get is that a red
test run means something is actually wrong, which is the only way a test run
is worth reading.

## Goals

- [x] Retry an environment the runtime merely refused, and take a permanent
      "this box has no runtime" answer immediately.
- [x] Skip with the reason named rather than failing the lane when the retries
      run out.
- [x] Make that decision testable without a live runtime, and test it.

## Validation criteria

- [x] The environment refusal this was filed over (`hr=0x80004005`) classifies
      as transient, so the floor asks again instead of reporting a red lane.
- [x] A permanent answer (no runtime installed, a DLL that will not load) is
      taken on the FIRST reply - the floor never spends its deadline waiting
      for an installer to run itself.
- [x] The retry cap is a stop, so the loop terminates rather than retrying a
      genuinely dead runtime forever.
- [x] That policy is proven by a test that does NOT need a live WebView2
      runtime on the box - the decision is a function of values, not a branch
      that only executes when the runtime misbehaves.
- [x] The host floor test is the policy's one caller, so the shipped behaviour
      and the tested behaviour cannot drift apart.
- [x] The win32 lane is green with the change in.

### How each was verified

- The `hr=0x80004005` path: `webview2.zig:222` maps that HRESULT to
  `create_callback_failed`, and `isTransient()` returns true for it - asserted
  by `test "a missing runtime is not a transient failure, a refused start is"`.
- Retry / cap / permanent-answer: `test "the floor retries a runtime that
  refused it, and never one that is absent"` (webview2.zig), green in the
  win32 lane. It was run RED first as its own negative control - flipping the
  `runtime_not_found` assertion produced `'apprt.win32.webview2.test.the floor
  retries a runtime that refused it, and never one that is absent' failed` at
  webview2.zig:198 - so the test is reached and can score red, not merely
  present.
- No live runtime needed: the test takes `Failure` values, so it runs on any
  box; the `inline for` over the enum means a new variant cannot be added
  without answering.
- One caller: the host floor loop in `ViewerPane.zig` now calls
  `webview2.shouldRetryEnvironment` with `webview2.floor_max_attempts` instead
  of its own inline `isTransient()`/cap pair.
- Lanes: `scripts\floor-lane.ps1 -Lane all` -> `lib#1=PASS none#1=PASS
  win32#1=PASS agent#1=PASS`, 2026-09-08. Acceptance harnesses the edit made
  due, all green and re-stamped: `printclient-audit` (8), `test-reach-audit`
  (14), `viewer-close` (44), `viewer-nav-pin` (24), `viewer-worktree-port`
  (23).
