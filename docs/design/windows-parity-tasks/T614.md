# T614 - An Activity Monitor panel keeps sampling a retired transport after its window reconnects

## In plain terms

If the link to a remote machine drops and comes back, the terminal window
recovers — but an Activity Monitor panel watching that machine stays stuck on
"Couldn't connect" forever, even though the window right next to it is working.
Closing and reopening the panel is the only way out.

## Goals

- [ ] A panel borrowing a window's connection follows that window onto the new
      connection when the reconnect ladder swaps transports.
- [ ] It resumes sampling on its own, with no reopen.
- [ ] A regression arm proves it (drop the agent, let it come back, assert the
      panel samples again).

## Summary

A panel borrows a **connection pointer**, not a window. When
`RemoteReconnect.applySwap` re-points the window's panes onto a freshly dialed
transport, the old one is RETIRED — shut down, kept alive until window teardown
so nothing dangles. The panel is still holding it, so every sample from that
moment fails and the card reads `failed`, permanently, while the window itself
is healthy.

Nothing is unsafe here (that is exactly what "retired, never destroyed" buys),
and T301's `ActivityMonitor.releaseBorrowed` covers the FREE at window teardown.
This is the other half: the swap should hand the panel the new connection the
same way it hands the panes theirs.

## Evidence

By inspection, not yet reproduced on the box:

- `RemoteReconnect.retire` calls `shutdownRetired(conn)` — the pointer the panel
  holds is deliberately left valid and permanently dead.
- `ActivityMonitor.RemoteConn` stores `conn` with `dialed == null` for a borrow
  and nothing re-resolves it; `beginMetrics`/`buildSnapshot` use it directly.
- Reachable two ways since T301: the palette entry (T296) and a carousel switch
  back to a machine a window is on.

## The shape of the fix

`applySwap` already knows the window and the new transport, so the natural
place is a sibling of `releaseBorrowed`:
`ActivityMonitor.rebindBorrowed(old_conn, new_conn)` — unsubscribe metrics on
the old, re-point `remote_conn`, `beginMetrics` on the new, `rebuildCards`. The
ordering constraints are the ones T301 already learned: do it after the pane
re-attach, and never while the state handler is mid-install.

Consider whether a borrow should store a re-resolvable KEY rather than a
pointer, so this class of drift cannot recur — but the sample worker needs a
stable pointer for the length of an RPC, so a key alone does not remove the
rebind, it only moves it.

## Validation criteria

- [ ] With a panel borrowing a remote window's connection, kill and restart the
      agent: the window reconnects AND the panel resumes sampling (root pid ==
      the agent's new pid) without being reopened.
- [ ] The panel's card leaves the `failed` state on its own.
- [ ] No leak or double-free across the swap (the retired transport is still
      freed exactly once, at window teardown).
- [ ] Both `zig build test` lanes plus `zig build test-agent` green; P1-P3 ALL
      PASS; `test/win32/activity-monitor-remote.ps1` ALL PASS.
