# T1370 - floor-lane.ps1 launched from the Bash tool crashes zig.exe in every lane, and it reads as a broken toolchain

## In plain terms

The command that runs all of the project's test suites fails instantly and
completely when it is started one particular way, and the failure it prints
looks exactly like the compiler itself being broken. Nobody is hurt by it
directly, but an agent that hits it spends its turn chasing a toolchain
problem that does not exist instead of doing the work.

## Summary

Observed 2026-09-05 in T1369's turn. Running

```
powershell -NoProfile -File scripts\floor-lane.ps1 -Lane all
```

through the Bash tool (Git Bash, MSYS environment) fails **all four lanes** in
about five seconds each, with the retry burnt as well:

```
CRASH 09:37:36 zig.exe pid=0xD4F4 0xc0000005 STATUS_ACCESS_VIOLATION in zig.exe+0x00000000000394d8
COMPILER CRASH: lane none is red because the toolchain died, not because the code is broken
FLOOR SUMMARY: lib#1=FAIL none#1=FAIL win32#1=FAIL agent#1=FAIL
FLOOR NOT GREEN
```

The same script, same tree, same `ZIG_GLOBAL_CACHE_DIR`, run from the
PowerShell tool moments later, is `lib#1=PASS none#1=PASS win32#1=PASS
agent#1=PASS`. So the tree was green throughout and the whole run was a false
red produced by the launch path.

Every crash is at the same address (`zig.exe+0x394d8`), which says it is a
deterministic environment difference rather than a flake — the likely suspects
are the MSYS environment the Bash tool exports (a `PATH`, `TMP`/`TEMP`,
`HOME`, or `MSYSTEM` that zig's build runner reads), not the cache-drive trap
(`ZIG_GLOBAL_CACHE_DIR` was on `D:` and `build.zig` refuses that case loudly
rather than crashing).

The cost is not the failure, it is that the failure is **articulate and
wrong**: `floor-lane.ps1` already recognises the crash, says "the toolchain
died, not the code", retries once, and then reports a considered verdict. A
turn that believes it goes looking for a broken zig install.

## Goals

- [ ] Identify what in the Bash tool's environment kills `zig.exe` (bisect the
      exported environment against a known-good PowerShell launch)
- [ ] `floor-lane.ps1` either normalises that environment itself, or REFUSES
      to run under it with a one-line "launch this from PowerShell" message —
      a refusal beats a false red
- [ ] The refusal (or the fix) is demonstrated, not asserted

## Validation criteria

- [ ] With the offending environment reproduced deliberately, `floor-lane.ps1`
      does not report `FLOOR NOT GREEN` over a green tree — it either passes or
      names the launch path as the problem.
- [ ] A normal PowerShell launch is unchanged (all four lanes still run).

## Notes

Filed from T1369's turn. Workaround for now: run `floor-lane.ps1` from the
PowerShell tool, never from Bash.
