# T802 - Double-clicking a link in a pane selects only the word - the link selection is overwritten immediately

## In plain terms

Double-click a URL or a file path in a terminal pane to grab it, and you get
back a piece of it — `https` out of `https://example.com/a`. On the Mac the
same double-click selects the whole link, which is the point of the gesture.
The terminal here DOES recognise the link; something wipes the selection and
re-selects the plain word a fraction of a second later.

## Summary

Found while building T757's acceptance script, which originally used the
double-click as its oracle.

✓ VERIFIED on the box (2026-08-12, instrumented Debug build): on a
double-click the core takes the link path — `Surface.zig`'s click-count-2
branch calls `linkAtPin(pin, null)`, which requires no modifier — and it
SUCCEEDS. The log showed, for a pane row holding `https://example.com/a`:

```
T757DBG dblclick links=1
T757DBG line=[https://example.com/a]
T757DBG match=[https://example.com/a] contains=true
T757DBG linkAtPin ok found=true
```

and yet `ctrl+c` immediately afterwards put `https` on the clipboard — a
`selectWord` result (`:` is a word boundary, `\` `/` `.` are not). So the
link selection is made and then replaced.

Leading hypothesis, unproven: a `WM_MOUSEMOVE` arriving while the left
button is still down drives the core's word-granularity DRAG
(`dragLeftClickDouble`) at the same pin, which re-selects exactly the word.
`Send-TestMouse` posts a move ahead of every gesture, so a harness artifact
is NOT ruled out — establish first whether a real user double-click on a
real desktop reproduces it, because that decides whether this is a product
defect or a harness one, and the two need opposite fixes.

Same instrumentation reproduces it: log in the click-count-2 branch and
compare against what the clipboard holds after `ctrl+c`.

## Root cause

The win32 apprt forwards a cursor position to the core ahead of EVERY mouse
button message (`handleMouseButton` in `src/apprt/win32/Surface.zig` — every
Windows mouse message carries a client point, and forwarding it is what makes
a press land on the right cell when no `WM_MOUSEMOVE` preceded it). With the
left button still down, the core reads a position update as a DRAG. So the
button-up that ENDS a double-click arrived as a zero-distance word-drag:
`dragLeftClickDouble` re-derived the word at the clicked cell and replaced the
link the press had just selected. `:` is a word boundary, hence `https`.

**Product defect, not a harness artifact.** The harness posts one move ahead
of the gesture, but that lands before the first press, when no button is
down; nothing is posted between the second press and its release. And the
release is unconditional in a real double-click too. macOS never had this —
`mouseUp` in `SurfaceView_AppKit.swift` sends no position at all.

The same shape was clobbering `ctrl`+triple-click: `dragLeftClickTriple` at
the click pin re-selects the LINE over the command OUTPUT the press selected.

## Fix

Two halves, one per layer:

- **Core** (`src/Surface.zig`): `samePin` — a double/triple-click drag that
  resolves to the very cell the click landed on returns without recomputing
  the selection. Re-deriving it from that cell can only reproduce what the
  click already made, or destroy something richer. This also covers the
  cross-platform case the win32 half cannot: a trackpad double-tap that
  wobbles a pixel INSIDE the clicked cell.
- **win32** (`src/apprt/win32/Surface.zig`): `cursorMoved` — a button message
  only forwards its point when that point is news, so the redundant drag
  event is no longer manufactured in the first place.
