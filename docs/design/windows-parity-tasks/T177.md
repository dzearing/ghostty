# T177 - Machine chooser: the detail action row is missing Activity (and Restore All)

## Summary

Found while building T176's `...` menu, by reading the Mac detail header the
menu lives in. Mac's action row (`MachineChooserView.detailHeader`,
`MachineChooserView.swift:456-494`) is:

```
[ New Window ]  [ Restore All ]?  [ Activity ]?  [ ... ]
```

- **New Window** - shipped (T175).
- **`...`** - shipped (T176).
- **Restore All** (`resumeAllAvailable`) - "Rebuild this machine's full window
  layout here". Belongs with cross-machine session browsing, i.e. **T146**;
  this task does NOT claim it, it just records that the row is short two
  buttons, not one.
- **Activity** (`onActivityMonitor(machine)`) - "Open Activity Monitor for
  \<machine\>". **Not filed anywhere before this task.** That is the gap.

So the Windows detail row is currently `New Window` + `...` where Mac has up to
four controls, and the layout in `chooser_layout.zig` only reserves slots for
the two that exist.

## Details

Scope this to the **Activity** button, and only after establishing what it
opens on Mac - `onActivityMonitor` is a closure the chooser is constructed
with, so the panel it presents lives outside `MachineChooserView` and has to be
traced before any port is designed. Do that reading FIRST; if the Mac side
turns out to be a per-machine session/process panel that depends on browsing a
remote agent's state, this folds into T146 and should be closed as such rather
than built twice.

`chooser_layout.layout` currently hardcodes `primary_btn` then `menu_btn` at a
fixed 8 DIP gap. Adding a third and fourth conditional button means the action
row wants to be laid out as a *run* (leading edge + gap, each button sized to
its own caption) rather than as named slots, so `menu_btn` stops being pinned
to `primary_btn.right`. That refactor is part of this task, and it is pure -
`chooser_layout` is fully unit-tested in the none lane.
