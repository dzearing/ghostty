# T382 - parity-tasks next resolves deps through a skipped(split) parent, so it hands out a task whose real prerequisites are still todo

## Summary

`next` offered T90e (`deps: [T90d]`) as this seat's next task. T90d is
`skipped(split -> T372, T373, T374, T375)`, and a `skipped` status counts as
resolved — so the dep looked satisfied even though T374 and T375 were still
`todo`. T90e cannot be started before them: it renders a file INTO a viewer pane
that, until T374, nothing could construct.

## Details

Evidence, 2026-08-02: `parity-tasks.ps1 next` printed
`NEXT: T90e - File viewers: offline markdown/code rendering (Phase K)` with
`deps=T90d`, while `T374.md` and `T375.md` both carried `status: "todo"`. The
turn worked T374 instead, by hand.

This is not a one-off. Splitting a task before starting it is the standing
answer to the context rule, so `skipped(split -> ...)` parents are common and
their children always have HIGHER ids than the tasks that depend on the parent.
Ordering by id therefore offers the dependent task first, every time.

The fix is a choice between two, and picking one is part of the task:

1. **Resolve through the split.** Parse the `skipped(split -> T…, T…)` status
   for child ids and treat the parent as satisfied only when every child is.
   The status string is already the only place the split is recorded, and it is
   written by `set-status`, so the format is ours.
2. **Rewrite the deps at split time.** Have the split author repoint dependents
   at the LAST child (`T90e deps: [T375]`). Cheaper to implement, but it is a
   manual step that nobody will remember, and the failure is silent — exactly
   the shape this defect already has.

(1) is the one that cannot be forgotten. Whichever lands, the other half of the
fix is the same: `next` should never offer a task whose transitive prerequisites
are open, and `validate` should say so out loud when it finds one.

*Validation:* a unit/pester-style check over a fixture task set — a
`skipped(split -> A, B)` parent with A done and B todo must NOT satisfy a
dependent; with both done it must. Plus `parity-tasks.ps1 next` on the live
directory offering T375 (or T90e once T375 is done) rather than jumping the
chain.

## In plain terms

The task tracker's "what should I work on next" command sometimes handed out
work whose prerequisites were not actually finished. When a big task is broken
into smaller pieces, the big task's file is marked "skipped (split into ...)",
and the picker treated that mark as "finished" — so anything waiting on the big
task looked ready even while the pieces were still on the to-do list. Now the
picker follows the trail into the pieces and only calls the big task satisfied
when every piece is truly done, so the autonomous loop stops being routed to
work it cannot start yet.
