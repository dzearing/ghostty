# T378 - Pane banners do not repaint while a split divider is dragged (overlay class has no CS_HREDRAW and updatePosition never invalidates)

## Summary

User report 2026-08-02: dragging a vertical split divider left/right does not repaint the pane banners during the move. They are correct again once the drag ends and something else forces a paint.

VERIFIED, by reading the path rather than inferring it from the symptom. The reposition DOES run on every motion tick: updateDividerDrag -> layoutSplits -> `defer updateDimOverlays()` -> updatePaneBanners -> BannerOverlay.updatePosition. What updatePosition does is SetWindowPos (new x/y/w/h) + healOverlayZOrder, and nothing else - there is no InvalidateRect in it (Window.zig ~2594, ~2165, ~2269; BannerOverlay.zig:279-313).

The overlay's window class registers `.style = 0` (BannerOverlay.zig:1312) - no CS_HREDRAW/CS_VREDRAW. So on a width change Windows invalidates only the newly exposed sliver when the window GROWS and nothing at all when it SHRINKS. The card backdrop, the wrapped table columns and every right-anchored piece stay rendered for the PREVIOUS width until an unrelated event invalidates the whole thing.

Why only the banner shows it, which is the part worth keeping: the dim overlay rides the exact same updateDimOverlays path with the same class style, but it paints a flat fill, and a flat fill repainted only in the newly-exposed strip is indistinguishable from a correct one. Banner content is width-DEPENDENT, so it is the one overlay where a stale paint is visible. Do not "fix" this by changing what dim does.

It also compounds with T123: insetHeight re-measures the content at the new pane width on the same tick and the reserved band changes height, so mid-drag the band the layout reserved and the pixels on screen actively disagree.

Fix: make a size change repaint. Prefer an explicit InvalidateRect in updatePosition when w/h actually changed over CS_HREDRAW on the class, for the T233 reason (the house rule is InvalidateRect, never a GetDC paint, and an explicit call is the one a test can assert). Per-tick full repaints are affordable because the glass-card backdrop is already cached and regenerated only when the band changes (BannerOverlay.zig:1109).

Validation: an acceptance script that sets a banner with width-dependent content (a table), drags the divider with the mouse, and reads the card off a PrintWindow capture MID-drag - the T233 precedent, where the color was proved mid-drag because dragging_split does not depend on a real cursor. A drag that ends before the capture proves nothing.
