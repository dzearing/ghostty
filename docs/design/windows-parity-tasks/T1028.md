# T1028 - A win32 acceptance script can measure a stale zig-out exe and stamp its guard green

## Summary

Acceptance scripts drive D:\git\ghoztty\zig-out\bin\ghoztty.exe but almost none of them BUILD it, and nothing checks that the exe is newer than the sources it is measuring. On 2026-08-20 T316's first relay-account run reported 3 FAILURE(S) against an exe built four hours earlier - the code under test was correct and the harness said otherwise. The inverse is the one that matters: a change a stale exe still passes gets a GREEN run, and since T783 a green run STAMPS the guard, so guard-due then records 'this harness has been run against the code as it stands' about an exe that was never built from it. lib\BuildMode.ps1 already refuses a wrong-MODE build before anything launches; the same seam should refuse (or rebuild on) a STALE one.

## In plain terms

The tests that drive the real Windows app run whatever copy of it happens to be
sitting on disk. If nobody rebuilt after the last code change, the tests are
grading yesterday's app — and they will say "all pass" about a change they never
saw. Nothing warns you. This makes the tests check that the app they are about
to launch was actually built from the code they are testing.

## Details

- Every `test\win32\*.ps1` that launches the app defaults `-Exe` to
  `D:\git\ghoztty\zig-out\bin\ghoztty.exe`. Eleven of them run `zig build`
  first; the rest (including `relay-account.ps1`, `ipc-machine-chooser.ps1`
  and the P1-P3 floor) do not.
- The false RED is merely annoying and self-correcting — you rebuild and re-run.
  The false GREEN is the defect: a run that proves nothing exits 0, and since
  T783 exiting 0 **stamps the guard**, so `guard-due` afterwards answers
  "current" for a harness that never saw the change. That is the one question
  the stamp exists to answer, and it can be made to lie without anybody acting
  in bad faith.
- The seam already exists: `test\win32\lib\BuildMode.ps1` is dot-sourced by
  `TestDesktop.ps1`, `CleanSlate.ps1` and `Isolation.ps1`, and it already
  refuses a wrong-MODE build **before** anything is launched (T350). Staleness
  is the same shape of refusal against the same exe.
- Freshness has to be defined carefully. Newest mtime under `src\` vs the exe's
  mtime is the cheap version and would have caught this case, but it goes red on
  a docs-only edit under `src\` and on a `git pull` that touches a file the
  build does not use. A build-stamp comparison (the exe's baked commit vs
  `git rev-parse HEAD`, the way `upgrade-staleness` already checks a delivery)
  is precise but blind to uncommitted work, which is exactly the state a turn
  is in when it runs its acceptance script. Probably both: commit mismatch is a
  hard refusal, mtime drift is a refusal that a rebuild clears.
- Whether the seam REBUILDS or merely REFUSES is a real fork. Rebuilding makes
  every harness self-sufficient at the cost of a possible multi-minute surprise
  inside a test run; refusing keeps the harness fast and honest and puts the
  build in the caller's hands. An opt-in `-Rebuild` over a default refusal is
  the likely shape.

## Validation criteria

- [ ] Launching an app-driving `test\win32` script against an exe older than
      the sources it measures refuses BEFORE anything is launched or typed,
      naming the exe, its age, and the rebuild command — the way
      `BuildMode.ps1` refuses a release build.
- [ ] The refusal is not defeatable by accident: a run that hits it exits
      non-zero and does NOT stamp its guard.
- [ ] A fresh exe is silent — no new line in the ordinary green path.
- [ ] An acceptance script of its own with a negative control: stale exe →
      refusal, fresh exe → the run proceeds.
- [ ] The rule is stated in `docs/claude/testing.md` beside the build-mode one.
- [ ] Floor: both `zig build test` lanes, `test-agent`, the `lib` build, P1-P3.
