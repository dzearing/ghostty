# T407 - The win32 lane hangs forever when the debug WebView2 profile is already in use (ViewerPane host floor waits with no timeout)

## Summary

`zig build test -Dapp-runtime=win32` hung three times in a row on 2026-08-03,
always at the same place, and the cause is not a test defect in the usual sense:

```
1649/3798 apprt.win32.ViewerPane.test.host floor: a real controller on a real window, on this box...
```

That test creates a **real WebView2 controller**, and it does so against the
**debug user-data directory** — `%LOCALAPPDATA%\ghoztty\EBWebView-debug\
EBWebView`, the same profile the debug app uses. A WebView2 user-data-dir has a
single owner. If a debug `ghoztty.exe` (or a leftover WebView2 host from one) is
holding it, the controller-created callback never fires, and the test waits on it
**with no timeout** — the process sits at a flat CPU number, threads parked, with
a live `msedgewebview2.exe --webview-exe-name=ghostty-test.exe` child, forever.
`zig build` never returns; the caller sees "exit 255" only when something kills
it.

## Why this matters more than a slow test

Running GUI acceptance scripts and the floor lanes in the same session is *the
normal thing to do on this box* — the 2026-08-02 log entry says exactly that
about a different lane hang (T183). Every one of those scripts launches a debug
`ghoztty.exe`, so the collision window is open most of the time. And the failure
mode is the worst-shaped one available: not a red test, but a lane that never
finishes, which reads as "the change broke the build" and costs a diagnosis
every time.

It cost ~40 minutes this turn, and the wrong conclusion was reachable at three
separate points (a flaky test, a build-runner pipe deadlock, T258's known hang).

## Evidence (2026-08-03, while validating T104)

- The lane's test binary runs to **3798/3798, 0 failed** standalone, twice —
  including with the build runner's own `--seed`. So the content is green; only
  the run under `--listen=-` hung.
- At hang time the process tree held:
  `msedgewebview2.exe --webview-exe-name=ghostty-test.exe
  --user-data-dir="C:\Users\David\AppData\Local\ghoztty\EBWebView-debug\EBWebView"`
- Killing the ghostty-test WebView2 hosts and every zig-out `ghoztty.exe` /
  `ghoztty-agent.exe`, then re-running the lane unchanged: **exit 0**. That is
  the confirmation — the variable is the profile holder, not the source.

## It also hangs with NOBODY else holding the profile (T108, 2026-08-03)

Reproduced the same day while running T108's floor, and this run **narrows the
diagnosis**: at hang time the ONLY processes touching
`%LOCALAPPDATA%\ghoztty\EBWebView-debug\EBWebView` were the test binary's own
WebView2 children —

```
36836 (parent 39984 = ghostty-test.exe)  --webview-exe-name=ghostty-test.exe
16556 / 47612 / 31536 / 17092            same user-data-dir, all parented by 36836
```

— no zig-out `ghoztty.exe`, no other holder. `ghostty-test.exe` sat at a flat
**48.98 s CPU across a 10 s sample (delta 0)** for 11 minutes with a 0-byte log.
So "the profile is already in use" is a SUFFICIENT trigger, not a necessary one:
the wait can also never complete when this process is the only claimant, which
points at the controller-created callback itself (or the `--listen=-` pipe the
WebView2 host inherits — the same suspicion T409 raises about the agent lane's
grandchildren).

Recovery was mechanical and worked first try: kill the `ghostty-test.exe`
WebView2 children and the test binary, re-run the lane unchanged → **exit 0**.
That is worth having written down; it is the difference between a 2-minute
recovery and the 40-minute diagnosis this task was filed after.

The unbounded wait (fix 1 below) is therefore the half that matters most —
under this shape a per-run user-data-dir would not have saved the run.

## Fix

Two independent halves; do both. Originally written as "the second is the one
that matters" — the 2026-08-03 reproduction above **reverses that**: a per-run
profile cannot help a run whose only claimant is itself, so the bounded wait is
now the load-bearing half and the isolation is the one that removes the common
trigger.

1. **Bound the wait.** The host-floor test must fail (or skip) on a deadline
   rather than parking forever. A test that cannot fail cannot report anything.
2. **Do not share the app's profile.** Give the test its own per-run user-data
   directory (a `.zig-cache\tmp` path, like the other hermetic tests) so a
   running debug app and the lane cannot contend at all. Check whether
   `EBWebView-debug` is derived in one place — if the test can pass an override,
   this is small.

A `SkipZigTest` when the profile is already held is acceptable as a third
fallback, but only with a printed reason: a silently-skipped host floor is the
"green and empty" failure this repo keeps re-learning.

## Validation

- With a debug `ghoztty.exe` deliberately running (the collision the fix is
  about), `zig build test -Dapp-runtime=win32` completes — green, or red with a
  named reason, but never hanging.
- The same lane still exercises the host floor when nothing else holds the
  profile (i.e. the fix must not silently turn the test off in the normal case —
  confirm it RUNS, by breaking it once).
