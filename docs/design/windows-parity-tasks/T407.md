# T407 - The win32 lane hangs forever when the debug WebView2 profile is already in use (ViewerPane host floor waits with no timeout)

## In plain terms

Before any change here is called finished it has to pass a set of automated
checks. One of those checks opens a real browser window, and it used to be able
to sit there doing nothing forever instead of passing or failing — most often
when a copy of the terminal was already open on the machine, which is the normal
state of affairs while someone is working. From the outside a stuck run looks
exactly like a slow one, so whoever is waiting either waits indefinitely or kills
it and cannot tell whether their own change was at fault.

After this, the check always ends. If the browser never answers, the run stops on
a deadline and prints the reason in words — "no controller within the deadline" —
instead of going quiet. And the checks no longer borrow the browser profile the
real app is using, so the collision that started this mostly cannot happen.

## Goals

- [x] The win32 lane completes with a debug Ghoztty deliberately running and
      holding the WebView2 profile
- [x] A wait that runs out fails with a named reason, not a bare state mismatch
- [x] The live host-floor test still really runs in the normal case (proven, not
      assumed)
- [x] One place owns the deadline, so "is this wait bounded?" has one answer

## Resolution (2026-08-04)

**First, a correction to this task's own premise, because it is the expensive
part.** The title says the host floor "waits with no timeout". It does not, and
never did: the 60s deadline has been in that loop since T373 (`4f5681bb3`), and
every other live-runtime wait in `ViewerPane.zig` (navigation, code mode, the
bridge) has had one too. The indefinite hang measured on 2026-08-03 was real,
but it was **downstream of that wait** — the `TestPage`/`ReloadPage` loopback
servers tearing down with close-then-join on a blocking `accept`, plus Chromium
preconnecting sockets it never sends a request on. **T430 root-caused and fixed
both** (`1262bb9c4`), and it also landed `webview2.TestProfile`, which is this
task's fix 2 verbatim.

So what was left here was not a missing bound. It was that a bound which fires
cannot say so, and that nobody had run the collision this task is named after.
Both are now done.

### 1. The deadline says TIMEOUT

Both live-runtime waits used to `break` out of their loop and fall through to
`try testing.expectEqual(State.ready, pane.state)`. A run that timed out
therefore reported

```
expected .ready, found .creating
```

which reads as *a broken pane* rather than *a wait that ran out* — and reading it
that way is precisely how this task came to be filed against a bound that was
already there. Both sites now fail on the deadline with the reason in words:

```
error: 'apprt.win32.ViewerPane.test.host floor: ...' failed:
[viewer_pane] (err): host floor: no controller within the deadline
(still creating); something is probably holding the WebView2 profile
```

### 2. One owner for the deadline: `webview2.pumpUntil`

Every WebView2 completion handler arrives on the calling thread's message loop,
so a test that waits on one has to *be* that loop — which is why these waits were
hand-rolled per test, and why answering "is this wait bounded?" meant reading
five loops. `webview2.pumpUntil(ctx, done)` is now the single pump-with-deadline
both live tests use, and `webview2.testDeadlineNs()` is the single place the
deadline comes from.

`GHOZTTY_WEBVIEW2_TEST_TIMEOUT_MS` overrides it. That override is not a knob for
convenience: it is the only way to **read the timeout's failure message without
waiting a real minute for it**, and a deadline whose failure nobody has ever seen
is a deadline nobody can trust. It is also what makes the timeout path testable —
a unit test sets 50ms, asserts `pumpUntil` on a never-true predicate returns
false, and asserts it actually waited (a deadline that returns instantly is not
bounding anything). A junk value falls back to 60s rather than to zero, so a typo
cannot turn every live test red on a deadline it never waited for.

### 3. Fix 2 was already done by T430

`TestProfile.begin()` points `LOCALAPPDATA` itself at
`%TEMP%\ghoztty-wv2test-<pid>` for the duration of the live tests, so
`userDataFolderW`'s real derivation lands on a private root and the lane cannot
contend with a running debug app for the profile at all. Verified in place, not
re-implemented.

## Original report

`zig build test -Dapp-runtime=win32` hung three times in a row on 2026-08-03,
always at the same place:

```
1649/3798 apprt.win32.ViewerPane.test.host floor: a real controller on a real window, on this box...
```

That test creates a **real WebView2 controller**, and it did so against the
**debug user-data directory** — `%LOCALAPPDATA%\ghoztty\EBWebView-debug\
EBWebView`, the same profile the debug app uses. A WebView2 user-data-dir has a
single owner. If a debug `ghoztty.exe` (or a leftover WebView2 host from one) is
holding it, the controller-created callback never fires — and the process sits at
a flat CPU number, threads parked, with a live `msedgewebview2.exe
--webview-exe-name=ghostty-test.exe` child, forever. `zig build` never returns.

### Why this mattered more than a slow test

Running GUI acceptance scripts and the floor lanes in the same session is *the
normal thing to do on this box*. Every one of those scripts launches a debug
`ghoztty.exe`, so the collision window is open most of the time. And the failure
mode is the worst-shaped one available: not a red test, but a lane that never
finishes, which reads as "the change broke the build" and costs a diagnosis every
time. It cost ~40 minutes, and the wrong conclusion was reachable at three
separate points (a flaky test, a build-runner pipe deadlock, T258's known hang).

### Evidence (2026-08-03, while validating T104)

- The lane's test binary ran to **3798/3798, 0 failed** standalone, twice —
  including with the build runner's own `--seed`. Only the run under `--listen=-`
  hung.
- At hang time the process tree held:
  `msedgewebview2.exe --webview-exe-name=ghostty-test.exe
  --user-data-dir="C:\Users\David\AppData\Local\ghoztty\EBWebView-debug\EBWebView"`
- Killing the ghostty-test WebView2 hosts and every zig-out `ghoztty.exe` /
  `ghoztty-agent.exe`, then re-running the lane unchanged: **exit 0**.

### It also hung with NOBODY else holding the profile (T108, 2026-08-03)

At hang time the ONLY processes touching the debug profile were the test
binary's own WebView2 children (pid 36836 parented by `ghostty-test.exe` 39984,
and four more under it). `ghostty-test.exe` sat at a flat **48.98 s CPU across a
10 s sample (delta 0)** for 11 minutes with a 0-byte log. So "the profile is
already in use" was a SUFFICIENT trigger, not a necessary one — which is the
observation that pointed past the profile and at the loopback-server teardown
T430 eventually found.

Recovery was mechanical and worked first try: kill the `ghostty-test.exe`
WebView2 children and the test binary, re-run the lane unchanged → **exit 0**.
Worth keeping written down; it is the difference between a 2-minute recovery and
a 40-minute diagnosis.
