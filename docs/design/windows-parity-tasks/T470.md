# T470 - A dead tombstone eagerly allocates a full 2 MB output ring it will never use

## In plain terms

For every terminal pane it remembers, the background service reserves 2 MB of
memory to hold that pane's recent output - even for panes whose program has
already finished and which are only being kept so you *could* bring them back.
With a few hundred remembered panes that is hundreds of megabytes reserved for
scrollback that does not exist. It should reserve the space when a pane is
actually revived, not while it is only a memory.

## Goals

- [x] A tombstone costs a small allocation, not a full ring
- [x] The ring grows to full size when the session is relaunched or attached
- [x] Reboot scrollback (the disk snapshot preload) still replays intact

## Summary

Found while fixing T278. `SessionTable.materialize` (`src/remote/agent/
session.zig`) calls `Session.init(..., ring_bytes, ...)`, and `OutputRing.init`
does `alloc.alloc(u8, capacity)` eagerly. So every record loaded from
`sessions.json` reserves `default_ring_bytes` (2 MB) up front, for a session
with `pid = 0` and no child producing output.

T278 bounds the count at `max_dead_sessions` (256), which caps the worst case at
~512 MB rather than letting it grow without limit - but it does not make the
cost right. A tombstone's ring is only ever written by two things:

1. `preloadRingSnapshot` - which loads a ring disk snapshot whose size is
   already known from the file, and
2. the relaunched child, after `RELAUNCH` - at which point a real ring is needed
   anyway.

Both are places the ring could be sized (or grown) on demand.

## Details

`OutputRing` assumes a fixed `buf` with wraparound arithmetic (`base_offset`,
`start`, `len`), so "grow" means allocate-and-copy, not a realloc in place. Two
shapes worth weighing:

- **Lazy**: materialize with a small ring (a few KB); `preloadRingSnapshot` and
  the relaunch path grow it to `ring_bytes` before writing. Smallest change, and
  the growth points are exactly the two writers above.
- **Optional**: make `Session.ring` an optional allocated on first write. Larger
  blast radius - every reader of `s.ring` has to handle null.

Lazy is the obvious first choice. The measurement to take first is the real one:
what does the agent's working set actually look like with 256 tombstones loaded?
Committed-but-untouched pages may already cost less than the arithmetic
suggests on Windows, in which case this is a smaller problem than it reads.

## Validation criteria

- [x] With 256 tombstones seeded, the agent's working set is materially lower
      than before. **Measured on box** with `scripts	470-ring-measure.ps1`
      (an agent on a private pipe and an explicit `--sessions-file`, so nothing
      touches the user's live agent), pre-fix binary vs. fixed binary built from
      the same tree:

      | roster | pre-fix | fixed |
      |---|---|---|
      | empty | ws 12.9 MB / private 67.5 MB | ws 12.0 MB / private 67.4 MB |
      | 256 tombstones | ws **524.7 MB** / private 580.9 MB | ws **13.8 MB** / private 69.1 MB |

      So the tombstone table's own cost went from **+511.8 MB** to **+1.8 MB**.
      That also settles the open question in Details: Windows really was
      charging for those pages, so the arithmetic was not an over-estimate.
- [x] `zig build test-agent` green, including the ring-snapshot preload test
      (`SessionStore ring snapshot: dirty alive ring persists; reload preloads
      scrollback + divider`) and four new `OutputRing` tests plus a
      `SessionTable.materialize` one that counts the bytes 256 tombstones
      actually request.
- [x] `test/win32/session-relaunch-notify.ps1` (ALL PASS, 129) and
      `test/win32/session-snapshot-reattach.ps1` (ALL PASS, 33) stay green - a
      relaunched session still replays its pre-restart scrollback.
- [x] `test/win32/agent-session-cap.ps1` ALL PASS (14) - the T278 cap behavior
      is unchanged.
- [x] Standing floor: all four `floor-lane.ps1` lanes PASS; P1/P2/P3 ALL PASS;
      the three guards this edit made due (`holder-volume`, `session-vanished`,
      `agent-relay-session`) re-run green and re-stamped.
