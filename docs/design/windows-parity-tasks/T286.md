# T286 - T226c: Activity Monitor process control - Kill with confirm, New Process, error banner

## Summary

Third of the four-way split of **T226**. The panel's destructive and creative
actions, which Mac puts in the control bar
(`RemoteActivityMonitorView.swift:935-1000`, `NewProcessSheet` at 1124):

- **Kill** appears only when one or more rows are selected, labelled "Kill" /
  "Kill N", and always goes through a confirmation - Mac's
  `confirmationDialog`, titled with the process name and pid for one row and
  the count for many. Backend: `src/remote/agent/proc_control.zig`
  (`killWindows`, `OpenProcess(PROCESS_TERMINATE)`; note the documented
  TERM==KILL caveat, which the confirm wording must not misrepresent on
  Windows).
- **New Process** sheet: command + optional working directory, 380 wide on
  Mac. Backend: `src/remote/agent/proc_spawn.zig` (`spawnDetached` windows
  branch).
- **Error banner** below the table when an action fails, dismissable, and the
  "Couldn't connect" empty state over the table.
- Selection pruning: when a sampled list no longer contains a selected pid,
  drop it, so the Kill count stays honest (Mac does this in `onChange`).

## What landed

Two new modules plus the panel wiring, on the "arithmetic and wording are pure,
HWNDs are not" split T284/T285 established:

- **`src/apprt/win32/activity_actions.zig`** (new, pure, in the none lane) - the
  Kill button caption, the confirmation title/body, the aggregated failure text,
  the spawn failure text, the empty-state and badge choice, the selection prune
  and the target marshalling. 15 unit tests.
- **`src/apprt/win32/NewProcessDialog.zig`** (new) - the win32 port of Mac's
  `NewProcessSheet`, built as a sibling of `HostSettingsDialog` (same two-row
  labeled form, same synchronous nested-pump API, same dark chrome) rather than a
  third `ConfirmDialog` flavor, for the reason that file already records. Pure
  `layoutFor` + 6 geometry/focus tests asserted at 1.0/1.25/1.5/2.0.
- **`ActivityMonitor.zig`** - the Kill button (created hidden, shown and
  re-captioned by `refreshChrome`), `Options.has_kill`/`has_banner` now read
  real state, `onKill` / `onNewProcess`, the painted error banner with an
  `icon_button` close glyph, the "Couldn't connect" overlay and the "Refresh
  failed" badge behind a new `refresh_failed` flag, and selection pruning in
  `adoptPending`.

Three decisions worth keeping:

1. **The confirmation wording is a deliberate Mac divergence.** Mac says "This
   sends a termination signal to the process." Windows has no such signal -
   `proc_control.killWindows` is `TerminateProcess` - so repeating Mac's sentence
   would misdescribe the button's own action. The Windows body says what actually
   happens, and a unit test asserts the word "signal" never appears in it.
2. **`modal` suspends snapshot adoption for the dialogs' whole nested pump.** The
   confirmation quotes row names BORROWED from `snap`, and both dialogs run their
   own message loop - so without the guard a poll landing mid-dialog would free
   the snapshot under the string on screen. Filed as **T292**, which records the
   copy-instead-of-borrow alternative.
3. **`refresh_failed` needed a worker->GUI channel of its own.** A failed sample
   posts with no snapshot, so `pending_failed` (taken under the same mutex as
   `pending`) is the only way the GUI thread can tell "nothing new" from "the
   source is unreachable" - and a failure clears `loading`, or a first-sample
   failure would sit on "Loading..." forever with "Couldn't connect" available to
   say instead.

- `test/win32/activity-monitor.ps1`: **ALL PASS (82 assertions)**, up from 63.
  `-NegativeControl` still fails (1 FAILURE, 81 passed), so the script can still
  report red.

The three new sections, and what each one actually proves:

- **H** - New Process opens a modal `GhozttyNewProcess` (asserted via
  `IsWindowEnabled` on the owner, the cross-process modality check), Start is
  DISABLED until a command is typed and ENABLED after, and starting one produced
  a **real running pid** (`Get-Process` on the pid the log reported) that then
  showed up as a **row in the table**.
- **I** - Kill is hidden with no selection and becomes visible with one, captioned
  `Kill` (not `Kill 1`); the confirmation names the process and its pid
  (`Kill cmd.exe (PID 16696)?`); **cancelling leaves the process alive** - the
  negative control for "the confirmation is mandatory", which is the assertion a
  cosmetic dialog would fail; confirming logs `killed=1 failed=0` and the pid is
  really gone.
- **J** - a spawn forced to fail (a working directory that does not exist) raises
  the banner: asserted in the log AND in pixels (`COLOR_BANNER_BG` present in the
  bottom band, absent above the control bar - the control that says it is a band
  and not a panel-wide tint), and clicking its dismiss glyph - located by
  searching the capture for the glyph's own color, not by re-deriving the layout
  module's rect - removes it.

**Nothing the box needs is ever a target.** H spawns `cmd.exe /C pause`, a
throwaway that blocks forever and has no child process to orphan, and I only
clicks the affirmative button when the confirmation dialog ITSELF named that pid
- so a mis-targeted row makes the script fail rather than kill a bystander. The
`finally` block reaps the throwaway if the run aborts mid-section.

Deliberate scope: multi-row kill is covered by unit tests only on the box
(**T293**), and `spawnDetached`'s `CREATE_NEW_CONSOLE` flashes a console window
on every spawn (**T291**).
