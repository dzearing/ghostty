# T1045 - holder-volume's B4/C3 fail on a slow box: the volume-trigger window is measured against a clock the flood does not keep to

## Summary

Observed twice in one sitting on 2026-08-21 while working T1042. Back to back,
same commit, same binaries, nothing else changed:

- run 1: 164 s wall, `2 FAILURE(S) (14 assertions passed)` - B4 (the marker
  reached a `.ring` file inside the periodic interval) and C3 (the marker
  survived the crash).
- run 2: 42 s wall, `ALL PASS (16 assertions)`.

The difference is box load: run 1 followed three other acceptance harnesses in
the same sweep. The harness's headline assertion is a race by construction - it
proves the VOLUME trigger fired rather than the 30 s periodic pass, so it must
observe the write inside a window narrower than that pass:

```
$floodSecs  = seconds from the last snapshot to the flood's end marker
$windowSecs = [Math]::Max(4, 24 - $floodSecs)
$early      = Wait-RingHas $tmp $marker $windowSecs
```

Run 1 logged `(flood complete 1 s after the last snapshot)`, so the window was
the full 23 s and the marker still never landed - which says the trigger itself
was late, not that the window was too tight. Two candidates worth separating
before touching anything:

1. `Wait-PaneHas` matched the flood's END MARKER in the ECHOED COMMAND LINE
   rather than in the flood's output (`'x' + '$done'` keeps the two apart in the
   output but the literal marker text still appears in the echo). Then B3 passes
   while the flood is still running, `$floodSecs` reads 1 s when the flood in
   fact took a minute, and B4 measures a window that expired before the flood
   produced enough bytes to trip the trigger. The 1 s reading against a 164 s
   run is the tell.
2. The trigger is genuinely late under load, in which case the assertion is
   right and the holder has a real latency problem worth knowing about.

Candidate 1 explains the observation without any product defect and is
falsifiable from the harness alone; check it first. Whatever the answer, the
harness must not have two outcomes on the same bytes - a guard-set harness that
flakes forces the next turn to re-run it or to reach for `-NoGuardDue`, which is
the exact muting T783 exists to prevent.

## In plain terms

One of the tests that proves "a busy pane's scrollback gets saved before it
scrolls away" gives different answers on a busy machine than on a quiet one. It
is not that the feature broke - the same test passed a minute later untouched -
it is that the test times itself against a clock the work does not keep to. A
test that reports failure when the machine is merely busy trains everybody to
ignore it.

## Validation criteria

- [ ] the cause is identified from evidence: either B3's end-marker match is
      hitting the echoed command line (fix the match), or the trigger really is
      late under load (then it is a product task, filed separately)
- [ ] `test\win32\holder-volume.ps1` passes with another acceptance harness
      running immediately before it, ten runs in a row
- [ ] the assertion still FAILS with `-NegativeControl` (the trigger disabled) -
      whatever makes it robust must not make it unfalsifiable
