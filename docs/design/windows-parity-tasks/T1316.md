# T1316 - The RDP acceptance run should measure whether a dimmed viewer pane keeps getting darker

## In plain terms

Someone reported that an HTML pane kept getting darker over a remote desktop
connection. There is now a fix, but nothing on this machine can tell whether it
worked - the only way to find out today is to ask that person to sit and watch
a pane again. The remote-desktop test run should just measure it.

## Goals

- [x] `rdp-session.ps1` opens a viewer pane, dims it, and samples its
      composited pixels over a couple of minutes.
- [x] The verdict is a drift bound, not an absolute brightness.
- [x] Every reading is written into the run's evidence artifact.
- [x] `-SelfTest` records "no composite here" rather than a fake series, and
      still proves the arm and its arithmetic execute.

## Summary

T1295 fixed the app's contribution to a compounding dim (the unfocused-split
overlay stopped re-blending when nothing had changed, and it now resets the
pixels under itself in a remote session). What it could not do is CONFIRM the
fix: this box serves one interactive session at a time, so it cannot make an
RDP session for itself - the same constraint `test\win32\rdp-session.ps1`
(T1253) is built around, and the reason that script asserts nothing at all
unless it is already running inside one.

`rdp-session.ps1` is therefore the right home for the measurement. It already
runs on the INTERACTIVE desktop by design (a background desktop is never
composited, so nothing drawn there is presented over the wire), which is
exactly what a composited-pixel sample needs.

Add an arm: open a viewer pane in a split, move focus off it so the T74 dim
overlay is showing, sample the pane's composited pixels over a couple of
minutes with `CopyFromScreen`, and record the mean luminance per sample. The
assertion is a DRIFT bound, not an absolute brightness - the pane is supposed
to look dimmer than the focused one; what it must not do is keep getting
dimmer. Record every sample in the run's evidence artifact the way arm E
records fps, because a number nobody wrote down has to be re-earned on a
machine the next reader may not have.

Two things to get right:

- **A server-side sample may not see a client-side blend.** If the
  accumulation turns out to happen in the RDP *client*, `CopyFromScreen` on the
  server's desktop will read steady pixels while the human sees a fading one.
  If the arm reads steady while the reporter still sees the fade, that is
  itself the finding, and it moves the suspect to the client/redirection side.
- **`-SelfTest` must not pretend.** It runs the body on the background desktop
  where `CopyFromScreen` is dead, so this arm has to record "no composite here"
  rather than a column of zeroes that reads like a measurement.

## Validation criteria

- [x] `rdp-session.ps1` gains the arm, and `-SelfTest` shows it executing
      without claiming a measurement it could not take. Verified: a `-SelfTest`
      run on this box prints `G1` (viewer pane opened), `G2` (the T74 overlay
      covers it) and `G3` (`not sampled: DWM composes only the input desktop`),
      and the artifact's `dim` block is `measured: false` with that reason and
      an EMPTY `samples` array - not a column of zeroes.
- [x] The verdict arithmetic is exercised without an RDP session. `-SelfTest`
      runs `Get-LuminanceDrift` over a steady series and a compounding one and
      asserts it separates them (`S2` -0.06% passes the 5% bound, `S3` 26.44%
      fails it), plus `S1`, a live capture proving the sampler returns a
      luminance for a composited region. Without this the first real RDP run
      would also be the first execution of the pass/fail logic.
- [ ] Run inside a real RDP session, the arm reports a per-sample luminance
      series and passes/fails on drift, not on absolute brightness. **Needs the
      second machine [[T1256]] is parked on** - this box serves one interactive
      session, so the arm cannot be run against a remote desktop from here.
- [x] The series lands in `test\win32\artifacts\rdp-session.json` - the `dim`
      block carries `samples`, `seconds`, `head_mean`, `tail_mean`,
      `drop_percent`, `bound_percent`, the sampled region and the interval.
- [ ] T1295 can be closed (or re-opened with a new suspect) from this run's
      output alone, without asking the reporter to watch a pane. The route is
      written into [[T1256]] step 6; the run itself is what is missing.
