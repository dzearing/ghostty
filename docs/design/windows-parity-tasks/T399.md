# T399 - T145 in-place recovery destroys and re-opens viewer panes that ride no agent connection

## In plain terms

If the background process that keeps your terminals alive crashes, Ghoztty
quietly rebuilds your terminal panes so you can keep typing. Until now it also
threw away every *document* pane in the same tab — the ones showing a file, a
web page or a diff — and re-opened them from scratch. You lost your scroll
position and anything you had typed or opened on the page, for a crash that had
nothing to do with those panes. Now they are simply left alone.

## Goals

- [x] The recovery rebuilds only the panes that were actually broken
- [x] A document/web pane keeps its identity, its page and its state across a recovery
- [x] Terminal panes still come back exactly as they did before, sessions intact
- [x] A tab whose layout changed mid-recovery still recovers (falls back to the old rebuild)

## Validation criteria

- [x] A viewer pane's `pane_id` is unchanged across an in-place recovery —
      `test\win32\agent-recovery.ps1` section F2. A re-created viewer draws a
      fresh random id in `ViewerPane.create`, so an unchanged id can only mean
      the pane object was never destroyed.
- [x] The viewer is still LIVE after the recovery, not a husk: it still reports
      its location and still answers `+reload` under the IPC name it was
      registered with before the crash (F3, F4).
- [x] The test is not vacuous — the same run proves recovery genuinely ran and
      rebuilt the terminals on NEW child processes (C5), with their sessions
      spared (D1) and their pane ids kept (E6).
- [x] `test\win32\agent-recovery.ps1` ALL PASS (31).
- [x] The two pure rules are unit-tested in the none lane
      (`agent_recovery.rebuildsLeaf` / `shapesCorrespond`), as is the tree
      primitive (`SplitTree.replaceLeaf`).
- [x] Standing floor green: `zig build test` (none + win32), `zig build
      test-agent`, P1-P3.

## Summary

In-place local-agent recovery (`rebuildWindowInPlace` / `rebuildTabInPlace`)
replaces a tab's ENTIRE split tree with fresh panes on the new connection. T90h
made that rebuild reproduce the recorded KIND, so a viewer no longer comes back
as a terminal — but it is still torn down and re-created for an event that has
nothing to do with it. A viewer holds no agent session, so its link cannot have
dropped.

## Details

Cost of the churn: the WebView2 host window and its browser process are
destroyed and rebuilt, the page reloads, and everything the user had done inside
it — scroll position, in-page state, and any navigation away from the recorded
location that has not been captured yet — is lost. For a markdown doc that is a
visible jump; for a `localhost` dev page it can be a lost form or a lost log
tail.

The fix is to leave viewer leaves in place and rebuild only the terminal ones,
which means the recovery walk has to become a tree EDIT rather than a wholesale
swap. That is why it is filed rather than done inside T90h: `replaceTabRoot`
exists precisely because the current path replaces the root, and doing this
properly changes the shape of the recovery, not just its leaf constructor.

Note the ordering trap for whoever takes it: the swap must still never call
`setSessionCloseIntent` on the departing terminal surfaces (the invariant
`agent_recovery.sessionSpared` states), so a partial rebuild has to keep that
property leaf by leaf instead of relying on the old tree's default teardown.

*Validation:* a viewer pane's identity (`pane_id`) survives an in-place recovery
unchanged — today it is regenerated, which is the cheap observable proof the
pane was re-created. Drive it the way the existing agent-recovery acceptance
coverage drives the terminal case, with a `--view` pane in the tree.
