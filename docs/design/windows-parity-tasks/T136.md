# T136 — zig build test-agent flaked once: remote.agent.server.test "RESIZE and SIGNAL are recorded on…

## In plain terms

The project's test suite very occasionally crashed on one specific test, and
running it again always passed — so a red result could never be trusted, and
every time it happened someone had to re-run a slow build to prove their
change was innocent. The underlying bugs turned out to be the same pair that
T183 later diagnosed and fixed: two parts of the session-keeper program could
save the same file at the same moment and corrupt it, and the test itself
crashed with a meaningless message instead of saying what it had waited for.
This task verifies, with many repeated runs, that the crash is actually gone.

## Validation evidence (2026-08-05)

- Root cause: shared with T183 (done, commit `0b295032c`). Same test, same
  exit-3 panic signature. T183 pinned two co-occurring defects: (1) fixed-name
  `<path>.tmp` staging collided across concurrent session persists (torn
  publish + FileNotFound), fixed via `src/remote/agent/atomic_write.zig`
  unique staging names; (2) the test discarded `waitUntil`'s bool so a timed
  out wait fell through to `.?` on a null, with FakeChild fields written by
  the control thread and polled by the test thread unsynchronized and the
  recorded signal a borrowed slice — all fixed (expect at the wait, 60s
  deadline, FakeChild mutex, owned signal copy). T136 was the earliest
  sighting (2026-07-28, test-agent lane, during T131's floor run) of the same
  crash; its "PtyChild teardown / use-after-free of the child handle"
  suspects from the summary are disproven by T183's diagnosis — the fake-child
  harness never spawns a real child.
- Filtered ×100: built `zig build test-agent -Dtest-filter="RESIZE and
  SIGNAL"` (exit 0), then looped the compiled
  `.zig-cache\...\ghoztty-agent-test.exe` 100 times directly: **0 failures**
  (6s total). Verified the loop really executes the target test: a captured
  run prints `4/77 remote.agent.server.test.RESIZE and SIGNAL are recorded on
  the child...OK` and `All 77 tests passed.`
- Full lane ×3: `scripts\floor-lane.ps1 -Lane agent -Repeat 3` →
  `FLOOR SUMMARY: agent#1=PASS agent#2=PASS agent#3=PASS` / `ALL LANES PASS`
  (160–161s each). The only warn (`Invalid timestamp in cache entry …
  err=error.Overflow`) is the ssh-cache test's own deliberate bad-input case.
- Wider floor: this task changed no code (docs only); the tree's last code
  commit `0b295032c` carried T183's full validation the same evening — all
  three lanes PASS, P1–P3 ALL PASS, plus 3× concurrent-stress rounds green.

## Summary

**`zig build test-agent` flaked once: `remote.agent.server.test "RESIZE and SIGNAL are recorded on the child"` exited with code 3** (expected 0), 2026-07-28 during T131's floor run; the identical re-run was green, and both app lanes were green in the same session. Not T97 (that was `ssh-cache.DiskCache`/`renameatW`, and `ZIG_GLOBAL_CACHE_DIR` was set correctly here). Exit code 3 from a test child is a PANIC, not an assertion failure, so this is a real crash in the agent's RESIZE/SIGNAL recording path that a re-run hides — the agent floor is a standing gate for every task, so a flake here silently costs a rebuild every time it hits. Investigate: run that one test in a loop (`--test-filter "RESIZE and SIGNAL"`) until it reproduces, then read the panic. Suspects are the child-process teardown race the T89b work touched (`PtyChild` teardown) and a use-after-free of the recorded child handle when the test's child exits before the SIGNAL is recorded. Validation: the filtered test green ×100, then `test-agent` green ×3
