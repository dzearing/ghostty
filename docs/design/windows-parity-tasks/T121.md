# T121 — auto `window-N` names can duplicate after a session restore

## In plain terms

Windows you open without naming them get automatic names — "window-1",
"window-2" and so on. After Ghoztty restarts and brings your old windows back,
it starts counting from one again, so the next few windows you open get names
that old windows are already using. Two different windows then answer to the
same name, and a script or agent that says "close window-3" can close the wrong
one — someone else's work, with no warning. After this change every window's
name is its own: reopened windows keep theirs, new windows carry on past them,
and closing by name always closes the window you meant.

## Goals

- [x] A name a window inherits (from a restore, or from `--target=`) pushes the
      auto-name counter past it, so it can never be handed out a second time
- [x] A window only records a name it actually owns — if something else already
      holds it, it takes a fresh one instead of advertising a name that routes
      elsewhere
- [x] Unit tests for the allocator: monotonic minting, reservation, no rewind,
      non-auto names ignored, and a conflicting registration reported
- [x] An on-box acceptance script that restores three named windows, opens
      three more, and proves no name is shared and `+close` hits its target
- [x] Negative control: the same script run against the pre-fix build fails

## Summary

Auto `window-N` target names can DUPLICATE after a session restore — `IpcRegistry.nextWindowName` is a bare `window_counter += 1` that restarts at zero every app launch, while T89f session restore re-adopts window names minted by a PREVIOUS run. A restored `window-3` plus three fresh windows ⇒ two live windows holding one target name, and `+close`/`+split`/`+rename` route to whichever registered first. Main fixed the same defect in `565b77a58` by RESERVING adopted names (advance the allocator past any adopted `window-N`) and by checking live windows, not just the registry, before honoring a name. Port both halves; the reservation must also cover `GHOZTTY_WINDOW_NAME` inherited at spawn and explicit `+new-window --target=`

## Details

`IpcRegistry.nextWindowName` is a bare counter:

    self.window_counter += 1;
    return std.fmt.allocPrint(alloc, "window-{d}", .{self.window_counter});

The counter restarts at zero every app launch, while T89f session restore
re-adopts window names minted by a PREVIOUS run. Restore a window named
`window-3`, open three fresh windows, and the third mints `window-3` again:
two live windows holding one target name, with `+close`/`+split`/`+rename`
routed to whichever registered first.

Main hit exactly this and fixed it in `565b77a58` with two independent halves,
both of which apply here:

1. **Reserve adopted names.** Any name a window ADOPTS rather than mints —
   a restored name, a `GHOZTTY_WINDOW_NAME` inherited at spawn, or an explicit
   `+new-window --target=` — advances the allocator past it if it matches the
   `window-N` pattern, so a later mint can never repeat it.
2. **Check live windows, not just the registry.** A live window can hold a name
   without being registered yet (registration is lazy — first `+list` or first
   targeting), so the registry alone is not authoritative.

**Validation:** restore a session whose windows are named `window-1..3`, then
open fresh windows past that count and assert `+list` shows no duplicate name
and that `+close --target=window-3` closes the one you meant.

## What landed

Both halves, translated to win32 — where the whole adoption path is one site
(`Window.init`'s `options.ipc_name`), because win32 registers a window's name
eagerly at init rather than lazily. There is no `GHOZTTY_WINDOW_NAME`
*inherited-at-spawn* path here to cover: win32 only ever WRITES that variable
into a child's environment (`IpcHandlers`), never reads it back.

1. **Reservation** — `IpcRegistry.reserveWindowName` advances `window_counter`
   past any adopted `window-N`, called from `Window.init` before anything is
   minted. Strict parse (`autoWindowNumber`): `window-` plus ASCII digits
   naming a non-zero number, so `--target=window-pane` or `window-1a` reserves
   nothing. Never rewinds.
2. **Hold what you record** — `IpcRegistry.register` now returns
   `registered` / `already_held` (`App.ipcRegisterChecked`; the void
   `ipcRegister` stays for the pane callers that don't care). `Window.init`
   only stores `ipc_name` for a name it actually holds, and falls back to
   minting when an incumbent kept it — the win32 analog of the Mac's
   "restored window not re-registered", which is what stops a window from
   advertising a `target` in `+list` that routes elsewhere. Bounded retry,
   because a *pane* can be named `window-N` too and the allocator doesn't
   know about pane names.

Also fixed in passing: `register` left the map keyed on the caller's BORROWED
slice if the key dupe OOM'd. It now removes the slot before returning the
error.

## Evidence

- Unit tests, `src/apprt/win32/IpcRegistry.zig` (win32 lane; the module is now
  named in `src/apprt/win32.zig`'s test block): monotonic minting, adopted
  names reserving their number, no rewind, eleven non-auto spellings reserving
  nothing, and `already_held` vs idempotent re-registration.
- Acceptance: `test\win32\window-name-restore.ps1` — **ALL PASS (22)**.
  Restores three auto-named windows, opens three more, asserts every `target`
  is unique, that no restored name moved to a different window, and that
  `+close --target=window-3` closes the pane id that held it and nothing else.
- **Negative control** (the same script against a build with `Window.init`
  reverted): `2 FAILURE(S) (20 passed)` — `C2 ... (dupes: window-1, window-2,
  window-3; all: window-1, window-2, window-3, window-1, window-2, window-3)`
  and `D3 window-3 no longer names any live window`. The defect reproduces
  exactly as described and the script catches it.
- Floor: `scripts\floor-lane.ps1 -Lane all` and P1–P3 — see the commit.
