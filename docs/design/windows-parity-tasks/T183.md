# T183 - agent-server test panics on a null when its temp dir vanishes (none-lane flake)

## In plain terms

The project's test suite sometimes went red with a crash message that named
nothing anyone could act on, and only when other test scripts happened to be
running at the same time - so people re-ran it, it passed, and nobody could
trust a red result. Two real bugs were hiding under that noise: the program
that keeps terminal sessions alive across reboots could corrupt its own
"which sessions exist" file when two parts of it saved at the same moment,
and the test suite crashed instead of saying "I waited for something that
never happened". Both are fixed: simultaneous saves are now safe (each save
publishes only a complete file), and a test that times out now says exactly
what it was waiting for.

## Goals

- [x] Find the real mechanism behind the `FileNotFound` warn + null panic
      pair (it was NOT a vanishing temp dir - see Root cause below)
- [x] Make concurrent saves of sessions.json / layouts / ring snapshots /
      the win32 session-layout manifest safe (unique staging name per write,
      one shared helper: `src/remote/agent/atomic_write.zig`)
- [x] Regression test that reproduces the exact observed failure with the
      old code (red) and passes with the new (green)
- [x] Make every timed-out test wait fail AT the wait, named - never fall
      through to a null panic (`try testing.expect(waitUntil(...))` at all
      five discarded-bool sites; deadline 10s -> 60s; FakeChild reads/writes
      now under its mutex, signal recorded as an owned copy)
- [x] Floor green: all three lanes + P1-P3
- [x] The task's stress validation: none lane concurrent with ipc-p1..p3,
      three times, green each time

## Root cause (corrected, 2026-08-05)

The task's original theory - an external actor sweeping `.zig-cache\tmp` out
from under a non-hermetic test - is **disproven**. No sweeper exists (searched
the acceptance scripts, floor-lane, delivery scripts, and zig's own std/build
runner: nothing deletes foreign entries under `.zig-cache\tmp`), and the
panicking RESIZE test never touches a temp dir at all (its store has
`meta_path = null`). The observed pair of log lines are TWO independent
defects that co-occur under load:

1. **The warn** (`session_meta: write to ...\sessions.json failed:
   FileNotFound`): `writeAtomic` staged every write at the FIXED name
   `<path>.tmp`. Two overlapping persists - and persists overlap by design:
   the control thread persists right after OPENED while a test (or the exit
   watcher, or shutdown) persists too - interleave as: B's create truncates
   A's staged file; A's rename publishes B's partial bytes; B's rename fails
   FileNotFound because A renamed the staging file away. The test at
   `server.zig` "OPEN records cwd" even documents its own explicit persist as
   racing the server's. Reproduced deliberately in
   `atomic_write.zig`'s "concurrent writers" test: with the fixed name it
   fails within a few rounds; the production risk was a torn/empty
   sessions.json - the reboot floor's roster.

2. **The panic** (`attempt to use null value` at `fc.last_resize.?`): the
   RESIZE test discarded `waitUntil`'s bool, so a wait that timed out (10s,
   spendable on a box saturated by concurrent acceptance scripts) fell
   through to `.?` on a still-null optional. The headline named the panic,
   not the timeout - unattributable by construction. (The FakeChild fields
   were also written by the control thread and polled by the test thread
   with no synchronization, and the recorded signal was a borrowed slice
   into the control frame - both now fixed.)

## Summary

`remote.agent.server.test."RESIZE and SIGNAL are recorded on the child"` took
the `-Dapp-runtime=none` lane RED with a `thread panic: attempt to use null
value` (exit 3) while `ipc-p1/p2/p3` were running concurrently in another
window. A solo re-run of the same lane on the same tree passed. A floor lane
that can go red for a reason that is not the code under test is expensive
precisely because `go.md` teaches "believe the last line" - this one lies.

## Details

Observed 2026-07-30 during T123's validation. The lane was launched in the
background while the P1-P3 acceptance scripts (which spawn and kill ghoztty +
ghoztty-agent processes, and sweep zig-out/temp state) ran in the foreground.

The log's own sequence names the mechanism:

```
[default] (warn): session_meta: write to D:\git\ghoztty\.zig-cache\tmp\MAB7IcQtRFpKXJfb\sessions.json failed: FileNotFound
thread 30832 panic: attempt to use null value
error: while executing test 'remote.agent.server.test.RESIZE and SIGNAL are recorded on the child',
       the following command exited with code 3 (expected exited with code 0)
Build Summary: 48/50 steps succeeded; 1 failed; 3135/3202 tests passed; 67 skipped
```

So the test's own temp directory went away underneath it (`FileNotFound` on the
`sessions.json` write), and instead of failing with that as the message it
carried a null forward and panicked somewhere later. Two separate defects:

1. **The test is not hermetic** - its scratch dir is reachable/removable by an
   unrelated concurrent process. It should own a dir nothing else can name, and
   it must not depend on `.zig-cache\tmp` surviving another actor's cleanup.
2. **The failure is unattributable** - a failed metadata write degrades to a
   null that panics later, so the log's headline is `attempt to use null value`
   instead of `could not write sessions.json`. Handle the write error where it
   happens; a panic on a null is never a diagnosis.

Do not "fix" this by serialising the test lanes: running the lanes while
acceptance scripts run is normal on this box, and a test that cannot survive
that is the thing to fix.

**Validation:** reproduce deliberately - delete the test's scratch dir out from
under it mid-run (or point it at a path that disappears) and assert the test
FAILS with the write error named, never panicking on a null. Then run the none
lane concurrently with `ipc-p1..p3` three times and require green each time.
