# T183 - agent-server test panics on a null when its temp dir vanishes (none-lane flake)

## Summary

`remote.agent.server.test."RESIZE and SIGNAL are recorded on the child"` took
the `-Dapp-runtime=none` lane RED with a `thread panic: attempt to use null
value` (exit 3) while `ipc-p1/p2/p3` were running concurrently in another
window. A solo re-run of the same lane on the same tree passed. A floor lane
that can go red for a reason that is not the code under test is expensive
precisely because `go.md` teaches "believe the last line" - this one lies.

## Second sighting, 2026-07-31 (T217 batch 3) - same signature, other lane

It is **not** specific to the none lane, and it is reproducible on demand by
doing the ordinary thing: `-Dapp-runtime=win32` went RED with the identical
pair of lines while the migrated GUI acceptance scripts ran concurrently in the
foreground (they kill ghoztty/ghoztty-agent processes and sweep state between
sections, which is what reaches into the scratch dir).

```
[default] (warn): session_meta: write to D:\git\ghoztty\.zig-cache\tmp\fC4jNx0NFQ5198T1\sessions.json failed: FileNotFound
thread 30532 panic: attempt to use null value
D:\git\ghoztty\src\remote\agent\server.zig:3480:68 in test.RESIZE and SIGNAL are recorded on the child
    try testing.expectEqual([4]u16{ 50, 120, 1, 2 }, fc.last_resize.?);
Build Summary: 48/50 steps succeeded; 1 failed; 3339/3406 tests passed; 67 skipped
```

Two things this pins down that the first sighting could not:

- The panicking line is `fc.last_resize.?` (server.zig:3480). The RESIZE was
  never recorded because the fake child's state went away with the temp dir, so
  the `.?` is the second defect (unattributable failure) landing on the first
  (non-hermetic scratch dir) - exactly as theorised below, now with a line
  number.
- The cost is recurring and is being paid by unrelated tasks: this is now the
  third turn (T131, T123, T217) whose floor run has to be re-run and explained.

## Details

Observed 2026-07-30 during T123's validation. The lane was launched in the
background while the P1-P3 acceptance scripts (which spawn and kill ghoztty +
ghoztty-agent processes, and sweep zig-out/temp state) ran in the foreground.

The log's own sequence names the mechanism:

```
[default] (warn): session_meta: write to D:\git\ghoztty\.zig-cache\tmp\MAB7IcQtRFpKXJfb\sessions.json failed: FileNotFound
thread 30832 panic: attempt to use null value
error: while executing test 'remote.agent.server.test.RESIZE and SIGNAL are recorded on the child',
       the following command exited with code 3 (expected exited with code 0)
Build Summary: 48/50 steps succeeded; 1 failed; 3135/3202 tests passed; 67 skipped
```

So the test's own temp directory went away underneath it (`FileNotFound` on the
`sessions.json` write), and instead of failing with that as the message it
carried a null forward and panicked somewhere later. Two separate defects:

1. **The test is not hermetic** - its scratch dir is reachable/removable by an
   unrelated concurrent process. It should own a dir nothing else can name, and
   it must not depend on `.zig-cache\tmp` surviving another actor's cleanup.
2. **The failure is unattributable** - a failed metadata write degrades to a
   null that panics later, so the log's headline is `attempt to use null value`
   instead of `could not write sessions.json`. Handle the write error where it
   happens; a panic on a null is never a diagnosis.

Do not "fix" this by serialising the test lanes: running the lanes while
acceptance scripts run is normal on this box, and a test that cannot survive
that is the thing to fix.

**Validation:** reproduce deliberately - delete the test's scratch dir out from
under it mid-run (or point it at a path that disappears) and assert the test
FAILS with the write error named, never panicking on a null. Then run the none
lane concurrently with `ipc-p1..p3` three times and require green each time.
