# T240 - Right-click shows no menu under mouse reporting

## Summary

User report, 2026-07-31, verbatim: *"there is no right click context menu like
in the mac version. WTF. another parity item missing."*

The menu is not missing - `context_menu.zig` builds all 17 items in Mac order
and T102 shipped it on 2026-07-20. **What is missing is the menu ever
appearing in the user's actual workflow**, and the reason is a one-line
divergence that T102 explicitly examined and got wrong.

**T102's disposition was:** *"The user's 'right-click pastes' was Claude Code
receiving the reported right-click (mouse reporting consumes the press -
Mac-identical)."*

**That claim is false.** Mac does NOT consume the right-click press for menu
purposes, and this is checkable in the Mac source in under a minute.

## Evidence (VERIFIED - read both implementations)

**Mac** (`macos/Sources/Ghostty/Surface View/SurfaceView_AppKit.swift:1646`,
`menu(for:)`):

```swift
switch event.type {
case .rightMouseDown:
    // Good
    break                      // <-- falls through and BUILDS THE MENU

case .leftMouseDown:
    if !event.modifierFlags.contains(.control) { return nil }
    ...
    if surfaceModel.mouseCaptured { return nil }   // <-- capture guard is HERE ONLY
```

The `mouseCaptured` guard lives **inside the `.leftMouseDown` case**, guarding
ctrl+left-click. The `.rightMouseDown` case has no guard of any kind: it breaks
out of the switch and returns a fully built `NSMenu` **unconditionally**.

And AppKit consults `menu(for:)` *before* delivering `rightMouseDown` - a
non-nil return means the view's mouse handler never runs. The Mac source says
so itself, in the leftMouseDown branch: *"If we return a non-nil menu then
mouse events will never be processed by the core, so we need to manually send a
right mouse down event."*

So on Mac: **right-click always shows the context menu**, mouse reporting or
not, and `rightMouseDown`'s `consumed` check (line 1024) is dead code for the
menu path.

**Win32** (`src/apprt/win32/Surface.zig:2822`):

```zig
if (!consumed and button == .right and action == .press) {
    self.showContextMenu(lparam);
}
```

Gated on `!consumed`. Under mouse reporting the core consumes the press, so the
menu never opens.

**Why this is 100% of the user's experience, not an edge case:** every pane
they use runs Claude Code, which enables mouse reporting. vim, tmux, htop,
lazygit and every other TUI do the same. So on Windows the context menu is
reachable only from a bare shell prompt - which is close to never - while on
Mac it is always one right-click away. The feature reads as absent because in
practice it is.

## The fix

Match Mac: **right-click opens the context menu unconditionally.** Move the
call out from behind `!consumed`, and follow Mac's compensating behavior - when
the menu is shown, the core still gets a synthesized right press/release pair
so its click state does not desync (`showContextMenu` already synthesizes the
release for the `TrackPopupMenuEx` capture problem; extend that reasoning).

Decisions to make explicitly, not by default:

- **`right-click-action = paste`** (the WT-style opt-in T102 added) must keep
  working, and under it right-click should still go to the app when reporting
  is on. Only the `menu` disposition changes.
- **Shift+right-click** already bypasses reporting and must keep opening the
  menu (it becomes redundant, not wrong).
- Confirm whether an app that has requested mouse reporting should be able to
  get right-click at all on Windows. Mac says no. Follow Mac - this is a
  parity task, and divergence here is what produced the report.

## The process failure, recorded

T102 marked itself `done` with `context-menu.ps1 ALL PASS (19) x3`. The script
passed because it drives the menu with **`PostMessage`** ("PostMessage-driven,
wedge-immune") - it posts the message that opens the menu, so it can never
observe that a real right-click under mouse reporting does not produce one.
A green suite and a broken feature, from a test that skips the input path the
user uses.

Two lessons for the tracker's bar:

1. **A parity claim about the Mac's behavior must cite the Mac source line**,
   not a plausible inference about what the shared core does. "Mac-identical"
   was asserted about a code path nobody read; reading it takes a minute and
   refutes it.
2. **An acceptance script that synthesizes the trigger cannot validate the
   trigger.** `context-menu.ps1` must gain a real-input case: turn mouse
   reporting ON in the pane, right-click for real, assert the menu appears.

## Validation

- With mouse reporting ON in the pane (run Claude Code, or emit
  `\033[?1000h`), a real right-click opens the menu. This is the case that
  fails today and is the whole task.
- With reporting OFF, unchanged behavior.
- `right-click-action = paste` still pastes.
- Shift+right-click still opens the menu.
- The core's click state is not desynced after the menu closes: right-click,
  dismiss, then drag-select - the selection must behave normally (this is the
  regression `showContextMenu`'s synthesized release exists to prevent).
- `test/win32/context-menu.ps1` gains the real-input case above and stays
  ALL PASS x3, with a negative control that fails when the gate is restored.
