# T319 - T146b: cross-machine session BROWSE in the chooser (remote roster over the relay)

Second child of the **T146 split (2026-08-01)**. Mac commit `c066f8681`.

## Summary

T318 gives the chooser a session roster for the local agent. This task points
the same roster at a **remote machine**: expanding a relay device's row dials
that machine's agent, runs `LIST_SESSIONS`, and shows its sessions with the
same rows, badges and labels.

The transport is already transport-agnostic on both sides. Mac says so
explicitly - *"the same call works against the local agent or a relay machine
(the Zig ABI resolves the transport via the connection handle)"*
(`SessionBrowserProbe.swift:93-96`) - and the Zig side is
`Connection.requestSessions` against whatever connection you hand it
(`src/remote/connection.zig:1598`). So there is **no new RPC**; the work is the
dial, its ownership, and the per-row state.

## Reuse T295's dial, do not re-derive it

T295 (`9b03eb93e`) already built exactly this for the Activity panel and wrote
down the parts that are easy to get wrong:

- `relay_dial.dial(alloc, base, device, token, .raw)`, with the relay base from
  `relay_directory.resolveBase` and the bearer from `IpcHandlers.resolveToken`
  (the `App.openRelayWindow` path).
- The dial blocks through a handshake, so it runs off the GUI thread; a dial
  that lands after the row collapsed or the dialog closed **frees what it
  dialed rather than adopting it**.
- Ownership decides teardown order. Mac's rule for the browse probe is
  narrower than the Activity panel's and must be kept: per-machine probe
  connections are **short-lived - dialed, read, freed**, while the local
  agent's warm shared connection is reused and **never freed here** because
  `LocalAgentManager` owns it (`SessionBrowserProbe.swift:145-149`; the win32
  owner is `App.local_agent`).

## Mac reference

- `SessionBrowserProbe.swift:231-295` - `toggle(machine:)`, token resolution,
  host/port capture, dial-then-list on the background queue.
- `:303-338` - `fetchIfNeeded(machine:)` and `refreshInPlace(machine:)`: the
  distinction matters, because a refresh must not flash the row back to
  `loading` under the user.
- `:339-395` - `kill(session:machine:)` over a remote connection.
- `MachineChooserView.swift:102-113` - the probe key per target
  (`SessionBrowserProbe.localKey` vs the machine uuid), and `:192-201`
  (`count(for:)`) which feeds the collapsed row's session count.

## Failure modes that must not become modals

A machine that is offline, mid-reboot, or on an expired token is the **normal**
case in a chooser listing every enrolled device. Every one of those resolves to
`failed` on that row with an in-row message. `Unauthorized` maps to the same
"Session expired - sign in again above." string the rest of
`MachineChooser.zig` already uses (`:728`, `:1567`, `:1577`) - do not invent a
second wording.

## Validation

- Unit: per-key state transitions (collapsed -> loading -> loaded/failed ->
  refresh-in-place) and the count formatting, in the none-runtime lane.
- On box: the relay path needs a reachable agent. Follow the harness the
  remote-window acceptance scripts already use (`+new-remote-window` against a
  local agent on a TCP port is the cheap stand-in for a relay device) and
  assert the row expands to the roster that `ghoztty +sessions` reports for
  that agent.
- A negative control is mandatory (T302/T312 lesson): point a row at a dead
  port and assert the row goes `failed` **and the dialog stays responsive** -
  the wedge is the defect this task is most likely to introduce.

## What landed (2026-08-01)

### The product change

- `chooser_sessions.Target` (`none` / `local` / `remote: <device id>`) and
  `transitionFor` - the pure state machine for "the selection moved". Windows is
  master-detail where Mac is a set of expandable rows, so there is exactly one
  target at a time and Mac's "collapsed" is spelled `none`. `refresh_in_place`
  vs `reset_and_fetch` is Mac's `refreshInPlace` vs `fetchIfNeeded`, and it is
  the rule that stops a re-selection flashing the region back to `Loading`.
- `SessionRoster.show()` drives that transition; `clear()` drops the rows, the
  scroll and the optimistic kill-hides on the way out, and BUMPS THE SERIAL so a
  reply already in flight for the old machine is dropped rather than adopted
  under the new machine's name.
- `SessionRoster.worker` grew the remote branch: `relay_dial.dial(.raw)`, read,
  **free**. Short-lived by design (`SessionBrowserProbe.swift:145-149`), unlike
  the local agent's warm connection which `LocalAgent` owns and this never
  touches. A remote target explicitly does NOT borrow the warm connection -
  that would list THIS box's sessions under another machine's name.
- `chooser_sessions.State` gained `unauthorized`, wired to the SAME sentence the
  rest of `MachineChooser.zig` uses for `error.Unauthorized`. Detecting it
  needed one change in the transport: `ws_client` collapsed every non-101 into
  `WebSocketUpgradeFailed`, so a rejected bearer was indistinguishable from an
  unreachable relay. It now returns `WebSocketUnauthorized` on 401/403.
  Signed out (no credential at all) resolves to the same state without dialling.
- `MachineChooser.syncRoster()` points the roster at the selected row from
  `open` and from `refreshDetail`, and `paintSessions`/`detailSubtitle` lost
  their `row != .local` gates.

### The finding the test caught

`sessionView` - the hit-test/hover/scroll entry point - had a THIRD `row !=
.local` gate, so a remote machine's rows painted but could not be clicked. It
now keys on the roster's own target, because a second reading of "does this row
have a roster" is a second place for the two to stop agreeing. Caught by the
Kill assertion, not by review.

### The test infrastructure (the part that did not exist)

`test/win32/lib/FakeRelay.ps1`: a loopback relay that serves the device
directory AND bridges `ws://.../v1/client/connect` to a real `ghoztty-agent
--listen`, single-threaded on ONE port because `relay_base` is one origin for
both. Failure injection by device id (`-UnauthorizedDevice` 401,
`-UnreachableDevice` 502) and a `-TripFile` that turns the relay off partway
through a run, so a negative control can invert an assertion without breaking
the fixture that was built through the same relay.

Before it, no relay-dialled surface could be exercised on box at all -
`activity-monitor-remote.ps1` says as much in its own header (**T329** now
closes that).

Two bugs it cost, both worth keeping:

- **`[int] -shr 56` is silently `-shr 24`** (.NET masks a shift count to the
  operand's width), so the 8-byte WebSocket length went out corrupt. Fixed, and
  the chunk is capped at 32 KiB so the path is unreachable anyway.
- **Both obvious peer-liveness probes are wrong.** `TcpClient.Connected` reports
  the state as of the last I/O; `Poll(SelectRead) && Available == 0` races the
  loop's own reads and tore down healthy bridges ~30 ms after the upgrade, which
  surfaced in the app as `error.ConnectionClosed`. There is deliberately no
  liveness probe now - a bridge dies when a read, a write, or a close frame says
  so.

`Get-TestChooserRosterGeometry` moved out of `chooser-sessions.ps1` into
`lib\ChromeGeometry.ps1` the moment a second script needed the same Kill button
(T257's rule).

### Validation (all on box, 2026-08-01)

- `zig build test -Dapp-runtime=none` PASS, `-Dapp-runtime=win32` PASS,
  `zig build test-agent` PASS, P1/P2/P3 ALL PASS.
- `test/win32/chooser-sessions-remote.ps1` **ALL PASS (19)**, and
  `-NegativeControl` **ALL PASS (13)** with C inverted.
  The discriminator is the fixture, not the assertion: the app runs with
  `--session-persistence=false` and every repo agent is killed first, so the
  **Local row must resolve to `failed`** while the device row loads **2** - a
  roster that quietly enumerated the local machine would show the same number on
  both. The relay's own request log is the independent witness that the bytes
  went through it.
- `test/win32/chooser-sessions.ps1` (T318, local) still ALL PASS (16).
- Nine unit tests for the target/transition model and `stateText` in the
  none-runtime lane, plus `ws_client.statusCode`.

### Known gap, filed not papered over

**T328**: a Kill on a REMOTE row loses its refetch - `CLOSE_SESSION` and the
`LIST_SESSIONS` behind it both fail (`ConnectionClosed`, sometimes `Timeout`,
which is T326 exactly). The user still sees the row vanish (the optimistic
hide), but the count behind it goes stale. The acceptance script prints
`NOTE T328: …` where that assertion belongs rather than asserting the bug green.
A retry on a fresh dial was tried and **wedged the worker**, so it was reverted;
the comment in `SessionRoster.worker` points at T328.
