# T293 - Activity Monitor: multi-row Kill (label, confirm, aggregated failure) is unit-tested but never exercised on the box

## Summary

A coverage gap T286 left open, named rather than hoped away. Everything about
the **N > 1** kill path is asserted only in the pure lane
(`activity_actions.zig`): the `Kill N` button caption, the
`Kill N processes?` confirmation title, the plural confirmation body, and the
aggregated `Killed K of N (F failed: a, b, c, …)` banner text.
`test/win32/activity-monitor.ps1` exercises **N == 1 only**.

So the on-box claims that are currently *unproven* are the wiring ones, and they
are exactly the kind that a pure test cannot reach:

- ctrl-click and shift-click really accumulate a multi-row selection through
  `toggleSelection` / `extendSelectionTo` (only a single plain click is covered);
- `refreshChrome` really re-captions the button as the count changes, and
  `Options.has_kill` really keeps the room made for the wider caption;
- a batch in which SOME rows fail really produces the aggregated banner rather
  than the single-failure sentence — the branch at `killFailureText`'s
  `total == 1` fork.

## Details

The batch fixture is the interesting part, and it must stay inside T286's
"nothing the box needs is ever a target" rule: spawn **three** throwaway
`cmd.exe /C pause` processes, filter to something that matches all three (they
are all `cmd.exe`, but so are others — prefer selecting by ctrl-clicking the
three known rows found by pid), then Kill.

For the PARTIAL-failure branch, kill one of the three from PowerShell first and
let the panel's selection go stale — but note that `adoptPending` **prunes** a
vanished pid, so the prune has to be beaten: either kill it during the
confirmation dialog (which `modal` freezes adoption for — see T292, and note
that a T292 fix would remove this lever), or point the batch at a pid that
exists but cannot be terminated.

### What shipped, and why it differs from the sketch above

Two deliberate departures, both because the sketch's version could not make the
"nothing the box needs is ever a target" rule STRUCTURAL:

- **The victims are `PING.EXE`, not `cmd.exe`.** A batch of `cmd.exe /C pause`
  throwaways cannot be isolated by the panel's own filter — the app's pane shell
  is a `cmd.exe` too, so "the three rows I meant" would have been a belief about
  pid ordering rather than something the harness could check. Each throwaway is
  spawned as `ping -n 600 127.0.0.1` instead, so the panel's own New Process
  leaves behind a child whose image name matches nothing else in the app's
  process tree: with "Show all" off and the needle set to `ping`, EVERY row on
  screen is one of this section's own, which makes a mis-click harmless by
  construction rather than by care. The row count is re-asserted at every click,
  not once before the first — see the progress log for why.
- **The already-dead row is a PINNED pid, not a vanished one.** Killing a victim
  outright leaves a pid Windows may recycle in the seconds before the batch runs,
  which would point `TerminateProcess` at a bystander. Holding a process handle
  open across the kill keeps the process OBJECT alive, so the pid cannot be
  reused, and `OpenProcess` + `TerminateProcess` then answer
  `ERROR_ACCESS_DENIED` — measured on the box before the arm was written, not
  assumed. The lever is therefore independent of T292's modal-freeze behaviour:
  a T292 fix cannot take it away.

## In plain terms

The Activity Monitor lets you pick several processes at once and end them all
with one button. Everything that button *says* about a group — "Kill 3", "Kill 3
processes?", and the summary it shows when some of them refuse to die — was
checked only in isolation, against made-up inputs. Nobody had ever selected
three real processes in the real window and pressed it. After this, a test does
exactly that on every run: it starts three harmless throwaway processes of its
own, selects them with ctrl-click and shift-click, ends them, and then repeats
the whole thing with one of them already dead so the "2 of 3 worked" message is
seen for real. Anyone touching that panel now finds out immediately if
multi-select or the group kill breaks.

## Goals

- [x] ctrl-click and shift-click really accumulate a multi-row selection on the box
- [x] the Kill button re-captions itself as the count grows, with room for the wider word
- [x] a three-row batch confirms as `Kill 3 processes?` and reports `killed=3 failed=0`
- [x] a batch in which one row is already gone shows the AGGREGATED banner
- [x] the section can never target anything the box needs

      reasons — a stray non-victim row in the table, and a row that had not been
      sampled yet — and both were product-truthful failures of the harness's own
      safety claim, not of the panel. See the progress log.
