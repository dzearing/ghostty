# T705 - The local agent cannot adopt a newer build without ending its sessions or asking

## Summary

Filed out of **T662**, which made the staleness observable (`+sessions --agent`)
and, in doing so, pinned down that the observation has only two exits and both
are lossy:

- **`refresh_now`** — silent restart, allowed only when there are ZERO live
  sessions. A box where a persistent pane is always open never reaches it.
- **`confirm_first`** — the mandatory dialog. Honest, but it costs every live
  session, and it is deliberately deferred during the unattended morning
  refresh (T525). The check that would ask later re-runs only at launch and when
  the last persistent window closes — i.e. on the same box, never.

CLAUDE.md's own agent contract already names the answer it prefers and does not
have: *"Prefer a lazy, non-destructive agent upgrade. Carry sessions across by
upgrading the agent when it is safe … draining/snapshotting and resuming so no
work is lost."* This task is that mechanism.

## In plain terms

The background process that keeps your terminal sessions alive can only pick up
a new version by closing everything you had open — either quietly when you
happen to have nothing open, or after asking you to sacrifice your sessions. If
you always have something open, it never picks one up at all. This task is
about updating it without either.

## What to work out

- The **handoff**: the running agent snapshots its session state (it already
  persists `sessions.json` and per-session output rings), execs the new binary,
  and the new process re-adopts the live PTYs — or, where a PTY cannot be
  handed across, the sessions are relaunched from the same tombstone path a
  reboot already uses, with the user told what happened.
- **Which half owns it.** Handing a ConPTY across an exec is the hard part on
  Windows; a design pass that says plainly what CAN and cannot be carried is
  worth more than an implementation that carries some of it silently.
- It rides the **compatibility boundary**: the new agent must be able to read
  the old one's snapshot, and a handoff that fails must leave the OLD agent
  running rather than neither.
- Until it exists, the documented path is an attended full delivery, and
  `+sessions --agent` is how a user knows one is due (T662).

## Validation criteria

- [ ] A running agent adopts a newer build with live sessions open, no dialog,
      and no session lost — measured with an acceptance script that types into
      a pane before and after (`Test-PaneLive`).
- [ ] A handoff that fails leaves the ORIGINAL agent running and its sessions
      reachable; it never lands on "neither agent".
- [ ] `+sessions --agent` reads `current` afterwards, from the same box, with
      the same pane still alive.
- [ ] Skew both ways still degrades exactly as the agent contract requires.
