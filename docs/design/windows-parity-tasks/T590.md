# T590 - A launch that restores nothing overwrites the session-layout manifest, losing the recorded layout for good

## In plain terms

If Ghoztty starts one time without the background piece that keeps your shells
alive, it opens a single empty window — and then immediately writes that empty
window down as "this is your layout", erasing the record of the windows, tabs
and splits you actually had. Even once the background piece is working again,
they are gone: the last copy was overwritten by the one bad launch.

## Summary

`syncSessionLayout` (`src/apprt/win32/App.zig:1261`) captures the LIVE topology
and `session_layout.write`s it wholesale — the manifest is regenerated, never
merged. A launch where `restoreSessionLayout` returns false opens the default
blank window, whose `addTab` calls `markLayoutDirty`
(`src/apprt/win32/Window.zig:1542`), and the debounced sync then replaces the
recorded layout with that one window.

Normally harmless (the agent holds layout blobs as the second source, T194), it
is total loss in exactly the case where the agent is the thing that is missing:
both copies are then unavailable and the only surviving one is overwritten.

**macOS does not have this bug and says so out loud** — on the no-connection
path it logs `"local agent unreachable; keeping N manifest entries for next
launch"` and returns without touching the file
(`macos/Sources/.../SessionLayoutRestore.swift:56-64`), on the stated reasoning
that the agent and its sessions outlive the app so a later retry recovers them.
This is a win32-only divergence.

## Details

Found while landing T398, which fixes the adjacent half: a no-agent launch now
restores the windows that need no agent. This task is about the ones it still
correctly drops — a terminal-only window — which today are also erased from
disk rather than left for the next launch.

Shape of the fix: suppress the capture-and-write while a launch has recorded
windows it did not restore. Options to weigh: (a) skip the sync entirely until
the first user-initiated mutation when restore was suppressed by a missing
agent; (b) merge rather than replace — carry unrestored manifest entries
forward into the next write, which is closer to Mac's per-entry model. Note the
same write also drives `pushLayoutBlobs`, so whichever is chosen must not
delete the agent's blobs either (a moot point when the agent is missing, but
not on the general "restored nothing" path).

Care needed on the legitimate erase paths, which must keep working: persistence
turned off (`session_layout.clear`), and a user genuinely closing every window.

## Validation criteria

- [ ] With the agent unspawnable, a relaunch that restores nothing leaves the
      recorded manifest intact on disk (not replaced by the blank window).
- [ ] With the agent restored, the NEXT launch brings the original windows back.
- [ ] `session-persistence = off` still clears the manifest.
- [ ] Closing every window with the agent healthy still shrinks the manifest —
      the fix must not make the manifest immortal.
- [ ] An acceptance script covers it (extend `test/win32/viewer-restore.ps1`'s
      no-agent section J, or a sibling script) plus both zig lanes green.
