# T1313 - The Wacatac false positive has not been reported to Microsoft

## In plain terms

Windows deleted Ghoztty on someone's machine because Microsoft's malware model
guessed wrong. Microsoft takes reports of exactly that from the people who build
the software, and corrections usually reach every machine within days. Nobody
has filed one, so every new machine keeps making the same guess.

## Summary

T1293 names this as "the actual remedy and it is free". The Security
Intelligence submission portal at `microsoft.com/en-us/wdsi/filesubmission`
takes a software-developer false-positive report: upload the file, say it is
detected incorrectly, point at the public build. A correction there is global
and permanent for those bytes, which is more than any note on the download page
can do.

**It cannot be done from this seat.** The portal requires signing in with a
Microsoft account, and this box has no browser session for one. That is what
makes it a task rather than something the turn that found it finished.

**A submission corrects BYTES, so the packet cannot be written down.** This
card used to carry a hand-typed table of `win-v1.36.2`'s two hashes. Four more
releases shipped before anyone read it - three of them on one day - so filing
from that table would have corrected a build nobody will ever download again.

So the packet is generated, from whatever is current when somebody sits down to
file. One command:

```
powershell -NoProfile -File scripts\report-false-positive.ps1
```

It downloads the newest release, expands the portable zip so the binaries a
user actually runs are attached by name, hashes them with the same code that
asks VirusTotal about them (`verify-release-clean.ps1`, T1312), looks up the
commit and the workflow run that built those bytes on a clean hosted runner,
and prints the form answers plus a ready-to-paste paragraph. The files are left
on disk to upload, with a `submission-packet.txt` beside them.

## What to do

1. Run the command above, then file the developer false-positive report at
   `microsoft.com/en-us/wdsi/filesubmission` with what it prints.
2. Record the submission id, so it is not carried in somebody's memory:

   ```
   powershell -NoProfile -File scripts\report-false-positive.ps1 -Record ^
       -SubmissionId <id> -Tag <the tag the packet named>
   ```

   It writes to T1313 and T1293 both.
3. Watch it: a submission gets a determination, and the determination is what
   closes T1293, not the act of submitting. Record it the same way, with
   `-Determination "<what Microsoft concluded>"`.
4. If it is upheld rather than corrected, T1293 escalates - that would mean
   Microsoft believes something about these bytes that we do not.
5. Decide whether this becomes a standing release step. Every unsigned release
   is a new set of bytes with no reputation, so the detection can recur on the
   next one; if it recurs twice, the answer is the certificate (D89), not a
   daily form. The generator makes the form cheap, which is exactly why it must
   not become the answer to a problem that is really about signing.

## Validation criteria

- [ ] A submission ID exists and is recorded in T1293.
- [ ] Microsoft's determination is recorded, with its date.
- [ ] A fresh install on a machine that previously quarantined completes
      cleanly, verified rather than assumed.
