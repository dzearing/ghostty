# T331 - Resuming a REMOTE browsed session has no on-box coverage: FakeRelay can now answer one

## Summary

T320 shipped both halves of resume: `App.resumeLocalSession` and
`App.resumeRelaySession`. Only the LOCAL half is exercised on box —
`test/win32/chooser-resume.ps1` builds its fixture out of the local agent's own
orphaned sessions, because that is the machine the script can create sessions
on.

The remote half is therefore code that compiles, is reachable from the UI, and
has never once run on this box:

- `MachineChooser.resumeRow`'s `.remote` branch (the dial and its two failure
  messages),
- `App.resumeRelaySession` (`src/apprt/win32/App.zig`),
- `openDialedWindow`'s new ATTACH shape — `session_id` set, and the per-host
  cwd/shell defaults deliberately SKIPPED because an attach does not spawn.

That last one is the interesting risk: an ATTACH that also sent a working
directory would be describing a spawn that is not happening, and nothing on box
would notice.

## Why it is testable now

T319 built `test/win32/lib/FakeRelay.ps1` — a device directory plus a real RFC
6455 upgrade bridged to a `ghoztty-agent --listen`, with 401/502 injection and a
trip file. `activity-monitor-remote.ps1` and the roster's own remote path
already run through it. A remote resume needs nothing new from it: the bridged
agent is a real agent, so it has real sessions to resume.

## The work

Extend `chooser-resume.ps1` (or a sibling) with a remote run:

1. Start FakeRelay over a `ghoztty-agent --listen` with at least one live,
   unattached session.
2. Select the relay device row, walk the cursor into its roster, Return.
3. Assert `resume session: attaching remote session id=… device=…`, the chooser
   dismissing, and — the independent oracle — the bridged agent reporting that
   session `attached`.
4. Negative: with the relay tripped (or the bearer rejected), the resume must
   leave the chooser OPEN with its hint set, never a half-open window.

## Validation

The new run is ALL PASS, and the local run is unchanged.
