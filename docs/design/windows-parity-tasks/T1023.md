# T1023 - Two release copies at different versions still share one app: the join is loud now, but not refused

## In plain terms

Ghoztty is installed in more than one place on this box - the Start-menu copy
and a portable copy on the Desktop - and they are normally the same build. If
one of them falls behind, starting the older one now hands you a window from the
newer one and tells you so with a notification. What it does not do is start the
older copy for you: to run it you have to quit the newer one first. Whether that
is right, or whether an older copy should be allowed to run on its own, is the
open question here.

## Summary

D79 chose "starting Ghoztty again opens a new window in the app you already
have", with the mitigation *"only join a copy of the same build, so two
DIFFERENT versions still start independently and side-by-side testing keeps
working"*. T1022 delivered that at the LINEAGE level, which is where the
mechanism actually keys:

- `ipc_client.endpointPath` derives the endpoint from the build MODE (the
  `-debug` suffix) plus `$USERNAME`, with `GHOZTTY_PIPE_SUFFIX` as an explicit
  override. So a debug `zig-out` build and the installed release never join -
  the everyday side-by-side development case the mitigation exists to protect,
  and the arm `test\win32\single-instance-join.ps1` section B pins.
- Two RELEASE copies share that endpoint regardless of version, so the stale
  portable joins the current installed one. T1022 made that loud (a `note` on
  the reply plus a desktop balloon naming the copy that owns the window) rather
  than silent, which was D79's stated con.

## Details

What refusing the join would take, and why it was not done in T1022: the endpoint
is only one of THREE things two same-lineage copies share. The local agent's
pipe (`LocalAgent.pipeName`) and the state directory
(`%LOCALAPPDATA%\ghoztty\local-agent[-debug]`) are lineage-derived too, and the
agent pipe has no env override at all. Letting a stale copy start its own app
without also re-keying those would produce two apps sharing one agent and one
saved layout - which is exactly option o2's cons that the user rejected in D79,
arriving through the back door. Doing it properly means a per-build discriminator
in the endpoint, the agent pipe and the state dir, and then answering what
happens to sessions opened under the other build.

Weigh that against the symptom: the case only exists while an install location
is stale, and `scripts\deliver-windows-build.ps1` verifies every delivered
`ghoztty.exe` answers `+version` with the commit being shipped, so the normal
state of the box is three copies at one commit.

Open questions for whoever takes this:

- Is a stale copy that explains itself and refuses to run acceptable, or should
  it be able to run standalone? (If the answer is "run standalone", this is no
  longer a small change - see above.)
- If it stays as it is, should the notice offer an action - "quit the running
  Ghoztty and start this one" - rather than only explaining? That is a much
  smaller change and may be the whole of what is missing.

## Validation criteria

- [ ] Either: a launch of a same-lineage DIFFERENT build starts its own app,

      behavior, with the notice carrying whatever action it should
- [ ] `test\win32\single-instance-join.ps1` grows an arm for whichever answer
