# T1023 - Two release copies at different versions still share one app: the join is loud now, but not refused

## In plain terms

Ghoztty is installed in more than one place on this box - the Start-menu copy
and a portable copy on the Desktop - and they are normally the same build. If
one of them fell behind, starting the older one handed you a window from the
newer one and told you so afterwards, with a notification that is easy to miss.
Now it asks first: the copy you started names both versions and lets you either
take the window from the Ghoztty already running, or back out and quit that one
so you can run the copy you actually started. When both copies are the same
build - the normal state - nothing appears and nothing changes.

## Goals

- [x] A launch of a same-lineage DIFFERENT build never opens a window silently:
      it names the build that is running, the build the user started, and where
      each of them lives
- [x] Both ways out are offered - take the window, or open nothing and quit the
      running copy first
- [x] The everyday case (same build) is completely unchanged, and no scripted
      launch can ever block on the question

## Summary

D79 chose "starting Ghoztty again opens a new window in the app you already
have", with the mitigation *"only join a copy of the same build, so two
DIFFERENT versions still start independently and side-by-side testing keeps
working"*. T1022 delivered that at the LINEAGE level, which is where the
mechanism actually keys:

- `ipc_client.endpointPath` derives the endpoint from the build MODE (the
  `-debug` suffix) plus `$USERNAME`, with `GHOZTTY_PIPE_SUFFIX` as an explicit
  override. So a debug `zig-out` build and the installed release never join -
  the everyday side-by-side development case the mitigation exists to protect,
  and the arm `test\win32\single-instance-join.ps1` section B pins.
- Two RELEASE copies share that endpoint regardless of version, so the stale
  portable joins the current installed one. T1022 made that loud (a `note` on
  the reply plus a desktop balloon naming the copy that owns the window) rather
  than silent, which was D79's stated con.

## Details

What refusing the join would take, and why it was not done in T1022: the endpoint
is only one of THREE things two same-lineage copies share. The local agent's
pipe (`LocalAgent.pipeName`) and the state directory
(`%LOCALAPPDATA%\ghoztty\local-agent[-debug]`) are lineage-derived too, and the
agent pipe has no PER-BUILD discriminator. (Correction, T490: it does have an
env override — `GHOZTTY_AGENT_INSTANCE`, T167 — which forks the pipe, the state
dir and the autostart value together. That is a test-isolation knob, not a
build identity, so the design question below stands; only the "no env override
at all" is wrong.) Letting a stale copy start its own app
without also re-keying those would produce two apps sharing one agent and one
saved layout - which is exactly option o2's cons that the user rejected in D79,
arriving through the back door. Doing it properly means a per-build discriminator
in the endpoint, the agent pipe and the state dir, and then answering what
happens to sessions opened under the other build.

Weigh that against the symptom: the case only exists while an install location
is stale, and `scripts\deliver-windows-build.ps1` verifies every delivered
`ghoztty.exe` answers `+version` with the commit being shipped, so the normal
state of the box is three copies at one commit.

## What landed, and why not the other answer

The second of the two answers the criteria allowed, with the action built
rather than only recorded (D82 carries the call for the user to overturn).

**Why a stale copy still cannot become its own app.** Re-keying the endpoint
alone is not enough, and the other two keys cannot follow it. The local agent's
pipe and the saved window layout are lineage-derived *on purpose*: both have to
survive an update, and an update is precisely the moment the build changes
underneath them. Key them per build and session persistence stops working
across every upgrade - the daily case - to fix a case that only exists while an
install location is stale. Leave them shared and a second app reopens the same
windows a second time and fights over what is saved, which is option o2's cons
arriving through the back door.

**What honours the mitigation instead is the choice.** The launch that loses
the race now asks `version` of the instance that won it
(`ipc_client.queryIdentity`), compares with its own identity
(`ipc_handoff.sameBuild`), and on a mismatch shows a dialog naming both builds
and both paths before anything opens: **Open Window** hands off as before,
**Cancel** opens nothing and leaves the running app alone. A same-build launch
never sees it.

Everything on the path fails toward the old behavior: no answer from the
running instance, an allocation failure, or `GHOZTTY_HANDOFF_PROMPT=join`
(what a scripted launch sets, so a modal dialog can never block one) all hand
off exactly as the build before this did.

Where it lives: `src/os/ipc_handoff.zig` (`mismatchPrompt`, the `prompted` wire
field), `src/os/ipc_client.zig` (`queryIdentity`), `src/apprt/win32/App.zig`
(`handoffChoice`, plus the debug-only `GHOZTTY_HANDOFF_VERSION`/`_COMMIT` seam
that makes the mismatch reachable from a test at all),
`src/apprt/win32/IpcHandlers.zig` (a launch that already asked does not also
earn a balloon).
