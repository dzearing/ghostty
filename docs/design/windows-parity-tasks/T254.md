# T254 - Own the non-client caption bar: NCCALCSIZE takeover, custom caption paint and buttons, Snap Layouts

## Summary

**Split out of T234 on 2026-07-31, because T234's central premise is false.**

T234 says, verbatim: *"**We do own the caption bar.** The window already runs a
custom-drawn caption (T78 title font, T203 accent/theming, T205's in-titlebar
tab work), so hosting a control there is a paint + hit-test change, not a new
mechanism."*

That is wrong, and it was already written down as wrong in **T205**, filed a day
earlier and never reconciled:

> - No `WM_NCCALCSIZE` handling anywhere in `src/apprt/win32/` - the non-client
>   area is entirely the system's, so the caption is stock.
> - `DwmExtendFrameIntoClientArea` is DECLARED in `win32.zig:1250` but has no
>   call site. The binding exists; the feature does not.

Re-verified on 2026-07-31 (✓ VERIFIED by reading, not grep alone):

- `Window.zig:562` creates every window with plain `WS_OVERLAPPEDWINDOW`. The
  caption, its title text, and the minimize/maximize/close group are drawn by
  **DWM**, in the non-client area, in another process's composition pass.
- `grep -n "WM_NCCALCSIZE\|WM_NCPAINT"` over `src/apprt/win32/` returns
  **nothing** — the constants are not even declared in `win32.zig`.
- What T78 and T203 actually do is *ask DWM to restyle its own caption*:
  `title_font.zig`'s own header says *"the DWM caption of a standard-frame
  window always draws with the system caption font"*, and T203 sets
  `DWMWA_CAPTION_COLOR` / `DWMWA_TEXT_COLOR` / `DWMWA_USE_IMMERSIVE_DARK_MODE`
  (`Window.zig:428-460`). Tinting a surface someone else paints is not owning
  it. There is no DC we can draw a button into, and `GetWindowDC` +
  `WM_NCPAINT` is composited away under DWM.

So "put a `...` button left of minimize" is **not** a paint + hit-test change on
an existing custom caption. It requires building the custom caption first, which
is a mechanism this codebase does not have yet, and it is the *same* mechanism
T205 needs. Building it once, here, is what makes both of them small.

## Scope

Ship the foundation, and nothing that rides on it:

1. **`caption_layout.zig`** — a pure geometry module in the
   `tab_strip_layout.zig` / `split_geometry.zig` mould (no OS imports, so it
   tests in the `-Dapp-runtime=none` lane). Input: client width, DPI scale,
   maximized flag. Output: the caption band height and the rects for the title
   text region, the drag region, and the min / max / close buttons. Asserted at
   **1.0, 1.25, 1.5 and 2.0** against the design system: 28 DIP painted squares
   on one vertical frame, >= 4 DIP clear of everything, gaps between PAINTED
   edges.
2. **`WM_NCCALCSIZE`** — consume the caption so the top band becomes client
   area, while the left/right/bottom resize borders stay. The maximized case is
   the one that bites: a maximized window must be inset by
   `SM_CXSIZEFRAME + SM_CXPADDEDBORDER` or its content runs off the monitor.
3. **`WM_NCHITTEST`** — `HTTOP` for the top resize band, `HTCAPTION` for the
   drag region, and `HTMINBUTTON` / `HTMAXBUTTON` / `HTCLOSE` for our own
   buttons. Returning `HTMAXBUTTON` is what keeps the **Snap Layouts** flyout
   working; it is not optional and it must be tested.
4. **Caption paint + button states** in the existing `WM_PAINT` cycle: title
   text in the T78 font, the three system glyphs as filled shapes (design
   system §4 — never `LineTo`), rest/hover/pressed/disabled through
   `icon_button.zig` so they cannot invent their own treatment. Close keeps
   Windows' red hover (`#C42B1C`) as a named platform divergence.
5. Everything downstream of "the client rect grew upward": `surfaceRect`,
   `tabBarHeight`'s origin, `invalidateTabBar`, the split/hero/banner overlay
   rects, `WM_DPICHANGED`, and the borderless (`window-decoration = false`)
   path at `Window.zig:3229`, which strips `WS_CAPTION` and must keep working.

**Out of scope, deliberately:** the `...` button itself and hiding the strip at
one tab (**T234**, now depends on this), and moving the tab strip into the
caption row (**T205**, whose scope shrinks to exactly that once this lands).

## Why this ordering (the decision T234 asked to have recorded)

T234's own "Constraints that will bite" section ends with: *"Sequence them
deliberately ... If T234 lands first, T205's scope shrinks to 'the 2+-tab case',
which is probably the better order. Record the decision."*

Recorded: **T254 → T234 → T205.** The custom caption is the shared prerequisite
of the other two, so it goes first and goes in once. T234 then becomes what it
claimed to be all along — a button rect plus a visibility rule — and T205
becomes "move the strip run into the caption band", with the band, its hit
testing and its buttons already built and asserted.

## Process lesson (file it here so it is not lost)

**Two tasks describing the same subsystem disagreed for a day and nobody
noticed**, because each was read alone at the moment it was worked. T205 had the
correct finding on 2026-07-30; T234 asserted the opposite on 2026-07-31 and used
it to size itself as small. The cost here is one turn of re-verification; the
cost of *not* catching it is starting a "paint + hit-test change" and
discovering mid-flight that there is no surface to paint on.

The general rule: **when a task's summary makes a load-bearing claim about
existing machinery, verify it against the source before sizing the task** — and
when a sibling task covers the same subsystem, read that one too. A claim
inherited from another task file is not evidence.

## Three lessons this task paid for

1. **A load-bearing claim inherited from another task file is not evidence.**
   T234 sized itself as "a paint + hit-test change" on a caption we did not
   own. T205 had the correct finding a day earlier. Verify against the source
   before sizing.
2. **The design system's "2 DIP stroke for every glyph" was written for OPEN
   marks.** A closed outline at 2 DIP on a 10 DIP box has a 6 DIP interior and
   reads as a filled square with a dot in it — which shipped for one build and
   was obvious the moment it was looked at. Amended in §4.2 with the reason
   and an assertion, not patched at the call site.
3. **Do not set hover state from a press handler.** `handleNcLButtonDown` set
   `caption_hover` alongside `caption_pressed`; nothing ever cleared it,
   because the only thing that clears hover is the pointer MOVING, and the
   pointer had never reported being there. The button stayed lit forever after
   one press. Caught by asserting the un-light, not the light.
