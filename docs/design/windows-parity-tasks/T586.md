# T586 - Nothing catches an acceptance script that cannot run: chrome-theme.ps1 shipped calling a helper that was never written and died on its first line

## In plain terms

One of the Windows UI test scripts was checked in calling a helper function
that does not exist anywhere in the repo, so it stopped on its very first line
with "the term is not recognized" - for a week nobody noticed, because nothing
runs these scripts except a person deciding to. A test that cannot start looks
exactly like a test nobody ran, and both read as silence.

## Goals

- [x] A cheap gate that catches a `test/win32/*.ps1` which cannot even start
- [x] It runs without launching the app or taking the box for an hour

## Summary

`test/win32/chrome-theme.ps1` called `Test-ExeIsDebugBuild`, a function that
exists nowhere in the repo. It was introduced by T308 (commit 778c44505,
2026-08-07) and the script has been unrunnable ever since - it throws at line
299, before a single assertion. Found on 2026-08-07 while validating T307,
which needed that script; fixed in the same commit by composing the two
`lib/BuildMode.ps1` helpers that already existed
(`Test-GhozttyIsolatedBuildMode (Get-GhozttyBuildMode -Exe $exe)`).

The one-line fix is not the interesting part. The gap is that a task closed
`done` with an acceptance script that could not execute, and nothing anywhere
would have said so. The standing floor is P1-P3 plus the zig lanes; the other
80+ scripts in `test/win32/` are only ever run by whoever remembers to.

## Where

- `test/win32/*.ps1` - 80+ scripts, most of them not in any standing lane.
- `test/win32/lib/*.ps1` - the shared helpers whose names they depend on.

## Options worth weighing

1. A parse-and-resolve smoke check: for each script, tokenize it with
   `[System.Management.Automation.Language.Parser]::ParseFile`, collect every
   command name it invokes, dot-source the same `lib/*.ps1` it does, and report
   any name that resolves to nothing. No app launch, seconds to run, and it is
   exactly the failure that happened here.
2. Run every script nightly. Honest but expensive (hours of box time) and it
   catches this class of failure no earlier than option 1.
3. Require the turn that touches a script to run it. Already the rule; it is
   what did not happen.

## Validation criteria

- [x] The check FAILS on a deliberately reintroduced call to a nonexistent
      helper, and PASSES on the repo as it stands - negative control run.
      Verified: `test\win32\command-resolve-audit.ps1 -TeethCheck` plants
      `Test-ExeIsDebugBuild` into a real file in the suite directory and C1/C2
      require the sweep to name it (ALL PASS, 18 assertions); the routine run
      is ALL PASS, 15 assertions, ~20s over 291 roots.
- [x] It is wired somewhere a turn will actually see it (a lane, or the
      validate step). Verified: guard-due row `command-resolve` covers
      `test\win32\*.ps1` and `test\win32\lib\*.ps1`, so any edit here makes it
      due, step 0's claim reports it and `parity-tasks.ps1 validate` fails
      until it has run green.
- [x] The sweep found a SECOND live instance of the defect and it is fixed:
      `release-artifacts.ps1` had its if/elseif/else chain pasted twice, so the
      second `elseif` parsed as a command and the run threw with B5-B9
      unmeasured. After removing the duplicate the script is ALL PASS and
      B5-B9 run.
