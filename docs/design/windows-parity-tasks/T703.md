# T703 - The agent never sets attached_elsewhere, so the documented steal handshake is dead code on both sides

## In plain terms

The design says that when a second window tries to open a terminal session
someone else already has open, the first one is asked politely and the second
one has to say "no really, give it to me". That conversation is written down in
three places and implemented in none: the background service just hands the
session over without ever objecting. Nothing is broken for a user today — the
handover works — but a chunk of the app is written to handle an answer it can
never receive, so nobody would notice if it stopped working.

## Summary

Found while landing T657. `protocol.Attached.attached_elsewhere` is documented
as §5.3's steal signal ("Set when the session already had an attached bridge;
the client may retry with `force = true` to steal"), and `protocol.Attach.force`
is the retry. Both halves of the CLIENT exist and are tested:

- `Connection.attachChannelCancellable` returns no pane when
  `attached_elsewhere and !force` (`connection.zig`, the `keep` condition).
- `Remote.threadEnter` detects that case and re-attaches with `force = true`.
- `connection.zig`'s test "attachChannel: steal — attached_elsewhere without
  force, then force succeeds (§5.3)" covers it.

But the only producer is `LifecycleAgent.attached_elsewhere_first`, the test
fake. Grepping `src/remote/agent/` finds no write to the field at all:
`Server.handleAttach` calls `bindLocked(s)` unconditionally on a live session,
which silently repoints the bridge at the new connection and never reports that
anyone else held it. `Attach.force` is likewise read by nobody on the agent side.

So today: every ATTACH steals, immediately and silently; the client's retry
branch is unreachable against a real agent; and one of the reason tokens T657's
notice renders (`attached_elsewhere`) can only ever come from a status the real
agent does not produce.

## Approach

Decide which way the divergence resolves — the code or the spec — and make the
other match. Do NOT implement the handshake just because it is written down;
"attach always wins" may well be the better behavior, and the reconnect swap
(WP-D1) plus restore (WP-D2) both DEPEND on a re-attach succeeding for a session
their own superseded connection still holds. The steal-with-force dance would
cost every one of those an extra round trip to reach the same place.

Two candidate resolutions:

1. **Spec follows code** (likely correct): document that a live ATTACH always
   re-binds, retire `attached_elsewhere` and `force` as no-ops kept for wire
   compatibility (never removed — an older client still sends `force`), and
   delete or re-point the client's retry branch. Keep the notice token: a
   FUTURE agent could produce it, and rendering a generic sentence for a token
   this build cannot see is exactly what the mapping is built for.
2. **Code follows spec**: have `handleAttach` report `attached_elsewhere` when
   `s.bound` and the bridge belongs to another connection, gated on a
   capability so an older client (which would then get no pane and no retry)
   is not regressed. This is the more invasive option and needs the reconnect
   and restore paths measured first — they are the common case, not the
   exception.

Either way the acceptance evidence is the same: the branch must be reachable
from a real agent, or gone.

## Validation criteria

- [ ] `attached_elsewhere` is either produced by the real agent on a real path,
      or documented as never produced (protocol.zig, CLAUDE.md, the
      session-persistence design) with the client's dead branch removed.
- [ ] The `connection.zig` steal test either exercises the real server or is
      re-labelled as pinning a wire shape rather than a behavior.
- [ ] The reconnect swap and launch restore still re-attach a session their own
      superseded connection holds, with no added round trip — measured, not
      assumed (`test/win32/session-persistence.ps1`, remote reconnect arms).
- [ ] Both skew directions asserted if a capability is introduced.
