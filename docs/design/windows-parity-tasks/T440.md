# T440 - The watchdog died at 09:14 and nothing noticed for 13 hours; the dashboard read 'nothing running' because the lock still named a claude the upgrade had killed

## Summary

Reported by the user 2026-08-03 22:00: "the status page isn't reporting what's
running". Two independent causes, both silent. The watchdog process died at
09:14 and its HKCU Run entry only restarts it at logon, so the loop had no
supervisor for 13 hours. And the loop lock still named claude pid 16800, which
the 20:51 upgrade killed, so every reader — the dashboard included — saw
`stale-dead` while a session was very much alive in that pane.

## In plain terms

There is a page that is supposed to answer "is the robot working, and on what".
It said nothing was happening while work was going on, and separately the thing
whose whole job is to restart the loop if it stops had itself stopped in the
morning without telling anyone. Neither failure makes a sound: you only find out
by looking, which is exactly what the page was supposed to save you from.

## Goals

- [x] A dead watchdog is visible — on the dashboard, not only in a log that
      stops
- [x] The watchdog comes back without waiting for a logon
- [x] The lock's claude pid follows a relaunch, so "alive" means alive

## What landed (2026-08-04)

### 1. The watchdog stamps a beacon on every tick

`go-loop-watchdog.ps1` now writes `watchdog_pid` / `tick_at` / `poll_seconds` /
`last_tick` into its state file after **every** tick, healthy ticks included.
That is the whole point: a supervisor doing its job takes no actions, so
`last_action` could not tell "watching quietly" from "gone", and the only other
evidence was a log that stops — which nobody reads until they already suspect.

Two details that are load-bearing rather than incidental:

- The write is **after** the tick, not before, so a watchdog wedged inside one
  goes stale exactly like a dead one.
- A `-Once` run writes **nothing**. The upgrade script's handoff
  (`Invoke-WatchdogNow`) is a `-Once` process that exits seconds later; stamping
  its pid here would have reported the supervisor as dead moments after a
  handoff that worked.

`Write-State` and the beacon **merge** into one file rather than overwriting it,
so the rearm hold-off's history and the liveness beacon coexist.

`-Status` prints the human-readable version: running, pids, last tick, and both
autostart hooks.

### 2. A revive task, because a Run entry only fires at logon

`-Install` now registers **two** things: the HKCU Run entry as before, plus a
per-user scheduled task (`schtasks /sc MINUTE /mo 10`, no elevation needed —
`/sc ONLOGON` is the one that does) that re-launches the watchdog every ten
minutes. Re-launching forever is safe because the single-instance mutex makes it
a no-op while the watchdog is alive, so the task is a **revival trigger**, not a
second supervisor. Worst-case dead time goes from "until the next logon" —
thirteen hours, on the day this was filed — to ten minutes.

### 3. The lock answers about the PANE, not the pid

`go-loop-lock.ps1 status`, when the recorded pid is a corpse, asks the owning
pane whether a claude is sitting in it, and reports `held` with
`owner_alive_by=pane` if so. That is the whole window after an upgrade relaunch,
before the fresh session reaches go.md step 0 — an entire turn, unbounded if the
resume failed (T439).

`acquire` is deliberately **not** pane-aware: a probe that misreads must never be
able to wedge the loop, so a dead recorded owner is still taken over.

**And the watchdog explicitly opts out** (`-NoPaneProbe`). This was caught by the
existing N4/N5 assertions failing, not by inspection: "the recorded pid is a
corpse but a claude is in the pane" is not a healthy loop to the watchdog, it is
its single most important cue — the relaunched-but-idle session the whole nudge
path exists for (T241, T439). Reading it as `held` made the watchdog do nothing
in exactly the case it was built for.

The dashboard gets the same answer by **asking the lock script** rather than
reimplementing the rule, cached 30s and only reached once the pid is already
dead.

### 4. The pane classifier had gone blind to a busy Claude Code

Not in the original report, and found only because goal 3 depends on it: probing
this very pane returned `unknown`. Every marker in `go-loop-pane-probe.ps1`
belonged to the **idle** composer (`bypass permissions`, `for shortcuts`,
`esc to interrupt`), and a Claude Code that is *working* scrolls all of them off
the screen.

`unknown` is not a harmless answer. With a dead recorded pid the watchdog would
have fallen through to the shim branch and typed a **shell command path into a
live TUI** — the T241 failure, silently back.

Fixed on two levels: the busy screen's token counter (`tokens)`) as a word
marker, and Claude Code's own transcript glyphs (U+25CF bullet, U+23BF
tool-result connector, built from code points so the file stays ASCII) as a
version-independent fallback. Chrome *wording* has now drifted twice; the glyphs
have not. Matching scrollback is safe only because rule 1 outranks it — a claude
that exited leaves its glyphs *and* a shell prompt at the bottom, and the prompt
is what the pane is classified by (asserted, M15).

## Details

### 1. The watchdog stopped and stayed stopped

`%TEMP%\ghoztty-go-loop-watchdog.log` runs `healthy` every 5 minutes up to
`2026-08-03 09:14:24` and then simply ends. The `GhozttyGoLoopWatchdog` HKCU Run
entry is intact, but a Run entry fires at logon only, so the process was gone for
the rest of the day. Restarted by hand at 22:03:47, which immediately logged
`healthy: pid=32248`.

Nothing anywhere reports "the supervisor is missing". The log ending IS the
signal, and reading a log to find out whether the thing that watches for silence
is silent is the wrong shape.

Note the second-order cost: with the watchdog dead, the T439 resume failure had
no recovery path at all. Its `RESUME-REUSE FAIL` message says "the watchdog will
re-enter", and there was no watchdog. Two mitigations that each assume the other
is present.

### 2. The lock named a dead claude

`temp/go-loop.lock.json` held `claude_pid: 16800`; `go-loop-lock.ps1 status`
answered `stale-dead ... alive=False age=74.3m`. The live session in that same
pane was pid 32248 — the upgrade killed and relaunched claude, and nothing
updated the lock.

The design deliberately leaves this to the NEXT `go-loop-exec.ps1 claim`, since
ownership is keyed on the pane and a relaunched claude in the same pane is the
same slot. That is fine for the loop's own correctness and wrong for every
observer: between the relaunch and the next claim — an entire turn, and
unbounded if the resume failed (T439) — the lock reads dead while the session
runs. `claim` at 22:03 fixed it in one call (`turn=88 pid=32248`).

Candidate fixes:

- Have the relaunch path hand the lock its new pid, rather than leaving it to
  the next claim (this is what T241 did for the watchdog's own nudge; the
  upgrade script has no `go-loop-lock` call at all).
- Or teach readers to trust the PANE over the pid: a live claude in the locked
  pane is the owner whatever pid the file remembers.

### 3. What the page should have said

Neither cause is the dashboard's fault, but the dashboard is where they became
visible, so it is where the fix has to land: a loop whose lock is stale-dead and
a watchdog that has not logged in 13 hours are both states worth SHOWING, not
states worth rendering as an empty "In flight".
