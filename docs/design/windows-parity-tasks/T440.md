# T440 - The watchdog died at 09:14 and nothing noticed for 13 hours; the dashboard read 'nothing running' because the lock still named a claude the upgrade had killed

## Summary

Reported by the user 2026-08-03 22:00: "the status page isn't reporting what's
running". Two independent causes, both silent. The watchdog process died at
09:14 and its HKCU Run entry only restarts it at logon, so the loop had no
supervisor for 13 hours. And the loop lock still named claude pid 16800, which
the 20:51 upgrade killed, so every reader — the dashboard included — saw
`stale-dead` while a session was very much alive in that pane.

## In plain terms

There is a page that is supposed to answer "is the robot working, and on what".
It said nothing was happening while work was going on, and separately the thing
whose whole job is to restart the loop if it stops had itself stopped in the
morning without telling anyone. Neither failure makes a sound: you only find out
by looking, which is exactly what the page was supposed to save you from.

## Goals

- [ ] A dead watchdog is visible — on the dashboard, not only in a log that
      stops
- [ ] The watchdog comes back without waiting for a logon
- [ ] The lock's claude pid follows a relaunch, so "alive" means alive

## Details

### 1. The watchdog stopped and stayed stopped

`%TEMP%\ghoztty-go-loop-watchdog.log` runs `healthy` every 5 minutes up to
`2026-08-03 09:14:24` and then simply ends. The `GhozttyGoLoopWatchdog` HKCU Run
entry is intact, but a Run entry fires at logon only, so the process was gone for
the rest of the day. Restarted by hand at 22:03:47, which immediately logged
`healthy: pid=32248`.

Nothing anywhere reports "the supervisor is missing". The log ending IS the
signal, and reading a log to find out whether the thing that watches for silence
is silent is the wrong shape.

Note the second-order cost: with the watchdog dead, the T439 resume failure had
no recovery path at all. Its `RESUME-REUSE FAIL` message says "the watchdog will
re-enter", and there was no watchdog. Two mitigations that each assume the other
is present.

### 2. The lock named a dead claude

`temp/go-loop.lock.json` held `claude_pid: 16800`; `go-loop-lock.ps1 status`
answered `stale-dead ... alive=False age=74.3m`. The live session in that same
pane was pid 32248 — the upgrade killed and relaunched claude, and nothing
updated the lock.

The design deliberately leaves this to the NEXT `go-loop-exec.ps1 claim`, since
ownership is keyed on the pane and a relaunched claude in the same pane is the
same slot. That is fine for the loop's own correctness and wrong for every
observer: between the relaunch and the next claim — an entire turn, and
unbounded if the resume failed (T439) — the lock reads dead while the session
runs. `claim` at 22:03 fixed it in one call (`turn=88 pid=32248`).

Candidate fixes:

- Have the relaunch path hand the lock its new pid, rather than leaving it to
  the next claim (this is what T241 did for the watchdog's own nudge; the
  upgrade script has no `go-loop-lock` call at all).
- Or teach readers to trust the PANE over the pid: a live claude in the locked
  pane is the owner whatever pid the file remembers.

### 3. What the page should have said

Neither cause is the dashboard's fault, but the dashboard is where they became
visible, so it is where the fix has to land: a loop whose lock is stale-dead and
a watchdog that has not logged in 13 hours are both states worth SHOWING, not
states worth rendering as an empty "In flight".

## Validation

- Kill the watchdog and assert the dashboard says so within one refresh.
- Relaunch claude in the locked pane and assert `go-loop-lock.ps1 status`
  reports held/alive without waiting for a claim.
