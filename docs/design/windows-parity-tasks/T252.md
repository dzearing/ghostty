# T252 - GetDC-painted chrome is not reproducible - audit the remaining sites (and the premise: it is NOT invisible to PrintWindow)

> Filed as *"GetDC-painted chrome never marks the region dirty, so it is
> invisible to PrintWindow"*. The first half holds; the second half was
> measured false while doing the audit, so the title carries the corrected
> claim. The Summary below is the task as filed and is left as written — what
> replaces it is **What was measured** further down.

## Summary (as filed)

**A surprise that cost real time in T233 and will cost it again.** The split
divider's hover shade was implemented, was correct on screen, and was
completely invisible to the acceptance test — two assertions failed against a
build whose behavior was right.

Root cause, measured 2026-07-31: painting via `GetDC(hwnd)` + draw +
`ReleaseDC` puts pixels on the glass but **never marks the region dirty**, so
they do not reach the window's backing store. Anything that RE-RENDERS rather
than re-composites — `PrintWindow`, which is how every test on the T211
background desktop reads pixels — replays the last real `WM_PAINT` and sees
the old content. The state existed on the glass and nowhere else.

The fix in T233 was `refreshDividerBand`: `InvalidateRect` on the one band's
rect + `UpdateWindow`, i.e. paint through the normal cycle.

**The shortcut is not wrong everywhere**, which is why this is an audit and
not a blanket removal. `layoutSplits` uses it for a band that MOVED — the old
pixels are already covered by a child window, so there is no dirty region to
mark and nothing else would repaint them. That is a legitimate use. The
hazard is that the two cases look identical at the call site.

## In plain terms

Nothing a user can see changes here. Windows chrome — the lines between split
panes, the titlebar — is drawn two different ways in this codebase, and one of
them draws pixels that nothing will ever draw again: they survive until the
next time that patch of the window is repainted for any reason, and then they
are gone. Both ways were being used side by side, three lines apart, with no
way to tell at the call site which one a piece of code needed. This sorts them
out, writes the rule down where the next person will hit it, and fixes the one
place that was using the fragile kind for a job that needed the durable kind.

It also corrects something the project believed and had written into three
files: that pixels drawn the fragile way are invisible to the screenshots our
tests take. Measured across three builds — they are not. The earlier
investigation blamed the wrong thing, and a wrong reason in a comment is worse
than no reason: it sends the next person hunting a bug in the test harness that
does not exist.

## What was measured (and what it overturns)

Three builds of the same tree, each running `split-divider.ps1` run 1 (a red
divider, then a live config reload to cyan), differing only in which painter
was compiled in:

| Arm | `paintWindow` dividers | `onConfigChange` GetDC | Startup band | After reload |
|---|---|---|---|---|
| control | off | off | **red, captured** | still red |
| GetDC only | off | on | red, captured | **cyan, captured** |
| WM_PAINT only | on | off | red | **cyan** |

Conclusions, in order of how much they change:

1. **A `GetDC` paint IS visible to `PrintWindow(PW_RENDERFULLCONTENT)`** — the
   capture every acceptance script on the background test desktop uses. The
   control arm (neither painter) is what makes that a measurement rather than a
   coincidence: with nothing painting, the stale colour stayed.
2. So T233's recorded root cause is wrong. What actually made T233's hover
   invisible is that the hover STATE does not survive on that desktop: a posted
   `WM_MOUSEMOVE` sets it and the OS posts `WM_MOUSELEAVE` within a frame,
   because `TrackMouseEvent` watches a real cursor that is not there.
   `split-divider.ps1`'s own header says exactly this, and its hover oracle is
   the debug log for that reason — the two explanations in the repo contradicted
   each other and this is the reconciliation.
3. The rule survives with a different reason: a `GetDC` paint is **not
   reproducible**. Nothing recorded that the region needs drawing, so those
   pixels stand only until the first `WM_PAINT` covering them, which then
   derives its own from state. For anything derivable from state, invalidating
   is shorter and self-healing.
4. **The red→cyan assertion was passing by luck**, in the strict sense: it
   still passed with `onConfigChange`'s repaint deleted outright, because
   something else in the reload path invalidates the client area. Not the DWM
   chrome calls, not `updateDimOverlays`, not `DarkMode.apply`, and not a
   relayout (arm 1 proves `layoutSplits` does not run — its own GetDC pass would
   have painted cyan). Unidentified, and filed as **T765**.

## Sites audited

Every `w32.GetDC` in `src/apprt/win32`, split by what it does:

- **Paints to its own window (3):** `Window.layoutSplits` (moved band — kept,
  commented), `Window.onConfigChange` (colour change — converted to
  `refreshAllDividerBands`), `ViewerFeedbackBar`'s RichEdit subclass (quote bars
  + placeholder — kept: an overlay on a control we do not own, which validates
  its own region inside `CallWindowProcW`, and which is re-run by every
  `WM_PAINT`, so it is reproducible; not capturable through the control's
  `WM_PRINT`, hence that script's log oracle).
- **`GetDC(null)` screen DC for text metrics (8):** `ConfirmDialog`,
  `HostSettingsDialog`, `NewProcessDialog`, `KeyStateIndicator`,
  `ReadonlyBadge`, `clipboard_image`, `gdiplus_decode`, `screen_capture`.
  Measurement, not painting.
- **`GetDC(hwnd)` for measurement only (5):** `Window.measurePillLabel`,
  `BannerOverlay.ensureContentHeight`, `MachineChooser.measureHintLines` /
  `measureWith`, `RegionSelector.measureHint`, `ViewerTOCPanel.measureRows`.
- **Buffer sources (2):** `Scrollbar` / `KeyStateIndicator` build a DIB for
  `UpdateLayeredWindow` (a layered window owns its own surface — a different
  mechanism, not this rule), and `Surface` holds a `CS_OWNDC` DC for the GL
  context.

## Original sites to audit

- `Window.zig` `layoutSplits` (~1868) — the legitimate case; confirm and
  comment it as such.
- `Window.zig` `onConfigChange` (~494) — re-colors dividers after a config
  reload. `split-divider.ps1`'s red→blue assertion currently passes through
  `PrintWindow`, so something else is invalidating; find out WHAT, because if
  it is incidental the test is passing by luck.
- Any other `GetDC` + paint in the win32 chrome (grep `w32.GetDC`).

## The fix

For each site, either (a) it is a moved-region case → keep and comment why, or
(b) it is a state/color change → convert to invalidate + paint cycle. Then
state the rule where a reader will hit it: **a chrome change that alters only
COLOR must go through `WM_PAINT`; `GetDC` is only for a region nothing will
invalidate.** `docs/design/win32-design-system.md` is the natural home.

## Validation

- Whatever changes, the T233 probes still read the hot color mid-drag, and

- If `onConfigChange` turns out to be passing by luck, add the missing
  invalidation and keep the red→blue assertion as its regression.
