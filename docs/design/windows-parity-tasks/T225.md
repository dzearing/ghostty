# T225 - Migrate the last three GUI scripts once their mechanism blockers land

## Summary

T217 finished the 19 keyboard-only GUI scripts that could be converted onto the
test desktop. Three could not, and each is blocked on a *mechanism* question
owned by another task rather than on migration effort:

| script | blocked on | the question |
|---|---|---|
| `split-dim` | **T214** | its oracle is a `GetPixel` over the OpenGL TERMINAL surface (focused pane vs dimmed pane); PrintWindow returns a flat fill there, so a "migrated" assertion would pass against nothing. |
| `overlay-zorder` | **T224** | its entire oracle is expressed against **the foreground window**, and `GetForegroundWindow` is 0 for every window on a background desktop. The z-order half is portable; the activation half needs a decision, and would *invert* rather than weaken if ported naively. |
| `profile-latency` | **T224** | its section-3 positive control is a PrintWindow pixel hash of the TERMINAL surface before/after `ctrl+home` (same flat fill), and it measures input LATENCY through `SendInput` - a posted-key port measures a different quantity. |

This task exists so the remaining three are not lost when T217 closes. It is
the *migration*; T214 and T224 are the *decisions*. Do not start it before
both have answered - a port that quietly substitutes a different quantity is
the vacuous-assertion failure mode T217 batches 3 and 4 both warn about.

## Status after T224 (2026-08-01): one script left, not three

- **`overlay-zorder`** - DONE. T224 answered its mechanism question (the
  ACTIVE window is a measured-faithful stand-in for the foreground window) and
  migrated it in the same turn, since a decision about an oracle is only real
  once something asserts with it. `ALL PASS (24)` x3, negative control FAILS.
  Its section E is skipped pending **T277**.
- **`profile-latency`** - DECIDED, and the decision is *not to migrate*:
  interactive by design, declared in `lib\TestDesktop.ps1`'s standing list.
  See T224 for the reasoning; nothing to do here.
- **`split-dim`** - the only one still open. T214 landed the terminal-surface
  route (ask which THREAD painted the pixels, find another native painter,
  drop the assertion in place, or declare it interactive), so the dim
  overlay's own `GhozttyDimOverlay` chrome is capturable even though the
  surface under it is not - which is route 1/2 territory, exactly as this task
  predicted. The z-order helpers it will want
  (`Get-TestZIndex`/`Get-TestOverlaySandwich`/`Set-TestWindowTopmost`) now
  exist in the harness.

## Details

The mechanical conversion is the one T217 documents (see that task's "The
mechanical change per script" plus the per-batch "things learned" notes, which
are the accumulated migration handbook). Everything those 19 scripts needed is
already in `test/win32/lib/TestDesktop.ps1`; expect the *new* work here to be
whatever oracle T214/T224 decide on, not harness plumbing.

Per-script starting points, from the T217 batch notes that deferred them:

- **`split-dim`** - if T214 lands a terminal-surface capture path, the existing
  probes port as-is. If it concludes there is none, the dim assertion has to be
  re-expressed against something observable off the input desktop (the dim
  overlay is a separate `GhozttyDimOverlay` popup - its own chrome may be
  capturable even when the surface under it is not, which is exactly the
  distinction that made `pane-banner` migrate cleanly in batch 8).
- **`overlay-zorder`** - the `EnumWindows` index / `WS_EX_TOPMOST` /
  owner-relative sandwich half only needs marshalling onto the worker thread
  (`Get-TestWindowStyle` already exists for the style reads). What T224 must
  settle first is whether `Focus-TestWindow`'s `SetActiveWindow` raises a window
  within its band the way real activation does - i.e. whether "the ACTIVE
  window" is a faithful stand-in for "the foreground window" for this claim.
- **`profile-latency`** - decide deliberately whether a posted-key latency
  number is worth measuring at all, or whether the script keeps an
  interactive-desktop lane (`-Interactive`) for the latency half and migrates
  only the parts that do not depend on input timing.

## Validation

- Each script ALL PASS x3 on the test desktop (or, where T214/T224 conclude a
  claim cannot be asserted off the input desktop, that claim is DELETED with
  the reason recorded here - never relabelled onto a weaker measurement).
- Each script's negative control still FAILS.
- Whole-suite run never takes foreground (asserted, not assumed).
- Harness regression: the already-migrated scripts re-run green after any
  `lib/TestDesktop.ps1` change.
