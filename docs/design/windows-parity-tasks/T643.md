# T643 - T400's stale-debounce fetch count is intermittent in the win32 lane

## In plain terms

One of the automated checks that guards against the viewer re-downloading a
page it already has sometimes reports the wrong number and fails the whole test
run. Nothing is wrong with the app — the check is measuring something that can
land a moment late — but a test that fails at random trains everyone to shrug
at red, which is how a real failure gets shrugged at too.

## Summary

Seen during T641 (2026-08-09), in `apprt.win32.ViewerPane.test.host floor: a
real controller on a real window, on this box`:

```
[viewer_pane] (warn): t400: a repeat navigation costs 1 fetch(es)
[viewer_pane] (warn): t400: stale-debounce window cost 0 fetch(es), expected 1
expected 1, found 0
```

...at `ViewerPane.zig:4346`, `try testing.expectEqual(nav_cost, after_nav)`.
Re-running the SAME tree twice more (once filtered to `host floor`, once as the
full `floor-lane.ps1 -Lane win32`) passed both times, with the repeat
navigation costing **0** fetches instead of 1 and the assertion comparing
0 == 0. So the flake is in `nav_cost` — the baseline the assertion derives its
expectation from — not in the debounce behaviour under test.

The read is that a repeat navigation's fetch count depends on whether WebView2's
own HTTP cache served it, which is not something the test controls. When the
baseline comes out 1 the assertion demands a fetch inside the debounce window
that the debounce is specifically there to prevent, and it fails; when the
baseline comes out 0 the assertion is vacuous and passes. Both outcomes are
wrong for different reasons — the passing one is not evidence.

Nothing about T641 touched this path; it is recorded here because it cost a
re-run and will cost the next turn one too.

## Details

The fix is to make the test assert the PROPERTY rather than a measured
baseline: a navigation inside the stale-debounce window must not add a fetch,
which is `after_nav == before` regardless of what an uncached first navigation
cost. If the baseline genuinely has to participate, the test should pin the
cache state (a `no_cache` navigation to establish it, as the reload arm already
does) instead of reading whatever the browser happened to do.

Landmarks: `src/apprt/win32/ViewerPane.zig` around line 4346, and the
`t400:` log lines just above it.

## Validation criteria

- [ ] The assertion is stated as a property that does not depend on an
      unpinned baseline (or the baseline is pinned by the test).
- [ ] `floor-lane.ps1 -Lane win32 -Repeat 3` is green — the flake needs
      repetition to be believed gone, not one passing run.
