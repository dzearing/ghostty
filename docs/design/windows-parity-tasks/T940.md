# T940 - Every window a pixel probe photographs can draw itself into the caller's DC on demand

## Summary

T843's first half, split out because the second half (converting 65 probes
across 34 acceptance scripts and re-running each several times) is many turns
of GUI work and this is not.

T835 measured the defect: `Get-TestWindowPixels` captures through
`PrintWindow(PW_RENDERFULLCONTENT)`, which asks DWM for an ASYNCHRONOUS copy of
the window's composited surface and returns before the copy has finished. Three
back-to-back captures of one unchanged overlay read the same row's ink at 1062,
1283 and 1179 px. `-Sync` is the cure — `PrintWindow` with no flags, so the
window paints the frame itself, synchronously, before the call returns — but it
only works on a window whose WndProc answers `WM_PRINTCLIENT`, and today
exactly one class does (`BannerOverlay`, T835).

So every other probe is stuck on the torn capture not because nobody converted
it but because the window it photographs cannot be captured any other way. This
task removes that: each window class answers `WM_PRINTCLIENT` by painting into
the caller's DC, exactly as `BannerOverlay` does.

Landed on all 11 classes that handle `WM_PAINT` and can have one: `Window`
(tab strip, caption, dividers, hero — the bulk, via a new `paintChromeInto` so
the painted and the printed copies cannot drift), `MachineChooser`,
`ActivityMonitor`, `ConfirmDialog` and `DimOverlay` (both gained a `paintInto`),
`RegionSelector`, `ViewerPane`, `ViewerNavBar`, `ViewerTOCPanel` and
`ViewerFeedbackBar`. The scope grew past the probed set on purpose: the last
four cost one switch arm each, and leaving a painting class without a handler
is the exact hole the audit below exists to keep closed.

Two things remain outside it, and both are real rather than deferred. `App.zig`
is exempt (see below). And the RichEdit composer inside `ViewerFeedbackBar` is
a child control that ignores `WM_PRINT`/`WM_PRINTCLIENT` — the bar's own chrome
prints, the typed text does not, which is noted at the handler and is T944's
subject along with the owner-drawn popup menus.

## In plain terms

The test suite photographs the app to check that it drew the right thing, and
most of those photographs can come out half-taken — which makes a correct build
look broken, and sometimes makes a broken one look fine. There is a way to ask a
window to sit still and pose, but a window has to know how to answer, and so far
only one of them does. This teaches the rest of them to answer.

## Goals

- [x] Every window class a pixel probe targets answers `WM_PRINTCLIENT` by
      running its existing paint into the caller's DC — 11 of the 12 classes
      that handle `WM_PAINT`; the twelfth is exempt with a reason (below)
- [x] The invariant is guarded so it cannot rot — a class that paints and
      cannot pose is a test failure, including a class that does not exist yet
- [x] At least one acceptance script is converted end to end as proof the
      handler works through the real capture path

## How it was proven, and why not unit tests

The `BannerOverlay` shape (build the window in a test, paint into two DIBs,
compare) does not generalise: that overlay can be constructed standalone, and
`Window`, `MachineChooser`, `ActivityMonitor` and `ConfirmDialog` cannot — they
need app state a unit test has no way to stand up. Writing four fragile
almost-tests would also have missed the case that actually matters: a NEW
window class arriving without a handler, which no per-class test can see.

So the guard is a static audit over source text —
`test\win32\printclient-audit.ps1`, with a `guard-due` row armed by any
`src\apprt\win32\*.zig` edit — plus one real acceptance conversion for the
end-to-end evidence a text audit cannot give.

That end-to-end evidence is `tab-color.ps1`: its assertions read the accent
stripe, which only `paintTabBar` draws, and under `-Sync` (`PrintWindow` with
no flags) those pixels can reach the capture ONLY through the new
`WM_PRINTCLIENT` handler. A green run is therefore proof the handler ran, not
merely that the capture returned something.

`App.zig` is the one exemption. It owns the terminal surface, whose pixels come
from the renderer rather than GDI, and `Get-TestWindowPixels` already refuses to
capture it at all (T214: `PrintWindow` returns a flat fill for it off the input
desktop, so any assertion over that capture passes against nothing). A handler
there would manufacture exactly the blank frame the refusal exists to prevent.
The exemption is recorded in the audit, not in a source comment, so adding one
is a visible edit to the test — and the audit fails if the exempted file stops
painting, which would otherwise leave a stale excuse behind.
