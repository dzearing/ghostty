# T184 - banner text lines and list items clip instead of wrapping to the pane width

## Summary

T123 taught the banner's TABLES to size themselves to the pane. Everything else
in the banner still renders as one unwrappable display line: a `.text` block, a
heading, and a list item each lay out with `drawInlineLine`, which walks the
segments left to right at a single `y` and returns a width nobody bounds. Too
long for the pane and it simply runs off the card and gets cut by the clip
region. Mac wraps all three (`Text(...).lineLimit(n).truncationMode(.tail)` in a
width-constrained VStack), so the same banner reads differently on the two
platforms - and it is the same user complaint T123 came from ("the text ...
doesn't use available space"), one block type over.

## Details

Where it lives, all in `src/apprt/win32/BannerOverlay.zig`:

- `renderContent` gives each `.text` / `.heading` block a height of exactly one
  line (`line_h`, or the heading's `hl`) with no reference to `content_w`.
- `renderList` does the same per item (`y += line_h`).
- `drawInlineLine` has no width parameter at all - it is the single-line
  primitive. The clip region set in `paint` is the only thing stopping the
  overflow from painting past the card, which is why this reads as "the text is
  cut off" rather than "the banner is broken".

The machinery to fix it already exists and is already proven by T123: tokenize
the run (`tokenizeCell`), hard-break over-long tokens (`breakWideTokens`), wrap
(`markdown.wrapTokens`), and cap with a tail ellipsis
(`banner_layout.fitWithEllipsis`). The work is lifting that path out of
`renderTable` into a shared "lay out an inline run in W pixels" helper and
calling it from the text, heading, and list arms - measure and paint must go
through the SAME helper or the reserved band and the paint will disagree (the
T101 lesson).

Two decisions to make from the Mac source rather than by guess: the display-line
budget per block type (Mac's `parseBlocks(maxLines:)` hands each `.text` block a
`lineLimit` out of the banner's 10-line budget, so a wrapped line must consume
from that budget - a wrapping banner must NOT be able to exceed 10 display
lines), and whether a list item's continuation lines indent to the marker gutter
(they should - the gutter exists to make content left-align).

**Validation:** extend `test/win32/pane-banner.ps1` in the shape section 6g
already uses - band height as the oracle, self-relative, no pixel constants. A
long single-line banner must grow the band when the pane narrows and shrink it
back when it widens; a long unbroken token must break mid-string; a list item
must wrap with its continuation aligned to the item content, not the gutter; and
a banner of many long lines must still stop at 10 display lines. Prove each with
a negative control the way `T123_NEUTERED` does.
