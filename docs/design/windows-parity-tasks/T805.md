# T805 - ghoztty +version prints two binaries' provenance and only one of them says 'commit'

## Summary

The only line labelled 'commit' in '+version' describes the RUNNING app, not the binary that was asked - which cost a P1 misfile (T773). Make the document self-disambiguating on both platforms.

## In plain terms

Asking Ghoztty for its version prints two answers on one page: the version of
the copy you asked, and the version of the copy that happens to be running on
the machine. Those are usually different — that is the whole reason the second
one is printed. But only the running copy's answer has the word "commit" next
to it, so that is the line a reader's eye lands on, and they walk away with the
wrong binary's identity. It has already happened once and produced a P1 bug
report about a defect that did not exist.

## Details

`src/cli/version.zig` prints a `Version` block for **this** binary
(`- version: 1.4.0-…-+<sha>`, the sha buried in semver build metadata) and then
a `Running Instance` block for the app it reached over IPC (T52), whose fields
include the only `- commit  : <sha>` line in the document.

Measured on the box 2026-08-12 — one command, two commits:

```
  - version: 1.4.0-users-dzearing-windows-amd64-+66ad87d45   <- this binary
Running Instance
  - commit  : 445780e49                                      <- the running app
```

The reading is not helped by the fact that the probed binary's sha has no
`commit` label at all, while the other binary's does.

Candidate shapes (pick one in the task, don't assume this list is the answer):
give the `Version` block its own `- commit :` line so the label is scoped by
its block rather than owned by one of them; and/or name the blocks for what
they describe (this binary vs the running app) instead of `Version` vs
`Running Instance`.

`src/cli/version.zig` is **shared core**, so whatever lands here lands on macOS
too — that is the point, not a hazard. What must not break: the delivery gates
parse this output (`Get-CommitFromVersionText` in `scripts/delivery-version.ps1`,
anchored on `- version:`) and so does `test/win32/lib/BuildMode.ps1` (anchored
on `- build mode`), both of which already have decoy arms for the two-block
trap (`upgrade-staleness.ps1` A31–A35, `build-mode-guard.ps1` B2).

## Validation criteria

- [ ] A reader who greps the output for `commit` can tell, from the line alone
      or its immediate context, which binary it describes.
- [ ] The same change is present on the macOS seat (shared file — verify the
      Mac output, do not just assume the compile covers it).
- [ ] `test\win32\upgrade-staleness.ps1` (A31-A35), `build-mode-guard.ps1` and
      `ipc-version.ps1` stay ALL PASS; the fixtures in them are updated to the
      new shape rather than the shape being chosen to fit old fixtures.
- [ ] An arm asserts the new labelling against a real `+version` run with an
      instance actually running, so the two blocks are both populated.
