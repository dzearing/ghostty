# T1231 - Backslash escapes were written into repo files as control characters, and some are inside live paths

## In plain terms

Somewhere along the way a tool wrote real control characters into repository
files wherever a Windows path contained a backslash followed by `a`, `b` or `f`
- so `zig-out\bin` became `zig-out<BS>in` and `test\win32\floor-...` became
`test\win32<FF>loor-...`. Thirteen files carry it. In documentation it is
invisible (a reader sees the two halves run together and assumes a typo); in a
script it is a path that quietly does not exist.

## Summary

Found while editing `scripts\guard-due.ps1` for T1170: the `install-prepare`
guard row's `Covers` list named `src<BEL>pprt\win32\install_prepare.zig`, so
that guard could never resolve the file it claims to cover. `docs\claude\testing.md` had `<repo>\zig-out<BS>in\ghoztty.exe`.

Full scan (control characters other than tab/newline/CR, over `.md .ps1 .zig
.json .sh .yml .yaml .txt .psm1`, excluding `.git`, caches and build output):

## What landed

**Fifteen files, not thirteen.** The scan was re-run at fix time and two task
files filed since (`T1251.md`, `T1252.md`) had picked up the same damage, which
is itself the argument for the guard: the source of the corruption was still
live while the task describing it sat in the queue.

**Repaired byte for byte, not re-encoded.** Each damaged byte was replaced in
place (`0x07` -> `\a`, `0x08` -> `\b`, `0x0c` -> `\f`) through
`ReadAllBytes`/`WriteAllBytes`, so nothing else in any file moved - the diff is
one line per file. A whole-file rewrite from PowerShell would have re-encoded
every one of them (PS 5.1 reads UTF-8 as the ANSI codepage and writes a BOM),
which is a far larger defect than the one being fixed.

One of the fifteen is prose rather than a path: `T851.md` read "the roster's
`\a`ttached flag", and the title of that same task says "ignores the attached
flag", so the backslash was itself part of the damage and the repair is the
plain word.

**Correction to the premise above:** all three `.ps1` occurrences turned out to
be in comments and help text (`scripts\suite-run.ps1`'s `.EXAMPLE` block, and a
rationale comment in each of the two `test\win32` scripts), not in live path
strings. The live case was the one T1170 had already fixed - `guard-due.ps1`'s
coverage row for `src\apprt\win32\install_prepare.zig`, where the broken path
silently disabled a guard.

**The guard.** `scripts\control-char-scan.ps1` fails on any byte below 0x20
other than tab/LF/CR, plus DEL, in a tracked file whose extension is in its
allowlist (the allowlist is what keeps the extensionless libghostty fuzz corpora
- whose whole point is to hold control bytes - out of scope without an exclusion
list anyone has to argue with). A full tracked-tree scan is about a second, so
it is affordable at both of its call sites:

- `scripts\parity-tasks.ps1 validate`, which is the gate go.md runs before every
  commit. It emits `CONTROL CHARACTERS:` as its own headline and counts as a
  problem.
- `scripts\githooks\pre-commit`, over staged files only. This is the half that
  covers the OTHER window sharing this working tree, which never runs `validate`.
  Exit 2 (the scan could not run at all) deliberately does NOT block a commit.
