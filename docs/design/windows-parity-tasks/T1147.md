# T1147 - The soak's 'median fps under load' assertion counts idle panes, so the first completed soak fails at fps 1

## In plain terms

The stability check now runs to the end for the first time, and it reports the
terminal drawing at one frame a second. It is almost certainly not: the number
is an average taken over every pane in the window, and three quarters of those
samples come from panes that were sitting idle with nothing to draw. Until the
measurement counts only the panes actually doing work, nobody can tell a real
slowdown from this.

## Summary

`test\win32\soak.ps1` was scored `stall` on every sweep until T1125 gave it its
own timeout. Its first completed run (2026-08-23, 30m 53s, HEAD staging release
at 820193367) came back `1 FAILURE(S) / 10 passed`, and the one failure is:

```
renderer telemetry: 10925 windows, median fps 1, worst frame gap 622ms
FAIL  median fps under load >= 20 (got 1)
```

The distribution in that run's own `log-slice.txt` is sharply bimodal:

| fps | windows |
|---|---|
| 1 | 7375 |
| 21-28 | ~1750 |
| 59-60 | ~1789 |

So two thirds of the samples are `fps=1` and the rest are 21-60. Four panes were
open: three under deliberate load (an endless `type` of an 8MB file, an
alt-screen churn loop, a 150k-line grow) and one idle probe pane touched once a
minute. An idle unfocused pane legitimately redraws about once a second, so it
reports `fps=1` every window - and there are far more of those windows than
loaded ones, which is what the median is reading.

The script ALREADY knows this shape and says so, two lines above the failing
assertion:

```
# max_gap is informational only: an IDLE unfocused pane legitimately
# reports gaps equal to the time between its redraws ... so a global
# stall assertion false-fails.
```

The same reasoning applies to fps and was not applied. Leading reading: the
assertion's denominator is wrong, not the renderer. It must be confirmed rather
than assumed - the loaded panes' own numbers (21-60) are what should be graded,
and if a loaded pane is genuinely sitting at 21 fps that is worth knowing too.

Second, smaller finding from the same run, worth a look while in here: the grow
pane did not finish (`grow finished: False` - 150k `echo` lines in 30 minutes),
and the baseline `+read` against the tiny-write storm took 11.9 seconds (the
known T62 renderer-mutex starvation, already unasserted here).

## Where

- `test/win32/soak.ps1` - the telemetry slice and the `median fps` assertion
- the `perf fps=` line's producer, for whether a window can say which pane it is

## Goals

- [ ] Establish whether `fps=1` windows are idle panes, from the telemetry itself rather than by inference.
- [ ] Grade what the assertion's name claims - panes under load - so the verdict answers the question it appears to.
- [ ] Keep a real renderer regression detectable: a loaded pane that drops must still turn this red.

## Validation criteria

- [ ] the fps=1 population is identified with evidence, not assumed to be idle panes
- [ ] a completed soak against a healthy build reports ALL PASS
- [ ] a negative control shows the assertion still goes red when a loaded pane's fps really drops
