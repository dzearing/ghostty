# T1383 - profile-latency.ps1 cannot run: it wants a zig-out-prof release build that nothing builds any more

## In plain terms

There is a script that measures how long Ghoztty takes to answer a keystroke.
It has not actually measured anything for weeks: it points at a build directory
nobody fills any more, so it refuses to run and says so. Nothing was watching,
because a broken capability check was skipping the script before it ever got
far enough to complain.

## Goals

- [ ] `test\win32\profile-latency.ps1` runs to a number on this box, or is
      retired on purpose with the reason written down
- [ ] Whatever it needs to build is either built by a documented command or
      built by the script itself

## Summary

Found while fixing the `real-input` capability probe under T572. That probe
could never say "available" (its `INPUT` struct was 48 bytes where x64 wants
40, so every injected event was rejected), and `profile-latency.ps1` is gated
on it — so the script exited `SKIP ALL` before reaching any of its own checks.

With the probe fixed the script now runs, and immediately refuses:

```
exe: D:\git\ghoztty\zig-out-prof\bin\ghoztty.exe (07/17/2026 00:10:57, 30064640 bytes)
Assert-GhozttyIsolatedBuild: REFUSING TO RUN. The exe under test ... is a
'ReleaseFast' build, so it does NOT use the -debug endpoints.
```

The refusal is correct and is exactly the T1033/T1158 guard doing its job — a
release-lineage binary would drive the user's own terminal. What is wrong is
that `zig-out-prof` is a stale July artifact that no documented build command
produces, so the script has no path to a runnable subject.

## Details

Two ways out, and the first is probably right:

1. **Point it at the debug build** the rest of the suite uses
   (`zig-out\bin\ghoztty.exe`) and say in its header that the numbers are
   debug-build numbers, useful as a regression signal rather than as an
   absolute latency claim.
2. **Keep the release subject** and give it a documented build step plus the
   three isolating knobs `Get-GhozttyReleaseSandboxGaps` names
   (`GHOZTTY_PIPE_SUFFIX`, `GHOZTTY_AGENT_INSTANCE`, `LOCALAPPDATA`), so a
   release-lineage run is sandboxed rather than merely permitted.

Either way the script should build what it needs, or fail with the command to
run — a stale directory from two months ago is the shape that reads as "the
feature is broken" to the next person.

## Validation criteria

- [ ] `powershell -NoProfile -File test\win32\profile-latency.ps1` produces a
      latency figure on this box, or the script is deleted and its retirement
      recorded here with the reason.
- [ ] The subject binary is one a documented command builds; no path in the
      script points at a directory nothing fills.
- [ ] If the release path is kept, the run holds all three isolating knobs and
      `Assert-GhozttyIsolated` proves the instance it drives is its own.
