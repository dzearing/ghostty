# T992 - Copying can hand the user another app's clipboard content because our copy claims no owner window

## Summary

Found by T947's new harness. The terminal's copy opens the clipboard with a NULL owner window, and OpenClipboard(NULL) excludes nobody - measured directly: while a process holds the clipboard that way, every other process opens it straight through. So the copy's EmptyClipboard-then-SetClipboardData is not atomic: another app can open, empty and write between our two calls, and the user's copy silently yields that app's content or nothing. Passing a real HWND (the surface's, as the paste read already does) makes the pair atomic the way every other Windows app's copy is. Same family as T947 but a different failure: T947 was the copy never starting, this is the copy being overtaken mid-flight.

## In plain terms

When you copy in the terminal, the copy is done in two steps: clear what was
there, then put your text in. Right now nothing stops another program writing
the clipboard in the gap between those two steps, so once in a while a copy
quietly gives you that other program's text - or nothing at all - and there is
no error to tell you what happened. After this, the terminal holds the
clipboard properly for the whole copy, the way every other Windows app does,
and the gap does not exist.

## Goals

- [x] The terminal's copy claims a real owner window, so its clear-then-write
      pair cannot be interleaved by another process
- [x] A surface freed mid-copy (the confirm-dialog path) falls back to the
      app's window rather than to no window at all
- [x] Every clipboard user in the app gets this, not just the one call site
      that was found
- [x] An acceptance arm that reads the owner back, with the pre-fix shape
      reproduced as its sensitivity control

## Validation criteria

- [x] `GetClipboardOwner()` is non-zero after a real OSC 52 copy from the app
      - arm D2 of `test\win32\clipboard-retry.ps1`, ALL PASS (owner 29623504)
- [x] That owner window belongs to the app under test - arm D3, owner pid
      17400 == app pid 17400
- [x] The oracle can tell the two shapes apart - arm D0 reproduces a
      null-owner write in-process and reads owner 0
- [x] Proven by putting the bug back: with `App.init`'s registration replaced
      by `setDefaultOwner(null)` and the app rebuilt, D2 FAILS with `got 0`;
      restored and rebuilt, ALL PASS
- [x] The registration cannot be silently dropped - arm C3 asserts `App.zig`
      still calls `clipboard_open.setDefaultOwner` (2 calls)
- [x] T947's retry behaviour is unchanged - arms A1-A3, B1-B2 still pass
- [x] Floor: `scripts\floor-lane.ps1 -Lane all` ALL LANES PASS (lib/none/
      win32/agent); ipc-p1 25, ipc-p2 20, ipc-p3 16 assertions ALL PASS;
      `guard-due check` back to exit 0 after re-running the four test-script
