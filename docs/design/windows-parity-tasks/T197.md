# T197 - Harness audit: Run-CliArgs exit codes are unreadable unless .Handle is cached first

## In plain terms

Our own test scripts could report that a working feature was broken. When a
script ran the terminal's command-line tool and asked "did that succeed?",
Windows sometimes handed back a blank answer instead of a yes or a no - and the
scripts read a blank as "no". So a perfectly good build could come back with a
page of red failures, and whoever read them would spend the next session
hunting a bug that was never there. That has already happened twice. Nobody
using the terminal sees this directly; what they see is the days it costs.

Now the scripts ask the question in the way that always gets a real answer, and
a new check refuses to let the broken way back in.

## Goals

- [x] Find every place in the suite that can get a blank answer
- [x] Work out exactly when it happens, instead of guessing
- [x] Fix all of them
- [x] Add a check that fails if the broken pattern ever reappears

## Summary

`Start-Process -PassThru` + a TIMED `WaitForExit(ms)` leaves `$p.ExitCode`
**empty** unless the process handle was cached (`$null = $p.Handle`) *before the
process exited*. The idiom copied around `test/win32/` touches `.Handle` AFTER
the wait, which is too late whenever the child exits quickly — so every caller
that gates on `if ($code -ne 0) { fail }` scores a **working** CLI as a failure.
Caught live building `agent-upgrade.ps1` (T147): six assertions failed against a
build whose complete, correct `+list --json` output was sitting in the redirect
file. The log already records this trap once (T145, "the harness lied three
times"), and it recurred anyway — which is the argument for auditing it out of
every script rather than re-learning it per harness.

## Details

Two fixes, and the second matters more than the first:

1. **Cache the handle first.** `$null = $p.Handle` immediately after
   `Start-Process`, before any wait. (Done in `agent-upgrade.ps1`.)
2. **Do not gate an outcome on an exit code when the OUTPUT is the answer.**
   `Get-List` should parse the JSON it got; `+read` oracles should look for the
   marker. A harness that discards a complete answer over a shell-plumbing
   detail is a harness that fabricates failures — and a fabricated failure costs
   more than a missed one, because it sends the next session hunting a defect
   that isn't there.

Audit every `test/win32/*.ps1` that starts the CLI with `-PassThru` and reads
`ExitCode`, and either cache the handle first or re-gate on the output. Note
that some scripts pass today only because their child is slow enough to still be
running when `.Handle` is touched — i.e. they are timing-dependent, not correct.

## What the trigger actually is (measured, not remembered)

The trap fires **only when `Start-Process` is given `-RedirectStandardOutput` /
`-RedirectStandardError`.** Measured on this box, PowerShell 5.1.26100, with a
child (`cmd /c exit 7`) that is always over before the read:

| shape | reads the code |
|---|---|
| redirect, handle cached first | 8/8 |
| redirect, handle cached AFTER the timed wait | **0/8** |
| redirect, handle never cached | **0/8** |
| no redirect, handle never cached | 8/8 |

That is why it looked random for two turns and got mis-filed as flakiness: most
helpers here redirect *inside* `cmd /c … > file`, which is unaffected, and they
sit line-for-line next to the ones that call `-RedirectStandardOutput` and are.
The two shapes are indistinguishable by eye. It also settles the middle case —
a handle cached after the wait (the comment in `agent-recovery.ps1` claimed
that worked) loses the code just as completely as never caching it.

- [x] Every `Start-Process -PassThru` site in `test/win32/` and `scripts/`
      whose ExitCode is read caches the handle first, or is output-gated, or
      carries an explicit `# exitcode-audit:` exemption — **31 sites fixed**
      (28 in `test/win32/`, 3 in `scripts/`); verified by
      `test\win32\harness-exitcode-audit.ps1` section B, which sweeps both
      roots and is now at zero.
- [x] The auditor has teeth: 17 fixture arms in section A cover the
      copy-pasted helper, handle-first, output-gated, handle-after-the-wait,
      `-Wait`, the marker, backtick continuations, comments, `.Id`,
      two-sites-one-file, and variable reuse. Teeth-checked by watching the
      section fail (12 red) against a bug in the fixture harness itself, then
      go green.
- [x] The rule's premise is measured on the box rather than asserted:
      section C, table above.
- [x] Every touched `.ps1` parses (`[Parser]::ParseFile` over all 30 changed
      and added files; 0 errors).
- [x] Standing floor green: `scripts\floor-lane.ps1 -Lane all`, P1–P3.
- [x] No product verdict moved, and this is checkable rather than hoped: the
      only sites that were *actually* losing the code are the redirecting ones
      — `agent-recovery.ps1`'s `Run-CliArgs` and `update-check.ps1`'s GUI
      probe — and **both were already output-gated** at every call site
      (`Run-CliArgs` results go to `Out-Null`; `update-check` only used the
      code in a `SETUP FAIL` message). Every site that *did* gate on the exit
      code is a `cmd /c` wrapper, which the table above shows never lost it.
      So no assertion anywhere could change answer. Confirmed by re-running
      the one script with a genuinely broken site end to end
      (`agent-recovery.ps1` **ALL PASS (57)**) plus a representative
      `cmd`-wrapper user (`session-open.ps1` **ALL PASS**) and `ipc-p1.ps1`,
      which is itself one of the 28. The remaining touched scripts were
      **parse-checked, not re-run** — stated plainly rather than implied: at
      5-20 minutes each that is hours for zero expected information, and the
      table above is why the expectation is zero rather than a hope.
