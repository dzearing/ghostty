# T241 - Watchdog re-entry types a .cmd path into a live Claude TUI because the upgrade never updates the lock's claude_pid

## Summary

**A near-miss that would have killed the loop silently.** Caught only because
the stray text landed in the user's prompt box and they pasted it back.

Delivering T232 on 2026-07-31 the upgrade relaunched claude in-pane via its
`reuse` path. Four minutes later the watchdog fired, concluded *"owner claude
is gone"*, and typed a `.cmd` **path** into the pane — which is running a Claude
Code TUI, so the path became a user message instead of a command. The loop was
NOT re-entered. Nothing failed loudly; the log says `send-keys exit=0`.

## Evidence (VERIFIED on the box)

`%TEMP%\ghoztty-go-loop-watchdog.log`:

```
2026-07-31 09:50:58 healthy: pane=6C13A7F3-... pid=22928 age=2.35m remaining=63
2026-07-31 09:55:58 re-entering: owner claude is gone, restarting it in pane 6C13A7F3-... (remaining=63)
2026-07-31 09:55:58   send-keys exit=0
```

`go-loop-lock.ps1 status -Json` at the time:

```
"claude_pid": 22928, "state": "stale-dead", "owner_alive": false, "mine": true
```

`Get-Process -Id 22928` → **not found**. The live claude was **pid 13060**
(started 09:55:51, the upgrade's `--continue` relaunch). And the file the
watchdog typed, `%TEMP%\ghoztty-go-loop-resume.cmd`, is three lines that would
have been right *at a shell prompt*:

```
@echo off
cd /d "D:\git\ghoztty"
claude --dangerously-skip-permissions --continue "read go.md and go"
```

## Two defects, both required for the failure

1. ~~**`upgrade-ghoztty-windows.ps1`'s `reuse` path relaunches claude but never
   updates the lock.**~~ **CORRECTED while fixing this (2026-07-31)** — the
   `reuse` path does not relaunch anything. `%TEMP%\ghoztty-upgrade.log` for
   that delivery reads `resume decision: reuse (loop claude pid=22928
   alive=True)` and then `UPGRADE OK (reused claude pid=22928 ...)`: it typed
   the prompt into the SURVIVING session and left the pid alone, which is
   exactly what the lock already recorded. Claude 22928 exited and 13060
   started at 09:55:51 with `--resume` on its command line — a relaunch in the
   pane by other means, seven seconds before the watchdog acted.

   The general defect stands and is what got fixed: **the lock's pid is stale
   for the whole window between a claude relaunching in the pane and that
   session running go.md step 0**, whatever caused the relaunch. `Test-OwnerAlive`
   is not the bug — it was right; the pid it was given was stale.
2. **`go-loop-watchdog.ps1`'s `restart-in-pane` branch assumes the pane is at a
   shell prompt** (`scripts/go-loop-watchdog.ps1:234-241`). It checks only
   whether the RECORDED pid is alive, never whether *some* claude is alive in
   that pane. In the go-loop the pane is by definition running Claude Code, so
   the branch's own premise is the rare case, and its failure mode is silent:
   `send-keys` succeeds, a path appears in the prompt box, nothing re-enters.
   Note the adjacent `nudge` branch (line 228) is already correct for a live
   TUI — it sends the resume PROMPT as text.

Worse near-miss: if a model had acted on the pasted path it would have run a
SECOND claude inside the pane of the first.

## The fix

- Upgrade script: after a `reuse` relaunch, refresh the lock's `claude_pid` /
  `claude_name` / `claude_start` to the new process (it knows the pid — it
  starts it), or call `go-loop-lock.ps1` with a `-AdoptPid` verb so the
  ownership record follows the relaunch. Same for the `new-window` path.
- Watchdog: before `restart-in-pane`, probe whether a claude is alive **in that
  pane** (pane-scoped, not pid-scoped — `+list --pid` ancestry inverted, or the
  pane tail showing a Claude Code prompt). If one is, take the `nudge` branch
  and send `$ResumePrompt` as text. Reserve the shim for a pane that really is
  sitting at a shell.
- Consider making the shim self-guarding too: a first line that exits if a
  claude is already attached to this pane, so a mis-typed path cannot fan out.

## Validation

- `test/win32/go-loop-guard.ps1` (or a new sibling): with the lock pointing at
  a DEAD pid while a live claude runs in the pane, `go-loop-watchdog.ps1 -Once
  -DryRun` must report `nudge`, not `restart-in-pane`. That test fails today —
  it is the negative control.
- An end-to-end delivery: run `launch-upgrade.ps1`, then assert the lock's
  `claude_pid` matches the RELAUNCHED claude, and that a watchdog tick
  immediately afterwards reports `healthy` rather than re-entering.
- Grep the watchdog log across a delivery for `owner claude is gone`: it must
  not appear.

## What shipped (2026-07-31)

The watchdog now asks the **pane** who is listening instead of trusting the
recorded pid, and every typed re-entry is verified afterwards.

- **`scripts/go-loop-pane-probe.ps1` (new).** `Get-PaneOccupant` classifies a
  pane's tail as `claude` / `shell` / `unknown`. Rule order matters: a shell
  prompt on the **last non-empty line wins**, because a live full-screen TUI
  always owns the bottom of the screen — so Claude output left in the
  scrollback above a prompt reads as "claude exited", not "claude is running".
  Only then do the Claude chrome markers (`esc to interrupt`, `bypass
  permissions`, `shift+tab to cycle`, …) apply. Markers are words, never box
  glyphs: PS 5.1 mojibakes non-ASCII in a BOM-less file.
- **`scripts/go-loop-watchdog.ps1`.** The nudge branch now fires on
  `owner_alive OR occupant == claude`; the shim branch is reserved for a pane
  that really is at a shell, and after it types the shim it re-reads the pane
  and logs `RESTART-IN-PANE OK` / `UNVERIFIED`. Every tick logs
  `pane <id> occupant=<who>`, so the log says what it saw.
- **`scripts/go-loop-lock.ps1` — new `adopt` verb.** Re-points `claude_pid` at
  a claude relaunched in the owning pane without touching the pane, the turn
  counter, or acquire's takeover rules. The watchdog calls it after a nudge
  when the recorded owner is dead AND exactly one candidate claude exists;
  when it is ambiguous it says so and leaves the lock alone (the nudged
  session reclaims it at step 0 anyway).
- **Latent bug found while building the control:** `+send-keys` interprets
  `\n`/`\t`/`\r`/`\e`/`\\` in text, so the shim PATH was being typed raw — under
  a user called "tom" `C:\Users\tom\...` arrives with a TAB in it. Reproduced
  live (the control's own `...\Temp\t241-negctl\` dir became `Temp241-negctl`
  and cmd said "cannot find the path"). Now escaped via
  `ConvertTo-SendKeysLiteral`.
- **`+list --pid` was the natural probe and could not be used** — on a
  session-persistence box every pane reports `pid: 0`, so it matches nothing.
  Filed as **T244**; the tail heuristic is the fallback until it lands.

## Still open

The end-to-end delivery assertion (lock `claude_pid` matches the relaunched
claude after `launch-upgrade.ps1`, next tick `healthy`) is not automated — it
needs a delivery to observe. The `owner claude is gone` grep is now a weaker
signal by design: that message no longer exists, and the log line to watch for
across a delivery is `occupant=claude` followed by `ACTION nudge`.
