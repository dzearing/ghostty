# T1311 - A pane printing non-stop still freezes the window for about a second every 30 seconds

## In plain terms

Leave a long build (or an agent) printing in a pane and the whole window stops
responding for about a second, roughly every half minute. Clicks queue up, the
drag you were in the middle of sticks, and then it comes back as if nothing
happened. Nothing is broken, so it reads as "this terminal is a bit janky"
rather than as a bug anyone would report.

## Goals

- [x] The forced (ceiling) refresh fits one display frame instead of freezing
      the window for about a second.
- [x] Every pane still gets its screen re-recorded while it is held busy — the
      cost is spread, not skipped.
- [x] `test\win32\layout-capture-cost.ps1` measures the forced refresh, and the
      arm demonstrably scores red against the pre-fix build.

## Summary

T412 measured `App.syncSessionLayout` on box and found the screen dump costing
**991 ms** with eight panes printing continuously — almost none of it the dump
itself (151 KB of VT), nearly all of it waiting on each pane's
`renderer_state.mutex`, which the IO thread holds while feeding output.

T412 fixed the common case: a topology or frame change now carries the last
screens forward (`ScreenCapture.reuse`) instead of re-dumping, so a drag end, a
new tab or a rename costs single-digit milliseconds no matter how busy the panes
are.

What it did NOT fix is the one caller that must have fresh screens: the T922
refresh. `layout_refresh.decide` waits for the panes to go quiet first, which is
free most of the time — but it has a `max_wait_ms` ceiling of 30 s, and a pane
that never goes quiet hits it. So a sustained-output pane still buys one full
`.fresh` capture every 30 seconds, on the UI thread, at the flooded price.

That ceiling is not removable: it exists so a permanently-busy pane still gets
its screen recorded, which is what a post-reboot restore paints (D78). The fix
has to be on the cost side, not the cadence side.

## Details

Where to look:

- `src\apprt\win32\App.zig` — `tickLayoutRefresh` / `captureLeafSnapshot`.
- `src\apprt\win32\layout_refresh.zig` — `LAYOUT_REFRESH_MAX_MS` (30 s) and
  the `decide` rule that walks into it.
- The core's `sessionSnapshot`, which is what takes the mutex.

Approaches worth measuring, cheapest first:

1. **Bound the wait rather than the work.** A snapshot that cannot get the
   renderer mutex within a few milliseconds gives up and the leaf reuses its
   cached screen for this round — the pane is busy, so the cached screen is
   only a few seconds old and the next tick tries again. This keeps the UI
   thread's worst case bounded by a number we choose rather than by how hard
   the IO thread is working.
2. **Spread the cost.** Refresh ONE pane per tick instead of all of them, so a
   30 s forced capture is eight 2-second-apart dumps rather than one long one.
3. **Move the dump off the UI thread**, which is the real answer and the
   largest change: the capture would have to hand the encoded bytes back to the
   UI thread to be written.

## Validation criteria

- [x] `test\win32\layout-capture-cost.ps1` grows an arm that holds the panes
      flooded past `LAYOUT_REFRESH_MAX_MS` and measures the FORCED refresh
      capture, which today is the ~1 s one. It is within the frame budget after
      the fix, and the arm demonstrably scores red against today's build
      (a new gate ships with the demonstration that it can fail).
      → **section G**. Against the PRE-FIX build: `max=194.98ms mean=105.37ms`,
      G3 and G4 FAIL. Against the fix: `max=15.13ms mean=3.46ms mode=bounded`,
      inside the 16.67 ms frame budget, all green.
- [x] A pane held busy for a minute still has a screen in the manifest that is
      no more than `LAYOUT_REFRESH_MAX_MS` old — whatever the fix does to the
      cost, it must not quietly stop recording the screen D78 restores.
      → **G5**, and stated as the stronger claim the manifest can actually
      answer: every flooded pane's `screen_snapshot_offset` MOVES FORWARD across
      45 s of unbroken output. (The two root panes sit at a prompt, so theirs
      standing still is them being idle.)
- [x] `test\win32\session-snapshot-reattach.ps1` stays green: the restore path
      that reads those screens is unchanged. → 33 assertions, ALL PASS.
