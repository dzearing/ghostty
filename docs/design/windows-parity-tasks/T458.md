# T458 - Catch the wild write itself: a hardware data breakpoint on verifyIntegrity's spilled parameters under cdb

## Summary

Filed out of **T454** (2026-08-04), which established that the long-running
intermittent test-binary crash is a **wild write landing on a live stack
frame** — `Page.verifyIntegrity`'s spilled incoming parameters (`self`, its
allocator, and Zig's hidden error-return-trace pointer) all read as zero/garbage
in the T450 dump, and nothing in the function writes those slots after its
prologue. See `T454.md` § RESOLUTION for the register/slot table and the
derivation.

Every attempt so far has worked *backwards* from where the damage was noticed.
This task proposes working *forwards*: stop at the moment of the write.

## In plain terms

Something in the test run is scribbling over memory it does not own, and we now
know it hits the stack. Rather than keep finding the wreckage afterwards, this
is about catching the culprit in the act — the debugger can stop the program at
the exact instruction that writes to a chosen address, which names the guilty
code directly instead of leaving us to guess.

The catch-it-in-the-act tool now exists and is proven: aimed at a staged
version of the crime it stops at the guilty instruction and prints its name,
its stack, and a full memory dump. The real culprit has not struck since
2026-08-04 (the hunt is deliberately parked until it does — see T443), so the
tool waits armed alongside the rest of the watch.

## Details

The approach, in order of cost:

1. **Hardware data breakpoint (`ba w8 <addr>`).** x86-64 gives four debug
   registers; cdb exposes them as `ba`. The obstacle is that the target address
   is a *stack* address that only exists once `verifyIntegrity` is running, so
   the breakpoint has to be armed from a code breakpoint inside the function —
   e.g. break on `verifyIntegrity+<prologue end>`, compute `@rbp+368`, `ba w8`
   that, `g`. cdb can script this (`bp … "…; g"`). Note the three cdb traps
   `scripts/lib/CrashCatch.ps1` already documents (backslashes eaten inside
   quoted commands, filters must be armed at the loader break, cdb echoes its
   own command back).
2. **Narrow which run to arm on.** The crash lands on roughly half of runs and
   `verifyIntegrity` is called constantly under `slow_runtime_safety`, so
   arming on every call is far too slow. Arming only after the first integrity
   violation has already been reported may be enough, since the reported
   violation and the stack damage look like the same event seen twice.
3. **If a data breakpoint proves impractical**, the fallback is a poisoned
   guard band: give `verifyIntegrity` a local canary array either side of the
   spill region and check it before the `log.warn`, which at least converts
   "mystery null" into "the frame was overwritten between X and Y".

Do **not** start by bisecting tests again — T442/T443 spent multiple contexts
there and the victim test is known to be arbitrary.

## RESOLUTION (2026-08-06) — the recipe exists, is proven against controls, and waits armed

What landed:

- **`scripts/lib/DataBreak.ps1`** — the mechanics: a two-session PROBE
  (resolve the symbol + module base, then disassemble by module+rva) parses
  the Zig Debug prologue (`push rbp / sub rsp,X / lea rbp,[rsp+Y]` followed
  by the leading run of `mov [rbp±off],reg` spills, including spills routed
  through a scratch register and bare `[rbp]` slots) and computes: the
  canonical spill slot per incoming register (the slots the T454 dump showed
  zeroed), the arm point (first instruction after the spill run), and the
  return-address slot (`rbp + 8 + X − Y`). The ARMED run then breaks at the
  arm point on every call, sets `ba1..baN w8` on the slots, plants a one-shot
  `bp /1 poi(<ret slot>)` that disarms them at return, and continues — so the
  armed window is exactly the live frame and stack reuse can never
  false-positive. A hit prints the writing instruction (`ub @rip` — a data
  breakpoint fires after the write retires), every thread's stack, and a full
  minidump. `New-CdbScript` in CrashCatch.ps1 gained an additive
  `-PrologCommands` parameter so the armed run keeps the T450 crash capture.
- **`scripts/crash-databreak.ps1`** — the driver. Exit 0 = armed and ran
  clean, 1 = wild write caught, 2 = could not run/probe, 3 = the program
  crashed without touching an armed slot (T450-style capture still taken).
  For the real target:

  ```powershell
  powershell -NoProfile -File scripts\crash-databreak.ps1 -Lane agent `
      -Symbol verifyIntegrity -SignatureFilter page.Page
  ```

  (`-SignatureFilter` because Zig gives `Page.verifyIntegrity` and
  `PageList.verifyIntegrity` the same bare symbol name; the probe refuses the
  ambiguity loudly and lists the candidates.)
- **`test/win32/crash-databreak.ps1`** — acceptance, ALL PASS: a staged wild
  write (a callee scribbling a live caller frame) is caught with the writing
  instruction, the full stack and a >100KB dump; a clean 200-call loop arms
  and disarms 200/200 with zero false positives; same-named overloads are
  refused bare and resolved by filter; a crash that never touches an armed
  slot exits 3 with the crash captured; bad input exits 2.

Three new cdb specifics, encoded in the lib header so they are not re-derived
(on top of CrashCatch.ps1's three): nested quotes in breakpoint commands do
not exist — a breakpoint command that must set another breakpoint-with-command
uses `$$<file` includes; explicit breakpoint IDs (`bp0`, `ba1..ba4`) keep the
disarm's `bc` deterministic; and tiny leaf functions can get a frameless
`push rax` prologue the probe refuses rather than arming the wrong bytes.

**Rehearsed against the real binary** (agent test binary filtered to the T454
deliberate-violation tests): the probe resolved `Page.verifyIntegrity`, parsed
spills `r8/rdx/rcx → rbp+0x458/0x460/0x468` (this build's rendition of the
exact T454 dump shape), armed 3 call cycles, zero false hits, clean exit.

**The practicality question in this task's Details is now measured, not
assumed**: 42,315 arm cycles in a 120s window on the FULL agent binary
(~2.8 ms/cycle, test 763/4008 reached), so a fully-armed lane run extrapolates
to roughly 10–30 minutes. That is viable for a targeted capture attempt — so
option 2's "arm only after the first violation" narrowing (which could not
work anyway: by the time a violation is reported, that frame's damage has
already happened, and after return the address means nothing) and option 3's
canary fallback are both unnecessary.

**What deliberately did NOT happen this turn: hunting.** D10/D12 parked T443
until a natural recurrence, and 190+ crash-free runs say there is nothing to
point this at today. The tool is part of the armed watch now; T443's unblock
path names it as the follow-up instrument once a recurrence identifies a
crashing build to aim at.
