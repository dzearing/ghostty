# T458 - Catch the wild write itself: a hardware data breakpoint on verifyIntegrity's spilled parameters under cdb

## Summary

Filed out of **T454** (2026-08-04), which established that the long-running
intermittent test-binary crash is a **wild write landing on a live stack
frame** — `Page.verifyIntegrity`'s spilled incoming parameters (`self`, its
allocator, and Zig's hidden error-return-trace pointer) all read as zero/garbage
in the T450 dump, and nothing in the function writes those slots after its
prologue. See `T454.md` § RESOLUTION for the register/slot table and the
derivation.

Every attempt so far has worked *backwards* from where the damage was noticed.
This task proposes working *forwards*: stop at the moment of the write.

## In plain terms

Something in the test run is scribbling over memory it does not own, and we now
know it hits the stack. Rather than keep finding the wreckage afterwards, this
is about catching the culprit in the act — the debugger can stop the program at
the exact instruction that writes to a chosen address, which names the guilty
code directly instead of leaving us to guess.

## Goals

- [ ] A repeatable recipe that stops the debugger on the *write*, not the crash
- [ ] The writing instruction and its call stack captured for at least one run
- [ ] The recipe folded into `scripts/lib/CrashCatch.ps1` (or a sibling) so it
      is not re-derived by hand next time

## Details

The approach, in order of cost:

1. **Hardware data breakpoint (`ba w8 <addr>`).** x86-64 gives four debug
   registers; cdb exposes them as `ba`. The obstacle is that the target address
   is a *stack* address that only exists once `verifyIntegrity` is running, so
   the breakpoint has to be armed from a code breakpoint inside the function —
   e.g. break on `verifyIntegrity+<prologue end>`, compute `@rbp+368`, `ba w8`
   that, `g`. cdb can script this (`bp … "…; g"`). Note the three cdb traps
   `scripts/lib/CrashCatch.ps1` already documents (backslashes eaten inside
   quoted commands, filters must be armed at the loader break, cdb echoes its
   own command back).
2. **Narrow which run to arm on.** The crash lands on roughly half of runs and
   `verifyIntegrity` is called constantly under `slow_runtime_safety`, so
   arming on every call is far too slow. Arming only after the first integrity
   violation has already been reported may be enough, since the reported
   violation and the stack damage look like the same event seen twice.
3. **If a data breakpoint proves impractical**, the fallback is a poisoned
   guard band: give `verifyIntegrity` a local canary array either side of the
   spill region and check it before the `log.warn`, which at least converts
   "mystery null" into "the frame was overwritten between X and Y".

Do **not** start by bisecting tests again — T442/T443 spent multiple contexts
there and the victim test is known to be arbitrary.

## Validation

- The recipe run against the agent lane produces a stack for the writing
  instruction, or a documented reason it cannot (e.g. the write is a `memset`
  from a thread with no symbols, which is itself a finding).
- Whatever is learned lands in `T443.md`, which remains the owner of the
  underlying corruption.
