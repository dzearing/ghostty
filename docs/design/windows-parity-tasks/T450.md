# T450 - A crashing test binary leaves no stack trace on Windows - the panic handler dies in a recursive panic, so every crash investigation starts blind

## Summary

Filed out of **T449** (2026-08-04). When a ghoztty test binary segfaults under
`zig build`, the output is two lines and nothing else:

```
Segmentation fault at address 0xffffffffffffffff
aborting due to recursive panic
```

Zig's segfault handler catches the fault and then **dies itself** while trying
to walk the stack — the second fault is recorded against `ntdll.dll` (e.g.
`ghoztty-agent-core-test.exe c0000005 ntdll.dll+0x164a57`, 2026-08-04 04:55:50),
which is the symbolisation path, not the original bug. So the one artefact that
would name the culprit is exactly the artefact the crash destroys.

T443 has now spent two full contexts on this class of crash. Both of them were
working from the *victim's* frame — the test that happened to be running — never
the corrupter's, because there is no way on this box to catch the access
violation with all thread stacks intact. `cdb` is not installed, and there is no
just-in-time debugger registered.

## In plain terms

When the tests crash, they are supposed to print a report saying where. On this
machine that report crashes too, so all anyone gets is "it crashed" with no
location. Every attempt to find the underlying bug has therefore started with no
evidence, which is why it has taken several days and still has no answer.

## Goals

- [x] A crashing test binary leaves a full crash dump on disk automatically,
      without anyone remembering to enable anything
- [x] A documented, working command that turns that dump into a stack with
      symbols on this box
- [x] The dump names *all* thread stacks, not just the faulting one — the whole
      point is to see the thread that did the damage, not the one that tripped
      over it

## DONE (2026-08-04) — and the premise was wrong

**`cdb` was on this box the whole time.** Not the Windows Kits copy, which is
genuinely absent (that directory ships `dbghelp.dll` and friends and no
debugger) — the **Microsoft Store WinDbg package**, which includes a console
`cdbX64.exe` at

```
%LOCALAPPDATA%\Microsoft\WindowsApps\Microsoft.WinDbg_8wekyb3d8bbwe\cdbX64.exe
```

No install, no elevation, no download. T443 said it was missing, T449 repeated
it, this file repeated it again, and two whole contexts were spent bisecting a
50%-flaky crash blind on the strength of that one unchecked sentence. It had
even been written down before: the T48 dump-analysis work used this exact
debugger in July and recorded the recipe.

**The lesson worth keeping is not about cdb.** A stated absence ("X is not
installed", "Y does not exist here") is a claim like any other, and it was
carried across three task files and two investigations without one `Test-Path`.
Cheap to check, and checking it was worth several days.

### What shipped

- **`scripts\lib\CrashCatch.ps1`** — runs a program under cdb with the fatal
  exception filters armed (`av`, `sov`, `ii`, `dz`, heap corruption, fastfail).
  On a hit it writes a **full minidump** (`.dump /ma`) plus the faulting
  thread's stack AND `~*kv` for **every** thread, and parses the transcript back
  into an object (exception code, fault site, thread count, source-line count,
  the test that was running).
- **`scripts\crash-catch.ps1`** — the CLI. `-Lane <none|win32|agent>` finds the
  newest test binary that lane built under `.zig-cache\o` and runs *that*, which
  costs ~24–110 s instead of a whole lane. `-Attempts N` re-runs until it
  catches one, because a single clean run of an intermittent crash proves
  nothing. Exit 0 = clean, 1 = crash captured, 2 = could not run.
- **`scripts\floor-lane.ps1`** — when a lane fails AND the Windows Application
  log records a crash in one of *our* test binaries, it now re-runs that binary
  under cdb automatically and prints a `-- crash stack --` block under the
  existing `-- crash diagnostics --` one. Default on (`-NoCatch` to skip,
  `-CatchAttempts` to tune): the crash it exists for is intermittent, so
  "remember to pass a flag next time" means the evidence is gone until it
  happens again. Nothing fires on an ordinary compile failure, or when the
  process that died was the compiler (T451).
- **`test\win32\crash-stacks.ps1`** — acceptance, ALL PASS. Builds a Zig crasher
  that faults **on a background thread**, and asserts the capture contains the
  *other* thread as well; that is the assertion carrying the whole task.

### It works, and it immediately moved T443

First real use, on the agent lane, caught the crash on attempt 1 in 24 s:

```
ghoztty_agent_test!print__anon_430783+0x26   std/debug.zig:227     <-- FAULT
ghoztty_agent_test!log__anon_417474+0x31     compiler/test_runner.zig:280
ghoztty_agent_test!log__anon_410253+0xf      std/log.zig:124
ghoztty_agent_test!warn__anon_406518+0xf     std/log.zig:181
ghoztty_agent_test!verifyIntegrity+0x19aa    src/terminal/page.zig:482
```

The binary is not dying of memory corruption. It is dying **while reporting**
a page integrity violation: the `log.warn` in `verifyIntegrity` reaches the test
runner's log path, which null-dereferences inside `std.debug.print`'s
stderr-writer lock. Filed as **T454**; T443 is updated with it, including that
the all-thread capture (three idle thread-pool workers and nothing else)
refutes its top-ranked "leaked background thread" hypothesis.

### Recipe, for a crash this tooling does not already cover

```powershell
$cdb = "$env:LOCALAPPDATA\Microsoft\WindowsApps\Microsoft.WinDbg_8wekyb3d8bbwe\cdbX64.exe"
$env:_NT_SYMBOL_PATH = "<directory holding the exe and its pdb>"
& $cdb -lines -c "g; .lines -e; ~*kv 40; .dump /ma C:/tmp/x.dmp; q" <exe> <args>
```

Two cdb behaviours that each cost an experiment, both commented in
`CrashCatch.ps1` so they cannot be quietly re-broken:

1. **Paths inside a quoted cdb command are parsed by cdb, which eats
   backslashes** — `.dump /ma D:\a\b.dmp` arrives as `D:ab.dmp`. Use forward
   slashes; Windows accepts them.
2. **`-c`/`-cf` commands run at the FIRST break, which is the loader
   breakpoint.** That is where the `sxe` filters must be registered, before `g`.
   Passing `-g` skips the loader break, so the first break becomes the crash
   itself and the filters are registered too late to ever fire.

And one that cost a false result: **cdb echoes its own initial command before
running it**, and that echo contains every `.echo` marker in it. A substring
match on a marker therefore reports a crash on every clean run. Markers are
matched anchored to a whole line.

### The recursive panic itself is still unexplained

This task made the crash legible; it did not fix Zig's handler. On a *simple*
access violation the handler works and prints the faulting thread (asserted in
the acceptance script). It only recurses in an already-damaged process — and
given T454, the likely reason is that the handler prints through the same
stderr-writer path that is broken. Worth revisiting after T454 rather than
guessing now.

Also unchanged: the handler only ever walks the thread that faulted, whatever
happens to it. That gap is structural, not a bug, and is the reason a debugger
was the right answer rather than a better in-process handler.

## Suggested approach (as filed — route 1 was not taken, see below)

Two independent mechanisms, because the failure mode here is precisely "the one
mechanism you were relying on also broke":

1. **WER local dumps.** `HKLM\SOFTWARE\Microsoft\Windows\Windows Error
   Reporting\LocalDumps\<exe>` with `DumpType=2` (full) makes Windows capture
   the dump itself, outside the crashing process, so a broken in-process handler
   cannot suppress it. Needs admin to write, and should be scoped to the test
   exe names rather than machine-wide.
2. **A debugger.** `cdb.exe` is absent (only `dbghelp.dll` and friends exist
   under `Windows Kits\10\Debuggers\x64`). Either install the Windows
   Debugging Tools, or carry a standalone `procdump` in the repo's tooling and
   have `floor-lane.ps1` run the lane under it.

Then wire whichever lands into `scripts/lib/CrashDiag.ps1`, which already
decodes the exit code and reports the faulting module and offset (T444) — the
dump path belongs in that same `-- crash diagnostics --` block.

Note the recursive panic is worth understanding on its own even after a dump
exists: a panic handler that cannot survive a segfault is a defect, and it is
ours to the extent that we choose the panic handler the test binaries use.

## Validation

- Deliberately crash a test binary (`test\win32\crash-diagnostics.ps1` already
  ships an access-violation generator for exactly this) and show the dump on
  disk plus a symbolised stack from it.
- The stack must resolve to ghoztty source lines, not raw offsets.

### Result (2026-08-04)

- `test\win32\crash-stacks.ps1` — **ALL PASS** (35 checks). It builds a Zig
  crasher that faults on a background thread and asserts: exit 1, a >100 KB
  dump on disk, `0xc0000005` named, the fault site symbolised
  (`avthread!boom`), frames carrying source lines (`avthread.zig @ 4`), **two
  threads captured**, and both the faulting AND the non-faulting thread present
  in the capture. Negative controls too: a clean run exits 0, writes no dump and
  leaves no transcript; a missing exe exits 2.
- `test\win32\crash-diagnostics.ps1` (T444) — ALL PASS, unchanged.
- P1 / P2 / P3 — **ALL PASS**, and actually run rather than skipped: setting
  `GHOZTTY_PIPE_SUFFIX` in the caller's environment before invoking them is
  enough to keep them off the user's live instance (T441's hazard). Verified
  first with a read-only probe — `ghoztty +list` under the suffix answers "No
  running Ghoztty instance found" instead of listing the user's windows.
- `scripts\floor-lane.ps1 -Lane all` — `none=FAIL win32=FAIL agent=FAIL`. All
  three, which has not happened before, and `none` had never failed at all.
  Pre-existing: the working tree during that run held only PowerShell and
  markdown changes (`git status` at 06:36 — no `.zig`, no app code), so nothing
  here can have caused it. It is T443/T454's crash, and this task's whole point
  is that it now leaves evidence:
  - `none` FAIL — auto-captured `c000001d` at `hash_map.zig:333` via
    `lookupHyperlink` (recorded in T443).
  - `win32` FAIL — same WER offset `+0xcc49e` as the `none` crash; the capture
    came back clean in both attempts, and said so rather than inventing one.
  - `agent` FAIL — both agent binaries crashed; the capture came back clean in
    two attempts.

  Two captures out of four crashes at `-CatchAttempts 2`. That is the honest
  hit rate for an intermittent crash and the reason **D6** asks the user how
  many minutes a red lane should be allowed to spend.
- Live use against the real thing: caught the agent-lane crash on attempt 1 in
  24 s with a full symbolised stack, which is what produced T454.
