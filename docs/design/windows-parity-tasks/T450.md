# T450 - A crashing test binary leaves no stack trace on Windows - the panic handler dies in a recursive panic, so every crash investigation starts blind

## Summary

Filed out of **T449** (2026-08-04). When a ghoztty test binary segfaults under
`zig build`, the output is two lines and nothing else:

```
Segmentation fault at address 0xffffffffffffffff
aborting due to recursive panic
```

Zig's segfault handler catches the fault and then **dies itself** while trying
to walk the stack — the second fault is recorded against `ntdll.dll` (e.g.
`ghoztty-agent-core-test.exe c0000005 ntdll.dll+0x164a57`, 2026-08-04 04:55:50),
which is the symbolisation path, not the original bug. So the one artefact that
would name the culprit is exactly the artefact the crash destroys.

T443 has now spent two full contexts on this class of crash. Both of them were
working from the *victim's* frame — the test that happened to be running — never
the corrupter's, because there is no way on this box to catch the access
violation with all thread stacks intact. `cdb` is not installed, and there is no
just-in-time debugger registered.

## In plain terms

When the tests crash, they are supposed to print a report saying where. On this
machine that report crashes too, so all anyone gets is "it crashed" with no
location. Every attempt to find the underlying bug has therefore started with no
evidence, which is why it has taken several days and still has no answer.

## Goals

- [ ] A crashing test binary leaves a full crash dump on disk automatically,
      without anyone remembering to enable anything
- [ ] A documented, working command that turns that dump into a stack with
      symbols on this box
- [ ] The dump names *all* thread stacks, not just the faulting one — the whole
      point is to see the thread that did the damage, not the one that tripped
      over it

## Suggested approach

Two independent mechanisms, because the failure mode here is precisely "the one
mechanism you were relying on also broke":

1. **WER local dumps.** `HKLM\SOFTWARE\Microsoft\Windows\Windows Error
   Reporting\LocalDumps\<exe>` with `DumpType=2` (full) makes Windows capture
   the dump itself, outside the crashing process, so a broken in-process handler
   cannot suppress it. Needs admin to write, and should be scoped to the test
   exe names rather than machine-wide.
2. **A debugger.** `cdb.exe` is absent (only `dbghelp.dll` and friends exist
   under `Windows Kits\10\Debuggers\x64`). Either install the Windows
   Debugging Tools, or carry a standalone `procdump` in the repo's tooling and
   have `floor-lane.ps1` run the lane under it.

Then wire whichever lands into `scripts/lib/CrashDiag.ps1`, which already
decodes the exit code and reports the faulting module and offset (T444) — the
dump path belongs in that same `-- crash diagnostics --` block.

Note the recursive panic is worth understanding on its own even after a dump
exists: a panic handler that cannot survive a segfault is a defect, and it is
ours to the extent that we choose the panic handler the test binaries use.

## Validation

- Deliberately crash a test binary (`test\win32\crash-diagnostics.ps1` already
  ships an access-violation generator for exactly this) and show the dump on
  disk plus a symbolised stack from it.
- The stack must resolve to ghoztty source lines, not raw offsets.
