# T727 - deliver-windows-build.ps1 has no -VerifyOnly: nothing audits the install locations between deliveries

## In plain terms

There is now a script that delivers a build to the Desktop portable and the
network share and then checks its own work. What there is no way to ask is
"never mind delivering - what is sitting in those places RIGHT NOW?". That
question would have answered in two seconds on 2026-08-10, when both portable
copies had been holding a debug build for most of a day and nobody could tell
without reading file sizes by hand.

## Summary

T198 added `scripts\deliver-windows-build.ps1`, which verifies every file it
writes (length + mtime, `+version`, PE subsystem) and the portable zip's entry
set. All of that verification only runs as part of a DELIVERY. There is
`-DryRun`, but it deliberately writes nothing and therefore checks nothing
either.

Add `-VerifyOnly`: run the verification pass alone against every configured
location - no copies, no backups, no zip rebuild - and report per location
whether its binaries answer the expected commit, whether their PE subsystems are
right, and whether the published zip's entry set still matches the manifest
rule. Exit 0 when everything is what it should be, 1 when a location is present
and wrong, and SKIP an unreachable one exactly as the delivery path does.

## Details

Two things that make this worth its own task rather than a flag added in
passing:

- **What is "expected" when nothing is being delivered?** The delivery path
  takes the commit from the staged exe. A standalone audit more usefully takes
  it from `git rev-parse --short HEAD`, or from whichever location is NEWEST, or
  from an explicit `-ExpectedCommit`. Picking wrong makes the audit cry wolf on
  a box that is deliberately a delivery behind.
- **Where it gets called from.** The candidates are `morning-refresh.ps1` (a
  once-a-day audit line in its log), the go-loop watchdog, and the dashboard.
  The failure this exists to catch is silent and long-lived, so it needs a
  reader that runs without anyone asking - a flag nobody invokes is not an
  improvement over today.

The vector by which a debug `ghoztty.exe` and `ghoztty-agent.exe` reached both
portable locations on 2026-08-10 was never identified: the upgrade log for that
day shows only `zig-out-release` staging, and no script in the repo names those
directories except `upgrade-ghoztty-windows.ps1`. The most likely explanation is
a hand-run copy from an earlier turn. That is precisely the kind of vector a
periodic audit catches and a delivery-time check cannot.

## Validation criteria

- [ ] `deliver-windows-build.ps1 -VerifyOnly` reports every configured location
      without writing a single byte (proved by comparing mtimes across the run).
- [ ] It exits 1 against a location seeded with a mismatched build, and names
      which location and what it found.
- [ ] It exits 0 with a SKIP line for an unreachable location.
- [ ] Some unattended reader calls it, and its verdict is visible without
      running it by hand.
- [ ] Arms added to `test\win32\deliver-windows-build.ps1`, green.
