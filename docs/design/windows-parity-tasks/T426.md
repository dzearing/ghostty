# T426 - Root-cause the app death inside terminateProcess during the destructive agent refresh (T421's third occurrence)

## In plain terms

Four times, a user clicked "update the background service" and Ghoztty simply
vanished mid-click — no crash report, no error, no windows. Earlier work made it
come back afterwards; nobody knew why it died. It turns out Windows had filed
Ghoztty and its background service into the same "kill these together" group, so
shutting the service down could take the terminal with it. The service is now
started outside that group, and the moment before every shutdown Ghoztty writes
down exactly who is grouped with whom — so if this ever happens again, the answer
is already in the log instead of costing another investigation.

## Goals

- [x] Measure, at the instant it matters, whether the app and the agent share a
      job object — and what kind of job it is
- [x] Stop the agent being spawned into the app's job in the first place
- [x] Prove the escape by OUTCOME (membership + surviving a teardown), not by
      reading a log line
- [x] Prove the pre-fix build fails that same test (a fix with no failing
      "before" is a fix for nothing)

## Validation criteria

- [x] The refresh logs the job facts BEFORE the terminate, with real answers and
      not `?` — `agent-upgrade.ps1` H21/H22, on a real destructive refresh
- [x] The agent spawn names which escape tier it got, and is loud when it
      degrades — `agent-upgrade.ps1` H23/H24
- [x] The agent a jailed app spawns is NOT a member of that job and SURVIVES its
      teardown — `test\win32\agent-job-escape.ps1` B2/C1
- [x] A control process in the same job DOES die with it, so the teardown is

- [x] Floor green (three zig lanes, P1–P3), `agent-upgrade.ps1` and

## Summary

**T421 fixed the outcome, not the cause.** The app now comes back if it dies
during the destructive agent refresh (the relaunch guard), and the kill target is
verified before it is killed. Neither of those explains why the process ends.

What is ✓ VERIFIED, from `%LOCALAPPDATA%\ghoztty\ghoztty.log` (T421 has the full
trail):

- The last line the dying process writes is `agent restart: terminating agent pid
  N`. The next line in the file is a DIFFERENT process's boot banner.
- **Both** branches after that call log, so `terminateProcess` did not return.
- No WER `Application Error` / `Application Hang` event exists for `ghoztty.exe`
  anywhere near it. It is a clean exit, not a caught crash.
- Three occurrences now (T229 twice, T421 once), all identical in shape.

What is inside that window: `OpenProcess`, `QueryFullProcessImageNameW` (new),
`TerminateProcess`, `WaitForSingleObject(3000)`, `CloseHandle`. None of them can
end the caller — unless the pid is not the agent, which T421 now blocks, or
something concurrent does. The other thing running at that instant is the
connection teardown thread T229 moved off the GUI thread (`LocalAgent.retire`),
joining the old connection's reader/writer/heartbeat threads while the pipe
server they are reading is being terminated.

## New lead (2026-08-06, fourth occurrence — see T524's evidence)

The T524 investigation established two facts that reshape this task:

- **The app runs inside a Windows Job object** (IsProcessInJob = true, measured
  on the live release instance), and kill-on-close jobs (`LimitFlags 0x3C00`)
  are demonstrably present in this process ecosystem.
- **The relaunch guard — a child spawned milliseconds before the death — dies
  in the same instant, before executing one instruction.** Only a job-object
  teardown kills a detached child that way.

That makes the leading hypothesis: the app and the OLD agent share a
kill-on-close job whose last handle lives inside the agent process, so
`TerminateProcess(agent)` closes the job's last handle and the job kills the
app before its own `TerminateProcess` call returns — a clean, WER-less death
between `terminating agent pid N` and the never-logged `terminate returned`,
which is exactly the observed signature, all four times. Verify by querying
job membership of app + agent at refresh time (log `IsProcessInJob` for both,
and whether they share a job) before terminating. The structural fix on the
agent side: spawn the agent with `CREATE_BREAKAWAY_FROM_JOB` — a daemon meant
to outlive the app must never sit in anyone's killable job.

## Outcome (2026-08-09) — the cause is established, and removed

### 1. The shared job is REAL, and now measured

`terminateAgent` writes the job facts before it kills anything. In a real
destructive refresh (`agent-upgrade.ps1` arm H) it printed:

```
agent restart: job facts before the kill — self_in_job=yes
    self_job_flags=0x2000 kill_on_close agent_in_job=yes SHARED_JOB=yes
```

The app and the agent are members of ONE kill-on-close job. That is the
condition T524 could only hypothesise, and it is the whole mechanism: a job
teardown kills every member simultaneously, which is a clean, WER-less
disappearance with no chance to log — exactly the signature all four times,
between `terminating agent pid N` and the never-reached `terminate returned`.
Note the flags carry **no** `breakaway_ok`, which is separately why tier-1
breakaway is refused with ACCESS_DENIED on this box.

The diagnostic reports `?` rather than `no` for anything it could not measure
(`job_object.describe`, asserted): an unanswerable question that reads as a
negative answer is what sends the next investigation down the wrong path.

### 2. The mechanism is removed, and the removal has teeth

`LocalAgent.spawnAgent` used a plain `CreateProcessW` with `DETACHED_PROCESS`,
and `DETACHED_PROCESS` does not leave a job — so the daemon whose entire purpose
is outliving the app was a member of a group that can kill it on the app's
account. It now spawns through `job_spawn.spawnEscapingJob`, the tiered escape
T524 built for the relaunch guard and which is extracted here into its own
module because both callers want the identical thing for the identical reason.

Measured by outcome, not by log scraping (`test\win32\agent-job-escape.ps1`):
the app under test is jailed in a kill-on-close job (0x2800), its agent is
probed with `IsProcessInJob` against that exact handle, and then the job is
torn down.

- **ALL PASS (9 assertions)** with the fix.
- **Teeth-checked**: with the pre-fix plain spawn restored and rebuilt, B2 (the
  agent is not a member of the job) and C1 (it survives the teardown) both FAIL.
  That is the first direct demonstration that the agent shared the app's
  killable job and died with its teardown.
- Arm D is the negative control — a control process in the same job DOES die —
  so B2/C1 cannot pass on a job that kills nothing.

### 3. What this does NOT prove, and what the next occurrence will say

It does not prove a fifth occurrence is impossible; it removes the only
mechanism consistent with all four and leaves the measurement in place. If it
happens again, the log now names the job situation at the instant before the
kill, so the next turn starts from a fact instead of a hypothesis.

The escape is environment-dependent, and says so: tier 1 needs a job chain that
permits breakaway (this box's does not) and tier 2 needs a shell window. On the
acceptance harness's background test desktop there is no shell, so the spawn
degrades to in-job and logs a warning naming that — asserted as its own
invariant (H24), and filed as **T674** for a tier that needs no shell.

is worse than one that says `?`, so the buffer is zeroed and only
