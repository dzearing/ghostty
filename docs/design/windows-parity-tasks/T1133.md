# T1133 - No gate in the turn has ever been shown to fail, except the acceptance scripts

## In plain terms

Several automatic checks run at the start and end of every work session and
report that everything is fine. Most of them have never once been observed
saying anything else. A check that has never failed is indistinguishable from a
check that cannot fail, and we have now been bitten by that three times in a
month.

## Summary

T1099 was the third instance: `upstream-remote.ps1 ensure` printed `UPSTREAM OK`
every morning while answering a weaker question than the one it existed to
answer, so it stayed green through an hour and a half in which every sha it
guards was gc bait. Before that, the go-loop guard sat 26-red for a day with
nothing tying the edit to the harness (T783), and the push gate was a habit
before it was a check (T1057).

The acceptance scripts do not have this problem, and the reason is structural:
every one of them carries `-NegativeControl`, a mode that inverts one assertion
so the script MUST score exactly one failure. That is what makes their greens
worth something. The gates in `go-loop-exec.ps1 claim` and
`parity-tasks.ps1 validate` have no equivalent.

The work is to give them one. For each gate the turn runs, construct the state it
is supposed to catch and prove it goes red:

- `claim`'s reports: stranded work, guard-due, push-clean, upstream, boot outage,
  build-cache, duplicate execution windows
- `validate`'s failures: stranded work, guard-due, push-ahead, priority outside
  the set, missing dep id, dep cycle, in-progress with no progress log
- `ship-readiness.ps1`'s ten criteria — an **unmeasured** criterion already counts
  as unmet there, which is the right shape and worth copying elsewhere

Most of these can be driven against a fixture repo the way
`test\win32\upstream-remote.ps1` section B and E do, so nothing has to be broken
on the live box to prove it.

The deliverable is a harness plus the rule that follows from it: **a new gate
ships with the demonstration that it can fail, or it is not a gate.** Write that
into `go.md` step 3 alongside the guard-due rule.

## Validation criteria

- [ ] Every reported condition in `go-loop-exec.ps1 claim` has a fixture that makes
      it fire, asserted by an acceptance script
- [ ] Every failure branch of `parity-tasks.ps1 validate` has the same
- [ ] The new harness has its own `-NegativeControl` and a `guard-due` coverage row
- [ ] `go.md` step 3 states the rule, and it names this harness
- [ ] Floor lanes green plus P1-P3
