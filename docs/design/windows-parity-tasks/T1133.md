# T1133 - No gate in the turn has ever been shown to fail, except the acceptance scripts

## In plain terms

Several automatic checks run at the start and end of every work session and
report that everything is fine. Most of them have never once been observed
saying anything else. A check that has never failed is indistinguishable from a
check that cannot fail, and we have now been bitten by that three times in a
month.

## Summary

T1099 was the third instance: `upstream-remote.ps1 ensure` printed `UPSTREAM OK`
every morning while answering a weaker question than the one it existed to
answer, so it stayed green through an hour and a half in which every sha it
guards was gc bait. Before that, the go-loop guard sat 26-red for a day with
nothing tying the edit to the harness (T783), and the push gate was a habit
before it was a check (T1057).

The acceptance scripts do not have this problem, and the reason is structural:
every one of them carries `-NegativeControl`, a mode that inverts one assertion
so the script MUST score exactly one failure. That is what makes their greens
worth something. The gates in `go-loop-exec.ps1 claim` and
`parity-tasks.ps1 validate` have no equivalent.

The work is to give them one. For each gate the turn runs, construct the state it
is supposed to catch and prove it goes red:

- `claim`'s reports: stranded work, guard-due, push-clean, upstream, boot outage,
  build-cache, duplicate execution windows
- `validate`'s failures: stranded work, guard-due, push-ahead, priority outside
  the set, missing dep id, dep cycle, in-progress with no progress log
- `ship-readiness.ps1`'s ten criteria — an **unmeasured** criterion already counts
  as unmet there, which is the right shape and worth copying elsewhere

Most of these can be driven against a fixture repo the way
`test\win32\upstream-remote.ps1` section B and E do, so nothing has to be broken
on the live box to prove it.

The deliverable is a harness plus the rule that follows from it: **a new gate
ships with the demonstration that it can fail, or it is not a gate.** Write that
into `go.md` step 3 alongside the guard-due rule.

## What shipped

`test\win32\gate-negatives.ps1` — 35 assertions, four sections.

**The registry (section A) is the durable half.** Every condition either gate
reports is a row: a `gate` (a red verdict, which must name a harness that
asserts on it), a `hatch` (an escape hatch, held to the same bar — one that
silently stops announcing itself is a gate that silently stopped existing), or
a `status` (an ordinary line). The label vocabulary is then DISCOVERED from the
two scripts' own source text and compared against the registry both ways: a
label nobody triaged fails A2, and a row whose label is no longer emitted fails
A3. A8/A9 are the teeth for that — a synthesized "TOMORROW GATE" is injected
into a copy of the claim script and must come back discovered-and-undeclared —
and A10 proves a marker that only appears in prose does not count as a
demonstration. A7 asserts each delegated gate is still reachable from `claim`,
so a row cannot outlive its wiring.

**Section B** drives the seven `validate` branches nothing else demonstrated —
`BAD FRONTMATTER`, `ID MISMATCH`, `NO TITLE`, `NO STATUS`, `ODD STATUS`,
`DANGLING DEP`, `DEP CYCLE` — one fixture task dir per case, plus B0, the
positive control that a clean fixture is green.

**Section C** drives `claim` red against a throwaway repo: stranded work,
unpushed work and a broken upstream in one run, then C5 shows `validate` FAILS
on the same stranded path (the two-ended arrangement the loop depends on,
measured end to end), then a clean pushed repo produces `tree clean at claim`
and `push clean`. Offline-safe: the fixture's `upstream` ref and fetch stamp
are wired by hand so the delegate reaches a real verdict without touching
GitHub, and the claim is handed `where.exe` as its ghoztty stand-in.

**`DEP CYCLE` did not exist.** The task listed it among `validate`'s failure
branches; it was not one. A ring of tasks that wait on each other is the one
tracker defect where every file reads correctly on its own — `next` skips every
member for "unmet deps" forever, indistinguishable from waiting on work that is
genuinely open. `Get-DepCycles` in `scripts\parity-tasks.ps1` now reports each
ring once, from its member set, and B7–B10 cover a two-task ring, a self-dep,
the once-per-ring rule, and a ring reached through a chain.
