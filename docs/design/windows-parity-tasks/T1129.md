# T1129 - Dragging a split divider on Windows still moves neighbouring edges, not just the one you grabbed

## In plain terms

When you drag the line between two panes, you expect exactly that line to move
and everything else to stay put. On Windows a drag can still shove the panes on
the far side of the layout around, because the drag is applied as a ratio change
up the tree rather than as a movement of one edge. The Mac build was fixed on
2026-08-21; this is the same fix for Windows.

## Summary

Main intake, 2026-08-22 (range `22c9c6d8a..origin/main`). Upstream commit
**77d21cb48** *"fix(splits): dragging a divider moves only that one edge"*
reworked the macOS side: `macos/Sources/Features/Splits/SplitTree.swift` (+209),
`SplitView.Divider.swift`, `SplitView.swift`, `TerminalSplitTreeView.swift`,
`BaseTerminalController.swift`, with `macos/Tests/Splits/SplitTreeDividerTests.swift`
(305 lines) as its proof. Nothing in the Windows split tree
(`src/apprt/win32/`) carries that change, so a Windows drag keeps the old
whole-subtree ratio semantics.

Read the Swift diff for the intended semantics before designing the Windows
half — the point is the *edge* is the thing being moved, and the tree walk that
finds which node owns that edge is where the behavior lives. Translate the
semantics, not the Swift.

**Reassessed on claiming (2026-08-23).** The intake's premise was half wrong:
the Windows MOUSE drag has had fixed-edge semantics since **T533**
(`src/apprt/win32/split_resize.zig`), filed from the user's own report on
2026-08-06 and noted there as a deliberate divergence AHEAD of Mac — 77d21cb48
is the Mac seat catching up. What Windows did not have is the other half of that
commit: *"the keyboard resize_split path shares the same math, since it is the
same gesture by another input."* `Window.resizeSplit` still went through
`SplitTree.resize`, which applies a ratio delta to the nearest matching split,
so the keyboard carried BOTH defects the mouse had already had fixed — T533's
(divider 2 slides when divider 1 moves) and T495's (a nested divider leaps,
because the delta is measured against the whole grid while the ratio is relative
to the node's own region: one press of "move right" jumped it ~170px LEFT on a
1600px-wide window).

Solved by routing `resize_split` through the same `split_resize.plan` the drag
uses, against the target node's own region. A held key is treated as ONE gesture
(`split_resize.KeyboardGesture`) for the reason the drag replays from a
snapshot: an `f16` ratio round-tripped through pixels once per press does not
round-trip cleanly, and eighty presses out and back left a held boundary 40px
from where it started — measured, and kept as a control test.

## Goals

- [x] `resize_split` moves the divider the same way a drag does: only the two
      panes flanking it change size.
- [x] A nested split's divider steps by the requested pixels instead of leaping
      (the keyboard's copy of the T495 defect).
- [x] A held key is one gesture, so out-and-back is exact rather than drifting.
- [x] A divider moved by keyboard survives a restore, as a dragged one does.

## Validation criteria

- [x] Moving a divider by keyboard in a 3-pane layout moves only the two panes
      that share it; every other pane keeps its size — `test\win32\split-divider.ps1`
      section T1129 (b), pane rects measured, with a control asserting the
      divider the user asked for really travelled.
- [x] A nested split's divider steps ~10px per press rather than teleporting —
      same script, section T1129 (a).
- [x] Ten steps out and ten back land on the starting pixels — same script,
      section T1129 (c).
- [x] Unit tests in the `none` lane cover the step math, the gesture, and the
      conditions that end it: `src/apprt/win32/split_resize.zig` (`nudgeRatio`,
      `KeyboardGesture`), plus `SplitTree.nearestSplit` in
      `src/datastruct/split_tree.zig`. Each holding assertion carries the
      uncompensated answer as its control.
- [x] Floor lanes green (`scripts\floor-lane.ps1 -Lane all`) plus P1-P3.
