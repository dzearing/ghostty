# T1129 - Dragging a split divider on Windows still moves neighbouring edges, not just the one you grabbed

## In plain terms

When you drag the line between two panes, you expect exactly that line to move
and everything else to stay put. On Windows a drag can still shove the panes on
the far side of the layout around, because the drag is applied as a ratio change
up the tree rather than as a movement of one edge. The Mac build was fixed on
2026-08-21; this is the same fix for Windows.

## Summary

Main intake, 2026-08-22 (range `22c9c6d8a..origin/main`). Upstream commit
**77d21cb48** *"fix(splits): dragging a divider moves only that one edge"*
reworked the macOS side: `macos/Sources/Features/Splits/SplitTree.swift` (+209),
`SplitView.Divider.swift`, `SplitView.swift`, `TerminalSplitTreeView.swift`,
`BaseTerminalController.swift`, with `macos/Tests/Splits/SplitTreeDividerTests.swift`
(305 lines) as its proof. Nothing in the Windows split tree
(`src/apprt/win32/`) carries that change, so a Windows drag keeps the old
whole-subtree ratio semantics.

Read the Swift diff for the intended semantics before designing the Windows
half — the point is the *edge* is the thing being moved, and the tree walk that
finds which node owns that edge is where the behavior lives. Translate the
semantics, not the Swift.

## Validation criteria

- [ ] Dragging a divider in a 3+ pane layout moves only the two panes that share
      that divider; every other pane keeps its size (pixel-measured, not eyeballed).
- [ ] A drag at a nested split's divider behaves the same as the equivalent
      drag on the Mac build for the same layout.
- [ ] Unit tests in the `none` lane cover the edge-ownership walk, mirroring what
      `SplitTreeDividerTests.swift` asserts on the Mac side.
- [ ] An on-box acceptance script in `test/win32/` drives real drags and asserts
      the neighbouring panes did not move.
- [ ] Floor lanes green (`scripts\floor-lane.ps1 -Lane all`) plus P1-P3.
