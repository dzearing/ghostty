# T746 - Ctrl+Shift+N does not open the machine chooser (New Remote Window dialog)

## In plain terms

Ctrl+Shift+N is supposed to open the window that lists your machines, so you
can start a terminal on another computer. Whether it worked depended on which
part of the window you had clicked last. If you were typing in a terminal it
opened. If you had clicked into a side pane showing a document or a web page,
it opened a plain new terminal window instead of the machine list. And if the
window itself had the keyboard — which happens after almost any small dialog
closes — the keystroke did nothing at all. Now it opens the machine list from
all three.

## Goals

- [x] the chord opens the chooser from a focused terminal pane (it already did)
- [x] the chord opens the chooser from a focused viewer pane, instead of
      opening a plain local window
- [x] the chord opens the chooser when the top-level window itself has focus,
      instead of being dropped
- [x] the chord has ONE definition rather than one per focus target
- [x] an acceptance script covers all three focus states, with a negative
      control that fails

## Summary

User report 2026-08-11: pressing Ctrl+Shift+N in the Windows build does nothing - the machine chooser / New Remote Window dialog never appears. Expected: the chord opens the chooser (the Windows analog of Cmd-Shift-N). Investigate whether the keybind is registered, being swallowed by another handler, or the chooser window fails to create.

## Root cause

The chord is not a core binding action - T22c decision 3 settled that the core
has no `new_remote_window` action and that Windows would intercept the chord
locally instead. It was intercepted in exactly ONE place, an `if` inside
`Surface.handleKeyEvent`, which is reached only while a **terminal pane** owns
the keyboard focus. The same keystroke therefore meant three different things
inside one window:

| focus | before | after |
|---|---|---|
| terminal pane | opens the chooser | unchanged |
| viewer pane | opens a plain local window | opens the chooser |
| top-level window | nothing at all | opens the chooser |

The viewer case is the interesting one: a focused viewer's chords come back
through `viewer_accel`, which forwards **binding actions** — and the
cross-platform `ctrl+shift+n -> new_window` default is still in the keybind
set, so the chord resolved to that instead. The top-level case is the literal
report: `Window.wndProc` had no `WM_KEYDOWN` arm, so the key was dropped.

Confirmed from the user's own installed-release log
(`%LOCALAPPDATA%\ghoztty\ghoztty.log`): the chord's log line appears
repeatedly through builds up to ~2026-08-04, and the user's most recent
session opens the chooser `via command surface` (the command palette) only —
the fallback somebody reaches for when the chord is dead.

## Fix

`src/apprt/win32/window_chord.zig` (new, pure, asserted in the `none` lane) is
the one definition of a window-scoped chord that has no binding action to be
looked up from. Three call sites consult it:

- `Surface.handleKeyEvent` — replaces the inline `GetKeyState` spelling.
- `Window.wndProc` — a new `WM_KEYDOWN` arm; anything that is not a window
  chord falls straight through to `DefWindowProc`.
- `ViewerPane.claimsChord` / `WM_APP_VIEWER_ACCEL` — checked **before** the
  keybind table, which is what stops the `new_window` default from winning.

`Surface.getModifiers` is now `pub` and read by `Window.wndProc` rather than a
third copy of the same `GetKeyState` block.
