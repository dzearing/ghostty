# T695 - ghoztty:// focus-only URL scheme has no Windows half - a link that raises a window or pane is dead here

## Summary

main c36456863 added a focus-only ghoztty:// URL scheme on macOS: ghoztty://focus/<target> raises the window or pane named by anything --target accepts. Windows registers no URL scheme at all, so such a link is dead here. Needs the win32 half: HKCU scheme registration (ghoztty:// release / ghoztty-debug:// debug, mirroring the pipe-name split), a strict parser shared with the Mac's shape (path form, one percent-decoded target, unknown verb/empty target/bare host all yield nothing), dispatch through the existing resolveTarget so the untrusted caller shares one naming system with --target, focus-only (no spawn, no type, no consolation focus), a coalesced not-found warning, and the three in-app link paths (banner links, WebView2 viewer navigation interception, viewer popup) handled in process so they never round-trip through the shell.

## In plain terms

On a Mac, a document can carry a link that jumps you straight to a terminal
window — click it in a build report or a dashboard and that window comes to the
front. On Windows nothing happens: the link is dead, because Windows was never
told that `ghoztty://` addresses belong to Ghoztty. When this lands, the same
link works on both machines, and it can still only ever raise a window — never
run anything.

## Goals

- [x] Windows knows `ghoztty://` (and `ghoztty-debug://` for a dev build) belongs
      to Ghoztty, and clicking such a link raises the named window or pane
- [x] The target is anything `--target` already accepts, resolved by the same code
- [x] A link that names nothing that exists says so once, and never creates or
      focuses something else instead
- [x] Links clicked inside Ghoztty (banner links, viewer pages) are handled in
      process, without a round trip through the shell

## Validation criteria

- [x] A pane name and a pane id both work as `<target>`; verified on box — arm B

      `src/apprt/ipc/url_scheme.zig`, plus arm C on the box, whose teeth are

- [x] A debug build registers only `ghoztty-debug://` and does not steal the
      user's `ghoztty://` links; verified on box — arm A, which snapshots the

### Decision D61 - Should a ghoztty:// link start Ghoztty when no instance is running?

Resolved 2026-08-14T18:02:09Z : Never launch - report not-found (Recommended)

Resolved by Claude (2026-08-14). Security beats convenience here: the whole design of the link scheme is that a web page can focus a window but can never start a program on the box. The user-visible cost is that clicking a ghoztty link with the app closed shows a not-found message instead of launching the terminal - if you want Mac-identical cold-click launch at the cost of link-triggered program start, overturn this.

### Decision D62 - Should ghoztty:// registration be gated to the canonical install directory, the way the PATH self-heal is?

Resolved 2026-08-14T18:02:09Z : Register on every launch, per build mode (Recommended)

Resolved by Claude (user delegated technical calls, 2026-08-14). Per-build-mode registration keeps debug and release isolated (the same isolation the IPC pipe has) and keeps the portable and share copies answering links; a release build run from an odd location self-corrects on the next installed launch.
