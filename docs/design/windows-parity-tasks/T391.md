# T391 - Viewer live reload: ReadDirectoryChangesW watcher + debounce (split from T90f)

## Summary

File viewers watch their file (including atomic saves) and re-render preserving scroll: ReadDirectoryChangesW watcher + debounce + WM_APP_VIEWER_RELOAD onto the GUI thread, re-armed on every navigation and on +reload.

## Details

`src/apprt/win32/viewer_watcher.zig` is the new module; the wiring is four
small edits to `ViewerPane.zig` (a `watcher` field, `syncWatcher` off
`navigate`, `stop` first in `deinit`, and two `wndProc` arms).

**Windows watches the DIRECTORY, not the file, and that is the whole
translation.** Mac's kqueue source is bound to an open file DESCRIPTOR, so an
atomic save -- write a scratch file, rename it over the target -- leaves the
watch holding an inode nobody will write to again; that platform has to notice
`.delete`/`.rename` and re-arm onto the new one, which is what
`ViewerView.reloadNeedsRearm` exists for. `ReadDirectoryChangesW` reports
changes by NAME within a directory, so the replacement arrives as an ordinary
notification for the same basename. **The Windows equivalent of Mac's re-arm
logic is its absence** -- `syncWatcher` is driven off `navigate` alone, because
`navigate` is the only thing that changes `file_path`.

Debounce is a `WM_TIMER` (100ms, Mac's 0.1s) on the pane's own host window:
`SetTimer` with an id that already has a timer RESETS it, which is
cancel-and-reschedule exactly. The watcher thread only ever decides "did the
watched name change" and posts; the debounce and the render both stay on the
GUI thread, where the browser is.

Three details that are not obvious:

- **Overlapped, not synchronous.** A synchronous `ReadDirectoryChangesW` +
  cross-thread `CancelIoEx` has a real race: stop can land in the window
  between the thread's last check and its next read, and then it blocks
  forever. The overlapped read parked in `WaitForMultipleObjects([io, stop])`
  has no such window -- a stop signalled before the wait starts returns from it
  immediately. On the stop path the read is cancelled AND drained
  (`GetOverlappedResult(bWait=1)`) before the thread's stack buffer goes away.
- **Zero bytes returned means the kernel's own buffer overflowed** and it threw
  the detail away. That reloads unconditionally: a spurious re-render costs a
  repaint, a missed one costs the feature.
- **`mentions` reads every field with `readInt`** rather than overlaying a
  struct on the record stream. The name that follows each 12-byte header is
  2-byte data at an offset the format makes no alignment promise about, and it
  lets the unit test build a batch out of plain bytes. A `NextEntryOffset` that
  does not advance past its own header ends the walk instead of spinning.

`FILE_SHARE_DELETE` is load-bearing on the directory handle for the same reason
the other two share flags are: the point of watching a file is that other
processes write to it, and an editor that could not replace the file because
the viewer was holding it would be a far worse bug than no live reload.

## Validation

Pure half, `zig build test -Dapp-runtime=win32`: three `mentions` tests --
case-folded match, the two-record chain an atomic save actually produces (a
walk that stops at the first entry misses every one of them), a prefix that
must NOT match (`design.md.tmp` is the editor's scratch file), and three
malformed streams that have to terminate.

Live half, appended to the real-WebView2 `host floor` test in `ViewerPane.zig`
-- a real controller, a real message loop, a real file on disk, and **nobody
calling `reloadContent`**: an in-place save re-renders (`headings=3 Zeta`), an
atomic save re-renders (`headings=2 Iota`), navigating to a website stops the
watch and navigating back re-arms it.

Both halves proven by mutation, and it took two:

1. `syncWatcher` returning before `start` -- the whole T391 section goes red at
   its first assertion. That proves the chain, and leaves the ATOMIC-save claim
   riding on the in-place one.
2. Dropping `FILE_NOTIFY_CHANGE_FILE_NAME` from the filter -- **the in-place
   save still reloads and the atomic save does not** (`watch: atomic save ->
   headings=3 first=Zeta`, still showing the previous document). That is the
   discriminating run: the two assertions are independent, and the flag is
   load-bearing rather than decorative.

Floor: `zig build test -Dapp-runtime=none` + `-Dapp-runtime=win32` +
`test-agent` all green, P1-P3 ALL PASS, `viewer-panes.ps1` ALL PASS (111).
