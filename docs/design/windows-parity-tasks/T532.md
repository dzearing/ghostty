# T532 - Re-attach after manual relaunch paints frozen, non-interactive panes

## In plain terms

Ghoztty is built so that closing or crashing the app never kills what is
running in your terminals — reopen it and your windows come back exactly where
they were, still running. One morning that promise broke in the worst possible
way: the windows came back looking perfect, and were dead. Typing did nothing.
Nothing new ever appeared. Everything the app could report said it had worked.
The only way out was to restart again and hope.

When this is fixed, a restored window either works or says out loud that it
could not reconnect. What it must never do is show you a photograph of your
work and let you think it is your work.

## Goals

- [x] The freeze can be reproduced on demand, or the exact condition that
      triggers it is named. — both: the condition is a resume point recorded
      against a byte stream that no longer exists, and
      `test\win32\session-reattach-zombie.ps1` section D reproduces it on
      demand.
- [x] A restored pane is genuinely live — typing echoes, output flows — or the
      pane tells you its reconnect failed.
- [x] A test types into a restored pane and fails if nothing comes back, so
      this cannot come back unnoticed.

## User report (2026-08-06, verbatim)

"When i reopened it ... the windows seemed to repaint correctly but were non
interactive, not painting, but seemed to still be working, as if we could not
reconnect the live stream, so resume didn't work."

Context: the 09:19 delivery (staging 1cda2827c) killed the release app with
`-NoResume` (so nothing restarted it - that half is understood, the delivery
flag skipped the relaunch). The user manually launched from the Start menu at
~09:19:53. The RESTORED windows painted their scrollback but were dead:
keyboard input did nothing and no new output arrived. The user got a working
state only after another restart.

## Evidence from %LOCALAPPDATA%\ghoztty\ghoztty.log (gathered at filing)

The app BELIEVES the re-attach succeeded - every line reports success:

```
199505 shared local-agent connection ready (agent pid 35492)
199509 attach: session=6a378608... offset=43394044 snapshot=14382
199510 attach: applying agent-reported cwd=D:\git\ghoztty\
199514 attach: session=d73fd413... offset=7395067 snapshot=10351
199518 session-restore: restored 1 window(s)
199519 session-restore: attached 2 pane(s); 0 live agent session(s) unattached
```

So this is the empty-rather-than-absent shape again (T302/T218 precedent): the
snapshot replay painted the panes, `attached N pane(s)` logged, and the LIVE
half (ongoing output stream + input forwarding) never functioned. Note the
skew in play at that moment: NEW app build (1cda2827c) + agent pid 35492
(build 20260806-8db5dc509, spawned minutes earlier by the OLD app during the
morning's destructive refresh) - and that same agent had ALSO been serving
the previous app instance's connection, which was killed HARD (taskkill) by
the upgrade script seconds before, with no clean DETACH. Likely lead: the
agent still holds the dead viewer's attachment/stream tap for those sessions
(a new ATTACH reports success but the live tap belongs to the corpse), or
the new connection's reader wired to a stale offset/stream state.

## Suspects (folded in from T529, 2026-08-09 triage — none verified)

- **App/agent build skew**: new app (1cda2827c, carries T524) against the older
  running agent (8db5dc509). The contract says additive-only, but this exact
  pairing froze. Check what changed on the agent wire between those two builds
  and whether HELLO negotiation covered it. (The 1.14.0 re-attach corruption
  precedent makes skew the first suspect.)
- **Replay-then-subscribe race**: snapshot applied (hence correct repaint) but
  the live output subscription / input channel never wired, or wired to a
  retired connection object.
- **Focus/foreground live-lock**: "non interactive" could be input never
  reaching the pane rather than a dead stream — though that shape was a
  two-window flip-flop and here one window restored per launch.

The same incident was written up twice, as T529 (first) and T532; T529 is now
`skipped(duplicate of T532)` and its repro recipe is the numbered timeline
above.

## Where to start

- Agent side: what happens when a viewer dies WITHOUT detaching and a new
  ATTACH arrives for the same session? Is the old tap cleaned up on pipe
  disconnect?
- App side: after `attach:` logs there is no proof the stream is LIVE.
  Consider a post-attach liveness check (stream-position advance, or a PTY
  echo probe) that logs loudly when the attach is a zombie.
- Reproduce: kill the app hard (taskkill - the upgrade script's exact kill),
  relaunch, then probe interactivity via `+send-keys` + `+read` delta - an
  acceptance arm that types into a restored pane and asserts output ADVANCES
  would have caught this.

## Evidence (2026-08-09, first investigation context)

**Ruled out — the agent cannot lose the tap to a corpse.** Both paths that
unbind a session are ownership-guarded and have been for months: `detachAll`
(`server.zig:490`, landed 2026-06-26) and `handleDetach` (`server.zig:1155`,
landed 2026-07-18) each refuse to clear a bridge whose `bridge_ctx` is not
their own connection. So a hard-killed viewer whose thread notices the
disconnect *after* the new app has already ATTACHed cannot tear the new
binding down. `handleAttach` rebinds unconditionally (`bindLocked`, line 976).

**Did not reproduce at HEAD, on either re-attach path.** Both acceptance
scripts kill the app with `Stop-Process -Force` — the same TerminateProcess
shape the upgrade script uses — and relaunch against the surviving agent:

- `session-reattach.ps1` section F: full-ring re-attach, 3 sessions, 2 windows.
- `session-snapshot-reattach.ps1` section C: the **WP-D3 delta path**, which is
  the path the incident took (`offset=43394044 snapshot=14382` — nonzero offset
  with a grid snapshot).

Both restore LIVE. See the arms below.

**Still untested — the conditions the incident actually had.** The harness
cannot yet create any of these, and each is a real difference:

1. **Sessions hours into their rings** (43 MB and 7.4 MB of ring offset). The
   test's sessions are seconds old.
2. **A TUI on the alternate screen.** The incident's panes were almost
   certainly Claude Code; an alt-screen session takes the `skip_replay` branch
   in `handleAttach` (line 1031), where the raw replay is suppressed and the
   snapshot stands alone. The test's panes are cmd.exe on the primary screen,
   so that branch never runs.
3. **App/agent build skew** — the agent was one delivery older than the app.
4. **~17 seconds with no viewer** between the kill and the relaunch.

Variable 2 is the sharpest hypothesis: it is genuinely different code, and it
is the one branch of the attach path that no test exercises.

## Root cause (2026-08-09, second investigation context) — FOUND

Variables 2 and 3 were run down and **eliminated**, and the answer turned out
to be hiding inside variable 1.

- **Alternate screen (2): eliminated by test.**
  `test/win32/session-reattach-zombie.ps1` A–C drives a `-e` fixture that
  enters the alternate screen (proven, not assumed: the manifest snapshot
  carries `?1049h`, which the formatter emits only for a differing mode), so
  the agent's `skip_replay` branch finally runs. Hard-kill + relaunch restores
  **live**.
- **Build skew (3): eliminated by diff.** `git diff --name-only
  8db5dc509..1cda2827c` touches nothing under `src/remote/`, `src/termio/`,
  `src/Surface.zig` or the win32 session path — the only session-related file
  in the range is a test script. The skew was real; the attach and streaming
  code on both sides of it was byte-identical.

**What it actually was: a resume point recorded against a byte stream that no
longer exists.**

On ATTACH the client arms the §7.3 resync watermark from the offset its own
manifest recorded — `discard_below = last_byte_offset - 1` — and never compared
it against the agent's stream head, which the `ATTACHED` reply has been
carrying all along as `snapshot_at_offset`. A session **id** outlives its byte
**stream**: an agent restart relaunches the session under the same id with a
fresh stream at 0, so a manifest written before that restart records an offset
into a stream nobody has any more. The incident's numbers say exactly that —
`offset=43394044` against an agent process spawned minutes earlier.

Arming that watermark makes `routeInboundData` drop every chunk forever
(`chunk_end <= keep_from`), `resync_active` never disarms, and the agent's own
grid snapshot is discarded along with all live output. Meanwhile the pane still
PAINTS, because the viewer replays its own persisted snapshot locally, and
input still reaches the child, which keeps working. Every log line reports
success. That is the report word for word: *"the windows seemed to repaint
correctly but were non interactive, not painting, but seemed to still be
working."*

**Fix — one rule: a client's resume point can never be ahead of the agent's
stream head.** `Connection.resumeOffset(last_byte_offset, agent_head)` clamps to
the head; `attachChannelCancellable` arms the watermark from the clamped value
and reports it as `AttachOutcome.resume_offset`; `termio.Remote` rebases its own
`attach_offset` onto it and `log.warn`s. The rebase is not bookkeeping — without
it `appliedOffset()` and the manifest entry written from it stay in the phantom
future and the *next* restore freezes too. A head of 0 never clamps (ambiguous
between "produced nothing" and "peer too old to report one"; a wrong clamp there
would trade a freeze for a double-paint). All of it is shared core, so **both
platforms get the fix**.

**And the writer half, found while fixing the reader.** `termio.Remote` never
reset `attach_offset` on the three paths that begin a BRAND-NEW byte stream at
0 — a `notify`-policy fresh shell, an `auto` RELAUNCH, and a prompt-deferred
relaunch. `Connection` already arms those panes with `discard_below = 0`
("a relaunch is a FRESH stream"), but `appliedOffset() = attach_offset +
applied_bytes` kept counting from the DEAD stream's base, so the next manifest
write recorded a resume point into a stream that no longer existed. That is how
a 43 MB offset against a minutes-old agent comes to be on disk in the first
place. Both halves are now closed: nothing writes such a record, and nothing
trusts one if it finds it. The reset sits after the three blocks that read
`attach_offset` (each already excludes these paths) and before the first drain.
