# T729 - Cover the viewer nav hover reveal and the TOC accent pill on the test desktop (both became reachable in T215)

## In plain terms

Two bits of viewer chrome only started working on the hidden desktop the tests
run on when T215 landed: the toolbar that slides in when you hover the top of
a viewer pane, and the highlighted row in a document's contents card painting
in the system accent colour rather than plain grey. Nothing checks either of
them there, so if one broke tomorrow the suite would stay green.

## Summary

T215 fixed four sites that read `GetForegroundWindow` and therefore answered
"no" forever on a background desktop. Two of the four are GUI behaviour with
no acceptance coverage at all, and their unreachability is precisely why:
before T215 no script running on the test desktop COULD have asserted them.

- **Nav hover reveal** (`ViewerPane.navHoverTick`). `in_pane` was pinned false,
  so the reveal never fired. It is drivable there now — the gate compares the
  desktop's own cursor position (`Set-TestCursorPos` / `Get-TestCursorPos` are
  in `lib\TestDesktop.ps1`) against the pane rect, and the bar is native GDI
  chrome, which `PrintWindow` captures.
- **TOC accent pill** (`ViewerTOCPanel.isEmphasized`). The selected row painted
  the unemphasized grey wash unconditionally; it now paints accent while the
  window is active. Also native chrome, so a pixel probe is the right oracle —
  and the emphasized/unemphasized pair is exactly the kind of assertion the
  T211 audit warned would be "fixed" by weakening it.

Do both in one script (a viewer window is the setup for each), and give each a
negative control: assert the reveal does NOT fire with the cursor outside the
pane, and that the pill is NOT accent when activation is on another window.

## Validation criteria

- [ ] A new (or extended) `test\win32\` script asserts the hover reveal fires
      on the test desktop, with a control that it does not fire off-pane
- [ ] The same script asserts the selection pill is accent while the window is
      active and unemphasized when activation moves away, by pixel probe
- [ ] `-NegativeControl` (or an equivalent inverted arm) FAILS
- [ ] ALL PASS x3
