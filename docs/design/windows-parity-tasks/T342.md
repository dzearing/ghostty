# T342 - chooser-restore-all.ps1 step 4 'Tab reaches the button again' is flaky

Found running T338 (2026-08-02), which extended this script's fixture but did
not touch its keyboard walk.

## The defect

`test\win32\chooser-restore-all.ps1` step 4 re-opens the chooser after the
rebuild and Tabs to **Restore All** again. That walk is deliberately a POSITIVE
CONTROL: the assertions after it prove that pressing the button rebuilds
NOTHING, and "nothing happened" is equally consistent with the keys never
arriving (the T240 lesson). A control that fails intermittently is worse than no
control - it trains a turn to re-run until green, which is precisely what T258
objects to.

Observed back to back on the same binary, same box:

```
run 1:  FAIL Tab reaches the button again (the positive control)   (35 passed)
run 2:  PASS Tab reaches the button again (the positive control)   ALL PASS (36)
```

Every other assertion in step 4 passed in BOTH runs, including "the window
already on screen is skipped" - so the Return that follows still landed
(`Send-TestKeys` aims at the button directly and SetFocus()es it), and only the
Tab walk that precedes it was unreliable.

## What was measured (2026-08-21)

The walk moved into `test\win32\lib\ChooserControls.ps1` as
`Focus-ChooserControl` - ONE copy where `chooser-restore-all.ps1`,
`-remote.ps1` and `-adopt.ps1` each kept a byte-identical private one - and it
now prints a per-step trail: the control focus landed on, how long the move
took, and whether the 300ms sample the old copies read would have got it
wrong. Six runs of `chooser-restore-all.ps1` on the same binary reproduced a
failure on the fifth, and the trail named it:

```
focus walk: filter -> list@0.3s (LOST: tab 1 moved focus OUT of the chooser
onto 'list' - something else took the app's focus mid-walk)
```

So focus after tab 1 was on a window carrying `LIST_ID`, which the walk's
membership check said was not one of the chooser's. Only a chooser owns that
id, and the relaunched app's own stderr - the one step 4 drives - shows exactly
ONE chooser opened in each of the fourteen runs checked (`chooser roster: sort
loaded` appears once per log), so the window can only have been that chooser's
own list: the single
`EnumChildWindows` sweep the walk had taken did not have it. A snapshot of a
dialog that is still settling is not evidence of absence, so a hwnd the set
does not know is now re-swept before it is called an escape.

The three transient states the old copies could not tell from defects, all now
polled through rather than sampled: focus still on the previous control at
300ms, focus momentarily 0 between two controls, and a control the first sweep
missed. What remains a hard failure - and says so with the class and handle of
whatever holds focus - is a genuine move out of the dialog.

## What was suspected before, and was NOT known

`Focus-RestoreAll` re-aims each Tab at whatever currently holds focus and gives
up after 6 steps, returning false if `Get-TestFocusedWindow` ever reads 0. Step
4 is the one place it runs with several windows on the desktop (the rebuild has
just created two more), so the plausible causes are a focus read taken while the
chooser is not yet the active window, or a Tab posted before the newly opened
chooser has settled its focus. **Neither is verified.** Do not fix by widening
the step budget or sleeping longer until the actual failing step is known -
instrument the walk (log the focused HWND's class/title per step, as T335 did
when it found the SetFocus trap) and make the oracle say WHICH step lost it.

## In plain terms

Nobody using Ghoztty sees this one - it is a test that lies. One of the checks
that proves the "Restore All" button works drives the dialog by keyboard, the
way a person would: press Tab until the button is highlighted, then press
Enter. Every so often the Tab part gave up, the check went red, and the run
said nothing about why - so the honest response was to run it again and hope,
which is how a test stops being evidence. When this lands the walk says which
Tab lost the highlight and what took it, so a red run is a fact to read
instead of a coin to re-flip.
