# T557 - The tab tooltip's dark theme is decided at creation and never re-evaluated on a mid-session theme flip

## In plain terms

Hovering a tab shows a little tooltip with the tab's folder. If you switch
Windows between light and dark mode while the app is open, that tooltip
keeps its old colors — a bright white box in an otherwise dark app (or the
reverse) — until you open a brand-new window. After this lands, the very
next tooltip you hover up already matches the new theme.

## Goals

- [x] Flipping the OS light/dark theme mid-session re-themes the next
      tooltip shown in an existing window
- [x] Changing `window-theme` in the config (reload) does the same
- [x] The swap is invisible: no leaked control, hover behavior unchanged

## Summary

Follow-up to T447. `Window.tabTipEnsure` decides the tooltip's dark theme
(`SetWindowTheme "DarkMode_Explorer"`) once, at control creation, from
`DarkMode.modeForTheme` + `systemUsesLightTheme()`. A config reload or an OS
apps-theme flip afterwards leaves an existing tooltip in the old scheme
until a new window is opened. Smallest honest fix: destroy the tooltip
control on `WM_SETTINGCHANGE` / config reload (it lazily recreates with the
fresh answer); the dialogs take the same latitude today, so consider
sweeping them in one pass if a shared helper falls out.
