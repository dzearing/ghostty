# T406 - A GUI launch command (-e / --command) is swallowed when session restore rebuilds the previous windows

## In plain terms

If you tell Ghoztty to start and immediately run something — `ghoztty -e npm
test` — and you also had terminal windows open the last time you used it, the
old windows come back and your command never runs. Nothing says it was ignored:
no window, no error message, no entry in the log. Because Ghoztty restores your
windows by default, this is what happens nearly every time; the command only
works on a truly clean start, which makes it look intermittent.

After this change you get both: your old windows come back, and the window you
asked for opens with your command running in it, in front.

## Goals

- [x] Decide what the behaviour SHOULD be, and write down why
- [x] A launch command opens its own window even when restore rebuilds windows
- [x] The requested window — not a restored pane — is the one that runs the
      command
- [x] The requested window ends up in front of the restored ones
- [x] An acceptance section that FAILS without the fix
- [x] The rule documented in CLAUDE.md, since it is not discoverable

## Summary

With T104 landed, `ghoztty -e <cmd…>` runs its command in the first window — but
only when there is nothing to restore. When the app starts with a
`session-layout-debug.json` / `session-layout.json` to re-attach, launch-time
restore rebuilds the previous windows and the pane that was asked for on the
command line never appears: the user gets their old panes and no sign that the
`-e` was seen at all.

`initial-command` is consumed by the FIRST core surface created (`app.first` in
`Surface.init`), and on a restoring launch that surface is a RESTORED pane, which
carries its own IPC overrides and re-attaches to a live session. The requested
command has nowhere to go.

## Evidence (2026-08-03, found while validating T104)

Reproduced twice by accident before it was understood, which is what makes it
worth a task — it looks exactly like "the fix does not work":

1. Launch `ghoztty.exe "--command=ping -n 30 127.0.0.1"` with a clean state ⇒
   the pane runs ping. ✓
2. Kill the app (leaving `session-layout-debug.json` and the agent's sessions),
   launch the same command line again ⇒ the restored pane comes back on a plain
   shell, ping is nowhere, exit code 0, nothing logged.

`test/win32/gui-launch-command.ps1` does not see this because it is hermetic
(per-run `$env:LOCALAPPDATA`), which is deliberate for T104 — the restore
interaction is this task's subject, not that one's.

## Open question: what SHOULD it do? — ANSWERED (2026-08-04, D15)

The T240 rule says answer from the Mac side first, with a cite. **The Mac side
cannot answer it: it has the same defect**, so there was no precedent to cite
and the call was made here and filed as decision **D15**.

The Mac evidence (read, not run — the Mac half is filed as **T488**):

- `AppDelegate.applicationDidBecomeActive` opens the initial window only when
  `TerminalController.all.isEmpty && derivedConfig.initialWindow && !hasPendingIpc
  && !hasPendingSessionRestore` (`macos/Sources/App/macOS/AppDelegate.swift`).
- `SessionLayoutRestore.sessionLayoutRestoreFinished()` opens one only if the
  restore ended with **zero** windows on screen.

So on a restoring launch macOS opens no requested window either, and the shared
core rule hands `initial-command` to a restored pane.

**Decided: do both.** Restore rebuilds what the user left behind AND the
requested window opens. It is the only option that drops nothing the user asked
for — the command was typed just now, and the restored windows are real work.
"Command wins, skip restore" loses the windows for that launch with no
explanation; "document today's behavior" leaves a silent drop, and
undiscoverable IS the defect.

## The fix

`src/apprt/win32/App.zig`, `run()` — the whole change is an ORDERING one:

```zig
const launch_command = self.config.@"initial-command" != null;
var startup_window: ?*Window = null;
if (launch_command) startup_window = try self.createWindow(.{});
const restored = self.restoreSessionLayout();
if (startup_window == null and !restored) startup_window = try self.createWindow(.{});
if (launch_command and restored) { ...SetForegroundWindow(startup_window)... }
```

Creating the requested window **before** restore is not cosmetic. Core
`Surface.init` gives `initial-command` to whichever surface is `app.first`
(`src/Surface.zig`), and every surface clears the flag on the way out — so if
restore goes first, a restored pane consumes the command and has nowhere to run
it: it ATTACHes to a session that already exists. Going first means the pane the
user asked for is the one `app.first` names, which is the mechanism the core
already has rather than a second command-injection path bolted alongside it.

Restore's windows are created after and land on top, so the requested window is
raised at the end. No core change; nothing in the non-restoring path moves.

## Validation (2026-08-04, on the box)

- `test/win32/gui-launch-command.ps1` — **ALL PASS** (sections A–C unchanged,
  new section D). D seeds a session on a plain launch, kills the **app only**
  (the agent keeps the PTY alive — a quit/crash, exactly the state that
  reproduces this), then relaunches the same state dir with `-e <marker> omega
  psi`:
  - **D5** some pane's scrollback shows `T104ARGS=[omega][psi][]` — the command
    ran.
  - **D6** there are >= 2 windows — restore also happened, so D5 is not passing
    because restore quietly did nothing.
  - **D7** the seed pane came back under its own stable pane id.
- **Negative control** (the reason to trust it): with `launch_command` forced to
  `false` and rebuilt, **D5 and D6 FAIL** and D7 still passes — i.e. the pre-fix
  build restores the window and silently drops the command, precisely as
  reported, and the section sees it.
- Floor: `zig build test -Dapp-runtime=none`, `-Dapp-runtime=win32`,
  `zig build test-agent` (via `scripts\floor-lane.ps1 -Lane all`), P1–P3.
