# T875 - mac: HookComponent treats an unreadable-but-present settings.json as absent and installs a fresh file over it - adopt the win32 typed refusal

## In plain terms

When Ghoztty on the Mac sets up Claude Code hooks, it merges its entries
into your existing settings file. If that file exists but momentarily
cannot be read, the Mac code assumes it is empty and writes a fresh file
containing only Ghoztty's hooks — your own settings are gone. Windows
refuses to touch the file in that situation; the Mac should too.

## Summary

Found while porting T868. Mac's `HookComponent.readJSON()` does:

```swift
guard let data = fileManager.contents(atPath: fileURL.path), !data.isEmpty else { return [:] }
```

`fileManager.contents` returns nil for BOTH "absent" and "present but
unreadable" (permission denied, transient lock). The absent case is the
intended fresh-install path; the unreadable case then flows into
`merge(into: [:])` + `writeJSON`, replacing the user's real
`~/.claude/settings.json` with only Ghoztty's hooks block. The one-time
`.ghoztty.bak` copy is best-effort (`try?`) and typically fails for the
same reason the read did, so nothing is recoverable.

The win32 port (`src/apprt/win32/HookComponent.zig`, `readSettings`)
distinguishes the cases: `FileNotFound` → empty base; any other read error
→ `error.UnparseableConfig` (typed refusal, state reports `outdated`, file
untouched). Adopt the same distinction on the Mac: only a genuinely absent
file returns the empty base; a present-but-unreadable one throws
`HookComponentError.unparseableConfig` (or a dedicated case).

## Validation criteria

- [ ] A `.claude/settings.json` with permissions `000` (present,
      unreadable): `install()` throws, `state()` is not `.notInstalled`,
      and the file's bytes are unchanged afterwards (Mac unit test).
- [ ] An absent settings.json still installs cleanly from an empty base
      (existing `claudeEmptySettingsInstallsCleanly` stays green).
- [ ] Mac test suite green.
