# T467 - Audit every win32 window class for a missing CS_HREDRAW/CS_VREDRAW where the painted content depends on the window size

## In plain terms

Some of Ghoztty's little floating panels on Windows can be left showing an
old picture of themselves after a resize — the scrollbar thumb the wrong
length, a popup drawn to the width it used to be — until something else
happens to make them redraw. T456 fixed one of these (the pane banner);
this is checking whether any of the others have the same problem, because
they were all built from the same template.

## Goals

- [ ] Every registered win32 window class is listed with its class style and
      a one-line verdict: does its painted content depend on the window size?
- [ ] Every class that answers yes carries `CS_HREDRAW | CS_VREDRAW`
- [ ] Each fix has a test with a confirmed negative control
- [ ] The rule is written down where the next window class will be added

## Details

T456 found `BannerOverlay` registered with `.style = 0`. Measured consequence:
a `SetWindowPos` that changes the window's SIZE invalidates **nothing** —
`GetUpdateRect` returns 0 after a 40px widen — so the card kept the geometry
it was last painted at while the band around it moved with a divider drag.

`.style = 0` is only safe when a partial repaint is indistinguishable from a
full one. That is true of a flat fill (`DimOverlay`) and false of anything
whose layout is derived from its own bounds.

Known suspects, none yet confirmed:

- **`Scrollbar`** (`Scrollbar.zig:658`, `.style = 0`) — the thumb's rect comes
  from `thumbRect(total, offset, len, h, min_h)`, i.e. it is a function of the
  track height. A pane resize should therefore restyle it, and today
  invalidates nothing. Probably masked in practice because scrolling repaints
  it anyway, which makes the stale window short rather than absent.
- **`ActivityMonitor`** (`ActivityMonitor.zig`) — owner-painted list, and it
  already returns 1 from `WM_ERASEBKGND` ("WM_PAINT covers the whole client"),
  which is exactly the pairing that goes wrong when the paint is never asked
  for.
- **`ViewerPane`**, the dialog classes (`BannerDialog`, `ConfirmDialog`,
  `RenameDialog`, `NewProcessDialog`, `HostSettingsDialog`, `MachineChooser`).

The audit is the deliverable, not just the fixes: a class that legitimately
does not need the style should say so, so this is not re-derived a third time.

## Validation

- Per fixed class, a win32-lane unit test in the shape of `banner class: a
  resize invalidates the whole card, not the exposed strip`
  (`BannerOverlay.zig`): create a real window of the class, resize it, assert
  `GetUpdateRect` covers the full client.
- **The test window must be on-screen at layered alpha 0.** Parked off every
  monitor it has an empty visible region, Windows invalidates nothing, and the
  test passes for the wrong reason (measured in T456).
- Every such test needs its negative control run once, since a test that
  asserts "the update region is the whole client" also passes when the update
  region is the whole client for an unrelated reason.
