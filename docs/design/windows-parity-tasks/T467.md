# T467 - Audit every win32 window class for a missing CS_HREDRAW/CS_VREDRAW where the painted content depends on the window size

## In plain terms

Some of Ghoztty's little floating panels on Windows can be left showing an
old picture of themselves after a resize — the scrollbar thumb the wrong
length, a popup drawn to the width it used to be — until something else
happens to make them redraw. T456 fixed one of these (the pane banner);
this is checking whether any of the others have the same problem, because
they were all built from the same template.

## Goals

- [x] Every registered win32 window class is listed with its class style and
      a one-line verdict: does its painted content depend on the window size?
- [x] Every class that answers yes carries `CS_HREDRAW | CS_VREDRAW`
- [x] Each fix has a test with a confirmed negative control
- [x] The rule is written down where the next window class will be added

## What the audit found

24 `RegisterClassExW` sites: 20 classes in the win32 app, the agent's
never-shown tray window, and 3 test-only parents in `ViewerPane.zig`. The full
table lives
in `docs/design/win32-design-system.md` §5c — it is the deliverable, so it sits
where the next window class will be added rather than in this file.

**Four classes answered yes and lacked the style**, all with the same shape as
T456's banner: an owner-painted window laid out against its own bounds, that
also returns 1 from `WM_ERASEBKGND` (so the stale pixels are not even erased).

- `ActivityMonitor` — the one panel the USER resizes by dragging its frame, and
  every element of it is measured from the client rect `layout()` reads back.
  `WM_SIZE` only re-places the child controls, so the owner-painted table's
  repaint was entirely the class's job and the class was not doing it.
- `GhozttyViewerNav` — right-anchored buttons, address field spanning the rest.
- `GhozttyViewerFeedback` — pill, image carousel and send row placed from width.
- `GhozttyViewerTOC` — rounded card against its own bounds. This one survived in
  practice, but for an accidental reason: `place()` calls
  `SetWindowRgn(.., TRUE)` right after its `MoveWindow`, and that redraws. A
  side effect is not a contract — the gutter branch passes a null region.

**Three suspects answered no, against the filed suspicion.** `Scrollbar`,
`KeyStateIndicator` and `ReadonlyBadge` never receive `WM_PAINT` at all: they
are `WS_EX_LAYERED` windows painted by `UpdateLayeredWindow`, i.e. push-model,
where the class style is inert. What matters for them is that every resize path
calls `repaint()` — `repositionAndResize` and the two `update` paths all do.
The task's note that the scrollbar thumb "is a function of the track height"
is right and its conclusion is not: it is repainted, just not by invalidation.

The rest are no for stated reasons: `DimOverlay` is a flat fill; the top-level
`Window` invalidates its caption band and tab strip by hand and deliberately;
the terminal surface is redrawn whole by the renderer; the dialogs are
fixed-size `WS_POPUP` windows that never resize; the message-only and tray
windows are never painted.

One latent case is named in §5c rather than fixed, and filed as **T819**: the
command palette and search popups ride the terminal's own class, so they cannot
take the style without giving it to every terminal surface.

## Validation criteria

- [x] Every registered class enumerated with style + verdict — 24 sites, table
      in `docs/design/win32-design-system.md` §5c
- [x] Each of the four fixed classes has a class-level test that resizes a real
      window and asserts `GetUpdateRect` covers the whole client — one per file,
      all via `class_redraw.expectResizeInvalidatesWholeClient`
- [x] Width and height asserted SEPARATELY, so a class carrying only one style
      bit cannot pass (`class_redraw.Axis`)
- [x] Confirmed negative control, measured not assumed: with `ActivityMonitor`
      rebuilt at `.style = 0` the win32 lane reports
      `width resize invalidated 40x200 of a 440x200 client` and the test FAILS;
      restored, it passes
- [x] A permanent negative control, so this stays confirmed: `class_redraw.zig`
      registers its own positive and negative control classes, identical but for
      the style bits, and asserts the exact strip geometry the unstyled one
      leaves (40x200 on a widen, 400x40 on a heighten)
- [x] The test window is on-screen at layered alpha 0 (T456's trap: parked
      off-monitor it has an empty visible region and passes for the wrong reason)
- [x] Floor: `zig build test` both lanes + `test-agent` via
      `scripts\floor-lane.ps1 -Lane all`, plus P1-P3

## Details

T456 found `BannerOverlay` registered with `.style = 0`. Measured consequence:
a `SetWindowPos` that changes the window's SIZE invalidates **nothing** —
`GetUpdateRect` returns 0 after a 40px widen — so the card kept the geometry
it was last painted at while the band around it moved with a divider drag.

`.style = 0` is only safe when a partial repaint is indistinguishable from a
full one. That is true of a flat fill (`DimOverlay`) and false of anything
whose layout is derived from its own bounds.

Known suspects, none yet confirmed:

- **`Scrollbar`** (`Scrollbar.zig:658`, `.style = 0`) — the thumb's rect comes
  from `thumbRect(total, offset, len, h, min_h)`, i.e. it is a function of the
  track height. A pane resize should therefore restyle it, and today
  invalidates nothing. Probably masked in practice because scrolling repaints
  it anyway, which makes the stale window short rather than absent.
- **`ActivityMonitor`** (`ActivityMonitor.zig`) — owner-painted list, and it
  already returns 1 from `WM_ERASEBKGND` ("WM_PAINT covers the whole client"),
  which is exactly the pairing that goes wrong when the paint is never asked
  for.
- **`ViewerPane`**, the dialog classes (`BannerDialog`, `ConfirmDialog`,
  `RenameDialog`, `NewProcessDialog`, `HostSettingsDialog`, `MachineChooser`).

The audit is the deliverable, not just the fixes: a class that legitimately
does not need the style should say so, so this is not re-derived a third time.

## Validation

- Per fixed class, a win32-lane unit test in the shape of `banner class: a
  resize invalidates the whole card, not the exposed strip`
  (`BannerOverlay.zig`): create a real window of the class, resize it, assert
  `GetUpdateRect` covers the full client.
- **The test window must be on-screen at layered alpha 0.** Parked off every
  monitor it has an empty visible region, Windows invalidates nothing, and the
  test passes for the wrong reason (measured in T456).
- Every such test needs its negative control run once, since a test that
  asserts "the update region is the whole client" also passes when the update
  region is the whole client for an unrelated reason.
