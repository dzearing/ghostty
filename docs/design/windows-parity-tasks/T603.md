# T603 - Ctrl+W over the Windows machine chooser closes the window behind it instead of the dialog

## In plain terms

You open the machine chooser, change your mind, and press Ctrl+W to dismiss it -
and the terminal window underneath closes instead. The Mac had this exact bug
and fixed it. Verify whether Windows has it; a close chord that hits the wrong
window can take a pane full of work with it.

## Summary

Upstream: `11fe14bc3` "fix(chooser): Cmd-W over the machine chooser closed the
window behind it".

**Reproduce first.** The win32 chooser may already route the chord correctly (it
is a separate HWND with its own message loop, unlike the Mac sheet). If it does,
close this as `skipped(not reproducible on win32: ...)` with the evidence and add
a regression arm anyway - the failure mode is expensive enough to be worth a
test even where it does not currently occur.

## Goals

- [x] Reproduce (or rule out) the Mac failure on win32, with evidence.
- [x] Ctrl+W over the chooser dismisses the chooser.
- [x] A regression arm that discriminates in both directions.

## What was measured

**The Mac bug does not reproduce on win32.** Built the app with the fix
disabled and ran the new script's `-NegativeControl` arm against it: ALL PASS —
Ctrl+W over the chooser did *nothing at all*, and the window behind it kept
every pane (`1 -> 1`) while the positive control in the same run closed a pane
with the same chord delivered the same way. Three things make the Mac failure
unreachable here: the chord arrives as a plain `WM_KEYDOWN` at whichever chooser
control holds the keyboard, the owner window is `EnableWindow(0)` for as long as
the chooser is up, and only a `Surface`'s own WndProc turns a key into a
binding — there is no responder chain to walk on into.

**So the fix is the other half of parity, not a crash fix.** Before it, Ctrl+W
over the chooser did nothing; Mac's Cmd-W dismisses the dialog. `handleKey` now
cancels on ctrl+w (and ctrl+shift+w — same verb), routing to the one teardown
path Escape and the close button already use. Alt must be UP, because AltGr
reports as ctrl+alt and an AltGr+W that types a character on someone's layout
still has to reach the filter EDIT.

## Validation criteria

- [x] Ctrl+W with the chooser focused dismisses the chooser and leaves every

- [x] Ctrl+W with a terminal focused still closes the pane/tab as before —
