# T1022 - Starting Ghoztty again should open a window in the copy already running, not a second app (D79's answer)

## In plain terms

Right now, starting Ghoztty when it is already running gives you a second,
separate app: two tray icons, two apps quietly sharing one session list and one
saved layout, and closing "Ghoztty" only closes half your terminals. The user
was asked about this (D79) and chose the other behavior: starting it again
should just open another window in the app you already have, the way it works
on a Mac and the way Windows Terminal behaves. This task builds that.

## Summary

T851 fixed the theft — a second launch no longer takes the first app's
terminals away and freezes them — but deliberately left the two copies
independent, and filed D79 for the wider call. The user answered on
2026-08-19 with option **o1**: *"Starting Ghoztty again opens a new window in
the app you already have (Recommended)"*. The answer was folded into T851,
which was already `done`, so no open task carries it. That is the gap this
file closes.

What the answer requires:

- A **single-instance handoff on launch**: a second launch of the same build
  finds the running instance, asks it to open a window (honouring the launch's
  own arguments — working directory, `--command`, session/restore flags), and
  exits without creating a second app, tray icon, or session-manager client.
- **Same-build only**, which is the mitigation the chosen option carries
  verbatim: two *different* builds must still start independently, because
  side-by-side testing of a debug `zig-out` build against the installed
  release is how this project is developed. The instance identity therefore
  has to key on the same lineage the IPC/agent endpoints already derive
  (build mode + install lineage), not on "an exe named ghoztty.exe is
  running".
- **The shortcut-looks-wrong case**, named as a con on the chosen option: a
  shortcut pointing at the portable copy will open a window from whichever
  same-build copy is already running. Whatever the app does here, it should
  not be silent about it.

Where it lives: the launch path in `src/apprt/win32/` that already resolves the
per-user IPC endpoint, plus the restore/attach gate T851 added.

## Goals

- [ ] A second launch of the SAME build opens a window in the running instance
      and exits, with no second tray icon and no second session-manager client
- [ ] The second launch's arguments (cwd, command, target flags) are honoured
      by the window that opens
- [ ] A launch of a DIFFERENT build still starts its own independent app
- [ ] An acceptance script in `test/win32/` covers both arms, with a
      `guard-due` row so it cannot drift

## Validation criteria

- [ ] Launch the debug build twice: the second invocation exits, one process
      remains, and a new window appears in the first (measured by `+list --json`
      instance/window counts, not by eye)
- [ ] With the debug build running, launch the installed release: two
      independent apps, both usable — the side-by-side development case
- [ ] `+list --json` shows a single instance across both launches in the
      same-build arm
- [ ] Floor lanes and P1–P3 stay green; the new acceptance script is ALL PASS
      and stamped
