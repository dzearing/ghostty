# T222 - Cover the VK_PACKET TranslateMessage exemption without SendInput

## In plain terms

Screen readers, on-screen keyboards and automation tools type into a window by
injecting characters rather than pressing keys. Ghoztty has a rule that lets
those characters through, and the rule sat in two hand-written `if`s that no
automated run could reach — the injection they exist for cannot be delivered to
a test. A future edit could have deleted either one and every test would still
have passed, with the first person to notice being someone using a screen
reader. The rule now lives in one place with tests around it, so breaking it
fails a build instead of failing a user.

## Goals

- [x] The TranslateMessage exemption is a pure function, asserted in the unit lane
- [x] The key handler's half of the same rule is asserted the same way
- [x] The literals cannot drift from the real Windows constants
- [x] Deliberately breaking the exemption turns the lane red

## Summary

Migrating `kb-actions.ps1` onto the test desktop (T217 batch 4) narrowed the
T64 coverage, and this is the residue.

T64's product path has three parts:

1. `App.run` exempts `VK_PACKET` from its TranslateMessage skip
   (`src/apprt/win32/App.zig`, the `WM_KEYDOWN` arm of `skip_translate`) -
   TranslateMessage is the only thing that turns the packet into a WM_CHAR.
2. `Surface.handleKeyEvent` sees `vk == VK_PACKET`, clears
   `key_event_produced_text`, and does NOT feed the packet to the terminal as
   a key (`src/apprt/win32/Surface.zig`).
3. `App.zig`'s `WM_CHAR` handler consumes the injected character - suppressing
   it when the preceding keydown already produced text, and re-encoding it as
   a synthetic win32-input sequence in mode 9001.

Part 3 is still covered on the test desktop (posted WM_CHAR). Parts 1 and 2
are **not**, because they need a real `SendInput(KEYEVENTF_UNICODE)`, which
win32 refuses off the input desktop (T207).

**The obvious workaround does not work, and this was measured, not assumed:**
posting `WM_KEYDOWN` with `wParam = VK_PACKET` and the character in the lParam
HIWORD is never translated - the character simply never arrives. (A real
packet carries its 16-bit character out of band; a posted lParam has only the
8-bit scan-code field.) A posted `WM_CHAR` to the same surface does arrive.
Recorded as "MECHANISM LIMIT - VK_PACKET" in `test/win32/lib/TestDesktop.ps1`
so it is not re-derived.

## Details

Proposed fix, cheapest first:

- **Unit-test the predicate.** Factor the `skip_translate` switch in
  `App.run` into a pure function over (message, wParam, class atom) and assert
  in the `-Dapp-runtime=win32` lane that `WM_KEYDOWN` + `VK_PACKET` (and
  `VK_PROCESSKEY`) return "translate", while an ordinary surface keydown
  returns "skip". That covers part 1 durably and with no desktop at all, and
  it is the part most likely to be broken by a future edit to that switch
  (it is a bare `if` inside a `blk:` today).
- **Part 2** can be covered the same way if `handleKeyEvent`'s VK_PACKET
  early-out is reachable from a test, or left to the interactive lane.
- **Interactive lane.** `kb-actions.ps1 -Interactive` still drives the real
  `SendInput(KEYEVENTF_UNICODE)` (`Send-TestInjectedChar` switches mechanism
  on `-Interactive`), so a by-hand run does exercise the full path. That is a
  fallback, not coverage: it steals focus and is never how a run is scored.

Do NOT "fix" this by relabelling the posted-WM_CHAR assertions as covering
the packet path - that is precisely the vacuous-assertion failure mode T216
and T217 batch 3 were about.

## What landed

`src/apprt/win32/translate_policy.zig` — pure, no OS import — holds all three
rules and the reasons for them:

- `isKeyMessage(message)`: the four raw key messages. The loop gates its
  `GetClassLongW` on this, so a class-atom syscall never runs for a mouse move
  or a timer tick; a unit test sweeps `0..0x1000` asserting `skipTranslate`
  answers false for everything this rejects, so the gate and the policy cannot
  diverge.
- `skipTranslate(message, wparam, class_atom, terminal_class_atom)`: part 1.
  `class_atom` 0 means "no HWND, or the class could not be read" — exactly what
  the old inline code treated as not-a-terminal.
- `keyDisposition(vk)` → `.key` / `.ime_pending` / `.injected_text`, with
  `dropsKey()` and `clearsProducedText()`: part 2. `Surface.handleKeyEvent` is
  now three lines that ask those two questions, so the "clear the flag for a
  packet, do NOT clear it for the IME" distinction is a tested claim rather
  than the order of two `if`s.

`App.zig` carries the drift guard (each literal vs the real `w32.*` constant,
plus `isKeyMessage` over the four real message ids) — the same shape
`viewer_accel.zig` uses, and the reason the literals are safe.

Not covered, deliberately: the real `SendInput(KEYEVENTF_UNICODE)` round trip,
which win32 refuses off the input desktop (T207). `kb-actions.ps1 -Interactive`
still drives it by hand; that remains a fallback, not coverage.
