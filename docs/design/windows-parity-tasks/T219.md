# T219 - Audit acceptance scripts for SKIP branches that hide un-run assertions

## In plain terms

Our on-box test scripts are allowed to skip a section when the machine cannot
run it - a shell that is not installed, no network, a build with the debug
logging compiled out. The problem was that skipping left no trace in the one
line the result is read from: the script still ended with "ALL PASS", so a
section that quietly stopped running looked exactly like a section that passed.
One test spent months asserting something that had been wrong since a redesign,
and every run said it was fine. After this, the last line says how many sections
were skipped, and a checker keeps every script honest about it.

## Goals

- [x] A mechanical rule, not a remembered one: an analyzer that finds scripts
      whose verdict line stays silent about skips
- [x] Convert the suite so the skip count rides the verdict line
- [x] An acceptance script that keeps it at zero, with its own teeth
- [x] The remaining scripts are a named, task-linked list that can only shrink

## Validation criteria

- [x] `test\win32\skip-visibility.ps1` is ALL PASS (run 3x) - analyzer fixtures,
      the suite sweep, and a live run whose last line carries the count
- [x] `-TeethCheck` turns section B red both ways (an unlisted violator, and a
      converted script still on the list)
- [x] A real script's skip count is measured on the wire, not asserted:
      `upgrade-resume-readiness.ps1 -PureOnly` ends `ALL PASS (2 SKIPPED)`
- [x] Every modified script still parses and still passes (parse check on all
      21; live runs of build-mode-guard, website-windows-download,
      upgrade-resume-readiness)
- [x] Standing floor green: both zig lanes, test-agent, P1-P3

## Summary

Found during T217 batch 1 (2026-07-31). `ipc-version.ps1` asserted the About
box is a `#32770` MessageBox. It has been a native `GhozttyConfirmDialog`
since the T50 chrome pass, so that assertion had been wrong for a long time -
and the script still reported ALL PASS, because its foreground grab kept
losing the race on a busy box and the whole palette section took its
`SKIP palette test: <reason>` branch instead. Migrating it onto the test
desktop made the chord land every time, and the stale assertion surfaced
immediately.

A `SKIP` that is reached routinely is indistinguishable from a passing test in
the summary line, so an assertion inside one can rot for months. The T217 and
T218 migrations fix this for the GUI scripts they touch (the injection they
skip on no longer fails), but the same pattern can exist in scripts outside
both lists, and in code paths that skip for other reasons - a missing debug
log, an absent optional dependency, a feature the config did not enable.

## Details

The work:

1. Enumerate every `SKIP` / `degraded` / "not attempted" branch across
   `test/win32/*.ps1` (grep for `SKIP`, `degraded`, and early `return`/
   `continue` around an assertion block).
2. For each, determine how often it is actually taken on this box. A branch
   that never fires is fine; a branch that fires routinely is a test that is
   not running.
3. For the routinely-taken ones, either remove the reason it skips (the T217
   answer: make the mechanism reliable) or make the skip LOUD - the run
   summary should say "N assertions SKIPPED", not just "ALL PASS".
4. Re-run each affected script and fix whatever stale assertion the newly
   executing section turns up. Expect more of these; `ipc-version` is
   unlikely to be the only one.

Note the summary lines themselves differ per script (`ALL PASS`,
`ALL PASS (N assertions)`, `T52 ACCEPTANCE: ALL PASS`). Whatever reporting
change lands should keep them greppable, since the loop reads the last line.

## Validation

- Every routinely-taken SKIP branch is either eliminated or reported in the
  script's summary line.
- Each script whose skipped section now runs is ALL PASS x3, with any stale
  assertion it surfaced fixed and recorded here.

## What landed

The audit's step 2 - "determine how often each branch is actually taken on this
box" - is not answerable by any reader, static or dynamic: a branch that fires
every run and one that has never fired look identical in the text, and running
80 GUI scripts enough times to sample them would still only describe THIS box on
THIS day. So the answer is the one that holds whenever a branch does fire: the
count rides the verdict line, and the loop's `| Select-Object -Last 1` sees it.

- `test\win32\lib\SkipAudit.ps1` - the analyzer. `unreported` (the script emits
  SKIP and no ALL PASS line names a count) and `uncounted` (a site the counter
  misses, which makes the printed number a lie that reads as audited). Exempt: a
  site that prints and immediately exits (it IS the last line), and a
  `# skip-audit:` marker.
- 21 scripts converted. Five of them already KEPT a count and printed it on the
  line above the verdict - invisible to the only reader there is.
- `test\win32\skip-visibility.ps1` - acceptance. A: 12 analyzer fixtures,
  including the three shapes a looser first draft reported (tracker fixture data
  `skipped(split -> T2)`, prose about a negative control, a `WARN ... skipped`)
  and the `-Host`-matched-as-an-operator bug that silently emptied the sweep to
  zero while looking like a tightening. B: the sweep, where `$SkipAuditPending`
  can only shrink - an entry that no longer violates fails the run exactly as an
  unlisted violator does. C: the rule on the wire.
- The three heavy scripts (overlay-zorder 14 sites, split-divider 11,
  pane-banner 6) are the pending list, filed as **T731**.

Measured, not asserted: `upgrade-resume-readiness.ps1 -PureOnly` ends
`ALL PASS (2 SKIPPED)`; `-TeethCheck` turns B1 and B2 red on demand; and B1 was
seen failing for real mid-task, on this script's own fixture text.
