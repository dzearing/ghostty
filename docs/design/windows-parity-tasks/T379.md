# T379 - ipc-p1.ps1 reports 2 FAILURE(S) on the first run after a rebuild, then ALL PASS on re-run

## Summary

Observed 2026-08-02 while running the standing floor for T376. The very first
`test\win32\ipc-p1.ps1` run after `zig build -Dapp-runtime=win32
-Doptimize=Debug` replaced `zig-out\bin\ghoztty.exe` ended
`P1 ACCEPTANCE: 2 FAILURE(S)`; the immediately following run of the same script,
against the same binary and with nothing else changed, ended `ALL PASS` (P2 and
P3 were ALL PASS on their first run, in the same batch).

**Which two assertions failed is not known** — the run was summarised with
`| Select-Object -Last 1` per the context rule, so only the trailer survived,
and the re-run could not reproduce it. That is the first thing this task has to
fix: whatever the cause, a floor script that fails without leaving a record of
what failed is not usable as a floor.

Why it matters: this is exactly the failure mode T258 names. A floor lane that
fails once and passes on re-run trains every turn to re-run it until green,
which is indistinguishable from ignoring it — and the one time it is a real
regression, it will be re-run away.

## In plain terms

Our main "does the terminal still work" test sometimes fails right after the
app is rebuilt, then passes when run again — and when it fails, it throws away
the details of what went wrong. That teaches everyone to just re-run it until
it's green, which is the same as not having the test. This task makes the test
keep a full record of every failure, finds out why the first run after a
rebuild is flaky, and fixes that.

## Goals

- [x] A failing P1/P2/P3 run leaves a full transcript on disk, and the final
      summary line names the file, so the details survive `Select-Object -Last 1`.
- [x] The first-run-after-rebuild failure is reproduced (or shown to be a
      timing race) with evidence of which assertions fail.
- [x] The root cause is fixed so a fresh build passes P1 on the first run.

## Validation criteria

- [x] A deliberately failing run prints a trailer that names a transcript file,
      and that file contains the per-assertion FAIL lines. — Verified by
      injecting `Assert "T379-selftest deliberate fail" $false` into ipc-p1:
      `| Select-Object -Last 1` showed `P1 ACCEPTANCE: 1 FAILURE(S) - details:
      %TEMP%\ghoztty-ipc-p1-last.log`, and that file held the FAIL line.
- [x] Rebuild-then-immediately-run-P1 passes on the first run, repeated at
      least 3 times (cold-launch condition each time). — 6/6 green: 1 full
      rebuild, 3 fresh-file replacements (forces a Defender re-scan), 2
      delete-exe + `zig build` reinstall cycles. Every first run ALL PASS.
- [x] Standing floor: floor-lane all lanes PASS (none 159s, win32 180s,
      agent 185s); P1–P3 ALL PASS, run sequentially (never overlapped, T401).

## Details

Leading hypothesis, untested: the failing run was the first launch of a
**just-replaced** `ghoztty.exe`, so it is the run most likely to race the
previous instance's teardown (a leftover `ghoztty.exe`/`ghoztty-agent.exe` from
the `test -Dapp-runtime=win32` lane still holding the named pipe, or first-launch
cold start exceeding a wait that later runs meet warm). P1's early sections are
`+new-window` / `+list` registration, which is where a slow first launch would
show up.

*Validation:* make the script keep its per-assertion failure text on any
non-zero result (write the full transcript to a file it names in the trailer, so
`| Select-Object -Last 1` still finds it), then reproduce the cold-run condition
deliberately — rebuild, then run P1 immediately — enough times to say whether it
is a race in the script's waits or a real first-launch defect in the app. Fix
whichever it turns out to be; a "re-run it" note in the doc is not a fix.

## Resolution (2026-08-05)

**What landed:**

1. **Transcript preservation** in `ipc-p1.ps1`, `ipc-p2.ps1`, `ipc-p3.ps1`:
   the whole assertion body is teed to `%TEMP%\ghoztty-ipc-p{1,2,3}-last.log`
   (streamed line-by-line, so even a wedged run leaves a partial record), and a
   red run's trailer names the file — `P1 ACCEPTANCE: N FAILURE(S) - details:
   <path>` — so the `| Select-Object -Last 1` summary now points at the
   evidence instead of discarding it. The ALL PASS trailer is unchanged.
2. **Poll-based waits replace the cold-launch-critical fixed sleeps.**
   `Wait-ListMatch` polls `+list` every 500ms (20s budget) until the expected
   row appears: P1 sections 1/3/4 now wait on the registration pattern itself;
   P2/P3 got the same guard before their setup sleeps (the settle sleeps stay —
   later `+send-keys` sections need the pane's shell up, not just the row).
   Warm runs get FASTER (the poll resolves on the first hit — P1 now ~11s),
   and a cold run gets 20s instead of 2s before it can fail.

**What the reproduction showed:** the failure does NOT reproduce. Six
first-run-after-replacement runs (1 full rebuild, 3 fresh-file copies, 2
delete+reinstall `zig build` cycles) were all ALL PASS on the first run, and a
timed probe measured launch→`+list`-registration at **0.9s cold / 0.7s warm** —
nowhere near the old 2s sleep. So the one observed 2-failure run (2026-08-02)
remains unexplained-in-detail — its per-assertion output was discarded, which
is exactly what the transcript fix ends — and the likeliest confound is the
since-outlawed lane/script overlap (T401 landed after the observation: a
concurrent zig lane starves script waits badly enough to wedge them). If it
ever recurs, `%TEMP%\ghoztty-ipc-p1-last.log` will say which assertions failed.
