# T616 - Cross-machine Restore All still dials its windows one after another

## In plain terms

Bringing another machine's windows back opens one connection per window, and it
opens them one at a time. Nothing freezes any more (T339 moved that work into
the background), but the wait still grows with the number of windows: six
windows on a slow link is six round trips of waiting before any of them appear.
Opening them together would make the wait roughly the same as for one window.

## Summary

`RestoreAllRelay.worker` (T339) dials the pull, then loops the decoded windows
dialing one transport each, SERIALLY. Off the GUI thread that is no longer a
freeze — the message loop pumps throughout, which is what T339 was for — but the
latency is still `(1 + N) x RTT` before the first window appears.

T339 deliberately did not also make them concurrent: the defect it was filed for
was *where* the dials happened, and one change at a time is what kept the
ownership rules checkable (D-T339, filed the same day). The per-window dials are
independent by construction — each window owns its own transport for life
(T336) — so they are a natural fan-out.

## Details

- The dials to parallelise are the LOOP's, not the pull's: the pull must land
  first, because its `GET_LAYOUTS` is what says how many windows there are.
- Ownership must survive a partial failure exactly as it does now: every dial a
  worker opens is either handed to a window by `App.adoptRestoreAll` or freed by
  `Job.destroy`. A fan-out has to keep that true when some threads fail and
  others succeed.
- Consider a bound (a small pool rather than N threads): a machine with 40
  windows should not open 40 simultaneous WebSocket upgrades at a relay that may
  rate-limit them.
- The fixture can measure this: `test/win32/lib/FakeRelay.ps1` gained
  `-SlowConnectFile` / `-SlowConnectMs` in T339, which defers each `/connect`
  answer without stalling the relay. With a 1500 ms delay, serial dialing of 2
  windows takes >= 4.5 s wall-clock and concurrent dialing ~3 s — a measurable
  difference, and it grows with N.

## Validation criteria

- [ ] With the slow-connect fixture armed, the wall clock from the keypress to
      `restore all: rebuilt N window(s)` is close to `2 x SlowMs`, not
      `(1 + N) x SlowMs` — asserted in `test/win32/chooser-restore-all-remote.ps1`
      rather than eyeballed.
- [ ] `chooser-restore-all-remote.ps1` stays ALL PASS, F (the 1+N connect count)
      included: concurrency must not change how many transports are opened.
- [ ] A dial that fails while its siblings succeed still costs exactly its own
      window, and leaks nothing (the failure arm of F/E).
- [ ] Both zig lanes and `test-agent` green.
