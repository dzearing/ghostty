# T1131 - A website or HTML page in a Windows viewer pane does not keep its address bar on screen

## In plain terms

When a viewer pane is showing a live page - a website or an HTML mock you are
iterating on - the address bar should stay visible so you can see where you are
and retype the URL without hunting for the chrome. On the Mac build it is now
pinned open for live pages. On Windows it still behaves like the document
viewers, where the bar hides itself.

## Summary

Main intake, 2026-08-22 (range `22c9c6d8a..origin/main`). Upstream commit
**5241d7bec** *"feat(viewer): pin the nav bar open for live pages"* changed
`macos/Sources/Features/Viewer/ViewerView.swift` (+63) so live-page viewers keep
their nav bar, with `ViewerChromeBarTests.swift` / `ViewerNavigationTests.swift`
as proof; it also updated `CLAUDE.md`'s viewer documentation.

The Windows half is in the win32 viewer chrome. The rule to carry across is
which viewer flavors count as "live" (website, local HTML with live reload) vs
which keep the auto-hiding bar (markdown, code, diff) - read the Swift diff and
the CLAUDE.md wording rather than guessing the split.

## Validation criteria

- [x] A `+split --view=<url>` pane shows its address bar without hovering.
      `test\win32\viewer-nav-pin.ps1` section B: a fresh website pane comes up
      with `GhozttyViewerNav` visible and 45px tall, with no cursor anywhere on
      the desktop (the test desktop cannot produce one). The address is
      deliberately one nothing answers - the pin follows the pane's MODE, which
      is decided from the location, so a page that fails to load is still a
      browser pane and still keeps its address field.
- [x] A local `.html` viewer pane behaves the same as a website pane.
      Section A of the same script, on a temp `.html` file.
- [x] Markdown / code / git-diff viewer panes keep their existing auto-hide
      behavior. Sections C and D measure a markdown and a code pane coming up
      with the bar HIDDEN (height 0); the diff arm is the win32-lane test
      `T1131: the pin follows where the pane IS ...`, which walks all five
      modes. A diff pane's own pin is Mac's and is T817's to carry, with the
      change/layout controls that are the reason it is worth pinning for.
- [x] The pinned bar is accounted for in the viewer's layout: content is not
      overlapped by it at any pane size. Two measurements: section A asserts the
      WebView2 child's top edge is at or below the bar's bottom on a real pane,
      and the win32-lane `host floor` test reads the live controller's own
      bounds back and asserts `top == Layout.bar_h` - the reserve and the paint
      from the same source. Width-independence is `viewer_nav_layout`'s
      `T1130:` tests, which walk every width at four scales.
- [x] An on-box acceptance script in `test/win32/` asserts the pinned/auto-hide
      split by flavor. `test\win32\viewer-nav-pin.ps1`: ALL PASS (15
      assertions); `-NegativeControl` inverts exactly the four flavor
      assertions and fails exactly four, so the split is what is being
      measured. Registered in `scripts\guard-due.ps1` as `viewer-nav-pin`.
- [x] Floor lanes green (`scripts\floor-lane.ps1 -Lane all`) plus P1-P3.
      `FLOOR SUMMARY: lib#1=PASS none#1=PASS win32#1=PASS agent#1=PASS`;
