# T1272 - Nothing stops a THIRD harness from arming the update applier at zig-out\bin

## Summary

T1268 fixed `update-apply.ps1` and T1271 fixed `update-failure-visible.ps1`:
both had armed the real update applier with `zig-out\bin\ghoztty.exe` as the
install directory, which hands a process whose job is to rename `ghoztty.exe`
aside the one binary the rest of the turn depends on. Both now use
`test\win32\lib\ApplierSandbox.ps1`. The two other scripts that set
`GHOZTTY_UPDATE_APPLY` (`update-graceful.ps1`, `update-real-msi.ps1`) already
point at a throwaway product install directory, so the suite is clean TODAY.

Nothing enforces it. The rule lives in two comments and a library nobody has to
use, which is exactly the shape the cleanslate audit's B2 ("no script carries a
private ghoztty kill") exists to close for the kill helpers. An audit assertion
- every `GHOZTTY_UPDATE_APPLY` spec's third field resolves to a scratch
directory, never the repo build - would make the third harness's mistake a red
test instead of a turn with no binary.

## In plain terms

Two tests were caught aiming the real updater at the freshly built app, which
can leave the machine with no app at all. Both are fixed, but nothing would
catch a third one written next month.
