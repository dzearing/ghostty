# T562 - reset-context types the continuation but Enter never submits it

## In plain terms

Every night the agent finishes a piece of work, wipes its own memory, and types
its next instruction back to itself. Sometimes the instruction got typed and
never sent — so the whole thing sat there, waiting at a full text box, until
somebody came along in the morning and pressed Enter. Worse, the checks that
were supposed to catch that read "the instruction is on the screen" as proof it
had been sent, which is exactly what a box holding an unsent message looks
like. Now the machinery watches for the session actually *reacting*, and if the
screen sits frozen with the instruction still showing, it presses Enter itself —
up to three times — and says so out loud if that still does not work.

## Goals

- [x] Stop calling "the prompt is on screen" a successful submit — it is the
      symptom, not the proof
- [x] Press Enter again, bounded and logged, when the pane holds the prompt and
      will not move
- [x] Prove it against a staged pane that swallows the submit
- [x] Give the watchdog and the upgrade's resume path the same gate

## User report (2026-08-07, with screenshot)

"we are absolutely still having issues with /reset-context not pressing
enter. I saw that the go loop stopped because enter wasn't pressed."

Observed state of the loop pane this morning: fresh session after `/clear`
(ctx 0k), composer holding `read go.md and go` intact, never submitted.
Recovery was one manual `+send-keys --target=<pane> Enter` (done from the
interactive session; the loop resumed immediately and cleanly).

## What is already known about this failure family

- The TEXT arrives intact now (the old mojibake/keys-file path problems were
  fixed - [[reset-context-keysfile-msys]], T261's false-FAIL). The remaining
  defect is narrower: the trailing Enter does not SUBMIT.
- The delivery flow logs the same shape as `RESUME-REUSE FAIL` - three
  consecutive upgrade deliveries (08-04, 08-05, 08-06 in
  `%TEMP%\ghoztty-upgrade.log`) ended with the prompt typed but not
  submitted. Same symptom, possibly same root cause.
- `+send-keys "text" Enter` frames text as a bracketed paste and sends Enter
  BARE outside the frame precisely so the TUI reads it as a keypress
  (CLAUDE.md, T210). A single manual Enter afterwards submits fine - so
  either the Enter is never sent on the failing path, is sent while the
  composer is in a state that swallows it (mid-render after /clear?), or is
  sent as part of a combined write the TUI reads as paste-internal newline.

## Where to look

1. The reset-context helper script's send sequence (BOTH repos - the skill
   source and the active cache copy, per the standing patch rule): does it
   send Enter as a separate `+send-keys` call, with what delay, and gated on
   what? Claude Code repaints the composer after /clear; an Enter that lands
   during the repaint may be dropped by the TUI, not by Ghoztty.
2. Add the missing half of the arrival gate: today it verifies the TEXT
   arrived; it must verify SUBMISSION (composer empty + spinner/response
   started within N seconds) and re-send Enter until it does, bounded.
3. The watchdog: the loop sat dead at a full composer for hours -
   `ghoztty-go-loop-watchdog` should read "typed prompt sitting unsubmitted
   with idle session" as a wedge and press Enter itself. That is the
   backstop that turns this whole family from a lost night into a 60-second
   blip.

      first character — is filed on its own as T664.
- [x] The submission gate exists: `reset-context.sh` presses Enter again (up to
      3 times, each logged `UNSUBMITTED: … pressing Enter (attempt n/3)`) when
      the prompt is on screen and the pane will not move — G1/G2, and H proves
      the press is load-bearing by cutting it out and staying wedged.
- [x] The watchdog detects composer-full+idle and recovers: it wipes the
      composer with C-u before typing (so a full one is not concatenated) and
      runs its nudge through `Wait-LoopSubmitted` — section S of
      `test\win32\go-loop-guard.ps1`, plus the whole-file run.
- [x] The upgrade script's RESUME-REUSE path shares the same gate
      (`Wait-LoopSubmitted` in `scripts\loop-session.ps1`), so
      `RESUME-REUSE OK` can no longer be printed over an unsubmitted prompt —
      S13.
- [x] Bonus, found on the way: the box was running a reset-context helper four
      days behind its own source repo. Upstream `84b5c16` (2026-08-05) had
      replaced typing the continuation with handing over a **file path** — the
      pane only ever receives `Read <path> - it contains your instructions…` —
      and this box never pulled it. The gate is now applied on top of THAT
      design, the active plugin cache carries it (D8), and the acceptance
      sections were reworked to probe the cont file's basename instead of the
      prose that no longer crosses the PTY.
