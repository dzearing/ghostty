# T749 - A split off a viewer pane lands in the app's launch folder instead of the sibling terminal's

## In plain terms

Split a terminal off a preview pane and the new shell should start in the same
folder you were already working in. Since this morning it starts in whatever
folder Ghoztty itself was launched from instead - so you split, and find
yourself somewhere else entirely, with no indication why.

## Summary

`test\win32\viewer-panes.ps1` fails one assertion:

```
FAIL  a web viewer contributes no cwd, so the fallback stands (got 'D:\git\ghoztty\')
```

The section builds a terminal in a known directory, then a WEB viewer pane
(`--view=about:blank`, so `ViewerPane.file_path` is null and
`viewer_content.splitWorkingDirectory` correctly answers "no override"), then a
terminal split OFF that viewer. With nothing contributed, the new pane is
supposed to fall back to inheriting from the last focused core surface - the
terminal in the known directory. It now lands in the app process's own working
directory instead.

**Cause, measured rather than assumed.** Re-running the identical script from a
different directory moves the answer with it:

| script run from | pane lands in |
|---|---|
| `D:\git\ghoztty` | `D:\git\ghoztty\` |
| `C:\Users\David` | `C:\Users\David\` |

That is T506's change (`d234701bd`, landed 2026-08-11 08:12): Windows'
`probableCliEnvironment()` used to return a hardcoded false, so the
`working-directory` config default resolved to `home`; it now resolves to the
launch cwd. Whatever consumed that default for a no-cwd split used to produce a
value the test did not look at, and now produces one that visibly wins over the
inheritance it should be losing to.

T506 itself is right and should stay - typing `ghoztty` in a folder must open a
window there. What needs deciding is the PRECEDENCE: an explicitly configured
`working-directory` should not outrank the parent pane's cwd for a *split*, only
for a new window. Check what Mac does with `working-directory = inherit` and a
viewer parent before changing the ordering.

Not caused by T601 (the html viewer work in flight when this was found): its
diff does not touch split cwd inheritance, and the failure reproduces with the
viewer in web mode, where every code path T601 added is inert.

## Validation criteria

- [ ] `test\win32\viewer-panes.ps1` is ALL PASS again, from any working
      directory (run it from at least two).
- [ ] The T506 behavior still holds: `test\win32\gui-launch-command.ps1` (or
      T506's own acceptance script) stays green, and a bare `ghoztty` in a
      folder still opens a window there.
- [ ] A new-window (not split) with no `--working-directory` still honors the
      launch folder, so the fix narrows precedence rather than reverting T506.
