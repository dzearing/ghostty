# T1282 - The caption-bar check cannot see the title bar on the background test desktop, so it reads as a chrome defect

## In plain terms

The check that proves the window's title bar is drawn correctly cannot take a
picture of it when it runs on the hidden test desktop, so it fails there every
time and looks like the title bar itself is broken. Nothing is wrong with the
title bar, and the picture is fine - the check's own "did I get a picture?"
safeguard looks at too few dots to notice the title bar in a window that big,
so it throws the good picture away. When this lands, the safeguard looks
closely enough that a title-bar-sized thing cannot slip past it.

## Goals

- [x] `Get-TestWindowPixels` reaches the working capture route for chrome on a background desktop
- [x] `caption-bar.ps1` is green there, or skips with a named capability
- [x] the red is re-attributed in writing: harness, not product

## Summary

T1115 measured that chrome IS capturable on a background desktop via PrintWindow; Get-TestWindowPixels reaches for CopyFromScreen there, so caption-bar.ps1's UNIFORM capture is a harness defect wearing a caption regression's clothes. Fix the helper, re-run, and re-attribute the red.

## What it actually was

The premise in the Summary above is **wrong, and the correction is the finding**:
`Get-TestWindowPixels` never reached for `CopyFromScreen`. It has captured
through `PrintWindow` on both routes since the file was written
(`CaptureWindowMode`, `PW_RENDERFULLCONTENT` or the `-Sync` WM_PRINTCLIENT
path), and the chrome pixels it brought back were correct all along - measured
here at 20,20,20 across the caption band of a maximized window, which is the
derived chrome color the assertion wanted.

What failed was the guard in front of it. `Test-TestCaptureUniform` sampled a
fixed 24x24 grid, so the STEP grew with the window: 160x88 px on a maximized
3858x2118 window. The only GDI-painted region there is the 40 px caption band
across the top - the rest is the terminal surface, which a background desktop
cannot compose (T1115, a documented limit, not a failure) - and not one sample
row landed inside the band. Every sample came back the same black, the guard
concluded "there is no picture here", and `caption-bar.ps1` section 6 died with
a message about DirectComposition on a capture that was fine.

The fix is a density bound: `-MaxStep` (16 px) caps the stride regardless of
window size, so nothing thicker than 16 px can hide between sample lines. 16
because the smallest thing the suite asserts on is the 32 DIP caption band,
which is 32 px at 100% scale. The scan already returns on the first disagreeing
sample, so a healthy capture still ends after a handful of pixels and the dense
sweep only runs to completion on the path that was going to throw anyway.

## Validation criteria

- [x] `test\win32\caption-bar.ps1` is ALL PASS on the background test desktop - 32 assertions, exit 0, including "maximized: the whole caption band is painted on screen (band bottom 40 >= 40)" which is the assertion the guard was eating.
- [x] `caption-bar.ps1 -NegativeControl` still FAILS (exit 1, 1 FAILURE) - the script kept its teeth rather than being made green by loosening it.
- [x] `test\win32\test-desktop-harness.ps1` ALL PASS (53 assertions) with two new synthetic assertions in section C: a to-scale maximized-window capture (3858x2118, black glass, 40 px band at the client origin) is PASSED by the guard, and the same shot under the count-bounded grid it replaced is called UNIFORM - so the fix is distinguishable from the number it replaced.
- [x] The guard is only ever less likely to fire: a denser grid can turn "uniform" into "not uniform" and never the other way, so no existing capture assertion is weakened by it.
