# T876 - TestDesktop child-class filter is an exact case-sensitive compare - 'static' silently matches nothing; make it case-insensitive or fail loudly on zero matches

## In plain terms

The GUI test toolkit lets a script ask for a window's child controls by
class name, but the name must match Windows' spelling exactly — asking for
"static" instead of "Static" quietly returns an empty list instead of an
error. A test then fails with confusing symptoms far from the real cause.

## Summary

`TestDesktop.ps1`'s C# `Children()` (and `Tops()`) compare the
`GetClassNameW` result with `==` — exact, case-sensitive. During T871 a new
helper passed `-Class 'static'`/`'button'`; every enumeration came back
empty, and 18 assertions failed with symptoms ("visible: ") that pointed at
the dialog rather than the filter. The older scripts dodge this by
enumerating `-Class '*'` and regex-filtering with `-match` (case-
insensitive), which is why the trap had never fired before.

Fix: make the class compare `OrdinalIgnoreCase` in `Children`/`Tops` (class
names are not case-significant to Win32's own `FindWindowExW`), or at
minimum have `Get-TestControls`/`Get-TestChildWindows` warn when a non-`*`
filter matches zero children of a window that HAS children. Prefer the
compare fix; it matches Win32 semantics.

## Validation criteria

- [ ] `Get-TestControls -Class 'static'` and `-Class 'Static'` return the
      same rows against a live dialog (exercised by an existing GUI script
      or a small self-test in the lib).
- [ ] The T871 helpers in `test\win32\claude-integration.ps1` can drop
      their case-sensitivity comment once the compare is insensitive.
- [ ] `test\win32\claude-integration.ps1` still ALL PASS.
