# T1333 - The next zig.exe crash leaves no stack, so a compiler-bug report has nothing to send

## Summary

Filed out of **T451** (2026-09-04), which made a lane say `COMPILER CRASH` and
retry when `zig.exe` itself faults, and closed the "is this build of zig
special?" question: the installed compiler is byte-for-byte the official
`zig-x86_64-windows-0.15.2` release (SHA256
`D408DD38EED3E5204AF841BCEBF70502A4DBBB8399A3A3262BE55059370BC018`), verified
against a fresh download whose zip matches ziglang.org's published shasum. So
the fault is in zig 0.15.2 as shipped, or in this box - and separating those,
or reporting it upstream to ziglang, needs a STACK.

We do not have one. `Invoke-LaneCrashCatch` (T450) and `scripts\lib\CrashDump.ps1`
(T460) exist and do exactly this job, but both are aimed at OUR test binaries:
the crash-catch path re-runs the binary that died, which is meaningless for a
compiler fault that happens once in a multi-thousand-file build, and the
dump-reading path only looks for dumps of the exes in
`$script:CRASHDIAG_TEST_EXES`.

What is left to build is the capture that does work for a once-a-week
non-reproducing fault: a WER `LocalDumps` registration for `zig.exe` (HKCU,
`Software\Microsoft\Windows\Windows Error Reporting\LocalDumps\zig.exe`), so
Windows writes the dump AT the moment of the crash, plus the read side in
`CrashDump.ps1` so the lane's `COMPILER CRASH` block names the dump it just
found and decodes its faulting stack the way a test-binary crash already is.

## In plain terms

The compiler we build with crashes about once a week. We now say so instead of
blaming the code - but we still cannot say WHY, because nothing captures a
stack when it happens, and it never happens twice in the same place on demand.
Ask Windows to save a crash dump of the compiler, and the next one will come
with the evidence a bug report needs.

## Goals

- [ ] Windows writes a dump when `zig.exe` faults on this box, without a
      re-run and without the user being asked anything
- [ ] The `COMPILER CRASH` block names the dump and decodes its faulting stack
- [ ] The dumps land somewhere bounded, so a crashy week cannot fill the drive

## Validation criteria

- [ ] A deliberately crashed process named `zig.exe` leaves a dump in the
      configured directory, and the lane report names it.
- [ ] The dump's faulting stack is printed, from the dump alone, with no re-run.
- [ ] The registration is idempotent and reversible, and its acceptance arm
      proves both.
