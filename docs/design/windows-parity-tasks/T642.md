# T642 - Prove the viewer feedback composer's IME composition on-box, or state why it cannot be

## In plain terms

Someone typing Japanese, Chinese or Korean into the feedback box types through
an input method: keystrokes go into a candidate window first and only the
chosen word lands in the text. That should now work, because the box is a
standard Windows text control and gets it from the OS — but nobody has proved
it on this machine, because no such keyboard is installed here.

## Summary

T635 replaced the composer's append-only buffer with a RichEdit, and the whole
argument for that control is that IME, undo, clipboard and selection come from
the OS rather than from code we wrote. The first three are covered by
`test/win32/viewer-feedback.ps1` sections I and J. IME is **not**: the box has
no IME installed, so the T635 turn could neither drive a composition nor assert
on one, and the claim currently rests on the control rather than on evidence.

Close the gap one of two ways, and say which in the task's evidence:

1. **Drive a real composition.** Install a Microsoft IME (Japanese is the usual
   choice), then post `WM_IME_STARTCOMPOSITION` / `WM_IME_COMPOSITION` with
   `GCS_RESULTSTR` / `WM_IME_ENDCOMPOSITION` at the control and assert the
   composed string arrives in the pane's mirrored buffer (the `action=send
   len=N` oracle, or `Get-TestControlText`). The interesting assertion is not
   just that the text arrives but that the mirror is not corrupted mid-
   composition: `EN_CHANGE` fires while a composition is still open, so the
   buffer sees partial text and must end correct.
2. **Record that it cannot be driven here**, with what was tried, and move the
   check to a manual pre-release step in `docs/design/` rather than leaving an
   unproven claim in a task file.

## Validation criteria

- [x] Either an acceptance section drives a composition into the composer and
      asserts the composed text reaches the pane's buffer, or the task records
      concretely why it cannot run on this box and where the check lives
      instead. — BOTH, as it turned out. `test/win32/viewer-feedback.ps1`
      section K drives the composition; the half that cannot be driven is
      written down in `docs/design/windows-parity-ime-manual.md`.
- [x] If it runs: the mirrored buffer is correct AFTER the composition ends,
      not merely non-empty during it. — the section compares the pane's
      reported buffer length against the **UTF-8 byte count** of what the
      control holds (11 bytes for three CJK characters plus `ok`), so an arm
      counting UTF-16 units would pass on ASCII and fail here.

## Evidence

- `powershell -NoProfile -File test/win32/viewer-feedback.ps1` → **ALL PASS
  (91)**, five of them new:
  - the control accepted the start of an IME composition
  - a composed string lands in the composer
  - ordinary typing continues after the composition ends
  - the pane's buffer mirrors the composed text exactly (buffer=11 bytes)
- Floor lanes (`scripts/floor-lane.ps1 -Lane all`) green.

## Outcome

**Option 1, further than the task expected, plus option 2 for the remainder.**

The task assumed a composition could only be driven with an IME installed. It
cannot on the `GCS_COMPSTR` path — RichEdit reads that out of the input context
— but the message an IME delivers a *settled* composition with,
`WM_IME_CHAR`, is inserted by RichEdit itself with no context at all. That was
measured on this box before anything was written, and it is what section K
posts, bracketed by the real `WM_IME_STARTCOMPOSITION` /
`WM_IME_ENDCOMPOSITION` pair.

**And the proof found a defect.** `editProc` reset the caret's typing
attributes before `WM_CHAR`, `WM_PASTE` and the text-inserting keys, but not
before either IME message — so the first word a Japanese, Chinese or Korean
user composed straight after a quote block would have been inserted wearing the
quote's tint and indent (T641). `win32.WM_IME_CHAR` is now a named constant and
both IME messages take the same reset. That is the whole reason a proof
obligation is worth doing: the claim rested on "RichEdit handles IME", and
RichEdit does — it was OUR pre-insert hook that did not know about it.

What is left is genuinely un-automatable here (candidate window, underlined
intermediate string, reconversion, the caret's resting place after a commit),
because this box has exactly one input method installed and adding a Japanese
one needs elevation and permanently changes the user's language bar. That is
now a manual pre-release checklist in
`docs/design/windows-parity-ime-manual.md` rather than an unproven claim in a
task file.
