# T681 - a closed split pane leaks its child HWND for the life of the app

## Summary

Surface.deinit deliberately never calls DestroyWindow on the pane's child HWND - OPENGL32.dll hooks window destruction and segfaults after the WGL context is gone - and leaves the reap to the parent window's own teardown. Measured while building T126's acceptance script: 10 seconds after +close, the closed pane's GhozttyTerminal child is still enumerable under the top window, hidden, at its last size. Bounded per close, but USER objects are a per-process quota (10k) and this box's sessions run for days. Wanted: reap the HWND at close without re-entering the OPENGL32 teardown path (destroy it from a posted message after the renderer thread and WGL context are fully gone, or move the GL surface to a child of the pane so the pane window itself carries no GL state). Discovered because arm C of test/win32/hero-nav.ps1 cannot count leaves from child windows and had to ask +list --json instead.
