# T681 - a closed split pane leaks its child HWND for the life of the app

## Summary

Surface.deinit deliberately never calls DestroyWindow on the pane's child HWND - OPENGL32.dll hooks window destruction and segfaults after the WGL context is gone - and leaves the reap to the parent window's own teardown. Measured while building T126's acceptance script: 10 seconds after +close, the closed pane's GhozttyTerminal child is still enumerable under the top window, hidden, at its last size. Bounded per close, but USER objects are a per-process quota (10k) and this box's sessions run for days. Wanted: reap the HWND at close without re-entering the OPENGL32 teardown path (destroy it from a posted message after the renderer thread and WGL context are fully gone, or move the GL surface to a child of the pane so the pane window itself carries no GL state). Discovered because arm C of test/win32/hero-nav.ps1 cannot count leaves from child windows and had to ask +list --json instead.

## In plain terms

Every time you close a split pane, Ghoztty threw away the pane but kept the
invisible window it was drawn in — forever, until you quit the app. Nobody sees
one of those. But Windows only lets a program hold about ten thousand windows at
once, and this box's terminal is left running for days across hundreds of opened
and closed panes, so they pile up in the direction of a program that eventually
stops being able to draw anything. After this change the pane's window is
actually destroyed when you close the pane, and nothing is left behind.

## Goals

- [x] a closed pane's child window is destroyed rather than hidden and abandoned
- [x] the destroy cannot re-enter the OpenGL teardown the original code was
      avoiding
- [x] closing a whole window (where the parent frees the children first) is
      still safe — no handle is destroyed out from under a new owner
- [x] an acceptance script that counts the leftovers, teeth-checked against a
      build without the fix

- [x] Closing panes leaves no `GhozttyTerminal` child windows behind: arms

- [x] The teeth-check: rebuilt with `reapSurfaceHwnd` disabled, B1 reports

## Progress log

- 2026-08-10 13:30: claimed; work starting.
- 2026-08-10 14:10: root cause confirmed — `Surface.deinit` never destroyed the
  pane HWND (comment dates to the very first win32 commit, e0118f682). Fix: the
  handle is posted to the app's message-only window (`WM_APP_REAP_SURFACE`) and
  destroyed from the top of the message loop, off the WGL teardown stack. New
  pure module `surface_reap.zig` gates the reap on class + cleared
  `GWLP_USERDATA` so a handle Win32 already freed with its parent (and possibly
  recycled) is never destroyed. Acceptance: `test/win32/pane-hwnd-reap.ps1`,
  teeth-checked against a build with the post disabled (B1 saw 3, want 1).
