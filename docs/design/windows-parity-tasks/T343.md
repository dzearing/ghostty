# T343 - In-place agent recovery matches captured windows by POSITION; the T338 uuid is a real key

Found doing T338 (2026-08-02), which created the identity this task can use.

## In plain terms

When the thing that keeps your shells alive in the background has to be
restarted, the terminal quietly puts every window back together underneath you
— same windows, same splits, same running programs. Today it works out which
window gets which layout by COUNTING: first window gets the first layout,
second gets the second. If a window closes during the few seconds that takes,
the count slips and a window can be rebuilt from a DIFFERENT window's layout —
your panes come back, but in the wrong window, wearing the wrong shells. Now
each window carries a name tag and gets its own layout back by name; a window
the rebuild doesn't recognise is left completely alone instead of being handed
somebody else's.

## Goals

- [x] Pair captured windows to live ones by their stable identity, not position
- [x] A live window absent from the capture is skipped, never mispaired
- [x] The same captured window can never be spent on two live windows
- [x] Unit coverage for the pairing, including a walk reordered in between
- [x] The on-box in-place recovery acceptance run stays ALL PASS

## The defect

`App.recoverLocalAgentInPlace` (the T229/T230 path: the agent was terminated and
re-dialed under the user's live windows) captures the topology, then walks
`self.windows.items` again and pairs each live window with a captured one **by
position**, replaying the capture's skip rule by hand:

```zig
// src/apprt/win32/App.zig (in-place recovery)
//   "we replay the skip rule here rather than trying to key on a synthesized
//    `win-N` id."
for (self.windows.items) |win| {
    if (win.is_quick_terminal) continue;
    if (win.remote_dialed != null) continue;
    if (win.tab_count == 0) continue;
    defer ci += 1;
    ...captured.windows[ci]
}
```

The comment is honest about why: at the time there was no id worth keying on.
The cost is that the pairing is correct only while the two walks agree exactly -
a skip rule that drifts, or a window closing between the capture and the rebuild
(the capture is followed by a `reconnectForRecovery` that can block for seconds),
silently pairs a window with **another window's** captured topology. There is no
assertion that would notice; every pane would be rebuilt from the wrong tree.

## Why it is worth fixing now

T338 gave every window a stable `layout_uuid`, recorded on the captured
`session_layout.Window` as `uuid`. The pairing can become a lookup by that value,
with a window whose uuid is absent from the capture simply skipped - which is
also the correct behavior for a window that appeared after the capture.

Not urgent: the two walks do agree today, and this has never been observed to
misfire. It is filed because a positional join that has to restate someone
else's filter is a latent defect, and the key that removes it now exists.

## How it was fixed

`session_layout.pairWindows(alloc, captured, live_keys)` is the whole join: one
entry per live window, holding the index of the captured window it owns or
`null`. Keys come from `Window.layoutUuid()` (T338) via `windowKey`, which keeps
the `uuid orelse id` derivation identical to the one the agent-side blob store
already uses. Each captured entry is handed out at most once, so a duplicated
key degrades to "the second window is skipped" rather than "two windows rebuild
from one tree".

`App.recoverLocalAgentInPlace` no longer restates `captureSessionLayout`'s skip
rule (quick terminal / cross-machine / no tabs): those windows are simply absent
from the capture, so the lookup returns `null` and they are left alone — as is a
window created while `reconnectForRecovery` blocked. The one filter that stays
is `local_agent_conn == null`, because the capture does NOT drop those windows
and their plain exec panes must not be replaced.
