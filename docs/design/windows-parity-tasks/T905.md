# T905 - New persistent sessions spawn holder-backed, so a shell no longer dies with the agent process

## Summary

Increment 2 of the T705 split (design:
`docs/design/agent-nondestructive-handoff.md`). The agent's session spawn path
(`pty_child.zig`) gains a holder-backed `session.Child`: instead of creating
the ConPTY in-process, it spawns a T904 holder and pumps the session over the
holder's control pipe. Flag-gated while it stabilizes
(`GHOSTTY_AGENT_PTY_HOLDER=1`, then default-on).

Load-bearing details:

- The holder must ESCAPE the agent's kill-on-close job — the point is that it
  outlives the agent. `spawnEscapingJob` is the existing pattern; plain
  breakaway is refused from the pane-shell chain, not from the agent spawning
  a supervisor.
- `sessions.json` gains ADDITIVE per-session fields (holder pipe name, holder
  pid, holder stamp). An older agent reading the file ignores them; nothing
  existing changes meaning.
- The holder is not adopted by anyone yet (that is T906) — if the agent dies,
  the shell lives on and the next agent start finds it via T906. Until T906
  lands, an orphaned holder must at minimum be discoverable and killable
  (`+sessions` still lists the session; closing it reaches the holder).

## In plain terms

With this, newly opened terminal sessions get their own caretaker process, so
the session's shell keeps running even if the background manager crashes or is
replaced. This is the first point where "the manager died" stops meaning "your
sessions died" — picking the survivors back up is the next task.

## What landed

New files:

- `src/remote/agent/pty_host_spec.zig` — the JSON **spawn spec**. Carries
  `protocol.Open` VERBATIM plus the session id, pipe name and holder limits;
  written atomically to `%TEMP%\ghoztty-ptyhost-<id>.json` and read-and-DELETED
  by the holder before it spawns the shell. Chosen over argv (arbitrary user
  strings into one 32 KiB command line — a quoting bug per user with a `"` in a
  path) and over the environment (the escaping spawn's shell-parent tier donates
  the CALLER's environment block, so per-session vars would leak into the next
  holder). Pure; round-trip, elision, unknown-field and version-refusal tests
  run in the `test-agent` lane.
- `src/remote/agent/pty_holder_child.zig` — the owner side as a
  `session.Child`, so nothing above it knows a second process exists. INPUT /
  RESIZE / SIGNAL out; offset-tagged OUTPUT → the session sink with a per-batch
  ACK releasing the holder's replay ring; EXIT → `tryWait`; SHUTDOWN plus a
  Job-Object-backed hard kill on `terminate`. A transient pipe drop with the
  holder still ALIVE re-dials and re-ATTACHes at the last delivered offset —
  the protocol's gap-fill in production, not just in the smoke. A holder that
  is really gone is reported as an exit, so a session never sits alive around a
  shell that no longer exists.

Changed: `pty_host.zig` (accepts a whole `Open`), `main.zig` (`--pty-host
--spec <path>`), `pty_child.zig` (`spawnFn` branches on the flag, falling back
to the in-process child on any holder failure), `server.zig`
(`Spawner.Result.holder`), `session.zig` (`setHolder`, persisted + materialized),
`session_meta.zig` (additive `holder_pipe` / `holder_pid` / `holder_stamp`).

## Decisions taken here (mechanism — Claude's call per go.md 5b)

- **Spec file rather than flags or environment** — reasons above; the
  alternative fails on quoting or on env leakage between sessions.
- **The holder's id is a fresh random 32-hex, not the agent's session id.** The
  session id does not exist yet when `spawnFn` runs (`SessionTable.create`
  assigns it afterwards), and the durable link is `sessions.json`'s
  `holder_pipe`, which is what T906 will dial. Nothing depends on the two ids
  matching, so nothing had to reorder the spawn against session creation.
- **Env var is `GHOZTTY_AGENT_PTY_HOLDER`**, not the `GHOSTTY_`-spelled name in
  this task's original summary: every other env knob in this fork is `GHOZTTY_`.
- **A holder-spawn failure degrades to the in-process child** rather than
  failing the OPEN, with a warning naming what was lost.
- **`job_spawn.zig` is imported across the apprt boundary** rather than copied.
  It depends on nothing but `std` + `os/windows.zig`, and a second copy of the
  breakaway → shell-parent-hop → in-job ladder is exactly the near-duplicate
  that drifts apart one bug fix at a time.
- **`terminate`'s SHUTDOWN grace is 400 ms**, not seconds: the hard kill is an
  equally COMPLETE teardown (the holder owns the only handle to the
  kill-on-close job over the shell subtree), so waiting longer buys latency and
  nothing else — and `+close` is latency-bounded by the persistence floor (T63,
  measured at 480 ms / 899 ms with holders on).

## Two hazards found by reading, not by a red test

Recorded because neither would have failed a test on this box, and both are the
kind that surface once, on someone else's machine, as a hang:

- **`terminate` vs the reader mid-reconnect.** `terminate` closed the stream
  and then joined the reader; if the reader was between "dial succeeded" and
  "install the new stream", terminate closed the OLD stream and the reader
  parked on a read on the NEW one that nothing would ever cancel — `join()`
  forever. Both sides now interlock on `write_mutex` and re-check `closed`
  inside it, so whichever runs second sees the other's decision.
- **A leaked pipe handle per reconnect.** The dead stream's handle was never
  closed before its wrapper was freed — invisible until a flaky link made the
  reconnect path run more than once.
