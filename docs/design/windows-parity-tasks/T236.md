# T236 - auto-launch startup window no longer starts in the requested --working-directory (auto-launch-cwd B3)

## In plain terms

If you ask for a new terminal window in a specific folder while the app is not
running yet, the app starts up — but its first window opens in your home folder
instead of the folder you asked for. Only the extra window the app creates on
its way up is wrong; the window you actually asked for is fine. When this
lands, every window that appears from that request sits in the folder you
named.

## Root cause & fix

T144 (`22fd789e6`) made the local-agent OPEN carry the surface's resolved
`working-directory` config (`termio.Remote.openWorkingDirectory`) — correct in
itself, but on Windows `Config.probableCliEnvironment()` is hardcoded `false`,
so the config default resolves to `.home` on every launch. The explicit home
path now outranked the agent-inherited process cwd that T132's
`lpCurrentDirectory` relied on, which is why the startup window moved from
"requested dir" (accidental, via inheritance) to "home" (explicit, wrong).

Fix: `autoLaunchInstance` (src/apprt/win32/App.zig) now passes the requested
directory on the spawned GUI's own command line as `--working-directory=<dir>`
— config CLI args are parsed on Windows, so the startup window resolves the
requested directory *explicitly* instead of hoping to inherit it.
`lpCurrentDirectory` is kept: the session-persistence agent still inherits the
process cwd, which is where a RELAUNCH of a session that recorded no cwd lands
(section C of the script). The token is built by a new pure
`args.autoLaunchCwdArg` with CreateProcessW quoting rules (whitespace quotes
the token, trailing backslashes double inside quotes, embedded `"` refuses).

The hardcoded-false `probableCliEnvironment` is itself a parity gap for plain
terminal launches — filed as **T506**.

## Summary

`test/win32/auto-launch-cwd.ps1` **B3 fails at HEAD**. Found 2026-07-31 while
validating T230; it is NOT a T230 regression (proved below).

```
FAIL B3 the startup window's shell is in the requested directory
     (expected 'c:\users\david\appdata\local\temp\ghoztty-auto-launch-cwd-36892\workdir',
      got 'c:\users\david')
```

Everything else in that script passes (20/21), including arm A — the window the
CLI actually asked for lands in the requested directory. It is only the
**startup window** the auto-launch creates on the way there that does not.

That is precisely the defect T132 was filed to fix (`349eba4f6`, "record the
session cwd, and auto-launch into it"): before it, a `+new-window
--working-directory=X` run from `System32` with no instance running spawned an
app whose own startup window sat in `System32`. The current symptom is
different — the startup window is in `%USERPROFILE%`, not the launcher's
directory (B4, which asserts it is not the launcher's, still passes) — so
something now resolves the startup surface's working directory to the GUI
platform default (`%HOMEDRIVE%%HOMEPATH%`) instead of the app process's cwd.

## Evidence (this is not T230)

VERIFIED by A/B on box, not inferred:

1. With T230's `PtySpawner.resolveSpawnCwd` active: B3 fails, `got
   'c:\users\david'`.
2. With `resolveSpawnCwd` short-circuited to a pass-through (one-line edit,
   rebuilt, same run): **B3 fails identically**, same expected/got.

So the fallback T230 added is not in the path. Separately verified that its
directory probe is not misfiring: an instrumented agent logged
`resolveSpawnCwd want='...\workdir' exists=true` for exactly this shape, i.e. a
real directory is passed through untouched.

## Where to look

- `src/Surface.zig` — `termio.Remote.openWorkingDirectory(explicit, local,
  is_local_agent)`; `local` is the surface config's already-resolved
  `working-directory`, which for a GUI launch is the platform default. The
  question is what the STARTUP surface resolves for `local` and whether the
  app's own cwd still reaches it.
- `src/apprt/win32/App.zig` — the auto-launch/startup-window path, and whatever
  T132 added to carry the requested directory into the spawned instance.
- The agent is not implicated: it spawns in whatever cwd the OPEN carries.
