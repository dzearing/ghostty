# T245 - ghoztty CLI output is lost when redirected from PowerShell (GUI-subsystem stdout)

## Summary

`ghoztty +<verb> > file` run from PowerShell writes an EMPTY file. The same
command redirected from `cmd.exe` writes the real output, and the same command
piped from PowerShell (`| Out-String`) also works. So the output exists - it
just does not survive PowerShell's file redirection.

Every automation on this box that captures a CLI verb by redirection gets
nothing, silently, with no error. go.md's own tool-output discipline ("redirect
first and filter the file") walks straight into it.

## Evidence (VERIFIED on the box 2026-07-31, release +eeb78b6f0)

```
PS> & $exe +list --json > $env:TEMP\l.json 2>&1 ; (Get-Item ...).Length
0
PS> & $exe +sessions --json > $env:TEMP\s.json 2>&1 ; (Get-Item ...).Length
0
PS> cmd /c "%LOCALAPPDATA%\Programs\Ghoztty\ghoztty.exe +list --json > %TEMP%\l2.json 2>&1"
cmd-exit=0
bytes=1457
PS> & $exe +list --json | ConvertFrom-Json      # works, full document
```

`$LASTEXITCODE` also came back empty on the redirected `+sessions` run, which
is the same symptom seen from another angle.

## Likely cause (INFERRED - not yet read)

`ghoztty.exe` is linked as a GUI-subsystem binary (it is the app), so it starts
with no console and no inherited standard handles unless something attaches
them. The CLI verbs appear to write through a console handle they attach
themselves (`AttachConsole`/`AllocConsole`-shaped behaviour), which lands on the
console rather than on the redirected handle PowerShell set up. cmd.exe's
redirection survives because it sets the handles before the child ever attaches;
PowerShell's does not. This wants reading before it is fixed, not guessing.

## Why it matters

- Silent. There is no error, no exit code, no partial file - just nothing.
- It is a trap for every future script, and it already cost two detours this
  session (a `+sessions` probe and a `+list` capture that both "returned
  nothing" and looked like IPC failures).
- The Mac CLI writes to stdout like an ordinary console program; this is a
  Windows-only divergence in a place scripts depend on.

## Workaround until it is fixed

Capture ghoztty CLI output with a PIPE, never `>`:
`$out = & $exe +list --json 2>&1 | Out-String`. That is what
`scripts/go-loop-*.ps1` and `test/win32/*.ps1` already do.

## The fix

Read how the CLI verbs acquire their output handle on win32 (the `+<verb>`
entry path in `src/cli/` / `src/main.zig` and whatever console attach the
win32 apprt does), and make them write to the process's real standard output
when one was inherited, only attaching/allocating a console when there is
none. Whatever the mechanism, the rule to restore is: if the parent gave us a
stdout handle, that is the one we write to.

## Validation

- `powershell -Command "ghoztty +list --json > out.json"` produces the same
  bytes as the `cmd /c` redirect and as the pipe.
- Same for `+version`, `+sessions`, `+read` (the verbs scripts capture).
- An assertion in `test/win32/ipc-version.ps1` (or nearest sibling) that
  captures a verb BY REDIRECTION, so the regression cannot come back invisibly.
- Non-goal: changing how the app itself logs.
