# T245 - ghoztty CLI output is lost when redirected from PowerShell (GUI-subsystem stdout)

## In plain terms

Saving the output of a `ghoztty` command to a file from PowerShell silently
saved nothing: the file came out empty, no error, no exit code. Anyone
scripting against the terminal - including this project's own automation -
got bitten, and the failure looked like the terminal not answering rather
than the output being dropped. After this lands, `ghoztty ... > file` from
PowerShell just works, the way it already did from cmd.exe and on macOS.

## Goals

- [x] `ghoztty +<verb> > file` from PowerShell captures the real output.
- [x] `$LASTEXITCODE` is set after every `ghoztty` CLI call from PowerShell.
- [x] A bare `ghoztty` (GUI launch) from a shell still returns immediately.
- [x] The fix ships in the build output and in every delivery location.
- [x] A regression test captures a verb BY REDIRECTION so this cannot come
      back invisibly.

## Validation criteria

- [x] `test\win32\cli-shim-redirect.ps1` ALL PASS (17 asserts: subsystem
      field, PS `>` capture content-matched against a cmd.exe redirect, exit
      code propagation incl. the child-PowerShell repro shape, detached GUI
      respawn via fake sibling with tail passthrough, pipe-vs-pipe identity).
- [x] The release shape is proven, not assumed: the installed release exe
      (subsystem 2) run through a patched twin captured 735 bytes under PS
      `>` with exit 0, on this box, before any delivery.
- [x] Windows Defender accepts the shipped artifact (custom scan of the twin:
      clean; the first-cut relay shim was quarantined, see Progress log).
- [x] Both zig test lanes + test-agent green (floor-lane -Lane all), P1-P3
      ALL PASS.

## Summary

`ghoztty +<verb> > file` run from PowerShell writes an EMPTY file. The same
command redirected from `cmd.exe` writes the real output, and the same command
piped from PowerShell (`| Out-String`) also works. So the output exists - it
just does not survive PowerShell's file redirection.

Every automation on this box that captures a CLI verb by redirection gets
nothing, silently, with no error. go.md's own tool-output discipline ("redirect
first and filter the file") walks straight into it.

## Evidence (VERIFIED on the box 2026-07-31, release +eeb78b6f0)

```
PS> & $exe +list --json > $env:TEMP\l.json 2>&1 ; (Get-Item ...).Length
0
PS> & $exe +sessions --json > $env:TEMP\s.json 2>&1 ; (Get-Item ...).Length
0
PS> cmd /c "%LOCALAPPDATA%\Programs\Ghoztty\ghoztty.exe +list --json > %TEMP%\l2.json 2>&1"
cmd-exit=0
bytes=1457
PS> & $exe +list --json | ConvertFrom-Json      # works, full document
```

`$LASTEXITCODE` also came back empty on the redirected `+sessions` run, which
is the same symptom seen from another angle.

## Likely cause (INFERRED - not yet read)

`ghoztty.exe` is linked as a GUI-subsystem binary (it is the app), so it starts
with no console and no inherited standard handles unless something attaches
them. The CLI verbs appear to write through a console handle they attach
themselves (`AttachConsole`/`AllocConsole`-shaped behaviour), which lands on the
console rather than on the redirected handle PowerShell set up. cmd.exe's
redirection survives because it sets the handles before the child ever attaches;
PowerShell's does not. This wants reading before it is fixed, not guessing.

## Why it matters

- Silent. There is no error, no exit code, no partial file - just nothing.
- It is a trap for every future script, and it already cost two detours this
  session (a `+sessions` probe and a `+list` capture that both "returned
  nothing" and looked like IPC failures).
- The Mac CLI writes to stdout like an ordinary console program; this is a
  Windows-only divergence in a place scripts depend on.

## Workaround until it is fixed

Capture ghoztty CLI output with a PIPE, never `>`:
`$out = & $exe +list --json 2>&1 | Out-String`. That is what
`scripts/go-loop-*.ps1` and `test/win32/*.ps1` already do.

## The fix

(Original hypothesis - "make the verbs write to the inherited handle" -
turned out to be unfixable from the child side; see the Progress log. What
shipped:)

`ghoztty.com`, a console-subsystem TWIN of `ghoztty.exe`, installed as a
required sibling (the `devenv.com` pattern). PATHEXT resolves `.COM` before
`.EXE`, so bare `ghoztty` from PowerShell or cmd finds the twin, which
PowerShell waits for and wires redirection to like any console program. The
twin is the SAME binary with one WORD flipped (PE optional header Subsystem,
GUI -> console) by a build-time host tool, so CLI verbs run in the console
process directly - byte-exact arguments, direct exit codes, working Ctrl-C.
A GUI launch through the twin (no `+action`) respawns the sibling
`ghoztty.exe` detached with the command-line tail passed through verbatim and
exits 0, so a shell never blocks on the terminal it just launched.

Pieces:

- `src/build/patch_subsystem_main.zig` - the 2-byte PE patch tool (offset 68
  of the optional header holds Subsystem in both PE32 and PE32+).
- `src/build/GhosttyExe.zig` - builds the tool, patches the exe, installs
  `zig-out\bin\ghoztty.com`.
- `src/cli/com_shim.zig` - pure logic (basename check, command-line tail
  index) + unit tests, and the design history in its doc comment.
- `src/apprt/win32/App.zig` `runComShimGuiRespawn` + the hook in
  `src/main_ghostty.zig` - the detached GUI respawn.
- `scripts/upgrade-ghoztty-windows.ps1` - ships the twin to the installed
  release and the extra install locations.
- `test/win32/cli-shim-redirect.ps1` - acceptance.

Why not a small relay shim (the first cut, fully built and green): Windows
Defender's ML quarantined it on sight as `Trojan:Win32/Bearfoos.A!ml` - a
tiny unsigned console exe that spawns processes with inherited handles is
the static shape of a dropper. The full app binary with its VERSIONINFO has
never been flagged, and the twin is byte-identical to it minus one word.
Scripts that call `ghoztty.exe` by EXPLICIT path still need pipe capture
(that binary is still GUI-subsystem, unavoidably); bare `ghoztty` and
explicit `ghoztty.com` calls get real redirection.

## Validation

- `powershell -Command "ghoztty +list --json > out.json"` produces the same
  bytes as the `cmd /c` redirect and as the pipe.
- Same for `+version`, `+sessions`, `+read` (the verbs scripts capture).
- An assertion in `test/win32/ipc-version.ps1` (or nearest sibling) that
  captures a verb BY REDIRECTION, so the regression cannot come back invisibly.
- Non-goal: changing how the app itself logs.
