# T850 - ViewerPane 'host floor' clipboard test fails under multi-process contention - the clipboard is a global resource 32 test binaries fight over

## Summary

Found during T480's validation soak (2026-08-15). Running 32 copies of the
win32 test binary simultaneously (`scripts\test-binary-soak.ps1 -Lane win32
-Mode standalone -Runs 32 -Concurrency 32`) produced **10 failures in 32
runs**, every one of them the same assert:

```
apprt.win32.ViewerPane.test.host floor: a real controller on a real window, on this box
src\apprt\win32\ViewerPane.zig:6121: try testing.expect(copied != null);
```

after a `[viewer_pane] (warn): copy[web]: clipboard=null` line. ProcSampler —
the test the soak was aimed at — failed **zero** times in the same 32 runs, so
this is the win32 lane's next-loudest source of load-only noise.

The Windows clipboard is one global, serialized resource: `OpenClipboard`
fails while any other process holds it, and 32 test binaries all running the
host-floor copy path at once guarantees collisions. The test asserts that a
copy from a real WebView2 controller lands on the clipboard; under contention
the open/read races another process's open/write and reads back null while the
code under test is behaving correctly.

Same class of defect as T480: a test whose verdict depends on what else the
box is doing, in the exact lane the floor runs.

## In plain terms

One of our tests copies text to the Windows clipboard and checks it arrived.
The clipboard is shared by the whole machine, so when several test runs (or
the user, or any other program) touch the clipboard at the same moment, the
check can come up empty even though copying works fine. The test should prove
"copy works" without depending on winning a machine-wide race.

## Goals

- [x] The copy test's verdict no longer depends on what else the box is doing
- [x] It still goes red when a copy genuinely does not land
- [x] No clipboard user in the app gives up on a single refused `OpenClipboard`

## What was done

Two defects, one root: the clipboard is a single machine-wide resource, and
this section treats it as private state.

1. **A refused open was a silent no-op.** `OpenClipboard` does not queue — it
   fails outright while another process holds it. New shared
   `src/apprt/win32/clipboard_open.zig` retries on a bounded budget (8
   attempts, 15ms apart, ~120ms worst case); ViewerPane's two text helpers and
   `clipboard_image`'s private copy of the same loop now both go through it.
   That is a real user-facing fix as well as a test one: the link menu's Copy
   (T826) silently did nothing when it lost that race.
2. **The bytes themselves were being clobbered.** This is what actually
   produced the 10 failures, and no deadline could have fixed it: between our
   browser writing the needle and our poll reading it, ANOTHER test process
   wrote its own sentinel — or put the user's saved clipboard back — and our
   poll then ran out and reported "the copy never landed" over a copy that
   landed perfectly. The processes now take turns on a named mutex
   (`Local\ghoztty-viewer-clipboard-test`) held across each critical region
   (sentinel → press → read) and the user-clipboard restore. It is acquired
   while still pumping the message loop, since WebView2 delivers everything
   through it; Windows releases it automatically if a holder dies, so a crashed
   run cannot wedge the lane.

## Fix directions weighed

- ~~Retry the clipboard read with a deadline~~ — **rejected on evidence**. The
  read is already a 30-second poll; the value it is polling for is being
  erased by another process, and no deadline fixes a byte that keeps being
  overwritten. This was the obvious-looking direction and it would have
  produced a slower test that still flaked.
- **Serialize clipboard-touching tests across processes with a named mutex** —
  taken. It is the only one that addresses the resource being global rather
  than the symptom being intermittent.
- ~~Verify the copy at the WebView2 message layer instead~~ — rejected. The
  toolbar's entire job is landing bytes on the SYSTEM clipboard, outside the
  browser process; asserting on the browser's own message would leave the last
  hop — the one that has actually broken before — unmeasured.
