# T246 - Mac seat: confirm menu(for:)/rightMouseDown ordering - does Mac show the right-click menu under mouse reporting?

## Summary

**One fact, checkable in minutes on a Mac, that decides whether T240 is a
parity fix or a deliberate divergence.**

T240 (done, 2026-07-31) made a win32 right-press open the context menu even
when the running application has mouse reporting on, because the user reported
the menu as unreachable — every pane they keep open (Claude Code, vim,
lazygit) turns reporting on, and the menu was gated on the core returning
"unconsumed".

T240 justified that as Mac parity, claiming AppKit consults `menu(for:)`
BEFORE delivering `rightMouseDown`. **Re-reading it from the Windows seat, that
ordering looks wrong**, and if it is wrong then Mac suppresses the menu under
reporting exactly the way win32 used to — making T240 a divergence in the
user's favor rather than a parity fix. Either answer is fine; an unrecorded
guess is not.

## What to check (Mac seat)

`macos/Sources/Ghostty/Surface View/SurfaceView_AppKit.swift`:

- `menu(for:)` (~1646) returns a fully built `NSMenu` for `.rightMouseDown`
  with no `consumed` and no `mouseCaptured` guard.
- `rightMouseDown(with:)` (~1024) sends the press to the core and **returns
  early when the core consumed it**, calling `super.rightMouseDown` only when
  it did not.

Those two are only consistent if `NSView`'s default `rightMouseDown:` is what
calls `menuForEvent:` and pops the menu — i.e. the menu is suppressed under
reporting. Supporting it: the "AppKit calls menu BEFORE calling any mouse
events" comment lives inside the `.leftMouseDown` (ctrl+click) case, and that
is also the only branch that compensates by manually sending a press. If the
right-click path went through `menu(for:)` first, that branch's compensation
would be needed for right-clicks too, and the override's early return would be
dead code for the menu.

## Validation

Empirical, not textual: on a Mac, run a mouse-reporting TUI (`vim` with
`:set mouse=a`, or Claude Code at its prompt — reporting is off at its trust
dialog, so get past that first) and right-click.

- **Menu appears** → T240 is a parity fix; delete this caveat from T240 and
  from `docs/design/windows-parity-log.md`.
- **No menu** → win32 now deliberately diverges. Decide which way both
  platforms should go (the user's complaint is the input: they want the menu),
  and if Mac should follow, move the divergence into the shared core so both
  apprts get it from one place — `Surface.rightPressWouldReport` already
  isolates the decision.
