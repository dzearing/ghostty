# T408 - focus-defer's IPC-under-load assertion has a 100x margin over the measured latency

## In plain terms

The test that proves the terminal stays responsive while a pane is spewing
output only ever asked "did it answer at all, within eight seconds?". On this
box it answers in about fifteen milliseconds, so the terminal could get
hundreds of times slower under load and the test would still say everything is
fine. Now the test times the answer and holds it to a budget, and prints the
number every run, so a slowdown shows up as a red test long before anyone has
to notice their terminal feeling sluggish.

## Goals

- [x] measure the `+list` round trip in-process, under the same flood
- [x] assert it against a budget derived from a recorded baseline
- [x] print the measured number on every run so drift is visible before it fails
- [x] keep the 8s out-of-process check as the wedge backstop it always was
- [x] prove the new assertion can actually fail

## Summary

Filed by T107 (2026-08-03). `focus-defer.ps1`'s `+list answers within 8s
(GUI-thread IPC listener alive)` assertion is a WEDGE detector wearing a
latency assertion's clothes: measured on box under the same flood the
assertion runs against, `+list` answers in **73 ms**. The bar is ~110x the
real number, so the IPC listener could get 50x slower under sustained PTY
output and this script would still report ALL PASS.

## Why it is worth fixing

The whole point of the section is behaviour UNDER LOAD, and T107 has just
made the load itself assertable (flood counter advancing, storm posted and
processed). What is still unmeasured is the thing the load is applied TO.
The bug class this guards - IPC starvation while a pane is flooding - would
show up as latency long before it shows up as a wedge, and an agent driving
a busy pane feels a 4-second `+list` as broken even though it "answers".

Note this is deliberately NOT a claim that the current 8s should just be
dialled down to 100 ms. The Start-Job wrapper costs a PowerShell process
launch, which is most of the current measurement's variance.

## The fix

- Measure `+list` latency in-process (`& $Exe +list` behind a Stopwatch),
  keeping the Start-Job/8s form only as the wedge backstop it already is.
- Assert against a budget derived from a recorded baseline, with the
  measured number printed on every run so a drift is visible before it is a
  failure. Record the baseline (73 ms on this box, Debug build, ~2,500
  lines/s flood) in the script so the next reader knows what the budget came
  from.
- Sanity-check the budget's headroom on a ReleaseFast build too - Debug is
  the slower of the two, so a Debug-derived budget should not be tight.

## Validation

`focus-defer.ps1` ALL PASS, plus a break-test that the new budget assertion
can actually fail (T107's method: break it and re-run, since an assertion
confirmed only by passing is indistinguishable from one that never ran).

## Validation criteria

- [x] `focus-defer.ps1` ALL PASS on the box - 19 assertions, three runs
      (medians 12 / 15 / 17 ms), Debug `zig-out`.
- [x] the measured latency is PRINTED every run, samples and budget included,
      so drift is readable before it is a failure.
- [x] the budget assertion can score red: `-NegativeControlBudget` (budget
      1 ms) produced exactly one FAIL, the budget assertion, exit 1.
- [x] a fast-failing `+list` cannot pass the budget - every sample's exit code
      is asserted alongside the timing.
- [x] the 8s out-of-process `Start-Job` wedge check is still present and still
      runs FIRST, so a genuinely hung GUI thread bounds the script rather than
      hanging it.
- [x] floor lanes lib / none / win32 / agent all PASS.
- [ ] ReleaseFast headroom sanity-check - NOT RUN, deliberately. Pointing this
      script at a release `zig-out` is what `test\win32\lib\BuildMode.ps1`
      refuses, since a release build derives the user's live IPC and agent
      endpoints. The headroom is carried in absolute terms instead (200 ms
      against a 15 ms Debug median), which covers a ReleaseFast app working its
      GUI thread harder several times over.

## Outcome

The `+list answers within 8s` assertion is kept, but as the wedge backstop it
always was rather than as a latency claim. Beside it, five in-process
`& $Exe +list` calls behind a Stopwatch, asserted on the MEDIAN against a
**200 ms** budget - about 13x the measured 12-17 ms, where 8s was ~500x.
Median-of-5 matters in practice: one run drew a 104 ms sample among four in the
14-18 ms band and the median absorbed it.

T408's recorded 73 ms baseline was deliberately not inherited. It was measured
through the `Start-Job` wrapper, which is mostly a second PowerShell's startup;
the in-process number on this box is 12-17 ms, and measuring in-process is what
lets the budget be 13x rather than 110x.
