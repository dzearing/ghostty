# T1056 - An app update can still restart the agent for a build-stamp gap alone, and liveness is read from this app's window count

## Summary

Main intake of 9a04b745c (upstream fix on origin/main, macos/ side; the Windows analog is src/apprt/win32/agent_upgrade.zig + App.zig:3722-3900). Mac's defect: an app update replaces the bundled agent binary while the running agent keeps every PTY attached, and agentIsStale read that build-stamp gap as a reason to restart it. It is not one - proto_version is negotiated in HELLO and a mismatch is fatal there, so an agent we can talk to has already agreed the wire contract, and everything since rides additive capabilities that degrade on their own. The 1.33.0 update took that path and tombstoned 95 live sessions for a binary refresh nothing required. Mac's fix, in three parts: (1) a stale-but-compatible agent is left strictly alone and adopted at the next natural cold start, with the mandatory-update prompt reserved for a skew the handshake actually flags as incompatible; (2) 'Later' becomes the prompt's DEFAULT button, so a stray Return during a post-update relaunch cannot end every session; (3) liveness comes from the agent's own LIST_SESSIONS instead of counting this app's windows - the window count reads 0 in all the wrong situations (a partial or slow restore, the user closing their last window while ninety pinned sessions keep running, a second app instance) and 0 meant a silent bootout; an unavailable roster is 'unknown' and never authorizes a restart. Work here: audit agent_upgrade.evaluate/applyDeferral against all three, decide which translate (the handoff path T907/T1044 migrates PTYs rather than killing them, so part 1 may already be softer on Windows - confirm rather than assume), fix what does not, and pin each part with a unit test in the none lane plus an arm in test/win32/agent-upgrade.ps1. Related: T1038 (the kill switch leaves the app waiting for a handoff that never comes).

## In plain terms

Ghoztty keeps your terminal sessions alive in a background process so they
survive closing the app. Until now, an ordinary Ghoztty update could put a box
on screen saying the background process needs restarting and that all your open
sessions will close - and there was no real reason for it. The update only
replaced a file on disk; the process already running was perfectly able to keep
talking to the new app. On the Mac side someone pressed the wrong button on that
box and lost 95 running sessions to it.

After this, an update never offers that trade. The background process is left
running exactly as it is, and the new version is picked up quietly the next time
nothing is open. The one time Ghoztty still asks is when it genuinely cannot
talk to that process any more - there, restarting really is the only way back to
a working terminal, and "Later" is the button Enter presses.

## Goals

- [x] A stale-but-compatible agent is left strictly alone while any session is
      live - no dialog, no restart - and adopted at the next quiet moment
- [x] The mandatory-update confirmation is reachable ONLY from an incompatible
      protocol skew, and the now-dead staleness dialog is removed rather than
      left in place unreachable
- [x] "Later" is the default button on the confirmation that remains
- [x] Liveness comes from the agent's own roster, and an unavailable roster is
      "unknown" and never authorizes a restart
- [x] The policy is pinned by unit tests in the `none` lane and by arms of
      `test/win32/agent-upgrade.ps1`

## Validation criteria

- [x] `evaluate` never returns `confirm_first` for a stale build with a live
      session, for ANY combination of stamps, roster and generation - pinned by
      the enumerated unit test "no build-stamp gap can ever produce a destructive
      restart of a live agent" (`none` + `win32` lanes).
- [x] Part 2 verified as already-correct rather than assumed: both confirmations
      go through `ConfirmDialog` with `default_cancel` left at its default
      `true`, which is MB_DEFBUTTON2 parity (focus + Enter on "Later").
- [x] Part 3 verified as already-correct rather than assumed: `App.agentSessionMix`
      counts `alive` sessions out of `requestSessions` (LIST_SESSIONS) and returns
      null on any failure, and `refreshLocalAgentIfStale` returns on that null
      with "agent session liveness unknown". No window count is consulted.
- [x] Acceptance: `test/win32/agent-upgrade.ps1` arm C (stale legacy agent + a
      live session => no dialog, same agent pid, no `agent restart: begin`, pane
      still responsive), arm H (the user's shape: restored windows + busy
      sessions + stale agent => all of it untouched), arm L (the draining arm no
      longer asks either), arm E (and it is genuinely adopted once idle).
- [x] The destructive-restart machinery keeps its end-to-end coverage: the T229 /
      T421 / T426 step-trail asserts moved from arms D/H onto arm J, which still
      reaches the same code through the skew.
