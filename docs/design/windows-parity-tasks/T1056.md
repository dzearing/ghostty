# T1056 - An app update can still restart the agent for a build-stamp gap alone, and liveness is read from this app's window count

## Summary

Main intake of 9a04b745c (upstream fix on origin/main, macos/ side; the Windows analog is src/apprt/win32/agent_upgrade.zig + App.zig:3722-3900). Mac's defect: an app update replaces the bundled agent binary while the running agent keeps every PTY attached, and agentIsStale read that build-stamp gap as a reason to restart it. It is not one - proto_version is negotiated in HELLO and a mismatch is fatal there, so an agent we can talk to has already agreed the wire contract, and everything since rides additive capabilities that degrade on their own. The 1.33.0 update took that path and tombstoned 95 live sessions for a binary refresh nothing required. Mac's fix, in three parts: (1) a stale-but-compatible agent is left strictly alone and adopted at the next natural cold start, with the mandatory-update prompt reserved for a skew the handshake actually flags as incompatible; (2) 'Later' becomes the prompt's DEFAULT button, so a stray Return during a post-update relaunch cannot end every session; (3) liveness comes from the agent's own LIST_SESSIONS instead of counting this app's windows - the window count reads 0 in all the wrong situations (a partial or slow restore, the user closing their last window while ninety pinned sessions keep running, a second app instance) and 0 meant a silent bootout; an unavailable roster is 'unknown' and never authorizes a restart. Work here: audit agent_upgrade.evaluate/applyDeferral against all three, decide which translate (the handoff path T907/T1044 migrates PTYs rather than killing them, so part 1 may already be softer on Windows - confirm rather than assume), fix what does not, and pin each part with a unit test in the none lane plus an arm in test/win32/agent-upgrade.ps1. Related: T1038 (the kill switch leaves the app waiting for a handoff that never comes).
