# T1224 - Ghoztty cannot start over Remote Desktop

## In plain terms

You install Ghoztty on a machine you are connected to remotely, double-click
it, and it tells you it could not start. There is nothing you can do about it -
no setting, no flag, no workaround. The terminal simply does not run on that
machine as long as you are connected remotely.

## What the user hit (2026-09-01)

Connected to a Windows machine with **Windows App** (Microsoft's RDP client)
from a MacBook. Installed Ghoztty. On launch:

> **Ghoztty could not start**
> Ghoztty ran into a problem while running the terminal and had to close.
> **Error: OpenGLOutdated**
> Start Ghoztty again. If it keeps failing, reinstall it - and please include
> this message in a bug report.

Reinstalling cannot help, because nothing about the install is wrong.

## Root cause

`src/renderer/OpenGL.zig` requires **OpenGL 4.3**:

```
pub const MIN_VERSION_MAJOR = 4;
pub const MIN_VERSION_MINOR = 3;
```

and `prepareContext` returns `error.OpenGLOutdated` when the loaded context is
older. An RDP session's display driver exposes a minimal OpenGL (classically
1.1) because the desktop is being encoded and shipped over the wire rather than
scanned out of a GPU. 4.3 is therefore unreachable, and there is **no second
path**: a search of `src/apprt/win32/` and `src/renderer/` finds no ANGLE, no
EGL, no software rasterizer, no D3D11 backend. One renderer, one hard version
floor, no degraded mode.

Worth stating plainly: **the dialog is T1177 working.** Before that task this
was a silent death with no window and no message. The user knew what happened
within a second, and the error name pointed straight at the cause. The
remaining defect is that being told is all that can happen.

## What to build

The standard Windows answer is **ANGLE** - translate GL ES to Direct3D 11,
which works over RDP because D3D11 is available there (falling back to WARP,
Microsoft's software rasterizer, when no GPU is presented). Alternatives worth
weighing before committing: a Mesa/llvmpipe software GL, or accepting a lower
GL version for a reduced-feature renderer.

Whatever the mechanism:

- **Detect rather than crash.** A context that cannot meet the floor should
  fall back, not abort. `GetSystemMetrics(SM_REMOTESESSION)` also names the
  case outright, but detection should key off the actual context, since a
  weak local GPU or a VM produces the same failure without RDP.
- **Say which renderer is in use**, in About and in the log, so a slow session
  over RDP is diagnosable instead of mysterious.
- **Keep the T1177 dialog for the genuinely impossible case**, and give it a
  remedy line that is true - "reinstall it" is not a remedy for this.
- **Mac parity:** macOS uses Metal and does not have this failure, so this is a
  Windows-only gap rather than a symmetric feature. No mac half to file.

## Validation criteria

- [ ] Ghoztty starts and renders over an RDP session, with an acceptance script
      that proves it rather than a manual check.
- [ ] The chosen fallback is exercised on a machine with no modern GL, and the
      renderer actually in use is reported in About and the log.
- [ ] A GL context below the floor selects the fallback instead of returning
      `error.OpenGLOutdated`.
- [ ] The startup dialog remains for a case where no renderer at all can be
      created, and its remedy text no longer says "reinstall it" for a cause
      reinstalling cannot fix.
- [ ] `ghoztty +list` and session restore behave the same over RDP as locally.
