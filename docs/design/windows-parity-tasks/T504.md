# T504 - Intermittent Zig panic in terminal.Screen test 'scrolling when viewport is pruned' crashes the none lane

## In plain terms

One of the core terminal tests crashes once in a while instead of passing or
failing cleanly. When it does, the whole test run goes red for a reason that
has nothing to do with whatever change was being tested, and the next person
wastes time re-running and second-guessing their own work.

## Summary

Observed 2026-08-05 22:15 during the T401 turn's standing floor, on a
**docs-only diff** (so the crash is in HEAD, not the change under test), with
nothing else running on the box (the T401 no-overlap rule was being followed):

```
error: while executing test 'terminal.Screen.test.Screen: scrolling when
viewport is pruned', the following command exited with code 3
CRASH 22:17:34 ghostty-test.exe pid=0x7E14 0x80000003 STATUS_BREAKPOINT
(Zig panic / segfault handler abort) in ghostty-test.exe+0x00000000000cc49e
```

Full log: `%TEMP%\floor-lane-none-20260805-221535-193.log` (box-local). The
watchdog's crash-catch re-ran the test binary under cdb once and it ran clean
(exit 0), and an immediate full `floor-lane.ps1 -Lane none` re-run was green —
so this is intermittent, likely order- or timing-dependent. `0x80000003` is a
Zig panic (or the segfault handler aborting), not a plain assertion failure,
so there is a real defect underneath: either the Screen pruning code or the
test has UB / a race.

Note this is a **shared-core** test (`src/terminal/Screen.zig`), not win32
apprt code — if the panic is in core scrolling/prune logic it affects the Mac
build too. Reproduce first (e.g. `scripts\crash-catch.ps1 -Lane none
-Attempts 6`, or loop the test binary with `-Repeat`), get the all-thread
stack from the minidump, then decide seat and scope from evidence.
