# T910 - A guard whose only unrunnable sections need Docker wedges every commit behind -NoGuardDue

## Summary

`test\win32\release-artifacts.ps1` has two sections (B1 FILEVERSION single
source, B2 portable ZIP layout) that need the msitools Docker image. Docker
Desktop is normally DOWN on this box on purpose (its WSL2 backend once reached
28 GB and buried the machine), so those sections SKIP — and `guard-due.ps1`
correctly refuses to stamp a run with skipped sections. The result is a guard
row that reports DUE forever, so `parity-tasks.ps1 validate` fails on it and
every turn that touches a covered file has to pass `-NoGuardDue`.

Measured 2026-08-17 in the T905 turn: the harness ran green (2 skipped), the
guard stayed due, and the commit went out under the escape hatch. That hatch
exists for "this harness genuinely cannot run here" — which is true of two
sections and false of the rest, and the all-or-nothing stamp cannot say so.

The gate is right to be strict; the granularity is what is wrong. Options to
weigh (mechanism, so this is the implementer's call): split the Docker-only
sections into their own guard row so the runnable half can stamp; or teach
`guard-due.ps1` a per-section/partial stamp that records WHICH sections were
covered and treats a Docker-gated skip as covered-with-caveat; or move the
Docker-dependent checks to CI, where Docker is available, and drop them from
the on-box row.

Note the failure mode to avoid: whatever is chosen must not make a skip that
matters (a section skipped because it broke) look like a satisfied guard. The
current strictness is protecting against exactly that.

## In plain terms

One of the self-checks can never say "I ran" on this machine because part of it
needs software we deliberately keep switched off. So the check that is supposed
to stop stale code from being committed gets waved through every single time —
which trains everyone to wave it through, including on the days it was right.

## Goals

- [ ] A green on-box `release-artifacts.ps1` run (Docker down) leaves the guard
      CURRENT for what it actually covered.
- [ ] A section that skips for any OTHER reason still leaves the guard DUE.
- [ ] `parity-tasks.ps1 validate` passes on this box without `-NoGuardDue`
      after a normal green run.

## Validation criteria

- [ ] With Docker down: run the harness, then `guard-due.ps1 check` reports the
      row CURRENT (or the Docker-only row is separate and reported as such).
- [ ] Negative control: force a non-Docker section to skip and confirm the row
      is still reported DUE — the gate must keep biting.
- [ ] `test\win32\guard-due.ps1` (or the harness that covers guard-due's own
      logic) green.
