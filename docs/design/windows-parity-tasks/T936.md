# T936 - Make the composer's image chips DOM nodes, with paste handled by the browser engine

## Summary

Image chips stop being hand-carried OLE/placeholder runs and become inline elements in the contenteditable, so deleting one is ordinary editing and clipboard image paste arrives as the page's own paste event instead of a Ctrl+V interception that has to swallow the WM_CHAR behind it. The attach paths that originate natively - the screenshot region selector and attachImage - post their PNG down the composer bridge. The thumbnail carousel keeps reading which image numbers are live from the document.

Split out of T830; read its `## Design` section first.

## In plain terms

When you report something from a viewer pane you can attach pictures, and each
one shows up in the box as the words `[Image #1]`. Until now those words were
just words: pressing Backspace next to one bit a bracket off it, and the
picture quietly stopped being attached while the text still looked like it
was. And pasting a screenshot only worked because the app was watching for
Ctrl+V itself and asking Windows for the clipboard's picture behind the
browser's back.

Now the chip is a real object in the box. The caret steps over it, selecting it
selects all of it, and one Backspace removes the whole thing — with the picture
leaving the report as it goes. Pasting is the browser's own paste, so a
screenshot, an image copied from a web page, or a picture dragged in from a
folder all land the same way, and a JPEG or a WebP is converted on arrival
instead of being refused. Clicking a thumbnail under the box now highlights its
chip rather than just putting the cursor near it.

## Goals

- [x] An image chip is one object in the text: the caret steps over it and one
      Backspace takes it away whole, picture and all.
- [x] Pasting a picture into the composer is the browser's own paste, not an
      interception the app has to run.
- [x] Dropping an image file into the composer attaches it too, and a picture
      that is not a PNG is converted rather than refused.
- [x] A picture too big to attach says so instead of being carried across the
      channel to be refused on the other side.
- [x] Clicking a thumbnail selects the whole chip it belongs to.
- [x] Everything downstream is untouched: the same buffer text, the same
      carousel, the same report.

## Validation criteria

- [x] The chip is a NODE and it deletes whole, proven against a real browser:
      the `host floor` test in `ViewerPane.zig` (win32 + agent lanes) pastes a
      PNG through the page, then puts the caret against the chip's trailing
      edge and presses Backspace — `image: one Backspace left 'just my own
      words '` in the win32 lane's log, with `[Image #` gone from the buffer
      entirely rather than `[Image #1` left behind, and the live image count
      back to 0.
- [x] The paste is the ENGINE's, end to end and with nothing stubbed: the same
      test dispatches a real `ClipboardEvent` carrying a `File` into the page,
      and the picture arrives in the pane's store — `image: pasted through the
      page, live=1`. The bytes crossed as the page's own base64 and were decoded
      by `viewer_feedback_page.imageMessage`; no native code looked at the
      clipboard.
- [x] The node serializes to exactly the chip and nothing else — the property
      everything downstream stands on: after the paste the pane's buffer is
      asserted byte-for-byte as `"just my own words\n[Image #1] "`, so a chip
      node that added a line break (the way a block element would) fails the
      test.
- [x] The chip's rebuild survives the buffer outliving the page: the seed
      carries `images: [{n,start,end}]` derived from `Store.live`, so an unknown
      or duplicated chip stays plain text exactly as it did on the RichEdit —
      `viewer_feedback_page.zig`'s "a seed names the runs of the text that are
      image chips" plus the js-agreement assertion (`none` lane, green).
- [x] The protocol is unit-tested with no browser: the `image` message's happy
      path, both refusals (`too-large`, `unreadable`), truncated base64, and an
      empty payload; `pick`'s wire form and that the script selects the NODE;
      and that both assets still agree on the chip's class, attribute and its
      `contenteditable="false"` — all in the `none` lane, green.
- [x] The composer does not grow by a line the text does not occupy: the chip
      rule is asserted to carry no vertical padding, margin or border, the same
      check the quote block has (the wrapped line count is scrollHeight /
      lineHeight).
- [x] Floor: `scripts\floor-lane.ps1` lib / none / win32 / agent ALL PASS,
      `ipc-p1/p2/p3` ALL PASS, `viewer-composer.ps1` ALL PASS (30),
      `viewer-feedback.ps1` ALL PASS (71) on the RichEdit fallback,
      `viewer-panes.ps1` ALL PASS (186), and the three guards the change made
      due (viewer-feedback, viewer-composer, printclient-audit) ALL PASS and
      re-stamped.

## What this deliberately did NOT do

- **The chip does not show the picture** the way Mac's attachment does — it
  shows its name, with the thumbnail in the carousel below. Now possible for
  the first time, filed as T986.
- **A pasted chip is still not undoable** (T983): it arrives as a native
  splice, which is a whole-document seed, and the browser's undo stack sees
  that as one opaque replacement.
- **The RichEdit fallback keeps its old paste path** — `tryPasteImage`, the
  swallowed `WM_CHAR` and `selectChipForDelete` are all still there, because
  the fallback is still the surface `viewer-feedback.ps1` drives. T937 retires
  them with the control.
- **An animated GIF loses its animation** when it is converted to a PNG on
  arrival. Attaching the first frame is better than refusing the file, and the
  report format has no animated type.
