# T680 - test\win32 sweep: scripts that dial IPC with no private endpoint (context-menu-real-input reads the user's panes)

## In plain terms

Some of the automated tests talk to whichever Ghoztty happens to be running
instead of the one they just built — which, when a person runs them, is the
terminal that person is sitting in. At best the test grades the wrong build and
reports a pass about it; at worst it reads the contents of the user's own panes,
or opens and closes windows in them. Every test should drive its own private
copy, and today a handful still do not.

## Goals

- [ ] Every `test\win32` script that makes an IPC call claims a private
      endpoint before the first one
- [ ] `context-menu-real-input.ps1` in particular stops reading whatever panes
      it finds
- [ ] The rule is checkable, not remembered — a script that regresses is caught
      by something other than a human noticing

## Summary

Filed 2026-08-09 from T89i/T485. T485 fixed `session-persistence.ps1` (it now
calls `Set-GhozttyTestIsolation` before its pre-flight) and asked for the sweep
its own note describes: "any other script under `test\win32\` that runs a CLI
call before dot-sourcing `CleanSlate.ps1` or calling
`Set-GhozttyTestIsolation` has the same latent defect."

A first pass over all 80+ scripts found **seven that never establish a private
endpoint at all** and still drive the CLI. Ranked by what a run actually does
to the box:

| Script | What it does unisolated |
|---|---|
| `context-menu-real-input.ps1` | `+list --json` **and `+read --name=…`** against whatever answers, plus a `Start-Process $exe` that loses the single-instance race — reads the user's pane contents |
| `log-append.ps1` | two `+list` runs; measures the wrong instance's log |
| `agent-autostart.ps1` | launches an app instance with no suffix |
| `path-selfheal.ps1` | ditto |
| `update-check.ps1` | ditto, plus `+version` |
| `crash-diagnostics.ps1` | ditto |
| `cli-shim-redirect.ps1` | `+version` only — no IPC, lowest risk, listed for completeness |

`test-desktop-spike.ps1` also has no isolation call of its own but runs under
`lib\TestDesktop.ps1`, which drops the variable — verify rather than assume.

## Details

The evidence above is a TEXT-ORDER scan (first `$Exe`/`+verb` line vs. first
isolation line), which is why it is stated as a candidate list and not a
verdict: the same scan flags ~13 more scripts as "LATE" purely because they
define a `Run-Cli` helper above the isolation call, which is correct code. Any
sweep has to check EXECUTION order — the first CLI *invocation*, not the first
mention.

That is also the argument for goal 3. The durable fix is not editing seven
files; it is making the property checkable, e.g. an `Assert-GhozttyIsolated`
that every script inherits, or a meta-test that greps for a CLI verb in a
script with no `Set-GhozttyTestIsolation`/`CleanSlate` and fails the suite. A
list curated by hand goes stale the next time someone adds a script.

## Validation criteria

- [ ] Each of the seven scripts above either claims a private endpoint before
      its first CLI call, or carries a comment saying why it cannot (with what
      protects it instead)
- [ ] `context-menu-real-input.ps1` run from a Ghoztty pane demonstrably reads
      its OWN pane: `Assert-GhozttyIsolated` passes in it
- [ ] A meta-check exists that fails when a `test\win32` script makes a CLI
      call with no isolation, and it is proven to bite (revert one fix, watch
      it go red)
- [ ] The affected scripts still pass after the change
