# T863 - Validate T514's bare-shell command forwarding on macOS (command = zsh on an agent-backed pane should un-nest and integrate)

## Summary

T514 changed shared core `Surface.init` (agent branch): an EXPLICIT
`config.command` that is nothing but a bare shell (single argv0 that
`shell_integration.detectShell` recognizes — `zsh`, `bash`, `fish`, `nu`,
`pwsh`, …) is now forwarded to the local agent as `OPEN.shell` instead of
`OPEN.command`. On Windows that un-nested `cmd /c pwsh` and re-enabled the
integration argv rewrite (validated on-box, section F of
`test\win32\gui-launch-command.ps1`).

The same code runs on macOS whenever session persistence makes panes
agent-backed: `command = zsh` used to travel as OPEN.command (`$SHELL -lic zsh`
nesting on the agent side) with env-only integration keyed off the INHERITED
$SHELL rather than the requested one. Post-T514 it should arrive as OPEN.shell,
spawn un-nested, and integration should detect against `zsh` itself.

Only the Mac seat can validate this end-to-end (the change is guarded by
`local_shell_integration`, which is true for the Mac's local agent too).

## In plain terms

If you set your preferred shell in the config file, panes should start that
shell directly — not buried inside another hidden shell — and features like
the terminal knowing your current folder should keep working. This was fixed
and proven on Windows; this task is the Mac double-check of the same shared fix.

## Validation criteria

- [ ] With `command = zsh` (or another bare recognized shell that is NOT the login shell) and session persistence on, a new pane's child process is that shell directly under the agent, not nested
- [ ] Shell integration is active in that pane (cwd tracking / prompt marks), keyed to the requested shell
- [ ] A `command` WITH arguments still runs as a command (unchanged behavior)
