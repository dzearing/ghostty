# T207 - GUI tests steal the user's foreground; isolate them from the interactive desktop

## Summary

User-reported 2026-07-30:

> "when you're running tests, you keep stealing focus. is there any way they
> could be run in docker image so i can use my compute"

The box is unusable while the loop runs its on-box scripts, which is most of
the time. Measured surface, `test/win32/*.ps1` (63 scripts):

- **35** call `GrabForeground` / `SetForegroundWindow`
- **36** drive the app with `SendInput` / `keybd_event`
- **6** capture pixels with `CopyFromScreen`

The foreground grabbing is not incidental and cannot simply be deleted:
`SendInput` delivers to whatever has focus on the calling thread's desktop, so
a test that types must own the foreground. T86 hardened this deliberately
across all 20 scripts that were then flaky. The fix is not to stop taking
foreground - it is to take foreground **somewhere the user is not**.

## Docker: no, and the reason matters

Windows containers have no interactive window station, no DWM, and no display
adapter. USER32 window creation works in session 0, but:

- DWM composition does not exist, so `DwmExtendFrameIntoClientArea`,
  `DWMWA_CAPTION_COLOR`, layered-window compositing, rounded-corner rendering
  and every pixel probe have nothing to compose against. All 6 capture scripts
  and every visual assertion in T202-T206 die here.
- No GPU/WARP surface for the terminal renderer.

Docker IS fine for the pure lanes (`zig build test`, the none lane) - but
those never touch the foreground, so containerizing them wins nothing. The
scripts that hurt are exactly the ones a container cannot host. Record this
so it is not re-proposed.

## Options, cheapest first

**A. A separate desktop (`CreateDesktopW`).** Win32 desktops are input
isolation boundaries: `SendInput` targets the calling thread's desktop, and a
window on a non-active desktop cannot take the interactive foreground. Launch
the app with `STARTUPINFO.lpDesktop = "ghoztty-test"` and have the harness
`SetThreadDesktop` onto it. Free, local, no VM, and it fixes all 35+36 focus
and input scripts.

  **Known risk, must be spiked before committing:** DWM composes only the
  *input* desktop. Windows on a background desktop are generally not composed,
  so `CopyFromScreen` will not work there, and the 6 pixel-probe scripts would
  need `PrintWindow(PW_RENDERFULLCONTENT)` instead - which T131 already found
  a trap in, and which is unreliable for GPU-rendered content like the
  terminal surface. Spike ONE capture assertion on a background desktop before
  planning the migration; if composition is genuinely absent, options are to
  keep the 6 capture scripts on option B, or accept running them in a batch the
  user can schedule.

**B. A Hyper-V VM.** A real session with a real DWM, so everything works
including capture. Costs VM lifecycle, artifact shuttling and wall-clock, and
Hyper-V's state could not be verified without elevation. This is the reliable
fallback for whatever option A cannot host.

**C. A second interactive session (RDP loopback).** Rejected: Windows 11 Pro
permits one active session, and connecting locks the console - it takes the
box away rather than giving it back.

**D. Shrink the GUI surface (do this regardless).** The project already
extracts pure geometry modules for exactly this reason - `banner_layout`,
`chooser_layout`, `split_geometry`, and now `tab_strip_layout`, whose unit
tests run in the none lane with no window at all. Every assertion pushed down
is one that never needs a desktop. This is the established pattern and the
cheapest partial win; it does not need to wait for A or B.

## Deliverables

1. Spike option A's capture question FIRST - it decides the shape of
   everything else. One script, one assertion, on a background desktop.
2. A shared harness helper that creates/reuses the test desktop, launches the
   app onto it, and cleans it up, so scripts opt in with one line rather than
   each rolling their own.
3. Migrate the 35 foreground scripts; keep a documented escape hatch to run on
   the interactive desktop for debugging.
4. Route whatever cannot work on a background desktop to option B or to an
   explicitly-scheduled batch, and SAY WHICH in the task log - a silent
   "some tests still steal focus" is the outcome the user is complaining about.
5. Continue pushing assertions into pure modules (D) as tasks touch them.

## Validation

- The acceptance test is behavioral and the user is the oracle: run the full
  script suite while typing in another window, and confirm focus is never
  taken. Assert programmatically too - poll `GetForegroundWindow` on the
  interactive desktop during a suite run and assert it never becomes a Ghoztty
  window.
- Every migrated script must still pass ALL PASS x3 on the test desktop, and
  its negative control must still fail - an isolated harness that has stopped
  actually driving the app would otherwise look like a clean pass.
