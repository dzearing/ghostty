# T568 - Test harness: no way to DEACTIVATE a window on the background desktop, so 'the focus ring goes away when the window does not have the keyboard' cannot be asserted

## In plain terms

Our on-box UI tests run on a hidden desktop so they never steal the screen from
whoever is using the machine. On that desktop there is no way for a test to say
"now click on that OTHER window" and have Windows really hand it the keyboard —
so any rule of the form "this only shows while the window is the active one"
has to be taken on trust instead of measured.

## Summary

Found while doing T289. The Activity Monitor's table draws design system
§2.2's focus ring, and the ring must vanish on `WM_KILLFOCUS` — when the panel
stops holding the keyboard at all, not merely when focus moves to another
control inside it. T289 asserts the second (Tab away, the ring goes) and left
the first unasserted rather than faking it, because:

- `Send-TestMouse` POSTS `WM_LBUTTONDOWN`. Real activation comes from
  `WM_MOUSEACTIVATE` on real input, which posted input never generates, so
  clicking another top-level window of the same app does not move the thread's
  focus.
- `SendInput` is dead off the input desktop (T207), so the usual escape hatch
  is not available either.
- `SetFocus` from the harness's own thread would need `AttachThreadInput`
  against a window on another desktop.

So today a whole class of claim — "chrome X appears only while the window is
active" — is unmeasurable here. That is worth fixing once, in the harness,
rather than dropping the assertion in each script that meets it.

## Goals

- [x] the harness can MOVE activation on the background desktop, both ways
      (a named window takes the keyboard; nobody holds it)
- [x] the move is verified off the input queue, never from a return value
- [x] the Activity Monitor's focus ring is asserted to LEAVE when the panel
      stops holding the keyboard, and to come back with it
- [x] the harness's own acceptance covers the new capability, with a control
      that inverts it

## Where

- `test/win32/lib/TestDesktop.ps1` — the `GhozttyTestDesktop` C# helper (its
  `ActiveHwnd` already reads activation on the background desktop, so the
  READ side exists; what is missing is the WRITE side).

Candidate mechanisms to evaluate: `SetForegroundWindow` from a thread bound to
the test desktop; `AttachThreadInput` + `SetFocus` from the harness's desktop
thread; or asking the app to do it (a test-only IPC verb) — the last is a last
resort, since a harness that drives the product through the product cannot
falsify the product.

## Validation criteria

- [x] A `Set-TestActiveWindow` (or equivalent) really moves the keyboard on the
      background desktop, proved by a positive control: the previously active
      window's `Get-TestFocusedWindow` goes to zero and the new one's does not.
      `test\win32\test-desktop-harness.ps1` ALL PASS (65 assertions):
      `Clear-TestActiveWindow` drives the thread's focus to literal 0,
      `Set-TestActiveWindow` puts it back, and activation MOVES between two
      top-level windows (`active=13242620` — the second window, not the first).
- [x] `test\win32\activity-monitor.ps1` section L gains the deactivation arm
      T289 could not write, and the "Not asserted, and why" note in T289 is
      removed. New L7: ALL PASS (182 assertions) — the ring measures 23 px
      painted with the table focused, 0 px with the panel deactivated, 23 px
      again when the keyboard comes back, and 0 px while a SIBLING window holds
      it.
- [x] A negative control that inverts it. `-NegativeControl` now inverts three
      claims instead of two and the run is red on all three, L7's included:
      `FAIL  L7 (inverted): the ring is still painted with the panel deactivated (0 px)`.

### Note on the criterion's wording

"the previously active window's `Get-TestFocusedWindow` goes to zero" is only
literally reachable through the DEACTIVATE arm. Every window in this app is on
the one UI thread, and focus is a property of a thread's input queue — so two
top-level windows read back the SAME focused hwnd, and moving activation
between them can never drive either read to zero. That is why the write side is
two calls rather than one: `Clear-TestActiveWindow` is the arm with the
unambiguous oracle (focus really is 0), `Set-TestActiveWindow` is the arm with
the realistic shape (a user clicking the window behind), and ACTIVE — which is
per-window — is what the second one is asserted against.
