# T723 - A WEDGED local agent (alive but not answering) aborts in-place recovery and nothing is known to retry

## In plain terms

If the background helper that owns your panes dies, the app notices and rebuilds
them. But if it is still *running* and merely stopped answering — swapped out,
stuck on a disk stall, frozen by a debugger or a suspend — the app tries to
re-dial it, cannot, and gives up. What is not established is whether it ever
tries again once the helper comes back. If it does not, your panes stay frozen
until you quit and relaunch, which is the exact failure in-place recovery was
built to remove.

## Goals

- [x] Measure what actually happens when the re-dial fails, rather than assuming
- [x] A recovery that could not re-dial retries, bounded and backed off
- [x] A retry stands down the moment the old link heals on its own
- [x] A pane that truly cannot be recovered says so instead of sitting silent
- [x] An acceptance arm that holds the wedge past the re-dial and proves the
      panes come back — and that fails without the fix

## Summary

Found while building T195's on-box settle-window test, and deliberately NOT
resolved there: it is a different defect from the one that task measures.

`recoverLocalAgentInPlace` (`src/apprt/win32/App.zig`) aborts with
`in-place recovery ABORTED: no local agent could be re-dialed` when
`reconnectForRecovery` → `findOrSpawn` cannot reach an agent. A wedged agent
reaches that path in a way a dead one does not: the process is alive, so its
single-instance guard still holds and no replacement agent can be spawned, and
its pipe accepts a connection the handshake then never completes.

The unknown is what happens next. The settle watch only opens on a link DOWN
EDGE (`onLocalAgentLinkChange`), and the link is already down by then, so the
one remaining chance is the `reconnecting → dead` transition posting a second
edge. Whether that reliably fires — and whether an agent that unwedges after the
abort is ever re-dialed at all — has not been measured.

## Evidence so far

T195's teeth check suspended the agent and held it past the settle window: the
verdict fired, recovery ran and SUCCEEDED, because the resume landed ~4s into
the re-dial and the handshake completed. That is the *near miss* — the same run
with a longer freeze would have taken the abort branch. Nothing was measured on
that branch.

## Validation criteria

- [x] Establish, by measurement, what the app does when the re-dial fails: does
      a later `reconnecting → dead` edge re-open the settle watch, and does an
      agent that recovers afterwards get re-dialed?
      **Answer: no, on both counts, and the abort was terminal.** Read from the
      code and then measured on the box. `Connection.withLink` fires the observer
      only when the state actually CHANGES, and the only transition left out of
      `reconnecting` is to `dead`, which `LinkState` reaches solely via
      `onSessionGone` — a server-sent DETACHED frame that a wedged or killed
      agent never sends. So no second down edge ever arrived,
      `beginAgentSettleWatch` was never re-armed, and nothing re-dialed. Measured
      with the retry compiled out (section I of `agent-recovery.ps1`): the abort
      fires, the agent is killed, and the panes are still dead 90s later — I6
      (surfaces rebuilt), I8 (fresh agent), I9 (sessions alive) and I10 (the
      pane answers a typed marker) all fail, while I7 (app pid) and I11
      (topology) still pass, which is exactly why neither can be the oracle.
- [x] If it does not: recovery retries (bounded, backed off) so an agent that
      comes back is picked up without an app relaunch, and a pane that cannot be
      recovered says so rather than sitting silently frozen.
      Policy is pure and unit-tested in `agent_recovery.zig`
      (`retry_delays_ms` = 2/4/8/15/30/30s, `retryDelayMs`, `evaluateRetry`);
      the mechanism is `App.armAgentRecoveryRetry` / `tickAgentRecoveryRetry`
      on `AGENT_RETRY_TIMER_ID`, armed at the one re-dial-failure site so every
      caller of recovery inherits it. A retry stands down the moment the old
      link heals on its own. Exhaustion sets a per-pane give-up banner
      (`reportAgentUnreachable`), and a pane already carrying a banner keeps it.
- [x] A section in `test\win32\agent-recovery.ps1` holding the suspend well past
      the re-dial timeout, then resuming: the panes must end up responsive.
      Section **J** is that arm; section **I** is the harder one it grew from —
      the same wedge, ended by KILLING the frozen agent, where a healed link
      cannot be the cure and only the retry can be. Both green
      (`AGENT-RECOVERY: ALL PASS (76)`), and section I is teeth-checked.
