# T356 - A cross-machine pane always shows the close confirmation: shellIsIdle has no way to ask the owning agent for descendants

## In plain terms

Close a pane that is running a shell on another machine and Ghoztty always asks
"a process is still running — close anyway?", even when the pane is just sitting
at an empty prompt with nothing running. A question that is always asked stops
being read, so the one time it matters it gets dismissed too. Panes running on
THIS machine already close quietly when they are idle; after this, so do panes
running elsewhere — and a pane that really is busy still asks.

## Goals

- [x] The machine that owns the shell reports whether anything is running under
      it, so the app has a real answer instead of a guess.
- [x] An idle cross-machine pane closes with no confirmation.
- [x] A busy cross-machine pane still confirms.
- [x] An older agent, or a pane whose connection has dropped, still confirms —
      never a wrong "idle" that quietly kills a running job.

## Summary

T41 skips the close confirmation for an idle shell by walking THIS box's
process table, so a cross-machine pane — whose shell lives on another machine —
can never be idle and always confirms.

## Details

`Surface.shellIsIdle` (`src/apprt/win32/Surface.zig`) answers false whenever it
cannot know, and a cross-machine pane is deliberately one of those cases:
`shellPid` returns 0 for `.remote` connections that are not `local`, because
that pid indexes the REMOTE machine's process table and matching it here would
name an unrelated local process. So the T41 improvement stops at the machine
boundary — closing an idle remote pane still asks.

The materials for the real answer already exist on the wire: the agent owns the
session's child and already enumerates processes for the Activity Monitor
(`src/remote/agent/proc.zig`). The shape is an additive query ("does session X
have descendants?") answered by the machine that can actually see them, gated
on a negotiated capability so an older agent degrades to today's behavior —
never a compile-time assumption (see CLAUDE.md, Agent contract).

Note the local-agent case is NOT affected: a session-persistence pane's child
runs under this box's `ghoztty-agent`, so its pid is a real local pid and T41
already covers it (asserted as section B/agent in
`test/win32/close-confirm-idle.ps1`).

*Validation:* extend `close-confirm-idle.ps1` with a relay/dialed section
(T319's `FakeRelay.ps1` + `PipeBridge.ps1` are the fixtures) — an idle remote
pane closes without a dialog, a busy one still confirms, and an agent that does
not advertise the capability still confirms both ways.

## Validation criteria

- [x] `close-confirm-idle.ps1` gains a `C/remote` section, dialed over TCP to a
      loopback `ghoztty-agent --listen`: an IDLE remote pane closes with no
      dialog, and a BUSY one (a `ping` running under it) still confirms. Busy
      and idle are judged from `Win32_Process`, never from anything the app says.
- [x] That section asserts `+list --json` reports pid 0 for the remote pane —
      proof the new path is what answered, not an accidental local walk.
- [x] The section's idle verdict follows a definite pushed `false`, not the
      app's never-told default: the pane is left idle long enough to be told so
      BEFORE the busy case runs, so the busy dialog is evidence of a transition.
- [x] `-NegativeControl` still fails the run (the script discriminates).
- [x] Agent unit tests: pushes on change only, silent for a peer that did not
      negotiate `session_busy`, silent for a shell absent from the process
      table, and re-pushes to a freshly re-bound viewer.
- [x] Protocol unit tests: `has_descendants` round-trips both values, a `false`
      is EMITTED rather than elided, an omitted field parses as null (unknown,
      not idle), and `session_busy` negotiates as an intersection.
- [x] Standing floor green: both `zig build test` lanes, `zig build test-agent`,
      P1–P3.
