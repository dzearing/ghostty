# T356 - A cross-machine pane always shows the close confirmation: shellIsIdle has no way to ask the owning agent for descendants

## Summary

T41 skips the close confirmation for an idle shell by walking THIS box's
process table, so a cross-machine pane — whose shell lives on another machine —
can never be idle and always confirms.

## Details

`Surface.shellIsIdle` (`src/apprt/win32/Surface.zig`) answers false whenever it
cannot know, and a cross-machine pane is deliberately one of those cases:
`shellPid` returns 0 for `.remote` connections that are not `local`, because
that pid indexes the REMOTE machine's process table and matching it here would
name an unrelated local process. So the T41 improvement stops at the machine
boundary — closing an idle remote pane still asks.

The materials for the real answer already exist on the wire: the agent owns the
session's child and already enumerates processes for the Activity Monitor
(`src/remote/agent/proc.zig`). The shape is an additive query ("does session X
have descendants?") answered by the machine that can actually see them, gated
on a negotiated capability so an older agent degrades to today's behavior —
never a compile-time assumption (see CLAUDE.md, Agent contract).

Note the local-agent case is NOT affected: a session-persistence pane's child
runs under this box's `ghoztty-agent`, so its pid is a real local pid and T41
already covers it (asserted as section B/agent in
`test/win32/close-confirm-idle.ps1`).

*Validation:* extend `close-confirm-idle.ps1` with a relay/dialed section
(T319's `FakeRelay.ps1` + `PipeBridge.ps1` are the fixtures) — an idle remote
pane closes without a dialog, a busy one still confirms, and an agent that does
not advertise the capability still confirms both ways.
