# T948 - A second Claude window committing with -A silently swallows the go-loop's staged work into its own commit

## Summary

Happened on 2026-08-17, during T850's turn, and cost that work its own commit.

Two Claude windows share ONE working tree — that is the normal arrangement
(go.md step 0: an unmarked window filing tasks or auditing is never a rival and
is never closed). The go-loop window had staged exactly its own eight paths and
was composing the commit message. Between the `git add` and the `git commit`,
the other window committed with `-A`, and git committed the INDEX — which by
then held both sets of changes. The result, `0d835a1b3
fix(t857): make the boost-off arm self-restoring…`, contains the whole T850
clipboard fix (new `clipboard_open.zig`, the ViewerPane lock, the win32
bindings) under a subject that describes none of it. It was pushed before this
was noticed, so it cannot be split.

Three separate things break when this happens:

- **The activity feed lies.** The dashboard builds each feed item from the
  commit that finished the work — subject as headline, first body paragraph as
  "what changed". A reader of that feed sees T857's message over T850's code.
- **`set-status -Commit <sha>` records a sha whose message is about something
  else**, so the task's own evidence trail points at a misleading artifact.
- **Unfinished code can ship.** The go-loop stages only after its lanes are
  green. A concurrent `-A` commits whatever is in the tree at that instant,
  including a half-written edit the other window was mid-way through — this
  time it was benign, but nothing about the mechanism makes it so.

Note the near-miss earlier in the same turn: an earlier `git commit` in the
go-loop window failed with `Unable to create '.git/index.lock': File exists`,
which is the same collision arriving loudly instead of silently. The lock only
covers the instant of the write, not the stage-then-commit window.

## In plain terms

Two assistant windows are working in the same folder at the same time. One of
them committed "everything in the folder" while the other was halfway through
preparing its own commit, so one window's work got filed under the other
window's description. Nothing was lost, but the project history now says the
wrong thing about what changed and why — and next time it could just as easily
package up code that was not finished yet.

## Fix directions worth weighing

- Have the go-loop commit only its own paths AND verify afterwards that the
  resulting commit contains exactly those paths, re-committing the remainder
  if not (detects the theft rather than preventing it).
- A repo-level commit advisory lock (the loop lock already exists and is
  pane-keyed) that any window takes for the stage→commit window.
- Forbid `git add -A` / `git commit -a` in this repo outright — a `pre-commit`
  hook that refuses a commit whose staged set spans paths the committing
  session did not touch this turn.
- Give the non-loop windows their own worktree, so a shared index is not the
  arrangement in the first place.

## Validation criteria

- [ ] A reproduction: stage paths in one session, run an `-A` commit from a
      second, and show the guard catches or prevents the swallow.
- [ ] The go-loop's own commit path proves its commit contains exactly the
      paths it staged, and says so loudly when it does not.
- [ ] `test\win32\go-loop-guard.ps1` covers the new behavior and stays ALL PASS.
