# T178 - remote-inherit.ps1: the remote-native --command split no longer reaches the agent (4 reds, pre-existing)

## Summary

`test/win32/remote-inherit.ps1` (the T68 remote-inheritance acceptance, last
recorded ALL PASS on 2026-07-18) is RED with 4 failures, and the root failure is
one: section `== 3`'s `+split --target=rem "--command=echo t68-split-marker"`
exits 0 but the marker never appears in the new pane. Sections 4 and 5 fail only
because they look for that same marker downstream (ctrl+t is expected to re-run
the parent pane's command; `+new-window --from-focused` likewise), so fixing
section 3 should clear all four.

**Proven pre-existing, not a T174 regression** (2026-07-30): a worktree built
from HEAD `f1f973b88` with no working-tree changes fails the identical four
assertions, and T174's only touch on this path (`buildRemoteInherit` now sets
`.shell` from the per-host defaults store) is a byte-for-byte no-op when no
store file exists — `Overrides.Remote.shell` already defaulted to null. Nothing
between 2026-07-18 and now re-ran this script: the standing floor is both test
lanes + `test-agent` + P1-P3, and remote-inherit is not in it.

Failing assertions, verbatim:

```
== 3: +split --target with a remote-native --command stays remote
  PASS split --target exit 0
  FAIL explicit command ran through the agent
== 4: ctrl+t - the new-tab keybind inherits the active pane's command
  FAIL new tab pane appeared
  FAIL new tab pane identified
== 5: +new-window --from-focused dials the SAME agent
  FAIL new window inherited the remote command
```

Everything else in the script passes, including section 2's live-cwd GET_CWD
inheritance and section 6/7's local-fallthrough and dead-agent paths — so the
remote transport, the split path, and the agent are all working; it is
specifically the explicit remote-native COMMAND that goes missing.

## Details

Where to look first (in likelihood order):

1. **The pane may be exiting before `+read` sees it.** A `--command` OPEN runs
   the command through the agent's shell; if the shell now exits when the
   command finishes, the pane is gone (or its scrollback empty) 3s later, when
   the script reads. That would also explain section 4's "new tab pane appeared"
   failing on a COUNT (the tab's inherited command pane may die immediately
   too). Check whether `waitAfterCommand`/hold semantics regressed — the Mac
   marks an explicit remote command so the agent keeps the session alive
   (`Machine.applyOpenDefaults` sets `waitAfterCommand = true` for exactly this
   reason); win32's `IpcHandlers` remote-split branch sets `.command` with no
   equivalent flag.
2. **The agent's per-shell argv convention for a command OPEN.** `echo
   t68-split-marker` through `cmd /c` prints; through `powershell -Command` it
   also prints. But a shell resolved differently (or an argv joined wrong)
   would silently produce nothing. `pty_child.zig` owns those conventions.
3. **The command may not be forwarded at all.** Confirm on the wire: run the
   loopback agent with logging and check the OPEN's `command` field for the
   split. The T99/T89 series reworked the IPC split's override batons; a
   regression there would drop the command while leaving cwd inheritance
   (section 2) intact — which is exactly the shape of this failure.

Candidate windows for the regression: T99 (IPC splits under the local agent),
T89d/T89f (session-persistence OPEN/ATTACH plumbing), T110/T111a (ring +
lock-cycle changes to the agent path).
