# T832 - T443's soak and data-breakpoint instruments run the test binary standalone, a condition the corruption has never once occurred in

## Summary

`scripts\test-binary-soak.ps1` and `scripts\crash-databreak.ps1` both take a
built test binary out of `.zig-cache\o` and run it **directly**. Every T443
crash ever observed came from `zig build` / `floor-lane.ps1` instead, and on
2026-08-14 that difference was measured rather than assumed:

| condition | binary | runs | crashes |
|---|---|---|---|
| standalone, 4 concurrent, 2026-08-14 | the exact `ghoztty-agent-core-test.exe` that had just dumped three times | 12 | **0** |
| standalone, everything T443 has ever cited | various | ~200 | **0** |
| under `zig build`, same box, 2026-08-14 | agent + win32 lanes | 26 | **5** |

`zig build` passes `--listen=-`, so `lib/compiler/test_runner.zig` runs
`mainServer()` — tests driven one per pipe message, with a blocking read and a
write around every single test — instead of `mainTerminal()`, which runs them
back to back off one stack frame. That is a different scheduling pattern and a
different set of stack leftovers under every test.

The consequence is that **both instruments measure a condition the defect has
never occurred in**. T443's whole "82 runs / 190+ runs / it will not reproduce"
body of evidence was produced this way, and an armed `crash-databreak` run would
have sat there for its 10-30 minutes and caught nothing, forever.

## In plain terms

The tools built to catch an intermittent test crash were running the tests a
different way from the way that makes them crash, so they could report "all
clear" indefinitely while the bug was still there. This makes the tools run the
tests the same way the build does, so a clean result means something.

## Details

The fix is to give both scripts a build-runner mode:

- **soak**: repeat `zig build test-agent` / `zig build test -Dapp-runtime=...`
  and classify each round, instead of (or as well as) running the exe. Slower
  per round; it is the only round that counts.
- **databreak**: cdb's `-o` follows children, so arming against
  `zig.exe build test-agent` can catch the crash in the child test process. The
  current `Get-LaneTestBinary` path stays for rehearsal against a staged wild
  write, which is what it was proven with.

Also worth doing: make the *default* the build-runner mode, so a future turn
cannot accidentally measure the wrong thing again, and have the standalone mode
print a one-line warning naming this task.

## Goals

- [ ] `test-binary-soak.ps1` can soak through the build runner and reports the
      mode it used in its SOAK summary line
- [ ] `crash-databreak.ps1` can arm against a build-runner lane run
- [ ] The standalone path says, in its own output, that it is the condition
      T443 has never reproduced in

## Validation criteria

- [ ] A build-runner soak of the agent lane reports a non-zero crash count on a
      box where the lane is currently failing (the condition is reproduced, not
      just plumbed)
- [ ] A standalone soak still works and prints the warning
- [ ] `test\win32\` acceptance for whichever script grows the mode, or a smoke
      run recorded here with its output
