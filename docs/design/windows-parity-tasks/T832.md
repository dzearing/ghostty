# T832 - T443's soak and data-breakpoint instruments run the test binary standalone, a condition the corruption has never once occurred in

## Summary

`scripts\test-binary-soak.ps1` and `scripts\crash-databreak.ps1` both take a
built test binary out of `.zig-cache\o` and run it **directly**. Every T443
crash ever observed came from `zig build` / `floor-lane.ps1` instead, and on
2026-08-14 that difference was measured rather than assumed:

| condition | binary | runs | crashes |
|---|---|---|---|
| standalone, 4 concurrent, 2026-08-14 | the exact `ghoztty-agent-core-test.exe` that had just dumped three times | 12 | **0** |
| standalone, everything T443 has ever cited | various | ~200 | **0** |
| under `zig build`, same box, 2026-08-14 | agent + win32 lanes | 26 | **5** |

`zig build` passes `--listen=-`, so `lib/compiler/test_runner.zig` runs
`mainServer()` — tests driven one per pipe message, with a blocking read and a
write around every single test — instead of `mainTerminal()`, which runs them
back to back off one stack frame. That is a different scheduling pattern and a
different set of stack leftovers under every test.

The consequence is that **both instruments measure a condition the defect has
never occurred in**. T443's whole "82 runs / 190+ runs / it will not reproduce"
body of evidence was produced this way, and an armed `crash-databreak` run would
have sat there for its 10-30 minutes and caught nothing, forever.

## In plain terms

The tools built to catch an intermittent test crash were running the tests a
different way from the way that makes them crash, so they could report "all
clear" indefinitely while the bug was still there. This makes the tools run the
tests the same way the build does, so a clean result means something.

## Details

The fix is to give both scripts a build-runner mode:

- **soak**: repeat `zig build test-agent` / `zig build test -Dapp-runtime=...`
  and classify each round, instead of (or as well as) running the exe. Slower
  per round; it is the only round that counts.
- **databreak**: arm against the test binary the build runner starts. (Filed
  expecting `cdb -o`; what actually works is attaching -- see "What landed".)
  The current `Get-LaneTestBinary` path stays for rehearsal against a staged
  wild write, which is what it was proven with.

Also worth doing: make the *default* the build-runner mode, so a future turn
cannot accidentally measure the wrong thing again, and have the standalone mode
print a one-line warning naming this task.

## What landed (2026-08-14)

**`test-binary-soak.ps1 -Mode auto|build-runner|standalone`**, defaulting to
`build-runner` for `-Lane` and `standalone` for `-Exe` (a bare exe has no lane
to build). A build-runner round is one `zig build <lane>` driven through
`floor-lane.ps1`, so the round inherits its CPU/stall watchdog and its crash
capture instead of this script growing a second copy of both; rounds are
sequential by construction, because an overlapped lane starves and wedges
(T401) and a wedge is not a data point. Each round is classified from
floor-lane's exit code plus a crash-pattern scan of the LANE log (`Select-String`,
not `Get-Content` -- a lane log is thousands of lines), and the summary now
leads with `mode=`.

**The pattern list gained `thread \d+ panic:`.** Four of the five aborts on
2026-08-14 were Zig panics, not faults, and a list that only knew about
segfaults classified this task's own signal as a red test.

**`crash-databreak.ps1 -UnderBuildRunner`** (also the default for `-Lane`)
starts the lane detached, waits for the build runner to launch one of the
lane's test binaries, and **attaches** cdb to it (`-p`). Everything after that
is the single-process arm/disarm recipe unchanged. The image path is read off
the RUNNING process rather than picked out of `.zig-cache` beforehand, which
removes the whole class of "armed against a binary nobody is running": a lane
that rebuilds, or a `-Filter` (which builds a different binary), is armed
correctly.

**Following children (`cdb -o`) was tried first and does not work here.** Both
failure modes were measured rather than reasoned about, and both are recorded
in the code so the next reader does not repeat the experiment:

- `g` returns once per child attach, so a script ending in `g; q` quits at the
  first child. The transcript showed `ModLoad: stompctl.exe` followed
  immediately by `quit:` -- which surfaces as `0 arm cycles, exit 0`, i.e.
  indistinguishable from a clean run. (`sxd ibp` stops the child breaking, and
  does not stop `g` returning.)
- `bu <module>+<rva>` is rejected outright: *"Bp expression contains symbols
  not qualified with module name"*. cdb reads a bare module name in a deferred
  breakpoint as a symbol, so the deferred form the whole approach needs is not
  available for a module-relative address.

Two smaller traps paid on the way, both now commented at the site: a
`param([string]$Args, ...)` never binds, because `$Args` is a PowerShell
automatic variable -- the lane silently ran a bare `zig build`; and the lane
command goes through a generated `.cmd` FILE rather than an argument list,
because `Start-Process` re-quotes arguments and mangles the embedded quotes in
`-Dtest-filter="x"` into a cmd that exits before it runs anything.

**Both standalone paths say what they are.** A warning naming this task, fired
only for OUR test binaries -- a fixture exe has no build runner to be the wrong
side of, and a warning that cries wolf stops being read.

**Both harnesses are now in `guard-due.ps1`'s coverage table**, which is the
part that keeps this fix from decaying: an instrument that has quietly stopped
measuring is indistinguishable from good news, which is the exact failure this
task is about.

## Validation criteria

- [x] A build-runner soak of the agent lane runs the lane, not the exe, and
      classifies each round — `test-binary-soak.ps1 -Lane agent -Runs 5
      -NoCatch` →
      `SOAK t832-buildrunner: mode=build-runner runs=5 concurrency=1 pass=5
      fail=0 crash=0` (335s / 191s / 186s / 186s / 187s), five real `zig build
      test-agent` runs.
      **The "non-zero crash count" half could not be met today and the reason
      is measured, not assumed:** the criterion's own precondition — "on a box
      where the lane is currently failing" — did not hold. The agent lane was
      3-aborts-in-5 this morning and is 0-in-5 this afternoon on the same tree.
      That is a T443 data point rather than a T832 failure, and it is logged
      there. What proves the classifier instead is the staged-crash arm of the
      acceptance script below, which drives the exact 2026-08-14 abort text
      through the real path and requires `crash=1` and exit 1.
- [x] A standalone soak still works and prints the warning — acceptance
      sections 4 (`mode=standalone runs=2 ... pass=2`, the warning, the summary
      caveat, a fatal NTSTATUS still classified CRASH, a plain nonzero exit
      still FAIL, and no warning at all for a fixture exe that is not one of
      ours)
- [x] `test\win32\` acceptance for both scripts —
      `test\win32\test-binary-soak.ps1` **ALL PASS (22 assertions)**, new;
      `test\win32\crash-databreak.ps1` **ALL PASS**, with a new section 8 that
      starts a fixture independently and proves the attach path catches the
      staged wild write (writer named, victim frame walked, dump on disk) plus
      the two new mode guard rails. Both are now rows in `guard-due.ps1`.
- [x] The build-runner databreak mode proven against a REAL lane, not only a
      fixture: `crash-databreak.ps1 -Lane none -Filter "terminal.Screen"
      -Symbol assertIntegrity -SignatureFilter "terminal.Screen"` started the
      lane, waited, attached to the `ghostty-test.exe` the build runner
      launched, and reported **84,356 arm cycles / 84,356 disarms over 193s,
      exit 0**. The same run against `verifyIntegrity` — T443's actual target —
      attaches correctly and then refuses at the probe, which is **T834**, not
      this task.
