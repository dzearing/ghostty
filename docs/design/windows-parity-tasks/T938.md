# T938 - A guard that is known-blocked invites a fresh duplicate task from every turn that meets it

## In plain terms

One safety check on this box cannot pass right now for a reason everybody
already knows and has already written down. Every session that runs into it
sees a red line with no hint that it is a known problem, does the responsible
thing, and files a fresh report for it. There are four reports of the same
thing. The check should say "this one is already known, it is T898" so the
next session spends its time elsewhere.

## Summary

`scripts\guard-due.ps1 check` reports `GUARD DUE <name>` with the changed files
and the command to run. That is exactly right for a guard that is due because
somebody edited its code. It is misleading for a guard that CANNOT be cleared
on this box — and there is one: `release-artifacts` only stamps on a zero-skip
run, two of its sections need Docker, and Docker is deliberately kept down
here. T898 has recorded that since 2026-08-16, with two designed remedies.

Since then the same gap has been filed three more times by three more turns —
T914, T920, T932 — all now closed as duplicates of T898. Each cost a turn the
work of writing it up, and each one landed in the M1 denominator before being
closed again. The report is doing this: it presents a known, tracked,
deliberately-accepted condition identically to a fresh regression, and step 5
of the turn ("every gap the work turned up becomes a NEW task") then does
precisely what it is told.

## Details

Wanted shape: a guard row can name an open task that explains why it is
blocked, e.g. `KnownBlockedBy = 'T898'`, and the report then reads

```
GUARD DUE release-artifacts: ... (known-blocked by T898 -- do not re-file;
    run it anyway if you can, then commit with validate -NoGuardDue)
```

so the escape hatch is still loud but the duplicate-filing reflex is answered
in the same line. The pointer must be VERIFIED rather than trusted: if the
named task is closed, the annotation disappears and the guard reads as an
ordinary due guard again, otherwise the note outlives the reason for it and
becomes the next false all-clear.

This is deliberately not a fix for the underlying block — that stays T898's
job, and this task depends on it only in the sense that it must not paper over
it. Both can be true: the guard is honestly due, AND the next turn should not
spend itself re-discovering why.

## Validation criteria

- [ ] A guard row can name a known-blocking task, and `guard-due check`
      prints that pointer beside the DUE line
- [ ] The pointer is dropped automatically once the named task is closed
      (negative control: close it in a fixture, the annotation goes away)
- [ ] A guard that is due for ordinary reasons is unchanged — no annotation,
      same wording, same exit code
- [ ] `test\win32\go-loop-guard.ps1` (or the guard-due harness) pins all three
