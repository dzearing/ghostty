# T452 - 6369 corrected PCIe errors in 30 days on root port 0:1D:0 - real hardware noise the user should know about

## Summary

Filed out of **T449** (2026-08-04). T449 needed to know whether the box was
faulting, and found that the Windows hardware error log is not quiet at all:

```
Microsoft-Windows-WHEA-Logger, id 17 (corrected hardware error)
6369 events in 30 days, 07-05 05:11 -> 08-04 04:48
all 6369 identical in kind:
  Component:    PCI Express Root Port
  Error Source: Advanced Error Reporting (PCI Express)
  Bus:Dev:Func: 0x0:0x1D:0x0
  Device:       PCI\VEN_8086&DEV_7A30&SUBSYS_88821043&REV_11
```

That is ~200 a day, every day, from one PCIe root port. T449's own evidence
section had recorded "zero WHEA events in 14 days" — that was wrong, and the
correction matters: these are Warning-level events, so a query filtered to
Error level finds nothing and reads as a clean bill of health.

**This is almost certainly not the cause of the crashes T443/T449 are chasing.**
They are *corrected* errors: the PCIe link detected the problem and recovered,
so no bad data reached the CPU, and they are confined to one link rather than to
memory or the processor. T449 separately measured 1.44 TB of self-verifying
computation with zero mismatches.

It is still worth the user knowing. A root port retrying 200 times a day is a
marginal link — typically a drive, a GPU, or a card that is reseatable — and
this box is the machine the whole Windows parity effort is validated on.

## In plain terms

The computer has been quietly logging about 200 hardware hiccups a day for the
last month, all on one internal connection. Windows caught and corrected every
one of them, so nothing has been lost, and this is not what has been crashing
the tests. But it is not normal, and it is the kind of thing that gets worse
rather than better.

**The device is named** (resolved 2026-08-04, during T449): the root port is
`Intel(R) PCI Express Root Port #9 - 7A30`, and the device behind it is a
**Samsung NVMe SSD controller** (`PCI\VEN_144D&DEV_A80C&SUBSYS_A801144D`).
So the link retrying ~200 times a day is the link to an NVMe drive — which is
also the class of device that carries the build cache and the repo.

## Goals

- [x] Confirm which volume that controller backs - it is **`D:`**, the drive
      holding the repo, the build cache and the work (verified by walking
      root port -> NVMe controller -> disk 1 -> partition, 2026-09-04)

      `scripts\whea-report.ps1` never filters by level and splits events into
      CORRECTED / UNCORRECTED / INFORMATIONAL / UNCLASSIFIED

## What the measurement says now (2026-09-04)

The link has not settled down in the month since this was filed - it has got
slightly busier:

| | 2026-08-04 (T449) | 2026-09-04 |
|---|---|---|
| corrected events / 30 days | 6369 | 8020 |
| rate | ~200/day | ~267/day |
| uncorrected events | 0 | 0 |
| distinct error sources | 1 | 1 |

The full chain, resolved end to end rather than inferred:

```
PCI\VEN_8086&DEV_7A30 at 0x0:0x1D:0x0
  = Intel(R) PCI Express Root Port #9 - 7A30
  -> Standard NVM Express Controller (PCI\VEN_144D&DEV_A80C, Samsung)
     -> disk 1: Samsung SSD 990 PRO 2TB
        -> D:
```

`Get-PhysicalDisk` reports both 990 PROs Healthy/OK, and there is still not a
single uncorrected event in the window - so this remains a marginal link, not a
failing one. But it is the link to the drive this whole effort is built on, and
it is the drive whose loss would cost the most.

## Suggested approach

`Get-PnpDevice` / `Get-CimInstance Win32_PnPEntity` filtered on the PCI location
`0:1D:0` names the child device. `DEV_7A30` is an Intel 600/700-series chipset
root port, so the interesting part is what is plugged into it.

Note this is a **report-to-the-user** task, not a code fix — nothing in ghoztty
can or should do anything about it.
