# T608 - QuickTerminal animation timer and the update-notification cleanup timer share id 3 on App.msg_hwnd

## Summary

Two unrelated timers are armed with the SAME id on the SAME window, so each
cancels the other. Found while adding the remote-reconnect poller (T366), which
needed a free timer id and therefore an audit of the taken ones.

## In plain terms

Two features quietly share one alarm clock. If Ghoztty tells you an update is
available while the drop-down terminal is sliding open, the slide stalls
part-way — and the update's tray icon can be left behind after its notification
is gone, because the alarm that was supposed to clear it went to the animation
instead.

## Details

`QuickTerminal.ANIM_TIMER_ID = 3` (`QuickTerminal.zig:19`) and
`App.NOTIF_UPDATE_TIMER_ID = 3` (`App.zig`) are both `SetTimer`'d on
`App.msg_hwnd`:

- `QuickTerminal.zig:149,165` arm id 3 at 16ms for the slide animation.
- `App.zig`'s update-notification path arms id 3 at 10s to remove the tray icon.

`SetTimer` with an existing (hwnd, id) pair REPLACES the timer, and `KillTimer`
kills whichever is there. So:

- Showing the update notification re-arms id 3 at 10s, stalling an in-flight
  quick-terminal animation.
- `msgWndProc` tests `QuickTerminal.ANIM_TIMER_ID` BEFORE the notification pair,
  so a genuine notification-cleanup tick is routed to `onAnimationTick` and the
  tray icon is never removed.

Every other id on that window is distinct (QUIT=1, NOTIF_DESKTOP=2,
LAYOUT_SYNC=4, AGENT_WATCH=5, remote reconnect=6); this is the one collision.

*Fix:* give the two ids distinct values and, so this cannot recur, collect every
`App.msg_hwnd` timer id in ONE place with a compile-time uniqueness assertion —
the ids are currently declared in three files with nothing checking them against
each other.

## Goals

- [x] The two colliding ids are distinct
- [x] Every `App.msg_hwnd` timer id is declared in one file, with a check that
      fails the BUILD on a duplicate
- [x] An acceptance harness that stops a future timer id from being declared
      anywhere else, with a negative control proving it can go red

## Validation criteria

- [x] The two ids are distinct, and every `App.msg_hwnd` timer id is declared in
      one place with a compile-time (or unit-tested) uniqueness check --
      `src\apprt\win32\msg_timer.zig`; `quick_terminal_anim` stays 3, the update
      balloon's cleanup moved to 15. Verified by `zig test
      src\apprt\win32\msg_timer.zig` (1/1 OK) and by the negative control in
      section D of the harness below, which injects a duplicate into a copy and
      shows the compile fail with `duplicate App.msg_hwnd timer id`.
- [x] An acceptance check that a quick-terminal slide completes while an update
      notification is on screen -- LANDED AS A SOURCE + COMPILE AUDIT,
      `test\win32\msg-timer-ids.ps1` (ALL PASS, 15 assertions;
      `-NegativeControl` fails as it must). The live version of this check
      cannot run on this box and would score a SKIP rather than an
      observation: the quick terminal is opened by a keybind and SendInput does
      not land on the background test desktop (T218), and this box draws no
      toasts at all (ToastEnabled=0, measured in `notification-click-real.ps1`),
      so the balloon cannot be put on screen to race the slide. The harness
      proves the property the symptom was made of instead -- the two ids differ,
      and no file outside the registry may declare an msg_hwnd timer id -- and
      the reasoning is written into its header so a later seat with a shell can
      add the live check knowingly. Filed as T1416.
- [x] Both zig test lanes and `test-agent` green; P1-P3 ALL PASS
