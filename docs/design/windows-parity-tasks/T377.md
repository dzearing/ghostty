# T377 - Banner paragraph, heading and list text do not wrap, and content runs under the collapse chevron

## In plain terms

Long lines in the pane's status banner get chopped off at the right edge
instead of flowing onto a second line, and the text runs underneath the little
collapse arrow in the corner. The user cannot read what the banner says, which
is the banner's whole job. Reported with a screenshot on 2026-08-02 and again
on 2026-08-04 - the second time as one of a handful of things "I keep coming
back to".

## Goals

- [x] A plain text block and a heading wrap onto as many lines as they need
- [x] A list item (bullet, ordered, checkbox) wraps, with continuation lines
      aligned to the shared marker gutter - not back under the marker
- [x] A very long run is capped at **3 lines** and the last visible line is
      tail-truncated with an ellipsis
- [x] The strip occupied by the collapse chevron is reserved: no block, cell,
      list row or heading ever paints under it
- [x] The wrapped height is what the renderer RETURNS, so the band, the pane
      inset and the 10-line cap all follow it

## Summary

User report 2026-08-02, with a screenshot: a long single-line banner is clipped
at the pane's right edge instead of wrapping ("... Log: /tmp" runs off the
card). Mac wraps a plain paragraph line; win32 does not.

VERIFIED root cause, not inferred. In `src/apprt/win32/BannerOverlay.zig` the
block renderer (`renderContent`, ~line 1008) handles `.text` and `.heading` by
calling `drawInlineLine` once at a fixed `line_h` and returning that height. It
is never handed `content_w`, so it has no width to break against.
`markdown.wrapTokens` - which already exists and is already correct
(`banner_markdown.zig:261`, unit-tested) - has exactly ONE call site in the
file: line 788, inside `renderTable`, against `widths[col]`. So table cells wrap
and nothing else does. List item content goes through `renderList` and
`drawInlineLine` the same way.

The fix is to run the same `wrapTokens` path for `.text`, `.heading` and
list-item content against `content_w` (which `renderContent` already receives
and passes to `renderTable`), and to return the WRAPPED height so the card
grows - the band height, the pane inset (`clampInset`) and the 10-line display
cap all derive from what this function returns, so a wrap that does not report
its height will paint over the terminal.

## Re-reported 2026-08-04, with two additions

The user sent a second screenshot of a `[go-loop]` banner. It shows the same
clipping in its checklist rows -

```
scripts/lib/CrashCatch.ps1 + scripts/crash-catch.ps1: catch a crash under cdb, kee
```

- cut mid-word at the card edge, no ellipsis, while the `Goal` and `Status`
rows in the SAME banner wrap correctly because they are table cells. That
contrast is what makes it read as a rendering bug rather than a limit.

Two requirements this adds to the original:

1. **Reserve the chevron column.** `renderContent` computes
   `const content_w = @max(client.right - inner * 2, 1);` (~line 1069) and
   never subtracts the chevron box (`chevronBox`, ~line 1038), so content
   overlaps it. The user's words: "the whole right side should be dedicated to
   the chevron column so that text never overlaps the chevron." Put the
   reservation in the pure geometry module (`banner_layout.zig`) next to
   `bandHeight`/`columnWidths` so it can be asserted, not inline in the paint
   routine.
2. **Cap a wrapped run at 3 lines with an ellipsis** - the user's explicit
   ask, and already the table-cell rule
   (`banner_layout.MAX_CELL_LINES` + `fitWithEllipsis`). Reuse that path
   rather than writing a second wrapper; a list row and a table cell wrapping
   by different rules is the same class of defect as the one being fixed.

## Constraints that are already written down and must hold

- The 10-line display cap counts a wrapped block once, the way a wrapped table
  row counts once.
- The card must never act as a minimum pane width - a single unbreakable token
  breaks mid-string, which is what `utf16PrefixBytes` is for.
- CLAUDE.md currently documents the single-line behaviour ("A cell that
  contains a task-list checkbox stays a single line ... like list checkbox
  rows"). A wrapping list row keeps its native checkbox on the first line, in
  the gutter; update CLAUDE.md in the same change.

## Validation

- Unit tests in the `none` lane for the wrapped height, the 3-line cap, the
  ellipsis on the last visible line, and the reserved chevron column - asserted
  at **1.0, 1.25, 1.5 and 2.0** scaling per the win32 design system.
- A real banner set through the CLI at a narrow pane and read back off a
  `PrintWindow` capture, in the manner of T123's "measure the band" test: a
  wrapped banner is measurably taller than a clipped one.

## What landed

**One wrap path, not two.** The wrap machinery that only `renderTable` could
reach was lifted into two methods every block now goes through -
`layoutInline` (tokenize -> break wide tokens -> `wrapTokens` -> cap at
`MAX_CELL_LINES`) and `drawWrapped` (paint the lines, tail-truncate the last
one, **return the height**). `.text`, `.heading`, list rows and table cells all
call the same pair, so they cannot wrap by different rules - which was the
defect the user could see: the `Goal`/`Status` rows of their screenshot wrapped
(table cells) while the checklist rows beside them were cut mid-word.

Everything that had been hardcoded to the base font (`tokenizeCell`,
`cellNaturalWidth`, `breakWideTokens`, `prefixFitting`) now takes a
`size_class`, so a heading is tokenized and broken in **its own** font rather
than measured in the body font and wrapped at the wrong words.

`renderContent` owns one scratch arena for the whole walk and hands it down;
`renderList` gained the available width and derives its content column as
`avail_w - gutter - GUTTER_GAP`, so continuation lines start at the shared
marker gutter. A list checkbox is the row's MARKER, drawn in the gutter, so a
task-list row now wraps like any other; only an *inline* checkbox still pins a
run to one line.

**The chevron column** is `banner_layout.contentWidth(client_w, inner, margin,
chevron_side, gap)` - pure, next to `bandHeight`/`columnWidths`, and used by
BOTH the measuring pass (`contentWidth`) and the paint (`contentWidthFor`), so
the band can never be reserved from one width and painted at another. It
reserves the strip only when the banner is collapsible, i.e. when a chevron is
actually drawn.
