# T377 - Banner paragraph, heading and list text do not wrap; only table cells do

## Summary

User report 2026-08-02, with a screenshot: a long single-line banner is clipped at the pane's right edge instead of wrapping ("... Log: /tmp" runs off the card). Mac wraps a plain paragraph line; win32 does not.

VERIFIED root cause, not inferred. In src/apprt/win32/BannerOverlay.zig the block renderer (renderBlocks, ~line 1008) handles .text and .heading by calling drawInlineLine once at a fixed line_h and returning that height. It is never handed content_w, so it has no width to break against. markdown.wrapTokens - which already exists and is already correct (banner_markdown.zig:261, unit-tested) - has exactly ONE call site in the file: line 788, inside renderTable, against widths[col]. So table cells wrap and nothing else does. List item content goes through renderList and drawInlineLine the same way.

The fix is to run the same wrapTokens path for .text, .heading and list-item content against content_w (which renderBlocks already receives and passes to renderTable), and to return the WRAPPED height so the card grows - the band height, the pane inset (clampInset) and the 10-line display cap all derive from what this function returns, so a wrap that does not report its height will paint over the terminal.

Constraints that are already written down and must hold: the 10-line display cap counts a wrapped block once the way a wrapped table row counts once; a checkbox mid-paragraph falls back to the glyph rather than the native box (CLAUDE.md says so for the wrapping case); and the card must still never act as a minimum pane width - a single unbreakable token breaks mid-string, which is what utf16PrefixBytes is for.

Validation: unit tests in the none lane for the wrapped height, plus a real banner set through the CLI at a narrow pane and read back off a PrintWindow capture.
