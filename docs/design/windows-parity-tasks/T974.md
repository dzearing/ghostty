# T974 - Nothing proves a pane stays alive when only the session manager restarts

## Summary

Since T909 a persistent session's ConPTY lives in a holder process that outlives the session manager, so an agent crash or upgrade should end with the panes re-attached to LIVE sessions and NO session-interrupted notice. test/win32/session-relaunch-notify.ps1 now kills the holders too (T922), because its subject is the REBOOT shape - which means the agent-restart shape it used to stand for is now measured by nothing. Add an arm (or a sibling script) that kills ONLY the manager and asserts the opposite outcome: the recorded command is still running, no notice appears in banner or scrollback, and the pane takes input on the same session.

## In plain terms

Ghoztty runs a small background program that looks after your persistent
terminals. It restarts sometimes - it crashes, or it gets upgraded. When it
does, nothing you are running should be disturbed: the build that was compiling
keeps compiling, your pane keeps its scrollback, and you never see a "session
interrupted" notice. That is how it behaves today, but nobody would find out if
it stopped: every test we had killed the background program together with the
processes holding your terminals, which is what a reboot looks like, not an
upgrade. So an upgrade that started closing people's panes would have shipped
green. This adds the missing test.

## Goals

- [x] A test kills ONLY the session manager and leaves the app and the PTY
      holders alone - the agent-restart shape, not the reboot shape
- [x] It proves the program the user was running is still the SAME process
      afterwards, not a re-executed one
- [x] It proves no pane claims an interruption, in the banner or in its own
      scrollback, and stays on the same session and still takes input
- [x] It has teeth: a documented switch reproduces the regression and the arm
      goes red
