# T229 - Confirming the agent-upgrade dialog kills the app: no windows come back, no log line, no explanation

## Summary

User report, 2026-07-31, verbatim: *"When I select upgrade, ghoztty does not
reopen afterwards. Dialog disappears, I have no idea what happened."*

The T147 mandatory-confirmation dialog ("Restart the Ghoztty background
terminal process?") promises the panes come back:
`promptAndRefreshLocalAgent` (`src/apprt/win32/App.zig:1611`) calls
`restartForUpgrade()` and then `recoverLocalAgentInPlace()`, whose whole job is
to rebuild the windows in place on the fresh agent. On the box it does not
happen. The dialog vanishes, the windows are gone, and the user is left with no
Ghoztty and nothing on screen that says why.

This is the worst possible shape for a destructive confirmation: the user is
asked to consent to losing their sessions, consents, and then loses the app
too, silently.

## Evidence (on-box, from the user's own `%LOCALAPPDATA%\ghoztty\ghoztty.log`)

VERIFIED by reading the log, not inferred. The confirm path has run **twice**
and behaved identically both times:

```
line 133296: warning(win32): user confirmed destructive agent refresh (running 20260728-349eba4f6 -> bundled 20260730-e69d41755, 3 live session(s))
line 133297: info: ghoztty version=1.4.0-users-dzearing-windows-amd64-+9968a62d9   <-- a NEW PROCESS

line 144775: warning(win32): user confirmed destructive agent refresh (running 20260730-e69d41755 -> bundled 20260730-c8449522f, 2 live session(s))
line 144776: info: ghoztty version=1.4.0-users-dzearing-windows-amd64-+28b76b6c5   <-- a NEW PROCESS
```

The line immediately after each confirm is a fresh app boot banner. **The old
process never logs another line.** In particular:

- `grep -c "in-place recovery"` over the ENTIRE log returns **0**. That string
  is `recoverLocalAgentInPlace`'s unconditional closing line
  (`App.zig:1876`, "in-place recovery: rebuilt {d} window(s)"), which it
  reaches even when it rebuilds zero windows. It has never been printed - so
  the function has never run to completion, on this path or on T145's
  crash-recovery path.
- No shutdown / quit lines, no window-close lines, no panic text.

So the app dies (or exits) somewhere between `restartForUpgrade()` returning
and `recoverLocalAgentInPlace()` finishing.

## Suspects (INFERRED - none confirmed yet, investigate in this order)

1. **The silent early return.** `recoverLocalAgentInPlace` has exactly one
   exit that logs NOTHING: `const conn = self.local_agent.reconnectForRecovery()
   orelse return;` (`App.zig:1826`). If the re-dial loses a race with the
   just-terminated agent's single-instance guard / named pipe teardown, the
   function returns with every surface still pointing at a retired connection.
   The panes are then dead, their windows close, and with
   `quit-after-last-window-closed` the app quits itself
   (`App.zig:3903-3917`) - which matches "dialog disappears, nothing comes
   back" exactly, and leaves no log line anywhere. **Highest prior.**
2. **A crash inside the rebuild.** `rebuildWindowInPlace` swaps every pane's
   termio while the old connection's reader thread is unwinding. A crash there
   would also produce a log that simply stops. Distinguish from (1) by whether
   a WER/crash entry exists for the pid, or by adding the log line in (4).
3. **The old connection's teardown posting window-close messages** that get
   pumped AFTER the rebuild, closing the freshly rebuilt panes.

## Direction

The fix has two independent halves, and BOTH are required:

1. **Make the outcome observable.** Every exit from
   `refreshLocalAgentIfStale` -> `promptAndRefreshLocalAgent` ->
   `restartForUpgrade` -> `recoverLocalAgentInPlace` must log, in the T201
   spirit that already applies to the decision. The silent
   `reconnectForRecovery() orelse return` is the specific line that made this
   bug invisible for two occurrences; it must never be silent again.
2. **Make the outcome correct.** The dialog promises the windows come back, so
   they must. If the in-place rebuild cannot be made reliable, the honest
   fallback is an explicit relaunch of the app (or a visible error dialog
   saying the restart failed and what to do) - never a silent disappearance.
   Suppress `quit-after-last-window-closed` for the duration of the refresh so
   a momentarily empty window list cannot quit the app out from under the
   rebuild.
3. **Never re-execute the old commands on the way back.** See **T230** - the
   rebuilt panes must come up as fresh shells with a notice, not as RELAUNCHes.
   T229 owns "the app survives and the windows return"; T230 owns "what is in
   them".

## Validation

- Reproduce deliberately: run an older agent (or fake the stamp) so
  `evaluate` returns `.confirm_first` with >= 2 live sessions, confirm the
  dialog, and observe the app on the box.
- The log must contain, in order: the confirm warning, a
  `restartForUpgrade` result line, and an `in-place recovery: rebuilt N
  window(s)` line with N == the number of persistent windows that were open.
  A run that produces the confirm line and then nothing is a FAIL, and that is
  exactly today's behavior.
- The windows must be on screen after the dialog closes, with the same layout
  and split ratios.
- Negative control: force `reconnectForRecovery` to fail and assert the user
  sees an explicit failure (dialog or in-pane notice), not an empty desktop.

## What shipped (2026-08-01)

Both halves the Direction asked for, plus a third the investigation forced:
**the log sink itself was losing lines, so the evidence this task rests on —
and every diagnostic added for it — could not be trusted.**

- **`main_ghostty.zig` — the shared log is an ATOMIC APPEND now.** The writer
  did `createFile` + `seekFromEnd(0)` + `write`, which is not an append: two
  processes that both resolve end-of-file to N both write AT N and the later
  one overwrites the earlier one's bytes. `ghoztty.log` is written concurrently
  by the GUI, the agent, and every one-shot `ghoztty +...` CLI. New
  `openAppendW` opens with `FILE_APPEND_DATA` (and *not* `FILE_WRITE_DATA`),
  which Windows defines as placing each write at the current end of file as one
  operation.
- **`LocalAgent.retire` — the teardown runs OFF the GUI thread.**
  `Connection.shutdown` **joins** the connection's writer, control-reader,
  data-reader and heartbeat threads, and every caller of `retire` is on the GUI
  thread. A peer that does not exit does not slow the app, it WEDGES it — no log
  line, no crash — which is the observed signature exactly. Safe to move because
  a retired connection is deliberately never freed; `deinit` (the one place it
  IS freed) now joins the teardown threads first. Spawn failure falls back to
  the old inline teardown, out loud.
- **`LocalAgent.restartForUpgrade` — a step trail.** `begin` → `retiring the
  shared connection` → `terminating agent pid`. A hang leaves no record unless
  the step before it announced itself; the last line present now names the step
  it stopped in (T268 is the runbook).
- **`App.recoverLocalAgentInPlace` returns `?usize` and no exit is silent.**
  The `reconnectForRecovery() orelse return` this task is named for now logs
  `in-place recovery ABORTED: no local agent could be re-dialed` at `err`
  level; the already-recovering and capture-failed exits log too. The confirmed
  path logs its OUTCOME (`destructive agent refresh finished: N window(s)
  rebuilt`), not just its intent.
- **A failed refresh TELLS the user** (`showAgentRefreshFailed`) in the same
  modal channel that asked for consent, instead of leaving an empty desktop.
- **The app cannot quit itself out from under the rebuild.**
  `agent_refresh_depth` (a count, not a flag) suppresses `startQuitTimer` for
  the duration and re-asks once the rebuild settles. Applied to all three
  recovery callers, not just the confirmed one. Defence in depth on this box —
  `quit-after-last-window-closed` defaults to **false** off Linux and the user's
  config is the untouched template, so this is not what killed their app.

PRE-FIX build (saved before the edit)  24 writers => 214 lines, expected 216   N1 PASS (inverted)

Two lines gone in one four-second window, silently. That is the sink T229's
primary evidence ("the app never logged another line") was read from.

**`test/win32/agent-upgrade.ps1` ALL PASS, 82 assertions, exit 0** (was 53).
New **arm H** is the user's shape, which arm D never was: the app RESTORES its

## What is NOT proven — read this before closing the loop

**The field failure was never reproduced.** Four shapes were tried on box (arm
D's fresh window; restored windows with 3 live sessions across 2; the same with
every pane streaming; the same again under a genuinely older agent binary built
with `-Dagent-version=`) and every one of them rebuilt correctly with the app
surviving. So the async-teardown change is a fix for the LEADING HYPOTHESIS, not
a fix for a defect anyone has seen fail.

Two findings narrow it, both VERIFIED:

- **It did not crash.** No `Application Error` / `Application Hang` / WER event
  exists for `ghoztty.exe` anywhere near the three confirms (the ghoztty crash
  events in that window are all Debug-build test binaries at a single
  breakpoint offset). So it exited cleanly — nothing on that path logs, so that
  is indistinguishable — or it hung.
- **The release configuration cannot be tested on this box at all** while the
  user's own agent is running: the single-instance guard is a named mutex keyed
  on the user SID, and unlike its POSIX sibling it has no override. Filed as
  **T269**, and it is why the release repro could only get as far as proving it
  could not run.

Follow-ups: **T268** (the runbook for the next occurrence — the step trail names
the step, and a `cdb` stack ends the guessing), **T269** (release-lineage
testability), **T270** (the log still has no timestamps or pids, which is what
made the archaeology in this task so expensive).
