# T1280 - test-desktop-spike.ps1's posted-input assertions flake, so the harness's own regression test can read as a product regression

## In plain terms

The small script that proves the hidden test desktop works fails now and then
for no reason - press a key, nothing arrives, run it again and it is fine. It is
the script everything else about that desktop is trusted on, so a random red
here looks like the app broke when nothing did.

## Summary

Observed on 2026-09-02 while closing [[T1115]]. Three consecutive runs of
`test\win32\test-desktop-spike.ps1` against the same Debug build at the same
commit:

| run | verdict |
|---|---|
| 1 | `2 FAILED / 14 passed` - `posted WM_KEYDOWN reaches the terminal` and `a posted ctrl+shift+t chord fires its keybind (tabs=1, want >=2)` |
| 2 | `ALL PASS (16 assertions)` |
| 3 | `ALL PASS (16 assertions)`, and green again through `suite-run.ps1` |

Both failures are the same event: the posted key never reached the app. The
chord assertion is downstream of the plain post, so one cause produces both
lines. The capture assertions were unaffected in all three runs.

The likely mechanism is a race between the launch and the input, not a
capability gap - the script posts as soon as it has found the window and taken
focus via `AttachThreadInput` + `SetActiveWindow` + `SetFocus`, and a window
that has been created but whose surface/keybind wiring has not finished
initialising will drop the message with no error. There is a fixed
`Thread.Sleep(150)` after the focus dance and a `Thread.Sleep(400)` after the
posts; neither waits on anything observable.

Why it matters more than a normal flake: this script is the certificate for the
background-desktop harness (`lib\TestDesktop.ps1`) that ~50 acceptance scripts
now run on. A red here is read as "the desktop harness regressed", and one that
is red a quarter of the time trains everyone to re-run rather than look - which
is exactly how [[T1115]]'s real, month-old wrong answer survived in the same
file.

## Where

- `test/win32/test-desktop-spike.ps1` - the focus dance and the two posted-input
  assertions
- `test/win32/lib/TestDesktop.ps1` - the shared post/focus helpers the harness
  scripts use, if the fix belongs there instead

## Goals

- [ ] Establish the actual cause with a repeat run (e.g. 20 iterations, logging
      the focus/tab state at each step) rather than assuming the race.
- [ ] Replace the fixed sleeps on the input path with a wait on something
      observable - focus actually held, or the app answering over IPC - so the
      assertion cannot fire before the app can receive.
- [ ] Confirm the fix with a repeat run that is green N-for-N.

## Validation criteria

- [ ] the cause is recorded in the task with the measurements that established it
- [ ] `test\win32\test-desktop-spike.ps1` is ALL PASS 20 runs out of 20
- [ ] no fixed sleep remains on the input path as the thing the assertion depends on
