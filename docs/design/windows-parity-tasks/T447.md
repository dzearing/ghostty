# T447 - The pane's working directory is never surfaced in the chrome on Windows (Mac shows it as the titlebar proxy icon)

## In plain terms

Ghoztty already knows which folder each pane is sitting in - the shell tells
it every time you `cd`. On a Mac that folder is right there in the title bar
as a little document icon you can hover, click, or drag into another app. On
Windows the app keeps the folder to itself: it will answer if a script asks
for it, but nothing in the window ever shows you. With several tabs open on
several checkouts, there is no way to tell them apart at a glance.

## Goals

- [x] The pane's current folder is discoverable from the chrome, without
      running a command (hover a tab: a native tooltip shows the focused
      pane's cwd, `~`-abbreviated and middle-elided; a viewer pane's tab
      shows its location)
- [x] It updates as the shell changes directory (livePwd-first, so cmd.exe
      without OSC 7 tracks too), and is right after a session restore
- [x] Covered by unit tests (pure `tab_tooltip.zig`, none lane) and an
      on-box acceptance script (`test\win32\tab-tooltip.ps1`). Scaling note:
      the tooltip is a NATIVE control (system-drawn, no owner-drawn
      geometry), so there is no per-scale layout module to assert — the one
      geometric input (the 4 DIP clearance under the strip) scales with
      `self.scale`.

## Validation criteria

- [x] Hovering the tab logs/derives the pane's starting directory,
      `~`-abbreviated — `tab-tooltip.ps1` arm A (ALL PASS)
- [x] The text follows a `cd` in a shell that never reports OSC 7

- [x] The text is correct right after a session-persistence restore

## Summary

Split out of T28 (2026-08-04). The `.pwd` action itself is NOT the gap - it
was wired by T111b and is handled at `App.zig:4024-4033`
(`Surface.setPwd`, `Surface.zig:1572`). The gap is that nothing in the win32
chrome ever renders the cached value; it only reaches `+list` and the IPC
handlers (`IpcHandlers.zig:1503-1542`).

## Details

**Mac's surfacing is `pwdDidChange`** (`BaseTerminalController.swift:1712-1721`),
and all it does is set `window.representedURL` when
`macos-titlebar-proxy-icon == .visible`. That is the AppKit proxy icon: a
draggable document icon in the title bar with a command-click path popup.
Windows has no such control, so this is the "translate the feature, not the
implementation" case that CLAUDE.md calls out.

**Options for the Windows-native equivalent, with costs:**

- **Tab tooltip.** Hovering a tab shows its pane's cwd (abbreviated with
  `~`). Cheapest, discoverable by habit, and matches how Explorer and VS
  Code label tabs. Costs: hidden until hover, and a tab holds a whole split
  tree so it must name the focused pane's cwd or say nothing.
- **Caption-bar subtitle.** A dimmed abbreviated path after the title in the
  caption band. Always visible, closest to Mac's placement. Costs: eats
  horizontal caption space the tab strip already competes for (T234 fought
  for that space), and it must not truncate the title.
- **Context-menu entry / palette subtitle only.** Mac's command palette
  already shows pwd as a subtitle (`TerminalCommandPalette.swift:239-241`)
  and Windows should match that regardless - but on its own it does not
  discharge "surfaced in the chrome".

Recommend the **tab tooltip** plus the **palette subtitle**, and file a
decision (`parity-decisions.ps1`) rather than picking silently: this is a
visible chrome choice the user may want to overturn, and the caption
subtitle is the option closest to Mac.

**Check first whether win32 tabs have tooltips at all** - if not, that
plumbing (`TTM_ADDTOOL` / `TTN_GETDISPINFO` against the tab strip's hit
rects) is the bulk of the work, and it is reusable for truncated tab titles.

**Design system** (`docs/design/win32-design-system.md`) applies to any
painted affordance; a native tooltip inherits the system's own styling and
should be left alone rather than owner-drawn.

**What was built (2026-08-07).** The tab tooltip, as recommended: a native
comctl32 `tooltips_class32` control in TRACK mode (the strip already owns
hover tracking, so the app decides show/hide; no tool-rect sync, no
TTM_RELAYEVENT). Armed on tab-hover with the system double-click time as
the delay; positioned 4 DIP under the strip at the tab's left edge; hidden
on hover-leave, tab click, and tab-switch/tree-change
(`resetPointerTransients`). Text = focused pane's cwd via **livePwd-first**
(T185 — cmd.exe never reports OSC 7, the cache alone stays frozen at the
start dir), else the OSC-7 cache; viewer panes report `viewer.location`.
Derivation is pure (`src/apprt/win32/tab_tooltip.zig`: home→`~`
case-insensitively on whole components, middle-component elision to 96
bytes keeping root+leaf, UTF-8-safe cuts), registered in `apprt.zig` for
the none lane. Dark mode: `DarkMode_Explorer` applied when
`DarkMode.modeForTheme` (+ OS apps theme for `system`) says dark — decided
at creation; T557 tracks re-theming on a mid-session flip. The debug
oracle `tab tooltip tab=N text=...` logs at hover-change because the
background test desktop cannot hold a hover across the show delay (T233).
Palette half: the Mac's pwd subtitle rides its `Focus:` jump entries,
which win32's palette lacks entirely — filed as T555 rather than shimmed.
T556 tracks reusing the tip for truncated titles. Decision D24 records the
affordance choice with caption-subtitle and palette-only as alternatives.

*Validation:* a unit test for the path-abbreviation helper (home to `~`,
long-path elision) in the `none` lane; an on-box acceptance script that
`cd`s in a pane and asserts the surfaced value follows, including after a
session-persistence restore. Both `zig build test` lanes,
`zig build test-agent`, and P1-P3 stay green.
