# T744 - four acceptance launches never declare session persistence, so persistence-flag.ps1 is red

## In plain terms

There is a check that makes sure each of our automated tests says out loud
whether it wants Ghoztty to reopen the windows from last time. Four tests never
said, so the check itself is failing — which means the next person to run it
cannot tell a new mistake from this old one.

## Goals

- [x] Every launch in the suite says what it wants from window-restoring, in a
      way the checker can see.
- [x] The check itself goes green, so a future failure means a new mistake.
- [x] The tests that were changed still pass, measured rather than assumed.

## Summary

`test\win32\persistence-flag.ps1` fails A1 (`undeclared: 4 of 169`). Found while
validating T506 (which added a script of its own and had to pass this audit).
Nothing about T506 caused it: the four sites are in files T506 never touched, so
this landed with the turns that wrote them and nobody re-ran the audit.

The undeclared sites, all `Start-OnTestDesktop` GUI launches:

- `test\win32\agent-attach-refused.ps1:276` — section C's control launch.
- `test\win32\url-scheme.ps1:359, 368, 381` — the three activations of the
  coalescing arm (two links, then the positive control).

Each needs one of the three declarations T158 defines: the flag itself, a
variable carrying it, or a `# persistence: <reason>` marker. Judge per site
rather than blanket-adding `--session-persistence=false` — `agent-attach-refused`
restores a manifest ON PURPOSE, so its launch may genuinely want persistence on
and just needs to say so; the `url-scheme` activations open no terminal at all
(an activation exits without becoming one), which is exactly the marker case.

## Validation criteria

- [x] Each of the four sites declares its intent, and the declaration matches
      what the section is actually testing. **Five by the time it was fixed** —
      `session-resume-offset.ps1:255` arrived with T739. Verified by reading each
      section: the two agent/session sites want persistence ON (one restores the
      manifest the section before it wrote, one writes the manifest the cycles
      below read) and say so; the three `url-scheme` sites are URL activations,
      which `runUrlSchemeActivation` answers and exits before the single-instance
      bind (`src/main_ghostty.zig:86`), so they open no terminal and never reach
      the restore path.
- [x] `test\win32\persistence-flag.ps1` is ALL PASS. Verified: `ALL PASS (20)`,
      and the sweep called directly reports `total=186 undeclared=0`.
- [x] `test\win32\agent-attach-refused.ps1` and `test\win32\url-scheme.ps1` are
      still ALL PASS (a declaration that changes behavior has to be re-measured,
      not assumed). Verified on the box: `url-scheme` ALL PASS (32 checks),
      `agent-attach-refused` ALL PASS (24 checks), and the third touched script
      `session-resume-offset` ALL PASS (68 assertions).
