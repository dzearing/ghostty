# T565 - The dashboard page's 74k of inline JS has no DOM-level test, so a broken button is only found by a human clicking it

## Summary

task-dashboard.js has a --selftest for its data layer and test\win32\parity-tasks-seat.ps1 section O now drives the server end to end, but nothing exercises task-dashboard.page.html's rendering or its handlers. T564 added a two-step Mark unblocked button whose arming step is verifiable only by clicking it. A headless check (jsdom, or a Playwright/headless-Edge pass over the served page) would cover render-without-throwing plus the handful of stateful controls: the two-step unblock, the stale reset, decision resolve, and the new-task form.

Landed 2026-09-05 as `test\win32\dashboard-dom.ps1`. One item on that list does
not exist: there is no new-task form in the page, and no `/api/new` on the
server - the only two write endpoints are `/api/status` and `/api/resolve`, and
both are covered. If a filing form is ever added, its check belongs in this
harness.

## In plain terms

The status dashboard is a web page with a lot of code behind its buttons. Every
other part of the tracker is tested, but the buttons were not: if one of them
quietly stopped working, the only way anyone would find out is by clicking it
and noticing nothing happened. Now a test opens the page in a real browser,
clicks the buttons that actually change something, and checks that each one did
what it says on the label.

## Goals

- [x] the page is driven in a REAL browser, not a mock of one
- [x] the buttons that change state are all covered: the two-step unblock, the
      stale reset, resolving a decision, the search filter, the task dialog
- [x] a click is judged by the REQUEST it sent, not only by what the page says
- [x] the test cannot rewrite real task files while it runs
- [x] the page itself is not edited to make the test possible
- [x] there is a demonstration that the test can go red
