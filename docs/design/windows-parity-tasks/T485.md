# T485 - session-persistence.ps1 aborts when run from a Ghoztty pane: it never drops the inherited GHOZTTY_IPC_SOCKET

## In plain terms

One of the test scripts refuses to run at all when it is started the normal way
— from a terminal inside Ghoztty. It stops with an error that sounds like a real
problem with the app, when in fact it has simply pointed itself at the wrong
terminal and given up. Nobody notices a test that is not being run, so the thing
it checks stops being checked.

## Goals

- [x] `session-persistence.ps1` runs from inside a Ghoztty pane without any
      manual environment fiddling — 3/3 full runs from a pane, 2026-08-09
- [x] Its endpoint pre-flight still refuses a genuinely non-hermetic run — the
      build-mode arm still aborts a release `-Exe`, and the `+list` arm now
      asks about a `$PID`-private pipe instead of the user's terminal

## Summary

Found 2026-08-04 while validating T194. `test\win32\session-persistence.ps1`
exits 2 with

```
ABORT: a Ghoztty instance is ALREADY answering on the endpoint
'D:\git\ghoztty\zig-out\bin\ghoztty.exe' uses.
```

whenever it is launched from a Ghoztty pane. The pre-flight is correct in
principle (T116) — it refuses to drive an instance it did not launch — but the
instance it finds is the USER'S installed release, reached because the script
inherits `$GHOZTTY_IPC_SOCKET` from the pane it was started in and never clears
it. That variable outranks the build-mode derivation in
`ipc_client.clientEndpointPathFrom`, so a Debug exe under test resolves to the
release pipe and the pre-flight fires on a build that is not even the one being
graded.

`lib\CleanSlate.ps1` already solves exactly this (`Remove-Item
Env:GHOZTTY_IPC_SOCKET` at load, T118) and every script that dot-sources it is
fine; this one does not.

## Details

Fix: dot-source `lib\CleanSlate.ps1` (or drop the variable directly) BEFORE the
`& $Exe +list` pre-flight. The pre-flight itself must stay — with the inherited
endpoint gone it is answering the right question again, and T116's lesson (a
release exe cannot be isolated here) is unchanged.

Worth a sweep while in there: any other script under `test\win32\` that runs a
CLI call before dot-sourcing `CleanSlate.ps1` or calling
`Set-GhozttyTestIsolation` has the same latent defect.

## Validation

`powershell -NoProfile -File test\win32\session-persistence.ps1` run from a
Ghoztty pane reaches section A instead of exiting 2, and a deliberately
non-hermetic run (point it at an already-running instance on its own endpoint)
still aborts.

## Fixed 2026-08-09 (with T89i)

`Set-GhozttyTestIsolation -Tag 'sesspersist'` now runs at the top of the
isolation-guard block, plus `Assert-GhozttyIsolated -Exe $Exe` once section A's
first window is up.

Two placement details that are the whole fix, not decoration:

- The suffix is set **above** the guard, not beside the `LOCALAPPDATA` switch
  40 lines further down. The guard's own `& $Exe +list` is itself a CLI call —
  the FIRST one in the script — so anything set after it is set too late. That
  is exactly how the abort happened.
- `CleanSlate.ps1` was the fix this task originally proposed and it is the
  weaker one here: dropping `$GHOZTTY_IPC_SOCKET` falls back to the build-mode
  derivation, which the user's own **debug** build (or a leaked instance from
  an earlier run) also answers on. `Set-GhozttyTestIsolation` gives the run a
  `$PID`-unique pipe that nothing else can be listening on, and the launched
  app binds it too, so both ends are isolated by one variable. The guard is
  then answering a question that can only be answered "nothing" — which is
  what makes an abort mean something again.

Validated: three consecutive full runs from a Ghoztty pane, 112s each, both
`[isolation]` asserts PASS in every one, reaching and completing sections A–E
(remaining reds B2.7/B3.7 are T484's, unrelated). Negative control: the
build-mode arm of the same guard still refuses `-Exe` pointed at a release
build, before anything is launched.

The "worth a sweep" item in Details is filed as **T680** — seven other
`test\win32` scripts make CLI calls with no private endpoint at all, one of
which (`context-menu-real-input.ps1`) `+read`s whatever panes it finds.
