# T900 - ipc-p2 can fail 16 of 18 assertions on its first run after another harness, then pass twice in a row - the first-run flake has no diagnostics

## In plain terms

While checking other work, the P2 test suite reported almost everything broken,
and then reported everything fine twice in a row minutes later without any code
change in between. Nothing is actually broken for a user - but a test that
cries wolf like this trains people to re-run instead of read, and the one time
it is telling the truth it will be ignored.

## Summary

Observed 2026-08-16 during T623 validation, running the standing floor
sequentially (never overlapped): `release-artifacts.ps1` finished green, then
the first `ipc-p2.ps1` run exited 1 with `P2 ACCEPTANCE: 16 FAILURE(S) (2
assertions passed)`. Two immediate re-runs were `ALL PASS (20 assertions)`.
The 16-of-18 shape smells like the app (or its pipe) never came up for the
whole run - the same family as T755's cold-launch waits - but the run's output
was filtered to the verdict line, so there is no evidence to reason from.

The task is therefore evidence-first:

- Make a red `ipc-p2` run leave its full transcript somewhere durable
  (`%TEMP%` with a stable name, printed in the verdict), the way the
  cross-lineage harness preserves artifacts on failure, so the NEXT flake is
  diagnosable rather than a shrug.
- If the transcript shows a launch/pipe race with the immediately preceding
  harness's teardown, fix that (e.g. wait for the prior instance's pipe to
  actually vanish before starting).

## Validation criteria

- [ ] A deliberately-failed ipc-p2 run names a preserved transcript path in its
      final output, and the file holds every assertion line
- [ ] Root cause of the first-run flake identified from a captured transcript,
      or the capture shipped and the task split so the fix has evidence to
      stand on
