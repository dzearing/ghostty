# T1067 - A mouse-driven program may never see your pointer in a persistent session pane

## Summary

Measured while validating T1055 (2026-08-21, `test/win32/session-snapshot-reattach.ps1` section M). A child in an agent-backed pane emitted `ESC[?1003h ESC[?1006h ESC[?1004h ESC[?2004h ESC[?7l`, and the app's terminal ended up with `?1004h` (focus events) and `?2004h` (bracketed paste) set — but NOT `?1003h` or `?1006h`, and not `?7l`. The two that went missing are exactly the mouse pair. Evidence is byte-level: the same run with the T1055 fix reverted recorded `[?1004h [?2004h [?9001h` in the persisted snapshot and nothing from the mouse family, so the modes were never in the app's terminal to begin with rather than being stripped by the serializer. The most likely explanation is that ConPTY consumes DECSET 1000/1002/1003/1006 itself (it owns mouse input on Windows) and does not pass them through to us. If so, a mouse-driven TUI in a persistent-session pane never gets pointer events at all — a Mac-parity gap the user would feel as "the mouse just doesn't work in my editor here". Work: confirm the mechanism (is it ConPTY, our GridEmulator, or the agent wire?), decide where the pointer reports have to be synthesized, and cover it. `?7l` not surviving is the same shape and probably the same cause (conhost owns the screen buffer's autowrap), but it is cosmetic by comparison.

## In plain terms

Programs that let you click and scroll with the mouse — an editor, a file browser, a
chat agent's picker — ask the terminal to start reporting where the pointer is. In a
pane backed by a persistent session on Windows, that request appears to get eaten
before it reaches Ghoztty, so the program never hears about the mouse and the pane
behaves as if you had none. On the Mac the same program works. This is finding out
where the request goes and putting it back.

## Outcome — the mouse was never broken; the probe was

The premise did not survive measurement. Nothing in Ghoztty, the agent or the
wire drops `?1003h`/`?1006h`. **conhost forwards a mouse-tracking DECSET out of
a ConPTY only while the child has `ENABLE_VIRTUAL_TERMINAL_INPUT` set on its
console input handle** — the one bit every mouse-driven program sets and no
`cmd /c type` ever does. T1055's arming child was a `type` of a byte file under
`cmd.exe`, so conhost swallowed its whole payload; the `?1004h`/`?2004h` that
looked like survivors were conhost's OWN ConPTY preamble (`?9001h ?1004h
?2004h`), never the child's. `?7l` genuinely never crosses, because conhost owns
the screen buffer's autowrap — cosmetic, and correct.

What landed instead of a fix is the coverage that was missing: the arming child
in `test/win32/session-snapshot-reattach.ps1` section M is now shaped like a
real TUI (VT input on, cooked input off, raw read), and a new **M1b** posts a
pointer move + click at the restored pane's surface and requires an SGR report
to come back to that child through app → agent → ConPTY. Side effect: T1055's
M3 negative control went from finding conhost's two preamble modes to finding
the whole armed family.

## Goals

- [x] Pin down WHO drops `?1003h`/`?1006h` between the child and the app's terminal
      — nobody does; the gate is the child's own `ENABLE_VIRTUAL_TERMINAL_INPUT`
      (measured with a standalone `CreatePseudoConsole` probe, three children:
      cooked `cmd`, a VT-input child, and node in raw mode)
- [x] A mouse-driven program in an agent-backed pane receives pointer reports
- [x] An acceptance arm that would go RED if the reports stop arriving again

## Validation criteria

- [x] A ConPTY child that sets `ENABLE_VIRTUAL_TERMINAL_INPUT` has its
      `?1003h`/`?1006h` forwarded verbatim out of the pty, and one that does not
      has them swallowed — measured with a scratch `CreatePseudoConsole` probe
      that dumps raw pty output; isolated to that single bit (the VT-input child
      changed only the input mode, output VT processing being on by default).
