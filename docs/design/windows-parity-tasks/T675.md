# T675 - The app is a member of the AGENT's kill-on-close job, so the destructive refresh kills the app with the agent - break out of it

## In plain terms

When Ghoztty asks permission to restart its background helper and you agree, the
whole terminal vanishes instead of putting your windows back. It is not a crash:
the app had been quietly grouped together with the helper's own processes, and
killing the helper is defined to kill everything in that group. A guard process
relaunches the terminal a moment later, so what a user sees is everything
blinking out and coming back empty. This task takes the app out of that group so
the refresh can finish the job it offered to do.

## The answer this task was originally asking for (T268, VERIFIED 2026-08-11)

The job is **the agent's own process-global PTY job** — created in
`src/remote/agent/pty_child.zig` with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
(0x2000, no breakaway bits), assigned every PTY child, its handle held by the
agent "for its entire life and NEVER closed" by that file's explicit design.

Measured live from inside a pane on this box: the probing process reports
`in_job=True`, `LimitFlags = 0x2000` — byte-identical to what the dying app
logged — and the job's complete member list is the agent's three `cmd.exe` pane
shells (`ppid` = `ghoztty-agent.exe`) plus their descendants. Anything launched
from a pane joins it, cannot break away (no `BREAKAWAY_OK`, which is why every
tier-1 escape on this box is `ACCESS_DENIED`), and dies when the agent dies.

So membership is **not** benign, and the verdict this task's third validation
item asked for is in: it is a live hazard, and it is the mechanism behind the
whole T229/T421/T426 family of unexplained deaths. Full evidence in
[T268](T268.md).

**Correction to this file's original summary:** the `SHARED_JOB=yes` quoted
below the fold is not the field's reading. It comes from `agent-upgrade.ps1` arm
H, where the harness deliberately jails the app in a kill-on-close job and
(pre-fix) the agent was spawned into it — a real measurement of a synthetic
shape. The only job-facts line the real log has ever carried says
`SHARED_JOB=no`. Both are correct, because they are about **different jobs**:
the harness's app-owned jail, versus the field's agent-owned PTY job. T426
removed the first direction (the agent no longer joins the app's job); this task
is the second, which that fix does not touch and which `no` does not exonerate.
Ownership kills; membership was the wrong question (see [T771](T771.md)).

## What has to change

The app must not be inside a job whose lifetime is owned by a process it
intends to terminate. Two places can deliver that, and they are not exclusive:

1. **The launch** — `scripts\upgrade-ghoztty-windows.ps1` relaunches the app
   with a plain `Start-Process` from a hidden PowerShell that is itself a
   descendant of a pane shell, which is precisely how the app is adopted into
   the agent's job. Same for any other path that starts the app from inside a
   pane.
2. **The app itself** — escape at startup (the re-exec this task originally
   floated), using the existing tier ladder in `job_spawn.zig` /
   `relaunch_guard.zig`. That covers every launch path at once, including the
   ones nobody has enumerated, and is the only option that holds for a user who
   types `ghoztty` in a pane by hand.

Design tension to resolve rather than paper over: a startup re-exec is not free
(double process start, `-e` / single-instance / `+verb` forwarding all have to
survive it), and the job forbids breakaway, so tier 1 will be `ACCESS_DENIED`
and the shell-parent hop is what actually works today — a visible-window
mechanism inside an app launch. **T674** (a headless job-escape tier) is
therefore load-bearing for option 2, not an optional nicety.

A third option worth measuring before choosing: give the agent's PTY job
`JOB_OBJECT_LIMIT_BREAKAWAY_OK` so descendants CAN escape it deliberately. That
is a one-flag change in `pty_child.zig` and it makes tier 1 work for every
future case — but it also weakens the guarantee that job exists for (no orphaned
PTY children), so it needs stating as a decision, not slipping in.

## Original summary (kept for the record)

T426's refresh diagnostic was expected to print, from a live app:

```
agent restart: job facts before the kill — self_in_job=yes
    self_job_flags=0x2000 kill_on_close agent_in_job=yes SHARED_JOB=yes
```

`self_in_job=yes` with `KILL_ON_JOB_CLOSE` set is the part this task is about.
T426 fixed the *agent* side — the daemon no longer joins that job — but the app
is still a member of a job that dies when its last handle closes, and:

- **Nobody has identified the job's creator.** T524 measured `IsProcessInJob =
  true` even for a Start-menu launch, so this is not just a
  harness/ConPTY artifact. (Still true and still unexplained for the
  Start-menu case: T268 identifies the job for the pane-launched app, which is
  the shape that dies. A Start-menu launch joining *some* job is a separate
  question and does not have the agent as its handle owner.)
- **It forbids breakaway** (no `BREAKAWAY_OK` bit), which is exactly why
  tier-1 escape is ACCESS_DENIED everywhere on this box.
- Anything Ghoztty spawns that should outlive it inherits the same problem and
  needs the same workaround, forever, one call site at a time.
