# T675 - Identify who puts the app itself in a kill-on-close job, and whether Ghoztty should break out of it at startup

## In plain terms

Windows has grouped Ghoztty itself into a "kill everything in here at once"
bucket, and we do not know who created that bucket or what else is in it.
Whatever tears it down takes the terminal with it, without a crash report — the
same disappearing act that cost four investigations before T426 named it. Worth
knowing whose bucket it is before assuming it is harmless.

## Summary

T426's new refresh diagnostic printed, from a live app:

```
agent restart: job facts before the kill — self_in_job=yes
    self_job_flags=0x2000 kill_on_close agent_in_job=yes SHARED_JOB=yes
```

`self_in_job=yes` with `KILL_ON_JOB_CLOSE` set is the part this task is about.
T426 fixed the *agent* side — the daemon no longer joins that job — but the app
is still a member of a job that dies when its last handle closes, and:

- **Nobody has identified the job's creator.** T524 measured `IsProcessInJob =
  true` even for a Start-menu launch, so this is not just a
  harness/ConPTY artifact.
- **It forbids breakaway** (no `BREAKAWAY_OK` bit), which is exactly why
  tier-1 escape is ACCESS_DENIED everywhere on this box.
- Anything Ghoztty spawns that should outlive it inherits the same problem and
  needs the same workaround, forever, one call site at a time.

The open question is whether the app should break OUT of that job at startup
(re-exec itself escaped, once, the way the escape tiers already do for
children) or whether membership is benign and only the children matter.

## Where to start

1. Identify the job: walk up the parent chain of a Start-menu-launched
   `ghoztty.exe` and check `IsProcessInJob` / `QueryInformationJobObject` at
   each level (`src/apprt/win32/job_object.zig` already has the probes). A
   named job would answer it outright.
2. Establish whether a teardown of that job is something that HAPPENS, or a
   theoretical hazard. Four unexplained deaths say something tore something
   down; T426 attributes them to the shared job with the agent, which is now
   gone — a fifth occurrence after that fix would point here.
3. Only then decide on a startup re-exec. A self-re-exec at launch is not free
   (it doubles process starts, complicates `-e`/single-instance/`+verb`
   forwarding, and would need the same tier ladder), so it needs evidence, not
   tidiness, behind it.

## Validation criteria

- [ ] The job the app sits in is IDENTIFIED (creator process and, if any, its
      name), recorded here with how it was measured
- [ ] A stated verdict on whether app-side membership is a live hazard or
      benign, with the evidence for it
- [ ] If it is a hazard: the app escapes at startup, proven by an
      `IsProcessInJob` probe against that job plus survival of its teardown
- [ ] Floor green
