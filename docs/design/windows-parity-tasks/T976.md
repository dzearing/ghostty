# T976 - A launch that beats the session manager to the punch leaves the windows unrestored until the next launch

## Summary

T975 fixed the two reasons the manager was late (a listener that wedged on an abandoned dial, and startup adoption paying a 2s dial per dead holder), but the app's launch restore is still ONE SHOT: findOrSpawn gives the freshly spawned agent spawn_deadline_ms=2000, and on expiry the launch restores only the windows that need no agent and logs 'keeping N unrestored manifest window(s) for the next launch'. On a loaded box - a big login storm, a slow disk, twenty recorded sessions - the user still opens to a blank terminal and has to relaunch to get their layout. The app already learns the agent arrived (it dials again for later work); the restore should complete when it does, rather than being decided in the first two seconds.

## In plain terms

When you log back in and Ghoztty starts, it asks the background session
manager for the windows you left open. If the manager is not answering yet -
and on a busy machine, just after a reboot, it often is not - Ghoztty gives up
after two seconds and shows you one empty terminal. Your windows are not lost,
but the only way to get them is to quit and start Ghoztty again, which is not
something anybody should have to know.

After this, Ghoztty keeps checking for about a minute. The moment the session
manager answers, the windows you left open appear by themselves, in the app
you already have open.

## What was decided here (no user question filed)

Two calls, both mechanism-level, recorded rather than asked:

- **The leftover blank window stays.** When the launch restores nothing, the
  app opens one empty terminal; when the deferred pass then rebuilds the real
  windows, that empty one is still there. Closing it automatically would mean
  destroying a pane the user may already have typed into, which is worse than
  an extra window they can close. Its `window-N` name no longer collides with
  a restored window's (see below).
- **The retry never spawns an agent, it only dials.** The launch already
  issued the spawn; a spawn per tick would start a process the single-instance
  guard immediately kills and re-block the GUI thread for 2s each time. If the
  spawn itself failed, the retry still completes as soon as anything else in
  the app resolves the agent (opening a window does), because it adopts the
  shared connection when one appears.

## Validation criteria

- [x] A launch that finds no agent within the spawn deadline no longer decides
      the restore: it arms a bounded retry and says so
      (`session-restore: N window(s) still need the local agent; retrying for
      up to 55s`). *Verified: `test\win32\restore-late-agent.ps1` phase B/C.*
- [x] When the agent turns up mid-run, the carried windows are rebuilt IN THE
      SAME app process - no relaunch. *Verified: C1/C2 of that script (the
      windows come back, and the pid showing them is the one that launched into
      the blackout).*
- [x] The rebuilt windows are LIVE, not a listed shell of one. *Verified: C3,
      `Test-PaneLive` types into a restored pane and requires new output.*
- [x] The deferred pass rebuilds ONLY what the launch carried - never a
      duplicate of a window already on screen. *Verified: C4 (no duplicate
      target names) plus the `only` filter in `restorePass`.*
- [x] A carried window keeps its `window-N` target name: the blank startup
      window cannot mint it first. *Verified: C4, and `A3` records the names
      before the blackout so a stolen name would show as a duplicate.*
- [x] The schedule is bounded and gives up rather than polling forever.
      *Verified: unit tests in `src\apprt\win32\restore_retry.zig` (win32 lane).*
- [x] Floor stays green. *Verified: `scripts\floor-lane.ps1 -Lane all`,
      P1-P3.*
