# T456 - Pane resize leaves unpainted gaps around the banner - the overlay lags the drag instead of moving with it

## In plain terms

Dragging a split divider makes the area around the status banner flicker with
blank, unpainted patches until you let go. Nothing is broken afterwards, but the
window looks like it is falling apart while you resize it. The user has reported
this more than once and believes it was already filed; if an earlier task exists
it never landed a fix.

## Goals

- [x] Dragging a split divider across a pane that has a banner shows no
      unpainted region at any point in the drag
- [x] The same holds for resizing the whole window
- [x] Verified at 1.0 / 1.25 / 1.5 / 2.0 scaling
- [x] The result is measured, not eyeballed (see Validation) - "looks smoother
      now" is how this gets reported a fourth time

## Where to look

The banner is a **separate child HWND** (`src/apprt/win32/BannerOverlay.zig`),
positioned by its own `SetWindowPos` (~line 301) off the pane layout in
`Window.zig` (`bannerLayoutInset` callers, ~lines 2245 / 2289 / 2394). A child
window moved by a separate call from the pass that moves the terminal panes is
repositioned in a different frame from the content around it - which is what a
lagging overlay looks like.

Candidate causes, none confirmed. **Measure before fixing:**

1. The overlay's `SetWindowPos` is not batched with the sibling panes'.
   `BeginDeferWindowPos`/`EndDeferWindowPos` moves them all in one pass.
2. `WM_ERASEBKGND` returns 1 (~line 1342, "WM_PAINT covers everything"), which
   is only correct if the paint lands in the same frame as the move. If the move
   outruns the paint, the uncovered strip is erased by nobody.
3. `SWP_NOCOPYBITS`, `WS_CLIPCHILDREN` on the parent, and the parent's
   `CS_HREDRAW|CS_VREDRAW` decide whether the parent repaints the strip the
   overlay just vacated.
4. A live drag runs inside a modal loop pumping `WM_SIZING` /
   `WM_WINDOWPOSCHANGED`; anything deferred to an idle or timer path does not
   run there at all.

## Validation

- An acceptance script under `test/win32/` that drives a divider drag and
  samples the pane region mid-drag, asserting no pixel matches the
  never-painted background. Use the existing pixel-probe recipe - a DPI-aware
  probe process with `CopyFromScreen` and the window topmost (`GetPixel` skips
  layered windows) - rather than inventing one.
- Runs against a **debug build from `zig-out\bin`**, never the user's installed
  release.
- Repeat at 1.0 / 1.25 / 1.5 / 2.0 scaling, per the win32 design system.

## Root cause (measured 2026-08-04)

**Candidate 2, in its strongest form: the banner popup repainted NOTHING on a
resize.** Its window class was registered with `.style = 0` — no
`CS_HREDRAW | CS_VREDRAW` (`BannerOverlay.zig:1467`). Measured directly: create
a window of that class, `SetWindowPos` it 40px wider, and `GetUpdateRect`
returns **0**. Not "only the exposed sliver" — nothing at all.

Every pixel of the card is laid out against the *current* band size: the
rounded rim and its shadow sit on the edges, the chevron column is measured in
from the right, and each block is word-wrapped to the content width (T377). So
while a drag moved and resized the band, the card kept the geometry it had
before the drag, and only recovered when something else happened to invalidate
it. That is exactly "unpainted gaps around the banner / the overlay lags the
drag", and it explains why the defect is banner-specific: `DimOverlay` shares
`.style = 0` but is a flat fill, where a partial repaint is indistinguishable
from a full one.

The other candidates were checked and are NOT the cause:

- **Candidate 1 (moves not batched)** — the pane and the banner do move in two
  separate calls, but the tiling arithmetic is correct at every settled point:
  measured 0 violations across a 14-step drag *before* the fix. Batching would
  have changed nothing visible.
- **Candidate 2 (`WM_ERASEBKGND` returns 1 on the parent)** — correct as it
  stands. T155's tiling argument holds; the exposed band is covered by the
  banner popup, not by a parent-owned region.
- **Candidate 3/4** — not reached; the class style accounts for the whole
  symptom.

## Fix

1. `BannerOverlay` registers its class with `CS_HREDRAW | CS_VREDRAW`, so any
   size change invalidates the whole card rather than nothing.
2. `updatePosition` detects a genuine *resize* (vs a move) and then
   (a) passes `SWP_NOCOPYBITS`, so Windows does not blit a stale card into the
   new rect for a frame, and (b) calls `UpdateWindow` to repaint **inside the
   same layout pass**. Without (b) the card still repaints, but one pumped
   `WM_PAINT` later — i.e. a whole drag frame behind the pane it is glued to,
   which is the "lags the drag" half of the title.

## Validation (done)

- `zig build test -Dapp-runtime=win32`, two new tests in `BannerOverlay.zig`:
  - *banner class: a resize invalidates the whole card, not the exposed strip* —
    asserts `GetUpdateRect` covers the full client after a widen.
  - *banner overlay: a size-changing updatePosition repaints in the same pass* —
    asserts no update region survives the call, at **1.0 / 1.25 / 1.5 / 2.0**.
  - Both have a confirmed **negative control**: reverting `.style` to 0 fails
    the first, and disabling the `UpdateWindow` fails the second.
  - Test-design note: the test window must be **on-screen at layered alpha 0**.
    Parked off every monitor it has an empty visible region, Windows invalidates
    nothing, and the test passes for the wrong reason — measured, and that is
    what the first draft did.
- `test/win32/banner-resize-repaint.ps1` — **ALL PASS (10 assertions)**, and
  `-NegativeControl` fails as required. Background test desktop; posted
  divider drag both directions plus five whole-window resizes; asserts the
  live banner window's class style and the band⇄pane tiling invariant at
  every step.

**What the Validation section originally asked for and why it changed.** It
asked for a mid-drag pixel sample. Two measurements moved that assertion:
off the input desktop, layered popups do not come back from `PrintWindow`
(the only capture that works there) and the banner *is* a layered popup; and
on the interactive desktop the remaining window between the pane's
`MoveWindow` and the popup's `SetWindowPos` is sub-frame, so polling it from
another process catches it essentially never. A pixel assertion would have
been a coin flip dressed as a test. The class style + the tiling invariant
assert the cause and the geometry instead, and neither is timing-dependent.
The visual result was still confirmed by hand on the interactive desktop
(before/after capture of a real posted drag).
