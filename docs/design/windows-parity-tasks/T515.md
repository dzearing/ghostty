# T515 - An explicit local +split --command opens in the agent default cwd, not the parent pane's

## Summary

Found while fixing T148. In `IpcHandlers.zig`'s `+split` handler, the LOCAL
session-persistence branch (T99) only takes the full-inheritance path
(`buildRemoteInherit`: parent cwd via GET_CWD) when there is NO explicit
command and NO explicit `--working-directory`. An explicit `--command=X` with
no `--working-directory` builds a `.remote{local_agent}` override whose
`working_directory` is null, so the agent OPEN falls back to its default cwd —
the split runs X in `%USERPROFILE%` instead of the parent pane's directory. A
terminal split is expected to open where its parent is unless told otherwise
(the same rule host_defaults.zig states for remote windows).

To verify first: (1) reproduce on the box (`+new-window
--working-directory=<marker>`, then `+split --command=echo hi`, read the
prompt's cwd); (2) check what the Mac does for the same shape — the fix should
land symmetrically or be recorded as intended behavior with the reason.
Likely fix: in the explicit-override local branch, when
`--working-directory` is absent, query the parent's cwd (same GET_CWD
`buildRemoteInherit` uses) and pass it in the override.

## What it actually was

The summary's guess was wrong in a way worth recording, because it is what
made the bug survive a reading of the code. The null `working_directory` in the
override does NOT reach the agent as "no cwd": T144's
`termio.Remote.openWorkingDirectory` already falls back to the surface config's
resolved cwd for the LOCAL agent, so the pane never lands in the agent's
default directory.

What answers instead is the CORE's inheritance, and that one is **app-global**:
`apprt/surface.zig` `newConfig` reads `app.focusedSurface`. So an
explicit-command split opens in whatever pane last had focus *anywhere* — the
right answer whenever the split parent happens to be that pane, which is why
every same-window test of this passed, and another window's directory the
moment one is in front. Measured on the box: with a second window focused,
`+split --pane=<parent> --command=…` opened in the SECOND window's directory.
Same class as T538, one seam over.

A cross-machine window has it worse: a local path is deliberately withheld
from a remote agent, so there the fallback does not exist at all and the pane
really does open in the agent's default cwd.

## In plain terms

If you split a terminal pane and ask the new pane to run a specific program,
the new pane can start in the wrong folder — whichever folder the window you
last clicked in was using, rather than the folder of the pane you split. You
expect a split to stay "where you are" unless you say otherwise.
