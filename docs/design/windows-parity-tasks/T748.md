# T748 - Session restore mis-restores maximized windows: maximized state without maximized geometry (no border, odd rendering)

## Summary

User report 2026-08-11: after an upgrade, restored windows came back flagged as maximized but were NOT actually sized/positioned as maximized - they rendered oddly with no window border. Restore must round-trip window placement correctly: persist and reapply both the show state (normal/maximized) and the normal-position rectangle, e.g. via GetWindowPlacement/SetWindowPlacement semantics, so a maximized window restores truly maximized (proper frame, correct monitor) and a normal window restores at its saved rect. Investigate the win32 session-layout save/restore path for how showCmd and the frame rect are captured and reapplied.

## In plain terms

If you work with your terminal maximized, every window that came back after a
restart came back broken: it claimed to be maximized - no window border, chrome
laid out for a full-screen window - while actually sitting at the small size it
had before you ever maximized it. It looked like a rendering bug and there was
no way to fix it short of un-maximizing and re-maximizing by hand. After this,
a maximized window restores genuinely maximized, and a window that was NOT
maximized restores as a normal window at the size and position you left it -
even when the last window you touched was maximized.

## Goals

- [x] A window recorded as maximized restores actually maximized (fills the
      screen, real frame), not merely flagged
- [x] Its restore-down size and position survive the trip, so un-maximizing it
      goes back to where it was
- [x] The mirror case: a window recorded as NOT maximized restores as a normal
      window even when the placement memory says maximized
- [x] The frames the manifest records are one coordinate space end to end
      (screen), so a top/left taskbar cannot shift a restored window

## Root cause

Restore applied the recorded frame with `SetWindowPos` **after** the window had
already been shown - and shown MAXIMIZED whenever the T85 placement memory said
the user's last window was, which for a user who works maximized is every
window on every launch. `SetWindowPos` moves and resizes a maximized window
without clearing `WS_MAXIMIZE`, so `IsZoomed` stayed true (caption drops its
resize border, chrome lays out for a maximized window) at the recorded
restore-down size. The `ShowWindow(SW_MAXIMIZE)` that followed could not undo
it: asking for a state the window is already in does nothing. The mirror image
was equally broken - a window the manifest recorded as normal, restored while
the memory said maximized, kept the maximize style at its small rect.

Measured directly on the box before the fix: `restored: 800x600 at 32,32
zoomed=True`.

The fix is `SetWindowPlacement`, the one call that sets `rcNormalPosition` and
the show state together, so there is no intermediate state to be caught in.
Two things fell out of doing it properly:

- `WINDOWPLACEMENT.rcNormalPosition` is in *workspace* coordinates (screen,
  shifted by the primary work area's origin) while everything else here -
  the manifest, `restore_frame`'s monitor math, `SetWindowPos` - is in screen
  coordinates. The capture side had been storing the raw workspace rect for a
  maximized window, a latent taskbar-sized drift on any desktop whose taskbar
  is at the top or the left. Both ends now go through `window_placement.zig`.
- `SW_SHOWNOACTIVATE` through `SetWindowPlacement` **does** clear a maximized
  state (measured), unlike what `ShowWindow`'s "most recent size and position"
  wording suggests - so the un-maximized case keeps the pre-existing
  no-activation promise instead of having to activate the window.
