# T611 - manual reconnect must open a fresh session when the remote session is gone, not go terminal

## In plain terms

Your window is running shells on another machine, that machine reboots, and the
window's titlebar offers you a **Reconnect** button. You click it. The machine
is back and reachable — but the shells that were running on it are gone with the
reboot, so Ghoztty gives up and leaves the window dead. Clicking Reconnect on a
machine that is plainly back should get you a working window: it reconnects and
opens a fresh shell where the old one used to be.

## Goals

- [x] a manual reconnect carries "the user asked for this" all the way to the
      outcome, and the flag rides the ATTEMPT rather than a window field a
      second drop could overwrite
- [x] the whole end-of-attempt rule is pure and asserted, so the call site
      cannot quietly disagree with the policy again
- [x] a fresh-session swap rebuilds the window the user arranged: same split
      layout, same pane ids, a working shell in every pane
- [x] an AUTOMATIC re-dial still goes terminal on `session_gone`

## Summary

Found by T367 (2026-08-08), which built the pill's Reconnect button and became
`RemoteReconnect.manualReconnect`'s first caller. The policy already models the
right answer and the driver never asks for it.

`remote_reconnect.onProbeOutcome(outcome, fresh_session_on_gone)` returns
`.swap{ fresh_session = true }` for `session_gone` when the reconnect was
MANUAL — the documented contract, and what CLAUDE.md's remote section describes
("it re-attaches when the session survived, or opens a fresh shell on the
machine when it didn't"). But `RemoteReconnect.onDialed` calls it with a
hardcoded `false`:

```zig
switch (policy.onProbeOutcome(outcome, false)) {
    .swap => |s| {
        std.debug.assert(!s.fresh_session);
```

so a manual reconnect against a machine whose sessions are gone takes the
`.terminal` arm. Measured, not inferred — `test\win32\remote-pill.ps1` kills the
loopback agent, restarts it, clicks Reconnect, and the app log reads:

```
remote reconnect: 'window-2' dropped; attempt 1/5 in 0ms     <- the manual attempt
remote reconnect: 'window-2' is terminal after attempt 1 (session_gone)
```

The `0ms` backoff is the manual signature, so the click reaches the driver
correctly; it is the outcome handling that stops short.

## Details

Two pieces:

1. **Carry the manual flag to the outcome.** `beginLadder` knows `manual`;
   `onDialed` does not. The flag has to ride the attempt (the `Result` the
   worker carries, alongside `gen`), not a field that a second drop could
   overwrite while the dial is in flight.
2. **Make `applySwap` able to rebuild WITHOUT an attach set.** Today it
   re-ATTACHes by recorded session id and treats `attached == 0` as a failed
   attempt — which is exactly the state a fresh-session swap lands in. A fresh
   swap needs `rebuildWindowInPlace` to OPEN a new session per pane instead,
   and the `attached == 0` guard needs to distinguish "nothing came back when
   something should have" from "nothing was supposed to come back".

   The guard is load-bearing (it is what keeps the old transport alive while
   the departing surfaces DETACH over it), so do not weaken it — give the fresh
   path its own success condition rather than relaxing the re-attach path's.

   **Half of this turned out to be wrong, and the correction is worth keeping**
   (2026-08-11). `rebuildWindowInPlace` already OPENs a fresh session for any
   leaf the attach set does not name — `leafAttachSessionId` returns null and
   `restoreAttachOverride` hands the surface a null `session_id` — so the fresh
   rebuild needed no new machinery at all. And the count it returns is *terminal
   leaves rebuilt on the new transport*, not sessions re-attached, so
   `attached == 0` was already the right success test for BOTH arms: a
   freshly-OPENed pane rides the new connection exactly as a re-ATTACHed one
   does, and a swap that produced neither has nothing to justify retiring the
   old transport for. What the fresh arm got instead is an explicitly EMPTY
   attach set rather than the probe's (so "fresh" means fresh for every pane,
   not just for the ones that were `core_surface_ready` when liveness was
   judged), a renamed count, and its own log line.

Worth deciding while here: what a fresh-session swap does to a MULTI-PANE grid.
Re-opening every pane as an empty shell preserves the layout the user built;
collapsing to one pane loses it. The layout is the thing they arranged by hand,
so preserving it is the default this task should argue against rather than for.

**Resolved: preserve it**, and it is free — the in-place rebuild replaces each
leaf in the slot it already holds, so the split tree, its ratios and every
pane's id come through untouched. Asserted rather than assumed:
`test\win32\remote-reconnect-fresh.ps1` arm B compares the shape and the pane
ids across the swap.
