# T1097 - Disambiguate 'merge back': the repo uses one phrase for three different merges, and two of them got confused for the third

## Summary

"Merge back" names three unrelated operations in this repo, with nothing in the
wording to tell them apart. On 2026-08-22 that collision cost a full round trip
with the user, twice, and produced a wrong correction that had to be undone.

| # | The operation | Direction | Status | Owned by |
|---|---|---|---|---|
| 1 | **Branch cutover** | `users/dzearing/windows-amd64` -> `main`, both on dzearing/ghoztty | The goal. One `main` carrying mac and windows so the PR pipeline builds both. Currently a clean fast-forward of 1427 commits. | T1074, gated by `scripts\ship-readiness.ps1` |
| 2 | **Upstream pull** | ghostty-org/ghostty -> this fork | Allowed, but only when the user calls for one, and it lands in the mac build first, then funnels to the windows port. | D80 |
| 3 | **Upstreaming** | this fork -> ghostty-org/ghostty | **Never happens.** No PR, no pushed branch. The `upstream` remote is fetch-only by construction. | D80 |

Sense 1 is what the user means by the phrase - and it is the one the docs never
use it for. Sense 2 is what the docs mean by it. Sense 3 is what a plain reading
of it says, which is why the 2026-08-21 digest sentence "The merge back to
upstream Ghostty actually began" read as this fork preparing pull requests
against the public Ghostty project.

## What to do

Retire the bare phrase. Give each sense its own name and use it everywhere a
future reader could act on the text:

- sense 1 -> **"cutover"** or **"merge the branch to main"**
- sense 2 -> **"upstream pull"** / **"upstream sync"**
- sense 3 -> **"upstreaming"**, and only ever in a sentence saying it does not happen

Sweep the live docs: `docs/design/windows-parity-merge-back-plan.md` including
its filename (it covers senses 1 and 2 under one title, which is the root of
this), `windows-parity-tasks.md`, `windows-parity-ship-workflow.md`, `go.md`,
`CLAUDE.md`, `docs/claude/*`, and any task file not already `done`.

Leave the dated digests and `windows-parity-log.md` as they are - both are
history-only by charter - except for the correction already appended to the
2026-08-21 digest.

## Validation criteria

- [ ] `git grep -i 'merge.back'` returns hits only in dated digests and
      `windows-parity-log.md`.
- [ ] The merge-back plan doc is split or retitled so a reader can tell at the
      filename which of the three it is about.
- [ ] Every surviving mention of an upstream operation states its direction in
      the same sentence, so no reader has to infer it.
- [ ] A reader who knows nothing of this history can read
      `windows-parity-ship-workflow.md` and D80 back to back and correctly say
      which merge each one governs.
