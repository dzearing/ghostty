# T1097 - Disambiguate 'merge back': the repo uses one phrase for three different merges, and two of them got confused for the third

## In plain terms

One phrase in this project's notes - "merge back" - was being used for three
completely different jobs: finishing the Windows work by making it the main
line, taking new work in from the original Ghostty project, and giving our work
back to that project (which we never do). Twice in one day someone read it as
the wrong one and started down the wrong road. This gives each job its own name
everywhere the wording still matters, and adds a check so the ambiguous phrase
cannot creep back in.

## Goals

- [x] Each of the three merges has its own name, used consistently
- [x] The plan document says at its filename which merge it is about
- [x] A reader can tell the direction of any merge from the sentence it is in
- [x] A harness fails if the bare phrase comes back

## Summary

"Merge back" names three unrelated operations in this repo, with nothing in the
wording to tell them apart. On 2026-08-22 that collision cost a full round trip
with the user, twice, and produced a wrong correction that had to be undone.

| # | The operation | Direction | Status | Owned by |
|---|---|---|---|---|
| 1 | **Branch cutover** | `users/dzearing/windows-amd64` -> `main`, both on dzearing/ghoztty | The goal. One `main` carrying mac and windows so the PR pipeline builds both. Currently a clean fast-forward of 1427 commits. | T1074, gated by `scripts\ship-readiness.ps1` |
| 2 | **Upstream pull** | ghostty-org/ghostty -> this fork | Allowed, but only when the user calls for one, and it lands in the mac build first, then funnels to the windows port. | D80 |
| 3 | **Upstreaming** | this fork -> ghostty-org/ghostty | **Never happens.** No PR, no pushed branch. The `upstream` remote is fetch-only by construction. | D80 |

Sense 1 is what the user means by the phrase - and it is the one the docs never
use it for. Sense 2 is what the docs mean by it. Sense 3 is what a plain reading
of it says, which is why the 2026-08-21 digest sentence "The merge back to
upstream Ghostty actually began" read as this fork preparing pull requests
against the public Ghostty project.

## What to do

Retire the bare phrase. Give each sense its own name and use it everywhere a
future reader could act on the text:

- sense 1 -> **"cutover"** or **"merge the branch to main"**
- sense 2 -> **"upstream pull"** / **"upstream sync"**
- sense 3 -> **"upstreaming"**, and only ever in a sentence saying it does not happen

Sweep the live docs: the upstream-pull plan including its filename (it covered
senses 1 and 2 under one title, which is the root of this),
`windows-parity-tasks.md`, `windows-parity-ship-workflow.md`, `go.md`,
`CLAUDE.md`, `docs/claude/*`, and any task file not already `done`.

## What is history, and is therefore left alone

Charter, settled while doing this: a file that records what was true or what was
asked on a given day is never rewritten to fit a naming rule. That is the dated
digests, `windows-parity-log.md`, the audit / details / spec / divergence /
feature-ideas files, **every decision record** (D32, D33 and D80 preserve a
question as it was asked and the user's answer verbatim - editing one would
falsify the record), any task file already `done` or `skipped(...)`, and the
`## Progress log` of a task still open.

Two more exemptions, and the lint below enforces both: a **quotation** is
reporting someone else's words rather than writing them, so a double-quoted span
or a markdown blockquote may carry the phrase (the user's own cutover directive
is quoted verbatim in `ship-readiness.ps1`, `ship-feature.ps1` and the
ship-workflow doc); and a **quoted mention** - `"merge back"` in a sentence
about the phrase itself - is how CLAUDE.md and D80 explain the ban.

## Validation criteria

- [x] No live file uses the bare phrase - history, quotations and quoted
      mentions excepted, per the charter above.
      **How verified:** `test\win32\merge-terminology.ps1` section B scans
      every tracked text file and every still-open task file; ALL PASS.
      A plain `git grep -i 'merg\w*[- ]back'` agrees.
- [x] The plan doc is retitled so a reader can tell at the filename which of the
      three it is about.
      **How verified:** `git mv` to
      `docs/design/windows-parity-upstream-pull-plan.md`, history intact under
      `git log --follow`; section D asserts the new name is on disk, the old one
      is gone, and that nothing still opens the plan by the old path.
- [x] Every surviving mention of an upstream operation states its direction in
      the same sentence, so no reader has to infer it.
      **How verified:** the three-sense table (operation / direction / where it
      is tracked) now opens the plan doc, the ship-workflow doc and
      `ship-readiness.ps1`; section C asserts all three plus CLAUDE.md.
- [x] A reader who knows nothing of this history can read
      `windows-parity-ship-workflow.md` and D80 back to back and correctly say
      which merge each one governs.
      **How verified:** both now open by naming all three senses and which one
      they govern ("covers the **cutover**" / "the operation *this decision*
      governs is an **upstream pull**"); section C4/C6 assert the sentence.
- [x] The ban cannot decay: a harness fails when the phrase comes back.
      **How verified:** `test\win32\merge-terminology.ps1` ALL PASS,
      `-NegativeControl` scores exactly 1 FAILURE, and
      `scripts\guard-due.ps1` carries a `merge-terminology` row so an edit to
      any covered file makes it due and `parity-tasks.ps1 validate` fails until
      it is re-run.
