# T332 - +list --json never reports which agent session a pane is bound to

## Summary

A pane backed by the session-persistence agent knows its session id
(`Surface.remote_session_id`, set from the ATTACH/OPEN override and read back by
`core_surface.remoteSessionId()`), but nothing on the CLI ever says it.
`+list --json` reports the pane id, type, title and — for viewers — the url;
`+sessions --json` reports the session and whether SOMEONE has it attached. The
join between the two lives only inside the app.

The consequence is that the obvious question has no CLI answer: *which pane is
this session open in* / *which session is this pane on*. T320's own validation
line assumed `+list --json` could report it and had to fall back to
`+sessions`'s `attached` flag plus an app log line.

Concretely, without it:

- a resume/attach test can prove a session became attached, but not WHICH pane
  took it (two panes attaching in the same second are indistinguishable);
- `session already open, focusing its pane` (T320's short-circuit) is only
  assertable through a log line, which is the app talking about itself rather
  than an independent reading;
- an agent scripting a layout across a restart cannot map its panes back to the
  sessions it knows by id.

## The work

Add the session id to `+list --json`'s terminal-pane object — absent when the
pane is a plain local ConPTY (no session), present for local-agent and
cross-machine panes alike. Consider `attached`-side symmetry: `+sessions --json`
could carry the pane id when the session is open in THIS app.

Keep the human tree unchanged unless there is a reason; the id is script data.
Additive fields only — `+list --json` is consumed by scripts on this box.

## Validation

- Unit: the serializer emits the field when set and omits it when null.
- On box: open a persistent pane, read its id from `+list --json`, and match it
  against the `+sessions --json` row that reports `attached`.
