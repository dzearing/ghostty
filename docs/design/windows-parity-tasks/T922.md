# T922 - A pane restored after a reboot comes back empty instead of showing what was lost

## In plain terms

Your machine reboots. The terminal comes back with the same windows and panes,
but each one is blank - just a note saying the session was closed, and a fresh
prompt. Whatever you were reading when the power went - the error, the build
output, the last thing your agent said - is gone. After this, the pane brings
that screen back with it, above the note, where you can scroll it.

## Goals

- [x] A restored pane shows the dead session's last screen instead of an empty prompt.
- [x] That screen is scrollback, above the notice - the new shell's opening repaint cannot erase it.
- [x] What comes back is RECENT. The screen is re-recorded as panes print, not only when a window is split or renamed.
- [x] A pane with nothing to bring back restores exactly as it did before.

## Summary

Under session-relaunch=restore the Windows client OPENs a brand-new session for a dead tombstone, and deliberately paints neither the agent ring replay nor the app's own WP-D3 screen snapshot above the fresh prompt (termio/Remote.zig excludes did_notify from both). Main's restore (c76b5c89d) keeps the dead session's scrollback so the user can read what the process left behind. So after a reboot a Mac pane shows the last output of the thing that died and a Windows pane shows only the notice and an empty prompt.

The paint was only half of it. The screen it paints comes from the session-layout manifest, and that file was written ONLY on topology mutations - a split, a tab, a rename, a banner. A pane that had merely been running for an hour therefore restored the screen it had when a window last moved. Freshness is part of the promise D78 made, so the manifest now refreshes on the panes' own output as well.

## Validation criteria

- [x] A pane restored under the default `restore` policy comes back showing what the dead session left on screen, instead of an empty prompt. (`test\win32\session-relaunch-notify.ps1` arm A15, scored on a marker only the dead session could have printed - ALL PASS 108.)
- [x] That restored screen sits ABOVE the session-interrupted notice, and both are in the pane's own scrollback - the fresh shell's opening repaint does not erase either. (A16/A17, plus A11/A12 for the notice itself.)
- [x] What the pane brings back reflects the session's LAST screen, not the last time its window changed shape. (The harness now waits on the manifest actually carrying the marker before the kill - `Wait-LayoutSnapshotHas`, a setup assertion that is A15's positive control - which only passes because of the new refresh tick.)
- [x] A pane with nothing to bring back (no snapshot, an empty one, or one recorded at stream offset 0) restores exactly as it did before, with no blank filler above the notice. (`restore_history.historyToPaint` null cases, `none` lane.)
- [x] A pane whose snapshot was taken inside a TUI comes back on the PRIMARY screen with a scrollback the user can scroll, and the dead program's modes (mouse tracking, bracketed paste, autowrap) do not leak onto the fresh shell. (`restore_history.alt_screen_exit` + `Remote.replay_mode_reset`, `none` lane; the alt-screen exit is emitted only when the terminal actually ended up there.)
- [x] An idle terminal pays nothing for the refresh: no manifest rewrite while nothing paints. (`session_layout.writeIfChanged` + its two `bodyId` tests, and the six `layout_refresh.decide` tests - idle / wait-for-quiet / capture / the streaming ceiling / idle outranking that ceiling / the first tick after launch. Both lanes; the poll itself is one lock-free atomic per pane.)
- [x] The standing floor stays green: all four `floor-lane` lanes (lib / none / win32 / agent ALL PASS, 2026-08-18) and P1-P3 (25/20/16 assertions, ALL PASS). The four other guards this touched re-run green and re-stamped: session-relaunch (108), session-layout-preserve (19), printclient-audit, isolation-meta (7), stderr-capture (25).
