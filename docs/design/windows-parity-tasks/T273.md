# T273 - window-theme no longer reaches the client-painted caption and tab strip

## Summary

`window-theme = light` used to give a light titlebar on Windows, because the
titlebar was DWM's and `applyChromeTheme` set `DWMWA_USE_IMMERSIVE_DARK_MODE`
on it (`src/apprt/win32/Window.zig:445`). Since **T254** took the caption over
with `WM_NCCALCSIZE` and **T205** merged the tab run into that same row, the
band is CLIENT pixels that WE paint - and `paintCaption` derives its fill from
`config.background` alone (`Window.zig:3221`, bg + 20 per channel), exactly
like the strip's `bar_*` (`Window.zig:3480`). Nothing in either painter reads
`window-theme`.

So the DWM calls still fire and still return success, and they no longer paint
anything a user can see. `window-theme = light|dark|system` is now a no-op for
the titlebar and tabs. It is NOT a no-op everywhere - `DarkMode.apply`
(`App.zig:333`) still themes the menus - which is why the setting looks alive
in a quick check.

## Evidence (measured on box 2026-08-01, debug build, test desktop)

Two windows, identical except for the theme, captured with
`Get-TestWindowPixels` and sampled down the middle:

| window | caption band rgb | band meanLum |
|---|---|---|
| `--window-theme=light --window-show-tab-bar=always` | 60,64,72 | 65 |
| `--window-theme=dark  --window-show-tab-bar=always` | 60,64,72 | 65 |

60,64,72 is the default background (40,44,52) + 20. The band is 0..~48 px at
125%; below it the capture goes flat 255 (the OpenGL surface, per T214).

Found by `test/win32/test-desktop-harness.ps1`, whose capture control WAS this
exact comparison. It is worth reading how it failed: the light half went red
and **the dark half stayed green on the identical pixels**, because 71
satisfies `< 100`. A two-sided control that does not assert the SEPARATION can
be half-green against a completely dead discriminator. T213 re-pointed that
control at `--background` (the input the band really derives from) and added
the gap assertion; this task owns the product question it was measuring.

## The design tension - decide it, do not skip it

Do not "just theme the caption" without settling this, because the two rules
collide:

- **T202/T206/T242 built the selected tab to MERGE into the pane below it.**
  That idiom only works while the chrome color is a function of the terminal
  background. It is why `bar_*` and `cap_*` share one derivation, and T254
  deliberately reused it so the caption and the strip could not drift apart.
- **`window-theme = light` on a dark terminal is a request for light chrome**,
  which by definition breaks that merge - the user asked for chrome that does
  NOT match the pane.

Candidate resolutions (pick one, say which and why in the task file and the
log; do not leave it implicit):

1. Explicit `light`/`dark`/`system` select a themed chrome surface (Windows 11
   uses ~#F3F3F3 / ~#202020) and the merge is accepted as broken *when the user
   asked for it*; `auto`/`ghostty` keep today's background derivation and keep
   the merge. This is the closest to what Mac does with `NSAppearance`.
2. The chrome stays background-derived always, and `window-theme` is documented
   as menus-only on Windows. Cheapest, but it silently redefines a shared
   config key per platform, which is the divergence this project does not ship.
3. Drop the dead `DwmSetWindowAttribute` caption calls either way - after T254
   they cannot paint the caption. Check whether `DWMWA_USE_IMMERSIVE_DARK_MODE`
   still affects the frame/border/shadow before deleting it, rather than
   assuming; that is a separate surface from the caption it no longer draws.

Whatever is chosen, **T274 is a prerequisite in spirit**: any theming that can
put a light band on screen makes the hardcoded light foregrounds unreadable.
Land T274 first or land them together.

## Validation

- `test/win32/test-desktop-harness.ps1` gains back a `window-theme` assertion
  ONLY if resolution 1 is chosen; if resolution 2, the doc says so instead.
- A dedicated assertion in `test/win32/caption-bar.ps1`: flip the theme with
  the background held constant, and the caption band must move (resolution 1)
  - with the SEPARATION asserted, not just each side's threshold.
- Contrast floor re-checked on whatever band results (design system, 4.5:1
  text / 3:1 glyphs). See T274.
