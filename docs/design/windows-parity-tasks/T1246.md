# T1246 - Ghoztty has no code signing certificate, so the signing pipeline has nothing to sign with

## In plain terms

Downloading Ghoztty for Windows still raises a full-screen warning naming the
publisher as unknown, and on some machines Defender deletes the download
outright. The machinery to stop that exists and runs on every release; what it
is missing is the certificate itself, which someone has to buy in Ghoztty's
name. You chose to buy an EV certificate (D89), and an EV certificate is not a
file - the key stays locked inside a hardware token or a cloud vault, which
the pipeline could not talk to. It can now. Everything left is the purchase
and loading a few values into the repo's settings; no more code has to
change.

## Goals

- [x] The pipeline can sign with a certificate whose key never leaves a token
      or a cloud HSM, which is the only kind an EV purchase produces
- [x] Nothing in the release output still tells a reader that no certificate
      will ever be bought
- [ ] A certificate exists in Ghoztty's name (the user's to buy - D89)
- [ ] Its secrets are loaded and a release ships signed

## Summary

T1203 built the signing pipeline: `dist/windows-installer/sign-artifacts.sh`,
called from the shared `build-release-artifacts.sh`, signs `ghoztty.exe`,
`ghoztty.com` and `ghoztty-agent.exe` before the packages are cut and then the
MSI itself, using `osslsigncode` on the Linux release runner. It reads two
secrets:

T1246 then added the SECOND backend, which is what D89's answer actually
needs. The pipeline reads one of two mutually exclusive sets:

| Backend | Secrets | For |
|---|---|---|
| PFX | `WINDOWS_SIGN_PFX_BASE64`, `WINDOWS_SIGN_PASSWORD` | an OV certificate, or any exportable `.pfx` |
| PKCS#11 | `WINDOWS_SIGN_PKCS11_MODULE`, `WINDOWS_SIGN_PKCS11_KEY`, and either `WINDOWS_SIGN_PKCS11_CERT` or `WINDOWS_SIGN_CERT_CHAIN_BASE64`, with `WINDOWS_SIGN_PASSWORD` as the PIN | an EV certificate on a hardware token or in a cloud HSM |

While neither is configured, every release builds normally and prints an
UNSIGNED banner naming this task. Nothing else has to change: adding the
secrets is the whole remaining act.

**Why PKCS#11 rather than an issuer's own CLI.** An EV certificate bought
today cannot be exported: the CA/B Forum rules put the private key on a
FIPS-140 token or in a cloud HSM, so no issuer will hand over a `.pfx`, and a
pfx-only pipeline is one the certificate being bought cannot use. PKCS#11 is
the interface every one of them already exposes - SafeNet and YubiKey tokens,
DigiCert KeyLocker, SSL.com eSigner, Azure Trusted Signing - so which issuer
is chosen stops being a code change here, and `osslsigncode` already speaks
it, so no new tool joins the release runner. The key never moves in either
direction: the signer sends the token a hash and gets a signature back.

Configuring BOTH backends is a hard error rather than a precedence rule, and
every PKCS#11 misconfiguration is refused before the first artifact is
touched - a token that failed on the third of four binaries would leave a
payload where some are signed and some are not, which is the one shape worse
than an openly unsigned release.

What remains is therefore not code. It is:

1. **Choose a certificate type.** ANSWERED by D89 (2026-09-04): **EV**. An OV
   certificate removes "Unknown publisher" but SmartScreen reputation accrues
   by download volume, so early downloads can keep warning for weeks; EV
   carries reputation immediately and the warning is gone from the first
   download. D87 had chosen to stay unsigned instead; D89 reversed it after
   Defender quarantined a published release on a second machine (T1293).
2. **Buy it**, which needs payment and organization/identity validation. Not
   something this seat can do.
3. **Load the secrets** into `dzearing/ghoztty` and cut a release. For a
   cloud-HSM issuer that is `WINDOWS_SIGN_PKCS11_MODULE` (the path their
   installer puts the `.so` at on the runner - if it does not come from an
   apt package, add its install step alongside `osslsigncode` in
   `release-windows.yml`), `WINDOWS_SIGN_PKCS11_KEY`, the certificate as
   either `WINDOWS_SIGN_PKCS11_CERT` or `WINDOWS_SIGN_CERT_CHAIN_BASE64`, and
   the PIN as `WINDOWS_SIGN_PASSWORD`. The runner already installs the OpenSSL
   pkcs11 engine and OpenSC on every run, so no workflow edit stands between
   the certificate arriving and a signed release.
