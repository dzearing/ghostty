# T979 - An acceptance script that reads a pane's banner straight out of +list can score a pane that has not published it yet

## Summary

A pane's sticky banner is published from that pane's own IO thread, after the pane already exists and already answers `+list`. So `+list` will happily hand back a leaf whose `banner` field is not filled in yet, and a script that reads it in the same breath as the leaf scores a pane that has not spoken. Not hypothetical: it sent arm E of `test/win32/session-relaunch-notify.ps1` red against a correct build, and the red was believed enough to be filed as a P0 defect (T977) about a restored pane losing its interrupted-session notice. The product was fine - the notice lands 0.8s after the leaf appears.

That script now waits (`Wait-BannerSettle`) and bounds the wait (E4b). Every other harness that reads `.banner` out of `+list` still has the unpolled shape: `agent-integrations.ps1`, `agent-recovery.ps1`, `cli-argv-fidelity.ps1`, `hook-json.ps1`, `pane-banner.ps1`, `pane-id.ps1`, `reset-context.ps1`, `window-name-env.ps1`. Most set the banner themselves through `+set-banner`, a synchronous IPC round-trip and therefore probably safe - but "probably" is the state this task exists to end. Sweep them, and where a read can outrun a publish, give it the same settle-then-score shape rather than a sleep.

## In plain terms

Some of our own tests ask the app "what banner is on this pane?" at the exact moment the pane appears, which is a moment before the pane has had a chance to answer. When that happens the test reports a missing banner and a real defect gets filed against working code - which is what already happened once. Nobody using Ghoztty sees anything from this; it costs engineering turns chasing bugs that are not there.

## Goals

- [ ] Enumerate every acceptance script that reads a pane banner out of `+list`
- [ ] For each, decide from the code whether the read can outrun the publish
- [ ] Give the racy ones a bounded settle-then-score wait, never a sleep

## Validation criteria

- [ ] Each named script either re-runs green with a settle wait, or carries a one-line comment saying why its read cannot race (e.g. the banner came from a synchronous `+set-banner` earlier in the same script)
- [ ] No new sleeps: the wait is bounded, so a slow publish is still a failure rather than an absorbed delay
