# T911 - Scrollback between ring snapshots survives an agent crash, not just the bytes the holder still holds

## Summary

T906 adopts a surviving holder and resumes at the exact offset the session's on-disk ring snapshot ends at, so nothing is duplicated and any real gap is named out loud. But the owner ACKs the holder the instant it delivers bytes to the ring, and an ACK is the holder's permission to FREE them - so after an agent crash the replay buffer no longer holds anything between the last ring snapshot and the crash, and the agent-side ring comes back missing that stretch. It is invisible today only because the app never restarted and still holds the grid; a viewer that restarts too (the T907 upgrade path, a reboot, a second viewer attaching) replays from the agent's ring and sees the hole. The fix is to make the ACK mean DURABLE rather than DELIVERED: a new Child.releaseTo(offset) called after a successful ring_snapshot write (outside the store lock, like the foreground-command sampler), with the holder-backed child acking min(received, durable). The 1MB replay buffer then covers the snapshot interval; a shell that outruns it drops oldest and reports the gap exactly as it does now.

## In plain terms

If the background session manager crashes, your pane keeps running and
reconnects — but the history it can replay to a *fresh* window stops at the last
time it saved scrollback to disk. Anything printed between that save and the
crash is gone from the saved history, even though the program that printed it is
still running. This closes that window so a restart after a crash shows you
everything, not everything-up-to-the-last-save.

## Goals

- [x] The holder keeps un-snapshotted output instead of freeing it on delivery.
- [x] A crash mid-output loses nothing a fresh viewer would have seen.
- [x] Overrunning the replay buffer stays loud (the existing gap warning), never
      silent.

## Validation criteria

- [x] Acceptance: with a holder-backed pane, print a marker, kill the agent
      WITHOUT letting a ring snapshot happen in between, and the marker is there
      afterwards. Measured by `test\win32\holder-durable.ps1` (ALL PASS, 15
      assertions) — which reads the **ring snapshot file on disk** rather than
      the pane. That is the same thing "restart the app too" was reaching for
      and a stronger version of it: the file IS what a fresh viewer replays
      from, so a marker in it cannot be the app's surviving grid, and the run
      does not depend on session restore putting the pane back.
- [x] Negative control: the same build on the same box with the durability gate
      off (`-NegativeControl` ⇒ `GHOZTTY_AGENT_DURABLE_ACK=0`) LOSES the marker
      — ALL PASS, 15 assertions. So the harness measures the fix, not the box.
- [x] Unit: `ackTarget` — `min(received, durable)`, `durable == 0` releasing
      nothing, an unarmed child unchanged, and a durable value that overshoots
      `received` (`pty_holder_child.zig`); plus the store side in
      `session.zig` (released at the snapshot's offset, never the live one; a
      clean ring does not re-release; no `rings_dir` releases nothing at all).
- [x] `zig build test-agent` + both zig lanes green; `holder-adopt.ps1`,
      `pty-holder.ps1` and `pty-host.ps1` stay ALL PASS.
