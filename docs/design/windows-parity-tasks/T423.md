# T423 - The session-interrupted notice never survives the ConPTY repaint: the user wants it inline in the scrollback, above the shell content

## In plain terms

When Ghoztty restarts and a terminal you had open cannot be resumed, it is
supposed to tell you so right there in that pane — a line of text sitting above
whatever the fresh shell prints, that you can scroll back to, select and copy
like any other output.

That message is written, but you never see it: the new shell clears the screen
a fraction of a second later and wipes it. All that survives is a sticky note
pinned over the pane, which is not the same thing and is not what was asked
for. This puts the message back where it belongs, in the pane's own history.

## Goals

- [x] The message appears in the pane's scrollback, above the shell's own output
- [x] It survives the new shell's startup screen-clear
- [x] It is selectable and scrollable like ordinary terminal text
- [x] It does not land below the prompt, where it would interrupt typing
- [x] It survives the pane being resized afterwards — including the moment a
      split is created next to it, which turned out to be the hard half: two
      earlier fixes looked right and still lost the message in exactly the
      panes the user has

## Summary

**User report, 2026-08-03**, after the T120 upgrade: *"I expected the session
interrupted message to be displayed inline, above the shell content but within
the console logging."*

The in-stream notice already exists and is already written —
`session_notice.format` at `src/termio/Remote.zig:784`, immediately before the
banner copy. The user did not see it, which means it is still being erased:
`session_notice.zig:70-77` records the measured reason, that a fresh `cmd.exe`
under ConPTY opens with a full-screen repaint (`ESC[H ESC[2J`) that wipes
anything printed microseconds earlier.

So the banner was added as the copy that survives. **The user is telling us the
fallback became the only carrier, and that is not what they want.** They want
the notice where terminal output belongs — in the scrollback, above the shell's
own content, selectable and scrollable with everything else.

## The real problem is ordering, not the carrier — WRONG, see "What it turned out to be"

`session_notice.zig` names both failure modes and they bracket the fix:
printing BEFORE the shell's repaint loses the notice; printing AFTER it lands
below the prompt, where the user is typing. Neither is what was asked for. What
is wanted is the notice at the TOP of the fresh shell's output — which means
writing it once the shell has finished its startup repaint but having it land
above the shell's banner/prompt, or suppressing/absorbing the repaint on this
path.

Worth checking whether the repaint can simply be waited out (write the notice
on the first output from the child rather than before it), and what the other
shell flavors do — the measurement in `session_notice.zig` is `cmd.exe`
specific and `pwsh`, `wsl` and git-bash may not repaint at all, in which case
the current code is already correct for them and only `cmd` needs the
treatment.

Related: **T422** (the banner carrier is clobbering the user's own banner). If
this task lands cleanly, the banner copy may not need to exist at all, which
would resolve half of T422 for free. Do not assume it — measure.

## Validation

`test\win32\session-relaunch-notify.ps1` already drives the notify path; extend
it to read the pane's scrollback after the relaunch (`+read`) and assert the
notice text is present, ABOVE the shell's first prompt. That assertion would
fail today, which is the point.

## What it turned out to be

Not the ordering problem the task above guessed at. Waiting the repaint out and
printing "at the top" is not available: a ConPTY child does not print into our
terminal, it hands us conhost's whole screen buffer as **absolutely positioned
VT**, and every repaint addresses rows from the top of the viewport. Anything we
leave on the active screen is either erased by the opening `ESC[H ESC[2J` or
painted over, and anything we insert shifts conhost's coordinate frame out from
under it. **Above the viewport is the only region conhost never addresses**, and
`ESC[2J` does not reach it — so the notice belongs in the SCROLLBACK, which is
also exactly where the user asked for it ("within the console logging").

So: write the notice, then scroll it off the top. `session_notice.foldIntoScrollback`
scrolls `cursor.y` rows — the notice's real height, wrapping included, because
it ends every line with CRLF — and re-homes. Re-homing is not cosmetic: conhost
believes the cursor is at (1,1) when the child starts, so a shell flavor that
does NOT repaint (the `cmd.exe` measurement does not generalise) would otherwise
paint offset from conhost's model of the same screen. **The shell-flavor question
this task raised dissolves**: the fix does not care whether the child repaints.

### The part that took the measurements: reflow drags it back

Folding once — at any moment — is not enough, and the first two attempts both
shipped a half-fix that the acceptance arm caught:

- A ConPTY pane's viewport is mostly trailing blank rows (the shell paints four
  lines into twenty) and **ghostty's reflow refills those out of the scrollback**.
  Measured at 64x20 -> 31x20: the notice's last two lines came back onto the
  active screen, where the child's next full repaint — conhost sends one after
  every resize — erased them.
- That is the whole reported shape. A restored pane is not done resizing when
  its notice is written: creating the sibling of a split narrows it. The pane
  alone in its window kept the entire notice; both panes of the split kept only
  its first line. Folding later (from the drain, on the last tick before the
  child's first bytes) fixed the pane that was narrowed BEFORE its child spoke
  and left the one narrowed after: 0 of 2 panes -> 1 of 2.
- The fix that holds is a **tracked pin** on the row just below the notice.
  A pin is the only handle that survives a reflow — it is what selections are
  tracked with — so after every resize, for the pane's whole life,
  `session_notice.holdAbove` asks where that row is now and scrolls it back out
  of the active area if the reflow dragged it in. No timers, no arming window,
  and a no-op (one `pointFromPin`) in the overwhelming case where nothing moved.

### Where it lives

- `src/termio/session_notice.zig` — `foldIntoScrollback`, `trackFold`,
  `holdAbove`, with unit tests in the none lane covering a geometry sweep
  (7 widths x 7 heights, including panes shorter than the notice), the
  resize-then-fold ordering rule, the measured 64x20 -> 31x20 reflow, and the
  cost-nothing no-op case.
- `src/termio/Termio.zig` — `armNoticeFold` / `settleNotice` /
  `holdNoticeAboveLocked`, the last called from both `resize` and
  `reflowLocalGrid`; the pin is untracked in `deinit` before the terminal that
  owns its storage.
- `src/termio/Remote.zig` — arms after writing the notice, settles from
  `drainRing` immediately before the child's first chunk is parsed (same
  thread, so no resize can interleave).

The **banner carrier is deliberately kept**: the in-stream copy is above the
viewport, so a user who does not scroll never sees it. Whether the second copy
still earns its cost — the pane's own banner — is T422's call, and it now gets
to make that call against a working in-stream copy rather than as the only
carrier.
