# T1120 - morning-refresh.ps1: only one of the two routes to the restart prompt is deferred

## In plain terms

The daily automatic update is meant to never interrupt you - in particular it must never pop up a box asking about restarting the background helper, since nobody is there to answer it. There are two ways that box can be triggered and only one of them is being suppressed.

## Summary

`test\win32\morning-refresh.ps1` scored `1 FAILURE(S)` in the T1094 sweep:

```
FAIL E3 both routes to that modal are deferred (staleness and skew)
```

The assertion names its own scope: there are TWO ways to reach the agent-restart modal - staleness and skew - and the deferral only covers one. T525's whole contract is that the morning refresh delivers the app and defers anything that would end the loop or require an answer, because it runs unattended in the user's session at 5am.

This is the same family as [[T1098]] (a delivery-time dialog that can block an unattended run), and the two should be checked against each other: any prompt reachable from the refresh path is a defect, regardless of which check raises it.

## Where

- `scripts/morning-refresh.ps1` and the deferral it passes down
- `scripts/upgrade-ghoztty-windows.ps1` - the agent-restart confirmation and both routes to it
- `test/win32/morning-refresh.ps1` section E

## What was actually wrong

`E3` counted `agent_upgrade.applyDeferral` call sites and demanded two, on the
theory that the agent-restart modal has two routes. **T1056 deleted one of the
routes**: a stale agent BUILD raises no modal any more (its `.confirm_first` arm
logs and refuses), so there is nothing left there to defer and a second
`applyDeferral` could only be decoration. The surviving route - a protocol skew -
has been deferred since T525 and still is.

So the failing assertion was stale rather than the code being wrong. Replacing it
with "neither route can put that modal on an empty desk" (`E3a` skew defers,
`E3b` staleness never asks) is what the contract has said since T1056, and both
halves have teeth: removing either guard fails the script.

**The audit that goal 2 asked for then found a real one.** The delivery kills only
the ghoztty processes running from the INSTALL dir, by design - so a
Desktop-portable or share copy of the same lineage keeps the IPC endpoint, the
freshly installed exe loses the bind race, and T1023's "a different build owns the
endpoint" prompt appears with nobody in front of it. That one is the worst shape
available: the asking process shows the modal and then exits, so the terminal the
delivery promised to bring back never appears at all until somebody clicks it.

## The enumeration (goal 2)

Every modal an unattended relaunch can raise on its own, and what it does now:

| Prompt | Route | Verdict |
|---|---|---|
| Agent restart, stale BUILD | `refreshLocalAgentIfStale` | **Cannot ask** since T1056 - the `.confirm_first` arm refuses and logs. `E3b` |
| Agent restart, protocol SKEW | `handleAgentProtocolSkew` | **Deferred** by the marker since T525. `E3a` |
| "A different build owns the endpoint" | `handoffChoice`, on the `AlreadyRunning` startup path | **Was reachable; now suppressed** - joins without asking while the marker is live, which is the non-destructive answer the function already fails toward. `E3c` |
| One-time agent-integration offer | `AgentIntegration.showFirstRunPrompt` | **Was reachable; now suppressed** - and returns BEFORE the state write, so the one-time offer is not burned on an empty desk. `E3d` |
| One-time plugin-migration offer | `AgentIntegration.showMigrationPrompt` | Same. `E3d` |
| Agent refresh failed | `showAgentRefreshFailed` | Not reachable unattended: only a user who confirmed the restart can get there. |
| Config errors | `showConfigErrorsIfAny` | **Deliberately NOT suppressed** - it reports the user's own broken config, the window opens behind it, and hiding it during the refresh would mean they only learn of it on a manual restart. Kept as a control, `E3e`, so this never becomes "suppress everything". |
| Remote-open failed / machine chooser / close confirmations / `ghoztty://` consent | user actions | Not on the refresh path at all. |

Script side: T1098 closed the other half (a damaged binary raising Windows' own
system-modal "Unsupported 16-Bit Application" box), by reading the PE header
instead of launching the file. Nothing in `morning-refresh.ps1` or
`upgrade-ghoztty-windows.ps1` calls `Read-Host` or a `-Confirm` prompt.

The marker is now documented as what it has actually become: not "the
agent-restart confirmation is deferred" but "an unattended delivery is in
progress, so the app raises no prompt of its own".

## Second stale expectation, same script

`D13 CONTROL: an ordinary delivery succeeds too` was failing for an unrelated
reason and had not been noticed: T1098 made the delivery fail outright when the
agent it is about to ship is not a real program, and this control stages an ascii
sentinel. It now stages the repo's own built `ghoztty-agent.exe`, so `AGENT
VERIFY` has a real build stamp to read back - which makes the control stronger
than it was (`D15` compares hashes, `D15b` requires `AGENT VERIFY OK`) rather than
merely green again.
