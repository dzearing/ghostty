# T627 - macOS has no protocol-skew mandatory-update path either

## Summary

Found while building T125, filed for the Mac seat under the platform-symmetry
rule. Windows now routes an incompatible agent HELLO into the mandatory-update
path CLAUDE.md's agent contract requires. macOS does not: `LocalAgentManager`
has the staleness half (`makeUpgradeAlert`, build-stamp comparison) but nothing
that acts on a handshake that failed to negotiate — the same silent give-up
Windows had.

## In plain terms

On a Mac, if the background process that keeps your terminal sessions running
ends up speaking a different language than Ghoztty — after an update, or after a
rollback — Ghoztty just cannot reach it and says nothing. Windows now explains
what happened and offers to fix it. The Mac should do the same thing.

## Goals

- [ ] The Mac dialer distinguishes an incompatible handshake from every other
      dial failure (the win32 half is `error.ProtocolIncompatible` in
      `src/remote/tcp_dial.zig`, which is SHARED Zig — so this half may already
      be done; check before rebuilding it).
- [ ] The direction is known before anything destructive happens (never
      downgrade a newer agent).
- [ ] Agent-older takes the existing `makeUpgradeAlert` path with skew copy.

## Details

The pure policy is already written and shared-shaped:
`src/apprt/win32/agent_upgrade.zig` `evaluateSkew` + `formatSkewConfirmText`.
It lives under `apprt/win32/` because that is where the staleness policy lives;
if the Mac wants it, the honest move is to hoist both to a shared module rather
than write a second copy — the two must never disagree about when it is safe to
kill an agent.

Windows evidence: `test/win32/agent-upgrade.ps1` arms J and K.

## Validation criteria

- [ ] A Mac-side test proving an incompatible peer is distinguishable from an
      unreachable one.
- [ ] The skew confirmation appears for an older agent and never for a newer
      one, with the Mac regression suite green.
