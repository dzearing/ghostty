# T1177 - Ghoztty never silently fails to start: a startup failure raises an error dialog immediately, not a timeout message minutes later

## Summary

Launching Ghoztty with a missing or unstartable agent produced NO window, NO dialog and no feedback at all - eventually surfacing some agent error long after the user gave up. That is the unacceptable case. Every startup precondition (agent binary present, agent spawnable, named pipe reachable, config loadable) must fail LOUD and FAST: a dark ConfirmDialog/MessageBox naming what failed and what to do, raised on the spot rather than after a probe timeout. Shorten the first-run agent probe so the feedback arrives in seconds, and make silent-exit-on-startup-error impossible by construction (no bare log.warn path that returns without a window).

## In plain terms

You double-click Ghoztty and nothing happens. No window, no error, no
explanation - just a shortcut that appears to do nothing, and if you wait long
enough, an unrelated complaint about something timing out. That is what a
half-installed or otherwise broken Ghoztty looked like, because the app has no
console to print to and every startup error simply fell out of the program into
nowhere. Now a startup that cannot put a terminal on screen says so, in a
window, within a fraction of a second: what went wrong, and what to do about
it. And if Ghoztty starts but a piece of it is missing, it says that too
instead of quietly dropping the feature.

## Goals

- [x] Any error during startup raises a dialog naming the failure and a remedy
- [x] A startup that ends with no window on screen is treated as a failure
- [x] The dialog arrives in well under a second, not after a probe deadline
- [x] A failed launch exits nonzero so a launcher can tell it failed
- [x] A missing session agent is reported instead of silently disabling
      persistence
- [x] The whole chain has an acceptance script and a staleness guard

## Validation criteria

- [x] A startup with no window raises Ghoztty's own dark dialog rather than
      exiting silently - `test\win32\startup-failure.ps1` arm A1, ALL PASS
      (18 assertions).
- [x] The dialog arrives fast: measured **227ms** from launch, against a 10s
      budget - arm A2.
- [x] The dialog is written for a person: it names the stage ("opening its
      first window"), the error (`NoStartupWindow`), a remedy ("Restart it")
      and the log path, read back out of the LIVE dialog with WM_GETTEXT -
      arms A3-A7.
- [x] Dismissing it ends the process with exit code **1**, so a launcher (the
      installer's launch step, T1176) can tell a failed launch from a good one
      - arm B2, with the exit code read through a cached handle so an
      unreadable code cannot pass.
- [x] Negative control: with the seam off the same build opens a real window,
      raises no dialog, and stays running - arms C1-C3.
- [x] A missing session agent is SAID rather than silently absorbed: the
      terminal still opens, a notice titled "Session persistence unavailable"
      names the consequence and the remedy, and dismissing it leaves the
      terminal running - arms D1-D5, driven by pointing
      `GHOSTTY_LOCAL_AGENT_BIN` at a path that does not exist.
- [x] Message composition is unit-tested in the win32 lane (`startup_error.zig`
      tests: remedy mapping, the unmapped-error fallback, the full body, and
      the too-small-buffer path returning empty rather than panicking) - and
      the tests were PROVEN to run: a deliberately broken assertion went green
      until `src/apprt/win32.zig`'s test-import list named the module, and red
      on the identical tree once it did. That gap is filed as T1191.
- [x] Floor: `scripts\floor-lane.ps1 -Lane all` green (lib + none + win32 +
      agent).
- [x] `scripts\guard-due.ps1` carries a `startup-failure` row, so an edit to
      the reporter, the dialog, the message text or `main_ghostty.zig`
      re-asks whether the failure still reaches the user.
