# T636 - Viewer feedback: report.json writer with staging + atomic rename, and native sourceLine

## In plain terms

This is the task where pressing Send actually does something: your message,
plus what you had selected and where you were, gets written into a folder
inside the repo the pane belongs to, where a separate tool can pick it up. It
is written so that the tool either sees a complete report or sees nothing at
all — never a half-written one.

## Goals

- [x] A pressed `↑` / Ctrl+Enter writes one self-contained report folder into
      `<worktree>/temp/feedback/new/`.
- [x] A watcher never sees a half-written report: the folder is built in
      `.staging/` and published with one rename.
- [x] The report names the exact revision the user was looking at (branch +
      commit), resolved off the UI thread.
- [x] Each quote carries the source file line it came from, or nothing at all
      rather than a wrong line.
- [x] The composer empties and says "Filed …" before closing itself.

## Summary

## Details

The format is portable as-is and CLAUDE.md's "Report output" section is the
spec — do not re-derive it:

```
<worktree>/temp/feedback/new/<timestamp>-<suffix>/
    report.json
    images/image-1.png
```

- **Atomicity is the load-bearing property.** Build the whole folder under
  `temp/feedback/.staging/` and move it into place with a **single rename** on
  the same filesystem (`MoveFileExW` without `COPY_ALLOWED`, so a cross-volume
  fallback can never silently turn one rename into a copy loop). A watcher sees
  nothing or a complete report.
- **JSON, not markdown-frontmatter** — a prose body containing `---` or a
  `key:` line breaks naive frontmatter splitting; JSON has one parse path.
- `body` is markdown, with each image chip rendered as
  `![Image #N](images/image-N.png)`, folder-relative so the folder survives
  being moved to an `in-progress/` queue.
- Context blocks, all of them: `source` (`location`, `kind`, `filePath`,
  `relativePath` repo-relative, `pageTitle`, `selection`, `paneID`,
  `viewport`), `worktree` (`path`, `name`, `branch`, `commit`), `app`,
  `quotes`, `images`.
  **Scope note (T633 landed 2026-08-08):** T633 shipped the resolver's ROOT
  half — `viewer_worktree.candidateDirectory`/`rootArgv`/`parseRoot`/
  `worktreeName` plus `ViewerWorktreeProbe`, which is where `path` and `name`
  come from. It did NOT ship Mac's `ViewerWorktreeResolver.revision(at:)`, so
  `branch` and `commit` are THIS task's to add: two more `git -C <root>
  rev-parse` calls (`--abbrev-ref HEAD`, `HEAD`), argv+parse in the pure module
  beside the existing pair, run on the probe's worker rather than at send time
  on the UI thread. A detached HEAD has no branch and a repo with no commits
  has no HEAD — both report null rather than a guess, exactly as Mac does.
- **`sourceLine` is resolved here, natively.** For file viewers, search the
  file for the passage and report a 1-based line; report **null rather than a
  confidently wrong line**. Mac's reasoning is explicit: mapping rendered DOM
  back to markdown source is unreliable, searching is not.
- The queue lives under `temp/` because that name is gitignored here and
  conventionally elsewhere — a top-level `.feedback/` showed up as untracked in
  `git status`. Do not relocate it.
- On success the composer clears and the toolbar shows a "Filed …"
  confirmation before closing.

Windows-specific care: paths are `\`-separated but the report's
`relativePath` and image references are folder-relative and should be written
with `/` so a report authored on Windows reads the same as one authored on a
Mac (the consumer is shared). The timestamp suffix must be filename-safe on
NTFS — no `:` — which the Mac stamp format may not guarantee; state the format
chosen and test it.

## Validation criteria

- [x] Unit tests (none lane): the report serializer round-trips every context
      block; `sourceLine` finds a unique passage, and returns null for a
      passage that is not in the file; `relativePath` and image references use
      `/`; the folder name is NTFS-safe.
      — `viewer_feedback_report.zig` (14 tests) + `viewer_worktree.zig`'s three
      new revision tests + `viewer_bridge.zig`'s selection tests;
      `scripts\floor-lane.ps1 -Lane all` PASS.
- [x] On-box acceptance script: from a viewer pane opened on a file in a
      throwaway git worktree, type a message and send — exactly one folder
      appears under `temp/feedback/new/` containing `report.json`, and its
      `worktree.branch`/`worktree.commit` match that worktree.
      — `test\win32\viewer-feedback.ps1` arm G, which now views a file in a
      `git init`'d temp repo rather than this checkout (a real send into this
      repo would drop junk in the user's own queue). The commit is compared
      against `git rev-parse HEAD` of that repo, so a stale value cannot pass.
- [x] On-box acceptance: atomicity — a watcher polling `new/` never observes a
      folder without its `report.json` (assert by staging path never being
      visible under `new/`, plus a poll loop across a send).
      — same arm: a 50 ms poll loop records any incomplete folder it sees, and
      the published stem's `.staging/` counterpart is asserted gone.
- [x] On-box acceptance: a quote made in T635 arrives in `quotes` with its
      heading and block context, and with a `sourceLine` pointing at the right
      line of the source file.
      — the live win32-lane test in `ViewerPane.zig` ("host floor"), which
      quotes through the REAL selection toolbar and then reads the filed
      `report.json` back: `headingText` = "Beta", `sourceLine` = 7.
- [x] On-box acceptance: after a successful send the composer is empty and the
      confirmation is shown.
      — arm G asserts the control's text is empty, the pane logs
      `filed=true stem=… status=Filed …`, and the composer closes itself behind
      the confirmation.
