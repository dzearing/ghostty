# T248 - Acceptance scripts that reuse a --target name can silently probe a PERSISTED pane from the previous run

## Summary

`+new-window --target=<name>` is idempotent by design: an existing target is
FOCUSED, not recreated. Session persistence is on by default and the agent
outlives the app, so a pane an acceptance script created in a previous run is
still alive — and killing `ghoztty.exe` does not remove it, because the agent
holds it and the next launch restores it.

Consequence for any script that reuses a target name: on the SECOND run
onward, `+new-window --target=X -e <fixture>` does not run the fixture at
all. It focuses last run's pane, complete with last run's painted screen. A
screen-pixel or `+read` oracle then measures the PREVIOUS build and passes.

Observed for real while building `test/win32/color-contrast.ps1` (T150): the
pane was running `cmd.exe` instead of the fixture, and the probe was reading
pixels the previous run had painted. It was caught only because two bands
returned an identical, suspicious value.

The fix that script now uses, and the pattern to spread:

- kill the repo's `ghoztty-agent.exe` alongside `ghoztty.exe` (path-filtered
  to `zig-out*`, so the user's installed agent is untouched);
- launch the GUI with `--session-persistence=off`;
- make any fixture handshake file run-unique (`$PID`), so a leftover file can
  never be mistaken for this run's fixture reporting in.

## Validation

- Audit `test/win32/*.ps1` for scripts that create a named target and assert
  on pane CONTENT (`+read`, screen pixels) — those are the ones that can go
  false-green. A script asserting only on `+list` structure is less exposed
  but still gets a stale pane.
- For each, apply the three-part fix above.
- Prove the exposure the same way it was found: run a script twice in a row
  with the fixture deliberately broken on the second run and confirm it now
  FAILS rather than passing on restored pixels.

## Outcome (2026-08-02)

The fix is hoisted, not copied: **`test\win32\lib\CleanSlate.ps1`**. One
`Reset-GhozttyTestState -Exe <exe>` does the whole reset — exact-exe kill of
the app AND its sibling agent, plus deletion of the debug session-layout
manifest — and 19 scripts call it instead of a private copy (the 15
`Stop-DebugGhoztty` copies, plus the inline kills in `ipc-under-load`,
`profile-latency`, `soak`, `wheel-scroll`). `focus-defer.ps1` keeps its own
FD-LOAD flood-shell sweep on top; that is its litter, not shared hygiene.

**The manifest is the second resurrection path, and no script had ever cut
it.** T248 named the agent, and killing the agent alone is not enough:
`%LOCALAPPDATA%\ghoztty\session-layout-debug.json` describes the window by
target NAME, so the next launch restores it whether the agent survived or not.
`Clear-DebugSessionLayout` only ever removes the `-debug` file — a ReleaseFast
build writes `session-layout.json`, which is the same file the user's
installed Ghoztty restores from, and that one is never ours to delete.

**Proof, executable and live: `test\win32\target-staleness.ps1` (ALL PASS).**
It runs one fixture three times under two hygienes and asserts they disagree:

- POSITIVE CONTROL — kill the app only (the old hygiene), re-issue the same
  `--target` with a different fixture. Reproduces on this box today: *"stale
  pane came back, fixture B never ran"*. If it ever stops reproducing the
  script says so and fails, rather than passing on a premise that has quietly
  expired.
- THE FIX — `Reset-GhozttyTestState`, same target again: the new marker is on
  screen and neither of the previous two is.

Its target and handshake names carry `$PID`, which is the third part of the
fix applied to the script that documents it.

**The audit turned up a bigger sibling, and it is filed as T350.** A script
aims by ENDPOINT, not by exe path: `-Exe zig-out\bin\ghoztty.exe` picks the
CLI binary, while the pipe name comes from the build MODE. A `zig build
-Dapp-runtime=win32` without `-Doptimize=Debug` therefore puts the entire
suite on the user's installed Ghoztty's endpoint. Observed for real, before
any change: `zig-out\bin\ghoztty.exe +list --json` answered
`"exe":"...\Programs\Ghoztty\ghoztty.exe"`, and that install was holding a
`[target: p1win] P1Title` window — an `ipc-p1.ps1` fixture leaked into the
user's running terminal by an earlier run. `Assert-GhozttyUnderTest` catches
it whenever a foreign app is already answering (the common case) and runs as a
pre-flight inside every reset; the cold-box half is T350.

Follow-ups: **T350** (endpoint aim / build-mode guard), **T351** (finish the
sweep — ~29 scripts still carry private kill helpers under other names),
**T352** (target names are still fixed strings shared across runs).

Floor at the boundary: `zig build test -Dapp-runtime=none` exit 0,
`-Dapp-runtime=win32` exit 0, `zig build test-agent` exit 0, P1/P2/P3 all
`ALL PASS`, `target-staleness.ps1` ALL PASS on two consecutive runs.
