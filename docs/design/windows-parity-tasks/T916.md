# T916 - The link-paths row walk does not actually walk rows: probe clicks land on a clamped bottom row

## In plain terms

A test that is supposed to click twelve different lines of a terminal pane
appears to keep clicking the same one near the bottom. Its answers are still
real, but it is measuring one line and reporting it as twelve — so a problem
that only shows on some lines would slip through.

## Summary

Found while adding T802's double-click arms to
`test\win32\terminal-link-paths.ps1`.

`Get-Column0Selections` walks rows by computing a y from the surface's client
rect (`Get-TestWindowRect -Client`, which returns the client area in SCREEN
coordinates) and handing it to `Send-TestMouse -Y`, which is also screen. That
should be right — but an instrumented Debug build logging the position the
core resolves for each press showed the app receiving a y about **39.4x** the
screen y that was posted, at a constant ratio across samples:

```
posted screen y   237     292     348
core pos.y       9328   11492   13696     (ratio 39.36 = 100/2.54, every row)
```

x came through unscaled (`4` in, `4` at the core). A y that large is below the
pane, so `posToViewport` clamps it and every probe resolves to the bottom
row(s) — which is why an 8-row walk returns one or two unique strings, and why
the same points can answer differently across two passes: when a probe's
ctrl+c finds no selection the performable binding falls through to the shell,
`^C` prints a fresh prompt, and the screen scrolls under the next pass.

That drift is what made T802's jitter arm (section E) read as a product
failure while the instrumented build showed the core doing exactly the right
thing (`samePin` firing, selection preserved). The arm was rewritten to assert
selection GRANULARITY rather than one exact string; it should go back to
asserting the string once the walk really walks.

Where to look: the y scaling is the whole question — DPI context of the
harness process vs the app on a background desktop is the first suspect
(2.54 is suspiciously exact), then `ClientRect`'s `ClientToScreen` under that
context, then `posToViewport`. Whatever the cause, the fix must make a probe's
target row PROVABLE: have the walk assert that at least two DIFFERENT row
contents were reached, so a future regression to one-row sampling fails
instead of passing quietly.

## Validation criteria

- [ ] The cause of the y scaling is named with evidence (not "adjusted until
      it worked")
- [ ] A probe at row i in `terminal-link-paths.ps1` demonstrably lands on row
      i — asserted, e.g. by the walk seeing at least two distinct row contents
- [ ] T802's section E goes back to asserting the exact URL string
- [ ] `test\win32\terminal-link-paths.ps1` stays ALL PASS
- [ ] Any other script using the same client-rect-to-Send-TestMouse idiom is
      swept for the same error
