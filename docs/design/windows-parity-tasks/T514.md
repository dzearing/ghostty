# T514 - A config 'command = <shell>' on an agent-backed pane runs nested under the default shell and loses shell integration

## Summary

The natural way to make PowerShell your everyday shell is `command = pwsh` in
the config. On the DIRECT spawn path that is exactly what T27 integrates:
`Exec` resolves `cfg.command` as the shell and injects the rewrite. But with
session persistence on (the default), every pane is agent-backed, and there
`config.command` travels as `OPEN.command` (`command_explicit`, T104) with
`OPEN.shell` null — so the agent spawns `cmd.exe /c pwsh`: the user's shell
runs NESTED under cmd.exe, and the shell-integration argv rewrite is dropped
by design (core `Surface.zig` discards `integ_argv` whenever a command is
present, the documented T04c scope cut). Net: a config that gives a direct
pane full integration gives the default (agent) pane a wrapper process and no
integration. Same shape exists on macOS (`command = zsh` still gets env-only
integration there, so the loss is Windows-biased: powershell has no env-only
half).

Fix directions to weigh (design first): detect when `config.command` names a
bare shell (single argv0 that `detectShell` recognizes) and forward it as
`OPEN.shell` instead of `OPEN.command`, which both unwraps the nesting and
re-enables the rewrite; or run integration detection against the command's
argv0 on the agent path the way `Exec` already does. Both must keep T104's
guarantee that an explicit command still runs.

## In plain terms

Setting your preferred shell in the config file works properly for panes
spawned the old direct way, but the normal panes (the persistent ones) start
that shell inside an extra hidden cmd.exe, and the terminal loses the
features that need shell cooperation — knowing your current folder, prompt
jumping. The fix makes the config-chosen shell behave the same as passing
`--shell` on the command line.

## Goals

- [x] A bare-shell `command` (config file or `--command=`/`-e` launch) reaches the agent as the session's SHELL, so the pane's child is that shell directly — no hidden cmd.exe wrapper
- [x] That shell gets the full shell-integration rewrite, so cwd tracking and prompt features work exactly like a `--shell` pane
- [x] Commands with arguments, IPC `--command` panes, and cross-machine windows behave exactly as before

## The fix (2026-08-15)

Took the first design direction from the Summary — forward, don't re-detect:

- **`shell_integration.bareShellCommand()`** (new, pub, `src/termio/
  shell_integration.zig`): answers "is this command nothing but a bare shell"
  — exactly one argv0, no arguments, and `detectShell` recognizes it (which
  since T513 includes the Windows spellings: `bash.exe`, mixed case, full
  paths). Returns the argv0 or null. Unit-tested in both zig lanes.
- **`Surface.init` agent branch** (`src/Surface.zig`): computes
  `command_shell` from that helper and forwards it as **`OPEN.shell`** instead
  of `OPEN.command`. Guarded four ways, each load-bearing:
  - `local_shell_integration` only — a cross-machine agent keeps the T104
    stall-fix invariant (nothing local is ever forwarded uninvited);
  - never when the apprt passed an explicit shell (`rb.shell` wins);
  - never when `wait-after-command` is set — the IPC `--command` path keeps
    its T468 keep-alive contract untouched, and it has `--shell` for this;
  - only for an EXPLICIT command (`command_explicit`), so the default shell
    `Config.finalize` fills in still forwards nothing (T104 section C).

  With `OPEN.command` now null for that pane, the integration argv rewrite is
  no longer suppressed, so the pane gets the full `-NoExit -Command`
  ghostty.ps1 invocation (T27) exactly like a `--shell` pane — un-nested AND
  integrated, on both seats (macOS `command = zsh` takes the same path; Mac
  validation filed as T863).

Residual gap filed as **T864**: a bare command naming a shell `detectShell`
does NOT recognize (`cmd`, `wsl`) still nests under the wrapper.
