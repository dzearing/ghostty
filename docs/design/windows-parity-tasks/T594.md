# T594 - Test runs open http pages in the user's default browser and leave them behind

## User report (2026-08-08, verbatim)

"i keep seeing these html files opening in edge and sticking around. i don't
want this happening. http://127.0.0.1:58332/t390.html it probably has
something to do with the test run."

Recurring, plural ("files", "sticking around") - every affected run leaves
another Edge window on the interactive desktop.

## Evidence and where to look

- The URL shape is a viewer-test page: an ephemeral-port localhost server and
  a task-named page. No literal `t390.html` exists in the repo, so the name
  is generated - the T390 `+reload` section of `test\win32\viewer-panes.ps1`
  (line ~513) or the TestPage/ReloadPage HTTP servers in `ViewerPane.zig`'s
  test support are the first places to look.
- Something in that path hands the URL to `ShellExecute`-the-default-browser.
  Known product paths that do exactly that, any of which a posted test click
  or a page script could trigger:
  1. a viewer page's `window.open()`/`target="_blank"` -> system default
     browser (documented behavior);
  2. a banner/link plain click -> default browser;
  3. any fallback that shell-opens when a viewer cannot host a location.
- **The escape matters as much as the open**: the harness runs on a
  background desktop (TestDesktop.ps1) precisely so tests never touch the
  user's screen - but ShellExecute launches the browser in the interactive
  session regardless of the caller's desktop, so this class of leak defeats
  the whole isolation. The foreground watcher only detects test-desktop APP
  leaks; a browser spawned into the user's session is invisible to it.

## Direction

1. Identify the exact trigger (run viewer-panes.ps1 while watching for
   browser process creation with the parent chain, the same
   Win32_Process-parent forensics used for T524).
2. Fix at the source: whatever fires the shell-open under test must either
   not fire (the test should not click through to the browser path) or be
   gated - e.g. the app suppresses default-browser handoffs when
   `GHOZTTY_TEST_*`/test-desktop markers are present, routing them to a log
   line the test can assert instead. A product behavior change needs the Mac
   question asked (does the Mac suite have the same leak?).
3. Add a harness-wide regression arm: after a viewer-suite run, assert no
   browser process was spawned with the test tree as its parent chain (and
   close any that were, so a failed assert cleans up after itself).

## Validation criteria

- [ ] Root cause named: which test line/product path opened the browser
- [ ] A full viewer-panes.ps1 run spawns zero browser windows on the
      interactive desktop
- [ ] Regression arm exists and fails if a future test leaks a browser
- [ ] Existing suite still ALL PASS
