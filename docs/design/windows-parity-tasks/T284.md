# T284 - T226a: pure activity_layout.zig + trend_gauge.zig for the win32 Activity Monitor

## Summary

First of the four-way split of **T226** (port the Mac Activity Monitor to
win32). This is the arithmetic half: two pure modules in the none-runtime test
lane, no HWNDs, no GDI - the same division that made `chooser_layout.zig` /
`chooser_rows.zig` testable while `MachineChooser.zig` kept the win32 calls.

Why the split at all: `RemoteActivityMonitorView.swift` is 1383 lines and the
comparable win32 surface (`MachineChooser.zig`) is 1872 - one context cannot
carry the whole panel, its actions, and its remote plumbing, so T226 was split
into T284 (layout math) -> T285 (window + local source) -> T286 (process
control) -> T287 (remote sources + switcher).

## Scope

`src/apprt/win32/activity_layout.zig`

The panel is a vertical stack, and unlike the chooser it is **resizable**
(Mac: `minWidth: 620, minHeight: 380`), so `layout()` takes the client size:

1. card carousel (machine switcher)
2. divider
3. header - two trend gauges split 50/50
4. divider
5. control bar - filter field, badges, "Show all", count, actions
6. divider
7. process table - header row + rows, the only region that absorbs slack
8. error banner (conditional, Mac: padding h16/v8)

Plus `columns()`: the five table columns with Mac's min/ideal/max widths
(PID 50/60/80, Name 120/200/-, % CPU 60/70/90, Memory 70/90/110, Path
120/240/-) distributed across the available width - the genuinely interesting
pure function here, because it must honour every min and max at any width.

`src/apprt/win32/trend_gauge.zig`

Maps a ring of 0..100 samples to a polyline + the fill polygon under it inside
a rect (Mac uses Swift Charts, which win32 does not have), plus the hover hit
test (sample index under an x) and the gridline rows.

  `zig build test-agent` green, P1-P3 ALL PASS.
- Unit tests assert at 1.0/1.25/1.5/2.0 scale (per the design system: most
  chrome defects are invisible at 1.0), that regions never overlap and always
  nest in the client, that only the table absorbs slack, that column widths
  respect every min/max and sum exactly to the table width, and that the gauge
  maps 0 and 100 to the rect's floor and ceiling with monotonic x.

### What the tests caught

The control bar did not fit at Mac's own default width. Laid out with a fixed
240-wide filter field, the row needs `16+240+8+96+8+110+8+96+8+124+16 = 730` px
at 100% and the window opens at **700**, so the badge slot inverted and the
count label overlapped the checkbox. Two assertions — left-to-right ordering,
and §0.1's "nothing touches anything" — failed on it.

The fix follows Mac rather than patching the symptom: `.frame(maxWidth: 240)` is
a **maximum**, and a SwiftUI `TextField` yields under pressure. So the filter is
now the row's one elastic control (the right-hand group and the checkbox are
fixed and laid out from the trailing margin inward), capped at Mac's 240 and
floored at 120 so it never becomes a stub. Asserted across 620..3000 px.

This is the case for building the geometry as a pure module first: the defect is
a *paint* defect, and it was found and fixed before a single line of GDI existed
to paint it wrong.

### Decisions worth carrying into T285

- **Mac's ad-hoc 10 pt paddings are snapped to the 4 DIP scale** (§1 admits
  2/4/8/12/16/24 and nothing else): control rows use `md` (8), the gauge band
  keeps Mac's 12 (`lg`), dialog margins are `xl` (16).
- **The separators are 1 px hairlines**, matching the sibling dialog
  (`chooser_layout.zig`). §5's 2 DIP band governs the draggable split lines
  BETWEEN PANES, where a vanishing line costs a grab target; an intra-dialog
  rule has no grab band. Recorded so nobody "fixes" it in either direction.
- **The table is the only region that absorbs slack.** Every other band is a
  fixed height, so growing the window grows the row count and nothing else.
  Absent bands take zero height (a hidden carousel takes its rule with it,
  §6), and an absent Kill button is a zero-width rect parked where it would
  appear, so a caller that paints unconditionally draws nothing rather than
  something misplaced.
- **Column widths sum EXACTLY to the table width** at every scale and width —
  the painter walks the array to place cells, so any other invariant leaves a
  seam. Growth is weighted by *ideal* rather than by headroom, or the two
  unbounded columns (Name, Path) would swallow everything simply because their
  headroom is infinite. Below the sum of the minimums (only reachable under
  `min_client_w`) the minimums win and the caller clips.
- **Gauge samples span the full chart width even when the ring is partly
  filled.** A chart that slides sideways for the first 90 seconds of every
  panel reads as a bug; `0` maps to the rect's last row and `100` to its first,
  so a full-scale sample paints ON the rect instead of one pixel outside it.
