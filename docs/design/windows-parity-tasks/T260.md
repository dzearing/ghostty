# T260 - The strip hamburger is now a duplicate of the caption's ... on every window that has one

## Summary

T234 asked to decide the strip's "menu" button explicitly - drop it (its
preferred answer) or keep it and say why. **T234 kept it, and this task is the
reason that was a deferral rather than a decision.**

Why it was kept:

1. **It is still the ONLY menu host on a window with no custom caption.**
   `customCaption()` is false for `window-decoration = none` (and for the quick
   terminal, which has no strip either). That is exactly why T234's visibility
   rule reads `tab_count > 1 or !customCaption()` - the strip has to stay on
   such a window precisely because it carries the menu. So the hamburger cannot
   simply be deleted; it has to become **conditional on there being a caption
   button**, which is a different change.
2. **Conditional means the strip's LAYOUT changes.** `runWidth()` in
   `tab_strip_layout.zig` reserves two 28 DIP squares and two group gaps. Drop
   one and the tab run grows - which is a *good* outcome (wider tabs, T235's
   direction) but it moves the datum three acceptance scripts key off, and
   T256/T259 are both about scripts that could not survive that datum moving.

So the honest state is: on a normal window at 2+ tabs there are now two
controls, one band apart, that open the same menu. That is the
"undifferentiated cluster" complaint in a new place, and it should go.

## The design

- `tab_strip_layout.layout()` takes a `has_menu: bool` (or the caller passes a
  button count). When false, `runWidth` reclaims the square and the group gap,
  the "+" moves right into the freed space, and `Strip.menu` is a zero rect so
  every existing hit test misses it by construction.
- `Window.updateTabBarVisibility` already knows `customCaption()`; the same
  answer decides `has_menu`.
- `openMenuBarAt(.strip)` must then be unreachable on a caption window - assert
  it rather than leaving a dead anchor.

## Validation

- Unit: `runWidth` with and without the menu differ by exactly
  `btn_paint + group_gap`, at 1.0/1.25/1.5/2.0; the "+" stays `group_gap` short
  of the run's right edge in both.
- `tab-strip.ps1` (which runs `--window-show-tab-bar=always`) grows its tab run
  by that amount and still ALL PASSes.
- `menu-bar.ps1`'s strip-button sections need a window WITHOUT a custom caption
  (`--window-decoration=none`) or they lose their subject - decide and record
  which, since T190's contract is about that button.
- `tab-strip-autohide.ps1` still ALL PASSes: the caption "..." is unaffected.

## What shipped (2026-07-31)

Taken ahead of T205 (the next UI item) on purpose: T205 merges the strip INTO
the caption row, and merging first would have put the "=" and the "..." eight
DIP apart in one row - the undifferentiated cluster, at its worst. The
`has_menu` plumbing is also exactly what T205 needs.

- **`tab_strip_layout.zig`**: `runWidth(m, client_w, has_menu)` and
  `layout(m, client_w, has_menu, prefer, out)`. The difference is expressed
  ONCE, in a private `plusPaintLimit`, which both read - so a menu-less strip
  cannot end up with a run that disagrees with where the "+" actually lands.
  With no menu the "+" inherits the right-anchored slot and `Strip.menu` is a
  **zero rect**, which every existing hit test (`x >= left and x < right`,
  half-open) misses by construction rather than by remembering to ask.
- **`Window.zig`**: `stripHasMenu()` is `!customCaption()` - one rule, one
  place, the same answer the caption uses to decide whether IT hosts the menu.
  The paint site asks `!strip.menu.isEmpty()` rather than assuming a zero rect
  is harmless (`paintIconButton` would happily paint a degenerate square at the
  strip's origin). `openMenuBarAt(.strip)` asserts `stripHasMenu()` and, in a
  release build, falls back to the caption host instead of anchoring a popup on
  a button that is not painted - the dead anchor this task asked to close.
- **`test/win32/lib/ChromeGeometry.ps1`**: `HasCaption` (from the window's
  `WS_CAPTION` bit, so the script asks the OS instead of trusting its launch
  flags), `HasStripMenu`, a conditional `CaptionH` (0 with no caption),
  `MenuLeft`/`MenuX` now `$null` where the button does not exist, plus
  `RunRight` (the "+"'s painted limit - the one right boundary that means the
  same thing with and without a menu, which is what the tab scan uses now) and
  `CaptionOverflowLeft`/`CaptionOverflowX` for the caption host.

**The decision this task asked for**, on `menu-bar.ps1`: NOT a
`--window-decoration=none` window for the whole script. The window a user
actually runs has a caption, and moving the entire script off it would have
left the mainstream case untested. Instead the script asks the WINDOW where its
menu host is (`Menu-Host`), so sections B/C/D/E/F/G are unchanged; section A
gained the T260 assertions on the normal window (no glyph and no hit at the
strip's right end); and a new **section H** runs one `--window-decoration=none`
window to prove the strip KEEPS its button where nothing else hosts the menu.
H is the load-bearing half: without it every A assertion would pass just as
well against a build that deleted the button outright.

## Evidence (2026-07-31, on the box)

- **Unit**, three new tests at 1.0/1.25/1.5/2.0: the run grows by exactly
  `btn_paint + group_gap`; the "+" keeps its `group_gap` in both modes and
  inherits the right-anchored inset without one; a zero menu rect is unhittable
  at x = 0, 1, w-1 and w; and a capped tab is measurably WIDER on a menu-less
  strip (the point, not just the arithmetic).
- **`menu-bar.ps1` ALL PASS (71 assertions)**, up from 54. Its negative control
  (`-NegativeControl`) still FAILS on exactly one assertion - `A(neg): the menu
  button paints NO glyph (27 ink pixels)` - so the pixel probe follows the host
  to the caption band and still measures real ink.
- **`tab-strip.ps1` ALL PASS (37)**, `tab-strip-autohide.ps1` ALL PASS (13),
  `caption-bar.ps1` ALL PASS (17), `tab-color.ps1` ALL PASS (16).
- **Standing floor**: `zig build test -Dapp-runtime=none` exit 0,
  `-Dapp-runtime=win32` exit 0, `zig build test-agent` exit 0 (first run hit
  the known **T258** `remote.agent.server` ConPTY flake; green on re-run, and
  nothing in this change touches that subsystem), P1/P2/P3 ACCEPTANCE ALL PASS.

## Two things it turned up

- **`Send-TestMouse` cannot click caption-band chrome** - it posts CLIENT mouse
  messages, and the caption band is client area the window claims back through
  `WM_NCHITTEST`, so Windows would deliver `WM_NCLBUTTONDOWN` and the harness
  delivers nothing. Cost a full red run (17 failures) while the pixel probe and
  F10 both said the button was there and worked. Worked around here by asking
  the app for the hit code and posting the NC pair; filed as **T263**, and it
  matters far more for T205, which moves EVERY strip click into that band.
- **`tab-strip.ps1` had a private copy of the button band** (`clientW - padR -
  2*btn - gap`) that counted two buttons. Same shape as the copies T257
  deleted; now `RunRight - gap` from the shared module. Its section 6 also
  changed subject honestly: on a caption window the right-most square opens no
  menu (T260's claim) and the "+" - measured, not assumed to be at its limit -
  still opens a tab. **T264** files the last private copy, in
  `caption-bar.ps1`.
