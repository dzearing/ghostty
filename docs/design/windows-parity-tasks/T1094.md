# T1094 - Nobody has swept the whole acceptance suite yet: the first run found 4 reds in its first 63 scripts and stopped there

## In plain terms

We just built the thing that can run all 241 automated app checks in one go, and
then ran the first quarter of them. Four were already broken - nobody knew,
because nothing had run them in months. This task is finishing that first sweep
and turning every broken check into its own piece of work, so the wall of green
means something again.

## Summary

T361 delivered `scripts\suite-run.ps1` and ran the first real sweep on
2026-08-22. It was stopped after 63 of 241 scripts (38 minutes) so the turn
could finish; the partial run is on disk and the runner resumes:

```
powershell -NoProfile -File scripts\suite-run.ps1 -Resume temp\suite-runswd1\summary.json
```

(If that directory has been cleaned, start a fresh sweep - the point is the
sweep, not this particular one.)

Measured in that sample: **36.1 s mean, 17.7 s median per script**, which puts a
full forward pass at about **2h 25m**. Budget a dedicated turn.

What the first 63 already found:

| script | verdict |
|---|---|
| `agent-autostart.ps1` | 1 FAILURE(S) |
| `caption-bar.ps1` | 1 FAILURE(S) - `Get-TestWindowPixels: the capture is UNIFORM - 3858x211` |
| `chooser-close-chord.ps1` | 3 FAILURE(S) (11 passed) |
| `chooser-orphan-badge.ps1` | 4 FAILURE(S) (12 passed) |

Two scripts also LEAKED a live process out of `zig-out` when they finished -
`agent-instance-lineage.ps1` and `agent-relay-session-e2e.ps1`. The runner's
between-script sweep caught both, which is the only reason they are visible;
before it, that leak poisoned whichever script ran next.

At the sample's 6% red rate, expect roughly fifteen reds across the suite.

## The work

1. Resume the sweep to the end (dedicated turn; nothing else should run on the
   box while it does).
2. One task per red script, with the failing assertion quoted - not one task
   for "the suite is red". Some will be product defects and some will be
   harness rot; the triage is the point.
3. Same for each leaking script: a script that leaves an app running is a
   harness defect regardless of its own verdict.
4. Record the full-sweep wall clock in T361, replacing its extrapolation with
   the measured number.

### What the sweep found beyond its own brief

Three findings that are not "a script is red" and matter more than most of the
list:

- **T1099 (P0)** - `upstream/main` does not resolve in the LIVE repo, so the
  eight commits the merge-back plan cites are unreferenced and a `git gc` may
  prune them. Worse, step 0's claim printed `UPSTREAM OK (upstream/main
  a88ad03e6, fetched 16h ago)` on the same turn: the gate that exists to catch
  this cannot go red.
- **T1098 (P1)** - filed mid-sweep from a live sighting by the user: a corrupt
  installed agent makes the upgrade pop a system-modal Windows dialog and hang.
  `upgrade-staleness.ps1` provokes it every run and still scored `ALL PASS (123
  assertions)`, and the dialog reached the INTERACTIVE desktop.
- **T1126** - `profile-latency.ps1` is scored `fail` for correctly refusing a
  Debug build. A suite that can never be all-green in its normal configuration
  trains everyone to stop reading the number, which is the thing T361 built the
  runner to fix.

The second and third share a theme worth carrying forward: **the suite cannot
see things that happen outside a script's own assertions.** A modal dialog, a
leaked process and a by-design refusal are all invisible to, or misreported by,
the verdict contract. The leak sweep was added for exactly this reason and it
is the only one of the three currently covered.
