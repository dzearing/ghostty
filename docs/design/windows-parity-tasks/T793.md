# T793 - chooser-resume.ps1 fails setup: the relaunched app's own pane never joins the roster, so there are 2 rows where the script needs 3

## In plain terms

There is a test that proves you can pick a still-running session out of the
machine chooser and take it over in a new window. It is failing before it gets
that far: after the app is restarted, the chooser lists the two sessions that
outlived it but not the one the freshly relaunched app just opened. Either the
app really is not registering its own new pane with the agent, or the test is
looking a beat too early — and until that is answered, the resume behaviour it
guards is unmeasured.

## Summary

Found while running T294's neighbouring suites. `test\win32\chooser-resume.ps1`
exits 1 in section 1, before any resume is attempted:

```
1. an orphaned live session exists to resume
  PASS the agent owns the app's panes (found 2)
  PASS the sessions outlived the app (2 alive)
  FAIL the roster has the orphans plus the new pane (2 rows)
  FAIL a live row with no viewer is rendered (index -1 of 2)
SETUP FAIL: no orphaned live session
```

Pre-existing and reproducible at `4ce6ff818` with the file at HEAD (checked by
stashing T294's one-line filter-field conversion and re-running: byte-identical
output), so it is neither T294's doing nor a one-off.

Both failures are the same fact: `Get-RenderedSessions` sees 2 rows where the
script expects 3 — the two orphans, and NOT the pane the relaunched GUI opened.
The second assertion then finds no `alive && !attached` row, because the two it
can see were re-attached by the relaunch.

Two candidate explanations, and the script cannot currently tell them apart:

1. **A race.** The roster is read `Start-Sleep -Seconds 2` after `Launch-Gui`.
   If the relaunched app re-attaches its restored panes first and opens its own
   new session later, 2s may simply be early. A poll-until (`3 rows or timeout`)
   would settle it, and is the right shape regardless.
2. **A real gap.** The relaunched app's own pane is not being registered with
   the agent at all — in which case the chooser genuinely cannot show it, and
   the defect is in the app, not the harness.

Answer (1) before (2): if a longer/polled wait produces the third row, this is a
harness fix; if it never appears, it is a product bug and this task should be
split.

## Validation criteria

- [ ] The cause is named from evidence — `+sessions --json` sampled repeatedly
      across the relaunch, showing whether the third session ever appears.
- [ ] `powershell -NoProfile -File test\win32\chooser-resume.ps1` ends ALL PASS
      and exits 0.
- [ ] If it was a race, the wait is a POLL with a timeout, not a longer sleep —
      a fixed sleep tuned on this box is the same defect at a different number.
- [ ] If it was a product gap, a separate task carries the app fix and this one
      cites it.
