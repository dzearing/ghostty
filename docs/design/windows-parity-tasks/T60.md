# T60 — FIX: window title jitters a few px left/right on a timer while busy

## Summary

FIX: window title jitters a few px left/right on a timer while busy (user, 2026-07-16; row renumbered from a duplicate T56 on 2026-07-16). Likely cause: Claude Code's title spinner — the braille glyphs (⠐/⠂/…) come from a FALLBACK font (MS Gothic per app log) with per-glyph advance widths, so the centered title re-centers to a different width every spinner frame. Investigate where the win32 tab/title text is drawn (Window.zig caption/tab paint); candidate fixes: left-align the title, reserve a fixed-width cell for the leading glyph, or measure/center on the title minus the spinner char

## Root cause (measured, 2026-08-02)

The filed guess named the wrong glyphs and the wrong mechanism, and both
corrections mattered.

**Not braille, and not centering.** The pane-title spinner IS braille
(U+2801..U+2880) and those all measure **15 px** in Segoe UI at the user's
125% — they cannot jitter anything. The glyphs that move are the ones Claude
Code leads a **tab/window** title with, and they come from four different
Unicode blocks. Measured with `GetTextExtentPoint32W` in the app's own title
font (Segoe UI, 16 DIP → a 20 px em at 125%):

| frame | codepoint | advance |
|---|---|---|
| `·` middle dot | U+00B7 | 4 px |
| `∗` asterisk operator | U+2217 | 10 px |
| `✦` four-petal | U+2726 | 16 px |
| `✢` teardrop-spoked | U+2722 | 18 px |
| `✻` six-petal | U+273B | 18 px |
| `✽` eight-petal | U+273D | 18 px |
| `✳` eight-spoked | U+2733 | 27 px |
| `✴` eight-pointed | U+2734 | 27 px |

A **23 px** swing, several times a second. And the title is not centered
anywhere — it is `DT_LEFT` in both the caption and the tab. The jitter is
simply that everything after the glyph is laid out **from the glyph's own
advance**, so each frame moved two separate things:

1. the title text slid left/right inside its box, and
2. the tab's width slid with it, because a tab asks for the width its own
   title needs (T235) — which drags the chiclet's close button, the "+", and
   every tab right of it.

## Fix

`src/apprt/win32/title_spinner.zig` (new, pure, no OS imports, tested in every
lane). A title that leads with a **non-ASCII symbol codepoint followed by a
space** gets that glyph drawn **centered in a fixed-width cell**, with the rest
of the title starting at the cell's right edge. The spinner then animates in
place — what a spinner is for — and nothing downstream is measured from it.

- The rule is **structural**, not a list of Claude Code's frames: a fix that
  special-cased those eight would be re-broken by the next agent's alphabet,
  and a fix that special-cased braille would have fixed nothing at all.
- ASCII leads are deliberately excluded: a fixed-advance `*` never jittered,
  and giving it a cell would move titles that were fine.
- The cell is `em * 3/2`, derived from the **font** rather than being a DIP
  constant on the spacing scale — what has to fit is a glyph, and a fallback
  font's dingbat overruns the em (27 px against a 20 px em, ratio 1.35).
- `Window.zig` gained `measureTitleText` / `drawTitleText`, and **both** the
  caption title and the tab label go through them. Measuring one way and
  painting the other would size a tab for a layout it does not use — the T235
  `preferredWidth`/`titleRect` inverse broken from the outside.

## Validation

**Unit tests** — 11 in `title_spinner.zig`, verified to actually execute
(74 tests with a filter that matches nothing → 85 with `title_spinner`):
every Claude Code frame splits identically, ordinary and ASCII-led titles are
left alone, a symbol with no separator is not a spinner, astral spinners are
two code units, malformed surrogates fall through, and the cell clears the
widest measured glyph at 1.0/1.25/1.5/2.0.

**On-box acceptance** — `test/win32/title-jitter.ps1`, ALL PASS (9
assertions). Ink profiles of the caption band per frame plus tab extents read
off the strip's pixels.

Both negative controls were RUN, not just written:

- `-NegativeControl` (inverts the two fix assertions) → **2 FAILURE(S)**,
  every control still green.
- Source-level `T60_NEUTERED = true`, rebuilt → the two fix assertions fail
  and the four controls do not, with the bug visible in numbers: the tab's
  right edge wandered across **672, 678, 683, 685, 694** (a 22 px swing,
  matching the measured 23 px advance swing) and the title text profiled to 5
  distinct positions. Shipped build: one extent, one profile.

**Floor** — `zig build test` both lanes, `zig build test-agent`, P1/P2/P3 all
green. The win32 lane failed once on an unrelated test and passed on re-run;
filed as **T369** rather than left as a shrug.

## Loose thread found on the way (not a bug — recorded so nobody re-derives it)

Driving a pane title for the test took four attempts. On this box **OSC 0 / OSC
2 written by a nested `powershell -Command`, the same written to the raw stdout
stream, and `$host.UI.RawUI.WindowTitle` from an interactive PS 5.1 pane all
leave the title untouched** — PS 5.1 does not enable VT processing on its
console, so the sequence is buffer text rather than a title change. What works
is `chcp 65001` then cmd's `title` builtin (SetConsoleTitleW, which ConPTY
forwards). Claude Code's own titles work live because it enables VT processing
itself. This is a PowerShell property, not a ghoztty defect, so no task was
filed — but the first version of the acceptance script drove the title through
one of the three dead mechanisms and its tab-extent assertion passed **against
a tab whose title never changed**. The "each frame really did retitle the tab"
control exists because of that, and it is the assertion that caught it.
