# T216 - Prove posted mouse input on the test desktop (dark-menus)

## Summary

T212 split, part 1 of 3: settle the ONE open mechanism question before any
mouse-driven script is converted. The T207 spike and T211 harness proved
KEYBOARD posting only. 13 of the 65 `test/win32` scripts drive the mouse
(`chooser-menu`, `context-menu`, `dark-menus`, `focus-follows-mouse`,
`focus-defer`, `hero-mode`, `host-settings`, `menu-bar`, `split-divider`,
`tab-color`, `tab-strip`, `title-font`, `window-color`), and whether they can
migrate at all is unknown until posted mouse input is measured on box.

The hard part is not the click: it is `TrackPopupMenuEx`. A `#32768` popup
menu runs its own modal loop that reads mouse position/state, and posted
`WM_LBUTTONDOWN` does not move the real cursor. If that cannot be driven, the
menu scripts route to the T207 option-B bucket and **that must be said in the
log, not left silent.**

## Scope

1. Add a mouse surface to `test/win32/lib/TestDesktop.ps1` (posted
   `WM_MOUSEMOVE` / `WM_*BUTTONDOWN` / `WM_*BUTTONUP` with correct
   client-coordinate lparam and `MK_*` wparam, plus a menu-selection path if
   posting into `#32768` does not work).
2. Migrate `dark-menus.ps1` (the smallest mouse script) as the worked example.
3. Record the verdict for the remaining 12 in this file so T218 does not
   re-derive it.

## Validation

- `dark-menus.ps1` ALL PASS x3 on the test desktop.
- Its negative control still FAILS.
- `Test-TestDesktopLeak` false and the foreground watch never sees the
  launched pid.

## Verdict (measured on box 2026-07-30)

**Posted mouse input WORKS, and so does `TrackPopupMenuEx`. The menu scripts
migrate; nothing routes to the T207 option-B bucket.** The feared blocker was
not one - but it hid behind a real product bug that had to be fixed first.

What each probe measured:

| Question | Answer |
|---|---|
| Does a posted `WM_LBUTTONDOWN` reach the app? | **Yes.** Focus moved to the clicked pane (`deferSetFocus` ran). |
| Does `TrackPopupMenuEx` run on a background desktop? | **Yes.** A posted `WM_CONTEXTMENU` produced a 326x388 `#32768` window. |
| Can a posted key dismiss it? | **Yes**, via `Send-TestControlKey` (posts without touching focus). `Send-TestKeys` would `SetFocus` first and close the menu out from under the test. |
| Can `PrintWindow` read a menu? | **Yes** - menus are GDI-painted chrome, the half of the CAPTURE LIMIT that survives. 52-53 distinct colors, dark 52 / light 240. |
| `SetCursorPos` / `GetCursorPos`? | **DEAD.** Both fail off the input desktop (`GetCursorPos` returned -1,-1). This is what broke right-click; see below. |

### The product bug this turned up (fixed here)

A posted right-click reached the app and then died with
`mouse button callback error: error.GetCursorPosFailed`. `Surface.getCursorPos`
had no answer when `GetCursorPos` fails, so it returned an error; the core
propagated it out of `mouseButtonCallback`; `handleMouseButton` caught it as
`consumed = true`; and the apprt only opens the context menu when the core
returns **unconsumed**. Net effect: right-click did nothing at all.

Fix (`src/apprt/win32/Surface.zig`): cache the client-coordinate position
carried by each mouse MESSAGE (`last_cursor_client`, set in
`handleMouseButton` and `handleMouseMove`) and fall back to it when
`GetCursorPos` fails. It is not a downgrade - a message-derived position is
queue-synchronized with the event being handled, where `GetCursorPos` reports
where the pointer is *now*. Only when there has been no mouse message at all
does it still error, which preserves the original reason for erroring (never
resolve a bogus {0,0} against the top-left cell).

This is not test-only: `GetCursorPos` also fails on a locked workstation, the
secure desktop, and a disconnected RDP session. Unit test
`cursorFromLparam decodes signed 16-bit halves` covers the lparam decode
(negative halves included - a drag past the top-left edge with capture held
reports them, and masking instead of sign-extending would read ~65500).

### The capture trap this turned up

The first green run read `dark surface menu is dark (avg 0)`. That was a
capture taken while the menu was still painting: solid black, which satisfies
"is it dark?" for entirely the wrong reason. Re-measured, the same menu read
meanLum 0 / **1** distinct color at 350ms and meanLum 52 / **53** colors at
400ms. So `Get-TestDistinctColors` went into the harness and `Measure-Menu`
now polls until the menu has real content before scoring it. Any migrated
brightness probe should do the same - a flat fill passes half of these
assertions by default.

## Harness additions (T217/T218 should use these, not re-derive them)

- `Send-TestMouse -Window -Target -X -Y [-Button left|right|middle]
  [-Action click|down|up|move|doubleclick|wheel] [-Modifiers] [-Delta]`.
  X/Y are SCREEN coordinates (the math the scripts already do); they are
  converted per target hwnd. **`-Target` is the window the message is POSTED
  to** - posted messages skip hit testing, so name the window that would
  really have received the click: the pane child for a surface click, the
  top-level window for the tab strip (`Window.zig` handles the tab bar on
  `WM_RBUTTONUP`).
- `Wait-TestPopupMenu -ProcessId` waits for a `#32768`. While a menu is up the
  app's GUI thread is inside a modal loop and answers nothing - but the
  harness worker is a different thread and `EnumWindows`/`GetWindowRect`/
  `PrintWindow` do not need the app's.
- `Get-TestDistinctColors -Shot` - the flat-fill guard described above.
- `Set-TestCursorPos` / `Get-TestCursorPos` exist but **do not work** off the
  input desktop. They are kept for `-Interactive` mode only; anything that
  depends on the real cursor position must be driven by message coordinates.

  tab-bar 244.

  (`test-desktop-harness` 19, `split-zoom-nav` 20).

  `-Dtest-filter=cursorFromLparam` runs 78 tests where a filter matching
  nothing runs 77.

Not run: `context-menu.ps1`, the interactive-desktop right-click script - the
no-GUI-tests-on-the-interactive-desktop rule is still in force until T218
migrates it. The `getCursorPos` change cannot affect that path by
construction: the fallback is reached only after `GetCursorPos` has already
failed, and on the interactive desktop it does not.
