# T943 - The activity monitor, confirm dialog and split-dim probes still take the torn photo - convert them to the synchronous capture

## Summary

T843's second half for the remaining classes we own, unblocked by T940's
`WM_PRINTCLIENT` handlers. Switch the probes to `-Sync` and re-run each script
several times.

Scripts, from the T843 survey: `activity-monitor.ps1` (10 sites) and the
`$panel` sites in `chrome-theme.ps1` (4) — both `ActivityMonitor`;
`confirm-dialogs.ps1` and `config-errors.ps1` — `ConfirmDialog`;
`split-dim.ps1` and `split-dim-viewer.ps1` — `DimOverlay` or the window behind
it, check which before converting.

The activity monitor is the priority inside this task: its probes read table
columns, and a torn frame stops mid-text at a glyph boundary, which is what
made T835's readings look like stable wrap positions rather than noise.

## In plain terms

The rest of the tests that photograph the app — the activity panel, the
confirmation dialogs, the dimmed pane — are reading a photograph that can come
out half-taken. This points them at the steady one.

## Goals

- [x] Every probe of the three classes we own captures synchronously
- [x] The before/after flake rate is MEASURED rather than asserted
- [x] Every converted script stays green over repeated runs

## What landed

**14 call sites converted**, which is all of them for these three classes:
`activity-monitor.ps1` (10), `confirm-dialogs.ps1` (1), `config-errors.ps1`
(1), `split-dim.ps1` (1), `split-dim-viewer.ps1` (1). `chrome-theme.ps1`'s four
`ActivityMonitor` sites were taken by T941. A sweep of the whole `test/win32`
tree leaves two default-route captures standing and both are deliberate:
`dark-menus.ps1` photographs a system `#32768` popup, which is not a class we
own or can teach `WM_PRINTCLIENT`, and `test-desktop-harness.ps1`'s subject IS
the default route.

Three sites needed more than the flag, all for the same reason: the sync route
**throws** on a window that drew nothing where the old one handed back a blank
frame. `Get-DialogDark` in both dialog scripts already retried for exactly that
case (its comment calls it "mid-paint black"), so the throw is caught and
retried inside the loop it was already running. `Get-OverlayFill` in both
split-dim scripts had one shot and returned `$null` on failure, which the
caller scores as "the overlay painted nothing" — it now retries ten times at
150 ms before giving that answer.

## The measurement

Two purpose-built probes on the Debug build, the T942 methodology (each
immediate frame scored against its OWN settled successor — a fixed per-state
reference loses phase the moment a keystroke is dropped).

**ActivityMonitor** (`WS_EX_*` plain, not layered). 242 sample points over the
TABLE band only: the two trend gauges repaint on the panel's own 1.5 s poll, so
a probe that samples them measures the poll and not the capture.

| | steady, consecutive pairs | first frame after a focus change |
|---|---|---|
| default | 0 of 19 disagree | 0 of 30 disagree |
| `-Sync` | 0 of 19 disagree | 5 of 30 disagree, worst 1 point of 242 |

**DimOverlay** (`WS_EX_LAYERED` — the T835 shape, and the one place a tear was
expected). The assertion is the overlay's centre pixel against the configured
fill, so the probe reads exactly that:

| | steady centre reads | first read after the overlay moves |
|---|---|---|
| default | 0 of 40 wrong | 0 of 20 wrong |
| `-Sync` | 0 of 40 wrong | 0 of 20 wrong |

**So the honest answer is T941's, not T835's: none of these three windows tears
through the default route**, and the panel is not layered, which is the same
structural reason the main window did not. The overlay IS layered and still
does not move the number, and the reason is worth keeping: it paints a SOLID
single-colour fill, so a torn frame of it is indistinguishable from a complete
one at any pixel. The tear can be there and this assertion cannot see it.

The `-Sync` column disagreeing 5 of 30 where the default never does is not the
capture being worse. `WM_PRINTCLIENT` forces a FRESH paint, so two sync frames
1.2 s apart differ wherever the panel's live data was re-rendered between them
— one sample point, once per six frames. The DWM copy shows the same composited
surface to both reads and therefore cannot disagree with itself.

What the conversion buys, then, is what T941 concluded and not a flake fix: a
timing dependency that sampling can never prove safe is gone, and a capture of
a window that drew NOTHING now fails loudly instead of handing back a frame for
a "no ink" or "is it dark" assertion to pass against.
