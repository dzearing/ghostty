# T632 - Activity Monitor: a kill that failed because the process already exited is reported as needing elevation

## In plain terms

You pick a process in the Activity Monitor and hit Kill. While you are reading
the confirmation the process finishes on its own, so by the time you click Kill
there is nothing left to kill. The panel tells you "It may require elevated
privileges" — which sends you off looking for an admin prompt that would not
have helped. It should just say the process is already gone.

## Summary

`actions.killFailureText` derives its whole sentence from the target list and
knows nothing about WHY each kill failed, so every failure gets the same
elevation guess (`activity_actions.zig`, mirroring
`RemoteActivityMonitorView.swift:587-596`). `ActivityMonitor.killOne` DOES have
the reason — `proc_control.killProc` returns an error string, and the remote
branch gets `out.error_msg` from `PROC_KILL` — but it only writes it to the log
and hands the caller a bare `bool`.

Windows can tell the two apart: `OpenProcess` on a pid that no longer exists
fails with `ERROR_INVALID_PARAMETER`, while a live process we are not allowed to
touch fails with `ERROR_ACCESS_DENIED`. So this is a plumbing job, not a guess.

## Details

Filed out of T292. Before it, snapshot adoption was suspended for the
confirmation's whole life, so the selection could not be pruned while the dialog
was up and "the target exited between the click and the confirm" needed the user
to be unlucky inside a single message handler. T292 makes the panel keep
polling behind the dialog — which is the point, and which Mac does too — so a
target exiting under an open confirmation is now an ordinary occurrence.

Shape of the fix:

- `killOne` returns a reason, not a bool — a small enum (`ok` / `gone` /
  `denied` / `other`) derived from `GetLastError` locally and from
  `out.error_msg` remotely. Keep the remote mapping generous: an older agent
  answers with a message string only, so an unrecognised one must land on
  `other` rather than being read as a confident `denied`.
- `Target` (or a parallel array) carries the reason into
  `killFailureText`, which then says "already exited" for a `gone` batch, keeps
  the elevation sentence for `denied`, and falls back to today's wording when
  the reasons are mixed or unknown.
- A pid that is `gone` is arguably not a FAILURE at all — the user asked for it
  to not be running and it is not running. Deciding whether it counts in the
  "Killed 1 of 3" tally is part of this task; whichever way it goes, the
  sentence must not contradict the count.

Mac has the same single-sentence wording, so getting this right on Windows puts
the two out of step. That is a divergence worth filing back to the Mac seat
rather than one to avoid — a banner that names the wrong cause is a defect on
both platforms.

## What was decided

**A `gone` target is not a failure, and not a kill either.** The tally now has
three parts that always sum to the batch size - killed + already-exited + failed
- so the sentence can never contradict its own count. An already-exited target
is left out of the "N failed: …" list it would otherwise be blamed by, and out
of the killed count nothing here earned.

**The diagnosis comes from the process object, not the error code.** The obvious
reading of the task - `OpenProcess` fails with `ERROR_INVALID_PARAMETER` for a
vanished pid - only covers the case where the pid has been RELEASED. The case
this task is actually about is the one T292 made ordinary and section M2 of the
acceptance script already builds: the process exited while somebody still holds
a handle, so its process object outlives it, `OpenProcess` succeeds and
`TerminateProcess` answers `ERROR_ACCESS_DENIED` - byte for byte the code a live
process we may not touch returns. `killWindows` now opens with `SYNCHRONIZE`
alongside `PROCESS_TERMINATE` and, on a failed terminate, asks whether the handle
is signalled. Diagnosis never costs the kill: an access-denied on the pair is
retried with `PROCESS_TERMINATE` alone and simply forgoes the distinction.

**The acceptance arm is M2, retrofitted rather than a new one.** M2 already
spawns three victims, pins one pid with a held handle, kills it behind the open
confirmation and confirms - which is precisely the fixture the criteria asked
for, and it was asserting the WRONG sentence. An unpinned variant would have to
race Windows pid reuse for no extra coverage, and a recycled pid is a bystander
this panel would then terminate.
