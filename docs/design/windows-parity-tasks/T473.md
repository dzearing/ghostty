# T473 - Decide whether the T443 half-clobbered pointer is a Zig/LLVM codegen bug: rebuild the failing lane with the self-hosted x86_64 backend and at ReleaseSafe

## Summary

Split out of **T443** on 2026-08-04. That task's dumps show a page pointer
reaching the hash map with its **low 32 bits exactly right and its high 32
bits replaced** by an unrelated page offset, across three `-O0` by-value
copies of an 8-byte struct (`get` → `getContext` → `getAdapted`) that do
nothing but move the value. See T443 § START HERE for the register/slot
derivation.

Either the compiler emitted a 4-byte store where an 8-byte one belongs (or
overlapped two stack slots), or something else is writing those 4 bytes.
This task settles the first half.

## In plain terms

A memory address is being copied around, and half of it keeps arriving wrong.
The code doing the copying is about as simple as code gets, which raises the
question of whether the compiler itself is at fault rather than our program.
This checks that by building the same tests a different way and seeing whether
the problem follows.

## Goals

- [x] Build the failing lane with the self-hosted x86_64 backend (`-fno-llvm`)
      and run it enough times to beat the ~50% flake rate (10+ runs)
      — **impossible**: `zig.exe` access-violates compiling it, 4/4, same
      offset. Filed as T476.
- [x] Build it at `-Doptimize=ReleaseSafe` and do the same
      — **built and soaked 10x**: crashes 10/10 on a *different*,
      deterministic panic before reaching the relevant tests. Filed as T477.
- [x] Record a verdict in T443: signature survives (our code) or disappears
      (toolchain), with the run counts behind it
      — **recorded, and it is INCONCLUSIVE**: the control arm went quiet too
      (0 crashes in 26 runs at HEAD), so there was nothing to discriminate.

## RESULT (2026-08-04) — both arms blocked, and the control went quiet

Full verdict, with the tables, lives in **T443 § T473 VERDICT**. In short:

| arm | outcome |
|---|---|
| control — win32 lane Debug+LLVM, bare | 10 runs, **0 crashes** |
| control — win32 lane Debug+LLVM, under cdb | 6 runs, **0 crashes** |
| control — none lane Debug+LLVM, bare | 10 runs, **0 crashes** |
| self-hosted backend (`-Dtest-llvm=false`) | **cannot build** — `zig.exe` AVs 4/4 at `zig.exe+0xfcb364` → **T476** |
| ReleaseSafe (`-Dtest-optimize=ReleaseSafe`) | **10/10 crash**, but on an unrelated deterministic panic at `renderer.cell.test.Contents with zero-sized screen` → **T477** |

The discriminator this task exists to run needs a reproducing control, and there
is not one at HEAD. That is not a null result to shrug at — it is the finding,
and it blocks **T474** outright (a hardware write breakpoint has nothing to arm
against). Next step is decision **D10**.

### What landed, so the next attempt is cheap

- **`build.zig`: `-Dtest-optimize` and `-Dtest-llvm`.** The three test binaries
  pinned `.optimize = .Debug` and `.use_llvm = true` in source, so "rebuild the
  lane a different way" meant editing build.zig — which is how a diagnostic
  build silently becomes a permanent one. Both default to exactly what the lanes
  have always built, so `zig build test` / `test-agent` are unchanged.
- **`scripts/test-binary-soak.ps1`.** Runs a built test binary N times and
  reports `pass/fail/crash` with a crash rate, separating a crash from a red
  test (stderr signature + low-byte NTSTATUS decode + `Application Error`
  correlation) and naming the victim test on each crash. Every claim about a
  ~50%-flaky signal needs a run count behind it; this is what produces one, at
  ~2 minutes a run instead of a full lane.
- Two traps it hit and now documents in place: WER writes the `Application
  Error` record *asynchronously*, so the correlation needs a short retry; and
  PowerShell 5.1 unrolls the array an `if` expression returns, so a
  single-candidate NTSTATUS decode arrived as a bare object whose `.Count` is
  `$null` — which filed ten consecutive crashes as red tests until it was fixed
  with `[array]`.

## Details

- The self-hosted backend may not compile the whole tree; if it does not,
  say so with the error rather than treating it as inconclusive, and fall
  back to narrowing with `-Dtest-filter` until it does.
- `zig.exe` itself has taken access violations on this box (**T451**), so a
  toolchain fault is not an exotic hypothesis here.
- A negative result is worth just as much: it removes the last non-code
  explanation and hands T443 back a bounded search.

## Validation

- Both alternate builds run 10+ times each with the crash counts recorded.
- The verdict is written into T443, with the evidence, not just an opinion.
