# T1193 - 62 acceptance scripts launch Ghoztty on the user desktop instead of the background test desktop, so a validation run steals focus

## Summary

test/win32/lib/TestDesktop.ps1 exists so GUI acceptance runs on a background Win32 desktop and cannot touch the users session; 144 of 250 scripts use it. The other 62 launch a real ghoztty.exe (Start-Process / zig-out\bin\ghoztty.exe) on the users own desktop, where every launched window activates and takes focus. Among them are ipc-p1.ps1, ipc-p2.ps1 and ipc-p3.ps1 - the three CLAUDE.md names as the floor for every change - so the loop steals focus from the user on essentially every task it validates. Convert them to New-TestDesktop / Start-OnTestDesktop, and add a sweep so a new script that launches ghoztty outside the harness is a finding rather than a discovery months later. Note the harness rule already exists and was simply not applied; the sweep is what makes it stick.

## In plain terms

When the loop tests its own work, terminal windows used to jump onto your screen
and steal what you were typing into. That is because the test scripts started
Ghoztty the ordinary way, on your desktop, instead of on the invisible one the
test harness keeps for exactly this. The three scripts the project runs on
EVERY change were among the worst offenders, so it happened constantly.

Those three no longer do it, there is now a tool that makes converting the rest
a few lines each, and a new check refuses to let a new script go back to the old
way. Forty-five scripts are still to convert, listed and tracked so the number
can only go down.

## What was measured, and why the count moved

The task was filed against 62 scripts. The analyzer counts 50, and the
difference is not a correction of the count but of the RULE. Two shapes look
like a launch and cannot create a process:

- **`+split`, `+list`, `+send-keys` and the rest.** `performIpc` in
  `src\apprt\win32\App.zig` answers `error.NoRunningInstance` by spawning the
  app for `.new_window` and for nothing else; every other verb prints "Start one
  with +new-window first" and returns 1. Reading those as launches would have
  put 79 innocent scripts on the exception list - the same rot from the other
  direction that T272's sweep produced.
- **A raw verb in a script that already owns a test desktop.** Its app is
  already up, so the CLI creates nothing. What still counts there is a BARE
  launch, which names no desktop however many the script created; that is the
  one site `go-loop-guard.ps1` has, and it is a declared fallback.

Three scripts are declared permanently rather than migrated:
`context-menu-real-input.ps1` and `profile-latency.ps1` are already
interactive-by-design in the sibling list (a real right-click, and injection
timing), and `go-loop-guard.ps1`'s single bare launch is the loudly-announced
fallback for a desktop that could not be created.
