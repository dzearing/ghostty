# T859 - Chooser roster: a stale pooled connection could retry on a fresh dial now that T510 bounded every dial phase

## In plain terms

When the machine chooser lists the sessions on a remote machine, it borrows a
shared connection to ask. If that shared connection has silently died, the
chooser shows a stale or empty list until the pool notices and reconnects on
its own. A careful "try once more over a brand-new connection" would fix that
moment — it used to be forbidden because a new connection attempt could hang
the chooser permanently, and that hang is now impossible (T510).

## Summary

T328's history: a retry-on-fresh-dial in the SessionRoster worker wedged the
worker thread permanently and was reverted; the root cause was
`relay_dial.dial`'s unbounded upgrade read, fixed by T510 (commit 75ac7fefb).
T461 then removed the per-fetch dial cycle in favor of a pooled connection,
which stands on its own merits — but the pooled design has a known soft spot:
a pooled connection that died silently serves one failed RPC before the pool
heals, and the chooser shows a stale roster for that beat.

Now that every phase of a dial is bounded (connect → TLS+upgrade → HELLO), a
single bounded retry over a fresh dial is safe to reintroduce where a pooled
borrow fails with a connection-shaped error. Scope: the SessionRoster worker
first (`src/apprt/win32/SessionRoster.zig` — see the T328/T510 comment block
there); assess whether the same pattern pays for other pool borrowers
(RemoteReconnect, MachineConnectionPool consumers) or whether the pool's own
healing is enough there.

## Validation criteria

- [ ] A roster fetch whose pooled connection is dead retries once over a fresh
      bounded dial and lands the roster (acceptance: extend
      `chooser-sessions-remote.ps1` or a dedicated scenario)
- [ ] The retry provably cannot wedge the worker: the dial path is bounded end
      to end (T510 tests) and the retry is single-shot with the failure
      surfaced as today's stale-roster behavior
- [ ] `chooser-sessions-remote.ps1` (incl. `-NegativeControl`) still ALL PASS
