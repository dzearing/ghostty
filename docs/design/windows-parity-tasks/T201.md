# T201 - Agent upgrade check is invisible in the log until the user answers

## Summary

`App.refreshLocalAgentIfStale` (T147) makes a decision with three outcomes and
logs **none of them at the moment it is made**:

- `.none` logs nothing at all, so "current", "newer, never downgrade", and
  "not knowable" are indistinguishable — and so is "the function returned
  early".
- `.confirm_first` logs only *after* `ConfirmDialog.show` returns, i.e. after
  the user answers. While the modal is up — which can be indefinitely — the log
  ends at `bundled agent build is …` and says nothing more.

The consequence, hit for real during the T196 delivery on 2026-07-30: a
correctly-working mandatory confirmation was indistinguishable from a check that
decided nothing, and from a check that never ran. The dialog was up on a second
monitor for ~20 minutes while the log offered no evidence it existed. An
unattended session cannot tell "waiting on the user" from "decided nothing", and
that is exactly the state the loop lands in after every upgrade.

## Details

Fix, in `src/apprt/win32/App.zig`:

1. **Log the decision where it is made**, before any modal. One line covering
   all three arms with the inputs that produced it (running stamp, bundled
   stamp, live session count, reason) — including `.none`, which should say
   *why* it is none (`current` / `running is newer` / `bundled unknown`).
2. **Log that the confirmation is being shown**, before `ConfirmDialog.show`
   blocks, so a pending dialog is visible in the log rather than inferred from
   an absence. The existing post-answer lines stay: they record what the user
   chose.
3. Keep the silent early returns auditable too — at minimum `!hasSharedConnection()`
   and the `agent_upgrade_attempts` ceiling deserve a debug-level line each;
   today both return with no trace, and the ceiling case is explicitly a
   "logged rather than silently absorbed" claim in the T147 comment that the
   code does not honor.

Also fix the stale doc comments this turned up: `src/remote/protocol.zig`'s
`build_version` field comment says an absent value is *"never treated as
stale"*, and the `HELLO build_version: additive + back-compat` test comment
asserts *"the app must treat null as not-stale"*. Both contradict
`agent_upgrade.isStale`, which deliberately treats null as **stale** (a peer too
old to advertise a stamp predates the whole feature) and is the behavior T147's
own docstring specifies. The code is right; correct the comments so the next
reader does not "fix" the policy to match them.

## What landed

- `agent_upgrade.Reason` + `Decision` + `evaluate()`: the policy now returns
  **why** alongside **what**. `isStale` stays the single authority on staleness
  and `evaluate` only classifies the not-stale case, so the two cannot drift.
  `decide()` is now a one-line projection of `evaluate()`, which keeps every
  pre-existing unit test meaningful and unchanged.
- `stampForLog()` so an absent stamp prints `<pre-versioned>` instead of an
  empty field — a blank in a log line reads as a bug in the logger, not as data.
- `App.refreshLocalAgentIfStale` logs the decision **before acting on it**, with
  all four inputs (running stamp, bundled stamp, live count, calling reason).
  `promptAndRefreshLocalAgent` announces the modal **before** `ConfirmDialog.show`
  blocks. The two silent early returns now speak: the attempt ceiling at info
  (the T147 comment claimed it was "logged rather than silently absorbed" and it
  was not), and the no-connection case at debug.
- `protocol.zig`: the `build_version` field comment and the back-compat test
  comment no longer claim null is "not stale", which contradicted
  `agent_upgrade.isStale` and invited someone to invert the policy to match.

## Validation

**`test/win32/agent-upgrade.ps1` ALL PASS (44)**, up from 38. Six new
assertions: B7 (a `.none` states its reason), C9/C10/C11, E8 (the silent arm
logs — it restarts the agent with no UI, so the log is its only record), F4
(persistence off writes no decision line at all).

C9-C11 are the point of the task and run **before the dialog is answered**:
C9 asserts the decision line, C10 the pending-modal line, and **C11 re-checks
that the dialog is still up**, so the two log assertions are proven to have
happened while the modal was blocking rather than racing its dismissal.

**Negative control, run for real.** With both new log calls stubbed out and the
GUI rebuilt, the suite failed **exactly** B7, C9, C10 and E8 — 4 failures / 40
passed. C11 and F4 still passed, so they are controls rather than filler, and
no pre-existing assertion moved. Restored and re-verified.

One harness detail worth keeping: the exe under test is a **Debug** build, i.e.
the Console subsystem, so `std.log` goes to **stderr** — the
`%LOCALAPPDATA%\ghoztty\ghoztty.log` sink is release-only (`builtin.mode !=
.Debug`), and it drops `.debug`-level lines besides. `Start-App` therefore
captures per-arm stderr with `-RedirectStandardError`, read back with
`FileShare.ReadWrite` because the app still holds the handle. Asserting against
the release log file would have silently matched nothing.

## Field probe worth reusing

Reading a running agent's build without involving the app: take `pipe` from
`%LOCALAPPDATA%\ghoztty\local-agent\port.json`, open it with
`NamedPipeClientStream`, and read the first frame — the HELLO JSON carries
`"build_version"` in plain text. Enumerating the app's dialogs needs
`EnumWindows` by pid with `CharSet=CharSet.Unicode`; `Get-Process |
Where MainWindowTitle` does not surface an owned dialog, and the Ansi
marshalling default truncates every wide string to one character.
