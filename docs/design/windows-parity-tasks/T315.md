# T315 - Account link hover can stick underlined when the pointer leaves the chooser without crossing it

## In plain terms

In the window you open to pick a machine, the "Sign Out" text beside your email
underlines when you point at it, the way a link should. But if you move the
pointer off it and straight out of the window — up past the title bar, or out to
the right, which is the shortest way out from where it sits — the underline
stays on. It looks like something is still highlighted long after you have moved
away. Nothing is broken, and the link still works; it just goes on advertising
itself. After this, the underline goes out as soon as the pointer leaves.

## Goals

- [x] Pointing at the link still underlines it (the affordance is not lost)
- [x] Moving the pointer straight out of the window clears the underline
- [x] It works every time, not just the first
- [x] The link keeps working as a button (label, size, click, focus)
- [x] An automated test that fails on the old behavior

## Summary

Known and deliberately deferred out of **T311**, which built the chooser's
"Sign Out" link. Its hover state comes from `WM_SETCURSOR`
(`MachineChooser.zig`, the `WM_SETCURSOR` arm): the message names the window
under the pointer, so "entered the link" and "left the link" are the same one
test, and the hand cursor is set where that is already known. No subclass, no
`TrackMouseEvent`, three lines.

The gap is the case where **no `WM_SETCURSOR` arrives at all**: the pointer
moves off the link and straight out of the dialog. `link_hot` stays true and the
link stays underlined until the pointer comes back. The link sits at the band's
trailing edge, a `margin` + `avatar_d` in from the client's top-right corner, so
"move up or right and you are out of the window" is the easy path, not a corner
case.

Cosmetic — the link is still correct, still clickable, and a focused or pressed
link underlines anyway — which is why it did not hold T311.

## Details

The obvious fix, `TrackMouseEvent(TME_LEAVE)` on the DIALOG, needs proving
before it is written: the link is a child window, so while the pointer is over
it `WindowFromPoint` returns the CHILD, and it is not established that Windows
still counts that as "inside" the tracked parent. If it does not, the parent
gets an immediate `WM_MOUSELEAVE` the moment the pointer enters the link and the
hover would never show at all — the opposite defect, and one a posted-input test
cannot see (T233: `TrackMouseEvent` watches the REAL cursor, so a posted
`WM_MOUSEMOVE` cannot hold a hover on the test desktop).

So: track on the LINK, which means subclassing it, or find out empirically what
the parent's leave does with a child under the cursor. The listbox in the same
file already subclasses for hover (`list_proc`, `tracking_leave`) and is the
worked example either way.

## Validation criteria

- [x] **The underline clears when the pointer leaves the window.** New
  `test/win32/chooser-link-hover.ps1` measures the link's PAINT — ink pixels in
  its rect from a `PrintWindow` capture of the chooser — across three states:
  rest **342**, hovered **407** (the underline is +65 px of ink), after
  `WM_MOUSELEAVE` **342 exactly**.
- [x] **Positive control: entering still underlines.** Same script, asserted
  before the leave (`rest=342 → hot=407`). A leave-on-entry regression — the
  danger of arming the tracker on the DIALOG — fails here rather than passing
  as a "fix".
- [x] **It discriminates.** Built once with the subclass install disabled
  (`if (false)`): after-leave stayed at **407** and the script reported
  3 FAILURES. The pre-fix defect is what the test measures, not a proxy for it.
- [x] **Repeatable**, not one-shot: a second enter/leave cycle reproduces
  `hot2=407, left2=342`.
- [x] **The subclass did not break the control.** Same script: the link keeps
  its label, rect, enabled state and `BS_OWNERDRAW`, and answers
  `WM_GETDLGCODE` with `DLGC_BUTTON` — the discriminating proof that messages
  still reach the stock BUTTON proc (`WM_GETTEXT` would not be, since
  `DefWindowProcW` serves it too).
- [x] `-NegativeControl` (inverting "the underline clears") FAILS, so the
  measurement is not scoring a constant.
- [x] `test/win32/ipc-machine-chooser.ps1` stays ALL PASS (it asserts the
  link's geometry and text, not its hover).
- [x] Standing floor: `scripts\floor-lane.ps1 -Lane all` and P1–P3.

Note on method: the original Validation said this needed a human on the real
desktop, because `TrackMouseEvent` watches the REAL cursor and `SetCursorPos` is
refused off the input desktop, so no automated run can HOLD a hover. That rules
out *driving a pointer*, not *measuring the app's repaint*: posting
`WM_SETCURSOR` sets the state the real message would without arming the tracker
that would instantly un-set it, and the posted `WM_MOUSELEAVE` is byte-for-byte
what Windows delivers on leave. Both shortcuts are in the input, none in the
oracle — the pixels are the app's own.
