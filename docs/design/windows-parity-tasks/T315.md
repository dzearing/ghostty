# T315 - Account link hover can stick underlined when the pointer leaves the chooser without crossing it

## Summary

Known and deliberately deferred out of **T311**, which built the chooser's
"Sign Out" link. Its hover state comes from `WM_SETCURSOR`
(`MachineChooser.zig`, the `WM_SETCURSOR` arm): the message names the window
under the pointer, so "entered the link" and "left the link" are the same one
test, and the hand cursor is set where that is already known. No subclass, no
`TrackMouseEvent`, three lines.

The gap is the case where **no `WM_SETCURSOR` arrives at all**: the pointer
moves off the link and straight out of the dialog. `link_hot` stays true and the
link stays underlined until the pointer comes back. The link sits at the band's
trailing edge, a `margin` + `avatar_d` in from the client's top-right corner, so
"move up or right and you are out of the window" is the easy path, not a corner
case.

Cosmetic — the link is still correct, still clickable, and a focused or pressed
link underlines anyway — which is why it did not hold T311.

## Details

The obvious fix, `TrackMouseEvent(TME_LEAVE)` on the DIALOG, needs proving
before it is written: the link is a child window, so while the pointer is over
it `WindowFromPoint` returns the CHILD, and it is not established that Windows
still counts that as "inside" the tracked parent. If it does not, the parent
gets an immediate `WM_MOUSELEAVE` the moment the pointer enters the link and the
hover would never show at all — the opposite defect, and one a posted-input test
cannot see (T233: `TrackMouseEvent` watches the REAL cursor, so a posted
`WM_MOUSEMOVE` cannot hold a hover on the test desktop).

So: track on the LINK, which means subclassing it, or find out empirically what
the parent's leave does with a child under the cursor. The listbox in the same
file already subclasses for hover (`list_proc`, `tracking_leave`) and is the
worked example either way.

## Validation

- Interactive, on the real desktop (a posted-input test cannot hold a hover):
  pointer onto the link → underlined; pointer off the top edge of the dialog →
  underline gone within a frame.
- The positive control matters as much: entering the link must still underline
  it. A leave that fires on entry would "fix" the sticking by killing the
  feature.
- `test/win32/ipc-machine-chooser.ps1` stays ALL PASS (it asserts the link's
  geometry and text, not its hover).
