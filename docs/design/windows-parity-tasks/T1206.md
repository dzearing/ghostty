# T1206 - A collided installer transaction disappears instead of saying so

## In plain terms

You double-click the installer, nothing seems to happen, so you double-click it
again. The second one flashes up, says it is configuring, and vanishes. Nothing
tells you that the first one is still running and that is why - you are simply
left wondering whether Ghoztty installed or not.

## Goals

- [x] An update that cannot be applied says so, in words, on screen
- [x] The message names the cause, what to do about it, and where the log is
- [x] It stays up until it is read, instead of flashing past
- [x] The terminal is already back by the time it appears
- [x] A build that stopped saying it would go red in a test

## Evidence (2026-08-31, the clean-machine walk)

`msiexec /i Ghoztty-1.35.0-x64.msi` (pid 23680) started at 06:52:35 and was
still running at 07:05. A second launch at 06:52:40 collided with it:

```
Error 1500. Another installation is in progress. You must complete that
installation before continuing this one.
Product: Ghoztty -- Installation failed.
Installation success or error status: 1602.
```

The likely trigger is the SmartScreen wall (T1203): the first double-click
starts an msiexec that then sits behind a dialog, so nothing looks like it is
happening. Whatever the trigger, only the disappearance was visible.

## What it should do

- A transaction that cannot start because another one holds the installer
  mutex says **that**, in words, and stays on screen until it is read.
- Where the message comes from is the open question, and it is the work:
  Windows Installer owns the UI for a double-clicked MSI, so this may need the
  install to be entered through something of ours (a small bootstrapper, or the
  download page handing out a launcher) rather than the raw package. Weigh that
  against T1203's signing work, which touches the same first-contact moment.
- The in-app updater (T1178) already runs msiexec itself and can report 1618 /
  1602 directly - that path should be the first one made loud, since it is
  entirely ours.

## Validation criteria

- [x] With one msiexec transaction deliberately held open, starting a Ghoztty
      install produces a visible, readable message naming that cause.
      `test\win32\update-failure-visible.ps1` arm B: the applier raises
      Ghoztty's own dialog reading "Another installation is already running on
      this PC..." and "Wait for the other installation to finish...". The 1618
      itself is forced through a Debug-only seam - see the note below on why a
      held mutex cannot produce one.
- [x] The message survives long enough to be read - it does not flash and close.
      Arm A9/A10: the dialog is still on screen 3s later and the applier is
      still alive holding it; A11: it is dismissal that ends the process.
- [x] The in-app update path reports the same condition rather than failing
      silently, and still relaunches the terminal it closed. Arm A: a real
      msiexec rejection produces the dialog, and A8 asserts the relaunch line
      is already in the log when it goes up - the terminal comes back first.
      The other silent outcome on the path (the app never closed, so nothing
      was installed) reports too; D1 holds that wiring.
- [x] An acceptance script drives the collision and fails if the outcome is
      silent. `test\win32\update-failure-visible.ps1`, 28 assertions, with arm
      C as the negative control: a successful apply raises NO dialog, so a
      build that showed one unconditionally would score red rather than green.

## What landed

- `update_apply.zig`: `failureCause` / `failureRemedy` / `describeFailure` /
  `describeAppStillRunning` - pure, unit-tested in every lane. Each named
  Windows Installer code gets its own sentence and its own remedy; an unmapped
  code still gets an actionable one. The message opens with what the user still
  HAS (their old version, still working), because that is the first thing
  someone whose update just failed wants to know.
- `update_install.zig`: the applier relaunches the terminal and THEN raises
  `ConfirmDialog.showStandalone` - modal, no App and no message loop needed,
  the same position `startup_error.zig` reports from.
- `test\win32\update-failure-visible.ps1` + a `guard-due.ps1` coverage row, so
  a later change that keeps the choreography and drops the dialog is caught.
  `update-apply.ps1` scenario 8 now dismisses the new modal and asserts it
  appeared.

## Why the collision code is forced rather than provoked

1618 (ERROR_INSTALL_ALREADY_RUNNING) cannot be manufactured from outside
msiexec. Measured on box 2026-09-01: a user-created `Global\_MSIExecute` mutex
is created successfully and msiexec runs straight past it (a valid package
under a held mutex returned 1603 from its own install, not 1618), and the only
other way to hold that mutex is a real installation running on the box, which
an acceptance script may not start. So the code alone is stubbed through a
Debug-only seam (`GHOZTTY_UPDATE_MSI_CODE`, compiled out of every non-Debug
build, the `GHOZTTY_STARTUP_FAIL` pattern) and everything downstream of it -
the message, the reporter, the dialog, the relaunch order - is the shipping
path. Arm A drives a REAL msiexec rejection end to end, so the seam is never
the only thing exercising the reporter.

## What is NOT in this task

The double-clicked MSI. Windows Installer owns the UI of a package started from
Explorer, and making that first-contact moment ours needs a bootstrapper or a
launcher handed out by the download page - which overlaps T1203's signing work
on the same moment. Filed as **T1247**.
