# T849 - the go-loop cannot reset its own context when no Ghoztty app is running, and only the 45-minute watchdog notices

## Summary

Found closing out **T478**, at go.md step 7. The turn was complete and pushed;
`/reset-context` then reported `FAILED: not in a Ghoztty pane`. It was right:

```
ghoztty +read --name=$GHOZTTY_PANE_ID  ->  No running Ghoztty instance found.
Get-Process ghoztty*   ->  only ghoztty-agent.exe (pid 22664)
pipes                  ->  \\.\pipe\ghoztty-agent-David, four ghostty-pty-*
```

The **app** was gone; the **agent** was still hosting this session's ConPTYs, so
the Claude session was alive, healthy, and detached with no UI to type into.
That is session persistence working exactly as designed — and it is also the one
state in which the loop cannot perpetuate itself, because every reset path ends
in "send keys to a pane".

No `Application Error` for `ghoztty*` in the preceding 12 hours, so the app
exited rather than crashed (a closed window, or a delivery restart that did not
come back). The watchdog was alive and ticking, which means the loop does
recover — after up to ~45 minutes of dead time, which is the safety net doing a
job the reset should not have handed it.

## In plain terms

The terminal window was closed while the assistant was still working in it. The
work itself was fine — it finished and shipped — but the way it normally starts
its next task is by typing into that window, so it had nowhere to type and had
to stop and wait for a supervisor to notice several minutes later.

## Goals

- [ ] A turn that ends with no app running gets the loop moving again in
      seconds, not in up to 45 minutes
- [ ] Whatever the recovery is, it must not surprise the user by opening windows
      they did not ask for while they are away from the machine

## Details

- The detection half already works and is cheap: the reset skill's probe chain
  falls through to `FAILED`, and `Get-Process`/pipe enumeration distinguishes
  "app gone, agent alive" from "not in a Ghoztty at all" in one call.
- Candidate recoveries, needing a judgement call about the second goal:
  re-launch the app and re-attach this session (the agent exists precisely so a
  session survives to be re-attached); or leave the app alone and have the turn
  signal the watchdog to act NOW rather than on its next stale-heartbeat sweep.
  The second is the smaller promise and does not touch the user's desktop.
- Whatever lands, `scripts\go-loop-watchdog.ps1` is where the recovery belongs,
  not the reset skill: the skill is shared with non-loop sessions, where "no app
  is running" genuinely does mean "ask the human".

## Validation criteria

- [ ] With the app killed and the agent left running, a turn ending in
      `/reset-context` reaches a fresh session (or a running watchdog re-entry)
      within a minute, proven on the box.
- [ ] The existing `test\win32\go-loop-guard.ps1` stays ALL PASS, and gains an
      arm for the app-gone case.
