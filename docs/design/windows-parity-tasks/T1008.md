# T1008 - The activity monitor's process table still wears the accent selection T828 took off the machine chooser

## Summary

ActivityMonitor paints a selected process row with panel_theme's `select` - the panel dragged 45 percent toward the accent (panel_theme.zig:91, ActivityMonitor.zig:3448) - and strokes its focus ring in the accent on top of it (`paintTableFocus`, ActivityMonitor.zig:3494). That is the pre-T828 treatment the user reported on the machine chooser as "a bright purple pill with a thick purple outline". T828 replaced it there with Windows 11's list convention: a NEUTRAL wash at two weights (0.10 unfocused, 0.16 focused), the accent spent on one 4x16 indicator capsule at the leading edge, and the focus rim in neutral ink so one control never carries two accent marks (`chooser_rows.zig`). The process table is the same kind of surface - a list of selectable rows - so the two panels now disagree about what a selected row looks like on this platform. Found while fixing T988's chooser probes.

## In plain terms

Pick a process in the activity monitor and the row lights up in a strong tint of
your accent colour with a matching outline around it. Pick a machine in the
machine chooser and you get Windows 11's quiet grey selection with one small
coloured bar at the left edge. The second one is what this app decided to look
like; the first one is what the user already asked us to stop doing once, on the
other panel.

## Goals

- [x] The process table's selected row paints the platform's neutral list
      selection instead of an accent-dragged fill
- [x] The accent on a selected row is one small capsule at its leading edge, and
      nothing else
- [x] The caret rim over that row is neutral ink, not a second accent mark
- [x] Both lists resolve those colours from ONE module, so they cannot drift
      apart again
- [x] A pixel probe on the box holds the treatment in place

## Validation criteria

- [x] A selected process row draws the neutral wash, not an accent-dragged fill,
      at both weights (list focused / not focused) — `test\win32\activity-selection.ps1`
      reads `#353535` unfocused and `#424242` focused on a `#1e1e1e` panel, which
      is `wash(panel, 0.10)` / `wash(panel, 0.16)` derived by the harness, not
      pasted
- [x] The accent appears exactly once on a selected row — same harness: the
      capsule is `#c466db` (the user's purple, chroma 117) and every one of the
      row's 28 lines is either the fill or the neutral `#ececec` caret rim
- [x] Unit tests in the `none` lane assert the row's resolved colours, the way
      `chooser_rows.zig` does — the model moved to `list_selection.zig` with its
      tests; both lanes green through `floor-lane.ps1 -Lane all`
- [x] An on-box pixel probe covers it, in the shape of
      `test\win32\chooser-selection.ps1` (which pins the focus-visual state
      rather than inheriting it — see T988) — `test\win32\activity-selection.ps1`,
      45 assertions ALL PASS, with a new `activity-selection` guard row; it pins
      the state from the panel's own focus messages, since the table is a
      custom-painted region with no `UISF_HIDEFOCUS` bit to post at (T1009)
