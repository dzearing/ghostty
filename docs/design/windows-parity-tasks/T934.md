# T934 - Host the feedback composer in its own WebView2 controller, replacing the RichEdit

## Summary

The foundation of D43's answer: the composer's text surface stops being a RichEdit child and becomes a second, lazily created ICoreWebView2Controller filling the pill's text rect, hosting an embedded contenteditable page. Plain-text parity only - seeding from pane.feedbackText(), mirroring every edit back, the placeholder, the wrapped line count that drives barHeight, focus handoff between the bar, the composer and the terminal, Ctrl+Enter send and Esc close. The controller is created on first open and destroyed on close with composer state kept on the pane, which is D43's own mitigation for the memory and startup cost. Quotes (T935) and image chips (T936) land on top of this and are deliberately out of scope.

Split out of T830, whose `## Design` section records the machinery this builds
on: `webview2.Host` and the pane's environment (`ViewerPane.zig:3940-4035`),
the bridge shim in `viewer_bridge.zig`, and `viewer_feedback_layout.zig` as the
single source of the design-system numbers the composer CSS gets. Read that
section before starting.

## In plain terms

When you report something from a viewer pane, a little composer slides in under
the toolbar and you type your report into it. Until now that box was a plain
Windows text control we drove by hand, and everything a text box is supposed to
do for free -- pasting a screenshot, typing Japanese or Chinese through an input
method, a screen reader reading back what you wrote -- was either missing or
hand-carried. This swaps the box itself for the same web view the page beside it
already uses, so all of that comes from the browser engine instead of from us.

Nothing about where the composer sits or how it looks changes: the capsule, the
two round buttons, the thumbnail strip and the hint row are all still painted by
the app. What changes is the strip of text inside the capsule -- and the fact
that it now behaves like every other text box on the machine.

## Goals

- [x] The composer's text rect is a second web view, created the first time you
      open the composer and given back when you close it.
- [x] What you type lands in the report: every edit is mirrored back into the
      pane's buffer, which is what survives a close and reopen.
- [x] The capsule still grows and shrinks with the wrapped line count, and the
      page still moves down and back up with it.
- [x] The empty composer still shows its cue, the caret still lands in the box
      when the composer opens, and Ctrl+Enter still sends / Escape still closes.
- [x] A box that cannot produce a web view still gets a composer -- the old
      control stays as the fallback until T937 retires it.

## What this deliberately did NOT do

- **Quoted blocks lose their wash** until T935 rebuilds them as CSS: the wash,
  the accent bar and the indent all lived in RichEdit formats. The quote is
  still in the text, still counted, still in the report.
- **Image chips stay literal text** until T936; the native carousel below the
  pill still works because it derives from the pane's buffer.
- **Ctrl+Z does not take a quote or a chip back out** (T983) -- a native
  insertion is a whole-document seed, which the browser's undo stack sees as
  one opaque replacement.
- **The RichEdit is not deleted** -- it is the runtime fallback until T937,
  which is also what keeps `viewer-feedback.ps1`'s editing arms meaningful.
