# T218 - Migrate the mouse-driven GUI scripts onto the test desktop

## Summary

T212 split, part 3 of 3: the 12 mouse-driving scripts left after T216 proves
(or disproves) the mechanism on `dark-menus.ps1`.

  chooser-menu, context-menu, focus-defer, focus-follows-mouse, hero-mode,
  host-settings, menu-bar, split-divider, tab-color, tab-strip, title-font,
  window-color

**UNBLOCKED 2026-07-30 - T216's verdict is YES.** Posted mouse input reaches
the app and `TrackPopupMenuEx` runs fine on a background desktop, so nothing
routes to the T207 option-B bucket. Read T216 before starting: it documents
`Send-TestMouse` / `Wait-TestPopupMenu` / `Get-TestDistinctColors`, why
`-Target` must name the window that would really have received the click, and
why menu keys go through `Send-TestControlKey` rather than `Send-TestKeys`.

Two things T216 measured that will bite these scripts specifically:

- **`SetCursorPos`/`GetCursorPos` are dead off the input desktop.** Anything
  that moved the real pointer and let the app read it back has to be driven
  by message coordinates instead. `focus-follows-mouse` and `split-divider`
  are the ones to check first - `focusFollowsMouse` gates on screen-coordinate
  motion.
- **A flat-fill capture passes half of these assertions.** Any brightness
  probe must require real content (`Get-TestDistinctColors`) before scoring.
  `dark-menus` read a false "dark" from an all-black mid-paint capture before
  the guard went in.

Also expect the T215 class of finding: foreground-gated product code silently
no-ops on a background desktop. T216 hit one (`getCursorPos` failing killed
every click); suspect a product no-op before weakening an assertion.

## Validation

- Each migrated script ALL PASS x3 on the test desktop.
- Each migrated script's negative control still FAILS.
- Any script that CANNOT migrate is named, with the measured reason, in this
  file and in the session log - never dropped silently.
