# T218 - Migrate the mouse-driven GUI scripts onto the test desktop

## Summary

T212 split, part 3 of 3: the 13 mouse-driving scripts left after T216 proves
(or disproves) the mechanism on `dark-menus.ps1`.

  chooser-menu, context-menu, focus-defer, focus-follows-mouse, hero-mode,
  host-settings, keybinds-t01, menu-bar, split-divider, tab-color, tab-strip,
  title-font, window-color

**`keybinds-t01` moved here from T217 on 2026-07-31** (batch 4). T212's
measured split put it in the keyboard-only bucket, and that was wrong: its
"ctrl+c WITH selection" section word-selects by driving a real
`SendInput` **mouse** double-click (`T01Drv::DoubleClick`, probing five
upper-screen rows until the clipboard proves a word-select happened), and
that section is live, not dead code. Everything else in the script is
keyboard, so it is a keyboard script with one mouse dependency - take it
early here, since the rest of the conversion is the plain T217 recipe and
only the double-click needs `Send-TestMouse -Action doubleclick`.

**UNBLOCKED 2026-07-30 - T216's verdict is YES.** Posted mouse input reaches
the app and `TrackPopupMenuEx` runs fine on a background desktop, so nothing
routes to the T207 option-B bucket. Read T216 before starting: it documents
`Send-TestMouse` / `Wait-TestPopupMenu` / `Get-TestDistinctColors`, why
`-Target` must name the window that would really have received the click, and
why menu keys go through `Send-TestControlKey` rather than `Send-TestKeys`.

Two things T216 measured that will bite these scripts specifically:

- **`SetCursorPos`/`GetCursorPos` are dead off the input desktop.** Anything
  that moved the real pointer and let the app read it back has to be driven
  by message coordinates instead. `focus-follows-mouse` and `split-divider`
  are the ones to check first - `focusFollowsMouse` gates on screen-coordinate
  motion.
- **A flat-fill capture passes half of these assertions.** Any brightness
  probe must require real content (`Get-TestDistinctColors`) before scoring.
  `dark-menus` read a false "dark" from an all-black mid-paint capture before
  the guard went in.

Also expect the T215 class of finding: foreground-gated product code silently
no-ops on a background desktop. T216 hit one (`getCursorPos` failing killed
every click); suspect a product no-op before weakening an assertion.

### Both scripts were already all-PostMessage, and it did not make them portable

Neither script ever used `SendInput`, so on paper both were already "background
desktop ready". Neither ran. The part that is desktop-bound is **window
ENUMERATION**: `EnumWindows`/`EnumChildWindows` walk the CALLING thread's
desktop, so every `FindTop` / `FindPane` / `MenuWindow` / `VisiblePanes` in the
scripts' own driver classes returned nothing and the scripts died at SETUP FAIL.
Moving those to the harness's worker thread is the whole migration for
`context-menu`.

What does NOT have to move: **HMENU reads**. `GetMenuItemCount`,
`GetMenuStringW`, `GetMenuState` and `GetSubMenu` take a menu HANDLE, not a
window, and a menu is not a desktop object - so the tree walk stays in-process
in both scripts (only the `MN_GETHMENU` that fetches the handle goes through
`Invoke-TestMessage`). Useful shape for the next batch: **ask whether the call
takes an HWND before assuming it needs the harness.**

Two more facts measured here, both of which remove work rather than add it:

- **`SetCursorPos` parking is not needed and is now deleted, not replaced.**
  `context-menu`'s section A parked the physical cursor before right-clicking,
  because the core resolves the right-clicked word through
  `rt_surface.getCursorPos()`. T216 had already given win32's `getCursorPos` a
  fallback to `last_cursor_client` - the position carried by the last mouse
  MESSAGE - and `Send-TestMouse` posts a `WM_MOUSEMOVE` ahead of every button
  event, so the posted click's own coordinates are what the word-select
  resolves against. Verified by reading `getCursorPos` +
  `noteCursorFromLparam` in `src/apprt/win32/Surface.zig`, then by the
  assertion passing. This is the counter-case to `split-divider`: a
  cursor-reading product path CAN migrate when the product has a
  message-derived fallback, so check for one before deleting an assertion.
- **The clipboard is a WINDOW STATION resource, not a desktop one.** A desktop
  is a child of a window station, so the script (interactive desktop) and the
  app (test desktop) share one clipboard and both paste sections migrated
  untouched. Nothing in the paste path needed a workaround.

### The stale-constant class again, this time DPI-blind as well

`menu-bar` section A clicked a hard-coded **46px left of the client's right
edge** to hit the "+" button. Five assertions failed against a healthy product,
for two compounding reasons:

- **It encodes a layout the product left behind.** The constant was written
  when a single tab STRETCHED to fill the strip, which parked the "+" hard
  against the menu button. **T202** stopped the stretch: `layout()` now clamps a
  lone tab to `max_tab_w` and puts the "+" at
  `min(tabs_right + group_gap, plus_limit)`, so with one tab it sits ~260px
  from the LEFT. (`T202_NEUTERED = false` in `tab_strip_layout.zig` - the
  stretch is genuinely gone, not toggled off.)
- **It is DPI-blind, and the box is at 125%.** The button group scales, so at
  `scale = 1.25` the menu button spans `[cw-50, cw-5)` and `cw-46` lands INSIDE
  it. The "+" click therefore opened the MENU, which is why the failures read
  "the + button did not open the menu" and "tabs 1 -> 1" at once.

Replaced by `Strip-Geometry`, which evaluates `tab_strip_layout.zig`'s
published metrics (`strip_pad_l/r`, `group_gap`, `btn_w`, `tab_gap`,
`min/max_tab_w`) at the window's live DPI and returns the "+" x, the menu-button
x, and a genuinely dead strip x. Two things make duplicating that model
acceptable rather than a second source of truth: every consumer asserts an
OUTCOME (a wrong model clicks dead space and fails the section, it cannot
quietly pass), and the "+" is re-derived on every click in the reflow loop
because it travels as tabs are added. It also bought a new assertion - the bare
strip between the "+" and the menu button now has to open neither a menu nor a
tab, where the old "mid-strip" click at x=200 had drifted onto tab 1.

Note the shape: the migration did not break this, and the interactive desktop
would not have caught it either. It is the same rot batch 2 found three times -
**a geometry constant a script hard-codes is a claim about the product, and an
unrun script's claims rot silently.**

### The measurement that decided both (and corrects the harness header)

`SetCursorPos` returns **FALSE** on a background desktop and `GetCursorPos`
returns **-1,-1**. The harness header claimed the opposite - *"SetCursorPos
DOES work on a background desktop"* - which is wrong and would have sent the
next author down a dead end. It is corrected in place, along with
`Set-TestCursorPos`/`Get-TestCursorPos`, which are kept only because they are
the honest way to find that out. `Send-TestMouse` calls `SetCursorPos` too and
ignores the result; nothing depends on it.

- **`focus-follows-mouse` never needed the cursor.** Reading
  `Surface.focusFollowsMouse` settles it: the motion gate compares
  `ClientToScreen(lparam)` against `app.ffm_last_screen_pos` - the coordinates
  travel IN the message. A posted `WM_MOUSEMOVE` with moving coordinates is the
  same evidence a hardware move is. What posting does not reproduce is
  hit-testing, so the new `Glide-TestPointer` addresses each step to the pane
  that CONTAINS that point; naming the wrong one would have the app focus
  whatever it was told and the assertion would pass on a broken product.
- **`split-divider`'s cursor assertions did need it, and are gone.** See
  **T228**, filed for this: `WM_SETCURSOR` carries no coordinates, so the
  product's handler must read `GetCursorPos`, and with nothing to read it falls
  through to `DefWindowProcW` (measured: returns 0 at every point on the band).
  Replaced by four `WM_NCHITTEST` probes on the pane - HTTRANSPARENT across the
  band, HTCLIENT at the pane center - which read the fall-through at the source
  and pin the band's extent better than a glyph. The literal glyph is what is
  unasserted.

### A composited-screen premise that a background desktop cannot hold

Also T228, and the more interesting half. `split-divider`'s T155 section
scanned a scanline ACROSS both panes and counted divider-colored runs, on the
premise that *a stale line under a pane has been overpainted by that pane*.
There is no composite off the input desktop, and measurement shows the premise
fails there: a `PrintWindow` capture keeps **every intermediate line a drag ever
painted** - 3 drags produced **13 runs** against a healthy product - because the
GL child does not overpaint the parent's backing store in that render. A
full-window repaint does not clear them; a window move does not either. Scored
that way the test fails for pixels no user can see.

The scan now covers the parent-visible strip between the two pane rects and
asserts the gap IS the band (`gap == bandPx` - pure geometry, and the pre-fix
~5 DIP gap fails it outright) and that the whole gap is one solid divider fill.
Watch for this shape elsewhere: **an oracle whose validity rests on one window
covering another is asserting something the capture path does not reproduce.**

### Things batch 3 confirms for the next batch

- **The drag gesture migrates cleanly.** `updateDividerDrag` reads its
  coordinates out of the `WM_MOUSEMOVE` lparam and consults neither MK_LBUTTON
  nor the cursor, so a posted down / moves / up on the TOP-LEVEL window is the
  same input a real drag delivers (measured: an 80px drag moved the line 80px).
  Post to the window the OS would have routed to after the pane answered
  HTTRANSPARENT - not to the pane the pointer is visually over.
- **`WM_NCHITTEST` is an underused oracle.** It is the product's own decision

### Three stale test assumptions, all failing against a HEALTHY product

None of these are migration artifacts - each would fail on the interactive
desktop today. They are what happens when a script is not re-run after the
product moves under it.

- **`tab-color` derived the bar height from a jump that no longer happens.**
  It launched with one tab, recorded the pane top as "client top, no bar yet",
  pressed ctrl+t and measured the bar as the difference. Since **T190** the
  strip is up from the FIRST window on Windows (`auto` shows it because the
  strip is also the app's menu host), so the pane never moves, `barH` came out
  0, and the positive control failed before a single tab-color assertion ran.
  Now the height is measured directly and ctrl+t only has to prove a 2nd tab
  appeared.
- **`tab-strip` compared the measured chiclet against `max_tab_w`.** The SLOT
  is `max_tab_w`; the drawn chiclet gives up `tab_gap` of it
  (`tab_strip_layout.zig`: `drawn_w = this_w - tab_gap`), so at 125% DPI the
  pixels read 243 against an expected 250 with a tolerance of 3. The expected
  value is `max_tab_w - tab_gap`, and a tab INDEX is measured in slot pitch
  (`chiclet + tab_gap`), not in chiclet widths.
- **`tab-strip` measured the selected tab as "first dark pixel until the first
  light one".** The chiclet's rounded left edge antialiases to a dark pixel,
  one or two lighter ones, then the fill - so the scan measured a **1px-wide
  tab** and failed four assertions. It now takes the LONGEST dark run on the
  scanline. (The old scan got away with it on a screen grab, where that edge
  blended differently: same claim, different pixels, which is exactly the class
  of difference a capture-path change exposes.)

### The harness bug batch 1 turned up (fixed here)

**`Send-TestMouse -Action doubleclick` was posting a message the terminal
surface never listens for.** It sent down / up / **WM_LBUTTONDBLCLK** / up
unconditionally, which is only what the OS delivers to a **CS_DBLCLKS**
window. `GhozttyWindow` has that style (`App.zig`, for the divider-equalize
gesture); the `GhozttyTerminal` surface class does NOT - it is `CS_OWNDC`, and
the core counts its own clicks from plain button-downs. So a posted DBLCLK was
dropped on the floor, the core saw ONE click, no word-select happened, and
`keybinds-t01`'s ctrl+c-copy assertion failed against a completely healthy
product.

`MouseEvent` now reads the TARGET's class style (`GetClassLongPtrW`,
cross-process) and sends what the OS would really send: down/up/DBLCLK/up for
a CS_DBLCLKS target, down/up/down/up otherwise. This matters beyond this
script - `split-divider` double-clicks the divider on the top-level window,
which is the CS_DBLCLKS half.

Worth generalizing: **a posted message is only faithful if the target would
have received that message.** T216 established the coordinate half of this
(name the window a real click would hit); this is the message-identity half.

### Harness additions batch 1 needed (all in `lib/TestDesktop.ps1`)

### Things batch 1 learned, for the next batch

- **Re-resolve the focused surface before every chord.** Every tab open,
  split, and pane close makes a NEW `GhozttyTerminal` child, and a chord
  posted at the stale HWND (or at the top-level window, which hands
  WM_KEYDOWN to DefWindowProc) is silently dropped. `Get-TestFocusedWindow` per
  chord is what the old drivers' "pass IntPtr.Zero to keep the last focus"
  meant.
- **A stale KNOWN-FAIL comment outlives its bug.** `keybinds-t01` carried
  "KNOWN FAIL until the ConPTY ^C-signal task is fixed" on its ctrl+c/SIGINT
  assertion. T84 fixed that (the inherited `CREATE_NEW_PROCESS_GROUP` flag),
  and the assertion passes on every run now. Comment removed. Check the other
  scripts' KNOWN-FAIL notes as they are migrated rather than porting them
  forward.
- **Assertion count went 24 -> 30 on `keybinds-t01`** without new coverage
  being invented: the old script wrapped nearly every section in
  `if ($r -like 'ABORT*') { SKIP }`, and the foreground grab lost that race
  often enough for whole sections to vanish from a "passing" run. Posted input
  cannot abort, so the SKIP branches are gone and the assertions always run.
  Same shape as the batch-1 `ipc-version` finding.
- **`Start-Job` inherits `GHOZTTY_PIPE_SUFFIX`** (it is a process env var, and
  the job host is a child process), so an IPC probe run from a job still talks
  to the isolated instance.
