# T1344 - Banners flicker when they expand and collapse

## In plain terms

A pane banner that expands or collapses flashes on the way. The Mac's does not.

## What the user reported (2026-09-04)

> "things flicker ... when i expand/contract banners, they flicker."

Split out of T1324. Separate from the divider-drag slowness (T1343) because it
is a different path: the T149 collapse animation, the reserved band the layout
hands the popup, and the layered popup's own repaint.

## Where to look

- `BannerOverlay.updatePosition` already reasons carefully about the animating
  case: while `collapse_anim` runs, the popup has to cover BOTH the settled
  band and the card's current height, and a resize sets `SWP_NOCOPYBITS` so a
  frame of stretched card is not blitted in. Whether that is enough is exactly
  the question.
- The terminal underneath snaps to the settled band before the card finishes
  animating, which is deliberate (it is what lets the inset snap at all) and is
  a plausible source of a one-frame gap.
- The band is reserved by `Surface.bannerLayoutInset` and applied by the
  window's layout pass; the popup is moved afterwards, in a separate
  `SetWindowPos`. Two windows changing size in two calls is a flicker shape
  even when each one is individually correct.

**Capture the flicker before theorising about it.** `banner-resize-repaint.ps1`
established that layered popups do not come back from `PrintWindow` on the
background test desktop, so a pixel oracle needs either the interactive desktop
or an in-app frame log. Say which one this used.

## Goals

- [x] Find the frame state the user is seeing, rather than theorising about it.
- [x] Assemble a banner frame offscreen and put it on the window in one blit.
- [x] Cover it with an assertion that goes red if a stage is drawn on the
      window again.

## What was found

`BannerOverlay.paint` drew a frame in stages, straight into the window's own
DC: the pane background across the whole client, the card backdrop blitted
over that, then the content, the collapse fade and the chevron. Every one of
those stages is a state the compositor is free to show, and the widest of them
- a bare band of pane background where the card should be - sits between the
first two.

At rest nobody sees it, because a settled banner only repaints when something
about it changes. A collapse or an expand repaints the whole client on every
one of ~11 frames in 180 ms (T149's animation, and T833's per-frame invalidate
in the expand direction), which is exactly the gesture the user named.

The fix is the one `activity_paint.zig` already uses, and for the same stated
reason: assemble the frame in a memory DC and put it on the target in a single
`BitBlt`. Both entry points go through it - WM_PAINT and WM_PRINTCLIENT - so a
capture still reads byte for byte what the screen gets, which is what T835's
unit test asserts.

`SWP_NOCOPYBITS` on the resize path was left alone deliberately: it is a
plausible second source of exposed pixels, but it is a theory this turn could
not demonstrate, and the card is what the user described. Filed as T1352.

## Capture method

**An in-app frame log, plus a compile-time negative control** - not the
interactive desktop. Layered popups do not come back from `PrintWindow` on the
background test desktop (`banner-resize-repaint.ps1` established that), so a
mid-animation pixel capture was never available here.

The oracle is an OBSERVATION rather than a restatement of the flag that
decided it: `WindowFromDC` answers the owning window for a DC that BeginPaint
or GetDC handed out, and null for a memory DC. `banner paint ... buffered=`
reports that reading, and the `last_frame_buffered` field carries the same one
into the unit lane.

      asserted, with the capture method written down. Demonstrated by the

      offscreen, not on the window`, which covers the settled frame, the
