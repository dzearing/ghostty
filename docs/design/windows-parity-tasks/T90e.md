## Done 2026-08-02

`ghoztty +split --view=README.md` renders a markdown document on Windows, and
`--view=build.zig` renders syntax-highlighted code, both entirely offline —
from a synthetic origin that does not resolve in DNS, on a box with no route
out.

**What landed, in the shape the design pinned.**

`src/apprt/win32/viewer_content.zig` (new, pure, none lane) is everything that
is arithmetic: mode by extension (Mac's table, and `about:`/`http(s)` wins over
it via the SAME `ipc_args.viewMode` the CLI and the IPC server use — three
copies of "what counts as a URL" is three chances to disagree), the
highlight.js and MIME tables byte-identical to Mac's, `file://` unwrapping with
percent-decoding, the 3-tier resolver's path math, and the `window.__viewer`
calls.

Its **directory-escape guard is lexical**, and that is the one deliberate
divergence from `ViewerSchemeHandler`: Mac resolves symlinks and prefix-checks
the real paths, which needs a live filesystem, so the check that stops
`![](../../../../secrets.txt)` could never be unit tested. `std.fs.path.resolve`
folds `.` and `..` without touching disk, so the guard is pure — and the tests
cover the absolute-`rel` escape (`/etc/passwd`, `C:\Windows\win.ini`), the
drive-relative one (`C:win.ini`), and the sibling-prefix one (`/app/viewer-evil`
is not under `/app/viewer`, which a naive `startsWith` would let through). The
one filesystem-shaped half — tiers tried in order, a DIRECTORY is not a
resource, a name present in two tiers resolves to the bundled one — is its own
test against a real temp tree in the win32 lane.

`appendJsString` escapes **U+2028 and U+2029**, which JSON does not have to and
JavaScript does: both are line terminators inside a JS string literal, so a
document containing one would end `setMarkdown("…` mid-string and the pane
would render nothing at all with no error anywhere.

`webview2_iface.zig` grew the four file-mode slots — `add_NavigationCompleted`
(15), `ExecuteScript` (29), `add_WebResourceRequested` (55),
`AddWebResourceRequestedFilter` (57) — plus `IStream`,
`CreateWebResourceResponse` (environment slot 4), and the request/response/args
interfaces. `ICoreWebView2` is now a 58-slot prefix of its 61.

`ViewerPane.zig` holds its own reference on the shared environment (the
response factory lives there), resolves the bundled assets once at `start`,
serves every intercepted request out of the three tiers, and injects the file's
content from `NavigationCompleted` — which is the earliest moment
`window.__viewer` exists.

The interim `--view` refusal is **deleted**, not disabled:
`view_file_unsupported_error` and its call site are gone from `args.zig` and
`IpcHandlers.zig`, so `viewArgResponse` has exactly one check left and it is the
permanent one.

**How the IIDs and slots were derived.** Not from memory. The
`Microsoft.Web.WebView2` SDK's own `WebView2.h` was read for every IID and every
vtable ORDER, and that mattered: the `ExecuteScriptCompletedHandler` IID
recalled from memory was plausible and WRONG
(`…-4bb9-9878-cd818fca5ea4` vs the real `…-4bca-9923-137112f4c4cc`). The
cross-check that made the rest cheap: T374/T375 had already pinned
`AddScriptToExecuteOnDocumentCreated` at 27, `add_WebMessageReceived` at 34 and
`add_NewWindowRequested` at 44, so a transcription that puts any of them
elsewhere is wrong by construction — and all three still sit where they were.

## Evidence

Every lane run on the box, 2026-08-02:

- `zig build test -Dapp-runtime=none` — exit 0.
- `zig build test -Dapp-runtime=win32` — exit 0.
- `zig build test-agent` — exit 0.
- `test\win32\ipc-p1/p2/p3.ps1` — `ALL PASS` each.
- `test\win32\viewer-panes.ps1` — `ALL PASS (78)`, run three times.

**The oracle that matters is the live one**, in the win32 lane's "host floor"
test, and it is a single number: `file mode: headings=2`. A two-heading markdown
file, opened as a pane, comes back as `pane.headings` only if EVERY link ran —
the filter and the interception fired for an origin that does not exist in DNS
(so a miss is a hard failure, not a slow network), `CreateWebResourceResponse`
built a body from a **rewound** `IStream` four times over, the resolver found
all four assets under the bundled directory, `add_NavigationCompleted` fired,
`ExecuteScript` ran `setMarkdown` with the file escaped as a JS literal, the
page rendered it, and it posted the headings back up T375's bridge. A wrong
slot index anywhere in that list produces silence, which is why the assertion is
on CONTENT arriving rather than on an HRESULT. The same test then drives CODE
mode (headings fall back to 0, which is `setCode` clearing the index — a
template that reloaded and was never injected would leave the host's copy
alone) and a missing file (the pane stays `.ready`).

That test overrides the assets path to the source tree, because a test binary is
not an installed ghoztty. So the acceptance script carries the **other half**:
it reads the GUI's own stderr and asserts `viewer file error: Cannot read file`
appeared for the missing-file pane. That line is written from the
NavigationCompleted handler, which only fires once the template has been
SERVED — so it says the real app resolved its own bundled assets and got all
the way to the injection, with no override anywhere. Paired with three negative
assertions (`no bundled viewer assets found`, `viewer resource not found:
(viewer\.|vendor/)`, `ExecuteScript failed` must all be absent).

`+list` needed no server change: T90b/T90c had already landed the `type`/`url`
fields and the `view:` row, and they report a file location exactly as they
report a URL. Dark mode likewise — T373's `PreferredColorScheme` sync is what
the bundled `viewer.css` and the two hljs themes key their
`prefers-color-scheme` off, so file mode inherited it working.

## Deliberate deviations from Mac, both filed

- **A UTF-8 BOM is stripped** before rendering. Left in place it is a stray
  glyph ahead of the first heading, and Windows editors write one routinely;
  Mac keeps it. **T387.**
- **A 32 MB cap**, past which the page shows `File is too large to display`.
  Mac's `Data(contentsOf:)` is unbounded, which makes `--view` on a huge file an
  unbounded allocation driven by a caller-supplied path. **T387.**

## Follow-ups filed

- **T387** — the two deviations above, closed from the Mac seat.
- **T388** — a leading `~` in a `--view` path is not expanded, so `~/x.md`
  resolves to `<cwd>\~\x.md`. Upstream of this port, in `view_args.zig`.
- **T389** — the injection holds three copies of the file at once (bytes, JS
