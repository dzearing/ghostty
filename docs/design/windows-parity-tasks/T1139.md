# T1139 - Two more chooser tests still walk the session roster blind, so a slow roster reads as a broken feature

## In plain terms

Two of our automated checks drive the session list with the keyboard the way a
person would, but they never look to see where the highlight actually went. When
the list takes a moment to load, the keys land on nothing and the check reports
that the feature is broken when it is not. Somebody then spends a day chasing a
bug that does not exist.

## Summary

T1107 traced `orphan-notify.ps1`'s two sweep failures to exactly this: the
script pressed Right to step into the roster and then counted Down keystrokes
against `+sessions --json` order. Neither assumption holds. The displayed order
is sorted (T602), and `MachineChooser.enterSessions` returns immediately when
the roster has not been fetched yet - so Right can be a no-op, no cursor is ever
set, and `resumeCursor` then declines the Return, which falls through to the
machine row's default action: a window opens and nothing is resumed.

T1107 put the walk that reads the app's own `chooser roster: cursor on session
id=` line back in one place (`test/win32/lib/ChooserCursor.ps1`) and converted
`orphan-notify.ps1`, `chooser-resume.ps1` and `chooser-resume-remote.ps1` to it.
Two scripts were left behind:

- `test/win32/chooser-roster-refetch.ps1:213` - Right, then `$rows.Count - 1`
  blind Downs, then an 800 ms sleep. Its assertion is a PIXEL (the cursor wash
  on the last card), so a mis-landed cursor shows up as a colour that did not
  move, with nothing naming the cause.
- `test/win32/chooser-session-sort.ps1` - drives the same roster without ever
  reading a cursor landing back.

Neither is red today. Both are the shape that goes red under sweep load and
gets filed as a broken feature, which is the cost this task removes.
