# T1341 - The zig self-hosted-backend compiler crash is reduced but still unreported upstream

## Summary

T476 reduced "zig 0.15.2's self-hosted x86_64 backend cannot compile
`ghostty-test`" to a standalone project with no ghoztty source in it:
`test/zig-repro/t476-selfhosted-backend`. What is left is telling the zig
project about it.

That last step was deliberately NOT done by the loop. Opening an issue on
`ziglang/zig` posts publicly under the user's GitHub identity, on a repository
this project has no other relationship with, and it is not retractable — the
same class of act the `--repo dzearing/ghoztty` rule exists to prevent by
accident. So the material is prepared and the posting waits for the user.

## In plain terms

We found a bug in the compiler we build with, and boiled it down to fifteen
lines that anyone can run. Telling the compiler's authors about it means
posting in public with the user's name on it, so that part waits for them to
say go.

## Goals

- [ ] Get the user's go-ahead to open an issue on `ziglang/zig`

## Details

Everything the report needs is already measured and written down:

- The reduction and how to run it: `test/zig-repro/t476-selfhosted-backend/README.md`
- The bisection that produced it, and the three failure signatures:
  T476's `## What the reduction turned out to be` section
- Environment: zig 0.15.2 (winget), Windows 11 Pro 26200, x86_64

Two details are worth leading with in the report, because they are what makes
this hard to diagnose from the outside:

1. **The compiler says nothing at all.** No panic message, no stack, no
   `error:` line — just a dead process. `zig build` reports it as
   `exited with error code 3` / `code 5`, which is `std.process.Child`
   truncating an NTSTATUS to a byte (T444). The real codes are `0x80000003`
   and `0xC0000005`.
2. **The trigger is the size and shape of a generated table**, not the ten
   lines of user code that read it: the same call against a trimmed
   `uucode_config.zig` compiles clean.

Check whether an issue already covers it before filing — upstream Ghostty has
carried `// Crash on x86_64 without this` next to `.use_llvm = true` for a
while, so somebody may have reported the family already; a comment with a
fresh reduction on an existing issue is worth more than a duplicate.
