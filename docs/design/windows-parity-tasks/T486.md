# T486 - Local Restore All has no on-box rebuild oracle after T194: the launch now recovers before the button can

## In plain terms

There is a "Restore All" button that rebuilds all of a machine's terminal
windows. On this machine it used to be the only way to get windows back after a
crash, so a test drove it end to end. Now the app does that recovery by itself
the moment it starts, which is better for the user but means the button has
nothing left to do in that test — so the button's own rebuild is no longer
checked here. Either give it a scenario where it still matters, or decide it
does not need one.

## Goals

- [ ] Decide whether the LOCAL Restore All still has a job worth testing now
      that launch-time recovery covers the crash case
- [ ] If yes: an on-box fixture where the button really rebuilds — the
      already-running viewer adopting sessions orphaned after it started
- [ ] If no: say so in the task file and leave the guard test as the coverage

## Summary

Filed from T194 (2026-08-04). T194 made launch-time restore consult the agent's
layout blobs, so a relaunch after a crash rebuilds the orphaned windows on its
own. `test\win32\chooser-restore-all.ps1` section 3 used to prove the BUTTON did
that rebuild; its fixture (kill the app, drop the manifest, relaunch) now
recovers before the chooser is ever opened, so section 3 was rewritten to assert
the automatic recovery and section 4 (the double-attach guard: pressing it with
those panes on screen must rebuild NOTHING) is what the button has left under
test locally.

`restoreAllFrom` — the shared rebuild both paths run — is still driven end to
end by `chooser-restore-all-remote.ps1` across the relay, so the CODE is
covered. What is not covered is `restoreAllLocalSessions`' own path: the local
transport plus the `markLayoutDirty` bind-back that only the local arm does.

## Details

The realistic local scenario the button still owns is a viewer that was ALREADY
RUNNING when the sessions were orphaned — it cannot have recovered them at
launch because they did not exist yet. A fixture for that needs two app
instances on the same agent (same `LOCALAPPDATA`, different
`GHOZTTY_PIPE_SUFFIX`): start B, build multi-pane windows in A, kill A, then
press Restore All in B. Both instances share the session-layout manifest, so the
fixture has to be explicit about which one writes it last.

Weigh that against simply accepting the guard test as the local coverage and
leaning on the remote script for the rebuild — the answer may well be that the
local button is now a convenience with no unique behaviour to protect.

## Validation

Whichever way it goes: `chooser-restore-all.ps1` and
`chooser-restore-all-remote.ps1` both ALL PASS, and the task file records the
decision so the next reader does not re-open it.
