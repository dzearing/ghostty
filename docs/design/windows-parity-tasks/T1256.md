# T1256 - Watch Ghoztty run over a real Remote Desktop session and record what it is actually like

## In plain terms

On 2026-09-01 the user reached this machine from a MacBook and Ghoztty would
not start. Four tasks since then have made it start - proved by a debug switch
that makes the graphics driver pretend to be old. Nobody has yet sat in a real
Remote Desktop session and watched. This is that: connect, run the checklist,
and write down what the terminal is actually like to use over the wire.

## Split from

[[T1253]]. Its sibling is [[T1255]], which is the checklist.

## Why this is not something the loop can do for itself

Windows 11 Pro serves ONE interactive session at a time. An RDP connection from
anywhere - localhost included - takes over the console session rather than
joining it, so this box cannot originate a remote session against itself
without blanking the desktop the loop is running on. Windows Sandbox and
Hyper-V both need an elevated feature install and a reboot. It takes a second
machine and a person on it.

A GitHub runner is no help either: it has no RDP session, and the subject here
is the ENVIRONMENT, not the code path. The code path is already covered by arms
E, F and H of `test\win32\startup-failure.ps1`.

## What to do

1. On this box: Settings > System > Remote Desktop, on. (`qwinsta` should list
   `rdp-tcp ... Listen`; it did on 2026-09-01.)
2. From a second machine - Microsoft's Windows App on macOS, or `mstsc` - sign
   in as the same user.
3. In the remote session:

   ```
   powershell -NoProfile -File test\win32\rdp-session.ps1
   ```

   The run takes about four minutes now: arm G ([[T1316]]) samples a dimmed
   viewer pane's brightness for two of them, which is the measurement [[T1295]]
   is parked on. Leave the session alone while it does - the pane it is
   watching has to stay on screen and unoccluded.
4. Commit `test\win32\artifacts\rdp-session.json` and paste the GL and pacing
   lines into this task, plus the `luminance:` line arm G prints.
5. File whatever it turns up. **Slow-but-working is a result, not a failure**,
   and belongs in a follow-up rather than blocking this task.
6. Answer [[T1295]] from the artifact's `dim` block: a drop inside the bound
   closes it, a drift beyond it reopens it with the composition path (the Mesa
   d3d12 fallback under RDP redirection) as the named suspect.

## What the answer is worth either way

`impl=fallback` means T1251 and T1252 are doing their job on the display that
motivated them. `impl=system` means the session's driver clears 4.3 on its own
and the whole chain was aimed at a narrower case than assumed - which is worth
knowing too. The one outcome that is a defect is the terminal coming up with no
account of either.

## Validation criteria

- [ ] `rdp-session.ps1` reports `ALL PASS` from inside a real remote session.
- [ ] The GL report is recorded here: version, renderer, vendor, and whether it
      fell back.
- [ ] Frame pacing over RDP is recorded here: sample count, median fps, worst
      inter-frame gap.
- [ ] Arm G's luminance series is recorded here, and [[T1295]] is closed or
      reopened from it.
- [ ] `test\win32\artifacts\rdp-session.json` is committed.
- [ ] Follow-ups filed for anything the session turned up.

## Readiness on this box (2026-09-01)

Everything that does not need a second machine is already in place:

- `qwinsta` reports `rdp-tcp ... Listen`, so the box will accept a connection.
- `test\win32\rdp-session.ps1` run from the console session refuses to score:
  `SKIP whole run: not running inside a Remote Desktop session
  (SM_REMOTESESSION is 0)` followed by `ASSERTED NOTHING (0 assertions) - this
  run proved nothing; it is not a pass`. That is [[T1255]] working as designed -
  the checklist cannot be faked from here - and it is also the proof that this
  task cannot be closed from this seat.

So the task is parked, not abandoned: the moment someone signs in over RDP,
step 3 of **What to do** is one command and the task closes.
