# T244 - +list --pid never matches on a session-persistence box: agent-owned panes report pid 0

## In plain terms

A program running inside a Ghoztty pane could not ask "which pane am I in?"
by giving its own process id, because with the default configuration the app
did not know the process ids of the shells in its panes. That core defect was
fixed under two sibling tasks (T41 gave the app the real ids, T153 verified
and locked it in). What this task adds on top: the watchdog that revives the
work loop now uses those real ids to check exactly whether a Claude session
is alive in a pane, instead of guessing from what happens to be on screen —
so it can no longer type a shell command into a busy Claude session whose
tell-tale screen text has scrolled away.

## Summary

`+list --pid=<pid>` is the documented Windows stand-in for the Mac's `+list
--tty` - "the tty-less way for a process inside a pane to discover its own
pane" (CLAUDE.md). On the default configuration it can never match anything,
because `session-persistence = on` means the agent owns the PTY and the app
has no handle for the child, so every pane reports `"pid": 0`.

## Evidence (VERIFIED on the box 2026-07-31, release +eeb78b6f0)

```
PS> ghoztty +list --pid=$PID
IPC request failed          # exit 1, from a pane in that very window

PS> ghoztty +list --json    # every terminal leaf:
    "id": "6C13A7F3-...", "pid": 0, "tty": "",
    "id": "2A331463-...", "pid": 0, "tty": "",
```

Both panes are ordinary local panes of the installed release, nothing remote.

`IpcHandlers.zig:1185` skips any surface whose `surfaceShellPid()` is 0 before
it even walks ancestry, so the loop cannot match a single pane and falls
through to `no pane found for pid N`. `surfaceShellPid`
(`IpcHandlers.zig:1394`) can only produce a pid from `.exec` +
`.fork_exec` - i.e. a shell the APP spawned. A session-persistence pane's
child belongs to `ghoztty-agent`, which is exactly the case the function has
no branch for. (INFERRED from the source; the observed `pid: 0` is verified.)

## Why it matters

- The advertised self-identification path for a process inside a pane is dead
  by default. `$GHOZTTY_PANE_ID` covers the common case, but `--pid` is what a
  process that did NOT inherit the pane env (a detached helper, a service, a
  tool started from another shell) has to use.
- It cost T241 its first design: the natural "is a claude alive in THIS pane?"
  probe is `+list --pid` per candidate process, and that had to be abandoned
  for a pane-tail heuristic (`scripts/go-loop-pane-probe.ps1`) once this was
  measured. The heuristic works, but the ancestry answer is the exact one.

## The fix

The agent already knows its sessions' child pids (`+sessions` reports one per
session). Plumb that pid back to the surface so `surfaceShellPid` can answer
for an agent-owned pane: either carry it on the session-backed IO backend at
attach/RELAUNCH time, or ask the agent for it when the local handle is absent.
`+list --json`'s `pid` field should then be non-zero for local persistent
panes, and the ancestry walk in `IpcHandlers.zig:1177` starts working again
with no change of its own.

Note the ancestry walk itself must stay honest: the agent is the parent of the
pane's shell, so `ProcessTree.isAncestor(shell_pid, query_pid)` is still the
right question - only the seed is missing.
