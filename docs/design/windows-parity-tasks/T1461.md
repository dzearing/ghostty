# T1461 - A Ghoztty pane drains streamed output at ~50 KB/s where conhost does ~1.3 MB/s

## Summary

Measured 2026-09-08 (T1458): a Ghoztty pane whose PTY is held by `ghoztty-agent`
drains a sustained stream at **~50 KB/s**. conhost, on the same desktop and the
same byte-identical 8 MB workload, does it at **~1.3 MB/s** - about 26x faster.
The writer is released after 9.1 s (conhost 6.1 s, the 1.5x everyone quotes) but
the pane is still parsing the backlog more than 20 seconds later, so the number
the user actually lives with is far worse than the writer's clock suggests.

This is the defect behind T1458's report. It is filed separately because T1458 is
the user-facing symptom and this is the specific throughput deficit that has to
close for the symptom to go away.

## In plain terms

When a program prints a lot of text quickly, a Ghoztty pane falls behind and
keeps catching up long after the program has finished - which is what "it feels
laggy, it arrives in lurches" means. The terminal Windows ships with keeps up
about twenty-six times better on the same output. This is that gap.

## What is already ruled out - do not re-investigate

From T1458's capture, all with numbers in that task file:

- **The present is not it.** `swapBuffers` costs 15-194 us and `swap_max_ms` was
  0 across 1,240 samples. The virtual/streamed display theory is dead.
- **The T111b priority handoff is not it.** `yield_ms_per_s` was 0 in every
  sustained second.
- **Slicing granularity is not obviously it.** `slices_per_s` tracks
  `kb_per_s` / 4 KiB exactly, so the slicer is doing what it says.

What is left is the ~500 ms/s inside `processOutputTracked`, which T1460 splits
into lock wait vs work. **Start there** - this task should not begin optimising
until T1460 says which side to optimise.

## Details

The leading reading is renderer starvation: 12 fps x ~40 ms of held pane mutex
per frame is ~480 ms/s, and the io thread waits on that same mutex. If that is
confirmed, the question becomes why a `drawFrame` costs ~40 ms when its present
costs 0.03 ms - which points at cell-buffer rebuild and upload, not presentation.

The reproduction is cheap and already written: the workload emitter and the A/B
runner used for T1458 live in this session's scratchpad and are described in
T1458's measurement section. Fold them into `test\win32\` as part of this task so
the number has a home and can regress.
