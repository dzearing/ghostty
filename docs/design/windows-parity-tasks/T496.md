# T496 - Caption min/max/close are app-styled squares, not native Win11 caption buttons

## Summary

User report (2026-08-05, with screenshots of ours vs a native Win11 titlebar):

> "the minimize/restore/close buttons at the top right do not match the
> windows 11 look and feel. This makes the app seem off. They should match the
> windows design language. ... The header should feel native with the correct
> height and buttons, icons used within should feel native. We can take
> creative liberties with border styles and such (for banners we have a very
> nice border and shadowing that I think we should keep.)"

The current treatment was a DELIBERATE T254 decision, documented in
`caption_layout.zig`: the trio paints the same 28 DIP rounded square as the
strip's "+"/hamburger, on the theory that "Windows' own caption buttons are
46x32 px slabs; matching that would put two button vocabularies one row apart
in the same window." The user has now seen both and overrides that theory: the
system trio reads as NOT-Windows, which is worse than two vocabularies. Edge
and Explorer themselves ship the split we are moving to - their own controls
("...", tab close) get small rounded hovers, while the system trio is native
full-height slabs.

## In plain terms

The minimize, maximize and close buttons in the top-right corner look like the
app's own small rounded buttons instead of the wide flat buttons every other
Windows 11 window has, so the whole app reads as slightly "off" and non-native.
When this lands, those three buttons look and behave exactly like the ones in
File Explorer or Edge — full-height, flush to the corner, red close hover —
while the app's own "…" menu button keeps its rounded style, which is the same
split Microsoft's own apps make.

## Goals

- [x] The three system buttons are 46 DIP wide, span the full caption height, and sit flush to the window's top-right corner with no gaps between them
- [x] Hover/press fills are full rectangular slabs (close hovers Windows red with a white glyph; min/max shade the bar color)
- [x] The standalone caption band is the native 32 DIP height; merged mode keeps the strip's height with slabs spanning it
- [x] The app's "…" button keeps the 28 DIP rounded-square treatment
- [x] Snap Layouts (HTMAXBUTTON) still works
- [x] The design system documents the trio as a named platform exception

## The native contract (what to build)

- Minimize / maximize-restore / close are **46 DIP wide, full band height,
  flush to the window's top and right edges, zero gaps** between them - the
  Fitts corner really is painted close now, not just hit-tested close.
- **Rectangular hover/pressed fills** covering the whole slab (square corners,
  no inset). Min/max shade the bar color (existing `fillDelta` +-15/25);
  close hovers `danger` #C42B1C with a white glyph (already the rule).
- Standalone band height goes 36 -> **32 DIP** (native Win11 caption height);
  merged mode keeps the strip's `bar_h` with the slabs spanning it full-height
  (what Windows Terminal does).
- The app's own "..." overflow button KEEPS the 28 DIP rounded-square
  treatment - it is our control, not the OS's; that split is itself the native
  pattern.
- `HTMAXBUTTON` (Snap Layouts) already works and must keep working.

## Where

`caption_layout.zig` (metrics + layout + tests re-pinned to the native
contract), `Window.zig` `paintCaption`/`paintCaptionRedFill` (rectangular slab
fills), `docs/design/win32-design-system.md` (the trio becomes a NAMED
platform exception to the 28-square/4-gap rules), and
`test/win32/caption-bar.ps1` (band height + geometry assertions).

Glyph thinning (Segoe Fluent Icons) is T497; the two land separately but were
one user report.
