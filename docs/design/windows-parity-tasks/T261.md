# T261 - reset-context false-FAILs: the 25-line tail probe misses a continuation the model is already processing

## In plain terms

When this project's automation restarts a Claude session and hands it its next
instruction, it checks afterwards that the instruction really arrived. The
check looked for the instruction's text still sitting on screen — but a session
that answers quickly scrolls its own prompt out of view within a second, so the
check kept announcing "RESET-CONTEXT FAILED" over resets that had worked
perfectly, and pasted a red "recover this by hand" banner across the pane.
Anyone watching saw a broken loop that was not broken; worse, a failed reset is
the one thing the automation is allowed to stop and ask a human about, so a lie
here can stall everything. Now the check accepts either proof that the
instruction landed — the prompt being visible, or the session visibly working —
and only complains about a pane that is silent, blank and doing nothing.

## Goals

- [x] Stop reporting failure when the session is visibly processing the prompt
- [x] Failure text describes what was observed, not a cause nobody watched
- [x] A genuinely undelivered continuation still fails loudly
- [x] Same fix in the marketplace source repo and the active plugin cache

## Summary

**The loop's own step 7 reports failure on a reset that fully succeeded**, and
tells the user to go fix it by hand. Found 2026-07-31 as a live banner sitting
on the go-loop pane at the start of a turn.

`/reset-context` cleared the session, typed the continuation, submitted it, and
the fresh session started working on it — and then the script declared:

```
!!! RESET-CONTEXT FAILED: the continuation text never appeared in the pane
```

and painted a sticky banner reading *"Recover by hand: press ctrl+u, run
/clear, then re-send the prompt."* Nothing was broken.

## Evidence

`%TEMP%\reset-context-last.log`, 2026-07-31 21:08:53 - 21:09:10. Every step
before the verdict reports success, including the app's own oracle for the
hard part:

```
21:09:05 verified: /clear landed (nothing left on screen)
21:09:06 typed continuation (424 chars) rc=0
21:09:07 submitted continuation rc=0
21:09:09 !!! RESET-CONTEXT FAILED: the continuation text never appeared
```

The script dumps the pane tail with the failure, and the dump is what settles
it — the session is mid-response:

```
| . Frolicking...
| ------------------------------------------------------------->
| ------------------------------------------------------------  ctx: 0k/1000k (0%) | ... (Opus 5)   /rc
|   users/dzearing/windows-amd64 | D:\git\ghoztty
```

`ctx: 0k/1000k` is a freshly cleared context and `Frolicking...` is the model
working. The continuation arrived, was submitted, and was being processed at
the exact moment the script said it never appeared.

## Root cause

`skills/reset-context/scripts/reset-context.sh` (dzearing-claude-marketplace),
the block after `submitted continuation`:

```sh
PROBE="$(head -1 "$C" | tr -d '\r' | cut -c1-24)"
sleep 2
if [ -n "$PROBE" ] && ! ghoztty +read --name="$P" --lines=25 2>/dev/null | grep -qF "$PROBE"; then
  fail_loud "the continuation text never appeared in the pane"
```

The oracle is "the first 24 chars of the continuation are in the last **25**
lines". That is only true in the narrow window between the prompt being echoed
and the model producing output. Once it starts responding, Claude Code's TUI
fills the bottom of the pane with the spinner, the two rules and the status bar
— and the tail dump above shows nine blank lines before those — so the echoed
prompt has scrolled out of a 25-line window. A 424-char continuation wraps to
several lines, pushing it out sooner.

So the probe is racing the model, and it loses whenever the model is quick. The
`sleep 2` makes losing MORE likely, not less.

## Why it matters beyond the noise

The banner instructs a recovery that is not needed, and the loop protocol
treats a failed reset as the one case where a turn stops and asks the user
(go.md's "one allowed exception"). A false FAILED can therefore stall the loop
in exactly the way step 7 exists to prevent — the failure mode T139/T241 were
filed for.

## The fix

Do not probe for text that is designed to disappear. Options, best first:

1. **Ask the pane what its context is.** The status bar the tail already
   captures carries `ctx: 0k/1000k` — a cleared, re-primed session. Verifying
   the CLEAR (already done, and reliable) plus "the session is alive and
   working" is the real postcondition; the prompt's visibility is not.
2. **Widen and re-try the read** (`--lines=200`, poll for a few seconds)
   instead of one 25-line shot after a fixed sleep. Cheap, but still racing.
3. **Accept a busy pane as success**: if the tail shows the model working
   (spinner / non-zero elapsed), the continuation landed by definition — an
   idle pane with an empty input box is the only real failure.

Whatever is chosen, `fail_loud` must stop claiming a specific mechanical cause
it did not observe.

## Validation

- A `/reset-context "<long prompt>"` on a fast-responding session logs
  `verified:` rather than `RESET-CONTEXT FAILED`, and paints no failure banner.
- Repeated 3x, including one continuation > 400 chars (the case that failed).
- A genuinely broken reset (e.g. point it at a pane with no Claude session)
  still fails loudly - the negative control.
- Fix lands in the dzearing-claude-marketplace source repo AND the active
  plugin cache version, per the standing "patch skills in both places" rule.

## What landed (2026-08-04)

`skills/reset-context/scripts/reset-context.sh`, the block after
`typed+submitted continuation`. The single 25-line read after a fixed `sleep 2`
is replaced by a poll that accepts **either** proof of delivery — option 2 and
option 3 of "The fix", together, because each covers the other's blind spot:

- **first sample is immediate** (no sleep) and reads `--lines=60`, so the
  echoed prompt is caught before the spinner and status bar push it out. This
  is what a >400-char continuation needed: it wraps to ~4 lines, and 25 lines
  of tail is mostly TUI chrome.
- **then up to 10 one-second samples**, and a tail that *changed* between two
  samples is success in its own right — a repainting pane is a session
  working on the continuation, which is delivery by definition.
- **failure is now the pane that proves nothing landed**: never echoed the
  prompt and never repainted for 10s. Its message states exactly that and
  hedges the conclusion ("may not have been submitted") instead of asserting
  the mechanical cause of option-1's old text.
- `fail_loud`'s dump widened 15 → 40 lines (15 was too narrow to show the
  `ctx:` line and spinner that settle it), and its banner now says to read the
  log first — a session showing `ctx: 0k` and a spinner needs no recovery.

Synced to `…\plugins\cache\dzearing-claude-marketplace\dzearing-skills\0.11.0\…`
(the version `installed_plugins.json` reports as active); `bash -n` clean.
