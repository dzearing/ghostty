# T372 - T90d1: WebView2 COM ABI floor + loader-less runtime probe + shared environment

## Summary

src/apprt/win32/webview2.zig: hand-declared COM primitives (GUID/IUnknown/HRESULT, a reusable Zig-side callback-object helper with vtable+refcount), the loader-less Evergreen runtime probe (HKLM WOW6432Node + HKCU EdgeUpdate client key, pv version parse/compare, install-dir join, LoadLibraryW EmbeddedBrowserWebView.dll, CreateWebViewEnvironmentWithOptionsInternal), and the ONE shared ICoreWebView2Environment per app with UDF %LOCALAPPDATA%\ghoztty\EBWebView[-debug]. Every step degrades to a typed error, never a crash (T90a design 1). No window, no controller, no IPC.

## Details

*Validation:* `zig build test -Dapp-runtime=none` (the pure path/version math),
`zig build test -Dapp-runtime=win32` (the COM vtable, the probe, and a LIVE
environment created on this box), `zig build test-agent`, P1-P3 ALL PASS.

### Done 2026-08-02

Two modules, split on the line the house pure modules use.

**`webview2_paths.zig` (pure, none lane).** Version parse/compare, the client
DLL join, the `location + pv` join, the user-data folder, last-path-component.
Everything works in UTF-8; `webview2.zig` converts at the registry and
`LoadLibraryW` boundaries, which is what keeps this module free of OS imports
and lets the none lane compile it alongside `tab_strip_layout.zig` and friends.

**`webview2.zig` (win32 lane).** The probe, the COM declarations, the completed
handler we implement, and the `Host` that owns the one shared environment.

Five things this turned up that are worth carrying forward.

**1. The design's registry key is not the one the reference loader uses, and
both are on this box.** T90a §1 pinned `EdgeUpdate\Clients\{guid}` (`pv` +
`location`, joined). `webview/webview`'s loader reads
`EdgeUpdate\ClientState\{guid}` value `EBWebView`, which is *already* the
versioned directory. Measured here: `Clients` has
`pv = 150.0.4078.105` and `location = ...\EdgeWebView\Application`; `ClientState`
has `EBWebView = ...\EdgeWebView\Application\150.0.4078.105`. Both are read,
`ClientState` first, each under HKLM then HKCU. Reading only the design's key
would have worked on this box and silently failed on one that has the other.

**2. `KEY_WOW64_32KEY`, not a hardcoded `WOW6432Node`.** EdgeUpdate writes the
32-bit view. Spelling `WOW6432Node` into the path string is correct on a 64-bit
box and wrong on a 32-bit one; the flag is correct on both, and it is one
character of policy instead of a branch.

**3. A client key that EXISTS is not a runtime.** EdgeUpdate leaves the key
behind after an uninstall with `pv = 0.0.0.0`, so the probe parses the version
and tests `usable()` rather than testing for the key -- and then `access()`es
the client DLL, because a registry entry pointing at a deleted install is
exactly as useless as no entry. `Version.usable()` has its own unit test naming
this.

**4. The undocumented ABI is now proven, not assumed.** The signature is
`(bool, webview2_runtime_type, PCWSTR userDataFolder, IUnknown *options,
handler *)` -- five parameters, and notably **no browser directory**: the DLL
knows where it lives, which is why loading it by full path IS "pointing at a
runtime". The test that proves it drives the entire chain (registry ->
`LoadLibraryW` -> `GetProcAddress` -> the internal export -> our completed
handler -> a live COM object) and then asks the environment for its own
`get_BrowserVersionString`, asserting it equals what the registry advertised:
`150.0.4078.105`. A guessed calling convention or a transposed parameter cannot
survive that. It also pins a fact T373 needs: creating an *environment* starts
no browser process -- no `msedgewebview2.exe` appears and the user-data folder
stays empty. The process arrives with the controller.

**5. The skip is loud.** The live test necessarily degrades to "no runtime
here" on a box without one, and a quiet skip is how a test reports success for
work it never did. It logs `SKIPPED live environment test` at **warn**, and the
first run of this turn is the reason: it passed while the user-data folder was
empty, which read exactly like a silent skip until the log said otherwise.

The runtime-absent branch is reachable on a box that HAS the runtime, via
`GHOZTTY_WEBVIEW2_BROWSER_DIR` -- when set, it IS the runtime and the registry
is not consulted, so pointing it at nowhere is a faithful drill. It mirrors the
runtime's own `WEBVIEW2_BROWSER_EXECUTABLE_FOLDER` and the `GHOSTTY_HOST_DEFAULTS`
idiom.

The `Host` is a small state machine (`idle -> creating -> ready|failed`) with a
waiter list, because creation is async and T373's panes will each ask mid-flight.
`drain` takes the list before walking it: a waiter is free to register another
(a split opened from a viewer's own ready callback), and appending to a list you
are iterating is how that becomes a crash. Asserted.

**One thing in the summary above did NOT land, deliberately: T376.** The
summary promised "a reusable Zig-side callback-object helper"; what shipped is
one concrete handler. Generalizing off a single instance is guessing at the
shape, and the second handler does not exist yet. T376 factors it out before
T373's four arrive, with `EnvCompletedHandler`'s existing vtable test as the
regression oracle -- which is the right moment, not after the fifth copy.
