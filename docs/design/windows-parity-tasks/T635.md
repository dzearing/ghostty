# T635 - Viewer feedback: the composer becomes a real text control (D43)

## In plain terms

The Windows feedback box looks right but does not behave like a text box: there
is no caret you can move, no selection, no copy/paste, no undo, and typing
Japanese or Chinese does not work at all — every keystroke is simply appended
to the end. This task makes it a real editable field, so writing a report feels
like writing anywhere else on Windows.

## Summary

Third of the T384 split, and the half that answers D43. T634 shipped the
composer's CHROME over a deliberately minimal editing surface: a plain UTF-8
buffer, appended by `WM_CHAR`, with backspace and newline and nothing else. This
task replaces that whole editing path with a real text control — caret,
selection, mouse selection, word wrap, undo, clipboard, and IME composition —
while the geometry, the paint, the open/close lifecycle and the pane's reflow
all survive the swap, exactly as T634 promised they would.

**Quote insertion moved to T641** (2026-08-08). The task as filed carried two
halves, the editing surface and the quoted block; they are sequential (a Quote
button needs somewhere to put text) and each is a turn's worth of work with its
own tests, so the second half is now its own task, dep-linked to this one.
`viewer_bridge.hide_quote_js` therefore stays until T641.

## Details

**The control is D43**, which is still open; this task proceeds on its
recommended option, **RichEdit (`MSFTEDIT.DLL`) hosted as a child of the
composer band**. What that buys is precisely what cannot be hand-rolled
correctly: caret and selection, word wrap, undo, drag-drop, clipboard, and IME
composition, all from the OS, plus text to screen readers. What it costs is
styling we do not own — the control paints itself, so the quote block's tinted
panel and accent bar (T641) have to come from a reserved gutter or from parent
painting under a transparent control.

Rules the swap must keep:

- **The text lives on the PANE, not on the bar window.** Mac is explicit that
  composer contents survive toggling the toolbar closed and open again, and the
  natural win32 mistake is to keep the buffer in the child window, where it dies
  with the window. `pane.feedbackText()` stays the way everything else reads it.
- **The pill still grows with its content**, one line to six, and the pane
  re-insets the page as it does. That means the line count now comes from the
  control's wrapped line count, not from counting `\n` in a buffer.
- **The band's theme still derives from the pane's background** in one place.
  RichEdit needs its background set explicitly (`EM_SETBKGNDCOLOR`) and its
  text colour through a default `CHARFORMAT2`; neither may become a second
  source of colour truth.
- **Ctrl+Enter sends and Escape closes** — a multi-line RichEdit swallows both,
  so they route through the main message loop the way the address field's
  Enter/Escape already do (`App.zig`, `ViewerNavBar.owningEdit`).

## Validation criteria

- [ ] The composer hosts a real text control: caret navigation, mouse and
      keyboard selection, and word wrap all work; typing no longer only
      appends.
- [ ] The standard editing chords work inside the composer: Ctrl+A select all,
      Ctrl+C/X/V copy/cut/paste, Ctrl+Z undo.
- [ ] Composer contents still survive closing and reopening the toolbar, and
      the pill still grows with its content and shrinks back.
- [ ] Ctrl+Enter still sends and Escape still closes from inside the control.
- [ ] Both zig test lanes + `zig build test-agent` green, P1-P3 ALL PASS.
