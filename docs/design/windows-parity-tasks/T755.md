# T755 - A CLI verb can hang FOREVER against an app that is still starting up (+list waited 34 min); P1's first section fails on a cold auto-launch

## In plain terms

A `ghoztty` command typed at a shell can sit there forever with no output and
no error, if it happens to run while the app it is talking to is still coming
up. Nothing tells the user what it is waiting for, and Ctrl-C is the only way
out. It should either answer or give up and say why.

## Summary

MEASURED during T528's turn (2026-08-11), not inferred. `test\win32\ipc-p1.ps1`
was launched at 11:48:28; at 12:22 - **34 minutes later** - a
`ghoztty.exe +list` child (pid 51480, started 11:48:29) was still alive with
0.06 s of CPU, i.e. blocked, not spinning. The app it was addressing (pid
39500) had auto-launched in the same second and was alive and rendering.

Two separate consequences, both worth fixing:

1. **The CLI has no timeout on this path.** A verb that cannot get an answer
   should fail with a sentence, not block indefinitely. A user who types
   `ghoztty +list` while the app is still starting gets a dead terminal.
2. **P1's first section then fails on a cold auto-launch.** The same run
   scored 3 failures - `exit 0`, `window registered under target`, `title
   override shows` - all in the FIRST `+new-window` section, with every later
   section passing. A clean re-run was ALL PASS. So the failure is a race
   against the app's own startup, and it reads as a real regression to whoever
   runs the floor next.
3. **A hung child holds the caller's stdout open**, which is why the harness
   invocation appeared to hang for 34 minutes after the script had already
   printed its verdict (`| Select-Object -Last 1` waits on every writer to the
   pipe). That is the known GUI-inheriting-stdout shape, here caused by an
   orphaned CLI rather than a GUI.

Where to look: `src/os/ipc_client.zig` (connect/read on the named pipe -
`WaitNamedPipe` and the read after it), and whatever the auto-launch path in
`src/cli/` waits on after spawning the app.

## Goals

- [x] No CLI verb can block indefinitely on the app.
- [x] The failure names the verb, the phase, and the way to wait longer.
- [x] A slow start reads as slow, not as a hung terminal.
- [x] A cold auto-launch no longer loses P1's first section.

## Validation criteria

- [x] A CLI verb whose peer never answers fails within a bounded time with a
      message naming what it was waiting for, on both the connect and the read.
      *Section A of `test\win32\ipc-timeout.ps1`: a wedged peer + a 2s bound
      exits nonzero in 2.1s naming `+list`, `get a response from`, and
      `GHOZTTY_IPC_TIMEOUT_MS`. The connect side was already bounded (a missing
      pipe fails immediately; `PIPE_BUSY` is capped at 10 x 1s), and the write
      side goes through the same bounded path (`.request` phase, asserted in
      the `none` lane).*
- [x] The bound is exercised by a test that does not depend on timing luck: a
      fake/wedged server (the `ipc-fake-server.ps1` idiom) that accepts and
      never replies.
      *`ipc-fake-server.ps1 -Wedge` (new) accepts, reads the request and
      answers nothing, forever - the peer is wedged by construction. Section C
      is the replying control, so A is measuring the wedge rather than the
      bound firing on everything. The harness caps the CLI itself, so a
      regression of the bound FAILS the script instead of hanging it.*
- [x] `ipc-p1.ps1` passes from a COLD box (no app running, no warm pipe) -
      the state that produced the 3 failures - repeated enough times to say the
      race is closed rather than un-hit.
      *6 consecutive runs, ALL PASS (25 assertions each), the first of them
      against a just-rebuilt exe (the Defender-cold case). P2/P3 ALL PASS.
      Mechanism, not just repetition: the auto-launch budget went from 20 fixed
      500ms attempts (10s) to a 30s deadline that also watches the launched
      process, so a slow start is waited out and a dead one is answered at
      once.*

## Evidence

- `test\win32\ipc-timeout.ps1` - ALL PASS (23 assertions).
- `test\win32\ipc-p1.ps1` x6, `ipc-p2.ps1`, `ipc-p3.ps1` - ALL PASS.
- `zig build test -Dapp-runtime=none` / `-Dapp-runtime=win32` /
  `zig build test-agent` via `scripts\floor-lane.ps1 -Lane all` - PASS.

## What changed

- `src/os/ipc_timeout.zig` (new, pure, asserted in the `none` lane) - the
  policy: 30s default bound, a 5s "still waiting" notice,
  `GHOZTTY_IPC_TIMEOUT_MS` (0 = forever, garbage = the default, never
  forever), the two phase names, and the auto-launch budget.
- `src/os/ipc_client.zig` - the client's pipe is opened
  `FILE_FLAG_OVERLAPPED` and every read/write carries a cancellable
  OVERLAPPED; posix gets the same bound from `SO_RCVTIMEO`/`SO_SNDTIMEO`.
  `exchange` splits the response wait into notice + remainder and prints the
  timeout sentence.
- `src/apprt/win32/App.zig` - the `+new-window` auto-launch wait is a deadline
  that watches the launched process instead of a fixed attempt count.
- Bug found and fixed mid-flight: `timeout_ms == 0` had been conflated with
  "synchronous handle", so the documented opt-out handed an overlapped handle
  to a synchronous `ReadFile` and wedged. Split into `Conn.owned` (we opened
  it) and `Conn.timeout_ms` (how long). Section D of the acceptance script is
  the arm that caught it.
