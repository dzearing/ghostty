# T1149 - No acceptance script can press a shortcut that uses the Windows key, so nothing guards those defaults

## In plain terms

A lot of Ghoztty's built-in shortcuts use the Windows key — moving a pane
divider is ctrl+win+arrow, moving focus between panes is win+alt+arrow. No
automated test can press those, so if one of them broke, nothing here would
notice until somebody tried it by hand. The first job is to find out whether
they actually work at all.

## Summary

Measured while validating T1129 (2026-08-23). The off-desktop test harness
drives keyboard shortcuts by posting `WM_KEYDOWN` with the modifier state faked
through `SetKeyboardState` (`test/win32/lib/TestDesktop.ps1`, `SendChord`).
Every non-super chord resolves this way — `ctrl+shift+e` opened a split in the
probe, and `ctrl+shift+alt+arrow` drove the whole T1129 acceptance. Three
super-modified chords in a row did nothing at all: `win+ctrl+right` and
`ctrl+win+right` (`resize_split`) and `win+alt+left` (`goto_split`), all posted
at the same window, with `SendChord` reporting success and the layout
unchanged.

`ApplyMods` sets `ks[0x5B]` (VK_LWIN) exactly as it sets the ctrl/shift/alt
pairs, and `Surface.zig`'s `keyMods()` reads `GetKeyState(VK_LWIN)`, so on
paper it should work. Two possibilities, and the task is to tell them apart
before fixing anything:

1. **Harness.** Windows does not honour a faked VK_LWIN through
   `SetKeyboardState` the way it honours the other modifiers, so no posted
   chord will ever carry `super`. Then the fix is a different injection route
   for these chords (or an explicit, documented inability, with the affected
   defaults listed).
2. **Product.** `super` never reaches the binding lookup on a real keypress
   either, and every Windows-key default shortcut is dead for users too. That
   is a P0 the moment it is confirmed.

T1129's acceptance works around it by binding the actions under test to
`ctrl+shift+alt+arrow` for that run, which tests what `resize_split` DOES but
not the chord that reaches it.

## Validation criteria

- [ ] The two possibilities above are told apart by evidence, and which one it
      is is written into this file.
- [ ] If it is the product: a fix, plus an acceptance assertion that a
      super-modified default resolves.
- [ ] If it is the harness: a chord route that carries `super`, used by at
      least one acceptance assertion over a shipping Windows-key default —
      or, if no route exists, the limitation documented in
      `test/win32/lib/TestDesktop.ps1` beside `SendChord` and the unguarded
      defaults listed here.
- [ ] `test\win32\split-divider.ps1` still ALL PASS.
