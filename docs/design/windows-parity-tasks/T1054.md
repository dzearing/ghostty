# T1054 - Nothing evicts the build cache, so the repo drive fills up and every lane fails with a bare 'error: Unexpected'

## Summary

On 2026-08-21 D: hit exactly 0 bytes free. `.zig-cache/o` held 31,359 entries
totalling 1,235 GB, none older than 30 days - roughly 40 GB of build output a
day that nothing ever evicts. Every floor lane died in 5s with a bare
`error: Unexpected` from zig, which reads as red code and is not.

## In plain terms

The machine quietly ran out of disk because the build cache had grown to 1.2
terabytes and nobody was ever deleting any of it. What that looks like from the
inside is worse than an out-of-disk message: every test lane fails in five
seconds saying `error: Unexpected`, which looks exactly like the code being
broken. A turn can burn its whole context chasing a compiler error that is
really a full drive. It needs to be cleaned on a schedule, and when the drive
is nearly full the loop should say so in those words.

## Details

Root cause is Zig's cache design plus this project's build frequency: every
distinct build hash keeps its full output in `.zig-cache/o/<hash>/`, and a debug
`ghoztty.exe` is 48 MB with a 100 MB `.pdb` beside it. Four floor lanes several
times a day, plus acceptance builds and the upgrade/staging builds, is ~40 GB a
day. Zig never evicts, and nothing in this repo did either - `scripts/lib/
CacheHeal.ps1` (T494) deletes a *torn* entry, which is a correctness fix, not a
size cap.

The manual remedy this turn went in two steps. First an age prune - the 28,369
entries in `.zig-cache/o` older than 3 days, 1,082 GB recovered - which
immediately exposed the trap in pruning `o/` alone: Zig's manifests in
`.zig-cache/h/` still recorded those outputs as hits, so the very next lane
failed with `failed to spawn build runner .zig-cache\o\<hash>\build.exe:
FileNotFound`. **An age prune is only safe if the manifest side is invalidated
with it.** The user's call on seeing that (2026-08-21): *"clear it completely
and start fresh if this is just build artifacts"* - so `.zig-cache` was removed
whole, taking the drive from 0 to 1,238 GB free, and the floor was re-run cold.

That directive settles the design question below: prefer wholesale clearing on
a cadence over clever partial eviction. A cache that is entirely regenerable
does not need a subtle policy, and the subtle policy is what produced the
dangling-manifest failure.

Design (settled, so the next turn builds rather than re-derives):

1. **Clear on a schedule the loop already has.** `scripts\go-loop-exec.ps1
   claim` runs once per turn and already reports box state (guards, stranded
   work, boot outages), so it is where this belongs: when the cache is over its
   ceiling, delete `.zig-cache` whole and print one line saying what was
   reclaimed. Whole, not partial - per the user's directive above, and because
   the partial prune's dangling manifests are a failure mode that costs a turn
   to diagnose. If a future version does prune by age, it MUST drop `h/` in the
   same pass.
2. **Only when it is worth doing.** A cold rebuild is the price, so do not pay
   it every turn: trigger on free space below a threshold or cache size above a
   ceiling, and answer the common case with one cheap size check rather than a
   30k-directory stat sweep.
3. **A free-space preflight that names the cause.** `scripts\floor-lane.ps1`
   should check free space before launching a lane and fail with "D: has N MB
   free - the build cache needs pruning" instead of relaying zig's
   `error: Unexpected`. That message is what cost this turn its detour, and it
   is the same class of fix as T243's `GlobalCacheOnDifferentDrive`: when the
   environment is the fault, say so in the error.
4. **The other drives too.** `zig-out-t473`, `zig-out-t206`, `zig-out-t229old`,
   `zig-out-prof`, `zig-out-release`, `.dumps` and the `t508-*` scratch dirs
   under `.zig-cache` are all leftovers from finished tasks (~3 GB). Sweep or
   report them; do not delete anything outside a cache without asking.

## Goals

- [x] The build cache is cleared automatically, on a cadence the loop owns
      (`go-loop-exec.ps1 claim` -> `build-cache.ps1 sweep`)
- [x] A near-full repo drive is reported in those words, before a lane runs
      (`floor-lane.ps1` pre-flight, 10 GB floor, remedy printed)
- [x] The prune is bounded in cost, so an ordinary turn does not pay for it
      (free space is O(1); the entry count is one non-recursive enumeration)
- [x] Stale per-task scratch dirs are reported rather than left to accumulate
      (reported, never deleted; resolving the eight of them is T1062)

## Validation criteria

- [x] A fixture cache over its ceiling is cleared, and one under it is left
      alone, verified by an acceptance script section --
      `test\win32\build-cache.ps1` sections B and C (C2-C4 clear, C5-C7 leave
      alone), ALL PASS (50 assertions); `-NegativeControl` goes red on C5
- [x] With free space below the threshold, `floor-lane.ps1` fails with the
      disk-space message and never launches zig -- section D. D6 proves the
      "launched nothing" claim by counting lane logs in `$env:TEMP`, and D0 is
      a positive control on that counter (a sentinel named like a lane log must
      be seen), so the check cannot pass by looking where nothing is ever
      written
- [x] A claim on a healthy box adds no measurable time (no full walk when the
      cache is under its ceiling) -- measured at **4-5 ms** for the state of
      both real caches (E5 asserts under a second); `build-cache.ps1 sweep`
      end to end including PowerShell startup was 224 ms
- [x] After a clear, the four floor lanes come back green from cold, and the
      turn after that builds incrementally again -- the cold run after this
      morning's manual clear was green, and this turn's re-run of all four
      lanes against the incremental cache was green again:
      `lib#1=PASS none#1=PASS win32#1=PASS agent#1=PASS`
