# T481 - +read on macOS still reports an empty pane as a failure (the T181 half the Windows seat cannot validate)

## In plain terms

Asking Ghoztty to show you what a terminal has printed answers with an error
when the terminal has printed nothing yet — which is exactly what every
terminal looks like for the first moment after you open it, and permanently if
whatever is running in it is quiet. The error reads the same as "that terminal
doesn't exist", so a script or an AI agent watching a pane can conclude the pane
is broken when it is simply new. Windows was fixed on 2026-08-04; the Mac still
does it.

## Goals

- [ ] An empty pane answers `+read` with success and empty text on macOS
- [ ] The remaining `+read` failures each name a different state
- [ ] `+send-keys` splits "died" from "never started" the same way
- [ ] A macOS check that reproduces before the fix and passes after

## Summary

Filed by **T181**, which fixed this on the win32 seat. The defect is in the
SHARED contract, and the Swift handler has its own copy of it:

`macos/Sources/Features/IPC/IPCServer.swift` (`+read`):

```swift
if resultText.isEmpty {
    return IPCResponse(success: false, error: "failed to read terminal content from '\(name)'")
}
```

A pane that has printed nothing dumps an empty screen, so this reports a
perfectly readable pane as a failure — with a message a caller cannot tell
apart from "no such pane", "the pane is wedged", or "the app is broken". It is
also transient on a brand-new pane (the window is registered, and `+list --json`
already reports its pane id and its child's pid, before the shell paints a
prompt), which is what makes it dangerous: an agent that reads once and believes
the answer records "the pane produced no output" as a product verdict.

Measured on Windows before the fix, with the same command shape:

```
+new-window --target=silent -e cmd /c "timeout /t 20 /nobreak > nul"
+list --json  ->  pane id present, pid 24376
+read --name=<id> --lines=5  ->  exit 1, "failed to read terminal content from '<id>'"  (x3)
```

## Why this is not already done

The win32 seat cannot compile or run Swift, and CLAUDE.md's rule is to land both
halves or file the other seat's. Deleting the `isEmpty` branch alone would ALSO
swallow the `guard let surface = surfaceView.surface else { return }` failure
above it into a silent empty success (both funnel into the same empty
`resultText`), so this needs a small restructure that separates "nothing to
read" from "nothing to read WITH" — which is the part that wants compiling and
running, not guessing.

## What Windows landed, to mirror

1. **Empty is an answer.** `+read` returns success with empty text — `tail` of
   an empty file exits 0.
2. **Every remaining failure names a distinct state**: `not found in registry`,
   `is no longer alive`, `is a viewer pane, not a terminal`, `is not readable:
   its terminal never finished starting up` (the surface never completed init,
   as opposed to having died), and `failed to read terminal content` — now
   reserved for a genuine internal failure to serialize the screen.
3. **`+send-keys` got the same liveness split** (`is not writable: its terminal
   never finished starting up`), because the `/reset-context` helper aims it at
   a freshly created pane.
4. **The "last N lines" rule is now shared, pure and tested**:
   `src/apprt/ipc/read_tail.zig` (`-Dapp-runtime=none` lane). The Swift side
   applies the same rule with `components(separatedBy:)` + `suffix(n)`; keep the
   two agreeing by description, and prefer calling the Zig rule if the bridge
   makes that cheap.

Note for whoever takes this: **T193** (`+read` on the alternate screen) turned
out to be THIS defect wearing a TUI costume — a bare `ESC[?1049h` alt screen
dumps empty, and the `isEmpty` branch converts that into the blanket failure.
On Windows the T181 fix made the alt screen behave correctly with no further
code: `+read` on an alt-screen pane returns the **visible screen** (the dump
reads `screens.active`), and recovers the primary scrollback on `ESC[?1049l` —
verified by arm G of `test/win32/ipc-read-race.ps1` (2026-08-06). So when you
fix the `isEmpty` branch here, **include an alt-screen arm in the macOS
validation**: enter `ESC[?1049h`, assert `+read` exits 0 with the visible
screen (not the primary marker), leave with `ESC[?1049l`, assert the
scrollback returns. Detect phases by child-printed markers, never by a failing
read (the T190 lesson).

## Validation

A macOS check that creates a pane running something silent (`sleep 20`), asserts
`+list --json` reports it with a real pid, and asserts `+read` on it exits 0
with empty output — plus controls that an unknown name, a viewer pane, and a
pane with real output all still behave. The Windows form of exactly this is
`test/win32/ipc-read-race.ps1`, whose arm A reproduced the defect (2 FAILURE(S))
against the pre-fix build and passes after.
