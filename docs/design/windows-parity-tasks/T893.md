# T893 - No external trigger can drive a config reload: no IPC action, no CLI path, menu returns in-process

## In plain terms

There is no way for a script or agent to tell a running Ghoztty window
"re-read your config file". A person can click Reload Configuration in the
menu or press the shortcut, but automation cannot — and neither can our own
tests, which means everything that happens on a config reload (fonts,
colors, tooltip themes, dividers) goes unverified by the harnesses.

## Summary

Found while validating T557. The win32 app reaches `reload_config` three
ways, all interactive: the menu bar (command comes back in-process from
`TrackPopupMenuEx` with `TPM_RETURNCMD` — never a postable `WM_COMMAND`),
the keybind, and the viewer chord. There is no IPC action for it
(`IpcHandlers.zig` has none; `+reload` is the VIEWER reload verb, T390),
so T557's harness section F could only score the `WM_SETTINGCHANGE` half
of the tooltip reset — the `onConfigChange` half is one adjacent line but
externally unreachable.

Options for the fix (whoever picks this up decides): an IPC
`reload-config` action surfaced as a CLI flag or verb. NOTE the standing
rule: the CLI surface is identical on both platforms — if a verb/flag is
added it lands on macOS in the same change or a `seat: mac` twin task is
filed with it.

## Validation criteria

- [ ] A script can trigger a hard config reload of a running instance
      (headless, no keyboard/menu)
- [ ] `test\win32\tab-tooltip.ps1` section F regains the config-reload arm
      using it
- [ ] Mac has the same trigger, or a `seat: mac` task is filed and linked
- [ ] Floor lanes + P1-P3 stay green
