# T441 - 22 acceptance scripts drive the USER'S installed Ghoztty: they isolate by USERNAME (or not at all), and the pane's baked GHOZTTY_IPC_SOCKET outranks it

## Summary

Hit live 2026-08-03 while validating T439. `test/win32/upgrade-no-fork.ps1` typed
its section B and E fixture prompts - and E1's `powershell -NoProfile -File
...\swallow.ps1` line - into the go-loop's own live Claude pane, where they
arrived as user messages. The suite believed it was driving a hermetic sandbox.
It was driving the user's installed release, because every CLI call it makes
inherits `$GHOZTTY_IPC_SOCKET` from the pane the suite was started in, and that
baked value outranks the derivation the suite's `$env:USERNAME` override moves.
`upgrade-no-fork.ps1` is fixed here; **21 other scripts have the same hole**,
including the P1-P3 regression floor.

## In plain terms

The test scripts are supposed to run against a throwaway copy of the terminal.
Instead they have been reaching into the terminal the user is actually sitting
in - opening windows in it, typing into it, and closing things in it. One of the
things they type is a command, and it lands wherever the cursor is. Separately,
this means the tests have been checking the copy of the app the user has
installed rather than the one just built, so a passing floor was not evidence
about the new code.

## Goals

- [x] `upgrade-no-fork.ps1` is isolated, and asserts it before it types anything
- [ ] The other 21 instance-driving scripts are isolated the same way
- [ ] Isolation is asserted, not assumed - a script that is talking to the
      caller's own app fails loudly instead of driving it
- [ ] P1-P3 measure the build under test, on a box where a release is installed

## Details

### The mechanism (verified on the box, not inferred)

`src/os/ipc_client.zig` `clientEndpointPathFrom` documents three sources for the
endpoint a CLI dials, in order:

1. an explicit `$GHOZTTY_PIPE_SUFFIX` - "a caller aiming on purpose"
2. the pane's baked `$GHOZTTY_IPC_SOCKET`
3. this build's own derivation, `endpointPath` (which is where `$USERNAME` acts)

Its own comment predicts this incident word for word: *"an acceptance script
inherits the env of the pane it was started from ... every `test\win32\*.ps1`
launched from one of the user's own panes would otherwise inherit the USER'S
endpoint and drive their terminal instead of the build under test."* The rule
is right and implemented; the scripts simply never set the suffix.

`upgrade-no-fork.ps1` overrode `$env:USERNAME` (header: *"own agent pipe
lineage"*) and that IS enough for the agent pipe - but the agent pipe is not the
app pipe, and source 3 never gets consulted while source 2 is present.

Measured in a loop pane (installed release, `GHOZTTY_IPC_SOCKET=\\.\pipe\ghoztty-David`,
no suffix set):

```
PS> zig-out\bin\ghoztty.exe +list --json      # the DEBUG build's CLI
exit=0 ... "title":"[go-loop] ghoztty parity" ...   # answered by the RELEASE

PS> $env:GHOZTTY_PIPE_SUFFIX = "-isotest$PID"
PS> zig-out\bin\ghoztty.exe +list --json
exit=1  No running Ghoztty instance found.          # isolated
```

The first result is the whole defect: a debug-build CLI, run from a pane,
answered by the user's installed release.

### Blast radius

`+send-keys`, `+new-window` and `+split` calls from these scripts land in the
user's live app. Scripts that drive an instance and never set
`GHOZTTY_PIPE_SUFFIX`:

```
agent-recovery, auto-launch-cwd, color-contrast, conformance, go-loop-guard,
gui-launch-command, ipc-p1, ipc-p2, ipc-p3, ipc-relay, ipc-remote,
ipc-send-keys-fidelity, ipc-when-idle, layout-blobs, pane-id, reset-context,
send-keys-bracketed, session-close, session-open, session-relaunch,
target-staleness, wheel-scroll
```

(`upgrade-no-fork` was the 23rd and is fixed.) 64 other scripts DO set it, so
the pattern is established and this is a gap, not a design question.

Two consequences, and the second is the quieter one:

- **Safety.** `+send-keys ... Enter` into whatever pane the fallback picks. A
  fixture that types a command line will run it if that pane holds a shell.
- **Evidence.** go.md's standing floor includes P1-P3. Run from a pane on a box
  with an installed release, they exercise the RELEASE. Every "P1-P3 ALL PASS"
  recorded from such a run is evidence about the installed build, not the one
  under test. That does not mean past results were wrong - it means they were
  not measuring what they claimed.

### Fix shape

`upgrade-no-fork.ps1` (done here) does two things, and both belong in the sweep:

1. sets `$env:GHOZTTY_PIPE_SUFFIX = "-nofork$PID"` beside the existing
   `$env:USERNAME` override, restoring it in the `finally`;
2. **asserts** isolation before typing anything - `B2a`, which looks for the
   CALLER's own `$GHOZTTY_PANE_ID` in the sandbox's `+list --json` and throws
   rather than continue. A suffix that silently stops working must not degrade
   back into driving the user's terminal.

The assert is the part worth generalizing: a shared helper in `test/win32/lib/`
that every instance-driving script calls after it launches its instance, so
"isolated" is a checked property rather than a convention.

## Validation

- `test/win32/upgrade-no-fork.ps1` ALL PASS (2026-08-03, after the fix) with no
  fixture text reaching the caller's pane.
- Per script converted: assert the caller's `$GHOZTTY_PANE_ID` is absent from
  the instance's `+list --json`.
- Re-run P1-P3 with the suffix set and confirm they still pass against the
  freshly built exe.
