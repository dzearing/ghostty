# T913 - The morning refresh delivers the agent too, now that adopting it costs no session

## Summary

`scripts\morning-refresh.ps1` delivers the **app only, never the agent** (T525),
and go.md records exactly why: *"an agent update ends the loop, which is what
the directive rules out"*. The staged agent then waits for a deliberate,
attended delivery — which on this box is rare — so agent-side fixes reach the
user days after they land.

T907 removes the premise. A delivered `ghoztty-agent.exe` is no longer an
interruption: the running agent notices it, hands its holder-backed sessions to
it, and exits. Nothing closes and nothing asks. So the morning refresh can ship
the agent binary like any other file, drop `-AppOnly`'s `AGENT VERIFY SKIP`, and
let the adoption happen on the agent's own schedule minutes later.

Depends on T912 (with holder-backed spawning off, delivering the agent would
just leave it `draining` forever — which is harmless, but buys nothing).

## In plain terms

Fixes to the background session manager currently sit on disk until someone runs
a full update by hand. This lets the ordinary morning refresh carry them, because
picking them up no longer costs you a terminal.

## Goals

- [ ] The morning refresh delivers `ghoztty-agent.exe` alongside the app.
- [ ] The delivery still VERIFIES the agent it wrote (T281's read-back), rather
      than reverting to the `AGENT VERIFY SKIP` the `-AppOnly` path logs.
- [ ] The loop survives it: the refresh does not restart the running agent, and
      the go-loop's session is not interrupted.

## Validation criteria

- [ ] `test\win32\morning-refresh.ps1` covers the agent-carrying path.
- [ ] After a refresh, `+sessions --agent` shows the newly delivered stamp as
      `bundled`, and within one supervisor interval shows it as `running` — with
      the SAME shell pids on either side of it.
- [ ] `test\win32\upgrade-staleness.ps1` section E stays green (the agent
      read-back is not weakened to let this through).
