# T872 - win32 agent integrations (8/8): no end-to-end acceptance coverage - sandboxed install/uninstall/rollback/refusal script for the whole agent-integration flow

## In plain terms

The final slice: a repeatable on-box test that proves the whole
agent-integration feature works end to end — install, update, remove,
graceful refusal — without ever touching the real user's agent
configuration. This is what keeps the feature honest after every future
change.

## Summary

Eighth slice of the T598 split: `test\win32\agent-integrations.ps1`
following the harness rules in `docs/claude/testing.md` (BuildMode refusal,
TestDesktop where GUI is driven, single ALL PASS / N FAILURE(S) verdict,
positive controls).

Sandboxing model: every path the subsystem touches must be overridable to a
temp sandbox (home dir override env var, or the components' existing test
seams surfaced through a hidden CLI/env hook) — the suite must NEVER read or
write the real `%USERPROFILE%\.claude`. Fake `claude.exe`/`copilot.exe`
stubs on a prepended PATH drive the probe and the migration's
`plugin uninstall` call (stub logs its argv for assertion).

Scenario floor (each is one lettered section):

- A: fresh install for Claude — skills, scripts, hooks all land marked;
  settings.json merge preserves pre-seeded user hooks.
- B: idempotence — second install byte-identical, reports up-to-date.
- C: staleness — doctored marked file → update refreshes it.
- D: refusals — unmarked same-named skill; unparseable settings.json;
  reparse-point at a destination. Nothing altered, typed errors surfaced.
- E: rollback — induced failure on the last component leaves no partial
  install, and a pre-existing component survives the rollback.
- F: shared banner refcount — both agents installed; removing one keeps the
  scripts, removing both clears them.
- G: uninstall exactness — user-added files in skills/ survive.
- H: migration — fake plugin registration + state files: uninstall invoked,
  state carried, stale script handled per T870's ownership rules.
- Register the harness in `scripts\guard-due.ps1`'s coverage table mapping
  the new `src/apprt/win32` integration modules to this script — that row
  is the T783 contract and is NOT optional.

## Validation criteria

- [ ] The script runs green on this box against the Debug build, prints one
      ALL PASS verdict, and refuses a release build (BuildMode guard).
- [ ] Every section above present with at least one positive control
      (deliberately-broken expectation that must FAIL) proving the oracle
      sees what it claims to.
- [ ] Zero reads/writes outside the sandbox during a run (verify with a
      canary: pre-hash the real `.claude` dir, compare after).
- [ ] `scripts\guard-due.ps1 check` reports the new harness row and goes
      due when an integration module changes (edit-a-file smoke check).
