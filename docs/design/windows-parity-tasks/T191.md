# T191 - toggle_window_float_on_top is unimplemented on win32 (Mac Window menu has Float on Top)

## In plain terms

Some windows should stay in front of everything else — a terminal you are
watching while you work in another app. On the Mac, Ghoztty's Window menu has
a "Float on Top" row for exactly that. On Windows the capability was built but
never given a door: it was in no menu and in no command palette, so the only
way to reach it was to hand-write a keyboard shortcut into a config file. When
this lands, the Windows Window menu has the same row, with a checkmark that
shows whether the window is currently pinned in front.

## Goals

- [x] "Float on Top" appears in the Windows Window menu, where the Mac puts it
- [x] Choosing it pins the window in front; choosing it again unpins it
- [x] The row shows a checkmark while the window is pinned
- [x] It is also findable by name in the command palette
- [x] The row is grayed on the quick terminal, which pins itself

## Summary

macOS's Window menu has **Float on Top** (`MainMenu.xib` -> `floatOnTop:`) and
the GTK command palette offers `toggle_window_float_on_top`. **Windows handles
the action nowhere.** Found while placing Mac's menu rows for T189: the row
had to be left out of the Windows tree because choosing it would do nothing.

Evidence (2026-07-30, read not grepped): `toggle_window_float_on_top` appears
in `src/apprt/win32/` only in COMMENTS - `overlay_zorder.zig:29`, `:143` and
`win32.zig:1616` all cite it as a legitimate reason a window may carry
`WS_EX_TOPMOST`. There is no handler in `App.zig`, `Window.zig` or
`Surface.zig`; the action falls through to the no-op tail.

**Correction (2026-08-08, on claiming this):** that last sentence is wrong.
`App.zig` HAS handled `.float_window` since the first win32 commit
(`e0118f682`, 2026-07-05) — `git log -L` on the block proves it — with the
`SetWindowPos(HWND_TOPMOST | HWND_NOTOPMOST)` toggle this task's Details
section goes on to propose. The search that produced the evidence above looked
for the CORE BINDING name (`toggle_window_float_on_top`), and the apprt
switches on the ACTION name (`float_window`), which is what
`Surface.zig:6534` translates it into. What was genuinely missing is everything
downstream of the handler: `commands.zig` had no id for it, so it was in no
menu and in no palette, and the only way to reach a working feature was to
hand-write a keybind. This task is therefore about the SURFACE, not the
mechanism.

## Details

The fix is small and the plumbing already exists - T142 built
`win32.healOverlayZOrder`, which is written to LEAVE a legitimately topmost
window topmost, precisely so this feature can exist:

- Handle the action on the window: `SetWindowPos(hwnd, HWND_TOPMOST |
  HWND_NOTOPMOST, ..., SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)`, tracking
  the state per window.
- Re-seat owned popups after the change (banner strip, dim overlays, palette)
  via the T142 helper - a window that becomes topmost while its banner does
  not is the exact defect T142 fixed, from the other direction.
- Add the row to `menu_bar.zig`'s Window menu (it is currently absent, not in
  `omitted`, because the command does not exist in `commands.zig` at all) and
  a `Float on Top` palette entry, and make the menu row CHECKED when the
  window is floating.

## Validation

`overlay-zorder.ps1` already owns the z-order oracle; extend it: toggle float
on top from the palette, assert `GetWindowLongW(GWL_EXSTYLE)` gains
`WS_EX_TOPMOST` and that the window stays above a foreign foreground window,
assert the banner overlay is still above its owner, then toggle off and assert
both revert. Negative control: the pre-fix binary must fail the first
assertion.
