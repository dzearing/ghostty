# T283 - Audit every *_NEUTERED negative control for claims it does not actually cover

## In plain terms

Several of our tests are "shown to fail on purpose" before we trust them: a
switch in the source turns the fix off, the test goes red, and that is what
makes a green run mean something. This checked all eight of those switches and
found two that were lying. One of them could not make the banner test fail on
the single assertion that describes the original bug a user reported, so every
green run of that assertion proved nothing; it now does. Nothing a user sees
changes — this is about whether the evidence behind the rest of the work is
real.

## Goals

- [x] Every `*_NEUTERED` flag has a live consumer on a paint/layout path
- [x] Every flag's doc-comment claims checked against what the code changes
- [x] `T202_NEUTERED` re-measured (first check since the strip was rebuilt)
- [x] `T123_NEUTERED` measured, and reshaped so it covers its own claims
- [x] The unpinned flags gained a shipped-value unit test
- [x] All affected acceptance scripts still ALL PASS with the flags clear

## Validation criteria

- [x] `tab-strip.ps1` with `T202_NEUTERED = true`: 8 FAILED / 62 passed, and
      the surviving set is the one the comment now names (measured, below)
- [x] `pane-banner.ps1` with `T123_NEUTERED = true`: exactly 6 FAILED / 109
      passed, all in the T123 table block, nothing in 6h (measured, below)
- [x] `pane-banner.ps1` with every flag clear: ALL PASS (115)
- [x] `tab-strip.ps1` with every flag clear: ALL PASS (70 assertions)
- [x] Floor: `floor-lane.ps1 -Lane all` + P1-P3

## Summary

T209 set out to write pixel assertions and found that **both** of the source
level negative controls it was told to use were claiming more than they did:

- **`icon_button.T204_NEUTERED`** moved no glyph at all. `glyphCentered()` was
  exported and unit-tested, and then consumed by NOBODY - both paint sites
  called `icon_button.targetBox` directly. Setting the flag changed the fills
  and left every glyph exactly where the shipped build puts it.
- **`tab_shape.T206_NEUTERED`** left the flare and the antialiasing on, while
  its own doc comment said in so many words that it removed the flare.

Both are fixed (T209), but two out of two is not a coincidence and the two
remaining flags have never been checked:

```
src/apprt/win32/BannerOverlay.zig:76     const T123_NEUTERED = false;
src/apprt/win32/tab_strip_layout.zig:49  const T202_NEUTERED = false;
```

`T202_NEUTERED` is the more urgent of the two: `tab-strip.ps1`'s header tells
a reader to flip it and states exactly which assertions must then fail, and
that promise has never been re-verified since T232/T235/T242/T254/T205 rebuilt
the strip around it.

## Why this is worth a task rather than a note

A negative control is the ONLY thing standing between "the assertion passed"
and "the assertion is capable of failing". When it is hollow, every run it
guards is a green that proves nothing - and it reads, in a task file and in a
commit message, exactly like evidence. That is a worse failure than a missing
test, because a missing test is visible.

The giveaway is never in the module that declares the flag. It is at the CALL
SITES: `glyphCentered()` looked completely healthy in `icon_button.zig` -
declared, documented, and asserted by a unit test - and the defect was that
nothing called it.

## What to do

For each remaining flag:

1. Grep for every consumer of the flag and of any helper that reads it
   (`glyphCentered`-shaped predicates are the trap: exported, tested, unused).
   A flag with no consumer on the paint/layout path is inert.
2. Read the flag's own doc comment as a list of CLAIMS, and check each claim
   against what the code under the flag actually changes. T206's comment
   promised the flare; the code did not deliver it.
3. Read the acceptance script's header as a second list of claims ("these
   assertions must fail, these must not") and RUN it with the flag set. Record
   the actual pass/fail split in the task file - not "the control works".
4. Fix the flag, not the comment, whenever the comment is the more useful
   promise.

Consider also a cheap standing guard. Most of these modules already pin the
shipped value (`try testing.expect(!T202_NEUTERED)`), but nothing pins that the
flag has a CONSUMER. Reshaping a predicate the way `glyphTarget` now is - the
branch taken as data rather than read from a comptime const - lets a unit test
assert that the two worlds produce DIFFERENT output, which is the property
that was actually missing.

## Validation

- Every `*_NEUTERED` flag has, in its own task file, the measured pass/fail
  split of the acceptance script it guards, with the flag set.
- Any flag whose doc comment over-promises is either fixed or the comment is
  corrected to what the code does.
- All affected acceptance scripts still ALL PASS with the flags clear.

### Finding 1 — `T123_NEUTERED` could not fail its own headline assertion

`layoutInline` opened with `if (T123_NEUTERED) return .{};`, i.e. the neutered
build did not wrap table cells **at all**. So the 360pt cap it claims to
restore had no observable consequence, and

```
PASS  wide pane: a >360px value does not wrap (short 121 == long 121 px)
```

— the assertion that states the user's report — **passed under the control**.
The pre-T123 world wrapped at a fixed cap; it did not stop wrapping. Same
shape as `glyphCentered()` in T209: the control answers a question the
assertion does not ask.

It also reached outside its claim. Because `layoutInline` became the shared
wrap engine in T377, the early return took paragraphs, headings and list rows
down with it: the measured split before the fix was **8 FAILED / 107 passed**,
only 3 of them in the T123 block and 5 in section 6h.

Fix: the two rules T123 added are now **data** (`CellWrap{break_wide,
cap_lines}`), passed in by the caller — `CellWrap.forCell()` for a table cell,
`CellWrap.shipped` for every other block. Measured after the reshape, and
exactly the doc comment's promise:

```
6 FAILURE(S) (109 passed)
FAIL  wide pane: a >360px value does not wrap (short 121 == long 146 px)
FAIL  narrow pane: the table reflowed taller (146 -> 146 px)
FAIL  narrow pane: reflow added a whole display line (+0 px, row ~35 px)
FAIL  narrow pane: a 90-char unbroken token breaks mid-string (121 px vs 1-row 121 px)
FAIL  cell capped at 3 wrapped lines: 4x the text is the same height (196 vs 446 px)
FAIL  capped cell stays within header + 3 lines (446 px, 1-row 121 px, row ~35 px)
```

Nothing in section 6h moves.

### Finding 2 — `universalHover()` was consumed by nobody

`icon_button.universalHover()` — exported, documented, and asserted by a unit
test — had **no** caller on any paint path. T282 replaced its two paint sites
with `lightsFill(glyph)` and left the predicate behind, so the only thing
still calling it was the test that pinned it. That is the `glyphCentered()`
defect exactly, and it was created by the turn that FIXED `glyphCentered()`'s
sibling. Deleted.

### Finding 3 — `T202_NEUTERED` covers its claims; both claim lists did not

Re-measured for the first time since T232/T235/T242/T254/T205 rebuilt the
strip: **8 FAILED / 62 passed**.

```
FAIL  single tab: does NOT span the client width (w=1096 of 1382)
FAIL  single tab: never wider than 50% of the tab run (1096 <= 551 - 5)
FAIL  + : clicking one gap past the last tab creates tab 2 (selected index=0)
FAIL  two tabs: each is still its own content's width (745 vs 1096)
FAIL  + : moved right with the new tab (1130 -> 1130)
FAIL  + : clicking at its NEW position creates tab 3 (selected index=1)
FAIL  long title: still capped at 50% of the run (1096 <= 551 - 5)
FAIL  T235: tab 2's left edge is exactly tab 1's slot (552 vs 1101)
```

The control is sound — every failure is a width rule or the "+"-follows-the-
last-tab family. What was wrong is the NEGATIVE half of both claim lists (the
module comment and `tab-strip.ps1`'s header), which said the "hit-test
assertions must NOT" fail while three "+"-click assertions do. They are the
gap claim expressed as a click, at a point derived from the last tab's right
edge. The surviving set — accent rule, dead-space and right-inset probes, the
TAB hit tests including the close "×", glyph centering, the whole shape
section — is now named in the comment instead.

### Finding 4 — five of eight flags had no shipped-value pin

`title_spinner`, `tab_shape` and `icon_button` each pin theirs
(`try testing.expect(!X_NEUTERED)`); `tab_strip_layout` (both) and
`BannerOverlay` (all three) did not, so a flag left `true` by an experiment
would have shipped and gone red only in an acceptance script somebody
remembered to run. Both modules gained a pin, and the banner's also asserts
that the T123 control's two worlds are *different values* — the cheap standing
form of "this control is capable of changing something".

The durable version of this sweep — an analyzer that enforces "every
`*_NEUTERED` flag has a consumer outside its own tests, and a shipped-value
pin" — is filed as its own task rather than hand-checked next time.
