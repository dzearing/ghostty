# T658 - A CRLF-terminated text argument submits twice: the peel treats \r\n as two Enter presses

## In plain terms

Ending a message with a Windows-style line ending sends it twice. The agent
typed one prompt and the pane submitted it, then submitted an empty line after
it — which in a chat-style TUI is a second, blank turn.

## Summary

The trailing-newline peel landed in T604 (ported from main's `a7f7476e1`)
walks back over *every* trailing `\n`/`\r` and turns each one into its own
`\r` keypress. That is deliberate for `"prompt\n\n"` — two newlines, two
presses — but `"prompt\r\n"` is ONE line ending written the Windows way, and
it produces two presses.

Inherited from main verbatim, on purpose: T604's directive was 100% parity
with main's semantics, so the wart was carried rather than silently fixed on
one seat. This task is the receipt.

Where: `resolveArgument` in `src/cli/send_keys.zig` —

```zig
while (end > start and (buf.items[end - 1] == '\n' or buf.items[end - 1] == '\r')) end -= 1;
```

Likely fix: collapse a `\r\n` PAIR to one press while still counting repeated
line endings separately (`"a\r\n\r\n"` = two). Because this is shared core the
change lands for both seats at once, so it wants a companion decision on
whether main takes it as a fix or keeps the current behavior.
