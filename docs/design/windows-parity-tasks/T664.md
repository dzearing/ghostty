# T664 - send-keys can lose the FIRST character of a keys-file text run that lands shortly after an Enter

## Summary

Seen 1-in-5 runs of test/win32/reset-context.ps1 section B: the pane received RC-TEXT[ontinue-marker-B] - the leading 'c' of a --keys-file text run was dropped. It landed about a second after a bare Enter (the helper's extra-Enter branch). In the go loop this would silently truncate the resume prompt into 'ead go.md and go'. T483 already filed that section as intermittently failing without finding a cause; this is the cause to chase. Reproduce by looping section B.

## In plain terms

When the loop restarts itself it types one sentence into its own pane. Once, a
letter went missing from the front of that sentence, and nothing noticed —
every check in the chain looked at the middle of the sentence, where the loss
does not show. Nobody could say whether the letter never arrived or whether the
screen simply drew it wrong.

Two things are different now. The delivery is measured **byte for byte on the
wire**, so a lost letter can be attributed instead of guessed at; and every
place that checks a handoff arrived now checks it arrived **whole**, so a
recurrence fails a test rather than being caught by eye. Under that
measurement — 315 deliveries of the exact shape that failed — nothing is losing
bytes on this box today.

## Goals

- [x] Reproduce the loss, or establish by measurement that our write path does
      not produce it
- [x] Measure the shape ON THE WIRE (a bare Enter, then a framed `--keys-file`
      text run), byte-exact, as a permanent regression arm
- [x] Make a recurrence LOUD: the sections that deliver a handoff assert it
      arrived whole, not that its file name appeared somewhere
- [x] Leave the reproduction instrument behind, not just a description of it
- [x] Rule out, by reading, the seams in our path that could truncate a run

## Verdict (measured 2026-08-10, against d8b4aacda)

**Not reproducible in our write path.** 315 deliveries of the failing shape,
across several instruments, byte-exact every time:

| Instrument | Shape | Sends | Losses |
|---|---|---|---|
| raw-VT capture + git-bash `read -e` | bare Enter, 1s, `--keys-file` + Enter | 20 | 0 |
| both, with the section-B prelude (`nn`, `/clear`, Enter, extra Enter, `--when-idle`) | same | 10 | 0 |
| both, under a concurrent `none` lane build | same | 50 | 0 |
| both, delay sweep 0..1500ms step 60, x2 reps | Enter, **D ms**, payload | 104 | 0 |
| receipt oracle + window churn | full section-B prelude | 30 | 0 |
| receipt hammer, randomised 80-1400ms gaps | alternating 17-byte and ~100-byte payloads | 150 | 0 |

Ruled out by reading, each with a reason:

- **`--segments=` encode/decode** (`src/apprt/ipc/segments.zig`) — hex, with a
  round-trip test over control bytes and non-UTF-8; a run boundary cannot shift.
- **`normalizeConptyInput`** (`src/apprt/ipc/args.zig`) — stateless per call, so
  a preceding CR from another run cannot influence it.
- **`SegmentedPool` buffer reuse** (`src/termio/Exec.zig`) — puts are in order
  on one stream, which is the invariant the pool documents.
- **The 64-byte pty write chunk** (`termio.Exec.queueWrite`) — the only seam
  that splits one run across two pty writes; measured directly by round 14 and
  by the soak's long payload, both whole.

What is NOT ruled out: the leg between our pty write and git-bash's line
editor — conhost's VT input translation and cygwin's console reader. The raw-VT
capture pane exercises a *different* conhost input path
(`ENABLE_VIRTUAL_TERMINAL_INPUT`) than cygwin does, so a fault there would show
in the readline oracle and not the raw one; 190 readline sends say it did not
happen here. If it recurs, that leg is where to instrument next, and
`test\win32\send-keys-soak.ps1` is the harness to do it from.

It is also possible the one observation was a DISPLAY loss rather than an input
loss — a `+read` of a pane cannot tell those apart, and no receipt existed for
that run. The new receipt arms can: they judge from a file the shell wrote,
outside the pane.
