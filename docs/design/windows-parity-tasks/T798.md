# T798 - persistence-flag.ps1 is RED at HEAD: 4 launch sites in url-scheme.ps1 and agent-attach-refused.ps1 never state their session persistence

## In plain terms

One of the checks that keeps the test suite honest has been failing, and
because nobody was looking at it, it stayed failing. It is the check that
makes sure a test says whether it wants the app to restore the windows from
the last run - a test that does not say gets whatever the previous test left
behind, and then fails for reasons that have nothing to do with what it is
testing.

## Summary

Found while landing T755 (2026-08-12): `test\win32\persistence-flag.ps1` -
the acceptance for the T158 "every launch declares its session persistence"
rule - reports `1 FAILURE(S) (19 passed)` at HEAD, with **4 undeclared launch
sites**, none of them touched by T755:

```
undeclared: agent-attach-refused.ps1:276  $app = Start-OnTestDesktop -Exe $Exe -Arguments @() -StdErr ...
undeclared: url-scheme.ps1:359  $a1 = Start-OnTestDesktop -Exe $exe -Arguments @("$debugScheme`://open/urlwin")
undeclared: url-scheme.ps1:368  $a2 = ...
undeclared: url-scheme.ps1:381  $a3 = ...
FAIL  A1 no launch leaves persistence unstated (undeclared: 4 of 182)
```

(T755 added two of its own and declared them; the sweep went 6 -> 4, which is
how the pre-existing four were noticed at all.)

**Why this is P1 rather than housekeeping.** The whole point of T158 is that
persistence is ON by default, so an undeclared launch restores whatever the
previous run left and each section writes the manifest the next one restores -
the self-poisoning shape that cost T131 and T155 real debugging time against
builds that were correct. An audit that is permanently red also stops being
read: the next person to add an undeclared site sees a script that was already
failing and has no signal.

**The judgement call this needs, and why T755 did not make it.** These four are
GUI app launches, not CLI verbs, so the answer is not a comment - it is
whether each of those tests WANTS a restore. `url-scheme.ps1`'s three launches
activate a `ghoztty://` URL against an app that may or may not be running;
`agent-attach-refused.ps1:276` is section C's app launch, in a script whose
whole subject is the agent attach path. Guessing wrong there silently changes
what those tests measure, which is worse than the red line. Whoever picks this
up should read each section's intent and pass the flag (or a `# persistence:`
marker where the launch genuinely has no session), not blanket-apply one.

## Validation criteria

- [ ] `powershell -NoProfile -File test\win32\persistence-flag.ps1` ends
      `ALL PASS`, with the sweep reporting 0 undeclared of 182+.
- [ ] Each of the four sites is declared by a DELIBERATE choice - the flag
      where the test has an opinion about restore, a `# persistence: <reason>`
      marker only where the launch has no session - and `url-scheme.ps1` and
      `agent-attach-refused.ps1` still pass their own acceptance afterwards.
