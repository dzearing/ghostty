# T339 - Cross-machine Restore All dials N+1 times on the GUI thread

Filed out of T336 (2026-08-02).

## Summary

`App.restoreAllRelaySessions` runs entirely on the GUI thread: one relay dial for
the layout pull, then **one more per rebuilt window**, each a full WebSocket
upgrade through the relay. On the loopback fixture that is milliseconds and
invisible; against a real rendezvous relay it is N+1 round trips with the message
loop stopped, so a 6-window machine on a 300 ms link freezes the app for ~2
seconds with no cursor, no paint and no way to cancel.

The N+1 dials themselves are NOT the defect - they are T336's deliberate
ownership rule (a win32 window owns its transport and frees it on close, so a
shared connection would die with the first window the user closed). What is wrong
is *where* they happen.

It shipped this way on purpose: the single-session remote resume it generalizes
(`resumeRelaySession`, T320) also dials synchronously, and matching it kept T336
to one new idea instead of two. Mac does the opposite - `resumeAllRemoteSessions`
dials on `DispatchQueue.global(qos: .userInitiated)` and hops back to the main
actor to build (`SessionLayoutRestore.swift:620-651`), which is the shape to port.

## Details

The pattern to reuse is already on box twice: `SessionRoster.fetch` (T295/T319)
spawns a worker, dials, and `PostMessage`s the result back to the GUI thread with
a serial so a stale reply is dropped. The wrinkle here is that the *rebuild* must
still run on the GUI thread (it creates windows), so the split is:

- worker: pull dial -> `GET_LAYOUTS` -> `LIST_SESSIONS` -> N window dials,
- GUI thread: decode + `restoreWindow` per window, taking ownership of each dial.

Ownership across that boundary is the part to get right: a reply that lands after
the chooser is gone, or after the app started quitting, must free every dial it
carries rather than leak or hand them to a window that no longer exists.

Consider also whether the per-window dials should be *concurrent* rather than
serial once they are off the GUI thread - N sequential upgrades is still N round
trips of latency, just no longer blocking paint.

## Validation

- `test/win32/chooser-restore-all-remote.ps1` must stay ALL PASS (it asserts the
  1+N connect count, which the move must preserve).
- Add an assertion that the app keeps pumping while the restore is in flight -
  e.g. the chooser (or the owner window) still answers a `WM_NULL`
  `SendMessageTimeout` during the dial, which today it would not.
