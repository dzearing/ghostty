# T339 - Cross-machine Restore All dials N+1 times on the GUI thread

Filed out of T336 (2026-08-02).

## In plain terms

"Restore All" on another machine brings that machine's whole set of windows
back onto this one. Until now, pressing it froze Ghoztty for as long as the
network took: no cursor, no redraw, nothing you could click, and no way to
change your mind — and the slower the connection to that machine, the longer
the freeze, because the app opens one connection per window it is bringing
back. On a fast local network you would never notice; over a real remote link
it is a few seconds of a dead application every time.

After this change the connecting happens in the background. The window stays
alive and responsive the whole time, the footer says "Restoring this machine's
windows...", and the windows appear when they are ready.

## Goals

- [x] the connecting (dial, layout pull, one dial per window) happens off the
      GUI thread
- [x] the app keeps painting and answering input while a restore is in flight
- [x] every connection a restore opens is accounted for — freed if its window is
      never built, if the chooser closed, or if the app is quitting
- [x] pressing the button twice does not restore the same machine twice
- [x] the failure sentences (unreachable / signed out / unreadable layouts) still
      reach the user, and a restore that rebuilds nothing still says so
- [x] on-box proof that the app is not blocked, not just that the code moved

## Summary

`App.restoreAllRelaySessions` runs entirely on the GUI thread: one relay dial for
the layout pull, then **one more per rebuilt window**, each a full WebSocket
upgrade through the relay. On the loopback fixture that is milliseconds and
invisible; against a real rendezvous relay it is N+1 round trips with the message
loop stopped, so a 6-window machine on a 300 ms link freezes the app for ~2
seconds with no cursor, no paint and no way to cancel.

The N+1 dials themselves are NOT the defect - they are T336's deliberate
ownership rule (a win32 window owns its transport and frees it on close, so a
shared connection would die with the first window the user closed). What is wrong
is *where* they happen.

It shipped this way on purpose: the single-session remote resume it generalizes
(`resumeRelaySession`, T320) also dials synchronously, and matching it kept T336
to one new idea instead of two. Mac does the opposite - `resumeAllRemoteSessions`
dials on `DispatchQueue.global(qos: .userInitiated)` and hops back to the main
actor to build (`SessionLayoutRestore.swift:620-651`), which is the shape to port.

## Details

The pattern to reuse is already on box twice: `SessionRoster.fetch` (T295/T319)
spawns a worker, dials, and `PostMessage`s the result back to the GUI thread with
a serial so a stale reply is dropped. The wrinkle here is that the *rebuild* must
still run on the GUI thread (it creates windows), so the split is:

- worker: pull dial -> `GET_LAYOUTS` -> `LIST_SESSIONS` -> N window dials,
- GUI thread: decode + `restoreWindow` per window, taking ownership of each dial.

Ownership across that boundary is the part to get right: a reply that lands after
the chooser is gone, or after the app started quitting, must free every dial it
carries rather than leak or hand them to a window that no longer exists.

Consider also whether the per-window dials should be *concurrent* rather than
serial once they are off the GUI thread - N sequential upgrades is still N round
trips of latency, just no longer blocking paint.

## What landed (2026-08-08)

`src/apprt/win32/RestoreAllRelay.zig` (new) owns the off-thread half; the GUI
half is `App.adoptRestoreAll`. `App.restoreAllRelaySessions`, `restoreAllFrom`'s
local/relay union and `App.dialRelay` are gone — the local arm is now
`restoreAllLocalFrom` and stays synchronous (bounded named-pipe RPCs; the tail
case is **T618**).

- **One `Job` allocation travels both ways.** The GUI thread fills in where to
  dial and a snapshot of which of that machine's sessions our panes already
  hold; the worker fills in what it pulled and dialed; the GUI thread consumes
  and frees it. `Job.destroy` frees every dial the rebuild did NOT hand to a
  window, which is what makes a reply landing after the chooser closed, while
  the app is quitting, or on a window that failed to build safe rather than a
  leaked connection per window.
- **The rebuild happens even if the chooser is gone.** Dismissing it was never
  offered as a cancel; only the sentence is dropped.
- **The double-attach guard runs twice on purpose**: against the GUI snapshot
  before dialing (an already-open window costs no dial at all — assertion H) and
  against the LIVE panes before building (a pane can attach while the worker is
  out).
- **`restore_inflight`** on the chooser gates a second press, which the
  synchronous version got for free by blocking the keystroke.
- **Serial dials, deliberately** — filed as **T616**, reasoning in **D38**.
- **Fixture**: `FakeRelay.ps1` gained `-SlowConnectFile`/`-SlowConnectMs`, which
  DEFERS each `/connect` answer to a later pass of the relay's loop instead of
  sleeping in it. The relay is one loop; a sleep would stall every live bridge
  and read to the app as connections that stopped answering.
- **Surprise, filed as T617**: assertions A and G of the script had been red
  since 2026-08-02 (T338 re-keyed layout blobs onto the window UUID 72 minutes
  after T336's last green run, so the fixture's `key -eq 't336-multi'` matched
  nothing) and it read as a product defect because
  `@($null.session_ids).Count` is **1** in PowerShell. The store held a correct
  3-id blob throughout; the oracle now matches the `ipc_name` inside the blob.
